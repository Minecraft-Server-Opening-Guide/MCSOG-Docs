本站的**版本時間線**（[/wiki/versions](/wiki/versions)）按時間倒序列出 Java 版與基岩版的正式版本。它是"我該開哪個版本、什麼時候升級、玩家為什麼進不來"這類問題的第一個查詢入口。

但時間線本身只給出**版本號、日期與一行說明**。這一頁講清楚：這些欄位分別意味著什麼、哪些直覺是錯的、以及怎麼把它變成一次具體的升級決定。

> 版本號命名規則、協議版本與發佈節奏由官方決定，隨時可能調整。本文只解釋**怎麼讀本站的時間線**；具體某個版本支援什麼、要求什麼，以官方發佈說明為準。
:::note 這一頁解決四個問題
- 時間線上的一行，每個欄位是什麼意思；
- Java 版與基岩版的版本號各自怎麼拆；
- LTS / CROSS-PLAY 標籤代表什麼、不代表什麼；
- 為什麼"發佈日期"不能回答"我的客戶端能不能進"。
:::

## 1. 時間線在哪、每一行是什麼

| 頁面 | 內容 |
| --- | --- |
| [/wiki/versions](/wiki/versions) | 預設開啟 Java 版時間線 |
| [/wiki/versions/java](/wiki/versions/java) | Java 版時間線 |
| [/wiki/versions/bedrock](/wiki/versions/bedrock) | 基岩版時間線 |

兩個版本的時間線是**分開的**，頁面上用兩個標籤頁切換。每一行的結構固定：

| 欄位 | 說明 |
| --- | --- |
| 版本號 | 該版本在遊戲裡顯示的正式版本號 |
| 標籤 | 只有條目帶標記時才出現（例如 LTS、CROSS-PLAY），不是每行都有 |
| 日期 | 該版本的發佈日期 |
| 一行說明 | 這個版本是什麼（大版本更新會寫明更新名，小版本一般是修復與穩定性改進） |

幾條讀法上的事實：

- **新版在上**：時間線按日期倒序排列，第一行是最新的版本，往下越讀越舊。
- **只收正式版**：快照（Snapshot）、預覽版（Preview）與測試版不在時間線裡，所以"時間線上沒有"不等於"官方沒發佈過"。
- **兩個版本的數量差得很多**：Java 版從 1.0 一路記到最新的 26.x；基岩版的修訂版發佈頻率高得多，條目數接近 Java 版的三倍，所以基岩版時間線往下翻會明顯更長。
- **基岩版條目多一個欄位**：基岩版的服務端（BDS）有自己的構建號，時間線資料裡額外記錄了它，用於對照"客戶端版本"與"服務端構建"。

## 2. Java 版的版本號怎麼讀

Java 版長期使用 `1.x.y` 的形式：

| 位置 | 含義 | 例子 |
| --- | --- | --- |
| `1.x` | 主版本，決定內容與玩法變化 | 1.21 |
| `.y` | 該主版本下的修訂版 | 1.21.9、1.21.10、1.21.11 |

**這裡有一個最常見的誤讀**：`1.21.10` 比 `1.21.9` **新**，因為 `.10` 是數字十，不是"一點一零"。**按數字比較，不要按字串比較**：字串排序會把 `1.21.10` 排在 `1.21.9` 前面，看起來像是更舊，其實相反。

### 2.1 新命名：26.x

時間線裡可以看到，Java 版在 2026 年之後出現了 `26.x` 形式的版本號（本站時間線中 26.1 記為 2026-03-24，26.2 記為 2026-06-16，26.3 記為 2026-09-15）。

這屬於**官方調整版本命名方式**，不是"1.21 的第 26 個修訂版"，也不能按 `1.x.y` 的直覺去推斷它和舊版本號的大小關係。遇到不認識的版本號形式，正確做法是**看日期，不要猜數字**：

- 想知道誰更新：比日期。
- 想知道能不能裝某個插件：看插件的支援列表，不看版本號形式。
- 想知道協議是否相容：看協議版本，不看版本號。

### 2.2 修訂版與主版本的區別

| 類型 | 變化幅度 | 升級風險 |
| --- | --- | --- |
| 修訂版（如 1.21.9 → 1.21.11） | 通常只修 bug 與穩定性 | 低；但插件仍可能受影響，仍要備份 |
| 主版本（如 1.21 → 26.1） | 內容、機制、資料格式都可能變 | 高；世界格式基本單行道，降級代價極大 |

## 3. 基岩版的版本號怎麼讀

基岩版的 `1.x.y` 與 Java 版**形似而神不同**：第三段的含義不是"第幾個小修訂"，而是按基岩版自己的節奏遞增。

| 形式 | 含義 | 例子 |
| --- | --- | --- |
| `1.x.y` | 基岩版正式版 | 1.20.10、1.21.100 |
| `1.x.y.z`（四段） | BDS 構建號，用於服務端 | BDS 1.20.62.03 |

三個要點：

1. **`1.20.1` 與 `1.20.10` 不是同一件事**，也不是"改了個位數"。基岩版的第三段常常一次跳十（1.20.10、1.20.20 這樣的節奏在時間線裡很常見），所以看到 `1.21.100` 不要以為是打錯了。
2. **BDS 構建號是四段**：例如 `BDS 1.20.62.03`。它是服務端自己的構建編號，和客戶端顯示的版本號**不是同一個字串**，但在同一次發佈裡互相對應。
3. **查不到構建號時會留佔位**：本站資料裡，查不到確切構建號的基岩版條目會寫成 `BDS <版本>.w` 這類形式（`w` 是構建號佔位），說明"這次發佈的構建號沒有確認到"，不代表這個版本沒有服務端。

### 3.1 基岩版的 26.x

基岩版同樣進入了 `26.x` 命名（本站時間線中 26.0 記為 2026-02-10）。與 Java 版一樣，**不要跨命名體系比較數字**，看日期。

### 3.2 客戶端與服務端同日發佈

基岩版的時間線說明裡常見"與客戶端同日發佈"這類描述，這反映了基岩版的實際節奏：**客戶端更新與服務端構建通常同步推進**。由此帶來兩個後果：

- 服務端跟進得慢，就等於玩家（尤其是自動更新的玩家）進不來；
- iOS 玩家**只能安裝商店裡的最新版**，無法回退到指定版本，所以"把服務端固定在舊版本"這條路的代價比 Java 版大得多。

## 4. LTS 與 CROSS-PLAY 標籤代表什麼

時間線上的標籤是**本站自己加的提示**，不是官方分類，也沒有任何官方承諾。它們只在條目帶標記時顯示。

| 標籤 | 本站用它表示 | 它**不**表示 |
| --- | --- | --- |
| LTS | 本站認為值得長期停留、適合作為穩定基線的版本 | 官方會長期為它提供更新；也不表示它"最安全" |
| CROSS-PLAY | 與跨平台聯機相關的版本提示 | 裝了它就能 Java 與基岩版互通；也不保證所有平台都能進 |

幾點務必分清：

- **LTS 不是 Minecraft 的官方術語**。官方沒有"長期支援版本"這一說，任何版本都可能在下一次更新後停止獲得修復。
- **CROSS-PLAY 也不等於跨端互通**。基岩版各平台之間互通是它本身的能力；**Java 版與基岩版之間互通必須依賴 Geyser 一類工具**，與服務端是哪個版本無關（見 [Java版 與 基岩版 的區別](/wiki/editions)）。
- **標籤會變**。本站可以在任何時候給條目加上或去掉標記，所以"某版本帶 LTS"這件事本身是本站的判斷，不是硬事實。以頁面當前顯示為準。

## 5. 發佈日期不等於"能不能進服"

這是時間線最容易被誤用的一點。日期只回答"這個版本什麼時候發佈"，**完全不回答**"你的客戶端能不能進這個服務端"。

真正決定能不能進的是**協議版本**：客戶端與服務端在握手階段用協議號對話，對不上就進不去，和版本號、發佈日期、更新內容都無關。

| 現象 | 真正的原因 | 去哪裡看 |
| --- | --- | --- |
| 玩家提示"版本不相容"（Java） | 客戶端協議與服務端不匹配 | [跨版本相容](/tutorials/java/via) |
| 玩家提示需要更新到最新版（基岩版） | 客戶端協議與服務端構建不匹配 | [協議版本與版本選擇](/tutorials/bedrock/protocol) |
| 時間線顯示昨天剛發新版，玩家卻進不來 | 你還沒更新服務端，或玩家已自動更新到更新版 | 先確認雙方版本，再決定跟不跟 |
| 時間線顯示版本很舊，但玩家能進 | 該客戶端版本仍在服務端接受的兼容範圍內 | 不要靠"能進"反推協議相容 |

### 5.1 一個具體例子

服務端跑 1.21.11，玩家報的客戶端是 1.21.9：

| 問題 | 答案 |
| --- | --- |
| 時間線怎麼看 | 兩行都在，1.21.11 比 1.21.9 新（按數字比：10、11 大於 9） |
| 玩家為什麼進不來 | 不是"版本太舊"四個字能解釋的：要看 1.21.11 的服務端是否接受 1.21.9 的協議 |
| 該怎麼辦 | 先看服務端日誌裡的握手錯誤；裝 Via 系列可以讓更舊的客戶端進來，見 [跨版本相容](/tutorials/java/via) |
| 時間線能回答嗎 | 不能。它只告訴你這兩個版本誰先發佈 |

**時間線回答"誰新誰舊"，協議回答"能不能連"**，這兩件事要分開查。

## 6. 為什麼協議版本比營銷版本號重要

"營銷版本號"指的是頁面上顯示的 `1.21.x`、`26.x` 這類版本號；**協議版本**是雙方通訊時實際使用的編號。兩者不是一回事：

- 同一個營銷版本號下，協議可能改過多次（基岩版尤其明顯）；
- 官方有時會在修訂版之間改協議，也會在修訂版之間**不改**協議；
- 插件、載入器與跨版本工具的相容判斷，多數情況下看的是協議與內部版本，而不是頁面上那個數字。

**基岩版卡得更死**：客戶端協議必須與服務端構建匹配，差一個協議號就是連不上。**Java 版有翻譯層**：Via 系列插件能在服務端一側翻譯協議，讓更舊或更新的客戶端進來，但跨得越遠，能對上的東西越少，體驗下降越明顯。

結論：**判斷"能不能進"，永遠先看協議，再看版本號；版本號只是給人看的名字。** 兩條路線的完整說明見 [協議版本與版本選擇](/tutorials/bedrock/protocol) 與 [跨版本相容](/tutorials/java/via)。

### 6.1 兩個版本對協議的態度不一樣

| 維度 | Java 版 | 基岩版 |
| --- | --- | --- |
| 協議不匹配時 | 握手失敗，提示版本不相容 | 握手失敗，提示需要更新到最新版 |
| 有沒有翻譯層 | 有：Via 系列在服務端一側翻譯協議 | 基本沒有：社群跨版本插件生態很小 |
| 客戶端自動更新 | 只在官方啟動器裡，玩家可以固定版本 | 應用商店預設自動更新，玩家常常"被動升級" |
| 固定舊版本的代價 | 相對可控 | 很高：iOS 玩家只能裝最新版 |
| 因此的預設策略 | 可以按插件生態決定何時升級 | **預設跟進最新版** |

## 7. 怎麼用時間線決定什麼時候升級

時間線給你的是**日期與順序**，升級決策要靠它加上"你的服現在跑什麼"。推薦順序：

1. **先查支援範圍，再查新版本**。你的核心、插件、模組載入器各自支援到哪個版本？把它們的交集寫下來，這是你能升到的上限。載入器與核心的版本約束見 [服務端核心對比](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7)。
2. **看目標版本後面有幾個修訂版**。剛發佈的主版本往往還在收尾；等一兩個修訂版出來再動，風險明顯更低。
3. **看你的插件生態跟到哪了**。核心支援新版不等於插件支援新版。
4. **備份，並驗證備份**。世界格式升級基本是單行道，只換核心不換世界的回滾是不成立的。
5. **在獨立實例裡試**。用一份存檔副本跑一次，別拿生產實例做實驗。
6. **挑維護視窗並提前公告**。

| 情況 | 建議 |
| --- | --- |
| 只是修 bug 的修訂版，且核心與插件都已支援 | 可以跟，仍然先備份 |
| 剛發佈的主版本 | 等第一個或第二個修訂版 |
| 你的插件裡有隻支援舊版的 | 停在舊版，或先找替代插件 |
| 基岩版 | 預設跟進最新版；固定舊版等於放棄 iOS 玩家 |
| 不確定 | 不動。留在當前版本的成本，通常低於一次失敗的升級 |

完整的升級流程、降級風險與回滾方法見 [服務端、插件與 MCDR 的更新維護](/tutorials/ops/updates)。

## 8. 一次"進不去"的排查順序

| 順序 | 檢查項 | 怎麼查 |
| --- | --- | --- |
| 1 | 客戶端版本 | 讓玩家報出準確的版本號（見下一節） |
| 2 | 服務端版本與協議 | 服務端日誌、核心版本輸出 |
| 3 | 埠與協議 | Java 版是 TCP 25565；基岩版是 UDP 19132（IPv6 為 19133） |
| 4 | 白名單與封禁 | `whitelist list`、`banlist players`（基岩版看 `allowlist.json`） |
| 5 | 正版驗證與登入方式 | `online-mode` 一類的配置會直接改變"能不能進" |
| 6 | 跨版本插件 | 裝了 Via 系列卻仍報版本不支援時，先更新插件本身 |

前兩步就要用版本號，所以**先問版本，再談其他**，能省掉一大半來回。

## 9. 先確認客戶端版本
:::tip 玩家說"進不去"時，第一件事是要版本號
讓玩家報出**準確的客戶端版本號**（截圖最省事），再去對照時間線與協議。沒有這一步，後面的排查全是猜。

- **Java 版**：主選單左下角顯示版本號；啟動器裡也能看到該安裝對應的版本；進入遊戲後按 `F3`，除錯介面頂部會顯示版本。
- **基岩版**：在設定的「關於」一類頁面裡能看到版本號（各平台介面位置不同，移動端與主機端尤其不一樣）。

拿到版本號之後，把玩家版本與服務端版本放到時間線上對照日期與順序，就能判斷這是"服務端太舊"還是"客戶端太新"。
:::

## 10. 時間線上容易誤讀的幾點

| 誤讀 | 實際情況 |
| --- | --- |
| 用字串比較版本號 | `1.21.10` 比 `1.21.9` 新；跨命名體系（1.x 與 26.x）更不能比數字，只能比日期 |
| 以為時間線收錄了快照 | 只收正式版；快照與預覽版不在其中 |
| 以為"發佈日期近"就是"必須升" | 發佈節奏與你的插件生態是兩回事 |
| 以為帶 LTS 就永遠安全 | LTS 是本站標記，不是官方承諾 |
| 以為基岩版 `1.20.1` 與 `1.20.10` 差一個小版本 | 基岩版第三段按自己的節奏跳，兩者是不同發佈 |
| 以為同一天只有一個版本 | 時間線裡同一天出現多個版本是正常現象 |
| 以為"最新的就是最合適的" | 最新版對新插件友好，對老插件不友好；要看你實際裝了什麼 |

### 10.1 時間線不回答的問題

| 你的問題 | 時間線能答嗎 | 該去哪 |
| --- | --- | --- |
| 這個版本什麼時候發佈 | 能 | 時間線本身 |
| 我的客戶端能不能進 | 不能 | 協議版本：見 [協議版本與版本選擇](/tutorials/bedrock/protocol) |
| 我的插件支不支援 | 不能 | 插件發佈頁的支援列表 |
| 我的核心跟上了沒有 | 不能 | 核心的官方下載頁與官方倉庫 |
| 這個版本更新了什麼 | 部分 | 時間線的一行說明；細節看官方更新日誌 |
| 去哪下載服務端 | 不能 | 本站下載區與官方下載頁 |

## 11. 一頁速查

```text
我要开新服
  → 选最新正式版，然后确认核心与插件都支持它

玩家说进不来
  → 先要客户端版本号 → 比协议 → 再查端口、白名单、正版验证

我想升级
  → 查核心/插件/加载器的支持交集 → 等修订版 → 备份并验证
  → 独立实例试跑 → 挑维护窗口 → 公告

我看到一个不认识的版本号
  → 看日期，不看数字大小
```

## 12. 把時間線當版本檔案用

時間線除了"看最新版"，還有三個更實用的用法。

### 12.1 查某個歷史版本屬於哪個主版本

想知道"1.20.4 屬於哪個大版本、它後面還有哪些修訂"，就在時間線裡定位到那一行，然後**往上讀**：同一主版本下的修訂版通常連續出現。在你需要"退回到某個已知可用的版本"時，這個動作比搜資料快得多。

### 12.2 判斷一箇舊主版本還會不會更新

時間線的順序能給你一個直覺：如果一個主版本之後已經出現了新的主版本，舊主版本通常只在必要時收到修復。**這只是觀察，不是官方承諾**；是否繼續更新以官方發佈說明為準。

### 12.3 基岩版用它對照客戶端與服務端

基岩版條目同時記錄了客戶端版本與 BDS 構建號，所以玩家報出客戶端版本後，可以直接在時間線上找到對應那一行，看它對應的服務端構建是什麼。這是排查"客戶端更新了、服務端沒跟上"最快的一步。
