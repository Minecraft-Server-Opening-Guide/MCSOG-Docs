開服第一步是選"跑什麼"。這一步之所以容易選錯，是因為**核心、插件、模組、載入器**這四個詞經常被混著用。這一頁把它們擺在一起對照：Java 版的核心家族與模組載入器、基岩版的官方與第三方核心、BDS 的社群載入器，最後給一條"我該選哪個"的判斷路徑。

> 各專案支援哪些遊戲版本、支援到什麼程度，**隨時間變化**：核心會停止維護，載入器會追趕新版本，插件會失去作者。本文只給"家族與定位"的對照，**具體版本區間與支援狀態以各專案官方倉庫與官方文件為準**。

## 1. 先把四個詞分開

| 詞 | 是什麼 | 典型形態 | 玩家要不要裝東西 |
| --- | --- | --- | --- |
| 核心（服務端） | 跑世界、跑邏輯的那個程式 | `paper-x.jar`、`bedrock_server.exe` | 不用 |
| 插件 | 呼叫核心提供的 API 擴充功能 | 放進 `plugins/` 的 jar 或 phar | 不用，原版客戶端即可 |
| 模組 | 直接改遊戲本體的程式碼 | 放進 `mods/` 的 jar | **多數內容模組要求客戶端裝同一套** |
| 載入器 | 讓模組能被載入並執行的框架 | Fabric、NeoForge、Forge、Quilt | 客戶端與服務端都要裝 |

一句話區分：**插件在服務端外面加功能，模組在遊戲裡面改內容。** 這個區別決定了玩家要不要配合裝東西，也決定了你後面所有的排錯方式。

## 2. Java 版服務端核心

Java 版的核心是一條清晰的分支鏈：Bukkit → Spigot → Paper → Purpur / Folia / Leaves / Leaf。**插件相容性大體沿上游繼承**：相容 Paper 的插件通常也相容 Purpur，但反過來不一定。

| 核心 | 特點 | 插件相容 | 適合誰 |
| --- | --- | --- | --- |
| Vanilla（原版） | 官方服務端，只支援資料包；不裝任何第三方東西 | 不支援插件 | 想驗證原版行為、跑純原版玩法 |
| Spigot | Bukkit 的延續，也是 Paper 的上游；更新節奏較慢 | 生態大，很多老插件以它為準 | 需要相容老插件、且不想用 Paper 的場景 |
| Paper | Spigot 分支；非同步區塊、實體與網路最佳化最成熟 | **生態最大**，絕大多數插件首選 | **第一次開服的首選**：穩、資料多、效能夠 |
| Purpur | Paper 分支，提供大量玩法開關 | 相容 Paper 插件 | 想精細調整原版機制、又不想寫程式碼 |
| Folia | Paper 分支，區域化多執行緒 | **相容性差**：多數插件未適配，需要專門支援 | 核心多、主頻低的機器；**不適合生電** |
| Leaves | Paper 分支，目標是修復被效能最佳化改壞的原版特性 | 相容 Paper 插件（以各自說明為準） | **生電（技術向）+ 想用插件** |
| Leaf | Paper 分支，追求效能、原版機制與穩定性之間的平衡 | 相容 Paper 插件（以各自說明為準） | 想兼顧效能與原版手感，但不需要 Leaves 的全部特性 |

三點提醒：

1. **Leaves 與 Leaf 是兩個不同專案**，名字只差一個字母。搜資料、下載核心時看準拼寫，別裝錯。
2. **Folia 不是"更快的 Paper"**。它把世界切成區域並行排程，跨區域互動的行為與 Paper 不同；沒適配的插件會直接報錯或行為異常。選它之前先確認你要用的插件是否聲明支援 Folia。
3. **原版只支援資料包（Data Pack）**。想用插件就必須換核心，想用模組就必須換載入器。

### 2.1 分支繼承關係

把這條鏈記住，插件相容性問題就有一半能自己判斷：

```text
Bukkit（最早的服務端 API）
  +- Spigot（Bukkit 的延續）
       +- Paper（主流分支，插件生態最大）
            +- Purpur（玩法開關最多）
            +- Folia（區域化多執行緒，插件相容差）
            +- Leaves（還原原版特性，生電向）
            +- Leaf（效能 / 原版機制 / 穩定性的平衡）
```

規則是**向下相容、向上不保證**：為 Paper 寫的插件通常能在 Purpur 上跑；為 Folia 寫的插件不一定會為 Paper 適配；只支援 Spigot 的老插件在 Paper 上一般也能跑，但可能報"使用了過時 API"。

完整的逐項對照與"按硬體怎麼選"見 [服務端核心對比](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7)；按玩法與硬體的完整選型講解見 [服務端選擇](/tutorials/java/core)。

## 3. Java 版模組載入器

模組服與插件服是兩套世界。載入器決定你能裝哪些模組，而**同一個模組通常只支援一個載入器**。

| 載入器 | 定位 | 生態 | 版本節奏 |
| --- | --- | --- | --- |
| Fabric | 輕量、啟動快；載入器本體與 API 分離，很多功能要靠 Fabric API 這個模組補 | 活躍；最佳化類與輕量內容類模組多 | 跟進新版本最快 |
| NeoForge | Forge 血脈在現代版本上的延續；功能 API 更完整 | 現代版本的大型內容與科技整合包主力 | 跟隨主版本推進 |
| Forge | 老牌載入器；歷史整合包與老版本大量使用 | 老整合包最多；新版本生態有相當一部分轉向 NeoForge | 仍在為多個版本發佈構建，但新版本跟進不如前兩者 |
| Quilt | 由 Fabric 分叉而來，目標是更開放的治理與新的 API | 明顯小於 Fabric；能載入相當一部分 Fabric 模組，但**並非全部** | 活躍度低於 Fabric，選之前先確認你要的模組在不在 |

判斷順序應該是**先定玩法，再定載入器**：

```text
列出你必須要的模組
  → 查每個模組支援的載入器與遊戲版本
  → 取交集最大的那個組合
  → 再裝服務端
```

反過來（先裝載入器再找模組）幾乎一定會返工。安裝流程、客戶端對齊與排查見 [模組服完整上手（Fabric / NeoForge）](/tutorials/java/modded)。

### 3.1 別忘了執行時版本

核心與載入器都要求匹配的 Java 執行時。裝錯 Java 是最常見的"啟動器打不開、服務端起不來"原因：

| Minecraft 版本 | 通常需要的 Java |
| --- | --- |
| 1.16.5 及更早 | 8 |
| 1.17.2 | 16 |
| 1.18.2 – 1.20.4 | 17 |
| 1.20.5 及更新 | 21 |

這張表是**寫作時的常見對應關係**，新版本隨時可能提高要求；以核心與載入器的官方文件為準。

### 3.2 客戶端也要裝載入器

模組服的一個常見誤解是"服務端裝好就行"。實際上：

| 模組類型 | 裝在哪 | 裝錯的後果 |
| --- | --- | --- |
| 僅客戶端（渲染、小地圖、介面增強） | 只裝客戶端 | 丟到服務端通常直接報錯或被載入器拒絕 |
| 僅服務端（邏輯與效能類） | 只裝服務端 | 客戶端裝了沒意義；服務端缺了功能不存在 |
| 雙端必需（新方塊、新物品、新維度） | 客戶端 + 服務端都要 | 缺任何一邊：連線被拒，或登錄檔不匹配報錯 |

所以發佈整合包時，**要同時給出客戶端與服務端兩份清單**，並在說明裡寫清哪些模組是可選的。

## 4. 代理端：不是核心，但常在選型裡出現

代理端自己不跑世界，只把玩家轉發到後端子服。它屬於"多服結構"的元件，**單服不需要它**。

| 代理端 | 定位 | 備註 |
| --- | --- | --- |
| Velocity | 現代代理端，效能好、活躍 | 多子服互聯的主流選擇 |
| BungeeCord | 老牌代理端 | 生態老、資料多，新專案通常優先 Velocity |

加了代理端之後，玩家的連線路徑變成"客戶端 → 代理端 → 後端子服"，插件要區分"裝在代理端"還是"裝在後端"，跨版本插件裝在哪一側也有不同代價。詳見 [跨版本相容](/tutorials/java/via) 與代理相關教學。

## 5. 基岩版：官方核心與第三方核心

基岩版的核心生態比 Java 版小，主流是四個。

| 核心 | 語言 | 插件生態 | 備註 |
| --- | --- | --- | --- |
| BDS（官方） | C++ | **本身不支援插件**，要靠社群載入器 | 官方服務端，相容性最好；生物運算壓在單執行緒，流暢度主要看單核效能 |
| Nukkit | Java | 原生插件系統，生態較小 | 輕量、上手簡單；**原版專案已不活躍**，實際應優先選活躍分支 |
| PowerNukkitX | Java | 相容 Nukkit 生態的大量插件，生態中等 | Nukkit 的現代主力分支：支援較新協議、多核最佳化、384 格世界高度、內建 Terra 地形生成器 |
| PocketMine-MP | PHP | **最大**（PHP 插件最多） | 會用 PHP 就能寫插件；高負載下有效能瓶頸，更新相對滯後 |

選型經驗：

- **要官方相容與穩定**：BDS，需要插件時再配社群載入器；
- **要高效能與高度自定義**：PowerNukkitX；
- **要最多的現成插件、且熟悉 PHP**：PocketMine-MP；
- **想從簡單開始**：先用 BDS 跑通，再考慮第三方核心。

基岩版核心的逐項對比與上手路徑見 [基岩版核心選擇](/tutorials/bedrock/cores) 與 [第三方核心（Nukkit / PNX / PMMP）](/tutorials/bedrock/third-party)。

### 5.1 第三方核心的執行環境

選核心之前先確認機器上裝了什麼執行時，否則第一步就會卡住：

| 核心家族 | 需要什麼 | 注意 |
| --- | --- | --- |
| BDS | 不需要 Java / PHP，解壓即用 | 平台壓縮包與可執行檔名以官方下載頁為準 |
| Nukkit 系（含 PNX） | **Java**，版本要求通常較新 | 64 位系統配 64 位 Java，否則會因記憶體上限中途崩潰 |
| PocketMine-MP | **PHP**（建議用官方打包好的執行時） | 發行版倉庫裡的 PHP 往往偏舊、擴充不全，先確認 `php -v` |

裝錯家族（例如給 PMMP 裝 Java、給 Nukkit 裝 PHP）不會"湊合能跑"，只會直接啟動失敗。

## 6. BDS 的插件載入器

官方 BDS 本身沒有插件系統。想在 BDS 上用插件，必須裝社群載入器，而**載入器與遊戲版本強繫結**：服務端升級前先確認載入器已經跟進。

| 載入器 | 寫插件用什麼 | 生態 | 備註 |
| --- | --- | --- | --- |
| LeviLamina | C++（前身是 LiteLoaderBDS） | 目前最成熟、生態最好 | 只支援特定版本區間，升級 BDS 前先核對 |
| BDSX | Node.js / TypeScript | 維護時間長，玩法偏底層（Hook 與網路包） | 支援範圍廣，適合願意寫程式碼的人 |
| EndStone | C++ / Python，API 風格接近 Bukkit | 生態很小，但方向清晰 | 適合想要類 Bukkit 開發體驗的場景 |
| BDSpyrunner | Python | 較小 | 具體形態與支援版本以專案官方倉庫為準 |

社群裡還有一些**替代服務端**（不是 BDS 載入器）：例如 Go 語言編寫的 gomint 與 Dragonfly、社群服務端 Allay，以及基岩版的代理端 WaterDogPE。它們的共同點是**生態與文件都薄**，遇到問題較難求助；除非有明確理由，不建議新手起步就選。

:::warn 載入器與遊戲版本強繫結
基岩版的服務端構建與協議高度繫結，社群載入器通常只支援**一段很窄的版本區間**。"先把 BDS 升到最新，再去找載入器"是最常見的翻車順序；正確順序是**先確認載入器支援到哪個構建，再決定服務端升到哪**。
:::

## 7. 我該選哪個

```text
玩家要用原版客戶端進服，並且需要管理/玩法插件
  → Paper（首選）
  → 想調原版機制：Purpur
  → 生電 + 插件：Leaves 或 Leaf（看清專案名）
  → 核心多、主頻低：再考慮 Folia（先確認插件適配）

玩家要裝模組、要新內容
  → 先定模組清單 → Fabric（輕量/最佳化類）或 NeoForge（現代內容整合包）
  → 老整合包：Forge
  → 只有 Quilt 獨有模組：才考慮 Quilt

玩家是基巖版
  → 原版生存、要官方相容：BDS（需要插件再配載入器）
  → 高效能 + 自定義：PowerNukkitX
  → 現成插件最多、會 PHP：PocketMine-MP

要多臺伺服器互聯
  → 加一層代理端（Velocity 優先）
```

## 8. 插件與模組是兩個世界

:::warn 插件和模組不是一回事，混著理解會一直踩坑
**插件（Plugin）**呼叫核心提供的 API，裝在服務端；玩家用**原版客戶端**就能進。典型內容是管理、經濟、領地、小遊戲。

**模組（Mod）**直接修改遊戲本體，裝在**載入器**上；絕大多數內容模組要求**客戶端和服務端裝同一套**，玩家不裝就進不來。典型內容是新方塊、新物品、新生物、新維度。

由此推出幾條硬規則：

- **插件服不能裝模組**：Paper 系核心沒有模組載入能力，`mods/` 目錄不存在。
- **模組服預設不能裝插件**：Fabric / NeoForge 服務端不認識 Bukkit 插件；`plugins/` 目錄不存在，`spigot.yml`、`paper-world-defaults.yml` 那一套配置也不存在。
- **兩邊的調優經驗不能互相照抄**：插件服的 JVM 參數、最佳化插件、熱過載習慣，搬到模組服基本無效，反之亦然。
- **同一個"功能"在兩邊的實現完全不同**：例如領地保護，插件服靠插件，模組服靠模組，配置與指令都不通用。
:::

## 9. 混合端的代價

**混合端（Hybrid）**指試圖同時提供插件 API 與模組載入能力的服務端專案。它確實能讓"插件 + 模組"跑在同一個服務端上，但代價要說清楚：

| 代價 | 說明 |
| --- | --- |
| 上游跟進慢 | 需要同時適配 Minecraft 版本、模組載入器與插件 API，新版本支援通常滯後 |
| 相容問題兩邊都有 | 插件與模組都可能出問題，而且難以判斷是哪一側引起的 |
| 求助困難 | 使用者規模小，遇到問題時幾乎沒有現成答案，作者精力也有限 |
| 升級與回滾風險高 | 世界格式、模組資料與插件資料混在一起，回滾比純插件服或純模組服複雜得多 |

:::warn 不要用混合端起步
混合端解決的是"我既要又要"的需求，但它把兩套系統的風險疊加在一起。**新手起步不要碰**；確有需要時，先把純插件服或純模組服跑穩，再評估混合端是否值得，並以其專案官方文件為準。歷史上有過多個混合端專案，支援狀態與維護情況各不相同，選之前務必看它的最新發佈與支援版本。
:::

## 10. 怎麼核對版本與生態

不要憑記憶選核心。每次決定前做這四步核對：

| 步驟 | 看什麼 | 去哪看 |
| --- | --- | --- |
| 1 | 目標遊戲版本下，核心有沒有發佈構建 | 核心的官方下載頁或官方倉庫 |
| 2 | 你要用的插件/模組，是否聲明支援該核心與該版本 | 插件/模組的發佈頁與支援列表 |
| 3 | 載入器（若有）支援到哪個版本區間 | 載入器官方文件 |
| 4 | 需要的 Java / PHP 執行時版本 | 核心與載入器官方文件 |

時間線只能告訴你"版本什麼時候發佈"，它不能告訴你"你的核心跟上了沒有"。這兩件事要分開查，參考 [版本時間線怎麼讀](/wiki/versions-guide)。

## 11. 常見選型錯誤

| 錯誤 | 後果 | 正確做法 |
| --- | --- | --- |
| 把模組丟進插件服 | 服務端根本不載入它，甚至報錯 | 先分清插件與模組，選對應的核心或載入器 |
| 先裝載入器再找模組 | 想要的內容模組不支援這個載入器，只能重來 | 先列模組清單，再定載入器 |
| 把 Leaves 與 Leaf 裝混 | 行為與原版特性還原程度不符預期 | 看準專案名與官方說明 |
| 以為 Folia 是"更快的 Paper" | 插件大面積不相容 | 先確認每個插件是否聲明支援 Folia |
| 只看"效能"不看生態 | 核心很快，但沒有你要的插件 | 生態與插件支援優先於效能數字 |
| 用混合端一步到位 | 相容問題疊加，升級困難 | 先跑純插件服或純模組服 |
| 給 BDS 直接升級到最新 | 社群載入器沒跟上，插件全部失效 | 先確認載入器支援區間，再升級服務端 |

## 12. 效能之外：三類開銷

選核心時最容易被"效能"兩個字帶偏。真正決定體驗的是三類開銷，它們指向不同的硬體：

| 開銷 | 由什麼決定 | 症狀 | 對應選擇 |
| --- | --- | --- | --- |
| 單核效能 | Minecraft 主邏輯基本跑在單執行緒上：實體、區塊、紅石與插件邏輯都壓在**一個核心** | 玩家一多就卡、TPS 掉、區塊載入慢 | 單核強的機器選 Paper 系；核心多但主頻低才考慮 Folia |
| 記憶體 | 視距、實體數量、插件快取與模組數量 | 頻繁 GC 卡頓、OOM 崩潰 | 先降視距與實體上限，再加記憶體；記憶體不能替代單核 |
| 磁碟與網路 | 區塊讀寫、自動儲存、玩家進出時的區塊傳送 | 儲存時全服卡頓、玩家進服慢 | SSD 優先；網路最佳化屬於另一條線 |

因此"這台機器幾核"遠不如"**單核多快**"重要。插件數量、模組數量與視距設定，對體驗的影響通常大於換核心帶來的收益。
