生電服的"最佳化"和普通服的最佳化不是一回事：普通服可以靠調低視距、換核心、加最佳化插件把 TPS 拉上來，而生電服每動一個開關，都要先問一句"這會不會改變原版行為"。這篇回答的是**生電服到底有哪些開關可以動、動了之後誰負責複驗**。

通用的效能最佳化（優先順序、視距與模擬距離、JVM 參數）見 [效能最佳化](/tutorials/java/optimize)，最佳化 mod 的選型見 [最佳化 mod](/tutorials/java/sd-optimize)，Carpet 規則與附屬包的完整清單見 [Carpet 及其附屬包](/tutorials/java/sd-carpet)。本篇只講配置層面的取捨，並且**不給任何具體配置欄位名與預設值**——那些東西隨版本變化，必須以各自官方文件為準。

## 一、生電服的三層開關

| 層面 | 典型例子 | 改了會怎樣 |
| --- | --- | --- |
| Carpet 規則 | `optimizedTNT`、`lagFreeSpawning`、`movableBlockEntities` | 有的只是省效能，有的**直接改變原版行為** |
| 最佳化 mod 的配置 | `ferrite-core`、`modernfix`、`c2me-fabric`、`async` | 各管一塊；改錯會引入卡頓、bug，或者改變時序 |
| 服務端自身配置 | 視距、模擬距離一類 | 屬於通用最佳化，見 [效能最佳化](/tutorials/java/optimize) |

三層裡最容易踩坑的是第一層：**Carpet 的規則名字聽起來都像"最佳化"，但性質完全不同**。所以下面先把它拆開。

## 二、Carpet 規則：先分清"純最佳化"與"改行為"

Carpet 是 Fabric 服務端 mod，提供規則系統，用 `/carpet <规则名> <值>` 開關原版細節行為。它的規則數量不小，生電服真正要關心的通常是下面這些：

| 規則 | 性質 |
| --- | --- |
| `optimizedTNT` | 純最佳化 |
| `lagFreeSpawning` | 純最佳化 |
| `fastRedstoneDust` | 純最佳化，但牽涉紅石，改完要複驗機器 |
| `maxEntityCollisions` | 上限類調參，會改變實體擠在一起時的表現 |
| `movableBlockEntities` | **改變原版行為**：給了原本沒有的能力 |
| `commandTick` | 除錯入口，不是最佳化項 |
| `tntDoNotUpdate` | **改變原版行為**，只在測試用 |
| `explosionNoBlockDamage` | **改變原版行為**，只在測試用 |

按性質分檔處理：

| 檔位 | 規則 | 怎麼用 |
| --- | --- | --- |
| 可以常開 | `optimizedTNT`、`lagFreeSpawning` | 先在測試服開，觀察機器與刷怪是否照常，再上主服 |
| 改了要複驗 | `fastRedstoneDust`、`maxEntityCollisions` | 記進變更記錄，通知技術組，機器自己複驗 |
| 改變原版行為，按需開 | `movableBlockEntities` | 它給了原版沒有的能力，開啟前要確認沒有機器依賴"活塞推不動方塊實體"這一點 |
| 只在測試服開 | `tntDoNotUpdate`、`explosionNoBlockDamage` | **正式開服不要開**；它們的用途是測試與實驗 |
| 工具類 | `commandTick` | 它是除錯入口，別當成最佳化項常開 |

:::warn 改了規則就要公告
玩家無法分辨"機器壞了"是自己的問題還是規則被改了。**每次改動都要留記錄並公告**：改了什麼、什麼時候改的、影響哪一類機器。這條紀律比具體開哪條規則更重要。
:::

## 三、最佳化 mod 的配置：各管一塊，一次只改一項

最佳化 mod 的設定項大多是**給不同子系統準備的**，所以要先知道每個 mod 負責哪一塊，再決定動誰：

| mod | 負責的方向 |
| --- | --- |
| `ferrite-core` | 記憶體佔用 |
| `modernfix` | 多合一：效能、記憶體、同時修 bug |
| `c2me-fabric` | 區塊效能 |
| `async` | 實體多執行緒 |
| `spark` | 測量工具（profiler），不是最佳化 mod |

**本篇刻意不寫任何具體配置欄位名與預設值**：這些 mod 的選項在版本之間會變，抄來的欄位名可能已經不存在，照抄預設值更可能直接把行為改掉。要調就在各 mod 自己的官方說明裡查。

改配置的紀律只有四條，但每一條都不能省：

1. **改之前先備份設定檔**（原則與做法見 [備份與恢復](/tutorials/java/backup)）——配置改壞了，你至少還能回到上一份。
2. **一次只改一項**，改完觀察一段時間。一次改五項，出事時你無法判斷是哪一項造成的。
3. **用 `spark` 對比改前改後**，用資料說話，而不是憑"感覺流暢了"。
4. **先在測試服或測試世界驗證**，尤其是 `c2me-fabric`、`async` 這類涉及區塊與多執行緒的項。

:::tip 多執行緒會改變時序
`c2me-fabric` 與 `async` 加速的是區塊與實體處理，多執行緒天然會改變執行順序與時序，而機器恰恰對時序敏感。只有在明確知道自己要什麼、並且願意承擔複驗成本時才動它們。
:::

## 四、版本差異：配置清單要跟著版本變

沒有一份"萬能最佳化配置"能跨版本通用。兩個必須記住的例子：

| mod | 變化 | 結論 |
| --- | --- | --- |
| `memoryleakfix` | 官方 README 說明：Minecraft `1.20.5+` 之後，它之前修復的所有記憶體洩漏官方都已修復，該 mod 在新版本上**已過時** | 新版本上不要再為了"最佳化"裝它 |
| `starlight` | 支援版本只到 `1.20.4`（Fabric）；官方 README 說明 `1.20` 上它與原版差距已經很小，且它是**侵入式**的光照引擎重寫，更容易與其他 mod 衝突 | 它不該繼續出現在新版本的配置清單裡 |

所以每次升級遊戲版本、升級 mod 或換核心之後，都要重新對照一遍：**這份清單裡的每一項，在當前版本上是否還存在、是否還有意義**。已經過時的項留在配置裡，通常不會報錯，只會安靜地佔著位置並增加相容風險。

## 五、改動優先順序清單

按順序做，價效比最高；順序反了，容易把機器改壞還找不到原因。

```text
1. 先测基线：用 spark 采样，记下正常时的 TPS / MSPT
2. 再动"纯优化"项：optimizedTNT、lagFreeSpawning，以及内存类优化 mod 的配置
3. 接着动上限与范围类调参：maxEntityCollisions 一类，改完让机器复验
4. 最后才考虑改时序的项：c2me-fabric、async 这类区块与多线程相关的配置
5. 改变原版行为的规则（tntDoNotUpdate、explosionNoBlockDamage）只在测试服用
```

配套的做法是"**改前備份、一次一項、留下記錄、公告玩家**"。生電服的配置管理，本質上是**版本管理**：你改的不是一個數字，而是所有機器的執行前提。

## 六、四個常見誤區

| 常見做法 | 問題 |
| --- | --- |
| 一次把看到的最佳化項全開 | 出問題無法定位是哪一項造成的，只能全部關掉重來 |
| 抄一份別人的最佳化配置直接用 | 版本、mod 組合與機器都不同，別人能開不代表你能開 |
| 拿"感覺變快了"當結論 | 沒有基線就沒有對比，先用 `spark` 取樣再下判斷 |
| 改了規則不記錄、不公告 | 機器壞了沒人知道原因，技術組只能把它當成 bug 排查 |

判斷一個改動值不值得保留，標準只有一個：**有資料表明它更好**，而不是"別人都這麼開"。
