這是 [生電與紅石](/tutorials/java/redstone) 的進階篇。入門篇回答的是"該選哪個核心"，這一篇回答三個更實際的問題：**技術玩家到底在造什麼、這些機器依賴哪些服務端設定、作為服主你要提前準備什麼。**

先明確本篇的邊界：這裡**不給機器圖紙，也不保證任何具體設計在你的版本上成立**。生電最基本的事實是——**機器的可用性繫結在具體的遊戲版本和具體的服務端實現上**。任何"這台機器永久有效"的說法都不可信。

## 1. 生電玩家到底在造什麼

技術玩家口中的"農場"（farm）指的是**自動化或半自動化的資源產線**：用遊戲機制換產出，而不是用手挖。先建立一張類別地圖，再談負載。

| 類別 | 機制要點 | 主要負載 | 版本敏感度 |
| --- | --- | --- | --- |
| 刷怪塔 / 掉落物農場 | 利用自然刷怪或刷怪籠，把怪物集中後處死 | 實體數量、AI 尋路、掉落物與經驗球、區塊常載入 | 中：刷怪規則、怪物 AI、碰撞箱改動都會影響效率 |
| 物品農場 | 依靠方塊自身行為產出（甘蔗、竹子、仙人掌、海帶、蜂蜜、羊毛等） | 方塊更新、隨機刻、漏斗與礦車收集 | 中低，但收集端的漏斗本身是負載 |
| 鐵農場 | 用村民與恐嚇機制（或襲擊機制）觸發鐵傀儡生成 | 村民 AI、工作網站方塊（POI）查詢、實體生成、常載入 | 高：村民與鐵傀儡的生成條件被反覆調整 |
| 金農場 | 用下界傳送門刷出殭屍豬靈（1.16 起由"殭屍豬人"改名而來）並集中處死 | 傳送門方塊實體、實體數量、下界區塊常載入 | 高：實體命名、AI 與傳送門機制都有改動 |
| 村民交易大廳 | 大量村民配工作網站方塊，重新整理並鎖定交易 | 村民 AI、POI、尋路、區塊常載入 | 中高：交易與職業機制多次調整 |
| 襲擊農場 | 觸發襲擊並處理波次，獲取綠寶石、不死圖騰等 | 成波生成的實體、AI、掉落物 | 高 |
| 凋靈骷髏農場 | 在下界要塞刷怪，配合雪傀儡或凋靈玫瑰等完成擊殺 | 要塞區塊常載入、實體、掉落物 | 中高 |
| 樹場 / 食物農場 | 自動種植與採伐（活塞或 TNT），以及各類作物農場 | 隨機刻、方塊更新、TNT 實體、掉落物 | 中 |
| TNT 複製與其他機制型農場 | 利用複製類特性獲得 TNT 等資源；利用活塞、重力方塊、傳送門等機制 | TNT 實體與爆炸、海量方塊更新，容易直接壓垮 TPS | 極高：這類特性被反覆修復又反覆出現，且很多伺服器明令禁止 |

按"負載"而不是按"產出"分類，是因為**對服主而言，機器的產出歸玩家，機器的成本歸伺服器**。下面逐類說明。

### 1.1 刷怪塔與掉落物農場

- **機制**：要麼讓怪物在黑暗區域自然生成後集中，要麼用刷怪籠持續產出。集中手段通常是水流、活塞推動、或者把怪物引到另一維度。
- **負載**：怪物是"會思考的實體"，每刻都要做 AI、尋路與碰撞判定；掉落物和經驗球還會繼續佔用實體額度。
- **服主要注意**：這是最容易把伺服器拖慢的一類機器，因為它同時消耗實體、AI、區塊與掉落物四項成本。

### 1.2 物品農場

- **機制**：不依賴刷怪，靠方塊自身行為產出，例如甘蔗、竹子、仙人掌、海帶、蜂蜜、羊毛。
- **負載**：以方塊更新和隨機刻為主，產出物需要用漏斗或礦車收集，**收集端往往比生產端更貴**。
- **服主要注意**：調低 `randomTickSpeed` 會直接讓這類農場變慢；調大漏斗搬運間隔（`hopper-transfer`）會讓所有收集系統變慢。

### 1.3 鐵農場

- **機制**：利用村民與"恐嚇"條件觸發鐵傀儡生成，也有基於襲擊機制的變體。
- **負載**：村民 AI 與工作網站方塊查詢是出了名的貴，加上區塊必須常載入。
- **版本注意**：鐵傀儡的生成條件、村民的工作與睡眠判定都改過多次，**這類機器幾乎每次大版本更新都要複驗**。

### 1.4 金農場

- **機制**：用下界傳送門刷出殭屍豬靈（1.16 起殭屍豬人改名為殭屍豬靈）後集中處死。
- **負載**：傳送門方塊實體、大量實體與掉落物，且必須讓下界區塊常載入。
- **版本注意**：實體改名、AI 調整、傳送門機制變化都會影響產出方式。

### 1.5 村民交易大廳

- **機制**：把大量村民關在一起，配工作網站方塊重新整理交易，直到出現想要的交易再鎖定。
- **負載**：村民是伺服器上最"重"的常見實體之一，尋路、POI 查詢、每刻行為都要算。
- **服主要注意**：交易大廳常常和鐵農場、繁殖機連在一起，形成一小片高負載區；`tick-inactive-villagers` 一類最佳化項會直接改變村民行為。

### 1.6 襲擊農場

- **機制**：主動觸發襲擊並處理一波波生成的襲擊者，換取綠寶石、不死圖騰等。
- **負載**：波次生成會在短時間內製造大量實體，屬於**突發型**負載，容易造成 MSPT 尖峰而不是平穩升高。
- **版本注意**：襲擊觸發條件、波次組成與掉落表都改過。

### 1.7 凋靈骷髏農場

- **機制**：在下界要塞範圍內刷怪，再用自動手段完成擊殺與收集。
- **負載**：要塞區塊必須常載入，實體與掉落物持續存在。
- **服主要注意**：要塞結構範圍有限，多個玩家同時建農場會互相搶刷怪額度。

### 1.8 樹場與食物農場

- **機制**：自動種植與採伐（活塞或 TNT），以及小麥、胡蘿蔔、馬鈴薯等作物農場。
- **負載**：隨機刻、方塊更新、TNT 實體與爆炸。
- **服主要注意**：TNT 型樹場的爆炸會帶來大量方塊更新，是**局部卡頓**的常見來源。

### 1.9 TNT 複製與其他機制型農場

- **機制**：利用遊戲中的複製類特性獲得 TNT 等本應昂貴的資源；或利用活塞、重力方塊、傳送門等機制的邊界行為。
- **負載**：TNT 實體與爆炸、成片方塊更新，一台大規模複製裝置足以讓 TPS 掉到個位數。
- **服主要注意**：這類特性**被官方反覆修復又反覆出現**，具體行為完全繫結版本；同時**很多伺服器在規則裡明確禁止**，因為它同時是效能問題與公平性問題。是否允許，必須在規則裡寫清楚。

:::warn 不要以為某個設計是"通用"的
同一台機器在不同遊戲版本上可能完全失效，原因可能是刷怪規則、實體 AI、方塊更新順序、某個被修掉的複製特性，甚至只是碰撞箱改了 0.1 格。所以：

- 玩家說"這機器能用"時，先問清**遊戲版本**和**服務端核心**；
- 服主說"我們升級到新版本"時，等於宣佈**所有機器都要重新驗證**；
- 任何教學（包括本篇）給出的設計都只能當"思路"，不能當"保證"。
:::

## 2. 一台機器會給服務端帶來什麼

把機器拆成六種成本，排查時才有方向：

| 成本類型 | 由什麼產生 | 典型表現 |
| --- | --- | --- |
| 實體數量 | 怪物、掉落物、經驗球、礦車、盔甲架、TNT | MSPT 上升，實體同步佔頻寬 |
| AI 與尋路 | 怪物與村民的每刻思考、路徑計算 | 村民密集區特別明顯，TPS 掉且難以定位 |
| 區塊載入 | 常載入區塊、傳送門載入器 | 無人時也持續吃 CPU 與記憶體 |
| 方塊更新與紅石排程 | 紅石元件、漏斗、活塞、偵測器 | 高頻時鐘與大面積紅石是經典殺手 |
| 隨機刻 | 作物、樹葉、冰霜、火勢 | 調高 `randomTickSpeed` 後 CPU 線性上升 |
| 光照與存檔 | 方塊變化觸發光照重算；區塊定期自動儲存 | 大面積改造時出現規律性卡頓 |

結論只有一句：**TPS 是這些成本疊加後的結果，不是某一個開關決定的。**

### 2.1 怎麼把成本量化

不要憑感覺判斷"這台機器貴不貴"，按下面的順序測：

```text
1. 记录基线：没有玩家在线时的 TPS / MSPT
2. 只让一名玩家站在机器旁，观察 5-10 分钟的 MSPT 曲线
3. 关掉机器再测一次，两次的差值就是这台机器的成本
4. 用 spark 采样，确认成本落在实体、方块实体还是区块上
5. 把数字记下来，下次升级版本或换配置时用同一方法复测
```

這樣做的價值在於：當玩家說"是伺服器卡才導致機器不工作"時，你手上有資料可以判斷，而不是互相猜。

## 3. 生電依賴的服務端設定

原則先擺在這裡：**原版行為是"預設值"，最佳化是"偏離預設值"。** 技術玩家要的是前者。

下面的鍵名、預設值與可選值**都隨版本變化**，也可能因為你用的核心分支不同而不存在。請以**你自己服務端的設定檔**和該核心的官方文件為準，本篇只講"這一項是幹什麼的、改了會發生什麼"。

### 3.1 刷怪上限（mob cap）

原版的刷怪上限**不是固定數字**，而是按玩家、按可刷怪區塊數量縮放的。要點：

- 上限隨**玩家數量**與**玩家周圍可刷怪區塊數量**縮放，所以"伺服器人多了刷怪變多"是正常現象；
- 怪物、動物、水生生物、環境生物各有各的上限；
- 上限按玩家計算，所以**沒有玩家線上時不會自然刷怪**——哪怕那片區塊被常載入；
- 插件端的 `spawn-limits`（`bukkit.yml`）會覆蓋這套演算法，把"按玩家縮放"改成別的口徑。不同核心分支的實現不同，改動它會直接改變所有刷怪塔的產能。

### 3.2 刷怪範圍與消失距離

- 原版怪物在玩家周圍一定距離內生成（有最小與最大距離），離玩家過遠會消失。
- `mob-spawn-range`（`spigot.yml`，單位是區塊）會改動這個範圍。
- 改動的連鎖反應：刷怪塔效率、怪物消失速度、村莊與襲擊相關機制的觸發範圍都會變。
- 生電服通常**保持原版範圍**，因為所有成熟設計都是圍繞原版距離做的。

### 3.3 實體啟用範圍（entity activation range）

- Spigot 的 `entity-activation-range` 會讓遠處實體**降頻甚至停止 tick**，預設值大致在十幾格到四十幾格之間（具體以你的 `spigot.yml` 為準）。
- 後果很直接：機器裡"離玩家遠"的那一半不工作，或者工作速度與原版不一致。
- 生電服要麼把它調到足夠大，要麼接受"部分機器行為與原版不同"。
- 注意：這一項對普通生存服是**收益極高**的最佳化，所以很多預設配置把它壓得很低，衝突就出在這裡。

### 3.4 隨機刻

- `randomTickSpeed` 是遊戲規則，原版預設值是 3。
- 影響範圍：作物生長、樹葉腐爛、冰霜形成與融化、火勢蔓延。
- 調高會讓依賴隨機刻的農場變快，同時**大幅**增加 CPU 開銷；調低則相反。
- 很多"最佳化"教學會建議調低它——那等於**改了原版行為**，作物類機器會跟著變慢。

### 3.5 紅石相關

- Paper 系核心提供可切換的**紅石實現方式**（設定項位於世界預設配置中，如 `misc.redstone-implementation` 一類，鍵路徑與可選值隨版本變化）。
- 生電服**必須保持 vanilla 實現**。換成為效能最佳化過的實現會改變紅石更新行為，機器可能直接失效。
- 另外注意：一些最佳化項會調整方塊更新順序或紅石排程延遲，這類改動比"效能下降"更致命，因為它**靜默地**讓機器壞掉。

### 3.6 其他常被改動的項

| 設定 | 原版行為 | 常見"最佳化"做法 | 生電的取捨 |
| --- | --- | --- | --- |
| `simulation-distance`（`server.properties`） | 該距離內的區塊真實運算 | 調低到 4-6 | 影響所有機器的可用範圍，調低等於砍掉遠處機器 |
| `view-distance` | 玩家能看到多遠 | 調低 | 隻影響觀感與頻寬，對機器影響小 |
| `entity-broadcast-range-percentage` | 實體同步給玩家的範圍比例 | 調低 | 玩家會看到實體"突然出現"，但不影響服務端運算 |
| `entity-tracking-range`（`spigot.yml`） | 實體被追蹤的距離 | 調低 | 隻影響同步，不改機器邏輯 |
| `max-entity-collisions` | 超過上限就停止處理實體碰撞 | 調低 | 密集實體機器需要調大，代價是效能 |
| `nerf-spawner-mobs` | 刷怪籠生成的怪物 AI 完整 | 設為 `true` 削弱 AI | 會讓刷怪籠農場產出方式改變 |
| `hopper-transfer` / `hopper-check`（`ticks-per`） | 漏斗每 8 刻搬運一次 | 調大以省效能 | **直接改變所有漏斗產能**，機器時序全變 |
| `merge-radius`（`spigot.yml`） | 掉落物與經驗球的合併半徑 | 調大 | 減少實體數量，但改變原版合併行為 |
| `randomTickSpeed` | 3 | 調低 | 作物類農場變慢 |
| `doMobSpawning` 等遊戲規則 | 見遊戲內 `/gamerule` 說明 | 關掉以減少負載 | 關掉就沒有刷怪塔了 |

### 3.7 這些設定長什麼樣

下面只是**示意**，用來讓你認識這些鍵在檔案裡的位置與形狀；**數值不是你要抄的答案**，請對照你本地的檔案。

```yaml
# spigot.yml（示意，键名与默认值随版本变化）
world-settings:
  default:
    mob-spawn-range: 8
    entity-activation-range:
      animals: 32
      monsters: 32
      raiders: 48
      misc: 16
      water: 16
      villagers: 32
      flying-monsters: 48
    max-entity-collisions: 8
    nerf-spawner-mobs: false
    merge-radius:
      item: 2.5
      exp: 3.0
    ticks-per:
      hopper-transfer: 8
      hopper-check: 8
```

```yaml
# bukkit.yml（示意，默认值随版本变化）
spawn-limits:
  monsters: 70
  animals: 10
  water-animals: 15
  water-ambient: 20
  ambient: 15
ticks-per:
  monster-spawns: 1
  animal-spawns: 400
  autosave: 6000
```

```text
# server.properties（示意）
simulation-distance=10
view-distance=10
entity-broadcast-range-percentage=100
```

```bash
# 游戏规则：这些是原版默认值，改之前先想清楚会破坏什么
/gamerule randomTickSpeed 3
/gamerule doMobSpawning true
/gamerule doFireTick true
/gamerule doInsomnia true
/gamerule doPatrolSpawning true
/gamerule doTraderSpawning true
/gamerule disableRaids false
/gamerule mobGriefing true
```

:::warn 很多"最佳化"插件改的就是原版行為
市面上大量"效能最佳化"插件與預設配置，做法是把上面這些值調到比原版激進得多：縮小實體啟用範圍、調低隨機刻、合併實體、改寫紅石排程、限制刷怪上限。對普通生存服這是好事，**對生電服就是災難**——機器會以難以排查的方式失效，而且往往不是"完全不動"，而是"偶爾少產出一點"。

所以：

- 裝任何最佳化插件前，先確認它**改了哪些原版行為**，最好在測試服上跑一台已知機器驗證；
- 最佳化項與生電需求是此消彼長的，不要指望兩者都拉滿，參見 [效能最佳化](/tutorials/java/optimize)；
- 如果症狀是"實體和掉落物堆著不清"，那屬於堆積問題而不是配置問題，見 [實體與掉落物堆積導致的卡頓](/tutorials/faq/entity-lag)。
:::

## 4. 區塊載入

區塊載入是生電服最容易被忽視、也最容易被玩家濫用的部分。

### 4.1 出生點區塊

- 世界出生點周圍的區塊會被遊戲**持續保持載入**，即使沒有玩家線上。這就是"出生點掛機農場"能 24 小時執行的原因。
- 注意區分"載入"和"刷怪"：**沒有玩家線上時不會自然刷怪**，但紅石、方塊實體、作物隨機刻會繼續推進。
- 出生點區塊的**範圍大小在版本之間改過**，較新的版本還提供了控制它的遊戲規則（例如 `spawnChunkRadius` 一類）。具體範圍與規則名請查對應版本的官方 wiki，不要照抄舊教學。
- 實踐建議：**別把最重要的機器建在出生點**，否則它會在你不知情的情況下 24 小時消耗資源。

### 4.2 `/forceload`

原版提供的強制載入指令，也是服主審計時最直接的抓手：

```bash
/forceload add <起点x> <起点z> [终点x 终点z]
/forceload remove <起点x> <起点z> [终点x 终点z]
/forceload remove all
/forceload query
/forceload query <x> <z>
```

要點：

- 座標是**方塊座標**，被載入的是包含這些座標的區塊；
- 單條指令能載入的區塊數量有上限（**最多 256 個區塊**）；
- 強制載入列表**隨存檔儲存**，重啟後依然生效；
- 需要管理員權限等級（通常 OP 二級）；
- 被強制載入的區塊是**完整運算**的，不是"只載入不運算"。

### 4.3 傳送門式區塊載入器

- 玩家常用的"區塊載入器"大多基於下界傳送門：傳送門會讓**另一維度對應的區塊**在一段時間內保持載入。
- 典型用法是"在下界放一個傳送門，讓主世界的機器繼續跑"，或者反過來。
- **具體保持多久、用什麼等級的票據，是版本相關的**，請以對應版本的機制說明為準；這也意味著一個載入器在升級後可能失效或變成"永久載入"。
- 服主視角：這類裝置**不會出現在 `/forceload query` 裡**，只能靠人工排查。

### 4.4 常載入區塊的代價

| 代價 | 說明 |
| --- | --- |
| 記憶體 | 每個已載入區塊的資料與實體都常駐記憶體，載入得越多，堆佔用越高，GC 壓力越大 |
| CPU | 被載入的區塊會走完整的 tick 流程：方塊實體、隨機刻、實體 tick |
| 刷怪上限 | 若載入區附近有玩家，這些區塊會**分攤**刷怪上限，導致別處的農場產量下降 |
| 存檔 | 載入中的區塊會定期自動儲存，常載入區域越大，自動儲存的抖動越明顯 |
| 隱蔽性 | 載入器常常建在玩家看不到的地方（下界、地下），出事時最難定位 |

### 4.5 怎麼審計

1. **逐個維度執行 `/forceload query`**：主世界、下界、末地都要查，載入器經常在另外兩個維度。
2. **排查傳送門載入器**：問玩家、看下界傳送門的位置，注意"為什麼這裡有個孤零零的傳送門"。
3. **看無人時的 MSPT**：玩家全部離線後，TPS/MSPT 仍然不健康，基本就是常載入區塊在跑。
4. **用效能分析工具定位**：spark 一類工具的取樣結果能告訴你時間花在哪些區塊與實體上，方法與 [效能最佳化](/tutorials/java/optimize) 相同。
5. **把結論寫進規則**：誰建的載入器、載入了多大範圍、用來跑什麼，登記下來，升級版本前逐個複驗。

## 5. 技術玩家必須理解的 tick 模型

### 5.1 20 TPS 與 50 毫秒

- 原版目標是 **20 TPS**，也就是每個遊戲刻 **50 毫秒**。
- 單刻逾時不會立刻掉 TPS：偶爾一個 200 毫秒的刻，平均下來 TPS 仍然接近 20，但玩家會感到一次卡頓。真正讓 TPS 掉下去的是**持續**超支。
- 所有依賴時間的機制（作物、熔爐、紅石、生物移動）都在這個迴圈裡推進，所以 TPS 一掉，**一切同時變慢**。
- 這也是為什麼"TPS 15"感覺遠不止慢 25%：所有機器都按同一個比例變慢，依賴精確時序的設計會直接停擺。

### 5.2 遊戲刻與紅石刻

| 單位 | 長度 | 用途 |
| --- | --- | --- |
| 遊戲刻（game tick） | 1/20 秒 = 50 毫秒 | 服務端主迴圈的最小單位 |
| 紅石刻（redstone tick） | 2 個遊戲刻 = 0.1 秒 | 社群用來描述紅石元件延遲的單位，中繼器、偵測器一類的延遲都以它計量 |

一個最小例子：

```text
第 0 刻（0 ms）     中继器被激活，安排"2 刻后输出"
第 1 刻（50 ms）    线路上的其他更新在同一刻内继续结算
第 2 刻（100 ms）   中继器输出，也就是 1 红石刻之后
```

要理解的關鍵點：**紅石刻是"延遲的計量單位"，不是"計算的執行單位"**。方塊更新在同一遊戲刻內可以沿著線路瞬間傳播，所以機器的行為往往取決於**同一刻內的更新順序**，而不只是延遲數值。

### 5.3 更新順序為什麼是命門

- 兩個元件在同一刻互相影響時，誰先誰後決定了最終狀態。
- 這正是"換個服務端核心機器就壞"的根本原因：核心為了實現並行或最佳化，可能改變遍歷順序。
- 也是為什麼升級遊戲版本後必須**逐台複驗**：官方修 bug 時會順帶改掉某些順序。
- 除錯手段：原版提供 `/tick` 一類的控制指令（凍結、步進、加速等，具體子指令隨版本變化），可以逐刻觀察機器狀態；也有 Carpet 一類的除錯工具。

### 5.4 "卡頓機器"是破壞手段

**卡頓機器（lag machine）指故意構造的、以壓垮伺服器為目標的裝置。** 常見形態：

- 極高頻紅石時鐘，配合大面積紅石線路製造更新風暴；
- 瞬間生成海量實體（TNT、掉落物、盔甲架、礦車、船）；
- 讓水流與岩漿大面積流動與更新；
- 利用區塊載入機制製造"永遠載入 + 每刻都在算"的迴圈；
- 反覆觸發生成/解除安裝區塊，讓主執行緒一直做區塊工作。

它的性質是**破壞行為，不是玩法**：目的是讓所有人掉線、讓伺服器無法正常儲存、甚至損壞存檔。

### 5.5 怎麼發現卡頓機器

| 訊號 | 說明 |
| --- | --- |
| MSPT 突然持續飆高，TPS 掉到個位數 | 最直接的表現 |
| 實體數量異常 | 用 `/kill` 類指令統計前先**別急著清**，那是證據 |
| spark 火焰圖裡出現集中的紅石/實體/區塊熱點 | 定位到具體區塊與座標 |
| 玩家報告"某個座標一靠近就卡" | 座標就是線索 |
| 日誌裡出現實體上限或看門狗相關警告 | 服務端已經在自保 |

處置順序建議：**先定位座標與裝置 → 截圖/記錄 → 按規則處理 → 恢復受影響區域**。反作弊、日誌與回滾手段見 [反作弊與防破壞](/tutorials/java/anticheat)。

## 6. 權限與工具

### 6.1 服務端側：Carpet 一類工具

- 技術向伺服器普遍使用 **Fabric + Carpet**（以及它的各類擴充）作為服務端側的規則與除錯工具：它能開關大量原版細節行為，也提供除錯指令。
- **具體規則名與可用規則集合隨 Carpet 版本變化**，請以對應版本的 Carpet 官方文件為準，不要照抄別人的規則清單。
- Carpet 是服務端 mod，原版客戶端可以直接進服，不需要玩家裝任何東西。
- 生電服的常見做法是：**把啟用的規則清單公開**，讓玩家知道哪些原版行為被改了。

### 6.2 客戶端側：MiniHUD / Litematica 一類工具

| 工具 | 用途 |
| --- | --- |
| MiniHUD | 在 HUD 上顯示座標、生物群系、光照、區塊邊界等 |
| Litematica | 原理圖投影，照著搭機器 |
| Tweakeroo | 一批便利性調整 |
| Servux | 服務端 mod，讓結構範圍顯示、原理圖貼上在伺服器上正常工作 |
| Syncmatica | 把原理圖上傳到伺服器，多人共享 |

### 6.3 伺服器要支援什麼

- 服務端側 mod（Carpet、Servux、Syncmatica 的服務端部分）**需要 Fabric 服務端**。插件端（Paper 系）不能直接跑 Fabric mod；用橋接方案會有相容性與效能代價，見 [模組服完整上手](/tutorials/java/modded)。
- 純客戶端 mod（MiniHUD、Litematica 的顯示部分）在任何服務端上都能用，但**依賴服務端資料的部分**（結構邊界、原理圖貼上、精準放置）需要服務端配合才能工作。
- 因此開生電服前要定一件事：**服務端是 Fabric 還是 Paper 系**。這個決定一旦做出，後面幾乎所有工具鏈都跟著它走。
- 還要對齊**版本**：客戶端 mod 的版本、服務端 mod 的版本、遊戲版本三者必須一致，否則玩家連不進來。

### 6.4 權限清單

給技術玩家的權限建議單獨分組，而不是直接給 OP：

| 權限 | 用途 | 風險 |
| --- | --- | --- |
| `/forceload` | 讓機器持續執行 | 濫用會導致伺服器長期高負載，建議登記制 |
| `/tick`（凍結/步進一類） | 除錯機器時序 | 凍結全服會打斷所有人，注意公告 |
| `/gamemode spectator`、`/tp` | 觀察與搭建 | 低風險 |
| `/spark` | 自查效能 | 低風險，建議放開給技術組 |
| `/give`、創造模式 | 搭建機器 | 只應在測試環境或明確授權的建築區使用 |
| WorldEdit 一類批次編輯 | 快速施工 | **一次錯誤的選擇就能毀掉存檔**，務必限定權限並先備份 |

## 7. 開一個技術向伺服器的檢查清單

| 專案 | 為什麼必須做 |
| --- | --- |
| **世界預生成** | 玩家跑圖觸發的區塊生成是 TPS 的主要殺手，預生成能把這項成本提前付掉，見 [效能最佳化](/tutorials/java/optimize) |
| **大工程前備份** | 技術玩家會做大範圍改造與爆炸性測試，出問題時你要能回到上一分鐘 |
| **獨立的測試世界/測試服** | 任何新機器、新配置、新核心版本先在測試服驗證，絕不在主服直接試 |
| **版本鎖定與升級流程** | 升級會讓機器失效，必須公告、備份、在測試服複驗後再上主服 |
| **Carpet 規則清單公開** | 玩家需要知道哪些原版行為被改了，否則會把機器失效誤判成自己的問題 |
| **關於卡頓機器與複製特性的明確規則** | 這兩件事必須在規則裡寫清楚，否則封人沒有依據 |
| **基線監控** | 記錄正常時的 TPS/MSPT，才能在"變慢了"時有對比，而不是憑感覺 |
| **儲存規劃** | 備份 + 原理圖 + 日誌的增長速度往往超出預期 |
| **權限分級** | 技術組權限與普通玩家權限分開，OP 不輕易給 |
| **機器登記與溝通渠道** | 誰在哪建了什麼機器，是排查問題時最有價值的資訊 |

一份可以直接改的規則骨架：

```text
1. 允许：常规红石机器、刷怪塔、作物农场、村民交易设施。
2. 需要登记：常加载区块、区块加载器、任何无人运行的大型装置。
3. 禁止：以压垮服务器为目的的装置（高频时钟阵列、海量实体生成、区块反复加载）。
4. 复制类特性：明确写"允许"或"禁止"，不要留空白。
5. 版本升级：提前公告，升级后机器需自行复验，服主不保证兼容。
6. 处罚：按日志与坐标证据处理，先警告后封禁。
```

## 8. 小結

- 生電玩家造的是**資源產線**，按負載分類比按產出分類更有用。
- 服務端要關心的設定集中在：**刷怪上限與範圍、實體啟用範圍、隨機刻、紅石實現、區塊載入**。
- **常載入區塊是有代價的**：記憶體、CPU、刷怪上限與存檔抖動，必須審計與登記。
- 理解 **20 TPS / 50 毫秒**與**紅石刻 = 2 遊戲刻**，才能理解機器為什麼壞、為什麼慢。
- **卡頓機器是破壞手段**，要有規則、有檢測、有回滾。
- 工具鏈選擇（Fabric + Carpet vs Paper 系）是生電服的**第一個決定**，它會決定後面一切。

:::tip 技術服的 TPS 是設計結果，不是配置結果
很多服主把"卡"當成配置問題，於是一直在調參數、換最佳化插件，最後把機器全調壞了。真實情況是：**TPS 由玩家造了什麼機器、機器多大、放在哪、載入了多少區塊決定**。參數只能讓你在原版行為與效能之間做取捨，不能憑空把一台設計糟糕的機器變便宜。先看設計，再談配置。
:::
