生電服的世界是**被持續大範圍改寫**的：機器一開，地形、方塊、實體都在成片變化。一次誤操作、一次崩潰寫壞存檔，代價往往不是"丟幾分鐘進度"，而是"整套工程白做"。所以在生電服裡，存檔保護不是順手做的事，而是要設計進流程裡的一環。

通用的備份原則——該備什麼、怎麼保證一致性、保留策略、恢復流程——已經寫在 [備份與恢復](/tutorials/java/backup) 裡，本篇不重複。這裡只講生電場景下額外的三件事：**用 MCDR 的備份插件把備份變成流程**、**用 `Ledger` 查清發生了什麼**、**把至少一份備份放到機器之外**。

## 一、為什麼生電服的備份要更勤

| 生電服的特點 | 對備份的要求 |
| --- | --- |
| 機器一旦跑起來，世界變化極大：成片清空區域的裝置、持續執行的農場，在很短時間裡就能改掉大片地形與實體 | 備份間隔必須短於你能接受的最大損失，不要指望一份隔夜備份兜住一次大工程 |
| 回檔是連坐的：整檔回退會把同一時間窗裡**所有**玩家的進度一起抹掉 | 出事時先爭取局部修復，只有修不好才整檔回退 |
| 大型工程投入極高：從備料、搭建到除錯，機器是"用時間換產出" | 備份保住的不是幾格方塊，而是已經投進去的那段時間 |
| 存檔與備份預設在同一台機器、同一塊盤上 | 本地備份之外，必須有一份離開這台機器 |

:::warn 沒有驗證過恢復的備份不算備份
這句話對生電服尤其成立：機器越猛，回檔越貴。等到真出事那天才發現備份從來沒成功過，損失無法補救。恢復演練的做法見 [備份與恢復](/tutorials/java/backup)。
:::

## 二、用 MCDR 的備份插件把備份變成流程

MCDR 是**獨立於服務端行程之外**的 Python 管理器，服務端崩了它還在，因此它能自動重啟服務端，也能在崩潰時執行備份——這正是備份該待的位置。它的安裝方式、插件機制與指令見 [MCDR 服務端管理器](/tutorials/java/mcdr)。

MCDR 官方插件目錄裡**確實存在**的備份類插件目錄名，可以按用途方向分成四組：

| 方向 | 插件目錄名 | 大致用途 |
| --- | --- | --- |
| 整檔備份 | `prime_backup`、`extra_prime_backup`、`quick_backup_multi`、`better_backup`、`permanent_backup`、`zip_backup`、`smart_backup`、`cushion_of_backup` | 以整個存檔或整個服務端目錄為單位備份與保留 |
| 定時備份 | `timed_quick_backup_multi`、`auto_backup` | 按間隔自動觸發，不依賴你記得手動執行 |
| 分區塊與分區域備份 | `chunk_backup`、`region_backup` | 以區塊或區域為單位，粒度比整檔更細 |
| 異地備份 | `ftp_backup`、`baidu_netdisk_backup` | 把備份送到遠端儲存 |

選插件前後有三件事必須確認：

1. **分組只是按插件目錄名看出的方向**，具體功能、設定項與保留規則以每個插件自己的說明為準；裝好後先在測試環境裡真的跑一遍"備份 → 恢復"。
2. **插件不會替你解決一致性**：無論用哪一個，都要確認它不會拷到寫了一半的存檔，原則見 [備份與恢復](/tutorials/java/backup)。
3. **別把備份產物留在同一塊盤上**，否則第四節與第六節說的問題照樣發生。

對生電服，比較實用的組合是"**一個定時整檔備份 + 一個分區塊備份**"：前者負責兜底，後者負責把回退範圍縮小到某個區域。兩個都裝時注意讓它們錯開時間，避免同時讀寫磁碟。

## 三、`Ledger`：先查清"發生了什麼"

`Ledger` 是服務端日誌 mod（loaders：`fabric`、`quilt`；支援版本 `1.17-rc1` 至 `26.3`）。

在插件端，同類工具裡最出名的是 **CoreProtect**（loaders：`bukkit`、`folia`、`paper`、`purpur`、`spigot`；支援版本 `1.14.1` 至 `26.2`；它是插件端的資料記錄與防破壞工具，支援回滾與恢復）。`Ledger` 可以理解為 Fabric 生態裡**對標 CoreProtect 的那一套**：同樣記錄方塊與容器的操作、同樣能按時間與位置回查；區別是 CoreProtect 跑在插件端且自帶回滾，而 `Ledger` 只負責記錄與查詢。

它和備份回答的是兩個不同的問題，不能互相替代：

| 對比項 | `Ledger` | 備份 |
| --- | --- | --- |
| 回答的問題 | 發生了什麼、誰做的、什麼時候、影響了哪裡 | 怎麼把世界整體退回到某個時間點 |
| 資料形態 | 事件記錄 | 存檔目錄的副本 |
| 粒度 | 事件級，可以一路查到具體的位置與容器 | 整檔（目錄級） |
| 出事時先做什麼 | 定位與定責，據此判斷"能不能只回退或修一小塊" | 定位不到時的兜底：整檔回退 |
| 代價 | 記錄會持續增長，需要維護 | 佔磁碟，回退會抹掉同期的所有進度 |

幾點使用提醒：

- `Ledger` 的定位是**記錄**，不是恢復手段。它給你的是"範圍與責任人"，真正把世界改回去還是要靠人工修復或備份。
- 記錄量需要長期維護：MCDR 官方插件目錄裡有 `ledger_cleaner`，作用就是清理 `Ledger` 的資料。這也說明它的資料不是放著不管就行。
- `Ledger` 是服務端 mod，需要 Fabric 服務端。防破壞的另一半（權限與即時手段）見 [反作弊與防破壞](/tutorials/java/anticheat)。

**兩者的正確順序是**：出事後先用 `Ledger` 把範圍縮到一小塊，能局部修就局部修；定位不到、或者破壞面太大，再用備份整檔回退。反過來做，你會為了一個人的行為把全服的進度一起抹掉。

## 四、異地備份：這一步不能省

本地備份和伺服器在同一台機器上，所以下面這些情況會**同時帶走存檔和你的全部備份**：

| 情況 | 結果 |
| --- | --- |
| 機器（或磁碟）壞了 | 存檔與本地備份一起沒 |
| 系統被重灌、磁碟被格式化、目錄被誤刪 | 同上 |
| 機器被服務商收回、機房出事 | 你可能連機器都拿不回來 |

插件層面已經有現成的異地思路：`ftp_backup` 與 `baidu_netdisk_backup` 都是**把備份送到遠端**的插件，也就是說異地備份不需要你從零寫腳本。

但"傳上去"不等於"能拿回來"。遠端憑據會不會過期、路徑還在不在、備份是不是完整、能不能恢復，都要定期驗證；異地的通用做法與維護見 [異地備份](/tutorials/ops/offsite-backup)。另外要注意：異地備份傳的是**同一條鏈路**，如果備份本身因為磁碟滿或權限問題失敗了，遠端只會安靜地少掉一份，所以本地的備份日誌同樣要看。

## 五、一份可以直接照做的檢查清單

| 時間點 | 動作 |
| --- | --- |
| 開服前 | 裝好一個定時整檔備份插件，把備份目錄指到另一塊盤 |
| 大工程開工前 | 手動打一份整檔備份，並記下時間點（回退時的錨點） |
| 每次改動配置或加 mod 前 | 備份配置與存檔，改完先觀察再繼續 |
| 平時 | 確認備份產物真的在生成（看目錄與日誌），而不是隻看插件載入成功 |
| 定期 | 把一份備份送到遠端；抽一份在測試環境裡解壓並恢復 |
| 出事時 | 先查 `Ledger` 定位範圍，能局部修就局部修，修不了再整檔回退 |

## 六、備份放在哪：三個位置

| 位置 | 能擋住什麼 | 擋不住什麼 |
| --- | --- | --- |
| 存檔旁邊或同一塊盤 | 手滑刪錯檔案、單份備份損壞 | 磁碟損壞、格式化、整個目錄被誤刪 |
| 同一台機器的另一塊盤 | 單塊磁碟損壞 | 系統重灌、整機故障、機器被收回 |
| 機器之外的遠端 | 整機故障、誤格式化、機器被收回 | 沒有明顯短板，但前提是你驗證過它能取回來 |

常見的錯誤就藏在這張表裡：

- 備份目錄設在 `world/` 裡面，回退時連備份一起被覆蓋；
- 備份與存檔在同一塊盤上，盤壞了兩個一起沒；
- 只保留最新一份，遇到"存檔已經壞了但還沒發現"的情況就沒救了；
- 裝了備份插件卻從來沒看過它的日誌，直到出事那天才發現它一直在失敗。

## 七、備份不是孤立的：三件套

機器越猛，越要**備份 + 權限 + 防崩規則**這三件東西一起上。它們各自負責一個環節，缺哪一環都會在出事那天暴露：

| 一環 | 解決什麼 | 去哪看 |
| --- | --- | --- |
| 備份 | 出事之後把世界退回去 | 本篇與 [備份與恢復](/tutorials/java/backup) |
| 權限與白名單 | 讓不該動手的人動不了手 | [反作弊與防破壞](/tutorials/java/anticheat) |
| 防崩規則 | 做更新抑制一類操作時，不讓服務端直接崩掉 | [Carpet 及其附屬包](/tutorials/java/sd-carpet) |
