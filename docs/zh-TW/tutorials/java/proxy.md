當伺服器從"一個服"變成"一組服"（大廳 + 生存 + 小遊戲……）時，就需要**跨服端（代理端）**來統一入口。

## 一、代理端做什麼

代理端**自己不跑世界**，它只做一件事：**接住玩家的連線，再轉發到後端的某個子服**。

```
玩家 → 代理端（Velocity / BungeeCord）
              ├→ 大厅服
              ├→ 生存服
              └→ 小游戏服
```

好處：

- **統一入口**：玩家只記一個位址，切換子服時不斷線、不用重連。
- **統一帳號驗證**：正版驗證在代理端做一次，後端全部設成離線模式（內部互信）。
- **好維護**：加一個子服只要在代理配置裡登記一條，玩家無感。
- **資源共享**：大廳、登入服、小遊戲可以各自獨立重啟，不影響其他服。

## 二、選哪個

| 代理端 | 說明 |
| --- | --- |
| **Velocity** | 現代方案，**效能更好、更活躍**，新專案優先選它。支援"現代轉發"（modern forwarding），驗證資訊通過金鑰安全傳遞 |
| **BungeeCord** | 老牌方案，生態成熟、資料極多，很多老教學基於它。適合維護既有老服 |

> 兩者思路一致，差別在配置細節與轉發機制。**新開服建議 Velocity**。

## 三、搭建要點

### 1. 代理端

- 下載代理端 jar，單獨放一個目錄，寫啟動腳本執行。
- 配置裡登記**子服列表**（名稱 + 內網位址 + 埠）。
- 正版驗證**只在代理端開**：代理端 `online-mode=true`，子服必須 `online-mode=false`。

### 2. 子服

子服要對代理端"交出信任"，即**只接受來自代理端的連線**：

- **Velocity**：使用**現代轉發**，在代理端與子服上配置同一個 `forwarding.secret`，子服開啟對應轉發模式。
- **BungeeCord**：在子服配置裡開啟 `bungeecord: true`（Spigot 系），並關閉子服自身的正版驗證。

### 3. 關鍵安全點

:::warn 轉發金鑰就是伺服器的鑰匙
子服一旦信任代理轉發，**任何知道金鑰的人都能偽造任意玩家身份進入**。所以：

- `forwarding.secret` **不要洩露、不要提交到公開倉庫**；
- 子服埠**不要直接暴露公網**，只允許代理端所在機器訪問（用防火牆限制來源）。
:::

## 四、注意事項

- **插件要區分位置**：有的插件裝在代理端（跨服聊天、全域權限），有的必須裝在子服。裝錯位置會出現"指令存在但沒反應"。
- **代理端會多一跳**：玩家延遲略有增加，通常可忽略，但鏈路差時會被放大。
- **模組端不好混**：代理轉發對模組端支援有限，模組服跨服通常需要專門方案。
- **背包/資料同步**：跨服時玩家的背包、位置等由代理端與子服協作處理，**不要在子服之間共享同一個世界資料夾**。
- **別把代理端當"效能最佳化"**：它不提升效能，只是**結構**上的統一入口。單服不需要它。

## 五、什麼時候該上代理

**該上**：有多個玩法分區、需要統一入口、玩家要在服之間自由切換、要做大廳與登入服。

**不該上**：只有一個服。**多一層就多一層故障點**，小服上代理純屬增加維護成本。
