插件服和模組服是兩套不同的世界。插件在服務端"外掛"功能，玩家用原版客戶端就能進；模組直接改遊戲程式碼，**絕大多數內容模組要求服務端和客戶端裝同一套東西**，玩家不裝就進不來。

這一篇把模組服從零到能開講完：選載入器、裝服務端、對齊客戶端、放模組、排查不匹配，以及模組服特有的效能、備份與更新問題。如果你還在糾結"到底開插件服還是模組服"，先看 [服務端選擇](/tutorials/java/core)。

## 1. 插件服和模組服的區別

| 對比項 | 插件服（Paper / Purpur 等） | 模組服（Fabric / NeoForge 等） |
| --- | --- | --- |
| 擴充方式 | 插件呼叫服務端提供的 API，不改遊戲本體 | 模組直接修改遊戲程式碼 |
| 玩家要不要裝東西 | 不用，原版客戶端即可 | 多數要裝**同款載入器 + 同一套模組** |
| 典型內容 | 管理、小遊戲、經濟、領地保護 | 新方塊、新物品、新生物、新機器、新維度 |
| 更新速度 | 核心更新快，插件跟得緊 | 慢，取決於每個模組作者 |
| 可調參數 | 核心配置 + 插件配置非常豐富 | 很少，主要靠模組本身與 JVM |
| 出問題時的排查 | 看插件列表與插件配置 | 看**模組清單是否完全一致**與崩潰日誌 |

**要玩法內容選模組，要管理功能選插件**。兩者混用的方案（混合端）存在，但相容性與維護成本都更高，不建議新手起步就碰。

### 1.1 三類模組：僅客戶端 / 僅服務端 / 雙端必需

模組不是"裝了就有用"，先分清它屬於哪一類，否則一定會踩坑：

| 類別 | 典型例子 | 應該裝在哪 | 裝錯會怎樣 |
| --- | --- | --- | --- |
| **僅客戶端（client-only）** | 渲染類（Sodium 等）、小地圖、光影相關、介面增強 | 只裝客戶端 | 丟到服務端通常直接報錯或崩潰，多數載入器會拒絕載入 |
| **僅服務端（server-only）** | 只在服務端生效的邏輯/效能類模組、部分管理類模組 | 只裝服務端（有些模組兩端都能裝，但裝在客戶端沒有意義） | 客戶端裝了一般不崩，但可能被服務端握手拒絕；服務端缺了則功能不存在 |
| **雙端必需（both-required）** | 新增新方塊、新物品、新生物、新維度、新機制的內容模組 | 客戶端 + 服務端都要 | 缺任何一邊：連線被拒，或登錄檔不匹配導致報錯 |

還有一類介於兩者之間：**雙端都可以裝、但不是必需**（例如記憶體最佳化、網路最佳化類模組）。這類模組的發佈頁會寫清"可選"。

### 1.2 怎麼知道一個模組屬於哪一類

以模組**自己的發佈頁與說明**為準，優先順序從高到低：

| 來源 | 看什麼 |
| --- | --- |
| 模組發佈頁（Modrinth / CurseForge） | 環境標記。Modrinth 現在用 `environment` 欄位（如 `client_only`、`server_only`、`client_and_server`），舊的 `client_side` / `server_side` 取值為 `required` / `optional` / `unsupported` |
| 模組 README / 作者公告 | 作者常直接寫 "server-side only"、"client-side only"、"required on both sides" |
| Fabric 模組 | `fabric.mod.json` 裡的 `environment` 欄位：`"*"`（預設，兩端都算）、`"client"`（客戶端）、`"server"`（獨立服務端，不含單人整合的服務端） |
| NeoForge 模組 | `META-INF/neoforge.mods.toml` 的元資料，以及程式碼中標註為僅客戶端載入的入口（如 `dist = Dist.CLIENT`） |
:::warn 別把插件服的經驗套到模組服
- `spigot.yml`、`paper-world-defaults.yml`、Bukkit 插件那一整套在模組服**不存在**，照著插件服教學調模組服只會白費功夫。
- 模組服預設**不能裝 Bukkit 插件**（要裝得用混合端，屬於另一套方案）。
- 插件服的 JVM 參數、最佳化插件、熱過載習慣都不能照抄（見第 10 節）。
- 反過來也一樣：模組服的經驗不要拿去套插件服。
:::

## 2. 選載入器：Fabric / NeoForge / Forge

| 載入器 | 定位 | 適合誰 |
| --- | --- | --- |
| **Fabric** | 輕量、啟動快、跟進新版本快，載入器本體與 API 分離 | 追求效能與快速更新，模組以最佳化類 + 少量內容類為主 |
| **NeoForge** | Forge 血脈在現代版本上的延續，功能 API 更完整 | 現代版本的大型內容整合包、機器/科技類玩法 |
| **Forge** | 老牌載入器，歷史整合包與老版本仍大量使用 | 要跑老整合包，或必須依賴只在 Forge 上維護的老模組 |

**版本格局要看清**：載入器"支援哪些 Minecraft 版本"是隨時間變化的，本文不列具體數字，只給判斷方法：

- Fabric：官方下載頁可以同時選遊戲版本與載入器版本，頁面會直接給出下載與啟動指令。Fabric 官方文件寫明支援 1.14 及之後的所有正式版（以及 18w43b 之後的快照）。
- NeoForge：官網首頁按 Minecraft 版本給出對應安裝器檔案；官方文件提供伺服器安裝步驟。
- Forge：官方下載頁按版本列出 latest / recommended 構建，至今仍在為多個版本（含較新版本）發佈；但新版本的模組生態有相當一部分已轉向 NeoForge。

> **本站可直接下載** —— 載入器核心（Fabric / NeoForge / Forge）見 **[資源下載 · 服務端核心](/downloads/core)**；模組本體見 **[資源下載 · 模組](/downloads/mods)**；如果最後決定走插件服，插件見 **[資源下載 · 插件](/downloads/plugins)**。三處收錄的都是官方與社群來源的下載連結，點「下載」按鈕並按提示登入即可，**本站不儲存任何檔案**。
:::note 載入器之間基本不通用
同一個模組通常只支援一個載入器。Fabric 的模組不能丟進 NeoForge 服，反之亦然。所以**選載入器本質上是在選"你要裝的模組都在哪一邊"**：先去模組發佈頁確認目標模組支援哪個載入器、哪個遊戲版本，再決定裝什麼。
:::

判斷順序建議：

```
先定玩法（要哪些模組） → 查這些模組支援的載入器與遊戲版本
  → 取交集最大的那個載入器 + 遊戲版本 → 再裝服務端
```

## 3. 在服務端安裝載入器

安裝器介面和檔名會隨版本變化，所以下面只講**通用流程**，每一步的準確做法以載入器官方文件為準。

### 3.1 先確認 Java 版本

| Minecraft 版本 | 需要的 Java |
| --- | --- |
| 1.16.5 及更早 | 8 |
| 1.17.2 | 16 |
| 1.18.2 – 1.20.4 | 17 |
| 1.20.5 及更新 | 21 |

Java 裝錯版本是最常見的"安裝器打不開/服務端起不來"原因，先排除它。

### 3.2 通用流程

1. 建一個空目錄作為服務端根目錄。
2. 到載入器官方下載頁選好 Minecraft 版本與載入器版本，下載安裝器（`.jar`）。
3. 執行安裝器，選擇**服務端（Server）**安裝方式。命令列方式通常是加 `--installServer` 參數。
4. 安裝器會產出一個**啟動腳本或啟動器 jar**（以及執行所需的庫目錄）。
5. **先啟動一次**。第一次啟動會生成 `eula.txt`、`server.properties`、`mods/`、`config/`、`logs/` 等，然後因為未同意 EULA 而退出。
6. 開啟 `eula.txt`，把 `eula=false` 改成 `eula=true`（表示你同意 Minecraft EULA）。
7. **再次啟動**，確認能正常起服、控制台沒有報錯。
8. 這時才往 `mods/` 裡放模組，然後重啟。

### 3.3 Fabric

- 官方伺服器下載頁（fabricmc.net 的 server 頁面）可以選擇版本，並給出下載指令與啟動指令；照著頁面顯示的**檔名與啟動指令**執行即可。
- 安裝器有 Server 索引標籤，用於在本地生成服務端啟動器。
- 絕大多數 Fabric 模組需要 **Fabric API**，它也是一個模組，放進 `mods/`。

```bash
# 官方頁面會給出類似這樣的下載與啟動指令，請以頁面實際顯示為準
# 1) 下載服務端啟動器
# 2) 首次啟動
java -jar <服務端啟動器檔名> nogui
```

### 3.4 NeoForge

NeoForge 官方文件給出的流程（以 21.x 系列為例）：

```bash
# 1) 下載安裝器（版本號以官網為準）
wget https://maven.neoforged.net/releases/net/neoforged/neoforge/<版本>/neoforge-<版本>-installer.jar

# 2) 安裝服務端
java -jar neoforge-<版本>-installer.jar --installServer

# 3) 首次啟動（會因 EULA 退出）
./run.sh        # Windows 用 run.bat
```

要點：

- 安裝後會生成 `run.sh` / `run.bat` 和 **`user_jvm_args.txt`**。**改記憶體請改 `user_jvm_args.txt`，不要手改 `run.sh`**。
- 首次啟動後出現 `mods` 資料夾，模組放這裡。
- 更新 NeoForge 只需用新版本安裝器再跑一遍同樣的指令；官方明確提醒：**更新前先備份世界**。

### 3.5 Forge（老版本 / 老整合包）

```bash
java -jar forge-<版本>-installer.jar --installServer
```

- 較新的 Forge 與 NeoForge 類似，會生成 `run.sh` / `run.bat` 與 `user_jvm_args.txt`。
- 更老的版本會生成一個可直接啟動的 `forge-<版本>.jar`，用 `java -jar` 啟動。
- 老版本的模組往往只維護在 Forge 上，此時沒有太多選擇餘地。
:::tip 起不來先看日誌
載入器安裝失敗、模組崩潰，日誌都在 `logs/latest.log`、`logs/debug.log` 和 `crash-reports/` 裡。定位思路見 [常見報錯與崩潰排查](/tutorials/faq/errors)。
:::

## 4. 客戶端一側：玩家必須裝同一套

模組服的"進不去"絕大多數不是網路問題，而是**客戶端和服務端的模組清單不一致**。

玩家的正確姿勢：

1. 裝**同一個載入器**，並且是**同一個 Minecraft 版本**。
2. 裝**同一套模組**（包含所有依賴，例如 Fabric API）。
3. 模組版本也要對齊（見第 6 節）。

### 4.1 為什麼清單不一致就進不去

進入伺服器時，客戶端與服務端會做一次"握手"：交換載入器資訊、模組清單以及部分登錄檔內容。只要出現下面任一情況，就會被拒絕或直接報錯：

- 服務端有、客戶端沒有的**雙端必需**模組；
- 客戶端有、服務端沒有的同類模組；
- 同一個模組**版本不同**；
- 缺少依賴模組。

### 4.2 玩家會看到什麼

| 載入器 | 表現 |
| --- | --- |
| NeoForge / Forge | 連線被拒，並彈出一個**列出被拒絕模組的介面**（社群常稱 "mod rejections" / 不相容模組介面），逐條給出原因，例如"服務端沒有這個模組""版本不匹配"。具體文案與佈局隨版本變化 |
| Fabric | 載入階段缺少依賴時，載入器會給出 "Incompatible mod set!" 一類的錯誤介面，並在日誌裡列出缺失/衝突的模組；Fabric 官方文件有崩潰報告與依賴覆蓋的專門頁面 |
:::tip 讓玩家少踩坑的做法
- 把客戶端 `mods/` 打包成壓縮包發給玩家，或在整合包平台發佈客戶端包與服務端包。
- 在群公告裡寫清：載入器、Minecraft 版本、載入器版本、模組清單版本號。
- 服務端更新模組後，**同步更新客戶端包**，否則老客戶端會立刻進不來。
:::

## 5. 模組放在哪裡

> **去哪裡找模組** —— 本站收錄了 Modrinth 的模組條目，見 **[資源下載 · 模組](/downloads/mods)**，可按載入器（Fabric / Forge / NeoForge / Quilt）與遊戲版本篩選，點「下載」按鈕並按提示登入即可拿到官方下載連結。放之前務必先確認它屬於「僅客戶端 / 僅服務端 / 雙端必需」哪一類（見 [1.1](#11-三类模组仅客户端--仅服务端--双端必需)）。

| 位置 | 說明 |
| --- | --- |
| 服務端 `mods/` | 服務端載入的所有模組（`.jar`） |
| 客戶端 `.minecraft/mods/` | 玩家客戶端載入的所有模組 |
| `config/` | 模組自己的設定檔，多數在**首次啟動後**生成，不在 `mods/` 裡 |
| `defaultconfigs/` | 部分載入器/整合包用來放"新世界預設配置"的目錄 |
:::warn 僅客戶端模組不要放服務端，反之亦然
這是模組服最常見的崩潰原因之一：

- 把渲染/介面類**僅客戶端模組**丟進服務端 `mods/`，服務端啟動時就會報錯甚至崩潰（服務端沒有客戶端類）。
- 把**僅服務端模組**丟給客戶端，輕則無用，重則因為類缺失導致客戶端崩潰。
- 只裝一半的**雙端必需模組**，結果就是玩家連不上。

判斷方法回到第 1.2 節：以模組發佈頁的環境標記與作者說明為準。
:::

## 6. 三方匹配規則

模組服能不能跑起來，取決於三個東西同時對上：

| 匹配項 | 要求 |
| --- | --- |
| 遊戲版本 | 服務端、客戶端、每個模組都要支援同一個 Minecraft 版本 |
| 載入器版本 | 客戶端與服務端用同一個載入器；載入器版本儘量一致（至少都在模組要求範圍內） |
| 模組版本 | 同一個模組在兩端必須**同版本**；依賴模組必須存在且滿足版本範圍 |

### 6.1 從日誌診斷不匹配

| 現象/日誌線索 | 含義 | 處理 |
| --- | --- | --- |
| 啟動即崩，崩潰報告列出某個模組名 | 該模組與當前遊戲版本/載入器不相容，或缺少依賴 | 換對應版本，或補依賴 |
| 日誌出現 "missing dependency" / 依賴解析失敗 | 模組聲明的依賴沒裝或版本不符 | 按日誌補齊依賴 |
| 日誌出現模組載入失敗、類找不到 | 常是把僅客戶端模組放到了服務端（或反之） | 從錯誤的一側移除 |
| 玩家連線被拒，介面列出模組 | 雙端清單/版本不一致 | 對齊兩端模組 |
| 崩潰報告裡 `Is Modded: Definitely; ... brand changed to 'fabric'/'neoforge'` | 只是說明當前是模組環境，本身不是錯誤 | 繼續往下看真正的異常棧 |

依賴語義（Fabric 規範，NeoForge 類似）：

| 聲明 | 含義 |
| --- | --- |
| `depends` | 硬依賴，缺失直接失敗 |
| `recommends` | 軟依賴，缺失只警告 |
| `conflicts` / `breaks` | 衝突，命中就報錯 |

### 6.2 找不到是哪個模組在搗亂

用**二分法**（NeoForge 官方文件推薦的做法）：

1. 把一半模組移出 `mods/`（注意保持依賴完整）。
2. 啟動，看問題是否還在。
3. 還在 → 繼續對當前這一半做二分；不在 → 把另一半換進來再試。
4. 重複到定位出具體模組。

## 7. 效能模組（按類別認識）

模組服的效能最佳化主要靠"裝對模組"，而不是調設定檔。下面這些是能確認存在、且被廣泛使用的（載入器支援情況來自各自專案頁，會隨版本變化，裝之前請再確認一次）：

| 類別 | 模組 | 作用 | 載入器 | 備註 |
| --- | --- | --- | --- | --- |
| 遊戲邏輯最佳化 | **Lithium** | 最佳化遊戲邏輯（刷怪、AI、方塊行為等）的效能，儘量不改變行為 | Fabric、NeoForge、Quilt | 兩端都可裝，服務端收益明顯 |
| 記憶體佔用 | **FerriteCore** | 降低記憶體佔用（方塊狀態等資料結構） | Fabric、Forge、NeoForge、Quilt | 記憶體吃緊的模組服很實用 |
| 網路最佳化 | **Krypton** | 最佳化網路棧，降低頻寬與 CPU 開銷 | Fabric | 主要面向服務端與連線 |
| 光照引擎 | **Starlight** | 重寫光照引擎，修光照效能與錯誤 | Fabric | 專案已歸檔，最高支援到 1.20.4；其說明也寫明 1.20 上它與原版差距已經很小。**新版本不要硬裝** |
| 區塊預生成 | **Chunky** | 提前生成區塊，減少玩家跑圖時的卡頓 | Fabric、Forge、NeoForge，以及 Paper/Spigot 等 | 長期開放的服幾乎是必備 |
| 客戶端渲染 | **Sodium** | 客戶端渲染最佳化（提升幀率） | Fabric、NeoForge、Quilt | **僅客戶端**，服務端不要裝 |
:::note 關於"最佳化模組"的兩條紀律
- **不要同時裝多個功能重疊的最佳化模組**（例如兩個光照重寫），它們互相沖突的機率很高。
- 最佳化模組會改變遊戲內部行為，**生電/精密機器服要謹慎**：寧可慢一點，也不要讓機器失效。
:::

## 8. 世界與資料相容性：刪除模組是不可逆的

模組新增的方塊、物品、實體、維度、生物群系，都會寫進世界存檔。**移除模組後，這些內容對應的資料仍在存檔裡，但遊戲已經不認識它們**：

- 輕則變成"缺失方塊/空實體"，看起來像空氣，實際資料還在；
- 重則區塊載入報錯，甚至讓存檔無法開啟；
- 重新裝回**同一個模組且版本相容**時，通常能恢復。
:::warn 先備份，再動模組
- 任何"加模組、刪模組、換載入器、換遊戲版本"的操作之前，**先完整備份世界目錄**（備份方法見 [備份與恢復](/tutorials/java/backup)）。
- 模組服的存檔**不能直接降級**：把模組服的世界拿回原版或低版本開啟，風險極高。
- 想"試裝一個模組看看"？請在**副本**上試，不要在正式存檔上試。
:::

## 9. 安全更新模組服 / 整合包服務端

推薦流程（順序不要省）：

1. **備份**：世界 + `config/` + 模組清單。
2. **凍結變更**：先關服，或在維護視窗內操作。
3. **先更新載入器**，啟動一次確認服務端本身沒問題（此時舊模組可能報錯，屬正常）。
4. **逐個更新模組**，不要一次全換。分批更新便於定位問題模組。
5. **對齊客戶端包**：把更新後的 `mods/`（客戶端側）重新打包發佈。
6. **觀察**：起服後看 `logs/latest.log` 有無異常，線上跑一段時間再看 TPS 與報錯（可用 [效能最佳化](/tutorials/java/optimize) 裡的方法）。
7. **保留回滾包**：把上一版服務端目錄與客戶端包留著，出問題能立刻退回。

## 10. 記憶體與 JVM 參數

模組服和插件服的記憶體特徵不一樣：

| 專案 | 插件服 | 模組服 |
| --- | --- | --- |
| 堆記憶體需求 | 相對低 | **明顯更高**：模組登錄檔、模型、配方、機器資料都吃記憶體 |
| 啟動時間 | 短 | 長（幾百個模組時啟動數分鐘很常見） |
| 主要瓶頸 | 主執行緒 + 插件品質 | 主執行緒 + 模組品質 + 記憶體/GC |
| 參數來源 | 核心官方文件的推薦組合 | **載入器自己的啟動檔案說明** |

實操建議：

- **記憶體給足但別過量**。堆開太大，GC 停頓反而變長；先按實際玩家數與模組規模給一個合理值（例如小型模組服 4–8 GB 起，逐步調），再觀察。
- NeoForge / 較新 Forge：改 `user_jvm_args.txt`（安裝時生成，檔案內自帶註釋說明），不要手改 `run.sh`。
- 其他啟動方式：在啟動腳本裡用 `-Xms` / `-Xmx` 指定記憶體。
- **不要照抄插件服的參數組合**。為 Paper/Spigot 設計的參數組合假設了不同的負載與 GC 行為；模組服請優先參考載入器官方文件與模組作者的說明。
- 參數只解決記憶體/GC 層面問題，**救不了單核瓶頸**，也救不了寫得很差的模組。

```bash
# 示意：把記憶體引數寫在啟動指令碼或 user_jvm_args.txt 中
# 具體數值按你的模組規模與玩家數調整
-Xms4G
-Xmx8G
```

## 11. 排錯速查表

| 現象 | 常見原因 | 處理 |
| --- | --- | --- |
| 服務端啟動即崩，日誌點名一個模組 | 模組版本與遊戲/載入器不匹配，或缺少依賴 | 換對應版本，補齊依賴 |
| 介面/日誌提示 "Incompatible mod set!" 或列出被拒絕的模組 | 雙端模組清單或版本不一致 | 對齊兩端模組與版本 |
| 刪掉模組後，世界裡出現缺失方塊/實體 | 模組資料殘留，遊戲不再認識 | 裝回相容版本恢復；**先備份**，不要繼續寫入存檔 |
| 玩家進不去，服務端沒有明顯報錯 | 客戶端缺模組/缺依賴/版本不同 | 讓玩家使用同一份客戶端包 |
| 服務端能起但很卡 | 模組本身效能差、實體/機器過多、記憶體不足 | 用 profiler 定位（見 [用 spark 分析伺服器效能](/tutorials/ops/spark)），再針對性處理 |
| 啟動卡在載入模組很久 | 模組數量多、首次生成配置、磁碟慢 | 屬正常現象；用 SSD，並耐心等待 |
| 裝了僅客戶端模組到服務端 | 服務端缺少客戶端類 | 從服務端 `mods/` 移除 |

## 結語

模組服的複雜度來自"兩端必須一致"這一條鐵律：**先定玩法與版本，再裝載入器，最後才加模組**。每加一個模組就啟動一次、每次動模組前先備份，能省下大量返工時間。
