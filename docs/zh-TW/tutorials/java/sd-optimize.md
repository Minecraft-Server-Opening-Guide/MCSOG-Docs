生電服要不要裝最佳化 mod，是一個容易走極端的問題：有人一個不裝，寧可卡；有人把能找到的全塞進 `mods`，結果機器開始莫名其妙地失效。兩種做法都不對——**問題不在"裝不裝"，而在"這一類的代價是什麼"**。

這一篇把 10 個常見的最佳化類 mod 分成三類：可以放心裝、要看版本、會改時序要謹慎。判斷標準只有一條：**它是否可能改變機器的行為**。

和調配置那類最佳化的關係，見 [效能最佳化](/tutorials/java/optimize)：那篇講的是配置與優先順序的通盤思路，本篇只講 mod 這一層。

## 一、全部 10 個 mod 一覽

下面的 loaders、支援版本與下載量來自 Modrinth 官方條目。

| mod | loaders | 支援版本 | 下載量（約） |
| --- | --- | --- | --- |
| `lithium` | fabric、neoforge、quilt | 1.16.2–26.3 | 1.337 億 |
| `ferrite-core` | fabric、forge、neoforge、quilt | 1.16.5–26.3 | 1.574 億 |
| `krypton` | fabric | 1.16.2–26.3 | 4304 萬 |
| `c2me-fabric` | fabric | 1.17.1–26.4-snapshot-3 | 3918 萬 |
| `modernfix` | fabric、forge、neoforge | 1.16.4–26.1.2 | 8023 萬 |
| `memoryleakfix` | fabric、forge、quilt | 1.14.4–1.20.4 | 3802 萬 |
| `starlight` | fabric | 1.17–1.20.4 | 1606 萬 |
| `async` | fabric、neoforge、quilt | （官方條目未給出固定區間） | 71.7 萬 |
| `spark` | fabric、forge、neoforge、quilt | 1.16.5–26.3 | 2317 萬 |
| `chunky` | bukkit、fabric、folia、forge | 1.13.2–26.3 | 1888 萬 |

讀這張表時有兩點要注意：

- **下載量高不等於"必須裝"**。它只說明用的人多，不代表它適合你的硬體與你的機器（裝置）。
- **`async` 的版本區間在官方條目上沒有固定的寫法**，所以上表沒有給它編一個範圍。以專案頁當前列出的遊戲版本為準。

## 二、可以放心裝：記憶體、啟動、分析與預生成

這一類是"行為無關"的：它們最佳化的地方不是遊戲的邏輯與順序，而是記憶體佔用、啟動過程、觀測手段與區塊生成。對生電服來說，這一類的代價最低。

| mod | 可以放心裝的理由 |
| --- | --- |
| `ferrite-core` | 動的是記憶體佔用這一層，不介入 tick 邏輯 |
| `modernfix` | 覆蓋面是效能、記憶體與 bug 修復，不是單一機制的改寫 |
| `spark` | 它只負責觀測，不修改遊戲行為 |
| `chunky` | 提前把區塊生成完，避免玩家跑圖時邊跑邊生成 |

幾點補充：

- **`spark` 不是最佳化 mod**，它是分析工具。"先測再改"的意思就是：裝 `spark` 是為了**看清瓶頸在哪**，而不是指望它讓伺服器變快。它的讀圖方法見 [用 spark 分析伺服器效能](/tutorials/ops/spark)。
- **`chunky` 解決的是生成期的卡頓**，與 [效能最佳化](/tutorials/java/optimize) 裡"世界預生成"一節講的是同一件事，只是以 mod 的形式提供。長期開放的服幾乎是必備。
- **這一類之間不衝突**：記憶體、啟動、分析、預生成各管一段，可以一起用。真正需要小心的是"功能重疊"的兩個 mod，例如兩個都在重寫光照引擎的實現。

## 三、要看版本：兩個官方結論

這兩個 mod 不是"不好"，而是它們的適用範圍有明確邊界，官方自己就把邊界寫清楚了。照抄結論即可：

### `memoryleakfix`：1.20.5+ 已過時

官方 README 的結論是：**Minecraft 1.20.5+ 之後，該 mod 之前修復的所有記憶體洩漏都已被官方修復**，因此它在新版本上已經過時。

對應的資料也能看出來：它的支援版本是 1.14.4–1.20.4，而新版遊戲已經不在這個區間裡。**在新版本上繼續裝它沒有意義**；只有在 1.20.4 及更早的版本上，它修的那些洩漏才還有官方未修復的餘地。

### `starlight`：只到 1.20.4，且官方給出了取捨

官方 README 裡有四條要點，一條比一條具體：

| 官方結論 | 對生電服的含義 |
| --- | --- |
| 支援到 1.20.4 為止（1.17–1.20.4） | 新版本上根本沒有可裝的檔案 |
| 1.20 上 Starlight 與原版差距已經很小 | 升級到 1.20 之後，裝它的收益已經不大了 |
| 與 Phosphor 完全不相容 | 兩者不能同時存在 |
| 它是**侵入式**的光照引擎重寫，更容易與其他 mod 衝突 | 生電服的 mod 組合通常不少，衝突風險要算進成本 |
| 1.20 之後的後續進展指向 Moonrise | 它的歷史使命已經交接出去 |

所以 `starlight` 的正確用法是：**明確知道自己停在 1.20.4 或更早、且沒有裝 Phosphor 時，才考慮它**。新版本的機器服不必再糾結這一個。

## 四、會改時序，要謹慎：四個模組

這一類是生電服真正要停下來想一想的。它們的共同點是**改變了事件發生的順序或時機**，而機器的正確性往往正建立在那個順序上。

| mod | 風險在哪 |
| --- | --- |
| `lithium` | 覆蓋範圍廣，會動到刷怪、AI、方塊行為等邏輯路徑；"通用最佳化"不等於"對你無害" |
| `krypton` | 改的是網路棧。官方 README 明確聲明：**作者不對其穩定性、與其他 mod 的相容性作任何保證** |
| `c2me-fabric` | 區塊處理多執行緒化，時序與單執行緒不再一樣 |
| `async` | 實體處理並行化（跨多個 CPU 核心與執行緒），實體的處理順序隨之改變 |

逐條說明：

- **`lithium`** 是這一類裡最常被推薦的，也是最容易讓人放鬆警惕的：它被描述為通用最佳化，但"儘量不改變行為"與"絕對不改變行為"是兩回事。**裝之前先在機器上實測**——尤其是那些對刷怪、AI、方塊更新敏感的裝置。
- **`krypton`** 的立場最明確：官方 README 直接寫明不對穩定性與相容性作任何保證。這不是"不能用"，而是"出問題時不要指望作者兜底"。用在公開服上要權衡。
- **`c2me-fabric`** 把區塊處理並行化。多執行緒會改變區塊的載入、生成與解除安裝時機，而**常載入區、機器跨區塊的部分正是最容易因此出問題的地方**。
- **`async`** 把實體處理並行到多個 CPU 核心與執行緒上。實體並行意味著 tick 順序不再逐一開始，依賴實體順序或碰撞時序的機器是最脆的一類。

本節結論：**這四類 mod 的收益是真的，機器失效的風險也是真的，所以只能"先測機器"。**

## 五、生電服裝最佳化 mod 的三條原則

把上面的內容收束成三條可執行的原則：

```
1. 行为无关的优先     —— 内存、启动、分析、预生成先装
2. 改时序的先测机器   —— 一次只加一个，加完就在机器上验证
3. 用 spark 做对比    —— 加之前测一次，加之后测一次，看数据而不是看感觉
```

展開一點：

1. **行為無關的優先**。先把第二節那一組裝上，它們幾乎不會影響機器行為，收益也最直接。很多服的問題到這一步就緩解了大半。
2. **改時序的先測機器**。第四節的四個 mod 不要一次性全上，**一次只加一個**，加完立刻在有代表性的機器上跑一遍——刷怪塔還出貨嗎、機器還按預期工作嗎。出問題就回退這一個，而不是全部推倒。
3. **一次只加一個並用 `spark` 對比**。`spark` 是分析工具，它的價值在於讓你知道"加了之後到底有沒有變快"。**沒有資料支撐的最佳化 mod 都是心理安慰**。

另外兩條維運習慣，和 mod 本身無關但同樣重要：

- 裝 mod 或換 mod 之前**先備份世界**，相關流程見 [備份與恢復](/tutorials/java/backup)。
- 出問題時**先移除最近新加的那個 mod**，這是最快的定位手段。
