伺服器上的插件只會越裝越多。往 `plugins/` 裡丟一個 jar 很容易，麻煩的是後面：某個插件要升級、某個插件出問題要臨時關掉、某個 jar 看起來不太對勁。這一篇講三件事：規範的裝卸流程、熱過載工具的能力邊界，以及怎麼判斷一個插件是不是被人動過手腳。

如果你還沒裝過插件，建議先看 [插件入門](/tutorials/java/plugins)。

## 1. 安裝、更新與解除安裝的規範流程

### 安裝

1. 確認來源可信（見第 5 節），順手記下版本號與下載網址。
2. **停服**。多數插件首次載入並不支援熱載入。
3. 備份 `plugins/` 目錄，見 [備份與恢復](/tutorials/java/backup)。
4. 把 `.jar` 放進 `plugins/`。
5. 啟動服務端並觀察控制台，載入成功與失敗的資訊都列印在這裡。
6. 用 `plugins` 指令確認載入狀態。
7. 再改配置，改完優先用插件自帶的 `reload` 子指令，而不是服務端原版的 `/reload`。

### 更新

更新比安裝更容易出事，因為新版本的配置結構可能已經變了。

| 步驟 | 要點 |
| --- | --- |
| 讀更新日誌 | 確認有沒有配置格式變更、有沒有需要手動遷移的資料 |
| 備份 | 至少備份 `plugins/<plugin-name>/`，涉及資料庫的還要備份資料庫 |
| 留舊 jar | 舊版本先改名為 `.jar.bak` 留著，確認新版正常再刪 |
| 停服替換 | 不要線上覆蓋正在使用的 jar |
| 重啟驗證 | 看控制台，再用 `plugins` 確認狀態 |
| 大版本跳躍 | 跨大版本（如 1.20 升到 1.21）時，插件可能需要先升到中間版本 |

### 解除安裝

解除安裝不只是"把 jar 刪掉"。

1. 停服。
2. 移走 jar。
3. 資料目錄**不要立刻刪**，先重新命名為 `<plugin-name>.bak` 觀察一段時間。
4. 檢查有沒有別的插件把它當前置依賴，有的話一起處理。
5. 清理它在權限插件裡留下的權限節點。
6. 清理它註冊的定時任務、自定義指令、計分板條目。
7. 留意世界裡它留下的自定義物品或方塊，缺失插件時可能報錯。

:::warn 解除安裝不等於清理
刪掉 jar 只解決了"載入"這一步。資料目錄、權限節點、資料庫表、其他插件對它的依賴，都還留在原地。
:::

## 2. 熱過載工具：PlugManX 與 ServerUtils

這類工具通常叫**插件管理插件**：它們能在服務端已經執行的情況下載入、解除安裝、過載別的插件。

### PlugManX

老牌的插件管理工具，前身是 PlugMan，現在由社群維護的 PlugManX 繼續更新。

| 專案 | 資訊 |
| --- | --- |
| 發佈頁 | SpigotMC 資源 88135 |
| 原始碼 | GitHub 上的 Test-Account666/PlugManX（舊版為 ryan-clancy/PlugMan） |
| 常見子指令 | `load`、`unload`、`reload`、`list`、`info`、`check` |
| 典型用法 | `/plugman <subcommand> <plugin-name>` |

具體的子指令名稱和參數會隨版本變化，以插件自帶的幫助資訊為準。

### ServerUtils

| 專案 | 資訊 |
| --- | --- |
| 發佈頁 | SpigotMC 資源 79599、Modrinth |
| 原始碼 | GitHub 上的 frankheijden/serverutils |
| 支援端 | Spigot、BungeeCord、Velocity |

除了插件管理，它還附帶一些服務端狀態檢視之類的工具。因為同時支援代理端，群組服可以在代理層統一管理插件，不必每台後端各裝一套。

### 熱過載的真實邊界

熱過載不是"不用重啟"，它有一批明確的做不到的事：

| 情況 | 能否靠熱過載解決 |
| --- | --- |
| 只是改配置 | 用插件自帶的 `reload` 即可 |
| 臨時停用出問題的插件 | 可以，這是熱過載最有價值的用法 |
| 換插件版本（換 jar） | 不建議，應當停服替換 |
| 插件註冊了指令、權限、監聽器、配方、世界生成器、進度 | 解除安裝後常留殘留，過載容易出錯 |
| 插件直接改服務端內部實現（NMS、反射） | 基本不能 |
| 插件持有資料庫連線、執行緒池或大量靜態快取 | 解除安裝後資源往往不釋放 |
| 反覆載入解除安裝同一個插件 | 類載入器無法回收，記憶體持續上漲，最終 OOM |
| 混合端或模組端 | 插件管理器管不了模組 |
| 服務端原版 `/reload` | 不推薦，容易讓插件狀態錯亂 |

:::warn 生產服不要只靠熱過載
熱過載適合"臨時關掉一個插件看看問題是否消失"和快速試配置。正式的版本更新、依賴變更，仍然應該走停服重啟的流程。
:::

:::tip 排查問題的正確用法
先用插件管理器把最近新裝的插件 `unload` 掉，觀察現象是否消失；確認是它之後再正式停服處理。這比通讀日誌快得多。
:::

## 3. 後門插件的常見特徵

插件是以服務端權限執行的第三方程式碼，一旦被塞了後門，等於把伺服器交到別人手裡。下面這些訊號值得警惕。

| 訊號 | 具體表現 |
| --- | --- |
| 權限與指令異常 | `plugin.yml` 裡聲明了與功能無關的高危指令，比如給自己 OP、執行任意指令、讀寫任意檔案 |
| 程式碼被混淆 | 類名是無意義的單字母或 `a/b/c` 結構；整包被加密，或用自定義類載入器在執行期解密載入 |
| 可疑的執行時呼叫 | 起子行程（`ProcessBuilder`、`Runtime.exec`）、主動外聯（`URL.openConnection`、HTTP 請求）、直接改 `ops.json`、用反射載入遠端類 |
| 偽裝成"更新器" | 聲稱自動更新，實際從作者自己的伺服器下載檔案並覆蓋自身 |
| 來源不明 | 論壇附件、網盤、群檔案裡轉發的 jar |
| "免費的高階插件" | 付費插件被破解重打包，破解者通常順手加了點東西 |
| 與上游不一致 | 插件名和版本號相同，但檔案大小或雜湊對不上，`plugin.yml` 裡的作者與網址被改過 |
| 名字無害的隱蔽配置 | 預設開啟的 `metrics`、`telemetry`、`update-check` 之類選項，實際在往外發資料 |

:::warn 不要只看插件名
後門插件經常直接冒用知名插件的名字和版本號。判斷依據應該是檔案的來源和實際內容，而不是檔名。
:::

## 4. 安全的下載來源

| 渠道 | 風險 |
| --- | --- |
| SpigotMC、Modrinth、Hangar、Bukkit Dev 等主流發佈平台 | 低，優先選擇 |
| 作者自己的 GitHub Releases | 低，注意認準倉庫所有者 |
| 付費插件的官方購買頁 | 低，注意別買成"代購" |
| 聚合下載站、映像站 | 中，可能二次打包，建議核對檔案雜湊 |
| 論壇附件、網盤、群檔案 | 高 |
| 二手交易平台上的"免費高階插件" | 極高，屬於重災區 |

判斷標準其實很簡單：**能不能追溯到作者本人發佈的、可以核對的那個檔案**。一個插件在多少個網站出現過，並不能說明它安全。

:::tip 只裝你需要的東西
插件裝得越少，攻擊面越小，排查也越容易。功能重疊的插件留一個就夠。
:::

## 5. 懷疑某個插件時的排查流程

1. **記錄現象**：什麼時候開始的、控制台報什麼、有沒有玩家回饋異常。
2. **先備份**：在動任何東西之前做一次完整備份，包括 `plugins/` 與世界資料。
3. **列出嫌疑名單**：最近 24 到 72 小時內新增或更新過的插件。
4. **二分定位**：停服，停用一半嫌疑插件，重啟觀察；現象消失就在被停用的那一半裡，否則在另一半裡。
5. **單獨復現**：縮小到單個插件後，用插件管理器只 `unload` 它，確認現象是否重現。
6. **靜態掃描**：按第 6 節的方法掃一遍 jar。
7. **人工看 `plugin.yml`**：核對 `author`、`website`、`main`、`commands`、`permissions`，和官方版本對比。
8. **看類檔案列表**：解開 jar，留意無意義的類名，以及上表中的可疑呼叫。
9. **比對雜湊**：和官方下載的檔案比大小、比雜湊。
10. **確認惡意後進入應急流程**。

應急處理清單：

- 檢查 `ops.json` 與 `whitelist.json` 是否被改動，有沒有陌生帳號拿到 OP。
- 檢查是否有異常登入記錄、陌生的玩家資料檔案。
- 輪換所有憑據：RCON 密碼、面板密碼、資料庫密碼、SSH 金鑰。
- 檢查 `plugins/` 下是否被塞進了別的 jar，服務端核心 jar 與啟動腳本是否被替換。
- 檢查系統層面的計劃任務，確認沒有被人加了自啟項。
- 通讀控制台日誌與插件日誌，找出後門第一次活躍的時間點。
- 視情況通知玩家並回檔，回檔前先保留現場用於分析。

## 6. 用 McGuard 做靜態掃描

McGuard（簡稱 MCG）是一個第三方靜態掃描工具，作者為 huzpsb。它能在**不啟動服務端**的前提下掃描 `plugins/` 下的全部 jar，找出可疑檔案。

### 控制台模式

把 MCG 的 jar 放到服務端根目錄，然後在該目錄執行：

```
java -Xmx1G -jar MCG.jar
```

啟動後會提示選擇模式，通常選 `0`（標準模式）即可，另外還有專家模式與開發者模式。

掃描結果的表現形式是：

| 情況 | 輸出 |
| --- | --- |
| 未檢出異常 | 只列印掃描過程，不輸出結果塊 |
| 檢出異常 | 輸出結果塊，並逐條給出嚴重級別與原因描述 |

原因描述會指明命中的行為類別，例如"可能通過設定權限位獲取 OP"或"可能通過啟動子行程執行遠端指令"。

:::warn MCG 只報告，不處理
它不會修改也不會刪除任何插件，需要你自己手動清理。同時要注意，專家模式用已知惡意程式碼特徵匹配並分析程式碼意圖，覆蓋大多數沒有刻意規避掃描的樣本，但仍然存在誤報。
:::

### 插件模式

MCG 也可以作為 Bukkit/Spigot 插件安裝，在服務端執行期間持續防護。官方對其定位的說明是：這種保護是相對的，極少數惡意插件仍可能繞過行為管控；**不要因為裝了 MCG 就去執行已知含有惡意插件的服務端**。

:::warn 掃描只是最後一道防線
任何掃描工具都不可能消除全部風險，正確做法仍然是從正規渠道獲取插件。如果要執行來源不明的服務端核心，建議先用控制台模式掃描，再在沙箱（如 Sandboxie）之類的隔離環境裡試跑。
:::

## 7. 日常維護建議

- 每個月至少檢查一次插件更新，尤其是跨版本相容與反作弊這類和安全直接相關的插件。
- 維護一份插件清單，記錄名稱、版本、來源、下載網址，出問題時能快速回溯。
- 生產服與測試服分開，新插件先在測試服跑一段時間。
- 不要用 root 或 Administrator 賬戶直接跑服務端行程，給服務端一個最小必要權限的專用賬戶。
- 關注作者倉庫的 issue 與公告，插件被投毒通常會在社群裡先有討論。
