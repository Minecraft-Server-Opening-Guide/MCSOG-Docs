基岩版的最佳化思路和 Java 版幾乎是兩套東西。Java 版有插件、有 `spark`、有幾十個可以調的設定項；官方基岩版服務端（BDS）**能擰的旋鈕很少**，而且不少鍵在不同版本裡連名字都不一樣。所以基岩版"最佳化"的重心在**世界設計**和**硬體**上，而不是在設定檔裡翻找。

本篇只講官方 **BDS**。還沒把服務端跑起來的話，先看 [BDS 服務端](/tutorials/bedrock/bds)。如果你用的是第三方核心，可以直接跳到第 7 節。

## 1. 基岩版的效能模型和 Java 版不一樣

| 對比項 | Java 版（Paper 等） | 基岩版（官方 BDS） |
| --- | --- | --- |
| 世界模擬 | 主執行緒 tick，但核心提供大量最佳化開關 | 世界模擬基本壓在**單個執行緒**上，核多幫不上太多忙 |
| 插件生態 | 極其豐富，很多最佳化靠插件完成 | 官方服務端**不支援插件**，替代品是附加包與腳本 API |
| 可調參數 | 核心配置加插件配置，幾十項 | `server.properties` 裡與效能相關的只有寥寥幾項 |
| 記憶體控制 | 用 `-Xmx` / `-Xms` 自己指定 | **沒有記憶體參數**，由程式自己向作業系統申請 |
| 分析工具 | `spark` 火焰圖、各種 profiler | **沒有 `spark`**，也沒有成熟的火焰圖流程 |
| 熱過載 | 部分場景可以 | 不支援 `/reload`，改配置只能重啟 |

最關鍵的一條是**單核主頻決定上限**：

- 世界模擬跑在一個執行緒上，多出來的核心主要分擔網路、存檔寫入等外圍工作；
- 所以"16 核 2.0 GHz"的機器通常跑不過"4 核 4.5 GHz"的機器；
- 選機器時先看單核效能，再看核數。
:::warn Java 版的最佳化經驗不能照搬
下面這些東西在 BDS 上**都不存在**，不要照著 Java 教學做：

- `spark` 火焰圖（不支援 BDS，詳見第 8 節）；
- Paper / Spigot 的 `paper.yml`、`spigot.yml` 那套配置；
- 實體啟用範圍、刷怪上限、每 tick 實體數之類的插件或核心開關；
- 最佳化類插件（官方服務端沒有插件系統）。

能照搬的只有**概念**：減少同時載入的區塊、減少實體、減少高頻紅石。
:::

## 2. 能調的：`server.properties`
:::warn 有哪些鍵、預設值是多少，隨 BDS 版本變化
不同 BDS 版本裡，`server.properties` 的**鍵名、取值範圍、預設值都可能不同**：有的鍵是後來才加入的，有的鍵在某個版本被改名或被拆成多個鍵（移動校驗那一組就是典型例子）。

所以本文只解釋這些鍵**在做什麼**、調它要付什麼代價。**請開啟你自己伺服器目錄下的 `server.properties` 逐項核對**：官方生成的預設檔案裡，每個鍵上方都有一行註釋，寫明它的含義、允許範圍和預設值，那才是對你這個版本最準確的說法。
:::

### 2.1 主要效能鍵

| 鍵 | 作用 | 調低的代價 | 建議方向 |
| --- | --- | --- | --- |
| `view-distance` | 服務端向玩家傳送多遠的區塊資料，也就是"玩家能看多遠"（官方預設 32，範圍下限 5） | 遠處發霧、地形"跳出來"，觀感變差 | **優先動的一項**：玩家裝置普遍一般或頻寬緊張時往下調 |
| `tick-distance` | 玩家周圍多遠的區塊**真正參與運算**（刷怪、作物、紅石、流體）（官方預設 4，範圍 4-12） | 遠處的機器、農場、紅石電路可能停擺 | 比視距更直接地影響 CPU；沒有"遠距離機器"需求時保持較小值 |
| `max-threads` | 服務端最多嘗試使用多少執行緒（官方預設 8，0 表示不限制；有的版本裡刪除該鍵亦同） | 調得過低可能讓網路、存檔等外圍任務排隊 | **它不會把世界模擬拆到多核**；調高不等於更快，先保持預設 |
| `player-idle-timeout` | 玩家掛機多少分鐘後被踢出 | 掛機玩家會更早掉線，影響掛機需求 | 接近零成本的減負手段，按你的掛機規則定 |
| `compression-threshold` | 多大的網路包才開始壓縮 | 調低表示壓縮更多包，**更吃 CPU**、更省頻寬 | 先看瓶頸在哪：頻寬緊張就調低，CPU 緊張就調高 |
| `compression-algorithm` | 網路壓縮演算法（常見為 `zlib` / `snappy` 這類選項） | 換成壓縮率更低的演算法，等於用頻寬換 CPU | 頻寬充足選更快的演算法，頻寬緊張選壓縮率更高的 |

關於這幾項，有三點要說清楚：

1. `view-distance` 和 `tick-distance` 是**兩件事**：前者決定"看不看得見"，後者決定"跑不跑運算"。降視距主要影響觀感，降模擬距離會影響機器。
2. `max-threads` 是**執行緒上限**，不是"並行世界模擬的開關"。把它調大不會讓單核瓶頸消失。
3. `player-idle-timeout` 是少數**幾乎沒有副作用**的減負項：踢掉掛機玩家就少載入區塊、少算實體。

### 2.2 與移動校驗、反作弊相關的鍵

這些鍵**不是效能開關**，但經常被當成"最佳化項"去調，所以單獨說明：

| 鍵 | 作用 | 放寬校驗的代價 | 建議方向 |
| --- | --- | --- | --- |
| `server-authoritative-movement`（部分版本） | 服務端權威移動，取值為幾種校驗模式之一，越靠服務端權威越嚴格 | 放寬等於位置糾正變少，但**作弊空間變大** | 公開服保持預設或更嚴格 |
| `server-authoritative-movement-strict`（部分版本） | 更嚴格地校驗玩家位置，糾正更頻繁 | 關掉等於抖動變少，但穿牆、瞬移更難發現 | 不要為了"省效能"關掉 |
| `player-position-acceptance-threshold` | 客戶端與服務端位置的**容忍度** | 調低表示糾正更頻繁，高延遲玩家更容易被"拉回" | 只在高延遲普遍、玩家頻繁被拉回時小幅放寬，並清楚這是安全取捨 |
:::warn 別把反作弊當成效能開關
位置糾正確實有網路開銷，但它換來的是"玩家不能隨便瞬移"。為了省一點點 CPU 或頻寬去放寬校驗，是典型的得不償失。只有在**延遲普遍很高、玩家頻繁被拉回**時，才考慮小幅調整，並且要明白你在拿什麼換什麼。
:::

### 2.3 其他可能存在的鍵

不同版本裡還能看到一些與效能沾邊的鍵，例如：

- 把**可視區塊生成**下放給客戶端的開關：服務端少幹一點活，代價是低配客戶端更卡；
- 附加包與腳本的**內容日誌**和**看門狗**相關鍵：用來發現腳本報錯、腳本跑得太慢、記憶體超限。

它們**是否存在、叫什麼、預設值是多少都隨版本變化**，這裡不給出具體鍵名與數值，請以你本地檔案與官方文件為準。使用前先確認你的版本確實有這些鍵，不要照抄網上其他版本的配置。

### 2.4 一份示例片段

```properties
# 视距：先往下调，观察观感与 CPU 变化
view-distance=12

# 模拟距离：没有远距离机器需求就保持较小值
tick-distance=4

# 线程上限：保持默认，不要当成提速开关
max-threads=8

# 挂机踢出：按你的挂机规则定
player-idle-timeout=15

# 压缩：带宽紧张用默认，CPU 紧张可调高阈值
compression-threshold=1
compression-algorithm=zlib
```

上面這些數值**只是示例**，既不是預設值也不是推薦值。請對照你本地檔案裡的註釋，改成適合你的值。
:::note 改完必須重啟
BDS 不支援 `/reload`。改完 `server.properties` 要用控制台正常 `stop` 再啟動，不要直接殺行程。
:::

## 3. 真正的大頭：世界設計

在基岩版上，**你能配置的東西很少，但你能建的東西很多**。絕大多數"伺服器卡"最後都能歸到地圖上：

| 負載來源 | 處理方向 |
| --- | --- |
| 同時載入的區塊太多 | 降低 `view-distance` 與 `tick-distance`，把常載入區域（ticking area）用到最少 |
| 常載入機器太多 | 每座"沒人在也要跑"的機器都在持續吃 CPU，不需要的拆掉或停掉 |
| 紅石時鐘一直跑 | 高頻時鐘是典型負載來源，能用低頻方案就別用高頻 |
| 實體太多 | 生物、掉落物、礦車堆積；控制農場規模，及時收集或清理掉落物 |
| 農場太大 | 產量遠超需求的農場是純負擔，縮小規模或按需開啟 |
| 掉落物堆積 | 收集與銷毀設計不當會讓實體長期留存 |

幾點說明：

- **常載入區域（ticking area）**讓指定區塊在沒有玩家時也持續運算。它很方便，但每個區域都在持續消耗 CPU，**用完就刪**。
- **實體堆積**有個典型症狀：CPU 總佔用看起來不高，但整個伺服器就是卡。這時要處理的是實體數量與複雜區塊，而不是再找一個參數。
- **做減法優先**：拆掉三座不用的農場，通常比調十遍設定檔更有效。
:::tip 先做減法，再談參數
在基岩版上，"最佳化"的第一手段是**少建、少跑、少載入**。參數只能在很小的範圍裡幫忙。
:::

實體與掉落物的排查思路可以看 [實體與掉落物堆積導致的卡頓](/tutorials/faq/entity-lag)。需要提醒的是：**那篇裡的診斷工具是 Java 版的**（例如 `spark`、TPS 與 MSPT 指標），基岩版用不了；但**"少實體、少掉落物、少常載入機器"的設計原則是通用的**，可以直接借鑑。

### 3.1 常載入區域與"離線機器"

常載入區域（ticking area）是基岩版少見的雙刃劍：

- **好處**：沒有玩家在場時，指定區塊裡的紅石、流體、作物、生物仍會照常運算，機器可以離線產出；
- **代價**：這些區塊會**一直**佔用主執行緒時間，和有沒有玩家線上無關；
- **建議**：只給真正需要的區域開，事情做完就刪；能改成"有人時再跑"的機器就不要常載入。

排查時先問自己三個問題：這座機器還需要嗎？它必須在沒人時也跑嗎？它的產出真的用得上嗎？三個問題裡只要有一個答"不"，就該關掉它。

## 4. 區塊、世界大小與預生成

視距和世界規模是兩筆不同的賬：

- **視距的賬**：`view-distance` 越大，每個玩家進服、移動、跨區域時要下發的區塊資料越多，CPU 與頻寬一起上漲。它是最大的 CPU 與頻寬槓桿，同時也是玩家最能直接感受到的觀感項。
- **世界大小的賬**：玩家探索過的區域都會寫進存檔。世界越大、越老，`worlds/` 目錄越大，**啟動、儲存、備份都變慢**，磁碟 I/O 壓力也更大。

能做的事情：

1. **限制活動範圍**：用"世界邊界"的思路把玩家集中在需要玩的區域，而不是讓世界無限擴張。你的版本或核心是否提供現成的邊界指令、怎麼用，請以官方文件為準。
2. **不鼓勵無目的遠行**：跑圖本身就會不斷生成新區塊，而新區塊生成是卡頓的常見來源。
3. **保持出生點整潔**：出生點附近通常是載入最頻繁的區域，建築、實體、紅石越少越好。
4. **定期歸檔舊區域**：不再使用的世界或區域及時清理，操作前**先備份**。

關於**預生成**，要說實話：**官方 BDS 沒有提供預生成工具**，可選手段比 Java 版少得多。

| 手段 | 官方 BDS 是否支援 | 說明 |
| --- | --- | --- |
| 內建預生成指令 | 不支援 | 官方服務端沒有這類指令 |
| 管理員提前跑圖 | 支援（就是普通遊戲行為） | 最穩、零依賴，缺點是耗時 |
| 常載入區域 | 支援 | 解決的是"沒人在場也要運算"，**不是**預生成，而且持續消耗效能 |
| Java 版工具（如 Chunky） | 不支援 BDS | 這類工具面向的是 Java 版服務端與模組平台 |
| 第三方預生成工具 | 不在官方能力範圍內 | 用之前確認它支援你的 BDS 版本，並**先備份世界** |
:::warn 不要相信"基岩版一鍵預生成"
網上能看到的基岩版"預生成插件或工具"，大多屬於第三方核心或社群工具，**不屬於官方 BDS 的能力範圍**。要用就以它自己的官方文件為準，不要按本文或別的版本的說明去猜。
:::

基岩版的預生成手段有限，能靠的主要是**提前跑圖**和**控制世界規模**。

## 5. 記憶體行為

基岩版的記憶體行為和 Java 版完全不同：

- **沒有記憶體參數**。BDS 沒有 `-Xmx` 這類開關，初始與最大記憶體由程式自己向作業系統申請，你無法在啟動參數裡指定。
- **佔用會隨時間緩慢上升**。長時間執行後明顯高於剛啟動時，這是普遍觀察到的現象。
- **不要強行清理記憶體**。用"記憶體清理""強制釋放"類工具去壓佔用，會導致**玩家下載資源包或附加包時進度條卡住**，還可能讓服務端變得不穩定。**重啟才是解法**，這一點與 [BDS 服務端](/tutorials/bedrock/bds) 裡的說明一致。

正確做法是**安排定時重啟**：

| 做法 | 說明 |
| --- | --- |
| 定時重啟 | 在低峰期重啟一次，把長期累積的記憶體交還給系統 |
| 重啟週期 | **沒有官方推薦值**，是判斷題：看你的玩家數、世界大小、附加包數量與記憶體增長曲線。每天一次、每幾天一次都有人用 |
| 優雅停止 | 用控制台 `stop` 正常關服再啟動，避免存檔與統計檔案損壞 |
| 提前公告 | **重啟前在遊戲內和群裡通知玩家**，並留出緩衝時間，避免玩家正在跑圖或對戰時被突然踢下線 |
:::tip 重啟間隔怎麼定
不要照抄別人的"每天重啟三次"。先記錄幾天：啟動後多久記憶體漲到機器吃不消、玩傢什麼時候最多。**玩家多、附加包多，間隔就短一些；小服、附加包少，間隔可以長一些。**
:::

## 6. 硬體與託管選擇

基岩版硬體的第一原則還是**單核效能優先**：

| 優先順序 | 專案 | 為什麼 |
| --- | --- | --- |
| 1 | 單核主頻與單核效能 | 世界模擬在單執行緒上，弱單核直接決定卡不卡 |
| 2 | SSD 或 NVMe | 區塊讀寫、存檔儲存、備份都是磁碟 I/O，機械盤與網路儲存會明顯拖慢 |
| 3 | 記憶體容量 | 要留足餘量；玩家、世界、附加包越多，需要越多 |
| 4 | 核數 | 有用，但排在上面三項之後 |

為什麼"便宜的 VPS 會莫名其妙地卡"：

- 便宜套餐常見的是**低主頻、多核、超售共享**的 CPU。BDS 吃單核，而共享 CPU 會被鄰居擠佔，於是出現週期性卡頓與延遲抖動；
- "突發效能"型實例平時看起來空閒，一旦 CPU 額度耗盡就整體變慢；
- 機械盤或網路儲存讓區塊讀寫變慢，玩家跑圖時最容易體現出來；
- 記憶體不足時系統開始換頁，表現就是"整服一頓一頓"。
:::warn 容器與虛擬化會額外搶 CPU
如果你把 BDS 放進容器或虛擬機器裡跑，**CPU 限額（limit / quota）可能把 BDS 餓死**：單核跑滿時被限流，表現就是週期性"卡一下"。請給足 CPU 份額，並避免和別的重負載服務擠在同一台機器上。用 Docker 部署的細節見 [用 Docker 部署基岩版服務端](/tutorials/bedrock/docker)。
:::

### 6.1 託管選擇速查

| 你的情況 | 建議 |
| --- | --- |
| 玩家不多、預算有限 | 一台單核強的機器，通常比多核超售的 VPS 更穩 |
| 需要長期線上、有固定玩家 | 選明確標註 CPU 主頻、不超售的套餐，先小規模試跑再擴充 |
| 用容器部署 | 給足 CPU 份額，避免與重負載服務同機，注意埠與資料卷，見 [用 Docker 部署基岩版服務端](/tutorials/bedrock/docker) |
| 想要插件生態 | 那就不是 BDS 的路線了，先看第 7 節 |

## 7. 第三方核心的效能差異

如果你要的是插件與多核，那走的就不是 BDS 這條路：

| 核心 | 語言 | 效能特點 |
| --- | --- | --- |
| Nukkit 系（含 PowerNukkitX） | Java | 主打多核與最佳化，有插件系統與大量可調項 |
| PocketMine-MP | PHP | 插件生態最大，但高負載下瓶頸明顯，解釋型語言本身有開銷 |

它們的效能模型、設定項和可用工具都與 BDS 不同，**最佳化經驗不能互相套用**。例如 `spark` 支援 Nukkit，但**不支援 BDS**；把 PMMP 或 Nukkit 的調優文章照搬到 BDS 上，通常只會白忙。
:::warn 先確認你要的是哪條路
選 BDS 就是"官方、穩定、可調項少"；選第三方核心就是"插件多、可調項多、但不是官方實現"。想了解它們的取捨與上手，見 [第三方核心（Nukkit / PNX / PMMP）](/tutorials/bedrock/third-party) 與 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup)。
:::

## 8. 怎麼測量

先說清楚：**基岩版沒有 `spark`**。`spark` 支援的是 Java 版的一系列平台與部分社群平台，**Bedrock Dedicated Server 不在其中**。所以在 BDS 上不要指望火焰圖，也不要照搬 Java 版"看 TPS 與 MSPT"的那套流程。

能用的手段：

| 手段 | 怎麼用 |
| --- | --- |
| 宿主級監控 | 看 CPU（尤其**單核佔用**）、記憶體、磁碟 I/O、網路頻寬。做法見 [監控與告警](/tutorials/ops/monitoring) |
| BDS 控制台輸出 | 看啟動與關閉資訊、報錯、附加包與腳本相關的告警 |
| 玩家回饋 | "什麼時候卡、幾個人線上、在哪片區域卡"往往比任何指標都直接 |
| 改動前後對比 | 一次只改一項，記錄改前與改後的 CPU 佔用和玩家感受 |
:::note 一次只改一項
沒有火焰圖，唯一可靠的辦法就是**控制變數**：改一項，觀察一段可比的時間，記錄，再改下一項。一次改五項，你永遠不知道是哪一項起了作用，或者起了反作用。
:::

測量紀律，建議照這個來：

1. **一次只改一個變數**，其他保持不變；
2. **在可比的時間段測量**：同一時段、相近線上人數、相近玩法（例如都在跑圖，或者都在掛機）；
3. **記錄到日誌裡**：改了什麼、什麼時候改的、改前改後的指標與玩家感受；
4. **觀察足夠長**：區塊生成、記憶體增長這類現象需要時間才能看出來，改完立刻下結論容易誤判。

宿主級記錄的一個簡單例子（Linux，僅示意）：

```bash
# 每 5 秒采样一次整体与各核负载，便于发现"总占用不高但单核跑满"
top -b -d 5 -n 60 > cpu-sample.log
```

Windows 上可以用工作管理員或效能監視器看同樣的東西，**重點是單核曲線，而不是總佔用**。

## 9. 調優順序

按這個順序做，價效比最高；順序反了容易白花錢：

1. **世界設計**：先做減法，少載入、少常載入機器、停掉不需要的農場、剋制紅石時鐘、控制實體與掉落物。收益最大且不花錢。
2. **視距與模擬距離**：調 `view-distance`、`tick-distance`、`player-idle-timeout` 以及壓縮相關鍵。幾乎免費、立竿見影。
3. **硬體**：單核效能優先，其次記憶體、SSD、核數。花錢但有效。
4. **重啟計劃**：定一個適合你的重啟週期並提前公告。治標，但能解決長期記憶體累積。
5. **換核心**：只有前四項都做完、你確實需要插件或多核時，才考慮 Nukkit 系或 PMMP。

### 9.1 收尾檢查表

| # | 檢查項 | 完成標準 |
| --- | --- | --- |
| 1 | 確認版本裡有哪些鍵 | 開啟本地 `server.properties`，逐項核對過鍵名與預設值 |
| 2 | 世界設計 | 不用的農場與機器已停，常載入區域已清理，高頻紅石已收斂 |
| 3 | 視距與模擬距離 | `view-distance` 與 `tick-distance` 已按玩家裝置與頻寬調整，且沒有破壞機器 |
| 4 | 掛機與壓縮 | `player-idle-timeout` 已設，壓縮相關鍵已按瓶頸方向調過 |
| 5 | 硬體 | 單核效能與磁碟 I/O 是瓶頸時優先解決；容器有足夠 CPU 份額 |
| 6 | 重啟計劃 | 有周期、有公告、用 `stop` 優雅關服 |
| 7 | 測量記錄 | 每次改動都有改前與改後的記錄，且一次只改一項 |
| 8 | 反作弊 | 沒有為了省效能而放寬移動校驗，或者已明確接受風險 |

基岩版最佳化說到底就三句話：**單核主頻決定上限，世界設計決定下限，定時重啟決定長期穩定。**
