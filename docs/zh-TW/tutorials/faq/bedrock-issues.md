基岩版開服遇到的"起不來 / 連不上 / 能進但不對"，現象經常長得很像：玩家那頭只會說一句"進不去"，而服務端這頭可能連行程都沒起來。這一篇是 [[BE] 常見問題](/tutorials/faq/faq-be) 的深入版，按"先分類、再定位"的順序展開，把每一步的判據儘量寫清楚。
:::tip 這一篇怎麼用
先看第 1 節的分類表，判斷自己遇到的是哪一類，再直接跳到對應章節。第 5 節給了一條從零開始的完整排查順序；第 6 節講求助時該提供哪些資訊。
:::

## 1. 先分類：連不上 / 起不來 / 能進但異常

分類的判據是：**服務端行程到底有沒有在跑、有沒有在監聽埠？**

| 現象 | 屬於哪一類 | 去看哪一節 |
| --- | --- | --- |
| 啟動器視窗一閃而過，或命令列立刻回到提示符 | 起不來 | 第 2 節 |
| 控制台刷出報錯，行程根本沒起來 | 起不來 | 第 2 節 |
| 行程在跑、控制台也正常，但玩家連不上 | 連不上 | 第 3 節 |
| 玩家能進，但卡頓、存檔異常、權限不對 | 能進但異常 | 第 4 節 |
| 一部分玩家能進、另一部分不能 | 連不上 | 第 3 節（先查協議版本與客戶端平台） |
| 埠檢測工具說"通過"，玩家還是進不去 | 連不上 | 第 3.2 節（多半是工具只測了 TCP） |
| 昨天還好，今天所有人都進不來 | 連不上 | 第 3.1 節（客戶端自動更新換了協議） |
| 服務端能起來，但玩幾分鐘就自己退出 | 能進但異常 | 第 4.1、4.2 節 |
:::note 先確認行程狀態，再談其他
"連不上"和"起不來"的排查路徑完全不同。第一步永遠是確認行程還在、還在監聽埠（第 5 節）。跳過這一步，後面所有判斷都只是猜。
:::

## 2. 服務端起不來（BDS 與第三方核心）

### 2.1 BDS：架構、執行庫與系統要求

BDS 是**原生編譯**的程式，不是腳本，所以它挑系統和執行庫。

| 專案 | 要求 | 說明 |
| --- | --- | --- |
| 架構 | **x86-64** | 官方只提供 Windows 與 Linux 的 x86-64 構建；ARM 裝置（如樹莓派）不在官方支援範圍內 |
| Windows | Windows 10 10.0.15063 及以上，或 Windows Server 2016 及以上 | 同時需要 **Microsoft Visual C++ 執行庫**（VC++ Redistributable） |
| Linux | 官方只支援 **Ubuntu 22.04 及以上** | 其他 x86-64 發行版只要庫齊全也能跑，其中包含 **glibc 2.35 或更高** |
| 記憶體 | 最低 4 GB | 玩家超過 10 人時通常需要更多；磁碟建議預留 1 GB |

關於執行庫缺失的典型表現：Windows 上 BDS 依賴 Microsoft Visual C++ 執行庫，**缺失時通常是啟動瞬間報缺少某個 DLL，或者視窗一閃就退出**，控制台裡往往什麼都沒有；Linux 上 glibc 版本偏低時，常見的是**動態庫載入失敗**（`error while loading shared libraries` 一類）。具體要求的執行庫與 libc 版本請以 **BDS 官方下載頁與 release notes** 為準，不要照抄第三方教學裡的版本號。
:::warn BDS 不能像 Java 版那樣指定記憶體
Java 版可以靠 `-Xms` / `-Xmx` 控制堆大小，**BDS 沒有對應的啟動參數**。它自己管理記憶體，你只能通過限制世界規模、實體數量和玩家數量來間接控制佔用。所以"給 BDS 加記憶體參數"這類建議是無效的。
:::

### 2.2 Linux：執行權限與工作目錄

Linux 下兩個最常見的"起不來"原因，都是操作層面的。**一是沒有執行權限**——從壓縮包解出來的 `bedrock_server` 預設不帶 `+x`：

```bash
chmod +x bedrock_server
```

**二是工作目錄不對**——BDS 的官方用法就是**在自己的目錄裡執行**，並讓動態庫搜尋路徑指向當前目錄：

```bash
cd /opt/bedrock-server
LD_LIBRARY_PATH=. ./bedrock_server
```

BDS 的**資料全部儲存在工作目錄裡**，並且它期望解壓出來的初始檔案就在那裡。所以：用 systemd 或其他方式拉起時，務必設定 `WorkingDirectory`，否則行程的工作目錄可能是 `/`；從別的目錄執行二進位制，輕則在錯誤的目錄裡憑空生成一套新的設定檔與世界，重則因為找不到同目錄的庫直接啟動失敗。還要注意 `LD_LIBRARY_PATH=.` 裡的 `.` 指的是**當前工作目錄**，不是二進位制所在目錄。
:::tip 排查"起不來"的第一條指令
在服務端目錄裡手動跑一次 `LD_LIBRARY_PATH=. ./bedrock_server`，把報錯原樣看完。很多問題在這一步就會暴露出來，比翻日誌快得多。
:::

### 2.3 改名與路徑的坑

BDS 的主程式可以改名，但**不建議**。改名之後，所有引用它的地方都要同步改：啟動腳本（`.bat` / `.sh`）、桌面快捷方式、面板或守護行程裡配置的啟動指令，以及第 2.2 節裡那條 `LD_LIBRARY_PATH=. ./bedrock_server` 指令本身。漏掉任何一處，結果就是"點了沒反應"或者"報找不到檔案"。如果已經改了名又起不來，先改回原名驗證，再決定是否要逐處修改。

同樣容易出問題的是**路徑本身**：服務端目錄建議放在純英文、無空格、無特殊符號的路徑下。中文路徑在部分面板和啟動腳本上會導致讀取失敗，而且報錯通常很難懂。

### 2.4 Nukkit 系：Java 版本與構建對齊

Nukkit 系（Nukkit / PowerNukkitX 等）是 **Java** 程式，兩個點要確認：

- **Java 版本夠不夠**：新分支通常要求較新的 Java，裝太舊會在啟動瞬間丟擲 `UnsupportedClassVersionError` 一類的錯誤，報錯裡一般會直接寫出它需要的版本，**以該核心的官方文件為準**。
- **位數對不對**：64 位系統必須配 64 位 Java。32 位 Java 會因為記憶體上限在啟動或執行中途崩掉。

更隱蔽的是**構建與協議版本對不上**：核心構建本身能啟動，但客戶端連不上，或者提示伺服器版本過舊。這一層請先看 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup)，那裡有完整的版本對齊說明。

### 2.5 PocketMine-MP：PHP 版本與擴充

PMMP 是 **PHP** 程式，它的官方要求是：**64 位 CPU + 64 位作業系統**，記憶體 1 GB 起；雙核及以上只是**推薦**而非硬性要求；官方儘量支援 Windows、Linux、macOS，原則上任何能跑 64 位 PHP 且擴充齊全的平台都可以。

兩個最容易踩的坑：**PHP 版本與擴充**——PMMP 需要特定版本的 PHP 以及一組擴充，版本不對或擴充沒載入，啟動時就會報錯，常見的一類是某個 PHP 擴充載入失敗（例如 `opcache`）；**具體需要哪些擴充、最低 PHP 版本是多少，以 PMMP 官方文件的 Setup requirements 為準**。**不要隨手用系統自帶的 PHP**——發行版倉庫裡的 PHP 往往版本偏舊、擴充不全，Windows 上也可能裝著別的軟體留下的 PHP；PMMP 官方提供了**為各系統打包好的 PHP 執行時**（在其發佈頁按作業系統取對應檔案），解壓即用。**推薦使用官方打包的 PHP，而不是任意的系統 PHP。**
:::warn 先確認你調的是哪一個 PHP
執行 `php -v`，確認輸出裡是你打算用的那個版本和位數。啟動腳本裡如果寫的是裸 `php`，它走的是 `PATH` 裡的第一個，很可能不是你裝的那個。
:::

### 2.6 埠被佔用

埠衝突的表現是：行程啟動後立刻退出，控制台提示無法繫結（bind）埠。

有一個**基岩版特有的坑**：`server.properties` 裡的 `enable-lan-visibility` 預設開啟，作用是響應區域網路裡尋找伺服器的客戶端。開啟時，**即使你把 `server-port` / `server-portv6` 改成了別的值，服務端仍然會去繫結預設的 19132 / 19133**。所以同一台機器上開第二個基岩服時，即使改了埠也可能衝突；如果不需要區域網路發現，可以關掉這個選項來避開，具體行為以官方文件為準。另外注意 `server-port` 的合法範圍是 **1–65535** 的整數。

### 2.7 server.properties 寫法錯誤

Bedrock 的 `server.properties` 是**逐行的 `键=值` 文本**，`#` 開頭的行為註釋。寫錯類型或超出範圍的取值，可能導致啟動失敗，或者該選項被忽略而"改了沒生效"。幾個已經確認的合法取值可以直接對照：

```properties
server-port=19132
server-portv6=19133
allow-list=true
gamemode=survival
difficulty=easy
default-player-permission-level=member
tick-distance=4
view-distance=32
max-players=10
compression-algorithm=zlib
```

| 鍵 | 合法值 / 範圍 |
| --- | --- |
| `server-port` / `server-portv6` | 1–65535 的整數 |
| `allow-list` | `true` / `false` |
| `gamemode` | `survival` / `creative` / `adventure` |
| `difficulty` | `peaceful` / `easy` / `normal` / `hard` |
| `default-player-permission-level` | `visitor` / `member` / `operator` |
| `tick-distance` | 4–12 的整數 |
| `view-distance` | 大於等於 5 的整數 |
| `max-players` | 正整數 |
| `compression-algorithm` | `zlib` / `snappy` |
:::warn 編輯前先備份，編輯時用純文字編輯器
用記事本一類的**純文字編輯器**改，不要用會插入格式的編輯器（比如帶富文本的辦公軟體），否則會寫入不可見字元導致解析失敗。改之前先複製一份 `server.properties`。某個值到底允許什麼，**以官方文件為準**。
:::

## 3. 連不上（cannot connect）

### 3.1 協議 / 版本不匹配

這是基岩版**最常見**的連不上原因，而且玩家側幾乎沒有自救空間：應用商店預設自動更新，客戶端一更新協議就變。這一層不在這裡重複展開，直接看 [協議版本與版本選擇](/tutorials/bedrock/protocol)。要點只有兩條：客戶端協議必須與服務端協議**一致**才能進服；iOS 玩家只能裝商店最新版，所以"讓玩家降級"這條路對 iOS 群體是堵死的。客戶端版本與服務端版本不一致時，玩家會看到"過舊的伺服器"一類的提示，**具體提示文案以官方為準**。

### 3.2 UDP 與 TCP：埠、防火牆、安全組

基岩版**走 UDP**，這一點和 Java 版完全不同，也是"埠檢測通過但玩家進不來"的頭號原因。

| 專案 | 值 |
| --- | --- |
| 預設 IPv4 埠 | **19132 / UDP** |
| 預設 IPv6 埠 | **19133 / UDP** |
| 需要放行的位置 | 系統防火牆 **和** 雲安全組，兩處都要 |
| 路由器埠轉發 | 協議必須選 **UDP**；若只能選 TCP，則需要另建 UDP 規則 |
:::warn 只測 TCP 的工具會騙你
很多線上"埠檢測"工具預設只探測 TCP。TCP 埠通不代表 UDP 埠通。確認基岩版埠時，一定要明確測的是 **UDP**。
:::

另外，多數內網穿透服務預設只支援 TCP，選方案時要確認它支援 **UDP**。跨端（讓手機 / 基岩版玩家進 Java 服，或反過來）的場景見 [手機玩家支援](/tutorials/java/mobile)。

### 3.3 CGNAT / 沒有公網 IPv4 / 雙重 NAT

服務端跑得好好的、防火牆也放行了，外部還是連不上，問題往往在運營商那一側。

| 情況 | 判斷 | 處理方向 |
| --- | --- | --- |
| 路由器 WAN 口拿到的是**私有位址或共享位址**（CGNAT） | 你沒有獨佔的公網 IPv4，埠轉發無處可轉 | 找運營商申請公網 IP，或改用支援 UDP 的隧道 / 虛擬區域網路方案 |
| **雙重 NAT**：光貓後面又接了一台路由器 | 轉發只做在其中一台上，鏈路斷在中間 | 轉發必須做在**直接連到 Internet 的那台**裝置上，並把下一跳的轉發串起來 |
| 公網 IP 是動態的 | 位址會變，玩家記不住 | 用動態網域服務，或改用隧道方案 |
| 只有 IPv6 公網 | 部分玩家網路不支援 IPv6 | 同時確認 IPv4 側的可達性 |

在無法做埠轉發時，一個常見替代方案是**虛擬區域網路**：讓服務端和玩家加入同一個虛擬網路，然後玩家用虛擬網路的 IP 連線。社群裡常用的有 ZeroTier、Radmin VPN、Hamachi 等，具體配置見各自的官方文件。

### 3.4 區域網路發現 vs 用 IP 連線

這兩種連線方式走的路徑不一樣，症狀也不一樣。

| | 區域網路發現 | 用 IP / 網域連線 |
| --- | --- | --- |
| 玩家需要做什麼 | 什麼都不用做，伺服器會出現在"遊戲"介面頂部 | 手動新增伺服器，填位址和埠 |
| 前提 | 雙方在同一區域網路內 | 服務端對外可達（埠轉發或隧道） |
| 受什麼影響 | `enable-lan-visibility`、UDP 19132/19133 是否可用 | 公網 IP、防火牆、安全組、隧道 |

幾個容易忽略的點：**基岩版必須顯式指定埠**，它不像 Java 版那樣支援靠 SRV 記錄省略埠，所以位址列和埠欄都要填對；區域網路發現依賴廣播 / 多播，在部分虛擬網路、容器網路或跨網段的網路裡不工作，這時只能改用 IP 連線；在**同一台機器上連線自己**可能因為迴環或防火牆規則失敗，換一台裝置測試可以快速區分是"服務端不可達"還是"這台機器自己的問題"。

### 3.5 主機平台（Xbox / PlayStation / Switch）

主機平台**不能在遊戲裡直接輸入 IP 加入伺服器**。常見的兩條路是：**自定義 DNS**（把網域解析指到你的伺服器，讓主機通過網域方式加入），以及**區域網路**（讓主機和服務端處在同一區域網路內，用區域網路發現加入）。
:::note 平台策略會變，且各平台不一樣
主機側的限制**隨平台政策與版本變化**。有資料指出主機版本整體上更傾向只能走區域網路，其中 Switch 的可選範圍更窄（可能僅限 Realms / 官方推薦伺服器）。**具體某個平台當前支援什麼，以官方文件與平台說明為準**，不要照搬舊教學。
:::

### 3.6 客戶端側的檢查

先排除最廉價的可能性，再動服務端：**位址格式**上，位址列只填 IP 或網域，**埠填到埠欄**，把 `ip:port` 整體塞進位址列在部分版本上會解析失敗；**埠**預設 19132，服務端改過埠玩家那也要改；**是不是同一個版本**——基岩版客戶端**不能**直接進 Java 版伺服器（反之亦然），跨端要靠額外方案，見 [手機玩家支援](/tutorials/java/mobile)；**客戶端版本必須與服務端版本相同**，基岩版不支援舊版本客戶端連新版服務端。最後**換一台裝置、換一個網路試**，能立刻區分是服務端問題、玩家網路問題，還是玩家裝置問題。

### 3.7 第三方核心的特有情況

第三方核心**不一定實現了官方服務端的全部協議特性與遊戲內容**，所以"同樣的客戶端，進官方服正常、進我的服就不對"是正常現象，不一定是配置錯誤。以 PocketMine-MP 為例，官方文件明確說明：PMMP 並**沒有**實現 Minecraft 的全部玩法特性，原因是開發者業餘維護、難以跟上官方更新速度；在撰寫時缺失的特性包括**生物（mobs）、紅石、礦車和維度**。

另一個要點是**核心構建與協議版本的對齊**：核心向客戶端報告的版本必須被客戶端接受，否則玩家會看到"伺服器版本過舊"一類的提示。PMMP 官方 FAQ 的處理方式是：在服務端控制台執行 `version` 指令，檢視當前核心支援的 Minecraft 版本，再據此選擇更新的核心構建；官方同時說明，**較新的補丁版本之間有時（但不總是）無需更新核心即可相容**。

## 4. 能進但異常（works but behaves oddly）

### 4.1 卡頓與記憶體

**卡頓的第一判據是單核效能。** BDS 的生物運算在單執行緒上完成，所以流暢度主要取決於單核效能，地圖越大越卡，這一點在 [BDS 服務端](/tutorials/bedrock/bds) 裡有說明。

| 可以調整的方向 | 說明 |
| --- | --- |
| 降低 `tick-distance` | 合法範圍 4–12，預設 4。值越大，參與運算的區塊越多 |
| 降低 `view-distance` | 需大於等於 5，預設 32。主要影響下發範圍 |
| 減少實體 / 生物農場規模 | 實體是單執行緒運算的主要負載 |
| 換單核更強的機器 | 最直接，但成本最高 |
| `max-threads` | Bedrock 有這一項（最大執行緒數），但它**改變不了單執行緒瓶頸**，不要指望靠它解決卡頓 |

關於 PHP 核心：PMMP 官方文件明確說它在多核利用上"出了名的差"，如果是為了跑 PMMP 買機器，**應優先選高主頻而不是多核心**。

**關於記憶體持續增長**：BDS 存在記憶體緩慢上漲的已知問題。關鍵提醒是——
:::warn 不要強行清理記憶體
強行清理記憶體會導致玩家在下載材質包 / Addon 時**進度條卡住**，而且**只能重啟服務端**才能恢復。正確做法是規劃定期重啟視窗，而不是"看到記憶體高就去清一下"。
:::

### 4.2 區塊與世界資料問題

BDS 的世界資料在 **`worlds/`** 目錄下，每個世界一個子資料夾。有一個非常關鍵的行為：

> 服務端啟動時會去 `worlds/` 裡找**與 `server.properties` 中 `level-name` 同名**的目錄。找到就用它；**找不到就新建一個世界**。

這意味著 **`level-name` 寫錯一個字母，服務端不會報錯，而是安靜地生成一個新世界**——玩家看到的就是"我的存檔沒了"。所以發現"存檔變了"時，第一件事是核對 `level-name` 和 `worlds/` 裡的目錄名。

| 現象 | 可能原因 | 處理 |
| --- | --- | --- |
| 世界載入失敗 / 啟動時報世界相關錯誤 | 存檔損壞，或上次儲存被中斷 | **停止反覆啟動**，從備份恢復 |
| 換了核心後世界讀不出來 | 第三方核心的存檔相容性不如官方 BDS | 恢復原核心，或按核心文件遷移 |
| 世界匯入後不生效 | 目錄名與 `level-name` 不一致 | 把世界目錄重新命名為 `level-name` 的值 |
| 存檔整體丟失 | 只備份了部分檔案 | 備份 `worlds/` **整個目錄** |

從備份恢復的完整流程見 [備份與恢復](/tutorials/java/backup)。
:::tip 複製或備份前先正常關服
在控制台執行 `stop`，等行程真正退出後再複製 `worlds/`。行程還在寫檔案時複製，得到的很可能是一個"看起來完整、實際損壞"的存檔。
:::

### 4.3 附加包與資源包

兩個前提：**必須是基岩版格式的包**——Java 版的資料包 / 資源包和基岩版的附加包是兩套東西，互不通用；**包必須被正確放置並註冊**——光把檔案拷進去，服務端不會自動啟用它。已驗證的目錄與註冊方式如下：

| 類型 | 放置目錄 |
| --- | --- |
| 行為包（Behavior Pack） | `development_behavior_packs` |
| 資源包（Resource Pack） | `development_resource_packs` |

要讓某個世界啟用包，需要在**該世界的工作目錄**裡建立對應的清單檔案，寫入包的 UUID 和版本；UUID 來自包自己的 `manifest.json`：

```json
[
    {
        "pack_id": "33556fcf-d192-4d5f-96a0-29357702af7b",
        "version": [ 1, 0, 0 ]
    }
]
```

其中：行為包寫入 `world_behavior_packs.json`，資源包寫入 `world_resource_packs.json`；多個包存在衝突時，**排在前面的包優先**。

其他要點：**`texturepack-required=true`** 會強制客戶端下載服務端的資源包，開啟後玩家自己啟用的客戶端資源包（包括市場包）會失效；**市場（Marketplace）裡的包不能應用到服務端**；服務端根目錄還有一個 **`valid_known_packs.json`**，它是服務端維護的**已知包列表**，服務端據此做校驗，它的確切格式與維護流程**以官方文件為準**，日常操作走上面那套"放目錄 + 寫 world_*_packs.json"的流程即可；**客戶端卡在下載資源包**，除了包本身的問題，也可能是服務端記憶體狀態導致的（見 4.1），此時重啟服務端往往能恢復。

對 PMMP 還有一個官方已知問題：**服務端使用較大的資源包時會出現連線問題**（官方舉例為大於 1 MB 的包）。官方給出的排查手段是移除大包後重試；另一個可能有效的變通做法是在 `pocketmine.yml` 中逐步降低 `network.max-mtu-size`（例如每次降 100 再測），但官方同時說明這只是**變通**，會降低頻寬效率，仍應找出根因。

### 4.4 權限與白名單

BDS 的權限與白名單是**兩個獨立檔案**，欄位也不一樣，很容易混。**管理員（OP）在 `permissions.json` 裡**，條目由 `xuid` 和 `permission` 組成：

```json
[
    {
        "permission": "operator",
        "xuid": "451298348"
    }
]
```

- `permission` 的合法值只有三個：**`operator` / `member` / `visitor`**。
- **`online-mode` 必須開啟**，因為 XUID 需要線上驗證帳號。
- 服務端執行中修改了該檔案，需要執行 **`permission reload`** 才會生效；`permission list` 可以檢視當前權限。
- 不在列表裡的新玩家，適用 `default-player-permission-level` 的設定。除了改檔案，也可以**在遊戲內直接改**玩家權限。

**白名單在 `allowlist.json` 裡**，條目欄位為：

| 欄位 | 含義 |
| --- | --- |
| `name` | 玩家的**遊戲名 / 暱稱（gamertag）**，必須完全一致 |
| `xuid` | 玩家的 XUID；**如果已經填了 `name`，這一項可以省略** |
| `ignoresPlayerLimit` | 為 `true` 時，該玩家在人數已滿時仍可進入 |

幾個關鍵行為：只填 `name` 時，**當同名玩家連線後 XUID 會被自動補上**，也就是說名字填錯了這個人永遠進不來，而且不會自動糾正；**白名單只在 `online-mode` 開啟時有效**，關閉正版驗證後玩家可以頂著白名單裡的名字進來，白名單形同虛設；玩家**改了 gamertag** 之後，舊名字的條目就不再匹配，需要更新；手工改檔案時服務端還在執行，需要用相應的 reload 指令讓改動生效。

| 現象 | 可能原因 | 處理 |
| --- | --- | --- |
| 該是 OP 的人不是 OP | 條目沒寫進 `permissions.json`，或寫了但沒 reload | 補條目並 reload，或在遊戲內直接設定 |
| 加進 `permissions.json` 卻沒生效 | `online-mode` 關閉，XUID 無法驗證 | 開啟 `online-mode` |
| 白名單裡的人進不來 | `name` 與實際 gamertag 不完全一致（大小寫、空格、改名） | 核對準確名字，或直接填 XUID |
| 誰都能進 | 白名單沒啟用，或 `online-mode` 關閉 | 檢查 `allow-list` 與 `online-mode` |
:::note 欄位名以官方文件為準
上面這些欄位名與行為取自官方說明。**不同版本之間可能調整欄位或預設值**，實際以 BDS 官方文件（以及隨包附帶的 `bedrock_server_how_to.html`）為準。
:::

### 4.5 與 Java 版的行為差異

玩家報的很多"bug"，其實是**兩個版本本來就不一樣**：紅石機制、生物生成規則等都有差異。這一層不在這裡重複解釋，直接看 [JAVA VS 基岩](/wiki/editions)。

## 5. 排查順序

按下面的順序走，每一步都能把可能性砍掉一半。**不要跳步**。

1. **確認服務端行程真的在跑。** 看控制台視窗是否還在、行程是否還在行程列表裡。
2. **確認它在監聽埠。** Linux 與 Windows 的指令見下。
3. **確認埠與協議。** 埠號對不對，放行的是不是 **UDP**（預設 19132，IPv6 為 19133）。
4. **確認客戶端版本。** 客戶端版本必須與服務端版本一致，見 [協議版本與版本選擇](/tutorials/bedrock/protocol)。
5. **確認網路路徑。** 區域網路 / 公網 IP / 隧道，三者走的路不一樣；有沒有 CGNAT 或雙重 NAT。
6. **看服務端控制台與日誌。** 報錯原文比任何猜測都值錢。BDS 的啟動與報錯都會列印在控制台。
7. **確認權限與白名單。** 玩家是被踢了，還是壓根沒連上？被踢通常能在控制台看到原因。
8. **確認世界與附加包完整性。** `level-name` 是否與 `worlds/` 下的目錄名一致；包是否放在正確目錄並註冊。

第 2 步的指令：Linux 用 `ss -ulnp | grep 19132`（`-u` 只看 UDP）；Windows 用 `netstat -ano | findstr 19132`（`-a` 全部連線與監聽，`-n` 不做名稱解析，`-o` 顯示行程號）；PowerShell 下更直觀的是 `Get-NetUDPEndpoint -LocalPort 19132`。

```bash
ss -ulnp | grep 19132
```

```bat
netstat -ano | findstr 19132
```

**現象對照表：**

| 現象 | 先查什麼 | 常見原因 |
| --- | --- | --- |
| 行程不在 | 控制台報錯原文 | 執行庫缺失、Java / PHP 版本不對、埠被佔用、配置寫錯 |
| 行程在，埠沒監聽 | 啟動日誌裡有沒有 bind 失敗 | 埠被佔用、`enable-lan-visibility` 搶綁 19132/19133 |
| 埠在監聽，本機能連、外部不能 | 公網可達性 | 安全組 / 防火牆沒放行 UDP、CGNAT、雙重 NAT |
| 埠檢測通過但玩家進不去 | 檢測工具測的是 TCP 還是 UDP | 只放行了 TCP |
| 提示伺服器版本過舊 | 客戶端與服務端版本 | 協議不匹配；第三方核心構建太舊 |
| 能進但一進就掉 | 控制台是否有踢出原因 | 白名單、權限、人數上限 |
| 能進但特別卡 | 單核佔用、`tick-distance`、實體數量 | 單核瓶頸、地圖過大 |
| 存檔"消失" | `level-name` 與 `worlds/` 目錄名 | `level-name` 寫錯，服務端新建了世界 |
| 附加包不生效 | 包類型與放置目錄 | 放錯目錄、沒寫 world_*_packs.json |

## 6. 求助時該給什麼

把下面這些一次性給全，能省掉好幾輪來回：

| 要提供的資訊 | 為什麼需要 |
| --- | --- |
| **服務端核心與構建版本** | BDS 的版本號，或 Nukkit 系 / PMMP 的核心名與構建號。不同核心的排查路徑不同 |
| **遊戲版本 / 協議版本** | 客戶端和服務端各是什麼版本，這是基岩版第一排查項 |
| **作業系統與架構** | Windows 還是 Linux、發行版與版本、是否 64 位、是否 x86-64 |
| **控制台報錯的完整原文** | **不要轉述、不要只截一半**。報錯原文裡的關鍵詞能直接定位問題 |
| **最近改過什麼** | 升級了核心？換了埠？加了附加包？改了 `server.properties`？ |
| **以前是否正常** | "一直沒成功"和"昨天還好"是兩條完全不同的排查路徑 |
| **已經試過什麼** | 避免重複建議；也說明哪些方向已經被排除 |
| **網路情況** | 區域網路還是公網、有沒有公網 IP、用了什麼隧道、埠轉發怎麼配的 |
:::tip 報錯原文怎麼給
直接把控制台輸出複製成文本，或者貼日誌檔案。**拍照、截圖、只貼最後一行**都會讓排查變慢。如果輸出很長，保留報錯前後各若干行，而不是隻留一句。
:::
