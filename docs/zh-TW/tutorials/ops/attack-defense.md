[網路安全基礎](/tutorials/ops/network-security) 講的是"把門關好"：只開必要的埠、限制來源、加固 SSH。這一篇講另一種情況：**門是關好的，但有人正拿卡車撞門**。

先給一個不討喜但必須說清楚的結論：**流量型攻擊（volumetric）不是靠服務端配置能解決的**。本文會解釋為什麼，以及在這個前提下你**真正**能做什麼。

## 1. 攻擊類型分類

按 OSI 層次粗分，你遇到的攻擊幾乎都落在這兩類裡。

### 1.1 第三、四層：流量型與協議型

| 攻擊 | 協議 | 特徵 | 主要影響 |
| --- | --- | --- | --- |
| **UDP flood** | UDP | 海量 UDP 包砸向某個埠或隨機埠 | 頻寬飽和、網絡卡與軟中斷被打滿 |
| **SYN flood** | TCP | 只發 `SYN` 不完成握手，佔滿連線表 | 新建連線失敗、`backlog` 溢位 |
| **ICMP flood** | ICMP | 大量 `echo request`（ping） | 頻寬與中斷開銷 |
| **反射放大** | UDP | 偽造源 IP 向第三方發查詢，回包砸向你 | 頻寬飽和，**且你看到的是無辜第三方** |

**反射放大（reflection / amplification）** 的原理值得單獨說清楚：攻擊者偽造**你的 IP** 作為源位址，向大量開放服務（DNS 解析器、NTP、memcached、SSDP、CLDAP）傳送一個**很小的請求**，這些伺服器把**很大的響應**發回給"請求者"，也就是你；你收到的流量 = 攻擊者發出的流量 × 放大倍數。

**放大倍數（amplification factor）** = 響應位元組數 / 請求位元組數。它取決於第三方服務的配置，不同協議、不同實現、不同版本差異極大，因此下表只是**量級參考**，不要當成精確值：

| 反射源 | 常見埠 | 放大倍數量級 | 說明 |
| --- | --- | --- | --- |
| DNS | UDP `53` | 約 數十倍 | 取決於響應大小與是否支援 EDNS |
| NTP | UDP `123` | 約 數百倍 | 主要是歷史上 `monlist` 查詢被濫用；現代 NTP 預設已限制 |
| memcached | UDP `11211` | 極高（可達數萬倍） | 影響極大，但前提是存在暴露在公網的 UDP 版 memcached |
| SSDP | UDP `1900` | 約 數十倍 | 家用路由器與智慧裝置的 UPnP 服務 |
| CLDAP | UDP `389` | 約 數十倍 | 暴露的 LDAP 服務 |

:::warn 為什麼"源 IP 是偽造的"
UDP 是**無連線**協議：核心收到一個 UDP 包，不會先去驗證"這個源位址真的能收到回包"，因此攻擊者可以隨意填寫源 IP，**把它寫成你的 IP**。

後果非常關鍵：**你抓到的包源位址是假的**。**對偽造源 IP 的 UDP 流量，溯源和封 IP 基本無意義**——封了只會誤傷無辜的第三方。
:::

### 1.2 第七層：應用層攻擊（Minecraft 專項）

應用層攻擊不打頻寬，打的是**你程式的處理能力**：每一個請求都要消耗 CPU、記憶體或資料庫連線，而攻擊者的成本遠低於你的成本。

Minecraft 相關的應用層攻擊主要有三類，本文後面各有一節：

| 類型 | 一句話描述 | 見 |
| --- | --- | --- |
| **狀態查詢（MOTD ping）洪水** | 瘋狂重新整理伺服器列表，逼你反覆構造響應 | 第 4 節 |
| **假人壓測（bot / 假人）** | 大量機器人進服或半開連線，佔滿槽位與資源 | 第 5 節 |

### 1.3 一個決定性的區別：能不能找到攻擊者

這是本文最重要的一條分界線：

| 流量類型 | 能否識別攻擊者 | 原因 |
| --- | --- | --- |
| **偽造源 IP 的 UDP 流量** | **基本不能** | 源位址是假的，回包不會到達攻擊者 |
| **基於 TCP 的機器人攻擊** | **通常可以** | 要建立 TCP 連線必須完成三次握手，握手要求**對方的 IP 真實可達** |
| **登入 / 進服類攻擊** | **通常可以** | 要走到握手（handshake）之後，必須先有真實 TCP 連線 |

**實踐含義**：

- 對 UDP 洪水，你的手段只剩"限速 + 上游清洗"，**別指望封 IP**；
- 對 TCP 機器人洪水，**連線層面的限制（connlimit、連線頻率）和帳號層面的驗證（`online-mode`、白名單）是有效的**，因為對方必須暴露真實位址、並且（如果開了正版驗證）必須持有真實帳號。

## 2. DDoS 基礎：為什麼"封攻擊者 IP"沒用

### 2.1 DDoS 是什麼

**DoS** 是用一份流量讓服務不可用；**DDoS（Distributed DoS）** 是用**成千上萬台**分佈在不同網路、不同運營商的機器同時打你。這些機器通常是被感染的普通裝置、廉價 VPS 或物聯網裝置，統稱**肉雞（botnet）**。關鍵不是"單台機器多強"，而是**聚合頻寬**：1000 台裝置各出 10 Mbps，就是 10 Gbps。

### 2.2 為什麼"封掉攻擊者 IP"對流量型攻擊無效

這是最普遍的誤解，值得完整解釋一遍：

1. **流量已經在你的鏈路上。** 你的防火牆（`iptables` / `nftables` / Windows 防火牆）執行在**你的機器或你的路由器上**。當攻擊流量到達這塊網絡卡時，你的**上行鏈路已經被佔滿了**。防火牆能做的只是"丟掉這些包"，但**丟包不會讓頻寬變回來**——鏈路依然是滿的，正常玩家依然連不上。
2. **丟包本身也要消耗資源。** 海量小包會在網絡卡中斷和軟中斷（softirq）上消耗大量 CPU，嚴重時連你的 SSH 都進不去，日誌也寫不出來。
3. **源 IP 數量巨大且不斷變化。** 你不可能維護一份百萬條的黑名單；而且對偽造的 UDP 源位址，黑名單裡全是無辜者。
4. **你的上游才是瓶頸。** 決定你能不能扛住的，是**機房的接入頻寬**和**運營商/服務商是否在你前面做了清洗**，而不是你機器上的規則。

### 2.3 服務商與機房真正能做的事

| 手段 | 在哪一層生效 | 說明 |
| --- | --- | --- |
| **容量（capacity）** | 上游 | 機房接入頻寬大於攻擊流量，攻擊"打不疼"。這是最根本的一層。 |
| **上游清洗（scrubbing）** | 上游 | 流量先被牽引到清洗中心，過濾後再回注給你。**這是應對流量型攻擊的主要手段。** |
| **邊緣限速（rate limiting）** | 上游或你的邊界 | 在進入你的機器之前限制速率，保護後端。 |
| **架構調整** | 你的設計 | 用代理隱藏源站、把服務放到有防護的入口後面、把靜態資源交給 CDN。 |

:::warn 不要假設"雲伺服器自帶 DDoS 防護"就夠了
各家雲服務商的免費防護**閾值、清洗方式、觸發條件、是否額外收費、是否提供高防 IP** 差異極大，且條款會變。**買之前去讀官方文件和合同條款**，明確：免費防護的閾值、超限後是黑洞（直接封掉你的 IP）還是清洗、是否有高防產品、換 IP 的政策。**這些細節本文不臆測，以你所用服務商的官方說明為準。**
:::

## 3. UDP flood 與基岩版的暴露面

### 3.1 基岩版為什麼天然更容易被打

| 事實 | 後果 |
| --- | --- |
| 基岩版使用 **UDP `19132`**（IPv6 為 `19133`） | UDP 無連線、易偽造，**既好打又難溯源** |
| **Geyser** 同樣監聽 UDP（預設與基岩版一致，可配置） | Java 服只要開了跨端，就多了一個 UDP 入口 |
| UDP 沒有握手 | 攻擊者不需要真實 IP，也不需要完成任何協商，**發一個位元組就是一個包** |
| 服務端需要回應 | 有些查詢類請求的處理成本高於請求本身，形成天然的放大面 |

### 3.2 被打時的症狀

- **頻寬曲線打滿**，但服務端日誌裡可能什麼異常都沒有；
- **TPS 正常、玩家卻頻繁超時**：服務端本身沒卡，是**網路路徑**被佔滿了；
- 網絡卡收包速率飆升、`softirq` 佔用高，SSH 變得極難連上甚至完全連不上。

觀察用的命令（均為只讀查詢）：

```bash
# UDP 监听套接字（ss 显示的是套接字，不是流量）
ss -uanp

# 网卡累计收发包与丢包计数（换成你实际的网卡名，如 eth0 / ens3）
ip -s link show dev eth0

# 内核计数器，对比两次采样的差值
cat /proc/net/dev

# 防火墙规则命中计数（需 root）
sudo iptables -L INPUT -v -n

# nftables：查看带计数器或动态集合的规则
sudo nft list ruleset
```

:::note 計數器怎麼看才有意義
`/proc/net/dev`、`ip -s link`、`nft list ruleset` 給出的都是**累計值**。判斷"是不是正在被打"，要看**單位時間的增量**：間隔十幾秒取樣兩次，比較 `RX bytes` / `RX packets` 的差值，再換算成 Mbps 與 pps。一次取樣說明不了問題。
:::

### 3.3 防禦：先縮小暴露面

**最重要的一條：只開你真正需要的 UDP 埠。** 純 Java 服（沒有 Geyser、沒有跨端）**不需要**任何 UDP 埠對公網開放；需要基岩版或 Geyser 時，只開 `19132`（以及確實需要的 IPv6 `19133`）；不要因為"教學裡寫了"就順手開一堆 UDP 埠，不需要的埠關掉，攻擊面直接消失。

### 3.4 主機側限速：iptables hashlimit

`hashlimit` 模組按"某個鍵"（這裡用源 IP）分別統計速率，超過閾值即命中規則：

```bash
# 1) 先"只记录不丢弃"，用来观察真实流量基线（推荐先跑一两天）
sudo iptables -A INPUT -p udp --dport 19132 \
  -m hashlimit --hashlimit-above 200/sec --hashlimit-burst 400 \
  --hashlimit-mode srcip --hashlimit-name mc-udp-observe \
  -j LOG --log-prefix "MC-UDP-OVER: " --log-level 4

# 2) 观察确认阈值合理后，再加真正的丢弃规则
sudo iptables -A INPUT -p udp --dport 19132 \
  -m hashlimit --hashlimit-above 200/sec --hashlimit-burst 400 \
  --hashlimit-mode srcip --hashlimit-name mc-udp \
  -j DROP
```

參數說明：

| 參數 | 含義 |
| --- | --- |
| `--hashlimit-above 200/sec` | 單源 IP 超過 200 包/秒即命中。**單位字尾必須寫**（`/sec`、`/min`、`/hour`、`/day`），寫成裸數字在多數版本上會報錯 |
| `--hashlimit-burst 400` | 允許的突發量：突發視窗內前 400 個包放行，用於容忍正常的瞬時抖動 |
| `--hashlimit-mode srcip` | 按**源 IP** 分別計數（也可用 `srcport`、`dstport` 等） |
| `--hashlimit-name mc-udp` | 核心裡的表名，**同名規則共享計數**，所以觀察規則和丟棄規則要用不同名字 |
| `-j LOG` / `-j DROP` | 前者記錄到核心日誌（`dmesg` / `journalctl -k`）用於觀察；後者靜默丟棄。也可用 `-j REJECT`，但 UDP 上 REJECT 會回 ICMP，通常沒必要 |

:::warn 這些命令的可用性取決於核心與版本
`hashlimit` 需要核心支援 `xt_hashlimit` 模組，且 `iptables` 要能在 `-m hashlimit` 時自動載入它。**規則語法在 `iptables-legacy` 與 `iptables-nft` 兩種前端上一致，但持久化方式不同。** 若提示找不到模組或選項，請對照你係統上 `iptables --version`、`modinfo xt_hashlimit` 的結果與發行版文件；另外 `iptables` 規則**預設不持久化**，重啟即丟，儲存方式見 [網路安全基礎](/tutorials/ops/network-security)。
:::

### 3.5 主機側限速：nftables 動態集合 + `limit rate over`

`nftables` 的現代做法是**按源 IP 建一個動態集合**，對超過閾值的源位址打標記，再丟棄。

下面是一個**完整可載入**的最小示例（儲存為 `mc-udp-limit.nft`，用 `sudo nft -f mc-udp-limit.nft` 載入）：

```bash
#!/usr/sbin/nft -f

# 先清掉同名旧表，避免重复加载报错；执行前确认没有别的规则依赖它
table inet mcguard
delete table inet mcguard

table inet mcguard {
    set udp_flood_v4 {
        type ipv4_addr
        flags dynamic, timeout
        timeout 10m
    }

    chain input {
        type filter hook input priority 0; policy accept;
        udp dport 19132 jump udp_guard
    }

    chain udp_guard {
        # 单源超过 200/秒（突发 400）时加入集合
        update @udp_flood_v4 { ip saddr limit rate over 200/second burst 400 packets }
        # 被限速的源写入内核日志，便于观察；再直接丢弃
        ip saddr @udp_flood_v4 log prefix "MC-UDP-OVER: " level warn
        ip saddr @udp_flood_v4 drop
    }
}
```

要點說明：

| 語法 | 含義 |
| --- | --- |
| `set ... { type ipv4_addr; flags dynamic, timeout; timeout 10m; }` | 動態集合，元素會自動過期，**不會無限增長** |
| `limit rate over 200/second burst 400 packets` | "**超過**" 200/秒才算命中（對比 `limit rate` 是"不超過"）。`over` 是關鍵字 |
| `update @set { ... }` | 命中時把鍵（`ip saddr`）**寫入集合** |
| `ip saddr @set drop` | 集合裡的源位址一律丟棄，因此**命中一次後，該源在集合過期前會被持續丟棄**；示例只按 `ip saddr`（IPv4）建集合，**IPv6 需另建 `ipv6_addr` 集合與對應規則** |

:::warn 上述 nftables 寫法與版本相關
`flags dynamic, timeout`、`limit rate over` 與 `update @set` 都屬於較新的語法，**請以你係統上 `nft --version` 與 nftables 官方 wiki 為準**。載入前建議先 `sudo nft -c -f mc-udp-limit.nft`（`-c` 為語法檢查，不實際載入）。**規則集一旦寫錯，可能把自己鎖在門外**——務必先確認你有云平台 VNC 或救援控制台。
:::

### 3.6 限速的代價：合法玩家也會被誤傷

**每一條限速規則都是一個潛在的誤報來源。** **正常玩家不會只發 200 包/秒**，但**網路抖動、丟包重傳、或某些客戶端/插件的突發行為**會造成短時高峰；閾值定得太低會**誤傷真實玩家**且很難排查，定得太高則攻擊流量早就穿透了。

因此推薦的做法是**先觀察，再丟棄**：

1. 先只加 `LOG`（iptables）或 `log`（nftables）規則，閾值設在**你預期正常峰值的數倍**；
2. 觀察一兩天，看日誌裡有多少來自"看起來正常"的 IP，確認不會誤傷後再改成 `DROP`；
3. 上線後持續關注玩家回饋，隨時調整。

:::tip 限速是"減傷"，不是"免疫"
主機側限速能顯著降低**低強度**洪水的傷害，也能讓高強度的洪水**稍微晚一點**打滿鏈路，但**無法**讓 10 Gbps 的攻擊不佔滿 1 Gbps 的鏈路。真正的解法永遠在上游。
:::

## 4. MOTD / 狀態查詢洪水（Minecraft 專項）

### 4.1 狀態查詢協議是什麼

Minecraft 客戶端在伺服器列表裡顯示"線上人數 / MOTD / 延遲 / 版本 / 圖示"，靠的是**狀態查詢**。它的特點是：**任何客戶端都能查詢，不需要登入、不需要帳號、不需要進服。**

| 平台 | 查詢方式 | 傳輸 |
| --- | --- | --- |
| **Java 版** | Server List Ping（現代狀態請求，在遊戲埠上） | **TCP**，預設 `25565` |
| **基岩版** | Unconnected Ping / Pong（RakNet） | **UDP**，預設 `19132` |

攻擊者喜歡它的原因很直接：**傳送成本極低**（一個很小的請求），**響應成本更高**（服務端要組裝 MOTD、玩家列表、圖示、版本資訊），**可以放大**（把源 IP 偽造成受害者位址，讓響應去打別人），**可以探路**（先用大量查詢測你的響應能力、看線上人數、判斷你背後是不是有防護，再決定打多大）。

### 4.2 關閉 query 協議：能做，但要理解它關的是什麼

原版 `server.properties` 裡有兩個相關鍵：

```properties
enable-query=false
query.port=25565
```

:::warn 關閉 query 不等於隱藏 MOTD
- **query 協議**（`enable-query`）是歷史遺留的 **GameSpy4 查詢協議**，走 **UDP**，預設埠由 `query.port` 指定，用來給第三方工具/網站查詢伺服器資訊；
- **伺服器列表看到的狀態資訊（MOTD、人數、延遲）** 走的是**現代 Server List Ping**，在 Java 版上是**遊戲埠上的 TCP 狀態請求**，與 query 是**兩套完全不同的東西**。

所以：**把 `enable-query` 設為 `false`，並不會讓你的伺服器從玩家的伺服器列表裡消失，也不會隱藏 MOTD**，它只是關掉了一個你大機率根本不需要的額外查詢入口。不需要第三方查詢工具時，關掉它是減少暴露面的好事，但別指望它防住 ping 洪水。
:::

### 4.3 針對狀態埠的限速

思路與第 3 節完全一樣，只是換成 TCP：

```bash
# Java 版：限制单源 IP 对 TCP 25565 的"新建连接"速率
# 注意：这条只对新建连接有效，已建立连接不受影响，因此不会影响正在游戏的玩家
sudo iptables -A INPUT -p tcp --dport 25565 --syn \
  -m hashlimit --hashlimit-above 10/sec --hashlimit-burst 20 \
  --hashlimit-mode srcip --hashlimit-name mc-ping \
  -j DROP
```

要點：`--syn` 只匹配**發起連線**的包，**不會誤傷已線上玩家**；閾值（示例 10/秒）要按你的實際情況調——一個玩家正常只會查詢幾次，但**同一個 NAT 出口後面的多個玩家會共享源 IP**，學校、網咖、家庭共享網路都容易誤傷，所以別設成 `1/sec`。nftables 等價寫法是把第 3.5 節的集合類型改成 `ipv4_addr`、匹配條件改成 `tcp dport 25565` 並加 `tcp flags syn`。

### 4.4 用代理擋住後端

把**代理（Velocity / BungeeCord）放在最前面**，後端服只接受代理的連線，是價效比很高的一步：

- 玩家的連線先打到代理，**後端服的 IP 不出現在玩家列表裡**，攻擊者需要先找到真實位址；
- 代理可以做連線頻率限制、配合轉發金鑰校驗，**未通過校驗的連線直接被拒**；後端服也可配置為只信任代理（轉發模式相關設定，**鍵名隨軟體與版本不同，請以你自己生成的配置與官方文件為準**）。

代理的搭建與轉發配置見 [跨服端](/tutorials/java/proxy)。

### 4.5 Minecraft 專用過濾服務

市面上有**面向 Minecraft 的過濾/防護服務**（例如 TCPShield 這一類）：玩家先連到服務商的接入點，由服務商做協議層識別與過濾，再把乾淨流量轉發到你的後端。

**這類服務通常是"選項"而非"必需品"**，因為：具體能力（支援哪些版本、是否支援基岩版/UDP、是否支援 Geyser、是否要求特定轉發模式、價格與流量額度）**各家差異很大，且會隨產品迭代變化**；引入第三方意味著**玩家流量經過第三方**，需要評估隱私與信任；配置通常要求後端只接受來自服務商 IP 的連線，**配錯會直接導致全服不可達**。

**結論：把它當成一個可評估的方案，實際能力請以服務商官方文件為準，本文不代其承諾。**

### 4.6 基岩版的誠實結論

**基岩版無法完全關閉狀態 ping**：客戶端要靠它顯示伺服器列表資訊，服務端必須應答 RakNet 的 unconnected ping。因此基岩版的抗 ping 洪水只有兩條路：

1. **上游防護 / 清洗**（最有效，取決於服務商）；
2. **在邊界或主機上按源 IP 限速 UDP**（第 3.4 / 3.5 節的規則，把 `--dport 19132` 用上即可）。

## 5. 假人壓測（bot / 假人洪水）

### 5.1 它是什麼

**假人壓測**指用自動化程式製造大量"玩家"或"半成品玩家"，目的是**佔滿槽位、燒掉 CPU 與記憶體、製造聊天垃圾、讓真實玩家進不來**。

常見變體：

| 變體 | 做法 | 主要消耗 |
| --- | --- | --- |
| **連線洪水（connection flood）** | 只完成 TCP 連線，不做任何 Minecraft 協議互動 | 連線表、檔案描述符、握手開銷 |
| **登入洪水（login flood）** | 發握手（handshake）與登入開始，但不完成登入 | 登入階段 CPU、認證請求、記憶體 |
| **假人掛機（idle bots）** | 完整進服後原地不動 | 玩家槽位、實體/區塊載入、記憶體 |
| **聊天 / 指令刷屏** | 進服後高頻發聊天或指令 | 主執行緒解析、日誌 IO、刷屏騷擾 |
| **物品 / 互動請求刷屏** | 高頻發包觸發互動邏輯 | 服務端主執行緒、反作弊插件開銷 |

:::note 為什麼遊戲服特別怕假人
Minecraft 是**有狀態的長連線**服務。Web 伺服器處理完一個請求就斷開，成本可以攤薄；而 Minecraft 每多一個玩家，就要**常駐記憶體、載入區塊、同步實體、維護連線**。同樣的攻擊成本，對遊戲服的傷害遠大於對靜態網站。
:::

### 5.2 防禦（按有效性排序）

#### 第 1 位：`online-mode=true`（Java）/ Xbox Live 驗證（基岩）

**這是單項最有效的措施。** 開啟正版驗證後，進服必須持有**真實的 Mojang/Microsoft 帳號**，機器人制作者必須為每一個假人準備真實帳號——成本瞬間從"幾乎為零"變成"按帳號計費"。

Java 版 `server.properties`：

```properties
online-mode=true
```

:::warn 離線模式的代價必須想清楚
`online-mode=false` 意味著**任何人都能用任意 ID 進服**，包括冒用管理員、冒用其他玩家的名字。這屬於身份層面的洞，防火牆補不了。**只有在你完全清楚代價、並且用白名單/登入插件補上身份校驗時，才考慮離線模式。** 相關討論見 [服務端配置](/tutorials/java/config)。
:::

基岩版沒有 `online-mode` 這個鍵，它使用 **Xbox Live 身份驗證**。具體開關名稱與預設值**隨服務端軟體（官方 BDS 與各類第三方基岩服務端）和版本而不同**，請以你自己生成的 `server.properties` 與官方文件為準。**但原則上：不要為了"方便"而關閉身份驗證。**

#### 第 2 位：白名單 / 允許列表

對小型伺服器，**白名單是比任何限速都徹底的方案**：不認識的人根本連不上，機器人連進門的資格都沒有。

Java 版 `server.properties`：

```properties
white-list=true
enforce-whitelist=true
```

| 鍵 | 作用 |
| --- | --- |
| `white-list` | 只允許名單內的玩家登入 |
| `enforce-whitelist` | 名單變化時**立即把不在名單上的線上玩家踢出**。不改這個鍵，新加入的名單要等玩家重連才生效 |

名單用控制台/遊戲內指令維護（`whitelist add <玩家名>`、`whitelist list` 等，**具體語法以你的服務端版本為準**）。

基岩版使用伺服器根目錄下的 **`allowlist.json`**，通常由 `allowlist` 相關指令自動維護。**檔案格式與開關鍵名隨服務端軟體和版本變化，請以你自己伺服器生成的 `allowlist.json` 和官方文件為準，不要照抄教學裡的示例檔案。**

#### 第 3 位：連線頻率限制（`spigot.yml`）

Spigot 及其衍生核心（Paper、Purpur 等）的 `spigot.yml` 裡有連線節流設定，鍵路徑為：

```yaml
settings:
  connection-throttle: 4000
```

| 項 | 說明 |
| --- | --- |
| `connection-throttle` | **同一來源位址兩次連線之間必須間隔的毫秒數**。示例 `4000` = 4 秒；設為 `-1` 通常表示**停用**節流 |
| 預設值 | **隨核心與版本不同**，常見預設是 4000 毫秒，但不要假設你的一定是 |

**它攔得住什麼**：同一個 IP 反覆快速重連的腳本。
**它攔不住什麼**：來自大量不同 IP 的分散式假人（每個 IP 只連一次，節流完全不觸發）。

:::warn 別把節流值設得過大
設成幾十秒會**嚴重影響正常玩家**：掉線後要等很久才能重連，多人共用一個出口 IP 的家庭/網咖更是直接進不來。建議從預設值開始，只在確有需要時小幅調整。
:::

#### 第 4 位：防火牆連線數限制

限制**單個源 IP 的併發連線數**，對連線洪水與半開登入有效：

```bash
# iptables：单 IPv4 地址最多 8 条到 25565 的并发连接
sudo iptables -A INPUT -p tcp --dport 25565 \
  -m connlimit --connlimit-above 8 --connlimit-mask 32 \
  -j REJECT --reject-with tcp-reset
```

| 參數 | 含義 |
| --- | --- |
| `--connlimit-above 8` | 超過 8 條併發連線才命中 |
| `--connlimit-mask 32` | 按 **/32** 歸組，即"每個 IPv4 位址"單獨計數 |
| `-j REJECT --reject-with tcp-reset` | 直接拒絕並回 RST（也可用 `-j DROP`，但 REJECT 能讓客戶端更快失敗而不是卡住） |

nftables 等價寫法（用連線跟蹤計數）：

```bash
#!/usr/sbin/nft -f

table inet mcguard
delete table inet mcguard

table inet mcguard {
    chain input {
        type filter hook input priority 0; policy accept;
        # 每个源地址最多 8 条已跟踪的 TCP 连接
        tcp dport 25565 ct count over 8 reject with tcp reset
    }
}
```

:::warn 併發連線數要按你的實際玩法定
一個真實玩家通常只佔 1 條連線（裝了某些模組/插件的客戶端可能更多）。但**同一 NAT 出口的多個玩家共享源 IP**，閾值設成 2 或 3 會直接踢掉正常玩家。**8 只是示例，請按你的玩家分佈調整**；`ct count` 需要連線跟蹤（`nf_conntrack`）正常工作，請確認沒有把 `ct` 相關的模組或表項關掉。
:::

#### 第 5 位：Paper 的封包限流器（packet limiter）

Paper 在**全域配置**裡提供了一個封包限流器：它按玩家統計**入站封包速率**，超過閾值時可以**踢出該玩家**並記錄日誌。它對"進服後瘋狂發小包"的攻擊（例如第 5.1 節的物品/互動刷屏、部分假人行為）有效。

:::warn 不要照抄教學裡的配置結構
**這個配置塊的鍵名、層級和預設值在不同 Paper 版本與不同分支之間都發生過變化。** 正確做法是：先正常啟動一次服務端讓它**自己生成**設定檔；開啟你自己生成的檔案，找到封包限流相關的塊；**以檔案裡的實際結構為準**修改，而不是複製網上的片段；改完看啟動日誌有沒有配置解析警告。

本節因此**刻意不給出具體鍵名和數值**——寫一個可能過期的結構，比不寫更危險。
:::

#### 第 6 位：把後端藏到代理後面

與第 4.4 節相同：**後端服的埠不要直接對公網開放**，只允許代理的 IP 連入。這樣即使有人拿到了你的真實 IP，也要先突破代理這一層。配置見 [跨服端](/tutorials/java/proxy)。

#### 關於反機器人插件

社群有各種"反假人 / 反機器人 / 進服驗證"插件（圖形驗證、指令驗證、限速等）。它們**能提高攻擊成本**，尤其對低質量腳本；但它們**都在應用層**：攻擊流量已經到達你的服務端、已經消耗了握手與部分登入資源；而且**質量參差**，部分插件本身有效能或相容性問題。

**建議自己評估**：看它是否還在維護、是否開源、是否與你的服務端版本相容、在測試服壓測一次再上生產。

### 5.3 `max-players` 是軟限制

```properties
max-players=20
```

`max-players` 只決定**伺服器列表裡顯示的上限**，以及在**登入階段**拒絕對應數量的玩家。它**不是**防洪措施：機器人**在登入階段就已經消耗了 CPU、認證請求和記憶體**，被拒絕之前成本已經付出；連線洪水（只建立 TCP 連線）**根本不會走到這個判斷**；它也不影響頻寬與查詢洪水。

**把 `max-players` 當成容量聲明，不要當成防禦手段。**

## 6. 實戰防禦清單

### 6.1 分層清單（從"必須做"到"錦上添花"）

| 優先順序 | 措施 | 說明 |
| --- | --- | --- |
| **必須** | `online-mode=true`（Java）/ 保持 Xbox Live 驗證（基岩） | 單項最有效的反假人措施 |
| **必須** | 只開放真正需要的埠 | 沒有暴露的服務無法被打；UDP 埠尤其要剋制 |
| **必須** | 主機防火牆預設拒絕入站，只放行白名單埠 | 見 [網路安全基礎](/tutorials/ops/network-security) |
| **必須** | 系統與軟體及時更新、權限收緊 | 見 [系統安全加固](/tutorials/ops/system-security) |
| **必須** | 定期備份，且**至少一份離線/異地** | 勒索與報復性刪檔的最後防線，見 [備份與恢復](/tutorials/java/backup) |
| **強烈建議** | 白名單 / 允許列表（小型服） | 不認識的人根本連不上 |
| **強烈建議** | 遊戲埠的按源 IP 限速 | 第 3.4 / 3.5 / 4.3 / 5.2 節的規則 |
| **強烈建議** | 監控與告警（頻寬、連線數、CPU、玩家數），並選擇防護條款清晰的服務商 | 見 6.3 節 |
| **建議** | 代理在前，後端不直接暴露 | 見 [跨服端](/tutorials/java/proxy) |
| **建議** | 基岩版 / 跨端玩家參考 [手機玩家支援](/tutorials/java/mobile) 規劃入口 | 跨端會引入額外 UDP 暴露面 |
| **建議** | 一份書面的事件響應預案 | 見 6.4 節 |
| **錦上添花** | Minecraft 專用過濾服務 | 能力因服務商而異，先小範圍驗證 |
| **錦上添花** | 反機器人插件 | 自己評估，別當唯一防線 |

### 6.2 攻擊類型對應表

| 攻擊類型 | 真正有幫助的 | 基本沒用的 |
| --- | --- | --- |
| **UDP flood（偽造源 IP）** | 上游清洗與容量、只開必要 UDP 埠、邊界按源 IP 限速 | 封單個 IP、服務端插件、`max-players` |
| **反射放大（DNS / NTP / memcached / SSDP / CLDAP）** | **上游清洗**（這是唯一有效層）、機房容量 | 任何主機側規則（鏈路已經滿了）、向第三方投訴（你也是受害者） |
| **SYN flood** | 上游清洗、核心 `syn` 相關參數調優、負載均衡/代理層吸收 | 應用層限速、白名單 |
| **MOTD / 狀態 ping 洪水** | 單源 TCP 連線速率限制、代理在前、上游過濾 | 關 `enable-query`（它管的不是這個）、封 IP（量大且分散） |
| **基岩版 ping 洪水** | 上游防護、按源 IP 限速 UDP `19132` | 關閉 ping（**做不到**）、服務端配置 |
| **連線洪水 / 登入洪水（半開登入）** | 防火牆 `connlimit` / `ct count`、`online-mode` 或身份驗證、代理在前、上游清洗 | `max-players`、聊天過濾、白名單（離線模式下白名單在登入後生效） |
| **假人掛機 / 刷屏** | `online-mode` + 白名單、`connection-throttle`、封包限流、管理指令處置 | 頻寬防護（這類攻擊幾乎不佔頻寬） |
| **漏洞利用 / 提權** | 及時更新、最小權限、`online-mode` | 防火牆（打的是應用層） |

### 6.3 監控與告警：沒有告警等於沒有監控

至少要能回答"現在是不是被打"：

| 指標 | 從哪裡看 | 異常特徵 |
| --- | --- | --- |
| **頻寬 / 收包速率** | 服務商控制台的流量圖、`/proc/net/dev`、`ip -s link`、`vnstat` | 遠超歷史峰值，且玩家數沒有相應增長 |
| **連線數** | `ss -tan state established \| wc -l`、`ss -s` | 連線數暴漲但玩家數不變 |
| **CPU 與軟中斷** | `top`、`mpstat -P ALL 1` | 玩家不多但 `%soft` 很高（多為小包洪水） |
| **玩家數與登入失敗** | 服務端日誌、面板 | 大量登入嘗試、大量異常 ID |
| **防火牆命中計數** | `iptables -L -v -n`、`nft list ruleset` | 限速規則命中數持續增長 |

```bash
# 已建立连接数（配合 ss -s 看套接字总览）
ss -tan state established | wc -l

# 每核 CPU（含软中断）每秒刷新
mpstat -P ALL 1

# 网卡累计计数（看两次采样的差值）
ip -s link show dev eth0

# 内核日志里的限速命中记录（配合 LOG / log 规则）
sudo journalctl -k | grep -i 'MC-UDP-OVER' | tail -n 20
```

:::tip 讓服務商的面板替你值班
大多數雲控制台提供**頻寬曲線與告警**。把閾值設在"歷史峰值 + 餘量"上，一旦觸發就收到通知——**這比事後翻日誌有用得多**。具體配置路徑因服務商而異，請以官方文件為準。
:::

### 6.4 事件響應預案（一頁紙）

被打的那一刻不是思考的時候。提前寫好：

1. **判斷**：對照 6.3 的指標，先確認是**攻擊**還是**自己的 bug**（插件死迴圈、備份任務佔滿磁碟 IO、世界檔案損壞導致的卡頓）。
2. **止血與求助**：能扛就扛；扛不住時臨時**只允許白名單 IP / 只允許代理 IP**，同時向服務商報障，說明時間、現象、流量特徵，詢問是否觸發清洗、是否需要換 IP。
3. **留證與恢復**：儲存流量圖、日誌、`ss` 輸出——**這些是申訴與復盤的唯一依據**；攻擊停止後確認 TPS、連線數與世界完整性，再解除臨時限制。
4. **復盤**：攻擊規模多大？哪一層頂住了、哪一層沒頂住？下次要買什麼、配什麼？

:::warn 備份是攻擊的一部分，不是附加項
**勒索與報復性刪檔**是真實存在的攻擊方式。攻擊者拿到面板或 RCON 權限後第一件事往往是刪備份。所以：**至少一份備份必須在離線介質或異地，且不掛在服務端機器的可寫路徑上。** 具體方案見 [備份與恢復](/tutorials/java/backup)。
:::

## 7. 誠實的邊界

把三句話寫在這裡，避免你對本文產生錯誤期待：

1. **服務端配置無法阻止大規模流量型攻擊。** 無論 `iptables`、`nftables`、插件還是 `max-players`，都執行在**攻擊流量已經到達之後**。1 Gbps 的鏈路面對 10 Gbps 的攻擊，配置再完美也沒用。**唯一真正的解法是上游容量與清洗能力。**
2. **上游能力是你買來的，不是配出來的。** 選購服務時就要看清 DDoS 條款：免費防護閾值多少、超限後是清洗還是黑洞、是否支援 UDP、是否有高防 IP、換 IP 是否收費。**這些問題在被打的當天再問就太晚了。**
3. **每一條限速都是潛在的誤傷。** 限速會誤傷突發流量的真實玩家、共享出口 IP 的網咖與家庭網路。**先觀察、再丟棄、持續調整**，不要把網上抄來的閾值直接上生產。
