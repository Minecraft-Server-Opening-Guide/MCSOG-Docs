遷移（migration）指的是**把整套服務端從一個環境搬到另一個環境**：換更好的硬體、換服務商、搬出網路品質差的機房，或者單純為了省錢。它比"從零裝一台新服"危險得多——裝新服失敗只是暫時沒有服，**遷移失敗是原有服務已經停了、新服務又起不來**。

這一篇講遷移的完整流程與檢查清單。要搬哪些檔案、哪些檔案千萬別碰，見 [服務端結構](/tutorials/java/structure)；備份範圍與恢復演練見 [備份與恢復](/tutorials/java/backup) 與 [異地備份](/tutorials/ops/offsite-backup)。

## 1. 什麼時候該遷移

| 觸發原因 | 典型訊號 | 遷移時要特別小心的地方 |
| --- | --- | --- |
| 硬體升級 | TPS 長期偏低、記憶體吃緊、磁碟 IO 打滿，而最佳化已經沒有空間 | 新機器的 CPU 單核效能比核數更重要；先確認瓶頸真在硬體 |
| 換服務商 | 工單沒人回、超售嚴重、跑路傳聞、計費不透明 | 資料出境與合規、出口流量費、退租前先確認新環境可用 |
| 搬出網路差的區域 | 玩家延遲高、繞路嚴重、丟包、被 DDoS 時沒有防護 | 目標區域的線路品質要**實測**，不要只看商家宣傳 |
| 降低成本 | 賬單壓力大，或長期閒置的配置過高 | 便宜的機器往往共享 CPU、磁碟更慢，先壓測再搬 |
| 架構調整 | 單機改群組服、加面板、加資料庫 | 這已經不是"遷移"，而是"重建 + 資料搬遷"，要另做方案 |

:::note 能就地解決就別遷移
遷移的每一步都有停機與資料風險。**如果只是記憶體不夠，加記憶體比遷移便宜；如果只是延遲高，先排查是不是路由或代理配置的問題。** 把遷移留給"確實解決不了"的場景。
:::

## 2. 遷移前檢查清單

遷移最容易翻車的環節不是 `rsync`，而是**"原來這台機器上到底跑著什麼，我自己都沒數"**。先把清單寫出來，再動手。

| 檢查項 | 怎麼查 | 通過標準 |
| --- | --- | --- |
| 這台機器上跑了哪些服務 | `systemctl list-units --type=service --state=running`、`ss -tlnp`、`docker ps`、`crontab -l` | 每一項都能說出用途，且知道要不要一起搬 |
| 遊戲與核心版本 | 服務端啟動日誌、`/version`、核心檔名 | 記錄到"遊戲版本 + 核心名 + 核心構建號" |
| 插件 / 模組版本清單 | `plugins/`、`mods/` 目錄列表 | 有清單檔案（版本號可復現），不只是目錄本身 |
| Java 版本 | `java -version` | 新舊機器一致；**升級 Java 是另一件事，別和遷移一起做** |
| 作業系統與核心 | `cat /etc/os-release`、`uname -a` | 知道差異（發行版、glibc、檔案系統） |
| DNS 記錄與 TTL | `dig +noall +answer example.com`、`dig _minecraft._tcp.example.com SRV` | 記錄類型（A / AAAA / SRV）與當前 TTL 都有記錄 |
| 誰有訪問權 | SSH 公鑰、面板帳號、服務商帳號、協管名單 | 遷移後**逐條核對**，該刪的刪 |
| 備份是否可恢復 | 真做一次恢復演練 | 不是"有備份檔案"，而是"**恢復過、能起來**" |
| 外部依賴 | 資料庫、物件儲存、API Key、Webhook、監控 | 新機器上能連通，憑據有效 |

:::warn 沒有驗證過備份的遷移就是賭博
`rsync --delete` 寫錯路徑、磁碟滿、權限不對、歸檔截斷——任何一種都能讓你在停服之後才發現"沒有可用的副本"。**動手前必須有一份離線、已驗證可恢復的備份**，並且在維護視窗內不要刪除它。備份做了但沒驗證過，等於沒有備份。
:::

## 3. 什麼必須搬

下表的每一行都是真實事故裡漏過的東西。**漏掉世界是災難，漏掉啟動方式則是"資料都在但服務起不來"。**

| 專案 | 位置（以 `/opt/mcserver` 為例） | 漏掉的後果 |
| --- | --- | --- |
| 世界存檔 | `world/`、`world_nether/`、`world_the_end/`（名字以 `server.properties` 的 `level-name` 為準） | **最嚴重**：玩家建築、背包、進度全丟 |
| 插件 / 模組本體 | `plugins/`、`mods/` | 進服後功能缺失，或玩家客戶端因模組不匹配進不來 |
| 插件 / 模組配置 | `plugins/<plugin-name>/`、`config/` | 權限、經濟、領地、傳送點、抽獎池全部回到預設值 |
| 核心配置 | `server.properties` | 埠、難度、正版驗證、視距、白名單開關全變預設 |
| 核心自身配置 | `bukkit.yml`、`spigot.yml`、`paper-*.yml`、`purpur.yml` | 最佳化參數、世界預設值丟失，效能可能明顯變化 |
| 名單檔案 | `ops.json`、`whitelist.json`、`banned-players.json`、`banned-ips.json` | 管理員權限丟失，或封禁失效、白名單形同虛設 |
| 玩家名快取 | `usercache.json` | 通常可重建，但離線模式的 UUID 與顯示名對映會短暫錯亂 |
| 啟動腳本 | `start.sh`、`start.bat`、Java 參數 | **最常見漏項**：服務起不來，或參數不對導致記憶體/效能異常 |
| systemd unit | `/etc/systemd/system/minecraft.service` | 開機不自啟、崩潰不重啟；`WorkingDirectory` 寫錯還會新建一個空世界 |
| 定時任務 | `crontab -l`、`/etc/cron.d/`、systemd timer | 備份、重啟、清理任務全部消失，且**很久之後才會發現** |
| 防火牆規則 | `ufw status`、`firewall-cmd --list-all`、雲安全組 | 埠不通，玩家連不上；或舊規則缺失導致意外暴露 |
| TLS 憑證 | `/etc/letsencrypt/`、`/etc/ssl/` | 面板、地圖、資源包等 HTTPS 服務中斷或憑證告警 |
| MCDR 資料 | MCDR 執行目錄下的 `config.yml`、`permission.yml`、`plugins/` | 機器人權限、指令別名、插件狀態丟失（具體檔名與結構以 MCDR 官方文件為準） |
| 面板資料 | 面板自身的配置與實例定義目錄 | 服務端檔案還在，但面板裡"什麼都沒有了"；詳見 [伺服器面板](/tutorials/ops/panels) |
| 憑據檔案 | `.env`、`rcon.password`、資料庫口令、雲端儲存金鑰 | 服務起不來，或起來後連不上依賴 |
| 反向代理配置 | Nginx / Caddy 網站檔案與憑證路徑 | 網域訪問 502，且容易誤判為"服務端沒起來" |
| 監控與告警 | 探針、Agent、告警規則 | 出問題時**沒人收到通知**，這是最危險的"靜默失敗" |

### 不需要搬的東西

| 專案 | 原因 |
| --- | --- |
| `logs/`、`crash-reports/` | 體積大；排查舊問題時再單獨取用 |
| `cache/`、`libraries/`、`versions/` | 啟動時自動重建 |
| `world/session.lock` | 執行期鎖檔案，目標端應刪除，服務端會自己重建 |
| 舊機器上的臨時歸檔、`*.tar.gz` | 容易把幾百 GB 的臨時檔案一起同步過去 |

## 4. 遷移方式

### 4.1 rsync over SSH（首選）

`rsync` 只傳變化的部分、保留權限與時間戳、走 SSH 加密通道，是遷移最常用的方式。

```bash
# 第一次：服务端还在运行时做"预同步"，把绝大部分数据先搬过去
rsync -aHAX --numeric-ids --delete --info=progress2 \
  --exclude='logs/' \
  --exclude='crash-reports/' \
  --exclude='cache/' \
  --exclude='libraries/' \
  --exclude='versions/' \
  --exclude='session.lock' \
  /opt/mcserver/ \
  mcserver@203.0.113.20:/opt/mcserver/
```

| 選項 | 作用 |
| --- | --- |
| `-a` | 歸檔模式（等價 `-rlptgoD`）：遞歸併保留符號連結、權限、時間、屬組、裝置檔案 |
| `-H` | 保留硬連結 |
| `-A` | 保留 ACL |
| `-X` | 保留擴充屬性（xattr） |
| `--numeric-ids` | 按數字 UID/GID 對映，**跨機器必須加**，否則屬主會錯亂 |
| `--delete` | 讓目標端與源端一致（**雙刃劍**，源端誤刪會被同步過去） |
| `--info=progress2` | 顯示整體進度（rsync 3.1 及以上） |

**任何帶 `--delete` 的指令，第一次都要先加 `-n`（`--dry-run`）與 `-i`（逐項列出變化）跑一遍**，確認它不會刪掉不該刪的東西：

```bash
rsync -aHAX --numeric-ids --delete -n -i \
  --exclude='logs/' --exclude='cache/' \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

:::warn 源路徑末尾的斜槓不能隨手寫
`/opt/mcserver/`（帶斜槓）表示"同步這個目錄裡的內容"；`/opt/mcserver`（不帶斜槓）表示"在目標端建立 `mcserver` 這個目錄再放進去"。**配合 `--delete` 寫錯，可能把目標端的整個目錄結構搞亂。**
:::

### 4.2 tar + scp（小資料量、無 rsync 時）

沒有 `rsync` 或資料量很小的時候，可以用管道直接打包傳輸，不落中間檔案：

```bash
# 在旧机器上执行：打包并通过 SSH 解到新机器
tar -C /opt/mcserver -czf - \
  --exclude='logs' --exclude='crash-reports' --exclude='cache' \
  --exclude='libraries' --exclude='versions' --exclude='session.lock' \
  . | ssh mcserver@203.0.113.20 'mkdir -p /opt/mcserver && tar -C /opt/mcserver -xzf -'
```

也可以先落地再傳：

```bash
tar -czf /tmp/mcserver-2026-10-04.tar.gz -C /opt/mcserver .
scp /tmp/mcserver-2026-10-04.tar.gz mcserver@203.0.113.20:/tmp/
```

缺點是**每次全量、沒有增量、中斷要重來**，幾百 GB 的存檔不適合。

### 4.3 服務商級快照 / 卷複製（最快）

同一家服務商內部遷移時，通常可以給系統盤或資料盤**打快照，再把快照掛到新實例上**，或者直接把雲盤從舊實例解除安裝、掛載到新實例。這比在網路上覆制檔案快幾個數量級。

必須注意：

- **快照的"一致性"取決於你打快照時服務端在不在寫盤。** 要做可靠快照，先停服（或至少 `save-all` + `save-off`），打完再 `save-on`。
- 卷掛載路徑、裝置名、檔案系統 UUID 可能變化，`/etc/fstab` 要用 UUID 或重新配置，否則新實例起不來。
- 跨服務商、跨區域通常**不能**直接掛盤，只能走網路複製。
- 快照裡包含舊機器的 SSH 主機金鑰、舊 IP 的配置、面板憑據——**遷移後要輪換憑據**。

### 4.4 為什麼必須同步兩次

| 階段 | 服務端狀態 | 目的 |
| --- | --- | --- |
| 第一次同步 | **執行中** | 把幾十上百 GB 的存量資料先搬過去，把維護視窗從"幾小時"壓到"幾分鐘" |
| 第二次同步 | **已停服** | 只傳變化的部分，讓目標端與停服瞬間的資料一致 |

第一次同步期間服務端仍在寫盤，所以那份副本**本身不一致**——它的價值只在於"大部分檔案已經就位"，正確性完全依賴第二次同步。因此：

- 第二次同步**必須在停服之後**，並且停服後不要再啟動舊機器（否則又要重新同步）。
- `rsync` 預設按"大小 + 修改時間"判斷是否需要重傳。要更嚴格地按內容比對，第二次可以加 `--checksum`（`-c`）：**更慢，但不會漏掉"大小相同、時間戳被保留、內容卻不同"的檔案。**
- 第二次同步完成後，**再做一次校驗（見下一節）**，不要憑"指令沒報錯"就開服。

## 5. 維護視窗：逐步操作

提前公告維護時間（並說明預計時長與補償方案），然後按下面的順序執行。**每一步都確認結果再進入下一步。**

1. **凍結變更**：通知協管不要再改配置、不要裝插件；確認沒有正在跑的備份/清理任務會與遷移衝突。

2. **再確認一次備份可用**：確認離線備份存在、校驗通過、且**不在**你即將刪除或覆蓋的路徑上。

3. **降低 DNS TTL**：如果還沒降，現在降到 60 - 300 秒（生效需要等舊 TTL 過期，所以這一步其實要**提前 24 - 48 小時**做，見第 6 節）。

4. **停服**：

```bash
sudo systemctl stop minecraft
pgrep -a java          # 必须没有输出，确认进程真的退出了
```

5. **最終同步**（第 4.1 節的指令去掉 `--exclude` 裡不該排的東西，並加上 `-c`）：

```bash
rsync -aHAX --numeric-ids --delete --checksum --info=progress2 \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

6. **校驗**：兩端各生成一份清單再比對。路徑必須是**相對路徑**，否則檔名對不上。

```bash
# 旧机器
cd /opt/mcserver && find . -type f -print0 | sort -z | xargs -0 sha256sum > /tmp/old.sha256

# 新机器（同样命令，输出到 /tmp/new.sha256），然后：
diff /tmp/old.sha256 /tmp/new.sha256 && echo "校验通过"
```

Windows 上可以用 `Get-FileHash -Algorithm SHA256` 逐檔案比對；資料量小時也可以只比對大小與檔案數：

```powershell
Get-ChildItem -Recurse -File C:\mcserver | Measure-Object -Property Length -Sum
```

7. **在新機器上清理執行期殘留**：

```bash
rm -f /opt/mcserver/world/session.lock
```

8. **確認新機器的環境**：Java 版本與舊機一致（`java -version`）、目錄屬主正確、`server.properties` 裡的埠沒和別的服務衝突。

9. **安裝並啟動託管服務**：

```bash
sudo cp minecraft.service /etc/systemd/system/minecraft.service
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
journalctl -u minecraft -n 50 --no-pager
```

10. **用同一個客戶端實測**：先用新 IP 直連（見第 6 節），進服後檢查關鍵建築、容器內容、背包、權限、插件指令是否正常。

11. **切換 DNS**：確認新服正常後，把記錄指向新 IP。

12. **保留舊機器一段時間**：**不要立刻退租或重灌**，它是你的回滾目標（見第 9 節）。

## 6. DNS 與切換

### TTL 要提前降

DNS 記錄有快取時間（TTL）。如果 TTL 是 24 小時，你切換記錄後**最長 24 小時內仍會有玩家被解析到舊 IP**。

```bash
# 查看当前解析与 TTL
dig +noall +answer mc.example.com
dig +noall +answer mc.example.com AAAA
dig +noall +answer _minecraft._tcp.mc.example.com SRV
```

**流程是**：遷移前 24 - 48 小時把 TTL 降到 60 - 300 秒 -> 等舊 TTL 過期 -> 遷移 -> 切換記錄 -> 確認穩定後再把 TTL 調回較大值（減少解析壓力）。

### 切換前怎麼測試新服

**不要在沒驗證新服的情況下先改 DNS。** 兩種安全的測試方式：

| 方式 | 做法 | 適用 |
| --- | --- | --- |
| hosts 檔案 | 在本機 hosts 裡把網域指向新 IP | 隻影響自己，適合服主與協管先驗一遍 |
| 直連新 IP | 客戶端直接填 `203.0.113.20:25565` | 所有人都能用，**不依賴 DNS** |

```text
# Windows: C:\Windows\System32\drivers\etc\hosts
# Linux / macOS: /etc/hosts
203.0.113.20  mc.example.com
```

:::tip 一定要"用同一個客戶端"測
換一台電腦、換一個網路、換一個遊戲版本去測，測出來的都不是玩家的真實體驗。**用平時玩的那個客戶端、在同一條網路上連一次**，才算驗證。
:::

### SRV 記錄別忘了

很多服使用 SRV 記錄讓玩家只填網域（不寫埠）。遷移時**要同時改 SRV 指向的目標**，否則玩家仍然被引導到舊機器：

```text
_minecraft._tcp.mc.example.com. 300 IN SRV 0 5 25565 mc.example.com.
```

### 舊機器要留作回滾目標

切換後**至少保留一個完整維護視窗的時間**（常見做法是 24 - 72 小時，視你的玩家規模與可接受的停機時間而定）：

- 保持舊機器**可以隨時啟動**（配置、資料、Java 環境都別動）。
- 但**不要**讓新舊兩台同時對外服務同一個網域——那會導致玩家資料分裂到兩個世界，後面無法合併。
- 如果舊機器仍會被 DNS 解析到（TTL 還沒過期），可以考慮把舊機器上的服務端**保持停止**，只在需要回滾時啟動。

## 7. IP 變了，連帶影響有哪些

IP 一變，所有"以 IP 為準"的東西都會失效。**這一節漏掉，症狀往往是"玩家能進服，但某個功能莫名其妙不工作"。**

| 受影響的東西 | 症狀 | 處理 |
| --- | --- | --- |
| 其他服務的白名單 | 資料庫、物件儲存、第三方 API 拒絕連線 | 把新 IP 加入允許列表，移除舊 IP |
| RCON / 面板的 IP 允許列表 | 面板顯示實例離線、RCON 連不上 | 面板與守護行程的 allowlist 都要更新（設定項以各面板官方文件為準） |
| 防火牆 / 雲安全組 | 埠不通，或反向代理連不上後端 | 新機器加規則，**舊機器記得收口**，避免留下暴露面 |
| TLS 憑證與反向代理 | HTTPS 報錯、憑證網域不符 | 憑證隨機器搬或重新簽發；代理的 upstream 改成新 IP |
| Geyser / Floodgate 與群組服 | 基岩版玩家進不來，或玩家 IP 全部變成代理 IP | 轉發配置要一起搬；詳見 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup) 與 [跨服端](/tutorials/java/proxy) |
| IP 封禁名單 | `banned-ips.json` 裡的條目可能指向舊環境；或者因為轉發配置變了，**所有玩家都顯示為代理 IP，一禁就是全服** | 遷移後檢查轉發是否生效，再決定是否清理 IP 封禁 |
| 監控與告警 | 探針還盯著舊 IP，新服掛了沒人知道 | 更新探針目標，並**故意觸發一次告警**確認鏈路通 |
| 備份任務 | 備份還在從舊機器取資料，或新機器的備份沒配 | 見 [備份與恢復](/tutorials/java/backup) 與 [異地備份](/tutorials/ops/offsite-backup) |
| 白名單裡的基岩版玩家 | 基岩版玩家的身份與 XUID 繫結，通常**不受 IP 變化影響** | 一般無需改動；但轉發/權限插件若依賴 IP，仍需複核 |

:::note 關於 IP 封禁
IP 封禁本來就不適合長期使用（家寬 IP 會變、機房 IP 會被複用）。遷移前後如果發現封禁列表裡有大量 IP 條目，**先確認它們還有效再決定是否保留**，不要盲目照搬。
:::

## 8. 遷移後驗證清單

| 驗證項 | 怎麼驗 | 通過標準 |
| --- | --- | --- |
| 玩家能進服 | 用真實客戶端（含基岩版，如果開了跨平台）各進一次 | 能進、能聊天、能正常移動與互動 |
| TPS / MSPT 正常 | `/tps`、`/spark tps` 或核心自帶指令 | 與舊機器同一量級，沒有持續性掉刻 |
| 插件 / 模組全部載入 | 啟動日誌裡搜 `Enabling`、`Loaded`、報錯關鍵字 | 沒有 `Could not load`、沒有版本不相容 |
| 配置生效 | 抽查權限、經濟、領地、傳送點 | 與遷移前一致 |
| 名單正確 | `/whitelist list`、`/op` 相關指令或直接看名單檔案 | 管理員與白名單與舊服一致 |
| 備份在新機器上跑 | 手動執行一次備份腳本 | 歸檔生成、大小合理、**並且真的能解出來** |
| 監控已更新 | 看監控面板 | 新 IP 有心跳，舊 IP 的告警已關閉 |
| 定時任務 | `crontab -l`、`systemctl list-timers` | 備份、重啟、清理任務都在，時間正確 |
| 效能與磁碟 | `df -h`、`iostat`、記憶體佔用 | 磁碟餘量充足，沒有明顯的 IO 瓶頸 |
| 舊機器下線 | 見下 | **只有在回滾視窗結束後**才退租或重灌 |

## 9. 回滾方案

回滾不是"再搬回去"，而是"**回到一個已知可用的狀態**"。所以回滾方案必須在遷移**之前**寫好：

1. **定義觸發條件**：什麼情況下回滾？（例如：新服 2 小時內無法穩定啟動、存檔校驗失敗、關鍵插件無法工作、TPS 只有舊機一半且無法定位原因。）
2. **明確回滾動作**：把 DNS 指回舊 IP -> 在舊機器上啟動服務 -> 公告說明 -> 事後分析。
3. **保留回滾目標**：舊機器的服務端目錄、Java 環境、systemd unit、防火牆規則**原樣保留**，直到回滾視窗結束。
4. **準備資料取捨規則**：如果新服已經開了一段時間、玩家已經在上面玩過，**舊世界的進度是落後的**。回滾意味著這段時間的進度丟失，或者需要人工把新世界的存檔搬回來（此時"新世界"才是最新的資料）。**這個決定必須在回滾前明確，不能邊回滾邊想。**
5. **回滾也要校驗**：從舊機器啟動前，確認它的資料與停機時一致（沒被備份腳本改過、沒被誤刪）。

:::warn 最壞的情況是"兩邊都在跑"
如果新舊兩台伺服器同時對外服務（例如 DNS 快取導致一部分玩家連舊服、一部分連新服），**玩家資料會分裂到兩個世界**。這種分裂通常無法自動合併，只能接受其中一份資料丟失。**切換前把舊服停掉，是避免這個事故最簡單的方法。**
:::

## 10. 小結

- **先盤點，再動手**：遷移失敗多半不是技術問題，而是"忘了自己還跑著什麼"。
- **備份必須驗證過**：沒驗證過的備份不是備份，是心理安慰。
- **同步兩次**：一次預熱（執行中），一次定稿（停服後），中間不要重啟舊服。
- **先測再切**：hosts 檔案或直連 IP 驗證新服，然後再改 DNS。
- **TTL 提前降**：這是唯一"必須提前做"的步驟，臨時降 TTL 來不及。
- **留好回滾目標**：舊機器不是垃圾，它是你的退路。
