很多人開服的第一台"伺服器"，就是自己桌上那台電腦。它便宜、效能好、你完全掌控——但它**不是為 7x24 小時執行設計的**。這一篇講清楚：家用電腦到底適不適合開服，以及如果你決定這麼做，**長期怎麼維護才不出事**。

如果你還沒決定路線，先看 [部署到可存取環境](/tutorials/java/deploy) 裡的三條路線對比。

## 1. 家用電腦到底適不適合開服

先把"能跑"和"適合長期跑"分開。家用機跑 MC 服務端**效能上通常綽綽有餘**（現代桌面 CPU 的單核效能普遍強於同價位雲伺服器），真正的短板在**可靠性、網路和維運成本**上。

| 維度 | 家用電腦 | VPS / 雲伺服器 |
| --- | --- | --- |
| 一次性成本 | 已有機器則近乎為零 | 無，但按月付費 |
| 持續成本 | **電費**（見下），夏天還有空調費 | 月租，配置越好越貴 |
| 單核效能 | 通常更強，同價位優勢明顯 | 同價位偏弱 |
| 公網 IP | **多數家庭寬頻沒有公網 IPv4** | 一般自帶 |
| 電力 | 自家停電即掉線，需 UPS | 機房有 UPS 與發電機 |
| 網路 | 家寬上行小、可能被運營商限速 | 機房頻寬大且對稱 |
| 噪音/發熱 | 在自己房間裡 | 在機房 |
| 被攻擊 | 打的是你家 IP，影響全家網路 | 打的是機房，可加高防 |
| 資料安全 | 硬碟壞了你自己負責 | 通常有快照，但**服務商會跑路** |

### 誰應該直接用 VPS

經常不在家（家裡出事無法遠端處理）、玩家已超過十幾人（上行頻寬先撐不住）、不想被 DDoS 牽連全家網路、對噪音發熱敏感（宿舍/合租/臥室），或者**資料重要性高於省錢**的人，直接買 VPS 更省心。

### 關於"24/7"：到底是什麼在打斷它

家用機做不到 24 小時線上，通常不是硬體不行，而是這些：

| 中斷來源 | 說明 | 緩解 |
| --- | --- | --- |
| 系統睡眠/休眠 | 預設電源計劃會在空閒後睡眠，**服務端直接斷線** | 關掉睡眠（見第 2 節） |
| 停電 | 最常見的掉線原因，且**可能損壞存檔** | UPS + BIOS 來電自啟 |
| 系統自動更新重啟 | Windows 預設會在夜裡自動重啟 | 設定活動時間 / 手動安排重啟視窗 |
| 路由器重啟或撥號掉線 | 家寬常見 | 定期檢查；DDNS 應對 IP 變化 |
| 過熱降頻或保護性關機 | 灰塵堵塞、風扇停轉 | 清灰、監控溫度 |
| 你自己手滑 | 踢到機箱、拔錯插頭 | 物理安全（見第 8 節） |

:::warn 一次意外關機可能比你想的貴
服務端正在寫區塊時斷電，最壞情況是**存檔損壞**，只能回檔到上一次可用備份。所以第 2 節和 [備份與恢復](/tutorials/java/backup) 是配套的：**供電保護與備份缺一不可**。
:::

### 電費：先算一筆賬再決定

電費 = 功率（kW）x 時間（h）x 電價（元/kWh）。用功率計（或插座式功耗計）實測最準，下面是**量級估算**，實際差異很大：

| 場景 | 整機功耗（量級） | 每月（30 天） |
| --- | --- | --- |
| 低功耗小主機 / 筆記本 | 10 - 25 W | 7 - 18 kWh |
| 桌面機待機/輕載 | 40 - 80 W | 29 - 58 kWh |
| 桌面機持續滿載（高頻 CPU + 獨顯空轉） | 120 - 250 W | 86 - 180 kWh |

把上面的 kWh 乘以你當地電價就是月成本。**獨立顯示卡待機也會耗電**（常見 5 - 20 W，具體看型號），純服務用途可以考慮核顯或拆掉獨顯。空調在夏天會把這份熱量**再放大一到兩倍**的製冷電費。

## 2. 供電穩定性

### 為什麼"存檔寫到一半斷電"很危險

MC 的區塊是**分檔案寫入**的，寫入過程中斷電可能留下**半寫狀態的檔案**。恢復時輕則丟幾個區塊，重則存檔無法載入。即使有 `save-all`，也無法保證斷電瞬間磁碟上的所有檔案都處於一致狀態。**這就是 UPS 與備份存在的理由**——不是為了"不斷線"，而是為了**讓服務端有機會安全停機**。

### UPS：家用該買多大

UPS 的目標不是讓你停電繼續玩幾個小時，而是**撐過短時閃斷 + 給服務端爭取安全關機的幾分鐘**。

估算方法：

1. 測出整機功耗 `P`（瓦）。
2. 決定需要的後備時間 `T`（分鐘），家用 **5 - 15 分鐘**通常足夠。
3. 需要的容量（Wh）≈ `P x T / 60 / 0.6`（0.6 是逆變效率與電池老化的保守係數）。
4. 換算成 VA：UPS 標稱 VA 與 W 的關係取決於功率因數，家用 UPS 常見 PF 約 0.5 - 0.6，**以產品銘牌標註的 W 為準**。

例子：整機 80 W，希望撐 10 分鐘，則約需 `80 x 10 / 60 / 0.6 ≈ 22 Wh` 的有效容量，選一台標稱 **500 - 650 VA / 300 W 左右**的後備式 UPS 就有餘量。**具體型號的容量與介面以廠商規格書為準**，不要按經驗值下單。

| UPS 類型 | 特點 | 適合 |
| --- | --- | --- |
| 後備式（Standby） | 便宜，切換時有幾毫秒中斷 | 家用小主機，電源素質好 |
| 線上互動式（Line-Interactive） | 帶 AVR 穩壓，切換更快 | 電壓不穩的地區，推薦 |
| 線上式（Online / Double-Conversion） | 全程逆變供電，輸出最乾淨，最貴、發熱最大 | 對供電極敏感的裝置 |

### 為什麼"純正弦波"重要

主動式 PFC（Active PFC）的電源**對輸入波形敏感**。方波/階梯波（模擬正弦）輸出的 UPS 可能讓主動 PFC 電源**識別異常、發出異響、甚至直接關機**——那正好發生在停電、你最需要它工作的時候。所以：

- 確認 UPS 輸出是 **純正弦波（Pure Sine Wave）**，而不是"模擬正弦/階梯波"；
- 如果整機功耗接近 UPS 上限，風險更大；
- 具體相容性**取決於電源型號與 UPS 型號**，無法一概而論，購買前查廠商說明。

:::tip 順便買一個帶浪湧保護（Surge Protection）的插座
雷擊與電網浪湧是另一類殺手。UPS 通常自帶浪湧保護，若不用 UPS，至少用合格的防浪湧插排。
:::

### 讓系統永不睡眠

**Windows（管理員權限的 PowerShell 或 CMD）**

```bat
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 0
powercfg /change disk-timeout-ac 0
```

- `standby-timeout-ac 0` 表示**交流供電時永不進入睡眠**（`0` 即"從不"）。
- 桌上型電腦一般沒有電池，`-ac`（交流）就是你要改的那一項；**筆記本**還要改 `-dc`（電池），否則拔掉電源後照樣睡眠。
- 檢視當前設定：`powercfg /query SCHEME_CURRENT SUB_SLEEP`。
- **注意**：Windows 的"快速啟動"與"休眠"是另一回事，企業策略或廠商電源管理軟體可能覆蓋這些值。

**Linux（systemd）**

先看哪些目標被"允許"進入：

```bash
systemctl status sleep.target suspend.target hibernate.target hybrid-sleep.target
```

阻止系統睡眠：

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

**筆記本合蓋**由 logind 處理，編輯 `/etc/systemd/logind.conf`：

```ini
HandleLidSwitch=ignore
HandleLidSwitchExternalPower=ignore
HandleLidSwitchDocked=ignore
```

改完執行 `sudo systemctl restart systemd-logind` 生效。

:::warn 具體鍵名與預設值隨發行版與 systemd 版本而不同
`logind.conf` 的可選值（`ignore` / `poweroff` / `suspend` / `hibernate` / `lock`）與預設行為在不同發行版、不同 systemd 版本上不完全一致，**改之前先讀 `man logind.conf`**，並確認改動不會被桌面環境的電源管理覆蓋。桌面發行版（GNOME/KDE）通常還有自己的"空白屏幕後掛起"開關。
:::

### BIOS：停電恢復後自動開機

斷電恢復後機器**預設不會自己開機**，你必須手動按電源鍵——如果人在外地，服務就一直是停的。

進 BIOS/UEFI，找到類似下面這些名字的選項（**名稱隨主機板廠商與 BIOS 版本不同**，通常在 `Power` / `Advanced` / `APM Configuration` 分類下）：

| 常見名稱 | 作用 |
| --- | --- |
| `Restore on AC Power Loss` | 來電後的行為，選 `Power On` / `Always On` |
| `AC Power Recovery` / `AC Recovery` | 同上，Dell 等常用此名 |
| `After Power Failure` | 同上，常見於 DIY 主機板 |

選 **`Power On` / `Always On`**（不要選 `Last State`：如果斷電時是開機狀態它也會開機，但若上次是關機狀態則不會）。

配套檢查：

- **關閉"快速啟動"**（Windows 的 Fast Startup 會讓關機變成混合休眠，影響自動開機與磁碟一致性）；
- **設定 BIOS 超級密碼**，防止誤改；
- 若機器要長期無人值守，**開啟來電自啟 + 關閉一切"節能待機"選項**。

## 3. 散熱與灰塵

### 風道與擺放

- **進風要有濾網，出風要通暢**。常見有效佈局：前面/底部進風、後面/頂部出風，保持**進風量略大於出風量**（正壓），灰塵更少從縫隙鑽進來。
- **別塞進封閉櫃子**，別貼牆、別放在地毯上。機器四周留出空間。
- **硬碟最怕震動**：機械硬碟不要放在會被踢到、撞到的位置（見第 8 節）。

### 清灰

| 頻率 | 做什麼 |
| --- | --- |
| 每 1 - 3 個月 | 檢查進風濾網，明顯積灰就清 |
| 每 3 - 6 個月 | 用壓縮空氣/吹塵器清理散熱器、風扇、電源進風口 |
| 每 6 - 12 個月 | 視積灰程度決定是否重新塗矽脂（**不是必須**，溫度正常就別動） |

清灰要點：**吹風扇時用手或塑膠片擋住扇葉**，別讓氣流把風扇吹到高速空轉（可能損壞軸承）；不要用吸塵器直接貼電路板（靜電風險）；清理後**確認所有風扇都轉**（含電源、顯示卡、機箱風扇）。

### 溫度監控

**Linux**：`lm-sensors` 是讀取主機板/CPU 溫度感測器的常用工具。是否可用、能讀到哪些感測器**取決於主機板與晶片組驅動**，部分平台（尤其是較新的筆記本與部分主機板）支援不完整。

```bash
sudo apt install lm-sensors      # Debian / Ubuntu
sudo dnf install lm_sensors      # Fedora / RHEL 系
sudo sensors-detect              # 探测可用传感器，交互式回答
sensors                          # 输出当前读数
watch -n 5 sensors               # 每 5 秒刷新
```

**Windows**：工作管理員（`Ctrl+Shift+Esc`）的"效能"頁可以看到 CPU/GPU 溫度（**可用性取決於硬體與驅動**）；需要更細的讀數（各核心、硬碟 SMART 溫度、風扇轉速）用 HWiNFO、HWMonitor 一類工具。

### 過熱的表現

| 現象 | 含義 |
| --- | --- |
| TPS 突然下降但 CPU 佔用不高 | CPU 被降頻（thermal throttling） |
| CPU 頻率低於基準頻率 | 同上，用 `lscpu`/`cpupower` 或 HWiNFO 看即時頻率 |
| 風扇長期滿載、聲音變大 | 積灰或矽脂老化 |
| 無故關機/重啟 | 觸發了過溫保護，**這是嚴重訊號**，要立刻處理 |

`dmesg` 裡出現 `CPU0: Core temperature above threshold`、`thermal throttling` 一類資訊，說明已經觸發了保護。**具體日誌文本隨核心與硬體不同**，以你機器上實際輸出為準。

## 4. 家庭網路

### 為什麼 Wi-Fi 不適合長期開服

- **延遲抖動（jitter）比平均延遲更致命**：MC 對丟包和抖動敏感，玩家會表現為"回彈""卡頓""瞬移"。
- **通道干擾與鄰居 Wi-Fi 擁擠**，晚上更明顯。
- **省電機制**：無線網絡卡會進入省電模式，帶來週期性延遲尖峰。
- **穩定性**：AP 重啟、韌體問題都會斷線。

**結論：能插網線就插網線。** 如果機器離路由器遠，用電力貓（受電路影響大）、MoCA（同軸）或乾脆拉一根網線。下面三條講清楚家寬最常見的三個坑。

### 有沒有公網 IPv4：怎麼判斷

1. 登入路由器，找到 **WAN 口 IP**。
2. 在機器上訪問一個"我的 IP"查詢網站，或執行 `curl -4 ifconfig.me`。
3. **兩者不一致**：你大機率處在運營商 NAT（CGNAT）後面，**沒有公網 IPv4**，做埠對映也沒用。
4. 補充判斷：CGNAT 的 WAN IP 常落在 `100.64.0.0/10` 這一段（RFC 6598 共享位址空間）。**這不是硬性規則**，只是常見特徵。

:::warn IPv6 是另一條路，但不是萬能藥
部分地區家寬有公網 IPv6，理論上可以直連，但**玩家的網路環境不一定支援 IPv6**，很多客戶端仍走 IPv4。以 IPv6 為主的方案要確認玩家側可用性。
:::

### 動態 IP 與 DDNS

家庭寬頻的公網 IP **會變**（重新撥號、運營商調整）。DDNS（動態域名解析）解決的就是這件事：

1. 註冊一個 DDNS 服務（或使用域名商的 API）。
2. 在路由器或機器上執行更新客戶端，**定期把當前公網 IP 上報**給 DDNS。
3. 玩家用**域名**而不是 IP 連線。

要點：

- **DDNS 只解決"IP 變了怎麼找到你"**，解決不了 CGNAT——沒有公網 IP 時 DDNS 也沒用。
- 更新間隔別太短（會被限流），幾分鐘一次通常夠。
- 如果你用內網穿透（frp 等），玩家的入口是**中轉伺服器的 IP**，DDNS 就不必要了。

### 上行頻寬才是瓶頸

家寬通常**下行幾百兆、上行幾十兆甚至更少**。MC 服務端的流量幾乎全是**上行**（把世界資料發給玩家）。

粗略估算：一個玩家正常遊玩的頻寬需求在**幾十到幾百 kbps** 量級，視視距、實體數量、區塊載入速度而定，**波動極大**。用 `Mbps` 簡單折算：

| 上行頻寬 | 理論併發上限（按每玩家 0.5 Mbps 保守估算） |
| --- | --- |
| 10 Mbps | 約 20 人 |
| 20 Mbps | 約 40 人 |
| 50 Mbps | 約 100 人 |

**這只是量級參考**，實際取決於玩法（紅石/大量實體/高視距會顯著提高需求）。務必**實測**：用路由器或系統工具觀察服務端行程的上行佔用。

:::tip 先測再定人數上限
在服務端目錄跑一段時間後，用 `iftop`、`nload`（Linux）或工作管理員/資源監視器（Windows）看實際上行佔用，再決定能帶多少人。**別按"我下行 500M"來估算。**
:::

## 5. 作業系統維護例程

### 更新策略

- **固定一個維護視窗**（例如每週一次），在視窗內做系統更新與重啟。
- **更新前先備份**（見 [備份與恢復](/tutorials/java/backup)），並確認備份檔案在**另一塊盤或異地**。
- **不要開無人值守自動重啟**：讓它在你選定的時間重啟，而不是半夜。
- 核心/系統大版本升級後，**重啟一次再確認服務端正常**。

**Debian / Ubuntu**

```bash
sudo apt update
sudo apt upgrade
sudo apt autoremove --purge
```

**Fedora / RHEL 系**

```bash
sudo dnf upgrade --refresh
sudo dnf autoremove
```

**Windows**：設定 -> Windows 更新 -> 進階選項，把"活動時間"設成你的維護視窗之外；重要更新手動重啟。

### 磁碟健康（SMART）

`smartmontools` 是讀取 SMART 資料的標準工具（`smartctl` 是其中的命令）。

```bash
sudo apt install smartmontools
sudo smartctl -a /dev/sda
```

:::warn 裝置名一定要確認
`/dev/sda` 只是**示例**。NVMe 盤通常是 `/dev/nvme0n1`，SATA 盤可能是 `/dev/sdb`。**用錯裝置名會讀到別的盤的資料，甚至（在寫操作時）造成破壞。** 先用 `lsblk` 確認：

```bash
lsblk -o NAME,SIZE,MODEL,MOUNTPOINT
```
:::

**SATA 盤要重點看的屬性**（屬性名與編號由 ATA/SMART 標準定義，不同廠商的原始值編碼可能不同，**看"VALUE/WORST/THRESH"與"RAW"要結合廠商說明**）：

| 屬性 | 含義 | 怎麼判斷 |
| --- | --- | --- |
| `Reallocated_Sector_Ct`（ID 5） | 已重對映的壞扇區數量 | **不為 0 就要警惕**，持續增長說明盤在退化 |
| `Current_Pending_Sector`（ID 197） | 待處理扇區（讀取失敗但尚未重對映） | **任何非 0 值都要立刻備份** |
| `Offline_Uncorrectable`（ID 198） | 離線掃描無法糾正的扇區 | 非 0 說明已有不可恢復錯誤 |
| `UDMA_CRC_Error_Count`（ID 199） | 傳輸校驗錯誤 | 增長通常是**線材/介面問題**，不是盤壞 |
| `Reported_Uncorrect`（ID 187） | 上報的不可糾正錯誤 | 與 197/198 一起看 |

**NVMe 盤**看的是另一組欄位：

```bash
sudo smartctl -a /dev/nvme0n1
```

關注 `Percentage Used`（壽命消耗百分比）、`Available Spare`（可用備用塊）、`Media and Data Integrity Errors`、`Critical Warning`。

**定期自檢**（會佔用一些時間，建議在維護視窗跑）：

```bash
sudo smartctl -t short /dev/sda     # 短自检，通常 1-2 分钟
sudo smartctl -t long  /dev/sda     # 长自检，可能数小时
sudo smartctl -l selftest /dev/sda  # 查看自检结果
```

**監控建議**：`smartd` 可以常駐並郵件告警；桌面使用者至少做到**每季度手動看一次**。

### SSD 壽命

SSD 的壽命由**寫入量（TBW）**決定，不是通電時間。頻繁全量備份、日誌狂寫、頻繁 `save-all` 都會消耗壽命。用 `smartctl` 的 `Data_Units_Written`（SATA）或 `Data Units Written`（NVMe）估算總寫入量；**把日誌與備份寫到別的盤**能顯著降低系統盤寫入。SSD 快滿時效能與壽命都會惡化，**留出至少 10% - 20% 空閒空間**。

### 檔案系統檢查與日誌

- **ext4**：異常斷電後可能要求 `fsck`。**不要在掛載狀態下對根分區執行 `fsck`**；現代發行版在啟動時自動檢查。手動檢查未掛載分區用 `sudo fsck -f /dev/sdb1`（先 `umount`）。
- **Btrfs / ZFS**：有各自的檢查與清理工具（`btrfs scrub`、`zpool scrub`），**具體命令與用法隨版本不同，以其官方文件為準**。
- **日誌增長**：用 `journalctl --disk-usage` 看 systemd 日誌佔用，用 `sudo journalctl --vacuum-size=500M` 限制大小；日誌輪轉由 `logrotate` 負責，一般預設已配好。
- **Windows**：事件檢視器會無限增長，可在"事件檢視器 -> Windows 日誌 -> 屬性"裡設定最大大小與覆蓋策略；`cleanmgr` 可清理系統檔案。

### 清理舊備份

**這是最容易把盤寫滿的地方**：服務端目錄持續增長，若保留策略是"全部留著"，幾個月就會塞滿磁碟——**磁碟滿會導致服務端寫存檔失敗**。明確保留策略（例如每日 7 份 + 每週 4 份）並讓腳本自動刪除超期備份，定期 `df -h` 確認剩餘空間。詳見 [異地備份](/tutorials/ops/offsite-backup) 的保留策略與磁碟空間計算。

## 6. 遊戲服務端維護例程

### 計劃性重啟

**定期重啟**能回收記憶體碎片、清理未釋放的資源，常見做法是**每天或每幾天一次**，選在低峰期（凌晨）。重啟方式：通過控制台傳送 `stop`（**不要直接殺行程**），等待行程完全退出後再啟動；**重啟前先確認備份成功**。用 systemd 託管時 `systemctl restart minecraft.service` 會走正常的停止流程（前提是服務端能收到 `stop`；若啟動方式無法接收控制台輸入，需要改用 `screen`/`tmux` 或 RCON 傳送命令）。

:::warn 直接斷電式重啟很危險
`kill -9`、工作管理員"結束任務"、直接按電源鍵，都可能讓服務端來不及儲存。**能用 `stop` 就用 `stop`。**
:::

### 確認備份真的在跑

**這是維護清單裡最容易被跳過、也最致命的一項。** 檢查**備份檔案的修改時間與大小**（不是檢查"腳本存在"），檢查**日誌裡的退出碼**（非 0 就是失敗），並定期**真的恢復一次**（見 [異地備份](/tutorials/ops/offsite-backup) 的恢復演練）。

```bash
ls -lh /backup/mcserver/ | tail -5
tail -20 /var/log/mc-backup.log
```

### 看日誌與崩潰報告

- **`logs/latest.log`**：當前/最近一次執行的日誌。搜尋 `WARN`、`ERROR`、`Exception`、`Caused by`。
- **`crash-reports/`**：崩潰報告，含完整堆疊與當時的環境資訊，**是排查崩潰的第一手資料**。
- 常見訊號：記憶體不足（`OutOfMemoryError`）、插件報錯、區塊載入失敗、端口占用。

```bash
grep -nE "ERROR|Exception|Caused by" logs/latest.log | tail -40
ls -lt crash-reports/ | head
```

### 用 spark 看 TPS

**spark** 是常用的效能分析插件/模組（Bukkit 系、Fabric、Forge 等都有對應版本），能取樣 TPS、MSPT 與卡頓來源。常用命令 `/spark tps`、`/spark profiler start` / `/spark profiler stop`（**具體子命令以 spark 官方文件為準**，不同版本略有差異）。**TPS 長期低於 20 說明服務端跟不上**，**MSPT 持續高於 50 ms** 同樣說明單個 tick 超時。先用 `/spark tps` 判斷"是不是真的卡"，再用 profiler 找"是誰在卡"；系統排查見 [效能最佳化](/tutorials/java/optimize)。

### 觀察記憶體增長

**Java 堆記憶體不是"用滿就是壞"**：GC 會保留一部分，關鍵是看**老年代在 Full GC 後能否回落**。如果 Full GC 後佔用**持續抬升**且不回落，很可能是**記憶體洩漏**（常見於插件）。排查手段：加 GC 日誌（JDK 9+ 用 `-Xlog:gc*`，JDK 8 用 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps`），或讓 spark 取樣。**不要用"加大 -Xmx"來掩蓋洩漏**，那隻會把崩潰推遲。

### 安全地更新服務端

固定流程，一步都別省：

1. **完整備份**（存檔 + 插件 + 配置），並確認備份檔案存在且大小正常。
2. **讀 changelog 並確認 Java 版本要求**：留意破壞性變更（配置格式變更、插件不相容、Java 版本提高）。
3. **先在測試副本上跑**：複製一份服務端目錄，用新版本啟動，確認能起來、插件載入正常。
4. **低峰期切換**：停服 -> 替換 jar -> 啟動 -> 觀察日誌 -> 讓玩家驗證，並**保留舊版本**以便回退。

:::tip 更新前把"回退方案"寫下來
"如果新版本起不來，我要執行哪幾條命令"——寫清楚。出事時人在慌，靠記憶容易漏步驟。
:::

## 7. Windows 與 Linux 的差異

| 事項 | Windows | Linux |
| --- | --- | --- |
| 禁止睡眠 | `powercfg /change standby-timeout-ac 0` | `systemctl mask sleep.target ...`；筆記本另配 `logind.conf` |
| 服務常駐 | 任務計劃程式 / NSSM 一類包裝器 / `start.bat` 迴圈 | systemd unit（推薦） |
| 定時任務 | 任務計劃程式（GUI） | cron / systemd timer |
| 更新 | Windows 更新，注意"活動時間"與自動重啟 | `apt` / `dnf`，自己決定何時重啟 |
| 磁碟健康 | 廠商工具 + 事件檢視器 | `smartctl` + `smartd` |
| 溫度 | 工作管理員 / HWiNFO 一類 | `lm-sensors`（支援程度依主機板而定） |
| 日誌 | 事件檢視器，需手動設上限 | `journalctl` + `logrotate` |
| 大小寫敏感 | **不敏感**（`World` 與 `world` 是同一個） | **敏感**（`World` 與 `world` 是兩個） |
| 換行符 | CRLF 可能導致腳本在 Linux 上無法執行 | LF |

:::warn 大小寫敏感是跨平台遷移的經典坑
把 Windows 上跑得好好的服務端目錄整體拷到 Linux，**插件配置裡寫錯的路徑大小寫**會立刻暴露成"檔案找不到"。遷移前統一檢查一遍。
:::

## 8. 物理安全

伺服器放哪裡，直接決定它會不會被打斷：

- **不要放在會被踢到、絆到線的地方**（走道、桌下伸腳處、床邊），也不要放在水杯、飲料、魚缸、窗台附近——液體進機箱是報廢級故障。
- **不要用容易被誤拔的插座**（和吹風機、電水壺共用的插排尤其危險）；**機箱放穩**，機械硬碟尤其怕震動。
- **給線纜貼標籤**：電源線、網線、顯示器線各是哪一根，寫清楚，並給網線介面做防拉（走線固定）。
- 有條件的話，**把機器和日常桌面分開**，減少"順手關機""順手拔線"的機率。

:::tip 做一個"禁止斷電"的標籤
在插頭和機箱上貼一張紙條："此機為伺服器，請勿斷電/拔線"。家裡有其他人時，這張紙的價值極高。
:::

## 9. 維護日曆

把下面這張表當成最低要求，按你的實際情況加密或放寬。

| 週期 | 任務 |
| --- | --- |
| **每日** | 看一次服務端是否線上；掃一眼 `logs/latest.log` 有無 ERROR；確認昨晚的備份檔案已生成 |
| **每週** | 檢查磁碟剩餘空間（`df -h`）；檢查備份日誌退出碼；看一次 TPS（`/spark tps`）；確認無異常重啟記錄 |
| **每月** | 檢查 SMART（`smartctl -a`）關鍵屬性；檢查記憶體趨勢與 Full GC 表現；清理超期備份；檢查系統更新並安排在視窗內重啟 |
| **每季度** | **恢復演練**（真的恢復一次並啟動驗證）；清灰與檢查風扇；檢查 UPS 電池狀態；審查埠對映/DDNS/防火牆規則；檢查磁碟空間增長趨勢並調整保留策略 |
| **每年** | 更換 UPS 電池（視型號與狀態）；評估硬體老化（硬碟通電時長、SSD 寫入量）；複核保留策略與異地副本是否仍然有效 |

:::warn 恢復演練不是可選項
"備份腳本每天在跑"和"備份能恢復"是兩件事。**沒驗證過恢復的備份不算備份**，詳見 [異地備份](/tutorials/ops/offsite-backup)。
:::

## 10. 小結

家用電腦開服**不是不行，而是要把"可靠性"當成一件需要主動維護的事**：關掉睡眠、配好 UPS 與來電自啟、插網線、按週期更新與檢查磁碟、定期真的恢復一次備份。做到這些，一台家用機可以穩穩跑很久。
