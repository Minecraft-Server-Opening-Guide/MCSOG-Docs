封禁是伺服器運營裡**唯一會直接剝奪玩家帳號權益**的動作，也是最容易引發爭吵的動作。這一篇講的不是工具，而是**流程**：誰有權限封人、依據什麼封、封多久、玩家怎麼申辯、你如何回覆。

工具層面見 [NDPReforged 聯合封禁系統](/tutorials/ops/ndpr)（講的是跨服同步封禁名單怎麼裝、怎麼配），證據採集見 [反作弊與防破壞](/tutorials/java/anticheat) 與 [[JAVA] 安全插件](/tutorials/ops/security-java)，日常玩家管理見 [[JAVA] 經營管理](/tutorials/ops/management-java)。

:::warn 本文的命令與配置以官方文件為準
下面出現的插件名、命令語法、路徑與服務名**會隨服務端軟體、插件版本、發行版與安裝方式變化**。示例的作用是說明"該做什麼"，**不是可以直接照抄的成品**；落地前請對照你所裝插件與系統的官方文件，以及你自己伺服器上實際生成的設定檔。
:::

## 1. 為什麼需要一份寫下來的流程

大多數伺服器不是"壞在管理太嚴"，而是**壞在沒有規則可循**。寫下來至少解決四件事。

**第一，一致性。** 同一個行為，今天封三天、明天封永久，玩家之間會互相傳："看人下菜碟。"一旦玩家相信處理結果是隨機的，規則就失去了約束力——**威懾來自可預測性，而不是嚴厲程度**。

**第二，擋住"管理濫用"的指控。** 只要封禁是"我當時的判斷"，任何一次封禁都可以被解讀成私人恩怨。而"依據第 3.2 條、證據是 CoreProtect 記錄、由 A 決定、由 B 複核"是**可以核驗的陳述**。指控不會因此消失，但你有東西可以拿出來。

**第三，減少無謂的爭吵。** 絕大多數"封禁糾紛"其實是**資訊不對稱**：玩家不知道被封的原因，或者只知道一句"違規"。流程裡規定"封禁時必須寫明原因並告知申訴渠道"，能消掉一大半這類對話。

**第四，讓自己少犯錯。** 冷靜期、複核、留檔，這些機制的成本很低，但能攔住"半夜被氣到、順手 /ban 了"這類事後後悔的操作。

:::tip 流程的最低可用版本
如果一次只能做一件事，那就做這件：**每一次封禁都留下"時間、玩家、原因、證據位置、決定人"五要素的記錄**。哪怕只是 Discord 裡一個固定頻道，也比什麼都沒有強得多。
:::

## 2. 什麼算可封禁的行為

規則必須**短、可檢查、不靠解釋**。下面這份清單可以直接抄進你的規則頁，括號裡是判定要點。

| 行為 | 判定要點 |
| --- | --- |
| 破壞建築（Griefing） | 未經許可改動他人建築或公共區域，有方塊記錄可查 |
| 偷竊 | 從他人容器取走物品；記錄插件能給出"誰、何時、哪個座標" |
| 作弊與漏洞利用 | 使用外掛、透視、自動點選，或利用複製、卡牆、刷物品等漏洞 |
| 仇恨言論 | 針對種族、性別、宗教、性取向、地域的攻擊性言論 |
| 廣告刷屏 | 在公共頻道反覆發佈其他伺服器、私服或交易資訊 |
| 人肉與威脅（Doxxing） | 公開他人真實身份資訊，或進行現實威脅 |
| 逃避封禁 | 換號、換 IP 繼續進入；這是**加重情節**，不是獨立小錯 |

這份清單有三個共同特徵，也是它可用的原因：**行為可觀察**（有記錄或截圖）、**規則已公佈**（玩家事先能看到）、**處置可解釋**（你能說出違反了哪一條）。

關於"逃避封禁"多說一句：它通常意味著**從臨時升級為永久**。理由不是"你更壞了"，而是"你已經證明臨時措施對你無效"。

## 3. 什麼不該封

同樣重要的是**邊界**。下面這些情況封人，是把自己推到理虧的一邊。

- **首次的輕微失誤。** 第一次誤挖了別人的田、第一次在公屏說錯話、第一次把東西放錯地方——先提醒、先要求恢復，比直接封禁更有效，也更容易被接受。
- **對未公佈規則的"違規"。** 如果某條規則從來沒有寫在玩家能看到的地方，那麼**它不存在**。你不能因為別人不知道一條你腦子裡的規定而處罰他。要處罰，先把規則補上，並說明"從即日起生效"。
- **規則解釋上的分歧。** 玩家對規則的理解與你不同，這是**規則寫得不夠清楚**的訊號，不是惡意。正確反應是修規則，而不是封人。
- **你不喜歡的行為。** 技術好、話多、愛提意見、不參與你的活動——這些都不是可封禁的行為。
- **連坐。** "他的朋友也罵過人""這個 IP 上次有問題"不是證據。處罰針對**具體帳號的具體行為**。

:::note 一條好用的自檢
在按下封禁之前問自己一句：**如果這條封禁被公開貼出來，我能不能只用"行為 + 已公佈規則 + 證據"三樣東西解釋清楚？** 如果答案需要補充"他平時就那樣""我早就看他不順眼"，那這次封禁的理由不成立。
:::

## 4. 證據要求

**沒有證據的封禁，等於把決定權交給了爭吵。** 要求不高，但要事先約定：

| 證據類型 | 適用場景 | 注意 |
| --- | --- | --- |
| 日誌（方塊 / 容器記錄） | 破壞、偷竊 | 最有力，能給出座標與時間；**只能記錄裝上之後的事** |
| 服務端控制台日誌 | 命令濫用、異常登入 | 會隨日誌輪轉而消失，需要及時儲存 |
| 截圖 | 聊天、廣告、建築外觀 | 容易被質疑裁剪，儘量保留上下文 |
| 錄屏 | 作弊、連續行為 | 體積大，建議保留原始檔案與時間戳 |
| 反作弊插件輸出 | 移動異常、攻擊異常 | 是**輔助**證據，單獨使用容易誤判 |

**記錄類插件是證據鏈的地基。** 主流方案是 **CoreProtect**（官方定位：面向 Minecraft 伺服器的資料記錄與防破壞工具，倉庫 <https://github.com/PlayPro/CoreProtect>），同類替代有 **Prism** 等。它的兩個關鍵限制必須記住：

1. **它只能記錄安裝之後發生的事。** 被破壞了才裝，之前的一概查不到。
2. **它記錄的是方塊與容器層面的行為**，不記錄"意圖"。

反作弊插件的輸出要**謹慎使用**：誤判是真實存在的，尤其在玩家網路抖動、TPS 掉到很低的時候。把它當作"值得人工複核的訊號"，而不是"判決書"。整套防護體系的分工見 [反作弊與防破壞](/tutorials/java/anticheat)，權限與記錄插件的配置見 [[JAVA] 安全插件](/tutorials/ops/security-java)。

:::tip 證據要存下來，而不是留在伺服器上
截圖、錄屏、匯出的查詢結果，應當**立刻複製到伺服器之外**（你的電腦、網盤、私有倉庫）。日誌會被輪轉、世界會被回滾、插件資料會被清理，而申訴可能在一個月後才來。
:::

## 5. 分級處置階梯

封禁不該是唯一手段。**階梯的意義在於"讓懲罰與情節匹配"**，同時給玩家改正的機會。

| 情節 | 處置 | 期限 | 記錄方式 |
| --- | --- | --- | --- |
| 首次輕微違規（誤挖、公屏失言） | 口頭/私聊警告 | 無 | 管理員日誌備註 |
| 重複輕微違規、刷屏、輕度辱罵 | 禁言（Mute） | 1 小時 ~ 24 小時 | 插件記錄 + 管理日誌 |
| 破壞、偷竊，情節與金額有限 | 臨時封禁 | 1 天 ~ 7 天 | 封禁記錄 + 證據存檔 |
| 破壞規模大、作弊、仇恨言論、人肉 | 長期封禁 | 30 天 ~ 永久 | 封禁記錄 + 證據存檔 + 複核 |
| 逃避封禁、報復性破壞 | 永久封禁 | 永久 | 封禁記錄 + 證據存檔 + 複核 |
| 誤判 / 證據不足 | 撤銷並致歉 | 立即 | 記錄撤銷原因 |

幾條使用規則：

1. **升級要有依據。** 從警告到封禁，中間應當有"上次已警告"的記錄。沒有記錄就沒有升級。
2. **永久封禁必須經第二人複核**（見下一節）。
3. **期限要寫清楚**。`/ban` 之後玩家看到的是"你被封禁了"，所以**必須同時告知期限與原因**，否則申訴時你無法自證。
4. **記錄與處置同時發生**。事後補記的"記錄"在爭議中幾乎無效。

具體命令語法**取決於你使用的封禁插件**（不同插件的 `/ban`、`/tempban`、`/mute` 參數格式不同），請以該插件的官方文件為準。

## 6. 誰來做決定

**"人人都是管理員"是伺服器管理崩壞的起點。** 不是因為它不信任人，而是因為它讓**責任無法定位、標準無法統一**。

建議的最小分工：

| 角色 | 職責 | 說明 |
| --- | --- | --- |
| 決定人（一人） | 判定情節、選擇處置、寫記錄 | 每個案件**只有一個**決定人，避免"誰先動手誰說了算" |
| 複核人（另一人） | 複核永久封禁與爭議案件 | **不能與決定人同一人**；只看證據與規則，不看交情 |
| 申訴受理人 | 收取申訴、核對證據、回覆 | 可以是決定人之外的人，減少"自己審自己"的觀感 |
| 記錄保管人 | 維護封禁與申訴檔案 | 保證記錄不丟、可檢索 |

為什麼"人人都是管理員"會破壞一致性：

- **標準不同。** 有人覺得刷屏無所謂，有人覺得該永久封。
- **權限不可追溯。** 出問題時無法確定是誰做的決定，也就無法糾正。
- **權限本身成為風險。** 權限插件（如 LuckPerms）的價值就在於**按權限節點精細授權**，而不是給所有人 OP。原版 OP 權限極大，一旦帳號被盜或情緒失控，破壞是全域的。配置見 [[JAVA] 安全插件](/tutorials/ops/security-java)。
- **人情壓力集中在少數人身上。** 有明確分工時，"我朋友被封了能不能通融"有一個標準答案："我複核不了，得走申訴。"

:::note 小伺服器的現實做法
如果伺服器只有你一個人，做不到"第二人複核"，那就用**時間**代替人：永久封禁**隔 24 小時再執行**，並在這 24 小時裡把證據整理一遍。隔一天再看，很多衝動的決定會自己消失。
:::

## 7. 申訴渠道

申訴渠道必須**公開、固定、可追溯**。三種常見形態：

| 形態 | 優點 | 缺點 |
| --- | --- | --- |
| 專用信箱（如 `appeal@example.com`） | 簡單、無需額外系統、天然留檔 | 玩家可能發錯、內容格式不統一 |
| 論壇/表單頁 | 欄位可控、可公開檢索（去隱私後） | 需要維護頁面 |
| Discord 工單頻道 | 門檻低、回覆快 | 容易被刷、需要管理權限 |

**不要用"私聊服主"作為唯一渠道。** 私聊沒有記錄、沒有排隊、容易被情緒帶走，也無法證明你處理過。

### 7.1 必填欄位

無論用哪種渠道，表單都應當要求以下欄位。缺一項就打回，這本身就是一種篩選。

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| 玩家名（遊戲內 ID） | 是 | 用於核對封禁記錄 |
| 封禁日期與時間（含時區） | 是 | 便於定位記錄 |
| 系統顯示的原因 | 是 | 讓玩家複述你寫的理由，可驗證他是否看過 |
| 玩家陳述 | 是 | 發生了什麼、為什麼認為處理有誤 |
| 相關證據連結 | 否 | 玩家自備的截圖或錄屏 |
| 聯絡方式 | 是 | 用於回覆，且**只在內部儲存** |

### 7.2 一個可以直接用的申訴模板

```text
【服务器名称】封禁申诉表

1. 游戏内 ID：
2. 封禁日期与时间（请注明时区）：
3. 封禁时系统显示的原因（原文照抄）：
4. 你的陈述（请写清事情经过，500 字以内）：
5. 你认为处理有误的理由（可多选）：
   [ ] 不是我做的
   [ ] 情况与记录不符
   [ ] 处罚过重
   [ ] 规则未公布 / 我不知情
   [ ] 其他（请说明）
6. 证据链接（可选）：
7. 可用的联系方式（仅管理员可见）：

提交后我们会在 72 小时内回复。请勿重复提交，重复提交不会加快处理。
```

### 7.3 響應時限（SLA）

**給一個明確的時間承諾，並儘量做到。** 建議：

- **首次回覆：72 小時內**（含"我們已收到，正在核對證據"這類中間回覆）。
- **複雜案件（永久封禁、涉及多人）：最長 7 天**，並在 72 小時內告知"需要更長時間"。
- **超時未回覆時，玩家有權再次催促一次**，且這次催促應當被優先處理。

SLA 的意義不只是禮貌：**沒有時限的申訴等於沒有申訴**，玩家在等待中會把不滿轉移到整個社群。

:::warn 不要承諾你做不到的時限
寫"24 小時內回覆"很漂亮，但一次漏回覆就會讓整份規則失信。**寧可寫 72 小時並穩定做到。**
:::

## 8. 收到申訴後怎麼處理

固定動作，按順序走：

1. **登記。** 記錄收到時間、申訴人、對應封禁記錄編號。**先登記再判斷**，避免"看過就忘"。
2. **核對證據。** 回到原始證據：記錄插件的查詢結果、日誌片段、截圖原文。**不要依賴記憶，也不要依賴別人轉述的結論。**
3. **確認規則依據。** 找出當時引用的規則條目。如果找不到，這本身就是問題（見第 11 節）。
4. **做出結論**，只有三種：
   - **維持（Uphold）**：證據充分，處置與情節匹配。回覆時給出理由與證據摘要。
   - **減輕（Reduce）**：行為成立，但處罰過重或已接近期限。改為更短的期限或警告。
   - **撤銷（Lift）**：證據不足、誤判、規則未公佈。立即解除並說明。
5. **書面回覆。** 通過玩家提供的渠道回覆，包含：結論、依據的規則、證據摘要（不必公開全部細節）、後續步驟。**不用嘲諷語氣，不引用玩家原話去反駁他。**
6. **留檔。** 把申訴原文、你的結論、時間戳寫進同一份記錄。**這一步最容易被跳過，也最關鍵**——它是你下次遇到同類案件時的參照。
7. **統計。** 每隔一段時間看一次：申訴量、維持率、撤銷率。撤銷率偏高說明前端判定有問題；申訴量突然上升，往往說明規則或溝通出了問題。

:::tip 回覆模板（維持）
"我們核對了 <日期> 的方塊記錄：<座標> 處的 <數量> 個方塊在 <時間> 被你的帳號移除，該行為違反規則第 <條>。因此本次封禁維持，期限至 <日期>。如果你認為記錄有誤，可以補充說明。"
:::

## 9. 公開與透明

透明不是"把一切公開"，而是**讓規則與處理標準可被檢驗**。

| 做法 | 建議 | 說明 |
| --- | --- | --- |
| 規則頁 | 必須有 | 公開、穩定連結、註明最後更新日期與生效日期 |
| 封禁名單 | 可選 | 公開"玩家名 + 原因 + 期限"即可，見下方隱私邊界 |
| 定期彙總 | 推薦 | 例如每月一條："本月封禁 N 例，其中永久 M 例，撤銷 K 例" |
| 申訴統計 | 推薦 | 讓玩家看到渠道是有效的，減少"申訴沒用"的印象 |

**隱私邊界（必須遵守）：**

- **不要公佈真實姓名、住址、電話、信箱、社交帳號、工作單位**等任何個人身份資訊。
- **不要公開玩家的完整 IP 位址**。需要說明時用掩碼（例如只保留網段），且只在內部記錄中使用完整值。
- **不要在公開說明裡附帶聊天原文的完整上下文**，只引用與判定直接相關的部分。
- **未成年玩家的資訊尤其敏感**，任何可定位到個人的內容都不應公開。
- **公開封禁原因時用規則條目表述**（"破壞他人建築"），而不是情緒化描述（"慣犯、人品差"）。

:::warn 公佈玩家個人資訊本身就是問題
把玩家的真實姓名、住址、電話、社交帳號或完整 IP 貼到公開頻道或論壇，**無論對方做過什麼，都是不能做的事**。它會讓你的伺服器從"處理違規的一方"變成"實施傷害的一方"，可能違反平台條款與當地法律，也會讓其他玩家立刻停止信任你。玩家違規，按規則處理；**用隱私作為報復手段，是運營者最嚴重的失誤之一**。如果這類資訊已經被貼出：立即刪除、儘可能通知當事人、記錄發生了什麼，並在內部明確"誰都不能這麼做"。
:::

## 10. 解封條件與觀察期

永久封禁也不該是"永遠沒有出口"。給出**可驗證的出口**，能顯著降低長期糾紛。

| 類型 | 解封條件 | 觀察期 |
| --- | --- | --- |
| 臨時封禁 | 到期自動解除 | 無（但記錄保留） |
| 長期封禁（30 天以上） | 到期 + 申訴中承認行為並承諾不再犯 | 30 天內再犯即永久 |
| 永久封禁（初犯、非惡性） | 滿 6~12 個月後申訴，說明改變 | 60~90 天，期間任何違規直接回到永久 |
| 永久封禁（人肉、現實威脅、報復性破壞） | 通常不解封 | — |
| 誤判 | 立即解封並致歉 | 無 |

寫清"觀察期"的好處是雙向的：玩家知道代價，你也知道**下一次不需要重新討論**。

:::note 解封不等於抹除記錄
解封應當**追加一條記錄**（"某日解封，理由：申訴通過 / 期限屆滿"），而不是刪除原記錄。刪除記錄會讓你在下次同類案件裡失去參照，也無法統計撤銷率。
:::

## 11. 封錯了怎麼辦

**誤判一定會發生。** 決定伺服器口碑的不是"從不犯錯"，而是**犯錯之後怎麼做**。

1. **立刻解封**，不要等申訴流程走完。證據不足時，"先解封再討論"是正確順序。
2. **明確道歉**，用詞直接："這次是我們判斷錯了，抱歉。"不要用"如果給你帶來不便，我們表示遺憾"這類迴避式表達——它比不道歉更傷人。
3. **說明原因**（簡要即可）：記錄插件資料被誤讀、反作弊誤報、同名帳號混淆。讓玩家知道你**知道**錯在哪。
4. **在記錄裡標註撤銷**，寫明日期與理由。這是後續統計與流程改進的依據。
5. **修補流程**，而不是隻修補這一次：
   - 反作弊誤報頻發 → 調整判定閾值，改為"人工複核後再封"。
   - 同名混淆 → 要求所有封禁記錄**以 UUID 為準**，不只寫玩家名。
   - 單人拍板 → 給永久封禁加上覆核或 24 小時冷靜期。
   - 規則未公佈 → 補上規則頁並公告生效日期。

**一個公開承認過的錯誤，比十個"我們從不出錯"的聲明更能留住玩家。**

## 12. 一頁流程清單

列印或貼在管理頻道里。**每一步都要能回答"留下了什麼"。**

**封禁前**

- [ ] 行為對應已公佈的規則條目（能說出第幾條）
- [ ] 證據已取得，並已複製到伺服器之外
- [ ] 已排除"首次輕微失誤"與"規則未公佈"兩種情形
- [ ] 已確認處罰與情節匹配（對照第 5 節階梯）

**封禁時**

- [ ] 填寫了時間、玩家名（含 UUID）、原因、證據位置、決定人五要素
- [ ] 原因寫的是**行為**，不是評價
- [ ] 已告知玩家期限與申訴渠道
- [ ] 永久封禁已進入複核（或已設定 24 小時冷靜期）

**收到申訴時**

- [ ] 已登記（收到時間 + 對應封禁記錄）
- [ ] 已回到原始證據核對，未依賴記憶
- [ ] 已確認規則依據確實存在且已公佈
- [ ] 結論為維持 / 減輕 / 撤銷三者之一，無"再看看"
- [ ] 已在 SLA 內書面回覆
- [ ] 申訴原文與結論已歸檔

**公開與復盤**

- [ ] 規則頁有連結、有更新日期
- [ ] 公開內容不含真實姓名、聯絡方式、完整 IP 等個人資訊
- [ ] 已撤銷的記錄標註了原因
- [ ] 已統計申訴量、維持率、撤銷率
- [ ] 已針對高撤銷率修補判定環節
