前面幾篇講的都是"你登入機器、自己敲指令"。這一篇講另一種常見的維運方式：**把伺服器交給一個 Web 面板管理**——開啟瀏覽器就能啟停實例、看控制台、傳檔案、改配置。

面板確實好用，但它是**這台機器上權限最高、也最容易成為目標的服務**。所以本文的重點不是"面板能做什麼"，而是**用了面板之後攻擊面多了什麼，以及怎麼把它收回來**。

:::note 本文的定位
本文只講**使用方式與安全邊界**，不替代各面板的官方安裝文件。安裝指令、預設埠、目錄結構**一律以官方文件為準**；本文只給出已與官方來源核對過的預設值，並標註出處。
:::

## 1. 面板能做什麼、代價是什麼

### 1.1 面板通常提供的能力

| 能力 | 具體表現 | 什麼時候真的省事 |
| --- | --- | --- |
| **Web 管理介面** | 瀏覽器裡啟停、重啟、檢視狀態，不用記一堆指令 | 手機上也能應急重啟 |
| **多實例管理** | 一台機器上同時跑多個服務端，統一切換 | 生存服、創造服、測試服並存 |
| **控制台訪問** | 網頁裡看即時日誌、直接發指令 | 遠端排查崩服原因 |
| **檔案管理器** | 上傳、下載、編輯 jar、配置與世界檔案 | 給玩家換整合包、加插件 |
| **計劃任務** | 定時重啟、定時備份、定時執行指令 | 每天凌晨重啟釋放記憶體 |
| **使用者與子使用者權限** | 給管理員、協管分配部分實例的操作權 | 讓協管重啟服，但不給 SSH |
| **資源統計** | CPU、記憶體、磁碟、線上人數曲線 | 判斷是配置問題還是機器不夠 |
| **Docker 整合** | 用容器隔離實例、限制資源 | 多實例互不干擾 |

:::note 功能集因面板而異
上表是"面板這一類工具"的常見能力，**具體某個面板是否提供、入口在哪裡，以該面板的官方文件與你的實際介面為準**。
:::

### 1.2 代價清單

| 代價 | 說明 |
| --- | --- |
| **多了一個要維護的服務** | 面板本身是 Web 應用，要更新、要看安全公告、要備份它自己的資料 |
| **攻擊面變大** | 多一個監聽埠、多一套帳號體系、多一條 API |
| **權限高度集中** | 面板（尤其是守護行程）能啟動任意行程、讀寫實例目錄，拿到它就等於拿到這台機器上所有服務端 |
| **反向代理更復雜** | 面板常需要 WebSocket；某些面板還要求瀏覽器直連守護行程（見 3.1） |
| **故障面變大** | 面板掛了不等於服務端掛了，但你可能暫時失去管理手段 |

:::warn 一句話理解風險
**面板不是"另一個軟體"，而是"這台機器上所有遊戲伺服器的總開關"。** 它的登入頁面對公網開放，就等於把整機管理權掛在公網上。
:::

### 1.3 先畫清信任邊界

用面板之前，先在腦子裡把這條線畫清楚：

- **面板能控制的東西 = 它執行身份能控制的東西。**
- 面板以 root 執行，那麼面板的任意一個遠端程式碼執行漏洞就等於整機淪陷。
- **守護行程的 API 本身就是"執行指令"的介面**——那是它存在的意義。所以它一旦暴露，等同於把一個 shell 掛到公網上。

## 2. MCSManager（MCSM）

### 2.1 官方定位

MCSManager 官方倉庫對自己的描述是：**"快速安裝，分散式架構，多使用者，現代化的 Minecraft 和 Steam 遊戲伺服器管理面板"**（英文版為 "Quick deployment, distributed, multi-user, modern management panel for Minecraft and Steam game servers"）。官方文件進一步說明：它是**開源、分散式、一鍵部署**，支援 Minecraft 與 Steam 遊戲伺服器的控制面板，可以幫助你集中管理多台物理伺服器、在任意主機上建立遊戲服務端，並提供安全可靠的多使用者權限系統。

這段話裡的三個關鍵詞，就是它的定位：

| 關鍵詞 | 含義 |
| --- | --- |
| **一鍵部署** | 提供安裝腳本，自動註冊為系統服務 |
| **分散式** | 一個面板可以管理**多台**機器 |
| **多使用者** | 內建帳號與權限體系，可以把權限分給協管，而不是給 SSH |

### 2.2 架構：一個面板 + 一個或多個守護行程

官方文件把 MCSManager 分成兩部分：

| 元件 | 官方描述的職責 |
| --- | --- |
| **Panel（Web 面板）** | 使用者管理、連線守護行程、多數操作的鑑權、API |
| **Daemon（守護行程）** | 行程管理（實例真正執行的地方）、Docker 映像管理、檔案管理、即時終端通訊 |

"分散式"的含義就在這裡：**面板本身不跑服務端**，它把指令下發給各台機器上的守護行程，由守護行程在本機啟動和管理實例。所以你可以是"一台面板 + N 台守護行程節點"。

:::warn 元件名、安裝指令、預設埠、目錄結構以官方文件為準
MCSManager 的服務名、安裝腳本位址、預設埠與資料目錄可能隨版本變化。**本文列出的數值只代表寫作時官方文件中的預設值，請以官方文件與你機器上的實際設定檔為準。** 正式環境不要照抄任何未經核對的埠或路徑。
:::

**本文已與官方文件核對過的預設值（供對照，仍建議自行確認）：**

| 專案 | 官方文件中的預設值 | 備註 |
| --- | --- | --- |
| 面板 Web 埠 | `23333` | 可在 Web 設定檔的 `httpPort` 修改 |
| 守護行程埠 | `24444` | 可在守護行程設定檔的 `port` 修改 |
| Linux 服務名 | `mcsm-web`、`mcsm-daemon` | systemd 服務 |
| 腳本安裝目錄 | `/opt/mcsmanager` | 官方示例路徑 |
| Web 設定檔 | `<Web 安装目录>/data/SystemConfig/config.json` | 含 `httpPort`、`httpIp`、`loginCheckIp` 等 |
| 守護行程設定檔 | `<Daemon 安装目录>/data/Config/global.json` | 含 `port`、`key`、`defaultInstancePath` 等 |
| 守護行程金鑰 | 上述 `global.json` 的 `key` 欄位 | 守護行程啟動時也會列印 |

:::tip 一個非常容易被忽略的官方警告
官方"分散式部署"文件明確寫著：在只跑守護行程的節點上，**必須先停止並停用 Web 服務**，否則**任何人都能訪問初始設定頁面並接管你的伺服器**：

```bash
systemctl stop mcsm-web
systemctl disable mcsm-web
```

這條警告值得單獨記住：**"忘記關掉的那個 Web 服務"就是一次完整的淪陷。**
:::

### 2.3 安裝與首次登入

官方 Linux 一鍵安裝腳本（官方文件強調：因為要註冊到系統服務，**必須以 root 權限執行**）：

```bash
sudo su -c "wget -qO- https://script.mcsmanager.com/setup.sh | bash"
```

:::note 中文文件與英文文件的腳本位址不同
官方英文文件使用 `setup.sh`，中文文件使用 `setup_cn.sh`。**請以你所看語言版本的官方文件給出的位址為準**，不要憑記憶拼寫腳本 URL。官方文件另有 Docker 安裝與環境隔離（Docker）章節，具體步驟同樣以官方文件為準。
:::

安裝後按官方文件啟動兩個服務（官方強調兩者缺一不可）：

```bash
# 先启动守护进程，再启动 Web 服务
systemctl start mcsm-daemon.service
systemctl start mcsm-web.service

# 需要开机自启时
systemctl enable mcsm-web.service
systemctl enable mcsm-daemon.service
```

手動安裝時，官方文件給出的啟動方式是 `./install.sh`、`./start-daemon.sh`、`./start-web.sh`，並提示手動啟動需要用 screen 之類的工具接管，否則 SSH 斷開後行程會被系統結束。Windows 版官方說明為下載壓縮包解壓後執行（壓縮包內若含啟動器，也可用啟動器啟動）。

**首次登入必須做的事（順序不要顛倒）：**

1. 用管理員帳號登入面板（初始帳號資訊以官方文件與你的安裝輸出為準）。
2. **立刻修改預設口令**，並使用與其他網站不同的長口令。
3. 按 3.5 的方式把它放到 HTTPS 反向代理後面，或至少限制來源 IP。
4. 檢查監聽位址與埠，確認沒有把守護行程直接暴露在公網。

### 2.4 典型工作流：從裝好到跑起一個實例

官方"搭建 Java 版"文件給出的流程大致如下（細節以官方文件為準）：

| 步驟 | 做什麼 | 注意 |
| --- | --- | --- |
| 1 | 裝面板 + 守護行程（或按官方文件用 Docker） | 節點機器上只留守護行程服務 |
| 2 | 登入並修改預設口令 | 見 2.3 |
| 3 | 在面板裡確認或新增守護行程節點 | 需要位址與金鑰；官方文件說明位址支援 IP、網域，也支援 `ws://` / `wss://` 字首 |
| 4 | 在"實例"頁點"建立" | 可選從市場安裝，或"直接建立"並選擇要執行的節點 |
| 5 | 填寫啟動指令 | 官方示例：`java -Dfile.encoding=UTF-8 -jar "paper-<version>.jar"`，可加 `-Xms` / `-Xmx` |
| 6 | 上傳服務端檔案 | 用面板的"檔案管理"上傳核心 jar |
| 7 | 在實例控制台點"啟動"並觀察日誌 | 首次啟動通常還要在"設定檔"裡把 `eula.txt` 改成 `eula=true` |
| 8 | 給協管建子帳號，只授權需要的實例 | 不要給"全部實例 + 檔案管理" |

官方文件還說明：實例資料預設位於 `<Daemon 安装目录>/data/InstanceData/<实例 ID>/`，實例配置位於 `<Daemon 安装目录>/data/InstanceConfig/<实例 ID>.json`（其中包含啟動指令等配置）。**這兩處是"丟了就很難重建"的東西，必須納入備份。**

:::warn 啟動指令裡的記憶體參數不要貪心
官方文件特別警告：**不要把機器全部記憶體都分給 JVM**，作業系統本身也需要資源，否則可能整機崩潰。`-Xmx` 要明顯小於機器物理記憶體。
:::

### 2.5 什麼時候面板真的幫到你

- **多實例**：十幾個服務端靠 SSH 一個個重啟不現實。
- **給協管有限權限**：讓協管重啟、看日誌，但**不給 SSH**——這是面板最大的安全收益。
- **定時重啟與備份**：面板類工具通常提供計劃任務能力，**MCSManager 是否提供、入口在哪裡、怎麼配置，以官方文件與你的實際介面為準**。
- **多機管理**：一個面板 + 多個守護行程，統一入口。
- **給不熟命令列的人用**：把操作限制在面板的功能範圍內，往往比直接給一個 shell 更安全。

## 3. 面板的安全（最重要）

### 3.1 第一原則：面板與守護行程 API 絕不直接暴露公網

這一條比其他所有條目加起來都重要：

:::warn 絕不把守護行程埠暴露到公網
守護行程 API 的職責就是**啟動行程、讀寫檔案、執行指令**——它本質上是一個**遠端程式碼執行介面**，只是外面套了一層鑑權。**它一旦暴露，攻擊者只需要一個金鑰洩露、一個鑑權繞過或一個未修補的漏洞，就能在你機器上執行任意指令。** 面板 Web 端同理，只是它至少還有一道登入頁。
:::

正確的做法：

1. **面板**：繫結 `127.0.0.1` 或內網位址，通過 HTTPS 反向代理對外，再加一層來源限制（VPN、IP 白名單或防火牆規則）。
2. **守護行程**：只允許面板主機（以及需要直連的客戶端）訪問。
3. **不要為了"方便"把守護行程埠開到 `0.0.0.0`。**

:::note MCSManager 的特殊之處：瀏覽器需要直連守護行程
MCSManager 官方"網路架構"文件說明：為了避免面板成為大流量（檔案上傳、控制台日誌）的瓶頸，**這些流量由瀏覽器直接與守護行程通訊**。因此官方文件指出，守護行程的位址**不能是區域網路位址**，否則守護行程狀態會一直停在"連線中"。

這帶來兩個必須知道的後果：

- 如果你把面板升級為 HTTPS，**每個守護行程也必須單獨配置 HTTPS 反向代理**，並在面板裡把位址改成 `wss://...`；官方文件明確說明瀏覽器會**拒絕**通過非 HTTPS 的 WebSocket 連線守護行程。
- "守護行程只在內網"這條通用建議，在 MCSManager 上要按官方文件的網路架構來落實：**要麼按官方文件給出的 HTTPS 反向代理方案配置，要麼用 VPN 或隧道保護"瀏覽器到守護行程"這條鏈路**，不要簡單地把埠暴露到公網。

**具體怎麼配，以官方文件的《網路架構》與《通過 NGINX 使用 HTTPS》兩篇為準。**
:::

### 3.2 不要用 root 執行

| 情況 | 事實（來自官方文件） | 建議 |
| --- | --- | --- |
| MCSManager 一鍵腳本 | 官方文件說明**因為要註冊系統服務，腳本必須以 root 權限執行** | 安裝可以用 root，但**實例應儘量用專用使用者或容器隔離**；官方另有"環境隔離（Docker）"文件 |
| Pterodactyl Wings | 官方文件給出的 systemd 單元中為 `User=root` | 這是官方設計（Wings 需要控制 Docker）；**用容器隔離實例本身就是它的緩解手段** |
| 通用伺服器面板 | 通常需要較高權限來管理系統服務與網站 | 不要把遊戲服務端和這類面板混在同一個信任邊界裡（見 4.2） |

原則：**能不用 root 就不用；必須用高權限時，用隔離（獨立使用者、容器、獨立機器）把爆炸半徑圈起來。**

### 3.3 憑據與帳號

- **立刻修改預設口令。** 預設口令是自動化掃描器的第一目標。
- 使用**長且唯一**的口令，最好由密碼管理器生成。**面板口令洩露 = 所有實例淪陷。**
- **若面板支援兩步驗證，務必開啟**；是否支援、如何開啟，**以官方文件為準**。
- **定期審計子使用者與權限**：誰還在？還需要嗎？權限是不是給多了？"檔案管理 + 全部實例"幾乎等於給 shell。
- **刪除不再需要的帳號**，包括離職的協管、測試帳號與不再使用的 API Key。
- 不要把面板口令寫進截圖、聊天記錄、Git 倉庫，或服務端目錄裡的文字檔。

### 3.4 保持面板本身更新

面板是 Web 應用，**有自己的漏洞歷史**。要做的事：

- 訂閱官方倉庫的 Release 與安全公告。
- 按官方文件中"更新"章節給出的流程升級。
- 升級前**備份面板自身資料**（見 3.7）。

:::warn MCSManager 升級時的一個坑
官方"更新與重置"文件提示：一鍵腳本更新會**自動重新啟用 `mcsm-web`**。如果你在節點機器上刻意停用了 Web 服務（見 2.2），更新後**必須再次手動停止並停用它**，否則初始設定頁面又會暴露出來。
:::

### 3.5 監聽位址與反向代理（nginx 示例）

思路是：**面板只綁回環位址，由 nginx 對外提供 HTTPS。** 下面的埠是**佔位符**，請替換成你自己的面板埠。

```nginx
# /etc/nginx/conf.d/panel.conf
# <panel-port> 是占位符，请替换为面板实际监听的本地端口。
# 证书路径由你的证书工具决定，不要照抄下面的示例路径。

server {
    listen 80;
    server_name panel.example.com;
    # 只做跳转；证书签发与续期方式以你所用的证书工具文档为准
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name panel.example.com;

    # 由你的证书工具生成与续期，请替换为实际路径（例如 certbot 的输出路径）
    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    # 面板控制台依赖 WebSocket，必须转发 Upgrade 头
    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 面板可能要上传较大的服务端或整合包文件；0 表示不限制
        client_max_body_size 0;

        # 控制台是长连接，别让它被缓冲或被过早切断
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

幾點說明：

- `proxy_http_version 1.1` 加上 `Upgrade` / `Connection` 三個頭是 WebSocket 的關鍵，**少一個控制台就可能連不上**。
- `ssl_certificate` 與 `ssl_certificate_key` 的**路徑來自你的憑證工具**（certbot 等），不同工具、不同部署方式路徑不同，**不要照抄**。
- 如果面板官方文件提供了自己的反向代理示例（MCSManager 官方就有 NGINX、IIS、Caddy 三篇），**以官方文件為準**——因為守護行程那條鏈路往往還需要單獨配置。
- 改完配置先測試語法再過載（MCSManager 官方文件同樣要求先驗證再過載）：

```bash
sudo nginx -t
sudo nginx -s reload
```

### 3.6 防火牆

只開必須開的，其餘預設拒絕：

| 埠 | 對誰開放 | 說明 |
| --- | --- | --- |
| 80 / 443 | 公網 | 面板入口（或你選定的 HTTPS 埠）；80 僅用於跳轉與憑證校驗 |
| 面板本地埠 | **僅本機** | 面板綁在 `127.0.0.1` 時不需要對外放行 |
| 守護行程埠 | **僅面板主機**（或按官方架構要求限定來源） | 絕不對公網開放；具體埠以官方文件為準 |
| 遊戲埠 | 公網（按需） | 玩家入口 |
| SSH | 你的管理 IP | 建議只允許金鑰登入 |

示例（埠與網段都是**佔位符**，請按你的實際配置替換；指令語法請對照你的發行版文件）：

```bash
# ufw 示例
sudo ufw default deny incoming
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp
# 只允许面板主机访问守护进程端口
sudo ufw allow from <panel-host-ip> to any port <daemon-port> proto tcp
sudo ufw enable
sudo ufw status verbose
```

埠與規則的完整思路見 [網路安全基礎](/tutorials/ops/network-security) 與 [路由器與防火牆](/tutorials/ops/router-firewall)。

### 3.7 備份面板自身的資料

**面板的資料目錄裡存著所有實例的定義、使用者與配置。丟了它，服務端檔案還在，但面板裡"什麼都沒有了"。**

| 要備份什麼 | 說明 |
| --- | --- |
| 面板的資料庫與配置目錄 | 使用者、權限、實例定義、計劃任務 |
| 守護行程的配置 | 埠、金鑰、實例配置 |
| 實例資料目錄 | 世界、插件、配置（通常體積最大） |

:::warn 路徑以官方文件為準
各面板的資料目錄位置不同，**必須從官方文件確認後再寫進備份腳本**，不要憑猜測寫路徑。

以 MCSManager 為例，官方文件給出的相關位置是：Web 配置在 `<Web 安装目录>/data/SystemConfig/config.json`，守護行程配置在 `<Daemon 安装目录>/data/Config/global.json`，實例資料在 `<Daemon 安装目录>/data/InstanceData/<实例 ID>/`，實例配置在 `<Daemon 安装目录>/data/InstanceConfig/<实例 ID>.json`。官方"更新與重置"文件則直接建議：**升級前把 `web/data` 與 `daemon/data` 兩個目錄備份到別處。**
:::

備份建議：

- 面板資料的備份要**離線或異地**存放，且**面板自身行程無法寫入**該位置（否則面板被入侵時備份會被一起刪掉）。
- 備份裡包含面板資料庫與金鑰，**必須加密或嚴格限制權限**。
- 定期做一次**恢復演練**——只備份不恢復等於沒備份。具體方法見 [備份與恢復](/tutorials/java/backup) 與 [異地備份](/tutorials/ops/offsite-backup)。

### 3.8 如果面板被入侵會怎樣

把最壞情況寫清楚，才知道該防什麼：

| 攻擊者拿到的東西 | 後果 |
| --- | --- |
| 面板帳號 | 控制**所有實例**：刪檔、改配置、踢人、給自己 op |
| 面板 + 檔案管理 | 上傳惡意 jar 或插件，把後門帶進服務端 |
| 守護行程 API | **在機器上執行任意指令**（這本來就是它的功能），通常直接等於 shell |
| 面板資料庫或金鑰 | 持久化訪問：即使你改了密碼，舊的 API Key 與會話仍可能有效 |
| 備份目錄的寫權限 | **刪掉你的備份**，讓你無法恢復（勒索與報復性刪檔的常見手法） |

所以：**一旦懷疑面板被入侵，按"整機已淪陷"處理。**

1. 立即切斷面板與守護行程的公網入口（改防火牆，而不是隻改密碼）。
2. 更換**所有**憑據：面板帳號、守護行程金鑰、服務端裡的 RCON 口令、資料庫密碼、雲服務商 API Key。
3. 檢查是否出現新的管理員帳號、新的 API Key、異常的計劃任務。
4. 檢查服務端目錄裡是否被塞了可疑的 jar、插件與定時腳本。
5. 從**已知乾淨**的備份恢復，而不是在已被入侵的機器上"清理一下繼續用"。
6. 復盤暴露原因（埠暴露、弱口令，還是沒打補丁），見 [網路安全基礎](/tutorials/ops/network-security) 與 [系統安全加固](/tutorials/ops/system-security)。

完整的處置流程見 [應急與取證](/tutorials/ops/incident-forensics)。

## 4. 其他面板與如何選擇

### 4.1 Pterodactyl

Pterodactyl 官方對自己的描述是：**免費、開源的遊戲伺服器管理面板，使用 PHP、React 和 Go 構建；為安全而設計，所有遊戲伺服器執行在隔離的 Docker 容器中**，並向最終使用者提供直觀的 Web 介面。它是 MIT 許可的開源專案，官方強調 bcrypt 口令雜湊、AES-256-CBC 加密與開箱即用的 HTTPS 支援。

它的架構與 MCSManager 同屬"面板 + 節點守護行程"這一類。官方術語表給出的定義是：

| 術語 | 官方含義 |
| --- | --- |
| **Panel** | Pterodactyl 面板本身，用於新增節點與伺服器 |
| **Node** | 執行 Wings 實例的物理機 |
| **Wings** | 用 Go 編寫的新一代服務，與 Docker 和 Panel 對接，通過面板安全地控制伺服器 |
| **Server** | 由面板建立、在節點上執行的實例；一個節點可以有多個 |
| **Docker / Image / Container** | 隔離的執行環境；每個伺服器跑在獨立容器裡，以限制 CPU、記憶體並避免互相干擾 |
| **Nest / Egg** | Nest 通常對應一個遊戲或服務，Egg 存某一類遊戲的具體配置 |
| **Yolks** | 與 Egg 系統配套的核心 Docker 映像集合 |

要點（均來自官方文件）：

- Wings **只支援 Linux**，官方明確 Windows 環境無法執行；需要能跑 Docker 的系統，OpenVZ、LXC 一類虛擬化通常不行（官方建議用 `systemd-detect-virt` 自查）。
- 官方安裝流程是：先在面板裡建立節點，再把面板生成的配置貼上為節點上的 `/etc/pterodactyl/config.yml`（或使用"生成權杖"給出的指令），然後以 systemd 服務執行 Wings。
- 官方給出的 systemd 單元中為 `User=root`，這是官方設計。
- 官方文件說明：**面板啟用 SSL 時，Wings 也必須為其 FQDN 配置憑證。**
- 節點需要配置 allocation（IP 與埠的組合），每個伺服器至少要有一個；官方提示**不要使用 `127.0.0.1`**。

:::note 未逐一核對的內容
Pterodactyl 的**具體安裝指令、預設埠、目錄結構與版本要求會隨版本變化**，本文不逐一列舉，**一律以官方文件為準**：面板安裝見官方 Panel 的 Getting Started，節點守護行程見官方 Wings 的 Installing Wings 文件。
:::

### 4.2 通用伺服器面板（1Panel、寶塔等）

這類工具**不是遊戲伺服器面板**，它們管理的是**作業系統層面的東西**：網站、資料庫、容器、檔案、計劃任務、防火牆等。

以 1Panel 為例，官方定位是**"現代化、開源的 Linux 伺服器維運管理面板"**（也是輕量級的 AI 管理平台），提供直觀易用的 Web 管理介面，可管理主機監控、檔案、資料庫、容器與計劃任務，並深度整合 WordPress、Halo 等建站程式；官方還提供 WAF、日誌審計與備份等安全能力。

**它和遊戲面板的區別：**

| 維度 | 遊戲伺服器面板 | 通用伺服器面板 |
| --- | --- | --- |
| 管理物件 | 遊戲實例（行程或容器） | 系統服務、網站、資料庫、容器 |
| 是否理解遊戲 | 能看控制台、傳插件、配啟動指令 | 通常不理解，只能當普通行程或容器管 |
| 權限範圍 | 實例與守護行程 | **經常是整個系統** |
| 典型用途 | 多實例、給協管分權 | 建站、跑服務、管 Docker |

**用通用面板管遊戲伺服器的風險：**

- **權限更大**：這類面板通常需要管理系統服務與檔案，一旦被入侵，影響面比遊戲面板更大。
- **不理解遊戲**：它不會替你處理"先發 stop、等世界儲存完"這類細節，容易把服務端當普通行程強殺。
- **多了一層**：你等於同時維護"遊戲服務端的部署方式"和"通用面板"兩套東西，攻擊面疊加。
- **歷史上出現過嚴重漏洞**：通用面板是公網掃描的重點目標。**任何面板都應被當作"面向公網的基礎設施"來對待**——及時更新、限制來源、啟用強認證。**具體漏洞資訊請以各廠商的官方安全公告為準，不要依賴第三方傳言。**

:::tip 更穩的組合
如果確實需要通用面板（比如同一台機器上還有網站），**把遊戲服務端放在獨立的機器、獨立使用者或獨立容器裡**，不要讓通用面板的權限和遊戲實例混在同一個信任邊界中。系統層面的加固見 [系統安全加固](/tutorials/ops/system-security)。
:::

### 4.3 對比表

| 面板 | 定位 | 是否需要獨立守護行程 | 適合誰 | 主要風險 |
| --- | --- | --- | --- | --- |
| **MCSManager** | 開源、分散式、多使用者的 Minecraft 與 Steam 遊戲伺服器管理面板 | **是**（Panel + Daemon，可多節點） | 多實例、多機器、需要給協管分權的服主 | 守護行程是遠端程式碼執行面；瀏覽器需直連守護行程，反向代理更復雜；升級可能重新啟用 Web 服務 |
| **Pterodactyl** | 免費開源的遊戲伺服器面板，實例執行在隔離的 Docker 容器中 | **是**（Panel + 每節點 Wings） | 想用容器隔離、面向多使用者與多節點的場景 | 依賴 Docker 與 Linux；Wings 官方以 root 執行；安裝與維護門檻較高；安裝方式與埠以官方文件為準 |
| **1Panel** | 現代化、開源的 Linux 伺服器維運管理面板（通用） | 否（自身即系統級管理面板） | 建站、管資料庫與容器、通用維運 | **系統級權限**，攻擊面大；不專門理解遊戲服務端；漏洞影響面大 |
| **寶塔等通用面板** | 通用伺服器維運面板 | 否 | 建站與通用維運 | 同 1Panel 一類；**安裝指令、預設埠與安全特性以官方文件為準** |
| **不用面板（SSH + systemd）** | 直接管理 | 否 | 單台機器、少量實例 | 沒有額外攻擊面；但 unit、日誌、更新都要自己維護 |

## 5. 實踐建議

### 5.1 安裝順序

1. **先把系統加固好**（專用使用者、SSH 金鑰、防火牆、自動更新），見 [系統安全加固](/tutorials/ops/system-security)。
2. **再裝面板**，裝完立刻修改預設口令。
3. **把面板放到 HTTPS 反向代理後面**，並限制來源（VPN、IP 白名單或防火牆規則）。
4. **最後接守護行程節點**，節點上只保留守護行程服務，關掉多餘的 Web 服務。
5. 建立實例、上傳檔案、跑通控制台。
6. 配置計劃任務與備份。
7. 給協管建子帳號，按最小權限授權。

**不要**在"公網裸奔"的狀態下先跑起來再說——面板暴露在公網上的每一分鐘都在被掃描。

### 5.2 加固清單

- [ ] 面板與守護行程都**不在公網直接可達**
- [ ] 面板經 HTTPS 訪問，且 WebSocket 正常
- [ ] 預設口令已修改；支援兩步驗證的已開啟
- [ ] 面板與守護行程的設定檔權限收緊（含金鑰或口令的檔案不要全域可讀）
- [ ] 實例以專用使用者或容器執行，不以 root
- [ ] 面板資料已備份，且備份位置面板無法寫入
- [ ] 已訂閱官方安全公告，並明確了自己的更新流程
- [ ] 子使用者權限已審計
- [ ] 節點機器上沒有殘留的初始設定頁面
- [ ] 已知曉被入侵後的應急步驟

### 5.3 該監控什麼

| 監控項 | 為什麼 |
| --- | --- |
| **面板登入失敗次數** | 暴力破解的第一訊號。部分面板自帶"登入失敗封禁 IP"一類的設定項（MCSManager 的 Web 配置中有 `loginCheckIp`，**具體含義與行為以官方文件為準**） |
| **異常的新實例** | 攻擊者常新建實例來跑別的東西 |
| **異常的計劃任務** | 定時任務是持久化的常見手法 |
| **新增的管理員或 API Key** | 持久化後門 |
| **資源突增** | CPU、記憶體、頻寬被拿去挖礦或發包 |
| **面板與守護行程的版本** | 及時打補丁 |
| **異常的出站連線** | 遊戲服務端通常不應該主動外連大量位址 |

日誌位置與審計指令見 [系統安全加固](/tutorials/ops/system-security)；被入侵後的處置見 [應急與取證](/tutorials/ops/incident-forensics)。

### 5.4 什麼時候不該用面板

面板不是預設選項。以下情況**通常不需要**面板：

- **只有一台機器、一個服務端**：SSH + systemd 更簡單，也少一個攻擊面。參考 [部署到可存取環境](/tutorials/java/deploy)。
- **只有你自己用，而且你熟悉命令列**：面板的收益（視覺化、分權）你用不上，成本（多一個服務、多一套帳號）卻要付。
- **機器效能緊張**：面板本身也要佔記憶體，小記憶體機器上不划算。
- **你不打算維護它**：**不更新的面板比沒有面板更危險。**

反過來，只要滿足下面任意一條，面板通常就值得：多個實例、多台機器、需要給協管有限權限、需要計劃任務、需要給不熟悉命令列的人使用。
