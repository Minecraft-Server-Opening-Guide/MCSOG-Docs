技術教學講到"插件怎麼裝、前置是什麼"就夠了，但真正決定伺服器像不像一個"遊戲"的，是**經濟與玩法插件**：錢從哪來、商店怎麼定價、任務給什麼獎勵、稱號怎麼展示、箱子裡開出什麼。

這一篇按**類別**講清楚每一類插件在做什麼、代價是什麼、風險在哪裡。凡是點名具體插件的段落，都只寫能從該插件的**官方頁面**（官方倉庫、官方文件站）核對到的能力；核對不到的部分，就只描述類別，不編造具體名字。前置依賴的基礎知識見 [插件入門](/tutorials/java/plugins) 與 [常用前置插件](/tutorials/java/plugin-deps)。
:::warn 玩法插件是"程式碼"，不是"內容包"
每裝一個玩法插件，你就多了一份：需要跟進更新的程式碼、可能與其他插件衝突的程式碼、可能被利用來刷物品的程式碼、以及會持續消耗主執行緒效能的程式碼。**玩法插件不是越多越好**。先想清楚要解決什麼問題，再去找插件；不要因為"別人服裡有"就裝。
:::

## 1. 先建立正確的心智模型

在挑插件之前，先把四件事想清楚：

| 問題 | 為什麼重要 |
| --- | --- |
| 這個插件解決什麼問題 | 說不出來就別裝。裝完之後沒人用，等於白付效能與風險成本 |
| 它依賴什麼 | 缺前置會載入失敗或功能靜默失效，見 [常用前置插件](/tutorials/java/plugin-deps) |
| 它把資料存在哪裡 | 檔案型儲存換服、開分服、做備份時的行為完全不同 |
| 它能不能被玩家利用 | 任何"能產出物品或貨幣"的插件，都是潛在的刷取入口 |

玩法插件的風險可以粗略分成四類，後面每一節都會反覆出現：

- **經濟風險**：能憑空產出貨幣或高價值物品，導致通貨膨脹。
- **安全風險**：複製漏洞、權限繞過、命令注入。
- **效能風險**：每 tick 的額外計算、實體數量、資料庫查詢頻率。
- **運營風險**：玩家覺得不公平、內容被玩穿、作者停更導致卡在舊版本。

## 2. 一張分類總表

先看全域，再逐節展開。

| 類別 | 增加什麼 | 難度 | 效能開銷 | 主要風險 |
| --- | --- | --- | --- | --- |
| 經濟系統（API + 實現） | 貨幣、餘額、轉賬的基礎 | 中 | 低（資料庫寫入與查詢） | 貨幣來源失控導致通脹；資料損壞 |
| 商店 | 買賣渠道、定價場所 | 中 | 低到中（取決於商店數量與查詢頻率） | 定價錯誤、無限收購、被刷 |
| 任務與成就 | 目標感、日常留存 | 中到高（內容設計成本高） | 低到中 | 獎勵擊穿經濟；內容被玩穿 |
| 稱號與頭銜 | 身份展示、社交符號 | 低 | 極低 | 與付費強度掛鉤會傷信任 |
| 抽獎與箱子 | 隨機獎勵、短期刺激 | 中 | 低到中（動畫與廣播） | 賭博成癮、付費隨機獎勵的合規與倫理問題 |
| 職業與技能 | 長期成長線 | 中到高 | 中（高頻事件監聽） | 產出失控；與生存玩法衝突 |
| 小遊戲與跑酷 | 獨立玩法、多人互動 | 高 | 中到高（獨立世界與實例） | 人數不足導致空場；維護成本高 |
| 領地與保護 | 財產安全感 | 中 | 中（方塊事件與查詢） | 規則複雜、新手勸退；與經濟聯動時易失衡 |
| 科技類大型玩法 | 完全不同的遊戲體驗 | 很高 | 高（大量自定義物品與機器邏輯） | 效能、版本升級困難、上手門檻高 |
| 反作弊與記錄 | 秩序與可追溯性 | 中 | 中（記錄型插件持續寫盤） | 記錄不全；裝晚了查不到歷史 |
:::tip 表格怎麼用
"難度"指的是**你配置和維護它的成本**，不是插件本身複雜不復雜。一個設定項上千行的插件，就算文件再全，也會吃掉你大量時間。**先算自己的時間預算，再算效能預算。**
:::

## 3. 經濟系統：一定是兩層

### 3.1 API 與實現必須分開理解

這是新手最容易踩的坑：**裝了 Vault 卻依然沒有經濟系統**。

Vault 的官方定位是 **Bukkit 的抽象庫**（官方倉庫描述：*Vault of common APIs for Bukkit Plugins*；README 標題：*Vault - Abstraction Library for Bukkit*）。它自己不產生任何貨幣，只定義一組統一介面，讓"需要經濟能力的插件"和"真正提供經濟能力的插件"能對上話。它的開發者 API 已經拆到單獨的 VaultAPI 倉庫（官方 README 說明）。

所以經濟系統永遠是**兩層**：

| 層 | 角色 | 例子（以官方頁面為準） |
| --- | --- | --- |
| 抽象層 | 定義"查餘額、扣錢、加錢"的介面 | Vault |
| 實現層 | 真正持有餘額資料、執行加減 | EssentialsX 的經濟模組、CMI 的經濟系統、XConomy 等 |

| Vault 這類抽象層提供什麼 | 誰來實現 | 誰在呼叫 |
| --- | --- | --- |
| 經濟（Economy） | 具體經濟插件 | 商店、任務、抽獎、領地維護費 |
| 權限（Permission） | 權限插件（如 LuckPerms） | 需要判斷權限的插件 |
| 聊天（Chat） | 聊天類插件 | 需要傳送或格式化聊天的插件 |

幾個可以核對的具體事實：

- **EssentialsX** 的官方模組說明寫明：核心 jar 包含大部分命令、牌子、kit **以及經濟系統**（*signs, kits and the economy*）。也就是說裝 EssentialsX 本體就已經有經濟實現了。
- **CMI** 的官方頁面寫明它提供 **Economy system（含餘額排行）** 與 **Cheque system（把金錢做成物品）**；它同時說明 CMI 的經濟要接入 Vault 體系，需要配合官方提供的 Vault 版本或經濟注入模組使用，並且要啟用設定檔裡的經濟開關。
- **XConomy** 的官方倉庫描述是"支援多服資料同步的經濟插件"，適合多服共用一套餘額的場景；使用前請自行確認它當前的維護狀態是否滿足你的版本要求。
- **Jobs Reborn** 的官方頁面把 **Vault** 列在依賴項裡——這就是"玩法插件通過抽象層呼叫經濟"的典型例子。
:::note 先確認"到底是誰在管錢"
排查經濟問題時，第一個要問的不是"商店插件壞了沒"，而是"**現在真正提供經濟實現的是哪個插件**"。很多"餘額變成 0""扣錢不生效"的問題，根源是同時裝了兩個經濟實現，或者抽象層指向了一個沒有資料的實現。
:::

### 3.2 物理貨幣物品

有些實現支援**把貨幣做成物品**（例如 CMI 官方文件中的 Cheque / 支票系統：建立一張包含金額的物品，可以在玩家之間流轉）。這類設計有利有弊：

- 好處：交易有實體感，適合 RP 與線下交易；可以離線交付。
- 風險：物品一旦能被複制、被非法獲取、或在跨服轉移中丟失，就等於貨幣失控；同時"物品形式的錢"繞過了插件層面的交易記錄。

如果你打算用物理貨幣，**必須同時解決三件事**：物品不可偽造（依賴物品資料校驗）、交易有記錄、丟失有申訴流程。

### 3.3 貨幣是管理員創造的，還是玩家賺來的

這是經濟設計的第一個決定，也是最重要的一票：

| 模式 | 錢的來源 | 後果 |
| --- | --- | --- |
| 管理員創造（發錢、賣物給系統） | 指令與商店回收 | 簡單直接，但極易通脹；必須配合強回收手段 |
| 玩家賺取（勞動、交易、任務） | 玩法產出 | 更健康，但設計成本高；產出速率必須可控 |
| 混合 | 系統發放基礎收入，玩家之間流通 | 現實中最常見；關鍵是把系統發放量當成"貨幣發行量"來管理 |

## 4. 商店

商店是經濟的**流通渠道**，也是最容易出事的地方——因為它直接決定"什麼東西值多少錢"。

### 4.1 互動形式：牌子 / 箱子商店 vs GUI 商店

| 形式 | 特點 | 適合 |
| --- | --- | --- |
| 牌子 / 箱子商店 | 玩家把箱子放在世界裡，用牌子標價；不需要命令即可買賣 | 玩家之間的自由市場、集中商業區 |
| GUI 商店 | 用選單介面瀏覽分類與購買；管理員配置商品表 | 管理員商店、新手引導、品類繁多的收購 |

可以核對的官方描述：

- **ChestShop**：官方倉庫描述為 *The original chest & sign shop plugin for Minecraft Servers running Bukkit/Spigot/Paper. Est. 2011*（最早的箱子與牌子商店插件）。
- **QuickShop-Hikari**：官方倉庫描述寫明它是"讓玩家無需任何命令就能從箱子裡買賣物品的商店插件"，並強調玩家實際上不需要用到它提供的任何命令。
- **Shopkeepers**：官方 README 寫明它讓服主設定"自定義村民商店"，並且**同時支援兩類商店**：**管理員商店（無限庫存）** 與 **玩家商店（從容器中取貨）**。
- **GUI 商店類**：以選單為互動方式的商店插件（例如 EconomyShopGUI，其官方倉庫 Gypopo/EconomyShopGUI-API 描述為"The API of EconomyShopGUI"，供其他插件對接）。

### 4.2 玩家商店 vs 管理員商店

| 類型 | 庫存 | 定價者 | 經濟含義 |
| --- | --- | --- | --- |
| 管理員商店 | 無限 | 服主 | 系統級的貨幣水龍頭與回收站，直接決定通脹 |
| 玩家商店 | 玩家自己的貨物 | 玩家 | 玩家之間的流通，服主只需提供規則與場地 |

### 4.3 "賣給伺服器"和"玩家之間交易"是兩件事

這是最需要向玩家解釋清楚的一點：

- **賣給伺服器**：伺服器無限收購，等於**貨幣發行**。收購價就是發行價，收購量就是發行量。
- **玩家之間交易**：一方付錢、一方交貨，貨幣總量不變，只是轉移。

很多"經濟崩了"的伺服器，問題都出在管理員商店的**無限收購價**上：只要某個物品可以穩定、無限地賣給系統，玩家就會把它變成刷錢機器。

### 4.4 商店經濟崩壞的典型路徑

| 崩壞方式 | 機制 | 預防 |
| --- | --- | --- |
| 無限收購定價過高 | 玩家批次刷取該物品賣給系統 | 定期審查收購表；給單玩家收購量設上限 |
| 複製漏洞 | 物品數量憑空翻倍，再賣給系統換錢 | 見第 9 節；所有產出型玩法都要有記錄 |
| 出售價格寫錯（少一個 0） | 一次交易就把經濟打穿 | 改動價格後先在測試服驗證；保留配置改動記錄 |
| 高價物品無人出售 | 貨幣只進不出，通脹 | 設計回收手段，見第 10 節 |
| 商店被用作跨玩家轉賬 | 變成洗錢或逃稅通道 | 明確規則；必要時對交易抽稅 |
:::warn 商店的價格表是經濟設定檔，不是隨便填的表格
改一個收購價之前，先算一遍：**單個玩家一小時能產出多少該物品？乘以收購價，就是他每小時的印鈔速度。** 如果這個數字和"正常玩一小時能賺的錢"差了一個數量級，經濟一定會在幾天內崩掉。
:::

## 5. 任務與成就

任務系統解決的是**目標感**問題：玩家上線之後有明確的"今天做什麼"。

可以核對的官方描述：

- **Quests**（PikaMug）：官方倉庫描述為"易用、開源的、用於在 Minecraft 伺服器上建立與執行任務的插件"。
- **BetonQuest**：官方倉庫描述為"高階且強大的任務腳本插件"，內建 RPG 風格對話，並整合 40 多個其他插件。它更適合"有劇本、有對話、有分支"的重內容伺服器。

### 5.1 日常 / 周常任務

- **日常任務**提供穩定的上線理由，但獎勵必須小。日常獎勵的設計目標是"值得做"，不是"必須做"。
- **周常任務**適合承載較大獎勵，因為它對產出速率有天然上限（一週一次）。
- **不要把任務做成簽到發錢**。純粹的"點一下就領錢"會把經濟變成按時間發鈔。

### 5.2 獎勵設計不能擊穿經濟

任務獎勵有三種安全形態：

| 形態 | 說明 | 風險 |
| --- | --- | --- |
| 外觀與稱號 | 不影響數值 | 低（前提是稱號不賣強度） |
| 消耗品與便利 | 藥水、傳送券、修理券 | 中（要算清每小時產出） |
| 貨幣與高價值物品 | 直接發錢、發裝備 | 高（必須按小時產出上限倒推定價） |

判斷標準是：**任務獎勵必須能和你已有的貨幣來源放在同一張表裡比較**。如果任務的每小時收益遠高於其他玩法，玩家就會只做任務，其他內容全部荒廢。

## 6. 稱號與頭銜

稱號屬於**展示層**，它的價值來自"別人看得見"，而不是數值。

| 類型 | 實現方式 | 說明 |
| --- | --- | --- |
| 權限型字首 / 字尾 | 權限插件存 meta，聊天或 TAB 類插件渲染出來 | 最常見，與權限組天然繫結 |
| 裝飾性稱號 | 玩家自己選擇並展示的文本 | 通常需要單獨的稱號插件與解鎖條件 |
| 玩法內頭銜 | 由玩法插件自身提供（例如職業插件顯示的職位名） | 例如 Jobs Reborn 官方文件中的 Chat Titles 功能 |

可以核對的事實：**LuckPerms** 的官方倉庫描述是"面向 Minecraft 伺服器的權限插件"，它負責存權限與字首後設資料；而 **EssentialsX 的官方模組文件**明確寫到，要讓玩家擁有字首與字尾，需要 **Vault 與 LuckPerms**。也就是說，**"誰存字首"和"誰把字首顯示出來"通常不是同一個插件**——顯示那一步由聊天類或 TAB 類插件完成，具體見 [聊天、選單與 MOTD](/tutorials/java/cosmetic)。

設計上的兩條底線：

- 稱號可以賣（作為支持者的標識），但**不能帶強度**。
- 稱號系統要能被撤回。玩家違規後，你應當能立刻摘掉他的稱號。

## 7. 抽獎與箱子

箱子（Crates）是"隨機獎勵"玩法，短期刺激極強，長期爭議極大。

### 7.1 獎勵表怎麼工作

主流箱子插件的核心都是一張**帶權重的獎勵表**：

- 每個獎勵有**權重（weight）**，權重越高越容易抽中。
- 獎勵常按**稀有度（rarity）**分組，稀有度再影響抽取機率。
- 鑰匙分**實體鑰匙**（可交易、可轉贈）與**虛擬鑰匙**（繫結玩家）。
- 通常還有**開啟成本、冷卻、權限要求、次數上限**等限制。

可以核對的官方描述：

- **CrazyCrates**：官方描述為"為你的伺服器新增無限數量的箱子，提供 11 種箱子類型"；官方文件站為 docs.crazycrew.us，安裝說明要求使用 Paper 及以上服務端，並提供 `/crazycrates debug` 用於測試獎勵。
- **ExcellentCrates**：官方 Wiki 列出稀有度權重（rarity weights）、獎勵權重（weights）、開啟成本（open cost）、冷卻、里程碑、獎勵次數上限（roll limits），並明確提供 **虛擬鑰匙**（官方說明其目的是**防止鑰匙被分享、交易或出售**）與 **獎勵日誌**（把每次抽取記錄到專門的日誌檔案）。

這兩點對你的運營有直接價值：**虛擬鑰匙**讓你能控制"鑰匙不被買賣"，**獎勵日誌**讓你在出問題時能查證。

### 7.2 賭博與成癮：必須正視的問題

隨機獎勵在心理機制上和賭博高度相似：可變比率強化、差點就中、沉沒成本。作為服主，你需要主動設限：

- **不要用"再抽一次就能中"的話術**。這屬於刻意誘導。
- **公開機率**。獎勵表與權重應當對玩家可見，至少在規則裡說明。
- **設定上限**。每日/每週開啟次數上限、單玩家獎勵上限，能顯著降低失控風險。
- **保護未成年人**。如果你的玩家群體偏年輕，這一點尤其重要。

### 7.3 付費隨機獎勵：合規與倫理警告
:::warn 不要做付費隨機獎勵
**把隨機獎勵和真實貨幣付費繫結（付費開箱 / 抽卡），在部分國家和地區受到專門的法規或平台規則約束，可能被認定為賭博類內容，也可能違反支付渠道與平台的政策。** 這類規則會變化，且不同地區差異很大，你必須自行核實適用於你的法律與平台要求，而不是照搬別人的做法。

從運營角度還有更現實的理由：**付費隨機獎勵是"pay-to-win 爭議"的放大器**。它讓"花錢能不能變強"這個問題從模糊變得具體，而玩家對它的容忍度極低。**建議的做法是：鑰匙只通過玩法獲得（活動、任務、貢獻），不通過真實貨幣出售。**
:::

## 8. 玩法類

### 8.1 職業與技能

- **Jobs Reborn**：官方頁面描述為"完全可配置的插件，讓你通過破壞、放置、擊殺、釣魚、合成等行為獲得報酬；基於職業（class-based professions），在執行工作時獲得經驗"，官方同時列出 Vault 依賴、MySQL 可選、自定義點券經濟、每日任務、聊天頭銜等特性。
- **mcMMO**：官方網站定位為"面向 Spigot/Paper 的 RPG 插件"，提供技能、升級、超級技能、排行榜與隊伍（party）系統，並有大量設定項。

這一類的風險集中在**產出**：技能等級提高收益、職業獎勵直接給錢，兩者疊加很容易形成"越玩越富"的正回饋。上線前一定要估算**滿級玩家的每小時收益**。

### 8.2 小遊戲與跑酷

這兩類通常需要**獨立世界或獨立實例**，並且對"同時線上人數"有硬性要求：

- 人數不足時對局開不起來，玩家看到的是空場，比沒有這個玩法更傷。
- 維護成本高：地圖、規則、平衡、漏洞，都需要持續投入。
- 建議在主線伺服器穩定、且有穩定線上人數之後再考慮，不要作為開服第一批插件。

具體插件的選擇空間很大且質量差異明顯，**請以各插件的官方頁面與更新記錄為準**，本篇不點名推薦。

### 8.3 領地、保護與經濟聯動

領地系統的核心價值是**財產安全感**——沒有它，玩家不願意長期投入建設。可以核對的官方描述：

- **GriefPrevention**：官方倉庫描述為"自 2011 年以來面向 Minecraft 伺服器的官方自助式防破壞 Bukkit 插件"。
- **WorldGuard**：官方倉庫描述為"保護你的 Minecraft 伺服器，並讓玩家圈定區域"。

與經濟聯動時要小心：**領地費用（購買、續費、按面積計費）是極好的貨幣回收手段，但如果定價過高，會直接把新玩家擋在門外**。建議把領地價格和"新手前幾小時能賺到的錢"對齊，而不是和"老玩家的餘額"對齊。更多保護體系的分工見 [領地與保護](/tutorials/java/protection) 與 [反作弊與防破壞](/tutorials/java/anticheat)。

### 8.4 科技類大型玩法（Slimefun 一類）

**Slimefun4** 的官方倉庫描述是"一個獨特、玩起來像整合包的 Spigot/Paper 插件"，自 2013 年起提供背包、噴氣背包、反應堆等大量內容。

這類插件等於**在伺服器裡再裝一個遊戲**：

| 代價 | 具體表現 |
| --- | --- |
| 效能 | 大量自定義物品、機器邏輯與定時任務 |
| 版本升級 | 依賴服務端版本，升級常需要等待適配 |
| 上手門檻 | 新玩家面對一整套新系統，容易勸退 |
| 相容性 | 與其他插件在物品、合成、掉落上容易衝突 |

如果你確定要做科技服，**先按"這是一個新遊戲"的規格來做規劃**：獨立的引導、獨立的教學、獨立的效能預算，而不是把它當成"再加一個插件"。

## 9. 反作弊與經濟安全

**複製漏洞（dupe）是經濟系統的頭號殺手**：它不改變規則，只改變數量，而數量一旦失控，價格、商店、任務獎勵全部失去意義。

### 9.1 原則

- **所有產出型玩法都要有日誌**。沒有日誌，你連"是不是被刷了"都無法判斷。
- **記錄每一筆交易**。誰在什麼時候、和誰、交易了什麼、金額多少。事後追查完全依賴這些記錄。
- **保留審計軌跡**。封禁、回檔、手動發錢都要留痕，避免"管理濫用"的指控，也方便復盤。
- **權限最小化**。能給權限節點就不要給 OP；能只給一個世界就不要給全服，見 [[JAVA] 安全插件](/tutorials/ops/security-java)。
- **有回滾預案**。出事之後能不能恢復到某個時間點，取決於你的備份策略，見 [備份與恢復](/tutorials/java/backup)。

可以核對的事實：**CoreProtect** 的官方倉庫描述為"面向 Minecraft 伺服器的、極快的資料記錄與防破壞工具"。它記錄的是**方塊與容器層面的行為**，是排查"東西怎麼沒了"的第一手證據；[反作弊與防破壞](/tutorials/java/anticheat) 講了它在整套防護體系中的位置。

### 9.2 違禁物品注入經濟的風險

所謂"違禁物品"，指的是通過漏洞、命令或插件錯誤產出的、本不該存在的物品（異常附魔、非法數量、破壞平衡的道具）。它們的危害在於：

- 一旦流入玩家手中，**會被當成正常資產參與交易**，汙染整個經濟。
- 發現得越晚，回滾的代價越大（可能要回滾幾十個玩家）。
- 處理時必須有依據：**先查記錄確認來源，再決定回收範圍**，不要憑感覺封人。

建議：對高價值物品建立"來源可查"的機制，並在規則裡寫清"違禁物品一律回收"。

## 10. 經濟平衡設計

經濟系統的本質是一個**水池**：進水和出水必須大致平衡。

| 方向 | 手段 | 說明 |
| --- | --- | --- |
| 貨幣來源（進水） | 管理員商店收購、任務獎勵、職業收益、活動獎勵 | 每一個來源都要能算出"每小時能產出多少錢" |
| 貨幣回收（出水） | 商店出售（玩家買系統的東西）、交易稅、領地購買與續費、修理費、傳送費、抽獎鑰匙 | 出水不足必然通脹，這是最常見的設計缺失 |

### 10.1 通脹的典型症狀

- 老玩家餘額高到"什麼都買得起"，商店失去意義。
- 新玩家覺得"永遠追不上"，直接離開。
- 高價物品被掃空，價格繼續上漲。
- 玩家之間的交易開始用"以物易物"繞開貨幣。

### 10.2 必須有的回收手段

至少準備三到四種，並且讓它們**自然融入玩法**而不是"罰款"：

- **交易稅**：玩家商店成交時抽成，自動回收，且與活躍度正相關。
- **領地維護費**：按面積或按時間收費，讓"佔地"有成本。
- **修理與附魔成本**：裝備維護消耗貨幣，回收量隨遊戲進度增長。
- **便利服務**：傳送、洗點、改名等收費服務。
:::tip 用資料而不是感覺來調經濟
定期記錄：伺服器貨幣總量、前 10% 玩家的餘額佔比、每日新增貨幣量、每日回收量。**當"每日新增"持續大於"每日回收"時，通脹已經在發生**，只是還沒顯現在價格上。
:::

## 11. 落地順序

不要一次把玩法裝齊。推薦的最小可用順序：

1. **最小經濟**：只裝一個經濟實現（外加抽象層），確認餘額能存能取、資料落在哪、備份是否覆蓋。
2. **基礎回收**：先把傳送費、修理費或領地費用中的一項做出來。**沒有回收手段的經濟不要對外開放。**
3. **商店**：先做管理員商店（可控定價），確認收購表不會變成印鈔機；需要自由市場時再加玩家商店。
4. **任務**：有了穩定的貨幣來源與回收之後，用任務去引導玩家體驗你希望他們體驗的內容。
5. **外觀與稱號**：最後再做展示層。它不影響數值，但能顯著提升長期玩家的歸屬感。
6. **抽獎與箱子**：放在最後，並且堅持"鑰匙只由玩法產出"。

每加一步，觀察一到兩週：貨幣總量、玩家行為、TPS。**出問題就回退上一步，而不是繼續往前加。**

## 12. 上線前檢查清單

- [ ] 每個玩法插件都能說清"它解決什麼問題"
- [ ] 前置依賴已全部安裝，控制台無載入報錯
- [ ] 經濟只有**一個**真正的實現，其餘插件通過抽象層呼叫
- [ ] 所有貨幣來源都能估算"每小時產出上限"
- [ ] 至少有三到四種貨幣回收手段，並已實際生效
- [ ] 管理員商店的收購表經過一次"印鈔速度"演算
- [ ] 任務獎勵與貨幣來源放在同一張收益表裡比較過
- [ ] 稱號與外觀不提供任何數值強度
- [ ] 抽獎鑰匙只通過玩法獲得，不通過真實貨幣出售
- [ ] 所有產出型玩法與交易都有日誌
- [ ] 記錄型插件（如 CoreProtect 一類）在開服**之前**就已安裝
- [ ] 備份策略覆蓋經濟資料庫與玩家資料
- [ ] 違禁物品的處理流程已寫進規則
- [ ] 有回滾預案，並演練過一次
- [ ] 每加一個玩法插件，都記錄了加裝前後的 TPS 與 MSPT 變化
