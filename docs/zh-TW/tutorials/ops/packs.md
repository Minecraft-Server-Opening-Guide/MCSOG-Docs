"資源包"和"資料包"名字很像，作用卻完全相反：**資源包改的是玩家看到和聽到的東西，資料包改的是遊戲本身的行為**。搞混這兩個概念，就會出現"我裝了材質包為什麼合成表沒變"或者"資料包為什麼改不了貼圖"這類問題。

本篇講 Java 版的資源包與資料包：兩者能做什麼、怎麼裝、服務端怎麼下發資源包、格式不相容怎麼排查。基岩版是另一套機制（資源包 + 行為包 + 附加包），見 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup)。

## 1. 兩者是什麼

| 維度 | 資源包（Resource Pack） | 資料包（Datapack） |
| --- | --- | --- |
| 作用位置 | **客戶端**：貼圖、模型、音效、語言檔案、字型、GUI | **服務端 / 存檔**：配方、戰利品表、進度、函式、結構、標籤 |
| 誰能看到效果 | 只有裝了（或被下發）該包的玩家 | 所有玩家（資料在世界/服務端上，與客戶端無關） |
| 裝在哪 | 客戶端 `resourcepacks/`，或由服務端下發 | 存檔目錄下的 `datapacks/` |
| 服務端能不能強制 | 可以下發並強制（`require-resource-pack`） | 不需要下發，本來就存在服務端 |
| 會不會改變玩法 | **不會**。改變的是外觀與聲音 | **會**。可以改配方、掉落、世界生成、執行命令 |
| 能不能跑程式碼 | **不能**。只有素材與設定檔 | **能**。函數里是一串命令，等價於服務端執行命令 |
| 典型用途 | 材質、UI、音效、漢化、字型、模型 | 自定義配方、掉落、成就、小遊戲邏輯、世界生成 |
| 與版本的關係 | `pack.mcmeta` 裡的格式號必須匹配客戶端版本 | `pack.mcmeta` 裡的格式號必須匹配服務端版本 |

一句話記憶：**資源包是"換皮"，資料包是"換規則"。**

### 目錄結構對照

```text
资源包/
  pack.mcmeta                 <- 必需，标识这是一个包
  pack.png                    <- 可选，选择界面里的图标
  assets/
    <命名空间>/
      textures/               <- .png 贴图
      models/                 <- .json 模型
      sounds/                 <- .ogg 音效
      lang/                   <- <语言代码>.json 翻译
      font/  blockstates/  gui/ ...

数据包/
  pack.mcmeta                 <- 必需
  pack.png                    <- 可选
  data/
    <命名空间>/
      function/               <- .mcfunction 命令函数
      recipe/                 <- .json 配方
      loot_table/             <- .json 战利品表
      advancement/            <- .json 进度
      structure/              <- .nbt 结构
      tags/                   <- 标签（例如 function/tick.json）
      predicate/  item_modifier/  worldgen/ ...
```

`pack.mcmeta` 是**唯一必需的檔案**，遊戲正是靠它來判斷一個目錄或 zip 是不是"包"。

## 2. 各自做不到什麼

| 想做的事 | 資源包 | 資料包 |
| --- | --- | --- |
| 換方塊貼圖、換音效、改字型與語言 | 可以 | **不行**（資料包不碰客戶端素材） |
| 加一條合成配方、改掉落物 | **不行** | 可以 |
| 改遊戲邏輯、加小遊戲規則、定時執行命令 | **不行**（不能執行程式碼） | 可以 |
| 加一個新方塊 / 新物品 | **不行**（只能改現有內容的素材） | **不行**（這需要模組） |
| 讓所有玩家都看到同樣效果 | 需要下發資源包，玩家仍可能拒絕 | 天然對所有玩家生效 |
| 改變伺服器效能 | 幾乎不影響服務端 | **會影響**：函式每 tick 執行就可能拖慢服務端 |

:::note 為什麼"資料包加不了新方塊"
資料包能定義配方、掉落、進度、世界生成等**資料**，但方塊與物品的註冊是硬編碼在遊戲裡的。想在服務端加真正的新方塊/新物品，需要模組（或基岩版的行為包）。**看到"資料包新增新礦物"的教學，多半是借用了已有方塊的外觀與材質。**
:::

## 3. 服務端怎麼給 Java 客戶端下發資源包

原版服務端通過 `server.properties` 裡的幾個鍵把資源包**推給**客戶端。**鍵名必須一字不差**（這是最常見的失敗原因之一）：

```properties
resource-pack=https://cdn.example.com/packs/survival-2026-10-04.zip
resource-pack-sha1=<40 位小写十六进制 SHA-1>
require-resource-pack=false
resource-pack-prompt={"text":"本服使用自定义材质包，建议启用。","color":"yellow"}
```

| 鍵名 | 類型 | 預設值 | 含義 |
| --- | --- | --- | --- |
| `resource-pack` | 字串（URL） | 空 | 資源包的下載網址。留空表示不下發任何資源包；玩家進服時可以選擇是否下載。**包的大小上限為 250 MiB** |
| `resource-pack-sha1` | 字串 | 空 | 資源包的 SHA-1，**小寫十六進位制**。用於客戶端校驗完整性，**強烈建議填** |
| `require-resource-pack` | 布林 | `false` | 為 `true` 時，**玩家拒絕使用資源包會被踢出伺服器** |
| `resource-pack-prompt` | 字串 | 空 | 在強制資源包時顯示的自定義提示文本。使用聊天元件（JSON 文本）語法，可以多行；留空則顯示預設提示 |
| `resource-pack-id` | UUID | 空 | 可選，給這個資源包一個標識；**較新版本才有這個鍵**，舊版本寫了不生效 |

### 必須知道的幾個細節

- **必須是客戶端能直接下載到的 HTTPS 位址。** 實踐中原版客戶端只接受 HTTPS 連結，明文 HTTP 或證書有問題的位址會導致下載失敗（客戶端側的校驗隨版本變化，以官方文件為準）。
- **下載成功或失敗只記錄在客戶端日誌裡，服務端看不到。** 所以"服務端沒報錯"不代表玩家拿到了包——排查時一定要去看客戶端的 `logs/latest.log`。
- 服務端**不會**替你託管這個檔案。你需要把它放到能被公網訪問的地方（物件儲存、CDN、Nginx 靜態目錄等），並確認**沒有防盜鏈、沒有鑑權、沒有重定向到 HTML 頁面**。
- 服務端啟動時會重寫 `server.properties`：它會補上缺失的鍵、把無效值改回預設值，並**轉義某些特殊字元**（例如 `:`）。所以手寫 `resource-pack-prompt` 的 JSON 是可行的，但不要因為檔案裡出現了反斜槓就以為寫錯了。
- 改了這些鍵**必須重啟服務端**才生效（`server.properties` 不會被 `/reload` 重新讀取）。

:::warn 強制資源包是一把雙刃劍
`require-resource-pack=true` 會讓**拒絕下載的玩家直接進不來**。如果資源包託管在你自己頻寬有限的小機器上，一次更新就可能讓全服玩家同時下載、把頻寬打滿，甚至被誤判為"伺服器進不去"。**強制之前先確認託管端的頻寬與可用性，並保留隨時關掉強制的能力。**
:::

## 4. 正確計算 SHA-1

雜湊必須是**檔案內容**的 SHA-1，小寫十六進位制，共 40 個字元。

```bash
# Linux / macOS
sha1sum survival-2026-10-04.zip
```

```powershell
# Windows PowerShell：Get-FileHash 默认输出大写，转成小写再填
(Get-FileHash -Algorithm SHA1 .\survival-2026-10-04.zip).Hash.ToLower()
```

### 雜湊錯了會怎樣

| 情況 | 後果 |
| --- | --- |
| 雜湊與實際檔案不符 | 客戶端下載後校驗失敗，**資源包不會被應用**；失敗只出現在客戶端日誌裡，服務端毫無感知 |
| 雜湊不是 40 位十六進位制字串 | 按協議文件說明，客戶端不會用它做校驗，**白白浪費一次下載頻寬** |
| 服務端啟動時提示 `Invalid sha1 for resource-pack-sha1` | 配置裡的這個值與實際包不一致（或格式不合法），控制台會出現黃色提示 |
| 換了包但沒更新雜湊 | 玩家反覆下載、反覆失敗；舊玩家可能還留著舊包 |

:::tip 三個最容易踩的坑
1. **重新打包會改變雜湊**：即使檔案內容一樣，重新壓縮（時間戳、壓縮級別不同）也會得到不同的 zip，雜湊隨之變化。**保留你算過雜湊的那個 zip 原件，不要重新壓。**
2. **上傳過程中可能被改動**：某些平台會自動壓縮、加水印或改寫內容，上傳後要**重新下載一次**並校驗雜湊是否與本地一致。
3. **大小寫**：填 `ABC...` 可能不被識別為合法雜湊，統一用小寫。
:::

## 5. 資料包放哪、怎麼裝

資料包放在**存檔目錄**下的 `datapacks/` 裡。服務端的存檔目錄由 `server.properties` 的 `level-name` 決定（預設是 `world`）：

```text
/opt/mcserver/
  server.properties          <- level-name=world
  world/
    datapacks/
      my-tweaks/             <- 目录形式的数据包
      economy.zip            <- zip 形式的数据包
    level.dat
    region/
```

安裝步驟：

1. 下載資料包（本站收錄的在 [資料包下載](/downloads/datapacks)），確認它是 **`.zip` 或目錄**。
2. 把它放進 `<level-name>/datapacks/`。**zip 裡必須直接就是 `pack.mcmeta`，不能多套一層資料夾**——從資料夾右鍵壓縮時最容易多出一層。
3. 如果服務端正在執行：執行 `/reload`，或用 `/datapack enable <名字>` 啟用（部分內容必須重啟，見第 6 節）。
4. 驗證是否載入成功：

```text
/datapack list             列出全部数据包
/datapack list enabled     只列出已启用的
/datapack list available   只列出可用但未启用的
```

輸出裡應當能看到你的包名（zip 形式會顯示為 `file/<文件名>`）。列表裡滑鼠懸停可以看到 `pack.mcmeta` 裡寫的 `description`。

### 啟用、停用與順序

```text
/datapack enable <名字>
/datapack disable <名字>
/datapack enable <名字> first        放到最低优先级
/datapack enable <名字> last         放到最高优先级
/datapack enable <名字> before <已有包>
/datapack enable <名字> after  <已有包>
```

- **順序很重要**：同名檔案**後載入的包覆蓋先載入的包**；標籤檔案預設會合並，除非寫了 `"replace": true`。
- 權限等級：`list` / `enable` / `disable` 需要權限等級 2；`create` 需要等級 4。
- 啟用的包列表儲存在**存檔**裡（`level.dat`），所以**換存檔、回檔會一起改變啟用了哪些資料包**。

:::note 服務端和單人存檔的路徑不一樣
單人遊戲的存檔在 `.minecraft/saves/<存档名>/datapacks/`；服務端在**工作目錄下**的 `<level-name>/datapacks/`。放錯位置是"資料包不生效"的最常見原因。
:::

## 6. `/reload` 到底過載了什麼

`/reload` 在 Java 版裡的作用是**重新載入當前已啟用資料包中的資料**。它**不是**萬能的，也不等於重啟：

| 內容 | `/reload` 是否生效 |
| --- | --- |
| 登錄檔標籤（tags） | 會重新載入 |
| 戰利品表（loot table） | 會重新載入 |
| 配方（recipe） | 會重新載入 |
| 進度（advancement） | 會重新載入 |
| 物品修飾器、謂詞 | 會重新載入 |
| 函式（function，`.mcfunction`） | 會重新載入 |
| 結構模板（structure） | 會重新載入 |
| 使用動態登錄檔 / 實驗性內容的部分（例如維度、生物群系、世界生成、附魔等，具體範圍隨版本變化） | **不會**，必須重啟服務端（單人則退出並重新進入世界） |
| `server.properties` 等核心配置 | **不會**，必須重啟 |
| 服務端行程、插件狀態 | **不會**，而且可能被 `/reload` 弄亂 |

兩個必須記住的行為：

1. **資料包裡有非法資料時，改動不會被應用**，遊戲會繼續使用之前的資料。所以"我 `/reload` 了但沒變化"有時是包本身寫錯了，而不是過載沒生效。
2. **在插件服上慎用 `/reload`。** 它可能讓插件狀態錯亂（例如計分板、監聽器、快取）。能用 `/datapack enable` / `/datapack disable` 或乾脆重啟解決時，優先選後者。

## 7. 包格式：`pack.mcmeta` 與 `pack_format`

`pack.mcmeta` 是包的後設資料檔案，資源包與資料包都用它，但**兩者要求的格式號不同**。

```json
{
  "pack": {
    "pack_format": <该版本要求的整数>,
    "description": "示例数据包"
  }
}
```

:::warn 上面的 `<该版本要求的整数>` 是佔位符，不是可以直接用的 JSON
**不要照抄任何教學裡的格式號**，包括本篇。`pack_format` 的數值隨每個 Minecraft 版本變化，資源包與資料包各有一套；填錯就會得到"格式不相容"的提示，包不會被載入。
:::

### 怎麼查你這個版本要填多少

| 途徑 | 說明 |
| --- | --- |
| 官方文件 / Minecraft Wiki 的包格式表 | 表中按版本列出資源包與資料包各自的格式號，**以它為準** |
| 你所用服務端核心的文件 | 部分核心會在文件裡註明當前版本對應的格式 |
| 遊戲給出的提示 | 載入失敗時的提示通常會同時給出"包聲明的格式"與"當前版本期望的格式"（具體文案隨版本變化） |
| 從當前版本的官方包反推 | 直接看官方資源包/內建資料包裡的 `pack.mcmeta` 寫了什麼 |

### 與版本有關的其他欄位

`pack.mcmeta` 不止 `pack_format` 一個欄位，而且**欄位本身也在隨版本演進**：

| 欄位 | 作用 | 注意 |
| --- | --- | --- |
| `pack.pack_format` | 該包的主要格式號 | 在較新版本中已變為可選；舊版本必需 |
| `pack.supported_formats` | 聲明一個格式區間（如 `[42, 45]`） | 1.20.2 引入；**在更新的版本中已被移除**，只在需要相容舊版本時保留 |
| `pack.min_format` / `pack.max_format` | 新版本引入的最小/最大支援格式（可帶次版本號） | 取代了 `supported_formats` 的角色 |
| `pack.description` | 懸停時顯示的文字，支援文本元件 | 資源包與資料包都用 |
| `pack.filter` | 過濾掉優先順序更低的包中的檔案（正則） | 1.19 引入 |
| `pack.overlays` | 按版本區間疊加子目錄 | 1.20.2 引入 |
| `features.enabled` | 啟用實驗性功能標誌 | 需要對應的實驗性開關 |

**欄位的名稱、是否必需、以及格式號的取值都以官方文件為準**，不要以本篇或任何第三方教學為準。

## 8. 效能與安全

### 資料包是"服務端程式碼"

函數里是一串**由服務端執行**的命令，因此：

- **只安裝你信任來源的資料包。** 一個函式可以做任何命令能做的事：給物品、傳送、改世界、清空容器、甚至把玩家丟進虛空。
- 安裝前**開啟 zip 看一眼**：`data/<命名空间>/function/` 裡有沒有你不想執行的命令；`pack.mcmeta` 裡的 `description` 與實際內容是否相符。
- 函式的權限等級由 `server.properties` 的 `function-permission-level` 決定（預設 2），這決定了函式能執行到多"高階"的命令。

### 每 tick 執行的函式會拖慢服務端

- 被 `minecraft:tick` 函式標籤引用的函式**每 tick（每秒 20 次）執行一次**。一次遍歷幾百個實體、或每 tick 放置/破壞方塊，都會穩定地吃掉 MSPT。
- 被 `minecraft:load` 引用的函式只在（重）載入時執行一次，代價小得多。
- 用 `/schedule`、`execute if` 之類的機制做"輪詢"時，要算清楚**每秒實際執行多少次**。
- 出現卡頓先量化再改：見 [效能分析 spark](/tutorials/ops/spark)。

```text
# 判断一个包有没有每 tick 的入口：看它有没有这个文件
data/<命名空间>/tags/function/tick.json
```

### 資源包的注意事項

- 資源包在客戶端執行的是**素材替換**，不能執行程式碼，所以"安全"層面風險低；但**下載與儲存成本**是真實的：包上限 250 MiB，玩家每次更新都要重下。
- 大包會顯著拉長玩家進服時間，弱網玩家可能直接放棄。**能用幾 MB 解決的，不要上幾十 MB。**
- 資源包可以替換任何貼圖，因此**也可能被用來誤導玩家**（例如把普通礦石畫成鑽石礦）。多人服裡這屬於公平性問題，不只是技術問題。
- 服務端下發資源包**不等於**玩家一定用它：除非 `require-resource-pack=true`，玩家可以拒絕；玩家自己的客戶端資源包順序也可能覆蓋你下發的包。

## 9. 排查表

| 現象 | 常見原因 | 怎麼查 |
| --- | --- | --- |
| 資源包完全沒下發 | `resource-pack` 為空或寫錯；URL 不可訪問；改完沒重啟服務端 | 檢查 `server.properties` 的鍵名拼寫與 URL；用瀏覽器/`curl -I` 確認能直接下載到 zip |
| 玩家進服時提示下載失敗 | 非 HTTPS、證書無效、需要鑑權、被防盜鏈、返回的是 HTML 而不是 zip | **看客戶端日誌**（服務端不會記錄下載失敗） |
| 雜湊校驗失敗、包反覆重下 | `resource-pack-sha1` 與實際檔案不符；重新打包過卻沒更新雜湊；雜湊寫成大寫或長度不對 | 用第 4 節的方法重新計算，確認下載到的是同一個檔案 |
| 服務端控制台出現 `Invalid sha1 for resource-pack-sha1` | 該鍵的值與實際包不一致或格式不合法 | 重新計算並更新；不確定就先留空（會失去校驗） |
| 玩家拒絕後進不去 | `require-resource-pack=true` | 改成 `false` 並重啟；或先修好下載問題再強制 |
| 貼圖沒變化 | 包內路徑或名稱空間寫錯；`pack.mcmeta` 缺失或格式號不對；被更高優先順序的包覆蓋；玩家自己的客戶端包覆蓋了它 | 確認 `assets/<命名空间>/textures/...` 路徑正確；把包放在資源包列表最上方；用原版客戶端單獨測試 |
| 只對部分玩家生效 | 玩家拒絕了下載，或用了自己的資源包 | 需要全服一致就開 `require-resource-pack`，並先解決託管頻寬 |
| 資料包沒出現在 `/datapack list` 裡 | 放錯目錄（應在 `<level-name>/datapacks/`）；zip 裡多套了一層資料夾；不是 `.zip` 也不是目錄 | 確認 `pack.mcmeta` 就在包的根目錄；用 `unzip -l` 看結構 |
| 資料包出現了但沒效果 | 未啟用；函式沒被 `tick` / `load` 標籤引用；名稱空間或路徑寫錯；屬於必須重啟才生效的內容 | `/datapack list enabled` 確認已啟用；`/reload` 後看日誌報錯；必要時重啟 |
| 提示"格式不相容" | `pack_format` 與當前版本不符（資源包與資料包格式號不同，別用錯） | 按第 7 節查官方格式表；更新到正確格式號 |
| `/reload` 後配置沒變 | 該內容屬於必須重啟的部分；或包裡有非法資料導致改動被整體丟棄 | 看服務端日誌有沒有載入錯誤；直接重啟驗證 |
| 裝了資料包之後明顯示卡頓 | 有函式掛在 `minecraft:tick` 上且每 tick 開銷大 | 檢查 `tags/function/tick.json`；用 [spark](/tutorials/ops/spark) 定位 |

## 10. 小結

- **資源包換外觀，資料包換規則**；一個在客戶端，一個在服務端。
- **服務端下發資源包靠 `server.properties` 的四個鍵**：`resource-pack`、`resource-pack-sha1`、`require-resource-pack`、`resource-pack-prompt`（較新版本還有 `resource-pack-id`），改完要重啟。
- **雜湊必須與實際檔案一致且為小寫 40 位十六進位制**；算完不要重新打包，上傳後要重新校驗。
- **資料包放在 `<level-name>/datapacks/`**，用 `/datapack list` 驗證；`/reload` 只過載一部分內容，動態登錄檔與核心配置必須重啟。
- **格式號隨版本變化**，一律查官方表格，別照抄教學。
- **資料包是服務端程式碼**：只裝可信來源；掛在 `tick` 上的函式會一直消耗效能。
