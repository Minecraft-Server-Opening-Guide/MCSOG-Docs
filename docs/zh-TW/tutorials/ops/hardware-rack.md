前面幾篇講的是軟體層：裝 Java、選服務端、配插件、做備份。這一篇講**物理層**——把伺服器放進機架之後，真正決定"它能不能連續跑三個月不出事"的那些東西。

適用物件從**家裡一台塔式機**到**機房裡的 1U 機器**。凡是隨型號、廠商、韌體版本變化的參數，本文都會明確標註"取決於型號"，不會替你編一個具體數字。

## 1. 先分清三個層次

| 層次 | 你關心什麼 | 出錯後的表現 |
| --- | --- | --- |
| **應用層** | 服務端核心、插件、配置 | 崩潰、卡頓、報錯 |
| **系統層** | Java、記憶體、防火牆、備份 | 起不來、被入侵、資料丟 |
| **物理層** | 機架、供電、網線、散熱、帶外管理 | **整機斷電、過熱降頻、遠端夠不著** |

物理層的特點是：**平時完全無感，出事時最難補救**。機房裡的機器一旦失聯，你能做的往往只有打電話請人按電源鍵。所以這一層的錢和時間，花在"預防"上最划算。

## 2. 機架基礎：19 英寸、U 高與導軌

標準機架來自 **EIA-310 / IEC 60297** 系列規範，幾個關鍵數字：

| 專案 | 數值 | 說明 |
| --- | --- | --- |
| 安裝寬度 | 19 英寸 = **482.6 mm** | 兩側安裝法蘭之間的淨寬 |
| 1U 高度 | **44.45 mm**（1.75 英寸） | 所有 U 數都是它的整數倍 |
| 42U 全高機架 | 約 **1866.9 mm** 可用安裝高度 | 整體外高通常約 2000 mm，取決於廠商 |
| 常見深度 | 600 / 800 / 1000 / 1200 mm | **伺服器機櫃通常要 800 mm 以上** |

常見規格：**1U**（最薄，散熱餘量最小、風扇轉速最高、最吵）、**2U**（散熱與擴充餘量明顯更好，可裝更多硬碟與半高 PCIe 卡）、**4U**（可裝全高卡、多盤位，接近塔式機的安靜程度）。家用或小規模優先考慮 2U/4U 或直接塔式機——1U 機器的噪音（常見 60–80 dBA 量級，取決於型號）不適合放在臥室。

安裝孔位有兩種：

- **方孔機架**：使用**卡式螺母（cage nut）** + M6 螺釘，最常見；
- **螺紋孔機架**：直接擰 10-32 或 M6 螺釘，不需要卡式螺母。

EIA-310 的孔位是**三個一組迴圈**（間距 15.875 mm / 15.875 mm / 12.7 mm），裝導軌時必須對齊這組迴圈，否則上下裝置會互相錯位。

**導軌（rail kit）** 的坑最多：

- **靜態導軌**：裝置放上去就不能抽出，便宜、穩固；
- **滑動導軌**：可把機器整體拉出維護，通常帶**理線臂（CMA）**，價格更高；
- 導軌多為**廠商/機型專用**，且**支援深度範圍有限**——買機櫃前先確認導軌支援的最小/最大深度，600 mm 機櫃裝不下很多長機身伺服器；
- 滑動導軌要預留**線纜餘量**，否則拉出時會把網線電源線扯斷。

機架內還有不佔 U 位的**豎裝 0U PDU**（見第 15 節），以及佔 1U 的橫裝 PDU、理線板、盲板。

## 3. 風道：前進後出、冷熱通道，以及"永遠別擋住進風口"

絕大多數機架式伺服器是**前進風、後出風**：冷空氣從前面板吸入，熱空氣從後面排出。機房的佈局邏輯由此而來：

- **冷通道**：機櫃正面，空調送冷風到這裡；
- **熱通道**：機櫃背面，裝置排出的熱風集中在這裡迴風；
- 理想狀態是**冷熱通道分離**（封閉通道或合理佈局），避免熱風被重新吸回進風口。

幾條硬性紀律：

1. **絕不遮擋進風口**。前面板被擋住、被塞進密閉櫃子、貼著牆放，都會直接導致過熱降頻甚至當機。
2. **空 U 位要裝盲板（blanking panel）**。空位會讓熱風從機櫃後方迴流到前方，被上方裝置重新吸入。
3. **防塵網要定期清洗**。堵死的濾網等於擋住了進風口。
4. **機櫃門要夠通透**。通常要求開孔率較高（常見 60% 以上，具體看廠商規格），實心玻璃門對高密度裝置是災難。
5. **注意風扇方向型號**。部分交換機和電源支援**可反轉風道**（埠側進風或埠側出風），屬於**不同 SKU**，必須按機櫃的氣流方向訂購；混裝會把冷熱通道搞亂。
6. **看進風溫度，不看機房溫度**。溫度感測器要放在裝置進風口附近；機房環境溫度有 ASHRAE 推薦的允許區間（不同等級 A1–A4 不同），但**裝置進風溫度**才是真正決定降頻與否的量。

託管時你通常只能控制機櫃正面：遵守機房方的冷熱通道規定，別為了自己方便把機器反過來裝。

## 4. 為 Minecraft 選伺服器硬體：單核優先

Minecraft 服務端的 tick 迴圈目標是 **20 TPS**，也就是每個 tick 有 **50 ms** 的預算。主執行緒負責絕大部分世界邏輯：實體、紅石、方塊更新、玩家移動、大部分區塊載入排程。因此：

**單核效能（頻率 × IPC）比核心數更重要。**

| 工作負載 | 執行緒特徵 |
| --- | --- |
| 主 tick 迴圈（實體、紅石、玩家、多數方塊邏輯） | 基本單執行緒，決定 TPS |
| 區塊生成 / 光照（Paper 等非同步化後） | 可多執行緒，核心多有益 |
| 插件/模組的非同步任務、資料庫、地圖渲染 | 可多執行緒 |
| 同時開多個服務端實例 | 核心數直接線性受益 |

結論：

- 一台只跑一箇中等規模原版/Paper 服，**2–4 個高頻核心**往往勝過 16 個低頻核心；
- 核心多**不是浪費**，但對單實例的邊際收益遞減；
- 選 CPU 時看**單執行緒跑分**（各類基準庫的單核成績），不要只看"幾核幾線程"；
- **消費級平台 vs 伺服器平台**的取捨：消費級（Ryzen、Core）通常單核更強、更便宜、更安靜；伺服器平台（Xeon E、Xeon Silver、EPYC 等）提供 ECC、IPMI、冗餘電源、更多記憶體通道與盤位。**具體型號的代際差異很大，請以廠商規格頁為準。**

記憶體方面：小型原版服 4–8 GB、中等規模或帶插件 8–16 GB、大型整合包 16 GB 以上是常見區間；**記憶體給多了沒有收益**（見 [服務端配置](/tutorials/java/config)），但給少了會頻繁 GC 卡頓。

## 5. ECC 與非 ECC

**ECC（Error-Correcting Code）** 記憶體能糾正單位元錯誤、檢測雙位元錯誤（SEC-DED），並在不可糾正錯誤時上報。它**不提升效能**，提升的是**長期執行的可靠性**：

- 一台連續開機幾個月的機器，記憶體出錯的機率不低；非 ECC 記憶體出錯時往往表現為**靜默資料損壞**——世界檔案被寫壞，你事後完全不知道原因；
- ECC 需要 **CPU + 主機板 + 記憶體模組三者同時支援**，缺一不可；
- **UDIMM（無緩衝）** 常見於消費級/入門伺服器；**RDIMM / LRDIMM（寄存/減載）** 只在伺服器平台可用，單條容量更大、單通道可插更多條；
- **DDR5 的片上 ECC（on-die ECC）不等於端到端 ECC**：它是 DDR5 顆粒內部機制，不向系統上報、不能替代帶外 ECC；
- ECC 錯誤可通過 BMC/IPMI 的 SEL 日誌或 Linux 的 EDAC 子系統（`/sys/devices/system/edac/`、`edac-util` 等）監控。

**結論**：家用作娛樂服，非 ECC 可以接受；**公網長期開放、玩家資料重要的伺服器，建議上 ECC**。注意 ECC 與非 ECC、RDIMM 與 UDIMM **混插通常無法開機**，擴記憶體前查主機板 QVL 相容列表。

## 6. 儲存：SSD / NVMe 與耐久度

| 介面 | 典型順序頻寬 | 備註 |
| --- | --- | --- |
| SATA SSD | 約 500–560 MB/s | 受 SATA 6 Gb/s 限制，隨機效能仍遠好於機械盤 |
| NVMe PCIe 3.0 x4 | 約 3.5 GB/s | 型號相關 |
| NVMe PCIe 4.0 x4 | 約 7 GB/s | 型號相關 |
| NVMe PCIe 5.0 x4 | 約 14 GB/s | 型號相關，發熱明顯 |

**對 Minecraft 來說，順序頻寬基本不是瓶頸**。真正影響體驗的是：

- **4K 隨機讀寫的延遲與佇列深度表現**（區塊檔案、日誌、資料庫）；
- **寫入放大與 SLC 快取耗盡後的掉速**（大量儲存或備份時）；
- **斷電保護（PLP）**：企業盤帶 PLP，掉電時能把在途寫入落盤；消費盤通常沒有，**靠 UPS 彌補**（見第 13 節）。

**耐久度**用 **TBW（總寫入位元組數）** 或 **DWPD（每日全盤寫入次數）** 衡量。要點：

- TLC 比 QLC 耐久與持續寫入表現更好；QLC 盤在大寫入後掉速明顯；
- **無 DRAM 快取的盤**（靠 HMB）在隨機負載下通常更弱，適合輕負載；
- Minecraft 本身的寫入量並不誇張：服務端週期性儲存世界（原版約每 5 分鐘一次，Spigot/Paper 可在 `spigot.yml` 的 `ticks-per.autosave` 調整），加上日誌與玩家資料；
- 但**插件會顯著放大寫入**：CoreProtect 這類記錄插件、Dynmap/BlueMap 的地圖渲染、頻繁的自動備份，都會持續寫盤；
- 因此**系統盤與資料盤分開**、**備份寫到另一塊盤或 NAS/HDD** 是常見做法；
- **RAID 不是備份**：RAID 1 能扛單盤故障，扛不住誤刪、勒索軟體和 rm -rf，異地備份仍然必須做（見 [備份與恢復](/tutorials/java/backup)）。

## 7. 冗餘電源（1+1）與託管環境

**1+1 冗餘電源**指機器有兩個熱插拔電源模組，任意一個故障時另一個能獨立帶滿整機負載。注意幾個容易誤解的點：

- **每個模組都要能單獨承擔全部負載**，不是"一人一半"；選配時按整機峰值功耗選單模組功率；
- 真正有意義的是**雙路供電（A/B 饋電）**：把電源 A 和電源 B 接到**不同的 PDU / 不同的支路**。如果兩個模組插在同一個插排上，插排一跳閘，1+1 等於沒有；
- 託管機櫃通常提供 A/B 兩路市電，**部分機房第二路要額外收費**，簽約前問清楚；
- 1+1 防的是"電源模組故障"和"單路供電故障"，**防不了兩路同時斷電**——那要靠 UPS 和發電機；
- 冗餘電源會帶來額外風扇噪音和少量效率損失；電源效率等級（80 PLUS 各檔）影響電費與發熱，長期託管值得關注。

## 8. IPMI / BMC 帶外管理

**BMC（基板管理控制器）** 是伺服器主機板上一個獨立的小系統，由待機電源供電，**作業系統關機甚至沒裝系統時依然線上**。廠商實現名稱不同：Dell 叫 iDRAC，HPE 叫 iLO，聯想叫 XClarity Controller，超微/華擎機架/技嘉等通常直接叫 BMC 或 IPMI。協議上，傳統是 **IPMI 2.0**，現代替代是 **Redfish**（基於 HTTPS 的 REST 介面）。

它能做的事：

- **遠端 KVM**：像坐在機器前面一樣看畫面、敲鍵盤，包括進 BIOS；
- **虛擬介質**：把本地 ISO 掛載成光碟機，用於裝系統/救援；
- **電源控制**：開機、關機、重啟、強制斷電；
- **感測器與日誌**：溫度、風扇、電壓、SEL 事件日誌；
- **Serial over LAN**：通過序列埠重定向看控制台。

常見埠（**具體埠與實現隨廠商/型號變化**）：

| 用途 | 常見埠 |
| --- | --- |
| IPMI RMCP / RMCP+ | UDP 623 |
| BMC Web 介面 | TCP 80 / 443 |
| 遠端 KVM（部分實現） | TCP 5900 / 5901 等 |
| Redfish | TCP 443 |

:::warn IPMI 絕對不要暴露到公網
這不是保守建議，而是明確的行業共識。原因：IPMI 2.0 歷史上存在認證繞過類漏洞（例如著名的 cipher 0 / RAKP 相關問題），很多廠商韌體帶有**預設帳號密碼**（具體預設值隨型號與韌體版本變化，務必自行更換），部分實現的管理流量加密薄弱，Web 介面也出過大量漏洞。**拿到 BMC 就等於拿到整機**：可以遠端開機、掛載映像、重灌系統。

正確做法：
- BMC 接**獨立的管理網段/VLAN**，不與業務口混用；
- 該網段**沒有到網際網路的路由**，需要訪問時先連 VPN 或跳板機；
- 修改預設密碼，關閉不用的服務（例如用不到 IPMI over LAN 就關掉），限制可訪問源 IP；
- 及時更新 BMC 韌體（BMC 韌體漏洞是真實攻擊面）；
- 優先使用 Redfish over IPMI。
:::

## 9. 交換機：非管理型與管理型

| 能力 | 非管理型 | 管理型（L2 / L2+） |
| --- | --- | --- |
| 即插即用 | 是 | 需要配置 |
| VLAN（802.1Q） | 無 | 有（access / trunk 口） |
| 鏈路聚合（LACP，802.3ad） | 無 | 有 |
| 埠映像（SPAN） | 無 | 有，抓包排障必備 |
| SNMP 監控 | 無 | 有（v2c / v3） |
| STP / RSTP 防環 | 通常有基礎實現 | 有 |
| IGMP snooping（組播最佳化） | 無 | 有 |
| 埠安全 / 風暴抑制 / DHCP snooping | 無 | 有 |

怎麼選：

- **家裡一兩台機器、一張平網**：非管理型千兆交換機足夠，便宜、無故障點、壞了直接換；
- **有機櫃、要分業務/管理網段、要做鏈路聚合或抓包**：上管理型。VLAN 能把 BMC、業務流量、訪客網路隔開，是第 8 節安全要求的前提。

兩個必須記住的概念：

1. **交換機不做 NAT，也不做埠轉發**。二層交換機只按 MAC 轉發；三層交換機可以在 VLAN 之間路由，但**通常不做 NAT**。公網埠對映必須由路由器/防火牆完成（見 [軟路由與埠轉發](/tutorials/ops/router-firewall)）。
2. 家用"路由器"其實是**路由 + 交換 + 無線 AP** 的一體機；不要把它和純交換機混為一談。

## 10. 速率選擇與上聯收斂比

| 標準 | 常見介質 | 距離 |
| --- | --- | --- |
| 1000BASE-T（1GbE） | Cat5e / Cat6 | 100 m |
| 2.5GBASE-T / 5GBASE-T | Cat5e / Cat6（802.3bz） | 100 m |
| 10GBASE-T | Cat6 約 55 m；Cat6a 100 m | 依佈線標準與廠商聲明 |
| 10GBASE-SR | OM3 / OM4 多模光纖 | 約 300 m / 400 m |
| 10GBASE-LR | OS2 單模光纖 | 約 10 km |
| SFP+ DAC / AOC | 銅纜直連 / 有源光纜 | 機櫃內短距，通常幾米 |

**對 Minecraft 什麼時候重要？**

- 單個玩家佔用的頻寬其實很小（平均幾十到幾百 kbit/s 量級，進服載入區塊時突發），**一台 1GbE 伺服器足夠帶很多玩家**；
- **1GbE 是絕大多數開服場景的正確答案**；
- 2.5GbE/10GbE 真正有用的是：**儲存/NAS/備份、虛擬機器遷移、大量伺服器之間的內部流量**；
- 別為了"看起來專業"給 MC 服上 10GbE，那筆錢花在 UPS 或 ECC 上更值。

**上聯與收斂比（oversubscription）**：接入埠總頻寬與上聯頻寬之比。例如 24 個千兆口配 2 個萬兆上聯 = 24 Gb/s 接入對 20 Gb/s 上聯，約 1.2:1；配 1 個千兆上聯則是 24:1。小機櫃用千兆上聯完全夠用。注意 **LACP 聚合的是總頻寬，單條流仍走單條鏈路**（雜湊選路），所以單個備份任務未必能跑滿聚合頻寬。

**PoE 只和電話、攝像頭、無線 AP 有關**。伺服器不吃 PoE。規格對照：802.3af 每口約 15.4 W（受電端約 12.95 W）、802.3at/PoE+ 約 30 W（約 25.5 W）、802.3bt Type 3/4 約 60 W / 90 W。整機 PoE 總功率預算有限（隨型號差異很大），帶多個高功率裝置前先算預算。

## 11. 硬體防火牆：它補的是"邊界"這一層

**主機防火牆**（Windows 防火牆、ufw、firewalld、nftables）只保護**它自己那台機器**，而且是在作業系統啟動之後才生效。它做不到：

- 在網路邊界做**有狀態檢測**（conntrack 跟蹤連線狀態），在流量到達任何主機之前就丟棄；
- **NAT / 埠轉發**（這是路由器/防火牆的職責）；
- **網站到網站 VPN**（把兩個地點的內網打通）與**遠端接入 VPN**；
- **統一策略**：一處定義規則，覆蓋整個網段，而不是在每台機器上重複配置；
- **日誌與審計集中**：誰在什麼時候試圖連什麼埠；
- **DMZ 分段**：把公網暴露的服務和內部機器隔開（見第 12 節）；
- 主機沒開機、系統崩了、被入侵後**仍然線上攔截**。

形態有兩種：

- **專用硬體裝置**（各廠商的防火牆/UTM/NGFW 裝置）；
- **x86 + 防火牆發行版**：pfSense（FreeBSD 系）、OPNsense、OpenWrt 等，跑在普通 x86 機器上，價效比高、功能完整，很適合小型機櫃。選型與配置見 [軟路由與埠轉發](/tutorials/ops/router-firewall)。

**關於規格書上的效能數字，務必謹慎**：

| 指標 | 含義 |
| --- | --- |
| Firewall throughput | 通常是大包、無深度檢測的裸轉發能力 |
| IPS / NGFW throughput | 開啟深度檢測後的能力，**往往只有裸轉發的一小部分** |
| VPN throughput | 加密隧道吞吐，與演算法和 CPU 有關 |
| Concurrent sessions | 併發連線表容量 |
| New sessions/sec | 新建連線速率 |

**各家測試方法不同**（包長、協議、是否開啟功能都不一樣），跨廠商直接比數字沒有意義，**以廠商官方 datasheet 的測試條件為準**。

對 Minecraft 場景來說，連線數只有幾百到幾千、頻寬需求通常不到幾百 Mbit/s，**一台入門級裝置或一台小 x86 軟路由就綽綽有餘**。買大號 NGFW 的理由應該是 VPN、分段和管理能力，而不是"MC 需要很多吞吐"。

## 12. 拓撲與 DMZ

標準順序：

```text
互联网 (WAN)
   |
光猫 / ONT
   |
[ 防火墙 / 路由器 ]        <- NAT、端口转发、状态检测、VPN 都在这里
   |
[ 交换机 ]                 <- VLAN 分段、链路聚合
   |----------|----------|
[ MC 服务器 ] [ 管理机 ] [ BMC 管理口 ]
```

**DMZ** 是一塊**獨立的網段/介面/VLAN**，用來放"必須對公網開放"的服務（例如面板、Web 服務）。規則思路：

- WAN 到 DMZ：只放行真正需要的埠；
- **DMZ 到 LAN：預設拒絕**（或只放行極少數必要流量）；
- LAN 到 DMZ：允許管理；
- 這樣即使公網服務被攻破，攻擊者也被困在 DMZ 裡，夠不到內網資料庫和其他機器。

:::warn 消費級路由器上的"DMZ 主機"是另一回事
很多家用路由器的"DMZ"功能是把**所有埠**無條件轉發給某一台內網機器。那不是分段，而是把一台機器完全裸露在公網上。**不要用這個功能**，要按埠逐個轉發。
:::

其他邊界紀律：關閉 WAN 側管理介面、改掉預設密碼、不需要就關掉 UPnP/NAT-PMP、開啟日誌、定期備份防火牆配置。另外，**防火牆擋不住應用層漏洞**——服務端本身的漏洞、插件的 RCE 要靠打補丁和權限管理（見 [安全插件](/tutorials/ops/security-java)）。

## 13. UPS：它到底保護什麼

| 威脅 | UPS 是否解決 | 說明 |
| --- | --- | --- |
| 完全斷電 | 是（有限時間） | 靠電池撐到優雅關機或發電機啟動 |
| 電壓跌落 / 欠壓（brownout） | 是 | 帶 AVR 的機型可升壓補償 |
| 浪湧 / 尖峰 | 部分 | 有鉗位能力，但**直擊雷不在保障範圍** |
| 頻率/電壓波動 | 視機型 | 線上式最徹底 |
| 過載 | 否 | 超載會直接轉旁路或關機 |
| 電池老化 | 否 | 需要定期更換 |

**VA 與 W 的區別**：VA 是視在功率（電壓 × 電流），W 是有功功率，兩者之比是功率因數（PF）。規格書上兩個都會標（例如 1500 VA / 900 W）。**按 W 選型**，並留餘量：負載長期控制在額定 W 的 60%–80% 以內；同時確認 VA 上限也不超。

**續航不是線性的**：負載減半，續航**不會正好翻倍**（鉛酸電池的 Peukert 效應與逆變器固定損耗），而且電池會隨時間和溫度老化。**以廠商的續航曲線為準**，不要自己線性估算。

**波形**：

- 後備式與多數線上互動式在電池模式下輸出的是**模擬正弦（階梯波）**；
- 線上式（雙變換）輸出**純正弦波**；
- **主動 PFC 電源按正弦輸入設計**，遇到階梯波可能出現嗡鳴、切換失敗甚至關機——**具體是否可用取決於電源型號**，以電源廠商規格為準；
- 結論：**主動 PFC 電源優先配純正弦 UPS**；帶電機類負載也應使用純正弦。

**三種拓撲**：

| 類型 | 切換時間 | 輸出波形 | 特點 |
| --- | --- | --- | --- |
| 後備式 / 離線式 | 常見幾毫秒到十幾毫秒 | 多為階梯波 | 最便宜，保護能力最弱 |
| 線上互動式 | 常見 2–10 ms | 多為階梯波，部分機型純正弦 | 小型機櫃最常見，帶 AVR |
| 線上式 / 雙變換 | 0（始終逆變） | 純正弦 | 穩壓隔離最好，發熱、噪音、能耗、價格都更高 |

切換時間與波形**均隨型號變化**，請查具體 datasheet。

**粗略估算負載**：1U 伺服器 250–400 W（取決於 CPU 與盤位）、交換機 30–60 W、防火牆 20–40 W，合計再留 30% 餘量，然後按 UPS 的 **W 額定值**選型，並確認續航滿足"至少撐到自動關機完成"（一般 10–15 分鐘足夠）。

## 14. UPS 監控與 NUT 自動關機

UPS 只有在**能通知主機**時才有意義——否則斷電後你只是多撐了十分鐘，然後照樣硬掉電。連線方式：

| 方式 | 說明 |
| --- | --- |
| USB HID | 現代 UPS 最常見，`usbhid-ups` 驅動直接支援 |
| USB 轉序列埠 | 部分機型走序列埠協議，常用 `nutdrv_qx` 等驅動 |
| RS-232 序列埠 | **線序常常是廠商專用的**，例如某些 APC 機型使用特定型號的專用線（如 940-0024C 一類）；普通交叉線不一定能用，**取決於機型** |
| SNMP 管理卡 | 企業級 UPS 可加網絡卡，通過網路監控，**網絡卡型號隨廠商變化** |

**NUT（Network UPS Tools）** 是 Linux 上最通用的方案，分三層：**驅動（driver）負責與 UPS 通訊，upsd 是服務端，upsmon 是監控客戶端**。upsmon 從 upsd 讀取狀態，並在需要時觸發關機。

安裝包名與服務名**隨發行版不同**：Debian/Ubuntu 通常是 `nut-server`（upsd）與 `nut-client`（upsmon），新版還會用 `nut-driver-enumerator` / `nut-driver@myups`；RHEL/Fedora 系服務名常見 `nut-server` 與 `nut-monitor`；設定檔目錄 Debian 係為 `/etc/nut/`，部分發行版（如 SUSE 系）為 `/etc/ups/`。**以下示例按 Debian/Ubuntu 的路徑給出**。

`/etc/nut/ups.conf`：

```ini
# 定义一台名为 myups 的 UPS
[myups]
    driver = usbhid-ups
    port = auto
    desc = "Rack UPS"
```

`/etc/nut/upsd.users`（`upsmon` 用來登入 upsd 的帳號）：

```ini
[monuser]
    password = secret
    upsmon primary
```

`/etc/nut/upsmon.conf`（最小可用配置）：

```conf
MONITOR myups@localhost 1 monuser secret master
MINSUPPLIES 1
SHUTDOWNCMD "/sbin/shutdown -h +0"
POLLFREQ 5
POLLFREQALERT 5
HOSTSYNC 15
DEADTIME 15
POWERDOWNFLAG /etc/killpower
```

說明與注意點：

- `MONITOR` 行的格式是 `MONITOR <ups> <powervalue> <username> <password> <mode>`；`1` 表示這台 UPS 為系統提供 1 份電源，`master` 表示本機負責在電池耗盡前發起關機；
- **NUT 2.8.0 起把 `master`/`slave` 改名為 `primary`/`secondary`**，舊寫法仍被相容接受；新版文件與示例多用 `primary`，**以你所裝版本的官方文件為準**；
- `/etc/nut/upsd.users` 與 `upsmon.conf` 含密碼，Debian 系應設為 `root:nut` 且權限 `640`，否則 `upsmon` 可能拒絕啟動；
- `upsd` 預設監聽 **TCP 3493**。如果只監控本機，就**不要把它暴露到網路**；確實要做多機監控時，用防火牆限制來源位址。

常用命令：

```bash
upsc myups                     # 列出 UPS 所有变量
upsc myups ups.status          # 只看状态，如 OL（市电）/ OB（电池）/ LB（低电量）
upscmd -l myups                # 列出该 UPS 支持的即时命令
upsrw -l myups                 # 列出可写变量
systemctl restart nut-server   # 改配置后重启（服务名随发行版变化）
upsmon -c fsd                  # 强制关机演练，慎用
```

**電池更換與自檢**：

- 常見的閥控鉛酸（VRLA/AGM）電池壽命通常 **3–5 年**；**環境溫度越高壽命越短**（工程經驗上每升高約 10 攝氏度壽命大致減半，屬經驗規律）；
- 很多 UPS 每兩週自動做一次自檢，也可手動觸發（面板按鍵或 `upscmd myups test.battery.start.quick`，命令名取決於機型）；
- **當自檢失敗或續航低於你的要求時就該換電池**；同一串電池要整組一起換；
- 鋰電池（如 LiFePO4）機型壽命通常更長，但**取決於具體型號**；
- 舊電池按當地規定回收，不要隨手丟棄。

## 15. 線纜與供電安全

**供電**

- **絕不串聯插排**（插排插插排）。串聯會增大接觸電阻、讓斷路器配合失效，並可能讓單個牆插過載。機架裡用**機架式 PDU**。
- PDU 有橫裝 1U 與豎裝 0U 兩種；插座常見 **IEC 60320 C13（約 10 A 級）** 與 **C19（約 16 A 級）**，進線為 C14/C20。選**計量型或可遠端控制**的 PDU 便於排查與遠端重啟。
- **把 UPS 輸出接到 PDU，把要保護的裝置接到該 PDU**；不要把關鍵裝置直接插牆上。
- **清楚支路容量**：中國常見 10 A / 250 V 插座約 2200 W；北美 NEMA 5-15 在 15 A / 120 V 支路上約 1800 VA，且按規範連續負載通常只取 80%（約 1440 W）；英國 BS 1363 為 13 A。**實際以現場電氣設計與電工判斷為準，不要頂著上限跑。**
- **接地**：不要掰掉地線腳、不要用"三轉二"轉接頭、機櫃要做等電位連線。浮地既是觸電與起火風險，也會造成莫名其妙的間歇性故障。

**線纜**

- **兩端都貼標籤**：一端寫對端裝置與埠，另一端寫回來。機房裡沒有標籤的線，等於沒有線。
- 保留一份簡單的拓撲圖或表格（哪台機器哪個口接到哪個交換機口）。
- 線束用**魔術貼**而不是紮帶：紮帶會勒傷線纜、且改動時必須剪斷。
- **光纖注意彎曲半徑**（一般不小於線纜直徑的 10 倍，具體看廠商規格），不要打死折；銅纜也不要長期過度彎折。
- 強弱電儘量分開走線；用滑動導軌時給線纜留夠餘量，並考慮理線臂。
- **常備備件**：各長度的網線各一根、C13/C19 電源線、SFP+/DAC 模組、卡式螺母與螺釘、一塊備用硬碟。在託管環境裡，一次"遠端手"上門費往往比這些備件貴得多。

## 16. 上架前檢查清單

- [ ] 機櫃深度與導軌支援範圍匹配，U 位已規劃並留出維護空間
- [ ] 空 U 位已裝盲板，前面板進風口無遮擋，防塵網乾淨
- [ ] 電源 A/B 分別接到不同 PDU / 不同支路，且每路都經過 UPS
- [ ] 支路總負載已核算，未超過額定值（含餘量）
- [ ] 接地正常，沒有使用任何破壞地線的轉接件
- [ ] BMC 已改預設密碼，接在獨立管理網段，**確認從公網不可達**
- [ ] 交換機上已劃分業務 / 管理 / 訪客 VLAN（如使用管理型交換機）
- [ ] 公網只開放必要埠（Java `TCP 25565`；基岩 `UDP 19132`），**RCON `TCP 25575` 與資料庫埠未暴露**
- [ ] 防火牆/路由器配置已匯出備份，WAN 側管理已關閉
- [ ] UPS 已接入監控，**已實際演練過一次自動關機**
- [ ] 所有線纜兩端已貼標籤，拓撲記錄已更新
- [ ] 備件（網線、電源線、模組、硬碟）已就位

埠速查（預設值，均可修改）：

| 用途 | 協議/埠 |
| --- | --- |
| Java 版遊戲 | TCP 25565 |
| 基岩版遊戲 | UDP 19132 |
| Query（可選） | UDP 25565 |
| RCON（**禁止暴露**） | TCP 25575 |
| IPMI / BMC | UDP 623 等 |
| SNMP | UDP 161 / 162 |
| NUT | TCP 3493 |
