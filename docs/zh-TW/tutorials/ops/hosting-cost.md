"開個服要多少錢"是一個沒有標準答案的問題，但**問錯方式**很常見。真正該問的是三個問題：**我的規模是多少？我的預算裡哪些是一次性、哪些是每月？以及我願意投入多少時間？**

很多人的第一反應是比價：把幾家的套餐價格列出來，挑最便宜的那一欄。這樣做通常會在半年後付出更高的代價——不是因為買貴了，而是因為**買錯了**，然後在遷移、丟檔、被攻擊的時候把省下的錢一次性還回去。

這一篇講怎麼把錢花在真正決定體驗的地方。主機層面的加固見 [系統安全加固](/tutorials/ops/system-security)，搬家的代價見 [伺服器遷移](/tutorials/ops/server-migration)，被攻擊時的現實見 [常見網路攻擊類型與 Minecraft 專項防禦](/tutorials/ops/attack-defense)。

:::warn 價格與套餐以服務商官方頁面為準
本文寫於無法聯網核對的狀態，**下面所有金額、單位與套餐形態都只是"量級示意"，不是報價**。價格、計費方式、退款政策、超流量單價、DDoS 防護是否贈送，**每一家都不一樣，而且隨時會變**。動手前請以服務商官方價格頁與合同條款為準。
:::

## 1. 先把"成本"這個詞拆開

一次開服的總成本，由四類東西構成，它們的性質完全不同：

| 類別 | 例子 | 特點 |
| --- | --- | --- |
| **一次性支出** | 硬體、域名首年、遷移的人工、初始配置 | 只在開始或大變更時付一次，容易被忽略 |
| **固定月支出** | 主機月費、頻寬包、備份儲存、面板 | 每月都要付，**決定你的長期負擔** |
| **變動支出** | 超流量費、快照儲存、高防附加費、按量計費 | 平時看不出來，出事或增長時突然變大 |
| **時間成本** | 更新、備份驗證、玩家管理、事故處理 | **最貴也最容易被算成 0** |

**把這四類分開算，選型就清楚了一半。** 很多"看起來便宜"的方案，便宜的是第二類，代價藏在第三類和第四類裡。

:::note 一個判斷標準
如果兩個方案月費相差不大，**選那個讓你以後更容易搬家、更容易加備份、更容易換配置的**。開服這件事上，"可遷移性"和"可觀測性"通常比省下的幾十塊錢值錢。
:::

## 2. 真正的成本驅動因素

### 2.1 CPU 單核效能（最容易被低估）

Minecraft 的**主邏輯（tick 迴圈）基本跑在單個執行緒上**。這意味著：

- **核多不代表流暢。** 一台 8 核但單核很弱的主機，跑一個 20 人的原版服，很可能不如一台 2 核但單核很強的主機。
- **掉 TPS 的直接原因常常是單核跑滿**，此時整機 CPU 使用率可能只有 15%。
- 世界生成、區塊載入、實體與紅石運算都會加劇單核壓力。

所以選主機時，**單核效能的優先順序高於核心數量**。這一點在廉價套餐裡尤其重要：超售的宿主上，你拿到的"3.0 GHz"是共享的。

### 2.2 記憶體

記憶體決定"能開多大、能裝多少東西"：

- 原版/Paper 服務端：小規模（幾個人到十幾人）通常幾 GB 堆就能跑，**但具體數字隨版本、視距、插件與玩法差異極大**。
- 模組服與整合包：記憶體需求通常是原版的數倍，**以整合包作者與載入器的官方說明為準**。
- 面板、網頁地圖、資料庫、代理端都會額外佔記憶體，**別隻給服務端算記憶體**。
- 記憶體給太多也有代價：堆過大時一次 GC 的停頓更長。**"記憶體越大越好"是錯的**，正確做法是給夠並觀察 GC 與 MSPT。

### 2.3 磁碟：SSD 與 IOPS

世界儲存、區塊載入、備份打包全都吃磁碟。**磁碟慢的時候 CPU 看起來還很閒**，這是最難定位的一類卡頓。

- **必須 SSD。** 機械盤跑現代服務端體驗極差，尤其是區塊載入。
- 比"是不是 SSD"更重要的是**隨機讀寫能力（IOPS）**與**是否與其他租戶共享**。
- **磁碟快滿是會毀資料的**，所以可用空間要留出餘量（備份、日誌、核心轉儲都吃空間）。

### 2.4 頻寬

- **上行（出方向）才是瓶頸**：玩家下載區塊、獲取資源包走的都是你的上行。
- **家寬通常是非對稱的**，上行很小；機房線路通常對稱。
- **流量計費與頻寬計費是兩種不同的模式**，前者按 GB 結算、後者按 Mbps 峰值結算，賬單風險完全不同。

### 2.5 DDoS 防護

對 Minecraft 來說，防護不是"進階選項"：

- Java 版走 TCP（預設 25565），基岩版走 **UDP**（預設 19132），**UDP 洪泛是基岩版最典型的攻擊形式**。
- 廉價套餐通常**不包含**有效防護，或者只送一層很薄的清洗。
- **高防通常是按月附加費，且價格與防護頻寬掛鉤**；具體形式與價格以服務商為準。

防護思路與攻擊類型見 [常見網路攻擊類型與 Minecraft 專項防禦](/tutorials/ops/attack-defense)。

### 2.6 備份空間

**備份要佔的空間往往和你的世界一樣大，而且需要多份。** 常見的錯誤是"主機買得很省，備份沒地方放"，結果備份腳本默默失敗好幾個月——直到你需要它的那一天。

- 備份要**放在你租的主機之外**（異地/物件儲存），見 [異地備份](/tutorials/ops/offsite-backup)。
- 物件儲存的**取回（下行）流量通常單獨計費**，恢復演練也會花錢。
- 保留策略（保留幾份、留多久）直接決定成本。

### 2.7 你自己的時間

這是唯一一項**幾乎所有人都算成 0** 的成本，而它通常是最大的一項：

- 每週的更新、插件相容排查、備份驗證。
- 玩家管理：白名單、申訴、糾紛、熊孩子。
- 事故處理：被攻擊、崩服、丟檔、被入侵。

**如果你的時間不值錢，那是因為你還沒有把它記進賬。** 一個需要你每週投入 5 小時的方案，和一個月費貴 50 元但省下 3 小時的方案，後者往往更划算。

### 2.8 線路與延遲

頻寬數字決定"能裝多少人"，**線路與延遲決定"手感好不好"**。兩者不能互相替代：

- 玩家與伺服器之間的**往返延遲（RTT）**直接影響挖掘、攻擊、走位的響應感受；延遲高的時候，頻寬再大也沒用。
- **機房位置與線路質量**往往比頻寬更重要：同樣的 100 Mbps，不同線路對國內玩家的實際體驗可能差很多。
- **跨運營商訪問**是常見的坑：某一家的玩家很快，另一家的玩家一直在跳延遲。
- 測法是**用真實客戶端從玩家的網路去連**，而不是隻在伺服器上 `ping` 閘道器：`mtr` / `traceroute` 能看出丟包發生在哪一跳。

### 2.9 計費週期、退款與合同

這些條款不影響效能，但**決定你"買錯了"要付多少代價**：

- **按小時/按量計費**適合試錯，但單價通常更高；**月付**是大多數個人服的平衡點；**年付**折扣最大、鎖定最深。
- **退款政策**要看清楚：有的商家"隨時退"，有的只在首次購買後若干天內退，有的按已用時長折算。
- **續費價可能高於首單價**，這是常見的促銷結構，算長期成本時要看續費價。

:::note 判斷"能不能試"的最快方法
下單前先問一句：**如果三天後發現效能不行，我能拿回多少錢？** 答案含糊的商家，把"年付"換成"月付"再決定。
:::

## 3. 七種方案對比

下表是**定性對比**，不涉及具體價格。讀的時候重點看最後兩列：**隱藏成本**和**什麼時候別選它**。

| 方案 | 適用規模 | 優點 | 缺點 | 隱藏成本 | 什麼時候別選它 |
| --- | --- | --- | --- | --- | --- |
| 家用電腦 / 家庭寬頻 | 朋友小服、測試、臨時開 | 一次性投入、資料在自己手裡、可隨時折騰 | 上行小、可能沒有公網 IP、斷電與斷網就停服、家裡網路被攻擊會波及全家 | 電費、噪聲與熱量、硬體折舊、需要自己維護 UPS 與路由器、時間成本最高 | 面向公網、需要 7x24 穩定、需要抗攻擊、玩家規模超過十餘人 |
| 共享虛擬主機 | 靜態網站、PHP 網站 | 便宜、開箱即用 | **通常不能跑長期行程，也不能開放自定義埠**，資源限額嚴格 | 升級無路可走、遷移成本 | **基本上都不適合 Minecraft 服務端**，除非商家明確賣的是遊戲服 |
| VPS | 中小規模、個人服、代理端 | 價格適中、有 root、可自選系統與核心 | 資源與鄰居共享、廉價套餐普遍超售、防護通常很薄 | 頻寬多為"共享"或按流量計費、快照另收費、被攻擊時可能被停機 | 需要大記憶體模組整合包、需要強防護、需要獨享物理效能 |
| 獨立伺服器 | 中大規模、模組整合包、多實例 | 物理獨享、效能穩定可預期、可自選硬體 | 月費高、開通慢、硬體故障要等機房處理 | 頻寬與防護常單獨計價、IP 與機位費、維保與備件 | 只有幾個人玩、預算敏感、自己不打算做維運 |
| 面板服 / 遊戲主機商 | 想少折騰的中小服 | 面板、備份、定時任務現成，按記憶體或槽位賣 | 只能用它給的環境、自定義受限、超售常見 | 附加記憶體與附加備份的加價、遷移受限於商家工具、CPU 限額不寫在廣告上 | 需要自定義系統或核心、需要特殊 mod 環境、需要長期低成本大規模 |
| 雲伺服器按量 | 波動負載、短期活動、測試 | 彈性、按需開停、生態完善（快照、映像、監控） | **賬單不可預測**、預設配置通常偏貴、需要自己搭一切 | 公網 IP、快照儲存、映像、日誌、出網流量的單獨計費；忘記關機就一直在燒錢 | 長期穩定負載（包年包月通常更划算）、不設預算告警的團隊 |
| 託管 / colocation | 自有硬體、規模化、合規需求 | 硬體自主、長期單位成本可能更低 | 需要自備硬體、籤合同、故障要自己處理 | 機位費、電力費、頻寬費、遠端手（remote hands）費用、到場時間 | 只有一台機器、沒有備件、沒有維運能力 |

### 3.1 家用電腦 / 家庭寬頻

它的定位很清楚：**成本最低、可控性最高、可靠性最低**。適合朋友之間的小服。判斷能不能用，先確認三件事：**有沒有公網 IP**（很多家寬是 CGNAT，根本沒有）、**上行有多大**、**運營商條款是否允許長期對外提供服務**。詳細做法與坑見 [家用電腦開服與維護](/tutorials/ops/home-hosting)。

### 3.2 共享虛擬主機

**它不是 Minecraft 的選項。** 共享主機賣的是"網站執行環境"：沒有長期駐留的行程、不能監聽任意埠、CPU 與記憶體有硬限額。少數商家把"遊戲服"也歸到這個詞下，那種其實是面板服或容器，按 3.5 判斷。

### 3.3 VPS

個人與小團隊最常用的方案。要點是：**便宜套餐的"核數"參考價值有限，單核效能與磁碟 IOPS 才是關鍵**；頻寬要看清是"獨享"還是"共享"、是"不限流量但限速"還是"按流量計費"。

### 3.4 獨立伺服器

當整合包、多實例或玩家規模把 VPS 逼到牆角時，獨服是自然的下一步。它的價值是**可預期**：物理核、物理盤、物理頻寬。代價是**月費與維運責任一起上升**。

### 3.5 面板服 / 遊戲主機商

適合"我不想碰 Linux"。它的錢主要花在**省時間**上，所以判斷標準是：**它省的維運時間，是否大於它的溢價**。注意兩點：**廣告上的 CPU 型號往往不等於你實際分到的效能**；**遷移工具通常只能遷出它自己的格式**，走之前先確認你的存檔與配置能不能完整帶走。

### 3.6 雲伺服器按量

按量的優勢是彈性，劣勢是**賬單的不可預測性**。開一台機器做測試很爽，忘關一個月也很"爽"。如果要用，先做三件事：設**預算告警**、設**自動關機或到期提醒**、把**公網 IP 與快照的計費方式**看明白。

### 3.7 託管 / colocation

它是"我已經有硬體，也有維運能力"的答案。單位成本隨規模下降，但**門檻與責任也隨規模上升**：硬體故障時沒有服務商替你換盤，只有你自己（或者付費的 remote hands）。

## 4. 容易漏掉的成本項

| 成本項 | 為什麼容易漏 | 怎麼避免 |
| --- | --- | --- |
| 公網 IP / 彈性 IP | 有些商家把 IP 單獨計價，閒置的 IP 也可能收費 | 下單前在價格頁確認 IP 是否包含、閒置是否計費 |
| 流量超額計費 | "不限流量"常附帶公平使用條款或限速 | 看清是限速還是計費、超額單價是多少 |
| 備份儲存 | 備份不佔主機空間，但佔物件儲存的錢 | 先算世界大小 x 份數，再選保留策略 |
| 快照 | 快照不是備份，而且按容量計費 | 用備份代替快照作為資料保全手段（見第 8 節） |
| DDoS 高防 | 防護頻寬越大越貴，且常是月付附加項 | 明確"基礎防護"能扛住什麼，再決定要不要買 |
| 域名與證書 | 域名按年續費，忘了續費會直接失去解析 | 開自動續費；證書見 [HTTPS 證書與自動續期](/tutorials/ops/https) |
| 電費與噪聲（家寬方案） | 電腦 7x24 開著，電錶與耳朵都知道 | 按當地電價估算（見下方示例），並考慮散熱與噪聲 |
| 時間成本 | 沒人把它寫進預算表 | 每週記錄一次實際投入，幾個月後你會改主意 |
| 遷移成本 | 搬家不是複製檔案，而是**一次維護視窗** | 見 [伺服器遷移](/tutorials/ops/server-migration) |

:::tip 電費的一個算例
一台平均功耗約 60 W 的機器 7x24 執行：60 W x 24 h = 1.44 kWh/天，約 43 kWh/月。按 0.6 元/kWh 計，約 **26 元/月**。這只是一個算例：**功耗與電價都要用你自己的數字重算**，顯示器、路由器、UPS 與空調的額外負擔另計。
:::

## 5. 誠實地估算規模

### 5.1 玩家數到資源的粗估

下表是**量級參考，不是規格書**。真實需求受版本、核心、視距、插件、世界大小與玩法影響極大。

| 規模 | CPU | 記憶體（服務端堆） | 頻寬 | 備註 |
| --- | --- | --- | --- | --- |
| 2 - 5 人，朋友服 | 單核較強的雙核即可 | 2 - 4 GB 量級 | 家寬上行通常夠用 | 家用電腦往往就夠 |
| 10 - 20 人，原版/輕插件 | 高單核效能，2 - 4 核 | 4 - 8 GB 量級 | 幾 Mbps 量級 | 視距與實體數量影響巨大 |
| 30 - 50 人，插件服 | 高單核 + 多核輔助 | 8 - 16 GB 量級 | 十幾 Mbps 量級 | 需要真正的 SSD 與穩定線路 |
| 模組 / 整合包 | 高單核效能優先 | 常為原版數倍 | 取決於同步量 | **以整合包官方說明為準** |
| 多實例 / 群組服 | 多核開始有意義 | 各實例相加再加代理與資料庫 | 疊加 | 見 [跨服端](/tutorials/java/proxy) |

**頻寬的粗估**：穩態下每個玩家通常只佔**幾十 KB/s 量級**（約 0.2 - 1 Mbit/s），但視距大、實體多、玩家飛行載入新區塊時會明顯更高，**進服瞬間傳送區塊的突發流量遠大於穩態**。這些數字高度依賴版本與玩法，**請以你自己的實測為準**（`vnstat`、`nload`、面板的流量圖都行）。

### 5.2 超售是廉價套餐的常態

"共享型""突發型""公平使用"這些詞背後通常是同一件事：**你買到的是一份配額，不是一個獨佔的核**。這本身不是欺騙，而是廉價套餐能存在的原因；問題在於**它讓"看參數買機器"這件事不可靠**。

實踐建議：

- 把**單核效能**當作首要指標，而不是核數或主頻數字。
- 對"長期高負載"的預期要保守：突發額度適合峰值，不適合 7x24 滿載。
- **先買短週期驗證**，跑起來再決定要不要長期。

### 5.3 別隻看單價，算單位成本

比較兩個方案時，把它們換算成同一口徑：**每月總支出 ÷ 可穩定支撐的玩家數**。這樣一算，"貴 30% 但能多帶一倍玩家"的方案往往立刻變得划算。

### 5.4 先買小、再長大

一個反直覺但很實用的策略：**先買明顯偏小的一檔，驗證真實瓶頸，再按瓶頸加錢。**

原因是**大多數人會高估自己的規模**。開服前想的是"以後會有 50 人"，現實往往是前三個月平均線上 3 人。如果一開始就按 50 人買，你會在很長一段時間裡為不存在的玩家付費。

具體做法：

1. 按"當前規模 + 一點餘量"買最小的可用檔位。
2. 用 [監控與告警](/tutorials/ops/monitoring) 記錄 CPU 單核佔用、記憶體、磁碟 I/O 與頻寬的真實曲線。
3. 資料說話再升級：**升配通常比降配容易**，而且很多商家支援線上升配（**是否支援、是否要重啟，以商家文件為準**）。
4. 如果瓶頸是磁碟 I/O 或單核效能，**加記憶體是沒用的**——這時要考慮換商家而不是升套餐。

## 6. 買之前怎麼測

### 6.1 單核效能比核數重要

第三方跑分（如常見的單執行緒評分）可以作為**粗篩**，用來排除明顯不行的機器，但它**測不出超售、鄰居干擾與磁碟瓶頸**。所以跑分只用來縮小範圍，最終判斷要靠實測。

### 6.2 要試用，或者先買最短週期

- 優先選**提供試用或按小時計費**的商家，跑一次真實負載再決定。
- 沒有試用就**先買最短週期**（月付甚至按天），不要一上來就年付。
- **一定要測"你的真實場景"**：把服務端、插件、存檔搬上去，叫幾個人進來玩一次，比任何跑分都有說服力。

### 6.3 測磁碟 I/O

磁碟是廉價套餐最容易偷工減料的地方。兩種常見測法：

```bash
# 顺序写测试：在目标文件系统上建临时文件，测完删掉
dd if=/dev/zero of=./io-test.bin bs=1M count=1024 conv=fdatasync status=progress
rm -f ./io-test.bin

# 随机读测试（需要安装 fio；参数含义以 fio 官方文档为准）
fio --name=randread --rw=randread --bs=4k --iodepth=32 \
    --size=1G --numjobs=1 --time_based --runtime=30s --group_reporting
```

讀結果時注意：`dd` 的順序寫數字**容易偏樂觀**（受快取與檔案系統影響），隨機讀的 IOPS 才更接近區塊載入與存檔寫入的真實壓力。**測試會在磁碟上產生大量寫入，請在臨時目錄做，測完刪除，不要在服務端資料目錄裡做。**

## 7. "現在便宜、以後貴"的陷阱

| 陷阱 | 便宜在哪 | 貴在哪 | 怎麼繞開 |
| --- | --- | --- | --- |
| 遷移成本被無視 | 選了最便宜的機器 | 搬家要停機一次，還要處理 DNS、白名單、備份、監控 | 一開始就選**能匯出完整資料**的方案，並把搬家當作必然事件；見 [伺服器遷移](/tutorials/ops/server-migration) |
| 沒有備份空間 | 只買了主機，沒買儲存 | 一次丟檔就是全部進度 | 備份從一開始就放在主機之外；見 [異地備份](/tutorials/ops/offsite-backup) |
| 沒有 DDoS 防護 | 省下防護月費 | 被攻擊時掉線、被商家停機、玩家流失 | 至少確認基礎防護的能力邊界；見 [常見網路攻擊類型與 Minecraft 專項防禦](/tutorials/ops/attack-defense) |
| 超流量賬單 | 按量計費單價看起來低 | 一次攻擊或一次資源包分發就能燒掉一個月預算 | 設預算告警、優先選限速而非計費、把資源包放物件儲存 |
| 年付鎖定 | 年付折扣很香 | 商家跑路、效能不達標、想換也換不了 | 第一年先月付，穩定後再考慮長期 |
| 時間被算成 0 | 自己動手"不要錢" | 每週幾小時的持續投入 | 把時間記進預算表，定期復盤 |

## 8. 合法地降低成本

這些做法**不犧牲可靠性**，只是把資源花在刀刃上：

- **降低視距（view-distance）**：這是最有效的單項最佳化，直接減少區塊傳送與實體處理。
- **減少常駐世界**：每個額外維度/世界都在吃記憶體與磁碟 I/O；不用的先關掉。
- **定時重啟**：緩解記憶體緩慢增長與控制代碼洩漏（**但它不是修復，只是掩蓋**；要同時查根因）。
- **用備份代替快照**：快照按容量計費且不等於可恢復的備份；正確的資料保全見 [備份與恢復](/tutorials/java/backup)。
- **預生成世界**：把區塊生成的開銷挪到開服前，減少執行時的單核尖峰。
- **自己跑面板**：面板服省的是時間，如果你本來就會 Linux，自建面板可以省下溢價（代價是多一個要維護的元件，見 [面板管理工具的使用與安全](/tutorials/ops/panels)）。
- **關掉不用的服務**：網頁地圖、額外實例、測試服，都是持續佔資源的。
- **合併低峰**：玩家集中在晚上時，可以只在那段時間開高配實例。

:::warn 降成本的兩條紅線
**不要省備份，不要省防護。** 這兩項省下來的錢，通常會在第一次事故里連本帶利還回去。可以降配、可以換便宜機器，但**能恢復的資料**與**能扛住的攻擊**是底線。
:::

## 10. 小結

- **先估規模，再選方案。** 玩家數、是否模組、是否對外公開，決定了你根本不需要考慮哪些選項。
- **單核效能 > 核心數量**，**磁碟 IOPS > 磁碟容量**（在夠用的前提下）。
- **把一次性、每月、變動、時間四類成本分開算**，隱藏成本大多在第三、四類。
- **小服的最優解通常很簡單**：朋友之間玩，家用電腦或最便宜的、夠用的 VPS 就很好，重點是**備份**。
- **公開服是另一回事**：一旦對公網開放，**真正的防護與真正的異地備份就不是可選項**，主機預算也要按這個前提來定。
- **搬家能力要在買的時候確認**，而不是在要搬的時候才發現。
