[宣傳與引流](/tutorials/ops/promotion) 解決的是"玩家怎麼找到你"，[經濟與玩法插件](/tutorials/ops/gameplay-plugins) 解決的是"伺服器裡有哪些系統"，[[JAVA] 經營管理](/tutorials/ops/management-java) 解決的是"團隊和錢怎麼安排"。這三篇講的都是**框架**。這一篇講的是框架裡真正發生的事：**某個晚上，一群人在你的伺服器裡一起做了一件事，做完之後還想再來。**

活動不是運營的裝飾品。它是把一批互不相識的玩家變成社群的最短路徑，也是讓老玩家有理由回來的少數手段之一。它同時也是最容易翻車的一環：時間定錯、規則沒寫、場地沒建、獎勵發崩，任何一項都能把一場本來不錯的活動變成退服潮。

本文不涉及具體插件選型。需要插件清單時看 [插件入門](/tutorials/java/plugins) 與 [常用前置插件](/tutorials/java/plugin-deps)。

:::note 本文的邊界
本文不給出任何具體活動插件、小遊戲插件或獎勵插件的名稱、命令與配置鍵。**這類插件的名稱、功能、可用命令與設定項差異很大，並且會隨版本變化**，所以本文只描述"要做哪一類事、這一類事通常由哪一類工具承擔"。具體到你的服務端能裝什麼、怎麼寫配置，請以各插件官方文件為準。
:::

## 1. 為什麼活動值得做

### 1.1 新玩家在最初幾分鐘就做了決定

新人進服後的前幾分鐘決定了他會不會留下。這段時間裡他面對的問題不是"玩法夠不夠多"，而是**"這裡有沒有人在，我該幹什麼"**。一個空蕩蕩的出生點配上一份長長的說明書，效果遠不如"今晚八點有跑酷比賽，來玩"。

### 1.2 迴歸玩家需要一個具體的理由

"伺服器還在開著"不構成回來的理由。"週六晚上有建築比賽，你上次那棟房子可以拿去參賽"才構成理由。活動給的是一個**時間點**，而人對時間點的反應遠強於對狀態的判斷。

### 1.3 活動把伺服器變成社群

玩家之間的關係不是靠規則建立的，是靠**共同經歷**建立的。一起輸掉一場團本、一起在尋寶裡找錯方向、一起看著別人建的城堡發呆，這些才是"我們是同一個服的人"的來源。

| 玩家狀態 | 他真正在問的問題 | 活動能提供什麼 |
| --- | --- | --- |
| 剛進服的新人 | 這裡有人嗎？我該幹什麼？ | 一場馬上能參與、門檻極低的活動 |
| 玩了幾天的玩家 | 除了蓋房子還能做什麼？ | 一個明確的時間點，有人一起玩 |
| 玩了幾週的老玩家 | 我留在這裡的意義是什麼？ | 身份、榮譽、被需要的位置 |
| 離開了一陣的人 | 有理由回來嗎？ | 一條活動通知就是那個理由 |
| 只在群裡聊天的人 | 我算這個服的人嗎？ | 一個露臉並被記住的機會 |

:::tip 活動真正的產出不是獎勵
獎勵發完就沒了，**共同記憶不會**。評價一場活動成不成功，看的不是"獎發出去沒有"，而是"活動結束後聊天頻道還熱不熱、有沒有人問下次什麼時候"。如果一場活動結束後立刻歸於死寂，那它更像一次發獎，而不是一次活動。
:::

:::warn 活動不是萬能藥
活動能放大一個已經能玩的伺服器，**不能修補一個不好玩的伺服器**。如果新人流失的原因是出生點看不懂、卡頓、沒人理他，那麼辦活動只會讓更多人更快地看到這些問題。先解決體驗，再談活動。
:::

## 2. 活動類型一覽

下面按類別列出常見活動。表格裡的"需要準備什麼"只寫類別，具體由哪一類工具承擔，請對照各插件官方文件確認。

| 類型 | 例子 | 需要準備什麼 | 適合人數 | 風險 |
| --- | --- | --- | --- | --- |
| 建築比賽 | 主題建築賽、一小時速建、改造出生點 | 一塊劃分好的場地、評分標準、評委、作品保護 | 5 至 50 人 | 評分主觀引發爭議；作品被破壞；超時收不了尾 |
| PvP 競技賽 | 1v1 決鬥、團隊戰場、裝備統一的擂台賽 | 競技場、統一裝備方案、裁判、觀戰位、復活點 | 8 至 40 人 | 裝備與延遲不公平；組隊刷名次；觀戰干擾比賽 |
| 跑酷競速 | 競速賽道、限時通關、團隊接力 | 賽道、計時方式、檢查點與掉落處理 | 5 至 30 人 | 賽道卡點被利用；掉線成績作廢；計時口徑不清 |
| 尋寶 / 解謎 | 藏寶圖、座標謎題、限時尋物 | 線索設計、藏點清單、答案核對人 | 10 至 100 人 | 線索被提前洩露；有人直接翻地圖檔案 |
| Boss / 團本夜 | 集體挑戰強敵、限時討伐、掉落分配 | 戰鬥場地、難度與人數匹配、掉落規則 | 10 至 30 人 | 人數不夠打不過；掉落分配吵架；伺服器負載高 |
| 節日活動 | 萬聖節、新年、伺服器週年 | 裝飾、限時玩法、節日獎勵 | 全服 | 排期撞車；裝飾改動影響正常玩法 |
| 社群目標 | 全服共建工程、累計收集目標 | 進度展示、貢獻記錄、階段獎勵 | 全服 | 少數人包辦；進度卡在中途失去動力 |
| 新人歡迎會 | 集體迎新、老帶新、新人專場 | 值班人員、講解流程、迎新禮包 | 5 至 20 人 | 老玩家搶戲；新人插不上話；變成單向宣講 |
| 劇情 / RP 活動 | 劇本演出、陣營對抗、世界事件 | 劇本、角色分配、場地與道具、主持人 | 10 至 30 人 | 劇本被打斷；有人不按設定走；準備量極大 |

### 2.1 各類活動的設計要點

| 類型 | 設計上最該花心思的地方 | 最常見的翻車方式 |
| --- | --- | --- |
| 建築比賽 | 評分標準要提前公開，並且拆成可打分的幾條 | 評委憑喜好打分，參賽者當場不服 |
| PvP 競技賽 | 裝備、附魔、藥水、延遲四項必須統一或明確聲明 | 有人帶著自己攢的裝備來，比賽變成單方面碾壓 |
| 跑酷競速 | 計時起點與終點必須唯一且可復現 | 有人抄近路，而規則沒寫"必須經過檢查點" |
| 尋寶 / 解謎 | 線索難度分層，保證前 10 分鐘人人都有事做 | 第一個謎題卡住所有人，活動十分鐘內散場 |
| Boss / 團本夜 | 人數與難度匹配，掉落規則提前說清 | 打完分配掉落時吵起來，比打不過更傷 |
| 節日活動 | 裝飾與限時玩法都要能一鍵還原 | 節日結束後裝飾留在主城，長期影響體驗 |
| 社群目標 | 進度要可見，個人貢獻要被記錄 | 目標定得太大，三天後沒人再提 |
| 新人歡迎會 | 讓新人做主角，老玩家只做引導 | 變成管理員的單向宣講會 |
| 劇情 / RP 活動 | 劇本留出玩家自由發揮的空間 | 玩家不按劇本走，主持人當場僵住 |

:::note 小服優先選"低準備成本"的類型
人手少的時候，跑酷競速、尋寶、新人歡迎會的價效比遠高於劇情活動和大型團本。**活動規模要匹配你能投入的準備時間**，而不是匹配你想像中的伺服器規模。
:::

### 2.2 按伺服器類型挑活動

同一個活動放在不同類型的伺服器上，效果可能完全相反。選類型之前先看你自己的伺服器定位（定位怎麼寫見 [宣傳與引流](/tutorials/ops/promotion)）。

| 伺服器類型 | 優先考慮的活動 | 儘量避免的活動 |
| --- | --- | --- |
| 原版生存服 | 建築比賽、社群共建、尋寶、節日活動 | 高強度 PvP 競技、會破壞世界狀態的玩法 |
| 生電 / 技術服 | 技術挑戰賽、機制解謎、全服共建工程 | 依賴大量實體與特效的混戰型活動 |
| 小遊戲服 | 排位賽、周賽、限時模式輪換 | 需要長期積累才能參與的活動 |
| RP / 角色扮演服 | 劇情事件、陣營對抗、世界事件 | 純競技類、與設定無關的娛樂活動 |
| 基岩版 / 跨端服 | 門檻低、不依賴客戶端模組的活動 | 依賴特定客戶端功能的玩法 |
| 模組服 | 與模組機制結合的活動 | 與模組機制衝突或需要額外客戶端配置的活動 |

## 3. 怎麼策劃一場活動

### 3.1 定時間：先確認玩家在哪個時區

這是最容易出錯、也最容易被忽略的一步。你的玩家可能分佈在多個時區，或者集中在某個你並不居住的時區。

- **以玩家為主，不是以你為主**。如果核心玩家群體在另一個時區，活動時間就該按他們的作息定，哪怕對你來說是凌晨。
- **先問，再定**。在群裡發一個簡單的投票，比你自己猜有效得多。
- **寫清時區**。公告裡寫"20:00"是不夠的，要寫成"北京時間 20:00"，並換算成主要玩家時區的時間。
- **避開工作日白天、考試周與節假日出行高峰**。週末晚上通常是最穩的選擇。
- **給足提前量**。小型活動至少提前 2 至 3 天，大型活動提前 1 至 2 周。

### 3.2 提前、反覆地公佈

只發一次通知等於沒發。玩家不會記住一條三天前的訊息，但會記住反覆出現的同一個時間點。

- **至少發三輪**：定檔時發一次，活動前一兩天發一次，開始前一兩小時再提醒一次。
- **內容要一致**。三輪公告裡的時間、地點、規則不能有任何變化；要改就明確說"改了哪裡"。
- **多渠道覆蓋**：遊戲內公告、群公告、伺服器列表頁的簡介、進服時的歡迎資訊。宣傳渠道的選擇見 [宣傳與引流](/tutorials/ops/promotion)。
- **把"怎麼參加"寫進公告**。玩家不該為了知道怎麼報名而先去問人。

### 3.3 把規則寫下來

口頭規則在爭議發生的那一刻就消失了。**寫下來的規則勝過任何一次爭論**。

- 寫清"允許什麼、禁止什麼、由誰判定、平局怎麼辦、違規怎麼處理"。
- 規則要在活動開始前公開，而不是等活動出問題再補充。
- 規則要短。超過一屏的規則沒人會讀，把最關鍵的三到五條放在最前面。
- 與伺服器總規則衝突時以總規則為準，見 [社群規範](/rules)。

### 3.4 場地要提前建好、提前載入

**絕不要在活動開始時才動手建場地。** 現場搭建幾乎必然延期，而且會把玩家的等待變成流失。

- **優先在獨立世界或副本里準備場地**，其次才是"在離出生點很遠的地方建"。前者的好處是：不影響主世界、不佔用主世界的區塊載入、活動結束後可以整體關掉。
- **如果只能在主世界建**，就選遠離出生點和主要建築區的位置，避免玩家傳送過來時順帶載入大量區塊。
- **提前載入好相關區塊**。第一次載入區塊是最貴的操作之一；在活動開始前把場地走一遍、讓相關區域處於已載入狀態，能顯著減少開場時的卡頓。具體用什麼方式預載入，取決於你的服務端與所用插件。
- **場地要在活動前完整演練一遍**。自己走一遍流程，比在腦子裡推演十遍都管用。

### 3.5 分工到人

一個人辦活動，等於沒有應急預案。至少要明確下面幾個角色，人手不足時可以由同一人兼任，但**必須有人負責**。

| 角色 | 負責什麼 | 需要幾個人 | 常見錯誤 |
| --- | --- | --- | --- |
| 主持人 | 宣佈流程、控制節奏、開場與收尾 | 1 人 | 一邊主持一邊處理技術問題，兩邊都顧不上 |
| 裁判 | 判定勝負、處理違規與爭議 | 1 至 2 人 | 裁判同時參賽，判罰失去公信力 |
| 建築 / 場地 | 活動前完成場地與道具準備 | 1 人以上 | 活動當天還在改場地 |
| 技術支援 | 處理掉線、卡頓、傳送失敗、權限問題 | 1 人 | 沒有人負責，出問題時全員沉默 |
| 記錄 | 截圖、錄影、記錄結果與貢獻 | 1 人 | 活動辦完了，一張能用的圖都沒有 |

:::tip 裁判不能參賽
這條看似苛刻，但它是**爭議最少**的做法。如果人手實在不足，就讓裁判迴避與自己相關的場次，並且把判定過程公開。公信力一旦丟了，後面每一場活動都會被質疑。
:::

### 3.6 應急方案

活動當天一定會出問題。區別只在於你有沒有準備。

| 可能出的問題 | 現場怎麼辦 | 提前要做什麼 |
| --- | --- | --- |
| 伺服器卡頓、TPS 下降 | 暫停或縮短流程，減少同時進行的實體與特效 | 提前壓測，準備好精簡版流程 |
| 關鍵玩家掉線 | 給出重連等待時間，超時按規則處理 | 規則裡寫明"掉線怎麼辦" |
| 人數遠少於預期 | 改成分組小規模進行，或改成自由參與 | 準備一套"人少也能玩"的備選方案 |
| 人數遠超預期 | 分批進行，或加開場地與場次 | 提前估算承載上限 |
| 有人作弊或破壞 | 立即隔離，按規則處理，事後留痕 | 規則寫清判定與處罰 |
| 活動時間嚴重超時 | 砍掉後面的環節，先保證有收尾 | 給每個環節設時間上限 |
| 獎勵發不出去 | 記錄名單，活動後補發 | 提前確認發放方式與權限 |

### 3.7 活動方案模板

把下面這份模板填完，一場活動基本就準備好了。**填不出來的空，就是還沒準備好的地方。**

```
活动名：______（一句话能说清是什么）
时间：______（日期 + 开始时间 + 预计时长 + 时区）
地点：______（世界 / 坐标 / 是否副本；玩家怎么去）
参与方式：______（怎么报名、能否现场参加、是否组队）
规则：______（允许与禁止、判定标准、平局怎么办）
奖励：______（名次与内容、发放方式与时间）
负责人：______（主持 / 裁判 / 建筑 / 技术支持 / 记录各是谁）
应急方案：______（卡顿、掉线、人数异常、作弊时怎么办）
```

## 4. 獎勵與經濟安全

### 4.1 獎勵為什麼會毀掉經濟

獎勵是活動最容易失控的部分，因為它直接往玩家的資產裡注入資源。經濟系統的脆弱點與常見事故見 [經濟與玩法插件](/tutorials/ops/gameplay-plugins)。在活動裡，需要特別警惕三種情況：

- **獎勵規模失控**。一場活動發出去的量，如果超過玩家正常遊玩幾天的產出，市場會當場被砸穿。
- **獎勵可以反覆刷**。只要活動能重複參加並且每次都發同樣的東西，它就從"活動"變成了"資源副本"。
- **獎勵綁定了稀缺資源**。把經濟體系裡的硬通貨當作活動獎品，等於自己給經濟埋了一顆定時炸彈。

### 4.2 外觀獎勵與物質獎勵

| 獎勵類型 | 例子 | 對經濟的影響 | 適合場景 |
| --- | --- | --- | --- |
| 外觀類 | 稱號、寵物、裝飾性物品、建築展示位 | 基本無影響，且不會被反覆變現 | 幾乎所有活動的首選 |
| 榮譽類 | 排行榜名次、公告表揚、專屬身份標識 | 無影響 | 競技類、比賽類活動 |
| 紀念類 | 活動專屬標記物、紀念性建築 | 影響很小，前提是不可交易或數量有限 | 節日活動、週年活動 |
| 便利類 | 一次性傳送、臨時增益、便利道具 | 取決於強度與是否可交易 | 謹慎使用，避免長期累積 |
| 物質類 | 貨幣、稀有材料、強力裝備 | 直接影響經濟，可能造成通脹 | 少量、一次性、且嚴格控制總量 |

:::warn 生存服不要發創造專屬物品
**在生存伺服器上發放只能通過創造模式獲得的物品，幾乎一定會出問題。** 這類物品無法在正常玩法中獲得，一旦出現在玩家手裡，就會變成不可複製的稀缺品，進而催生黑市、詐騙和"管理給熟人發東西"的指控。想讓獎勵看起來特別，用稱號、裝飾與展示位，而不是用破壞規則邊界的物品。
:::

### 4.3 發放要留痕

- **提前確定獎勵清單**，不要現場臨時加碼。
- **記錄每一個獲獎者與發放時間**，避免"我明明拿了第一卻沒收到"的爭議。
- **發放渠道盡量統一**，減少"有人私下領到了"的猜疑。
- **公示獎勵內容**。公開的獎勵清單本身就是公平的一部分。

## 5. 公平與防濫用

技術層面的作弊與破壞防護見 [反作弊與防破壞](/tutorials/java/anticheat)；這一節講的是活動規則層面的公平。

### 5.1 隊伍必須平衡

組隊活動的公平從分隊那一刻就決定了。讓最強的幾個人分在同一隊，比賽在第 30 秒就結束了，剩下的人只是在陪跑。

- **按能力而不是按關係分隊**。讓玩家自己選隊友，幾乎必然出現"高手抱團"。
- **公開分隊依據**。哪怕只是"按報名順序蛇形分配"，寫出來就比暗箱操作可信。
- **準備讓分隊機制**。例如弱隊獲得額外資源、限制強隊的裝備上限。
- **允許觀戰**。被淘汰的人如果只能乾等，下一場就不會報名了。

### 5.2 小號與帳號共享

這是活動裡最常見、也最難查的濫用方式。它同時破壞排行榜與獎勵發放。

- **規則裡明確禁止**多帳號參賽與帳號共享，並寫清判定方式與後果。
- **按玩家而不是按帳號統計**。同一個人的多個帳號，應當被視為同一個人。
- **留意異常訊號**：同 IP、同時間登入、帳號間物品轉移、只在活動期間出現的帳號。
- **處罰要有證據**。懷疑不等於證據，處罰必須留痕，否則會傷到正常玩家。

### 5.3 臨時加入的玩家

活動開始後才進服的人，處理不好會兩頭得罪。

- **規則提前寫清**：能不能中途加入、加入後是否計入成績、能不能拿獎勵。
- **給出統一口徑**。最常見的做法是允許觀戰與自由參與，但成績從下一場開始算。
- **不要現場臨時改規則**。為一個人改規則，就是對所有已參加的人不公平。

### 5.4 當場爭議怎麼處理

爭議一定會發生，關鍵是有沒有預設的處理路徑。

- **先看規則，再看現場**。有規則就按規則判，不要臨場發揮。
- **判定要公開說明理由**，哪怕只是一句話。
- **不要在情緒裡做決定**。有人罵你，和他是否違規是兩件事。
- **爭議升級就暫停**。寧可暫停五分鐘，也不要在全場注視下爭吵。
- **事後統一復盤**。規則裡沒寫清楚的地方，下一場補上；這比當場爭輸贏更有價值。

## 6. 技術準備

### 6.1 場地

- **獨立世界或副本優先**，其次才是主世界偏遠位置。理由見 3.4。
- **活動前完整走一遍流程**，包括傳送、復活、計時、獎勵發放的每一步。
- **活動結束後清理**。臨時場地、臨時權限、臨時道具都要能一鍵還原，否則它們會一直留在伺服器裡。
- **不要在活動前臨時改主世界**。改動的風險會在活動當天集中爆發。

### 6.2 小遊戲系統與獨立小遊戲服

- **小規模活動**通常用一類"小遊戲 / 競技場"插件就夠：它們負責場地隔離、隊伍、計分與復活。
- **大型或高頻活動**更適合放在獨立的 minigame 伺服器上，通過跨服端把玩家送過去，見 [跨服端](/tutorials/java/proxy)。好處是活動玩法不會汙染主世界，負載也分開。
- **跨服活動要多測一遍**。跨服傳送、權限繼承、聊天頻道、獎勵發放跨服之後都可能出問題，這些都要在活動前驗證。
- **具體的插件名稱、命令與設定項，請以各插件官方文件為準。** 本文不列出它們，因為它們隨版本變化，而且照抄配置往往比不寫更危險。

### 6.3 活動前後都做備份

活動是"世界狀態變化最集中"的時段：有人會破壞場地、有人會拿走獎勵、有人會掉線在奇怪的位置。備份的做法與驗證方式見 [備份與恢復](/tutorials/java/backup)。

- **活動前備份**：出事可以直接回到活動前的狀態。
- **活動後備份**：把活動成果（建築、記錄、獎勵發放）固定下來。
- **備份要驗證可恢復**。沒有驗證過的備份，不算備份。

### 6.4 卡頓風險

:::warn 大活動是伺服器最容易卡的時候
**一場人數多、實體多、特效多的活動，是伺服器全年最可能卡頓甚至崩潰的時刻。** 大量玩家集中在同一區域、同時生成大量實體與粒子、同時觸發大量插件邏輯，負載會遠超平時的峰值。

所以：**提前測**。用接近真實的人數與流程做一次彩排，觀察 TPS 與 MSPT 的變化；如果彩排就掉幀，正式活動只會更糟。分析手段見 [用 spark 分析伺服器效能](/tutorials/ops/spark)。同時準備一套"精簡版流程"，在卡頓時能立刻切過去。
:::

活動前的技術檢查可以按這張表逐項過一遍：

| 檢查項 | 為什麼重要 |
| --- | --- |
| 場地區塊已提前載入 | 避免開場時集中載入區塊造成卡頓 |
| 玩家傳送與復活點已測試 | 傳送失敗會讓活動直接中斷 |
| 權限與臨時身份已配置 | 主持人與裁判需要相應權限 |
| 獎勵發放流程已演練 | 發不出去比不發更難看 |
| 觀戰與旁聽通道已準備 | 讓被淘汰的人也有事做 |
| 活動前後備份已安排 | 出事後能回到已知狀態 |
| 備用流程已就緒 | 卡頓或人數異常時能立刻切換 |
| 記錄人員已就位 | 事後需要截圖、結果與回饋 |

## 7. 活動之後

活動結束的那一刻，工作才完成了一半。**沒有收尾的活動，等於沒辦。**

### 7.1 公佈結果與截圖

- 公佈名次、獲獎名單與判定依據。
- 發佈截圖或錄影。這是唯一能證明"活動真的發生過、真的有人來"的東西，也是下一場活動最好的宣傳素材。
- 把結果固定在一個長期可訪問的位置，而不是讓它淹沒在聊天記錄裡。

### 7.2 感謝幫忙的人

- 公開感謝主持、裁判、建築與技術支援。**願意幫忙的人是你最稀缺的資源**，他們需要被看見。
- 記錄下誰做了什麼。下次辦活動時，這份名單就是你的班底。
- 對參與者也要有回應，哪怕只是一句總結。

### 7.3 收集回饋

- **問具體的問題**，不要只問"好玩嗎"。問"哪個環節最無聊""哪裡卡住了""下次想玩什麼"。
- **給一個固定的回饋入口**，而不是讓意見散落在各個群。
- **區分"意見"和"情緒"**。有人罵人，不代表他的意見沒有價值，但也不代表你必須照做。

### 7.4 復盤記錄

每次活動後寫一份簡短記錄，內容包括：

- 實際參與人數與預期差多少；
- 哪個環節超時、哪個環節沒人玩；
- 出了哪些技術問題，怎麼解決的；
- 爭議是怎麼判的，規則哪裡沒寫清；
- 下次要改的三件事。

這份記錄不需要長，但**必須寫下來**。三個月後你不會記得當時為什麼卡了五分鐘。

### 7.5 建立固定節奏

零散的活動靠熱情，持續的活動靠節奏。讓玩家知道"什麼時候一定有事發生"，比每次臨時通知有效得多。

| 節奏 | 規模 | 目的 | 注意 |
| --- | --- | --- | --- |
| 每週一次小活動 | 30 至 60 分鐘，低準備成本 | 保持日常活躍，給新人一個入口 | 類型要輪換，不要每週都是跑酷 |
| 每月一次大活動 | 2 小時以上，需要提前準備 | 製造話題，拉回離開的玩家 | 提前 1 至 2 周宣傳 |
| 節日 / 週年活動 | 跟隨現實節日 | 借勢吸引流量與迴歸 | 排期避開其他大活動 |
| 長期社群目標 | 持續數週 | 給全服一個共同目標 | 進度必須可見 |

:::tip 節奏比創意更重要
玩家記不住你辦了哪一場活動，但會記住"這個服每週六晚上都有活動"。**可預期本身就是吸引力。** 寧可每週辦一場簡單的小活動，也不要三個月辦一場盛大的、然後消失。
:::

## 8. 一頁活動清單

### 8.1 活動前

- [ ] 活動類型已確定，並且與可投入的準備時間匹配
- [ ] 時間已按主要玩家時區確定，並寫明時區
- [ ] 已至少提前 2 至 3 天（大型活動 1 至 2 周）開始宣傳
- [ ] 宣傳至少發了三輪，內容前後一致
- [ ] 規則已成文、已公開，包含判定標準與平局處理
- [ ] 場地已在獨立世界或副本中建好，並提前載入過
- [ ] 完整流程已彩排一遍，包括傳送、計時與獎勵發放
- [ ] 主持人、裁判、建築、技術支援、記錄人員已確定到人
- [ ] 裁判不參賽（或已迴避相關場次）
- [ ] 獎勵清單已確定，規模已評估過對經濟的影響
- [ ] 生存服未發放創造專屬物品
- [ ] 分隊方式已確定並公開，機制上儘量平衡
- [ ] 多帳號與帳號共享的判定方式已寫進規則
- [ ] 中途加入、掉線、超時的處理方式已寫進規則
- [ ] 應急方案已準備好：卡頓、掉線、人數異常、作弊
- [ ] 活動前備份已完成，並且驗證過可恢復
- [ ] 活動後備份已安排
- [ ] 關鍵玩家與觀戰者的通道已準備

### 8.2 活動中

- [ ] 開場先講清流程、規則與時間上限
- [ ] 每個環節控制時長，超時就進入下一環節
- [ ] 爭議按規則判定，並公開說明理由
- [ ] 卡頓時立即切換到精簡流程
- [ ] 全程記錄：截圖、錄影、名次、獲獎名單

### 8.3 活動後

- [ ] 結果與獲獎名單已公佈，並附判定依據
- [ ] 截圖或錄影已發佈
- [ ] 幫忙的人已公開感謝
- [ ] 獎勵已按清單發放，並留有記錄
- [ ] 回饋已收集，並區分意見與情緒
- [ ] 復盤記錄已寫下，包括下次要改的三件事
- [ ] 臨時場地、臨時權限、臨時道具已清理
- [ ] 下一場活動的時間已公佈
