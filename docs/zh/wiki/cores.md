开服第一步是选"跑什么"。这一步之所以容易选错，是因为**核心、插件、模组、加载器**这四个词经常被混着用。这一页把它们摆在一起对照：Java 版的核心家族与模组加载器、基岩版的官方与第三方核心、BDS 的社区加载器，最后给一条"我该选哪个"的判断路径。

> 各项目支持哪些游戏版本、支持到什么程度，**随时间变化**：核心会停止维护，加载器会追赶新版本，插件会失去作者。本文只给"家族与定位"的对照，**具体版本区间与支持状态以各项目官方仓库与官方文档为准**。

## 1. 先把四个词分开

| 词 | 是什么 | 典型形态 | 玩家要不要装东西 |
| --- | --- | --- | --- |
| 核心（服务端） | 跑世界、跑逻辑的那个程序 | `paper-x.jar`、`bedrock_server.exe` | 不用 |
| 插件 | 调用核心提供的 API 扩展功能 | 放进 `plugins/` 的 jar 或 phar | 不用，原版客户端即可 |
| 模组 | 直接改游戏本体的代码 | 放进 `mods/` 的 jar | **多数内容模组要求客户端装同一套** |
| 加载器 | 让模组能被加载并运行的框架 | Fabric、NeoForge、Forge、Quilt | 客户端与服务端都要装 |

一句话区分：**插件在服务端外面加功能，模组在游戏里面改内容。** 这个区别决定了玩家要不要配合装东西，也决定了你后面所有的排错方式。

## 2. Java 版服务端核心

Java 版的核心是一条清晰的分支链：Bukkit → Spigot → Paper → Purpur / Folia / Leaves / Leaf。**插件兼容性大体沿上游继承**：兼容 Paper 的插件通常也兼容 Purpur，但反过来不一定。

| 核心 | 特点 | 插件兼容 | 适合谁 |
| --- | --- | --- | --- |
| Vanilla（原版） | 官方服务端，只支持数据包；不装任何第三方东西 | 不支持插件 | 想验证原版行为、跑纯原版玩法 |
| Spigot | Bukkit 的延续，也是 Paper 的上游；更新节奏较慢 | 生态大，很多老插件以它为准 | 需要兼容老插件、且不想用 Paper 的场景 |
| Paper | Spigot 分支；异步区块、实体与网络优化最成熟 | **生态最大**，绝大多数插件首选 | **第一次开服的首选**：稳、资料多、性能够 |
| Purpur | Paper 分支，提供大量玩法开关 | 兼容 Paper 插件 | 想精细调整原版机制、又不想写代码 |
| Folia | Paper 分支，区域化多线程 | **兼容性差**：多数插件未适配，需要专门支持 | 核心多、主频低的机器；**不适合生电** |
| Leaves | Paper 分支，目标是修复被性能优化改坏的原版特性 | 兼容 Paper 插件（以各自说明为准） | **生电（技术向）+ 想用插件** |
| Leaf | Paper 分支，追求性能、原版机制与稳定性之间的平衡 | 兼容 Paper 插件（以各自说明为准） | 想兼顾性能与原版手感，但不需要 Leaves 的全部特性 |

三点提醒：

1. **Leaves 与 Leaf 是两个不同项目**，名字只差一个字母。搜资料、下载核心时看准拼写，别装错。
2. **Folia 不是"更快的 Paper"**。它把世界切成区域并行调度，跨区域交互的行为与 Paper 不同；没适配的插件会直接报错或行为异常。选它之前先确认你要用的插件是否声明支持 Folia。
3. **原版只支持数据包（Data Pack）**。想用插件就必须换核心，想用模组就必须换加载器。

### 2.1 分支继承关系

把这条链记住，插件兼容性问题就有一半能自己判断：

```text
Bukkit（最早的服务端 API）
  +- Spigot（Bukkit 的延续）
       +- Paper（主流分支，插件生态最大）
            +- Purpur（玩法开关最多）
            +- Folia（区域化多线程，插件兼容差）
            +- Leaves（还原原版特性，生电向）
            +- Leaf（性能 / 原版机制 / 稳定性的平衡）
```

规则是**向下兼容、向上不保证**：为 Paper 写的插件通常能在 Purpur 上跑；为 Folia 写的插件不一定会为 Paper 适配；只支持 Spigot 的老插件在 Paper 上一般也能跑，但可能报"使用了过时 API"。

完整的逐项对照与"按硬件怎么选"见 [服务端核心对比](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7)；按玩法与硬件的完整选型讲解见 [服务端选择](/tutorials/java/core)。

## 3. Java 版模组加载器

模组服与插件服是两套世界。加载器决定你能装哪些模组，而**同一个模组通常只支持一个加载器**。

| 加载器 | 定位 | 生态 | 版本节奏 |
| --- | --- | --- | --- |
| Fabric | 轻量、启动快；加载器本体与 API 分离，很多功能要靠 Fabric API 这个模组补 | 活跃；优化类与轻量内容类模组多 | 跟进新版本最快 |
| NeoForge | Forge 血脉在现代版本上的延续；功能 API 更完整 | 现代版本的大型内容与科技整合包主力 | 跟随主版本推进 |
| Forge | 老牌加载器；历史整合包与老版本大量使用 | 老整合包最多；新版本生态有相当一部分转向 NeoForge | 仍在为多个版本发布构建，但新版本跟进不如前两者 |
| Quilt | 由 Fabric 分叉而来，目标是更开放的治理与新的 API | 明显小于 Fabric；能加载相当一部分 Fabric 模组，但**并非全部** | 活跃度低于 Fabric，选之前先确认你要的模组在不在 |

判断顺序应该是**先定玩法，再定加载器**：

```text
列出你必须要的模组
  → 查每个模组支持的加载器与游戏版本
  → 取交集最大的那个组合
  → 再装服务端
```

反过来（先装加载器再找模组）几乎一定会返工。安装流程、客户端对齐与排查见 [模组服完整上手（Fabric / NeoForge）](/tutorials/java/modded)。

### 3.1 别忘了运行时版本

核心与加载器都要求匹配的 Java 运行时。装错 Java 是最常见的"启动器打不开、服务端起不来"原因：

| Minecraft 版本 | 通常需要的 Java |
| --- | --- |
| 1.16.5 及更早 | 8 |
| 1.17.2 | 16 |
| 1.18.2 – 1.20.4 | 17 |
| 1.20.5 及更新 | 21 |

这张表是**写作时的常见对应关系**，新版本随时可能提高要求；以核心与加载器的官方文档为准。

### 3.2 客户端也要装加载器

模组服的一个常见误解是"服务端装好就行"。实际上：

| 模组类型 | 装在哪 | 装错的后果 |
| --- | --- | --- |
| 仅客户端（渲染、小地图、界面增强） | 只装客户端 | 丢到服务端通常直接报错或被加载器拒绝 |
| 仅服务端（逻辑与性能类） | 只装服务端 | 客户端装了没意义；服务端缺了功能不存在 |
| 双端必需（新方块、新物品、新维度） | 客户端 + 服务端都要 | 缺任何一边：连接被拒，或注册表不匹配报错 |

所以发布整合包时，**要同时给出客户端与服务端两份清单**，并在说明里写清哪些模组是可选的。

## 4. 代理端：不是核心，但常在选型里出现

代理端自己不跑世界，只把玩家转发到后端子服。它属于"多服结构"的组件，**单服不需要它**。

| 代理端 | 定位 | 备注 |
| --- | --- | --- |
| Velocity | 现代代理端，性能好、活跃 | 多子服互联的主流选择 |
| BungeeCord | 老牌代理端 | 生态老、资料多，新项目通常优先 Velocity |

加了代理端之后，玩家的连接路径变成"客户端 → 代理端 → 后端子服"，插件要区分"装在代理端"还是"装在后端"，跨版本插件装在哪一侧也有不同代价。详见 [跨版本兼容](/tutorials/java/via) 与代理相关教程。

## 5. 基岩版：官方核心与第三方核心

基岩版的核心生态比 Java 版小，主流是四个。

| 核心 | 语言 | 插件生态 | 备注 |
| --- | --- | --- | --- |
| BDS（官方） | C++ | **本身不支持插件**，要靠社区加载器 | 官方服务端，兼容性最好；生物运算压在单线程，流畅度主要看单核性能 |
| Nukkit | Java | 原生插件系统，生态较小 | 轻量、上手简单；**原版项目已不活跃**，实际应优先选活跃分支 |
| PowerNukkitX | Java | 兼容 Nukkit 生态的大量插件，生态中等 | Nukkit 的现代主力分支：支持较新协议、多核优化、384 格世界高度、内置 Terra 地形生成器 |
| PocketMine-MP | PHP | **最大**（PHP 插件最多） | 会用 PHP 就能写插件；高负载下有性能瓶颈，更新相对滞后 |

选型经验：

- **要官方兼容与稳定**：BDS，需要插件时再配社区加载器；
- **要高性能与高度自定义**：PowerNukkitX；
- **要最多的现成插件、且熟悉 PHP**：PocketMine-MP；
- **想从简单开始**：先用 BDS 跑通，再考虑第三方核心。

基岩版核心的逐项对比与上手路径见 [基岩版核心选择](/tutorials/bedrock/cores) 与 [第三方核心（Nukkit / PNX / PMMP）](/tutorials/bedrock/third-party)。

### 5.1 第三方核心的运行环境

选核心之前先确认机器上装了什么运行时，否则第一步就会卡住：

| 核心家族 | 需要什么 | 注意 |
| --- | --- | --- |
| BDS | 不需要 Java / PHP，解压即用 | 平台压缩包与可执行文件名以官方下载页为准 |
| Nukkit 系（含 PNX） | **Java**，版本要求通常较新 | 64 位系统配 64 位 Java，否则会因内存上限中途崩溃 |
| PocketMine-MP | **PHP**（建议用官方打包好的运行时） | 发行版仓库里的 PHP 往往偏旧、扩展不全，先确认 `php -v` |

装错家族（例如给 PMMP 装 Java、给 Nukkit 装 PHP）不会"凑合能跑"，只会直接启动失败。

## 6. BDS 的插件加载器

官方 BDS 本身没有插件系统。想在 BDS 上用插件，必须装社区加载器，而**加载器与游戏版本强绑定**：服务端升级前先确认加载器已经跟进。

| 加载器 | 写插件用什么 | 生态 | 备注 |
| --- | --- | --- | --- |
| LeviLamina | C++（前身是 LiteLoaderBDS） | 目前最成熟、生态最好 | 只支持特定版本区间，升级 BDS 前先核对 |
| BDSX | Node.js / TypeScript | 维护时间长，玩法偏底层（Hook 与网络包） | 支持范围广，适合愿意写代码的人 |
| EndStone | C++ / Python，API 风格接近 Bukkit | 生态很小，但方向清晰 | 适合想要类 Bukkit 开发体验的场景 |
| BDSpyrunner | Python | 较小 | 具体形态与支持版本以项目官方仓库为准 |

社区里还有一些**替代服务端**（不是 BDS 加载器）：例如 Go 语言编写的 gomint 与 Dragonfly、社区服务端 Allay，以及基岩版的代理端 WaterDogPE。它们的共同点是**生态与文档都薄**，遇到问题较难求助；除非有明确理由，不建议新手起步就选。

:::warn 加载器与游戏版本强绑定
基岩版的服务端构建与协议高度绑定，社区加载器通常只支持**一段很窄的版本区间**。"先把 BDS 升到最新，再去找加载器"是最常见的翻车顺序；正确顺序是**先确认加载器支持到哪个构建，再决定服务端升到哪**。
:::

## 7. 我该选哪个

```text
玩家要用原版客户端进服，并且需要管理/玩法插件
  → Paper（首选）
  → 想调原版机制：Purpur
  → 生电 + 插件：Leaves 或 Leaf（看清项目名）
  → 核心多、主频低：再考虑 Folia（先确认插件适配）

玩家要装模组、要新内容
  → 先定模组清单 → Fabric（轻量/优化类）或 NeoForge（现代内容整合包）
  → 老整合包：Forge
  → 只有 Quilt 独有模组：才考虑 Quilt

玩家是基岩版
  → 原版生存、要官方兼容：BDS（需要插件再配加载器）
  → 高性能 + 自定义：PowerNukkitX
  → 现成插件最多、会 PHP：PocketMine-MP

要多台服务器互联
  → 加一层代理端（Velocity 优先）
```

## 8. 插件与模组是两个世界

:::warn 插件和模组不是一回事，混着理解会一直踩坑
**插件（Plugin）**调用核心提供的 API，装在服务端；玩家用**原版客户端**就能进。典型内容是管理、经济、领地、小游戏。

**模组（Mod）**直接修改游戏本体，装在**加载器**上；绝大多数内容模组要求**客户端和服务端装同一套**，玩家不装就进不来。典型内容是新方块、新物品、新生物、新维度。

由此推出几条硬规则：

- **插件服不能装模组**：Paper 系核心没有模组加载能力，`mods/` 目录不存在。
- **模组服默认不能装插件**：Fabric / NeoForge 服务端不认识 Bukkit 插件；`plugins/` 目录不存在，`spigot.yml`、`paper-world-defaults.yml` 那一套配置也不存在。
- **两边的调优经验不能互相照抄**：插件服的 JVM 参数、优化插件、热重载习惯，搬到模组服基本无效，反之亦然。
- **同一个"功能"在两边的实现完全不同**：例如领地保护，插件服靠插件，模组服靠模组，配置与命令都不通用。
:::

## 9. 混合端的代价

**混合端（Hybrid）**指试图同时提供插件 API 与模组加载能力的服务端项目。它确实能让"插件 + 模组"跑在同一个服务端上，但代价要说清楚：

| 代价 | 说明 |
| --- | --- |
| 上游跟进慢 | 需要同时适配 Minecraft 版本、模组加载器与插件 API，新版本支持通常滞后 |
| 兼容问题两边都有 | 插件与模组都可能出问题，而且难以判断是哪一侧引起的 |
| 求助困难 | 用户规模小，遇到问题时几乎没有现成答案，作者精力也有限 |
| 升级与回滚风险高 | 世界格式、模组数据与插件数据混在一起，回滚比纯插件服或纯模组服复杂得多 |

:::warn 不要用混合端起步
混合端解决的是"我既要又要"的需求，但它把两套系统的风险叠加在一起。**新手起步不要碰**；确有需要时，先把纯插件服或纯模组服跑稳，再评估混合端是否值得，并以其项目官方文档为准。历史上有过多个混合端项目，支持状态与维护情况各不相同，选之前务必看它的最新发布与支持版本。
:::

## 10. 怎么核对版本与生态

不要凭记忆选核心。每次决定前做这四步核对：

| 步骤 | 看什么 | 去哪看 |
| --- | --- | --- |
| 1 | 目标游戏版本下，核心有没有发布构建 | 核心的官方下载页或官方仓库 |
| 2 | 你要用的插件/模组，是否声明支持该核心与该版本 | 插件/模组的发布页与支持列表 |
| 3 | 加载器（若有）支持到哪个版本区间 | 加载器官方文档 |
| 4 | 需要的 Java / PHP 运行时版本 | 核心与加载器官方文档 |

时间线只能告诉你"版本什么时候发布"，它不能告诉你"你的核心跟上了没有"。这两件事要分开查，参考 [版本时间线怎么读](/wiki/versions-guide)。

## 11. 常见选型错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 把模组丢进插件服 | 服务端根本不加载它，甚至报错 | 先分清插件与模组，选对应的核心或加载器 |
| 先装加载器再找模组 | 想要的内容模组不支持这个加载器，只能重来 | 先列模组清单，再定加载器 |
| 把 Leaves 与 Leaf 装混 | 行为与原版特性还原程度不符预期 | 看准项目名与官方说明 |
| 以为 Folia 是"更快的 Paper" | 插件大面积不兼容 | 先确认每个插件是否声明支持 Folia |
| 只看"性能"不看生态 | 核心很快，但没有你要的插件 | 生态与插件支持优先于性能数字 |
| 用混合端一步到位 | 兼容问题叠加，升级困难 | 先跑纯插件服或纯模组服 |
| 给 BDS 直接升级到最新 | 社区加载器没跟上，插件全部失效 | 先确认加载器支持区间，再升级服务端 |

## 12. 性能之外：三类开销

选核心时最容易被"性能"两个字带偏。真正决定体验的是三类开销，它们指向不同的硬件：

| 开销 | 由什么决定 | 症状 | 对应选择 |
| --- | --- | --- | --- |
| 单核性能 | Minecraft 主逻辑基本跑在单线程上：实体、区块、红石与插件逻辑都压在**一个核心** | 玩家一多就卡、TPS 掉、区块加载慢 | 单核强的机器选 Paper 系；核心多但主频低才考虑 Folia |
| 内存 | 视距、实体数量、插件缓存与模组数量 | 频繁 GC 卡顿、OOM 崩溃 | 先降视距与实体上限，再加内存；内存不能替代单核 |
| 磁盘与网络 | 区块读写、自动保存、玩家进出时的区块发送 | 保存时全服卡顿、玩家进服慢 | SSD 优先；网络优化属于另一条线 |

因此"这台机器几核"远不如"**单核多快**"重要。插件数量、模组数量与视距设置，对体验的影响通常大于换核心带来的收益。
