本站的**版本时间线**（[/wiki/versions](/wiki/versions)）按时间倒序列出 Java 版与基岩版的正式版本。它是"我该开哪个版本、什么时候升级、玩家为什么进不来"这类问题的第一个查询入口。

但时间线本身只给出**版本号、日期与一行说明**。这一页讲清楚：这些字段分别意味着什么、哪些直觉是错的、以及怎么把它变成一次具体的升级决定。

> 版本号命名规则、协议版本与发布节奏由官方决定，随时可能调整。本文只解释**怎么读本站的时间线**；具体某个版本支持什么、要求什么，以官方发布说明为准。
:::note 这一页解决四个问题
- 时间线上的一行，每个字段是什么意思；
- Java 版与基岩版的版本号各自怎么拆；
- LTS / CROSS-PLAY 标签代表什么、不代表什么；
- 为什么"发布日期"不能回答"我的客户端能不能进"。
:::

## 1. 时间线在哪、每一行是什么

| 页面 | 内容 |
| --- | --- |
| [/wiki/versions](/wiki/versions) | 默认打开 Java 版时间线 |
| [/wiki/versions/java](/wiki/versions/java) | Java 版时间线 |
| [/wiki/versions/bedrock](/wiki/versions/bedrock) | 基岩版时间线 |

两个版本的时间线是**分开的**，页面上用两个标签页切换。每一行的结构固定：

| 字段 | 说明 |
| --- | --- |
| 版本号 | 该版本在游戏里显示的正式版本号 |
| 标签 | 只有条目带标记时才出现（例如 LTS、CROSS-PLAY），不是每行都有 |
| 日期 | 该版本的发布日期 |
| 一行说明 | 这个版本是什么（大版本更新会写明更新名，小版本一般是修复与稳定性改进） |

几条读法上的事实：

- **新版在上**：时间线按日期倒序排列，第一行是最新的版本，往下越读越旧。
- **只收正式版**：快照（Snapshot）、预览版（Preview）与测试版不在时间线里，所以"时间线上没有"不等于"官方没发布过"。
- **两个版本的数量差得很多**：Java 版从 1.0 一路记到最新的 26.x；基岩版的修订版发布频率高得多，条目数接近 Java 版的三倍，所以基岩版时间线往下翻会明显更长。
- **基岩版条目多一个字段**：基岩版的服务端（BDS）有自己的构建号，时间线数据里额外记录了它，用于对照"客户端版本"与"服务端构建"。

## 2. Java 版的版本号怎么读

Java 版长期使用 `1.x.y` 的形式：

| 位置 | 含义 | 例子 |
| --- | --- | --- |
| `1.x` | 主版本，决定内容与玩法变化 | 1.21 |
| `.y` | 该主版本下的修订版 | 1.21.9、1.21.10、1.21.11 |

**这里有一个最常见的误读**：`1.21.10` 比 `1.21.9` **新**，因为 `.10` 是数字十，不是"一点一零"。**按数字比较，不要按字符串比较**：字符串排序会把 `1.21.10` 排在 `1.21.9` 前面，看起来像是更旧，其实相反。

### 2.1 新命名：26.x

时间线里可以看到，Java 版在 2026 年之后出现了 `26.x` 形式的版本号（本站时间线中 26.1 记为 2026-03-24，26.2 记为 2026-06-16，26.3 记为 2026-09-15）。

这属于**官方调整版本命名方式**，不是"1.21 的第 26 个修订版"，也不能按 `1.x.y` 的直觉去推断它和旧版本号的大小关系。遇到不认识的版本号形式，正确做法是**看日期，不要猜数字**：

- 想知道谁更新：比日期。
- 想知道能不能装某个插件：看插件的支持列表，不看版本号形式。
- 想知道协议是否兼容：看协议版本，不看版本号。

### 2.2 修订版与主版本的区别

| 类型 | 变化幅度 | 升级风险 |
| --- | --- | --- |
| 修订版（如 1.21.9 → 1.21.11） | 通常只修 bug 与稳定性 | 低；但插件仍可能受影响，仍要备份 |
| 主版本（如 1.21 → 26.1） | 内容、机制、数据格式都可能变 | 高；世界格式基本单行道，降级代价极大 |

## 3. 基岩版的版本号怎么读

基岩版的 `1.x.y` 与 Java 版**形似而神不同**：第三段的含义不是"第几个小修订"，而是按基岩版自己的节奏递增。

| 形式 | 含义 | 例子 |
| --- | --- | --- |
| `1.x.y` | 基岩版正式版 | 1.20.10、1.21.100 |
| `1.x.y.z`（四段） | BDS 构建号，用于服务端 | BDS 1.20.62.03 |

三个要点：

1. **`1.20.1` 与 `1.20.10` 不是同一件事**，也不是"改了个位数"。基岩版的第三段常常一次跳十（1.20.10、1.20.20 这样的节奏在时间线里很常见），所以看到 `1.21.100` 不要以为是打错了。
2. **BDS 构建号是四段**：例如 `BDS 1.20.62.03`。它是服务端自己的构建编号，和客户端显示的版本号**不是同一个字符串**，但在同一次发布里互相对应。
3. **查不到构建号时会留占位**：本站数据里，查不到确切构建号的基岩版条目会写成 `BDS <版本>.w` 这类形式（`w` 是构建号占位），说明"这次发布的构建号没有确认到"，不代表这个版本没有服务端。

### 3.1 基岩版的 26.x

基岩版同样进入了 `26.x` 命名（本站时间线中 26.0 记为 2026-02-10）。与 Java 版一样，**不要跨命名体系比较数字**，看日期。

### 3.2 客户端与服务端同日发布

基岩版的时间线说明里常见"与客户端同日发布"这类描述，这反映了基岩版的实际节奏：**客户端更新与服务端构建通常同步推进**。由此带来两个后果：

- 服务端跟进得慢，就等于玩家（尤其是自动更新的玩家）进不来；
- iOS 玩家**只能安装商店里的最新版**，无法回退到指定版本，所以"把服务端固定在旧版本"这条路的代价比 Java 版大得多。

## 4. LTS 与 CROSS-PLAY 标签代表什么

时间线上的标签是**本站自己加的提示**，不是官方分类，也没有任何官方承诺。它们只在条目带标记时显示。

| 标签 | 本站用它表示 | 它**不**表示 |
| --- | --- | --- |
| LTS | 本站认为值得长期停留、适合作为稳定基线的版本 | 官方会长期为它提供更新；也不表示它"最安全" |
| CROSS-PLAY | 与跨平台联机相关的版本提示 | 装了它就能 Java 与基岩版互通；也不保证所有平台都能进 |

几点务必分清：

- **LTS 不是 Minecraft 的官方术语**。官方没有"长期支持版本"这一说，任何版本都可能在下一次更新后停止获得修复。
- **CROSS-PLAY 也不等于跨端互通**。基岩版各平台之间互通是它本身的能力；**Java 版与基岩版之间互通必须依赖 Geyser 一类工具**，与服务端是哪个版本无关（见 [Java版 与 基岩版 的区别](/wiki/editions)）。
- **标签会变**。本站可以在任何时候给条目加上或去掉标记，所以"某版本带 LTS"这件事本身是本站的判断，不是硬事实。以页面当前显示为准。

## 5. 发布日期不等于"能不能进服"

这是时间线最容易被误用的一点。日期只回答"这个版本什么时候发布"，**完全不回答**"你的客户端能不能进这个服务端"。

真正决定能不能进的是**协议版本**：客户端与服务端在握手阶段用协议号对话，对不上就进不去，和版本号、发布日期、更新内容都无关。

| 现象 | 真正的原因 | 去哪里看 |
| --- | --- | --- |
| 玩家提示"版本不兼容"（Java） | 客户端协议与服务端不匹配 | [跨版本兼容](/tutorials/java/via) |
| 玩家提示需要更新到最新版（基岩版） | 客户端协议与服务端构建不匹配 | [协议版本与版本选择](/tutorials/bedrock/protocol) |
| 时间线显示昨天刚发新版，玩家却进不来 | 你还没更新服务端，或玩家已自动更新到更新版 | 先确认双方版本，再决定跟不跟 |
| 时间线显示版本很旧，但玩家能进 | 该客户端版本仍在服务端接受的兼容范围内 | 不要靠"能进"反推协议兼容 |

### 5.1 一个具体例子

服务端跑 1.21.11，玩家报的客户端是 1.21.9：

| 问题 | 答案 |
| --- | --- |
| 时间线怎么看 | 两行都在，1.21.11 比 1.21.9 新（按数字比：10、11 大于 9） |
| 玩家为什么进不来 | 不是"版本太旧"四个字能解释的：要看 1.21.11 的服务端是否接受 1.21.9 的协议 |
| 该怎么办 | 先看服务端日志里的握手错误；装 Via 系列可以让更旧的客户端进来，见 [跨版本兼容](/tutorials/java/via) |
| 时间线能回答吗 | 不能。它只告诉你这两个版本谁先发布 |

**时间线回答"谁新谁旧"，协议回答"能不能连"**，这两件事要分开查。

## 6. 为什么协议版本比营销版本号重要

"营销版本号"指的是页面上显示的 `1.21.x`、`26.x` 这类版本号；**协议版本**是双方通信时实际使用的编号。两者不是一回事：

- 同一个营销版本号下，协议可能改过多次（基岩版尤其明显）；
- 官方有时会在修订版之间改协议，也会在修订版之间**不改**协议；
- 插件、加载器与跨版本工具的兼容判断，多数情况下看的是协议与内部版本，而不是页面上那个数字。

**基岩版卡得更死**：客户端协议必须与服务端构建匹配，差一个协议号就是连不上。**Java 版有翻译层**：Via 系列插件能在服务端一侧翻译协议，让更旧或更新的客户端进来，但跨得越远，能对上的东西越少，体验下降越明显。

结论：**判断"能不能进"，永远先看协议，再看版本号；版本号只是给人看的名字。** 两条路线的完整说明见 [协议版本与版本选择](/tutorials/bedrock/protocol) 与 [跨版本兼容](/tutorials/java/via)。

### 6.1 两个版本对协议的态度不一样

| 维度 | Java 版 | 基岩版 |
| --- | --- | --- |
| 协议不匹配时 | 握手失败，提示版本不兼容 | 握手失败，提示需要更新到最新版 |
| 有没有翻译层 | 有：Via 系列在服务端一侧翻译协议 | 基本没有：社区跨版本插件生态很小 |
| 客户端自动更新 | 只在官方启动器里，玩家可以固定版本 | 应用商店默认自动更新，玩家常常"被动升级" |
| 固定旧版本的代价 | 相对可控 | 很高：iOS 玩家只能装最新版 |
| 因此的默认策略 | 可以按插件生态决定何时升级 | **默认跟进最新版** |

## 7. 怎么用时间线决定什么时候升级

时间线给你的是**日期与顺序**，升级决策要靠它加上"你的服现在跑什么"。推荐顺序：

1. **先查支持范围，再查新版本**。你的核心、插件、模组加载器各自支持到哪个版本？把它们的交集写下来，这是你能升到的上限。加载器与核心的版本约束见 [服务端核心对比](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7)。
2. **看目标版本后面有几个修订版**。刚发布的主版本往往还在收尾；等一两个修订版出来再动，风险明显更低。
3. **看你的插件生态跟到哪了**。核心支持新版不等于插件支持新版。
4. **备份，并验证备份**。世界格式升级基本是单行道，只换核心不换世界的回滚是不成立的。
5. **在独立实例里试**。用一份存档副本跑一次，别拿生产实例做实验。
6. **挑维护窗口并提前公告**。

| 情况 | 建议 |
| --- | --- |
| 只是修 bug 的修订版，且核心与插件都已支持 | 可以跟，仍然先备份 |
| 刚发布的主版本 | 等第一个或第二个修订版 |
| 你的插件里有只支持旧版的 | 停在旧版，或先找替代插件 |
| 基岩版 | 默认跟进最新版；固定旧版等于放弃 iOS 玩家 |
| 不确定 | 不动。留在当前版本的成本，通常低于一次失败的升级 |

完整的升级流程、降级风险与回滚方法见 [服务端、插件与 MCDR 的更新维护](/tutorials/ops/updates)。

## 8. 一次"进不去"的排查顺序

| 顺序 | 检查项 | 怎么查 |
| --- | --- | --- |
| 1 | 客户端版本 | 让玩家报出准确的版本号（见下一节） |
| 2 | 服务端版本与协议 | 服务端日志、核心版本输出 |
| 3 | 端口与协议 | Java 版是 TCP 25565；基岩版是 UDP 19132（IPv6 为 19133） |
| 4 | 白名单与封禁 | `whitelist list`、`banlist players`（基岩版看 `allowlist.json`） |
| 5 | 正版验证与登录方式 | `online-mode` 一类的配置会直接改变"能不能进" |
| 6 | 跨版本插件 | 装了 Via 系列却仍报版本不支持时，先更新插件本身 |

前两步就要用版本号，所以**先问版本，再谈其他**，能省掉一大半来回。

## 9. 先确认客户端版本
:::tip 玩家说"进不去"时，第一件事是要版本号
让玩家报出**准确的客户端版本号**（截图最省事），再去对照时间线与协议。没有这一步，后面的排查全是猜。

- **Java 版**：主菜单左下角显示版本号；启动器里也能看到该安装对应的版本；进入游戏后按 `F3`，调试界面顶部会显示版本。
- **基岩版**：在设置的「关于」一类页面里能看到版本号（各平台界面位置不同，移动端与主机端尤其不一样）。

拿到版本号之后，把玩家版本与服务端版本放到时间线上对照日期与顺序，就能判断这是"服务端太旧"还是"客户端太新"。
:::

## 10. 时间线上容易误读的几点

| 误读 | 实际情况 |
| --- | --- |
| 用字符串比较版本号 | `1.21.10` 比 `1.21.9` 新；跨命名体系（1.x 与 26.x）更不能比数字，只能比日期 |
| 以为时间线收录了快照 | 只收正式版；快照与预览版不在其中 |
| 以为"发布日期近"就是"必须升" | 发布节奏与你的插件生态是两回事 |
| 以为带 LTS 就永远安全 | LTS 是本站标记，不是官方承诺 |
| 以为基岩版 `1.20.1` 与 `1.20.10` 差一个小版本 | 基岩版第三段按自己的节奏跳，两者是不同发布 |
| 以为同一天只有一个版本 | 时间线里同一天出现多个版本是正常现象 |
| 以为"最新的就是最合适的" | 最新版对新插件友好，对老插件不友好；要看你实际装了什么 |

### 10.1 时间线不回答的问题

| 你的问题 | 时间线能答吗 | 该去哪 |
| --- | --- | --- |
| 这个版本什么时候发布 | 能 | 时间线本身 |
| 我的客户端能不能进 | 不能 | 协议版本：见 [协议版本与版本选择](/tutorials/bedrock/protocol) |
| 我的插件支不支持 | 不能 | 插件发布页的支持列表 |
| 我的核心跟上了没有 | 不能 | 核心的官方下载页与官方仓库 |
| 这个版本更新了什么 | 部分 | 时间线的一行说明；细节看官方更新日志 |
| 去哪下载服务端 | 不能 | 本站下载区与官方下载页 |

## 11. 一页速查

```text
我要开新服
  → 选最新正式版，然后确认核心与插件都支持它

玩家说进不来
  → 先要客户端版本号 → 比协议 → 再查端口、白名单、正版验证

我想升级
  → 查核心/插件/加载器的支持交集 → 等修订版 → 备份并验证
  → 独立实例试跑 → 挑维护窗口 → 公告

我看到一个不认识的版本号
  → 看日期，不看数字大小
```

## 12. 把时间线当版本档案用

时间线除了"看最新版"，还有三个更实用的用法。

### 12.1 查某个历史版本属于哪个主版本

想知道"1.20.4 属于哪个大版本、它后面还有哪些修订"，就在时间线里定位到那一行，然后**往上读**：同一主版本下的修订版通常连续出现。在你需要"退回到某个已知可用的版本"时，这个动作比搜资料快得多。

### 12.2 判断一个旧主版本还会不会更新

时间线的顺序能给你一个直觉：如果一个主版本之后已经出现了新的主版本，旧主版本通常只在必要时收到修复。**这只是观察，不是官方承诺**；是否继续更新以官方发布说明为准。

### 12.3 基岩版用它对照客户端与服务端

基岩版条目同时记录了客户端版本与 BDS 构建号，所以玩家报出客户端版本后，可以直接在时间线上找到对应那一行，看它对应的服务端构建是什么。这是排查"客户端更新了、服务端没跟上"最快的一步。
