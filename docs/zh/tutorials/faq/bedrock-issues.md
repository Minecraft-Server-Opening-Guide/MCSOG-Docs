基岩版开服遇到的"起不来 / 连不上 / 能进但不对"，现象经常长得很像：玩家那头只会说一句"进不去"，而服务端这头可能连进程都没起来。这一篇是 [[BE] 常见问题](/tutorials/faq/faq-be) 的深入版，按"先分类、再定位"的顺序展开，把每一步的判据尽量写清楚。
:::tip 这一篇怎么用
先看第 1 节的分类表，判断自己遇到的是哪一类，再直接跳到对应章节。第 5 节给了一条从零开始的完整排查顺序；第 6 节讲求助时该提供哪些信息。
:::

## 1. 先分类：连不上 / 起不来 / 能进但异常

分类的判据是：**服务端进程到底有没有在跑、有没有在监听端口？**

| 现象 | 属于哪一类 | 去看哪一节 |
| --- | --- | --- |
| 启动器窗口一闪而过，或命令行立刻回到提示符 | 起不来 | 第 2 节 |
| 控制台刷出报错，进程根本没起来 | 起不来 | 第 2 节 |
| 进程在跑、控制台也正常，但玩家连不上 | 连不上 | 第 3 节 |
| 玩家能进，但卡顿、存档异常、权限不对 | 能进但异常 | 第 4 节 |
| 一部分玩家能进、另一部分不能 | 连不上 | 第 3 节（先查协议版本与客户端平台） |
| 端口检测工具说"通过"，玩家还是进不去 | 连不上 | 第 3.2 节（多半是工具只测了 TCP） |
| 昨天还好，今天所有人都进不来 | 连不上 | 第 3.1 节（客户端自动更新换了协议） |
| 服务端能起来，但玩几分钟就自己退出 | 能进但异常 | 第 4.1、4.2 节 |
:::note 先确认进程状态，再谈其他
"连不上"和"起不来"的排查路径完全不同。第一步永远是确认进程还在、还在监听端口（第 5 节）。跳过这一步，后面所有判断都只是猜。
:::

## 2. 服务端起不来（BDS 与第三方核心）

### 2.1 BDS：架构、运行库与系统要求

BDS 是**原生编译**的程序，不是脚本，所以它挑系统和运行库。

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| 架构 | **x86-64** | 官方只提供 Windows 与 Linux 的 x86-64 构建；ARM 设备（如树莓派）不在官方支持范围内 |
| Windows | Windows 10 10.0.15063 及以上，或 Windows Server 2016 及以上 | 同时需要 **Microsoft Visual C++ 运行库**（VC++ Redistributable） |
| Linux | 官方只支持 **Ubuntu 22.04 及以上** | 其他 x86-64 发行版只要库齐全也能跑，其中包含 **glibc 2.35 或更高** |
| 内存 | 最低 4 GB | 玩家超过 10 人时通常需要更多；磁盘建议预留 1 GB |

关于运行库缺失的典型表现：Windows 上 BDS 依赖 Microsoft Visual C++ 运行库，**缺失时通常是启动瞬间报缺少某个 DLL，或者窗口一闪就退出**，控制台里往往什么都没有；Linux 上 glibc 版本偏低时，常见的是**动态库加载失败**（`error while loading shared libraries` 一类）。具体要求的运行库与 libc 版本请以 **BDS 官方下载页与 release notes** 为准，不要照抄第三方教程里的版本号。
:::warn BDS 不能像 Java 版那样指定内存
Java 版可以靠 `-Xms` / `-Xmx` 控制堆大小，**BDS 没有对应的启动参数**。它自己管理内存，你只能通过限制世界规模、实体数量和玩家数量来间接控制占用。所以"给 BDS 加内存参数"这类建议是无效的。
:::

### 2.2 Linux：执行权限与工作目录

Linux 下两个最常见的"起不来"原因，都是操作层面的。**一是没有执行权限**——从压缩包解出来的 `bedrock_server` 默认不带 `+x`：

```bash
chmod +x bedrock_server
```

**二是工作目录不对**——BDS 的官方用法就是**在自己的目录里运行**，并让动态库搜索路径指向当前目录：

```bash
cd /opt/bedrock-server
LD_LIBRARY_PATH=. ./bedrock_server
```

BDS 的**数据全部保存在工作目录里**，并且它期望解压出来的初始文件就在那里。所以：用 systemd 或其他方式拉起时，务必设置 `WorkingDirectory`，否则进程的工作目录可能是 `/`；从别的目录执行二进制，轻则在错误的目录里凭空生成一套新的配置文件与世界，重则因为找不到同目录的库直接启动失败。还要注意 `LD_LIBRARY_PATH=.` 里的 `.` 指的是**当前工作目录**，不是二进制所在目录。
:::tip 排查"起不来"的第一条命令
在服务端目录里手动跑一次 `LD_LIBRARY_PATH=. ./bedrock_server`，把报错原样看完。很多问题在这一步就会暴露出来，比翻日志快得多。
:::

### 2.3 改名与路径的坑

BDS 的主程序可以改名，但**不建议**。改名之后，所有引用它的地方都要同步改：启动脚本（`.bat` / `.sh`）、桌面快捷方式、面板或守护进程里配置的启动命令，以及第 2.2 节里那条 `LD_LIBRARY_PATH=. ./bedrock_server` 命令本身。漏掉任何一处，结果就是"点了没反应"或者"报找不到文件"。如果已经改了名又起不来，先改回原名验证，再决定是否要逐处修改。

同样容易出问题的是**路径本身**：服务端目录建议放在纯英文、无空格、无特殊符号的路径下。中文路径在部分面板和启动脚本上会导致读取失败，而且报错通常很难懂。

### 2.4 Nukkit 系：Java 版本与构建对齐

Nukkit 系（Nukkit / PowerNukkitX 等）是 **Java** 程序，两个点要确认：

- **Java 版本够不够**：新分支通常要求较新的 Java，装太旧会在启动瞬间抛出 `UnsupportedClassVersionError` 一类的错误，报错里一般会直接写出它需要的版本，**以该核心的官方文档为准**。
- **位数对不对**：64 位系统必须配 64 位 Java。32 位 Java 会因为内存上限在启动或运行中途崩掉。

更隐蔽的是**构建与协议版本对不上**：核心构建本身能启动，但客户端连不上，或者提示服务器版本过旧。这一层请先看 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup)，那里有完整的版本对齐说明。

### 2.5 PocketMine-MP：PHP 版本与扩展

PMMP 是 **PHP** 程序，它的官方要求是：**64 位 CPU + 64 位操作系统**，内存 1 GB 起；双核及以上只是**推荐**而非硬性要求；官方尽量支持 Windows、Linux、macOS，原则上任何能跑 64 位 PHP 且扩展齐全的平台都可以。

两个最容易踩的坑：**PHP 版本与扩展**——PMMP 需要特定版本的 PHP 以及一组扩展，版本不对或扩展没加载，启动时就会报错，常见的一类是某个 PHP 扩展加载失败（例如 `opcache`）；**具体需要哪些扩展、最低 PHP 版本是多少，以 PMMP 官方文档的 Setup requirements 为准**。**不要随手用系统自带的 PHP**——发行版仓库里的 PHP 往往版本偏旧、扩展不全，Windows 上也可能装着别的软件留下的 PHP；PMMP 官方提供了**为各系统打包好的 PHP 运行时**（在其发布页按操作系统取对应文件），解压即用。**推荐使用官方打包的 PHP，而不是任意的系统 PHP。**
:::warn 先确认你调的是哪一个 PHP
执行 `php -v`，确认输出里是你打算用的那个版本和位数。启动脚本里如果写的是裸 `php`，它走的是 `PATH` 里的第一个，很可能不是你装的那个。
:::

### 2.6 端口被占用

端口冲突的表现是：进程启动后立刻退出，控制台提示无法绑定（bind）端口。

有一个**基岩版特有的坑**：`server.properties` 里的 `enable-lan-visibility` 默认开启，作用是响应局域网里寻找服务器的客户端。开启时，**即使你把 `server-port` / `server-portv6` 改成了别的值，服务端仍然会去绑定默认的 19132 / 19133**。所以同一台机器上开第二个基岩服时，即使改了端口也可能冲突；如果不需要局域网发现，可以关掉这个选项来避开，具体行为以官方文档为准。另外注意 `server-port` 的合法范围是 **1–65535** 的整数。

### 2.7 server.properties 写法错误

Bedrock 的 `server.properties` 是**逐行的 `键=值` 文本**，`#` 开头的行为注释。写错类型或超出范围的取值，可能导致启动失败，或者该选项被忽略而"改了没生效"。几个已经确认的合法取值可以直接对照：

```properties
server-port=19132
server-portv6=19133
allow-list=true
gamemode=survival
difficulty=easy
default-player-permission-level=member
tick-distance=4
view-distance=32
max-players=10
compression-algorithm=zlib
```

| 键 | 合法值 / 范围 |
| --- | --- |
| `server-port` / `server-portv6` | 1–65535 的整数 |
| `allow-list` | `true` / `false` |
| `gamemode` | `survival` / `creative` / `adventure` |
| `difficulty` | `peaceful` / `easy` / `normal` / `hard` |
| `default-player-permission-level` | `visitor` / `member` / `operator` |
| `tick-distance` | 4–12 的整数 |
| `view-distance` | 大于等于 5 的整数 |
| `max-players` | 正整数 |
| `compression-algorithm` | `zlib` / `snappy` |
:::warn 编辑前先备份，编辑时用纯文本编辑器
用记事本一类的**纯文本编辑器**改，不要用会插入格式的编辑器（比如带富文本的办公软件），否则会写入不可见字符导致解析失败。改之前先复制一份 `server.properties`。某个值到底允许什么，**以官方文档为准**。
:::

## 3. 连不上（cannot connect）

### 3.1 协议 / 版本不匹配

这是基岩版**最常见**的连不上原因，而且玩家侧几乎没有自救空间：应用商店默认自动更新，客户端一更新协议就变。这一层不在这里重复展开，直接看 [协议版本与版本选择](/tutorials/bedrock/protocol)。要点只有两条：客户端协议必须与服务端协议**一致**才能进服；iOS 玩家只能装商店最新版，所以"让玩家降级"这条路对 iOS 群体是堵死的。客户端版本与服务端版本不一致时，玩家会看到"过旧的服务器"一类的提示，**具体提示文案以官方为准**。

### 3.2 UDP 与 TCP：端口、防火墙、安全组

基岩版**走 UDP**，这一点和 Java 版完全不同，也是"端口检测通过但玩家进不来"的头号原因。

| 项目 | 值 |
| --- | --- |
| 默认 IPv4 端口 | **19132 / UDP** |
| 默认 IPv6 端口 | **19133 / UDP** |
| 需要放行的位置 | 系统防火墙 **和** 云安全组，两处都要 |
| 路由器端口转发 | 协议必须选 **UDP**；若只能选 TCP，则需要另建 UDP 规则 |
:::warn 只测 TCP 的工具会骗你
很多在线"端口检测"工具默认只探测 TCP。TCP 端口通不代表 UDP 端口通。确认基岩版端口时，一定要明确测的是 **UDP**。
:::

另外，多数内网穿透服务默认只支持 TCP，选方案时要确认它支持 **UDP**。跨端（让手机 / 基岩版玩家进 Java 服，或反过来）的场景见 [手机玩家支持](/tutorials/java/mobile)。

### 3.3 CGNAT / 没有公网 IPv4 / 双重 NAT

服务端跑得好好的、防火墙也放行了，外部还是连不上，问题往往在运营商那一侧。

| 情况 | 判断 | 处理方向 |
| --- | --- | --- |
| 路由器 WAN 口拿到的是**私有地址或共享地址**（CGNAT） | 你没有独占的公网 IPv4，端口转发无处可转 | 找运营商申请公网 IP，或改用支持 UDP 的隧道 / 虚拟局域网方案 |
| **双重 NAT**：光猫后面又接了一台路由器 | 转发只做在其中一台上，链路断在中间 | 转发必须做在**直接连到 Internet 的那台**设备上，并把下一跳的转发串起来 |
| 公网 IP 是动态的 | 地址会变，玩家记不住 | 用动态域名服务，或改用隧道方案 |
| 只有 IPv6 公网 | 部分玩家网络不支持 IPv6 | 同时确认 IPv4 侧的可达性 |

在无法做端口转发时，一个常见替代方案是**虚拟局域网**：让服务端和玩家加入同一个虚拟网络，然后玩家用虚拟网络的 IP 连接。社区里常用的有 ZeroTier、Radmin VPN、Hamachi 等，具体配置见各自的官方文档。

### 3.4 局域网发现 vs 用 IP 连接

这两种连接方式走的路径不一样，症状也不一样。

| | 局域网发现 | 用 IP / 域名连接 |
| --- | --- | --- |
| 玩家需要做什么 | 什么都不用做，服务器会出现在"游戏"界面顶部 | 手动添加服务器，填地址和端口 |
| 前提 | 双方在同一局域网内 | 服务端对外可达（端口转发或隧道） |
| 受什么影响 | `enable-lan-visibility`、UDP 19132/19133 是否可用 | 公网 IP、防火墙、安全组、隧道 |

几个容易忽略的点：**基岩版必须显式指定端口**，它不像 Java 版那样支持靠 SRV 记录省略端口，所以地址栏和端口栏都要填对；局域网发现依赖广播 / 多播，在部分虚拟网络、容器网络或跨网段的网络里不工作，这时只能改用 IP 连接；在**同一台机器上连接自己**可能因为回环或防火墙规则失败，换一台设备测试可以快速区分是"服务端不可达"还是"这台机器自己的问题"。

### 3.5 主机平台（Xbox / PlayStation / Switch）

主机平台**不能在游戏里直接输入 IP 加入服务器**。常见的两条路是：**自定义 DNS**（把域名解析指到你的服务器，让主机通过域名方式加入），以及**局域网**（让主机和服务端处在同一局域网内，用局域网发现加入）。
:::note 平台策略会变，且各平台不一样
主机侧的限制**随平台政策与版本变化**。有资料指出主机版本整体上更倾向只能走局域网，其中 Switch 的可选范围更窄（可能仅限 Realms / 官方推荐服务器）。**具体某个平台当前支持什么，以官方文档与平台说明为准**，不要照搬旧教程。
:::

### 3.6 客户端侧的检查

先排除最廉价的可能性，再动服务端：**地址格式**上，地址栏只填 IP 或域名，**端口填到端口栏**，把 `ip:port` 整体塞进地址栏在部分版本上会解析失败；**端口**默认 19132，服务端改过端口玩家那也要改；**是不是同一个版本**——基岩版客户端**不能**直接进 Java 版服务器（反之亦然），跨端要靠额外方案，见 [手机玩家支持](/tutorials/java/mobile)；**客户端版本必须与服务端版本相同**，基岩版不支持旧版本客户端连新版服务端。最后**换一台设备、换一个网络试**，能立刻区分是服务端问题、玩家网络问题，还是玩家设备问题。

### 3.7 第三方核心的特有情况

第三方核心**不一定实现了官方服务端的全部协议特性与游戏内容**，所以"同样的客户端，进官方服正常、进我的服就不对"是正常现象，不一定是配置错误。以 PocketMine-MP 为例，官方文档明确说明：PMMP 并**没有**实现 Minecraft 的全部玩法特性，原因是开发者业余维护、难以跟上官方更新速度；在撰写时缺失的特性包括**生物（mobs）、红石、矿车和维度**。

另一个要点是**核心构建与协议版本的对齐**：核心向客户端报告的版本必须被客户端接受，否则玩家会看到"服务器版本过旧"一类的提示。PMMP 官方 FAQ 的处理方式是：在服务端控制台执行 `version` 命令，查看当前核心支持的 Minecraft 版本，再据此选择更新的核心构建；官方同时说明，**较新的补丁版本之间有时（但不总是）无需更新核心即可兼容**。

## 4. 能进但异常（works but behaves oddly）

### 4.1 卡顿与内存

**卡顿的第一判据是单核性能。** BDS 的生物运算在单线程上完成，所以流畅度主要取决于单核性能，地图越大越卡，这一点在 [BDS 服务端](/tutorials/bedrock/bds) 里有说明。

| 可以调整的方向 | 说明 |
| --- | --- |
| 降低 `tick-distance` | 合法范围 4–12，默认 4。值越大，参与运算的区块越多 |
| 降低 `view-distance` | 需大于等于 5，默认 32。主要影响下发范围 |
| 减少实体 / 生物农场规模 | 实体是单线程运算的主要负载 |
| 换单核更强的机器 | 最直接，但成本最高 |
| `max-threads` | Bedrock 有这一项（最大线程数），但它**改变不了单线程瓶颈**，不要指望靠它解决卡顿 |

关于 PHP 核心：PMMP 官方文档明确说它在多核利用上"出了名的差"，如果是为了跑 PMMP 买机器，**应优先选高主频而不是多核心**。

**关于内存持续增长**：BDS 存在内存缓慢上涨的已知问题。关键提醒是——
:::warn 不要强行清理内存
强行清理内存会导致玩家在下载材质包 / Addon 时**进度条卡住**，而且**只能重启服务端**才能恢复。正确做法是规划定期重启窗口，而不是"看到内存高就去清一下"。
:::

### 4.2 区块与世界数据问题

BDS 的世界数据在 **`worlds/`** 目录下，每个世界一个子文件夹。有一个非常关键的行为：

> 服务端启动时会去 `worlds/` 里找**与 `server.properties` 中 `level-name` 同名**的目录。找到就用它；**找不到就新建一个世界**。

这意味着 **`level-name` 写错一个字母，服务端不会报错，而是安静地生成一个新世界**——玩家看到的就是"我的存档没了"。所以发现"存档变了"时，第一件事是核对 `level-name` 和 `worlds/` 里的目录名。

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 世界加载失败 / 启动时报世界相关错误 | 存档损坏，或上次保存被中断 | **停止反复启动**，从备份恢复 |
| 换了核心后世界读不出来 | 第三方核心的存档兼容性不如官方 BDS | 恢复原核心，或按核心文档迁移 |
| 世界导入后不生效 | 目录名与 `level-name` 不一致 | 把世界目录重命名为 `level-name` 的值 |
| 存档整体丢失 | 只备份了部分文件 | 备份 `worlds/` **整个目录** |

从备份恢复的完整流程见 [备份与恢复](/tutorials/java/backup)。
:::tip 复制或备份前先正常关服
在控制台执行 `stop`，等进程真正退出后再复制 `worlds/`。进程还在写文件时复制，得到的很可能是一个"看起来完整、实际损坏"的存档。
:::

### 4.3 附加包与资源包

两个前提：**必须是基岩版格式的包**——Java 版的数据包 / 资源包和基岩版的附加包是两套东西，互不通用；**包必须被正确放置并注册**——光把文件拷进去，服务端不会自动启用它。已验证的目录与注册方式如下：

| 类型 | 放置目录 |
| --- | --- |
| 行为包（Behavior Pack） | `development_behavior_packs` |
| 资源包（Resource Pack） | `development_resource_packs` |

要让某个世界启用包，需要在**该世界的工作目录**里创建对应的清单文件，写入包的 UUID 和版本；UUID 来自包自己的 `manifest.json`：

```json
[
    {
        "pack_id": "33556fcf-d192-4d5f-96a0-29357702af7b",
        "version": [ 1, 0, 0 ]
    }
]
```

其中：行为包写入 `world_behavior_packs.json`，资源包写入 `world_resource_packs.json`；多个包存在冲突时，**排在前面的包优先**。

其他要点：**`texturepack-required=true`** 会强制客户端下载服务端的资源包，开启后玩家自己启用的客户端资源包（包括市场包）会失效；**市场（Marketplace）里的包不能应用到服务端**；服务端根目录还有一个 **`valid_known_packs.json`**，它是服务端维护的**已知包列表**，服务端据此做校验，它的确切格式与维护流程**以官方文档为准**，日常操作走上面那套"放目录 + 写 world_*_packs.json"的流程即可；**客户端卡在下载资源包**，除了包本身的问题，也可能是服务端内存状态导致的（见 4.1），此时重启服务端往往能恢复。

对 PMMP 还有一个官方已知问题：**服务端使用较大的资源包时会出现连接问题**（官方举例为大于 1 MB 的包）。官方给出的排查手段是移除大包后重试；另一个可能有效的变通做法是在 `pocketmine.yml` 中逐步降低 `network.max-mtu-size`（例如每次降 100 再测），但官方同时说明这只是**变通**，会降低带宽效率，仍应找出根因。

### 4.4 权限与白名单

BDS 的权限与白名单是**两个独立文件**，字段也不一样，很容易混。**管理员（OP）在 `permissions.json` 里**，条目由 `xuid` 和 `permission` 组成：

```json
[
    {
        "permission": "operator",
        "xuid": "451298348"
    }
]
```

- `permission` 的合法值只有三个：**`operator` / `member` / `visitor`**。
- **`online-mode` 必须开启**，因为 XUID 需要在线验证账号。
- 服务端运行中修改了该文件，需要执行 **`permission reload`** 才会生效；`permission list` 可以查看当前权限。
- 不在列表里的新玩家，适用 `default-player-permission-level` 的设置。除了改文件，也可以**在游戏内直接改**玩家权限。

**白名单在 `allowlist.json` 里**，条目字段为：

| 字段 | 含义 |
| --- | --- |
| `name` | 玩家的**游戏名 / 昵称（gamertag）**，必须完全一致 |
| `xuid` | 玩家的 XUID；**如果已经填了 `name`，这一项可以省略** |
| `ignoresPlayerLimit` | 为 `true` 时，该玩家在人数已满时仍可进入 |

几个关键行为：只填 `name` 时，**当同名玩家连接后 XUID 会被自动补上**，也就是说名字填错了这个人永远进不来，而且不会自动纠正；**白名单只在 `online-mode` 开启时有效**，关闭正版验证后玩家可以顶着白名单里的名字进来，白名单形同虚设；玩家**改了 gamertag** 之后，旧名字的条目就不再匹配，需要更新；手工改文件时服务端还在运行，需要用相应的 reload 命令让改动生效。

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 该是 OP 的人不是 OP | 条目没写进 `permissions.json`，或写了但没 reload | 补条目并 reload，或在游戏内直接设置 |
| 加进 `permissions.json` 却没生效 | `online-mode` 关闭，XUID 无法验证 | 开启 `online-mode` |
| 白名单里的人进不来 | `name` 与实际 gamertag 不完全一致（大小写、空格、改名） | 核对准确名字，或直接填 XUID |
| 谁都能进 | 白名单没启用，或 `online-mode` 关闭 | 检查 `allow-list` 与 `online-mode` |
:::note 字段名以官方文档为准
上面这些字段名与行为取自官方说明。**不同版本之间可能调整字段或默认值**，实际以 BDS 官方文档（以及随包附带的 `bedrock_server_how_to.html`）为准。
:::

### 4.5 与 Java 版的行为差异

玩家报的很多"bug"，其实是**两个版本本来就不一样**：红石机制、生物生成规则等都有差异。这一层不在这里重复解释，直接看 [JAVA VS 基岩](/wiki/editions)。

## 5. 排查顺序

按下面的顺序走，每一步都能把可能性砍掉一半。**不要跳步**。

1. **确认服务端进程真的在跑。** 看控制台窗口是否还在、进程是否还在进程列表里。
2. **确认它在监听端口。** Linux 与 Windows 的命令见下。
3. **确认端口与协议。** 端口号对不对，放行的是不是 **UDP**（默认 19132，IPv6 为 19133）。
4. **确认客户端版本。** 客户端版本必须与服务端版本一致，见 [协议版本与版本选择](/tutorials/bedrock/protocol)。
5. **确认网络路径。** 局域网 / 公网 IP / 隧道，三者走的路不一样；有没有 CGNAT 或双重 NAT。
6. **看服务端控制台与日志。** 报错原文比任何猜测都值钱。BDS 的启动与报错都会打印在控制台。
7. **确认权限与白名单。** 玩家是被踢了，还是压根没连上？被踢通常能在控制台看到原因。
8. **确认世界与附加包完整性。** `level-name` 是否与 `worlds/` 下的目录名一致；包是否放在正确目录并注册。

第 2 步的命令：Linux 用 `ss -ulnp | grep 19132`（`-u` 只看 UDP）；Windows 用 `netstat -ano | findstr 19132`（`-a` 全部连接与监听，`-n` 不做名称解析，`-o` 显示进程号）；PowerShell 下更直观的是 `Get-NetUDPEndpoint -LocalPort 19132`。

```bash
ss -ulnp | grep 19132
```

```bat
netstat -ano | findstr 19132
```

**现象对照表：**

| 现象 | 先查什么 | 常见原因 |
| --- | --- | --- |
| 进程不在 | 控制台报错原文 | 运行库缺失、Java / PHP 版本不对、端口被占用、配置写错 |
| 进程在，端口没监听 | 启动日志里有没有 bind 失败 | 端口被占用、`enable-lan-visibility` 抢绑 19132/19133 |
| 端口在监听，本机能连、外部不能 | 公网可达性 | 安全组 / 防火墙没放行 UDP、CGNAT、双重 NAT |
| 端口检测通过但玩家进不去 | 检测工具测的是 TCP 还是 UDP | 只放行了 TCP |
| 提示服务器版本过旧 | 客户端与服务端版本 | 协议不匹配；第三方核心构建太旧 |
| 能进但一进就掉 | 控制台是否有踢出原因 | 白名单、权限、人数上限 |
| 能进但特别卡 | 单核占用、`tick-distance`、实体数量 | 单核瓶颈、地图过大 |
| 存档"消失" | `level-name` 与 `worlds/` 目录名 | `level-name` 写错，服务端新建了世界 |
| 附加包不生效 | 包类型与放置目录 | 放错目录、没写 world_*_packs.json |

## 6. 求助时该给什么

把下面这些一次性给全，能省掉好几轮来回：

| 要提供的信息 | 为什么需要 |
| --- | --- |
| **服务端核心与构建版本** | BDS 的版本号，或 Nukkit 系 / PMMP 的核心名与构建号。不同核心的排查路径不同 |
| **游戏版本 / 协议版本** | 客户端和服务端各是什么版本，这是基岩版第一排查项 |
| **操作系统与架构** | Windows 还是 Linux、发行版与版本、是否 64 位、是否 x86-64 |
| **控制台报错的完整原文** | **不要转述、不要只截一半**。报错原文里的关键词能直接定位问题 |
| **最近改过什么** | 升级了核心？换了端口？加了附加包？改了 `server.properties`？ |
| **以前是否正常** | "一直没成功"和"昨天还好"是两条完全不同的排查路径 |
| **已经试过什么** | 避免重复建议；也说明哪些方向已经被排除 |
| **网络情况** | 局域网还是公网、有没有公网 IP、用了什么隧道、端口转发怎么配的 |
:::tip 报错原文怎么给
直接把控制台输出复制成文本，或者贴日志文件。**拍照、截图、只贴最后一行**都会让排查变慢。如果输出很长，保留报错前后各若干行，而不是只留一句。
:::
