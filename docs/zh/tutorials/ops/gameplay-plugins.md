技术教程讲到"插件怎么装、前置是什么"就够了，但真正决定服务器像不像一个"游戏"的，是**经济与玩法插件**：钱从哪来、商店怎么定价、任务给什么奖励、称号怎么展示、箱子里开出什么。

这一篇按**类别**讲清楚每一类插件在做什么、代价是什么、风险在哪里。凡是点名具体插件的段落，都只写能从该插件的**官方页面**（官方仓库、官方文档站）核对到的能力；核对不到的部分，就只描述类别，不编造具体名字。前置依赖的基础知识见 [插件入门](/tutorials/java/plugins) 与 [常用前置插件](/tutorials/java/plugin-deps)。
:::warn 玩法插件是"代码"，不是"内容包"
每装一个玩法插件，你就多了一份：需要跟进更新的代码、可能与其他插件冲突的代码、可能被利用来刷物品的代码、以及会持续消耗主线程性能的代码。**玩法插件不是越多越好**。先想清楚要解决什么问题，再去找插件；不要因为"别人服里有"就装。
:::

## 1. 先建立正确的心智模型

在挑插件之前，先把四件事想清楚：

| 问题 | 为什么重要 |
| --- | --- |
| 这个插件解决什么问题 | 说不出来就别装。装完之后没人用，等于白付性能与风险成本 |
| 它依赖什么 | 缺前置会加载失败或功能静默失效，见 [常用前置插件](/tutorials/java/plugin-deps) |
| 它把数据存在哪里 | 文件型存储换服、开分服、做备份时的行为完全不同 |
| 它能不能被玩家利用 | 任何"能产出物品或货币"的插件，都是潜在的刷取入口 |

玩法插件的风险可以粗略分成四类，后面每一节都会反复出现：

- **经济风险**：能凭空产出货币或高价值物品，导致通货膨胀。
- **安全风险**：复制漏洞、权限绕过、命令注入。
- **性能风险**：每 tick 的额外计算、实体数量、数据库查询频率。
- **运营风险**：玩家觉得不公平、内容被玩穿、作者停更导致卡在旧版本。

## 2. 一张分类总表

先看全局，再逐节展开。

| 类别 | 增加什么 | 难度 | 性能开销 | 主要风险 |
| --- | --- | --- | --- | --- |
| 经济系统（API + 实现） | 货币、余额、转账的基础 | 中 | 低（数据库写入与查询） | 货币来源失控导致通胀；数据损坏 |
| 商店 | 买卖渠道、定价场所 | 中 | 低到中（取决于商店数量与查询频率） | 定价错误、无限收购、被刷 |
| 任务与成就 | 目标感、日常留存 | 中到高（内容设计成本高） | 低到中 | 奖励击穿经济；内容被玩穿 |
| 称号与头衔 | 身份展示、社交符号 | 低 | 极低 | 与付费强度挂钩会伤信任 |
| 抽奖与箱子 | 随机奖励、短期刺激 | 中 | 低到中（动画与广播） | 赌博成瘾、付费随机奖励的合规与伦理问题 |
| 职业与技能 | 长期成长线 | 中到高 | 中（高频事件监听） | 产出失控；与生存玩法冲突 |
| 小游戏与跑酷 | 独立玩法、多人互动 | 高 | 中到高（独立世界与实例） | 人数不足导致空场；维护成本高 |
| 领地与保护 | 财产安全感 | 中 | 中（方块事件与查询） | 规则复杂、新手劝退；与经济联动时易失衡 |
| 科技类大型玩法 | 完全不同的游戏体验 | 很高 | 高（大量自定义物品与机器逻辑） | 性能、版本升级困难、上手门槛高 |
| 反作弊与记录 | 秩序与可追溯性 | 中 | 中（记录型插件持续写盘） | 记录不全；装晚了查不到历史 |
:::tip 表格怎么用
"难度"指的是**你配置和维护它的成本**，不是插件本身复杂不复杂。一个配置项上千行的插件，就算文档再全，也会吃掉你大量时间。**先算自己的时间预算，再算性能预算。**
:::

## 3. 经济系统：一定是两层

### 3.1 API 与实现必须分开理解

这是新手最容易踩的坑：**装了 Vault 却依然没有经济系统**。

Vault 的官方定位是 **Bukkit 的抽象库**（官方仓库描述：*Vault of common APIs for Bukkit Plugins*；README 标题：*Vault - Abstraction Library for Bukkit*）。它自己不产生任何货币，只定义一组统一接口，让"需要经济能力的插件"和"真正提供经济能力的插件"能对上话。它的开发者 API 已经拆到单独的 VaultAPI 仓库（官方 README 说明）。

所以经济系统永远是**两层**：

| 层 | 角色 | 例子（以官方页面为准） |
| --- | --- | --- |
| 抽象层 | 定义"查余额、扣钱、加钱"的接口 | Vault |
| 实现层 | 真正持有余额数据、执行加减 | EssentialsX 的经济模块、CMI 的经济系统、XConomy 等 |

| Vault 这类抽象层提供什么 | 谁来实现 | 谁在调用 |
| --- | --- | --- |
| 经济（Economy） | 具体经济插件 | 商店、任务、抽奖、领地维护费 |
| 权限（Permission） | 权限插件（如 LuckPerms） | 需要判断权限的插件 |
| 聊天（Chat） | 聊天类插件 | 需要发送或格式化聊天的插件 |

几个可以核对的具体事实：

- **EssentialsX** 的官方模块说明写明：核心 jar 包含大部分命令、牌子、kit **以及经济系统**（*signs, kits and the economy*）。也就是说装 EssentialsX 本体就已经有经济实现了。
- **CMI** 的官方页面写明它提供 **Economy system（含余额排行）** 与 **Cheque system（把金钱做成物品）**；它同时说明 CMI 的经济要接入 Vault 体系，需要配合官方提供的 Vault 版本或经济注入模块使用，并且要启用配置文件里的经济开关。
- **XConomy** 的官方仓库描述是"支持多服数据同步的经济插件"，适合多服共用一套余额的场景；使用前请自行确认它当前的维护状态是否满足你的版本要求。
- **Jobs Reborn** 的官方页面把 **Vault** 列在依赖项里——这就是"玩法插件通过抽象层调用经济"的典型例子。
:::note 先确认"到底是谁在管钱"
排查经济问题时，第一个要问的不是"商店插件坏了没"，而是"**现在真正提供经济实现的是哪个插件**"。很多"余额变成 0""扣钱不生效"的问题，根源是同时装了两个经济实现，或者抽象层指向了一个没有数据的实现。
:::

### 3.2 物理货币物品

有些实现支持**把货币做成物品**（例如 CMI 官方文档中的 Cheque / 支票系统：创建一张包含金额的物品，可以在玩家之间流转）。这类设计有利有弊：

- 好处：交易有实体感，适合 RP 与线下交易；可以离线交付。
- 风险：物品一旦能被复制、被非法获取、或在跨服转移中丢失，就等于货币失控；同时"物品形式的钱"绕过了插件层面的交易记录。

如果你打算用物理货币，**必须同时解决三件事**：物品不可伪造（依赖物品数据校验）、交易有记录、丢失有申诉流程。

### 3.3 货币是管理员创造的，还是玩家赚来的

这是经济设计的第一个决定，也是最重要的一票：

| 模式 | 钱的来源 | 后果 |
| --- | --- | --- |
| 管理员创造（发钱、卖物给系统） | 指令与商店回收 | 简单直接，但极易通胀；必须配合强回收手段 |
| 玩家赚取（劳动、交易、任务） | 玩法产出 | 更健康，但设计成本高；产出速率必须可控 |
| 混合 | 系统发放基础收入，玩家之间流通 | 现实中最常见；关键是把系统发放量当成"货币发行量"来管理 |

## 4. 商店

商店是经济的**流通渠道**，也是最容易出事的地方——因为它直接决定"什么东西值多少钱"。

### 4.1 交互形式：牌子 / 箱子商店 vs GUI 商店

| 形式 | 特点 | 适合 |
| --- | --- | --- |
| 牌子 / 箱子商店 | 玩家把箱子放在世界里，用牌子标价；不需要命令即可买卖 | 玩家之间的自由市场、集中商业区 |
| GUI 商店 | 用菜单界面浏览分类与购买；管理员配置商品表 | 管理员商店、新手引导、品类繁多的收购 |

可以核对的官方描述：

- **ChestShop**：官方仓库描述为 *The original chest & sign shop plugin for Minecraft Servers running Bukkit/Spigot/Paper. Est. 2011*（最早的箱子与牌子商店插件）。
- **QuickShop-Hikari**：官方仓库描述写明它是"让玩家无需任何命令就能从箱子里买卖物品的商店插件"，并强调玩家实际上不需要用到它提供的任何命令。
- **Shopkeepers**：官方 README 写明它让服主设置"自定义村民商店"，并且**同时支持两类商店**：**管理员商店（无限库存）** 与 **玩家商店（从容器中取货）**。
- **GUI 商店类**：以菜单为交互方式的商店插件（例如 EconomyShopGUI，其官方仓库 Gypopo/EconomyShopGUI-API 描述为"The API of EconomyShopGUI"，供其他插件对接）。

### 4.2 玩家商店 vs 管理员商店

| 类型 | 库存 | 定价者 | 经济含义 |
| --- | --- | --- | --- |
| 管理员商店 | 无限 | 服主 | 系统级的货币水龙头与回收站，直接决定通胀 |
| 玩家商店 | 玩家自己的货物 | 玩家 | 玩家之间的流通，服主只需提供规则与场地 |

### 4.3 "卖给服务器"和"玩家之间交易"是两件事

这是最需要向玩家解释清楚的一点：

- **卖给服务器**：服务器无限收购，等于**货币发行**。收购价就是发行价，收购量就是发行量。
- **玩家之间交易**：一方付钱、一方交货，货币总量不变，只是转移。

很多"经济崩了"的服务器，问题都出在管理员商店的**无限收购价**上：只要某个物品可以稳定、无限地卖给系统，玩家就会把它变成刷钱机器。

### 4.4 商店经济崩坏的典型路径

| 崩坏方式 | 机制 | 预防 |
| --- | --- | --- |
| 无限收购定价过高 | 玩家批量刷取该物品卖给系统 | 定期审查收购表；给单玩家收购量设上限 |
| 复制漏洞 | 物品数量凭空翻倍，再卖给系统换钱 | 见第 9 节；所有产出型玩法都要有记录 |
| 出售价格写错（少一个 0） | 一次交易就把经济打穿 | 改动价格后先在测试服验证；保留配置改动记录 |
| 高价物品无人出售 | 货币只进不出，通胀 | 设计回收手段，见第 10 节 |
| 商店被用作跨玩家转账 | 变成洗钱或逃税通道 | 明确规则；必要时对交易抽税 |
:::warn 商店的价格表是经济配置文件，不是随便填的表格
改一个收购价之前，先算一遍：**单个玩家一小时能产出多少该物品？乘以收购价，就是他每小时的印钞速度。** 如果这个数字和"正常玩一小时能赚的钱"差了一个数量级，经济一定会在几天内崩掉。
:::

## 5. 任务与成就

任务系统解决的是**目标感**问题：玩家上线之后有明确的"今天做什么"。

可以核对的官方描述：

- **Quests**（PikaMug）：官方仓库描述为"易用、开源的、用于在 Minecraft 服务器上创建与执行任务的插件"。
- **BetonQuest**：官方仓库描述为"高级且强大的任务脚本插件"，内置 RPG 风格对话，并集成 40 多个其他插件。它更适合"有剧本、有对话、有分支"的重内容服务器。

### 5.1 日常 / 周常任务

- **日常任务**提供稳定的上线理由，但奖励必须小。日常奖励的设计目标是"值得做"，不是"必须做"。
- **周常任务**适合承载较大奖励，因为它对产出速率有天然上限（一周一次）。
- **不要把任务做成签到发钱**。纯粹的"点一下就领钱"会把经济变成按时间发钞。

### 5.2 奖励设计不能击穿经济

任务奖励有三种安全形态：

| 形态 | 说明 | 风险 |
| --- | --- | --- |
| 外观与称号 | 不影响数值 | 低（前提是称号不卖强度） |
| 消耗品与便利 | 药水、传送券、修理券 | 中（要算清每小时产出） |
| 货币与高价值物品 | 直接发钱、发装备 | 高（必须按小时产出上限倒推定价） |

判断标准是：**任务奖励必须能和你已有的货币来源放在同一张表里比较**。如果任务的每小时收益远高于其他玩法，玩家就会只做任务，其他内容全部荒废。

## 6. 称号与头衔

称号属于**展示层**，它的价值来自"别人看得见"，而不是数值。

| 类型 | 实现方式 | 说明 |
| --- | --- | --- |
| 权限型前缀 / 后缀 | 权限插件存 meta，聊天或 TAB 类插件渲染出来 | 最常见，与权限组天然绑定 |
| 装饰性称号 | 玩家自己选择并展示的文本 | 通常需要单独的称号插件与解锁条件 |
| 玩法内头衔 | 由玩法插件自身提供（例如职业插件显示的职位名） | 例如 Jobs Reborn 官方文档中的 Chat Titles 功能 |

可以核对的事实：**LuckPerms** 的官方仓库描述是"面向 Minecraft 服务器的权限插件"，它负责存权限与前缀元数据；而 **EssentialsX 的官方模块文档**明确写到，要让玩家拥有前缀与后缀，需要 **Vault 与 LuckPerms**。也就是说，**"谁存前缀"和"谁把前缀显示出来"通常不是同一个插件**——显示那一步由聊天类或 TAB 类插件完成，具体见 [聊天、菜单与 MOTD](/tutorials/java/cosmetic)。

设计上的两条底线：

- 称号可以卖（作为支持者的标识），但**不能带强度**。
- 称号系统要能被撤回。玩家违规后，你应当能立刻摘掉他的称号。

## 7. 抽奖与箱子

箱子（Crates）是"随机奖励"玩法，短期刺激极强，长期争议极大。

### 7.1 奖励表怎么工作

主流箱子插件的核心都是一张**带权重的奖励表**：

- 每个奖励有**权重（weight）**，权重越高越容易抽中。
- 奖励常按**稀有度（rarity）**分组，稀有度再影响抽取概率。
- 钥匙分**实体钥匙**（可交易、可转赠）与**虚拟钥匙**（绑定玩家）。
- 通常还有**开启成本、冷却、权限要求、次数上限**等限制。

可以核对的官方描述：

- **CrazyCrates**：官方描述为"为你的服务器添加无限数量的箱子，提供 11 种箱子类型"；官方文档站为 docs.crazycrew.us，安装说明要求使用 Paper 及以上服务端，并提供 `/crazycrates debug` 用于测试奖励。
- **ExcellentCrates**：官方 Wiki 列出稀有度权重（rarity weights）、奖励权重（weights）、开启成本（open cost）、冷却、里程碑、奖励次数上限（roll limits），并明确提供 **虚拟钥匙**（官方说明其目的是**防止钥匙被分享、交易或出售**）与 **奖励日志**（把每次抽取记录到专门的日志文件）。

这两点对你的运营有直接价值：**虚拟钥匙**让你能控制"钥匙不被买卖"，**奖励日志**让你在出问题时能查证。

### 7.2 赌博与成瘾：必须正视的问题

随机奖励在心理机制上和赌博高度相似：可变比率强化、差点就中、沉没成本。作为服主，你需要主动设限：

- **不要用"再抽一次就能中"的话术**。这属于刻意诱导。
- **公开概率**。奖励表与权重应当对玩家可见，至少在规则里说明。
- **设置上限**。每日/每周开启次数上限、单玩家奖励上限，能显著降低失控风险。
- **保护未成年人**。如果你的玩家群体偏年轻，这一点尤其重要。

### 7.3 付费随机奖励：合规与伦理警告
:::warn 不要做付费随机奖励
**把随机奖励和真实货币付费绑定（付费开箱 / 抽卡），在部分国家和地区受到专门的法规或平台规则约束，可能被认定为赌博类内容，也可能违反支付渠道与平台的政策。** 这类规则会变化，且不同地区差异很大，你必须自行核实适用于你的法律与平台要求，而不是照搬别人的做法。

从运营角度还有更现实的理由：**付费随机奖励是"pay-to-win 争议"的放大器**。它让"花钱能不能变强"这个问题从模糊变得具体，而玩家对它的容忍度极低。**建议的做法是：钥匙只通过玩法获得（活动、任务、贡献），不通过真实货币出售。**
:::

## 8. 玩法类

### 8.1 职业与技能

- **Jobs Reborn**：官方页面描述为"完全可配置的插件，让你通过破坏、放置、击杀、钓鱼、合成等行为获得报酬；基于职业（class-based professions），在执行工作时获得经验"，官方同时列出 Vault 依赖、MySQL 可选、自定义点券经济、每日任务、聊天头衔等特性。
- **mcMMO**：官方网站定位为"面向 Spigot/Paper 的 RPG 插件"，提供技能、升级、超级技能、排行榜与队伍（party）系统，并有大量配置项。

这一类的风险集中在**产出**：技能等级提高收益、职业奖励直接给钱，两者叠加很容易形成"越玩越富"的正反馈。上线前一定要估算**满级玩家的每小时收益**。

### 8.2 小游戏与跑酷

这两类通常需要**独立世界或独立实例**，并且对"同时在线人数"有硬性要求：

- 人数不足时对局开不起来，玩家看到的是空场，比没有这个玩法更伤。
- 维护成本高：地图、规则、平衡、漏洞，都需要持续投入。
- 建议在主线服务器稳定、且有稳定在线人数之后再考虑，不要作为开服第一批插件。

具体插件的选择空间很大且质量差异明显，**请以各插件的官方页面与更新记录为准**，本篇不点名推荐。

### 8.3 领地、保护与经济联动

领地系统的核心价值是**财产安全感**——没有它，玩家不愿意长期投入建设。可以核对的官方描述：

- **GriefPrevention**：官方仓库描述为"自 2011 年以来面向 Minecraft 服务器的官方自助式防破坏 Bukkit 插件"。
- **WorldGuard**：官方仓库描述为"保护你的 Minecraft 服务器，并让玩家圈定区域"。

与经济联动时要小心：**领地费用（购买、续费、按面积计费）是极好的货币回收手段，但如果定价过高，会直接把新玩家挡在门外**。建议把领地价格和"新手前几小时能赚到的钱"对齐，而不是和"老玩家的余额"对齐。更多保护体系的分工见 [领地与保护](/tutorials/java/protection) 与 [反作弊与防破坏](/tutorials/java/anticheat)。

### 8.4 科技类大型玩法（Slimefun 一类）

**Slimefun4** 的官方仓库描述是"一个独特、玩起来像整合包的 Spigot/Paper 插件"，自 2013 年起提供背包、喷气背包、反应堆等大量内容。

这类插件等于**在服务器里再装一个游戏**：

| 代价 | 具体表现 |
| --- | --- |
| 性能 | 大量自定义物品、机器逻辑与定时任务 |
| 版本升级 | 依赖服务端版本，升级常需要等待适配 |
| 上手门槛 | 新玩家面对一整套新系统，容易劝退 |
| 兼容性 | 与其他插件在物品、合成、掉落上容易冲突 |

如果你确定要做科技服，**先按"这是一个新游戏"的规格来做规划**：独立的引导、独立的教程、独立的性能预算，而不是把它当成"再加一个插件"。

## 9. 反作弊与经济安全

**复制漏洞（dupe）是经济系统的头号杀手**：它不改变规则，只改变数量，而数量一旦失控，价格、商店、任务奖励全部失去意义。

### 9.1 原则

- **所有产出型玩法都要有日志**。没有日志，你连"是不是被刷了"都无法判断。
- **记录每一笔交易**。谁在什么时候、和谁、交易了什么、金额多少。事后追查完全依赖这些记录。
- **保留审计轨迹**。封禁、回档、手动发钱都要留痕，避免"管理滥用"的指控，也方便复盘。
- **权限最小化**。能给权限节点就不要给 OP；能只给一个世界就不要给全服，见 [[JAVA] 安全插件](/tutorials/ops/security-java)。
- **有回滚预案**。出事之后能不能恢复到某个时间点，取决于你的备份策略，见 [备份与恢复](/tutorials/java/backup)。

可以核对的事实：**CoreProtect** 的官方仓库描述为"面向 Minecraft 服务器的、极快的数据记录与防破坏工具"。它记录的是**方块与容器层面的行为**，是排查"东西怎么没了"的第一手证据；[反作弊与防破坏](/tutorials/java/anticheat) 讲了它在整套防护体系中的位置。

### 9.2 违禁物品注入经济的风险

所谓"违禁物品"，指的是通过漏洞、命令或插件错误产出的、本不该存在的物品（异常附魔、非法数量、破坏平衡的道具）。它们的危害在于：

- 一旦流入玩家手中，**会被当成正常资产参与交易**，污染整个经济。
- 发现得越晚，回滚的代价越大（可能要回滚几十个玩家）。
- 处理时必须有依据：**先查记录确认来源，再决定回收范围**，不要凭感觉封人。

建议：对高价值物品建立"来源可查"的机制，并在规则里写清"违禁物品一律回收"。

## 10. 经济平衡设计

经济系统的本质是一个**水池**：进水和出水必须大致平衡。

| 方向 | 手段 | 说明 |
| --- | --- | --- |
| 货币来源（进水） | 管理员商店收购、任务奖励、职业收益、活动奖励 | 每一个来源都要能算出"每小时能产出多少钱" |
| 货币回收（出水） | 商店出售（玩家买系统的东西）、交易税、领地购买与续费、修理费、传送费、抽奖钥匙 | 出水不足必然通胀，这是最常见的设计缺失 |

### 10.1 通胀的典型症状

- 老玩家余额高到"什么都买得起"，商店失去意义。
- 新玩家觉得"永远追不上"，直接离开。
- 高价物品被扫空，价格继续上涨。
- 玩家之间的交易开始用"以物易物"绕开货币。

### 10.2 必须有的回收手段

至少准备三到四种，并且让它们**自然融入玩法**而不是"罚款"：

- **交易税**：玩家商店成交时抽成，自动回收，且与活跃度正相关。
- **领地维护费**：按面积或按时间收费，让"占地"有成本。
- **修理与附魔成本**：装备维护消耗货币，回收量随游戏进度增长。
- **便利服务**：传送、洗点、改名等收费服务。
:::tip 用数据而不是感觉来调经济
定期记录：服务器货币总量、前 10% 玩家的余额占比、每日新增货币量、每日回收量。**当"每日新增"持续大于"每日回收"时，通胀已经在发生**，只是还没显现在价格上。
:::

## 11. 落地顺序

不要一次把玩法装齐。推荐的最小可用顺序：

1. **最小经济**：只装一个经济实现（外加抽象层），确认余额能存能取、数据落在哪、备份是否覆盖。
2. **基础回收**：先把传送费、修理费或领地费用中的一项做出来。**没有回收手段的经济不要对外开放。**
3. **商店**：先做管理员商店（可控定价），确认收购表不会变成印钞机；需要自由市场时再加玩家商店。
4. **任务**：有了稳定的货币来源与回收之后，用任务去引导玩家体验你希望他们体验的内容。
5. **外观与称号**：最后再做展示层。它不影响数值，但能显著提升长期玩家的归属感。
6. **抽奖与箱子**：放在最后，并且坚持"钥匙只由玩法产出"。

每加一步，观察一到两周：货币总量、玩家行为、TPS。**出问题就回退上一步，而不是继续往前加。**

## 12. 上线前检查清单

- [ ] 每个玩法插件都能说清"它解决什么问题"
- [ ] 前置依赖已全部安装，控制台无加载报错
- [ ] 经济只有**一个**真正的实现，其余插件通过抽象层调用
- [ ] 所有货币来源都能估算"每小时产出上限"
- [ ] 至少有三到四种货币回收手段，并已实际生效
- [ ] 管理员商店的收购表经过一次"印钞速度"演算
- [ ] 任务奖励与货币来源放在同一张收益表里比较过
- [ ] 称号与外观不提供任何数值强度
- [ ] 抽奖钥匙只通过玩法获得，不通过真实货币出售
- [ ] 所有产出型玩法与交易都有日志
- [ ] 记录型插件（如 CoreProtect 一类）在开服**之前**就已安装
- [ ] 备份策略覆盖经济数据库与玩家数据
- [ ] 违禁物品的处理流程已写进规则
- [ ] 有回滚预案，并演练过一次
- [ ] 每加一个玩法插件，都记录了加装前后的 TPS 与 MSPT 变化
