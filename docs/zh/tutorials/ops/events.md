[宣传与引流](/tutorials/ops/promotion) 解决的是"玩家怎么找到你"，[经济与玩法插件](/tutorials/ops/gameplay-plugins) 解决的是"服务器里有哪些系统"，[[JAVA] 经营管理](/tutorials/ops/management-java) 解决的是"团队和钱怎么安排"。这三篇讲的都是**框架**。这一篇讲的是框架里真正发生的事：**某个晚上，一群人在你的服务器里一起做了一件事，做完之后还想再来。**

活动不是运营的装饰品。它是把一批互不相识的玩家变成社区的最短路径，也是让老玩家有理由回来的少数手段之一。它同时也是最容易翻车的一环：时间定错、规则没写、场地没建、奖励发崩，任何一项都能把一场本来不错的活动变成退服潮。

本文不涉及具体插件选型。需要插件清单时看 [插件入门](/tutorials/java/plugins) 与 [常用前置插件](/tutorials/java/plugin-deps)。

:::note 本文的边界
本文不给出任何具体活动插件、小游戏插件或奖励插件的名称、命令与配置键。**这类插件的名称、功能、可用命令与配置项差异很大，并且会随版本变化**，所以本文只描述"要做哪一类事、这一类事通常由哪一类工具承担"。具体到你的服务端能装什么、怎么写配置，请以各插件官方文档为准。
:::

## 1. 为什么活动值得做

### 1.1 新玩家在最初几分钟就做了决定

新人进服后的前几分钟决定了他会不会留下。这段时间里他面对的问题不是"玩法够不够多"，而是**"这里有没有人在，我该干什么"**。一个空荡荡的出生点配上一份长长的说明书，效果远不如"今晚八点有跑酷比赛，来玩"。

### 1.2 回归玩家需要一个具体的理由

"服务器还在开着"不构成回来的理由。"周六晚上有建筑比赛，你上次那栋房子可以拿去参赛"才构成理由。活动给的是一个**时间点**，而人对时间点的反应远强于对状态的判断。

### 1.3 活动把服务器变成社区

玩家之间的关系不是靠规则建立的，是靠**共同经历**建立的。一起输掉一场团本、一起在寻宝里找错方向、一起看着别人建的城堡发呆，这些才是"我们是同一个服的人"的来源。

| 玩家状态 | 他真正在问的问题 | 活动能提供什么 |
| --- | --- | --- |
| 刚进服的新人 | 这里有人吗？我该干什么？ | 一场马上能参与、门槛极低的活动 |
| 玩了几天的玩家 | 除了盖房子还能做什么？ | 一个明确的时间点，有人一起玩 |
| 玩了几周的老玩家 | 我留在这里的意义是什么？ | 身份、荣誉、被需要的位置 |
| 离开了一阵的人 | 有理由回来吗？ | 一条活动通知就是那个理由 |
| 只在群里聊天的人 | 我算这个服的人吗？ | 一个露脸并被记住的机会 |

:::tip 活动真正的产出不是奖励
奖励发完就没了，**共同记忆不会**。评价一场活动成不成功，看的不是"奖发出去没有"，而是"活动结束后聊天频道还热不热、有没有人问下次什么时候"。如果一场活动结束后立刻归于死寂，那它更像一次发奖，而不是一次活动。
:::

:::warn 活动不是万能药
活动能放大一个已经能玩的服务器，**不能修补一个不好玩的服务器**。如果新人流失的原因是出生点看不懂、卡顿、没人理他，那么办活动只会让更多人更快地看到这些问题。先解决体验，再谈活动。
:::

## 2. 活动类型一览

下面按类别列出常见活动。表格里的"需要准备什么"只写类别，具体由哪一类工具承担，请对照各插件官方文档确认。

| 类型 | 例子 | 需要准备什么 | 适合人数 | 风险 |
| --- | --- | --- | --- | --- |
| 建筑比赛 | 主题建筑赛、一小时速建、改造出生点 | 一块划分好的场地、评分标准、评委、作品保护 | 5 至 50 人 | 评分主观引发争议；作品被破坏；超时收不了尾 |
| PvP 竞技赛 | 1v1 决斗、团队战场、装备统一的擂台赛 | 竞技场、统一装备方案、裁判、观战位、复活点 | 8 至 40 人 | 装备与延迟不公平；组队刷名次；观战干扰比赛 |
| 跑酷竞速 | 竞速赛道、限时通关、团队接力 | 赛道、计时方式、检查点与掉落处理 | 5 至 30 人 | 赛道卡点被利用；掉线成绩作废；计时口径不清 |
| 寻宝 / 解谜 | 藏宝图、坐标谜题、限时寻物 | 线索设计、藏点清单、答案核对人 | 10 至 100 人 | 线索被提前泄露；有人直接翻地图文件 |
| Boss / 团本夜 | 集体挑战强敌、限时讨伐、掉落分配 | 战斗场地、难度与人数匹配、掉落规则 | 10 至 30 人 | 人数不够打不过；掉落分配吵架；服务器负载高 |
| 节日活动 | 万圣节、新年、服务器周年 | 装饰、限时玩法、节日奖励 | 全服 | 排期撞车；装饰改动影响正常玩法 |
| 社区目标 | 全服共建工程、累计收集目标 | 进度展示、贡献记录、阶段奖励 | 全服 | 少数人包办；进度卡在中途失去动力 |
| 新人欢迎会 | 集体迎新、老带新、新人专场 | 值班人员、讲解流程、迎新礼包 | 5 至 20 人 | 老玩家抢戏；新人插不上话；变成单向宣讲 |
| 剧情 / RP 活动 | 剧本演出、阵营对抗、世界事件 | 剧本、角色分配、场地与道具、主持人 | 10 至 30 人 | 剧本被打断；有人不按设定走；准备量极大 |

### 2.1 各类活动的设计要点

| 类型 | 设计上最该花心思的地方 | 最常见的翻车方式 |
| --- | --- | --- |
| 建筑比赛 | 评分标准要提前公开，并且拆成可打分的几条 | 评委凭喜好打分，参赛者当场不服 |
| PvP 竞技赛 | 装备、附魔、药水、延迟四项必须统一或明确声明 | 有人带着自己攒的装备来，比赛变成单方面碾压 |
| 跑酷竞速 | 计时起点与终点必须唯一且可复现 | 有人抄近路，而规则没写"必须经过检查点" |
| 寻宝 / 解谜 | 线索难度分层，保证前 10 分钟人人都有事做 | 第一个谜题卡住所有人，活动十分钟内散场 |
| Boss / 团本夜 | 人数与难度匹配，掉落规则提前说清 | 打完分配掉落时吵起来，比打不过更伤 |
| 节日活动 | 装饰与限时玩法都要能一键还原 | 节日结束后装饰留在主城，长期影响体验 |
| 社区目标 | 进度要可见，个人贡献要被记录 | 目标定得太大，三天后没人再提 |
| 新人欢迎会 | 让新人做主角，老玩家只做引导 | 变成管理员的单向宣讲会 |
| 剧情 / RP 活动 | 剧本留出玩家自由发挥的空间 | 玩家不按剧本走，主持人当场僵住 |

:::note 小服优先选"低准备成本"的类型
人手少的时候，跑酷竞速、寻宝、新人欢迎会的性价比远高于剧情活动和大型团本。**活动规模要匹配你能投入的准备时间**，而不是匹配你想象中的服务器规模。
:::

### 2.2 按服务器类型挑活动

同一个活动放在不同类型的服务器上，效果可能完全相反。选类型之前先看你自己的服务器定位（定位怎么写见 [宣传与引流](/tutorials/ops/promotion)）。

| 服务器类型 | 优先考虑的活动 | 尽量避免的活动 |
| --- | --- | --- |
| 原版生存服 | 建筑比赛、社区共建、寻宝、节日活动 | 高强度 PvP 竞技、会破坏世界状态的玩法 |
| 生电 / 技术服 | 技术挑战赛、机制解谜、全服共建工程 | 依赖大量实体与特效的混战型活动 |
| 小游戏服 | 排位赛、周赛、限时模式轮换 | 需要长期积累才能参与的活动 |
| RP / 角色扮演服 | 剧情事件、阵营对抗、世界事件 | 纯竞技类、与设定无关的娱乐活动 |
| 基岩版 / 跨端服 | 门槛低、不依赖客户端模组的活动 | 依赖特定客户端功能的玩法 |
| 模组服 | 与模组机制结合的活动 | 与模组机制冲突或需要额外客户端配置的活动 |

## 3. 怎么策划一场活动

### 3.1 定时间：先确认玩家在哪个时区

这是最容易出错、也最容易被忽略的一步。你的玩家可能分布在多个时区，或者集中在某个你并不居住的时区。

- **以玩家为主，不是以你为主**。如果核心玩家群体在另一个时区，活动时间就该按他们的作息定，哪怕对你来说是凌晨。
- **先问，再定**。在群里发一个简单的投票，比你自己猜有效得多。
- **写清时区**。公告里写"20:00"是不够的，要写成"北京时间 20:00"，并换算成主要玩家时区的时间。
- **避开工作日白天、考试周与节假日出行高峰**。周末晚上通常是最稳的选择。
- **给足提前量**。小型活动至少提前 2 至 3 天，大型活动提前 1 至 2 周。

### 3.2 提前、反复地公布

只发一次通知等于没发。玩家不会记住一条三天前的消息，但会记住反复出现的同一个时间点。

- **至少发三轮**：定档时发一次，活动前一两天发一次，开始前一两小时再提醒一次。
- **内容要一致**。三轮公告里的时间、地点、规则不能有任何变化；要改就明确说"改了哪里"。
- **多渠道覆盖**：游戏内公告、群公告、服务器列表页的简介、进服时的欢迎信息。宣传渠道的选择见 [宣传与引流](/tutorials/ops/promotion)。
- **把"怎么参加"写进公告**。玩家不该为了知道怎么报名而先去问人。

### 3.3 把规则写下来

口头规则在争议发生的那一刻就消失了。**写下来的规则胜过任何一次争论**。

- 写清"允许什么、禁止什么、由谁判定、平局怎么办、违规怎么处理"。
- 规则要在活动开始前公开，而不是等活动出问题再补充。
- 规则要短。超过一屏的规则没人会读，把最关键的三到五条放在最前面。
- 与服务器总规则冲突时以总规则为准，见 [社区规范](/rules)。

### 3.4 场地要提前建好、提前加载

**绝不要在活动开始时才动手建场地。** 现场搭建几乎必然延期，而且会把玩家的等待变成流失。

- **优先在独立世界或副本里准备场地**，其次才是"在离出生点很远的地方建"。前者的好处是：不影响主世界、不占用主世界的区块加载、活动结束后可以整体关掉。
- **如果只能在主世界建**，就选远离出生点和主要建筑区的位置，避免玩家传送过来时顺带加载大量区块。
- **提前加载好相关区块**。第一次加载区块是最贵的操作之一；在活动开始前把场地走一遍、让相关区域处于已加载状态，能显著减少开场时的卡顿。具体用什么方式预加载，取决于你的服务端与所用插件。
- **场地要在活动前完整演练一遍**。自己走一遍流程，比在脑子里推演十遍都管用。

### 3.5 分工到人

一个人办活动，等于没有应急预案。至少要明确下面几个角色，人手不足时可以由同一人兼任，但**必须有人负责**。

| 角色 | 负责什么 | 需要几个人 | 常见错误 |
| --- | --- | --- | --- |
| 主持人 | 宣布流程、控制节奏、开场与收尾 | 1 人 | 一边主持一边处理技术问题，两边都顾不上 |
| 裁判 | 判定胜负、处理违规与争议 | 1 至 2 人 | 裁判同时参赛，判罚失去公信力 |
| 建筑 / 场地 | 活动前完成场地与道具准备 | 1 人以上 | 活动当天还在改场地 |
| 技术支持 | 处理掉线、卡顿、传送失败、权限问题 | 1 人 | 没有人负责，出问题时全员沉默 |
| 记录 | 截图、录像、记录结果与贡献 | 1 人 | 活动办完了，一张能用的图都没有 |

:::tip 裁判不能参赛
这条看似苛刻，但它是**争议最少**的做法。如果人手实在不足，就让裁判回避与自己相关的场次，并且把判定过程公开。公信力一旦丢了，后面每一场活动都会被质疑。
:::

### 3.6 应急方案

活动当天一定会出问题。区别只在于你有没有准备。

| 可能出的问题 | 现场怎么办 | 提前要做什么 |
| --- | --- | --- |
| 服务器卡顿、TPS 下降 | 暂停或缩短流程，减少同时进行的实体与特效 | 提前压测，准备好精简版流程 |
| 关键玩家掉线 | 给出重连等待时间，超时按规则处理 | 规则里写明"掉线怎么办" |
| 人数远少于预期 | 改成分组小规模进行，或改成自由参与 | 准备一套"人少也能玩"的备选方案 |
| 人数远超预期 | 分批进行，或加开场地与场次 | 提前估算承载上限 |
| 有人作弊或破坏 | 立即隔离，按规则处理，事后留痕 | 规则写清判定与处罚 |
| 活动时间严重超时 | 砍掉后面的环节，先保证有收尾 | 给每个环节设时间上限 |
| 奖励发不出去 | 记录名单，活动后补发 | 提前确认发放方式与权限 |

### 3.7 活动方案模板

把下面这份模板填完，一场活动基本就准备好了。**填不出来的空，就是还没准备好的地方。**

```
活动名：______（一句话能说清是什么）
时间：______（日期 + 开始时间 + 预计时长 + 时区）
地点：______（世界 / 坐标 / 是否副本；玩家怎么去）
参与方式：______（怎么报名、能否现场参加、是否组队）
规则：______（允许与禁止、判定标准、平局怎么办）
奖励：______（名次与内容、发放方式与时间）
负责人：______（主持 / 裁判 / 建筑 / 技术支持 / 记录各是谁）
应急方案：______（卡顿、掉线、人数异常、作弊时怎么办）
```

## 4. 奖励与经济安全

### 4.1 奖励为什么会毁掉经济

奖励是活动最容易失控的部分，因为它直接往玩家的资产里注入资源。经济系统的脆弱点与常见事故见 [经济与玩法插件](/tutorials/ops/gameplay-plugins)。在活动里，需要特别警惕三种情况：

- **奖励规模失控**。一场活动发出去的量，如果超过玩家正常游玩几天的产出，市场会当场被砸穿。
- **奖励可以反复刷**。只要活动能重复参加并且每次都发同样的东西，它就从"活动"变成了"资源副本"。
- **奖励绑定了稀缺资源**。把经济体系里的硬通货当作活动奖品，等于自己给经济埋了一颗定时炸弹。

### 4.2 外观奖励与物质奖励

| 奖励类型 | 例子 | 对经济的影响 | 适合场景 |
| --- | --- | --- | --- |
| 外观类 | 称号、宠物、装饰性物品、建筑展示位 | 基本无影响，且不会被反复变现 | 几乎所有活动的首选 |
| 荣誉类 | 排行榜名次、公告表扬、专属身份标识 | 无影响 | 竞技类、比赛类活动 |
| 纪念类 | 活动专属标记物、纪念性建筑 | 影响很小，前提是不可交易或数量有限 | 节日活动、周年活动 |
| 便利类 | 一次性传送、临时增益、便利道具 | 取决于强度与是否可交易 | 谨慎使用，避免长期累积 |
| 物质类 | 货币、稀有材料、强力装备 | 直接影响经济，可能造成通胀 | 少量、一次性、且严格控制总量 |

:::warn 生存服不要发创造专属物品
**在生存服务器上发放只能通过创造模式获得的物品，几乎一定会出问题。** 这类物品无法在正常玩法中获得，一旦出现在玩家手里，就会变成不可复制的稀缺品，进而催生黑市、诈骗和"管理给熟人发东西"的指控。想让奖励看起来特别，用称号、装饰与展示位，而不是用破坏规则边界的物品。
:::

### 4.3 发放要留痕

- **提前确定奖励清单**，不要现场临时加码。
- **记录每一个获奖者与发放时间**，避免"我明明拿了第一却没收到"的争议。
- **发放渠道尽量统一**，减少"有人私下领到了"的猜疑。
- **公示奖励内容**。公开的奖励清单本身就是公平的一部分。

## 5. 公平与防滥用

技术层面的作弊与破坏防护见 [反作弊与防破坏](/tutorials/java/anticheat)；这一节讲的是活动规则层面的公平。

### 5.1 队伍必须平衡

组队活动的公平从分队那一刻就决定了。让最强的几个人分在同一队，比赛在第 30 秒就结束了，剩下的人只是在陪跑。

- **按能力而不是按关系分队**。让玩家自己选队友，几乎必然出现"高手抱团"。
- **公开分队依据**。哪怕只是"按报名顺序蛇形分配"，写出来就比暗箱操作可信。
- **准备让分队机制**。例如弱队获得额外资源、限制强队的装备上限。
- **允许观战**。被淘汰的人如果只能干等，下一场就不会报名了。

### 5.2 小号与账号共享

这是活动里最常见、也最难查的滥用方式。它同时破坏排行榜与奖励发放。

- **规则里明确禁止**多账号参赛与账号共享，并写清判定方式与后果。
- **按玩家而不是按账号统计**。同一个人的多个账号，应当被视为同一个人。
- **留意异常信号**：同 IP、同时间登录、账号间物品转移、只在活动期间出现的账号。
- **处罚要有证据**。怀疑不等于证据，处罚必须留痕，否则会伤到正常玩家。

### 5.3 临时加入的玩家

活动开始后才进服的人，处理不好会两头得罪。

- **规则提前写清**：能不能中途加入、加入后是否计入成绩、能不能拿奖励。
- **给出统一口径**。最常见的做法是允许观战与自由参与，但成绩从下一场开始算。
- **不要现场临时改规则**。为一个人改规则，就是对所有已参加的人不公平。

### 5.4 当场争议怎么处理

争议一定会发生，关键是有没有预设的处理路径。

- **先看规则，再看现场**。有规则就按规则判，不要临场发挥。
- **判定要公开说明理由**，哪怕只是一句话。
- **不要在情绪里做决定**。有人骂你，和他是否违规是两件事。
- **争议升级就暂停**。宁可暂停五分钟，也不要在全场注视下争吵。
- **事后统一复盘**。规则里没写清楚的地方，下一场补上；这比当场争输赢更有价值。

## 6. 技术准备

### 6.1 场地

- **独立世界或副本优先**，其次才是主世界偏远位置。理由见 3.4。
- **活动前完整走一遍流程**，包括传送、复活、计时、奖励发放的每一步。
- **活动结束后清理**。临时场地、临时权限、临时道具都要能一键还原，否则它们会一直留在服务器里。
- **不要在活动前临时改主世界**。改动的风险会在活动当天集中爆发。

### 6.2 小游戏系统与独立小游戏服

- **小规模活动**通常用一类"小游戏 / 竞技场"插件就够：它们负责场地隔离、队伍、计分与复活。
- **大型或高频活动**更适合放在独立的 minigame 服务器上，通过跨服端把玩家送过去，见 [跨服端](/tutorials/java/proxy)。好处是活动玩法不会污染主世界，负载也分开。
- **跨服活动要多测一遍**。跨服传送、权限继承、聊天频道、奖励发放跨服之后都可能出问题，这些都要在活动前验证。
- **具体的插件名称、命令与配置项，请以各插件官方文档为准。** 本文不列出它们，因为它们随版本变化，而且照抄配置往往比不写更危险。

### 6.3 活动前后都做备份

活动是"世界状态变化最集中"的时段：有人会破坏场地、有人会拿走奖励、有人会掉线在奇怪的位置。备份的做法与验证方式见 [备份与恢复](/tutorials/java/backup)。

- **活动前备份**：出事可以直接回到活动前的状态。
- **活动后备份**：把活动成果（建筑、记录、奖励发放）固定下来。
- **备份要验证可恢复**。没有验证过的备份，不算备份。

### 6.4 卡顿风险

:::warn 大活动是服务器最容易卡的时候
**一场人数多、实体多、特效多的活动，是服务器全年最可能卡顿甚至崩溃的时刻。** 大量玩家集中在同一区域、同时生成大量实体与粒子、同时触发大量插件逻辑，负载会远超平时的峰值。

所以：**提前测**。用接近真实的人数与流程做一次彩排，观察 TPS 与 MSPT 的变化；如果彩排就掉帧，正式活动只会更糟。分析手段见 [用 spark 分析服务器性能](/tutorials/ops/spark)。同时准备一套"精简版流程"，在卡顿时能立刻切过去。
:::

活动前的技术检查可以按这张表逐项过一遍：

| 检查项 | 为什么重要 |
| --- | --- |
| 场地区块已提前加载 | 避免开场时集中加载区块造成卡顿 |
| 玩家传送与复活点已测试 | 传送失败会让活动直接中断 |
| 权限与临时身份已配置 | 主持人与裁判需要相应权限 |
| 奖励发放流程已演练 | 发不出去比不发更难看 |
| 观战与旁听通道已准备 | 让被淘汰的人也有事做 |
| 活动前后备份已安排 | 出事后能回到已知状态 |
| 备用流程已就绪 | 卡顿或人数异常时能立刻切换 |
| 记录人员已就位 | 事后需要截图、结果与反馈 |

## 7. 活动之后

活动结束的那一刻，工作才完成了一半。**没有收尾的活动，等于没办。**

### 7.1 公布结果与截图

- 公布名次、获奖名单与判定依据。
- 发布截图或录像。这是唯一能证明"活动真的发生过、真的有人来"的东西，也是下一场活动最好的宣传素材。
- 把结果固定在一个长期可访问的位置，而不是让它淹没在聊天记录里。

### 7.2 感谢帮忙的人

- 公开感谢主持、裁判、建筑与技术支持。**愿意帮忙的人是你最稀缺的资源**，他们需要被看见。
- 记录下谁做了什么。下次办活动时，这份名单就是你的班底。
- 对参与者也要有回应，哪怕只是一句总结。

### 7.3 收集反馈

- **问具体的问题**，不要只问"好玩吗"。问"哪个环节最无聊""哪里卡住了""下次想玩什么"。
- **给一个固定的反馈入口**，而不是让意见散落在各个群。
- **区分"意见"和"情绪"**。有人骂人，不代表他的意见没有价值，但也不代表你必须照做。

### 7.4 复盘记录

每次活动后写一份简短记录，内容包括：

- 实际参与人数与预期差多少；
- 哪个环节超时、哪个环节没人玩；
- 出了哪些技术问题，怎么解决的；
- 争议是怎么判的，规则哪里没写清；
- 下次要改的三件事。

这份记录不需要长，但**必须写下来**。三个月后你不会记得当时为什么卡了五分钟。

### 7.5 建立固定节奏

零散的活动靠热情，持续的活动靠节奏。让玩家知道"什么时候一定有事发生"，比每次临时通知有效得多。

| 节奏 | 规模 | 目的 | 注意 |
| --- | --- | --- | --- |
| 每周一次小活动 | 30 至 60 分钟，低准备成本 | 保持日常活跃，给新人一个入口 | 类型要轮换，不要每周都是跑酷 |
| 每月一次大活动 | 2 小时以上，需要提前准备 | 制造话题，拉回离开的玩家 | 提前 1 至 2 周宣传 |
| 节日 / 周年活动 | 跟随现实节日 | 借势吸引流量与回归 | 排期避开其他大活动 |
| 长期社区目标 | 持续数周 | 给全服一个共同目标 | 进度必须可见 |

:::tip 节奏比创意更重要
玩家记不住你办了哪一场活动，但会记住"这个服每周六晚上都有活动"。**可预期本身就是吸引力。** 宁可每周办一场简单的小活动，也不要三个月办一场盛大的、然后消失。
:::

## 8. 一页活动清单

### 8.1 活动前

- [ ] 活动类型已确定，并且与可投入的准备时间匹配
- [ ] 时间已按主要玩家时区确定，并写明时区
- [ ] 已至少提前 2 至 3 天（大型活动 1 至 2 周）开始宣传
- [ ] 宣传至少发了三轮，内容前后一致
- [ ] 规则已成文、已公开，包含判定标准与平局处理
- [ ] 场地已在独立世界或副本中建好，并提前加载过
- [ ] 完整流程已彩排一遍，包括传送、计时与奖励发放
- [ ] 主持人、裁判、建筑、技术支持、记录人员已确定到人
- [ ] 裁判不参赛（或已回避相关场次）
- [ ] 奖励清单已确定，规模已评估过对经济的影响
- [ ] 生存服未发放创造专属物品
- [ ] 分队方式已确定并公开，机制上尽量平衡
- [ ] 多账号与账号共享的判定方式已写进规则
- [ ] 中途加入、掉线、超时的处理方式已写进规则
- [ ] 应急方案已准备好：卡顿、掉线、人数异常、作弊
- [ ] 活动前备份已完成，并且验证过可恢复
- [ ] 活动后备份已安排
- [ ] 关键玩家与观战者的通道已准备

### 8.2 活动中

- [ ] 开场先讲清流程、规则与时间上限
- [ ] 每个环节控制时长，超时就进入下一环节
- [ ] 争议按规则判定，并公开说明理由
- [ ] 卡顿时立即切换到精简流程
- [ ] 全程记录：截图、录像、名次、获奖名单

### 8.3 活动后

- [ ] 结果与获奖名单已公布，并附判定依据
- [ ] 截图或录像已发布
- [ ] 帮忙的人已公开感谢
- [ ] 奖励已按清单发放，并留有记录
- [ ] 反馈已收集，并区分意见与情绪
- [ ] 复盘记录已写下，包括下次要改的三件事
- [ ] 临时场地、临时权限、临时道具已清理
- [ ] 下一场活动的时间已公布
