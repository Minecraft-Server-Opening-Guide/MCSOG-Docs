迁移（migration）指的是**把整套服务端从一个环境搬到另一个环境**：换更好的硬件、换服务商、搬出网络质量差的机房，或者单纯为了省钱。它比"从零装一台新服"危险得多——装新服失败只是暂时没有服，**迁移失败是原有服务已经停了、新服务又起不来**。

这一篇讲迁移的完整流程与检查清单。要搬哪些文件、哪些文件千万别碰，见 [服务端结构](/tutorials/java/structure)；备份范围与恢复演练见 [备份与恢复](/tutorials/java/backup) 与 [异地备份](/tutorials/ops/offsite-backup)。

## 1. 什么时候该迁移

| 触发原因 | 典型信号 | 迁移时要特别小心的地方 |
| --- | --- | --- |
| 硬件升级 | TPS 长期偏低、内存吃紧、磁盘 IO 打满，而优化已经没有空间 | 新机器的 CPU 单核性能比核数更重要；先确认瓶颈真在硬件 |
| 换服务商 | 工单没人回、超售严重、跑路传闻、计费不透明 | 数据出境与合规、出口流量费、退租前先确认新环境可用 |
| 搬出网络差的区域 | 玩家延迟高、绕路严重、丢包、被 DDoS 时没有防护 | 目标区域的线路质量要**实测**，不要只看商家宣传 |
| 降低成本 | 账单压力大，或长期闲置的配置过高 | 便宜的机器往往共享 CPU、磁盘更慢，先压测再搬 |
| 架构调整 | 单机改群组服、加面板、加数据库 | 这已经不是"迁移"，而是"重建 + 数据搬迁"，要另做方案 |

:::note 能就地解决就别迁移
迁移的每一步都有停机与数据风险。**如果只是内存不够，加内存比迁移便宜；如果只是延迟高，先排查是不是路由或代理配置的问题。** 把迁移留给"确实解决不了"的场景。
:::

## 2. 迁移前检查清单

迁移最容易翻车的环节不是 `rsync`，而是**"原来这台机器上到底跑着什么，我自己都没数"**。先把清单写出来，再动手。

| 检查项 | 怎么查 | 通过标准 |
| --- | --- | --- |
| 这台机器上跑了哪些服务 | `systemctl list-units --type=service --state=running`、`ss -tlnp`、`docker ps`、`crontab -l` | 每一项都能说出用途，且知道要不要一起搬 |
| 游戏与核心版本 | 服务端启动日志、`/version`、核心文件名 | 记录到"游戏版本 + 核心名 + 核心构建号" |
| 插件 / 模组版本清单 | `plugins/`、`mods/` 目录列表 | 有清单文件（版本号可复现），不只是目录本身 |
| Java 版本 | `java -version` | 新旧机器一致；**升级 Java 是另一件事，别和迁移一起做** |
| 操作系统与内核 | `cat /etc/os-release`、`uname -a` | 知道差异（发行版、glibc、文件系统） |
| DNS 记录与 TTL | `dig +noall +answer example.com`、`dig _minecraft._tcp.example.com SRV` | 记录类型（A / AAAA / SRV）与当前 TTL 都有记录 |
| 谁有访问权 | SSH 公钥、面板账号、服务商账号、协管名单 | 迁移后**逐条核对**，该删的删 |
| 备份是否可恢复 | 真做一次恢复演练 | 不是"有备份文件"，而是"**恢复过、能起来**" |
| 外部依赖 | 数据库、对象存储、API Key、Webhook、监控 | 新机器上能连通，凭据有效 |

:::warn 没有验证过备份的迁移就是赌博
`rsync --delete` 写错路径、磁盘满、权限不对、归档截断——任何一种都能让你在停服之后才发现"没有可用的副本"。**动手前必须有一份离线、已验证可恢复的备份**，并且在维护窗口内不要删除它。备份做了但没验证过，等于没有备份。
:::

## 3. 什么必须搬

下表的每一行都是真实事故里漏过的东西。**漏掉世界是灾难，漏掉启动方式则是"数据都在但服务起不来"。**

| 项目 | 位置（以 `/opt/mcserver` 为例） | 漏掉的后果 |
| --- | --- | --- |
| 世界存档 | `world/`、`world_nether/`、`world_the_end/`（名字以 `server.properties` 的 `level-name` 为准） | **最严重**：玩家建筑、背包、进度全丢 |
| 插件 / 模组本体 | `plugins/`、`mods/` | 进服后功能缺失，或玩家客户端因模组不匹配进不来 |
| 插件 / 模组配置 | `plugins/<插件名>/`、`config/` | 权限、经济、领地、传送点、抽奖池全部回到默认值 |
| 核心配置 | `server.properties` | 端口、难度、正版验证、视距、白名单开关全变默认 |
| 核心自身配置 | `bukkit.yml`、`spigot.yml`、`paper-*.yml`、`purpur.yml` | 优化参数、世界默认值丢失，性能可能明显变化 |
| 名单文件 | `ops.json`、`whitelist.json`、`banned-players.json`、`banned-ips.json` | 管理员权限丢失，或封禁失效、白名单形同虚设 |
| 玩家名缓存 | `usercache.json` | 通常可重建，但离线模式的 UUID 与显示名映射会短暂错乱 |
| 启动脚本 | `start.sh`、`启动.bat`、Java 参数 | **最常见漏项**：服务起不来，或参数不对导致内存/性能异常 |
| systemd unit | `/etc/systemd/system/minecraft.service` | 开机不自启、崩溃不重启；`WorkingDirectory` 写错还会新建一个空世界 |
| 定时任务 | `crontab -l`、`/etc/cron.d/`、systemd timer | 备份、重启、清理任务全部消失，且**很久之后才会发现** |
| 防火墙规则 | `ufw status`、`firewall-cmd --list-all`、云安全组 | 端口不通，玩家连不上；或旧规则缺失导致意外暴露 |
| TLS 证书 | `/etc/letsencrypt/`、`/etc/ssl/` | 面板、地图、资源包等 HTTPS 服务中断或证书告警 |
| MCDR 数据 | MCDR 运行目录下的 `config.yml`、`permission.yml`、`plugins/` | 机器人权限、指令别名、插件状态丢失（具体文件名与结构以 MCDR 官方文档为准） |
| 面板数据 | 面板自身的配置与实例定义目录 | 服务端文件还在，但面板里"什么都没有了"；详见 [服务器面板](/tutorials/ops/panels) |
| 凭据文件 | `.env`、`rcon.password`、数据库口令、云存储密钥 | 服务起不来，或起来后连不上依赖 |
| 反向代理配置 | Nginx / Caddy 站点文件与证书路径 | 域名访问 502，且容易误判为"服务端没起来" |
| 监控与告警 | 探针、Agent、告警规则 | 出问题时**没人收到通知**，这是最危险的"静默失败" |

### 不需要搬的东西

| 项目 | 原因 |
| --- | --- |
| `logs/`、`crash-reports/` | 体积大；排查旧问题时再单独取用 |
| `cache/`、`libraries/`、`versions/` | 启动时自动重建 |
| `world/session.lock` | 运行期锁文件，目标端应删除，服务端会自己重建 |
| 旧机器上的临时归档、`*.tar.gz` | 容易把几百 GB 的临时文件一起同步过去 |

## 4. 迁移方式

### 4.1 rsync over SSH（首选）

`rsync` 只传变化的部分、保留权限与时间戳、走 SSH 加密通道，是迁移最常用的方式。

```bash
# 第一次：服务端还在运行时做"预同步"，把绝大部分数据先搬过去
rsync -aHAX --numeric-ids --delete --info=progress2 \
  --exclude='logs/' \
  --exclude='crash-reports/' \
  --exclude='cache/' \
  --exclude='libraries/' \
  --exclude='versions/' \
  --exclude='session.lock' \
  /opt/mcserver/ \
  mcserver@203.0.113.20:/opt/mcserver/
```

| 选项 | 作用 |
| --- | --- |
| `-a` | 归档模式（等价 `-rlptgoD`）：递归并保留符号链接、权限、时间、属组、设备文件 |
| `-H` | 保留硬链接 |
| `-A` | 保留 ACL |
| `-X` | 保留扩展属性（xattr） |
| `--numeric-ids` | 按数字 UID/GID 映射，**跨机器必须加**，否则属主会错乱 |
| `--delete` | 让目标端与源端一致（**双刃剑**，源端误删会被同步过去） |
| `--info=progress2` | 显示整体进度（rsync 3.1 及以上） |

**任何带 `--delete` 的命令，第一次都要先加 `-n`（`--dry-run`）与 `-i`（逐项列出变化）跑一遍**，确认它不会删掉不该删的东西：

```bash
rsync -aHAX --numeric-ids --delete -n -i \
  --exclude='logs/' --exclude='cache/' \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

:::warn 源路径末尾的斜杠不能随手写
`/opt/mcserver/`（带斜杠）表示"同步这个目录里的内容"；`/opt/mcserver`（不带斜杠）表示"在目标端创建 `mcserver` 这个目录再放进去"。**配合 `--delete` 写错，可能把目标端的整个目录结构搞乱。**
:::

### 4.2 tar + scp（小数据量、无 rsync 时）

没有 `rsync` 或数据量很小的时候，可以用管道直接打包传输，不落中间文件：

```bash
# 在旧机器上执行：打包并通过 SSH 解到新机器
tar -C /opt/mcserver -czf - \
  --exclude='logs' --exclude='crash-reports' --exclude='cache' \
  --exclude='libraries' --exclude='versions' --exclude='session.lock' \
  . | ssh mcserver@203.0.113.20 'mkdir -p /opt/mcserver && tar -C /opt/mcserver -xzf -'
```

也可以先落地再传：

```bash
tar -czf /tmp/mcserver-2026-10-04.tar.gz -C /opt/mcserver .
scp /tmp/mcserver-2026-10-04.tar.gz mcserver@203.0.113.20:/tmp/
```

缺点是**每次全量、没有增量、中断要重来**，几百 GB 的存档不适合。

### 4.3 服务商级快照 / 卷复制（最快）

同一家服务商内部迁移时，通常可以给系统盘或数据盘**打快照，再把快照挂到新实例上**，或者直接把云盘从旧实例卸载、挂载到新实例。这比在网络上复制文件快几个数量级。

必须注意：

- **快照的"一致性"取决于你打快照时服务端在不在写盘。** 要做可靠快照，先停服（或至少 `save-all` + `save-off`），打完再 `save-on`。
- 卷挂载路径、设备名、文件系统 UUID 可能变化，`/etc/fstab` 要用 UUID 或重新配置，否则新实例起不来。
- 跨服务商、跨区域通常**不能**直接挂盘，只能走网络复制。
- 快照里包含旧机器的 SSH 主机密钥、旧 IP 的配置、面板凭据——**迁移后要轮换凭据**。

### 4.4 为什么必须同步两次

| 阶段 | 服务端状态 | 目的 |
| --- | --- | --- |
| 第一次同步 | **运行中** | 把几十上百 GB 的存量数据先搬过去，把维护窗口从"几小时"压到"几分钟" |
| 第二次同步 | **已停服** | 只传变化的部分，让目标端与停服瞬间的数据一致 |

第一次同步期间服务端仍在写盘，所以那份副本**本身不一致**——它的价值只在于"大部分文件已经就位"，正确性完全依赖第二次同步。因此：

- 第二次同步**必须在停服之后**，并且停服后不要再启动旧机器（否则又要重新同步）。
- `rsync` 默认按"大小 + 修改时间"判断是否需要重传。要更严格地按内容比对，第二次可以加 `--checksum`（`-c`）：**更慢，但不会漏掉"大小相同、时间戳被保留、内容却不同"的文件。**
- 第二次同步完成后，**再做一次校验（见下一节）**，不要凭"命令没报错"就开服。

## 5. 维护窗口：逐步操作

提前公告维护时间（并说明预计时长与补偿方案），然后按下面的顺序执行。**每一步都确认结果再进入下一步。**

1. **冻结变更**：通知协管不要再改配置、不要装插件；确认没有正在跑的备份/清理任务会与迁移冲突。

2. **再确认一次备份可用**：确认离线备份存在、校验通过、且**不在**你即将删除或覆盖的路径上。

3. **降低 DNS TTL**：如果还没降，现在降到 60 - 300 秒（生效需要等旧 TTL 过期，所以这一步其实要**提前 24 - 48 小时**做，见第 6 节）。

4. **停服**：

```bash
sudo systemctl stop minecraft
pgrep -a java          # 必须没有输出，确认进程真的退出了
```

5. **最终同步**（第 4.1 节的命令去掉 `--exclude` 里不该排的东西，并加上 `-c`）：

```bash
rsync -aHAX --numeric-ids --delete --checksum --info=progress2 \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

6. **校验**：两端各生成一份清单再比对。路径必须是**相对路径**，否则文件名对不上。

```bash
# 旧机器
cd /opt/mcserver && find . -type f -print0 | sort -z | xargs -0 sha256sum > /tmp/old.sha256

# 新机器（同样命令，输出到 /tmp/new.sha256），然后：
diff /tmp/old.sha256 /tmp/new.sha256 && echo "校验通过"
```

Windows 上可以用 `Get-FileHash -Algorithm SHA256` 逐文件比对；数据量小时也可以只比对大小与文件数：

```powershell
Get-ChildItem -Recurse -File C:\mcserver | Measure-Object -Property Length -Sum
```

7. **在新机器上清理运行期残留**：

```bash
rm -f /opt/mcserver/world/session.lock
```

8. **确认新机器的环境**：Java 版本与旧机一致（`java -version`）、目录属主正确、`server.properties` 里的端口没和别的服务冲突。

9. **安装并启动托管服务**：

```bash
sudo cp minecraft.service /etc/systemd/system/minecraft.service
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
journalctl -u minecraft -n 50 --no-pager
```

10. **用同一个客户端实测**：先用新 IP 直连（见第 6 节），进服后检查关键建筑、容器内容、背包、权限、插件命令是否正常。

11. **切换 DNS**：确认新服正常后，把记录指向新 IP。

12. **保留旧机器一段时间**：**不要立刻退租或重装**，它是你的回滚目标（见第 9 节）。

## 6. DNS 与切换

### TTL 要提前降

DNS 记录有缓存时间（TTL）。如果 TTL 是 24 小时，你切换记录后**最长 24 小时内仍会有玩家被解析到旧 IP**。

```bash
# 查看当前解析与 TTL
dig +noall +answer mc.example.com
dig +noall +answer mc.example.com AAAA
dig +noall +answer _minecraft._tcp.mc.example.com SRV
```

**流程是**：迁移前 24 - 48 小时把 TTL 降到 60 - 300 秒 -> 等旧 TTL 过期 -> 迁移 -> 切换记录 -> 确认稳定后再把 TTL 调回较大值（减少解析压力）。

### 切换前怎么测试新服

**不要在没验证新服的情况下先改 DNS。** 两种安全的测试方式：

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| hosts 文件 | 在本机 hosts 里把域名指向新 IP | 只影响自己，适合服主与协管先验一遍 |
| 直连新 IP | 客户端直接填 `203.0.113.20:25565` | 所有人都能用，**不依赖 DNS** |

```text
# Windows: C:\Windows\System32\drivers\etc\hosts
# Linux / macOS: /etc/hosts
203.0.113.20  mc.example.com
```

:::tip 一定要"用同一个客户端"测
换一台电脑、换一个网络、换一个游戏版本去测，测出来的都不是玩家的真实体验。**用平时玩的那个客户端、在同一条网络上连一次**，才算验证。
:::

### SRV 记录别忘了

很多服使用 SRV 记录让玩家只填域名（不写端口）。迁移时**要同时改 SRV 指向的目标**，否则玩家仍然被引导到旧机器：

```text
_minecraft._tcp.mc.example.com. 300 IN SRV 0 5 25565 mc.example.com.
```

### 旧机器要留作回滚目标

切换后**至少保留一个完整维护窗口的时间**（常见做法是 24 - 72 小时，视你的玩家规模与可接受的停机时间而定）：

- 保持旧机器**可以随时启动**（配置、数据、Java 环境都别动）。
- 但**不要**让新旧两台同时对外服务同一个域名——那会导致玩家数据分裂到两个世界，后面无法合并。
- 如果旧机器仍会被 DNS 解析到（TTL 还没过期），可以考虑把旧机器上的服务端**保持停止**，只在需要回滚时启动。

## 7. IP 变了，连带影响有哪些

IP 一变，所有"以 IP 为准"的东西都会失效。**这一节漏掉，症状往往是"玩家能进服，但某个功能莫名其妙不工作"。**

| 受影响的东西 | 症状 | 处理 |
| --- | --- | --- |
| 其他服务的白名单 | 数据库、对象存储、第三方 API 拒绝连接 | 把新 IP 加入允许列表，移除旧 IP |
| RCON / 面板的 IP 允许列表 | 面板显示实例离线、RCON 连不上 | 面板与守护进程的 allowlist 都要更新（配置项以各面板官方文档为准） |
| 防火墙 / 云安全组 | 端口不通，或反向代理连不上后端 | 新机器加规则，**旧机器记得收口**，避免留下暴露面 |
| TLS 证书与反向代理 | HTTPS 报错、证书域名不符 | 证书随机器搬或重新签发；代理的 upstream 改成新 IP |
| Geyser / Floodgate 与群组服 | 基岩版玩家进不来，或玩家 IP 全部变成代理 IP | 转发配置要一起搬；详见 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup) 与 [跨服端](/tutorials/java/proxy) |
| IP 封禁名单 | `banned-ips.json` 里的条目可能指向旧环境；或者因为转发配置变了，**所有玩家都显示为代理 IP，一禁就是全服** | 迁移后检查转发是否生效，再决定是否清理 IP 封禁 |
| 监控与告警 | 探针还盯着旧 IP，新服挂了没人知道 | 更新探针目标，并**故意触发一次告警**确认链路通 |
| 备份任务 | 备份还在从旧机器取数据，或新机器的备份没配 | 见 [备份与恢复](/tutorials/java/backup) 与 [异地备份](/tutorials/ops/offsite-backup) |
| 白名单里的基岩版玩家 | 基岩版玩家的身份与 XUID 绑定，通常**不受 IP 变化影响** | 一般无需改动；但转发/权限插件若依赖 IP，仍需复核 |

:::note 关于 IP 封禁
IP 封禁本来就不适合长期使用（家宽 IP 会变、机房 IP 会被复用）。迁移前后如果发现封禁列表里有大量 IP 条目，**先确认它们还有效再决定是否保留**，不要盲目照搬。
:::

## 8. 迁移后验证清单

| 验证项 | 怎么验 | 通过标准 |
| --- | --- | --- |
| 玩家能进服 | 用真实客户端（含基岩版，如果开了跨平台）各进一次 | 能进、能聊天、能正常移动与交互 |
| TPS / MSPT 正常 | `/tps`、`/spark tps` 或核心自带命令 | 与旧机器同一量级，没有持续性掉刻 |
| 插件 / 模组全部加载 | 启动日志里搜 `Enabling`、`Loaded`、报错关键字 | 没有 `Could not load`、没有版本不兼容 |
| 配置生效 | 抽查权限、经济、领地、传送点 | 与迁移前一致 |
| 名单正确 | `/whitelist list`、`/op` 相关命令或直接看名单文件 | 管理员与白名单与旧服一致 |
| 备份在新机器上跑 | 手动执行一次备份脚本 | 归档生成、大小合理、**并且真的能解出来** |
| 监控已更新 | 看监控面板 | 新 IP 有心跳，旧 IP 的告警已关闭 |
| 定时任务 | `crontab -l`、`systemctl list-timers` | 备份、重启、清理任务都在，时间正确 |
| 性能与磁盘 | `df -h`、`iostat`、内存占用 | 磁盘余量充足，没有明显的 IO 瓶颈 |
| 旧机器下线 | 见下 | **只有在回滚窗口结束后**才退租或重装 |

## 9. 回滚方案

回滚不是"再搬回去"，而是"**回到一个已知可用的状态**"。所以回滚方案必须在迁移**之前**写好：

1. **定义触发条件**：什么情况下回滚？（例如：新服 2 小时内无法稳定启动、存档校验失败、关键插件无法工作、TPS 只有旧机一半且无法定位原因。）
2. **明确回滚动作**：把 DNS 指回旧 IP -> 在旧机器上启动服务 -> 公告说明 -> 事后分析。
3. **保留回滚目标**：旧机器的服务端目录、Java 环境、systemd unit、防火墙规则**原样保留**，直到回滚窗口结束。
4. **准备数据取舍规则**：如果新服已经开了一段时间、玩家已经在上面玩过，**旧世界的进度是落后的**。回滚意味着这段时间的进度丢失，或者需要人工把新世界的存档搬回来（此时"新世界"才是最新的数据）。**这个决定必须在回滚前明确，不能边回滚边想。**
5. **回滚也要校验**：从旧机器启动前，确认它的数据与停机时一致（没被备份脚本改过、没被误删）。

:::warn 最坏的情况是"两边都在跑"
如果新旧两台服务器同时对外服务（例如 DNS 缓存导致一部分玩家连旧服、一部分连新服），**玩家数据会分裂到两个世界**。这种分裂通常无法自动合并，只能接受其中一份数据丢失。**切换前把旧服停掉，是避免这个事故最简单的方法。**
:::

## 10. 小结

- **先盘点，再动手**：迁移失败多半不是技术问题，而是"忘了自己还跑着什么"。
- **备份必须验证过**：没验证过的备份不是备份，是心理安慰。
- **同步两次**：一次预热（运行中），一次定稿（停服后），中间不要重启旧服。
- **先测再切**：hosts 文件或直连 IP 验证新服，然后再改 DNS。
- **TTL 提前降**：这是唯一"必须提前做"的步骤，临时降 TTL 来不及。
- **留好回滚目标**：旧机器不是垃圾，它是你的退路。
