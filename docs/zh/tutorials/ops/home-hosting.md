很多人开服的第一台"服务器"，就是自己桌上那台电脑。它便宜、性能好、你完全掌控——但它**不是为 7x24 小时运行设计的**。这一篇讲清楚：家用电脑到底适不适合开服，以及如果你决定这么做，**长期怎么维护才不出事**。

如果你还没决定路线，先看 [部署到可访问环境](/tutorials/java/deploy) 里的三条路线对比。

## 1. 家用电脑到底适不适合开服

先把"能跑"和"适合长期跑"分开。家用机跑 MC 服务端**性能上通常绰绰有余**（现代桌面 CPU 的单核性能普遍强于同价位云服务器），真正的短板在**可靠性、网络和运维成本**上。

| 维度 | 家用电脑 | VPS / 云服务器 |
| --- | --- | --- |
| 一次性成本 | 已有机器则近乎为零 | 无，但按月付费 |
| 持续成本 | **电费**（见下），夏天还有空调费 | 月租，配置越好越贵 |
| 单核性能 | 通常更强，同价位优势明显 | 同价位偏弱 |
| 公网 IP | **多数家庭宽带没有公网 IPv4** | 一般自带 |
| 电力 | 自家停电即掉线，需 UPS | 机房有 UPS 与发电机 |
| 网络 | 家宽上行小、可能被运营商限速 | 机房带宽大且对称 |
| 噪音/发热 | 在自己房间里 | 在机房 |
| 被攻击 | 打的是你家 IP，影响全家网络 | 打的是机房，可加高防 |
| 数据安全 | 硬盘坏了你自己负责 | 通常有快照，但**服务商会跑路** |

### 谁应该直接用 VPS

经常不在家（家里出事无法远程处理）、玩家已超过十几人（上行带宽先撑不住）、不想被 DDoS 牵连全家网络、对噪音发热敏感（宿舍/合租/卧室），或者**数据重要性高于省钱**的人，直接买 VPS 更省心。

### 关于"24/7"：到底是什么在打断它

家用机做不到 24 小时在线，通常不是硬件不行，而是这些：

| 中断来源 | 说明 | 缓解 |
| --- | --- | --- |
| 系统睡眠/休眠 | 默认电源计划会在空闲后睡眠，**服务端直接断线** | 关掉睡眠（见第 2 节） |
| 停电 | 最常见的掉线原因，且**可能损坏存档** | UPS + BIOS 来电自启 |
| 系统自动更新重启 | Windows 默认会在夜里自动重启 | 设定活动时间 / 手动安排重启窗口 |
| 路由器重启或拨号掉线 | 家宽常见 | 定期检查；DDNS 应对 IP 变化 |
| 过热降频或保护性关机 | 灰尘堵塞、风扇停转 | 清灰、监控温度 |
| 你自己手滑 | 踢到机箱、拔错插头 | 物理安全（见第 8 节） |

:::warn 一次意外关机可能比你想的贵
服务端正在写区块时断电，最坏情况是**存档损坏**，只能回档到上一次可用备份。所以第 2 节和 [备份与恢复](/tutorials/java/backup) 是配套的：**供电保护与备份缺一不可**。
:::

### 电费：先算一笔账再决定

电费 = 功率（kW）x 时间（h）x 电价（元/kWh）。用功率计（或插座式功耗计）实测最准，下面是**量级估算**，实际差异很大：

| 场景 | 整机功耗（量级） | 每月（30 天） |
| --- | --- | --- |
| 低功耗小主机 / 笔记本 | 10 - 25 W | 7 - 18 kWh |
| 桌面机待机/轻载 | 40 - 80 W | 29 - 58 kWh |
| 桌面机持续满载（高频 CPU + 独显空转） | 120 - 250 W | 86 - 180 kWh |

把上面的 kWh 乘以你当地电价就是月成本。**独立显卡待机也会耗电**（常见 5 - 20 W，具体看型号），纯服务用途可以考虑核显或拆掉独显。空调在夏天会把这份热量**再放大一到两倍**的制冷电费。

## 2. 供电稳定性

### 为什么"存档写到一半断电"很危险

MC 的区块是**分文件写入**的，写入过程中断电可能留下**半写状态的文件**。恢复时轻则丢几个区块，重则存档无法加载。即使有 `save-all`，也无法保证断电瞬间磁盘上的所有文件都处于一致状态。**这就是 UPS 与备份存在的理由**——不是为了"不断线"，而是为了**让服务端有机会安全停机**。

### UPS：家用该买多大

UPS 的目标不是让你停电继续玩几个小时，而是**撑过短时闪断 + 给服务端争取安全关机的几分钟**。

估算方法：

1. 测出整机功耗 `P`（瓦）。
2. 决定需要的后备时间 `T`（分钟），家用 **5 - 15 分钟**通常足够。
3. 需要的容量（Wh）≈ `P x T / 60 / 0.6`（0.6 是逆变效率与电池老化的保守系数）。
4. 换算成 VA：UPS 标称 VA 与 W 的关系取决于功率因数，家用 UPS 常见 PF 约 0.5 - 0.6，**以产品铭牌标注的 W 为准**。

例子：整机 80 W，希望撑 10 分钟，则约需 `80 x 10 / 60 / 0.6 ≈ 22 Wh` 的有效容量，选一台标称 **500 - 650 VA / 300 W 左右**的后备式 UPS 就有余量。**具体型号的容量与接口以厂商规格书为准**，不要按经验值下单。

| UPS 类型 | 特点 | 适合 |
| --- | --- | --- |
| 后备式（Standby） | 便宜，切换时有几毫秒中断 | 家用小主机，电源素质好 |
| 在线互动式（Line-Interactive） | 带 AVR 稳压，切换更快 | 电压不稳的地区，推荐 |
| 在线式（Online / Double-Conversion） | 全程逆变供电，输出最干净，最贵、发热最大 | 对供电极敏感的设备 |

### 为什么"纯正弦波"重要

主动式 PFC（Active PFC）的电源**对输入波形敏感**。方波/阶梯波（模拟正弦）输出的 UPS 可能让主动 PFC 电源**识别异常、发出异响、甚至直接关机**——那正好发生在停电、你最需要它工作的时候。所以：

- 确认 UPS 输出是 **纯正弦波（Pure Sine Wave）**，而不是"模拟正弦/阶梯波"；
- 如果整机功耗接近 UPS 上限，风险更大；
- 具体兼容性**取决于电源型号与 UPS 型号**，无法一概而论，购买前查厂商说明。

:::tip 顺便买一个带浪涌保护（Surge Protection）的插座
雷击与电网浪涌是另一类杀手。UPS 通常自带浪涌保护，若不用 UPS，至少用合格的防浪涌插排。
:::

### 让系统永不睡眠

**Windows（管理员权限的 PowerShell 或 CMD）**

```bat
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 0
powercfg /change disk-timeout-ac 0
```

- `standby-timeout-ac 0` 表示**交流供电时永不进入睡眠**（`0` 即"从不"）。
- 台式机一般没有电池，`-ac`（交流）就是你要改的那一项；**笔记本**还要改 `-dc`（电池），否则拔掉电源后照样睡眠。
- 查看当前设置：`powercfg /query SCHEME_CURRENT SUB_SLEEP`。
- **注意**：Windows 的"快速启动"与"休眠"是另一回事，企业策略或厂商电源管理软件可能覆盖这些值。

**Linux（systemd）**

先看哪些目标被"允许"进入：

```bash
systemctl status sleep.target suspend.target hibernate.target hybrid-sleep.target
```

阻止系统睡眠：

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

**笔记本合盖**由 logind 处理，编辑 `/etc/systemd/logind.conf`：

```ini
HandleLidSwitch=ignore
HandleLidSwitchExternalPower=ignore
HandleLidSwitchDocked=ignore
```

改完执行 `sudo systemctl restart systemd-logind` 生效。

:::warn 具体键名与默认值随发行版与 systemd 版本而不同
`logind.conf` 的可选值（`ignore` / `poweroff` / `suspend` / `hibernate` / `lock`）与默认行为在不同发行版、不同 systemd 版本上不完全一致，**改之前先读 `man logind.conf`**，并确认改动不会被桌面环境的电源管理覆盖。桌面发行版（GNOME/KDE）通常还有自己的"空白屏幕后挂起"开关。
:::

### BIOS：停电恢复后自动开机

断电恢复后机器**默认不会自己开机**，你必须手动按电源键——如果人在外地，服务就一直是停的。

进 BIOS/UEFI，找到类似下面这些名字的选项（**名称随主板厂商与 BIOS 版本不同**，通常在 `Power` / `Advanced` / `APM Configuration` 分类下）：

| 常见名称 | 作用 |
| --- | --- |
| `Restore on AC Power Loss` | 来电后的行为，选 `Power On` / `Always On` |
| `AC Power Recovery` / `AC Recovery` | 同上，Dell 等常用此名 |
| `After Power Failure` | 同上，常见于 DIY 主板 |

选 **`Power On` / `Always On`**（不要选 `Last State`：如果断电时是开机状态它也会开机，但若上次是关机状态则不会）。

配套检查：

- **关闭"快速启动"**（Windows 的 Fast Startup 会让关机变成混合休眠，影响自动开机与磁盘一致性）；
- **设置 BIOS 超级密码**，防止误改；
- 若机器要长期无人值守，**开启来电自启 + 关闭一切"节能待机"选项**。

## 3. 散热与灰尘

### 风道与摆放

- **进风要有滤网，出风要通畅**。常见有效布局：前面/底部进风、后面/顶部出风，保持**进风量略大于出风量**（正压），灰尘更少从缝隙钻进来。
- **别塞进封闭柜子**，别贴墙、别放在地毯上。机器四周留出空间。
- **硬盘最怕震动**：机械硬盘不要放在会被踢到、撞到的位置（见第 8 节）。

### 清灰

| 频率 | 做什么 |
| --- | --- |
| 每 1 - 3 个月 | 检查进风滤网，明显积灰就清 |
| 每 3 - 6 个月 | 用压缩空气/吹尘器清理散热器、风扇、电源进风口 |
| 每 6 - 12 个月 | 视积灰程度决定是否重新涂硅脂（**不是必须**，温度正常就别动） |

清灰要点：**吹风扇时用手或塑料片挡住扇叶**，别让气流把风扇吹到高速空转（可能损坏轴承）；不要用吸尘器直接贴电路板（静电风险）；清理后**确认所有风扇都转**（含电源、显卡、机箱风扇）。

### 温度监控

**Linux**：`lm-sensors` 是读取主板/CPU 温度传感器的常用工具。是否可用、能读到哪些传感器**取决于主板与芯片组驱动**，部分平台（尤其是较新的笔记本与部分主板）支持不完整。

```bash
sudo apt install lm-sensors      # Debian / Ubuntu
sudo dnf install lm_sensors      # Fedora / RHEL 系
sudo sensors-detect              # 探测可用传感器，交互式回答
sensors                          # 输出当前读数
watch -n 5 sensors               # 每 5 秒刷新
```

**Windows**：任务管理器（`Ctrl+Shift+Esc`）的"性能"页可以看到 CPU/GPU 温度（**可用性取决于硬件与驱动**）；需要更细的读数（各核心、硬盘 SMART 温度、风扇转速）用 HWiNFO、HWMonitor 一类工具。

### 过热的表现

| 现象 | 含义 |
| --- | --- |
| TPS 突然下降但 CPU 占用不高 | CPU 被降频（thermal throttling） |
| CPU 频率低于基准频率 | 同上，用 `lscpu`/`cpupower` 或 HWiNFO 看实时频率 |
| 风扇长期满载、声音变大 | 积灰或硅脂老化 |
| 无故关机/重启 | 触发了过温保护，**这是严重信号**，要立刻处理 |

`dmesg` 里出现 `CPU0: Core temperature above threshold`、`thermal throttling` 一类信息，说明已经触发了保护。**具体日志文本随内核与硬件不同**，以你机器上实际输出为准。

## 4. 家庭网络

### 为什么 Wi-Fi 不适合长期开服

- **延迟抖动（jitter）比平均延迟更致命**：MC 对丢包和抖动敏感，玩家会表现为"回弹""卡顿""瞬移"。
- **信道干扰与邻居 Wi-Fi 拥挤**，晚上更明显。
- **省电机制**：无线网卡会进入省电模式，带来周期性延迟尖峰。
- **稳定性**：AP 重启、固件问题都会断线。

**结论：能插网线就插网线。** 如果机器离路由器远，用电力猫（受电路影响大）、MoCA（同轴）或干脆拉一根网线。下面三条讲清楚家宽最常见的三个坑。

### 有没有公网 IPv4：怎么判断

1. 登录路由器，找到 **WAN 口 IP**。
2. 在机器上访问一个"我的 IP"查询站点，或运行 `curl -4 ifconfig.me`。
3. **两者不一致**：你大概率处在运营商 NAT（CGNAT）后面，**没有公网 IPv4**，做端口映射也没用。
4. 补充判断：CGNAT 的 WAN IP 常落在 `100.64.0.0/10` 这一段（RFC 6598 共享地址空间）。**这不是硬性规则**，只是常见特征。

:::warn IPv6 是另一条路，但不是万能药
部分地区家宽有公网 IPv6，理论上可以直连，但**玩家的网络环境不一定支持 IPv6**，很多客户端仍走 IPv4。以 IPv6 为主的方案要确认玩家侧可用性。
:::

### 动态 IP 与 DDNS

家庭宽带的公网 IP **会变**（重新拨号、运营商调整）。DDNS（动态域名解析）解决的就是这件事：

1. 注册一个 DDNS 服务（或使用域名商的 API）。
2. 在路由器或机器上运行更新客户端，**定期把当前公网 IP 上报**给 DDNS。
3. 玩家用**域名**而不是 IP 连接。

要点：

- **DDNS 只解决"IP 变了怎么找到你"**，解决不了 CGNAT——没有公网 IP 时 DDNS 也没用。
- 更新间隔别太短（会被限流），几分钟一次通常够。
- 如果你用内网穿透（frp 等），玩家的入口是**中转服务器的 IP**，DDNS 就不必要了。

### 上行带宽才是瓶颈

家宽通常**下行几百兆、上行几十兆甚至更少**。MC 服务端的流量几乎全是**上行**（把世界数据发给玩家）。

粗略估算：一个玩家正常游玩的带宽需求在**几十到几百 kbps** 量级，视视距、实体数量、区块加载速度而定，**波动极大**。用 `Mbps` 简单折算：

| 上行带宽 | 理论并发上限（按每玩家 0.5 Mbps 保守估算） |
| --- | --- |
| 10 Mbps | 约 20 人 |
| 20 Mbps | 约 40 人 |
| 50 Mbps | 约 100 人 |

**这只是量级参考**，实际取决于玩法（红石/大量实体/高视距会显著提高需求）。务必**实测**：用路由器或系统工具观察服务端进程的上行占用。

:::tip 先测再定人数上限
在服务端目录跑一段时间后，用 `iftop`、`nload`（Linux）或任务管理器/资源监视器（Windows）看实际上行占用，再决定能带多少人。**别按"我下行 500M"来估算。**
:::

## 5. 操作系统维护例程

### 更新策略

- **固定一个维护窗口**（例如每周一次），在窗口内做系统更新与重启。
- **更新前先备份**（见 [备份与恢复](/tutorials/java/backup)），并确认备份文件在**另一块盘或异地**。
- **不要开无人值守自动重启**：让它在你选定的时间重启，而不是半夜。
- 内核/系统大版本升级后，**重启一次再确认服务端正常**。

**Debian / Ubuntu**

```bash
sudo apt update
sudo apt upgrade
sudo apt autoremove --purge
```

**Fedora / RHEL 系**

```bash
sudo dnf upgrade --refresh
sudo dnf autoremove
```

**Windows**：设置 -> Windows 更新 -> 高级选项，把"活动时间"设成你的维护窗口之外；重要更新手动重启。

### 磁盘健康（SMART）

`smartmontools` 是读取 SMART 数据的标准工具（`smartctl` 是其中的命令）。

```bash
sudo apt install smartmontools
sudo smartctl -a /dev/sda
```

:::warn 设备名一定要确认
`/dev/sda` 只是**示例**。NVMe 盘通常是 `/dev/nvme0n1`，SATA 盘可能是 `/dev/sdb`。**用错设备名会读到别的盘的数据，甚至（在写操作时）造成破坏。** 先用 `lsblk` 确认：

```bash
lsblk -o NAME,SIZE,MODEL,MOUNTPOINT
```
:::

**SATA 盘要重点看的属性**（属性名与编号由 ATA/SMART 标准定义，不同厂商的原始值编码可能不同，**看"VALUE/WORST/THRESH"与"RAW"要结合厂商说明**）：

| 属性 | 含义 | 怎么判断 |
| --- | --- | --- |
| `Reallocated_Sector_Ct`（ID 5） | 已重映射的坏扇区数量 | **不为 0 就要警惕**，持续增长说明盘在退化 |
| `Current_Pending_Sector`（ID 197） | 待处理扇区（读取失败但尚未重映射） | **任何非 0 值都要立刻备份** |
| `Offline_Uncorrectable`（ID 198） | 离线扫描无法纠正的扇区 | 非 0 说明已有不可恢复错误 |
| `UDMA_CRC_Error_Count`（ID 199） | 传输校验错误 | 增长通常是**线材/接口问题**，不是盘坏 |
| `Reported_Uncorrect`（ID 187） | 上报的不可纠正错误 | 与 197/198 一起看 |

**NVMe 盘**看的是另一组字段：

```bash
sudo smartctl -a /dev/nvme0n1
```

关注 `Percentage Used`（寿命消耗百分比）、`Available Spare`（可用备用块）、`Media and Data Integrity Errors`、`Critical Warning`。

**定期自检**（会占用一些时间，建议在维护窗口跑）：

```bash
sudo smartctl -t short /dev/sda     # 短自检，通常 1-2 分钟
sudo smartctl -t long  /dev/sda     # 长自检，可能数小时
sudo smartctl -l selftest /dev/sda  # 查看自检结果
```

**监控建议**：`smartd` 可以常驻并邮件告警；桌面用户至少做到**每季度手动看一次**。

### SSD 寿命

SSD 的寿命由**写入量（TBW）**决定，不是通电时间。频繁全量备份、日志狂写、频繁 `save-all` 都会消耗寿命。用 `smartctl` 的 `Data_Units_Written`（SATA）或 `Data Units Written`（NVMe）估算总写入量；**把日志与备份写到别的盘**能显著降低系统盘写入。SSD 快满时性能与寿命都会恶化，**留出至少 10% - 20% 空闲空间**。

### 文件系统检查与日志

- **ext4**：异常断电后可能要求 `fsck`。**不要在挂载状态下对根分区执行 `fsck`**；现代发行版在启动时自动检查。手动检查未挂载分区用 `sudo fsck -f /dev/sdb1`（先 `umount`）。
- **Btrfs / ZFS**：有各自的检查与清理工具（`btrfs scrub`、`zpool scrub`），**具体命令与用法随版本不同，以其官方文档为准**。
- **日志增长**：用 `journalctl --disk-usage` 看 systemd 日志占用，用 `sudo journalctl --vacuum-size=500M` 限制大小；日志轮转由 `logrotate` 负责，一般默认已配好。
- **Windows**：事件查看器会无限增长，可在"事件查看器 -> Windows 日志 -> 属性"里设置最大大小与覆盖策略；`cleanmgr` 可清理系统文件。

### 清理旧备份

**这是最容易把盘写满的地方**：服务端目录持续增长，若保留策略是"全部留着"，几个月就会塞满磁盘——**磁盘满会导致服务端写存档失败**。明确保留策略（例如每日 7 份 + 每周 4 份）并让脚本自动删除超期备份，定期 `df -h` 确认剩余空间。详见 [异地备份](/tutorials/ops/offsite-backup) 的保留策略与磁盘空间计算。

## 6. 游戏服务端维护例程

### 计划性重启

**定期重启**能回收内存碎片、清理未释放的资源，常见做法是**每天或每几天一次**，选在低峰期（凌晨）。重启方式：通过控制台发送 `stop`（**不要直接杀进程**），等待进程完全退出后再启动；**重启前先确认备份成功**。用 systemd 托管时 `systemctl restart minecraft.service` 会走正常的停止流程（前提是服务端能收到 `stop`；若启动方式无法接收控制台输入，需要改用 `screen`/`tmux` 或 RCON 发送命令）。

:::warn 直接断电式重启很危险
`kill -9`、任务管理器"结束任务"、直接按电源键，都可能让服务端来不及保存。**能用 `stop` 就用 `stop`。**
:::

### 确认备份真的在跑

**这是维护清单里最容易被跳过、也最致命的一项。** 检查**备份文件的修改时间与大小**（不是检查"脚本存在"），检查**日志里的退出码**（非 0 就是失败），并定期**真的恢复一次**（见 [异地备份](/tutorials/ops/offsite-backup) 的恢复演练）。

```bash
ls -lh /backup/mcserver/ | tail -5
tail -20 /var/log/mc-backup.log
```

### 看日志与崩溃报告

- **`logs/latest.log`**：当前/最近一次运行的日志。搜索 `WARN`、`ERROR`、`Exception`、`Caused by`。
- **`crash-reports/`**：崩溃报告，含完整堆栈与当时的环境信息，**是排查崩溃的第一手资料**。
- 常见信号：内存不足（`OutOfMemoryError`）、插件报错、区块加载失败、端口占用。

```bash
grep -nE "ERROR|Exception|Caused by" logs/latest.log | tail -40
ls -lt crash-reports/ | head
```

### 用 spark 看 TPS

**spark** 是常用的性能分析插件/模组（Bukkit 系、Fabric、Forge 等都有对应版本），能采样 TPS、MSPT 与卡顿来源。常用命令 `/spark tps`、`/spark profiler start` / `/spark profiler stop`（**具体子命令以 spark 官方文档为准**，不同版本略有差异）。**TPS 长期低于 20 说明服务端跟不上**，**MSPT 持续高于 50 ms** 同样说明单个 tick 超时。先用 `/spark tps` 判断"是不是真的卡"，再用 profiler 找"是谁在卡"；系统排查见 [性能优化](/tutorials/java/optimize)。

### 观察内存增长

**Java 堆内存不是"用满就是坏"**：GC 会保留一部分，关键是看**老年代在 Full GC 后能否回落**。如果 Full GC 后占用**持续抬升**且不回落，很可能是**内存泄漏**（常见于插件）。排查手段：加 GC 日志（JDK 9+ 用 `-Xlog:gc*`，JDK 8 用 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps`），或让 spark 采样。**不要用"加大 -Xmx"来掩盖泄漏**，那只会把崩溃推迟。

### 安全地更新服务端

固定流程，一步都别省：

1. **完整备份**（存档 + 插件 + 配置），并确认备份文件存在且大小正常。
2. **读 changelog 并确认 Java 版本要求**：留意破坏性变更（配置格式变更、插件不兼容、Java 版本提高）。
3. **先在测试副本上跑**：复制一份服务端目录，用新版本启动，确认能起来、插件加载正常。
4. **低峰期切换**：停服 -> 替换 jar -> 启动 -> 观察日志 -> 让玩家验证，并**保留旧版本**以便回退。

:::tip 更新前把"回退方案"写下来
"如果新版本起不来，我要执行哪几条命令"——写清楚。出事时人在慌，靠记忆容易漏步骤。
:::

## 7. Windows 与 Linux 的差异

| 事项 | Windows | Linux |
| --- | --- | --- |
| 禁止睡眠 | `powercfg /change standby-timeout-ac 0` | `systemctl mask sleep.target ...`；笔记本另配 `logind.conf` |
| 服务常驻 | 任务计划程序 / NSSM 一类包装器 / `start.bat` 循环 | systemd unit（推荐） |
| 定时任务 | 任务计划程序（GUI） | cron / systemd timer |
| 更新 | Windows 更新，注意"活动时间"与自动重启 | `apt` / `dnf`，自己决定何时重启 |
| 磁盘健康 | 厂商工具 + 事件查看器 | `smartctl` + `smartd` |
| 温度 | 任务管理器 / HWiNFO 一类 | `lm-sensors`（支持程度依主板而定） |
| 日志 | 事件查看器，需手动设上限 | `journalctl` + `logrotate` |
| 大小写敏感 | **不敏感**（`World` 与 `world` 是同一个） | **敏感**（`World` 与 `world` 是两个） |
| 换行符 | CRLF 可能导致脚本在 Linux 上无法执行 | LF |

:::warn 大小写敏感是跨平台迁移的经典坑
把 Windows 上跑得好好的服务端目录整体拷到 Linux，**插件配置里写错的路径大小写**会立刻暴露成"文件找不到"。迁移前统一检查一遍。
:::

## 8. 物理安全

服务器放哪里，直接决定它会不会被打断：

- **不要放在会被踢到、绊到线的地方**（走道、桌下伸脚处、床边），也不要放在水杯、饮料、鱼缸、窗台附近——液体进机箱是报废级故障。
- **不要用容易被误拔的插座**（和吹风机、电水壶共用的插排尤其危险）；**机箱放稳**，机械硬盘尤其怕震动。
- **给线缆贴标签**：电源线、网线、显示器线各是哪一根，写清楚，并给网线接口做防拉（走线固定）。
- 有条件的话，**把机器和日常桌面分开**，减少"顺手关机""顺手拔线"的概率。

:::tip 做一个"禁止断电"的标签
在插头和机箱上贴一张纸条："此机为服务器，请勿断电/拔线"。家里有其他人时，这张纸的价值极高。
:::

## 9. 维护日历

把下面这张表当成最低要求，按你的实际情况加密或放宽。

| 周期 | 任务 |
| --- | --- |
| **每日** | 看一次服务端是否在线；扫一眼 `logs/latest.log` 有无 ERROR；确认昨晚的备份文件已生成 |
| **每周** | 检查磁盘剩余空间（`df -h`）；检查备份日志退出码；看一次 TPS（`/spark tps`）；确认无异常重启记录 |
| **每月** | 检查 SMART（`smartctl -a`）关键属性；检查内存趋势与 Full GC 表现；清理超期备份；检查系统更新并安排在窗口内重启 |
| **每季度** | **恢复演练**（真的恢复一次并启动验证）；清灰与检查风扇；检查 UPS 电池状态；审查端口映射/DDNS/防火墙规则；检查磁盘空间增长趋势并调整保留策略 |
| **每年** | 更换 UPS 电池（视型号与状态）；评估硬件老化（硬盘通电时长、SSD 写入量）；复核保留策略与异地副本是否仍然有效 |

:::warn 恢复演练不是可选项
"备份脚本每天在跑"和"备份能恢复"是两件事。**没验证过恢复的备份不算备份**，详见 [异地备份](/tutorials/ops/offsite-backup)。
:::

## 10. 小结

家用电脑开服**不是不行，而是要把"可靠性"当成一件需要主动维护的事**：关掉睡眠、配好 UPS 与来电自启、插网线、按周期更新与检查磁盘、定期真的恢复一次备份。做到这些，一台家用机可以稳稳跑很久。
