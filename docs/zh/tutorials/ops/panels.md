前面几篇讲的都是"你登录机器、自己敲命令"。这一篇讲另一种常见的运维方式：**把服务器交给一个 Web 面板管理**——打开浏览器就能启停实例、看控制台、传文件、改配置。

面板确实好用，但它是**这台机器上权限最高、也最容易成为目标的服务**。所以本文的重点不是"面板能做什么"，而是**用了面板之后攻击面多了什么，以及怎么把它收回来**。

:::note 本文的定位
本文只讲**使用方式与安全边界**，不替代各面板的官方安装文档。安装命令、默认端口、目录结构**一律以官方文档为准**；本文只给出已与官方来源核对过的默认值，并标注出处。
:::

## 1. 面板能做什么、代价是什么

### 1.1 面板通常提供的能力

| 能力 | 具体表现 | 什么时候真的省事 |
| --- | --- | --- |
| **Web 管理界面** | 浏览器里启停、重启、查看状态，不用记一堆命令 | 手机上也能应急重启 |
| **多实例管理** | 一台机器上同时跑多个服务端，统一切换 | 生存服、创造服、测试服并存 |
| **控制台访问** | 网页里看实时日志、直接发指令 | 远程排查崩服原因 |
| **文件管理器** | 上传、下载、编辑 jar、配置与世界文件 | 给玩家换整合包、加插件 |
| **计划任务** | 定时重启、定时备份、定时执行命令 | 每天凌晨重启释放内存 |
| **用户与子用户权限** | 给管理员、协管分配部分实例的操作权 | 让协管重启服，但不给 SSH |
| **资源统计** | CPU、内存、磁盘、在线人数曲线 | 判断是配置问题还是机器不够 |
| **Docker 集成** | 用容器隔离实例、限制资源 | 多实例互不干扰 |

:::note 功能集因面板而异
上表是"面板这一类工具"的常见能力，**具体某个面板是否提供、入口在哪里，以该面板的官方文档与你的实际界面为准**。
:::

### 1.2 代价清单

| 代价 | 说明 |
| --- | --- |
| **多了一个要维护的服务** | 面板本身是 Web 应用，要更新、要看安全公告、要备份它自己的数据 |
| **攻击面变大** | 多一个监听端口、多一套账号体系、多一条 API |
| **权限高度集中** | 面板（尤其是守护进程）能启动任意进程、读写实例目录，拿到它就等于拿到这台机器上所有服务端 |
| **反向代理更复杂** | 面板常需要 WebSocket；某些面板还要求浏览器直连守护进程（见 3.1） |
| **故障面变大** | 面板挂了不等于服务端挂了，但你可能暂时失去管理手段 |

:::warn 一句话理解风险
**面板不是"另一个软件"，而是"这台机器上所有游戏服务器的总开关"。** 它的登录页面对公网开放，就等于把整机管理权挂在公网上。
:::

### 1.3 先画清信任边界

用面板之前，先在脑子里把这条线画清楚：

- **面板能控制的东西 = 它运行身份能控制的东西。**
- 面板以 root 运行，那么面板的任意一个远程代码执行漏洞就等于整机沦陷。
- **守护进程的 API 本身就是"执行命令"的接口**——那是它存在的意义。所以它一旦暴露，等同于把一个 shell 挂到公网上。

## 2. MCSManager（MCSM）

### 2.1 官方定位

MCSManager 官方仓库对自己的描述是：**"快速安装，分布式架构，多用户，现代化的 Minecraft 和 Steam 游戏服务器管理面板"**（英文版为 "Quick deployment, distributed, multi-user, modern management panel for Minecraft and Steam game servers"）。官方文档进一步说明：它是**开源、分布式、一键部署**，支持 Minecraft 与 Steam 游戏服务器的控制面板，可以帮助你集中管理多台物理服务器、在任意主机上创建游戏服务端，并提供安全可靠的多用户权限系统。

这段话里的三个关键词，就是它的定位：

| 关键词 | 含义 |
| --- | --- |
| **一键部署** | 提供安装脚本，自动注册为系统服务 |
| **分布式** | 一个面板可以管理**多台**机器 |
| **多用户** | 内置账号与权限体系，可以把权限分给协管，而不是给 SSH |

### 2.2 架构：一个面板 + 一个或多个守护进程

官方文档把 MCSManager 分成两部分：

| 组件 | 官方描述的职责 |
| --- | --- |
| **Panel（Web 面板）** | 用户管理、连接守护进程、多数操作的鉴权、API |
| **Daemon（守护进程）** | 进程管理（实例真正运行的地方）、Docker 镜像管理、文件管理、实时终端通信 |

"分布式"的含义就在这里：**面板本身不跑服务端**，它把指令下发给各台机器上的守护进程，由守护进程在本机启动和管理实例。所以你可以是"一台面板 + N 台守护进程节点"。

:::warn 组件名、安装命令、默认端口、目录结构以官方文档为准
MCSManager 的服务名、安装脚本地址、默认端口与数据目录可能随版本变化。**本文列出的数值只代表写作时官方文档中的默认值，请以官方文档与你机器上的实际配置文件为准。** 生产环境不要照抄任何未经核对的端口或路径。
:::

**本文已与官方文档核对过的默认值（供对照，仍建议自行确认）：**

| 项目 | 官方文档中的默认值 | 备注 |
| --- | --- | --- |
| 面板 Web 端口 | `23333` | 可在 Web 配置文件的 `httpPort` 修改 |
| 守护进程端口 | `24444` | 可在守护进程配置文件的 `port` 修改 |
| Linux 服务名 | `mcsm-web`、`mcsm-daemon` | systemd 服务 |
| 脚本安装目录 | `/opt/mcsmanager` | 官方示例路径 |
| Web 配置文件 | `<Web 安装目录>/data/SystemConfig/config.json` | 含 `httpPort`、`httpIp`、`loginCheckIp` 等 |
| 守护进程配置文件 | `<Daemon 安装目录>/data/Config/global.json` | 含 `port`、`key`、`defaultInstancePath` 等 |
| 守护进程密钥 | 上述 `global.json` 的 `key` 字段 | 守护进程启动时也会打印 |

:::tip 一个非常容易被忽略的官方警告
官方"分布式部署"文档明确写着：在只跑守护进程的节点上，**必须先停止并禁用 Web 服务**，否则**任何人都能访问初始设置页面并接管你的服务器**：

```bash
systemctl stop mcsm-web
systemctl disable mcsm-web
```

这条警告值得单独记住：**"忘记关掉的那个 Web 服务"就是一次完整的沦陷。**
:::

### 2.3 安装与首次登录

官方 Linux 一键安装脚本（官方文档强调：因为要注册到系统服务，**必须以 root 权限运行**）：

```bash
sudo su -c "wget -qO- https://script.mcsmanager.com/setup.sh | bash"
```

:::note 中文文档与英文文档的脚本地址不同
官方英文文档使用 `setup.sh`，中文文档使用 `setup_cn.sh`。**请以你所看语言版本的官方文档给出的地址为准**，不要凭记忆拼写脚本 URL。官方文档另有 Docker 安装与环境隔离（Docker）章节，具体步骤同样以官方文档为准。
:::

安装后按官方文档启动两个服务（官方强调两者缺一不可）：

```bash
# 先启动守护进程，再启动 Web 服务
systemctl start mcsm-daemon.service
systemctl start mcsm-web.service

# 需要开机自启时
systemctl enable mcsm-web.service
systemctl enable mcsm-daemon.service
```

手动安装时，官方文档给出的启动方式是 `./install.sh`、`./start-daemon.sh`、`./start-web.sh`，并提示手动启动需要用 screen 之类的工具接管，否则 SSH 断开后进程会被系统结束。Windows 版官方说明为下载压缩包解压后运行（压缩包内若含启动器，也可用启动器启动）。

**首次登录必须做的事（顺序不要颠倒）：**

1. 用管理员账号登录面板（初始账号信息以官方文档与你的安装输出为准）。
2. **立刻修改默认口令**，并使用与其它站点不同的长口令。
3. 按 3.5 的方式把它放到 HTTPS 反向代理后面，或至少限制来源 IP。
4. 检查监听地址与端口，确认没有把守护进程直接暴露在公网。

### 2.4 典型工作流：从装好到跑起一个实例

官方"搭建 Java 版"文档给出的流程大致如下（细节以官方文档为准）：

| 步骤 | 做什么 | 注意 |
| --- | --- | --- |
| 1 | 装面板 + 守护进程（或按官方文档用 Docker） | 节点机器上只留守护进程服务 |
| 2 | 登录并修改默认口令 | 见 2.3 |
| 3 | 在面板里确认或新增守护进程节点 | 需要地址与密钥；官方文档说明地址支持 IP、域名，也支持 `ws://` / `wss://` 前缀 |
| 4 | 在"实例"页点"创建" | 可选从市场安装，或"直接创建"并选择要运行的节点 |
| 5 | 填写启动命令 | 官方示例：`java -Dfile.encoding=UTF-8 -jar "paper-<version>.jar"`，可加 `-Xms` / `-Xmx` |
| 6 | 上传服务端文件 | 用面板的"文件管理"上传核心 jar |
| 7 | 在实例控制台点"启动"并观察日志 | 首次启动通常还要在"配置文件"里把 `eula.txt` 改成 `eula=true` |
| 8 | 给协管建子账号，只授权需要的实例 | 不要给"全部实例 + 文件管理" |

官方文档还说明：实例数据默认位于 `<Daemon 安装目录>/data/InstanceData/<实例 ID>/`，实例配置位于 `<Daemon 安装目录>/data/InstanceConfig/<实例 ID>.json`（其中包含启动命令等配置）。**这两处是"丢了就很难重建"的东西，必须纳入备份。**

:::warn 启动命令里的内存参数不要贪心
官方文档特别警告：**不要把机器全部内存都分给 JVM**，操作系统本身也需要资源，否则可能整机崩溃。`-Xmx` 要明显小于机器物理内存。
:::

### 2.5 什么时候面板真的帮到你

- **多实例**：十几个服务端靠 SSH 一个个重启不现实。
- **给协管有限权限**：让协管重启、看日志，但**不给 SSH**——这是面板最大的安全收益。
- **定时重启与备份**：面板类工具通常提供计划任务能力，**MCSManager 是否提供、入口在哪里、怎么配置，以官方文档与你的实际界面为准**。
- **多机管理**：一个面板 + 多个守护进程，统一入口。
- **给不熟命令行的人用**：把操作限制在面板的功能范围内，往往比直接给一个 shell 更安全。

## 3. 面板的安全（最重要）

### 3.1 第一原则：面板与守护进程 API 绝不直接暴露公网

这一条比其它所有条目加起来都重要：

:::warn 绝不把守护进程端口暴露到公网
守护进程 API 的职责就是**启动进程、读写文件、执行命令**——它本质上是一个**远程代码执行接口**，只是外面套了一层鉴权。**它一旦暴露，攻击者只需要一个密钥泄露、一个鉴权绕过或一个未修补的漏洞，就能在你机器上执行任意命令。** 面板 Web 端同理，只是它至少还有一道登录页。
:::

正确的做法：

1. **面板**：绑定 `127.0.0.1` 或内网地址，通过 HTTPS 反向代理对外，再加一层来源限制（VPN、IP 白名单或防火墙规则）。
2. **守护进程**：只允许面板主机（以及需要直连的客户端）访问。
3. **不要为了"方便"把守护进程端口开到 `0.0.0.0`。**

:::note MCSManager 的特殊之处：浏览器需要直连守护进程
MCSManager 官方"网络架构"文档说明：为了避免面板成为大流量（文件上传、控制台日志）的瓶颈，**这些流量由浏览器直接与守护进程通信**。因此官方文档指出，守护进程的地址**不能是局域网地址**，否则守护进程状态会一直停在"连接中"。

这带来两个必须知道的后果：

- 如果你把面板升级为 HTTPS，**每个守护进程也必须单独配置 HTTPS 反向代理**，并在面板里把地址改成 `wss://...`；官方文档明确说明浏览器会**拒绝**通过非 HTTPS 的 WebSocket 连接守护进程。
- "守护进程只在内网"这条通用建议，在 MCSManager 上要按官方文档的网络架构来落实：**要么按官方文档给出的 HTTPS 反向代理方案配置，要么用 VPN 或隧道保护"浏览器到守护进程"这条链路**，不要简单地把端口暴露到公网。

**具体怎么配，以官方文档的《网络架构》与《通过 NGINX 使用 HTTPS》两篇为准。**
:::

### 3.2 不要用 root 运行

| 情况 | 事实（来自官方文档） | 建议 |
| --- | --- | --- |
| MCSManager 一键脚本 | 官方文档说明**因为要注册系统服务，脚本必须以 root 权限运行** | 安装可以用 root，但**实例应尽量用专用用户或容器隔离**；官方另有"环境隔离（Docker）"文档 |
| Pterodactyl Wings | 官方文档给出的 systemd 单元中为 `User=root` | 这是官方设计（Wings 需要控制 Docker）；**用容器隔离实例本身就是它的缓解手段** |
| 通用服务器面板 | 通常需要较高权限来管理系统服务与网站 | 不要把游戏服务端和这类面板混在同一个信任边界里（见 4.2） |

原则：**能不用 root 就不用；必须用高权限时，用隔离（独立用户、容器、独立机器）把爆炸半径圈起来。**

### 3.3 凭据与账号

- **立刻修改默认口令。** 默认口令是自动化扫描器的第一目标。
- 使用**长且唯一**的口令，最好由密码管理器生成。**面板口令泄露 = 所有实例沦陷。**
- **若面板支持两步验证，务必开启**；是否支持、如何开启，**以官方文档为准**。
- **定期审计子用户与权限**：谁还在？还需要吗？权限是不是给多了？"文件管理 + 全部实例"几乎等于给 shell。
- **删除不再需要的账号**，包括离职的协管、测试账号与不再使用的 API Key。
- 不要把面板口令写进截图、聊天记录、Git 仓库，或服务端目录里的文本文件。

### 3.4 保持面板本身更新

面板是 Web 应用，**有自己的漏洞历史**。要做的事：

- 订阅官方仓库的 Release 与安全公告。
- 按官方文档中"更新"章节给出的流程升级。
- 升级前**备份面板自身数据**（见 3.7）。

:::warn MCSManager 升级时的一个坑
官方"更新与重置"文档提示：一键脚本更新会**自动重新启用 `mcsm-web`**。如果你在节点机器上刻意禁用了 Web 服务（见 2.2），更新后**必须再次手动停止并禁用它**，否则初始设置页面又会暴露出来。
:::

### 3.5 监听地址与反向代理（nginx 示例）

思路是：**面板只绑回环地址，由 nginx 对外提供 HTTPS。** 下面的端口是**占位符**，请替换成你自己的面板端口。

```nginx
# /etc/nginx/conf.d/panel.conf
# <panel-port> 是占位符，请替换为面板实际监听的本地端口。
# 证书路径由你的证书工具决定，不要照抄下面的示例路径。

server {
    listen 80;
    server_name panel.example.com;
    # 只做跳转；证书签发与续期方式以你所用的证书工具文档为准
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name panel.example.com;

    # 由你的证书工具生成与续期，请替换为实际路径（例如 certbot 的输出路径）
    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    # 面板控制台依赖 WebSocket，必须转发 Upgrade 头
    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 面板可能要上传较大的服务端或整合包文件；0 表示不限制
        client_max_body_size 0;

        # 控制台是长连接，别让它被缓冲或被过早切断
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

几点说明：

- `proxy_http_version 1.1` 加上 `Upgrade` / `Connection` 三个头是 WebSocket 的关键，**少一个控制台就可能连不上**。
- `ssl_certificate` 与 `ssl_certificate_key` 的**路径来自你的证书工具**（certbot 等），不同工具、不同部署方式路径不同，**不要照抄**。
- 如果面板官方文档提供了自己的反向代理示例（MCSManager 官方就有 NGINX、IIS、Caddy 三篇），**以官方文档为准**——因为守护进程那条链路往往还需要单独配置。
- 改完配置先测试语法再重载（MCSManager 官方文档同样要求先验证再重载）：

```bash
sudo nginx -t
sudo nginx -s reload
```

### 3.6 防火墙

只开必须开的，其余默认拒绝：

| 端口 | 对谁开放 | 说明 |
| --- | --- | --- |
| 80 / 443 | 公网 | 面板入口（或你选定的 HTTPS 端口）；80 仅用于跳转与证书校验 |
| 面板本地端口 | **仅本机** | 面板绑在 `127.0.0.1` 时不需要对外放行 |
| 守护进程端口 | **仅面板主机**（或按官方架构要求限定来源） | 绝不对公网开放；具体端口以官方文档为准 |
| 游戏端口 | 公网（按需） | 玩家入口 |
| SSH | 你的管理 IP | 建议只允许密钥登录 |

示例（端口与网段都是**占位符**，请按你的实际配置替换；命令语法请对照你的发行版文档）：

```bash
# ufw 示例
sudo ufw default deny incoming
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp
# 只允许面板主机访问守护进程端口
sudo ufw allow from <panel-host-ip> to any port <daemon-port> proto tcp
sudo ufw enable
sudo ufw status verbose
```

端口与规则的完整思路见 [网络安全基础](/tutorials/ops/network-security) 与 [路由器与防火墙](/tutorials/ops/router-firewall)。

### 3.7 备份面板自身的数据

**面板的数据目录里存着所有实例的定义、用户与配置。丢了它，服务端文件还在，但面板里"什么都没有了"。**

| 要备份什么 | 说明 |
| --- | --- |
| 面板的数据库与配置目录 | 用户、权限、实例定义、计划任务 |
| 守护进程的配置 | 端口、密钥、实例配置 |
| 实例数据目录 | 世界、插件、配置（通常体积最大） |

:::warn 路径以官方文档为准
各面板的数据目录位置不同，**必须从官方文档确认后再写进备份脚本**，不要凭猜测写路径。

以 MCSManager 为例，官方文档给出的相关位置是：Web 配置在 `<Web 安装目录>/data/SystemConfig/config.json`，守护进程配置在 `<Daemon 安装目录>/data/Config/global.json`，实例数据在 `<Daemon 安装目录>/data/InstanceData/<实例 ID>/`，实例配置在 `<Daemon 安装目录>/data/InstanceConfig/<实例 ID>.json`。官方"更新与重置"文档则直接建议：**升级前把 `web/data` 与 `daemon/data` 两个目录备份到别处。**
:::

备份建议：

- 面板数据的备份要**离线或异地**存放，且**面板自身进程无法写入**该位置（否则面板被入侵时备份会被一起删掉）。
- 备份里包含面板数据库与密钥，**必须加密或严格限制权限**。
- 定期做一次**恢复演练**——只备份不恢复等于没备份。具体方法见 [备份与恢复](/tutorials/java/backup) 与 [异地备份](/tutorials/ops/offsite-backup)。

### 3.8 如果面板被入侵会怎样

把最坏情况写清楚，才知道该防什么：

| 攻击者拿到的东西 | 后果 |
| --- | --- |
| 面板账号 | 控制**所有实例**：删档、改配置、踢人、给自己 op |
| 面板 + 文件管理 | 上传恶意 jar 或插件，把后门带进服务端 |
| 守护进程 API | **在机器上执行任意命令**（这本来就是它的功能），通常直接等于 shell |
| 面板数据库或密钥 | 持久化访问：即使你改了密码，旧的 API Key 与会话仍可能有效 |
| 备份目录的写权限 | **删掉你的备份**，让你无法恢复（勒索与报复性删档的常见手法） |

所以：**一旦怀疑面板被入侵，按"整机已沦陷"处理。**

1. 立即切断面板与守护进程的公网入口（改防火墙，而不是只改密码）。
2. 更换**所有**凭据：面板账号、守护进程密钥、服务端里的 RCON 口令、数据库密码、云服务商 API Key。
3. 检查是否出现新的管理员账号、新的 API Key、异常的计划任务。
4. 检查服务端目录里是否被塞了可疑的 jar、插件与定时脚本。
5. 从**已知干净**的备份恢复，而不是在已被入侵的机器上"清理一下继续用"。
6. 复盘暴露原因（端口暴露、弱口令，还是没打补丁），见 [网络安全基础](/tutorials/ops/network-security) 与 [系统安全加固](/tutorials/ops/system-security)。

完整的处置流程见 [应急与取证](/tutorials/ops/incident-forensics)。

## 4. 其他面板与如何选择

### 4.1 Pterodactyl

Pterodactyl 官方对自己的描述是：**免费、开源的游戏服务器管理面板，使用 PHP、React 和 Go 构建；为安全而设计，所有游戏服务器运行在隔离的 Docker 容器中**，并向最终用户提供直观的 Web 界面。它是 MIT 许可的开源项目，官方强调 bcrypt 口令哈希、AES-256-CBC 加密与开箱即用的 HTTPS 支持。

它的架构与 MCSManager 同属"面板 + 节点守护进程"这一类。官方术语表给出的定义是：

| 术语 | 官方含义 |
| --- | --- |
| **Panel** | Pterodactyl 面板本身，用于添加节点与服务器 |
| **Node** | 运行 Wings 实例的物理机 |
| **Wings** | 用 Go 编写的新一代服务，与 Docker 和 Panel 对接，通过面板安全地控制服务器 |
| **Server** | 由面板创建、在节点上运行的实例；一个节点可以有多个 |
| **Docker / Image / Container** | 隔离的运行环境；每个服务器跑在独立容器里，以限制 CPU、内存并避免互相干扰 |
| **Nest / Egg** | Nest 通常对应一个游戏或服务，Egg 存某一类游戏的具体配置 |
| **Yolks** | 与 Egg 系统配套的核心 Docker 镜像集合 |

要点（均来自官方文档）：

- Wings **只支持 Linux**，官方明确 Windows 环境无法运行；需要能跑 Docker 的系统，OpenVZ、LXC 一类虚拟化通常不行（官方建议用 `systemd-detect-virt` 自查）。
- 官方安装流程是：先在面板里创建节点，再把面板生成的配置粘贴为节点上的 `/etc/pterodactyl/config.yml`（或使用"生成令牌"给出的命令），然后以 systemd 服务运行 Wings。
- 官方给出的 systemd 单元中为 `User=root`，这是官方设计。
- 官方文档说明：**面板启用 SSL 时，Wings 也必须为其 FQDN 配置证书。**
- 节点需要配置 allocation（IP 与端口的组合），每个服务器至少要有一个；官方提示**不要使用 `127.0.0.1`**。

:::note 未逐一核对的内容
Pterodactyl 的**具体安装命令、默认端口、目录结构与版本要求会随版本变化**，本文不逐一列举，**一律以官方文档为准**：面板安装见官方 Panel 的 Getting Started，节点守护进程见官方 Wings 的 Installing Wings 文档。
:::

### 4.2 通用服务器面板（1Panel、宝塔等）

这类工具**不是游戏服务器面板**，它们管理的是**操作系统层面的东西**：网站、数据库、容器、文件、计划任务、防火墙等。

以 1Panel 为例，官方定位是**"现代化、开源的 Linux 服务器运维管理面板"**（也是轻量级的 AI 管理平台），提供直观易用的 Web 管理界面，可管理主机监控、文件、数据库、容器与计划任务，并深度集成 WordPress、Halo 等建站程序；官方还提供 WAF、日志审计与备份等安全能力。

**它和游戏面板的区别：**

| 维度 | 游戏服务器面板 | 通用服务器面板 |
| --- | --- | --- |
| 管理对象 | 游戏实例（进程或容器） | 系统服务、网站、数据库、容器 |
| 是否理解游戏 | 能看控制台、传插件、配启动命令 | 通常不理解，只能当普通进程或容器管 |
| 权限范围 | 实例与守护进程 | **经常是整个系统** |
| 典型用途 | 多实例、给协管分权 | 建站、跑服务、管 Docker |

**用通用面板管游戏服务器的风险：**

- **权限更大**：这类面板通常需要管理系统服务与文件，一旦被入侵，影响面比游戏面板更大。
- **不理解游戏**：它不会替你处理"先发 stop、等世界保存完"这类细节，容易把服务端当普通进程强杀。
- **多了一层**：你等于同时维护"游戏服务端的部署方式"和"通用面板"两套东西，攻击面叠加。
- **历史上出现过严重漏洞**：通用面板是公网扫描的重点目标。**任何面板都应被当作"面向公网的基础设施"来对待**——及时更新、限制来源、启用强认证。**具体漏洞信息请以各厂商的官方安全公告为准，不要依赖第三方传言。**

:::tip 更稳的组合
如果确实需要通用面板（比如同一台机器上还有网站），**把游戏服务端放在独立的机器、独立用户或独立容器里**，不要让通用面板的权限和游戏实例混在同一个信任边界中。系统层面的加固见 [系统安全加固](/tutorials/ops/system-security)。
:::

### 4.3 对比表

| 面板 | 定位 | 是否需要独立守护进程 | 适合谁 | 主要风险 |
| --- | --- | --- | --- | --- |
| **MCSManager** | 开源、分布式、多用户的 Minecraft 与 Steam 游戏服务器管理面板 | **是**（Panel + Daemon，可多节点） | 多实例、多机器、需要给协管分权的服主 | 守护进程是远程代码执行面；浏览器需直连守护进程，反向代理更复杂；升级可能重新启用 Web 服务 |
| **Pterodactyl** | 免费开源的游戏服务器面板，实例运行在隔离的 Docker 容器中 | **是**（Panel + 每节点 Wings） | 想用容器隔离、面向多用户与多节点的场景 | 依赖 Docker 与 Linux；Wings 官方以 root 运行；安装与维护门槛较高；安装方式与端口以官方文档为准 |
| **1Panel** | 现代化、开源的 Linux 服务器运维管理面板（通用） | 否（自身即系统级管理面板） | 建站、管数据库与容器、通用运维 | **系统级权限**，攻击面大；不专门理解游戏服务端；漏洞影响面大 |
| **宝塔等通用面板** | 通用服务器运维面板 | 否 | 建站与通用运维 | 同 1Panel 一类；**安装命令、默认端口与安全特性以官方文档为准** |
| **不用面板（SSH + systemd）** | 直接管理 | 否 | 单台机器、少量实例 | 没有额外攻击面；但 unit、日志、更新都要自己维护 |

## 5. 实践建议

### 5.1 安装顺序

1. **先把系统加固好**（专用用户、SSH 密钥、防火墙、自动更新），见 [系统安全加固](/tutorials/ops/system-security)。
2. **再装面板**，装完立刻修改默认口令。
3. **把面板放到 HTTPS 反向代理后面**，并限制来源（VPN、IP 白名单或防火墙规则）。
4. **最后接守护进程节点**，节点上只保留守护进程服务，关掉多余的 Web 服务。
5. 创建实例、上传文件、跑通控制台。
6. 配置计划任务与备份。
7. 给协管建子账号，按最小权限授权。

**不要**在"公网裸奔"的状态下先跑起来再说——面板暴露在公网上的每一分钟都在被扫描。

### 5.2 加固清单

- [ ] 面板与守护进程都**不在公网直接可达**
- [ ] 面板经 HTTPS 访问，且 WebSocket 正常
- [ ] 默认口令已修改；支持两步验证的已开启
- [ ] 面板与守护进程的配置文件权限收紧（含密钥或口令的文件不要全局可读）
- [ ] 实例以专用用户或容器运行，不以 root
- [ ] 面板数据已备份，且备份位置面板无法写入
- [ ] 已订阅官方安全公告，并明确了自己的更新流程
- [ ] 子用户权限已审计
- [ ] 节点机器上没有残留的初始设置页面
- [ ] 已知晓被入侵后的应急步骤

### 5.3 该监控什么

| 监控项 | 为什么 |
| --- | --- |
| **面板登录失败次数** | 暴力破解的第一信号。部分面板自带"登录失败封禁 IP"一类的配置项（MCSManager 的 Web 配置中有 `loginCheckIp`，**具体含义与行为以官方文档为准**） |
| **异常的新实例** | 攻击者常新建实例来跑别的东西 |
| **异常的计划任务** | 定时任务是持久化的常见手法 |
| **新增的管理员或 API Key** | 持久化后门 |
| **资源突增** | CPU、内存、带宽被拿去挖矿或发包 |
| **面板与守护进程的版本** | 及时打补丁 |
| **异常的出站连接** | 游戏服务端通常不应该主动外连大量地址 |

日志位置与审计命令见 [系统安全加固](/tutorials/ops/system-security)；被入侵后的处置见 [应急与取证](/tutorials/ops/incident-forensics)。

### 5.4 什么时候不该用面板

面板不是默认选项。以下情况**通常不需要**面板：

- **只有一台机器、一个服务端**：SSH + systemd 更简单，也少一个攻击面。参考 [部署到可访问环境](/tutorials/java/deploy)。
- **只有你自己用，而且你熟悉命令行**：面板的收益（可视化、分权）你用不上，成本（多一个服务、多一套账号）却要付。
- **机器性能紧张**：面板本身也要占内存，小内存机器上不划算。
- **你不打算维护它**：**不更新的面板比没有面板更危险。**

反过来，只要满足下面任意一条，面板通常就值得：多个实例、多台机器、需要给协管有限权限、需要计划任务、需要给不熟悉命令行的人使用。
