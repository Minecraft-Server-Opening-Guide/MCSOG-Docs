"开个服要多少钱"是一个没有标准答案的问题，但**问错方式**很常见。真正该问的是三个问题：**我的规模是多少？我的预算里哪些是一次性、哪些是每月？以及我愿意投入多少时间？**

很多人的第一反应是比价：把几家的套餐价格列出来，挑最便宜的那一栏。这样做通常会在半年后付出更高的代价——不是因为买贵了，而是因为**买错了**，然后在迁移、丢档、被攻击的时候把省下的钱一次性还回去。

这一篇讲怎么把钱花在真正决定体验的地方。主机层面的加固见 [系统安全加固](/tutorials/ops/system-security)，搬家的代价见 [服务器迁移](/tutorials/ops/server-migration)，被攻击时的现实见 [常见网络攻击类型与 Minecraft 专项防御](/tutorials/ops/attack-defense)。

:::warn 价格与套餐以服务商官方页面为准
本文写于无法联网核对的状态，**下面所有金额、单位与套餐形态都只是"量级示意"，不是报价**。价格、计费方式、退款政策、超流量单价、DDoS 防护是否赠送，**每一家都不一样，而且随时会变**。动手前请以服务商官方价格页与合同条款为准。
:::

## 1. 先把"成本"这个词拆开

一次开服的总成本，由四类东西构成，它们的性质完全不同：

| 类别 | 例子 | 特点 |
| --- | --- | --- |
| **一次性支出** | 硬件、域名首年、迁移的人工、初始配置 | 只在开始或大变更时付一次，容易被忽略 |
| **固定月支出** | 主机月费、带宽包、备份存储、面板 | 每月都要付，**决定你的长期负担** |
| **变动支出** | 超流量费、快照存储、高防附加费、按量计费 | 平时看不出来，出事或增长时突然变大 |
| **时间成本** | 更新、备份验证、玩家管理、事故处理 | **最贵也最容易被算成 0** |

**把这四类分开算，选型就清楚了一半。** 很多"看起来便宜"的方案，便宜的是第二类，代价藏在第三类和第四类里。

:::note 一个判断标准
如果两个方案月费相差不大，**选那个让你以后更容易搬家、更容易加备份、更容易换配置的**。开服这件事上，"可迁移性"和"可观测性"通常比省下的几十块钱值钱。
:::

## 2. 真正的成本驱动因素

### 2.1 CPU 单核性能（最容易被低估）

Minecraft 的**主逻辑（tick 循环）基本跑在单个线程上**。这意味着：

- **核多不代表流畅。** 一台 8 核但单核很弱的主机，跑一个 20 人的原版服，很可能不如一台 2 核但单核很强的主机。
- **掉 TPS 的直接原因常常是单核跑满**，此时整机 CPU 使用率可能只有 15%。
- 世界生成、区块加载、实体与红石运算都会加剧单核压力。

所以选主机时，**单核性能的优先级高于核心数量**。这一点在廉价套餐里尤其重要：超售的宿主上，你拿到的"3.0 GHz"是共享的。

### 2.2 内存

内存决定"能开多大、能装多少东西"：

- 原版/Paper 服务端：小规模（几个人到十几人）通常几 GB 堆就能跑，**但具体数字随版本、视距、插件与玩法差异极大**。
- 模组服与整合包：内存需求通常是原版的数倍，**以整合包作者与加载器的官方说明为准**。
- 面板、网页地图、数据库、代理端都会额外占内存，**别只给服务端算内存**。
- 内存给太多也有代价：堆过大时一次 GC 的停顿更长。**"内存越大越好"是错的**，正确做法是给够并观察 GC 与 MSPT。

### 2.3 磁盘：SSD 与 IOPS

世界保存、区块加载、备份打包全都吃磁盘。**磁盘慢的时候 CPU 看起来还很闲**，这是最难定位的一类卡顿。

- **必须 SSD。** 机械盘跑现代服务端体验极差，尤其是区块加载。
- 比"是不是 SSD"更重要的是**随机读写能力（IOPS）**与**是否与其他租户共享**。
- **磁盘快满是会毁数据的**，所以可用空间要留出余量（备份、日志、核心转储都吃空间）。

### 2.4 带宽

- **上行（出方向）才是瓶颈**：玩家下载区块、获取资源包走的都是你的上行。
- **家宽通常是非对称的**，上行很小；机房线路通常对称。
- **流量计费与带宽计费是两种不同的模式**，前者按 GB 结算、后者按 Mbps 峰值结算，账单风险完全不同。

### 2.5 DDoS 防护

对 Minecraft 来说，防护不是"高级选项"：

- Java 版走 TCP（默认 25565），基岩版走 **UDP**（默认 19132），**UDP 洪泛是基岩版最典型的攻击形式**。
- 廉价套餐通常**不包含**有效防护，或者只送一层很薄的清洗。
- **高防通常是按月附加费，且价格与防护带宽挂钩**；具体形式与价格以服务商为准。

防护思路与攻击类型见 [常见网络攻击类型与 Minecraft 专项防御](/tutorials/ops/attack-defense)。

### 2.6 备份空间

**备份要占的空间往往和你的世界一样大，而且需要多份。** 常见的错误是"主机买得很省，备份没地方放"，结果备份脚本默默失败好几个月——直到你需要它的那一天。

- 备份要**放在你租的主机之外**（异地/对象存储），见 [异地备份](/tutorials/ops/offsite-backup)。
- 对象存储的**取回（下行）流量通常单独计费**，恢复演练也会花钱。
- 保留策略（保留几份、留多久）直接决定成本。

### 2.7 你自己的时间

这是唯一一项**几乎所有人都算成 0** 的成本，而它通常是最大的一项：

- 每周的更新、插件兼容排查、备份验证。
- 玩家管理：白名单、申诉、纠纷、熊孩子。
- 事故处理：被攻击、崩服、丢档、被入侵。

**如果你的时间不值钱，那是因为你还没有把它记进账。** 一个需要你每周投入 5 小时的方案，和一个月费贵 50 元但省下 3 小时的方案，后者往往更划算。

### 2.8 线路与延迟

带宽数字决定"能装多少人"，**线路与延迟决定"手感好不好"**。两者不能互相替代：

- 玩家与服务器之间的**往返延迟（RTT）**直接影响挖掘、攻击、走位的响应感受；延迟高的时候，带宽再大也没用。
- **机房位置与线路质量**往往比带宽更重要：同样的 100 Mbps，不同线路对国内玩家的实际体验可能差很多。
- **跨运营商访问**是常见的坑：某一家的玩家很快，另一家的玩家一直在跳延迟。
- 测法是**用真实客户端从玩家的网络去连**，而不是只在服务器上 `ping` 网关：`mtr` / `traceroute` 能看出丢包发生在哪一跳。

### 2.9 计费周期、退款与合同

这些条款不影响性能，但**决定你"买错了"要付多少代价**：

- **按小时/按量计费**适合试错，但单价通常更高；**月付**是大多数个人服的平衡点；**年付**折扣最大、锁定最深。
- **退款政策**要看清楚：有的商家"随时退"，有的只在首次购买后若干天内退，有的按已用时长折算。
- **续费价可能高于首单价**，这是常见的促销结构，算长期成本时要看续费价。

:::note 判断"能不能试"的最快方法
下单前先问一句：**如果三天后发现性能不行，我能拿回多少钱？** 答案含糊的商家，把"年付"换成"月付"再决定。
:::

## 3. 七种方案对比

下表是**定性对比**，不涉及具体价格。读的时候重点看最后两列：**隐藏成本**和**什么时候别选它**。

| 方案 | 适用规模 | 优点 | 缺点 | 隐藏成本 | 什么时候别选它 |
| --- | --- | --- | --- | --- | --- |
| 家用电脑 / 家庭宽带 | 朋友小服、测试、临时开 | 一次性投入、数据在自己手里、可随时折腾 | 上行小、可能没有公网 IP、断电与断网就停服、家里网络被攻击会波及全家 | 电费、噪声与热量、硬件折旧、需要自己维护 UPS 与路由器、时间成本最高 | 面向公网、需要 7x24 稳定、需要抗攻击、玩家规模超过十余人 |
| 共享虚拟主机 | 静态网站、PHP 站点 | 便宜、开箱即用 | **通常不能跑长期进程，也不能开放自定义端口**，资源限额严格 | 升级无路可走、迁移成本 | **基本上都不适合 Minecraft 服务端**，除非商家明确卖的是游戏服 |
| VPS | 中小规模、个人服、代理端 | 价格适中、有 root、可自选系统与内核 | 资源与邻居共享、廉价套餐普遍超售、防护通常很薄 | 带宽多为"共享"或按流量计费、快照另收费、被攻击时可能被停机 | 需要大内存模组整合包、需要强防护、需要独享物理性能 |
| 独立服务器 | 中大规模、模组整合包、多实例 | 物理独享、性能稳定可预期、可自选硬件 | 月费高、开通慢、硬件故障要等机房处理 | 带宽与防护常单独计价、IP 与机位费、维保与备件 | 只有几个人玩、预算敏感、自己不打算做运维 |
| 面板服 / 游戏主机商 | 想少折腾的中小服 | 面板、备份、定时任务现成，按内存或槽位卖 | 只能用它给的环境、自定义受限、超售常见 | 附加内存与附加备份的加价、迁移受限于商家工具、CPU 限额不写在广告上 | 需要自定义系统或内核、需要特殊 mod 环境、需要长期低成本大规模 |
| 云服务器按量 | 波动负载、短期活动、测试 | 弹性、按需开停、生态完善（快照、镜像、监控） | **账单不可预测**、默认配置通常偏贵、需要自己搭一切 | 公网 IP、快照存储、镜像、日志、出网流量的单独计费；忘记关机就一直在烧钱 | 长期稳定负载（包年包月通常更划算）、不设预算告警的团队 |
| 托管 / colocation | 自有硬件、规模化、合规需求 | 硬件自主、长期单位成本可能更低 | 需要自备硬件、签合同、故障要自己处理 | 机位费、电力费、带宽费、远程手（remote hands）费用、到场时间 | 只有一台机器、没有备件、没有运维能力 |

### 3.1 家用电脑 / 家庭宽带

它的定位很清楚：**成本最低、可控性最高、可靠性最低**。适合朋友之间的小服。判断能不能用，先确认三件事：**有没有公网 IP**（很多家宽是 CGNAT，根本没有）、**上行有多大**、**运营商条款是否允许长期对外提供服务**。详细做法与坑见 [家用电脑开服与维护](/tutorials/ops/home-hosting)。

### 3.2 共享虚拟主机

**它不是 Minecraft 的选项。** 共享主机卖的是"网站运行环境"：没有长期驻留的进程、不能监听任意端口、CPU 与内存有硬限额。少数商家把"游戏服"也归到这个词下，那种其实是面板服或容器，按 3.5 判断。

### 3.3 VPS

个人与小团队最常用的方案。要点是：**便宜套餐的"核数"参考价值有限，单核性能与磁盘 IOPS 才是关键**；带宽要看清是"独享"还是"共享"、是"不限流量但限速"还是"按流量计费"。

### 3.4 独立服务器

当整合包、多实例或玩家规模把 VPS 逼到墙角时，独服是自然的下一步。它的价值是**可预期**：物理核、物理盘、物理带宽。代价是**月费与运维责任一起上升**。

### 3.5 面板服 / 游戏主机商

适合"我不想碰 Linux"。它的钱主要花在**省时间**上，所以判断标准是：**它省的运维时间，是否大于它的溢价**。注意两点：**广告上的 CPU 型号往往不等于你实际分到的性能**；**迁移工具通常只能迁出它自己的格式**，走之前先确认你的存档与配置能不能完整带走。

### 3.6 云服务器按量

按量的优势是弹性，劣势是**账单的不可预测性**。开一台机器做测试很爽，忘关一个月也很"爽"。如果要用，先做三件事：设**预算告警**、设**自动关机或到期提醒**、把**公网 IP 与快照的计费方式**看明白。

### 3.7 托管 / colocation

它是"我已经有硬件，也有运维能力"的答案。单位成本随规模下降，但**门槛与责任也随规模上升**：硬件故障时没有服务商替你换盘，只有你自己（或者付费的 remote hands）。

## 4. 容易漏掉的成本项

| 成本项 | 为什么容易漏 | 怎么避免 |
| --- | --- | --- |
| 公网 IP / 弹性 IP | 有些商家把 IP 单独计价，闲置的 IP 也可能收费 | 下单前在价格页确认 IP 是否包含、闲置是否计费 |
| 流量超额计费 | "不限流量"常附带公平使用条款或限速 | 看清是限速还是计费、超额单价是多少 |
| 备份存储 | 备份不占主机空间，但占对象存储的钱 | 先算世界大小 x 份数，再选保留策略 |
| 快照 | 快照不是备份，而且按容量计费 | 用备份代替快照作为数据保全手段（见第 8 节） |
| DDoS 高防 | 防护带宽越大越贵，且常是月付附加项 | 明确"基础防护"能扛住什么，再决定要不要买 |
| 域名与证书 | 域名按年续费，忘了续费会直接失去解析 | 开自动续费；证书见 [HTTPS 证书与自动续期](/tutorials/ops/https) |
| 电费与噪声（家宽方案） | 电脑 7x24 开着，电表与耳朵都知道 | 按当地电价估算（见下方示例），并考虑散热与噪声 |
| 时间成本 | 没人把它写进预算表 | 每周记录一次实际投入，几个月后你会改主意 |
| 迁移成本 | 搬家不是复制文件，而是**一次维护窗口** | 见 [服务器迁移](/tutorials/ops/server-migration) |

:::tip 电费的一个算例
一台平均功耗约 60 W 的机器 7x24 运行：60 W x 24 h = 1.44 kWh/天，约 43 kWh/月。按 0.6 元/kWh 计，约 **26 元/月**。这只是一个算例：**功耗与电价都要用你自己的数字重算**，显示器、路由器、UPS 与空调的额外负担另计。
:::

## 5. 诚实地估算规模

### 5.1 玩家数到资源的粗估

下表是**量级参考，不是规格书**。真实需求受版本、核心、视距、插件、世界大小与玩法影响极大。

| 规模 | CPU | 内存（服务端堆） | 带宽 | 备注 |
| --- | --- | --- | --- | --- |
| 2 - 5 人，朋友服 | 单核较强的双核即可 | 2 - 4 GB 量级 | 家宽上行通常够用 | 家用电脑往往就够 |
| 10 - 20 人，原版/轻插件 | 高单核性能，2 - 4 核 | 4 - 8 GB 量级 | 几 Mbps 量级 | 视距与实体数量影响巨大 |
| 30 - 50 人，插件服 | 高单核 + 多核辅助 | 8 - 16 GB 量级 | 十几 Mbps 量级 | 需要真正的 SSD 与稳定线路 |
| 模组 / 整合包 | 高单核性能优先 | 常为原版数倍 | 取决于同步量 | **以整合包官方说明为准** |
| 多实例 / 群组服 | 多核开始有意义 | 各实例相加再加代理与数据库 | 叠加 | 见 [跨服端](/tutorials/java/proxy) |

**带宽的粗估**：稳态下每个玩家通常只占**几十 KB/s 量级**（约 0.2 - 1 Mbit/s），但视距大、实体多、玩家飞行加载新区块时会明显更高，**进服瞬间发送区块的突发流量远大于稳态**。这些数字高度依赖版本与玩法，**请以你自己的实测为准**（`vnstat`、`nload`、面板的流量图都行）。

### 5.2 超售是廉价套餐的常态

"共享型""突发型""公平使用"这些词背后通常是同一件事：**你买到的是一份配额，不是一个独占的核**。这本身不是欺骗，而是廉价套餐能存在的原因；问题在于**它让"看参数买机器"这件事不可靠**。

实践建议：

- 把**单核性能**当作首要指标，而不是核数或主频数字。
- 对"长期高负载"的预期要保守：突发额度适合峰值，不适合 7x24 满载。
- **先买短周期验证**，跑起来再决定要不要长期。

### 5.3 别只看单价，算单位成本

比较两个方案时，把它们换算成同一口径：**每月总支出 ÷ 可稳定支撑的玩家数**。这样一算，"贵 30% 但能多带一倍玩家"的方案往往立刻变得划算。

### 5.4 先买小、再长大

一个反直觉但很实用的策略：**先买明显偏小的一档，验证真实瓶颈，再按瓶颈加钱。**

原因是**大多数人会高估自己的规模**。开服前想的是"以后会有 50 人"，现实往往是前三个月平均在线 3 人。如果一开始就按 50 人买，你会在很长一段时间里为不存在的玩家付费。

具体做法：

1. 按"当前规模 + 一点余量"买最小的可用档位。
2. 用 [监控与告警](/tutorials/ops/monitoring) 记录 CPU 单核占用、内存、磁盘 I/O 与带宽的真实曲线。
3. 数据说话再升级：**升配通常比降配容易**，而且很多商家支持在线升配（**是否支持、是否要重启，以商家文档为准**）。
4. 如果瓶颈是磁盘 I/O 或单核性能，**加内存是没用的**——这时要考虑换商家而不是升套餐。

## 6. 买之前怎么测

### 6.1 单核性能比核数重要

第三方跑分（如常见的单线程评分）可以作为**粗筛**，用来排除明显不行的机器，但它**测不出超售、邻居干扰与磁盘瓶颈**。所以跑分只用来缩小范围，最终判断要靠实测。

### 6.2 要试用，或者先买最短周期

- 优先选**提供试用或按小时计费**的商家，跑一次真实负载再决定。
- 没有试用就**先买最短周期**（月付甚至按天），不要一上来就年付。
- **一定要测"你的真实场景"**：把服务端、插件、存档搬上去，叫几个人进来玩一次，比任何跑分都有说服力。

### 6.3 测磁盘 I/O

磁盘是廉价套餐最容易偷工减料的地方。两种常见测法：

```bash
# 顺序写测试：在目标文件系统上建临时文件，测完删掉
dd if=/dev/zero of=./io-test.bin bs=1M count=1024 conv=fdatasync status=progress
rm -f ./io-test.bin

# 随机读测试（需要安装 fio；参数含义以 fio 官方文档为准）
fio --name=randread --rw=randread --bs=4k --iodepth=32 \
    --size=1G --numjobs=1 --time_based --runtime=30s --group_reporting
```

读结果时注意：`dd` 的顺序写数字**容易偏乐观**（受缓存与文件系统影响），随机读的 IOPS 才更接近区块加载与存档写入的真实压力。**测试会在磁盘上产生大量写入，请在临时目录做，测完删除，不要在服务端数据目录里做。**

## 7. "现在便宜、以后贵"的陷阱

| 陷阱 | 便宜在哪 | 贵在哪 | 怎么绕开 |
| --- | --- | --- | --- |
| 迁移成本被无视 | 选了最便宜的机器 | 搬家要停机一次，还要处理 DNS、白名单、备份、监控 | 一开始就选**能导出完整数据**的方案，并把搬家当作必然事件；见 [服务器迁移](/tutorials/ops/server-migration) |
| 没有备份空间 | 只买了主机，没买存储 | 一次丢档就是全部进度 | 备份从一开始就放在主机之外；见 [异地备份](/tutorials/ops/offsite-backup) |
| 没有 DDoS 防护 | 省下防护月费 | 被攻击时掉线、被商家停机、玩家流失 | 至少确认基础防护的能力边界；见 [常见网络攻击类型与 Minecraft 专项防御](/tutorials/ops/attack-defense) |
| 超流量账单 | 按量计费单价看起来低 | 一次攻击或一次资源包分发就能烧掉一个月预算 | 设预算告警、优先选限速而非计费、把资源包放对象存储 |
| 年付锁定 | 年付折扣很香 | 商家跑路、性能不达标、想换也换不了 | 第一年先月付，稳定后再考虑长期 |
| 时间被算成 0 | 自己动手"不要钱" | 每周几小时的持续投入 | 把时间记进预算表，定期复盘 |

## 8. 合法地降低成本

这些做法**不牺牲可靠性**，只是把资源花在刀刃上：

- **降低视距（view-distance）**：这是最有效的单项优化，直接减少区块发送与实体处理。
- **减少常驻世界**：每个额外维度/世界都在吃内存与磁盘 I/O；不用的先关掉。
- **定时重启**：缓解内存缓慢增长与句柄泄漏（**但它不是修复，只是掩盖**；要同时查根因）。
- **用备份代替快照**：快照按容量计费且不等于可恢复的备份；正确的数据保全见 [备份与恢复](/tutorials/java/backup)。
- **预生成世界**：把区块生成的开销挪到开服前，减少运行时的单核尖峰。
- **自己跑面板**：面板服省的是时间，如果你本来就会 Linux，自建面板可以省下溢价（代价是多一个要维护的组件，见 [面板管理工具的使用与安全](/tutorials/ops/panels)）。
- **关掉不用的服务**：网页地图、额外实例、测试服，都是持续占资源的。
- **合并低峰**：玩家集中在晚上时，可以只在那段时间开高配实例。

:::warn 降成本的两条红线
**不要省备份，不要省防护。** 这两项省下来的钱，通常会在第一次事故里连本带利还回去。可以降配、可以换便宜机器，但**能恢复的数据**与**能扛住的攻击**是底线。
:::

## 10. 小结

- **先估规模，再选方案。** 玩家数、是否模组、是否对外公开，决定了你根本不需要考虑哪些选项。
- **单核性能 > 核心数量**，**磁盘 IOPS > 磁盘容量**（在够用的前提下）。
- **把一次性、每月、变动、时间四类成本分开算**，隐藏成本大多在第三、四类。
- **小服的最优解通常很简单**：朋友之间玩，家用电脑或最便宜的、够用的 VPS 就很好，重点是**备份**。
- **公开服是另一回事**：一旦对公网开放，**真正的防护与真正的异地备份就不是可选项**，主机预算也要按这个前提来定。
- **搬家能力要在买的时候确认**，而不是在要搬的时候才发现。
