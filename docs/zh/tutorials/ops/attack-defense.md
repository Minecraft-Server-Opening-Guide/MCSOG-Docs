[网络安全基础](/tutorials/ops/network-security) 讲的是"把门关好"：只开必要的端口、限制来源、加固 SSH。这一篇讲另一种情况：**门是关好的，但有人正拿卡车撞门**。

先给一个不讨喜但必须说清楚的结论：**流量型攻击（volumetric）不是靠服务端配置能解决的**。本文会解释为什么，以及在这个前提下你**真正**能做什么。

## 1. 攻击类型分类

按 OSI 层次粗分，你遇到的攻击几乎都落在这两类里。

### 1.1 第三、四层：流量型与协议型

| 攻击 | 协议 | 特征 | 主要影响 |
| --- | --- | --- | --- |
| **UDP flood** | UDP | 海量 UDP 包砸向某个端口或随机端口 | 带宽饱和、网卡与软中断被打满 |
| **SYN flood** | TCP | 只发 `SYN` 不完成握手，占满连接表 | 新建连接失败、`backlog` 溢出 |
| **ICMP flood** | ICMP | 大量 `echo request`（ping） | 带宽与中断开销 |
| **反射放大** | UDP | 伪造源 IP 向第三方发查询，回包砸向你 | 带宽饱和，**且你看到的是无辜第三方** |

**反射放大（reflection / amplification）** 的原理值得单独说清楚：攻击者伪造**你的 IP** 作为源地址，向大量开放服务（DNS 解析器、NTP、memcached、SSDP、CLDAP）发送一个**很小的请求**，这些服务器把**很大的响应**发回给"请求者"，也就是你；你收到的流量 = 攻击者发出的流量 × 放大倍数。

**放大倍数（amplification factor）** = 响应字节数 / 请求字节数。它取决于第三方服务的配置，不同协议、不同实现、不同版本差异极大，因此下表只是**量级参考**，不要当成精确值：

| 反射源 | 常见端口 | 放大倍数量级 | 说明 |
| --- | --- | --- | --- |
| DNS | UDP `53` | 约 数十倍 | 取决于响应大小与是否支持 EDNS |
| NTP | UDP `123` | 约 数百倍 | 主要是历史上 `monlist` 查询被滥用；现代 NTP 默认已限制 |
| memcached | UDP `11211` | 极高（可达数万倍） | 影响极大，但前提是存在暴露在公网的 UDP 版 memcached |
| SSDP | UDP `1900` | 约 数十倍 | 家用路由器与智能设备的 UPnP 服务 |
| CLDAP | UDP `389` | 约 数十倍 | 暴露的 LDAP 服务 |

:::warn 为什么"源 IP 是伪造的"
UDP 是**无连接**协议：内核收到一个 UDP 包，不会先去验证"这个源地址真的能收到回包"，因此攻击者可以随意填写源 IP，**把它写成你的 IP**。

后果非常关键：**你抓到的包源地址是假的**。**对伪造源 IP 的 UDP 流量，溯源和封 IP 基本无意义**——封了只会误伤无辜的第三方。
:::

### 1.2 第七层：应用层攻击（Minecraft 专项）

应用层攻击不打带宽，打的是**你程序的处理能力**：每一个请求都要消耗 CPU、内存或数据库连接，而攻击者的成本远低于你的成本。

Minecraft 相关的应用层攻击主要有三类，本文后面各有一节：

| 类型 | 一句话描述 | 见 |
| --- | --- | --- |
| **状态查询（MOTD ping）洪水** | 疯狂刷新服务器列表，逼你反复构造响应 | 第 4 节 |
| **假人压测（bot / 假人）** | 大量机器人进服或半开连接，占满槽位与资源 | 第 5 节 |

### 1.3 一个决定性的区别：能不能找到攻击者

这是本文最重要的一条分界线：

| 流量类型 | 能否识别攻击者 | 原因 |
| --- | --- | --- |
| **伪造源 IP 的 UDP 流量** | **基本不能** | 源地址是假的，回包不会到达攻击者 |
| **基于 TCP 的机器人攻击** | **通常可以** | 要建立 TCP 连接必须完成三次握手，握手要求**对方的 IP 真实可达** |
| **登录 / 进服类攻击** | **通常可以** | 要走到握手（handshake）之后，必须先有真实 TCP 连接 |

**实践含义**：

- 对 UDP 洪水，你的手段只剩"限速 + 上游清洗"，**别指望封 IP**；
- 对 TCP 机器人洪水，**连接层面的限制（connlimit、连接频率）和账号层面的验证（`online-mode`、白名单）是有效的**，因为对方必须暴露真实地址、并且（如果开了正版验证）必须持有真实账号。

## 2. DDoS 基础：为什么"封攻击者 IP"没用

### 2.1 DDoS 是什么

**DoS** 是用一份流量让服务不可用；**DDoS（Distributed DoS）** 是用**成千上万台**分布在不同网络、不同运营商的机器同时打你。这些机器通常是被感染的普通设备、廉价 VPS 或物联网设备，统称**肉鸡（botnet）**。关键不是"单台机器多强"，而是**聚合带宽**：1000 台设备各出 10 Mbps，就是 10 Gbps。

### 2.2 为什么"封掉攻击者 IP"对流量型攻击无效

这是最普遍的误解，值得完整解释一遍：

1. **流量已经在你的链路上。** 你的防火墙（`iptables` / `nftables` / Windows 防火墙）运行在**你的机器或你的路由器上**。当攻击流量到达这块网卡时，你的**上行链路已经被占满了**。防火墙能做的只是"丢掉这些包"，但**丢包不会让带宽变回来**——链路依然是满的，正常玩家依然连不上。
2. **丢包本身也要消耗资源。** 海量小包会在网卡中断和软中断（softirq）上消耗大量 CPU，严重时连你的 SSH 都进不去，日志也写不出来。
3. **源 IP 数量巨大且不断变化。** 你不可能维护一份百万条的黑名单；而且对伪造的 UDP 源地址，黑名单里全是无辜者。
4. **你的上游才是瓶颈。** 决定你能不能扛住的，是**机房的接入带宽**和**运营商/服务商是否在你前面做了清洗**，而不是你机器上的规则。

### 2.3 服务商与机房真正能做的事

| 手段 | 在哪一层生效 | 说明 |
| --- | --- | --- |
| **容量（capacity）** | 上游 | 机房接入带宽大于攻击流量，攻击"打不疼"。这是最根本的一层。 |
| **上游清洗（scrubbing）** | 上游 | 流量先被牵引到清洗中心，过滤后再回注给你。**这是应对流量型攻击的主要手段。** |
| **边缘限速（rate limiting）** | 上游或你的边界 | 在进入你的机器之前限制速率，保护后端。 |
| **架构调整** | 你的设计 | 用代理隐藏源站、把服务放到有防护的入口后面、把静态资源交给 CDN。 |

:::warn 不要假设"云服务器自带 DDoS 防护"就够了
各家云服务商的免费防护**阈值、清洗方式、触发条件、是否额外收费、是否提供高防 IP** 差异极大，且条款会变。**买之前去读官方文档和合同条款**，明确：免费防护的阈值、超限后是黑洞（直接封掉你的 IP）还是清洗、是否有高防产品、换 IP 的政策。**这些细节本文不臆测，以你所用服务商的官方说明为准。**
:::

## 3. UDP flood 与基岩版的暴露面

### 3.1 基岩版为什么天然更容易被打

| 事实 | 后果 |
| --- | --- |
| 基岩版使用 **UDP `19132`**（IPv6 为 `19133`） | UDP 无连接、易伪造，**既好打又难溯源** |
| **Geyser** 同样监听 UDP（默认与基岩版一致，可配置） | Java 服只要开了跨端，就多了一个 UDP 入口 |
| UDP 没有握手 | 攻击者不需要真实 IP，也不需要完成任何协商，**发一个字节就是一个包** |
| 服务端需要回应 | 有些查询类请求的处理成本高于请求本身，形成天然的放大面 |

### 3.2 被打时的症状

- **带宽曲线打满**，但服务端日志里可能什么异常都没有；
- **TPS 正常、玩家却频繁超时**：服务端本身没卡，是**网络路径**被占满了；
- 网卡收包速率飙升、`softirq` 占用高，SSH 变得极难连上甚至完全连不上。

观察用的命令（均为只读查询）：

```bash
# UDP 监听套接字（ss 显示的是套接字，不是流量）
ss -uanp

# 网卡累计收发包与丢包计数（换成你实际的网卡名，如 eth0 / ens3）
ip -s link show dev eth0

# 内核计数器，对比两次采样的差值
cat /proc/net/dev

# 防火墙规则命中计数（需 root）
sudo iptables -L INPUT -v -n

# nftables：查看带计数器或动态集合的规则
sudo nft list ruleset
```

:::note 计数器怎么看才有意义
`/proc/net/dev`、`ip -s link`、`nft list ruleset` 给出的都是**累计值**。判断"是不是正在被打"，要看**单位时间的增量**：间隔十几秒采样两次，比较 `RX bytes` / `RX packets` 的差值，再换算成 Mbps 与 pps。一次采样说明不了问题。
:::

### 3.3 防御：先缩小暴露面

**最重要的一条：只开你真正需要的 UDP 端口。** 纯 Java 服（没有 Geyser、没有跨端）**不需要**任何 UDP 端口对公网开放；需要基岩版或 Geyser 时，只开 `19132`（以及确实需要的 IPv6 `19133`）；不要因为"教程里写了"就顺手开一堆 UDP 端口，不需要的端口关掉，攻击面直接消失。

### 3.4 主机侧限速：iptables hashlimit

`hashlimit` 模块按"某个键"（这里用源 IP）分别统计速率，超过阈值即命中规则：

```bash
# 1) 先"只记录不丢弃"，用来观察真实流量基线（推荐先跑一两天）
sudo iptables -A INPUT -p udp --dport 19132 \
  -m hashlimit --hashlimit-above 200/sec --hashlimit-burst 400 \
  --hashlimit-mode srcip --hashlimit-name mc-udp-observe \
  -j LOG --log-prefix "MC-UDP-OVER: " --log-level 4

# 2) 观察确认阈值合理后，再加真正的丢弃规则
sudo iptables -A INPUT -p udp --dport 19132 \
  -m hashlimit --hashlimit-above 200/sec --hashlimit-burst 400 \
  --hashlimit-mode srcip --hashlimit-name mc-udp \
  -j DROP
```

参数说明：

| 参数 | 含义 |
| --- | --- |
| `--hashlimit-above 200/sec` | 单源 IP 超过 200 包/秒即命中。**单位后缀必须写**（`/sec`、`/min`、`/hour`、`/day`），写成裸数字在多数版本上会报错 |
| `--hashlimit-burst 400` | 允许的突发量：突发窗口内前 400 个包放行，用于容忍正常的瞬时抖动 |
| `--hashlimit-mode srcip` | 按**源 IP** 分别计数（也可用 `srcport`、`dstport` 等） |
| `--hashlimit-name mc-udp` | 内核里的表名，**同名规则共享计数**，所以观察规则和丢弃规则要用不同名字 |
| `-j LOG` / `-j DROP` | 前者记录到内核日志（`dmesg` / `journalctl -k`）用于观察；后者静默丢弃。也可用 `-j REJECT`，但 UDP 上 REJECT 会回 ICMP，通常没必要 |

:::warn 这些命令的可用性取决于内核与版本
`hashlimit` 需要内核支持 `xt_hashlimit` 模块，且 `iptables` 要能在 `-m hashlimit` 时自动加载它。**规则语法在 `iptables-legacy` 与 `iptables-nft` 两种前端上一致，但持久化方式不同。** 若提示找不到模块或选项，请对照你系统上 `iptables --version`、`modinfo xt_hashlimit` 的结果与发行版文档；另外 `iptables` 规则**默认不持久化**，重启即丢，保存方式见 [网络安全基础](/tutorials/ops/network-security)。
:::

### 3.5 主机侧限速：nftables 动态集合 + `limit rate over`

`nftables` 的现代做法是**按源 IP 建一个动态集合**，对超过阈值的源地址打标记，再丢弃。

下面是一个**完整可加载**的最小示例（保存为 `mc-udp-limit.nft`，用 `sudo nft -f mc-udp-limit.nft` 加载）：

```bash
#!/usr/sbin/nft -f

# 先清掉同名旧表，避免重复加载报错；执行前确认没有别的规则依赖它
table inet mcguard
delete table inet mcguard

table inet mcguard {
    set udp_flood_v4 {
        type ipv4_addr
        flags dynamic, timeout
        timeout 10m
    }

    chain input {
        type filter hook input priority 0; policy accept;
        udp dport 19132 jump udp_guard
    }

    chain udp_guard {
        # 单源超过 200/秒（突发 400）时加入集合
        update @udp_flood_v4 { ip saddr limit rate over 200/second burst 400 packets }
        # 被限速的源写入内核日志，便于观察；再直接丢弃
        ip saddr @udp_flood_v4 log prefix "MC-UDP-OVER: " level warn
        ip saddr @udp_flood_v4 drop
    }
}
```

要点说明：

| 语法 | 含义 |
| --- | --- |
| `set ... { type ipv4_addr; flags dynamic, timeout; timeout 10m; }` | 动态集合，元素会自动过期，**不会无限增长** |
| `limit rate over 200/second burst 400 packets` | "**超过**" 200/秒才算命中（对比 `limit rate` 是"不超过"）。`over` 是关键字 |
| `update @set { ... }` | 命中时把键（`ip saddr`）**写入集合** |
| `ip saddr @set drop` | 集合里的源地址一律丢弃，因此**命中一次后，该源在集合过期前会被持续丢弃**；示例只按 `ip saddr`（IPv4）建集合，**IPv6 需另建 `ipv6_addr` 集合与对应规则** |

:::warn 上述 nftables 写法与版本相关
`flags dynamic, timeout`、`limit rate over` 与 `update @set` 都属于较新的语法，**请以你系统上 `nft --version` 与 nftables 官方 wiki 为准**。加载前建议先 `sudo nft -c -f mc-udp-limit.nft`（`-c` 为语法检查，不实际加载）。**规则集一旦写错，可能把自己锁在门外**——务必先确认你有云平台 VNC 或救援控制台。
:::

### 3.6 限速的代价：合法玩家也会被误伤

**每一条限速规则都是一个潜在的误报来源。** **正常玩家不会只发 200 包/秒**，但**网络抖动、丢包重传、或某些客户端/插件的突发行为**会造成短时高峰；阈值定得太低会**误伤真实玩家**且很难排查，定得太高则攻击流量早就穿透了。

因此推荐的做法是**先观察，再丢弃**：

1. 先只加 `LOG`（iptables）或 `log`（nftables）规则，阈值设在**你预期正常峰值的数倍**；
2. 观察一两天，看日志里有多少来自"看起来正常"的 IP，确认不会误伤后再改成 `DROP`；
3. 上线后持续关注玩家反馈，随时调整。

:::tip 限速是"减伤"，不是"免疫"
主机侧限速能显著降低**低强度**洪水的伤害，也能让高强度的洪水**稍微晚一点**打满链路，但**无法**让 10 Gbps 的攻击不占满 1 Gbps 的链路。真正的解法永远在上游。
:::

## 4. MOTD / 状态查询洪水（Minecraft 专项）

### 4.1 状态查询协议是什么

Minecraft 客户端在服务器列表里显示"在线人数 / MOTD / 延迟 / 版本 / 图标"，靠的是**状态查询**。它的特点是：**任何客户端都能查询，不需要登录、不需要账号、不需要进服。**

| 平台 | 查询方式 | 传输 |
| --- | --- | --- |
| **Java 版** | Server List Ping（现代状态请求，在游戏端口上） | **TCP**，默认 `25565` |
| **基岩版** | Unconnected Ping / Pong（RakNet） | **UDP**，默认 `19132` |

攻击者喜欢它的原因很直接：**发送成本极低**（一个很小的请求），**响应成本更高**（服务端要组装 MOTD、玩家列表、图标、版本信息），**可以放大**（把源 IP 伪造成受害者地址，让响应去打别人），**可以探路**（先用大量查询测你的响应能力、看在线人数、判断你背后是不是有防护，再决定打多大）。

### 4.2 关闭 query 协议：能做，但要理解它关的是什么

原版 `server.properties` 里有两个相关键：

```properties
enable-query=false
query.port=25565
```

:::warn 关闭 query 不等于隐藏 MOTD
- **query 协议**（`enable-query`）是历史遗留的 **GameSpy4 查询协议**，走 **UDP**，默认端口由 `query.port` 指定，用来给第三方工具/网站查询服务器信息；
- **服务器列表看到的状态信息（MOTD、人数、延迟）** 走的是**现代 Server List Ping**，在 Java 版上是**游戏端口上的 TCP 状态请求**，与 query 是**两套完全不同的东西**。

所以：**把 `enable-query` 设为 `false`，并不会让你的服务器从玩家的服务器列表里消失，也不会隐藏 MOTD**，它只是关掉了一个你大概率根本不需要的额外查询入口。不需要第三方查询工具时，关掉它是减少暴露面的好事，但别指望它防住 ping 洪水。
:::

### 4.3 针对状态端口的限速

思路与第 3 节完全一样，只是换成 TCP：

```bash
# Java 版：限制单源 IP 对 TCP 25565 的"新建连接"速率
# 注意：这条只对新建连接有效，已建立连接不受影响，因此不会影响正在游戏的玩家
sudo iptables -A INPUT -p tcp --dport 25565 --syn \
  -m hashlimit --hashlimit-above 10/sec --hashlimit-burst 20 \
  --hashlimit-mode srcip --hashlimit-name mc-ping \
  -j DROP
```

要点：`--syn` 只匹配**发起连接**的包，**不会误伤已在线玩家**；阈值（示例 10/秒）要按你的实际情况调——一个玩家正常只会查询几次，但**同一个 NAT 出口后面的多个玩家会共享源 IP**，学校、网吧、家庭共享网络都容易误伤，所以别设成 `1/sec`。nftables 等价写法是把第 3.5 节的集合类型改成 `ipv4_addr`、匹配条件改成 `tcp dport 25565` 并加 `tcp flags syn`。

### 4.4 用代理挡住后端

把**代理（Velocity / BungeeCord）放在最前面**，后端服只接受代理的连接，是性价比很高的一步：

- 玩家的连接先打到代理，**后端服的 IP 不出现在玩家列表里**，攻击者需要先找到真实地址；
- 代理可以做连接频率限制、配合转发密钥校验，**未通过校验的连接直接被拒**；后端服也可配置为只信任代理（转发模式相关设置，**键名随软件与版本不同，请以你自己生成的配置与官方文档为准**）。

代理的搭建与转发配置见 [跨服端](/tutorials/java/proxy)。

### 4.5 Minecraft 专用过滤服务

市面上有**面向 Minecraft 的过滤/防护服务**（例如 TCPShield 这一类）：玩家先连到服务商的接入点，由服务商做协议层识别与过滤，再把干净流量转发到你的后端。

**这类服务通常是"选项"而非"必需品"**，因为：具体能力（支持哪些版本、是否支持基岩版/UDP、是否支持 Geyser、是否要求特定转发模式、价格与流量额度）**各家差异很大，且会随产品迭代变化**；引入第三方意味着**玩家流量经过第三方**，需要评估隐私与信任；配置通常要求后端只接受来自服务商 IP 的连接，**配错会直接导致全服不可达**。

**结论：把它当成一个可评估的方案，实际能力请以服务商官方文档为准，本文不代其承诺。**

### 4.6 基岩版的诚实结论

**基岩版无法完全关闭状态 ping**：客户端要靠它显示服务器列表信息，服务端必须应答 RakNet 的 unconnected ping。因此基岩版的抗 ping 洪水只有两条路：

1. **上游防护 / 清洗**（最有效，取决于服务商）；
2. **在边界或主机上按源 IP 限速 UDP**（第 3.4 / 3.5 节的规则，把 `--dport 19132` 用上即可）。

## 5. 假人压测（bot / 假人洪水）

### 5.1 它是什么

**假人压测**指用自动化程序制造大量"玩家"或"半成品玩家"，目的是**占满槽位、烧掉 CPU 与内存、制造聊天垃圾、让真实玩家进不来**。

常见变体：

| 变体 | 做法 | 主要消耗 |
| --- | --- | --- |
| **连接洪水（connection flood）** | 只完成 TCP 连接，不做任何 Minecraft 协议交互 | 连接表、文件描述符、握手开销 |
| **登录洪水（login flood）** | 发握手（handshake）与登录开始，但不完成登录 | 登录阶段 CPU、认证请求、内存 |
| **假人挂机（idle bots）** | 完整进服后原地不动 | 玩家槽位、实体/区块加载、内存 |
| **聊天 / 指令刷屏** | 进服后高频发聊天或指令 | 主线程解析、日志 IO、刷屏骚扰 |
| **物品 / 交互请求刷屏** | 高频发包触发交互逻辑 | 服务端主线程、反作弊插件开销 |

:::note 为什么游戏服特别怕假人
Minecraft 是**有状态的长连接**服务。Web 服务器处理完一个请求就断开，成本可以摊薄；而 Minecraft 每多一个玩家，就要**常驻内存、加载区块、同步实体、维护连接**。同样的攻击成本，对游戏服的伤害远大于对静态网站。
:::

### 5.2 防御（按有效性排序）

#### 第 1 位：`online-mode=true`（Java）/ Xbox Live 验证（基岩）

**这是单项最有效的措施。** 打开正版验证后，进服必须持有**真实的 Mojang/Microsoft 账号**，机器人制作者必须为每一个假人准备真实账号——成本瞬间从"几乎为零"变成"按账号计费"。

Java 版 `server.properties`：

```properties
online-mode=true
```

:::warn 离线模式的代价必须想清楚
`online-mode=false` 意味着**任何人都能用任意 ID 进服**，包括冒用管理员、冒用其他玩家的名字。这属于身份层面的洞，防火墙补不了。**只有在你完全清楚代价、并且用白名单/登录插件补上身份校验时，才考虑离线模式。** 相关讨论见 [服务端配置](/tutorials/java/config)。
:::

基岩版没有 `online-mode` 这个键，它使用 **Xbox Live 身份验证**。具体开关名称与默认值**随服务端软件（官方 BDS 与各类第三方基岩服务端）和版本而不同**，请以你自己生成的 `server.properties` 与官方文档为准。**但原则上：不要为了"方便"而关闭身份验证。**

#### 第 2 位：白名单 / 允许列表

对小型服务器，**白名单是比任何限速都彻底的方案**：不认识的人根本连不上，机器人连进门的资格都没有。

Java 版 `server.properties`：

```properties
white-list=true
enforce-whitelist=true
```

| 键 | 作用 |
| --- | --- |
| `white-list` | 只允许名单内的玩家登录 |
| `enforce-whitelist` | 名单变化时**立即把不在名单上的在线玩家踢出**。不改这个键，新加入的名单要等玩家重连才生效 |

名单用控制台/游戏内指令维护（`whitelist add <玩家名>`、`whitelist list` 等，**具体语法以你的服务端版本为准**）。

基岩版使用服务器根目录下的 **`allowlist.json`**，通常由 `allowlist` 相关指令自动维护。**文件格式与开关键名随服务端软件和版本变化，请以你自己服务器生成的 `allowlist.json` 和官方文档为准，不要照抄教程里的示例文件。**

#### 第 3 位：连接频率限制（`spigot.yml`）

Spigot 及其衍生核心（Paper、Purpur 等）的 `spigot.yml` 里有连接节流设置，键路径为：

```yaml
settings:
  connection-throttle: 4000
```

| 项 | 说明 |
| --- | --- |
| `connection-throttle` | **同一来源地址两次连接之间必须间隔的毫秒数**。示例 `4000` = 4 秒；设为 `-1` 通常表示**禁用**节流 |
| 默认值 | **随核心与版本不同**，常见默认是 4000 毫秒，但不要假设你的一定是 |

**它拦得住什么**：同一个 IP 反复快速重连的脚本。
**它拦不住什么**：来自大量不同 IP 的分布式假人（每个 IP 只连一次，节流完全不触发）。

:::warn 别把节流值设得过大
设成几十秒会**严重影响正常玩家**：掉线后要等很久才能重连，多人共用一个出口 IP 的家庭/网吧更是直接进不来。建议从默认值开始，只在确有需要时小幅调整。
:::

#### 第 4 位：防火墙连接数限制

限制**单个源 IP 的并发连接数**，对连接洪水与半开登录有效：

```bash
# iptables：单 IPv4 地址最多 8 条到 25565 的并发连接
sudo iptables -A INPUT -p tcp --dport 25565 \
  -m connlimit --connlimit-above 8 --connlimit-mask 32 \
  -j REJECT --reject-with tcp-reset
```

| 参数 | 含义 |
| --- | --- |
| `--connlimit-above 8` | 超过 8 条并发连接才命中 |
| `--connlimit-mask 32` | 按 **/32** 归组，即"每个 IPv4 地址"单独计数 |
| `-j REJECT --reject-with tcp-reset` | 直接拒绝并回 RST（也可用 `-j DROP`，但 REJECT 能让客户端更快失败而不是卡住） |

nftables 等价写法（用连接跟踪计数）：

```bash
#!/usr/sbin/nft -f

table inet mcguard
delete table inet mcguard

table inet mcguard {
    chain input {
        type filter hook input priority 0; policy accept;
        # 每个源地址最多 8 条已跟踪的 TCP 连接
        tcp dport 25565 ct count over 8 reject with tcp reset
    }
}
```

:::warn 并发连接数要按你的实际玩法定
一个真实玩家通常只占 1 条连接（装了某些模组/插件的客户端可能更多）。但**同一 NAT 出口的多个玩家共享源 IP**，阈值设成 2 或 3 会直接踢掉正常玩家。**8 只是示例，请按你的玩家分布调整**；`ct count` 需要连接跟踪（`nf_conntrack`）正常工作，请确认没有把 `ct` 相关的模块或表项关掉。
:::

#### 第 5 位：Paper 的封包限流器（packet limiter）

Paper 在**全局配置**里提供了一个封包限流器：它按玩家统计**入站封包速率**，超过阈值时可以**踢出该玩家**并记录日志。它对"进服后疯狂发小包"的攻击（例如第 5.1 节的物品/交互刷屏、部分假人行为）有效。

:::warn 不要照抄教程里的配置结构
**这个配置块的键名、层级和默认值在不同 Paper 版本与不同分支之间都发生过变化。** 正确做法是：先正常启动一次服务端让它**自己生成**配置文件；打开你自己生成的文件，找到封包限流相关的块；**以文件里的实际结构为准**修改，而不是复制网上的片段；改完看启动日志有没有配置解析警告。

本节因此**刻意不给出具体键名和数值**——写一个可能过期的结构，比不写更危险。
:::

#### 第 6 位：把后端藏到代理后面

与第 4.4 节相同：**后端服的端口不要直接对公网开放**，只允许代理的 IP 连入。这样即使有人拿到了你的真实 IP，也要先突破代理这一层。配置见 [跨服端](/tutorials/java/proxy)。

#### 关于反机器人插件

社区有各种"反假人 / 反机器人 / 进服验证"插件（图形验证、指令验证、限速等）。它们**能提高攻击成本**，尤其对低质量脚本；但它们**都在应用层**：攻击流量已经到达你的服务端、已经消耗了握手与部分登录资源；而且**质量参差**，部分插件本身有性能或兼容性问题。

**建议自己评估**：看它是否还在维护、是否开源、是否与你的服务端版本兼容、在测试服压测一次再上生产。

### 5.3 `max-players` 是软限制

```properties
max-players=20
```

`max-players` 只决定**服务器列表里显示的上限**，以及在**登录阶段**拒绝对应数量的玩家。它**不是**防洪措施：机器人**在登录阶段就已经消耗了 CPU、认证请求和内存**，被拒绝之前成本已经付出；连接洪水（只建立 TCP 连接）**根本不会走到这个判断**；它也不影响带宽与查询洪水。

**把 `max-players` 当成容量声明，不要当成防御手段。**

## 6. 实战防御清单

### 6.1 分层清单（从"必须做"到"锦上添花"）

| 优先级 | 措施 | 说明 |
| --- | --- | --- |
| **必须** | `online-mode=true`（Java）/ 保持 Xbox Live 验证（基岩） | 单项最有效的反假人措施 |
| **必须** | 只开放真正需要的端口 | 没有暴露的服务无法被打；UDP 端口尤其要克制 |
| **必须** | 主机防火墙默认拒绝入站，只放行白名单端口 | 见 [网络安全基础](/tutorials/ops/network-security) |
| **必须** | 系统与软件及时更新、权限收紧 | 见 [系统安全加固](/tutorials/ops/system-security) |
| **必须** | 定期备份，且**至少一份离线/异地** | 勒索与报复性删档的最后防线，见 [备份与恢复](/tutorials/java/backup) |
| **强烈建议** | 白名单 / 允许列表（小型服） | 不认识的人根本连不上 |
| **强烈建议** | 游戏端口的按源 IP 限速 | 第 3.4 / 3.5 / 4.3 / 5.2 节的规则 |
| **强烈建议** | 监控与告警（带宽、连接数、CPU、玩家数），并选择防护条款清晰的服务商 | 见 6.3 节 |
| **建议** | 代理在前，后端不直接暴露 | 见 [跨服端](/tutorials/java/proxy) |
| **建议** | 基岩版 / 跨端玩家参考 [手机玩家支持](/tutorials/java/mobile) 规划入口 | 跨端会引入额外 UDP 暴露面 |
| **建议** | 一份书面的事件响应预案 | 见 6.4 节 |
| **锦上添花** | Minecraft 专用过滤服务 | 能力因服务商而异，先小范围验证 |
| **锦上添花** | 反机器人插件 | 自己评估，别当唯一防线 |

### 6.2 攻击类型对应表

| 攻击类型 | 真正有帮助的 | 基本没用的 |
| --- | --- | --- |
| **UDP flood（伪造源 IP）** | 上游清洗与容量、只开必要 UDP 端口、边界按源 IP 限速 | 封单个 IP、服务端插件、`max-players` |
| **反射放大（DNS / NTP / memcached / SSDP / CLDAP）** | **上游清洗**（这是唯一有效层）、机房容量 | 任何主机侧规则（链路已经满了）、向第三方投诉（你也是受害者） |
| **SYN flood** | 上游清洗、内核 `syn` 相关参数调优、负载均衡/代理层吸收 | 应用层限速、白名单 |
| **MOTD / 状态 ping 洪水** | 单源 TCP 连接速率限制、代理在前、上游过滤 | 关 `enable-query`（它管的不是这个）、封 IP（量大且分散） |
| **基岩版 ping 洪水** | 上游防护、按源 IP 限速 UDP `19132` | 关闭 ping（**做不到**）、服务端配置 |
| **连接洪水 / 登录洪水（半开登录）** | 防火墙 `connlimit` / `ct count`、`online-mode` 或身份验证、代理在前、上游清洗 | `max-players`、聊天过滤、白名单（离线模式下白名单在登录后生效） |
| **假人挂机 / 刷屏** | `online-mode` + 白名单、`connection-throttle`、封包限流、管理指令处置 | 带宽防护（这类攻击几乎不占带宽） |
| **漏洞利用 / 提权** | 及时更新、最小权限、`online-mode` | 防火墙（打的是应用层） |

### 6.3 监控与告警：没有告警等于没有监控

至少要能回答"现在是不是被打"：

| 指标 | 从哪里看 | 异常特征 |
| --- | --- | --- |
| **带宽 / 收包速率** | 服务商控制台的流量图、`/proc/net/dev`、`ip -s link`、`vnstat` | 远超历史峰值，且玩家数没有相应增长 |
| **连接数** | `ss -tan state established \| wc -l`、`ss -s` | 连接数暴涨但玩家数不变 |
| **CPU 与软中断** | `top`、`mpstat -P ALL 1` | 玩家不多但 `%soft` 很高（多为小包洪水） |
| **玩家数与登录失败** | 服务端日志、面板 | 大量登录尝试、大量异常 ID |
| **防火墙命中计数** | `iptables -L -v -n`、`nft list ruleset` | 限速规则命中数持续增长 |

```bash
# 已建立连接数（配合 ss -s 看套接字总览）
ss -tan state established | wc -l

# 每核 CPU（含软中断）每秒刷新
mpstat -P ALL 1

# 网卡累计计数（看两次采样的差值）
ip -s link show dev eth0

# 内核日志里的限速命中记录（配合 LOG / log 规则）
sudo journalctl -k | grep -i 'MC-UDP-OVER' | tail -n 20
```

:::tip 让服务商的面板替你值班
大多数云控制台提供**带宽曲线与告警**。把阈值设在"历史峰值 + 余量"上，一旦触发就收到通知——**这比事后翻日志有用得多**。具体配置路径因服务商而异，请以官方文档为准。
:::

### 6.4 事件响应预案（一页纸）

被打的那一刻不是思考的时候。提前写好：

1. **判断**：对照 6.3 的指标，先确认是**攻击**还是**自己的 bug**（插件死循环、备份任务占满磁盘 IO、世界文件损坏导致的卡顿）。
2. **止血与求助**：能扛就扛；扛不住时临时**只允许白名单 IP / 只允许代理 IP**，同时向服务商报障，说明时间、现象、流量特征，询问是否触发清洗、是否需要换 IP。
3. **留证与恢复**：保存流量图、日志、`ss` 输出——**这些是申诉与复盘的唯一依据**；攻击停止后确认 TPS、连接数与世界完整性，再解除临时限制。
4. **复盘**：攻击规模多大？哪一层顶住了、哪一层没顶住？下次要买什么、配什么？

:::warn 备份是攻击的一部分，不是附加项
**勒索与报复性删档**是真实存在的攻击方式。攻击者拿到面板或 RCON 权限后第一件事往往是删备份。所以：**至少一份备份必须在离线介质或异地，且不挂在服务端机器的可写路径上。** 具体方案见 [备份与恢复](/tutorials/java/backup)。
:::

## 7. 诚实的边界

把三句话写在这里，避免你对本文产生错误期待：

1. **服务端配置无法阻止大规模流量型攻击。** 无论 `iptables`、`nftables`、插件还是 `max-players`，都运行在**攻击流量已经到达之后**。1 Gbps 的链路面对 10 Gbps 的攻击，配置再完美也没用。**唯一真正的解法是上游容量与清洗能力。**
2. **上游能力是你买来的，不是配出来的。** 选购服务时就要看清 DDoS 条款：免费防护阈值多少、超限后是清洗还是黑洞、是否支持 UDP、是否有高防 IP、换 IP 是否收费。**这些问题在被打的当天再问就太晚了。**
3. **每一条限速都是潜在的误伤。** 限速会误伤突发流量的真实玩家、共享出口 IP 的网吧与家庭网络。**先观察、再丢弃、持续调整**，不要把网上抄来的阈值直接上生产。
