封禁是服务器运营里**唯一会直接剥夺玩家账号权益**的动作，也是最容易引发争吵的动作。这一篇讲的不是工具，而是**流程**：谁有权限封人、依据什么封、封多久、玩家怎么申辩、你如何回复。

工具层面见 [NDPReforged 联合封禁系统](/tutorials/ops/ndpr)（讲的是跨服同步封禁名单怎么装、怎么配），证据采集见 [反作弊与防破坏](/tutorials/java/anticheat) 与 [[JAVA] 安全插件](/tutorials/ops/security-java)，日常玩家管理见 [[JAVA] 经营管理](/tutorials/ops/management-java)。

:::warn 本文的命令与配置以官方文档为准
下面出现的插件名、命令语法、路径与服务名**会随服务端软件、插件版本、发行版与安装方式变化**。示例的作用是说明"该做什么"，**不是可以直接照抄的成品**；落地前请对照你所装插件与系统的官方文档，以及你自己服务器上实际生成的配置文件。
:::

## 1. 为什么需要一份写下来的流程

大多数服务器不是"坏在管理太严"，而是**坏在没有规则可循**。写下来至少解决四件事。

**第一，一致性。** 同一个行为，今天封三天、明天封永久，玩家之间会互相传："看人下菜碟。"一旦玩家相信处理结果是随机的，规则就失去了约束力——**威慑来自可预测性，而不是严厉程度**。

**第二，挡住"管理滥用"的指控。** 只要封禁是"我当时的判断"，任何一次封禁都可以被解读成私人恩怨。而"依据第 3.2 条、证据是 CoreProtect 记录、由 A 决定、由 B 复核"是**可以核验的陈述**。指控不会因此消失，但你有东西可以拿出来。

**第三，减少无谓的争吵。** 绝大多数"封禁纠纷"其实是**信息不对称**：玩家不知道被封的原因，或者只知道一句"违规"。流程里规定"封禁时必须写明原因并告知申诉渠道"，能消掉一大半这类对话。

**第四，让自己少犯错。** 冷静期、复核、留档，这些机制的成本很低，但能拦住"半夜被气到、顺手 /ban 了"这类事后后悔的操作。

:::tip 流程的最低可用版本
如果一次只能做一件事，那就做这件：**每一次封禁都留下"时间、玩家、原因、证据位置、决定人"五要素的记录**。哪怕只是 Discord 里一个固定频道，也比什么都没有强得多。
:::

## 2. 什么算可封禁的行为

规则必须**短、可检查、不靠解释**。下面这份清单可以直接抄进你的规则页，括号里是判定要点。

| 行为 | 判定要点 |
| --- | --- |
| 破坏建筑（Griefing） | 未经许可改动他人建筑或公共区域，有方块记录可查 |
| 偷窃 | 从他人容器取走物品；记录插件能给出"谁、何时、哪个坐标" |
| 作弊与漏洞利用 | 使用外挂、透视、自动点击，或利用复制、卡墙、刷物品等漏洞 |
| 仇恨言论 | 针对种族、性别、宗教、性取向、地域的攻击性言论 |
| 广告刷屏 | 在公共频道反复发布其他服务器、私服或交易信息 |
| 人肉与威胁（Doxxing） | 公开他人真实身份信息，或进行现实威胁 |
| 逃避封禁 | 换号、换 IP 继续进入；这是**加重情节**，不是独立小错 |

这份清单有三个共同特征，也是它可用的原因：**行为可观察**（有记录或截图）、**规则已公布**（玩家事先能看到）、**处置可解释**（你能说出违反了哪一条）。

关于"逃避封禁"多说一句：它通常意味着**从临时升级为永久**。理由不是"你更坏了"，而是"你已经证明临时措施对你无效"。

## 3. 什么不该封

同样重要的是**边界**。下面这些情况封人，是把自己推到理亏的一边。

- **首次的轻微失误。** 第一次误挖了别人的田、第一次在公屏说错话、第一次把东西放错地方——先提醒、先要求恢复，比直接封禁更有效，也更容易被接受。
- **对未公布规则的"违规"。** 如果某条规则从来没有写在玩家能看到的地方，那么**它不存在**。你不能因为别人不知道一条你脑子里的规定而处罚他。要处罚，先把规则补上，并说明"从即日起生效"。
- **规则解释上的分歧。** 玩家对规则的理解与你不同，这是**规则写得不够清楚**的信号，不是恶意。正确反应是修规则，而不是封人。
- **你不喜欢的行为。** 技术好、话多、爱提意见、不参与你的活动——这些都不是可封禁的行为。
- **连坐。** "他的朋友也骂过人""这个 IP 上次有问题"不是证据。处罚针对**具体账号的具体行为**。

:::note 一条好用的自检
在按下封禁之前问自己一句：**如果这条封禁被公开贴出来，我能不能只用"行为 + 已公布规则 + 证据"三样东西解释清楚？** 如果答案需要补充"他平时就那样""我早就看他不顺眼"，那这次封禁的理由不成立。
:::

## 4. 证据要求

**没有证据的封禁，等于把决定权交给了争吵。** 要求不高，但要事先约定：

| 证据类型 | 适用场景 | 注意 |
| --- | --- | --- |
| 日志（方块 / 容器记录） | 破坏、偷窃 | 最有力，能给出坐标与时间；**只能记录装上之后的事** |
| 服务端控制台日志 | 命令滥用、异常登录 | 会随日志轮转而消失，需要及时保存 |
| 截图 | 聊天、广告、建筑外观 | 容易被质疑裁剪，尽量保留上下文 |
| 录屏 | 作弊、连续行为 | 体积大，建议保留原始文件与时间戳 |
| 反作弊插件输出 | 移动异常、攻击异常 | 是**辅助**证据，单独使用容易误判 |

**记录类插件是证据链的地基。** 主流方案是 **CoreProtect**（官方定位：面向 Minecraft 服务器的数据记录与防破坏工具，仓库 <https://github.com/PlayPro/CoreProtect>），同类替代有 **Prism** 等。它的两个关键限制必须记住：

1. **它只能记录安装之后发生的事。** 被破坏了才装，之前的一概查不到。
2. **它记录的是方块与容器层面的行为**，不记录"意图"。

反作弊插件的输出要**谨慎使用**：误判是真实存在的，尤其在玩家网络抖动、TPS 掉到很低的时候。把它当作"值得人工复核的信号"，而不是"判决书"。整套防护体系的分工见 [反作弊与防破坏](/tutorials/java/anticheat)，权限与记录插件的配置见 [[JAVA] 安全插件](/tutorials/ops/security-java)。

:::tip 证据要存下来，而不是留在服务器上
截图、录屏、导出的查询结果，应当**立刻复制到服务器之外**（你的电脑、网盘、私有仓库）。日志会被轮转、世界会被回滚、插件数据会被清理，而申诉可能在一个月后才来。
:::

## 5. 分级处置阶梯

封禁不该是唯一手段。**阶梯的意义在于"让惩罚与情节匹配"**，同时给玩家改正的机会。

| 情节 | 处置 | 期限 | 记录方式 |
| --- | --- | --- | --- |
| 首次轻微违规（误挖、公屏失言） | 口头/私聊警告 | 无 | 管理员日志备注 |
| 重复轻微违规、刷屏、轻度辱骂 | 禁言（Mute） | 1 小时 ~ 24 小时 | 插件记录 + 管理日志 |
| 破坏、偷窃，情节与金额有限 | 临时封禁 | 1 天 ~ 7 天 | 封禁记录 + 证据存档 |
| 破坏规模大、作弊、仇恨言论、人肉 | 长期封禁 | 30 天 ~ 永久 | 封禁记录 + 证据存档 + 复核 |
| 逃避封禁、报复性破坏 | 永久封禁 | 永久 | 封禁记录 + 证据存档 + 复核 |
| 误判 / 证据不足 | 撤销并致歉 | 立即 | 记录撤销原因 |

几条使用规则：

1. **升级要有依据。** 从警告到封禁，中间应当有"上次已警告"的记录。没有记录就没有升级。
2. **永久封禁必须经第二人复核**（见下一节）。
3. **期限要写清楚**。`/ban` 之后玩家看到的是"你被封禁了"，所以**必须同时告知期限与原因**，否则申诉时你无法自证。
4. **记录与处置同时发生**。事后补记的"记录"在争议中几乎无效。

具体命令语法**取决于你使用的封禁插件**（不同插件的 `/ban`、`/tempban`、`/mute` 参数格式不同），请以该插件的官方文档为准。

## 6. 谁来做决定

**"人人都是管理员"是服务器管理崩坏的起点。** 不是因为它不信任人，而是因为它让**责任无法定位、标准无法统一**。

建议的最小分工：

| 角色 | 职责 | 说明 |
| --- | --- | --- |
| 决定人（一人） | 判定情节、选择处置、写记录 | 每个案件**只有一个**决定人，避免"谁先动手谁说了算" |
| 复核人（另一人） | 复核永久封禁与争议案件 | **不能与决定人同一人**；只看证据与规则，不看交情 |
| 申诉受理人 | 收取申诉、核对证据、回复 | 可以是决定人之外的人，减少"自己审自己"的观感 |
| 记录保管人 | 维护封禁与申诉档案 | 保证记录不丢、可检索 |

为什么"人人都是管理员"会破坏一致性：

- **标准不同。** 有人觉得刷屏无所谓，有人觉得该永久封。
- **权限不可追溯。** 出问题时无法确定是谁做的决定，也就无法纠正。
- **权限本身成为风险。** 权限插件（如 LuckPerms）的价值就在于**按权限节点精细授权**，而不是给所有人 OP。原版 OP 权限极大，一旦账号被盗或情绪失控，破坏是全局的。配置见 [[JAVA] 安全插件](/tutorials/ops/security-java)。
- **人情压力集中在少数人身上。** 有明确分工时，"我朋友被封了能不能通融"有一个标准答案："我复核不了，得走申诉。"

:::note 小服务器的现实做法
如果服务器只有你一个人，做不到"第二人复核"，那就用**时间**代替人：永久封禁**隔 24 小时再执行**，并在这 24 小时里把证据整理一遍。隔一天再看，很多冲动的决定会自己消失。
:::

## 7. 申诉渠道

申诉渠道必须**公开、固定、可追溯**。三种常见形态：

| 形态 | 优点 | 缺点 |
| --- | --- | --- |
| 专用邮箱（如 `appeal@example.com`） | 简单、无需额外系统、天然留档 | 玩家可能发错、内容格式不统一 |
| 论坛/表单页 | 字段可控、可公开检索（去隐私后） | 需要维护页面 |
| Discord 工单频道 | 门槛低、回复快 | 容易被刷、需要管理权限 |

**不要用"私聊服主"作为唯一渠道。** 私聊没有记录、没有排队、容易被情绪带走，也无法证明你处理过。

### 7.1 必填字段

无论用哪种渠道，表单都应当要求以下字段。缺一项就打回，这本身就是一种筛选。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 玩家名（游戏内 ID） | 是 | 用于核对封禁记录 |
| 封禁日期与时间（含时区） | 是 | 便于定位记录 |
| 系统显示的原因 | 是 | 让玩家复述你写的理由，可验证他是否看过 |
| 玩家陈述 | 是 | 发生了什么、为什么认为处理有误 |
| 相关证据链接 | 否 | 玩家自备的截图或录屏 |
| 联系方式 | 是 | 用于回复，且**只在内部保存** |

### 7.2 一个可以直接用的申诉模板

```text
【服务器名称】封禁申诉表

1. 游戏内 ID：
2. 封禁日期与时间（请注明时区）：
3. 封禁时系统显示的原因（原文照抄）：
4. 你的陈述（请写清事情经过，500 字以内）：
5. 你认为处理有误的理由（可多选）：
   [ ] 不是我做的
   [ ] 情况与记录不符
   [ ] 处罚过重
   [ ] 规则未公布 / 我不知情
   [ ] 其他（请说明）
6. 证据链接（可选）：
7. 可用的联系方式（仅管理员可见）：

提交后我们会在 72 小时内回复。请勿重复提交，重复提交不会加快处理。
```

### 7.3 响应时限（SLA）

**给一个明确的时间承诺，并尽量做到。** 建议：

- **首次回复：72 小时内**（含"我们已收到，正在核对证据"这类中间回复）。
- **复杂案件（永久封禁、涉及多人）：最长 7 天**，并在 72 小时内告知"需要更长时间"。
- **超时未回复时，玩家有权再次催促一次**，且这次催促应当被优先处理。

SLA 的意义不只是礼貌：**没有时限的申诉等于没有申诉**，玩家在等待中会把不满转移到整个社区。

:::warn 不要承诺你做不到的时限
写"24 小时内回复"很漂亮，但一次漏回复就会让整份规则失信。**宁可写 72 小时并稳定做到。**
:::

## 8. 收到申诉后怎么处理

固定动作，按顺序走：

1. **登记。** 记录收到时间、申诉人、对应封禁记录编号。**先登记再判断**，避免"看过就忘"。
2. **核对证据。** 回到原始证据：记录插件的查询结果、日志片段、截图原文。**不要依赖记忆，也不要依赖别人转述的结论。**
3. **确认规则依据。** 找出当时引用的规则条目。如果找不到，这本身就是问题（见第 11 节）。
4. **做出结论**，只有三种：
   - **维持（Uphold）**：证据充分，处置与情节匹配。回复时给出理由与证据摘要。
   - **减轻（Reduce）**：行为成立，但处罚过重或已接近期限。改为更短的期限或警告。
   - **撤销（Lift）**：证据不足、误判、规则未公布。立即解除并说明。
5. **书面回复。** 通过玩家提供的渠道回复，包含：结论、依据的规则、证据摘要（不必公开全部细节）、后续步骤。**不用嘲讽语气，不引用玩家原话去反驳他。**
6. **留档。** 把申诉原文、你的结论、时间戳写进同一份记录。**这一步最容易被跳过，也最关键**——它是你下次遇到同类案件时的参照。
7. **统计。** 每隔一段时间看一次：申诉量、维持率、撤销率。撤销率偏高说明前端判定有问题；申诉量突然上升，往往说明规则或沟通出了问题。

:::tip 回复模板（维持）
"我们核对了 <日期> 的方块记录：<坐标> 处的 <数量> 个方块在 <时间> 被你的账号移除，该行为违反规则第 <条>。因此本次封禁维持，期限至 <日期>。如果你认为记录有误，可以补充说明。"
:::

## 9. 公开与透明

透明不是"把一切公开"，而是**让规则与处理标准可被检验**。

| 做法 | 建议 | 说明 |
| --- | --- | --- |
| 规则页 | 必须有 | 公开、稳定链接、注明最后更新日期与生效日期 |
| 封禁名单 | 可选 | 公开"玩家名 + 原因 + 期限"即可，见下方隐私边界 |
| 定期汇总 | 推荐 | 例如每月一条："本月封禁 N 例，其中永久 M 例，撤销 K 例" |
| 申诉统计 | 推荐 | 让玩家看到渠道是有效的，减少"申诉没用"的印象 |

**隐私边界（必须遵守）：**

- **不要公布真实姓名、住址、电话、邮箱、社交账号、工作单位**等任何个人身份信息。
- **不要公开玩家的完整 IP 地址**。需要说明时用掩码（例如只保留网段），且只在内部记录中使用完整值。
- **不要在公开说明里附带聊天原文的完整上下文**，只引用与判定直接相关的部分。
- **未成年玩家的信息尤其敏感**，任何可定位到个人的内容都不应公开。
- **公开封禁原因时用规则条目表述**（"破坏他人建筑"），而不是情绪化描述（"惯犯、人品差"）。

:::warn 公布玩家个人信息本身就是问题
把玩家的真实姓名、住址、电话、社交账号或完整 IP 贴到公开频道或论坛，**无论对方做过什么，都是不能做的事**。它会让你的服务器从"处理违规的一方"变成"实施伤害的一方"，可能违反平台条款与当地法律，也会让其他玩家立刻停止信任你。玩家违规，按规则处理；**用隐私作为报复手段，是运营者最严重的失误之一**。如果这类信息已经被贴出：立即删除、尽可能通知当事人、记录发生了什么，并在内部明确"谁都不能这么做"。
:::

## 10. 解封条件与观察期

永久封禁也不该是"永远没有出口"。给出**可验证的出口**，能显著降低长期纠纷。

| 类型 | 解封条件 | 观察期 |
| --- | --- | --- |
| 临时封禁 | 到期自动解除 | 无（但记录保留） |
| 长期封禁（30 天以上） | 到期 + 申诉中承认行为并承诺不再犯 | 30 天内再犯即永久 |
| 永久封禁（初犯、非恶性） | 满 6~12 个月后申诉，说明改变 | 60~90 天，期间任何违规直接回到永久 |
| 永久封禁（人肉、现实威胁、报复性破坏） | 通常不解封 | — |
| 误判 | 立即解封并致歉 | 无 |

写清"观察期"的好处是双向的：玩家知道代价，你也知道**下一次不需要重新讨论**。

:::note 解封不等于抹除记录
解封应当**追加一条记录**（"某日解封，理由：申诉通过 / 期限届满"），而不是删除原记录。删除记录会让你在下次同类案件里失去参照，也无法统计撤销率。
:::

## 11. 封错了怎么办

**误判一定会发生。** 决定服务器口碑的不是"从不犯错"，而是**犯错之后怎么做**。

1. **立刻解封**，不要等申诉流程走完。证据不足时，"先解封再讨论"是正确顺序。
2. **明确道歉**，用词直接："这次是我们判断错了，抱歉。"不要用"如果给你带来不便，我们表示遗憾"这类回避式表达——它比不道歉更伤人。
3. **说明原因**（简要即可）：记录插件数据被误读、反作弊误报、同名账号混淆。让玩家知道你**知道**错在哪。
4. **在记录里标注撤销**，写明日期与理由。这是后续统计与流程改进的依据。
5. **修补流程**，而不是只修补这一次：
   - 反作弊误报频发 → 调整判定阈值，改为"人工复核后再封"。
   - 同名混淆 → 要求所有封禁记录**以 UUID 为准**，不只写玩家名。
   - 单人拍板 → 给永久封禁加上复核或 24 小时冷静期。
   - 规则未公布 → 补上规则页并公告生效日期。

**一个公开承认过的错误，比十个"我们从不出错"的声明更能留住玩家。**

## 12. 一页流程清单

打印或贴在管理频道里。**每一步都要能回答"留下了什么"。**

**封禁前**

- [ ] 行为对应已公布的规则条目（能说出第几条）
- [ ] 证据已取得，并已复制到服务器之外
- [ ] 已排除"首次轻微失误"与"规则未公布"两种情形
- [ ] 已确认处罚与情节匹配（对照第 5 节阶梯）

**封禁时**

- [ ] 填写了时间、玩家名（含 UUID）、原因、证据位置、决定人五要素
- [ ] 原因写的是**行为**，不是评价
- [ ] 已告知玩家期限与申诉渠道
- [ ] 永久封禁已进入复核（或已设定 24 小时冷静期）

**收到申诉时**

- [ ] 已登记（收到时间 + 对应封禁记录）
- [ ] 已回到原始证据核对，未依赖记忆
- [ ] 已确认规则依据确实存在且已公布
- [ ] 结论为维持 / 减轻 / 撤销三者之一，无"再看看"
- [ ] 已在 SLA 内书面回复
- [ ] 申诉原文与结论已归档

**公开与复盘**

- [ ] 规则页有链接、有更新日期
- [ ] 公开内容不含真实姓名、联系方式、完整 IP 等个人信息
- [ ] 已撤销的记录标注了原因
- [ ] 已统计申诉量、维持率、撤销率
- [ ] 已针对高撤销率修补判定环节
