前面几篇讲的是软件层：装 Java、选服务端、配插件、做备份。这一篇讲**物理层**——把服务器放进机架之后，真正决定"它能不能连续跑三个月不出事"的那些东西。

适用对象从**家里一台塔式机**到**机房里的 1U 机器**。凡是随型号、厂商、固件版本变化的参数，本文都会明确标注"取决于型号"，不会替你编一个具体数字。

## 1. 先分清三个层次

| 层次 | 你关心什么 | 出错后的表现 |
| --- | --- | --- |
| **应用层** | 服务端核心、插件、配置 | 崩溃、卡顿、报错 |
| **系统层** | Java、内存、防火墙、备份 | 起不来、被入侵、数据丢 |
| **物理层** | 机架、供电、网线、散热、带外管理 | **整机断电、过热降频、远程够不着** |

物理层的特点是：**平时完全无感，出事时最难补救**。机房里的机器一旦失联，你能做的往往只有打电话请人按电源键。所以这一层的钱和时间，花在"预防"上最划算。

## 2. 机架基础：19 英寸、U 高与导轨

标准机架来自 **EIA-310 / IEC 60297** 系列规范，几个关键数字：

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| 安装宽度 | 19 英寸 = **482.6 mm** | 两侧安装法兰之间的净宽 |
| 1U 高度 | **44.45 mm**（1.75 英寸） | 所有 U 数都是它的整数倍 |
| 42U 全高机架 | 约 **1866.9 mm** 可用安装高度 | 整体外高通常约 2000 mm，取决于厂商 |
| 常见深度 | 600 / 800 / 1000 / 1200 mm | **服务器机柜通常要 800 mm 以上** |

常见规格：**1U**（最薄，散热余量最小、风扇转速最高、最吵）、**2U**（散热与扩展余量明显更好，可装更多硬盘与半高 PCIe 卡）、**4U**（可装全高卡、多盘位，接近塔式机的安静程度）。家用或小规模优先考虑 2U/4U 或直接塔式机——1U 机器的噪音（常见 60–80 dBA 量级，取决于型号）不适合放在卧室。

安装孔位有两种：

- **方孔机架**：使用**卡式螺母（cage nut）** + M6 螺钉，最常见；
- **螺纹孔机架**：直接拧 10-32 或 M6 螺钉，不需要卡式螺母。

EIA-310 的孔位是**三个一组循环**（间距 15.875 mm / 15.875 mm / 12.7 mm），装导轨时必须对齐这组循环，否则上下设备会互相错位。

**导轨（rail kit）** 的坑最多：

- **静态导轨**：设备放上去就不能抽出，便宜、稳固；
- **滑动导轨**：可把机器整体拉出维护，通常带**理线臂（CMA）**，价格更高；
- 导轨多为**厂商/机型专用**，且**支持深度范围有限**——买机柜前先确认导轨支持的最小/最大深度，600 mm 机柜装不下很多长机身服务器；
- 滑动导轨要预留**线缆余量**，否则拉出时会把网线电源线扯断。

机架内还有不占 U 位的**竖装 0U PDU**（见第 15 节），以及占 1U 的横装 PDU、理线板、盲板。

## 3. 风道：前进后出、冷热通道，以及"永远别挡住进风口"

绝大多数机架式服务器是**前进风、后出风**：冷空气从前面板吸入，热空气从后面排出。机房的布局逻辑由此而来：

- **冷通道**：机柜正面，空调送冷风到这里；
- **热通道**：机柜背面，设备排出的热风集中在这里回风；
- 理想状态是**冷热通道分离**（封闭通道或合理布局），避免热风被重新吸回进风口。

几条硬性纪律：

1. **绝不遮挡进风口**。前面板被挡住、被塞进密闭柜子、贴着墙放，都会直接导致过热降频甚至宕机。
2. **空 U 位要装盲板（blanking panel）**。空位会让热风从机柜后方回流到前方，被上方设备重新吸入。
3. **防尘网要定期清洗**。堵死的滤网等于挡住了进风口。
4. **机柜门要够通透**。通常要求开孔率较高（常见 60% 以上，具体看厂商规格），实心玻璃门对高密度设备是灾难。
5. **注意风扇方向型号**。部分交换机和电源支持**可反转风道**（端口侧进风或端口侧出风），属于**不同 SKU**，必须按机柜的气流方向订购；混装会把冷热通道搞乱。
6. **看进风温度，不看机房温度**。温度传感器要放在设备进风口附近；机房环境温度有 ASHRAE 推荐的允许区间（不同等级 A1–A4 不同），但**设备进风温度**才是真正决定降频与否的量。

托管时你通常只能控制机柜正面：遵守机房方的冷热通道规定，别为了自己方便把机器反过来装。

## 4. 为 Minecraft 选服务器硬件：单核优先

Minecraft 服务端的 tick 循环目标是 **20 TPS**，也就是每个 tick 有 **50 ms** 的预算。主线程负责绝大部分世界逻辑：实体、红石、方块更新、玩家移动、大部分区块加载调度。因此：

**单核性能（频率 × IPC）比核心数更重要。**

| 工作负载 | 线程特征 |
| --- | --- |
| 主 tick 循环（实体、红石、玩家、多数方块逻辑） | 基本单线程，决定 TPS |
| 区块生成 / 光照（Paper 等异步化后） | 可多线程，核心多有益 |
| 插件/模组的异步任务、数据库、地图渲染 | 可多线程 |
| 同时开多个服务端实例 | 核心数直接线性受益 |

结论：

- 一台只跑一个中等规模原版/Paper 服，**2–4 个高频核心**往往胜过 16 个低频核心；
- 核心多**不是浪费**，但对单实例的边际收益递减；
- 选 CPU 时看**单线程跑分**（各类基准库的单核成绩），不要只看"几核几线程"；
- **消费级平台 vs 服务器平台**的取舍：消费级（Ryzen、Core）通常单核更强、更便宜、更安静；服务器平台（Xeon E、Xeon Silver、EPYC 等）提供 ECC、IPMI、冗余电源、更多内存通道与盘位。**具体型号的代际差异很大，请以厂商规格页为准。**

内存方面：小型原版服 4–8 GB、中等规模或带插件 8–16 GB、大型整合包 16 GB 以上是常见区间；**内存给多了没有收益**（见 [服务端配置](/tutorials/java/config)），但给少了会频繁 GC 卡顿。

## 5. ECC 与非 ECC

**ECC（Error-Correcting Code）** 内存能纠正单比特错误、检测双比特错误（SEC-DED），并在不可纠正错误时上报。它**不提升性能**，提升的是**长期运行的可靠性**：

- 一台连续开机几个月的机器，内存出错的概率不低；非 ECC 内存出错时往往表现为**静默数据损坏**——世界文件被写坏，你事后完全不知道原因；
- ECC 需要 **CPU + 主板 + 内存条三者同时支持**，缺一不可；
- **UDIMM（无缓冲）** 常见于消费级/入门服务器；**RDIMM / LRDIMM（寄存/减载）** 只在服务器平台可用，单条容量更大、单通道可插更多条；
- **DDR5 的片上 ECC（on-die ECC）不等于端到端 ECC**：它是 DDR5 颗粒内部机制，不向系统上报、不能替代带外 ECC；
- ECC 错误可通过 BMC/IPMI 的 SEL 日志或 Linux 的 EDAC 子系统（`/sys/devices/system/edac/`、`edac-util` 等）监控。

**结论**：家用作娱乐服，非 ECC 可以接受；**公网长期开放、玩家数据重要的服务器，建议上 ECC**。注意 ECC 与非 ECC、RDIMM 与 UDIMM **混插通常无法开机**，扩内存前查主板 QVL 兼容列表。

## 6. 存储：SSD / NVMe 与耐久度

| 接口 | 典型顺序带宽 | 备注 |
| --- | --- | --- |
| SATA SSD | 约 500–560 MB/s | 受 SATA 6 Gb/s 限制，随机性能仍远好于机械盘 |
| NVMe PCIe 3.0 x4 | 约 3.5 GB/s | 型号相关 |
| NVMe PCIe 4.0 x4 | 约 7 GB/s | 型号相关 |
| NVMe PCIe 5.0 x4 | 约 14 GB/s | 型号相关，发热明显 |

**对 Minecraft 来说，顺序带宽基本不是瓶颈**。真正影响体验的是：

- **4K 随机读写的延迟与队列深度表现**（区块文件、日志、数据库）；
- **写入放大与 SLC 缓存耗尽后的掉速**（大量保存或备份时）；
- **断电保护（PLP）**：企业盘带 PLP，掉电时能把在途写入落盘；消费盘通常没有，**靠 UPS 弥补**（见第 13 节）。

**耐久度**用 **TBW（总写入字节数）** 或 **DWPD（每日全盘写入次数）** 衡量。要点：

- TLC 比 QLC 耐久与持续写入表现更好；QLC 盘在大写入后掉速明显；
- **无 DRAM 缓存的盘**（靠 HMB）在随机负载下通常更弱，适合轻负载；
- Minecraft 本身的写入量并不夸张：服务端周期性保存世界（原版约每 5 分钟一次，Spigot/Paper 可在 `spigot.yml` 的 `ticks-per.autosave` 调整），加上日志与玩家数据；
- 但**插件会显著放大写入**：CoreProtect 这类记录插件、Dynmap/BlueMap 的地图渲染、频繁的自动备份，都会持续写盘；
- 因此**系统盘与数据盘分开**、**备份写到另一块盘或 NAS/HDD** 是常见做法；
- **RAID 不是备份**：RAID 1 能扛单盘故障，扛不住误删、勒索软件和 rm -rf，异地备份仍然必须做（见 [备份与恢复](/tutorials/java/backup)）。

## 7. 冗余电源（1+1）与托管环境

**1+1 冗余电源**指机器有两个热插拔电源模块，任意一个故障时另一个能独立带满整机负载。注意几个容易误解的点：

- **每个模块都要能单独承担全部负载**，不是"一人一半"；选配时按整机峰值功耗选单模块功率；
- 真正有意义的是**双路供电（A/B 馈电）**：把电源 A 和电源 B 接到**不同的 PDU / 不同的支路**。如果两个模块插在同一个插排上，插排一跳闸，1+1 等于没有；
- 托管机柜通常提供 A/B 两路市电，**部分机房第二路要额外收费**，签约前问清楚；
- 1+1 防的是"电源模块故障"和"单路供电故障"，**防不了两路同时断电**——那要靠 UPS 和发电机；
- 冗余电源会带来额外风扇噪音和少量效率损失；电源效率等级（80 PLUS 各档）影响电费与发热，长期托管值得关注。

## 8. IPMI / BMC 带外管理

**BMC（基板管理控制器）** 是服务器主板上一个独立的小系统，由待机电源供电，**操作系统关机甚至没装系统时依然在线**。厂商实现名称不同：Dell 叫 iDRAC，HPE 叫 iLO，联想叫 XClarity Controller，超微/华擎机架/技嘉等通常直接叫 BMC 或 IPMI。协议上，传统是 **IPMI 2.0**，现代替代是 **Redfish**（基于 HTTPS 的 REST 接口）。

它能做的事：

- **远程 KVM**：像坐在机器前面一样看画面、敲键盘，包括进 BIOS；
- **虚拟介质**：把本地 ISO 挂载成光驱，用于装系统/救援；
- **电源控制**：开机、关机、重启、强制断电；
- **传感器与日志**：温度、风扇、电压、SEL 事件日志；
- **Serial over LAN**：通过串口重定向看控制台。

常见端口（**具体端口与实现随厂商/型号变化**）：

| 用途 | 常见端口 |
| --- | --- |
| IPMI RMCP / RMCP+ | UDP 623 |
| BMC Web 界面 | TCP 80 / 443 |
| 远程 KVM（部分实现） | TCP 5900 / 5901 等 |
| Redfish | TCP 443 |

:::warn IPMI 绝对不要暴露到公网
这不是保守建议，而是明确的行业共识。原因：IPMI 2.0 历史上存在认证绕过类漏洞（例如著名的 cipher 0 / RAKP 相关问题），很多厂商固件带有**默认账号密码**（具体默认值随型号与固件版本变化，务必自行更换），部分实现的管理流量加密薄弱，Web 界面也出过大量漏洞。**拿到 BMC 就等于拿到整机**：可以远程开机、挂载镜像、重装系统。

正确做法：
- BMC 接**独立的管理网段/VLAN**，不与业务口混用；
- 该网段**没有到互联网的路由**，需要访问时先连 VPN 或跳板机；
- 修改默认密码，关闭不用的服务（例如用不到 IPMI over LAN 就关掉），限制可访问源 IP；
- 及时更新 BMC 固件（BMC 固件漏洞是真实攻击面）；
- 优先使用 Redfish over IPMI。
:::

## 9. 交换机：非管理型与管理型

| 能力 | 非管理型 | 管理型（L2 / L2+） |
| --- | --- | --- |
| 即插即用 | 是 | 需要配置 |
| VLAN（802.1Q） | 无 | 有（access / trunk 口） |
| 链路聚合（LACP，802.3ad） | 无 | 有 |
| 端口镜像（SPAN） | 无 | 有，抓包排障必备 |
| SNMP 监控 | 无 | 有（v2c / v3） |
| STP / RSTP 防环 | 通常有基础实现 | 有 |
| IGMP snooping（组播优化） | 无 | 有 |
| 端口安全 / 风暴抑制 / DHCP snooping | 无 | 有 |

怎么选：

- **家里一两台机器、一张平网**：非管理型千兆交换机足够，便宜、无故障点、坏了直接换；
- **有机柜、要分业务/管理网段、要做链路聚合或抓包**：上管理型。VLAN 能把 BMC、业务流量、访客网络隔开，是第 8 节安全要求的前提。

两个必须记住的概念：

1. **交换机不做 NAT，也不做端口转发**。二层交换机只按 MAC 转发；三层交换机可以在 VLAN 之间路由，但**通常不做 NAT**。公网端口映射必须由路由器/防火墙完成（见 [软路由与端口转发](/tutorials/ops/router-firewall)）。
2. 家用"路由器"其实是**路由 + 交换 + 无线 AP** 的一体机；不要把它和纯交换机混为一谈。

## 10. 速率选择与上联收敛比

| 标准 | 常见介质 | 距离 |
| --- | --- | --- |
| 1000BASE-T（1GbE） | Cat5e / Cat6 | 100 m |
| 2.5GBASE-T / 5GBASE-T | Cat5e / Cat6（802.3bz） | 100 m |
| 10GBASE-T | Cat6 约 55 m；Cat6a 100 m | 依布线标准与厂商声明 |
| 10GBASE-SR | OM3 / OM4 多模光纤 | 约 300 m / 400 m |
| 10GBASE-LR | OS2 单模光纤 | 约 10 km |
| SFP+ DAC / AOC | 铜缆直连 / 有源光缆 | 机柜内短距，通常几米 |

**对 Minecraft 什么时候重要？**

- 单个玩家占用的带宽其实很小（平均几十到几百 kbit/s 量级，进服加载区块时突发），**一台 1GbE 服务器足够带很多玩家**；
- **1GbE 是绝大多数开服场景的正确答案**；
- 2.5GbE/10GbE 真正有用的是：**存储/NAS/备份、虚拟机迁移、大量服务器之间的内部流量**；
- 别为了"看起来专业"给 MC 服上 10GbE，那笔钱花在 UPS 或 ECC 上更值。

**上联与收敛比（oversubscription）**：接入端口总带宽与上联带宽之比。例如 24 个千兆口配 2 个万兆上联 = 24 Gb/s 接入对 20 Gb/s 上联，约 1.2:1；配 1 个千兆上联则是 24:1。小机柜用千兆上联完全够用。注意 **LACP 聚合的是总带宽，单条流仍走单条链路**（哈希选路），所以单个备份任务未必能跑满聚合带宽。

**PoE 只和电话、摄像头、无线 AP 有关**。服务器不吃 PoE。规格对照：802.3af 每口约 15.4 W（受电端约 12.95 W）、802.3at/PoE+ 约 30 W（约 25.5 W）、802.3bt Type 3/4 约 60 W / 90 W。整机 PoE 总功率预算有限（随型号差异很大），带多个高功率设备前先算预算。

## 11. 硬件防火墙：它补的是"边界"这一层

**主机防火墙**（Windows 防火墙、ufw、firewalld、nftables）只保护**它自己那台机器**，而且是在操作系统启动之后才生效。它做不到：

- 在网络边界做**有状态检测**（conntrack 跟踪连接状态），在流量到达任何主机之前就丢弃；
- **NAT / 端口转发**（这是路由器/防火墙的职责）；
- **站点到站点 VPN**（把两个地点的内网打通）与**远程接入 VPN**；
- **统一策略**：一处定义规则，覆盖整个网段，而不是在每台机器上重复配置；
- **日志与审计集中**：谁在什么时候试图连什么端口；
- **DMZ 分段**：把公网暴露的服务和内部机器隔开（见第 12 节）；
- 主机没开机、系统崩了、被入侵后**仍然在线拦截**。

形态有两种：

- **专用硬件设备**（各厂商的防火墙/UTM/NGFW 设备）；
- **x86 + 防火墙发行版**：pfSense（FreeBSD 系）、OPNsense、OpenWrt 等，跑在普通 x86 机器上，性价比高、功能完整，很适合小型机柜。选型与配置见 [软路由与端口转发](/tutorials/ops/router-firewall)。

**关于规格书上的性能数字，务必谨慎**：

| 指标 | 含义 |
| --- | --- |
| Firewall throughput | 通常是大包、无深度检测的裸转发能力 |
| IPS / NGFW throughput | 开启深度检测后的能力，**往往只有裸转发的一小部分** |
| VPN throughput | 加密隧道吞吐，与算法和 CPU 有关 |
| Concurrent sessions | 并发连接表容量 |
| New sessions/sec | 新建连接速率 |

**各家测试方法不同**（包长、协议、是否开启功能都不一样），跨厂商直接比数字没有意义，**以厂商官方 datasheet 的测试条件为准**。

对 Minecraft 场景来说，连接数只有几百到几千、带宽需求通常不到几百 Mbit/s，**一台入门级设备或一台小 x86 软路由就绰绰有余**。买大号 NGFW 的理由应该是 VPN、分段和管理能力，而不是"MC 需要很多吞吐"。

## 12. 拓扑与 DMZ

标准顺序：

```text
互联网 (WAN)
   |
光猫 / ONT
   |
[ 防火墙 / 路由器 ]        <- NAT、端口转发、状态检测、VPN 都在这里
   |
[ 交换机 ]                 <- VLAN 分段、链路聚合
   |----------|----------|
[ MC 服务器 ] [ 管理机 ] [ BMC 管理口 ]
```

**DMZ** 是一块**独立的网段/接口/VLAN**，用来放"必须对公网开放"的服务（例如面板、Web 服务）。规则思路：

- WAN 到 DMZ：只放行真正需要的端口；
- **DMZ 到 LAN：默认拒绝**（或只放行极少数必要流量）；
- LAN 到 DMZ：允许管理；
- 这样即使公网服务被攻破，攻击者也被困在 DMZ 里，够不到内网数据库和其他机器。

:::warn 消费级路由器上的"DMZ 主机"是另一回事
很多家用路由器的"DMZ"功能是把**所有端口**无条件转发给某一台内网机器。那不是分段，而是把一台机器完全裸露在公网上。**不要用这个功能**，要按端口逐个转发。
:::

其他边界纪律：关闭 WAN 侧管理界面、改掉默认密码、不需要就关掉 UPnP/NAT-PMP、开启日志、定期备份防火墙配置。另外，**防火墙挡不住应用层漏洞**——服务端本身的漏洞、插件的 RCE 要靠打补丁和权限管理（见 [安全插件](/tutorials/ops/security-java)）。

## 13. UPS：它到底保护什么

| 威胁 | UPS 是否解决 | 说明 |
| --- | --- | --- |
| 完全断电 | 是（有限时间） | 靠电池撑到优雅关机或发电机启动 |
| 电压跌落 / 欠压（brownout） | 是 | 带 AVR 的机型可升压补偿 |
| 浪涌 / 尖峰 | 部分 | 有钳位能力，但**直击雷不在保障范围** |
| 频率/电压波动 | 视机型 | 在线式最彻底 |
| 过载 | 否 | 超载会直接转旁路或关机 |
| 电池老化 | 否 | 需要定期更换 |

**VA 与 W 的区别**：VA 是视在功率（电压 × 电流），W 是有功功率，两者之比是功率因数（PF）。规格书上两个都会标（例如 1500 VA / 900 W）。**按 W 选型**，并留余量：负载长期控制在额定 W 的 60%–80% 以内；同时确认 VA 上限也不超。

**续航不是线性的**：负载减半，续航**不会正好翻倍**（铅酸电池的 Peukert 效应与逆变器固定损耗），而且电池会随时间和温度老化。**以厂商的续航曲线为准**，不要自己线性估算。

**波形**：

- 后备式与多数在线互动式在电池模式下输出的是**模拟正弦（阶梯波）**；
- 在线式（双变换）输出**纯正弦波**；
- **主动 PFC 电源按正弦输入设计**，遇到阶梯波可能出现嗡鸣、切换失败甚至关机——**具体是否可用取决于电源型号**，以电源厂商规格为准；
- 结论：**主动 PFC 电源优先配纯正弦 UPS**；带电机类负载也应使用纯正弦。

**三种拓扑**：

| 类型 | 切换时间 | 输出波形 | 特点 |
| --- | --- | --- | --- |
| 后备式 / 离线式 | 常见几毫秒到十几毫秒 | 多为阶梯波 | 最便宜，保护能力最弱 |
| 在线互动式 | 常见 2–10 ms | 多为阶梯波，部分机型纯正弦 | 小型机柜最常见，带 AVR |
| 在线式 / 双变换 | 0（始终逆变） | 纯正弦 | 稳压隔离最好，发热、噪音、能耗、价格都更高 |

切换时间与波形**均随型号变化**，请查具体 datasheet。

**粗略估算负载**：1U 服务器 250–400 W（取决于 CPU 与盘位）、交换机 30–60 W、防火墙 20–40 W，合计再留 30% 余量，然后按 UPS 的 **W 额定值**选型，并确认续航满足"至少撑到自动关机完成"（一般 10–15 分钟足够）。

## 14. UPS 监控与 NUT 自动关机

UPS 只有在**能通知主机**时才有意义——否则断电后你只是多撑了十分钟，然后照样硬掉电。连接方式：

| 方式 | 说明 |
| --- | --- |
| USB HID | 现代 UPS 最常见，`usbhid-ups` 驱动直接支持 |
| USB 转串口 | 部分机型走串口协议，常用 `nutdrv_qx` 等驱动 |
| RS-232 串口 | **线序常常是厂商专用的**，例如某些 APC 机型使用特定型号的专用线（如 940-0024C 一类）；普通交叉线不一定能用，**取决于机型** |
| SNMP 管理卡 | 企业级 UPS 可加网卡，通过网络监控，**网卡型号随厂商变化** |

**NUT（Network UPS Tools）** 是 Linux 上最通用的方案，分三层：**驱动（driver）负责与 UPS 通信，upsd 是服务端，upsmon 是监控客户端**。upsmon 从 upsd 读取状态，并在需要时触发关机。

安装包名与服务名**随发行版不同**：Debian/Ubuntu 通常是 `nut-server`（upsd）与 `nut-client`（upsmon），新版还会用 `nut-driver-enumerator` / `nut-driver@myups`；RHEL/Fedora 系服务名常见 `nut-server` 与 `nut-monitor`；配置文件目录 Debian 系为 `/etc/nut/`，部分发行版（如 SUSE 系）为 `/etc/ups/`。**以下示例按 Debian/Ubuntu 的路径给出**。

`/etc/nut/ups.conf`：

```ini
# 定义一台名为 myups 的 UPS
[myups]
    driver = usbhid-ups
    port = auto
    desc = "Rack UPS"
```

`/etc/nut/upsd.users`（`upsmon` 用来登录 upsd 的账号）：

```ini
[monuser]
    password = secret
    upsmon primary
```

`/etc/nut/upsmon.conf`（最小可用配置）：

```conf
MONITOR myups@localhost 1 monuser secret master
MINSUPPLIES 1
SHUTDOWNCMD "/sbin/shutdown -h +0"
POLLFREQ 5
POLLFREQALERT 5
HOSTSYNC 15
DEADTIME 15
POWERDOWNFLAG /etc/killpower
```

说明与注意点：

- `MONITOR` 行的格式是 `MONITOR <ups> <powervalue> <username> <password> <mode>`；`1` 表示这台 UPS 为系统提供 1 份电源，`master` 表示本机负责在电池耗尽前发起关机；
- **NUT 2.8.0 起把 `master`/`slave` 改名为 `primary`/`secondary`**，旧写法仍被兼容接受；新版文档与示例多用 `primary`，**以你所装版本的官方文档为准**；
- `/etc/nut/upsd.users` 与 `upsmon.conf` 含密码，Debian 系应设为 `root:nut` 且权限 `640`，否则 `upsmon` 可能拒绝启动；
- `upsd` 默认监听 **TCP 3493**。如果只监控本机，就**不要把它暴露到网络**；确实要做多机监控时，用防火墙限制来源地址。

常用命令：

```bash
upsc myups                     # 列出 UPS 所有变量
upsc myups ups.status          # 只看状态，如 OL（市电）/ OB（电池）/ LB（低电量）
upscmd -l myups                # 列出该 UPS 支持的即时命令
upsrw -l myups                 # 列出可写变量
systemctl restart nut-server   # 改配置后重启（服务名随发行版变化）
upsmon -c fsd                  # 强制关机演练，慎用
```

**电池更换与自检**：

- 常见的阀控铅酸（VRLA/AGM）电池寿命通常 **3–5 年**；**环境温度越高寿命越短**（工程经验上每升高约 10 摄氏度寿命大致减半，属经验规律）；
- 很多 UPS 每两周自动做一次自检，也可手动触发（面板按键或 `upscmd myups test.battery.start.quick`，命令名取决于机型）；
- **当自检失败或续航低于你的要求时就该换电池**；同一串电池要整组一起换；
- 锂电池（如 LiFePO4）机型寿命通常更长，但**取决于具体型号**；
- 旧电池按当地规定回收，不要随手丢弃。

## 15. 线缆与供电安全

**供电**

- **绝不串联插排**（插排插插排）。串联会增大接触电阻、让断路器配合失效，并可能让单个墙插过载。机架里用**机架式 PDU**。
- PDU 有横装 1U 与竖装 0U 两种；插座常见 **IEC 60320 C13（约 10 A 级）** 与 **C19（约 16 A 级）**，进线为 C14/C20。选**计量型或可远程控制**的 PDU 便于排查与远程重启。
- **把 UPS 输出接到 PDU，把要保护的设备接到该 PDU**；不要把关键设备直接插墙上。
- **清楚支路容量**：中国常见 10 A / 250 V 插座约 2200 W；北美 NEMA 5-15 在 15 A / 120 V 支路上约 1800 VA，且按规范连续负载通常只取 80%（约 1440 W）；英国 BS 1363 为 13 A。**实际以现场电气设计与电工判断为准，不要顶着上限跑。**
- **接地**：不要掰掉地线脚、不要用"三转二"转接头、机柜要做等电位连接。浮地既是触电与起火风险，也会造成莫名其妙的间歇性故障。

**线缆**

- **两端都贴标签**：一端写对端设备与端口，另一端写回来。机房里没有标签的线，等于没有线。
- 保留一份简单的拓扑图或表格（哪台机器哪个口接到哪个交换机口）。
- 线束用**魔术贴**而不是扎带：扎带会勒伤线缆、且改动时必须剪断。
- **光纤注意弯曲半径**（一般不小于线缆直径的 10 倍，具体看厂商规格），不要打死折；铜缆也不要长期过度弯折。
- 强弱电尽量分开走线；用滑动导轨时给线缆留够余量，并考虑理线臂。
- **常备备件**：各长度的网线各一根、C13/C19 电源线、SFP+/DAC 模块、卡式螺母与螺钉、一块备用硬盘。在托管环境里，一次"远程手"上门费往往比这些备件贵得多。

## 16. 上架前检查清单

- [ ] 机柜深度与导轨支持范围匹配，U 位已规划并留出维护空间
- [ ] 空 U 位已装盲板，前面板进风口无遮挡，防尘网干净
- [ ] 电源 A/B 分别接到不同 PDU / 不同支路，且每路都经过 UPS
- [ ] 支路总负载已核算，未超过额定值（含余量）
- [ ] 接地正常，没有使用任何破坏地线的转接件
- [ ] BMC 已改默认密码，接在独立管理网段，**确认从公网不可达**
- [ ] 交换机上已划分业务 / 管理 / 访客 VLAN（如使用管理型交换机）
- [ ] 公网只开放必要端口（Java `TCP 25565`；基岩 `UDP 19132`），**RCON `TCP 25575` 与数据库端口未暴露**
- [ ] 防火墙/路由器配置已导出备份，WAN 侧管理已关闭
- [ ] UPS 已接入监控，**已实际演练过一次自动关机**
- [ ] 所有线缆两端已贴标签，拓扑记录已更新
- [ ] 备件（网线、电源线、模块、硬盘）已就位

端口速查（默认值，均可修改）：

| 用途 | 协议/端口 |
| --- | --- |
| Java 版游戏 | TCP 25565 |
| 基岩版游戏 | UDP 19132 |
| Query（可选） | UDP 25565 |
| RCON（**禁止暴露**） | TCP 25575 |
| IPMI / BMC | UDP 623 等 |
| SNMP | UDP 161 / 162 |
| NUT | TCP 3493 |
