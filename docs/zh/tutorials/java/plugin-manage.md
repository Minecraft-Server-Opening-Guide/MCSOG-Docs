服务器上的插件只会越装越多。往 `plugins/` 里丢一个 jar 很容易，麻烦的是后面：某个插件要升级、某个插件出问题要临时关掉、某个 jar 看起来不太对劲。这一篇讲三件事：规范的装卸流程、热重载工具的能力边界，以及怎么判断一个插件是不是被人动过手脚。

如果你还没装过插件，建议先看 [插件入门](/tutorials/java/plugins)。

## 1. 安装、更新与卸载的规范流程

### 安装

1. 确认来源可信（见第 5 节），顺手记下版本号与下载地址。
2. **停服**。多数插件首次加载并不支持热加载。
3. 备份 `plugins/` 目录，见 [备份与恢复](/tutorials/java/backup)。
4. 把 `.jar` 放进 `plugins/`。
5. 启动服务端并观察控制台，加载成功与失败的信息都打印在这里。
6. 用 `plugins` 指令确认加载状态。
7. 再改配置，改完优先用插件自带的 `reload` 子指令，而不是服务端原版的 `/reload`。

### 更新

更新比安装更容易出事，因为新版本的配置结构可能已经变了。

| 步骤 | 要点 |
| --- | --- |
| 读更新日志 | 确认有没有配置格式变更、有没有需要手动迁移的数据 |
| 备份 | 至少备份 `plugins/<插件名>/`，涉及数据库的还要备份数据库 |
| 留旧 jar | 旧版本先改名为 `.jar.bak` 留着，确认新版正常再删 |
| 停服替换 | 不要在线覆盖正在使用的 jar |
| 重启验证 | 看控制台，再用 `plugins` 确认状态 |
| 大版本跳跃 | 跨大版本（如 1.20 升到 1.21）时，插件可能需要先升到中间版本 |

### 卸载

卸载不只是"把 jar 删掉"。

1. 停服。
2. 移走 jar。
3. 数据目录**不要立刻删**，先重命名为 `<插件名>.bak` 观察一段时间。
4. 检查有没有别的插件把它当前置依赖，有的话一起处理。
5. 清理它在权限插件里留下的权限节点。
6. 清理它注册的定时任务、自定义指令、计分板条目。
7. 留意世界里它留下的自定义物品或方块，缺失插件时可能报错。

:::warn 卸载不等于清理
删掉 jar 只解决了"加载"这一步。数据目录、权限节点、数据库表、其他插件对它的依赖，都还留在原地。
:::

## 2. 热重载工具：PlugManX 与 ServerUtils

这类工具通常叫**插件管理插件**：它们能在服务端已经运行的情况下加载、卸载、重载别的插件。

### PlugManX

老牌的插件管理工具，前身是 PlugMan，现在由社区维护的 PlugManX 继续更新。

| 项目 | 信息 |
| --- | --- |
| 发布页 | SpigotMC 资源 88135 |
| 源码 | GitHub 上的 Test-Account666/PlugManX（旧版为 ryan-clancy/PlugMan） |
| 常见子指令 | `load`、`unload`、`reload`、`list`、`info`、`check` |
| 典型用法 | `/plugman <子指令> <插件名>` |

具体的子指令名称和参数会随版本变化，以插件自带的帮助信息为准。

### ServerUtils

| 项目 | 信息 |
| --- | --- |
| 发布页 | SpigotMC 资源 79599、Modrinth |
| 源码 | GitHub 上的 frankheijden/serverutils |
| 支持端 | Spigot、BungeeCord、Velocity |

除了插件管理，它还附带一些服务端状态查看之类的工具。因为同时支持代理端，群组服可以在代理层统一管理插件，不必每台后端各装一套。

### 热重载的真实边界

热重载不是"不用重启"，它有一批明确的做不到的事：

| 情况 | 能否靠热重载解决 |
| --- | --- |
| 只是改配置 | 用插件自带的 `reload` 即可 |
| 临时禁用出问题的插件 | 可以，这是热重载最有价值的用法 |
| 换插件版本（换 jar） | 不建议，应当停服替换 |
| 插件注册了指令、权限、监听器、配方、世界生成器、进度 | 卸载后常留残留，重载容易出错 |
| 插件直接改服务端内部实现（NMS、反射） | 基本不能 |
| 插件持有数据库连接、线程池或大量静态缓存 | 卸载后资源往往不释放 |
| 反复加载卸载同一个插件 | 类加载器无法回收，内存持续上涨，最终 OOM |
| 混合端或模组端 | 插件管理器管不了模组 |
| 服务端原版 `/reload` | 不推荐，容易让插件状态错乱 |

:::warn 生产服不要只靠热重载
热重载适合"临时关掉一个插件看看问题是否消失"和快速试配置。正式的版本更新、依赖变更，仍然应该走停服重启的流程。
:::

:::tip 排查问题的正确用法
先用插件管理器把最近新装的插件 `unload` 掉，观察现象是否消失；确认是它之后再正式停服处理。这比通读日志快得多。
:::

## 3. 后门插件的常见特征

插件是以服务端权限运行的第三方代码，一旦被塞了后门，等于把服务器交到别人手里。下面这些信号值得警惕。

| 信号 | 具体表现 |
| --- | --- |
| 权限与指令异常 | `plugin.yml` 里声明了与功能无关的高危指令，比如给自己 OP、执行任意指令、读写任意文件 |
| 代码被混淆 | 类名是无意义的单字母或 `a/b/c` 结构；整包被加密，或用自定义类加载器在运行期解密加载 |
| 可疑的运行时调用 | 起子进程（`ProcessBuilder`、`Runtime.exec`）、主动外联（`URL.openConnection`、HTTP 请求）、直接改 `ops.json`、用反射加载远程类 |
| 伪装成"更新器" | 声称自动更新，实际从作者自己的服务器下载文件并覆盖自身 |
| 来源不明 | 论坛附件、网盘、群文件里转发的 jar |
| "免费的高级插件" | 付费插件被破解重打包，破解者通常顺手加了点东西 |
| 与上游不一致 | 插件名和版本号相同，但文件大小或哈希对不上，`plugin.yml` 里的作者与网址被改过 |
| 名字无害的隐蔽配置 | 默认开启的 `metrics`、`telemetry`、`update-check` 之类选项，实际在往外发数据 |

:::warn 不要只看插件名
后门插件经常直接冒用知名插件的名字和版本号。判断依据应该是文件的来源和实际内容，而不是文件名。
:::

## 4. 安全的下载来源

| 渠道 | 风险 |
| --- | --- |
| SpigotMC、Modrinth、Hangar、Bukkit Dev 等主流发布平台 | 低，优先选择 |
| 作者自己的 GitHub Releases | 低，注意认准仓库所有者 |
| 付费插件的官方购买页 | 低，注意别买成"代购" |
| 聚合下载站、镜像站 | 中，可能二次打包，建议核对文件哈希 |
| 论坛附件、网盘、群文件 | 高 |
| 二手交易平台上的"免费高级插件" | 极高，属于重灾区 |

判断标准其实很简单：**能不能追溯到作者本人发布的、可以核对的那个文件**。一个插件在多少个站点出现过，并不能说明它安全。

:::tip 只装你需要的东西
插件装得越少，攻击面越小，排查也越容易。功能重叠的插件留一个就够。
:::

## 5. 怀疑某个插件时的排查流程

1. **记录现象**：什么时候开始的、控制台报什么、有没有玩家反馈异常。
2. **先备份**：在动任何东西之前做一次完整备份，包括 `plugins/` 与世界数据。
3. **列出嫌疑名单**：最近 24 到 72 小时内新增或更新过的插件。
4. **二分定位**：停服，禁用一半嫌疑插件，重启观察；现象消失就在被禁用的那一半里，否则在另一半里。
5. **单独复现**：缩小到单个插件后，用插件管理器只 `unload` 它，确认现象是否重现。
6. **静态扫描**：按第 6 节的方法扫一遍 jar。
7. **人工看 `plugin.yml`**：核对 `author`、`website`、`main`、`commands`、`permissions`，和官方版本对比。
8. **看类文件列表**：解开 jar，留意无意义的类名，以及上表中的可疑调用。
9. **比对哈希**：和官方下载的文件比大小、比哈希。
10. **确认恶意后进入应急流程**。

应急处理清单：

- 检查 `ops.json` 与 `whitelist.json` 是否被改动，有没有陌生账号拿到 OP。
- 检查是否有异常登录记录、陌生的玩家数据文件。
- 轮换所有凭据：RCON 密码、面板密码、数据库密码、SSH 密钥。
- 检查 `plugins/` 下是否被塞进了别的 jar，服务端核心 jar 与启动脚本是否被替换。
- 检查系统层面的计划任务，确认没有被人加了自启项。
- 通读控制台日志与插件日志，找出后门第一次活跃的时间点。
- 视情况通知玩家并回档，回档前先保留现场用于分析。

## 6. 用 McGuard 做静态扫描

McGuard（简称 MCG）是一个第三方静态扫描工具，作者为 huzpsb。它能在**不启动服务端**的前提下扫描 `plugins/` 下的全部 jar，找出可疑文件。

### 控制台模式

把 MCG 的 jar 放到服务端根目录，然后在该目录执行：

```
java -Xmx1G -jar MCG.jar
```

启动后会提示选择模式，通常选 `0`（标准模式）即可，另外还有专家模式与开发者模式。

扫描结果的表现形式是：

| 情况 | 输出 |
| --- | --- |
| 未检出异常 | 只打印扫描过程，不输出结果块 |
| 检出异常 | 输出结果块，并逐条给出严重级别与原因描述 |

原因描述会指明命中的行为类别，例如"可能通过设置权限位获取 OP"或"可能通过启动子进程执行远程指令"。

:::warn MCG 只报告，不处理
它不会修改也不会删除任何插件，需要你自己手动清理。同时要注意，专家模式用已知恶意代码特征匹配并分析代码意图，覆盖大多数没有刻意规避扫描的样本，但仍然存在误报。
:::

### 插件模式

MCG 也可以作为 Bukkit/Spigot 插件安装，在服务端运行期间持续防护。官方对其定位的说明是：这种保护是相对的，极少数恶意插件仍可能绕过行为管控；**不要因为装了 MCG 就去运行已知含有恶意插件的服务端**。

:::warn 扫描只是最后一道防线
任何扫描工具都不可能消除全部风险，正确做法仍然是从正规渠道获取插件。如果要运行来源不明的服务端核心，建议先用控制台模式扫描，再在沙箱（如 Sandboxie）之类的隔离环境里试跑。
:::

## 7. 日常维护建议

- 每个月至少检查一次插件更新，尤其是跨版本兼容与反作弊这类和安全直接相关的插件。
- 维护一份插件清单，记录名称、版本、来源、下载地址，出问题时能快速回溯。
- 生产服与测试服分开，新插件先在测试服跑一段时间。
- 不要用 root 或 Administrator 账户直接跑服务端进程，给服务端一个最小必要权限的专用账户。
- 关注作者仓库的 issue 与公告，插件被投毒通常会在社区里先有讨论。
