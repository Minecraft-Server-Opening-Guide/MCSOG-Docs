当服务器从"一个服"变成"一组服"（大厅 + 生存 + 小游戏……）时，就需要**跨服端（代理端）**来统一入口。

## 一、代理端做什么

代理端**自己不跑世界**，它只做一件事：**接住玩家的连接，再转发到后端的某个子服**。

```
玩家 → 代理端（Velocity / BungeeCord）
              ├→ 大厅服
              ├→ 生存服
              └→ 小游戏服
```

好处：

- **统一入口**：玩家只记一个地址，切换子服时不断线、不用重连。
- **统一账号验证**：正版验证在代理端做一次，后端全部设成离线模式（内部互信）。
- **好维护**：加一个子服只要在代理配置里登记一条，玩家无感。
- **资源共享**：大厅、登录服、小游戏可以各自独立重启，不影响其他服。

## 二、选哪个

| 代理端 | 说明 |
| --- | --- |
| **Velocity** | 现代方案，**性能更好、更活跃**，新项目优先选它。支持"现代转发"（modern forwarding），验证信息通过密钥安全传递 |
| **BungeeCord** | 老牌方案，生态成熟、资料极多，很多老教程基于它。适合维护既有老服 |

> 两者思路一致，差别在配置细节与转发机制。**新开服建议 Velocity**。

## 三、搭建要点

### 1. 代理端

- 下载代理端 jar，单独放一个目录，写启动脚本运行。
- 配置里登记**子服列表**（名称 + 内网地址 + 端口）。
- 正版验证**只在代理端开**：代理端 `online-mode=true`，子服必须 `online-mode=false`。

### 2. 子服

子服要对代理端"交出信任"，即**只接受来自代理端的连接**：

- **Velocity**：使用**现代转发**，在代理端与子服上配置同一个 `forwarding.secret`，子服开启对应转发模式。
- **BungeeCord**：在子服配置里开启 `bungeecord: true`（Spigot 系），并关闭子服自身的正版验证。

### 3. 关键安全点

:::warn 转发密钥就是服务器的钥匙
子服一旦信任代理转发，**任何知道密钥的人都能伪造任意玩家身份进入**。所以：

- `forwarding.secret` **不要泄露、不要提交到公开仓库**；
- 子服端口**不要直接暴露公网**，只允许代理端所在机器访问（用防火墙限制来源）。
:::

## 四、注意事项

- **插件要区分位置**：有的插件装在代理端（跨服聊天、全局权限），有的必须装在子服。装错位置会出现"指令存在但没反应"。
- **代理端会多一跳**：玩家延迟略有增加，通常可忽略，但链路差时会被放大。
- **模组端不好混**：代理转发对模组端支持有限，模组服跨服通常需要专门方案。
- **背包/数据同步**：跨服时玩家的背包、位置等由代理端与子服协作处理，**不要在子服之间共享同一个世界文件夹**。
- **别把代理端当"性能优化"**：它不提升性能，只是**结构**上的统一入口。单服不需要它。

## 五、什么时候该上代理

**该上**：有多个玩法分区、需要统一入口、玩家要在服之间自由切换、要做大厅与登录服。

**不该上**：只有一个服。**多一层就多一层故障点**，小服上代理纯属增加维护成本。
