这是 [生电与红石](/tutorials/java/redstone) 的进阶篇。入门篇回答的是"该选哪个核心"，这一篇回答三个更实际的问题：**技术玩家到底在造什么、这些机器依赖哪些服务端设置、作为服主你要提前准备什么。**

先明确本篇的边界：这里**不给机器图纸，也不保证任何具体设计在你的版本上成立**。生电最基本的事实是——**机器的可用性绑定在具体的游戏版本和具体的服务端实现上**。任何"这台机器永久有效"的说法都不可信。

## 1. 生电玩家到底在造什么

技术玩家口中的"农场"（farm）指的是**自动化或半自动化的资源产线**：用游戏机制换产出，而不是用手挖。先建立一张类别地图，再谈负载。

| 类别 | 机制要点 | 主要负载 | 版本敏感度 |
| --- | --- | --- | --- |
| 刷怪塔 / 掉落物农场 | 利用自然刷怪或刷怪笼，把怪物集中后处死 | 实体数量、AI 寻路、掉落物与经验球、区块常加载 | 中：刷怪规则、怪物 AI、碰撞箱改动都会影响效率 |
| 物品农场 | 依靠方块自身行为产出（甘蔗、竹子、仙人掌、海带、蜂蜜、羊毛等） | 方块更新、随机刻、漏斗与矿车收集 | 中低，但收集端的漏斗本身是负载 |
| 铁农场 | 用村民与恐吓机制（或袭击机制）触发铁傀儡生成 | 村民 AI、工作站点方块（POI）查询、实体生成、常加载 | 高：村民与铁傀儡的生成条件被反复调整 |
| 金农场 | 用下界传送门刷出僵尸猪灵（1.16 起由"僵尸猪人"改名而来）并集中处死 | 传送门方块实体、实体数量、下界区块常加载 | 高：实体命名、AI 与传送门机制都有改动 |
| 村民交易大厅 | 大量村民配工作站点方块，刷新并锁定交易 | 村民 AI、POI、寻路、区块常加载 | 中高：交易与职业机制多次调整 |
| 袭击农场 | 触发袭击并处理波次，获取绿宝石、不死图腾等 | 成波生成的实体、AI、掉落物 | 高 |
| 凋灵骷髅农场 | 在下界要塞刷怪，配合雪傀儡或凋灵玫瑰等完成击杀 | 要塞区块常加载、实体、掉落物 | 中高 |
| 树场 / 食物农场 | 自动种植与采伐（活塞或 TNT），以及各类作物农场 | 随机刻、方块更新、TNT 实体、掉落物 | 中 |
| TNT 复制与其他机制型农场 | 利用复制类特性获得 TNT 等资源；利用活塞、重力方块、传送门等机制 | TNT 实体与爆炸、海量方块更新，容易直接压垮 TPS | 极高：这类特性被反复修复又反复出现，且很多服务器明令禁止 |

按"负载"而不是按"产出"分类，是因为**对服主而言，机器的产出归玩家，机器的成本归服务器**。下面逐类说明。

### 1.1 刷怪塔与掉落物农场

- **机制**：要么让怪物在黑暗区域自然生成后集中，要么用刷怪笼持续产出。集中手段通常是水流、活塞推动、或者把怪物引到另一维度。
- **负载**：怪物是"会思考的实体"，每刻都要做 AI、寻路与碰撞判定；掉落物和经验球还会继续占用实体额度。
- **服主要注意**：这是最容易把服务器拖慢的一类机器，因为它同时消耗实体、AI、区块与掉落物四项成本。

### 1.2 物品农场

- **机制**：不依赖刷怪，靠方块自身行为产出，例如甘蔗、竹子、仙人掌、海带、蜂蜜、羊毛。
- **负载**：以方块更新和随机刻为主，产出物需要用漏斗或矿车收集，**收集端往往比生产端更贵**。
- **服主要注意**：调低 `randomTickSpeed` 会直接让这类农场变慢；调大漏斗搬运间隔（`hopper-transfer`）会让所有收集系统变慢。

### 1.3 铁农场

- **机制**：利用村民与"恐吓"条件触发铁傀儡生成，也有基于袭击机制的变体。
- **负载**：村民 AI 与工作站点方块查询是出了名的贵，加上区块必须常加载。
- **版本注意**：铁傀儡的生成条件、村民的工作与睡眠判定都改过多次，**这类机器几乎每次大版本更新都要复验**。

### 1.4 金农场

- **机制**：用下界传送门刷出僵尸猪灵（1.16 起僵尸猪人改名为僵尸猪灵）后集中处死。
- **负载**：传送门方块实体、大量实体与掉落物，且必须让下界区块常加载。
- **版本注意**：实体改名、AI 调整、传送门机制变化都会影响产出方式。

### 1.5 村民交易大厅

- **机制**：把大量村民关在一起，配工作站点方块刷新交易，直到出现想要的交易再锁定。
- **负载**：村民是服务器上最"重"的常见实体之一，寻路、POI 查询、每刻行为都要算。
- **服主要注意**：交易大厅常常和铁农场、繁殖机连在一起，形成一小片高负载区；`tick-inactive-villagers` 一类优化项会直接改变村民行为。

### 1.6 袭击农场

- **机制**：主动触发袭击并处理一波波生成的袭击者，换取绿宝石、不死图腾等。
- **负载**：波次生成会在短时间内制造大量实体，属于**突发型**负载，容易造成 MSPT 尖峰而不是平稳升高。
- **版本注意**：袭击触发条件、波次组成与掉落表都改过。

### 1.7 凋灵骷髅农场

- **机制**：在下界要塞范围内刷怪，再用自动手段完成击杀与收集。
- **负载**：要塞区块必须常加载，实体与掉落物持续存在。
- **服主要注意**：要塞结构范围有限，多个玩家同时建农场会互相抢刷怪额度。

### 1.8 树场与食物农场

- **机制**：自动种植与采伐（活塞或 TNT），以及小麦、胡萝卜、马铃薯等作物农场。
- **负载**：随机刻、方块更新、TNT 实体与爆炸。
- **服主要注意**：TNT 型树场的爆炸会带来大量方块更新，是**局部卡顿**的常见来源。

### 1.9 TNT 复制与其他机制型农场

- **机制**：利用游戏中的复制类特性获得 TNT 等本应昂贵的资源；或利用活塞、重力方块、传送门等机制的边界行为。
- **负载**：TNT 实体与爆炸、成片方块更新，一台大规模复制装置足以让 TPS 掉到个位数。
- **服主要注意**：这类特性**被官方反复修复又反复出现**，具体行为完全绑定版本；同时**很多服务器在规则里明确禁止**，因为它同时是性能问题与公平性问题。是否允许，必须在规则里写清楚。

:::warn 不要以为某个设计是"通用"的
同一台机器在不同游戏版本上可能完全失效，原因可能是刷怪规则、实体 AI、方块更新顺序、某个被修掉的复制特性，甚至只是碰撞箱改了 0.1 格。所以：

- 玩家说"这机器能用"时，先问清**游戏版本**和**服务端核心**；
- 服主说"我们升级到新版本"时，等于宣布**所有机器都要重新验证**；
- 任何教程（包括本篇）给出的设计都只能当"思路"，不能当"保证"。
:::

## 2. 一台机器会给服务端带来什么

把机器拆成六种成本，排查时才有方向：

| 成本类型 | 由什么产生 | 典型表现 |
| --- | --- | --- |
| 实体数量 | 怪物、掉落物、经验球、矿车、盔甲架、TNT | MSPT 上升，实体同步占带宽 |
| AI 与寻路 | 怪物与村民的每刻思考、路径计算 | 村民密集区特别明显，TPS 掉且难以定位 |
| 区块加载 | 常加载区块、传送门加载器 | 无人时也持续吃 CPU 与内存 |
| 方块更新与红石调度 | 红石元件、漏斗、活塞、侦测器 | 高频时钟与大面积红石是经典杀手 |
| 随机刻 | 作物、树叶、冰霜、火势 | 调高 `randomTickSpeed` 后 CPU 线性上升 |
| 光照与存档 | 方块变化触发光照重算；区块定期自动保存 | 大面积改造时出现规律性卡顿 |

结论只有一句：**TPS 是这些成本叠加后的结果，不是某一个开关决定的。**

### 2.1 怎么把成本量化

不要凭感觉判断"这台机器贵不贵"，按下面的顺序测：

```text
1. 记录基线：没有玩家在线时的 TPS / MSPT
2. 只让一名玩家站在机器旁，观察 5-10 分钟的 MSPT 曲线
3. 关掉机器再测一次，两次的差值就是这台机器的成本
4. 用 spark 采样，确认成本落在实体、方块实体还是区块上
5. 把数字记下来，下次升级版本或换配置时用同一方法复测
```

这样做的价值在于：当玩家说"是服务器卡才导致机器不工作"时，你手上有数据可以判断，而不是互相猜。

## 3. 生电依赖的服务端设置

原则先摆在这里：**原版行为是"默认值"，优化是"偏离默认值"。** 技术玩家要的是前者。

下面的键名、默认值与可选值**都随版本变化**，也可能因为你用的核心分支不同而不存在。请以**你自己服务端的配置文件**和该核心的官方文档为准，本篇只讲"这一项是干什么的、改了会发生什么"。

### 3.1 刷怪上限（mob cap）

原版的刷怪上限**不是固定数字**，而是按玩家、按可刷怪区块数量缩放的。要点：

- 上限随**玩家数量**与**玩家周围可刷怪区块数量**缩放，所以"服务器人多了刷怪变多"是正常现象；
- 怪物、动物、水生生物、环境生物各有各的上限；
- 上限按玩家计算，所以**没有玩家在线时不会自然刷怪**——哪怕那片区块被常加载；
- 插件端的 `spawn-limits`（`bukkit.yml`）会覆盖这套算法，把"按玩家缩放"改成别的口径。不同核心分支的实现不同，改动它会直接改变所有刷怪塔的产能。

### 3.2 刷怪范围与消失距离

- 原版怪物在玩家周围一定距离内生成（有最小与最大距离），离玩家过远会消失。
- `mob-spawn-range`（`spigot.yml`，单位是区块）会改动这个范围。
- 改动的连锁反应：刷怪塔效率、怪物消失速度、村庄与袭击相关机制的触发范围都会变。
- 生电服通常**保持原版范围**，因为所有成熟设计都是围绕原版距离做的。

### 3.3 实体激活范围（entity activation range）

- Spigot 的 `entity-activation-range` 会让远处实体**降频甚至停止 tick**，默认值大致在十几格到四十几格之间（具体以你的 `spigot.yml` 为准）。
- 后果很直接：机器里"离玩家远"的那一半不工作，或者工作速度与原版不一致。
- 生电服要么把它调到足够大，要么接受"部分机器行为与原版不同"。
- 注意：这一项对普通生存服是**收益极高**的优化，所以很多预设配置把它压得很低，冲突就出在这里。

### 3.4 随机刻

- `randomTickSpeed` 是游戏规则，原版默认值是 3。
- 影响范围：作物生长、树叶腐烂、冰霜形成与融化、火势蔓延。
- 调高会让依赖随机刻的农场变快，同时**大幅**增加 CPU 开销；调低则相反。
- 很多"优化"教程会建议调低它——那等于**改了原版行为**，作物类机器会跟着变慢。

### 3.5 红石相关

- Paper 系核心提供可切换的**红石实现方式**（配置项位于世界默认配置中，如 `misc.redstone-implementation` 一类，键路径与可选值随版本变化）。
- 生电服**必须保持 vanilla 实现**。换成为性能优化过的实现会改变红石更新行为，机器可能直接失效。
- 另外注意：一些优化项会调整方块更新顺序或红石调度延迟，这类改动比"性能下降"更致命，因为它**静默地**让机器坏掉。

### 3.6 其他常被改动的项

| 设置 | 原版行为 | 常见"优化"做法 | 生电的取舍 |
| --- | --- | --- | --- |
| `simulation-distance`（`server.properties`） | 该距离内的区块真实运算 | 调低到 4-6 | 影响所有机器的可用范围，调低等于砍掉远处机器 |
| `view-distance` | 玩家能看到多远 | 调低 | 只影响观感与带宽，对机器影响小 |
| `entity-broadcast-range-percentage` | 实体同步给玩家的范围比例 | 调低 | 玩家会看到实体"突然出现"，但不影响服务端运算 |
| `entity-tracking-range`（`spigot.yml`） | 实体被追踪的距离 | 调低 | 只影响同步，不改机器逻辑 |
| `max-entity-collisions` | 超过上限就停止处理实体碰撞 | 调低 | 密集实体机器需要调大，代价是性能 |
| `nerf-spawner-mobs` | 刷怪笼生成的怪物 AI 完整 | 设为 `true` 削弱 AI | 会让刷怪笼农场产出方式改变 |
| `hopper-transfer` / `hopper-check`（`ticks-per`） | 漏斗每 8 刻搬运一次 | 调大以省性能 | **直接改变所有漏斗产能**，机器时序全变 |
| `merge-radius`（`spigot.yml`） | 掉落物与经验球的合并半径 | 调大 | 减少实体数量，但改变原版合并行为 |
| `randomTickSpeed` | 3 | 调低 | 作物类农场变慢 |
| `doMobSpawning` 等游戏规则 | 见游戏内 `/gamerule` 说明 | 关掉以减少负载 | 关掉就没有刷怪塔了 |

### 3.7 这些设置长什么样

下面只是**示意**，用来让你认识这些键在文件里的位置与形状；**数值不是你要抄的答案**，请对照你本地的文件。

```yaml
# spigot.yml（示意，键名与默认值随版本变化）
world-settings:
  default:
    mob-spawn-range: 8
    entity-activation-range:
      animals: 32
      monsters: 32
      raiders: 48
      misc: 16
      water: 16
      villagers: 32
      flying-monsters: 48
    max-entity-collisions: 8
    nerf-spawner-mobs: false
    merge-radius:
      item: 2.5
      exp: 3.0
    ticks-per:
      hopper-transfer: 8
      hopper-check: 8
```

```yaml
# bukkit.yml（示意，默认值随版本变化）
spawn-limits:
  monsters: 70
  animals: 10
  water-animals: 15
  water-ambient: 20
  ambient: 15
ticks-per:
  monster-spawns: 1
  animal-spawns: 400
  autosave: 6000
```

```text
# server.properties（示意）
simulation-distance=10
view-distance=10
entity-broadcast-range-percentage=100
```

```bash
# 游戏规则：这些是原版默认值，改之前先想清楚会破坏什么
/gamerule randomTickSpeed 3
/gamerule doMobSpawning true
/gamerule doFireTick true
/gamerule doInsomnia true
/gamerule doPatrolSpawning true
/gamerule doTraderSpawning true
/gamerule disableRaids false
/gamerule mobGriefing true
```

:::warn 很多"优化"插件改的就是原版行为
市面上大量"性能优化"插件与预设配置，做法是把上面这些值调到比原版激进得多：缩小实体激活范围、调低随机刻、合并实体、改写红石调度、限制刷怪上限。对普通生存服这是好事，**对生电服就是灾难**——机器会以难以排查的方式失效，而且往往不是"完全不动"，而是"偶尔少产出一点"。

所以：

- 装任何优化插件前，先确认它**改了哪些原版行为**，最好在测试服上跑一台已知机器验证；
- 优化项与生电需求是此消彼长的，不要指望两者都拉满，参见 [性能优化](/tutorials/java/optimize)；
- 如果症状是"实体和掉落物堆着不清"，那属于堆积问题而不是配置问题，见 [实体与掉落物堆积导致的卡顿](/tutorials/faq/entity-lag)。
:::

## 4. 区块加载

区块加载是生电服最容易被忽视、也最容易被玩家滥用的部分。

### 4.1 出生点区块

- 世界出生点周围的区块会被游戏**持续保持加载**，即使没有玩家在线。这就是"出生点挂机农场"能 24 小时运行的原因。
- 注意区分"加载"和"刷怪"：**没有玩家在线时不会自然刷怪**，但红石、方块实体、作物随机刻会继续推进。
- 出生点区块的**范围大小在版本之间改过**，较新的版本还提供了控制它的游戏规则（例如 `spawnChunkRadius` 一类）。具体范围与规则名请查对应版本的官方 wiki，不要照抄旧教程。
- 实践建议：**别把最重要的机器建在出生点**，否则它会在你不知情的情况下 24 小时消耗资源。

### 4.2 `/forceload`

原版提供的强制加载命令，也是服主审计时最直接的抓手：

```bash
/forceload add <起点x> <起点z> [终点x 终点z]
/forceload remove <起点x> <起点z> [终点x 终点z]
/forceload remove all
/forceload query
/forceload query <x> <z>
```

要点：

- 坐标是**方块坐标**，被加载的是包含这些坐标的区块；
- 单条命令能加载的区块数量有上限（**最多 256 个区块**）；
- 强制加载列表**随存档保存**，重启后依然生效；
- 需要管理员权限等级（通常 OP 二级）；
- 被强制加载的区块是**完整运算**的，不是"只加载不运算"。

### 4.3 传送门式区块加载器

- 玩家常用的"区块加载器"大多基于下界传送门：传送门会让**另一维度对应的区块**在一段时间内保持加载。
- 典型用法是"在下界放一个传送门，让主世界的机器继续跑"，或者反过来。
- **具体保持多久、用什么等级的票据，是版本相关的**，请以对应版本的机制说明为准；这也意味着一个加载器在升级后可能失效或变成"永久加载"。
- 服主视角：这类装置**不会出现在 `/forceload query` 里**，只能靠人工排查。

### 4.4 常加载区块的代价

| 代价 | 说明 |
| --- | --- |
| 内存 | 每个已加载区块的数据与实体都常驻内存，加载得越多，堆占用越高，GC 压力越大 |
| CPU | 被加载的区块会走完整的 tick 流程：方块实体、随机刻、实体 tick |
| 刷怪上限 | 若加载区附近有玩家，这些区块会**分摊**刷怪上限，导致别处的农场产量下降 |
| 存档 | 加载中的区块会定期自动保存，常加载区域越大，自动保存的抖动越明显 |
| 隐蔽性 | 加载器常常建在玩家看不到的地方（下界、地下），出事时最难定位 |

### 4.5 怎么审计

1. **逐个维度执行 `/forceload query`**：主世界、下界、末地都要查，加载器经常在另外两个维度。
2. **排查传送门加载器**：问玩家、看下界传送门的位置，注意"为什么这里有个孤零零的传送门"。
3. **看无人时的 MSPT**：玩家全部离线后，TPS/MSPT 仍然不健康，基本就是常加载区块在跑。
4. **用性能分析工具定位**：spark 一类工具的采样结果能告诉你时间花在哪些区块与实体上，方法与 [性能优化](/tutorials/java/optimize) 相同。
5. **把结论写进规则**：谁建的加载器、加载了多大范围、用来跑什么，登记下来，升级版本前逐个复验。

## 5. 技术玩家必须理解的 tick 模型

### 5.1 20 TPS 与 50 毫秒

- 原版目标是 **20 TPS**，也就是每个游戏刻 **50 毫秒**。
- 单刻超时不会立刻掉 TPS：偶尔一个 200 毫秒的刻，平均下来 TPS 仍然接近 20，但玩家会感到一次卡顿。真正让 TPS 掉下去的是**持续**超支。
- 所有依赖时间的机制（作物、熔炉、红石、生物移动）都在这个循环里推进，所以 TPS 一掉，**一切同时变慢**。
- 这也是为什么"TPS 15"感觉远不止慢 25%：所有机器都按同一个比例变慢，依赖精确时序的设计会直接停摆。

### 5.2 游戏刻与红石刻

| 单位 | 长度 | 用途 |
| --- | --- | --- |
| 游戏刻（game tick） | 1/20 秒 = 50 毫秒 | 服务端主循环的最小单位 |
| 红石刻（redstone tick） | 2 个游戏刻 = 0.1 秒 | 社区用来描述红石元件延迟的单位，中继器、侦测器一类的延迟都以它计量 |

一个最小例子：

```text
第 0 刻（0 ms）     中继器被激活，安排"2 刻后输出"
第 1 刻（50 ms）    线路上的其他更新在同一刻内继续结算
第 2 刻（100 ms）   中继器输出，也就是 1 红石刻之后
```

要理解的关键点：**红石刻是"延迟的计量单位"，不是"计算的执行单位"**。方块更新在同一游戏刻内可以沿着线路瞬间传播，所以机器的行为往往取决于**同一刻内的更新顺序**，而不只是延迟数值。

### 5.3 更新顺序为什么是命门

- 两个元件在同一刻互相影响时，谁先谁后决定了最终状态。
- 这正是"换个服务端核心机器就坏"的根本原因：核心为了实现并行或优化，可能改变遍历顺序。
- 也是为什么升级游戏版本后必须**逐台复验**：官方修 bug 时会顺带改掉某些顺序。
- 调试手段：原版提供 `/tick` 一类的控制命令（冻结、步进、加速等，具体子命令随版本变化），可以逐刻观察机器状态；也有 Carpet 一类的调试工具。

### 5.4 "卡顿机器"是破坏手段

**卡顿机器（lag machine）指故意构造的、以压垮服务器为目标的装置。** 常见形态：

- 极高频红石时钟，配合大面积红石线路制造更新风暴；
- 瞬间生成海量实体（TNT、掉落物、盔甲架、矿车、船）；
- 让水流与岩浆大面积流动与更新；
- 利用区块加载机制制造"永远加载 + 每刻都在算"的循环；
- 反复触发生成/卸载区块，让主线程一直做区块工作。

它的性质是**破坏行为，不是玩法**：目的是让所有人掉线、让服务器无法正常保存、甚至损坏存档。

### 5.5 怎么发现卡顿机器

| 信号 | 说明 |
| --- | --- |
| MSPT 突然持续飙高，TPS 掉到个位数 | 最直接的表现 |
| 实体数量异常 | 用 `/kill` 类命令统计前先**别急着清**，那是证据 |
| spark 火焰图里出现集中的红石/实体/区块热点 | 定位到具体区块与坐标 |
| 玩家报告"某个坐标一靠近就卡" | 坐标就是线索 |
| 日志里出现实体上限或看门狗相关警告 | 服务端已经在自保 |

处置顺序建议：**先定位坐标与装置 → 截图/记录 → 按规则处理 → 恢复受影响区域**。反作弊、日志与回滚手段见 [反作弊与防破坏](/tutorials/java/anticheat)。

## 6. 权限与工具

### 6.1 服务端侧：Carpet 一类工具

- 技术向服务器普遍使用 **Fabric + Carpet**（以及它的各类扩展）作为服务端侧的规则与调试工具：它能开关大量原版细节行为，也提供调试命令。
- **具体规则名与可用规则集合随 Carpet 版本变化**，请以对应版本的 Carpet 官方文档为准，不要照抄别人的规则清单。
- Carpet 是服务端 mod，原版客户端可以直接进服，不需要玩家装任何东西。
- 生电服的常见做法是：**把启用的规则清单公开**，让玩家知道哪些原版行为被改了。

### 6.2 客户端侧：MiniHUD / Litematica 一类工具

| 工具 | 用途 |
| --- | --- |
| MiniHUD | 在 HUD 上显示坐标、生物群系、光照、区块边界等 |
| Litematica | 原理图投影，照着搭机器 |
| Tweakeroo | 一批便利性调整 |
| Servux | 服务端 mod，让结构范围显示、原理图粘贴在服务器上正常工作 |
| Syncmatica | 把原理图上传到服务器，多人共享 |

### 6.3 服务器要支持什么

- 服务端侧 mod（Carpet、Servux、Syncmatica 的服务端部分）**需要 Fabric 服务端**。插件端（Paper 系）不能直接跑 Fabric mod；用桥接方案会有兼容性与性能代价，见 [模组服完整上手](/tutorials/java/modded)。
- 纯客户端 mod（MiniHUD、Litematica 的显示部分）在任何服务端上都能用，但**依赖服务端数据的部分**（结构边界、原理图粘贴、精准放置）需要服务端配合才能工作。
- 因此开生电服前要定一件事：**服务端是 Fabric 还是 Paper 系**。这个决定一旦做出，后面几乎所有工具链都跟着它走。
- 还要对齐**版本**：客户端 mod 的版本、服务端 mod 的版本、游戏版本三者必须一致，否则玩家连不进来。

### 6.4 权限清单

给技术玩家的权限建议单独分组，而不是直接给 OP：

| 权限 | 用途 | 风险 |
| --- | --- | --- |
| `/forceload` | 让机器持续运行 | 滥用会导致服务器长期高负载，建议登记制 |
| `/tick`（冻结/步进一类） | 调试机器时序 | 冻结全服会打断所有人，注意公告 |
| `/gamemode spectator`、`/tp` | 观察与搭建 | 低风险 |
| `/spark` | 自查性能 | 低风险，建议放开给技术组 |
| `/give`、创造模式 | 搭建机器 | 只应在测试环境或明确授权的建筑区使用 |
| WorldEdit 一类批量编辑 | 快速施工 | **一次错误的选择就能毁掉存档**，务必限定权限并先备份 |

## 7. 开一个技术向服务器的检查清单

| 项目 | 为什么必须做 |
| --- | --- |
| **世界预生成** | 玩家跑图触发的区块生成是 TPS 的主要杀手，预生成能把这项成本提前付掉，见 [性能优化](/tutorials/java/optimize) |
| **大工程前备份** | 技术玩家会做大范围改造与爆炸性测试，出问题时你要能回到上一分钟 |
| **独立的测试世界/测试服** | 任何新机器、新配置、新核心版本先在测试服验证，绝不在主服直接试 |
| **版本锁定与升级流程** | 升级会让机器失效，必须公告、备份、在测试服复验后再上主服 |
| **Carpet 规则清单公开** | 玩家需要知道哪些原版行为被改了，否则会把机器失效误判成自己的问题 |
| **关于卡顿机器与复制特性的明确规则** | 这两件事必须在规则里写清楚，否则封人没有依据 |
| **基线监控** | 记录正常时的 TPS/MSPT，才能在"变慢了"时有对比，而不是凭感觉 |
| **存储规划** | 备份 + 原理图 + 日志的增长速度往往超出预期 |
| **权限分级** | 技术组权限与普通玩家权限分开，OP 不轻易给 |
| **机器登记与沟通渠道** | 谁在哪建了什么机器，是排查问题时最有价值的信息 |

一份可以直接改的规则骨架：

```text
1. 允许：常规红石机器、刷怪塔、作物农场、村民交易设施。
2. 需要登记：常加载区块、区块加载器、任何无人运行的大型装置。
3. 禁止：以压垮服务器为目的的装置（高频时钟阵列、海量实体生成、区块反复加载）。
4. 复制类特性：明确写"允许"或"禁止"，不要留空白。
5. 版本升级：提前公告，升级后机器需自行复验，服主不保证兼容。
6. 处罚：按日志与坐标证据处理，先警告后封禁。
```

## 8. 小结

- 生电玩家造的是**资源产线**，按负载分类比按产出分类更有用。
- 服务端要关心的设置集中在：**刷怪上限与范围、实体激活范围、随机刻、红石实现、区块加载**。
- **常加载区块是有代价的**：内存、CPU、刷怪上限与存档抖动，必须审计与登记。
- 理解 **20 TPS / 50 毫秒**与**红石刻 = 2 游戏刻**，才能理解机器为什么坏、为什么慢。
- **卡顿机器是破坏手段**，要有规则、有检测、有回滚。
- 工具链选择（Fabric + Carpet vs Paper 系）是生电服的**第一个决定**，它会决定后面一切。

:::tip 技术服的 TPS 是设计结果，不是配置结果
很多服主把"卡"当成配置问题，于是一直在调参数、换优化插件，最后把机器全调坏了。真实情况是：**TPS 由玩家造了什么机器、机器多大、放在哪、加载了多少区块决定**。参数只能让你在原版行为与性能之间做取舍，不能凭空把一台设计糟糕的机器变便宜。先看设计，再谈配置。
:::
