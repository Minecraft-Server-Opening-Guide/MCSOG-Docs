插件服和模组服是两套不同的世界。插件在服务端"外挂"功能，玩家用原版客户端就能进；模组直接改游戏代码，**绝大多数内容模组要求服务端和客户端装同一套东西**，玩家不装就进不来。

这一篇把模组服从零到能开讲完：选加载器、装服务端、对齐客户端、放模组、排查不匹配，以及模组服特有的性能、备份与更新问题。如果你还在纠结"到底开插件服还是模组服"，先看 [服务端选择](/tutorials/java/core)。

## 1. 插件服和模组服的区别

| 对比项 | 插件服（Paper / Purpur 等） | 模组服（Fabric / NeoForge 等） |
| --- | --- | --- |
| 扩展方式 | 插件调用服务端提供的 API，不改游戏本体 | 模组直接修改游戏代码 |
| 玩家要不要装东西 | 不用，原版客户端即可 | 多数要装**同款加载器 + 同一套模组** |
| 典型内容 | 管理、小游戏、经济、领地保护 | 新方块、新物品、新生物、新机器、新维度 |
| 更新速度 | 核心更新快，插件跟得紧 | 慢，取决于每个模组作者 |
| 可调参数 | 核心配置 + 插件配置非常丰富 | 很少，主要靠模组本身与 JVM |
| 出问题时的排查 | 看插件列表与插件配置 | 看**模组清单是否完全一致**与崩溃日志 |

**要玩法内容选模组，要管理功能选插件**。两者混用的方案（混合端）存在，但兼容性与维护成本都更高，不建议新手起步就碰。

### 1.1 三类模组：仅客户端 / 仅服务端 / 双端必需

模组不是"装了就有用"，先分清它属于哪一类，否则一定会踩坑：

| 类别 | 典型例子 | 应该装在哪 | 装错会怎样 |
| --- | --- | --- | --- |
| **仅客户端（client-only）** | 渲染类（Sodium 等）、小地图、光影相关、界面增强 | 只装客户端 | 丢到服务端通常直接报错或崩溃，多数加载器会拒绝加载 |
| **仅服务端（server-only）** | 只在服务端生效的逻辑/性能类模组、部分管理类模组 | 只装服务端（有些模组两端都能装，但装在客户端没有意义） | 客户端装了一般不崩，但可能被服务端握手拒绝；服务端缺了则功能不存在 |
| **双端必需（both-required）** | 添加新方块、新物品、新生物、新维度、新机制的内容模组 | 客户端 + 服务端都要 | 缺任何一边：连接被拒，或注册表不匹配导致报错 |

还有一类介于两者之间：**双端都可以装、但不是必需**（例如内存优化、网络优化类模组）。这类模组的发布页会写清"可选"。

### 1.2 怎么知道一个模组属于哪一类

以模组**自己的发布页与说明**为准，优先级从高到低：

| 来源 | 看什么 |
| --- | --- |
| 模组发布页（Modrinth / CurseForge） | 环境标记。Modrinth 现在用 `environment` 字段（如 `client_only`、`server_only`、`client_and_server`），旧的 `client_side` / `server_side` 取值为 `required` / `optional` / `unsupported` |
| 模组 README / 作者公告 | 作者常直接写 "server-side only"、"client-side only"、"required on both sides" |
| Fabric 模组 | `fabric.mod.json` 里的 `environment` 字段：`"*"`（默认，两端都算）、`"client"`（客户端）、`"server"`（独立服务端，不含单人集成的服务端） |
| NeoForge 模组 | `META-INF/neoforge.mods.toml` 的元数据，以及代码中标注为仅客户端加载的入口（如 `dist = Dist.CLIENT`） |
:::warn 别把插件服的经验套到模组服
- `spigot.yml`、`paper-world-defaults.yml`、Bukkit 插件那一整套在模组服**不存在**，照着插件服教程调模组服只会白费功夫。
- 模组服默认**不能装 Bukkit 插件**（要装得用混合端，属于另一套方案）。
- 插件服的 JVM 参数、优化插件、热重载习惯都不能照抄（见第 10 节）。
- 反过来也一样：模组服的经验不要拿去套插件服。
:::

## 2. 选加载器：Fabric / NeoForge / Forge

| 加载器 | 定位 | 适合谁 |
| --- | --- | --- |
| **Fabric** | 轻量、启动快、跟进新版本快，加载器本体与 API 分离 | 追求性能与快速更新，模组以优化类 + 少量内容类为主 |
| **NeoForge** | Forge 血脉在现代版本上的延续，功能 API 更完整 | 现代版本的大型内容整合包、机器/科技类玩法 |
| **Forge** | 老牌加载器，历史整合包与老版本仍大量使用 | 要跑老整合包，或必须依赖只在 Forge 上维护的老模组 |

**版本格局要看清**：加载器"支持哪些 Minecraft 版本"是随时间变化的，本文不列具体数字，只给判断方法：

- Fabric：官方下载页可以同时选游戏版本与加载器版本，页面会直接给出下载与启动命令。Fabric 官方文档写明支持 1.14 及之后的所有正式版（以及 18w43b 之后的快照）。
- NeoForge：官网首页按 Minecraft 版本给出对应安装器文件；官方文档提供服务器安装步骤。
- Forge：官方下载页按版本列出 latest / recommended 构建，至今仍在为多个版本（含较新版本）发布；但新版本的模组生态有相当一部分已转向 NeoForge。

> **本站可直接下载** —— 加载器核心（Fabric / NeoForge / Forge）见 **[资源下载 · 服务端核心](/downloads/core)**；模组本体见 **[资源下载 · 模组](/downloads/mods)**；如果最后决定走插件服，插件见 **[资源下载 · 插件](/downloads/plugins)**。三处收录的都是官方与社区来源的下载链接，点「下载」按钮并按提示登录即可，**本站不存储任何文件**。
:::note 加载器之间基本不通用
同一个模组通常只支持一个加载器。Fabric 的模组不能丢进 NeoForge 服，反之亦然。所以**选加载器本质上是在选"你要装的模组都在哪一边"**：先去模组发布页确认目标模组支持哪个加载器、哪个游戏版本，再决定装什么。
:::

判断顺序建议：

```
先定玩法（要哪些模组） → 查这些模组支持的加载器与游戏版本
  → 取交集最大的那个加载器 + 游戏版本 → 再装服务端
```

## 3. 在服务端安装加载器

安装器界面和文件名会随版本变化，所以下面只讲**通用流程**，每一步的准确做法以加载器官方文档为准。

### 3.1 先确认 Java 版本

| Minecraft 版本 | 需要的 Java |
| --- | --- |
| 1.16.5 及更早 | 8 |
| 1.17.2 | 16 |
| 1.18.2 – 1.20.4 | 17 |
| 1.20.5 及更新 | 21 |

Java 装错版本是最常见的"安装器打不开/服务端起不来"原因，先排除它。

### 3.2 通用流程

1. 建一个空目录作为服务端根目录。
2. 到加载器官方下载页选好 Minecraft 版本与加载器版本，下载安装器（`.jar`）。
3. 运行安装器，选择**服务端（Server）**安装方式。命令行方式通常是加 `--installServer` 参数。
4. 安装器会产出一个**启动脚本或启动器 jar**（以及运行所需的库目录）。
5. **先启动一次**。第一次启动会生成 `eula.txt`、`server.properties`、`mods/`、`config/`、`logs/` 等，然后因为未同意 EULA 而退出。
6. 打开 `eula.txt`，把 `eula=false` 改成 `eula=true`（表示你同意 Minecraft EULA）。
7. **再次启动**，确认能正常起服、控制台没有报错。
8. 这时才往 `mods/` 里放模组，然后重启。

### 3.3 Fabric

- 官方服务器下载页（fabricmc.net 的 server 页面）可以选择版本，并给出下载命令与启动命令；照着页面显示的**文件名与启动命令**执行即可。
- 安装器有 Server 选项卡，用于在本地生成服务端启动器。
- 绝大多数 Fabric 模组需要 **Fabric API**，它也是一个模组，放进 `mods/`。

```bash
# 官方页面会给出类似这样的下载与启动命令，请以页面实际显示为准
# 1) 下载服务端启动器
# 2) 首次启动
java -jar <服务端启动器文件名> nogui
```

### 3.4 NeoForge

NeoForge 官方文档给出的流程（以 21.x 系列为例）：

```bash
# 1) 下载安装器（版本号以官网为准）
wget https://maven.neoforged.net/releases/net/neoforged/neoforge/<版本>/neoforge-<版本>-installer.jar

# 2) 安装服务端
java -jar neoforge-<版本>-installer.jar --installServer

# 3) 首次启动（会因 EULA 退出）
./run.sh        # Windows 用 run.bat
```

要点：

- 安装后会生成 `run.sh` / `run.bat` 和 **`user_jvm_args.txt`**。**改内存请改 `user_jvm_args.txt`，不要手改 `run.sh`**。
- 首次启动后出现 `mods` 文件夹，模组放这里。
- 更新 NeoForge 只需用新版本安装器再跑一遍同样的命令；官方明确提醒：**更新前先备份世界**。

### 3.5 Forge（老版本 / 老整合包）

```bash
java -jar forge-<版本>-installer.jar --installServer
```

- 较新的 Forge 与 NeoForge 类似，会生成 `run.sh` / `run.bat` 与 `user_jvm_args.txt`。
- 更老的版本会生成一个可直接启动的 `forge-<版本>.jar`，用 `java -jar` 启动。
- 老版本的模组往往只维护在 Forge 上，此时没有太多选择余地。
:::tip 起不来先看日志
加载器安装失败、模组崩溃，日志都在 `logs/latest.log`、`logs/debug.log` 和 `crash-reports/` 里。定位思路见 [常见报错与崩溃排查](/tutorials/faq/errors)。
:::

## 4. 客户端一侧：玩家必须装同一套

模组服的"进不去"绝大多数不是网络问题，而是**客户端和服务端的模组清单不一致**。

玩家的正确姿势：

1. 装**同一个加载器**，并且是**同一个 Minecraft 版本**。
2. 装**同一套模组**（包含所有依赖，例如 Fabric API）。
3. 模组版本也要对齐（见第 6 节）。

### 4.1 为什么清单不一致就进不去

进入服务器时，客户端与服务端会做一次"握手"：交换加载器信息、模组清单以及部分注册表内容。只要出现下面任一情况，就会被拒绝或直接报错：

- 服务端有、客户端没有的**双端必需**模组；
- 客户端有、服务端没有的同类模组；
- 同一个模组**版本不同**；
- 缺少依赖模组。

### 4.2 玩家会看到什么

| 加载器 | 表现 |
| --- | --- |
| NeoForge / Forge | 连接被拒，并弹出一个**列出被拒绝模组的界面**（社区常称 "mod rejections" / 不兼容模组界面），逐条给出原因，例如"服务端没有这个模组""版本不匹配"。具体文案与布局随版本变化 |
| Fabric | 加载阶段缺少依赖时，加载器会给出 "Incompatible mod set!" 一类的错误界面，并在日志里列出缺失/冲突的模组；Fabric 官方文档有崩溃报告与依赖覆盖的专门页面 |
:::tip 让玩家少踩坑的做法
- 把客户端 `mods/` 打包成压缩包发给玩家，或在整合包平台发布客户端包与服务端包。
- 在群公告里写清：加载器、Minecraft 版本、加载器版本、模组清单版本号。
- 服务端更新模组后，**同步更新客户端包**，否则老客户端会立刻进不来。
:::

## 5. 模组放在哪里

> **去哪里找模组** —— 本站收录了 Modrinth 的模组条目，见 **[资源下载 · 模组](/downloads/mods)**，可按加载器（Fabric / Forge / NeoForge / Quilt）与游戏版本筛选，点「下载」按钮并按提示登录即可拿到官方下载链接。放之前务必先确认它属于「仅客户端 / 仅服务端 / 双端必需」哪一类（见 [1.1](#11-三类模组仅客户端--仅服务端--双端必需)）。

| 位置 | 说明 |
| --- | --- |
| 服务端 `mods/` | 服务端加载的所有模组（`.jar`） |
| 客户端 `.minecraft/mods/` | 玩家客户端加载的所有模组 |
| `config/` | 模组自己的配置文件，多数在**首次启动后**生成，不在 `mods/` 里 |
| `defaultconfigs/` | 部分加载器/整合包用来放"新世界默认配置"的目录 |
:::warn 仅客户端模组不要放服务端，反之亦然
这是模组服最常见的崩溃原因之一：

- 把渲染/界面类**仅客户端模组**丢进服务端 `mods/`，服务端启动时就会报错甚至崩溃（服务端没有客户端类）。
- 把**仅服务端模组**丢给客户端，轻则无用，重则因为类缺失导致客户端崩溃。
- 只装一半的**双端必需模组**，结果就是玩家连不上。

判断方法回到第 1.2 节：以模组发布页的环境标记与作者说明为准。
:::

## 6. 三方匹配规则

模组服能不能跑起来，取决于三个东西同时对上：

| 匹配项 | 要求 |
| --- | --- |
| 游戏版本 | 服务端、客户端、每个模组都要支持同一个 Minecraft 版本 |
| 加载器版本 | 客户端与服务端用同一个加载器；加载器版本尽量一致（至少都在模组要求范围内） |
| 模组版本 | 同一个模组在两端必须**同版本**；依赖模组必须存在且满足版本范围 |

### 6.1 从日志诊断不匹配

| 现象/日志线索 | 含义 | 处理 |
| --- | --- | --- |
| 启动即崩，崩溃报告列出某个模组名 | 该模组与当前游戏版本/加载器不兼容，或缺少依赖 | 换对应版本，或补依赖 |
| 日志出现 "missing dependency" / 依赖解析失败 | 模组声明的依赖没装或版本不符 | 按日志补齐依赖 |
| 日志出现模组加载失败、类找不到 | 常是把仅客户端模组放到了服务端（或反之） | 从错误的一侧移除 |
| 玩家连接被拒，界面列出模组 | 双端清单/版本不一致 | 对齐两端模组 |
| 崩溃报告里 `Is Modded: Definitely; ... brand changed to 'fabric'/'neoforge'` | 只是说明当前是模组环境，本身不是错误 | 继续往下看真正的异常栈 |

依赖语义（Fabric 规范，NeoForge 类似）：

| 声明 | 含义 |
| --- | --- |
| `depends` | 硬依赖，缺失直接失败 |
| `recommends` | 软依赖，缺失只警告 |
| `conflicts` / `breaks` | 冲突，命中就报错 |

### 6.2 找不到是哪个模组在捣乱

用**二分法**（NeoForge 官方文档推荐的做法）：

1. 把一半模组移出 `mods/`（注意保持依赖完整）。
2. 启动，看问题是否还在。
3. 还在 → 继续对当前这一半做二分；不在 → 把另一半换进来再试。
4. 重复到定位出具体模组。

## 7. 性能模组（按类别认识）

模组服的性能优化主要靠"装对模组"，而不是调配置文件。下面这些是能确认存在、且被广泛使用的（加载器支持情况来自各自项目页，会随版本变化，装之前请再确认一次）：

| 类别 | 模组 | 作用 | 加载器 | 备注 |
| --- | --- | --- | --- | --- |
| 游戏逻辑优化 | **Lithium** | 优化游戏逻辑（刷怪、AI、方块行为等）的性能，尽量不改变行为 | Fabric、NeoForge、Quilt | 两端都可装，服务端收益明显 |
| 内存占用 | **FerriteCore** | 降低内存占用（方块状态等数据结构） | Fabric、Forge、NeoForge、Quilt | 内存吃紧的模组服很实用 |
| 网络优化 | **Krypton** | 优化网络栈，降低带宽与 CPU 开销 | Fabric | 主要面向服务端与联机 |
| 光照引擎 | **Starlight** | 重写光照引擎，修光照性能与错误 | Fabric | 项目已归档，最高支持到 1.20.4；其说明也写明 1.20 上它与原版差距已经很小。**新版本不要硬装** |
| 区块预生成 | **Chunky** | 提前生成区块，减少玩家跑图时的卡顿 | Fabric、Forge、NeoForge，以及 Paper/Spigot 等 | 长期开放的服几乎是必备 |
| 客户端渲染 | **Sodium** | 客户端渲染优化（提升帧率） | Fabric、NeoForge、Quilt | **仅客户端**，服务端不要装 |
:::note 关于"优化模组"的两条纪律
- **不要同时装多个功能重叠的优化模组**（例如两个光照重写），它们互相冲突的概率很高。
- 优化模组会改变游戏内部行为，**生电/精密机器服要谨慎**：宁可慢一点，也不要让机器失效。
:::

## 8. 世界与数据兼容性：删除模组是不可逆的

模组添加的方块、物品、实体、维度、生物群系，都会写进世界存档。**移除模组后，这些内容对应的数据仍在存档里，但游戏已经不认识它们**：

- 轻则变成"缺失方块/空实体"，看起来像空气，实际数据还在；
- 重则区块加载报错，甚至让存档无法打开；
- 重新装回**同一个模组且版本兼容**时，通常能恢复。
:::warn 先备份，再动模组
- 任何"加模组、删模组、换加载器、换游戏版本"的操作之前，**先完整备份世界目录**（备份方法见 [备份与恢复](/tutorials/java/backup)）。
- 模组服的存档**不能直接降级**：把模组服的世界拿回原版或低版本打开，风险极高。
- 想"试装一个模组看看"？请在**副本**上试，不要在正式存档上试。
:::

## 9. 安全更新模组服 / 整合包服务端

推荐流程（顺序不要省）：

1. **备份**：世界 + `config/` + 模组清单。
2. **冻结变更**：先关服，或在维护窗口内操作。
3. **先更新加载器**，启动一次确认服务端本身没问题（此时旧模组可能报错，属正常）。
4. **逐个更新模组**，不要一次全换。分批更新便于定位问题模组。
5. **对齐客户端包**：把更新后的 `mods/`（客户端侧）重新打包发布。
6. **观察**：起服后看 `logs/latest.log` 有无异常，在线跑一段时间再看 TPS 与报错（可用 [性能优化](/tutorials/java/optimize) 里的方法）。
7. **保留回滚包**：把上一版服务端目录与客户端包留着，出问题能立刻退回。

## 10. 内存与 JVM 参数

模组服和插件服的内存特征不一样：

| 项目 | 插件服 | 模组服 |
| --- | --- | --- |
| 堆内存需求 | 相对低 | **明显更高**：模组注册表、模型、配方、机器数据都吃内存 |
| 启动时间 | 短 | 长（几百个模组时启动数分钟很常见） |
| 主要瓶颈 | 主线程 + 插件质量 | 主线程 + 模组质量 + 内存/GC |
| 参数来源 | 核心官方文档的推荐组合 | **加载器自己的启动文件说明** |

实操建议：

- **内存给足但别过量**。堆开太大，GC 停顿反而变长；先按实际玩家数与模组规模给一个合理值（例如小型模组服 4–8 GB 起，逐步调），再观察。
- NeoForge / 较新 Forge：改 `user_jvm_args.txt`（安装时生成，文件内自带注释说明），不要手改 `run.sh`。
- 其他启动方式：在启动脚本里用 `-Xms` / `-Xmx` 指定内存。
- **不要照抄插件服的参数组合**。为 Paper/Spigot 设计的参数组合假设了不同的负载与 GC 行为；模组服请优先参考加载器官方文档与模组作者的说明。
- 参数只解决内存/GC 层面问题，**救不了单核瓶颈**，也救不了写得很差的模组。

```bash
# 示意：把内存参数写在启动脚本或 user_jvm_args.txt 中
# 具体数值按你的模组规模与玩家数调整
-Xms4G
-Xmx8G
```

## 11. 排错速查表

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 服务端启动即崩，日志点名一个模组 | 模组版本与游戏/加载器不匹配，或缺少依赖 | 换对应版本，补齐依赖 |
| 界面/日志提示 "Incompatible mod set!" 或列出被拒绝的模组 | 双端模组清单或版本不一致 | 对齐两端模组与版本 |
| 删掉模组后，世界里出现缺失方块/实体 | 模组数据残留，游戏不再认识 | 装回兼容版本恢复；**先备份**，不要继续写入存档 |
| 玩家进不去，服务端没有明显报错 | 客户端缺模组/缺依赖/版本不同 | 让玩家使用同一份客户端包 |
| 服务端能起但很卡 | 模组本身性能差、实体/机器过多、内存不足 | 用 profiler 定位（见 [用 spark 分析服务器性能](/tutorials/ops/spark)），再针对性处理 |
| 启动卡在加载模组很久 | 模组数量多、首次生成配置、磁盘慢 | 属正常现象；用 SSD，并耐心等待 |
| 装了仅客户端模组到服务端 | 服务端缺少客户端类 | 从服务端 `mods/` 移除 |

## 结语

模组服的复杂度来自"两端必须一致"这一条铁律：**先定玩法与版本，再装加载器，最后才加模组**。每加一个模组就启动一次、每次动模组前先备份，能省下大量返工时间。
