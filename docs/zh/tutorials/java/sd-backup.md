生电服的世界是**被持续大范围改写**的：机器一开，地形、方块、实体都在成片变化。一次误操作、一次崩溃写坏存档，代价往往不是"丢几分钟进度"，而是"整套工程白做"。所以在生电服里，存档保护不是顺手做的事，而是要设计进流程里的一环。

通用的备份原则——该备什么、怎么保证一致性、保留策略、恢复流程——已经写在 [备份与恢复](/tutorials/java/backup) 里，本篇不重复。这里只讲生电场景下额外的三件事：**用 MCDR 的备份插件把备份变成流程**、**用 `Ledger` 查清发生了什么**、**把至少一份备份放到机器之外**。

## 一、为什么生电服的备份要更勤

| 生电服的特点 | 对备份的要求 |
| --- | --- |
| 机器一旦跑起来，世界变化极大：成片清空区域的装置、持续运行的农场，在很短时间里就能改掉大片地形与实体 | 备份间隔必须短于你能接受的最大损失，不要指望一份隔夜备份兜住一次大工程 |
| 回档是连坐的：整档回退会把同一时间窗里**所有**玩家的进度一起抹掉 | 出事时先争取局部修复，只有修不好才整档回退 |
| 大型工程投入极高：从备料、搭建到调试，机器是"用时间换产出" | 备份保住的不是几格方块，而是已经投进去的那段时间 |
| 存档与备份默认在同一台机器、同一块盘上 | 本地备份之外，必须有一份离开这台机器 |

:::warn 没有验证过恢复的备份不算备份
这句话对生电服尤其成立：机器越猛，回档越贵。等到真出事那天才发现备份从来没成功过，损失无法补救。恢复演练的做法见 [备份与恢复](/tutorials/java/backup)。
:::

## 二、用 MCDR 的备份插件把备份变成流程

MCDR 是**独立于服务端进程之外**的 Python 管理器，服务端崩了它还在，因此它能自动重启服务端，也能在崩溃时执行备份——这正是备份该待的位置。它的安装方式、插件机制与指令见 [MCDR 服务端管理器](/tutorials/java/mcdr)。

MCDR 官方插件目录里**确实存在**的备份类插件目录名，可以按用途方向分成四组：

| 方向 | 插件目录名 | 大致用途 |
| --- | --- | --- |
| 整档备份 | `prime_backup`、`extra_prime_backup`、`quick_backup_multi`、`better_backup`、`permanent_backup`、`zip_backup`、`smart_backup`、`cushion_of_backup` | 以整个存档或整个服务端目录为单位备份与保留 |
| 定时备份 | `timed_quick_backup_multi`、`auto_backup` | 按间隔自动触发，不依赖你记得手动执行 |
| 分区块与分区域备份 | `chunk_backup`、`region_backup` | 以区块或区域为单位，粒度比整档更细 |
| 异地备份 | `ftp_backup`、`baidu_netdisk_backup` | 把备份送到远端存储 |

选插件前后有三件事必须确认：

1. **分组只是按插件目录名看出的方向**，具体功能、配置项与保留规则以每个插件自己的说明为准；装好后先在测试环境里真的跑一遍"备份 → 恢复"。
2. **插件不会替你解决一致性**：无论用哪一个，都要确认它不会拷到写了一半的存档，原则见 [备份与恢复](/tutorials/java/backup)。
3. **别把备份产物留在同一块盘上**，否则第四节与第六节说的问题照样发生。

对生电服，比较实用的组合是"**一个定时整档备份 + 一个分区块备份**"：前者负责兜底，后者负责把回退范围缩小到某个区域。两个都装时注意让它们错开时间，避免同时读写磁盘。

## 三、`Ledger`：先查清"发生了什么"

`Ledger` 是服务端日志 mod（loaders：`fabric`、`quilt`；支持版本 `1.17-rc1` 至 `26.3`）。

在插件端，同类工具里最出名的是 **CoreProtect**（loaders：`bukkit`、`folia`、`paper`、`purpur`、`spigot`；支持版本 `1.14.1` 至 `26.2`；它是插件端的数据记录与防破坏工具，支持回滚与恢复）。`Ledger` 可以理解为 Fabric 生态里**对标 CoreProtect 的那一套**：同样记录方块与容器的操作、同样能按时间与位置回查；区别是 CoreProtect 跑在插件端且自带回滚，而 `Ledger` 只负责记录与查询。

它和备份回答的是两个不同的问题，不能互相替代：

| 对比项 | `Ledger` | 备份 |
| --- | --- | --- |
| 回答的问题 | 发生了什么、谁做的、什么时候、影响了哪里 | 怎么把世界整体退回到某个时间点 |
| 数据形态 | 事件记录 | 存档目录的副本 |
| 粒度 | 事件级，可以一路查到具体的位置与容器 | 整档（目录级） |
| 出事时先做什么 | 定位与定责，据此判断"能不能只回退或修一小块" | 定位不到时的兜底：整档回退 |
| 代价 | 记录会持续增长，需要维护 | 占磁盘，回退会抹掉同期的所有进度 |

几点使用提醒：

- `Ledger` 的定位是**记录**，不是恢复手段。它给你的是"范围与责任人"，真正把世界改回去还是要靠人工修复或备份。
- 记录量需要长期维护：MCDR 官方插件目录里有 `ledger_cleaner`，作用就是清理 `Ledger` 的数据。这也说明它的数据不是放着不管就行。
- `Ledger` 是服务端 mod，需要 Fabric 服务端。防破坏的另一半（权限与实时手段）见 [反作弊与防破坏](/tutorials/java/anticheat)。

**两者的正确顺序是**：出事后先用 `Ledger` 把范围缩到一小块，能局部修就局部修；定位不到、或者破坏面太大，再用备份整档回退。反过来做，你会为了一个人的行为把全服的进度一起抹掉。

## 四、异地备份：这一步不能省

本地备份和服务器在同一台机器上，所以下面这些情况会**同时带走存档和你的全部备份**：

| 情况 | 结果 |
| --- | --- |
| 机器（或磁盘）坏了 | 存档与本地备份一起没 |
| 系统被重装、磁盘被格式化、目录被误删 | 同上 |
| 机器被服务商收回、机房出事 | 你可能连机器都拿不回来 |

插件层面已经有现成的异地思路：`ftp_backup` 与 `baidu_netdisk_backup` 都是**把备份送到远端**的插件，也就是说异地备份不需要你从零写脚本。

但"传上去"不等于"能拿回来"。远端凭据会不会过期、路径还在不在、备份是不是完整、能不能恢复，都要定期验证；异地的通用做法与维护见 [异地备份](/tutorials/ops/offsite-backup)。另外要注意：异地备份传的是**同一条链路**，如果备份本身因为磁盘满或权限问题失败了，远端只会安静地少掉一份，所以本地的备份日志同样要看。

## 五、一份可以直接照做的检查清单

| 时间点 | 动作 |
| --- | --- |
| 开服前 | 装好一个定时整档备份插件，把备份目录指到另一块盘 |
| 大工程开工前 | 手动打一份整档备份，并记下时间点（回退时的锚点） |
| 每次改动配置或加 mod 前 | 备份配置与存档，改完先观察再继续 |
| 平时 | 确认备份产物真的在生成（看目录与日志），而不是只看插件加载成功 |
| 定期 | 把一份备份送到远端；抽一份在测试环境里解压并恢复 |
| 出事时 | 先查 `Ledger` 定位范围，能局部修就局部修，修不了再整档回退 |

## 六、备份放在哪：三个位置

| 位置 | 能挡住什么 | 挡不住什么 |
| --- | --- | --- |
| 存档旁边或同一块盘 | 手滑删错文件、单份备份损坏 | 磁盘损坏、格式化、整个目录被误删 |
| 同一台机器的另一块盘 | 单块磁盘损坏 | 系统重装、整机故障、机器被收回 |
| 机器之外的远端 | 整机故障、误格式化、机器被收回 | 没有明显短板，但前提是你验证过它能取回来 |

常见的错误就藏在这张表里：

- 备份目录设在 `world/` 里面，回退时连备份一起被覆盖；
- 备份与存档在同一块盘上，盘坏了两个一起没；
- 只保留最新一份，遇到"存档已经坏了但还没发现"的情况就没救了；
- 装了备份插件却从来没看过它的日志，直到出事那天才发现它一直在失败。

## 七、备份不是孤立的：三件套

机器越猛，越要**备份 + 权限 + 防崩规则**这三件东西一起上。它们各自负责一个环节，缺哪一环都会在出事那天暴露：

| 一环 | 解决什么 | 去哪看 |
| --- | --- | --- |
| 备份 | 出事之后把世界退回去 | 本篇与 [备份与恢复](/tutorials/java/backup) |
| 权限与白名单 | 让不该动手的人动不了手 | [反作弊与防破坏](/tutorials/java/anticheat) |
| 防崩规则 | 做更新抑制一类操作时，不让服务端直接崩掉 | [Carpet 及其附属包](/tutorials/java/sd-carpet) |
