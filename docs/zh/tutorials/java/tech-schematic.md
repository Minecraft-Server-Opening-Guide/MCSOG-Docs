生电玩法绕不开原理图：别人设计的世吞、刷怪塔、切门机器，你不可能凭记忆照抄，得靠投影一层层对着搭。单人存档里这很简单，装上客户端投影 mod 就行；一旦到了多人服务器，原理图就散落在每个人自己的电脑上，谁想照着搭，都得先向原作者要一份文件。

`syncmatica` 解决的正是这件事。它的官方描述原文是：Syncmatica is a mod which aims to mod into litematica so that schematics and their placements can be easily shared. 也就是说，它是给 Litematica 做同步的配套，让原理图和放置能被方便地共享。

这一篇只讲三件事：为什么需要它、它装在哪一侧、版本怎么对齐。**具体怎么上传、谁有权限、用什么命令，请以 mod 官方说明为准，本篇不复述操作步骤**——那部分每个版本都可能变，照着过期教程走反而更容易出错。

## 一、多人服务器上原理图卡在哪

单人存档里，原理图文件和投影都在你自己的客户端上，不存在"共享"问题。多人服务器上则有三层麻烦：

| 麻烦 | 具体表现 |
| --- | --- |
| 文件在个人电脑上 | 每来一个新玩家，原作者都要重新发一次文件 |
| 位置对不上 | 投影需要知道"这份原理图放在世界的哪个坐标"，口头报坐标很容易传错 |
| 版本与来源混杂 | 传着传着就分不清谁手里那份是不是最新的 |

`syncmatica` 要处理的就是前两层：把原理图与它的放置变成"可以方便地共享"的东西。注意它的官方描述用的是 aims to（目标是）这个说法，说明它做的是同步与共享这一层，而不是替你做投影显示——投影显示仍然是 Litematica 的活。

> 想先了解投影在生电工具链里的位置，可以回看 [生电与红石](/tutorials/java/redstone) 里的客户端 mod 表，以及 [生电与红石进阶](/tutorials/java/redstone-advanced) 里对 MiniHUD、Litematica 一类工具的说明。

## 二、两侧各装什么

这是本篇最需要记住的一张表。共享原理图不是"装一个 mod 就完事"，而是**服务端和客户端都要装 Syncmatica，客户端还要额外装 Litematica**。

| 位置 | 需要装 | 说明 |
| --- | --- | --- |
| 服务端 | `syncmatica` | 同步的服务端一半。只装客户端是共享不起来的 |
| 客户端 | `syncmatica` | 同步的客户端一半，和 Litematica 配合工作 |
| 客户端 | `litematica` | 真正负责投影显示的 mod。`syncmatica` 是为它做同步的配套 |

三条容易踩的坑：

1. **只给玩家装了 Syncmatica**，服务端没装，同步无从发生。
2. **服务端装了 Syncmatica 却没让玩家装 Litematica**，共享出来的原理图没有东西去显示它。
3. **两边版本不一致**，这是最常见的问题，第三节单独讲。

## 三、三个 mod 的加载器与版本区间

下面的数据来自 Modrinth 官方条目，写作时核对过。把它当作选版本的起点，实际下载前再核对一次项目页。

| mod | loaders | 支持版本 | 下载量（约） |
| --- | --- | --- | --- |
| `syncmatica` | fabric、quilt | 1.16–26.3 | 83.9 万 |
| `litematica` | fabric、forge、liteloader、ornithe | 1.12–26.3 | 2644 万 |
| `servux` | fabric | 1.14.4–26.3 | 98.4 万 |

几点补充：

- 三个 mod 的版本区间都很宽，从 1.12 / 1.14 / 1.16 一直覆盖到 26.x 一类的近期版本。**区间宽不代表随便挑一版就能用**，真正要对齐的是"游戏版本一致、两侧的 Syncmatica 同属一个版本区间"。
- 还有一个常被一起提到的 mod：`servux`。它的官方描述原文是：Servux is a server-side mod that provides extra support and features for some client-side mods when playing on a that server. 它是**服务端 mod**，为部分客户端 mod 提供额外支持与功能。它不是共享原理图的必需品，但它解决的是同一类问题——"客户端 mod 想要更多数据，得服务端配合"。
- `litematica` 的 loaders 里有 forge 与 liteloader、ornithe，说明它本身不止 Fabric 一条路；但 `syncmatica` 只有 fabric 与 quilt，**这一侧的同步能力是把选择面收窄的那一环**。

## 四、版本对齐：这一侧最容易错

共享原理图是两侧配合的机制，所以"对齐"不是一句口号，而是四个必须同时成立的版本关系：

| 要核对的东西 | 要求 |
| --- | --- |
| 游戏版本 | 客户端与服务端必须是同一个游戏版本 |
| `syncmatica`（服务端） | 落在该游戏版本的支持区间内 |
| `syncmatica`（客户端） | 与上面同一个版本区间，两边不要混用 |
| `litematica`（客户端） | 与该游戏版本匹配 |

现实里最常见的翻车方式有两种：一是**只更新了一侧**（比如只换了客户端的 mod，服务端还停在旧版），二是**为了让某个 mod 跑起来把游戏版本往回退**，结果另一侧的 mod 又对不上了。

给一个稳妥的操作顺序：

1. 先定游戏版本，再按第三节的表把三个 mod 都挑好。
2. 服务端与客户端的 `syncmatica` 用同一版本区间的文件。
3. 装完先确认能正常进服、投影能显示，再谈共享。
4. 出问题时的第一判据永远是**版本**，而不是配置。

## 五、为什么本篇只讲"装在哪一侧"

共享原理图是一套**跨两侧协作**的机制，任何一步错位都不会报出清晰的错误，只会表现为"共享没反应"。而具体的操作方式——怎么把原理图放上去、谁可以放、用什么命令管理——属于 mod 自身的功能面，会随版本变化。

所以本篇的口径是：

1. **原理讲清楚**：为什么需要它、数据在哪两侧之间流动。
2. **位置说清楚**：服务端装什么、客户端装什么，一个都不能少。
3. **版本对齐说清楚**：三份东西的版本关系。
4. **操作交给官方**：mod 官方说明里怎么写，就怎么做。

这样写不是偷懒，而是避免把某一版的界面和命令写死在这里，等 mod 更新之后误导你。

## 六、它和 Carpet 是什么关系

一句话：**同属生电工具箱，但解决的是不同问题**。

| | Carpet | Syncmatica |
| --- | --- | --- |
| 解决什么 | 用规则开关原版细节行为 | 让原理图与放置能被方便地共享 |
| 形态 | Fabric 服务端 mod，提供规则系统 | 同步 mod，服务端与客户端各一半 |
| 典型用法 | `/carpet <规则名> <值>` | 与 Litematica 配合共享原理图 |

两者的共同点是都以 Fabric 为主：Carpet 及其全部附属包都是 Fabric，`syncmatica` 的 loaders 也是 fabric 与 quilt。这也是 [服务端选择](/tutorials/java/tech-server) 里推荐 Fabric 服务端 + MCDR 的原因之一——工具链在同一侧，不用做桥接。

Carpet 本体的定位与规则用法，见 [Carpet 及其附属包](/tutorials/java/tech-carpet)。

## 七、和世吞、切门怎么配合

投影最典型的用途就是搭大机器：世吞是 TNT 阵列加飞行器、成片清空区域的机器，尺寸大、结构重复、对位置精度要求高，靠人脑记是不可能搭对的。正常流程是：**先有原理图，再用投影照着搭**。

共享原理图在这个流程里解决的是协作问题：一台世吞往往不是一个人搭完的，需要几个人分片施工；投影一致，几个人的方块才能拼得上。

而一旦机器开始运转，重点就不再是投影，而是风险控制：[世吞与切门](/tutorials/java/tech-machine) 讲的是机器越猛，越要"备份 + 权限 + 防崩规则"三件套，以及新版本上更新抑制（社区俗称"切门"）要靠社区 mod 恢复这些事实。搭机器之前先把那篇读完。

## 八、底线清单

```
服务端装 Syncmatica + 客户端装 Syncmatica + 客户端装 Litematica
再把三份版本对齐 —— 缺一项，共享就不成立
```

- **服务端侧别忘了**：只配客户端是新手最常见的错。
- **操作照官方**：不要在没核对 mod 官方说明的情况下照抄别人的步骤。
- **先对齐版本再装**：版本区间见第三节的表，装之前核对项目页。
