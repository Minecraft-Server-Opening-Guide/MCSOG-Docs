基岩版的优化思路和 Java 版几乎是两套东西。Java 版有插件、有 `spark`、有几十个可以调的配置项；官方基岩版服务端（BDS）**能拧的旋钮很少**，而且不少键在不同版本里连名字都不一样。所以基岩版"优化"的重心在**世界设计**和**硬件**上，而不是在配置文件里翻找。

本篇只讲官方 **BDS**。还没把服务端跑起来的话，先看 [BDS 服务端](/tutorials/bedrock/bds)。如果你用的是第三方核心，可以直接跳到第 7 节。

## 1. 基岩版的性能模型和 Java 版不一样

| 对比项 | Java 版（Paper 等） | 基岩版（官方 BDS） |
| --- | --- | --- |
| 世界模拟 | 主线程 tick，但核心提供大量优化开关 | 世界模拟基本压在**单个线程**上，核多帮不上太多忙 |
| 插件生态 | 极其丰富，很多优化靠插件完成 | 官方服务端**不支持插件**，替代品是附加包与脚本 API |
| 可调参数 | 核心配置加插件配置，几十项 | `server.properties` 里与性能相关的只有寥寥几项 |
| 内存控制 | 用 `-Xmx` / `-Xms` 自己指定 | **没有内存参数**，由程序自己向操作系统申请 |
| 分析工具 | `spark` 火焰图、各种 profiler | **没有 `spark`**，也没有成熟的火焰图流程 |
| 热重载 | 部分场景可以 | 不支持 `/reload`，改配置只能重启 |

最关键的一条是**单核主频决定上限**：

- 世界模拟跑在一个线程上，多出来的核心主要分担网络、存档写入等外围工作；
- 所以"16 核 2.0 GHz"的机器通常跑不过"4 核 4.5 GHz"的机器；
- 选机器时先看单核性能，再看核数。
:::warn Java 版的优化经验不能照搬
下面这些东西在 BDS 上**都不存在**，不要照着 Java 教程做：

- `spark` 火焰图（不支持 BDS，详见第 8 节）；
- Paper / Spigot 的 `paper.yml`、`spigot.yml` 那套配置；
- 实体激活范围、刷怪上限、每 tick 实体数之类的插件或核心开关；
- 优化类插件（官方服务端没有插件系统）。

能照搬的只有**概念**：减少同时加载的区块、减少实体、减少高频红石。
:::

## 2. 能调的：`server.properties`
:::warn 有哪些键、默认值是多少，随 BDS 版本变化
不同 BDS 版本里，`server.properties` 的**键名、取值范围、默认值都可能不同**：有的键是后来才加入的，有的键在某个版本被改名或被拆成多个键（移动校验那一组就是典型例子）。

所以本文只解释这些键**在做什么**、调它要付什么代价。**请打开你自己服务器目录下的 `server.properties` 逐项核对**：官方生成的默认文件里，每个键上方都有一行注释，写明它的含义、允许范围和默认值，那才是对你这个版本最准确的说法。
:::

### 2.1 主要性能键

| 键 | 作用 | 调低的代价 | 建议方向 |
| --- | --- | --- | --- |
| `view-distance` | 服务端向玩家发送多远的区块数据，也就是"玩家能看多远"（官方默认 32，范围下限 5） | 远处发雾、地形"跳出来"，观感变差 | **优先动的一项**：玩家设备普遍一般或带宽紧张时往下调 |
| `tick-distance` | 玩家周围多远的区块**真正参与运算**（刷怪、作物、红石、流体）（官方默认 4，范围 4-12） | 远处的机器、农场、红石电路可能停摆 | 比视距更直接地影响 CPU；没有"远距离机器"需求时保持较小值 |
| `max-threads` | 服务端最多尝试使用多少线程（官方默认 8，0 表示不限制；有的版本里删除该键亦同） | 调得过低可能让网络、存档等外围任务排队 | **它不会把世界模拟拆到多核**；调高不等于更快，先保持默认 |
| `player-idle-timeout` | 玩家挂机多少分钟后被踢出 | 挂机玩家会更早掉线，影响挂机需求 | 接近零成本的减负手段，按你的挂机规则定 |
| `compression-threshold` | 多大的网络包才开始压缩 | 调低表示压缩更多包，**更吃 CPU**、更省带宽 | 先看瓶颈在哪：带宽紧张就调低，CPU 紧张就调高 |
| `compression-algorithm` | 网络压缩算法（常见为 `zlib` / `snappy` 这类选项） | 换成压缩率更低的算法，等于用带宽换 CPU | 带宽充足选更快的算法，带宽紧张选压缩率更高的 |

关于这几项，有三点要说清楚：

1. `view-distance` 和 `tick-distance` 是**两件事**：前者决定"看不看得见"，后者决定"跑不跑运算"。降视距主要影响观感，降模拟距离会影响机器。
2. `max-threads` 是**线程上限**，不是"并行世界模拟的开关"。把它调大不会让单核瓶颈消失。
3. `player-idle-timeout` 是少数**几乎没有副作用**的减负项：踢掉挂机玩家就少加载区块、少算实体。

### 2.2 与移动校验、反作弊相关的键

这些键**不是性能开关**，但经常被当成"优化项"去调，所以单独说明：

| 键 | 作用 | 放宽校验的代价 | 建议方向 |
| --- | --- | --- | --- |
| `server-authoritative-movement`（部分版本） | 服务端权威移动，取值为几种校验模式之一，越靠服务端权威越严格 | 放宽等于位置纠正变少，但**作弊空间变大** | 公开服保持默认或更严格 |
| `server-authoritative-movement-strict`（部分版本） | 更严格地校验玩家位置，纠正更频繁 | 关掉等于抖动变少，但穿墙、瞬移更难发现 | 不要为了"省性能"关掉 |
| `player-position-acceptance-threshold` | 客户端与服务端位置的**容忍度** | 调低表示纠正更频繁，高延迟玩家更容易被"拉回" | 只在高延迟普遍、玩家频繁被拉回时小幅放宽，并清楚这是安全取舍 |
:::warn 别把反作弊当成性能开关
位置纠正确实有网络开销，但它换来的是"玩家不能随便瞬移"。为了省一点点 CPU 或带宽去放宽校验，是典型的得不偿失。只有在**延迟普遍很高、玩家频繁被拉回**时，才考虑小幅调整，并且要明白你在拿什么换什么。
:::

### 2.3 其他可能存在的键

不同版本里还能看到一些与性能沾边的键，例如：

- 把**可视区块生成**下放给客户端的开关：服务端少干一点活，代价是低配客户端更卡；
- 附加包与脚本的**内容日志**和**看门狗**相关键：用来发现脚本报错、脚本跑得太慢、内存超限。

它们**是否存在、叫什么、默认值是多少都随版本变化**，这里不给出具体键名与数值，请以你本地文件与官方文档为准。使用前先确认你的版本确实有这些键，不要照抄网上其他版本的配置。

### 2.4 一份示例片段

```properties
# 视距：先往下调，观察观感与 CPU 变化
view-distance=12

# 模拟距离：没有远距离机器需求就保持较小值
tick-distance=4

# 线程上限：保持默认，不要当成提速开关
max-threads=8

# 挂机踢出：按你的挂机规则定
player-idle-timeout=15

# 压缩：带宽紧张用默认，CPU 紧张可调高阈值
compression-threshold=1
compression-algorithm=zlib
```

上面这些数值**只是示例**，既不是默认值也不是推荐值。请对照你本地文件里的注释，改成适合你的值。
:::note 改完必须重启
BDS 不支持 `/reload`。改完 `server.properties` 要用控制台正常 `stop` 再启动，不要直接杀进程。
:::

## 3. 真正的大头：世界设计

在基岩版上，**你能配置的东西很少，但你能建的东西很多**。绝大多数"服务器卡"最后都能归到地图上：

| 负载来源 | 处理方向 |
| --- | --- |
| 同时加载的区块太多 | 降低 `view-distance` 与 `tick-distance`，把常加载区域（ticking area）用到最少 |
| 常加载机器太多 | 每座"没人在也要跑"的机器都在持续吃 CPU，不需要的拆掉或停掉 |
| 红石时钟一直跑 | 高频时钟是典型负载来源，能用低频方案就别用高频 |
| 实体太多 | 生物、掉落物、矿车堆积；控制农场规模，及时收集或清理掉落物 |
| 农场太大 | 产量远超需求的农场是纯负担，缩小规模或按需开启 |
| 掉落物堆积 | 收集与销毁设计不当会让实体长期留存 |

几点说明：

- **常加载区域（ticking area）**让指定区块在没有玩家时也持续运算。它很方便，但每个区域都在持续消耗 CPU，**用完就删**。
- **实体堆积**有个典型症状：CPU 总占用看起来不高，但整个服务器就是卡。这时要处理的是实体数量与复杂区块，而不是再找一个参数。
- **做减法优先**：拆掉三座不用的农场，通常比调十遍配置文件更有效。
:::tip 先做减法，再谈参数
在基岩版上，"优化"的第一手段是**少建、少跑、少加载**。参数只能在很小的范围里帮忙。
:::

实体与掉落物的排查思路可以看 [实体与掉落物堆积导致的卡顿](/tutorials/faq/entity-lag)。需要提醒的是：**那篇里的诊断工具是 Java 版的**（例如 `spark`、TPS 与 MSPT 指标），基岩版用不了；但**"少实体、少掉落物、少常加载机器"的设计原则是通用的**，可以直接借鉴。

### 3.1 常加载区域与"离线机器"

常加载区域（ticking area）是基岩版少见的双刃剑：

- **好处**：没有玩家在场时，指定区块里的红石、流体、作物、生物仍会照常运算，机器可以离线产出；
- **代价**：这些区块会**一直**占用主线程时间，和有没有玩家在线无关；
- **建议**：只给真正需要的区域开，事情做完就删；能改成"有人时再跑"的机器就不要常加载。

排查时先问自己三个问题：这座机器还需要吗？它必须在没人时也跑吗？它的产出真的用得上吗？三个问题里只要有一个答"不"，就该关掉它。

## 4. 区块、世界大小与预生成

视距和世界规模是两笔不同的账：

- **视距的账**：`view-distance` 越大，每个玩家进服、移动、跨区域时要下发的区块数据越多，CPU 与带宽一起上涨。它是最大的 CPU 与带宽杠杆，同时也是玩家最能直接感受到的观感项。
- **世界大小的账**：玩家探索过的区域都会写进存档。世界越大、越老，`worlds/` 目录越大，**启动、保存、备份都变慢**，磁盘 I/O 压力也更大。

能做的事情：

1. **限制活动范围**：用"世界边界"的思路把玩家集中在需要玩的区域，而不是让世界无限扩张。你的版本或核心是否提供现成的边界命令、怎么用，请以官方文档为准。
2. **不鼓励无目的远行**：跑图本身就会不断生成新区块，而新区块生成是卡顿的常见来源。
3. **保持出生点整洁**：出生点附近通常是加载最频繁的区域，建筑、实体、红石越少越好。
4. **定期归档旧区域**：不再使用的世界或区域及时清理，操作前**先备份**。

关于**预生成**，要说实话：**官方 BDS 没有提供预生成工具**，可选手段比 Java 版少得多。

| 手段 | 官方 BDS 是否支持 | 说明 |
| --- | --- | --- |
| 内置预生成命令 | 不支持 | 官方服务端没有这类命令 |
| 管理员提前跑图 | 支持（就是普通游戏行为） | 最稳、零依赖，缺点是耗时 |
| 常加载区域 | 支持 | 解决的是"没人在场也要运算"，**不是**预生成，而且持续消耗性能 |
| Java 版工具（如 Chunky） | 不支持 BDS | 这类工具面向的是 Java 版服务端与模组平台 |
| 第三方预生成工具 | 不在官方能力范围内 | 用之前确认它支持你的 BDS 版本，并**先备份世界** |
:::warn 不要相信"基岩版一键预生成"
网上能看到的基岩版"预生成插件或工具"，大多属于第三方核心或社区工具，**不属于官方 BDS 的能力范围**。要用就以它自己的官方文档为准，不要按本文或别的版本的说明去猜。
:::

基岩版的预生成手段有限，能靠的主要是**提前跑图**和**控制世界规模**。

## 5. 内存行为

基岩版的内存行为和 Java 版完全不同：

- **没有内存参数**。BDS 没有 `-Xmx` 这类开关，初始与最大内存由程序自己向操作系统申请，你无法在启动参数里指定。
- **占用会随时间缓慢上升**。长时间运行后明显高于刚启动时，这是普遍观察到的现象。
- **不要强行清理内存**。用"内存清理""强制释放"类工具去压占用，会导致**玩家下载资源包或附加包时进度条卡住**，还可能让服务端变得不稳定。**重启才是解法**，这一点与 [BDS 服务端](/tutorials/bedrock/bds) 里的说明一致。

正确做法是**安排定时重启**：

| 做法 | 说明 |
| --- | --- |
| 定时重启 | 在低峰期重启一次，把长期累积的内存交还给系统 |
| 重启周期 | **没有官方推荐值**，是判断题：看你的玩家数、世界大小、附加包数量与内存增长曲线。每天一次、每几天一次都有人用 |
| 优雅停止 | 用控制台 `stop` 正常关服再启动，避免存档与统计文件损坏 |
| 提前公告 | **重启前在游戏内和群里通知玩家**，并留出缓冲时间，避免玩家正在跑图或对战时被突然踢下线 |
:::tip 重启间隔怎么定
不要照抄别人的"每天重启三次"。先记录几天：启动后多久内存涨到机器吃不消、玩家什么时候最多。**玩家多、附加包多，间隔就短一些；小服、附加包少，间隔可以长一些。**
:::

## 6. 硬件与托管选择

基岩版硬件的第一原则还是**单核性能优先**：

| 优先级 | 项目 | 为什么 |
| --- | --- | --- |
| 1 | 单核主频与单核性能 | 世界模拟在单线程上，弱单核直接决定卡不卡 |
| 2 | SSD 或 NVMe | 区块读写、存档保存、备份都是磁盘 I/O，机械盘与网络存储会明显拖慢 |
| 3 | 内存容量 | 要留足余量；玩家、世界、附加包越多，需要越多 |
| 4 | 核数 | 有用，但排在上面三项之后 |

为什么"便宜的 VPS 会莫名其妙地卡"：

- 便宜套餐常见的是**低主频、多核、超售共享**的 CPU。BDS 吃单核，而共享 CPU 会被邻居挤占，于是出现周期性卡顿与延迟抖动；
- "突发性能"型实例平时看起来空闲，一旦 CPU 额度耗尽就整体变慢；
- 机械盘或网络存储让区块读写变慢，玩家跑图时最容易体现出来；
- 内存不足时系统开始换页，表现就是"整服一顿一顿"。
:::warn 容器与虚拟化会额外抢 CPU
如果你把 BDS 放进容器或虚拟机里跑，**CPU 限额（limit / quota）可能把 BDS 饿死**：单核跑满时被限流，表现就是周期性"卡一下"。请给足 CPU 份额，并避免和别的重负载服务挤在同一台机器上。用 Docker 部署的细节见 [用 Docker 部署基岩版服务端](/tutorials/bedrock/docker)。
:::

### 6.1 托管选择速查

| 你的情况 | 建议 |
| --- | --- |
| 玩家不多、预算有限 | 一台单核强的机器，通常比多核超售的 VPS 更稳 |
| 需要长期在线、有固定玩家 | 选明确标注 CPU 主频、不超售的套餐，先小规模试跑再扩容 |
| 用容器部署 | 给足 CPU 份额，避免与重负载服务同机，注意端口与数据卷，见 [用 Docker 部署基岩版服务端](/tutorials/bedrock/docker) |
| 想要插件生态 | 那就不是 BDS 的路线了，先看第 7 节 |

## 7. 第三方核心的性能差异

如果你要的是插件与多核，那走的就不是 BDS 这条路：

| 核心 | 语言 | 性能特点 |
| --- | --- | --- |
| Nukkit 系（含 PowerNukkitX） | Java | 主打多核与优化，有插件系统与大量可调项 |
| PocketMine-MP | PHP | 插件生态最大，但高负载下瓶颈明显，解释型语言本身有开销 |

它们的性能模型、配置项和可用工具都与 BDS 不同，**优化经验不能互相套用**。例如 `spark` 支持 Nukkit，但**不支持 BDS**；把 PMMP 或 Nukkit 的调优文章照搬到 BDS 上，通常只会白忙。
:::warn 先确认你要的是哪条路
选 BDS 就是"官方、稳定、可调项少"；选第三方核心就是"插件多、可调项多、但不是官方实现"。想了解它们的取舍与上手，见 [第三方核心（Nukkit / PNX / PMMP）](/tutorials/bedrock/third-party) 与 [基岩版第三方核心上手](/tutorials/bedrock/third-party-setup)。
:::

## 8. 怎么测量

先说清楚：**基岩版没有 `spark`**。`spark` 支持的是 Java 版的一系列平台与部分社区平台，**Bedrock Dedicated Server 不在其中**。所以在 BDS 上不要指望火焰图，也不要照搬 Java 版"看 TPS 与 MSPT"的那套流程。

能用的手段：

| 手段 | 怎么用 |
| --- | --- |
| 宿主级监控 | 看 CPU（尤其**单核占用**）、内存、磁盘 I/O、网络带宽。做法见 [监控与告警](/tutorials/ops/monitoring) |
| BDS 控制台输出 | 看启动与关闭信息、报错、附加包与脚本相关的告警 |
| 玩家反馈 | "什么时候卡、几个人在线、在哪片区域卡"往往比任何指标都直接 |
| 改动前后对比 | 一次只改一项，记录改前与改后的 CPU 占用和玩家感受 |
:::note 一次只改一项
没有火焰图，唯一可靠的办法就是**控制变量**：改一项，观察一段可比的时间，记录，再改下一项。一次改五项，你永远不知道是哪一项起了作用，或者起了反作用。
:::

测量纪律，建议照这个来：

1. **一次只改一个变量**，其他保持不变；
2. **在可比的时间段测量**：同一时段、相近在线人数、相近玩法（例如都在跑图，或者都在挂机）；
3. **记录到日志里**：改了什么、什么时候改的、改前改后的指标与玩家感受；
4. **观察足够长**：区块生成、内存增长这类现象需要时间才能看出来，改完立刻下结论容易误判。

宿主级记录的一个简单例子（Linux，仅示意）：

```bash
# 每 5 秒采样一次整体与各核负载，便于发现"总占用不高但单核跑满"
top -b -d 5 -n 60 > cpu-sample.log
```

Windows 上可以用任务管理器或性能监视器看同样的东西，**重点是单核曲线，而不是总占用**。

## 9. 调优顺序

按这个顺序做，性价比最高；顺序反了容易白花钱：

1. **世界设计**：先做减法，少加载、少常加载机器、停掉不需要的农场、克制红石时钟、控制实体与掉落物。收益最大且不花钱。
2. **视距与模拟距离**：调 `view-distance`、`tick-distance`、`player-idle-timeout` 以及压缩相关键。几乎免费、立竿见影。
3. **硬件**：单核性能优先，其次内存、SSD、核数。花钱但有效。
4. **重启计划**：定一个适合你的重启周期并提前公告。治标，但能解决长期内存累积。
5. **换核心**：只有前四项都做完、你确实需要插件或多核时，才考虑 Nukkit 系或 PMMP。

### 9.1 收尾检查表

| # | 检查项 | 完成标准 |
| --- | --- | --- |
| 1 | 确认版本里有哪些键 | 打开本地 `server.properties`，逐项核对过键名与默认值 |
| 2 | 世界设计 | 不用的农场与机器已停，常加载区域已清理，高频红石已收敛 |
| 3 | 视距与模拟距离 | `view-distance` 与 `tick-distance` 已按玩家设备与带宽调整，且没有破坏机器 |
| 4 | 挂机与压缩 | `player-idle-timeout` 已设，压缩相关键已按瓶颈方向调过 |
| 5 | 硬件 | 单核性能与磁盘 I/O 是瓶颈时优先解决；容器有足够 CPU 份额 |
| 6 | 重启计划 | 有周期、有公告、用 `stop` 优雅关服 |
| 7 | 测量记录 | 每次改动都有改前与改后的记录，且一次只改一项 |
| 8 | 反作弊 | 没有为了省性能而放宽移动校验，或者已明确接受风险 |

基岩版优化说到底就三句话：**单核主频决定上限，世界设计决定下限，定时重启决定长期稳定。**
