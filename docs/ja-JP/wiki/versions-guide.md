当サイトの**バージョン履歴**（[/wiki/versions](/wiki/versions)）は、Java 版と統合版の正式リリースを新しい順に並べたものです。「どのバージョンを立てればいいのか、いつアップグレードするのか、なぜプレイヤーが入れないのか」といった疑問を最初に調べる入り口になります。

ただし履歴そのものが示すのは**バージョン番号・日付・一行の説明**だけです。このページでは、それぞれの項目が何を意味するのか、どの直感が間違っているのか、そしてそれを具体的なアップグレードの判断にどう結びつけるのかを説明します。

> バージョン番号の命名規則、プロトコルバージョン、リリースのペースは公式が決めており、いつ変更されてもおかしくありません。本記事は**当サイトの履歴の読み方**だけを説明します。特定のバージョンが何に対応し、何を要求するかは、公式のリリースノートを確認してください。
:::note このページで解決する 4 つの疑問
- 履歴の 1 行について、各項目は何を意味するのか；
- Java 版と統合版のバージョン番号は、それぞれどう分解するのか；
- LTS / CROSS-PLAY タグが示すもの、示さないもの；
- 「リリース日」が「自分のクライアントは入れるか」に答えられない理由。
:::

## 1. 履歴はどこにあり、各行は何か

| ページ | 内容 |
| --- | --- |
| [/wiki/versions](/wiki/versions) | 既定では Java 版の履歴を開く |
| [/wiki/versions/java](/wiki/versions/java) | Java 版の履歴 |
| [/wiki/versions/bedrock](/wiki/versions/bedrock) | 統合版の履歴 |

2 つのエディションの履歴は**別々**で、ページ上では 2 つのタブで切り替えます。各行の構造は固定です：

| 項目 | 説明 |
| --- | --- |
| バージョン番号 | そのバージョンがゲーム内に表示する正式なバージョン番号 |
| タグ | 項目に印がある場合だけ表示される（LTS、CROSS-PLAY など）。毎行あるわけではない |
| 日付 | そのバージョンのリリース日 |
| 一行の説明 | そのバージョンが何なのか（メジャーアップデートでは更新名を明記し、マイナー版は通常バグ修正と安定性の改善） |

読み方についていくつかの事実：

- **新しいものが上**：履歴は日付の新しい順で、1 行目が最新、下に行くほど古くなります。
- **正式版のみ収録**：スナップショット（Snapshot）、プレビュー版（Preview）、ベータ版は履歴に含まれないため、「履歴にない」＝「公式が公開していない」ではありません。
- **2 つのエディションで件数が大きく違う**：Java 版は 1.0 から最新の 26.x まで、統合版はリビジョンのリリース頻度がずっと高く、件数は Java 版の約 3 倍あるため、統合版の履歴はずっと長くなります。
- **統合版の項目は 1 つ多い**：統合版のサーバー（BDS）には独自のビルド番号があり、履歴データにもそれを記録して、「クライアントのバージョン」と「サーバーのビルド」を突き合わせられるようにしています。

## 2. Java 版のバージョン番号の読み方

Java 版は長らく `1.x.y` の形式を使ってきました：

| 位置 | 意味 | 例 |
| --- | --- | --- |
| `1.x` | メジャーバージョン。内容とゲームプレイの変化を決める | 1.21 |
| `.y` | そのメジャーバージョン配下のリビジョン | 1.21.9、1.21.10、1.21.11 |

**ここに最も多い誤読があります**：`1.21.10` は `1.21.9` より**新しい**です。`.10` は数値の 10 であって「1 点 10」ではありません。**数値で比較し、文字列で比較しないでください**：文字列の並べ替えでは `1.21.10` が `1.21.9` の前に来て古く見えますが、実際は逆です。

### 2.1 新しい命名：26.x

履歴を見ると、Java 版では 2026 年以降に `26.x` 形式のバージョン番号が現れています（当サイトの履歴では 26.1 が 2026-03-24、26.2 が 2026-06-16、26.3 が 2026-09-15）。

これは**公式がバージョンの命名方式を変更した**もので、「1.21 の 26 番目のリビジョン」ではなく、`1.x.y` の直感で旧バージョン番号との大小関係を推測することもできません。見慣れない形式のバージョン番号に出会ったら、**日付を見て、数字で推測しない**のが正解です：

- どちらが新しいか知りたい：日付を比べる。
- あるプラグインを入れられるか知りたい：プラグインの対応リストを見る。バージョン番号の形式では判断しない。
- プロトコルが互換か知りたい：プロトコルバージョンを見る。バージョン番号では判断しない。

### 2.2 リビジョンとメジャーバージョンの違い

| 種類 | 変化の幅 | アップグレードのリスク |
| --- | --- | --- |
| リビジョン（例：1.21.9 → 1.21.11） | 通常はバグ修正と安定性のみ | 低い。ただしプラグインが影響を受ける可能性があるため、バックアップは必要 |
| メジャーバージョン（例：1.21 → 26.1） | 内容、仕組み、データ形式が変わりうる | 高い。ワールド形式はほぼ一方通行で、ダウングレードの代償は非常に大きい |

## 3. 統合版のバージョン番号の読み方

統合版の `1.x.y` は Java 版と**見た目は似ているが中身が違います**。第 3 段の意味は「何番目の小さなリビジョン」ではなく、統合版独自のペースで増えていきます。

| 形式 | 意味 | 例 |
| --- | --- | --- |
| `1.x.y` | 統合版の正式版 | 1.20.10、1.21.100 |
| `1.x.y.z`（4 段） | サーバー用の BDS ビルド番号 | BDS 1.20.62.03 |

3 つの要点：

1. **`1.20.1` と `1.20.10` は別物**で、「1 桁変わっただけ」でもありません。統合版の第 3 段は一度に 10 飛ぶことが多く（1.20.10、1.20.20 というペースは履歴でもよく見られます）、`1.21.100` を見ても打ち間違いだと思わないでください。
2. **BDS のビルド番号は 4 段**：例えば `BDS 1.20.62.03`。これはサーバー自身のビルド番号で、クライアントが表示するバージョン番号とは**同じ文字列ではありません**が、同じリリースの中で対応しています。
3. **ビルド番号が不明な場合はプレースホルダを残す**：当サイトのデータでは、正確なビルド番号が確認できない統合版の項目を `BDS <バージョン>.w` のような形式で記載しています（`w` はビルド番号のプレースホルダ）。「このリリースのビルド番号は確認できていない」という意味で、このバージョンにサーバーがないという意味ではありません。

### 3.1 統合版の 26.x

統合版も同じく `26.x` の命名に入っています（当サイトの履歴では 26.0 が 2026-02-10）。Java 版と同様に、**命名体系をまたいで数字を比較せず**、日付を見てください。

### 3.2 クライアントとサーバーが同日リリース

統合版の説明には「クライアントと同日リリース」といった記述がよくあり、これは統合版の実際のペースを反映しています：**クライアントの更新とサーバーのビルドは通常同時に進みます**。その結果、2 つのことが起きます：

- サーバーの対応が遅れると、プレイヤー（とくに自動更新されるプレイヤー）が入れなくなる；
- iOS のプレイヤーは**ストアにある最新版しかインストールできず**、特定のバージョンへ戻せないため、「サーバーを旧バージョンに固定する」道の代償は Java 版よりずっと大きくなります。

## 4. LTS と CROSS-PLAY タグが示すもの

履歴上のタグは**当サイトが独自に付けた目印**であり、公式の分類でも公式の約束でもありません。項目に印がある場合だけ表示されます。

| タグ | 当サイトでの意味 | **意味しない**こと |
| --- | --- | --- |
| LTS | 長く留まり、安定した基準として使う価値があると当サイトが判断したバージョン | 公式が長期にわたり更新を提供する；「最も安全」である |
| CROSS-PLAY | クロスプラットフォームのマルチプレイに関係するバージョンへの注意 | 導入すれば Java と統合版が相互接続できる；すべてのプラットフォームから入れることが保証される |

必ず区別しておきたい点：

- **LTS は Minecraft の公式用語ではありません**。公式に「長期サポート版」という区分はなく、どのバージョンも次の更新で修正を受けられなくなる可能性があります。
- **CROSS-PLAY もクロスプレイと同義ではありません**。統合版の各プラットフォーム間の相互接続は統合版自体の機能です。**Java 版と統合版の相互接続には Geyser のようなツールが必須**で、サーバーがどのバージョンかとは関係ありません（[Java 版と統合版の違い](/wiki/editions)参照）。
- **タグは変わります**。当サイトはいつでも項目に印を付けたり外したりできます。したがって「あるバージョンに LTS が付いている」こと自体が当サイトの判断であり、確定した事実ではありません。ページに現在表示されている内容が基準です。

## 5. リリース日は「入れるかどうか」ではない

これが履歴の最も誤用されやすい点です。日付が答えるのは「このバージョンがいつリリースされたか」だけで、**「あなたのクライアントがこのサーバーに入れるか」には全く答えません**。

入れるかどうかを実際に決めるのは**プロトコルバージョン**です。クライアントとサーバーはハンドシェイクの段階でプロトコル番号をやり取りし、一致しなければ入れません。バージョン番号、リリース日、更新内容とは関係ありません。

| 現象 | 本当の原因 | どこを見るか |
| --- | --- | --- |
| プレイヤーに「バージョンが互換ではありません」と表示される（Java） | クライアントのプロトコルとサーバーが不一致 | [クロスバージョン互換](/tutorials/java/via) |
| プレイヤーに最新版への更新を求められる（統合版） | クライアントのプロトコルとサーバーのビルドが不一致 | [プロトコルバージョンとバージョン選択](/tutorials/bedrock/protocol) |
| 履歴では昨日新版が出たのに、プレイヤーは入れない | サーバーをまだ更新していない、またはプレイヤーが自動更新でさらに新しい版になっている | まず双方のバージョンを確認し、追従するかを決める |
| 履歴ではかなり古いのに、プレイヤーは入れる | そのクライアントのバージョンがまだサーバーの許容範囲にある | 「入れる」からプロトコルの互換性を逆算しない |

### 5.1 具体的な例

サーバーが 1.21.11 で稼働し、プレイヤーが申告したクライアントは 1.21.9：

| 疑問 | 答え |
| --- | --- |
| 履歴ではどう見えるか | 両方の行があり、1.21.11 が 1.21.9 より新しい（数値では 10、11 が 9 より大きい） |
| なぜプレイヤーは入れないのか | 「バージョンが古い」だけでは説明できない。1.21.11 のサーバーが 1.21.9 のプロトコルを受け入れるかを見る |
| どうすればいいか | まずサーバーログのハンドシェイクのエラーを見る。Via 系を入れればより古いクライアントも入れる。詳細は[クロスバージョン互換](/tutorials/java/via) |
| 履歴で答えられるか | いいえ。どちらが先にリリースされたかしかわからない |

**履歴が答えるのは「どちらが新しいか」、プロトコルが答えるのは「接続できるか」**。この 2 つは分けて調べてください。

## 6. プロトコルバージョンがマーケティング上のバージョン番号より重要な理由

「マーケティング上のバージョン番号」とは、ページに表示される `1.21.x`、`26.x` のような番号のことです。**プロトコルバージョン**は、双方が通信する際に実際に使う番号です。両者は別物です：

- 同じマーケティング上のバージョン番号でも、プロトコルは何度も変わっていることがある（統合版では特に顕著）；
- 公式はリビジョン間でプロトコルを変更することもあれば、**変更しない**こともある；
- プラグイン、ローダー、クロスバージョンツールの互換性の判断は、多くの場合プロトコルと内部バージョンで行われ、ページ上の数字ではありません。

**統合版のほうが厳格です**：クライアントのプロトコルがサーバーのビルドと一致しなければ、プロトコル番号が 1 つ違うだけで接続できません。**Java 版には翻訳レイヤーがあります**：Via 系のプラグインはサーバー側でプロトコルを翻訳し、より古い、またはより新しいクライアントを入れられますが、離れるほど一致するものが減り、体験の劣化がはっきり現れます。

結論：**「入れるかどうか」を判断するときは、必ずプロトコルを先に見て、そのあとバージョン番号を見てください。バージョン番号は人に見せる名前でしかありません。** 2 つの路線の詳細は [プロトコルバージョンとバージョン選択](/tutorials/bedrock/protocol) と [クロスバージョン互換](/tutorials/java/via) を参照してください。

### 6.1 2 つのエディションのプロトコルへの向き合い方

| 観点 | Java 版 | 統合版 |
| --- | --- | --- |
| プロトコルが一致しないとき | ハンドシェイクに失敗し、バージョン非互換を表示 | ハンドシェイクに失敗し、最新版への更新を表示 |
| 翻訳レイヤーの有無 | あり：Via 系がサーバー側でプロトコルを翻訳 | ほぼなし：コミュニティのクロスバージョンプラグインは極めて少ない |
| クライアントの自動更新 | 公式ランチャー内のみで、プレイヤーはバージョンを固定できる | アプリストアは既定で自動更新され、プレイヤーは「受動的に更新」させられがち |
| 旧バージョンに固定する代償 | 比較的制御できる | 非常に高い：iOS のプレイヤーは最新版しか入れられない |
| そのため既定の方針は | プラグインのエコシステムに応じて更新時期を決めてよい | **既定で最新版に追従** |

## 7. 履歴を使ってアップグレード時期を決めるには

履歴が与えるのは**日付と順序**です。アップグレードの判断には、それに加えて「あなたのサーバーが今何で動いているか」が必要です。推奨する順番：

1. **対応範囲を先に調べ、そのあと新バージョンを調べる**。コア、プラグイン、MOD ローダーはそれぞれどこまで対応しているか？ その共通部分を書き出せば、それが上げられる上限です。ローダーとコアのバージョン制約は[サーバーコア比較](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7)を参照。
2. **目標バージョンの後にリビジョンがいくつ出ているかを見る**。出たばかりのメジャーバージョンはまだ調整中であることが多く、リビジョンが 1〜2 個出てから動かすとリスクが明らかに下がります。
3. **自分のプラグインのエコシステムがどこまで追いついているかを見る**。コアが新版に対応していても、プラグインが対応しているとは限りません。
4. **バックアップを取り、そのバックアップを検証する**。ワールド形式のアップグレードはほぼ一方通行で、ワールドを変えずにコアだけ変えるというロールバックは成立しません。
5. **独立したインスタンスで試す**。セーブデータのコピーで一度動かし、本番インスタンスで実験しないこと。
6. **メンテナンス時間を選び、事前に告知する**。

| 状況 | 推奨 |
| --- | --- |
| バグ修正だけのリビジョンで、コアもプラグインも対応済み | 追従してよい。ただしバックアップは取る |
| 出たばかりのメジャーバージョン | 1 つ目か 2 つ目のリビジョンを待つ |
| プラグインの中に旧版しか対応していないものがある | 旧版に留まるか、代替プラグインを先に探す |
| 統合版 | 既定で最新版に追従。旧版に固定するのは iOS のプレイヤーを諦めるのと同じ |
| 判断できない | 動かさない。現状維持のコストは、通常、失敗した 1 回のアップグレードより低い |

アップグレードの完全な手順、ダウングレードのリスク、ロールバックの方法は[サーバー・プラグイン・MCDR の更新と保守](/tutorials/ops/updates)を参照してください。

## 8. 「入れない」ときの切り分け順序

| 順序 | 確認項目 | 確認方法 |
| --- | --- | --- |
| 1 | クライアントのバージョン | プレイヤーに正確なバージョン番号を報告してもらう（次の節を参照） |
| 2 | サーバーのバージョンとプロトコル | サーバーログ、コアのバージョン出力 |
| 3 | ポートとプロトコル | Java 版は TCP 25565、統合版は UDP 19132（IPv6 は 19133） |
| 4 | ホワイトリストと BAN | `whitelist list`、`banlist players`（統合版は `allowlist.json`） |
| 5 | 正規アカウント認証とログイン方式 | `online-mode` などの設定が「入れるかどうか」を直接変える |
| 6 | クロスバージョンプラグイン | Via 系を入れているのにバージョン非対応と出る場合は、まずプラグイン自体を更新 |

最初の 2 ステップでバージョン番号が必要になるので、**まずバージョンを聞き、そのあと他の話をする**だけで往復の大半を省けます。

## 9. まずクライアントのバージョンを確認する
:::tip プレイヤーが「入れない」と言ったら、まずバージョン番号を聞く
プレイヤーに**正確なクライアントのバージョン番号**を報告してもらい（スクリーンショットが一番簡単です）、そのうえで履歴とプロトコルを照らし合わせます。この一手間がないと、以降の切り分けはすべて推測になります。

- **Java 版**：メインメニューの左下にバージョン番号が表示されます。ランチャーでもそのインストールのバージョンを確認でき、ゲーム内で `F3` を押すとデバッグ画面の上部にバージョンが表示されます。
- **統合版**：設定の「情報」のようなページでバージョン番号を確認できます（プラットフォームごとに場所が異なり、モバイルと家庭用ゲーム機では特に違います）。

バージョン番号がわかったら、プレイヤーのバージョンとサーバーのバージョンを履歴上で日付と順序に照らせば、「サーバーが古い」のか「クライアントが新しすぎる」のかを判断できます。
:::

## 10. 履歴で誤読しやすい点

| 誤読 | 実際 |
| --- | --- |
| バージョン番号を文字列で比較する | `1.21.10` は `1.21.9` より新しい。命名体系をまたぐ場合（1.x と 26.x）は数字では比較できず、日付でしか比べられない |
| 履歴にスナップショットが収録されていると思う | 正式版のみ。スナップショットとプレビュー版は含まれない |
| 「リリース日が近い」＝「必ず上げる」と思う | リリースのペースと自分のプラグインのエコシステムは別物 |
| LTS が付いていれば永遠に安全だと思う | LTS は当サイトの目印であり、公式の約束ではない |
| 統合版の `1.20.1` と `1.20.10` は 1 つ違いだと思う | 統合版の第 3 段は独自のペースで飛ぶため、両者は別のリリース |
| 同じ日に 1 つしかバージョンがないと思う | 履歴で同じ日に複数のバージョンが出るのは正常 |
| 「最新が最適」だと思う | 最新版は新しいプラグインに優しく、古いプラグインには厳しい。実際に何を入れているか次第 |

### 10.1 履歴が答えない疑問

| あなたの疑問 | 履歴で答えられるか | どこを見るべきか |
| --- | --- | --- |
| このバージョンはいつリリースされたか | はい | 履歴そのもの |
| 自分のクライアントは入れるか | いいえ | プロトコルバージョン：[プロトコルバージョンとバージョン選択](/tutorials/bedrock/protocol) |
| 自分のプラグインは対応しているか | いいえ | プラグインの公開ページの対応リスト |
| 自分のコアは追いついているか | いいえ | コアの公式ダウンロードページと公式リポジトリ |
| このバージョンで何が変わったか | 一部 | 履歴の一行の説明。詳細は公式の更新ログ |
| サーバーはどこからダウンロードするか | いいえ | 当サイトのダウンロードページと公式のダウンロードページ |

  → 选最新正式版，然后确认核心与插件都支持它

  → 看日期，不看数字大小

## 12. 履歴をバージョン台帳として使う

履歴は「最新版を見る」以外にも、3 つの実用的な使い方があります。

### 12.1 ある過去のバージョンがどのメジャーバージョンに属するかを調べる

「1.20.4 はどのメジャーバージョンに属し、その後にどのリビジョンがあるか」を知りたいときは、履歴でその行を特定し、**上に向かって読んで**ください。同じメジャーバージョンのリビジョンは通常連続して並びます。「動作が確認できているバージョンへ戻したい」とき、この操作は資料を検索するよりずっと速いです。

### 12.2 古いメジャーバージョンがまだ更新されるかを判断する

履歴の順序から直感が得られます。あるメジャーバージョンの後に新しいメジャーバージョンが現れていれば、古いほうは通常、必要なときだけ修正を受けます。**これは観察であり、公式の約束ではありません**。更新が続くかどうかは公式のリリースノートを確認してください。

### 12.3 統合版でクライアントとサーバーを突き合わせる

統合版の項目はクライアントのバージョンと BDS のビルド番号を同時に記録しているため、プレイヤーがクライアントのバージョンを報告したら、履歴上で対応する行をすぐに見つけ、それに対応するサーバーのビルドを確認できます。「クライアントは更新されたがサーバーが追いついていない」を切り分ける最短の一手です。
