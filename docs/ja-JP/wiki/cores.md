サーバー構築の第一歩は「何を動かすか」を決めることです。ここで間違えやすいのは、**コア・プラグイン・MOD・ローダー**という 4 つの言葉がよく混同されるからです。このページではそれらを並べて対照します：Java 版のコアの系統と MOD ローダー、統合版の公式コアとサードパーティコア、BDS のコミュニティ製ローダー、最後に「自分はどれを選ぶべきか」の判断手順です。

> 各プロジェクトがどのゲームバージョンに対応し、どこまで対応しているかは、**時間とともに変わります**。コアは保守を終了し、ローダーは新バージョンに追いつき、プラグインは作者を失います。本記事は「系統と位置づけ」の対照のみを示します。**具体的なバージョン範囲と対応状況は、各プロジェクトの公式リポジトリと公式ドキュメントを基準にしてください**。

## 1. まず 4 つの言葉を分ける

| 言葉 | 何か | 典型例 | プレイヤー側に導入が要るか |
| --- | --- | --- | --- |
| コア（サーバー） | ワールドとロジックを動かすプログラム本体 | `paper-x.jar`、`bedrock_server.exe` | 不要 |
| プラグイン | コアが提供する API を呼んで機能を拡張するもの | `plugins/` に入れる jar や phar | 不要。バニラのクライアントでよい |
| MOD | ゲーム本体のコードを直接変更するもの | `mods/` に入れる jar | **内容を追加する MOD の多くは、クライアントにも同じ構成が必要** |
| ローダー | MOD を読み込んで動作させるフレームワーク | Fabric、NeoForge、Forge、Quilt | クライアントとサーバーの両方に必要 |

一言で分けると：**プラグインはサーバーの外側に機能を足し、MOD はゲームの内側で内容を変えます。** この違いが、プレイヤー側に導入が必要かどうかを決め、以後のトラブルシューティングのやり方も決めます。

## 2. Java 版のサーバーコア

Java 版のコアははっきりしたフォークの系統です：Bukkit → Spigot → Paper → Purpur / Folia / Leaves / Leaf。**プラグインの互換性はおおむね上流から受け継ぎます**：Paper 対応のプラグインは通常 Purpur でも動きますが、逆は保証されません。

| コア | 特徴 | プラグイン互換 | 向いている人 |
| --- | --- | --- | --- |
| Vanilla（バニラ） | 公式サーバー。データパックのみ対応で、サードパーティ製のものを一切入れない | プラグイン非対応 | バニラの挙動を検証したい、純粋なバニラのゲームプレイを動かしたい |
| Spigot | Bukkit の後継で、Paper の上流でもある。更新ペースはやや遅い | エコシステム大。多くの古いプラグインがこれを基準にしている | 古いプラグインとの互換性が必要で、Paper を使いたくない場合 |
| Paper | Spigot のフォーク。非同期チャンク、エンティティ、ネットワークの最適化が最も成熟 | **エコシステム最大**。ほとんどのプラグインの第一候補 | **初めてのサーバー構築の第一候補**：安定し、情報が多く、性能も十分 |
| Purpur | Paper のフォーク。大量のゲームプレイスイッチを提供 | Paper のプラグインと互換 | バニラの仕組みを細かく調整したいが、コードは書きたくない |
| Folia | Paper のフォーク。リージョン単位のマルチスレッド | **互換性が低い**：多くのプラグインが未対応で、専用の対応が必要 | コアが多くクロックが低いマシン。**レッドストーン技術には不向き** |
| Leaves | Paper のフォーク。性能最適化で壊れたバニラ特性を修復することを目的とする | Paper のプラグインと互換（各プロジェクトの説明を基準に） | **レッドストーン技術（テクニカル）+ プラグインも使いたい** |
| Leaf | Paper のフォーク。性能、バニラの仕組み、安定性のバランスを狙う | Paper のプラグインと互換（各プロジェクトの説明を基準に） | 性能とバニラの手触りを両立したいが、Leaves の全機能は不要 |

3 つの注意：

1. **Leaves と Leaf は別プロジェクト**で、名前が 1 文字しか違いません。資料を探すとき、コアをダウンロードするときは綴りをよく確認し、取り違えないでください。
2. **Folia は「より速い Paper」ではありません**。ワールドをリージョンに分割して並列にスケジュールするため、リージョンをまたぐやり取りの挙動が Paper と異なります。対応していないプラグインはそのままエラーになるか、挙動がおかしくなります。選ぶ前に、使うプラグインが Folia 対応を明言しているか確認してください。
3. **バニラはデータパック（Data Pack）のみ対応**です。プラグインを使いたければコアを替え、MOD を使いたければローダーを替える必要があります。

### 2.1 フォークの継承関係

この系統を覚えておけば、プラグインの互換性の問題は半分自分で判断できます：

```text
Bukkit（最古のサーバー API）
  +- Spigot（Bukkit の後継）
       +- Paper（主流のフォーク、プラグインエコシステムが最大）
            +- Purpur（ゲームプレイのスイッチが最も多い）
            +- Folia（リージョン化マルチスレッド、プラグイン互換性は低い）
            +- Leaves（バニラの特性を再現、技術志向）
            +- Leaf（性能 / バニラ挙動 / 安定性のバランス）
```

ルールは**下位互換はあり、上位互換は保証されない**です。Paper 向けに書かれたプラグインは通常 Purpur でも動きます。Folia 向けに書かれたプラグインが Paper 向けに調整されるとは限りません。Spigot しか対応していない古いプラグインは Paper でもおおむね動きますが、「非推奨 API を使用しています」という警告が出ることがあります。

項目ごとの完全な対照と「ハードウェアでどう選ぶか」は[サーバーコア比較](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7)を、遊び方とハードウェアからの選型の完全な解説は[サーバーの選択](/tutorials/java/core)を参照してください。

## 3. Java 版の MOD ローダー

MOD サーバーとプラグインサーバーは別の世界です。ローダーがどの MOD を入れられるかを決め、**同じ MOD は通常 1 つのローダーしか対応しません**。

| ローダー | 位置づけ | エコシステム | バージョンのペース |
| --- | --- | --- | --- |
| Fabric | 軽量で起動が速い。ローダー本体と API が分離しており、多くの機能は Fabric API という MOD で補う | 活発。最適化系と軽量な内容追加系の MOD が多い | 新バージョンへの追従が最も速い |
| NeoForge | Forge の血筋を現代のバージョンへ引き継いだもの。API の機能がより完全 | 現代バージョンの大型コンテンツやテック系 MOD パックの主力 | メジャーバージョンに合わせて進む |
| Forge | 老舗ローダー。過去の MOD パックと旧バージョンで広く使われている | 古い MOD パックが最多。新バージョンのエコシステムはかなり NeoForge へ移行 | 複数バージョン向けにビルドを出し続けているが、新バージョンの追従は前者 2 つに劣る |
| Quilt | Fabric からフォークし、より開かれたガバナンスと新しい API を目指す | Fabric より明らかに小さい。Fabric の MOD のかなりの部分を読み込めるが、**すべてではない** | 活発さは Fabric より低い。選ぶ前に目的の MOD があるか確認 |

判断の順序は**先にゲームプレイを決め、次にローダーを決める**です：

```text
どうしても外せない MOD を書き出す
  -> 各 MOD が対応するローダーとゲームバージョンを調べる
  -> 積集合が最大になる組み合わせを選ぶ
  -> そのあとでサーバーを導入
```

逆（先にローダーを入れてから MOD を探す）はほぼ確実に作り直しになります。導入手順、クライアント側の合わせ方、切り分けは[MOD サーバーの完全ガイド（Fabric / NeoForge）](/tutorials/java/modded)を参照してください。

### 3.1 ランタイムのバージョンを忘れずに

コアとローダーはどちらも適合する Java ランタイムを要求します。Java の入れ間違いは「ランチャーが開かない、サーバーが起動しない」の最もよくある原因です：

| Minecraft のバージョン | 通常必要な Java |
| --- | --- |
| 1.16.5 以前 | 8 |
| 1.17.2 | 16 |
| 1.18.2 – 1.20.4 | 17 |
| 1.20.5 以降 | 21 |

この表は**執筆時点でよくある対応関係**です。新しいバージョンはいつでも要求を引き上げる可能性があるため、コアとローダーの公式ドキュメントを基準にしてください。

### 3.2 クライアントにもローダーが必要

MOD サーバーでよくある誤解は「サーバー側だけ入れればいい」です。実際には：

| MOD の種類 | どこに入れるか | 入れ間違えた結果 |
| --- | --- | --- |
| クライアント専用（描画、ミニマップ、UI 拡張） | クライアントのみ | サーバーに入れると、通常はそのままエラーになるかローダーに拒否される |
| サーバー専用（ロジックと性能系） | サーバーのみ | クライアントに入れても意味がない。サーバー側にないと機能自体が存在しない |
| 両側必須（新しいブロック、アイテム、ディメンション） | クライアント + サーバーの両方 | どちらかが欠けると、接続が拒否されるかレジストリ不一致でエラー |

そのため MOD パックを配布するときは、**クライアント用とサーバー用の 2 つのリストを同時に用意し**、どれが任意の MOD かを説明に明記してください。

## 4. プロキシ：コアではないが、選型でよく出てくる

プロキシ自体はワールドを動かさず、プレイヤーを後段のサブサーバーへ転送するだけです。「複数サーバー構成」の部品であり、**単一サーバーには不要**です。

| プロキシ | 位置づけ | 備考 |
| --- | --- | --- |
| Velocity | 現代的なプロキシ。性能がよく活発 | 複数サブサーバーの相互接続の主流 |
| BungeeCord | 老舗プロキシ | エコシステムが古く情報は多い。新規プロジェクトは通常 Velocity を優先 |

プロキシを追加すると、プレイヤーの接続経路は「クライアント → プロキシ → 後段のサブサーバー」になり、プラグインを「プロキシに入れる」のか「後段に入れる」のかを区別する必要があります。クロスバージョンのプラグインをどちら側に入れるかでも代償が変わります。詳しくは[クロスバージョン互換](/tutorials/java/via)とプロキシ関連のチュートリアルを参照してください。

## 5. 統合版：公式コアとサードパーティコア

統合版のコアのエコシステムは Java 版より小さく、主流は 4 つです。

| コア | 言語 | プラグインのエコシステム | 備考 |
| --- | --- | --- | --- |
| BDS（公式） | C++ | **それ自体はプラグイン非対応**で、コミュニティ製ローダーが必要 | 公式サーバーで互換性が最もよい。モブの演算がシングルスレッドに集中するため、快適さは主にシングルコア性能次第 |
| Nukkit | Java | ネイティブのプラグイン機構。エコシステムは小さめ | 軽量で導入が簡単。**本家プロジェクトはすでに低活発**なので、実際には活発なフォークを優先すべき |
| PowerNukkitX | Java | Nukkit エコシステムの多数のプラグインと互換。エコシステムは中くらい | Nukkit の現代的な主力フォーク：新しいプロトコルへの対応、マルチコア最適化、384 ブロックのワールド高、Terra 地形生成器の内蔵 |
| PocketMine-MP | PHP | **最大**（PHP プラグインが最多） | PHP が書ければプラグインを作れる。高負荷では性能のボトルネックがあり、更新は比較的遅れる |

選型の経験則：

- **公式の互換性と安定性が欲しい**：BDS。プラグインが必要になったらコミュニティ製ローダーを足す；
- **高性能と高度なカスタマイズが欲しい**：PowerNukkitX；
- **既成のプラグインが最も多く、PHP に慣れている**：PocketMine-MP；
- **まずは簡単に始めたい**：BDS で一通り動かしてから、サードパーティコアを検討する。

統合版コアの項目別比較と導入の道筋は[統合版のサーバーコアの選択](/tutorials/bedrock/cores)と[サードパーティコア（Nukkit / PNX / PMMP）](/tutorials/bedrock/third-party)を参照してください。

### 5.1 サードパーティコアの実行環境

コアを選ぶ前に、マシンに入っているランタイムを確認しないと、最初の手順で止まります：

| コアの系統 | 必要なもの | 注意 |
| --- | --- | --- |
| BDS | Java / PHP は不要。展開すればすぐ動く | プラットフォームごとのアーカイブと実行ファイル名は公式ダウンロードページを基準に |
| Nukkit 系（PNX を含む） | **Java**。要求バージョンは通常新しめ | 64 ビット OS には 64 ビットの Java を。さもないとメモリ上限で途中クラッシュする |
| PocketMine-MP | **PHP**（公式がまとめたランタイムの利用を推奨） | ディストリビューションのリポジトリにある PHP は古く拡張も不足しがち。まず `php -v` を確認 |

系統を間違える（PMPP に Java、Nukkit に PHP など）と「なんとか動く」ことはなく、起動に失敗するだけです。

## 6. BDS のプラグインローダー

公式 BDS にはプラグイン機構がありません。BDS でプラグインを使うにはコミュニティ製ローダーが必要で、**ローダーはゲームのバージョンと強く結びつきます**：サーバーを更新する前に、ローダーが追従しているか確認してください。

| ローダー | プラグインを書く言語 | エコシステム | 備考 |
| --- | --- | --- | --- |
| LeviLamina | C++（前身は LiteLoaderBDS） | 現在最も成熟し、エコシステムが最良 | 特定のバージョン範囲のみ対応。BDS を更新する前に必ず確認 |
| BDSX | Node.js / TypeScript | 保守期間が長く、低レイヤー寄り（フックとネットワークパケット） | 対応範囲が広く、コードを書く気がある人向け |
| EndStone | C++ / Python。API のスタイルは Bukkit に近い | エコシステムは極小だが方向性は明快 | Bukkit 風の開発体験が欲しい場合に |
| BDSpyrunner | Python | 小さめ | 具体的な形態と対応バージョンはプロジェクトの公式リポジトリを基準に |

コミュニティには**代替サーバー**（BDS のローダーではない）もあります：Go 言語で書かれた gomint と Dragonfly、コミュニティ製サーバーの Allay、統合版のプロキシである WaterDogPE などです。共通するのは**エコシステムもドキュメントも薄い**ことで、問題が起きたときに助けを求めるのが難しいです。明確な理由がない限り、初心者が最初に選ぶことはおすすめしません。

:::warn ローダーはゲームのバージョンと強く結びつく
統合版のサーバービルドはプロトコルと高度に結びついており、コミュニティ製ローダーは通常**非常に狭いバージョン範囲**しか対応しません。「まず BDS を最新に上げ、そのあとローダーを探す」は最もよくある失敗の順序です。正しい順序は、**ローダーがどのビルドまで対応しているかを先に確認し、そのうえでサーバーをどこまで上げるかを決める**ことです。
:::

## 7. 自分はどれを選ぶべきか

```text
バニラクライアントで参加し、管理系／ゲームプレイ系プラグインが必要
  -> Paper（第一候補）
  -> バニラの挙動を調整したい：Purpur
  -> 技術志向 + プラグイン：Leaves か Leaf（名前をよく確認）
  -> コア数が多くクロックが低い：Folia を検討（先にプラグイン対応を確認）

MOD を入れたい、新しいコンテンツが欲しい
  -> まず MOD リストを確定 -> Fabric（軽量／最適化系）または NeoForge（現代的なコンテンツ系）
  -> 古い MOD パック：Forge
  -> Quilt 専用の MOD がある場合のみ：Quilt を検討

プレイヤーが統合版
  -> バニラサバイバルで公式互換が必要：BDS（プラグインが必要ならローダーを追加）
  -> 高性能 + カスタム：PowerNukkitX
  -> 既製プラグインが最も豊富、PHP を使える：PocketMine-MP

複数のサーバーを接続したい
  -> プロキシ層を追加（Velocity を優先）
```

## 8. プラグインと MOD は別の世界

:::warn プラグインと MOD は別物。混同するとつまずき続ける
**プラグイン（Plugin）**はコアが提供する API を呼び、サーバー側に入れます。プレイヤーは**バニラのクライアント**で参加できます。典型例は管理、経済、保護、ミニゲームです。

**MOD（Mod）**はゲーム本体を直接変更し、**ローダー**の上に入れます。内容を追加する MOD のほとんどは**クライアントとサーバーに同じ構成**を要求し、プレイヤーが入れていないと参加できません。典型例は新しいブロック、アイテム、モブ、ディメンションです。

そこからいくつかの厳格なルールが導かれます：

- **プラグインサーバーに MOD は入れられない**：Paper 系のコアには MOD を読み込む機能がなく、`mods/` ディレクトリも存在しません。
- **MOD サーバーは既定でプラグインを入れられない**：Fabric / NeoForge のサーバーは Bukkit プラグインを認識しません。`plugins/` ディレクトリも、`spigot.yml` や `paper-world-defaults.yml` といった設定一式も存在しません。
- **両側のチューニング経験は流用できない**：プラグインサーバーの JVM 引数、最適化プラグイン、ホットリロードの習慣を MOD サーバーへ持ち込んでもほぼ無効で、逆も同じです。
- **同じ「機能」でも両側で実装がまったく違う**：例えば保護（領地）は、プラグインサーバーならプラグイン、MOD サーバーなら MOD で実現し、設定もコマンドも共通ではありません。
:::

## 9. ハイブリッドサーバーの代償

**ハイブリッド（Hybrid）**とは、プラグイン API と MOD ローディングの両方を提供しようとするサーバープロジェクトです。「プラグイン + MOD」を 1 つのサーバーで動かせますが、代償を明確にしておく必要があります：

| 代償 | 説明 |
| --- | --- |
| 上流への追従が遅い | Minecraft のバージョン、MOD ローダー、プラグイン API を同時に追う必要があり、新バージョンへの対応は通常遅れる |
| 互換問題が両側に出る | プラグインも MOD も問題を起こしうるうえ、どちら側が原因か判断しにくい |
| 助けを求めにくい | 利用者が少なく、問題が起きても既成の答えがほとんどない。作者の余力も限られる |
| アップグレードとロールバックのリスクが高い | ワールド形式、MOD のデータ、プラグインのデータが混在し、純粋なプラグインサーバーや MOD サーバーよりはるかに複雑 |

:::warn ハイブリッドサーバーから始めない
ハイブリッドサーバーは「あれもこれも欲しい」という要求に応えますが、2 つのシステムのリスクを重ね合わせます。**初心者は手を出さないでください**。どうしても必要な場合は、純粋なプラグインサーバーか MOD サーバーをまず安定させ、そのうえでハイブリッドサーバーに価値があるか評価し、そのプロジェクトの公式ドキュメントを基準にしてください。歴史的に複数のハイブリッドプロジェクトがあり、対応状況や保守状況はそれぞれ異なるため、選ぶ前に必ず最新のリリースと対応バージョンを確認してください。
:::

## 10. バージョンとエコシステムの確認方法

記憶でコアを選ばないでください。決定する前に次の 4 ステップを確認します：

| ステップ | 何を見るか | どこで見るか |
| --- | --- | --- |
| 1 | 対象のゲームバージョン向けに、コアがビルドを出しているか | コアの公式ダウンロードページまたは公式リポジトリ |
| 2 | 使うプラグイン／MOD が、そのコアとそのバージョンへの対応を明言しているか | プラグイン／MOD の公開ページと対応リスト |
| 3 | ローダー（あれば）がどのバージョン範囲まで対応しているか | ローダーの公式ドキュメント |
| 4 | 必要な Java / PHP ランタイムのバージョン | コアとローダーの公式ドキュメント |

履歴がわかるのは「バージョンがいつリリースされたか」だけで、「自分のコアが追いついているか」はわかりません。この 2 つは分けて調べてください。詳しくは[バージョン履歴の読み方](/wiki/versions-guide)を参照。

## 11. よくある選型ミス

| ミス | 結果 | 正しい方法 |
| --- | --- | --- |
| MOD をプラグインサーバーに入れる | サーバーがそもそも読み込まず、エラーになることさえある | まずプラグインと MOD を区別し、対応するコアかローダーを選ぶ |
| 先にローダーを入れてから MOD を探す | 欲しい内容の MOD がそのローダーに対応しておらず、やり直しになる | 先に MOD のリストを作り、そのあとローダーを決める |
| Leaves と Leaf を取り違える | 挙動やバニラ特性の再現度が期待と合わない | プロジェクト名と公式説明をよく確認 |
| Folia を「より速い Paper」と思う | プラグインが広範囲で非互換になる | 各プラグインが Folia 対応を明言しているか先に確認 |
| 「性能」だけを見てエコシステムを見ない | コアは速いが、必要なプラグインがない | エコシステムとプラグイン対応を性能の数字より優先 |
| ハイブリッドサーバーで一気に解決しようとする | 互換問題が重なり、アップグレードも困難 | まず純粋なプラグインサーバーか MOD サーバーを動かす |
| BDS をそのまま最新へ上げる | コミュニティ製ローダーが追いつかず、プラグインがすべて無効になる | 先にローダーの対応範囲を確認し、そのあとサーバーを更新 |

## 12. 性能以外の 3 種類のコスト

コアを選ぶときに「性能」という言葉に引っ張られがちです。体験を実際に決めるのは 3 種類のコストで、それぞれ求めるハードウェアが違います：

| コスト | 何で決まるか | 症状 | 対応する選択 |
| --- | --- | --- | --- |
| シングルコア性能 | Minecraft の主要ロジックはほぼシングルスレッドで動く：エンティティ、チャンク、レッドストーン、プラグインのロジックが**1 つのコア**に集中する | プレイヤーが増えると重くなる、TPS が下がる、チャンクの読み込みが遅い | シングルコアが強いマシンは Paper 系。コアが多くクロックが低い場合だけ Folia を検討 |
| メモリ | 描画距離、エンティティ数、プラグインのキャッシュ、MOD の数 | 頻繁な GC によるカクつき、OOM によるクラッシュ | まず描画距離とエンティティ上限を下げ、そのあとメモリを増やす。メモリはシングルコアの代わりにならない |
| ディスクとネットワーク | チャンクの読み書き、自動保存、プレイヤーの出入りに伴うチャンク送信 | 保存時にサーバー全体が固まる、入場が遅い | SSD を優先。ネットワーク最適化は別の話 |

したがって「このマシンは何コアか」よりも「**シングルコアがどれだけ速いか**」のほうがずっと重要です。プラグインの数、MOD の数、描画距離の設定は、コアを替えて得られる利益より体験への影響が大きいのが普通です。
