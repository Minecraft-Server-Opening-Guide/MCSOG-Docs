レッドストーン技術サーバーに最適化 MOD を入れるかどうかは、極端に走りやすい問題です：1 つも入れず重いまま我慢する人もいれば、見つけたものを全部 `mods` に詰め込んで装置が不可解に動かなくなる人もいます。どちらも正しくありません —— **問題は「入れるかどうか」ではなく「この類の代償は何か」**です。

本記事ではよくある最適化系 MOD 10 個を 3 種類に分けます：安心して入れられるもの、バージョンを見る必要があるもの、タイミングを変えるので慎重にすべきもの。判断基準は 1 つだけ：**装置の挙動を変えうるか**。

設定を調整する類の最適化との関係は [パフォーマンス最適化](/tutorials/java/optimize) を参照：あちらは設定と優先順位の全体的な考え方、本記事は MOD の層だけを扱います。

## 1. 10 個の MOD 一覧

以下の loaders、対応バージョン、ダウンロード数は Modrinth の公式エントリによります。

| MOD | loaders | 対応バージョン | ダウンロード数（約） |
| --- | --- | --- | --- |
| `lithium` | fabric、neoforge、quilt | 1.16.2–26.3 | 1 億 3370 万 |
| `ferrite-core` | fabric、forge、neoforge、quilt | 1.16.5–26.3 | 1 億 5740 万 |
| `krypton` | fabric | 1.16.2–26.3 | 4304 万 |
| `c2me-fabric` | fabric | 1.17.1–26.4-snapshot-3 | 3918 万 |
| `modernfix` | fabric、forge、neoforge | 1.16.4–26.1.2 | 8023 万 |
| `memoryleakfix` | fabric、forge、quilt | 1.14.4–1.20.4 | 3802 万 |
| `starlight` | fabric | 1.17–1.20.4 | 1606 万 |
| `async` | fabric、neoforge、quilt | （公式エントリに固定の帯の記載なし） | 71.7 万 |
| `spark` | fabric、forge、neoforge、quilt | 1.16.5–26.3 | 2317 万 |
| `chunky` | bukkit、fabric、folia、forge | 1.13.2–26.3 | 1888 万 |

この表を読むときの注意が 2 点：

- **ダウンロード数が多い＝「必ず入れる」ではない**。使う人が多いというだけで、あなたのハードウェアと装置に合うとは限りません。
- **`async` のバージョン帯は公式エントリに固定の書き方がない**ため、上表では範囲を作っていません。プロジェクトページに現在記載されているゲームバージョンを優先してください。

## 2. 安心して入れられる：メモリ、起動、分析、プリ生成

この類は「挙動と無関係」です：最適化するのはゲームのロジックや順序ではなく、メモリ使用量、起動プロセス、観測手段、チャンク生成です。レッドストーン技術サーバーにとって、この類の代償は最も小さいです。

| MOD | 安心して入れられる理由 |
| --- | --- |
| `ferrite-core` | 動かすのはメモリ使用量の層で、tick ロジックには介入しない |
| `modernfix` | 対象は性能、メモリ、バグ修正で、単一の仕組みの書き換えではない |
| `spark` | 観測だけを担い、ゲームの挙動は変えない |
| `chunky` | 事前にチャンクを生成し終え、プレイヤーが走りながら生成するのを避ける |

補足：

- **`spark` は最適化 MOD ではありません**。分析ツールです。「まず測ってから変える」とは、`spark` を入れるのは**ボトルネックがどこかを見るため**であり、サーバーが速くなることを期待するものではない、ということです。グラフの読み方は [spark でサーバー性能を分析する](/tutorials/ops/spark) を参照。
- **`chunky` が解決するのは生成期のラグ**で、[パフォーマンス最適化](/tutorials/java/optimize) の「ワールドのプリ生成」節と同じ話を MOD の形で提供するものです。長期運営のサーバーではほぼ必須。
- **この類同士は競合しません**：メモリ、起動、分析、プリ生成がそれぞれ別の区間を担うので、併用できます。本当に注意すべきは「機能が重複する」2 つの MOD で、たとえば両方がライトエンジンの実装を書き換える場合です。

## 3. バージョンを見る：公式の結論 2 つ

この 2 つの MOD は「悪い」のではなく、適用範囲に明確な境界があり、公式自身が境界を書いています。結論をそのまま使えば十分です：

### `memoryleakfix`：1.20.5+ では不要

公式 README の結論は：**Minecraft 1.20.5+ 以降、この MOD が以前修正していたメモリリークはすべて公式に修正済み**であり、新しいバージョンではすでに不要です。

対応するデータからも分かります：対応バージョンは 1.14.4–1.20.4 で、新しいゲームはこの帯に入りません。**新しいバージョンで入れ続けても意味はありません**；1.20.4 以前のバージョンでのみ、それが修正していたリークに公式未修正の余地が残ります。

### `starlight`：1.20.4 まで、しかも公式が取捨を示している

公式 README には 4 つの要点があり、1 つずつ具体的です：

| 公式の結論 | レッドストーン技術サーバーへの意味 |
| --- | --- |
| 1.20.4 まで対応（1.17–1.20.4） | 新しいバージョンには入れられるファイル自体がない |
| 1.20 では Starlight とバニラの差はすでに小さい | 1.20 に上げたあとは、入れる利得はもう大きくない |
| Phosphor と完全に非互換 | 両者は同時に存在できない |
| **侵襲的**なライトエンジンの書き換えで、他の MOD と衝突しやすい | レッドストーン技術サーバーの MOD 構成は通常多く、衝突リスクをコストに算入する必要がある |
| 1.20 以降の後続は Moonrise を指す | 歴史的な役割はすでに引き継がれている |

したがって `starlight` の正しい使い方は：**1.20.4 以前に留まると明確に分かっていて、Phosphor を入れていないときだけ検討する**。新しいバージョンの装置サーバーでは、これで悩む必要はありません。

## 4. タイミングを変える、慎重に：4 つの MOD

この類こそ、レッドストーン技術サーバーが立ち止まって考えるべきものです。共通点は**イベントが起きる順序やタイミングを変える**ことで、装置の正しさはしばしばその順序の上に成り立っています。

| MOD | リスクの所在 |
| --- | --- |
| `lithium` | 対象範囲が広く、スポーン、AI、ブロック挙動などのロジック経路に触れる。「汎用の最適化」は「あなたに無害」ではない |
| `krypton` | 変えるのはネットワークスタック。公式 README が明確に宣言：**作者は安定性と他の MOD との互換性についていかなる保証もしない** |
| `c2me-fabric` | チャンク処理のマルチスレッド化で、タイミングがシングルスレッドと変わる |
| `async` | エンティティ処理の並列化（複数の CPU コアとスレッドにまたがる）で、エンティティの処理順が変わる |

1 つずつ説明：

- **`lithium`** はこの類で最も勧められるもので、最も警戒が緩みやすいものでもあります：汎用の最適化と説明されていますが、「できるだけ挙動を変えない」と「絶対に挙動を変えない」は別物です。**入れる前に装置で実測してください** —— 特にスポーン、AI、ブロック更新に敏感な装置。
- **`krypton`** の立場は最も明確です：公式 README が安定性と互換性について一切保証しないと直接書いています。これは「使えない」ではなく「問題が起きたときに作者の底支えを期待するな」ということです。公開サーバーで使うなら天秤にかけてください。
- **`c2me-fabric`** はチャンク処理を並列化します。マルチスレッドはチャンクの読み込み、生成、アンロードのタイミングを変え、**常時読み込み区域や装置がチャンクをまたぐ部分こそ、これで問題が出やすいところ**です。
- **`async`** はエンティティ処理を複数の CPU コアとスレッドへ並列化します。エンティティの並列化は tick 順序が 1 つずつではなくなるということで、エンティティの順序や衝突のタイミングに依存する装置が最も脆い類です。

本節の結論：**これら 4 つの利得は本物で、装置が動かなくなるリスクも本物です。だから「まず装置で測る」しかありません。**

## 5. レッドストーン技術サーバーで最適化 MOD を入れる 3 原則

上を 3 つの実行可能な原則にまとめます：

```
1. 挙動と無関係なものを優先 —— メモリ、起動、分析、プリ生成を先に入れる
2. タイミングを変えるものは先に装置で測る —— 1 回に 1 つだけ足し、足したら装置で検証する
3. spark で比較する —— 入れる前に 1 回、入れたあとに 1 回測り、感覚ではなくデータを見る
```

少し展開します：

1. **挙動と無関係なものを優先**。まず第 2 節の組を入れます。装置の挙動にはほとんど影響せず、利得も最も直接的です。多くのサーバーの問題はこの段階で大半が緩和されます。
2. **タイミングを変えるものは先に装置で測る**。第 4 節の 4 つは一度に全部入れず、**1 回に 1 つだけ**足し、足したらすぐ代表的な装置で 1 回動かす —— トラップタワーはまだ産出するか、装置は想定どおり動くか。問題が出たらその 1 つだけ戻し、全部を倒さない。
3. **1 回に 1 つだけ足し、`spark` で比較する**。`spark` は分析ツールで、価値は「入れたあと本当に速くなったか」を知れることにあります。**データの裏付けがない最適化 MOD は心理的な慰め**です。

運用上の習慣がもう 2 つ、MOD 自体とは関係ありませんが同じくらい重要です：

- MOD を入れる、替える前に**まずワールドをバックアップ**する。手順は [バックアップと復元](/tutorials/java/backup) を参照。
- 問題が出たら**直近に足した MOD をまず外す**。これが最速の特定手段です。
