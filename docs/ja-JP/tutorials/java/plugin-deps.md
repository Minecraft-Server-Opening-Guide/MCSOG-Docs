プラグイン導入で最もよくある失敗は、バージョンを間違えることではなく、**前提プラグインの入れ忘れ**です：プラグインは確かに `plugins/` に入れたのに `/plugins` では赤くなっている、あるいは読み込めても機能が欠けている。

本記事では前提とは何か、欠けるとどうなるか、そして Vault、PlaceholderAPI、ProtocolLib、LuckPerms という最も依存される 4 つのプラグインがそれぞれ何をするのかを整理します。

## 1. 前提プラグインとは

プラグイン同士は依存し合えます。作者がプラグインを書くとき、車輪の再発明を避けたいなら「別のプラグインが提供する能力が必要だ」と宣言します。必要とされる側が**前提（依存、dependency）**です。

依存関係はプラグインの jar 内の `plugin.yml` に書かれ、2 種類あります：

| 宣言 | 意味 | 欠けるとどうなるか |
| --- | --- | --- |
| `depend`（ハード前提） | これがないと動作しない | プラグインは**読み込みに失敗**し、`/plugins` で赤く表示される |
| `softdepend`（ソフト前提） | あれば追加機能が有効になり、なくても動く | プラグインは正常に読み込まれ、**関連機能が静かに無効化される** |

サーバーは起動時に前提を先に読み込み、そのあと依存するプラグインを読み込みます。これが「前提は先に入れる必要がある」理由です。

:::note どのプラグインも前提になりうる
前提は特別な種類のプラグインではありません。理論上はどのプラグインも他のプラグインから依存として宣言されえます。ただし以下のいくつかは依存されることが非常に多く、次第に「前提プラグイン」という総称が付きました。
:::

## 2. 前提が欠けるとどうなるか

症状は「エラー」ほど分かりやすいとは限りません。以下の現れ方を押さえておくと多くの時間を節約できます：

| 現象 | 説明 |
| --- | --- |
| `/plugins` で赤く表示される | サーバーはプラグインを認識したが読み込みに失敗した。コンソールに必ず理由がある |
| コンソールに `Unknown dependency` | 最も明確なケース：`plugin.yml` で宣言されたハード前提が `plugins/` にない |
| コンソールに `ClassNotFoundException` / `NoClassDefFoundError` | コードが前提の提供するクラスを参照しているが、そのクラスが存在しない |
| プラグインは入ったのに、ある機能が「反応しない」 | 多くはソフト前提の欠落で、機能が自動的に無効化されている |
| 変数が `%player_name%` のまま表示される | PlaceholderAPI を入れていない、または対応する変数拡張をダウンロードしていない |
| 経済系コマンドが経済システムが見つからないと表示する | Vault は入っているが、実際に経済を提供するプラグインがない |

:::warn まずコンソールを見て、それから推測する
プラグインの読み込み失敗の理由は必ず起動ログに書かれています。**`logs/latest.log` を開いてプラグイン名で検索する**ほうが、チャットで「プラグインが赤い」と説明するよりずっと速いです。
:::

## 3. 前提が必要かを判断する方法

信頼度の高い順に：

1. **プラグインの配布ページを見る**。SpigotMC、Modrinth、Hangar、GitHub の説明には通常 `Requires`、`Dependencies`、あるいは「前提」の欄があります。
2. **jar 内の `plugin.yml` を見る**。圧縮ソフトで jar を開き `plugin.yml` を探すと、`depend` と `softdepend` の 2 行が答えです。これが最も権威があります。
3. **コンソールのエラーを見る**。起動時に何が足りないと言われたら、それを補います。
4. **`/plugins` の色を見る**。赤い項目はまず前提を疑い、次にバージョン不一致を疑います。
5. **プラグインのドキュメントや issue を見る**。作者は通常、依存とバージョン要件を明記しています。

## 4. Vault

**何なのか**：Vault は Bukkit 系サーバー向けの**抽象ライブラリ**です。自分では具体的な機能を何もせず、インターフェースの組を定義するだけで、「経済／権限／チャットの能力を必要とするプラグイン」と「それらの能力を実際に実装するプラグイン」が会話できるようにします。

**経済プラグインではありません**。ここが最も誤解されやすい点です：Vault 自体は通貨を一切生み出さず、統一インターフェースにすぎません。実際に経済システムを持つには、経済プラグイン（XConomy、EssentialsX の経済モジュール、CMI など）を入れ、それが Vault にサービスを登録し、他のプラグインが Vault 経由で残高を読み書きします。

| Vault が提供するインターフェース | 誰が実装するか | 誰が呼ぶか |
| --- | --- | --- |
| 経済（Economy） | 経済プラグイン | ショップ、ログインボーナス、抽選など |
| 権限（Permission） | 権限プラグイン（LuckPerms など） | プレイヤーの権限を判定する必要のあるプラグイン |
| チャット（Chat） | チャットプラグイン | チャットの送信／整形が必要なプラグイン |

**誰が必要か**：プラグイン一覧に「Vault に依存」という項目があれば入れてください。運営者が Vault に何かを設定する必要はなく、入れるだけで済みます。

:::tip バージョン表記は無視してよい
Vault は古いバージョンと新しいバージョンの Minecraft の両方に対応しているので、SpigotMC のページに書かれた対応バージョンを気にする必要はありません。
:::

## 5. PlaceholderAPI

**何なのか**：PlaceholderAPI（略称 PAPI）は変数プレースホルダーの仕組みです。`%変数拡張_引数%` の形のテキストを、他のプラグインが提供する情報に置き換えます。

```
%player_name%        プレイヤー名
%player_level%       プレイヤーのレベル
%vault_eco_balance%  プレイヤーの残高
%server_online%      オンライン人数
```

`%player_name%` を例にすると、`player` が変数拡張の名前、`name` が引数で、「プレイヤー名を取る」という意味です。

**変数拡張**：PAPI 本体はほとんど変数を提供せず、変数は 1 つ 1 つの**拡張**が提供します。拡張はゲーム内から eCloud でダウンロードでき、現在は数百種類があり、EssentialsX、LuckPerms、Vault など多くのプラグインをカバーしています。

```
/papi ecloud download Player     Player 拡張をダウンロード
/papi list                       インストール済みの拡張を表示
/papi info <拡張名>               ある拡張が提供する変数を表示
/papi reload                     PAPI と拡張をリロード
```

**デバッグ**：変数を書いたらまずゲーム内で検証し、プレイヤーからの報告を待たないこと。

```
/papi parse me %player_name%
```

このコマンドは解析結果をそのまま返します。`me` は自分をコンテキストにする意味です。

**変数のネスト**：ある変数の解析結果を別の変数の引数に入れるとき、内側は `%%` の代わりに `{}` を使います：

```
%math_2_{player_health}%
```

上例には math 拡張が必要で、プレイヤーの体力を小数 2 桁に丸めます。

**変数以外にできること**：一部の拡張は「値を取る」を超えた能力を提供します。たとえば Math（数学演算）、CheckItem（プレイヤーのアイテム判定）、JavaScript（スクリプト実行）、Progress（プログレスバー生成）などです。

**誰が必要か**：TAB、スコアボード、ホログラム、メニュー、チャットの書式、MOTD といった「他のプラグインのデータを表示する」プラグインは、ほぼ PAPI に頼っています。プラグイン系で最も早めに入れておく価値のあるプラグインの 1 つです。

## 6. ProtocolLib

**何なのか**：ProtocolLib は Minecraft のネットワークプロトコル（パケット）への低レベルなアクセスを提供し、プラグインがパケットを傍受・改変・能動的に送信できるようにして、Bukkit API 自体が公開していないことを行えるようにします。

**誰が必要か**：これは**プラグイン開発者向け**です。運営者として設定するものは何もありません —— あるプラグインが ProtocolLib を要求するなら、入れるだけです。

| 項目 | 説明 |
| --- | --- |
| 設定は必要か | 不要。入れるだけで動く |
| バージョンの選択 | 1.8 から 1.19.4 は 5.0.0、それ以降は最新版 |
| よくある設定 | `plugins/ProtocolLib/config.yml` の `auto updater.notify` を `false` にすると更新通知を切れる |

:::warn バージョンは必ず合わせる
ProtocolLib はサーバーの内部実装を直接操作するため、**バージョンが合わないとサーバー全体がエラーになったり落ちたりします**。プラグイン単体の問題では済みません。サーバーコアを上げるときは、これを同期して確認するのを忘れないでください。
:::

## 7. LuckPerms

**何なのか**：LuckPerms は現在最も主流の**権限プラグイン**で、「誰がどのコマンドを使えるか、誰がどのワールドに入れるか、どのプレフィックスを表示するか」を管理します。Bukkit/Spigot/Paper、BungeeCord、Velocity、Sponge、Fabric など多くのプラットフォームに対応します。

**中核となる概念**：

| 概念 | 役割 |
| --- | --- |
| 権限ノード（permission） | 最小単位。`essentials.fly` の形で、`true` が許可、`false` が拒否 |
| グループ（group） | 権限の集合。`default`、`vip`、`admin` など |
| 継承（inheritance） | グループが他のグループを継承でき、`admin` が `vip` を継承すれば重複設定が不要 |
| コンテキスト（context） | 権限を特定のワールド、サーバー、モードでのみ有効にする |
| プレフィックス／サフィックス（meta） | チャットや TAB などのプラグインが読む表示情報 |

**よく使うコマンド**：

```
/lp user <プレイヤー> permission set <ノード> true
/lp group <グループ> permission set <ノード> true
/lp group <グループ> parent add <親グループ>
/lp user <プレイヤー> parent add <グループ>
/lp editor
```

`/lp editor` は Web エディタのリンクを生成します。GUI で権限を変えるほうがコマンドを打つより直感的で、変更後に保存すれば反映されます。

**ストレージ**：既定ではファイル型（H2/SQLite）で、データは `plugins/LuckPerms/` の下にあります。**複数サーバーで 1 つの権限を共有するなら、MySQL/MariaDB などのデータベースに必ず変えてください**。そうしないと各サーバーが個別に管理することになります。

**Vault との関係**：LuckPerms は Vault に権限サービスを登録するので、「Vault 経由で権限を判定する」プラグインは、LuckPerms を入れれば追加設定なしで正常に動きます。

:::note プレフィックスは誰が表示するのか
LuckPerms はプレフィックスを保存するだけで、**表示は担当しません**。プレフィックスをチャット欄や TAB に出すのは、チャットプラグイン（TrChat、Carbon など）や TAB 系のプラグインで、それらが LuckPerms の meta 情報を読みます。
:::

## 8. 導入順序と組み合わせ

前提は**先に入れ、先に再起動**し、そのあと依存するプラグインを入れます。よくある立ち上げ順：

| 順序 | プラグイン | 理由 |
| --- | --- | --- |
| 1 | LuckPerms | 権限は他のプラグインが「使えるか」を判断する土台 |
| 2 | 経済プラグイン（XConomy / EssentialsX / CMI） | Vault に実際の経済実装を提供する |
| 3 | Vault | 経済、権限、チャットに統一インターフェースを与える |
| 4 | PlaceholderAPI | 入れたあと、必要に応じて変数拡張をダウンロード |
| 5 | ProtocolLib | 明確に要求するプラグインがあるときだけ入れる |
| 6 | その他の機能プラグイン | ショップ、メニュー、称号、TAB など |

:::tip 入れたら検証してから次へ
前提を 1 つ入れるたびに再起動し、`/plugins` で緑になっていることを確認します。十数個のプラグインを一度に放り込むと、問題が出たときの切り分けコストが倍増します。
:::

## 9. 切り分けチェックリスト

| 確認項目 | どう確かめるか |
| --- | --- |
| 前提が本当に `plugins/` にあるか | ファイル名と拡張子が `.jar` かを見る |
| ハード前提の欠落か | コンソールで `Unknown dependency` を検索 |
| ソフト前提の欠落か | 機能が反応しないのにプラグインが緑なら、ドキュメントで何に依存しているか確認 |
| バージョンが合っているか | プラグインの配布ページに書かれたサーバーバージョンと前提バージョンと照合 |
| 変数が解析されない | PAPI を入れ、対応する拡張をダウンロードしたうえで `/papi parse me` で検証 |
| 経済が使えない | Vault **と**実際の経済プラグインの両方が入っているか確認 |
| 権限が効かない | `/lp user <プレイヤー> permission check <ノード>` で判定結果を見る |
| 変更が反映されない | プラグイン自身の reload コマンド、または再起動 |
