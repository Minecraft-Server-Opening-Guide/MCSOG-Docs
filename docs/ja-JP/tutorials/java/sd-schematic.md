レッドストーン技術の遊びはスケマティック（原理図）を避けて通れません：他人が設計したワールドイーター、トラップタワー、ゲートカッティング装置を記憶だけで写すことは不可能で、投影を見ながら 1 層ずつ合わせて建てる必要があります。シングルのセーブデータなら簡単で、クライアント側の投影 MOD を入れれば済みます。しかしマルチプレイサーバーになると、スケマティックは各人の PC に散らばり、真似して建てたい人はまず原作者にファイルをもらう必要があります。

`syncmatica` が解決するのはまさにこれです。Litematica のための同期の相棒で、スケマティックと配置を手軽に共有できるようにします。

本記事は 3 つだけ扱います：なぜ必要か、どちら側に入れるか、バージョンをどう揃えるか。**具体的なアップロード方法、誰に権限があるか、どのコマンドを使うかは MOD の公式説明を優先し、本記事では操作手順を復唱しません** —— その部分はバージョンごとに変わりうるので、古いチュートリアルに従うほうがむしろ間違えやすいです。

## 1. マルチプレイサーバーでスケマティックが詰まる点

シングルのセーブデータでは、スケマティックのファイルも投影も自分のクライアント上にあり、「共有」の問題は存在しません。マルチプレイサーバーでは 3 層の面倒があります：

| 面倒 | 具体的な現れ方 |
| --- | --- |
| ファイルが個人の PC にある | 新しいプレイヤーが来るたびに、原作者がファイルを送り直す |
| 位置が合わない | 投影は「このスケマティックがワールドのどの座標にあるか」を知る必要があり、口頭で座標を伝えると間違えやすい |
| バージョンと出所が混ざる | 受け渡しを重ねるうちに、誰の手元のものが最新か分からなくなる |

`syncmatica` が扱うのは前の 2 層です：スケマティックとその配置を「手軽に共有できる」ものにします。やるのは同期と共有の層で、投影表示を代わりにやってくれるわけではありません —— 投影表示は依然として Litematica の仕事です。

> 投影がレッドストーン技術のツールチェーンでどこに位置するかを先に知りたいなら、[レッドストーン技術とレッドストーン](/tutorials/java/redstone) のクライアント MOD の表と、[レッドストーン技術とレッドストーン上級](/tutorials/java/redstone-advanced) の MiniHUD、Litematica などのツールの説明を参照してください。

## 2. 両側に何を入れるか

これが本記事で最も覚えるべき表です。スケマティックの共有は「MOD を 1 つ入れれば終わり」ではなく、**サーバーとクライアントの両方に Syncmatica を入れ、クライアントにはさらに Litematica を入れる**必要があります。

| 位置 | 必要なもの | 説明 |
| --- | --- | --- |
| サーバー | `syncmatica` | 同期のサーバー側半分。クライアントだけでは共有できない |
| クライアント | `syncmatica` | 同期のクライアント側半分。Litematica と連携して動く |
| クライアント | `litematica` | 投影表示を実際に担う MOD。`syncmatica` はそのための同期の相棒 |

つまずきやすい 3 点：

1. **プレイヤーにだけ Syncmatica を入れた**がサーバーには入れていない、同期は起こりようがない。
2. **サーバーに Syncmatica を入れたがプレイヤーに Litematica を入れさせていない**、共有されたスケマティックを表示するものが何もない。
3. **両側のバージョンが不一致**。これが最もよくある問題で、第 3 節で個別に扱います。

## 3. 3 つの MOD のローダーとバージョン帯

以下のデータは Modrinth の公式エントリによるもので、執筆時に確認済みです。バージョン選びの出発点として扱い、実際にダウンロードする前にプロジェクトページをもう一度確認してください。

| MOD | loaders | 対応バージョン | ダウンロード数（約） |
| --- | --- | --- | --- |
| `syncmatica` | fabric、quilt | 1.16–26.3 | 83.9 万 |
| `litematica` | fabric、forge、liteloader、ornithe | 1.12–26.3 | 2644 万 |
| `servux` | fabric | 1.14.4–26.3 | 98.4 万 |

補足：

- 3 つの MOD のバージョン帯はどれも広く、1.12 / 1.14 / 1.16 から 26.x のような最近のバージョンまでカバーします。**帯が広いからといって適当に 1 つ選べば動くわけではなく**、本当に揃えるべきは「ゲームバージョンが一致し、両側の Syncmatica が同じバージョン帯に属すること」です。
- よく一緒に挙げられる MOD がもう 1 つあります：`servux`。**サーバー側の MOD** で、一部のクライアント MOD に追加のサポートと機能を提供します。スケマティック共有の必需品ではありませんが、解いているのは同じ類の問題 ——「クライアント MOD がより多くのデータを欲しがるとき、サーバーの協力が要る」です。
- `litematica` の loaders には forge と liteloader、ornithe があり、それ自体は Fabric 一本ではないことが分かります。しかし `syncmatica` は fabric と quilt だけです。**この側の同期能力が、選択肢を狭める環**です。

## 4. バージョンの整合：この側が最も間違えやすい

スケマティックの共有は両側が協力する仕組みなので、「揃える」はスローガンではなく、同時に成立しなければならない 4 つのバージョン関係です：

| 確認するもの | 要件 |
| --- | --- |
| ゲームバージョン | クライアントとサーバーが同じゲームバージョンであること |
| `syncmatica`（サーバー） | そのゲームバージョンの対応帯に入っていること |
| `syncmatica`（クライアント） | 上と同じバージョン帯。両側で混用しない |
| `litematica`（クライアント） | そのゲームバージョンに合っていること |

現実に最もよくある失敗は 2 つです：1 つは**片側だけ更新した**（クライアントの MOD だけ替えてサーバーは旧版のまま、など）、もう 1 つは**ある MOD を動かすためにゲームバージョンを戻した**結果、もう片側の MOD が合わなくなる、です。

堅実な操作順を示します：

1. まずゲームバージョンを決め、第 3 節の表で 3 つの MOD を選ぶ。
2. サーバーとクライアントの `syncmatica` は同じバージョン帯のファイルを使う。
3. 入れたらまず正常に入場でき、投影が表示できることを確認し、そのうえで共有を語る。
4. 問題が出たときの第一の判断材料は常に**バージョン**であり、設定ではない。

## 5. なぜ本記事は「どちら側に入れるか」しか扱わないのか

スケマティックの共有は**両側をまたぐ協力**の仕組みで、どこか 1 歩ずれると明確なエラーは出ず、「共有が反応しない」という形でしか現れません。一方、具体的な操作方法 —— スケマティックをどう置くか、誰が置けるか、どのコマンドで管理するか —— は MOD 自身の機能面に属し、バージョンで変わります。

だから本記事のスタンスは：

1. **原理をはっきり**：なぜ必要か、データは両側のどこを流れるか。
2. **位置をはっきり**：サーバーに何を入れ、クライアントに何を入れるか。1 つも欠かせない。
3. **バージョンの整合をはっきり**：3 つのもののバージョン関係。
4. **操作は公式に任せる**：MOD の公式説明にどう書いてあるか、それに従う。

こう書くのは手抜きではなく、あるバージョンの UI とコマンドをここに固定して、MOD が更新されたあとにあなたを誤らせないためです。

## 6. Carpet との関係

**同じレッドストーン技術のツールボックスに属しますが、解いている問題は違います**。

| | Carpet | Syncmatica |
| --- | --- | --- |
| 何を解決するか | ルールでバニラの細かい挙動をオン／オフする | スケマティックと配置を手軽に共有できるようにする |
| 形態 | Fabric サーバー MOD で、ルールシステムを提供 | 同期 MOD。サーバーとクライアントに半分ずつ |
| 典型的な使い方 | `/carpet <ルール名> <値>` | Litematica と連携してスケマティックを共有する |

両者の共通点はどちらも Fabric 主体であることです：Carpet とそのすべてのアドオンは Fabric、`syncmatica` の loaders も fabric と quilt です。これも [サーバーコアの選択](/tutorials/java/sd-server) で Fabric サーバー + MCDR を勧める理由の 1 つ —— ツールチェーンが同じ側にあり、ブリッジが要りません。

Carpet 本体の位置づけとルールの使い方は [Carpet とそのアドオン](/tutorials/java/sd-carpet) を参照。

## 7. ワールドイーター、ゲートカッティングとの連携

投影の最も典型的な用途は大型装置を建てることです：ワールドイーターは TNT アレイと飛行装置で区域をまとめて空にする装置で、サイズが大きく構造が反復し、位置精度の要求が高いため、頭で覚えて正しく建てることは不可能です。正常な流れは：**まずスケマティックがあり、投影を見ながら建てる**。

スケマティックの共有がこの流れで解くのは協力の問題です：1 台のワールドイーターは 1 人で建て切ることは少なく、複数人が分担して施工する必要があります。投影が一致していればこそ、複数人のブロックがつながります。

そして装置が動き出せば、重点は投影ではなくリスク管理になります：[ワールドイーターとゲートカッティング](/tutorials/java/sd-machine) は、装置が強力なほど「バックアップ + 権限 + クラッシュ防止ルール」の三点セットが必要なこと、新しいバージョンではアップデート抑制（コミュニティ通称「ゲートカッティング」）をコミュニティ MOD で復元する必要があること、といった事実を扱っています。装置を建てる前にあの記事を読み終えてください。

## 8. 一線チェックリスト

```
サーバーに Syncmatica + クライアントに Syncmatica + クライアントに Litematica
そのうえで 3 つのバージョンを揃える —— 1 つ欠けると共有は成立しない
```

- **サーバー側を忘れない**：クライアントだけ設定するのが初心者に最も多い誤り。
- **操作は公式どおり**：MOD の公式説明を確認せずに他人の手順をそのまま真似しない。
- **バージョンを揃えてから入れる**：バージョン帯は第 3 節の表、入れる前にプロジェクトページを確認。
