「レッドストーン技術」はサバイバルと回路を組み合わせた技術寄りの遊び方で、レッドストーンの装置、トラップタワー、正確なブロック挙動を中心に据えます。普通のサバイバルサーバーとの最大の違いは：**「バニラの挙動が変更されていないか」に極めて敏感**なことです。

最適化で消されたブロック更新の順序が 1 つ、修正された複製の特性が 1 つあるだけで、装置全体が使い物にならなくなります。

## 1. プラグイン系では 100% バニラにできない

Paper の公式ドキュメントにも書かれています：

> *Unfortunately, it currently is not possible to get a 100% Vanilla experience in Paper.*

つまり、**Paper / Purpur でレッドストーン技術をやるのは、本質的に妥協**です。だからまずコアを正しく選び、そのうえで設定を語ります。

| あなたの目標 | 推奨コア |
| --- | --- |
| **純粋なレッドストーン技術 / 技術寄り** | **Fabric**（最適化 MOD を入れなければバニラに最も近い）、**Leaves**（Paper 分岐で、壊されたバニラ特性を専門に修復） |
| バニラの検証 / 最小構成 | **Vanilla**（公式のバニラサーバー） |
| **軽度のレッドストーン技術**で、プラグインも使いたい | Paper 系 + 下記の設定チューニング |

> `Leaves` を別に挙げる理由：その位置づけが「バニラ特性の修復」であり、Paper のエコシステム（プラグイン、性能）を保ちながら変更された挙動を戻せます。「プラグインもレッドストーン技術も」という場合に現実的な選択です。

## 2. プラグイン系でのバニラ特性のチューニング

Paper 系で**軽度のレッドストーン技術**をやると決めたなら、ここを重点的に調整します（ファイル：`config/paper-world-defaults.yml`）。

### チャンクのアンロード遅延

```yaml
chunks:
  delay-chunk-unloads-by: 0s
```

既定では一定の遅延があります。`0s` にしないと、**エンダーパールの滞留を利用したテレポート**のような「チャンクが即座にアンロードされること」に依存する装置が正常に動きません。

### エンティティの衝突

```yaml
collisions:
  allow-player-cramming-damage: true
  max-entity-collisions: 2147483647
```

- `allow-player-cramming-damage`：エンティティが多すぎて圧迫されたときにプレイヤーがダメージを受けるか。バニラと一致させるなら `true`。
- `max-entity-collisions`：この数を超えるとサーバーは**エンティティの衝突処理を停止**します。密集するエンティティ装置（大規模なトラップタワーなど）では極端に大きな値にする必要があり、**代償は性能低下**です。

### エンティティの挙動

```yaml
entities:
  behavior:
    # ミツバチが巣を離れる際の失敗クールダウン。バニラの挙動に関係する
```

Paper は性能のために一部のエンティティ挙動に「クールダウン」や制限を加えています。レッドストーン技術では項目ごとに確認して無効にします。

### レッドストーンの実装

Paper は**レッドストーンの実装方式**を切り替えられます。**vanilla 実装のままにしてください** —— 他の実装（性能向けに最適化されたもの）に変えるとレッドストーンの更新挙動が変わり、装置は即座に動かなくなります。
:::warn 設定を変える前にバックアップ
`config/` 下のファイルを間違えるとサーバーの起動が異常になります。**変更前にコピーを取っておき**、問題が出たらすぐ戻してください。
:::

## 3. レッドストーン技術でよく使う MOD（MOD 系）

レッドストーン技術のプレイヤーは通常クライアント MOD を一通り入れ、サーバー側にも対応が必要です：

| MOD | 役割 |
| --- | --- |
| **Carpet** | サーバー側のルール制御。レッドストーン技術サーバーではほぼ必須（バニラの細かい挙動を多数オン／オフできる） |
| **MiniHUD** | 座標、バイオーム、明るさなどを HUD 表示 |
| **Litematica** | スケマティックの投影。見ながら装置を建てる |
| **Tweakeroo** | 便利な調整が多数 |
| **Servux** | MiniHUD の構造物表示やスケマティックの貼り付けをサーバー上で正しく動作させる |
| **Syncmatica** | スケマティックをサーバーにアップロードして他のプレイヤーと共有 |
| **BBOR** | 自然構造物の範囲、3D のバイオーム境界、スライムチャンクを表示 |
| **Jade / JEI（または REI）** | ブロック情報 / クラフトレシピの表示 |
| **Xaero's Minimap / World Map** | ミニマップとワールドマップ |
| **AppleSkin** | 空腹値と満腹度の回復を表示 |
| **EasyAuth** | サーバー側のログイン MOD |
| **Fuji** | 多機能な管理 MOD |

> 多くの MOD は一部の機能を**サーバー側にも入れて**初めて正しい数値が表示されます（AppleSkin の正確な満腹度など）。レッドストーン技術サーバーを立てるときはプレイヤーとバージョンを揃えてください。

## 4. レッドストーン専用のサーバー

**レッドストーン回路そのもの**だけに関心がある場合（大型の計算機を作る、装置のタイミングを検証するなど）、レッドストーン向けに最適化された専用のサーバーコアもあります（**MCHPRS** など）：サバイバル関連の負担を削り、レッドストーンの演算速度を極限まで上げます。

代償は**正常なサバイバルサーバーではない**ことで、多くのバニラの仕組みが不完全です。**装置のテスト**には向きますが、プレイヤーに遊ばせるサーバーには向きません。

## 5. 選定のまとめ

```
本物のレッドストーン技術（装置が正確でなければならない）
   → Fabric / Leaves / Vanilla
   → プラグイン系はどう調整しても 100% バニラには届かない

軽度のレッドストーン技術 + プラグインも使いたい
   → Paper 系 + 上記第 2 節の設定チューニング
   → 「一部の装置は動かないかもしれない」を受け入れる

レッドストーン回路のテストだけ
   → MCHPRS などの専用コア
```
