レッドストーン技術サーバーのワールドは**継続的に大規模に書き換えられる**：装置が動き出せば、地形、ブロック、エンティティがまとめて変化します。1 回の誤操作、1 回のクラッシュによるセーブデータの破損の代償は、しばしば「数分の進行を失う」ではなく「プロジェクト全体が無駄になる」です。だからレッドストーン技術サーバーでは、セーブデータの保護は片手間の作業ではなく、フローに組み込むべき一環です。

汎用のバックアップ原則 —— 何を取るか、整合性をどう保つか、保持方針、復元手順 —— は [バックアップと復元](/tutorials/java/backup) に書いてあるので繰り返しません。ここではレッドストーン技術の場面で追加になる 3 点だけを扱います：**MCDR のバックアッププラグインでバックアップをフローにする**、**`Ledger` で何が起きたかを突き止める**、**少なくとも 1 部をマシンの外に置く**。

## 1. レッドストーン技術サーバーのバックアップをより頻繁にすべき理由

| レッドストーン技術サーバーの特徴 | バックアップへの要求 |
| --- | --- |
| 装置が動き出すと世界の変化が非常に大きい：区域をまとめて空にする装置、常時稼働する農場は、ごく短時間で広い地形とエンティティを書き換える | バックアップ間隔は許容できる最大損失より短くする。一晩前のバックアップで大規模工事を守れると考えない |
| ロールバックは連座する：全体を戻すと同じ時間帯の**すべて**のプレイヤーの進行も一緒に消える | 事故のときはまず部分的な修復を狙い、直せないときだけ全体を戻す |
| 大規模工事の投入が非常に大きい：材料集め、組み立て、調整と、装置は「時間を産出に変える」もの | バックアップが守るのは数ブロックではなく、すでに投じた時間そのもの |
| セーブデータとバックアップは既定では同じマシン、同じディスクにある | ローカルバックアップに加えて、このマシンを離れた 1 部が必須 |

:::warn 復元を検証していないバックアップはバックアップではない
この言葉はレッドストーン技術サーバーでこそ当てはまります：装置が強力なほど、ロールバックの代償は大きい。本当に事故が起きた日に、バックアップが一度も成功していなかったと気づいても、損失は取り返せません。復元演習のやり方は [バックアップと復元](/tutorials/java/backup) を参照。
:::

## 2. MCDR のバックアッププラグインでバックアップをフローにする

MCDR は**サーバープロセスの外側にいる**Python のマネージャーで、サーバーが落ちても残ります。だからサーバーを自動再起動でき、クラッシュ時にもバックアップを実行できます —— まさにバックアップがいるべき場所です。インストール方法、プラグインの仕組み、コマンドは [MCDR サーバーマネージャー](/tutorials/java/mcdr) を参照。

MCDR の公式プラグイン一覧に**実在する**バックアップ系プラグインのディレクトリ名は、用途の方向で 4 つの組に分けられます：

| 方向 | プラグインのディレクトリ名 | おおよその用途 |
| --- | --- | --- |
| 全体バックアップ | `prime_backup`、`extra_prime_backup`、`quick_backup_multi`、`better_backup`、`permanent_backup`、`zip_backup`、`smart_backup`、`cushion_of_backup` | セーブデータ全体またはサーバーディレクトリ全体を単位にバックアップし保持する |
| 定時バックアップ | `timed_quick_backup_multi`、`auto_backup` | 間隔で自動的に起動し、手動実行を覚えておく必要がない |
| チャンク単位・区域単位のバックアップ | `chunk_backup`、`region_backup` | チャンクや区域を単位にし、全体より細かい粒度 |
| 遠隔地バックアップ | `ftp_backup`、`baidu_netdisk_backup` | バックアップを遠隔のストレージへ送る |

プラグインを選ぶ前後に必ず確認すべき 3 点：

1. **分類はプラグインのディレクトリ名から見た方向にすぎない**。具体的な機能、設定項目、保持ルールは各プラグインの説明に従う。入れたらまずテスト環境で「バックアップ → 復元」を実際に 1 回通す。
2. **プラグインは整合性を代わりに解決してくれない**：どれを使っても、書きかけのセーブデータをコピーしないことを確認する。原則は [バックアップと復元](/tutorials/java/backup) を参照。
3. **バックアップの成果物を同じディスクに残さない**。そうしないと第 4 節と第 6 節で述べる問題がそのまま起きます。

レッドストーン技術サーバーでは、「**定時の全体バックアップ 1 つ + チャンク単位バックアップ 1 つ**」が実用的な組み合わせです：前者が底支え、後者がロールバック範囲をある区域に絞ります。両方を入れるときは時間をずらし、同時にディスクを読み書きしないようにします。

## 3. `Ledger`：まず「何が起きたか」を突き止める

`Ledger` はサーバー側のログ MOD です（loaders：`fabric`、`quilt`；対応バージョン `1.17-rc1` 〜 `26.3`）。

プラグイン系で同種のツールとして最も有名なのは **CoreProtect** です（loaders：`bukkit`、`folia`、`paper`、`purpur`、`spigot`；対応バージョン `1.14.1` 〜 `26.2`；プラグイン系のデータ記録と破壊対策ツールで、ロールバックと復元に対応）。`Ledger` は Fabric エコシステムにおける**CoreProtect に相当するもの**と理解できます：同じくブロックとコンテナの操作を記録し、同じく時間と位置で遡って調べられます。違いは、CoreProtect がプラグイン系で動きロールバックを内蔵するのに対し、`Ledger` は記録と検索だけを担う点です。

これとバックアップは異なる 2 つの問いに答えるもので、互いに代替できません：

| 比較項目 | `Ledger` | バックアップ |
| --- | --- | --- |
| 答える問い | 何が起きたか、誰がやったか、いつ、どこに影響したか | 世界全体をある時点へ戻す方法 |
| データの形態 | イベントの記録 | セーブデータディレクトリの複製 |
| 粒度 | イベント単位。具体的な位置やコンテナまで遡れる | 全体（ディレクトリ単位） |
| 事故のとき最初にすること | 特定と責任の確定。それにより「一部だけ戻す／直せるか」を判断する | 特定できないときの底支え：全体ロールバック |
| 代償 | 記録が増え続けるので保守が必要 | ディスクを食い、ロールバックは同時期の進行をすべて消す |

使用上の注意：

- `Ledger` の位置づけは**記録**であり、復元手段ではありません。「範囲と責任者」を与えてくれますが、実際に世界を戻すのは手作業の修復かバックアップです。
- 記録量は長期的な保守が必要です：MCDR の公式プラグイン一覧に `ledger_cleaner` があり、`Ledger` のデータを掃除する役割です。これは、そのデータが放置していいものではないことも示しています。
- `Ledger` はサーバー側の MOD で、Fabric サーバーが必要です。破壊対策のもう半分（権限とリアルタイムの手段）は [チート対策と破壊行為の防止](/tutorials/java/anticheat) を参照。

**両者の正しい順序は**：事故が起きたらまず `Ledger` で範囲を小さく絞り、部分修理できるなら部分修理する。特定できない、あるいは破壊が広すぎる場合にバックアップで全体を戻す。逆にすると、1 人の行為のために全サーバーの進行を一緒に消すことになります。

## 4. 遠隔地バックアップ：この手順は省けない

ローカルバックアップとサーバーは同じマシンにあるため、以下の場合は**セーブデータとすべてのバックアップを同時に持っていかれます**：

| 状況 | 結果 |
| --- | --- |
| マシン（またはディスク）が壊れた | セーブデータもローカルバックアップも一緒に失われる |
| OS が入れ直された、ディスクがフォーマットされた、ディレクトリを誤って削除した | 同上 |
| マシンが事業者に回収された、データセンターで事故があった | マシン自体を取り戻せないかもしれない |

プラグインの層にはすでに既成の遠隔地の手段があります：`ftp_backup` と `baidu_netdisk_backup` はどちらも**バックアップを遠隔へ送る**プラグインで、つまり遠隔地バックアップのためにゼロからスクリプトを書く必要はありません。

ただし「アップロードできた」は「取り戻せる」と同じではありません。遠隔の認証情報が期限切れにならないか、パスが残っているか、バックアップが完全か、復元できるかを定期的に検証する必要があります。遠隔地の一般的なやり方と保守は [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照。もう 1 点注意：遠隔地バックアップは**同じ経路**で送るので、バックアップ自体がディスク満杯や権限の問題で失敗していれば、遠隔側は静かに 1 部欠けるだけです。ローカルのバックアップログも必ず見てください。

## 5. そのまま実行できるチェックリスト

| 時点 | 行動 |
| --- | --- |
| サーバー構築前 | 定時の全体バックアッププラグインを入れ、バックアップ先を別のディスクに向ける |
| 大規模工事の着工前 | 手動で全体バックアップを 1 つ取り、時点を控える（ロールバック時のアンカー） |
| 設定変更や MOD 追加のたび | 設定とセーブデータをバックアップし、変更後はまず観察してから続ける |
| 平常時 | バックアップの成果物が本当に生成されているかを確認する（ディレクトリとログを見る）。プラグインの読み込み成功だけを見ない |
| 定期的に | 1 部を遠隔へ送る；1 部をテスト環境で展開し復元する |
| 事故のとき | まず `Ledger` で範囲を特定し、部分修理できるなら部分修理、できなければ全体ロールバック |

## 6. バックアップをどこに置くか：3 つの位置

| 位置 | 防げるもの | 防げないもの |
| --- | --- | --- |
| セーブデータの隣、または同じディスク | 手元の誤削除、単一バックアップの破損 | ディスクの故障、フォーマット、ディレクトリ全体の誤削除 |
| 同じマシンの別のディスク | 単一ディスクの故障 | OS の入れ直し、マシン全体の故障、マシンの回収 |
| マシンの外の遠隔地 | マシン全体の故障、誤フォーマット、マシンの回収 | 目立った弱点はないが、取り戻せることを検証してあることが前提 |

よくある誤りはこの表の中に隠れています：

- バックアップディレクトリを `world/` の中に置き、ロールバック時にバックアップごと上書きされる；
- バックアップとセーブデータが同じディスクにあり、ディスクが壊れると両方失う；
- 最新の 1 部だけを保持し、「セーブデータは壊れているがまだ気づいていない」場合に救いがない；
- バックアッププラグインを入れたのにログを一度も見ておらず、事故の日にずっと失敗していたと気づく。

## 7. バックアップは孤立しない：三点セット

装置が強力なほど、**バックアップ + 権限 + クラッシュ防止ルール**の 3 つをまとめて導入する必要があります。それぞれが 1 つの環を担い、どれが欠けても事故の日に露見します：

| 環 | 何を解決するか | どこを見るか |
| --- | --- | --- |
| バックアップ | 事故のあと世界を戻す | 本記事と [バックアップと復元](/tutorials/java/backup) |
| 権限とホワイトリスト | 触るべきでない人が触れないようにする | [チート対策と破壊行為の防止](/tutorials/java/anticheat) |
| クラッシュ防止ルール | アップデート抑制などの操作で、サーバーがそのまま落ちないようにする | [Carpet とそのアドオン](/tutorials/java/sd-carpet) |
