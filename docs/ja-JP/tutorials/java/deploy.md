サーバーがローカルで動くのは、まだ第一歩です。**他人も接続できる**ようになって初めて、本当にサーバーを開いたことになります。この段階の難しさはほぼすべてネットワーク側にあり、Minecraft 自体にはありません。

## 1. 3 つの路線から 1 つ選ぶ

| 方案 | 向いている | 利点 | 代償 |
| --- | --- | --- | --- |
| **クラウドサーバー** | 長期に 24 時間稼働させたい | 公衆 IP があり、安定し、停電や断網を恐れなくてよい | 費用がかかり、構成が良いほど高い |
| **自宅 PC + 公衆 IP** | 家に公衆 IPv4 がある | 追加費用なし、性能を制御できる | 電気代／騒音／停電・断網。しかも**多くの家庭回線には公衆 IPv4 がない** |
| **トンネリング（frp など）** | 家に公衆 IP がない | 回線を変えずに開ける | 転送の層が 1 つ増え、遅延と安定性はトンネルサービス次第 |

:::warn まず公衆 IPv4 があるか確認する
IPv4 アドレスは枯渇しており、**多くの家庭回線では事業者の大規模 NAT 配下のアドレス**が割り当てられます。この場合、ルーターのポートマッピングをどう設定しても無駄です。判定方法：ルーターの WAN 側 IP と「自分の公衆 IP」の検索結果が**一致しない**なら、公衆 IPv4 はありません。

公衆 IP がない場合の選択肢：事業者に申請する（地域によって無料・有料・不可）、クラウドサーバーに変える、トンネリングを使う。
:::

## 2. クラウドサーバーの路線

1. **マシンを買う**：「サーバー構築のプロトコルと推奨構成」に従って選び、**シングルコアの周波数**を重視。OS は Ubuntu / Debian の Server 版。
2. **環境を整える**：「環境準備（Windows と Linux）」に従って対応バージョンの Java を入れ、専用ユーザーとディレクトリを作る。
3. **ポートを開放**：セキュリティグループで `TCP 25565` を開放し、OS のファイアウォール（ufw / firewalld）でも開放する。**両方必要**。
4. **サーバーをアップロード**：SFTP か `scp` でサーバーディレクトリ全体を転送。
5. **起動して常駐**：systemd で管理し、起動時の自動開始とクラッシュ時の再起動を実現（「環境準備」のステップ 5 を参照）。
6. **検証**：**別のマシン**から `あなたの公衆IP:25565` に接続。

## 3. 自宅 PC の路線

1. **公衆 IPv4 を申請・確認**（上記）。
2. **ルーターのポートマッピング**：外部の `25565` を、内網のそのマシンの `25565`（TCP）へ転送。
3. **内網 IP を固定**：このマシンにルーターで静的 IP を割り当て、再起動で IP が変わってマッピングが無効になるのを避ける。
4. **OS のファイアウォール**で `25565` を開放。
5. **落ちないようにする**：電源オプションを**スリープしない**にし、停電と断網のリスクも考える。

## 4. トンネリングの路線（frp）

原理：**公衆 IP を持つマシン**（frps サーバー）でポートを開き、流量を自宅の内網マシン（frpc クライアント）へ転送します。よくあるのは、最も安いクラウドサーバーを 1 台借りて frps にする方法です。

```ini
# frps.ini（公衆 IP のあるサーバーに置く）
[common]
bind_port = 7000
```

```ini
# frpc.ini（自宅の内網マシンに置く）
[common]
server_addr = あなたの公衆サーバーIP
server_port = 7000

[minecraft]
type = tcp
local_ip = 127.0.0.1
local_port = 25565
remote_port = 25565
```

起動順：先に `frps`、次に `frpc`。あとはプレイヤーが**公衆サーバーの IP:25565** に接続すれば入れます。

:::tip 既成のトンネルサービスも使える
ノードを自分で維持したくないなら、商用のトンネルサービスも使えます。手軽ですが通常は流量／帯域の制限があり、**品質もまちまち**です —— 選ぶときはまず **TCP** に対応しているかを見てください（UDP は通常追加料金。統合版やクロスプレイでのみ必要）。
:::

## 5. ドメイン（任意だが推奨）

ドメインがあればプレイヤーは IP を覚えなくて済みます：

- **A レコード**：`mc.あなたのドメイン.com` → サーバーの公衆 IPv4。
- **SRV レコード**：プレイヤーのポート入力を省きたいなら、SRV で `_minecraft._tcp` を実際のポートへ向けられます。これでプレイヤーはドメインだけ入れれば入れます。

注意：**中国国内のサーバーでドメインを解決するには通常 ICP 登録が必要**で、海外のサーバーは不要です。

## DNS と SRV レコード

前節で「ドメインがあればプレイヤーは IP を覚えなくて済む」と書きましたが、実際にそれを支えるのは DNS レコードです。この節では、サーバー構築で使うレコード種別、SRV の正確な書き方、切り分け方法をまとめて説明します。

### サーバー構築で使ういくつかのレコード

| レコード種別 | 役割 | 例 | 注意点 |
| --- | --- | --- | --- |
| `A` | ドメイン → IPv4 アドレス | `mc.example.com` → `203.0.113.10` | 最も基本の 1 条。同じ名前で複数の A レコードを持てる |
| `AAAA` | ドメイン → IPv6 アドレス | `mc.example.com` → `2001:db8::10` | サーバーに IPv6 がある場合のみ必要。プレイヤーが IPv6 でつながらないときはまずここを見る |
| `CNAME` | 別名。別のドメインを指す | `mc.example.com` → `node1.example.net` | **同じ名前で他のレコードと共存できない**：CNAME があれば A / AAAA / TXT などは置けない。ルートドメインでも通常は不可 |
| `SRV` | あるサービスがどのホストのどのポートにあるかを宣言 | `_minecraft._tcp.example.com` | Java 版専用。後述 |
| `TXT` | テキストレコード。検証や宣言によく使う | `_acme-challenge.example.com` の検証値 | ドメイン所有権の検証やメール設定でよく使う。サーバー構築自体には直接影響しない |

**TTL** は各レコードのキャッシュ時間で、単位は秒です。「レコードを変えてから世界中が新しい値を見るまでどれだけかかるか」を決めます。普段は大きめ（`3600` など）で構いませんが、**移行を計画したら先に TTL を小さく**（`300` など）し、古い TTL が切れてから切り替えると、問題が出たときに素早く戻せます。移行の完全な手順は [サーバー移行](/tutorials/ops/server-migration) を参照。

### SRV レコードとは何か

Minecraft の既定ポートは `25565` です。サービスが別のポートで動いている、あるいは別のマシンにある場合、プレイヤーは `mc.example.com:25566` のようにポート付きのアドレスを入力する必要があります。**SRV レコードはそのポートを省くためのもの**です：クライアントに「このドメインに対応する Minecraft サービスは実はどのホストのどのポートにあるか」を伝え、プレイヤーはドメインだけで入れます。

Java 版の SRV 問い合わせ名は固定で `_minecraft._tcp.<あなたのドメイン>` です。ゾーンファイルに書くとこうなります：

```dns
; プレイヤーは mc.example.com を入力、サービスは実際には node1.example.com の 25566 ポートで動作
_minecraft._tcp.example.com.  3600  IN  SRV  10 5 25566 node1.example.com.
node1.example.com.            3600  IN  A    203.0.113.10
```

4 つの数値フィールドの意味：

| フィールド | 例 | 意味 |
| --- | --- | --- |
| `priority` | `10` | 優先度。**数値が最小のものが優先**。優先度が同じレコード同士でのみ負荷を分け合う |
| `weight` | `5` | 重み。優先度が同じ場合のみ有効で、比率で分配され、数値が大きいほど選ばれやすい |
| `port` | `25566` | **サービスが実際に待ち受けるポート**。25565 ではない |
| `target` | `node1.example.com.` | サービスが実際にあるホスト名。**それ自体が解決できなければならない** |

`target` には 2 つの厳格な要件があります：ホスト名でなければならず、通常は `A` / `AAAA` レコードを指すべきです。CNAME を指してはいけませんし、CNAME が CNAME を指すのはなおさら駄目です。

:::warn target に IP リテラルは書けない
`target` に IP（例：`SRV 10 5 25566 203.0.113.10.`）を入れるのはプロトコル上**無効**で、クライアントはそのレコードを使いません。一部のパネルが入力を受け付けるとしてもです。正しいやり方は、対象ホストに `A` / `AAAA` レコードを作り、`target` をそのホスト名に向けることです。
:::

:::warn 最もよくある誤り：target の末尾のドットを落とす
多くの DNS 事業者のコンソールでは、`target` は**末尾のドット付き**の完全修飾ドメイン（`node1.example.com.`）で書く必要があります。このドットを落とすと、コンソールは「現在のゾーンからの相対名」と解釈し、`node1.example.com.example.com.` になってしまいます —— レコードは書いただけ無駄で、しかも**エラーは一切出ません**。
:::

### 統合版は SRV に対応しない

この点は明確にしておきます：

- **Java 版のクライアントは `_minecraft._tcp` の SRV レコードを問い合わせる**ので、Java のプレイヤーはドメインだけで入れます。
- **統合版のクライアントは SRV レコードを使わない**。統合版のプレイヤーは `ホスト:ポート`（例：`mc.example.com:19132`）を入力するか、正しいアドレスへ直接解決されポートも一致するドメインを使う必要があります。

つまり SRV は **Java 版専用の便利機能**です。両方のバージョンを同時に提供するとき、1 条の SRV ですべてのプレイヤーを片付けようと考えないでください —— 統合版側はポートを書く必要があります。

### レコードが本当に効いているかの検証

```bash
# SRV レコードを問い合わせる（Linux / macOS）
dig +short SRV _minecraft._tcp.example.com

# SRV レコードを問い合わせる（Windows、または dig のないマシン）
nslookup -type=SRV _minecraft._tcp.example.com

# A レコードを問い合わせる
dig +short A example.com
```

- `dig +short SRV` は通常 `10 5 25566 node1.example.com.` のような 4 段の内容を返します。空ならレコードが効いていない、名前が間違っている、あるいは権威サーバーに問い合わせていないかのいずれかです。
- さらに `dig +short A node1.example.com` で **target 自体が解決できる**ことを確認 —— この手順が最も抜けやすいです。
- 最後に**クライアントで実測**：ゲーム内でサーバーを追加し、ドメインだけを入れて、クライアントが自分でポートを補って接続できるか見ます。

DNS の変更は即座には効かず、古い TTL の期限切れを待つ必要があります。切り分けではまず `dig @ns1.example.com ...` で権威サーバーに直接問い合わせ、レコードが正しく書けていることを確認してからキャッシュの期限切れを待ちます。**SRV の誤りが最も厄介なのは「エラーが出ない」こと**です：クライアントはつながらないとしか示さず、SRV に問題があるとは教えてくれません。

### よくある故障の対照表

| 現象 | 原因 | 確認方法 |
| --- | --- | --- |
| IP ではつながるがドメインではつながらない | SRV の `target` が解決できない、または `port` が間違い | `dig +short SRV _minecraft._tcp.あなたのドメイン`、さらに `dig +short A` で target を確認 |
| つながるが別のサーバーに入る | レコードが古い、または変更後に TTL の期限切れを待っていない | `dig` の結果と実際の IP / ポートを比較。必要なら TTL を下げてから変更 |
| 統合版のプレイヤーが短いアドレスで入れない | 統合版は SRV 非対応 | `ホスト:ポート` を入力させるか、直接接続用のドメインを別に用意する |
| レコードを足したのに変化がない | TTL がまだ切れていない、またはゾーンを間違えて変更（`example.com` を変えたがプレイヤーは `mc.example.com` を引いている等） | 権威サーバーに直接問い合わせる。レコードが正しいゾーンにあるか確認 |
| 名前解決は正常なのにつながらない | DNS は問題なく、ファイアウォールかセキュリティグループが開放されていない | 外部のマシンから `telnet ドメイン ポート` か `nc -vz ドメイン ポート` で試す |

### プロキシとパネルの追加レコード

- 手前に **Velocity / BungeeCord プロキシ**を置く場合、SRV の `target` は**プロキシ**のアドレスを指し、`port` はプロキシの待ち受けポートを書きます。バックエンドのサブサーバーではありません。
- **パネル**（MCSManager、Pterodactyl など）を使う場合、パネルのアクセス先は別の話です：通常は独立したサブドメイン（`panel.example.com` など）とリバースプロキシが必要で、**ゲーム用の SRV レコードとは互いに影響しません**。同じレコードに混ぜないでください。
- 事業者やデータセンターによっては追加の検証レコード（`TXT`、`CNAME`）を求められることがあります。指示に従って追加してください。

## 6. 公開前のセキュリティチェックリスト

- [ ] `online-mode` は `true` のまま（リスクを明確に理解している場合を除く）
- [ ] コンソール / RCON ポート（`25575` など）を**絶対に公衆へ露出させない**
- [ ] Linux では**root でサーバーを動かさない**。専用ユーザーを使う
- [ ] ホワイトリストか入場審査を設定済み（公開前に小規模でテスト）
- [ ] **自動バックアップ**を有効化済み（「バックアップと復元」を参照）
- [ ] **破壊対策／記録系プラグイン**を導入済み（「プラグイン」と「チート対策」を参照）
- [ ] 外部のマシンからポートの到達性を検証済み
