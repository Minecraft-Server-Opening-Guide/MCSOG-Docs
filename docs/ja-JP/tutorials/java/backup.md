**バックアップはサーバー構築で唯一省略できないことです。** ハードウェアは壊れ、事業者は逃げ、プレイヤーは荒らし、プラグインはセーブデータを書き壊します。いざというとき、他のものは作り直せても、セーブデータが失われたら本当に終わりです。

## 1. 何をバックアップするか

| 必要性 | 内容 |
| --- | --- |
| 必須 | `world/`、`world_nether/`、`world_the_end/`（**セーブデータ本体。最も重要**） |
| 必須 | `plugins/`（プラグイン本体と設定）、`mods/`（MOD サーバーの場合） |
| 必須 | `server.properties`、`ops.json`、`whitelist.json`、`banned-*.json` |
| 必須 | コア固有の設定（`bukkit.yml` / `spigot.yml` / `paper-*.yml` / 該当コアの yml） |
| 任意 | `logs/`、`crash-reports/`（任意だが、切り分けに役立つ） |
| 不要 | `libraries/`、`versions/`、`cache/`（自動再生成できるのでバックアップ不要） |

## 2. 最も重要な原則：バックアップは「一貫」でなければならない

**サーバーがセーブデータを書き込んでいる最中にコピーしないでください**。書き込み途中のチャンクファイルを控えてしまい、復元後にセーブデータが壊れます。

正しい方法は 2 つです：

**方法 A：ホットバックアップ（停止しない）**

```
save-all        先把数据刷到磁盘
save-off        关闭自动保存（避免备份过程中继续写入）
（此时执行复制/打包）
save-on         备份完恢复自动保存
```

**方法 B：停止してからバックアップ（最も確実）**

```
stop            安全关服
（复制/打包整个目录）
（重新启动）
```

:::tip 定時バックアップのスクリプトには方法 A がおすすめ
定時処理と組み合わせ、閑散時間に「`save-all` → `save-off` → アーカイブ → `save-on`」を実行すれば、プレイヤーはほとんど気づきません。
:::

## 3. 自動化

**Linux（cron）**：バックアップスクリプトを書いて（アーカイブ + 日付で命名 + 古いアーカイブの削除）、`crontab -e` で定時実行します。

**Windows（タスクスケジューラ）**：起動スクリプトを「バックアップスクリプト」に作り替え、タスクスケジューラで毎日決まった時刻に実行します。

**プラグインによる方法**：専用のバックアッププラグインもあり、一定間隔で自動バックアップし、数世代の履歴を保持できます。自分でスクリプトを書く手間が省けます。**注意**：プラグインによるバックアップも一貫性の確保が必要で、**バックアップファイルは同じディスクに置かない**でください。

## 4. 保持の方針

- **複数の世代を残す**：最新の 1 つだけ残すと、「セーブデータが壊れていることにまだ気づいていない」ときに手遅れになります。**日次で数日分 + 週次で数週分**を残すことをおすすめします。
- **ディスクに注意**：ワールドのファイルは増え続けます。**定期的に古いバックアップを削除**し、ディスクを満杯にしないでください（満杯になるとサーバーがセーブデータを書き込めなくなり、深刻な結果を招きます）。
- **1 つは遠隔地に**：内蔵ディスクが壊れれば、ローカルのバックアップも一緒に失われます。

:::warn 事業者は逃げ、データセンターでも事故は起きる
すべてのデータを借りているマシン 1 台だけに置くのは、運命を他人に預けるのと同じです。**少なくとも定期的に、バックアップを自分の PC か別の保存先へダウンロード**してください。
:::

## 5. 復元（ロールバック）の手順

1. **サーバーを停止**（必ず先に `stop`）。
2. **現在のセーブデータを改名して残す**（例：`world_broken_20261004`）。**そのまま削除しない**でください。新しいバックアップにも問題があった場合に戻せます。
3. バックアップを展開し、`world*` をサーバーディレクトリへ戻す。
4. サーバーを起動し、ログにセーブデータ関連のエラーがないか確認する。
5. プレイヤーに、重要な建造物やアイテムが正常か確認してもらう。

## 6. 最後にひとつ

> **復元を検証していないバックアップは、バックアップとは言えない。**

定期的に（例えば月 1 回）、バックアップを**テスト環境で実際に復元**してください。多くの人は、本当に事故が起きた日に初めて気づきます：バックアップスクリプトはとっくに権限やパスの問題で失敗していた、あるいは出力されたファイルが空だった、と。
