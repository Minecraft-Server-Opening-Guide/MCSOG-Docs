プラグインサーバーと MOD サーバーは別の世界です。プラグインはサーバーに「外付け」で機能を足し、プレイヤーはバニラのクライアントで入れます；MOD はゲームのコード自体を書き換えるため、**ほとんどのコンテンツ系 MOD はサーバーとクライアントに同じものを入れる必要があり**、プレイヤーが入れなければ入れません。

本記事では MOD サーバーをゼロから起動できるところまで説明します：ローダーの選択、サーバーの導入、クライアントの整合、MOD の配置、不一致の切り分け、そして MOD サーバー特有の性能、バックアップ、更新の問題。「プラグインサーバーと MOD サーバーのどちらにするか」で迷っているなら、まず [サーバーコアの選択](/tutorials/java/core) を読んでください。

## 1. プラグインサーバーと MOD サーバーの違い

| 比較項目 | プラグインサーバー（Paper / Purpur など） | MOD サーバー（Fabric / NeoForge など） |
| --- | --- | --- |
| 拡張の方法 | プラグインがサーバーの提供する API を呼ぶ。ゲーム本体は変えない | MOD がゲームのコードを直接書き換える |
| プレイヤー側に導入が必要か | 不要。バニラのクライアントでよい | 多くは**同じローダー + 同じ MOD 一式**が必要 |
| 典型的な内容 | 管理、ミニゲーム、経済、領地保護 | 新しいブロック、アイテム、モブ、装置、ディメンション |
| 更新の速さ | コアの更新が速く、プラグインも追随する | 遅い。各 MOD 作者次第 |
| 調整できる項目 | コア設定 + プラグイン設定が非常に豊富 | 少ない。主に MOD 自体と JVM |
| 問題が出たときの切り分け | プラグイン一覧とプラグイン設定を見る | **MOD 一覧が完全に一致しているか**とクラッシュログを見る |

**遊びの中身が欲しいなら MOD、管理機能が欲しいならプラグイン**。両者を混ぜる方案（ハイブリッドコア）は存在しますが、互換性と保守コストがどちらも高く、初心者が最初に手を出すものではありません。

### 1.1 3 種類の MOD：クライアント専用 / サーバー専用 / 両側必須

MOD は「入れたら効く」ものではありません。まずどれに属するかを見分けないと、必ずつまずきます：

| 種類 | 典型的な例 | どこに入れるか | 間違えるとどうなるか |
| --- | --- | --- | --- |
| **クライアント専用（client-only）** | レンダリング系（Sodium など）、ミニマップ、シェーダー関連、UI 強化 | クライアントだけ | サーバーに入れると通常は即エラーかクラッシュ。多くのローダーは読み込みを拒否する |
| **サーバー専用（server-only）** | サーバーでのみ効くロジック／性能系 MOD、一部の管理系 MOD | サーバーだけ（両側に入れられる MOD もあるが、クライアントに入れる意味はない） | クライアントに入れても通常は落ちないが、サーバーのハンドシェイクで拒否されることがある。サーバーに欠けると機能自体が存在しない |
| **両側必須（both-required）** | 新しいブロック、アイテム、モブ、ディメンション、新機構を追加するコンテンツ系 MOD | クライアント + サーバーの両方 | どちらかが欠けると接続が拒否されるか、レジストリの不一致でエラーになる |

もう 1 種類、間にあるものがあります：**両側に入れられるが必須ではない**もの（メモリ最適化、ネットワーク最適化など）。この類の配布ページには「任意」と明記されています。

### 1.2 ある MOD がどの種類かを見分ける方法

**MOD 自身の配布ページと説明**を優先します。信頼度の高い順に：

| 出所 | 何を見るか |
| --- | --- |
| MOD の配布ページ（Modrinth / CurseForge） | 環境のマーク。Modrinth は現在 `environment` フィールド（`client_only`、`server_only`、`client_and_server` など）を使い、旧来の `client_side` / `server_side` は `required` / `optional` / `unsupported` の値を取る |
| MOD の README / 作者の告知 | 作者は "server-side only"、"client-side only"、"required on both sides" と直接書いていることが多い |
| Fabric の MOD | `fabric.mod.json` の `environment` フィールド：`"*"`（既定、両側）、`"client"`（クライアント）、`"server"`（独立サーバー。シングルの統合サーバーは含まない） |
| NeoForge の MOD | `META-INF/neoforge.mods.toml` のメタデータ、およびコード内でクライアント専用読み込みと記された入口（`dist = Dist.CLIENT` など） |
:::warn プラグインサーバーの経験を MOD サーバーに持ち込まない
- `spigot.yml`、`paper-world-defaults.yml`、Bukkit プラグイン一式は MOD サーバーには**存在しません**。プラグインサーバーのチュートリアルどおりに MOD サーバーを調整しても無駄です。
- MOD サーバーは既定では**Bukkit プラグインを入れられません**（入れるならハイブリッドコアで、別の方案になります）。
- プラグインサーバーの JVM 引数、最適化プラグイン、ホットリロードの習慣はそのまま真似できません（第 10 節）。
- 逆も同じです：MOD サーバーの経験をプラグインサーバーに当てはめないこと。
:::

## 2. ローダーを選ぶ：Fabric / NeoForge / Forge

| ローダー | 位置づけ | 向いている人 |
| --- | --- | --- |
| **Fabric** | 軽量、起動が速い、新バージョンへの追随が速い。ローダー本体と API が分離 | 性能と迅速な更新を重視し、MOD が最適化系 + 少数のコンテンツ系中心 |
| **NeoForge** | Forge の血統を現代バージョンへ継承したもの。機能 API がより充実 | 現代バージョンの大型コンテンツ MOD パック、機械／技術系の遊び |
| **Forge** | 老舗ローダー。歴史的な MOD パックと旧バージョンで今も広く使われる | 古い MOD パックを動かす、または Forge でしか保守されていない旧 MOD に依存する必要がある |

**バージョンの状況は見極める必要があります**：ローダーが「どの Minecraft バージョンに対応するか」は時間で変わります。本記事では具体的な数字を挙げず、判断方法だけを示します：

- Fabric：公式ダウンロードページでゲームバージョンとローダーバージョンを同時に選べ、ページがダウンロードと起動コマンドを直接示します。Fabric の公式ドキュメントには 1.14 以降のすべての正式版（および 18w43b 以降のスナップショット）に対応すると書かれています。
- NeoForge：公式サイトのトップページが Minecraft バージョンごとに対応するインストーラーのファイルを示し、公式ドキュメントがサーバーへの導入手順を提供しています。
- Forge：公式ダウンロードページがバージョンごとに latest / recommended のビルドを並べ、今も複数のバージョン（比較的新しいものも含む）向けに公開しています。ただし新バージョンの MOD エコシステムはかなりの部分が NeoForge へ移っています。

> **当サイトから直接ダウンロードできます** —— ローダー本体（Fabric / NeoForge / Forge）は **[リソースダウンロード · サーバーコア](/downloads/core)**、MOD 本体は **[リソースダウンロード · MOD](/downloads/mods)**、最終的にプラグインサーバーにするならプラグインは **[リソースダウンロード · プラグイン](/downloads/plugins)** を参照。「ダウンロード」ボタンを押して案内に従いログインしてください。3 か所とも公式およびコミュニティ由来のダウンロードリンクで、**当サイトはファイルを一切保存していません**。
:::note ローダー同士は基本的に互換しない
同じ MOD は通常 1 つのローダーしか対応しません。Fabric の MOD を NeoForge サーバーに入れることはできず、逆も同じです。つまり**ローダーを選ぶことは「入れたい MOD がどちら側にあるか」を選ぶこと**：まず配布ページで目的の MOD がどのローダー、どのゲームバージョンに対応するか確認し、それから何を入れるか決めます。
:::

判断の順序の目安：

```
まず遊びを決める（どの MOD が欲しいか） → それらの MOD が対応するローダーとゲームバージョンを調べる
  → 交点が最も大きいローダー + ゲームバージョンを取る → そのうえでサーバーを入れる
```

## 3. サーバー側にローダーを導入する

インストーラーの画面とファイル名はバージョンで変わるため、以下では**汎用の流れ**だけを扱います。各手順の正確なやり方はローダーの公式ドキュメントを優先してください。

### 3.1 まず Java のバージョンを確認する

| Minecraft のバージョン | 必要な Java |
| --- | --- |
| 1.16.5 以前 | 8 |
| 1.17.2 | 16 |
| 1.18.2 – 1.20.4 | 17 |
| 1.20.5 以降 | 21 |

Java のバージョン違いは「インストーラーが開かない／サーバーが起動しない」の最もよくある原因です。まずこれを除外してください。

### 3.2 汎用の流れ

1. サーバーのルートディレクトリにする空のディレクトリを作る。
2. ローダーの公式ダウンロードページで Minecraft バージョンとローダーバージョンを選び、インストーラー（`.jar`）をダウンロード。
3. インストーラーを実行し、**サーバー（Server）**の導入方式を選ぶ。コマンドラインでは通常 `--installServer` 引数を付けます。
4. インストーラーは**起動スクリプトまたは起動用 jar**（および実行に必要なライブラリディレクトリ）を生成します。
5. **まず 1 回起動**。初回起動で `eula.txt`、`server.properties`、`mods/`、`config/`、`logs/` などが生成され、EULA 未同意のため終了します。
6. `eula.txt` を開き、`eula=false` を `eula=true` に変更（Minecraft EULA への同意を表明）。
7. **もう一度起動**し、正常に起動してコンソールにエラーがないことを確認。
8. ここで初めて `mods/` に MOD を入れ、再起動します。

### 3.3 Fabric

- 公式のサーバーダウンロードページ（fabricmc.net の server ページ）でバージョンを選ぶと、ダウンロードコマンドと起動コマンドが示されます。ページに表示される**ファイル名と起動コマンド**のとおりに実行してください。
- インストーラーには Server タブがあり、ローカルでサーバー用ランチャーを生成します。
- ほとんどの Fabric MOD は **Fabric API** を必要とします。これも MOD なので `mods/` に入れます。

```bash
# 公式ページにはこのようなダウンロードと起動コマンドが示されます。実際の表示を優先してください
# 1) サーバー用ランチャーをダウンロード
# 2) 初回起動
java -jar <サーバー起動ファイル名> nogui
```

### 3.4 NeoForge

NeoForge の公式ドキュメントが示す流れ（21.x 系を例に）：

```bash
# 1) インストーラーをダウンロード（バージョンは公式サイトを優先）
wget https://maven.neoforged.net/releases/net/neoforged/neoforge/<バージョン>/neoforge-<バージョン>-installer.jar

# 2) サーバーをインストール
java -jar neoforge-<バージョン>-installer.jar --installServer

# 3) 初回起動（EULA で終了する）
./run.sh        # Windows では run.bat
```

要点：

- インストール後に `run.sh` / `run.bat` と **`user_jvm_args.txt`** が生成されます。**メモリを変えるなら `user_jvm_args.txt` を変え、`run.sh` を手で編集しないでください**。
- 初回起動後に `mods` フォルダが現れます。MOD はここに入れます。
- NeoForge の更新は、新しいバージョンのインストーラーで同じコマンドをもう一度実行するだけです。公式が明確に注意しています：**更新前にワールドをバックアップ**。
### 3.5 Forge（旧バージョン / 古い MOD パック）

```bash
java -jar forge-<バージョン>-installer.jar --installServer
```

- 比較的新しい Forge は NeoForge と同様に、`run.sh` / `run.bat` と `user_jvm_args.txt` を生成します。
- さらに古いバージョンは直接起動できる `forge-<バージョン>.jar` を生成し、`java -jar` で起動します。
- 旧バージョンの MOD は Forge でしか保守されていないことが多く、その場合は選択の余地がありません。
:::tip 起動しないときはまずログ
ローダーの導入失敗も MOD のクラッシュも、ログは `logs/latest.log`、`logs/debug.log`、`crash-reports/` にあります。切り分けの考え方は [よくあるエラーとクラッシュの切り分け](/tutorials/faq/errors) を参照。
:::

## 4. クライアント側：プレイヤーも同じ一式を入れる必要がある

MOD サーバーの「入れない」はほとんどがネットワークの問題ではなく、**クライアントとサーバーの MOD 一覧の不一致**です。

プレイヤーの正しい手順：

1. **同じローダー**を入れ、しかも**同じ Minecraft バージョン**であること。
2. **同じ MOD 一式**を入れる（Fabric API など依存もすべて含む）。
3. MOD のバージョンも揃える（第 6 節）。

### 4.1 なぜ一覧が一致しないと入れないのか

サーバーに入るとき、クライアントとサーバーは 1 回「ハンドシェイク」を行い、ローダー情報、MOD 一覧、一部のレジストリ内容を交換します。次のいずれかが起きると拒否されるか、そのままエラーになります：

- サーバーにあってクライアントにない**両側必須**の MOD；
- クライアントにあってサーバーにない同類の MOD；
- 同じ MOD の**バージョン違い**；
- 依存 MOD の欠落。

### 4.2 プレイヤーには何が見えるか

| ローダー | 現れ方 |
| --- | --- |
| NeoForge / Forge | 接続が拒否され、**拒否された MOD を一覧する画面**が出る（コミュニティでは "mod rejections" / 非互換 MOD 画面と呼ばれる）。理由が 1 件ずつ示され、たとえば「サーバーにこの MOD がない」「バージョン不一致」など。具体的な文言と配置はバージョンで変わる |
| Fabric | 読み込み段階で依存が欠けていると、"Incompatible mod set!" のようなエラー画面が出て、ログに欠落／衝突した MOD が並ぶ。Fabric の公式ドキュメントにはクラッシュレポートと依存の上書きに関する専用ページがある |
:::tip プレイヤーがつまずかないようにする工夫
- クライアントの `mods/` を圧縮してプレイヤーに配るか、MOD パックのプラットフォームでクライアントパックとサーバーパックを公開する。
- グループの告知に明記する：ローダー、Minecraft バージョン、ローダーのバージョン、MOD 一覧のバージョン番号。
- サーバー側で MOD を更新したら、**クライアントパックも同期して更新**する。そうしないと古いクライアントは即座に入れなくなる。
:::

## 5. MOD はどこに置くか

> **MOD をどこで探すか** —— 当サイトは Modrinth の MOD エントリを収録しています。**[リソースダウンロード · MOD](/downloads/mods)** を参照し、ローダー（Fabric / Forge / NeoForge / Quilt）とゲームバージョンで絞り込めます。「ダウンロード」ボタンを押して案内に従いログインすれば公式のダウンロードリンクが得られます。置く前に、それが「クライアント専用 / サーバー専用 / 両側必須」のどれかを必ず確認してください（[1.1](#11-三类模组仅客户端--仅服务端--双端必需) を参照）。

| 位置 | 説明 |
| --- | --- |
| サーバーの `mods/` | サーバーが読み込むすべての MOD（`.jar`） |
| クライアントの `.minecraft/mods/` | プレイヤーのクライアントが読み込むすべての MOD |
| `config/` | MOD 自身の設定ファイル。多くは**初回起動後**に生成され、`mods/` の中ではない |
| `defaultconfigs/` | 一部のローダー／MOD パックが「新しいワールドの既定設定」を置くディレクトリ |
:::warn クライアント専用 MOD をサーバーに入れない。逆も同じ
これは MOD サーバーで最もよくあるクラッシュ原因の 1 つです：

- レンダリング／UI 系の**クライアント専用 MOD** をサーバーの `mods/` に入れると、サーバーは起動時にエラーを出し、場合によっては落ちます（サーバーにクライアントのクラスはありません）。
- **サーバー専用 MOD** をクライアントに渡すと、軽ければ無意味、ひどければクラス欠落でクライアントが落ちます。
- **両側必須 MOD** を片側だけ入れると、結果はプレイヤーが接続できないことです。

判断方法は第 1.2 節に戻ります：MOD の配布ページの環境マークと作者の説明を優先してください。
:::

## 6. 三者一致のルール

MOD サーバーが動くかどうかは、3 つが同時に揃うかで決まります：

| 一致させる項目 | 要件 |
| --- | --- |
| ゲームバージョン | サーバー、クライアント、各 MOD がすべて同じ Minecraft バージョンに対応していること |
| ローダーのバージョン | クライアントとサーバーが同じローダーを使い、ローダーのバージョンもできるだけ一致（少なくとも MOD の要件範囲内） |
| MOD のバージョン | 同じ MOD は両端で**同一バージョン**。依存 MOD が存在し、バージョン範囲を満たすこと |

### 6.1 ログから不一致を診断する

| 現象 / ログの手がかり | 意味 | 対処 |
| --- | --- | --- |
| 起動直後にクラッシュし、クラッシュレポートに MOD 名が出る | その MOD が現在のゲームバージョン／ローダーと非互換、または依存が欠けている | 対応バージョンに替える、または依存を補う |
| ログに "missing dependency" / 依存解決の失敗 | MOD が宣言した依存が入っていない、またはバージョンが合わない | ログに従って依存を補う |
| ログに MOD の読み込み失敗、クラスが見つからない | クライアント専用 MOD をサーバーに入れた（またはその逆）ことが多い | 誤った側から外す |
| プレイヤーの接続が拒否され、画面に MOD が並ぶ | 両端の一覧／バージョンが不一致 | 両端の MOD を揃える |
| クラッシュレポートに `Is Modded: Definitely; ... brand changed to 'fabric'/'neoforge'` | 現在が MOD 環境であることを示すだけで、それ自体はエラーではない | さらに下の本当の例外スタックを見る |

依存の意味（Fabric の仕様。NeoForge も同様）：

| 宣言 | 意味 |
| --- | --- |
| `depends` | ハード依存。欠けると即失敗 |
| `recommends` | ソフト依存。欠けても警告のみ |
| `conflicts` / `breaks` | 衝突。該当すればエラー |

### 6.2 どの MOD が悪さをしているか分からないとき

**二分法**を使います（NeoForge 公式ドキュメントが推奨する方法）：

1. 半分の MOD を `mods/` から外す（依存が壊れないよう注意）。
2. 起動して問題が残るか見る。
3. 残る → その半分でさらに二分する。残らない → もう半分を入れ替えて試す。
4. 具体的な MOD を特定するまで繰り返す。

## 7. 性能 MOD（種類別に知る）

MOD サーバーの性能最適化は、設定ファイルの調整ではなく「正しい MOD を入れる」ことが中心です。以下は実在が確認でき、広く使われているものです（ローダーの対応状況は各プロジェクトページによるもので、バージョンで変わります。入れる前にもう一度確認してください）：

| 種類 | MOD | 役割 | ローダー | 備考 |
| --- | --- | --- | --- | --- |
| ゲームロジックの最適化 | **Lithium** | ゲームロジック（スポーン、AI、ブロック挙動など）の性能を最適化し、挙動はできるだけ変えない | Fabric、NeoForge、Quilt | 両側に入れられる。サーバー側の利得が大きい |
| メモリ使用量 | **FerriteCore** | メモリ使用量（ブロックステートなどのデータ構造）を削減 | Fabric、Forge、NeoForge、Quilt | メモリが厳しい MOD サーバーで実用的 |
| ネットワーク最適化 | **Krypton** | ネットワークスタックを最適化し、帯域と CPU のコストを削減 | Fabric | 主にサーバーとマルチプレイ向け |
| ライトエンジン | **Starlight** | ライトエンジンを書き換え、ライトの性能と不具合を修正 | Fabric | プロジェクトはアーカイブ済みで、対応は 1.20.4 まで。説明にも 1.20 ではバニラとの差がすでに小さいとある。**新しいバージョンに無理に入れない** |
| チャンクのプリ生成 | **Chunky** | 事前にチャンクを生成し、プレイヤーが走り回るときのラグを減らす | Fabric、Forge、NeoForge、および Paper/Spigot など | 長期運営のサーバーではほぼ必須 |
| クライアントのレンダリング | **Sodium** | クライアントのレンダリング最適化（フレームレート向上） | Fabric、NeoForge、Quilt | **クライアント専用**。サーバーには入れない |
:::note 「最適化 MOD」に関する 2 つの規律
- **機能が重複する最適化 MOD を同時に入れない**（ライトの書き換えが 2 つなど）。互いに衝突する確率が高いです。
- 最適化 MOD はゲーム内部の挙動を変えるため、**レッドストーン技術／精密装置のサーバーでは慎重に**：多少遅くても、装置を動かなくさせないほうがよいです。
:::

## 8. ワールドとデータの互換性：MOD の削除は不可逆

MOD が追加したブロック、アイテム、エンティティ、ディメンション、バイオームは、すべてワールドのセーブデータに書き込まれます。**MOD を外しても、それらの内容に対応するデータはセーブデータに残ったまま、ゲームはもう認識できません**：

- 軽ければ「欠落ブロック／空エンティティ」になり、空気のように見えるがデータは残っている；
- ひどければチャンクの読み込みでエラーになり、セーブデータ自体が開けなくなる；
- **同じ MOD を互換バージョンで入れ直せば**、通常は復旧できる。
:::warn まずバックアップ、それから MOD を触る
- 「MOD を足す、消す、ローダーを替える、ゲームバージョンを替える」どの操作の前にも、**ワールドディレクトリを完全にバックアップ**する（方法は [バックアップと復元](/tutorials/java/backup)）。
- MOD サーバーのセーブデータは**そのまま降格できません**。MOD サーバーのワールドをバニラや低いバージョンで開くのはリスクが非常に高いです。
- 「MOD を 1 つ試しに入れてみたい」？ 必ず**コピー**で試し、本番のセーブデータでは試さないでください。
:::

## 9. MOD サーバー / MOD パックサーバーを安全に更新する

推奨する流れ（順序は省かない）：

1. **バックアップ**：ワールド + `config/` + MOD 一覧。
2. **変更を凍結**：先にサーバーを止めるか、メンテナンス時間内に作業する。
3. **先にローダーを更新**し、1 回起動してサーバー自体に問題がないことを確認（この時点で旧 MOD がエラーを出すのは正常）。
4. **MOD を 1 つずつ更新**。一度に全部入れ替えない。分割して更新すると問題の MOD を特定しやすい。
5. **クライアントパックを揃える**：更新後の `mods/`（クライアント側）を再パッケージして公開。
6. **観察**：起動後に `logs/latest.log` に異常がないか見て、しばらくオンラインで動かしてから TPS とエラーを確認（[パフォーマンス最適化](/tutorials/java/optimize) の方法が使えます）。
7. **ロールバック用パックを残す**：前のバージョンのサーバーディレクトリとクライアントパックを残しておけば、問題が出たときすぐ戻せます。

## 10. メモリと JVM 引数

MOD サーバーとプラグインサーバーはメモリの性格が違います：

| 項目 | プラグインサーバー | MOD サーバー |
| --- | --- | --- |
| ヒープの需要 | 比較的低い | **明らかに高い**：MOD のレジストリ、モデル、レシピ、装置データがメモリを食う |
| 起動時間 | 短い | 長い（数百 MOD なら数分かかるのはよくある） |
| 主なボトルネック | メインスレッド + プラグインの品質 | メインスレッド + MOD の品質 + メモリ／GC |
| 引数の出所 | コア公式ドキュメントの推奨組み合わせ | **ローダー自身の起動ファイルの説明** |

実務的な提案：

- **メモリは十分に、ただし過剰にしない**。ヒープを開きすぎると GC の停止がかえって長くなります。まず実際のプレイヤー数と MOD 規模に応じた妥当な値（小型 MOD サーバーなら 4〜8 GB から始めて段階的に調整）を与え、それから観察します。
- NeoForge / 比較的新しい Forge：`user_jvm_args.txt` を変更する（インストール時に生成され、ファイル内にコメントで説明がある）。`run.sh` を手で編集しないこと。
- その他の起動方式：起動スクリプトで `-Xms` / `-Xmx` によりメモリを指定します。
- **プラグインサーバーの引数の組み合わせをそのまま真似しない**。Paper/Spigot 向けに設計された組み合わせは、異なる負荷と GC の挙動を前提にしています。MOD サーバーではローダーの公式ドキュメントと MOD 作者の説明を優先してください。
- 引数はメモリ／GC 層の問題しか解決せず、**シングルコアのボトルネックは救えず**、ひどく出来の悪い MOD も救えません。

```bash
# 例：メモリ引数を起動スクリプトまたは user_jvm_args.txt に書く
# 具体的な数値はあなたの MOD 規模とプレイヤー数に合わせて調整する
-Xms4G
-Xmx8G
```

## 11. トラブル対応の早見表

| 現象 | よくある原因 | 対処 |
| --- | --- | --- |
| サーバーが起動直後に落ち、ログが特定の MOD を名指しする | MOD のバージョンがゲーム／ローダーと合わない、または依存が欠けている | 対応バージョンに替え、依存を補う |
| 画面／ログに "Incompatible mod set!" や拒否された MOD の一覧 | 両端の MOD 一覧またはバージョンが不一致 | 両端の MOD とバージョンを揃える |
| MOD を消したらワールドに欠落ブロック／エンティティが出た | MOD のデータが残り、ゲームが認識できない | 互換バージョンを入れ直して復旧。**まずバックアップ**し、セーブデータへの書き込みを続けない |
| プレイヤーが入れず、サーバーに目立ったエラーもない | クライアントの MOD／依存の欠落、バージョン違い | プレイヤーに同じクライアントパックを使わせる |
| サーバーは起動するがとても重い | MOD 自体の性能が悪い、エンティティ／装置が多すぎる、メモリ不足 | profiler で特定し（[spark でサーバー性能を分析する](/tutorials/ops/spark)）、的を絞って対処 |
| 起動が MOD の読み込みで長時間止まる | MOD が多い、初回の設定生成、ディスクが遅い | 正常な現象。SSD を使い、気長に待つ |
| クライアント専用 MOD をサーバーに入れた | サーバーにクライアントのクラスがない | サーバーの `mods/` から外す |

## 結び

MOD サーバーの複雑さは「両端が一致していなければならない」という鉄則から来ます：**まず遊びとバージョンを決め、次にローダーを入れ、最後に MOD を足す**。MOD を 1 つ足すたびに 1 回起動し、MOD を触る前に必ずバックアップすれば、手戻りの時間を大きく節約できます。
