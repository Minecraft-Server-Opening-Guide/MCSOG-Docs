「サーバーが重い」は最もよくある問題ですが、**最適化には優先順位があります**。以下の順に進めるのが費用対効果で最も高く、逆順だと大きな労力を使ってほとんど効果が出ません。

## 1. 優先順位

```
1. ハードウェア（シングルコア性能）        ← 効果最大、コストも最大
2. サーバー設定（描画距離／シミュレーション距離）  ← ほぼ無料、即効性あり
3. コアの選択（Paper 系 vs バニラ）
4. プラグイン／MOD の品質（質の悪いプラグインが最大の元凶）
5. JVM 引数
```

**先に結論**：マシンのシングルコアが弱ければ、**設定を変えても引数を調整しても救えません**。メインスレッドは 1 つしかないからです。

## 2. 設定の最適化（最も費用対効果が高い）

### 描画距離とシミュレーション距離

| オプション | 影響 |
| --- | --- |
| `view-distance` | プレイヤーがどこまで見えるか。下げると CPU と帯域を節約できるが、遠くが霧がかる |
| `simulation-distance` | どの距離までのチャンクを**実際に演算するか**（スポーン、レッドストーン、作物）。**描画距離を下げるよりずっと節約でき、見た目にも影響しない** |

多くの小規模サーバーでは、`simulation-distance` を 10 から 6 程度に下げるだけでラグが明らかに緩和されます。

### Spigot 層のエンティティ制御

`spigot.yml` にはエンティティ関連の重要な項目がいくつかあります（バージョンにより名称が多少異なります）：

- **エンティティの有効範囲**：モブがどこまでなら tick されるかを制御します。小さくすると CPU を大幅に節約できます。
- **スポーン範囲**：モブがスポーンする距離を制御します。
- **エンティティ／アイテムのマージ半径**：大きくするとエンティティ数（ドロップアイテム、経験値オーブなど）を減らせますが、**バニラの挙動が変わります**（レッドストーン技術では慎重に）。
- **1 tick あたりの最大エンティティ tick 数**：エンティティの演算に上限を設け、爆発的な増加によるサーバー停止を防ぎます。

### Paper 層のワールド設定

`config/paper-world-defaults.yml` では、エンティティの衝突上限、自動保存するチャンク数、チャンクのアンロード遅延などを調整できます。

:::warn 最適化と「バニラの挙動」はトレードオフ
上記の多くのスイッチは**既定値の時点ですでに最適化されています**。攻めた設定にするほどバニラから離れます。**レッドストーン技術サーバーでは逆に —— バニラの挙動に影響する項目をバニラへ戻してください**（「レッドストーン技術とレッドストーン」を参照）。
:::

## 3. まず「どこが重いか」を見つけてから動く

**勘で最適化しないでください**。まず計測します：

| ツール | 用途 |
| --- | --- |
| **spark** | 現在最も主流の性能分析プラグイン／コマンド。フレームグラフを生成し、どのプラグイン／エンティティ／チャンクが CPU を食っているかを直接示します |
| `/tps` 系のコマンド | 現在の TPS を確認（20 を下回ると tick 落ち） |
| **timings**（旧 Paper） | 旧バージョンでの性能レポート |

spark でしばらくサンプリングし、**フレームグラフで最も幅の広い帯**を見てから的を絞って対処します。よくある原因：

- 質の悪いプラグインがループの中で重い処理をしている；
- エンティティが大量に溜まっている（トラップタワーで回収できていない、ドロップアイテムを消していない）；
- ホッパー／レッドストーン装置が多すぎる（ホッパーは古典的な性能キラー）；
- プレイヤーが走り回って大量の新区画が生成される（下記）。

## 4. ワールドのプリ生成

**プレイヤーが走りながら新区画を生成する**ことはラグの重要な原因です：新区画の生成は CPU を大量に使う処理で、TPS が瞬間的に落ちます。

解決策は**プリ生成**です：`Chunky` などのプラグインで、あらかじめ一定範囲のマップを生成しておきます。プレイヤーがその区域に来たときは既存のチャンクを読み込むだけで、生成は発生しません。

**長期運営のサバイバルサーバー**では、プリ生成はほぼ必須です。

## 5. JVM 引数

- **メモリ**：`-Xmx` は十分に、ただし過剰にしない（大きすぎるとかえって GC の停止が長くなります）。専用機では `-Xms` と `-Xmx` を揃えてヒープの伸縮を減らせます。
- **GC 引数**：コミュニティに成熟した推奨の組み合わせがあります（**Aikar's Flags** など）。Paper の公式ドキュメントには起動引数の生成ツールと説明があります。**ネット上で矛盾する「オカルト引数」を盲目的に真似しないでください**。
- 引数は**メモリ／GC の層**でしか助けにならず、**シングルコアのボトルネックは救えません**。

## 6. その他の実用的な手段

- **定期的なエンティティの掃除**：ドロップアイテムや経験値オーブに妥当な寿命を設定します。定時掃除を行うプラグインもあります。
- **TNT／高頻度レッドストーンの制限**：公開サーバーでは、爆発と高頻度レッドストーンを制限すると悪意あるラグ攻撃を大きく減らせます。
- **走り回りの制限**：ワールドボーダーで活動範囲を制約し、無限の生成を避けます。
- **定期的な再起動**：「最適化」ではありませんが、一部のプラグインのメモリリークを解消できます。**一時的な緩和**としては有効です（対症療法）。
- **ハードウェアの増強**：spark で CPU がメインスレッドに食い尽くされ、設定もチューニング済みなら、**シングルコアの強いマシンに替えるべき**です。

## 7. 最適化の一線

```
最適化は「バニラの挙動」を犠牲にしてはいけない —— バニラの挙動が不要だと明確に言える場合を除いて
```

レッドストーン技術サーバー：**多少重くなっても、装置が動くことを優先**。
一般的なサバイバルサーバー：**適度に攻めてよい**。オンラインでの体験を優先します。

## 結び

ここまでで、Java 版のサーバー構築の全行程が終わります：

```
プロトコルと設定 → OS → 環境準備 → サーバーコアの選択 → サーバーの起動
   → サーバーの構成 → サーバーの設定 → デプロイ → よく使うコマンド
   → MCDR → プラグイン → レッドストーン技術
   → 運用管理 → プロキシ → スマホのプレイヤー → バックアップ → チート対策 → パフォーマンス最適化
```

ある段階を見返したいときは、左の目次から該当する章に戻ってください。コア選定の項目別の対照は [サーバーコア比較](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7) を参照。
