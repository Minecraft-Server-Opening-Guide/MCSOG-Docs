レッドストーン技術サーバーの「最適化」は普通のサーバーの最適化とは別物です：普通のサーバーは描画距離を下げ、コアを替え、最適化プラグインを入れて TPS を上げられますが、レッドストーン技術サーバーではスイッチを 1 つ動かすたびに「これはバニラの挙動を変えないか」を先に問う必要があります。本記事が答えるのは**レッドストーン技術サーバーで実際に動かせるスイッチは何か、動かしたあと誰が再検証するのか**です。

汎用の性能最適化（優先順位、描画距離とシミュレーション距離、JVM 引数）は [パフォーマンス最適化](/tutorials/java/optimize)、最適化 MOD の選定は [最適化 MOD](/tutorials/java/sd-optimize)、Carpet のルールとアドオンの完全な一覧は [Carpet とそのアドオン](/tutorials/java/sd-carpet) を参照。本記事は設定層の取捨選択だけを扱い、**具体的な設定フィールド名と既定値は一切書きません** —— それらはバージョンで変わるため、各公式ドキュメントを優先する必要があります。

## 1. レッドストーン技術サーバーの 3 層のスイッチ

| 層 | 典型的な例 | 変えるとどうなるか |
| --- | --- | --- |
| Carpet のルール | `optimizedTNT`、`lagFreeSpawning`、`movableBlockEntities` | 性能を節約するだけのものもあれば、**バニラの挙動を直接変える**ものもある |
| 最適化 MOD の設定 | `ferrite-core`、`modernfix`、`c2me-fabric`、`async` | それぞれ別の部分を担う。間違えるとラグやバグを持ち込む、あるいはタイミングが変わる |
| サーバー自身の設定 | 描画距離、シミュレーション距離の類 | 汎用の最適化。[パフォーマンス最適化](/tutorials/java/optimize) を参照 |

3 層で最もつまずきやすいのは第 1 層です：**Carpet のルール名はどれも「最適化」に聞こえますが、性質はまったく違います**。そこでまずこれを分解します。

## 2. Carpet のルール：「純粋な最適化」と「挙動の変更」を切り分ける

Carpet は Fabric サーバー MOD で、ルールシステムを提供し、`/carpet <ルール名> <値>` でバニラの細かい挙動をオン／オフします。ルールの数は少なくなく、レッドストーン技術サーバーで本当に気にするのは通常以下です：

| ルール | 性質 |
| --- | --- |
| `optimizedTNT` | 純粋な最適化 |
| `lagFreeSpawning` | 純粋な最適化 |
| `fastRedstoneDust` | 純粋な最適化だが、レッドストーンに関わるので変更後は装置を再検証する |
| `maxEntityCollisions` | 上限系の調整。エンティティが密集したときの挙動が変わる |
| `movableBlockEntities` | **バニラの挙動を変える**：本来なかった能力を与える |
| `commandTick` | デバッグの入口。最適化項目ではない |
| `tntDoNotUpdate` | **バニラの挙動を変える**。テストのみ |
| `explosionNoBlockDamage` | **バニラの挙動を変える**。テストのみ |

性質別に段階を分けて扱います：

| 段階 | ルール | どう使うか |
| --- | --- | --- |
| 常時オンでよい | `optimizedTNT`、`lagFreeSpawning` | まずテストサーバーでオンにし、装置とスポーンが普段どおりか観察してから本番へ |
| 変更後に再検証 | `fastRedstoneDust`、`maxEntityCollisions` | 変更記録に書き、技術班に通知し、装置は各自で再検証する |
| バニラの挙動を変える。必要に応じてオン | `movableBlockEntities` | バニラにない能力を与えるので、オンにする前に「ピストンがブロックエンティティを押せない」ことに依存した装置がないか確認する |
| テストサーバーでのみオン | `tntDoNotUpdate`、`explosionNoBlockDamage` | **本番ではオンにしない**。用途はテストと実験 |
| ツール類 | `commandTick` | デバッグの入口であり、最適化項目として常時オンにしない |

:::warn ルールを変えたら告知する
プレイヤーは「装置が壊れた」のが自分のせいなのか、ルールが変わったせいなのか区別できません。**変更のたびに記録を残し告知する**：何を、いつ変え、どの種類の装置に影響するのか。この規律は、どのルールをオンにするかより重要です。
:::

## 3. 最適化 MOD の設定：それぞれ別の部分、1 回に 1 項目

最適化 MOD の設定項目はほとんどが**別々のサブシステム向け**なので、まず各 MOD がどの部分を担うかを知ってから、どれを動かすか決めます：

| MOD | 担う方向 |
| --- | --- |
| `ferrite-core` | メモリ使用量 |
| `modernfix` | 多合一：性能、メモリ、同時にバグ修正も |
| `c2me-fabric` | チャンクの性能 |
| `async` | エンティティのマルチスレッド |
| `spark` | 計測ツール（profiler）。最適化 MOD ではない |

**本記事では具体的な設定フィールド名と既定値を意図的に書きません**：これらの MOD のオプションはバージョン間で変わり、コピーしてきたフィールド名がすでに存在しないことがあり、既定値をそのまま真似すると挙動を変えてしまう可能性のほうが高い。調整するなら各 MOD 自身の公式説明で調べてください。

設定変更の規律は 4 つだけですが、どれも省けません：

1. **変更前に設定ファイルをバックアップする**（原則とやり方は [バックアップと復元](/tutorials/java/backup)）—— 設定を壊しても、少なくとも前の版に戻せます。
2. **1 回に 1 項目だけ変え**、変えたらしばらく観察する。5 項目同時に変えると、事故のときどれが原因か分かりません。
3. **`spark` で変更前後を比較する**。データで語り、「速くなった気がする」で判断しない。
4. **まずテストサーバーかテストワールドで検証する**。特に `c2me-fabric`、`async` のようなチャンクとマルチスレッドに関わる項目。

:::tip マルチスレッドはタイミングを変える
`c2me-fabric` と `async` が加速するのはチャンクとエンティティの処理で、マルチスレッドは本質的に実行順序とタイミングを変えます。そして装置はまさにタイミングに敏感です。何が欲しいかを明確に分かっていて、再検証のコストを負担する覚悟があるときだけ動かしてください。
:::

## 4. バージョン差異：設定一覧もバージョンに追随させる

「万能の最適化設定」でバージョンをまたげるものはありません。必ず覚えておくべき 2 つの例：

| MOD | 変化 | 結論 |
| --- | --- | --- |
| `memoryleakfix` | 公式 README の説明：Minecraft `1.20.5+` 以降、これが以前修正していたメモリリークはすべて公式に修正済みで、この MOD は新しいバージョンでは**すでに不要** | 新しいバージョンで「最適化」のために入れるのはやめる |
| `starlight` | 対応バージョンは `1.20.4`（Fabric）まで；公式 README の説明では `1.20` ではバニラとの差はすでに小さく、しかも**侵襲的**なライトエンジンの書き換えで他の MOD と衝突しやすい | 新しいバージョンの設定一覧に載せ続けるべきではない |

したがって、ゲームバージョンを上げる、MOD を上げる、コアを替えるたびに、次のことを照合し直します：**この一覧の各項目は、現在のバージョンでまだ存在するか、まだ意味があるか**。すでに不要な項目を設定に残しても通常はエラーにならず、静かに場所を占めて互換性のリスクを増やすだけです。

## 5. 変更の優先順位リスト

順番にやると費用対効果が最も高く、逆順だと装置を壊して原因も分からなくなります。

```text
1. 先にベースラインを測る：spark でサンプリングし、正常時の TPS / MSPT を記録する
2. 次に「純粋な最適化」項目：optimizedTNT、lagFreeSpawning、およびメモリ系最適化 MOD の設定
3. 続いて上限と範囲の調整：maxEntityCollisions の類。変更後は装置で再検証する
4. 最後にタイミングを変える項目：c2me-fabric、async のようなチャンクとマルチスレッドに関わる設定
5. バニラの挙動を変えるルール（tntDoNotUpdate、explosionNoBlockDamage）はテストサーバーでのみ使う
```

これに伴うやり方は「**変更前にバックアップ、1 回に 1 項目、記録を残す、プレイヤーに告知**」です。レッドストーン技術サーバーの設定管理は、本質的に**バージョン管理**です：変えているのは 1 つの数字ではなく、すべての装置の動作前提です。

## 6. 4 つのよくある誤り

| よくあるやり方 | 問題 |
| --- | --- |
| 目についた最適化項目を一度に全部オンにする | 問題が出たときどれが原因か特定できず、全部オフにしてやり直すしかない |
| 他人の最適化設定をコピーしてそのまま使う | バージョン、MOD の組み合わせ、装置がすべて違う。他人がオンにできても自分もできるとは限らない |
| 「速くなった気がする」を結論にする | ベースラインがなければ比較にならない。まず `spark` でサンプリングしてから判断する |
| ルールを変えて記録も告知もしない | 装置が壊れても誰も原因を知らず、技術班はバグとして調査するしかない |

ある変更を残す価値があるかの判断基準は 1 つだけです：**データがより良いことを示している**こと。「みんなそうしている」ではありません。
