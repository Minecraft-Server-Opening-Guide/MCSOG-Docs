チート対策は普通のサバイバルサーバーでは加点要素ですが、レッドストーン技術サーバーではしばしばマイナスになります。理由は「チート対策が使い物にならない」からではなく、**レッドストーン技術のプレイヤーの正常な遊び方が、それ自体で継続的にチート対策の判定を引き起こす**からです。

さらに直接的な事実があります：公式の Carpet 自体が `antiCheatDisabled` というルールを提供しています（移動が速すぎるとプレイヤーが引き戻されるのを防ぐ役割）。公式がルールシステムにこのスイッチを用意しているということは、レッドストーン技術サーバーに本当に必要なのは**バニラの高速移動に対する引き戻し検知を切ること**であり、判定をもう一層足すことではない、ということです。

本記事は結論と代替案だけを扱います：なぜ衝突するのか、誤判定はどこから来るのか、チート対策を入れないなら何をすべきか。[チート対策と破壊行為の防止](/tutorials/java/anticheat) は汎用の 2 層防御と設定方法を扱っており、本記事ではそれらを繰り返しません。

## 1. 公式が出している逆方向のシグナル

まず最も説得力のある事実を挙げます。

| ルール | 意味 |
| --- | --- |
| `antiCheatDisabled` | これを切ると、移動が速すぎてプレイヤーが引き戻される現象が起きなくなる |

このルールは一句ずつ読む価値があります：

- 扱っているのは「**移動が速すぎて引き戻される**」という 1 点、つまりバニラの高速移動に対する検知です。ここでいう「検知」はバニラ自身の挙動であり、第三者のチート対策ではありません。
- これが存在するということは：**レッドストーン技術サーバーに本当に必要なのは、バニラのこの引き戻し検知を切ること**であり、その上にさらに判定を重ねることではない、ということです。

## 2. 正常な遊び方がなぜ判定を引くのか

レッドストーン技術のプレイヤーの日常的な操作は、判定ロジックから見るとほぼすべて異常信号です：

| レッドストーン技術の遊び方 | 判定ロジックから見た姿 |
| --- | --- |
| 高速移動（エリトラ、氷の道、トロッコ、ピストンの射出などの移動手段） | 速度超過の移動、位置の不連続 |
| 大量のエンティティ（トラップタワー、TNT の列、ドロップアイテムと経験値オーブの堆積） | 異常なエンティティ挙動と異常な密度 |
| 装置と自動化（飛行装置、連射装置、無人での長時間稼働） | 高頻度・反復・人手の操作と一致しない動作 |

鍵は「継続」の 2 文字です：たまたま判定に引っかかるのではなく、**遊び方そのものが長期的に判定の境界に沿って進む**のです。結果は 2 種類の損失になります：

1. **誤判定が装置とテストを直接中断させる**：引き戻され、動作をキャンセルされ、キックされる。1 回のテストが無駄になることがあります。
2. **誤判定は再現できない**：装置が壊れた原因は通常特定が難しく、さらに移動と操作にランダムに介入する判定が重なると、調査コストは倍増します。

:::warn 本記事では具体的な判定しきい値には触れない
チート対策ごとに実装としきい値は異なり、ここでは列挙も比較もせず、特定の製品の評価もしません。判断すべきは**論理上の衝突**です：「人間の正常な操作」を基準にした判定が、「人間の操作の上限を突破する」ことを目的とした遊び方に出会えば、衝突は必然です。
:::

## 3. どちら側に入れるか、代償は何か

チート対策は通常**プラグイン系または最適化コア**への導入を要求します。問題は、最適化コア自体がバニラの挙動を変えることであり、この 2 つはレッドストーン技術の目的と直接衝突します：

| 衝突点 | 説明 |
| --- | --- |
| プラットフォームの衝突 | チート対策は主にプラグイン系のエコシステム向けで、レッドストーン技術のツールチェーン（Carpet とそのアドオン）は Fabric 上にある |
| 挙動の衝突 | 最適化コアの既定設定自体がバニラの挙動から外れており、装置が動かない、あるいは出力が不安定になる |
| 目的の衝突 | チート対策は「異常を制限する」、レッドストーン技術は「異常を利用する」。方向が逆 |

コア選定と最適化コアの取捨選択は [サーバーコアの選択](/tutorials/java/core) を、プラグイン系でなぜ項目ごとにバニラの挙動へ戻す必要があるかは [レッドストーン技術とレッドストーン](/tutorials/java/redstone) を参照。本記事では結論を 1 つだけ：**方向が逆の部品は、入れても互いに打ち消し合うだけ**です。

## 4. チート対策を入れないなら、何を入れるか

逆に問うほうが役に立ちます：**結局何を防ぎたいのか？** この問いを分解すれば、それぞれの種類にチート対策より確実な手段があります：

| 防ぎたいこと | 使うべき手段 | 説明 |
| --- | --- | --- |
| 見知らぬ人の狼藉 | ホワイトリストと権限 | 敷居を入場前に置くほうが、事後の判定よりはるかに安い |
| 破壊と窃盗 | `ledger` の記録と遡及 | サーバー側の記録 MOD で、プラグイン系の CoreProtect に相当する |
| 最悪の事態 | 定期バックアップと遠隔地バックアップ | 事故のときに全体をロールバックできる。最後の防衛線 |
| 人肉シールドマシン（プレイヤーによる高速掘削）、自動岩盤破壊の類 | `playerOperationLimiter` | 1 gt あたりプレイヤーは 2 ブロックの設置、1 ブロックの即時破壊ができ、この 2 操作は 1 gt に 1 種類のみ。人肉シールドマシンとプレイヤーの自動岩盤破壊 MOD の対策 |

補足：

- **ホワイトリストと権限**：レッドストーン技術サーバーは通常身内の輪であり、「誰が入れるか」を制御するほうが、サーバー内でリアルタイムに判定するよりはるかに有効です。権限を分けて設定する考え方は [領地と保護](/tutorials/java/protection) を参照。
- **記録と遡及**：`ledger`（プラグイン系の CoreProtect に相当）は記録系のツールで、リアルタイムの遮断はしませんが、**「誰が、いつ、何をしたか」に答えられます**。記録がなければ、対処の根拠すらありません。
- **バックアップ**：定期バックアップと遠隔地バックアップは「それまでの対策がすべて失敗した」場合に備えるものです。完全な戦略と復元手順は [セーブデータの保護](/tutorials/java/sd-backup) を参照。
- **`playerOperationLimiter`**：これは**サーバー側の制限手段**で、サーバー自身に作用し、プレイヤーに何も入れさせる必要がない点に注意してください。制限するのは 1 gt あたりの設置と破壊の操作で、狙いは自動化の濫用であり、正常なプレイヤーを採点することではありません。Carpet のアドオンプロジェクトが提供するルールなので、**導入前にゲームバージョンと MOD の組み合わせで使えるか確認**してください。

## 5. どうすべきか：前向きなチェックリスト

「チート対策を入れるな」を繰り返し論証するより、そのまま実行するほうが早いです：

1. **まず入場の敷居**：ホワイトリストか入場審査で、流入元を制御します。
2. **次に権限の階層化**：一般プレイヤー、技術班、管理権限を分け、OP を気軽に渡さない。誰が装置に触れられるか、誰が高リスクの操作を使えるかを事前に明記します。
3. **記録ツールを入れる**：`ledger` などの記録 MOD は早く入れるほどよい。導入後に起きたことしか記録できないからです。
4. **バックアップを整える**：定期バックアップに遠隔地バックアップを加え、**復元手順を 1 回実際に演習する** —— 検証していないバックアップはバックアップではありません。
5. **リアルタイム判定の代わりにサーバー側の制限を使う**：たとえば `playerOperationLimiter` のように、サーバー自身で効き、プレイヤーのクライアントに依存しない手段。
6. **ルールを明文化する**：何が許され、何が禁止され、どう対処するかを、プレイヤーが見える場所に書きます。
7. **バニラの引き戻し検知が必要なときは `antiCheatDisabled` で切る**：公式のルールシステムが用意したスイッチで、第三者の部品を入れるより制御しやすく、プレイヤーへの説明も容易です。

## 6. 本記事の一線

```
1. 公式が antiCheatDisabled を用意している —— レッドストーン技術サーバーに必要なのはバニラの引き戻しを切ることで、層を足すことではない
2. レッドストーン技術の正常な遊び方は継続的に判定を引く。誤判定は必然で、偶発ではない
3. チート対策はプラグイン系／最適化コアに入れるもので、レッドストーン技術の目的と方向が逆
4. 代替案：ホワイトリストと権限 + ledger の記録 + 定期の遠隔地バックアップ + サーバー側の制限
```
