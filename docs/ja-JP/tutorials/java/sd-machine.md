ワールドイーター（world eater）は TNT アレイと飛行装置を組み合わせたマシンで、区域をまとめて空にするために使います。「ゲートカッティング」はコミュニティがアップデート抑制（update suppression）系の操作を指す通称です。この 2 つは、レッドストーン技術サーバーでサーバーを直接落としやすい遊び方の代表です。

**本記事はリスク管理だけを扱い、作り方は扱いません。** 作り方は確認済みの範囲にないうえ、ネットに流れている図面や手順があなたのバージョンで成立する保証もないため、ここでは書かず、復唱もしません。

まず境界をはっきりさせます：ワールドイーターに直接関係する公式 Carpet のルールは 3 条だけで、うち 2 条はバニラの挙動を変えるため本番ではオンにしません。本当に事前に用意すべきなのはクラッシュ防止ルールで、しかも**先にルール、あとで装置**です。

## 1. ワールドイーターとは、リスクはどこにあるか

ワールドイーターのやり方は、TNT アレイで爆破を続け、飛行装置で構造全体を平行移動させながら地形を空にしていくものです。産出は「くり抜かれた区域」、コストはサーバーで最も高くつくいくつかのものです：大量の TNT エンティティ、まとまった爆発計算、破壊されたブロックによる膨大なブロック更新、そして常に動き続ける飛行装置。

| リスク | 発生源 |
| --- | --- |
| TPS が落ちる | 同一時刻に大量の TNT エンティティと爆発計算が存在する |
| セーブデータと帯域の負荷 | 1 回の稼働で広い区域を書き換えるため、ブロック更新量が膨大 |
| 無人で暴走する | 装置は飛行装置で自走するため、問題が起きても人がいるとは限らない |
| 操作自体が境界を越える | アップデート抑制（「ゲートカッティング」）は隣接更新スタックを埋め、その結果サーバーがクラッシュしうる |

別の角度から見ると、同じ装置がプレイヤーと運営者にとって逆の意味を持ちます：

| 役割 | ワールドイーターの意味 |
| --- | --- |
| プレイヤー | 広い空き区域を効率よく得る生産ライン。産出は自分のもの |
| 運営者 | 1 区域の全量のブロック変更 + 継続的な高負荷 + クラッシュリスク 1 つ |

つまりワールドイーターは「作れるかどうか」ではなく、「事故のあと収拾できるか」の問題です。

## 2. ワールドイーターに直接関係する公式ルール

Carpet は `/carpet <ルール名> <値>` でバニラの細かい挙動をオン／オフします。ワールドイーターに直接関係するのは以下の 3 条だけです：

| ルール | バニラの挙動への影響 |
| --- | --- |
| `optimizedTNT` | 爆発の効果自体は変えず、同位置と液体中の爆発をより省資源にするだけ |
| `tntDoNotUpdate` | **バニラの挙動を変える**：TNT を動力源の隣に置いても更新されなくなる |
| `explosionNoBlockDamage` | **バニラの挙動を変える**：爆発がブロックを破壊しなくなる |

使い方の基準：

- `optimizedTNT` が説明するのは**同位置・液体中**の爆発のラグが小さいことで、ワールドイーターのような「同じ区域を繰り返し爆発させる」場面に意味があります。最適化するのはコストであり、効果ではありません。
- `tntDoNotUpdate` と `explosionNoBlockDamage` は**バニラの挙動を変える**ため、テストや特定の場面だけで使います。本番ではオンにしない —— `tntDoNotUpdate` は「動力源の隣に TNT を置く」遊び方を無効にし、`explosionNoBlockDamage` は爆発の破壊力をそのままなくすので、装置が区域を空にする能力自体が失われます。

:::warn バニラの挙動を変える 2 条はテスト環境だけのもの
`tntDoNotUpdate` と `explosionNoBlockDamage` はテストサーバーで構造を検証する、無害なデモをするといった用途に向き、**本番には向きません**。これらをオンにして測った装置の挙動と、実際に公開したあとの挙動は別物です。
:::

## 3. 「ゲートカッティング」の正確な定義

**「ゲートカッティング」はコミュニティが「アップデート抑制（update suppression）」系の操作を指す通称です。** 特定のブロックや特定の装置ではなく、アップデート抑制という現象を利用する技巧の一類全体を指します。

公式 Carpet はこれに制御された入口を与えていて、ルール名は `updateSuppressionBlock` です：**バリアブロックの上にアクティベーターレールを置くと、レールが向きを変えるときに隣接更新スタックを埋めます。**

ここで必ず覚えておくべき点が 2 つあります：

1. これは**公式が提供する制御された入口**であり、つまりこの事柄自体は追加の MOD なしでサーバー側からオン／オフできます。
2. その帰結は「隣接更新スタックを埋める」という一句に書かれています —— 隣接更新スタックが埋まることが、まさにクラッシュリスクの源です。

## 4. なぜ先にクラッシュ防止をオンにするのか

アップデート抑制の仕組みは**隣接更新スタックを埋める**ことです。埋まったあとに起きることはあなたの装置では制御できません：**その結果サーバーがクラッシュしうる**のです。

これが順序の問題の答えです。「先に装置を動かし、落ちてからルールを探す」人が多いですが、クラッシュは毎回穏やかに収拾できるものではありません —— サーバーが落ちる瞬間、書き込み中のチャンクと稼働中の装置の状態が完全であるとは限りません。だから正しい順序は：

```
1. 先にクラッシュ防止ルールを入れる（本節）
2. そのあと装置を入れ、プレイヤーに作業を開始させる
```

確認できたクラッシュ防止ルールは以下で、出所別に 2 組に分けます。ルール名と選択できる値は [Carpet とそのアドオン](/tutorials/java/sd-carpet) ですでに一覧として挙げたので、**ここで補うのは使用順序**です：

| 出所 | ルール | 選択できる値 |
| --- | --- | --- |
| Carpet AMS Addition | `amsUpdateSuppressionCrashFix` | `false` / `true` / `silence` |
| Carpet AMS Addition | `customBlockUpdateSuppressor` | `none` / `minecraft:bone_block` / `minecraft:diamond_ore` / `minecraft:magma_block` |
| Carpet TIS Addition | `yeetUpdateSuppressionCrash` | 該当バージョンの MOD の説明を参照 |
| Carpet TIS Addition | `updateSuppressionSimulator` | 該当バージョンの MOD の説明を参照 |

いくつか補足：

- `amsUpdateSuppressionCrashFix` は**3 状態のスイッチ**です：`false` と `true` は一般的なオフとオン、`silence` は 3 つ目の扱い方です。3 つそれぞれの正確な意味は MOD の公式説明を優先し、ここでは定義しません。
- `customBlockUpdateSuppressor` の役割は**指定したブロックをアップデート抑制ブロックに変える**ことで、選べる値は上表のブロックです。
- Carpet TIS Addition の `yeetUpdateSuppressionCrash` と `updateSuppressionSimulator` がカバーするのは**別の 2 つの方向**です：1 つはクラッシュ処理、1 つはシミュレーション。両者の具体的な挙動と利用できる値は、該当バージョンの MOD の説明を優先します。

:::tip ルールが本当に効いているのを確認してから装置を動かす
クラッシュ防止ルールは「入れたら永久に安全」ではなく、1 層の受け止めです。やり方は：**設定したらまず自分でアップデート抑制を 1 回起こして挙動を見る**。ルールが想定どおりに止めていることを確認してから、プレイヤーに装置を触らせてください。
:::

## 5. バージョン差異：新しいバージョンではコミュニティ MOD で復元する

必ずそのまま書くべき事実があります：**公式のバージョンはアップデート抑制を修正済み**です。つまり新しいバージョンで同種の操作をするには、コミュニティが提供する復元・補助 MOD が必要で、それぞれカバーするバージョン帯が異なります：

| MOD | loaders | カバーするバージョン帯 |
| --- | --- | --- |
| `update-depression` | fabric、quilt | 1.19.4–1.21.1 |
| `better-update-suppression` | fabric | 1.21.10–26.2 |
| `suppressed` | fabric | 26.1.1–26.2 |
| `lithonate` | fabric | 1.16.5 のみ |

この表の正しい読み方：

- これは「どれか 1 つを選ぶ」一覧ではなく、**4 つがそれぞれ異なり、重ならないバージョン帯**です。まずゲームバージョンを決め、そのバージョンがどの帯に入るかを見ます。
- `suppressed` と `better-update-suppression` の帯はいずれも 26.x 付近、`update-depression` は古めの 1.19.4 から 1.21.1、`lithonate` は 1.16.5 のみです。
- **バージョンを変えたら、この選択はやり直しになります。** 装置が動くか、どの MOD を入れるかはバージョンが前提で、「アップグレードしてもそのまま使える」とは考えないでください。

## 6. 三点セット：バックアップ、権限、クラッシュ防止ルール

装置が強力なほど、この 3 つは省けません。それぞれ当サイトの 3 記事に対応します：

| 事項 | 役割 | 詳細 |
| --- | --- | --- |
| **バックアップ** | サーバー落ち、誤操作、装置の暴走のあと、直前の使える状態に戻れる | [セーブデータの保護](/tutorials/java/sd-backup) |
| **権限** | 誰が装置に触れ、誰がアップデート抑制のような高リスク操作を使えるかを決める | [領地と保護](/tutorials/java/protection) |
| **クラッシュ防止ルール** | アップデート抑制のような操作を「サーバーを落としうる」から制御可能な範囲へ押し戻す | 本記事第 4 節 |

装置の挙動に直接関わる読み物をもう 1 つ：装置がなぜ壊れるか、なぜ遅いかは、tick モデルと同一 tick 内の更新順序に依存します。[レッドストーン技術とレッドストーン上級](/tutorials/java/redstone-advanced) を参照。

## 7. 本記事の一線

```
1. 公式ルールは 3 条だけ：`optimizedTNT` は残してよい。残り 2 条はバニラを変えるので本番ではオンにしない
2. ゲートカッティング = アップデート抑制のコミュニティでの通称。公式の制御された入口は `updateSuppressionBlock`
3. 先にクラッシュ防止ルール、そのあと装置 —— 順序を逆にするとセーブデータを賭けることになる
4. 新しいバージョンで同種の操作をするなら、まずバージョンで復元・補助 MOD を選ぶ
```
