サーバーのプラグインは増える一方です。`plugins/` に jar を放り込むのは簡単ですが、面倒なのはそのあとです：あるプラグインを上げたい、あるプラグインが問題を起こしたので一時的に止めたい、ある jar がどうも怪しい。本記事は 3 つを扱います：標準的な導入・更新・削除の流れ、ホットリロードツールの能力の境界、そしてあるプラグインに手が加えられているかを見分ける方法。

まだプラグインを入れたことがないなら、まず [プラグイン入門](/tutorials/java/plugins) を読むことを勧めます。

## 1. 導入・更新・削除の標準的な流れ

### 導入

1. 入手元が信頼できるか確認し（第 5 節）、ついでにバージョン番号とダウンロード元を控える。
2. **サーバーを停止**。多くのプラグインは初回読み込みでホットロードに対応していません。
3. `plugins/` ディレクトリをバックアップ。[バックアップと復元](/tutorials/java/backup) を参照。
4. `.jar` を `plugins/` に入れる。
5. サーバーを起動してコンソールを観察。読み込みの成功も失敗もここに出ます。
6. `plugins` コマンドで読み込み状態を確認。
7. そのあと設定を変え、変更後はサーバーのバニラ `/reload` ではなく、プラグイン付属の `reload` サブコマンドを優先する。

### 更新

更新は導入より事故が起きやすいです。新バージョンで設定の構造が変わっている可能性があるからです。

| 手順 | 要点 |
| --- | --- |
| 更新ログを読む | 設定形式の変更がないか、手動で移行すべきデータがないか確認 |
| バックアップ | 少なくとも `plugins/<プラグイン名>/` を、データベースに関わるならデータベースも |
| 旧 jar を残す | 旧バージョンを `.jar.bak` に改名して残し、新バージョンが正常と確認してから削除 |
| 停止して差し替え | 使用中の jar をオンラインで上書きしない |
| 再起動して検証 | コンソールを見て、`plugins` で状態を確認 |
| 大きなバージョン飛び | メジャーバージョンをまたぐ（1.20 から 1.21 など）ときは、中間バージョンを先に経る必要があることがある |

### 削除

削除は「jar を消す」だけではありません。

1. サーバーを停止。
2. jar を移動する。
3. データディレクトリは**すぐには消さず**、まず `<プラグイン名>.bak` に改名してしばらく観察する。
4. 他のプラグインがこれを前提として依存していないか確認し、あればまとめて対処する。
5. 権限プラグインに残した権限ノードを整理する。
6. それが登録した定期タスク、独自コマンド、スコアボード項目を整理する。
7. ワールドに残した独自アイテムやブロックに注意する。プラグインが欠けるとエラーになることがあります。

:::warn 削除はクリーンアップではない
jar を消すのは「読み込み」の段階を片付けただけです。データディレクトリ、権限ノード、データベースのテーブル、他のプラグインからの依存は、すべてそのまま残っています。
:::

## 2. ホットリロードツール：PlugManX と ServerUtils

この類のツールは通常**プラグイン管理プラグイン**と呼ばれ、サーバーが稼働したまま他のプラグインを読み込み・アンロード・リロードできます。

### PlugManX

老舗のプラグイン管理ツールで、前身は PlugMan。現在はコミュニティが維持する PlugManX が更新を続けています。

| 項目 | 情報 |
| --- | --- |
| 配布ページ | SpigotMC リソース 88135 |
| ソース | GitHub の Test-Account666/PlugManX（旧版は ryan-clancy/PlugMan） |
| よく使うサブコマンド | `load`、`unload`、`reload`、`list`、`info`、`check` |
| 典型的な使い方 | `/plugman <サブコマンド> <プラグイン名>` |

具体的なサブコマンド名と引数はバージョンで変わるため、プラグイン付属のヘルプを優先してください。

### ServerUtils

| 項目 | 情報 |
| --- | --- |
| 配布ページ | SpigotMC リソース 79599、Modrinth |
| ソース | GitHub の frankheijden/serverutils |
| 対応プラットフォーム | Spigot、BungeeCord、Velocity |

プラグイン管理のほかに、サーバー状態の表示などのツールも付属します。プロキシにも対応しているため、グループサーバーではプロキシ層で一括管理でき、バックエンドごとに 1 セット入れる必要がありません。

### ホットリロードの実際の限界

ホットリロードは「再起動不要」ではありません。明確にできないことが一群あります：

| 状況 | ホットリロードで解決できるか |
| --- | --- |
| 設定を変えただけ | プラグイン付属の `reload` で足りる |
| 問題のあるプラグインを一時的に無効化 | できる。これがホットリロードの最も価値ある使い方 |
| プラグインのバージョンを変える（jar を替える） | 勧めない。停止して差し替えるべき |
| プラグインがコマンド、権限、リスナー、レシピ、ワールド生成器、進捗を登録している | アンロード後に残留しやすく、リロードでエラーになりやすい |
| プラグインがサーバーの内部実装（NMS、リフレクション）を直接いじる | ほぼ不可 |
| プラグインがデータベース接続、スレッドプール、大量の静的キャッシュを保持 | アンロードしてもリソースが解放されないことが多い |
| 同じプラグインを繰り返しロード・アンロード | クラスローダーが回収されずメモリが増え続け、最終的に OOM |
| ハイブリッドコアや MOD 系 | プラグイン管理ツールは MOD を扱えない |
| サーバーのバニラ `/reload` | 非推奨。プラグインの状態が壊れやすい |

:::warn 本番サーバーはホットリロードだけに頼らない
ホットリロードは「あるプラグインを一時的に止めて問題が消えるか見る」ことと、設定の素早い試行に向きます。正式なバージョン更新や依存の変更は、やはり停止して再起動する流れで行うべきです。
:::

:::tip 切り分けでの正しい使い方
まずプラグイン管理ツールで直近に入れたプラグインを `unload` し、現象が消えるか観察します。それだと確認できてから正式に停止して対処します。ログを通読するよりずっと速いです。
:::

## 3. バックドア入りプラグインによくある特徴

プラグインはサーバーの権限で動く第三者製のコードで、バックドアを仕込まれるとサーバーを他人に渡すのと同じです。以下の兆候は警戒に値します。

| 兆候 | 具体的な現れ方 |
| --- | --- |
| 権限とコマンドが不自然 | `plugin.yml` に機能と無関係な高危険度コマンドが宣言されている。自分に OP を付与する、任意コマンドを実行する、任意ファイルを読み書きするなど |
| コードが難読化されている | クラス名が意味のない 1 文字や `a/b/c` 構造。パッケージ全体が暗号化され、独自クラスローダーで実行時に復号して読み込む |
| 不審な実行時呼び出し | 子プロセスの起動（`ProcessBuilder`、`Runtime.exec`）、外部への能動的な通信（`URL.openConnection`、HTTP リクエスト）、`ops.json` の直接改変、リフレクションによる遠隔クラスの読み込み |
| 「アップデータ」を装う | 自動更新を称し、実際には作者自身のサーバーからファイルをダウンロードして自身を上書きする |
| 出所が不明 | フォーラムの添付、クラウドストレージ、グループのファイル共有で転送された jar |
| 「無料の高級プラグイン」 | 有料プラグインをクラックして再パッケージしたもので、クラックした人物がついでに何かを足しているのが常 |
| 上流と一致しない | プラグイン名とバージョンは同じなのに、ファイルサイズやハッシュが合わない。`plugin.yml` の作者や URL が書き換えられている |
| 無害な名前の隠れた設定 | 既定で有効な `metrics`、`telemetry`、`update-check` などの項目が、実際には外部へデータを送っている |

:::warn プラグイン名だけで判断しない
バックドア入りのプラグインは、有名プラグインの名前とバージョンをそのまま騙ることがよくあります。判断材料はファイル名ではなく、ファイルの出所と実際の中身であるべきです。
:::

## 4. 安全なダウンロード元

| チャネル | リスク |
| --- | --- |
| SpigotMC、Modrinth、Hangar、Bukkit Dev などの主要配布プラットフォーム | 低。優先して選ぶ |
| 作者自身の GitHub Releases | 低。リポジトリの所有者を確かめること |
| 有料プラグインの公式購入ページ | 低。「代行購入」を買わないよう注意 |
| まとめダウンロードサイト、ミラーサイト | 中。二次パッケージの可能性があり、ファイルのハッシュ確認を勧める |
| フォーラムの添付、クラウドストレージ、グループのファイル共有 | 高 |
| 中古売買サイトの「無料の高級プラグイン」 | 極めて高。最も危険な地域 |

判断基準は実は単純です：**作者本人が公開した、照合できるあのファイルまでたどれるか**。あるプラグインがいくつのサイトに載っているかは、安全であることの証拠になりません。

:::tip 必要なものだけ入れる
プラグインが少ないほど攻撃面が小さく、切り分けも容易です。機能が重複するプラグインは 1 つで十分です。
:::

## 5. あるプラグインを疑ったときの切り分け手順

1. **現象を記録**：いつ始まったか、コンソールに何が出ているか、プレイヤーから異常の報告があるか。
2. **まずバックアップ**：何かに触る前に完全なバックアップを取る。`plugins/` とワールドデータを含める。
3. **容疑者リストを作る**：直近 24〜72 時間に追加または更新されたプラグイン。
4. **二分探索で特定**：サーバーを停止し、容疑者の半分を無効化して再起動して観察。現象が消えれば無効化した半分に、消えなければ残りの半分にいる。
5. **単独で再現**：1 つのプラグインまで絞ったら、プラグイン管理ツールでそれだけ `unload` し、現象が再現するか確認。
6. **静的スキャン**：第 6 節の方法で jar を一通りスキャン。
7. **`plugin.yml` を人手で確認**：`author`、`website`、`main`、`commands`、`permissions` を公式版と比較。
8. **クラスファイル一覧を見る**：jar を展開し、意味のないクラス名と、上表の不審な呼び出しに注意。
9. **ハッシュを照合**：公式からダウンロードしたファイルとサイズ・ハッシュを比較。
10. **悪意を確認したらインシデント対応の流れへ**。

緊急対応チェックリスト：

- `ops.json` と `whitelist.json` が改変されていないか、見知らぬアカウントが OP を得ていないか確認する。
- 異常なログイン記録、見知らぬプレイヤーデータファイルがないか確認する。
- すべての認証情報をローテーションする：RCON パスワード、パネルのパスワード、データベースのパスワード、SSH 鍵。
- `plugins/` の下に別の jar が入れられていないか、サーバーコアの jar と起動スクリプトが差し替えられていないか確認する。
- OS 側のスケジュールタスクを確認し、自動起動項目を追加されていないか確かめる。
- コンソールログとプラグインのログを通読し、バックドアが最初に動いた時点を探す。
- 状況に応じてプレイヤーに通知しロールバックする。ロールバック前に現場を保全して分析に使う。

## 6. McGuard で静的スキャンする

McGuard（略称 MCG）は huzpsb 氏によるサードパーティの静的スキャンツールです。**サーバーを起動せずに** `plugins/` 下のすべての jar をスキャンし、疑わしいファイルを見つけられます。

### コンソールモード

MCG の jar をサーバーのルートディレクトリに置き、そのディレクトリで実行します：

```
java -Xmx1G -jar MCG.jar
```

起動するとモードの選択を求められます。通常は `0`（標準モード）で構いません。ほかにエキスパートモードと開発者モードがあります。

スキャン結果の現れ方：

| 状況 | 出力 |
| --- | --- |
| 異常なし | スキャンの過程だけを出力し、結果ブロックは出さない |
| 異常を検出 | 結果ブロックを出力し、重大度と理由の説明を 1 件ずつ示す |

理由の説明は該当した行為の種別を示します。たとえば「権限ビットの設定によって OP を取得する可能性」や「子プロセスの起動によって遠隔コマンドを実行する可能性」などです。

:::warn MCG は報告するだけで、対処はしない
プラグインを変更も削除もしません。自分で手動で整理する必要があります。また、エキスパートモードは既知の悪意あるコードの特徴で照合しコードの意図を分析するため、スキャンを意図的に回避していない大多数のサンプルをカバーしますが、誤検知も残ります。
:::

### プラグインモード

MCG は Bukkit/Spigot のプラグインとして導入し、サーバーの稼働中に継続的に保護することもできます。公式の位置づけの説明は：この保護は相対的なもので、ごく少数の悪意あるプラグインは行為の管理を回避できる。**MCG を入れたからといって、悪意あるプラグインを含むと分かっているサーバーを動かしてはいけない**。

:::warn スキャンは最後の防衛線にすぎない
どんなスキャンツールもすべてのリスクを消せません。正しいやり方は、やはり正規のチャネルからプラグインを入手することです。出所不明のサーバーコアを動かすなら、まずコンソールモードでスキャンし、さらにサンドボックス（Sandboxie など）のような隔離環境で試運転することを勧めます。
:::

## 7. 日常のメンテナンスのすすめ

- 月に 1 回以上はプラグインの更新を確認する。特にバージョン間の互換やチート対策のように、安全と直接関わるプラグインは必ず。
- プラグイン一覧を維持し、名前、バージョン、入手元、ダウンロード元を記録する。問題が出たときに素早く遡れます。
- 本番サーバーとテストサーバーを分け、新しいプラグインはまずテストサーバーでしばらく動かす。
- root や Administrator のアカウントでサーバープロセスを直接動かさない。サーバーには最小限の権限を持つ専用アカウントを与える。
- 作者のリポジトリの issue と告知を追う。プラグインに毒が仕込まれると、通常はコミュニティで先に議論されます。
