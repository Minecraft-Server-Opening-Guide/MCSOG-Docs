これは [レッドストーン技術とレッドストーン](/tutorials/java/redstone) の上級編です。入門編が答えたのは「どのコアを選ぶか」でした。本記事はより実践的な 3 つの問いに答えます：**技術系プレイヤーは結局何を作っているのか、それらの装置はどのサーバー設定に依存するのか、運営者として何を事前に用意すべきか。**

まず本記事の境界を明確にします：ここでは**装置の図面は示さず、特定の設計があなたのバージョンで成立することも保証しません**。レッドストーン技術の最も基本的な事実は —— **装置の可用性は、具体的なゲームバージョンと具体的なサーバー実装に縛られる**ということです。「この装置は永久に有効」という主張は信頼できません。

## 1. レッドストーン技術のプレイヤーは何を作っているのか

技術系プレイヤーの言う「ファーム」（farm）は**自動または半自動の資源生産ライン**を指します：手で掘るのではなく、ゲームの仕組みで産出を得る。まずカテゴリの地図を作り、それから負荷を語ります。

| カテゴリ | 仕組みの要点 | 主な負荷 | バージョン敏感度 |
| --- | --- | --- | --- |
| トラップタワー / ドロップファーム | 自然スポーンやスポナーを利用し、モブを集めて処分する | エンティティ数、AI の経路探索、ドロップアイテムと経験値オーブ、チャンク常時読み込み | 中：スポーン規則、モブ AI、当たり判定の変更が効率に影響する |
| アイテムファーム | ブロック自身の挙動で産出（サトウキビ、竹、サボテン、昆布、ハチミツ、羊毛など） | ブロック更新、ランダム tick、ホッパーとトロッコでの回収 | 中低。ただし回収側のホッパー自体が負荷 |
| 鉄ファーム | 村人と威嚇の仕組み（または襲撃の仕組み）でアイアンゴーレムの生成を誘発 | 村人の AI、作業ブロック（POI）の照会、エンティティ生成、常時読み込み | 高：村人とアイアンゴーレムの生成条件は繰り返し調整されている |
| 金ファーム | ネザーポータルでゾンビピグリン（1.16 で「ゾンビピッグマン」から改名）を出現させ、集めて処分 | ポータルのブロックエンティティ、エンティティ数、ネザーのチャンク常時読み込み | 高：エンティティ名、AI、ポータルの仕組みがすべて変更されている |
| 村人取引ホール | 多数の村人に作業ブロックを持たせ、取引を更新・固定する | 村人の AI、POI、経路探索、チャンク常時読み込み | 中高：取引と職業の仕組みが何度も調整されている |
| 襲撃ファーム | 襲撃を発生させてウェーブを処理し、エメラルドや不死のトーテムを得る | ウェーブ単位で生成されるエンティティ、AI、ドロップアイテム | 高 |
| ウィザースケルトンファーム | ネザー要塞でスポーンさせ、スノウゴーレムやウィザーローズなどで撃破 | 要塞チャンクの常時読み込み、エンティティ、ドロップアイテム | 中高 |
| 木ファーム / 食料ファーム | 自動植栽と伐採（ピストンまたは TNT）、および各種作物ファーム | ランダム tick、ブロック更新、TNT エンティティ、ドロップアイテム | 中 |
| TNT 複製その他の仕組み系ファーム | 複製系の特性で TNT などの本来高価な資源を得る。ピストン、重力ブロック、ポータルなどの境界挙動を利用 | TNT エンティティと爆発、膨大なブロック更新。TPS を直接押し潰しやすい | 極めて高：こうした特性は修正されては再発を繰り返し、多くのサーバーが明確に禁止している |

「産出」ではなく「負荷」で分類するのは、**運営者にとって装置の産出はプレイヤーのもので、装置のコストはサーバーのもの**だからです。以下、種類ごとに説明します。

### 1.1 トラップタワーとドロップファーム

- **仕組み**：暗い場所でモブを自然スポーンさせて集めるか、スポナーで継続的に産出させる。集める手段は通常、水流、ピストンでの押し出し、あるいは別ディメンションへの誘導。
- **負荷**：モブは「考えるエンティティ」で、毎 tick AI、経路探索、衝突判定を行います。ドロップアイテムと経験値オーブもエンティティ枠を占め続けます。
- **運営者の注意**：サーバーを最も遅くしやすい種類の装置です。エンティティ、AI、チャンク、ドロップアイテムの 4 つのコストを同時に消費するからです。

### 1.2 アイテムファーム

- **仕組み**：スポーンに依存せず、ブロック自身の挙動で産出する。サトウキビ、竹、サボテン、昆布、ハチミツ、羊毛など。
- **負荷**：ブロック更新とランダム tick が中心で、産出物はホッパーやトロッコで回収する必要があります。**回収側が生産側より高くつくことがよくあります**。
- **運営者の注意**：`randomTickSpeed` を下げるとこの種のファームは直接遅くなります。ホッパーの搬送間隔（`hopper-transfer`）を大きくすると、すべての回収システムが遅くなります。

### 1.3 鉄ファーム

- **仕組み**：村人と「威嚇」の条件でアイアンゴーレムの生成を誘発する。襲撃の仕組みによる変種もあります。
- **負荷**：村人の AI と作業ブロックの照会は非常に高コストで知られており、さらにチャンクの常時読み込みが必要です。
- **バージョンの注意**：アイアンゴーレムの生成条件、村人の作業と睡眠の判定は何度も変更されており、**この種の装置はほぼメジャーアップデートのたびに再検証が必要**です。

### 1.4 金ファーム

- **仕組み**：ネザーポータルでゾンビピグリン（1.16 でゾンビピッグマンから改名）を出現させ、集めて処分する。
- **負荷**：ポータルのブロックエンティティ、大量のエンティティとドロップアイテム。しかもネザーのチャンクを常時読み込みにする必要があります。
- **バージョンの注意**：エンティティの改名、AI の調整、ポータルの仕組みの変化が産出方法に影響します。

### 1.5 村人取引ホール

- **仕組み**：多数の村人を 1 か所に閉じ込め、作業ブロックで取引を更新し、欲しい取引が出るまで回して固定する。
- **負荷**：村人はサーバー上で最も「重い」よくあるエンティティの 1 つで、経路探索、POI 照会、毎 tick の挙動をすべて計算します。
- **運営者の注意**：取引ホールは鉄ファームや繁殖機と隣接して高負荷の小区域を作りがちです。`tick-inactive-villagers` のような最適化項目は村人の挙動を直接変えます。

### 1.6 襲撃ファーム

- **仕組み**：能動的に襲撃を発生させ、ウェーブごとに生成される襲撃者を処理してエメラルドや不死のトーテムなどを得る。
- **負荷**：ウェーブ生成は短時間に大量のエンティティを作る**突発型**の負荷で、MSPT がなだらかに上がるのではなく急峻なスパイクになりやすいです。
- **バージョンの注意**：襲撃の発生条件、ウェーブの構成、ドロップ表が変更されています。

### 1.7 ウィザースケルトンファーム

- **仕組み**：ネザー要塞の範囲でスポーンさせ、自動手段で撃破と回収を行う。
- **負荷**：要塞チャンクを常時読み込みにする必要があり、エンティティとドロップアイテムが持続的に存在します。
- **運営者の注意**：要塞の構造範囲は限られており、複数のプレイヤーが同時にファームを作るとスポーン枠を取り合います。

### 1.8 木ファームと食料ファーム

- **仕組み**：自動植栽と伐採（ピストンまたは TNT）、および小麦、ニンジン、ジャガイモなどの作物ファーム。
- **負荷**：ランダム tick、ブロック更新、TNT エンティティと爆発。
- **運営者の注意**：TNT 型の木ファームの爆発は大量のブロック更新を生み、**局所的なラグ**のよくある発生源です。

### 1.9 TNT 複製その他の仕組み系ファーム

- **仕組み**：ゲーム内の複製系の特性で TNT などの本来高価な資源を得る。あるいはピストン、重力ブロック、ポータルなどの境界挙動を利用する。
- **負荷**：TNT エンティティと爆発、まとまったブロック更新。大規模な複製装置 1 台で TPS が 1 桁まで落ちます。
- **運営者の注意**：こうした特性は**公式に修正されては再発を繰り返し**、具体的な挙動は完全にバージョンに縛られます。同時に**多くのサーバーがルールで明確に禁止**しています。性能の問題であると同時に公平性の問題でもあるからです。許可するかどうかはルールに明記しなければなりません。

:::warn ある設計が「汎用」だと思わない
同じ装置が別のゲームバージョンではまったく動かないことがあります。原因はスポーン規則、エンティティ AI、ブロック更新の順序、修正された複製特性、あるいは当たり判定が 0.1 ブロック変わっただけかもしれません。したがって：

- プレイヤーが「この装置は動く」と言ったら、まず**ゲームバージョン**と**サーバーコア**を聞く；
- 運営者が「新バージョンに上げた」と言ったら、**すべての装置を再検証する**という宣言に等しい；
- どのチュートリアル（本記事を含む）の設計も「考え方」としてしか使えず、「保証」にはならない。
:::

## 2. 装置 1 台がサーバーに何をもたらすか

装置を 6 種類のコストに分解すれば、切り分けの方向が見えます：

| コストの種類 | 何が生むか | 典型的な現れ方 |
| --- | --- | --- |
| エンティティ数 | モブ、ドロップアイテム、経験値オーブ、トロッコ、アーマースタンド、TNT | MSPT が上昇し、エンティティ同期が帯域を食う |
| AI と経路探索 | モブと村人の毎 tick の思考、経路計算 | 村人が密集した区域で顕著。TPS が落ちて特定しにくい |
| チャンク読み込み | 常時読み込みチャンク、ポータルのローダー | 無人のときも CPU とメモリを消費し続ける |
| ブロック更新とレッドストーン処理 | レッドストーンの素子、ホッパー、ピストン、オブザーバー | 高頻度クロックと広範囲のレッドストーンが古典的なキラー |
| ランダム tick | 作物、葉、霜、火の広がり | `randomTickSpeed` を上げると CPU が線形に増える |
| ライトとセーブデータ | ブロック変化によるライト再計算、チャンクの定期的な自動保存 | 大規模改造時に規則的なラグが出る |

結論は 1 つだけ：**TPS はこれらのコストが積み重なった結果であり、何か 1 つのスイッチで決まるものではありません。**

### 2.1 コストを定量化する方法

「この装置は高いか安いか」を感覚で判断しないでください。次の順で測ります：

```text
1. ベースラインを記録：プレイヤーがオンラインでないときの TPS / MSPT
2. プレイヤー 1 人だけを装置のそばに立たせ、5〜10 分の MSPT 曲線を観察
3. 装置を止めてもう一度測る。2 回の差がこの装置のコスト
4. spark でサンプリングし、コストがエンティティ、ブロックエンティティ、チャンクのどれにあるか確認
5. 数字を記録し、次にバージョンを上げる／設定を変えるときに同じ方法で再測定
```

こうする価値は：プレイヤーが「サーバーが重いから装置が動かないんだ」と言ったとき、あなたの手元にデータがあり、互いに推測し合わずに判断できることです。

## 3. レッドストーン技術が依存するサーバー設定

原則を先に置きます：**バニラの挙動が「既定値」で、最適化は「既定値からの逸脱」**。技術系プレイヤーが求めるのは前者です。

以下のキー名、既定値、選択できる値は**すべてバージョンで変わり**、使っているコアの分岐によっては存在しないこともあります。**自分のサーバーの設定ファイル**とそのコアの公式ドキュメントを優先してください。本記事は「この項目が何をするのか、変えると何が起きるのか」だけを扱います。

### 3.1 スポーン上限（mob cap）

バニラのスポーン上限は**固定の数字ではなく**、プレイヤーごと、スポーン可能なチャンク数に応じてスケールします。要点：

- 上限は**プレイヤー数**と**プレイヤー周辺のスポーン可能チャンク数**でスケールするので、「人数が増えるとスポーンも増える」のは正常な現象です；
- モブ、動物、水生生物、環境生物それぞれに上限があります；
- 上限はプレイヤー単位で計算されるため、**プレイヤーがオンラインでないと自然スポーンは起きません** —— そのチャンクが常時読み込みであっても；
- プラグイン系の `spawn-limits`（`bukkit.yml`）はこのアルゴリズムを上書きし、「プレイヤー単位のスケール」を別の基準に変えます。コアの分岐によって実装が異なり、変更するとすべてのトラップタワーの生産量が直接変わります。

### 3.2 スポーン範囲と消滅距離

- バニラのモブはプレイヤーの周囲一定距離（最小と最大がある）にスポーンし、プレイヤーから離れすぎると消滅します。
- `mob-spawn-range`（`spigot.yml`、単位はチャンク）がこの範囲を変更します。
- 変更の連鎖：トラップタワーの効率、モブの消滅速度、村と襲撃に関する仕組みの発生範囲がすべて変わります。
- レッドストーン技術サーバーは通常**バニラの範囲を維持**します。成熟した設計はすべてバニラの距離を前提に作られているからです。

### 3.3 エンティティの有効範囲（entity activation range）

- Spigot の `entity-activation-range` は遠くのエンティティの**頻度を下げ、場合によっては tick を止めます**。既定値はおおよそ十数ブロックから四十数ブロックの間です（具体的にはあなたの `spigot.yml` を優先）。
- 結果は直接的です：装置のうち「プレイヤーから遠い」半分が動かない、あるいは動作速度がバニラと一致しません。
- レッドストーン技術サーバーは、十分に大きくするか、「一部の装置の挙動がバニラと違う」を受け入れるかのどちらかです。
- 注意：この項目は普通のサバイバルサーバーでは**極めて費用対効果の高い**最適化なので、多くのプリセット設定がこれをかなり小さくしており、衝突はここで起きます。

### 3.4 ランダム tick

- `randomTickSpeed` はゲームルールで、バニラの既定値は 3。
- 影響範囲：作物の成長、葉の腐敗、霜の形成と融解、火の延焼。
- 上げるとランダム tick に依存するファームが速くなり、同時に CPU コストが**大幅に**増えます。下げると逆になります。
- 多くの「最適化」チュートリアルがこれを下げるよう勧めますが、それは**バニラの挙動を変える**ことで、作物系の装置はそれに伴って遅くなります。

### 3.5 レッドストーン関連

- Paper 系のコアは切り替え可能な**レッドストーンの実装方式**を提供します（設定項目はワールド既定設定にあり、`misc.redstone-implementation` のような形。キーのパスと選択できる値はバージョンで変わる）。
- レッドストーン技術サーバーは**vanilla 実装を維持しなければなりません**。性能向けに最適化された実装に変えるとレッドストーンの更新挙動が変わり、装置は直接動かなくなることがあります。
- もう 1 点：一部の最適化項目はブロック更新の順序やレッドストーンの処理遅延を調整します。こうした変更は「性能低下」より致命的です。装置を**静かに**壊すからです。

### 3.6 そのほかよく変更される項目

| 設定 | バニラの挙動 | よくある「最適化」 | レッドストーン技術での取捨 |
| --- | --- | --- | --- |
| `simulation-distance`（`server.properties`） | その距離内のチャンクを実際に演算 | 4〜6 に下げる | すべての装置の可用範囲に影響。下げることは遠くの装置を切り捨てること |
| `view-distance` | プレイヤーがどこまで見えるか | 下げる | 見た目と帯域にのみ影響。装置への影響は小さい |
| `entity-broadcast-range-percentage` | エンティティをプレイヤーへ同期する範囲の割合 | 下げる | プレイヤーにはエンティティが「突然現れる」ように見えるが、サーバーの演算には影響しない |
| `entity-tracking-range`（`spigot.yml`） | エンティティを追跡する距離 | 下げる | 同期にのみ影響し、装置のロジックは変えない |
| `max-entity-collisions` | 上限を超えるとエンティティの衝突処理を止める | 下げる | 密集するエンティティ装置では大きくする必要があり、代償は性能 |
| `nerf-spawner-mobs` | スポナー産モブの AI は完全 | `true` にして AI を弱体化 | スポナーファームの産出方法が変わる |
| `hopper-transfer` / `hopper-check`（`ticks-per`） | ホッパーは 8 tick ごとに搬送 | 大きくして性能を節約 | **すべてのホッパーの生産量が直接変わり**、装置のタイミングがすべて変わる |
| `merge-radius`（`spigot.yml`） | ドロップアイテムと経験値オーブの結合半径 | 大きくする | エンティティ数は減るが、バニラの結合挙動が変わる |
| `randomTickSpeed` | 3 | 下げる | 作物系ファームが遅くなる |
| `doMobSpawning` などのゲームルール | ゲーム内の `/gamerule` の説明を参照 | 切って負荷を減らす | 切るとトラップタワーがなくなる |

### 3.7 これらの設定はどんな形か

以下は**あくまで例**で、これらのキーがファイルのどこにどんな形で現れるかを知るためのものです。**数値は真似すべき答えではありません**。手元のファイルと照合してください。

```yaml
# spigot.yml（例。キー名と既定値はバージョンで変わる）
world-settings:
  default:
    mob-spawn-range: 8
    entity-activation-range:
      animals: 32
      monsters: 32
      raiders: 48
      misc: 16
      water: 16
      villagers: 32
      flying-monsters: 48
    max-entity-collisions: 8
    nerf-spawner-mobs: false
    merge-radius:
      item: 2.5
      exp: 3.0
    ticks-per:
      hopper-transfer: 8
      hopper-check: 8
```

```yaml
# bukkit.yml（例。既定値はバージョンで変わる）
spawn-limits:
  monsters: 70
  animals: 10
  water-animals: 15
  water-ambient: 20
  ambient: 15
ticks-per:
  monster-spawns: 1
  animal-spawns: 400
  autosave: 6000
```

```text
# server.properties（例）
simulation-distance=10
view-distance=10
entity-broadcast-range-percentage=100
```

```bash
# ゲームルール：これらはバニラの既定値。変える前に何が壊れるかよく考える
/gamerule randomTickSpeed 3
/gamerule doMobSpawning true
/gamerule doFireTick true
/gamerule doInsomnia true
/gamerule doPatrolSpawning true
/gamerule doTraderSpawning true
/gamerule disableRaids false
/gamerule mobGriefing true
```

:::warn 多くの「最適化」プラグインが変えているのはバニラの挙動
世の中の大量の「性能最適化」プラグインやプリセット設定は、上記の値をバニラよりはるかに攻めた値にするのがやり方です：エンティティの有効範囲を縮め、ランダム tick を下げ、エンティティを結合し、レッドストーンの処理を書き換え、スポーン上限を制限する。普通のサバイバルサーバーには良いことですが、**レッドストーン技術サーバーには災難**です —— 装置は特定しにくい形で壊れ、しかも「まったく動かない」ではなく「たまに産出が少し減る」ことが多いです。

したがって：

- 最適化プラグインを入れる前に、それが**どのバニラの挙動を変えるか**を確認し、できればテストサーバーで既知の装置を動かして検証する；
- 最適化項目とレッドストーン技術の要件はトレードオフで、両方を最大にはできません。[パフォーマンス最適化](/tutorials/java/optimize) を参照；
- 症状が「エンティティとドロップアイテムが溜まったまま消えない」なら、それは設定ではなく堆積の問題です。[エンティティとドロップアイテムの堆積によるラグ](/tutorials/faq/entity-lag) を参照。
:::

## 4. チャンク読み込み

チャンク読み込みは、レッドストーン技術サーバーで最も見落とされ、最もプレイヤーに濫用されやすい部分です。

### 4.1 スポーン地点のチャンク

- ワールドのスポーン地点周辺のチャンクは、プレイヤーがオンラインでなくてもゲームが**読み込み続けます**。これが「スポーン地点の放置ファーム」が 24 時間動く理由です。
- 「読み込み」と「スポーン」を区別してください：**プレイヤーがオンラインでないと自然スポーンは起きません**が、レッドストーン、ブロックエンティティ、作物のランダム tick は進み続けます。
- スポーン地点チャンクの**範囲の大きさはバージョン間で変更されています**。比較的新しいバージョンはこれを制御するゲームルール（`spawnChunkRadius` など）も提供しています。具体的な範囲とルール名は該当バージョンの公式 wiki を調べ、古いチュートリアルをそのまま真似しないでください。
- 実務的な提案：**最も重要な装置をスポーン地点に建てない**。そうしないと、あなたが知らないうちに 24 時間資源を消費します。

### 4.2 `/forceload`

バニラが提供する強制読み込みコマンドで、運営者が監査するときの最も直接的な手がかりでもあります：

```bash
/forceload add <開始x> <開始z> [終了x 終了z]
/forceload remove <開始x> <開始z> [終了x 終了z]
/forceload remove all
/forceload query
/forceload query <x> <z>
```

要点：

- 座標は**ブロック座標**で、読み込まれるのはそれらの座標を含むチャンクです；
- 1 つのコマンドで読み込めるチャンク数には上限があります（**最大 256 チャンク**）；
- 強制読み込みの一覧は**セーブデータとともに保存され**、再起動後も有効です；
- 管理者権限レベルが必要です（通常は OP レベル 2）；
- 強制読み込みされたチャンクは**完全に演算**されます。「読み込むだけで演算しない」わけではありません。

### 4.3 ポータル式のチャンクローダー

- プレイヤーがよく使う「チャンクローダー」の多くはネザーポータルが元です：ポータルは**別ディメンションの対応するチャンク**を一定時間読み込み続けます。
- 典型的な使い方は「ネザーにポータルを置いて、メインワールドの装置を動かし続ける」、あるいはその逆です。
- **具体的にどれだけ保持されるか、どのレベルのチケットを使うかはバージョン依存**です。該当バージョンの仕組みの説明を優先してください。これはつまり、ローダーがアップグレード後に無効になったり「永久読み込み」に変わったりしうるということです。
- 運営者の視点：こうした装置は**`/forceload query` には現れません**。人手で調べるしかありません。

### 4.4 常時読み込みチャンクのコスト

| コスト | 説明 |
| --- | --- |
| メモリ | 読み込み済みの各チャンクのデータとエンティティが常駐し、読み込むほどヒープ占有が増え、GC の圧力も大きくなる |
| CPU | 読み込まれたチャンクは完全な tick の流れを通る：ブロックエンティティ、ランダム tick、エンティティ tick |
| スポーン上限 | 読み込み区域の近くにプレイヤーがいると、これらのチャンクがスポーン上限を**分け合い**、他の場所のファームの生産量が下がる |
| セーブデータ | 読み込み中のチャンクは定期的に自動保存され、常時読み込み区域が広いほど自動保存の揺れが目立つ |
| 隠蔽性 | ローダーはプレイヤーに見えない場所（ネザー、地下）に建てられることが多く、事故のときに最も特定しにくい |

### 4.5 監査の方法

1. **ディメンションごとに `/forceload query` を実行**：メインワールド、ネザー、エンドのすべてを調べる。ローダーは残り 2 つのディメンションにあることが多い。
2. **ポータルローダーを探す**：プレイヤーに聞き、ネザーポータルの位置を見る。「なぜここにポータルが 1 つだけあるのか」に注意。
3. **無人のときの MSPT を見る**：プレイヤーが全員オフラインなのに TPS/MSPT が不健全なら、ほぼ常時読み込みチャンクが動いています。
4. **性能分析ツールで特定**：spark などのサンプリング結果は、時間がどのチャンクとエンティティに使われているかを示します。方法は [パフォーマンス最適化](/tutorials/java/optimize) と同じ。
5. **結論をルールに書く**：誰がローダーを建てたか、どれだけの範囲を読み込んでいるか、何を動かすためか。登録しておき、バージョンアップ前に 1 つずつ再検証する。

## 5. 技術系プレイヤーが必ず理解すべき tick モデル

### 5.1 20 TPS と 50 ミリ秒

- バニラの目標は **20 TPS**、つまり 1 ゲーム tick が **50 ミリ秒**です。
- 1 tick の超過で即 TPS が落ちるわけではありません：たまに 200 ミリ秒の tick があっても平均すれば TPS は 20 に近いままですが、プレイヤーは 1 回のラグを感じます。本当に TPS を落とすのは**持続的な**超過です。
- 時間に依存するすべての仕組み（作物、かまど、レッドストーン、モブの移動）がこのループで進むので、TPS が落ちれば**すべてが同時に遅く**なります。
- だからこそ「TPS 15」は 25% 遅いだけでは済みません：すべての装置が同じ比率で遅くなり、精密なタイミングに依存する設計はそのまま停止します。

### 5.2 ゲーム tick とレッドストーン tick

| 単位 | 長さ | 用途 |
| --- | --- | --- |
| ゲーム tick（game tick） | 1/20 秒 = 50 ミリ秒 | サーバーのメインループの最小単位 |
| レッドストーン tick（redstone tick） | ゲーム tick 2 個 = 0.1 秒 | レッドストーン素子の遅延を表すコミュニティの単位。リピーター、オブザーバーなどの遅延はこれで計る |

最小の例：

```text
0 tick 目（0 ms）      リピーターが起動し「2 tick 後に出力」を予約
1 tick 目（50 ms）     回路上の他の更新が同じ tick 内で決済され続ける
2 tick 目（100 ms）    リピーターが出力。つまり 1 レッドストーン tick 後
```

理解すべき要点：**レッドストーン tick は「遅延の計量単位」であり、「計算の実行単位」ではありません**。ブロック更新は同じゲーム tick 内で回路上を瞬時に伝播するので、装置の挙動は遅延の数値だけでなく、**同一 tick 内の更新順序**に依存することが多いです。

### 5.3 更新順序がなぜ急所なのか

- 2 つの素子が同じ tick で互いに影響するとき、どちらが先かで最終状態が決まります。
- これが「サーバーコアを替えると装置が壊れる」根本原因です：コアは並列化や最適化のために走査順序を変えることがあります。
- ゲームバージョンを上げたら**1 台ずつ再検証**しなければならない理由でもあります：公式がバグを直すときに順序の一部も変えるからです。
- デバッグ手段：バニラは `/tick` などの制御コマンド（凍結、ステップ実行、加速など。具体的なサブコマンドはバージョンで変わる）を提供し、tick ごとに装置の状態を観察できます。Carpet などのデバッグツールもあります。

### 5.4 「ラグマシン」は破壊手段

**ラグマシン（lag machine）とは、サーバーを押し潰すことを目的に意図的に組み上げられた装置です。** よくある形態：

- 極端に高頻度のレッドストーンクロックと、広範囲のレッドストーン回路による更新の嵐；
- 瞬間的に大量のエンティティ（TNT、ドロップアイテム、アーマースタンド、トロッコ、ボート）を生成する；
- 水流と溶岩を大面積で流し更新させる；
- チャンク読み込みの仕組みを利用して「常に読み込み + 毎 tick 計算」のループを作る；
- チャンクの生成／アンロードを繰り返し、メインスレッドにチャンク処理をさせ続ける。

その性質は**破壊行為であり、遊びではありません**：全員を切断させ、サーバーが正常に保存できなくし、セーブデータを壊すことさえ目的になりえます。

### 5.5 ラグマシンの見つけ方

| 信号 | 説明 |
| --- | --- |
| MSPT が突然持続的に跳ね上がり、TPS が 1 桁に落ちる | 最も直接的な現れ |
| エンティティ数が異常 | `/kill` 系のコマンドで数える前に**急いで消さない**。それは証拠 |
| spark のフレームグラフにレッドストーン／エンティティ／チャンクの集中したホットスポットが出る | 具体的なチャンクと座標を特定できる |
| プレイヤーが「ある座標に近づくと重くなる」と報告する | 座標が手がかり |
| ログにエンティティ上限やウォッチドッグ関連の警告が出る | サーバーがすでに自衛している |

対処の順序の目安：**まず座標と装置を特定 → スクリーンショット／記録 → ルールに従って処理 → 影響を受けた区域を復旧**。チート対策、ログ、ロールバックの手段は [チート対策と破壊行為の防止](/tutorials/java/anticheat) を参照。

## 6. 権限とツール

### 6.1 サーバー側：Carpet などのツール

- 技術寄りのサーバーは **Fabric + Carpet**（およびその各種拡張）をサーバー側のルール・デバッグツールとして広く使っています：バニラの細かい挙動を多数オン／オフでき、デバッグコマンドも提供します。
- **具体的なルール名と利用できるルールの集合は Carpet のバージョンで変わります**。該当バージョンの Carpet 公式ドキュメントを優先し、他人のルール一覧をそのまま真似しないでください。
- Carpet はサーバー側の MOD なので、バニラのクライアントでそのまま入れます。プレイヤーに何も入れさせる必要はありません。
- レッドストーン技術サーバーのよくあるやり方は：**有効にしているルールの一覧を公開する**こと。プレイヤーはどのバニラの挙動が変わったかを知る必要があります。

### 6.2 クライアント側：MiniHUD / Litematica などのツール

| ツール | 用途 |
| --- | --- |
| MiniHUD | HUD に座標、バイオーム、明るさ、チャンク境界などを表示 |
| Litematica | スケマティックの投影。見ながら装置を建てる |
| Tweakeroo | 便利な調整が多数 |
| Servux | サーバー側 MOD。構造物の範囲表示やスケマティックの貼り付けをサーバー上で正しく動かす |
| Syncmatica | スケマティックをサーバーにアップロードし、多人数で共有 |

### 6.3 サーバー側が対応すべきこと

- サーバー側 MOD（Carpet、Servux、Syncmatica のサーバー部分）は**Fabric サーバーが必要**です。プラグイン系（Paper 系）は Fabric の MOD を直接動かせません。ブリッジの方案には互換性と性能のコストがかかります。[MOD サーバーの完全ガイド](/tutorials/java/modded) を参照。
- 純粋なクライアント MOD（MiniHUD、Litematica の表示部分）はどのサーバーでも使えますが、**サーバーのデータに依存する部分**（構造物の境界、スケマティックの貼り付け、正確な設置）はサーバー側の対応が必要です。
- したがってレッドストーン技術サーバーを立てる前に 1 つ決める必要があります：**サーバーは Fabric か Paper 系か**。この決定をしたら、そのあとのほぼすべてのツールチェーンがそれに従います。
- **バージョン**も揃える必要があります：クライアント MOD のバージョン、サーバー MOD のバージョン、ゲームバージョンの 3 つが一致しないとプレイヤーは入れません。

### 6.4 権限一覧

技術系プレイヤーへの権限は、OP を直接渡すのではなく専用のグループに分けることを勧めます：

| 権限 | 用途 | リスク |
| --- | --- | --- |
| `/forceload` | 装置を動かし続ける | 濫用するとサーバーが長期的に高負荷になる。登録制を勧める |
| `/tick`（凍結／ステップ実行など） | 装置のタイミングをデバッグ | 全サーバーを凍結すると全員が止まる。告知に注意 |
| `/gamemode spectator`、`/tp` | 観察と建築 | 低リスク |
| `/spark` | 性能の自己診断 | 低リスク。技術班に開放することを勧める |
| `/give`、クリエイティブモード | 装置の建築 | テスト環境か明確に許可された建築区域でのみ使うべき |
| WorldEdit などの一括編集 | 素早い施工 | **1 回の誤った選択でセーブデータを壊せる**。必ず権限を限定し、先にバックアップ |

## 7. 技術寄りサーバーを開くためのチェックリスト

| 項目 | なぜ必須か |
| --- | --- |
| **ワールドのプリ生成** | プレイヤーが走り回って起こすチャンク生成は TPS の主要なキラー。プリ生成でこのコストを前払いできる。[パフォーマンス最適化](/tutorials/java/optimize) を参照 |
| **大規模工事の前のバックアップ** | 技術系プレイヤーは大規模な改造と爆発的なテストをする。問題が出たとき 1 分前へ戻れる必要がある |
| **独立したテストワールド／テストサーバー** | 新しい装置、設定、コアバージョンはまずテストサーバーで検証。本番で直接試さない |
| **バージョン固定とアップグレード手順** | アップグレードは装置を無効にする。告知、バックアップ、テストサーバーでの再検証を経てから本番へ |
| **Carpet ルール一覧の公開** | プレイヤーはどのバニラ挙動が変わったかを知る必要がある。そうしないと装置の不具合を自分のせいだと誤解する |
| **ラグマシンと複製特性に関する明確なルール** | この 2 つはルールに明記しなければならない。そうしないと BAN の根拠がない |
| **ベースラインの監視** | 正常時の TPS/MSPT を記録して初めて「遅くなった」を比較できる。感覚ではない |
| **ストレージの計画** | バックアップ + スケマティック + ログの増加速度はしばしば予想を超える |
| **権限の階層化** | 技術班の権限と一般プレイヤーの権限を分け、OP を気軽に渡さない |
| **装置の登録と連絡チャネル** | 誰がどこに何を建てたかは、切り分けで最も価値のある情報 |

そのまま使えるルールの骨子：

```text
1. 許可：通常のレッドストーン装置、トラップタワー、作物ファーム、村人取引施設。
2. 登録制：常時読み込みチャンク、チャンクローダー、無人の大型装置。
3. 禁止：サーバーを押し潰すことを目的とする装置（高頻度クロックの列、大量エンティティ生成、チャンクの反復読み込み）。
4. 複製系の特性：「許可」か「禁止」かを明記し、空白を残さない。
5. バージョンアップ：事前に告知。アップグレード後は装置を各自で再検証。運営は互換性を保証しない。
6. 処罰：ログと座標の証拠に基づいて処理。まず警告、そのあと BAN。
```

## 8. まとめ

- レッドストーン技術のプレイヤーが作るのは**資源生産ライン**で、産出で分類するより負荷で分類するほうが役に立つ。
- サーバー側が気にすべき設定は：**スポーン上限と範囲、エンティティの有効範囲、ランダム tick、レッドストーンの実装、チャンク読み込み**に集中している。
- **常時読み込みチャンクにはコストがある**：メモリ、CPU、スポーン上限、セーブデータの揺れ。監査と登録が必要。
- **20 TPS / 50 ミリ秒**と**レッドストーン tick = ゲーム tick 2 個**を理解して初めて、装置がなぜ壊れるか、なぜ遅いかが分かる。
- **ラグマシンは破壊手段**。ルールがあり、検知があり、ロールバックがあるべき。
- ツールチェーンの選択（Fabric + Carpet か Paper 系か）はレッドストーン技術サーバーの**最初の決定**で、そのあとのすべてを決める。

:::tip 技術系サーバーの TPS は設計の結果であり、設定の結果ではない
多くの運営者が「重い」を設定の問題と捉え、パラメータをいじり、最適化プラグインを入れ替え続け、最後には装置をすべて壊してしまいます。実際には：**TPS はプレイヤーがどんな装置を作り、それがどれだけ大きく、どこに置かれ、どれだけのチャンクを読み込んでいるかで決まります**。パラメータはバニラの挙動と性能の間で取捨選択させるだけで、設計の悪い装置を魔法のように安くはできません。まず設計を見て、それから設定を語ってください。
:::
