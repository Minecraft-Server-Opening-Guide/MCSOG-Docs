レッドストーン技術サーバーに必要なのは「起動できるサーバー」ではなく、**ルールで細かく制御できるバニラの仕組み一式**です：装置が想定どおり動き、TNT とアップデート抑制が制御でき、落ちてもすぐ立ち上げられること。本記事では 3 つの路線それぞれの代償を整理し、PCA プロトコルを個別に掘り下げます。

## 1. 3 つの路線の一覧

| 路線 | 代表 | 得られるもの | 代償 |
| --- | --- | --- | --- |
| **Fabric サーバー + MCDR**（最も推奨） | Fabric + `MCDR` | Carpet とそのすべてのアドオン、プロセス外のマネージャー、公式プラグイン一覧 | MOD を自分で入れる必要があり、プラグインエコシステムのような即戦力はない |
| レッドストーン技術向け最適化コア | Paper 系などのプラグイン系 | TPS の最適化、プラグインエコシステム | バニラの挙動を変えるため、装置が動かないことがある |
| マルチスレッドコア | `c2me-fabric`、`async` | チャンクとエンティティ処理の加速 | マルチスレッドがタイミングを変え、装置の挙動に影響する |

**先に結論**：レッドストーン技術サーバーを立てるなら **Fabric サーバー + MCDR**。残りの 2 つは、自分が何を欲しいかを明確に分かっているときだけ使います。

## 2. なぜ Fabric サーバー + MCDR が最も推奨なのか

これは好みの問題ではなく、3 つの厳然たる事実が重なった結果です。

### レッドストーン技術のツールチェーンがすべて Fabric 上にある

`Carpet` 本体、およびその 4 つの主要アドオン（`Carpet Extra`、`Carpet TIS Addition`、`Carpet AMS Addition`、`Carpet Org Addition`）は**すべて Fabric サーバー MOD** です。つまりレッドストーン技術のプレイヤーが本当に依存しているルールシステムは、Fabric にしか完全な実装がありません。別のコアを選ぶことは、このツールチェーンを捨てることと同じです。ルールとアドオンの詳細は [Carpet とそのアドオン](/tutorials/java/sd-carpet) を参照。

### MCDR はサーバープロセスの外側にいる

`MCDR`（MCDReforged）は Python で書かれたサーバーマネージャーです。

鍵は**サーバープロセスの外側で動く**ことです：

- サーバーが落ちても MCDR 自身は生きており、**自動で再起動**できる；
- クラッシュした瞬間にも実行能力があるので、**クラッシュ時にバックアップを実行できる**；
- コンソールとログを通じてサーバーとやり取りし、サーバー自身のロジックには侵入しない。

この 3 点はレッドストーン技術サーバーでとりわけ重要です：ワールドイーター、アップデート抑制、大規模な TNT アレイは、いずれもサーバーを直接落としうる遊び方であり、マネージャーはサーバーより「しぶとく」なければなりません。インストールとコマンドは [MCDR サーバーマネージャー](/tutorials/java/mcdr) を参照。

### MCDR には公式のプラグイン一覧がある

MCDR は公式にプラグイン一覧（`MCDReforged/PluginCatalogue`）を維持しており、バックアップ系、検索系、権限系のプラグインが揃っています。バックアップだけでも、一覧には `prime_backup`、`quick_backup_multi`、`timed_quick_backup_multi`、`better_backup`、`auto_backup`、`permanent_backup`、`zip_backup`、`chunk_backup`、`region_backup`、`ftp_backup`、`baidu_netdisk_backup`、`extra_prime_backup`、`smart_backup`、`cushion_of_backup` などの項目があり、うち `ftp_backup` と `baidu_netdisk_backup` は**遠隔地バックアップ**の発想です。

言い換えれば：管理スクリプトを自分で書く必要はなく、MCDR を入れれば運用ツールボックスが一式手に入ります。

## 3. 残り 2 つの選択肢とその代償

### レッドストーン技術向け最適化コア（プラグイン系）

Paper 系のようなプラグイン系は TPS をよく最適化でき、プラグインエコシステムも成熟していますが、多くの既定設定が**すでに最適化済み**でバニラの挙動と一致しません：エンティティの衝突、レッドストーンの実装、チャンクのアンロード遅延といった項目が変わると、装置が動かない、あるいは出力が不安定になることがあります。

この類のコアは普通のサバイバルサーバー、ミニゲームサーバー、プラグイン機能を大量に必要とするサーバーに向いています；**レッドストーン技術サーバーでは逆に、バニラの挙動に影響する項目を 1 つずつバニラへ戻す**必要があります。どの項目をどう調整するかは、当サイトに専用の 2 記事があります：

- [サーバーコアの選択](/tutorials/java/core) —— 汎用の選型と各コアの位置づけ；
- [レッドストーン技術とレッドストーン](/tutorials/java/redstone) —— プラグイン系でのバニラ特性チューニング一覧と、MCHPRS などの専用コア。

本記事ではこの 2 記事の内容を繰り返しません。

### マルチスレッドコア

マルチスレッドコアの発想は、チャンクやエンティティの処理を複数のスレッドに分割することです：

| MOD | レッドストーン技術の視点での問題 |
| --- | --- |
| `c2me-fabric` | チャンク処理の並列化で、タイミングがバニラと異なる |
| `async` | エンティティの並列処理で、装置が依存する更新順序が変わる |

レッドストーンとレッドストーン技術の装置は**更新順序とタイミングに大きく依存**します。マルチスレッドが加速するのはスループットで、代償は「同一 tick 内の誰が先か」が予測できなくなること —— 装置はたまたま合うこともあれば外れることもあり、これは安定して遅いより調査が難しくなります。

結論：自分が何を欲しいかを明確に分かっているとき（たとえば走り回っても重くならないようにしたいだけで、装置の挙動のずれを受け入れられる）だけマルチスレッドコアを使います。

## 4. レッドストーン技術サーバーにチート対策は勧めない

はっきり言います：**レッドストーン技術サーバーにチート対策プラグインは勧めません**。

理由は論理上の衝突です：

- レッドストーン技術のプレイヤーの正常な遊び方自体が継続的にチート対策の判定を引く —— 高速移動、大量のエンティティ、装置と自動化が生む異常な挙動は、すべて疑わしいと見なされる；
- チート対策は通常**プラグイン系または最適化コア**への導入を要求し、この 2 類のコア自体がバニラの挙動を変えるため、レッドストーン技術の目的と直接衝突する；
- バニラの高速移動に対する検知と引き戻しには、Carpet 自身にスイッチがある：`antiCheatDisabled`（移動が速すぎてプレイヤーが引き戻されるのを防ぐ）。

本当に必要なのは**ホワイトリストと権限、操作の記録と遡及、定期の遠隔地バックアップ**といった代替案であり、誤判定する判定をさらに重ねることではありません。完全な論証は [チート対策を勧めない理由](/tutorials/java/sd-anticheat)、ログとロールバックの手段は [チート対策と破壊行為の防止](/tutorials/java/anticheat) を参照。

## 5. PCA プロトコル

`PCA` の正確な正体は `plusls-carpet-addition`（Plusls Carpet Addition）で、Carpet の拡張 MOD です。コミュニティで「サーバーに PCA プロトコルを入れる」と言うのはこれを指し、しばしば **PCA Protect** と略されます。プロトコルのドキュメントは [plusls/plusls-carpet-addition](https://github.com/plusls/plusls-carpet-addition) にあります。

### 何なのか

PCA 同期プロトコルは、サーバーとクライアントの間で Entity と BlockEntity を同期するためのプロトコルで、現在は MasaGadget がマルチプレイでのコンテナプレビューを実装するために使っています。

分解すると 3 層の意味があります：

1. **サーバーとクライアントの間**のプロトコルで、両端に対応が必要；
2. 同期する対象は **Entity と BlockEntity** のデータ；
3. 現在の主な用途は **MasaGadget がこれでマルチプレイのコンテナプレビューを実装**すること —— マルチプレイ環境で他人のチェスト、ホッパー、装置の中身を見る。

### 2 つのルール

| ルール | 型 | 既定値 | 選択できる値 | 説明 |
| --- | --- | --- | --- | --- |
| `pcaSyncProtocol` | `boolean` | `false` | `true` / `false` | 同期プロトコルのスイッチ。分類は `PCA`、`protocal` |
| `pcaSyncPlayerEntity` | `enum` | `OPS` | `NOBODY` / `BOT` / `OPS` / `OPS_AND_SELF` / `EVERYONE` | どのプレイヤーのデータを PCA 同期プロトコルで同期するかを決める |

`pcaSyncProtocol` は**既定でオフ**である点に注意：プロトコルは能力であり既定の挙動ではありません。使う前に、誰に見せるために同期するのかを自分で考える必要があります。

### メンテナンス状況（この段落は必ず読む）

| プロジェクト | 状態 |
| --- | --- |
| `plusls/plusls-carpet-addition`（元のプロジェクト） | 2022 年に更新停止 |
| `Nyan-Work/plusls-carpet-addition`（その fork の 1 つ） | 2024 年に更新停止 |
| `pca-protocol` | 現行で利用可。Modrinth、`fabric`、1.14.4–26.3、作者 fallen-breath。|
| `pca-protocol-plugin` | 現行で利用可。Modrinth、`bukkit` / `paper` / `purpur` / `spigot`、1.17–1.21.8。|

つまり：元のプロジェクトとその fork はすでに更新停止しており、**いま使えるのはプロトコル機能だけを残した 2 つの簡素化 fork** —— `pca-protocol` は Fabric サーバー向け、`pca-protocol-plugin` は Spigot 系サーバー向けです。

### サーバーに PCA プロトコルを入れる（PCA Protect）

コミュニティは「サーバーに PCA プロトコルを喋らせる」ことを **PCA Protect** と略し、やり方は上記 2 つの簡素化 fork のうち対応するほうを入れるだけです：

- **Fabric サーバー**：`pca-protocol` を入れる（ソース：[Fallen-Breath/pca-protocol](https://github.com/Fallen-Breath/pca-protocol)）。追加の前提は不要で、Fabric Loader があれば動きます。
- **Spigot 系サーバー**（`bukkit` / `paper` / `purpur` / `spigot`）：`pca-protocol-plugin` を入れる。
- **クライアント**：サーバーは「喋れる」ようになるだけで、実際に使うにはそのプロトコルを使う MOD をクライアントにも入れる必要があります。たとえば `MasaGadget`（マルチプレイのコンテナプレビューはこれが実装しています）。

入れたあともプロトコルは**既定でオフ**です：`pcaSyncProtocol` を手動でオンにし、`pcaSyncPlayerEntity` で同期範囲を決めます。

:::warn 簡素化 fork と完全版は衝突する
公式が明確に説明しています：簡素化 fork と完全な `plusls-carpet-addition` は**衝突**します。つまり完全版（他の機能を含むが更新停止）を使うか、簡素版（プロトコルのみで、まだ保守されている）を使うかで、**同時に入れないでください**。
:::

## 6. 本記事の 3 つの一線

```
1. コアは Fabric を選ぶ —— レッドストーン技術のツールチェーンはここにしか完全な形がない
2. 管理は MCDR に任せる —— サーバープロセスの外側にいて、落ちても救える
3. チート対策は入れない —— 誤判定は必然。権限、ログ、バックアップで代替する
```
