多くの人がサーバーを開くときの最初の「サーバー」は、自分の机の上の PC です。安く、性能がよく、完全に自分で制御できます。ただし、それは**7x24 時間の稼働を前提に設計されていません**。この記事では、家庭用 PC がサーバーに向くのか、そしてそうすると決めた場合に**長期的にどう保守すれば事故らないか**を整理します。

まだ方針を決めていないなら、まず [アクセス可能な環境へのデプロイ](/tutorials/java/deploy) の 3 つの方針の比較を見てください。

## 1. 家庭用 PC はサーバーに向くのか

まず「動く」と「長期稼働に向く」を分けます。家庭用機で MC サーバーを動かすのは**性能面では通常余裕があります**（現代のデスクトップ CPU のシングルコア性能は、同価格帯のクラウドサーバーより総じて強い）。本当の弱点は**信頼性、ネットワーク、運用コスト**です。

| 観点 | 家庭用 PC | VPS / クラウドサーバー |
| --- | --- | --- |
| 一時コスト | すでにマシンがあればほぼゼロ | なし。ただし月額を払う |
| 継続コスト | **電気代**（下記）、夏は冷房代も | 月額。構成が良いほど高い |
| シングルコア性能 | 通常はより強い。同価格帯での優位が明らか | 同価格帯では弱め |
| グローバル IP | **多くの家庭回線にはグローバル IPv4 がない** | 通常は付属 |
| 電力 | 自宅の停電で即切断。UPS が必要 | データセンターに UPS と発電機がある |
| ネットワーク | 家庭回線は上りが小さく、事業者の速度制限もあり得る | データセンターの帯域は広く対称 |
| 騒音 / 発熱 | 自分の部屋の中 | データセンターの中 |
| 攻撃を受けたとき | 自宅の IP が狙われ、家庭のネットワーク全体に影響 | データセンターが狙われ、高防御を追加できる |
| データの安全 | ディスクが壊れたら自分の責任 | 通常はスナップショットがあるが、**事業者が夜逃げし得る** |

### VPS を直接使うべき人

普段あまり家にいない（家で問題が起きても遠隔で対応できない）、プレイヤーが十数人を超えた（上りの帯域が先に破綻する）、DDoS を家庭のネットワーク全体に巻き込みたくない、騒音と発熱が気になる（寮 / シェアハウス / 寝室）、あるいは**データの重要性が節約より高い**人は、VPS を買うほうが気が楽です。

### 「24/7」について：何がそれを中断させるのか

家庭用機が 24 時間稼働できないのは、通常ハードウェアのせいではなく、次のような理由です。

| 中断の原因 | 説明 | 緩和 |
| --- | --- | --- |
| システムのスリープ / 休止 | 既定の電源プランはアイドル後にスリープし、**サーバーはそのまま切断される** | スリープを無効化する（第 2 節を参照） |
| 停電 | 最もよくある切断の原因で、**セーブデータを壊し得る** | UPS + BIOS の電源復帰時の自動起動 |
| システム更新による再起動 | Windows は既定で夜間に自動再起動する | 活動時間を設定する / 再起動の時間帯を手動で決める |
| ルーターの再起動や接続の切断 | 家庭回線ではよくある | 定期的に確認する。IP の変化には DDNS |
| 過熱によるクロック低下や保護シャットダウン | 埃詰まり、ファンの停止 | 清掃、温度の監視 |
| 自分自身の不注意 | ケースを蹴る、違うプラグを抜く | 物理的な安全（第 8 節を参照） |

:::warn 1 回の不意の電源断は、思っているより高くつく
サーバーがチャンクを書き込んでいる最中の停電は、最悪の場合**セーブデータの破損**で、最後に使えたバックアップまで巻き戻すしかありません。だから第 2 節と [バックアップと復元](/tutorials/java/backup) はセットです。**電源保護とバックアップはどちらも欠かせません**。
:::

### 電気代：まず計算してから決める

電気代 = 電力（kW）x 時間（h）x 電気料金（元/kWh）。電力計（またはコンセント型の消費電力計）で実測するのが最も正確です。以下は**桁感の見積もり**で、実際の差は大きくなります。

| 場面 | マシン全体の消費電力（桁感） | 毎月（30 日） |
| --- | --- | --- |
| 低消費電力の小型機 / ノート PC | 10 - 25 W | 7 - 18 kWh |
| デスクトップのアイドル / 軽負荷 | 40 - 80 W | 29 - 58 kWh |
| デスクトップの連続フル稼働（高クロック CPU + グラボは空回り） | 120 - 250 W | 86 - 180 kWh |

上の kWh に現地の電気料金を掛ければ月のコストです。**単体 GPU はアイドルでも電力を食います**（多くは 5 - 20 W。型番による）。純粋なサーバー用途なら内蔵 GPU にするか、単体 GPU を外すことも考えられます。夏はエアコンがこの熱を**さらに 1〜2 倍に増幅**した冷房代として請求してきます。

## 2. 電源の安定性

### 「セーブデータの書き込み中に停電」が危険な理由

MC のチャンクは**ファイルに分けて書き込まれ**、書き込みの途中で停電すると**書きかけの状態のファイル**が残り得ます。復元すると、軽ければ数チャンクを失い、重ければセーブデータが読み込めません。`save-all` があっても、停電の瞬間にディスク上のすべてのファイルが一貫した状態であることは保証できません。**これが UPS とバックアップの存在理由**です。「切断しないため」ではなく、**サーバーが安全に停止できる機会を作るため**です。

### UPS：家庭用ならどれくらい買うか

UPS の目標は、停電しても数時間遊び続けられることではなく、**短い瞬断を乗り切り + サーバーが安全に停止する数分を稼ぐ**ことです。

見積もり方：

1. マシン全体の消費電力 `P`（ワット）を測る。
2. 必要なバックアップ時間 `T`（分）を決める。家庭用なら **5 - 15 分**で通常足ります。
3. 必要な容量（Wh）≈ `P x T / 60 / 0.6`（0.6 はインバータ効率とバッテリー劣化を見込んだ保守的な係数）。
4. VA に換算する：UPS の公称 VA と W の関係は力率に依存し、家庭用 UPS の力率は約 0.5 - 0.6 が一般的。**製品の銘板に書かれた W を基準にしてください**。

例：マシン全体 80 W で 10 分持ちこたえたいなら、必要な有効容量は約 `80 x 10 / 60 / 0.6 ≈ 22 Wh`。公称 **500 - 650 VA / 300 W 程度**の常時商用給電式 UPS なら余裕があります。**具体的な型番の容量とインターフェースはメーカーの仕様書に従ってください**。経験値で注文しないこと。

| UPS の種類 | 特徴 | 向く場面 |
| --- | --- | --- |
| 常時商用給電式（Standby） | 安い。切り替え時に数ミリ秒の中断がある | 家庭用の小型機で、電源の質が良い場合 |
| ラインインタラクティブ式（Line-Interactive） | AVR による電圧安定化があり、切り替えが速い | 電圧が不安定な地域。推奨 |
| 常時インバータ式（Online / Double-Conversion） | 常にインバータ経由で給電し、出力が最もきれい。最も高価で発熱も最大 | 電源に極めて敏感な機器 |

### 「純正弦波」が重要な理由

アクティブ PFC（Active PFC）の電源は**入力波形に敏感**です。矩形波 / 階段波（擬似正弦波）を出力する UPS では、アクティブ PFC の電源が**異常を検知し、異音を出し、最悪そのまま落ちる**ことがあります。しかもそれは停電の最中、まさに電源に頼りたい瞬間です。したがって：

- UPS の出力が**純正弦波（Pure Sine Wave）**であることを確認し、「擬似正弦波 / 階段波」ではないことを確かめる。
- マシン全体の消費電力が UPS の上限に近いほどリスクは大きい。
- 具体的な相性は**電源の型番と UPS の型番による**ので一概には言えません。購入前にメーカーの説明を確認してください。

:::tip ついでにサージ保護付きの電源タップを買う
落雷と電力網のサージは別の殺し屋です。UPS には通常サージ保護が付いていますが、UPS を使わないなら、少なくとも適合したサージ保護付きの電源タップを使ってください。
:::

### システムを決してスリープさせない

**Windows（管理者権限の PowerShell または CMD）**

```bat
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 0
powercfg /change disk-timeout-ac 0
```

- `standby-timeout-ac 0` は**交流給電時に決してスリープしない**（`0` は「しない」）という意味です。
- デスクトップ機は通常バッテリーがないので、`-ac`（交流）が変更すべき項目です。**ノート PC** は `-dc`（バッテリー）も変える必要があり、さもないと電源を抜いた途端にスリープします。
- 現在の設定を確認：`powercfg /query SCHEME_CURRENT SUB_SLEEP`。
- **注意**：Windows の「高速スタートアップ」と「休止状態」は別の話で、企業ポリシーやメーカーの電源管理ソフトがこれらの値を上書きすることがあります。

**Linux（systemd）**

まず、どのターゲットへの移行が「許可」されているかを見ます。

```bash
systemctl status sleep.target suspend.target hibernate.target hybrid-sleep.target
```

システムのスリープを止める：

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

**ノート PC の蓋を閉じたときの動作**は logind が扱います。`/etc/systemd/logind.conf` を編集します。

```ini
HandleLidSwitch=ignore
HandleLidSwitchExternalPower=ignore
HandleLidSwitchDocked=ignore
```

変更後は `sudo systemctl restart systemd-logind` で反映します。

:::warn 具体的なキー名と既定値はディストリビューションと systemd のバージョンで異なる
`logind.conf` の選択肢（`ignore` / `poweroff` / `suspend` / `hibernate` / `lock`）と既定の動作は、ディストリビューションや systemd のバージョンで完全には一致しません。**変更の前に `man logind.conf` を読み**、変更がデスクトップ環境の電源管理に上書きされないことを確認してください。デスクトップ向けディストリビューション（GNOME/KDE）は通常、独自の「画面消灯後にサスペンド」のスイッチも持っています。
:::

### BIOS：停電復旧後に自動で電源を入れる

停電が復旧しても、マシンは**既定では自分で電源が入りません**。手で電源ボタンを押す必要があり、外出中ならサービスは止まったままです。

BIOS/UEFI に入り、次のような名前の項目を探します（**名前はマザーボードのメーカーと BIOS のバージョンで異なります**。通常は `Power` / `Advanced` / `APM Configuration` の分類の下にあります）。

| よくある名前 | 役割 |
| --- | --- |
| `Restore on AC Power Loss` | 通電後の動作。`Power On` / `Always On` を選ぶ |
| `AC Power Recovery` / `AC Recovery` | 同上。Dell などはこの名前が多い |
| `After Power Failure` | 同上。自作マザーボードでよくある |

**`Power On` / `Always On`** を選びます（`Last State` は選ばないこと。停電時に電源が入っていれば入りますが、前回が電源オフなら入りません）。

あわせて確認すること：

- **「高速スタートアップ」を無効にする**（Windows の Fast Startup はシャットダウンをハイブリッド休止に変え、自動起動とディスクの一貫性に影響します）。
- **BIOS のスーパーパスワードを設定**し、誤って変更されないようにする。
- 長期間無人で運用するなら、**通電時の自動起動を有効にし、あらゆる「省電力待機」の項目を無効にする**。

## 3. 冷却と埃

### エアフローと設置

- **吸気にはフィルター、排気はスムーズに**。よく効く構成は、前面 / 底面から吸気し、背面 / 上面から排気する形で、**吸気量を排気量より少し多く**（正圧）すると、隙間から埃が入りにくくなります。
- **密閉した棚に押し込まない**。壁に密着させず、カーペットの上に置かない。マシンの周囲に空間を空けます。
- **HDD は振動に弱い**：蹴られたりぶつかったりする場所に機械式ディスクを置かない（第 8 節を参照）。

### 清掃

| 頻度 | やること |
| --- | --- |
| 1〜3 か月ごと | 吸気フィルターを確認し、明らかな埃は清掃する |
| 3〜6 か月ごと | 圧縮空気 / エアダスターでクーラー、ファン、電源の吸気口を清掃する |
| 6〜12 か月ごと | 埃の程度を見てサーマルグリスの塗り直しを判断する（**必須ではない**。温度が正常なら触らない） |

清掃の要点：**ファンを吹くときは手かプラスチック片で羽根を押さえる**。気流でファンを高速空転させないこと（ベアリングを傷める可能性があります）。掃除機を基板に直接当てない（静電気のリスク）。清掃後に**すべてのファンが回っている**ことを確認する（電源、グラボ、ケースファンを含む）。

### 温度の監視

**Linux**：`lm-sensors` はマザーボード / CPU の温度センサーを読む定番ツールです。使えるかどうか、どのセンサーが読めるかは**マザーボードとチップセットのドライバ次第**で、一部のプラットフォーム（とくに新しいノート PC や一部のマザーボード）では対応が不完全です。

```bash
sudo apt install lm-sensors      # Debian / Ubuntu
sudo dnf install lm_sensors      # Fedora / RHEL 系
sudo sensors-detect              # 利用可能なセンサーを検出する。対話形式で答える
sensors                          # 現在の値を出力する
watch -n 5 sensors               # 5 秒ごとに更新する
```

**Windows**：タスクマネージャー（`Ctrl+Shift+Esc`）の「パフォーマンス」タブで CPU/GPU の温度が見られます（**可否はハードウェアとドライバ次第**）。より細かい値（各コア、ディスクの SMART 温度、ファン回転数）が必要なら HWiNFO や HWMonitor のようなツールを使います。

### 過熱の現れ方

| 現象 | 意味 |
| --- | --- |
| TPS が急に下がるのに CPU 使用率は高くない | CPU がクロックを下げられている（thermal throttling） |
| CPU の周波数がベース周波数を下回る | 同上。`lscpu`/`cpupower` や HWiNFO で実周波数を見る |
| ファンが長時間全開で、音が大きくなった | 埃かサーマルグリスの劣化 |
| 理由もなくシャットダウン / 再起動する | 過熱保護が働いた。**深刻なシグナル**なので直ちに対処する |

`dmesg` に `CPU0: Core temperature above threshold`、`thermal throttling` のような情報が出ていれば、保護がすでに働いています。**具体的なログの文言はカーネルとハードウェアで異なる**ため、あなたのマシンの実際の出力に従ってください。

## 4. 家庭のネットワーク

### Wi-Fi が長期のサーバー運用に向かない理由

- **遅延の揺らぎ（jitter）は平均遅延より致命的**。MC はパケットロスと揺らぎに敏感で、プレイヤーには「跳ね返り」「ラグ」「瞬間移動」として現れます。
- **チャンネルの干渉と近隣の Wi-Fi の混雑**。夜に顕著になります。
- **省電力の仕組み**：無線 NIC は省電力モードに入り、周期的な遅延のスパイクを生みます。
- **安定性**：AP の再起動やファームウェアの問題で切断します。

**結論：有線を挿せるなら有線にしてください。** マシンがルーターから遠いなら、PLC アダプタ（電路の影響を強く受けます）、MoCA（同軸）、あるいは LAN ケーブルを 1 本引く。次の 3 項では、家庭回線で最もよくある 3 つの落とし穴を整理します。

### グローバル IPv4 があるか：どう判断するか

1. ルーターにログインし、**WAN 側の IP** を探す。
2. マシンから「私の IP」を調べるサイトにアクセスするか、`curl -4 ifconfig.me` を実行する。
3. **両者が一致しない**：あなたは事業者の NAT（CGNAT）の内側にいる可能性が高く、**グローバル IPv4 はありません**。ポートマッピングをしても無駄です。
4. 補足の判断材料：CGNAT の WAN IP は `100.64.0.0/10` の範囲（RFC 6598 の共有アドレス空間）にあることが多い。**これは絶対の規則ではなく**、よくある特徴にすぎません。

:::warn IPv6 は別の道だが、万能薬ではない
一部の地域の家庭回線にはグローバル IPv6 があり、理論上は直接接続できますが、**プレイヤーのネットワーク環境が IPv6 に対応しているとは限らず**、多くのクライアントは依然として IPv4 を使います。IPv6 主体の方案では、プレイヤー側の可用性を確認してください。
:::

### 動的 IP と DDNS

家庭回線のグローバル IP は**変わります**（再接続、事業者側の調整）。DDNS（動的ドメイン名解決）はまさにこれを解決します。

1. DDNS サービスに登録する（またはドメイン事業者の API を使う）。
2. ルーターかマシン上で更新クライアントを動かし、**現在のグローバル IP を定期的に DDNS へ通知**する。
3. プレイヤーは IP ではなく**ドメイン**で接続する。

要点：

- **DDNS が解決するのは「IP が変わってもあなたを見つけられるか」だけ**で、CGNAT は解決できません。グローバル IP がなければ DDNS も無意味です。
- 更新の間隔を短くしすぎない（レート制限されます）。数分に 1 回で通常は十分です。
- トンネル（frp など）を使う場合、プレイヤーの入口は**中継サーバーの IP** になるので、DDNS は不要です。

### 上りの帯域こそボトルネック

家庭回線は通常**下りが数百メガ、上りが数十メガかそれ以下**です。MC サーバーの通信はほぼすべて**上り**（ワールドデータをプレイヤーへ送る）です。

粗い見積もり：プレイヤー 1 人が普通に遊ぶのに必要な帯域は**数十〜数百 kbps** の桁で、描画距離、エンティティ数、チャンクの読み込み速度によって**大きく変動します**。`Mbps` で単純に換算すると：

| 上りの帯域 | 理論上の同時接続上限（1 人 0.5 Mbps の保守的な見積もり） |
| --- | --- |
| 10 Mbps | 約 20 人 |
| 20 Mbps | 約 40 人 |
| 50 Mbps | 約 100 人 |

**これは桁感の参考にすぎません**。実際は遊び方に依存します（レッドストーン / 大量のエンティティ / 大きい描画距離は需要を明確に押し上げます）。必ず**実測**してください。ルーターやシステムのツールでサーバープロセスの上り使用量を観察します。

:::tip まず測ってから人数の上限を決める
サーバーのディレクトリでしばらく動かした後、`iftop`、`nload`（Linux）またはタスクマネージャー / リソースモニター（Windows）で実際の上り使用量を見てから、何人連れられるかを決めます。**「下りが 500M あるから」で見積もらないでください。**
:::

## 5. OS 保守のルーチン

### 更新の方針

- **メンテナンス時間を固定する**（たとえば週 1 回）。その時間内にシステム更新と再起動を行います。
- **更新の前にバックアップする**（[バックアップと復元](/tutorials/java/backup) を参照）。バックアップファイルが**別のディスクか遠隔地**にあることを確認します。
- **無人での自動再起動を有効にしない**。あなたが選んだ時間に再起動させ、深夜に勝手に再起動させないこと。
- カーネル / システムのメジャーアップグレードの後は、**一度再起動してからサーバーが正常か確認する**。

**Debian / Ubuntu**

```bash
sudo apt update
sudo apt upgrade
sudo apt autoremove --purge
```

**Fedora / RHEL 系**

```bash
sudo dnf upgrade --refresh
sudo dnf autoremove
```

**Windows**：設定 -> Windows Update -> 詳細オプション で「アクティブ時間」をメンテナンス時間の外に設定し、重要な更新は手動で再起動します。

### ディスクの健全性（SMART）

`smartmontools` は SMART データを読む標準ツールです（`smartctl` がそのコマンド）。

```bash
sudo apt install smartmontools
sudo smartctl -a /dev/sda
```

:::warn デバイス名は必ず確認する
`/dev/sda` はあくまで**例**です。NVMe は通常 `/dev/nvme0n1`、SATA は `/dev/sdb` のこともあります。**デバイス名を間違えると別のディスクのデータを読み、さらに（書き込み操作では）破壊し得ます。** まず `lsblk` で確認してください。

```bash
lsblk -o NAME,SIZE,MODEL,MOUNTPOINT
```
:::

**SATA ディスクで重点的に見る属性**（属性名と番号は ATA/SMART 標準で定義され、メーカーによって生値の符号化が異なることがあります。**「VALUE/WORST/THRESH」と「RAW」はメーカーの説明と合わせて読みます**）。

| 属性 | 意味 | 判断の仕方 |
| --- | --- | --- |
| `Reallocated_Sector_Ct`（ID 5） | 再マッピングされた不良セクタの数 | **0 でなければ警戒**。増え続けるならディスクが劣化している |
| `Current_Pending_Sector`（ID 197） | 保留中のセクタ（読み取り失敗でまだ再マッピングされていない） | **0 以外なら直ちにバックアップする** |
| `Offline_Uncorrectable`（ID 198） | オフラインスキャンで訂正できなかったセクタ | 0 以外は回復不能なエラーがすでにある |
| `UDMA_CRC_Error_Count`（ID 199） | 転送のチェックサムエラー | 増加は通常**ケーブル / インターフェースの問題**で、ディスクの故障ではない |
| `Reported_Uncorrect`（ID 187） | 報告された訂正不能エラー | 197/198 と合わせて見る |

**NVMe ディスク**は別の項目群を見ます。

```bash
sudo smartctl -a /dev/nvme0n1
```

注目するのは `Percentage Used`（寿命の消費率）、`Available Spare`（利用可能な予備ブロック）、`Media and Data Integrity Errors`、`Critical Warning` です。

**定期的な自己診断**（多少時間を食うので、メンテナンス時間に実行するのが望ましい）：

```bash
sudo smartctl -t short /dev/sda     # 短い自己診断。通常 1〜2 分
sudo smartctl -t long  /dev/sda     # 長い自己診断。数時間かかることがある
sudo smartctl -l selftest /dev/sda  # 自己診断の結果を見る
```

**監視の推奨**：`smartd` を常駐させてメールで警告できます。デスクトップの利用者なら、少なくとも**四半期に 1 回は手で確認**してください。

### SSD の寿命

SSD の寿命は**書き込み量（TBW）**で決まり、通電時間ではありません。頻繁なフルバックアップ、ログの大量書き込み、頻繁な `save-all` は寿命を消費します。`smartctl` の `Data_Units_Written`（SATA）または `Data Units Written`（NVMe）で総書き込み量を見積もれます。**ログとバックアップを別のディスクに書く**と、システムディスクの書き込みを明確に減らせます。SSD は満杯に近づくと性能も寿命も悪化するので、**少なくとも 10% - 20% の空きを残して**ください。

### ファイルシステムの検査とログ

- **ext4**：異常な電源断の後に `fsck` を求められることがあります。**マウントしたままルートパーティションに `fsck` を実行しないでください**。現代のディストリビューションは起動時に自動で検査します。未マウントのパーティションを手で検査するには `sudo fsck -f /dev/sdb1`（先に `umount`）。
- **Btrfs / ZFS**：それぞれの検査とスクラブのツールがあります（`btrfs scrub`、`zpool scrub`）。**具体的なコマンドと使い方はバージョンで異なるため、公式ドキュメントに従ってください**。
- **ログの増加**：`journalctl --disk-usage` で systemd のログの使用量を見て、`sudo journalctl --vacuum-size=500M` で大きさを制限します。ログのローテーションは `logrotate` が担い、通常は既定で設定済みです。
- **Windows**：イベントビューアーは無限に増えます。「イベントビューアー -> Windows ログ -> プロパティ」で最大サイズと上書きの方式を設定できます。`cleanmgr` でシステムファイルを整理できます。

### 古いバックアップの掃除

**ここが最もディスクを満杯にしやすい場所**です。サーバーのディレクトリは増え続け、保持方針が「全部残す」なら数か月でディスクが埋まります。**ディスクが満杯になるとサーバーはセーブデータを書けなくなります**。保持方針を明確にし（たとえば毎日 7 部 + 毎週 4 部）、スクリプトに期限切れのバックアップを自動削除させ、定期的に `df -h` で空きを確認してください。詳しくは [遠隔地バックアップ](/tutorials/ops/offsite-backup) の保持方針とディスク容量の計算を参照。

## 6. ゲームサーバー保守のルーチン

### 計画的な再起動

**定期的な再起動**はメモリの断片化を回収し、解放されていない資源を片付けます。よくあるのは**毎日か数日ごとに 1 回**、低負荷の時間帯（未明）に選ぶやり方です。再起動の方法は、コンソールから `stop` を送る（**プロセスを直接殺さない**）。プロセスが完全に終了するのを待ってから起動します。**再起動の前にバックアップの成功を確認**してください。systemd で管理している場合、`systemctl restart minecraft.service` は正常な停止の流れを通ります（サーバーが `stop` を受け取れることが前提です。起動方法がコンソール入力を受け取れないなら、`screen`/`tmux` か RCON でコマンドを送る必要があります）。

:::warn 電源を切るような再起動は危険
`kill -9`、タスクマネージャーの「タスクの終了」、電源ボタンを直接押す。どれもサーバーが保存する間もなく終わる可能性があります。**`stop` が使えるなら `stop` を使ってください。**
:::

### バックアップが本当に動いているか確認する

**保守チェックリストで最も飛ばされやすく、最も致命的な項目です。** **バックアップファイルの更新時刻とサイズ**を確認し（「スクリプトが存在するか」ではありません）、**ログの終了コード**を確認し（0 以外は失敗）、定期的に**実際に 1 回復元する**（[遠隔地バックアップ](/tutorials/ops/offsite-backup) の復元演習を参照）。

```bash
ls -lh /backup/mcserver/ | tail -5
tail -20 /var/log/mc-backup.log
```

### ログとクラッシュレポートを見る

- **`logs/latest.log`**：現在 / 直近の実行のログ。`WARN`、`ERROR`、`Exception`、`Caused by` を検索します。
- **`crash-reports/`**：クラッシュレポート。完全なスタックとそのときの環境情報を含み、**クラッシュを調べる第一級の資料**です。
- よくあるシグナル：メモリ不足（`OutOfMemoryError`）、プラグインのエラー、チャンク読み込みの失敗、ポートの競合。

```bash
grep -nE "ERROR|Exception|Caused by" logs/latest.log | tail -40
ls -lt crash-reports/ | head
```

### spark で TPS を見る

**spark** はよく使われる性能分析のプラグイン / MOD です（Bukkit 系、Fabric、Forge などに対応版があります）。TPS、MSPT、ラグの発生源をサンプリングできます。よく使うコマンドは `/spark tps`、`/spark profiler start` / `/spark profiler stop`（**具体的なサブコマンドは spark の公式ドキュメントに従ってください**。バージョンで多少異なります）。**TPS が長期的に 20 を下回るならサーバーが追いついていません**。**MSPT が継続的に 50 ms を超える**のも、単一 tick の超過を示します。まず `/spark tps` で「本当に重いのか」を判断し、それから profiler で「誰が重くしているか」を探します。体系的な調査は [性能の最適化](/tutorials/java/optimize) を参照。

### メモリの増加を観察する

**Java のヒープは「使い切ったら壊れている」わけではありません**。GC がある程度保持するので、鍵は**Full GC の後に老世代が戻るか**です。Full GC の後に使用量が**上がり続けて戻らない**なら、**メモリリーク**の可能性が高いです（プラグインでよくあります）。調べ方：GC ログを追加する（JDK 9+ は `-Xlog:gc*`、JDK 8 は `-XX:+PrintGCDetails -XX:+PrintGCDateStamps`）、または spark にサンプリングさせる。**「-Xmx を増やして」リークを覆い隠さないでください**。クラッシュが先送りになるだけです。

### サーバーを安全に更新する

決まった手順を、1 段階も省かずに：

1. **完全バックアップ**（セーブデータ + プラグイン + 設定）。バックアップファイルが存在し、サイズが正常であることを確認する。
2. **changelog を読み、Java のバージョン要件を確認する**：破壊的変更（設定形式の変更、プラグインの非互換、Java バージョンの引き上げ）に注意する。
3. **まずテスト用のコピーで動かす**：サーバーのディレクトリを複製し、新しいバージョンで起動して、立ち上がるか、プラグインが正常に読み込まれるかを確認する。
4. **低負荷の時間帯に切り替える**：停止 -> jar を差し替え -> 起動 -> ログを観察 -> プレイヤーに確認してもらう。**旧バージョンは戻せるように残しておく**。

:::tip 更新の前に「戻し方」を書き下ろす
「新しいバージョンが起動しなければ、自分はどのコマンドを実行するか」を明確に書いておきます。事故のときは人は慌てており、記憶に頼ると手順を飛ばしがちです。
:::

## 7. Windows と Linux の違い

| 事項 | Windows | Linux |
| --- | --- | --- |
| スリープの禁止 | `powercfg /change standby-timeout-ac 0` | `systemctl mask sleep.target ...`。ノート PC は `logind.conf` も設定 |
| サービスの常駐 | タスクスケジューラ / NSSM などのラッパー / `start.bat` のループ | systemd unit（推奨） |
| 定期タスク | タスクスケジューラ（GUI） | cron / systemd timer |
| 更新 | Windows Update。「アクティブ時間」と自動再起動に注意 | `apt` / `dnf`。再起動の時期は自分で決める |
| ディスクの健全性 | メーカーのツール + イベントビューアー | `smartctl` + `smartd` |
| 温度 | タスクマネージャー / HWiNFO など | `lm-sensors`（対応程度はマザーボード次第） |
| ログ | イベントビューアー。上限は手動で設定 | `journalctl` + `logrotate` |
| 大文字小文字の区別 | **区別しない**（`World` と `world` は同じ） | **区別する**（`World` と `world` は別） |
| 改行コード | CRLF は Linux 上でスクリプトが実行できなくなることがある | LF |

:::warn 大文字小文字の区別はプラットフォーム間の移行で定番の罠
Windows で問題なく動いていたサーバーのディレクトリを丸ごと Linux へコピーすると、**プラグインの設定に書かれたパスの大文字小文字の誤り**が即座に「ファイルが見つからない」として現れます。移行の前に一通り確認してください。
:::

## 8. 物理的な安全

サーバーをどこに置くかが、中断されるかどうかを直接決めます。

- **蹴られたり、足を引っかけたりする場所に置かない**（通路、机の下の足元、ベッドの脇）。コップ、飲み物、水槽、窓辺の近くにも置かないこと。液体がケースに入ると廃棄級の故障です。
- **誤って抜かれやすいコンセントを使わない**（ドライヤーや電気ケトルと共有の電源タップはとくに危険）。**ケースは安定して置く**。機械式 HDD はとくに振動に弱いです。
- **ケーブルにラベルを貼る**：電源ケーブル、LAN ケーブル、モニターケーブルがどれか。LAN ケーブルのコネクタには抜け止め（這わせて固定）を。
- 可能なら、**マシンと日常の机を分ける**。「ついでに電源を切る」「ついでにケーブルを抜く」確率を下げます。

:::tip 「電源を切らないで」の札を作る
プラグとケースに紙を貼ります。「この PC はサーバーです。電源を切ったりケーブルを抜いたりしないでください」。家に他の人がいるなら、この紙の価値は極めて高いです。
:::

## 9. 保守カレンダー

次の表を最低限の要求として、実際の状況に合わせて頻度を上げたり下げたりしてください。

| 周期 | タスク |
| --- | --- |
| **毎日** | サーバーがオンラインかを 1 回確認する。`logs/latest.log` に ERROR がないかざっと見る。昨夜のバックアップファイルが生成されたか確認する |
| **毎週** | ディスクの空きを確認（`df -h`）。バックアップログの終了コードを確認。TPS を 1 回確認（`/spark tps`）。異常な再起動の記録がないか確認 |
| **毎月** | SMART（`smartctl -a`）の主要属性を確認。メモリの傾向と Full GC の挙動を確認。期限切れのバックアップを削除。システム更新を確認し、時間内の再起動を予定する |
| **四半期ごと** | **復元演習**（実際に復元して起動を検証）。清掃とファンの確認。UPS のバッテリー状態を確認。ポートマッピング / DDNS / ファイアウォール規則を見直す。ディスク容量の増加傾向を確認し、保持方針を調整する |
| **毎年** | UPS のバッテリーを交換（型番と状態による）。ハードウェアの老朽化を評価（HDD の通電時間、SSD の書き込み量）。保持方針と遠隔地のコピーが今も有効か見直す |

:::warn 復元演習は選択肢ではない
「バックアップスクリプトは毎日動いている」と「バックアップから復元できる」は別の話です。**復元を検証していないバックアップはバックアップに数えません**。詳しくは [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照。
:::

## 10. まとめ

家庭用 PC での開設は**不可能ではありません。むしろ「信頼性」を自ら進んで保守すべき事柄として扱う**ことです。スリープを止め、UPS と通電時の自動起動を設定し、有線を挿し、周期に沿って更新とディスクの確認を行い、定期的に本当にバックアップから復元する。これができれば、家庭用機でも長く安定して動きます。

あわせて読む：[アクセス可能な環境へのデプロイ](/tutorials/java/deploy)、[サーバー構成](/tutorials/java/structure)、[サーバーの起動](/tutorials/java/start)、[性能の最適化](/tutorials/java/optimize)、[バックアップと復元](/tutorials/java/backup)、[遠隔地バックアップ](/tutorials/ops/offsite-backup)。

> コマンドと設定は各ソフトウェアの公式ドキュメントに従ってください。マザーボード、電源、UPS の具体的な挙動はメーカーの仕様書に従ってください。
