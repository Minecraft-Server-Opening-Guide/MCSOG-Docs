「リソースパック」と「データパック」は名前がよく似ていますが、役割はまったく逆です：**リソースパックが変えるのはプレイヤーが見て聞くもので、データパックが変えるのはゲーム自体の挙動**です。この 2 つを混同すると、「テクスチャパックを入れたのにクラフトレシピが変わらない」「データパックでなぜテクスチャを変えられないのか」といった問題が起きます。

本記事は Java 版のリソースパックとデータパックを扱います：それぞれ何ができ、どう入れ、サーバーがどう配信し、形式が非互換のときどう切り分けるか。統合版は別の仕組み（リソースパック + ビヘイビアパック + アドオンパック）です。[統合版サードパーティコアの導入](/tutorials/bedrock/third-party-setup) を参照。

## 1. 両者とは何か

| 観点 | リソースパック（Resource Pack） | データパック（Datapack） |
| --- | --- | --- |
| 作用する場所 | **クライアント**：テクスチャ、モデル、効果音、言語ファイル、フォント、GUI | **サーバー / セーブデータ**：レシピ、ルートテーブル、進捗、関数、構造物、タグ |
| 誰に効果が見えるか | そのパックを入れた（または配信された）プレイヤーだけ | すべてのプレイヤー（データはワールド／サーバー側にあり、クライアントと無関係） |
| どこに入れるか | クライアントの `resourcepacks/`、またはサーバーが配信 | セーブデータディレクトリの `datapacks/` |
| サーバーが強制できるか | 配信して強制できる（`require-resource-pack`） | 配信は不要。もともとサーバー側にある |
| 遊びが変わるか | **変わらない**。変わるのは見た目と音 | **変わる**。レシピ、ドロップ、ワールド生成、コマンド実行を変えられる |
| コードを動かせるか | **動かない**。素材と設定ファイルだけ | **動く**。関数の中身はコマンド列で、サーバーがコマンドを実行するのと同じ |
| 典型的な用途 | テクスチャ、UI、効果音、日本語化、フォント、モデル | 独自レシピ、ドロップ、実績、ミニゲームのロジック、ワールド生成 |
| バージョンとの関係 | `pack.mcmeta` のフォーマット番号がクライアントのバージョンと一致する必要 | `pack.mcmeta` のフォーマット番号がサーバーのバージョンと一致する必要 |

一言で覚えるなら：**リソースパックは「見た目を替える」、データパックは「ルールを替える」。**

### ディレクトリ構成の対照

```text
リソースパック/
  pack.mcmeta                 <- 必須。これがパックであることを示す
  pack.png                    <- 任意。選択画面のアイコン
  assets/
    <名前空間>/
      textures/               <- .png テクスチャ
      models/                 <- .json モデル
      sounds/                 <- .ogg 効果音
      lang/                   <- <言語コード>.json の翻訳
      font/  blockstates/  gui/ ...

データパック/
  pack.mcmeta                 <- 必須
  pack.png                    <- 任意
  data/
    <名前空間>/
      function/               <- .mcfunction コマンド関数
      recipe/                 <- .json レシピ
      loot_table/             <- .json ルートテーブル
      advancement/            <- .json 進捗
      structure/              <- .nbt 構造物
      tags/                   <- タグ（function/tick.json など）
      predicate/  item_modifier/  worldgen/ ...
```

`pack.mcmeta` は**唯一の必須ファイル**で、ゲームはこれによってあるディレクトリや zip が「パック」かどうかを判断します。

## 2. それぞれ何ができないか

| やりたいこと | リソースパック | データパック |
| --- | --- | --- |
| ブロックのテクスチャを替える、効果音を替える、フォントと言語を変える | できる | **できない**（データパックはクライアントの素材に触れない） |
| クラフトレシピを 1 条足す、ドロップを変える | **できない** | できる |
| ゲームロジックを変える、ミニゲームのルールを足す、コマンドを定時実行する | **できない**（コードを実行できない） | できる |
| 新しいブロック／アイテムを足す | **できない**（既存の内容の素材しか変えられない） | **できない**（MOD が必要） |
| 全プレイヤーに同じ効果を見せる | リソースパックの配信が必要で、プレイヤーは拒否できる | もともと全プレイヤーに効く |
| サーバーの性能を変える | サーバーにはほぼ影響しない | **影響する**：関数が毎 tick 動けばサーバーを遅くしうる |

:::note なぜ「データパックで新しいブロックは足せない」のか
データパックはレシピ、ドロップ、進捗、ワールド生成などの**データ**を定義できますが、ブロックとアイテムの登録はゲームにハードコードされています。サーバー側に本当の新ブロック／新アイテムを足すには MOD（または統合版のビヘイビアパック）が必要です。**「データパックで新しい鉱物を追加」というチュートリアルは、既存ブロックの見た目と材質を借りているだけのことが多い**です。
:::

## 3. サーバーが Java クライアントへリソースパックを配信する方法

バニラのサーバーは `server.properties` のいくつかのキーでリソースパックをクライアントへ**プッシュ**します。**キー名は 1 文字も違えてはいけません**（最もよくある失敗原因の 1 つ）：

```properties
resource-pack=https://cdn.example.com/packs/survival-2026-10-04.zip
resource-pack-sha1=<40 桁の小文字十六進 SHA-1>
require-resource-pack=false
resource-pack-prompt={"text":"当サーバーは独自テクスチャパックを使用しています。有効化を推奨します。","color":"yellow"}
```

| キー名 | 型 | 既定値 | 意味 |
| --- | --- | --- | --- |
| `resource-pack` | 文字列（URL） | 空 | リソースパックのダウンロード先。空なら何も配信せず、プレイヤーは入場時にダウンロードするか選べる。**パックのサイズ上限は 250 MiB** |
| `resource-pack-sha1` | 文字列 | 空 | リソースパックの SHA-1。**小文字の 16 進**。クライアントが完全性を検証するのに使い、**記入を強く推奨** |
| `require-resource-pack` | 真偽値 | `false` | `true` のとき、**リソースパックの使用を拒否したプレイヤーはサーバーから蹴られる** |
| `resource-pack-prompt` | 文字列 | 空 | リソースパックを強制するときに表示する独自のプロンプト。チャットコンポーネント（JSON テキスト）の文法で、複数行も可能。空なら既定のプロンプト |
| `resource-pack-id` | UUID | 空 | 任意。このリソースパックに識別子を与える。**比較的新しいバージョンにしかないキー**で、旧バージョンで書いても効かない |

### 必ず知っておくべき細部

- **クライアントが直接ダウンロードできる HTTPS の URL でなければなりません。** 実際にはバニラのクライアントは HTTPS のリンクしか受け付けず、平文 HTTP や証明書に問題のあるアドレスはダウンロードに失敗します（クライアント側の検証はバージョンで変わるので公式ドキュメントを優先）。
- **ダウンロードの成否はクライアントのログにしか記録されず、サーバーからは見えません。** だから「サーバーにエラーが出ていない」はプレイヤーがパックを受け取った証拠になりません —— 切り分けでは必ずクライアントの `logs/latest.log` を見てください。
- サーバーはこのファイルを**ホストしてくれません**。公網からアクセスできる場所（オブジェクトストレージ、CDN、Nginx の静的ディレクトリなど）に置き、**ホットリンク防止・認証・HTML ページへのリダイレクトがない**ことを確認します。
- サーバーは起動時に `server.properties` を書き換えます：欠けているキーを補い、無効な値を既定値に戻し、**一部の特殊文字をエスケープ**します（`:` など）。だから `resource-pack-prompt` の JSON を手で書くのは可能ですが、ファイルにバックスラッシュが出てきたからといって書き間違いとは限りません。
- これらのキーを変えたら**サーバーの再起動が必要**です（`server.properties` は `/reload` では読み直されません）。

:::warn リソースパックの強制は諸刃の剣
`require-resource-pack=true` は**ダウンロードを拒否したプレイヤーをそのまま締め出します**。リソースパックを帯域の限られた小さなマシンでホストしていると、1 回の更新で全プレイヤーが同時にダウンロードし、帯域を使い切って「サーバーに入れない」と誤解されることさえあります。**強制する前にホスト側の帯域と可用性を確認し、いつでも強制を切れる状態にしておいてください。**
:::

## 4. SHA-1 を正しく計算する

ハッシュは**ファイル内容**の SHA-1 で、小文字の 16 進、40 文字です。

```bash
# Linux / macOS
sha1sum survival-2026-10-04.zip
```

```powershell
# Windows PowerShell：Get-FileHash は既定で大文字を出すので、小文字にしてから記入する
(Get-FileHash -Algorithm SHA1 .\survival-2026-10-04.zip).Hash.ToLower()
```

### ハッシュを間違えるとどうなるか

| 状況 | 結果 |
| --- | --- |
| ハッシュが実際のファイルと一致しない | クライアントはダウンロード後に検証で失敗し、**リソースパックが適用されない**。失敗はクライアントのログにしか出ず、サーバーは何も気づかない |
| ハッシュが 40 桁の 16 進文字列でない | プロトコルのドキュメントによれば、クライアントはそれで検証せず、**ダウンロード帯域を一度無駄にする** |
| サーバー起動時に `Invalid sha1 for resource-pack-sha1` | 設定の値が実際のパックと一致しない（または形式が不正）。コンソールに黄色のヒントが出る |
| パックを替えたのにハッシュを更新していない | プレイヤーがダウンロードと失敗を繰り返す。古いプレイヤーは古いパックを持ったままかもしれない |

:::tip 最もつまずきやすい 3 点
1. **再パッケージするとハッシュが変わる**：内容が同じでも、再圧縮（タイムスタンプ、圧縮レベルの違い）で別の zip になり、ハッシュも変わります。**ハッシュを計算した zip の現物を保管し、再圧縮しないこと。**
2. **アップロード中に変わりうる**：一部のプラットフォームは自動で圧縮、透かし、内容の書き換えをします。アップロード後に**もう一度ダウンロードして**、ローカルとハッシュが一致するか検証してください。
3. **大文字小文字**：`ABC...` と書くと有効なハッシュとして認識されないことがあります。小文字に統一してください。
:::

## 5. データパックはどこに置き、どう入れるか

データパックは**セーブデータディレクトリ**の `datapacks/` に置きます。サーバーのセーブデータディレクトリは `server.properties` の `level-name` で決まります（既定は `world`）：

```text
/opt/mcserver/
  server.properties          <- level-name=world
  world/
    datapacks/
      my-tweaks/             <- ディレクトリ形式のデータパック
      economy.zip            <- zip 形式のデータパック
    level.dat
    region/
```

導入手順：

1. データパックをダウンロードし（当サイトの収録は [データパックダウンロード](/downloads/datapacks)）、**`.zip` かディレクトリ**であることを確認する。
2. `<level-name>/datapacks/` に入れる。**zip の中に直接 `pack.mcmeta` がなければなりません**。フォルダを 1 層余計に包んではいけません —— フォルダを右クリックで圧縮すると 1 層余計になりがちです。
3. サーバーが稼働中なら：`/reload` を実行するか、`/datapack enable <名前>` で有効にする（一部の内容は再起動が必要。第 6 節を参照）。
4. 読み込まれたか検証する：

```text
/datapack list             すべてのデータパックを列挙
/datapack list enabled     有効なものだけを列挙
/datapack list available   利用可能だが未使用のものだけを列挙
```

出力にあなたのパック名が見えるはずです（zip 形式なら `file/<ファイル名>` と表示されます）。リスト上でマウスを重ねると `pack.mcmeta` に書いた `description` が見えます。

### 有効化、無効化、順序

```text
/datapack enable <名前>
/datapack disable <名前>
/datapack enable <名前> first        最も低い優先度に置く
/datapack enable <名前> last         最も高い優先度に置く
/datapack enable <名前> before <既存パック>
/datapack enable <名前> after  <既存パック>
```

- **順序が重要**：同名ファイルは**後に読み込まれたパックが先のものを上書き**します；タグファイルは既定で結合され、`"replace": true` を書いた場合を除きます。
- 権限レベル：`list` / `enable` / `disable` は権限レベル 2、`create` はレベル 4 が必要。
- 有効なパックの一覧は**セーブデータ**（`level.dat`）に保存されるので、**セーブデータを替えたりロールバックすると、有効なデータパックも一緒に変わる**。
:::note サーバーとシングルのセーブデータはパスが違う
シングルのセーブデータは `.minecraft/saves/<セーブ名>/datapacks/`、サーバーは**作業ディレクトリ下**の `<level-name>/datapacks/` です。置き場所の間違いは「データパックが効かない」の最もよくある原因です。
:::

## 6. `/reload` は結局何を再読み込みするのか

Java 版の `/reload` の役割は**現在有効なデータパックのデータを再読み込みする**ことです。万能ではなく、再起動とも違います：

| 内容 | `/reload` が効くか |
| --- | --- |
| レジストリのタグ（tags） | 再読み込みする |
| ルートテーブル（loot table） | 再読み込みする |
| レシピ（recipe） | 再読み込みする |
| 進捗（advancement） | 再読み込みする |
| アイテム修飾子、述語 | 再読み込みする |
| 関数（function、`.mcfunction`） | 再読み込みする |
| 構造物テンプレート（structure） | 再読み込みする |
| 動的レジストリ／実験的コンテンツを使う部分（ディメンション、バイオーム、ワールド生成、エンチャントなど。具体的な範囲はバージョンで変わる） | **しない**。サーバーの再起動が必要（シングルならワールドを出て入り直す） |
| `server.properties` などのコア設定 | **しない**。再起動が必要 |
| サーバーのプロセス、プラグインの状態 | **しない**。しかも `/reload` で壊れうる |

必ず覚えておく挙動が 2 つ：

1. **データパックに不正なデータがあると、変更は適用されず**、ゲームは以前のデータを使い続けます。だから「`/reload` したのに変わらない」は、再読み込みが効いていないのではなくパック自体の書き間違いであることがあります。
2. **プラグインサーバーでは `/reload` を慎重に。** プラグインの状態（スコアボード、リスナー、キャッシュなど）が壊れることがあります。`/datapack enable` / `/datapack disable` か、いっそ再起動で解決できるなら、後者を優先してください。

## 7. パック形式：`pack.mcmeta` と `pack_format`

`pack.mcmeta` はパックのメタデータファイルで、リソースパックもデータパックも使いますが、**要求されるフォーマット番号は別**です。

```json
{
  "pack": {
    "pack_format": <そのバージョンが要求する整数>,
    "description": "サンプルのデータパック"
  }
}
```

:::warn 上の `<そのバージョンが要求する整数>` はプレースホルダーで、そのまま使える JSON ではない
**本記事を含め、どのチュートリアルのフォーマット番号もそのまま真似しないでください。** `pack_format` の数値は Minecraft のバージョンごとに変わり、リソースパックとデータパックで別の体系です。間違えると「フォーマットが非互換」と表示され、パックは読み込まれません。
:::

### 自分のバージョンでいくつを書くか調べる方法

| 手段 | 説明 |
| --- | --- |
| 公式ドキュメント / Minecraft Wiki のパック形式表 | バージョンごとにリソースパックとデータパックのフォーマット番号が並んでいる。**これを優先** |
| 使っているサーバーコアのドキュメント | 一部のコアは現在のバージョンに対応する形式をドキュメントに記す |
| ゲームが出すヒント | 読み込み失敗時のヒントは通常「パックが宣言した形式」と「現在のバージョンが期待する形式」を併記する（文言はバージョンで変わる） |
| 現行バージョンの公式パックから逆算 | 公式のリソースパック／内蔵データパックの `pack.mcmeta` に何が書かれているか見る |

### バージョンに関わるそのほかのフィールド

`pack.mcmeta` には `pack_format` 以外のフィールドもあり、**フィールド自体もバージョンで進化しています**：

| フィールド | 役割 | 注意 |
| --- | --- | --- |
| `pack.pack_format` | そのパックの主要なフォーマット番号 | 比較的新しいバージョンでは任意になり、旧バージョンでは必須 |
| `pack.supported_formats` | フォーマットの範囲（`[42, 45]` など）を宣言 | 1.20.2 で導入され、**より新しいバージョンでは削除済み**。旧バージョンとの互換が必要なときだけ残す |
| `pack.min_format` / `pack.max_format` | 新しいバージョンが導入した最小／最大対応フォーマット（副バージョン番号付きも可） | `supported_formats` の役割を置き換えた |
| `pack.description` | ホバー時に表示されるテキスト。テキストコンポーネントに対応 | リソースパックもデータパックも使う |
| `pack.filter` | 優先度の低いパックのファイルを除外する（正規表現） | 1.19 で導入 |
| `pack.overlays` | バージョン帯ごとにサブディレクトリを重ねる | 1.20.2 で導入 |
| `features.enabled` | 実験的機能のフラグを有効にする | 対応する実験的スイッチが必要 |

**フィールドの名前、必須かどうか、フォーマット番号の値はすべて公式ドキュメントを優先**し、本記事や第三者のチュートリアルを基準にしないでください。

## 8. 性能とセキュリティ

### データパックは「サーバー側のコード」

関数の中身は**サーバーが実行する**コマンド列なので：

- **信頼できる出所のデータパックだけを入れてください。** 関数はコマンドにできることなら何でもできます：アイテム付与、テレポート、ワールド変更、コンテナの空化、プレイヤーを奈落へ落とすことまで。
- 導入前に**zip を開いて一目見る**：`data/<名前空間>/function/` に実行したくないコマンドがないか；`pack.mcmeta` の `description` と実際の中身が合っているか。
- 関数の権限レベルは `server.properties` の `function-permission-level`（既定 2）で決まり、関数がどこまで「高度な」コマンドを実行できるかが決まります。

### 毎 tick 実行される関数はサーバーを遅くする

- `minecraft:tick` の関数タグから参照される関数は**毎 tick（毎秒 20 回）実行**されます。数百のエンティティを走査する、毎 tick ブロックを設置／破壊する、といった処理は MSPT を着実に食います。
- `minecraft:load` から参照される関数は（再）読み込み時に 1 回だけ実行され、コストはずっと小さいです。
- `/schedule`、`execute if` などで「ポーリング」するなら、**毎秒実際に何回実行されるか**を計算してください。
- ラグが出たらまず定量化してから変える：[性能分析 spark](/tutorials/ops/spark) を参照。

```text
# あるパックに毎 tick の入口があるか：このファイルがあるかを見る
data/<名前空間>/tags/function/tick.json
```

### リソースパックの注意点

- リソースパックがクライアントで行うのは**素材の差し替え**で、コードは実行できないので「安全」面のリスクは低いです。ただし**ダウンロードと保存のコスト**は現実で、パックの上限は 250 MiB、更新のたびにプレイヤーは再ダウンロードします。
- 大きなパックは入場時間を目に見えて伸ばし、回線の弱いプレイヤーはそのまま諦めるかもしれません。**数 MB で済むものを数十 MB にしないこと。**
- リソースパックはあらゆるテクスチャを差し替えられるので、**プレイヤーを誤らせるのにも使えます**（普通の鉱石をダイヤ鉱石の絵にするなど）。マルチプレイサーバーではこれは公平性の問題で、単なる技術の問題ではありません。
- サーバーがリソースパックを配信しても、**プレイヤーが必ず使うとは限りません**：`require-resource-pack=true` でない限り拒否できますし、プレイヤー自身のクライアントのリソースパックの順序が配信されたパックを上書きすることもあります。

## 9. 切り分け表

| 現象 | よくある原因 | どう調べるか |
| --- | --- | --- |
| リソースパックがまったく配信されない | `resource-pack` が空か書き間違い。URL に到達できない。変更後にサーバーを再起動していない | `server.properties` のキー名の綴りと URL を確認。ブラウザか `curl -I` で zip を直接ダウンロードできるか確認 |
| プレイヤーが入場時にダウンロード失敗の表示 | HTTPS でない、証明書が無効、認証が必要、ホットリンク防止、返ってくるのが zip ではなく HTML | **クライアントのログを見る**（サーバーはダウンロード失敗を記録しない） |
| ハッシュ検証に失敗し、パックを繰り返しダウンロードする | `resource-pack-sha1` が実際のファイルと違う。再パッケージしたのにハッシュを更新していない。ハッシュが大文字、または長さが違う | 第 4 節の方法で再計算し、ダウンロードしたのが同じファイルか確認 |
| サーバーのコンソールに `Invalid sha1 for resource-pack-sha1` | そのキーの値が実際のパックと違う、または形式が不正 | 再計算して更新。確信がなければまず空にする（検証は失われる） |
| プレイヤーが拒否して入れない | `require-resource-pack=true` | `false` にして再起動。またはダウンロードの問題を直してから強制する |
| テクスチャが変わらない | パック内のパスや名前空間が間違い。`pack.mcmeta` がない、またはフォーマット番号が違う。優先度の高いパックに上書きされている。プレイヤー自身のクライアントのパックに上書きされている | `assets/<名前空間>/textures/...` のパスが正しいか確認。パックをリソースパック一覧の最上部に置く。バニラのクライアントで単独テスト |
| 一部のプレイヤーにしか効かない | プレイヤーがダウンロードを拒否した、または自分のリソースパックを使っている | 全サーバーで揃えるなら `require-resource-pack` を有効にし、先にホスト側の帯域を解決する |
| データパックが `/datapack list` に出ない | 置き場所が違う（`<level-name>/datapacks/` であるべき）。zip にフォルダが 1 層余計。`.zip` でもディレクトリでもない | `pack.mcmeta` がパックのルートにあるか確認。`unzip -l` で構造を見る |
| データパックは出るが効果がない | 有効でない。関数が `tick` / `load` タグから参照されていない。名前空間やパスが間違い。再起動が必要な内容 | `/datapack list enabled` で有効を確認。`/reload` 後にログのエラーを見る。必要なら再起動 |
| 「フォーマットが非互換」と表示される | `pack_format` が現在のバージョンと違う（リソースパックとデータパックで番号が違うので取り違えない） | 第 7 節に従って公式の形式表を調べ、正しい番号に更新 |
| `/reload` しても設定が変わらない | その内容が再起動必須の部分。またはパックに不正なデータがあり変更が丸ごと捨てられた | サーバーのログに読み込みエラーがないか見る。そのまま再起動して検証 |
| データパックを入れたら明らかに重い | `minecraft:tick` に載った関数の毎 tick コストが大きい | `tags/function/tick.json` を確認し、[spark](/tutorials/ops/spark) で特定 |

## 10. まとめ

- **リソースパックは見た目、データパックはルール**。前者はクライアント、後者はサーバー。
- **サーバーからのリソースパック配信は `server.properties` の 4 つのキー**：`resource-pack`、`resource-pack-sha1`、`require-resource-pack`、`resource-pack-prompt`（新しいバージョンには `resource-pack-id` も）。変更後は再起動。
- **ハッシュは実際のファイルと一致し、小文字 40 桁の 16 進**であること。計算後に再パッケージせず、アップロード後に再検証する。
- **データパックは `<level-name>/datapacks/`** に置き、`/datapack list` で検証する。`/reload` は一部しか再読み込みせず、動的レジストリとコア設定は再起動が必要。
- **フォーマット番号はバージョンで変わる**ので、必ず公式の表を調べ、チュートリアルを真似しない。
- **データパックはサーバー側のコード**：信頼できる出所だけを入れ、`tick` に載せた関数は性能を食い続ける。

リソースのダウンロード：[データパックダウンロード](/downloads/datapacks)。関連する読み物：[サーバーの構成](/tutorials/java/structure)（`datapacks/` の場所）、[サーバーの設定](/tutorials/java/config)（`server.properties` の他のキー）、[性能分析 spark](/tutorials/ops/spark)（関数によるラグの特定）、[バックアップと復元](/tutorials/java/backup)（セーブデータを替えると有効なデータパックも変わる）。

> パック形式のバージョンと設定キー名はゲームのバージョンで変わります。公式ドキュメントを優先してください。
