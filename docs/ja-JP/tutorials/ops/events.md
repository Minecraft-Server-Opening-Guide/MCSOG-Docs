[宣伝と集客](/tutorials/ops/promotion) が扱うのは「プレイヤーがどうあなたを見つけるか」、[経済と遊び方プラグイン](/tutorials/ops/gameplay-plugins) が扱うのは「サーバーにどんな仕組みがあるか」、[[JAVA] 運用管理](/tutorials/ops/management-java) が扱うのは「チームとお金をどう配置するか」です。この 3 つはすべて**枠組み**の話です。この記事が扱うのは、枠組みの中で実際に起きることです。**ある夜、何人かがあなたのサーバーで一緒に何かを成し遂げ、終わったあともう一度来たいと思う。**

イベントは運営の飾りではありません。互いに知らないプレイヤーの集まりをコミュニティに変える最短の道であり、古参のプレイヤーが戻ってくる理由を作れる数少ない手段の 1 つです。同時に最も失敗しやすい部分でもあります。時間を間違える、ルールを書いていない、会場を作っていない、報酬が経済を壊す。どれか 1 つでも、そこそこ良いイベントが一気に離脱の波になります。

本記事は具体的なプラグインの選定には触れません。プラグインの一覧が必要なときは [プラグイン入門](/tutorials/java/plugins) と [よく使う前提プラグイン](/tutorials/java/plugin-deps) を参照してください。

:::note 本記事の範囲
本記事では、具体的なイベント用プラグイン、ミニゲーム用プラグイン、報酬用プラグインの名前、コマンド、設定キーは一切挙げません。**こうしたプラグインは名前、機能、使えるコマンド、設定項目の差が大きく、しかもバージョンで変わります**。そのため本記事は「どういう種類のことをするのか、その種類のことは通常どういう種類のツールが担うのか」だけを説明します。あなたのサーバーに何が入るか、設定をどう書くかは、各プラグインの公式ドキュメントに従ってください。
:::

## 1. イベントを行う価値

### 1.1 新規プレイヤーは最初の数分で決めている

新規が入室してからの数分が、残るかどうかを決めます。その時間に彼が向き合う問題は「遊び方が足りるか」ではなく、**「ここに誰かがいるか、自分は何をすればいいのか」**です。空っぽのスポーン地点に長い説明書が添えられているより、「今夜 8 時にパルクール大会がある、来てね」のほうがはるかに効きます。

### 1.2 復帰するプレイヤーには具体的な理由が要る

「サーバーはまだ動いている」は戻る理由になりません。「土曜の夜に建築コンテストがある、前回建てたあの家を出せる」なら理由になります。イベントが与えるのは**時点**であり、人は状態の判断よりも時点に強く反応します。

### 1.3 イベントがサーバーをコミュニティにする

プレイヤー同士の関係はルールで築かれるのではなく、**共通の経験**で築かれます。一緒にレイドに負ける、一緒に宝探しで道を間違える、一緒に誰かの建てた城をぼんやり眺める。こうしたものが「私たちは同じサーバーの人間だ」の源です。

| プレイヤーの状態 | 本当に問うていること | イベントが提供できるもの |
| --- | --- | --- |
| 入室したばかりの新規 | ここに人はいる？何をすればいい？ | すぐ参加でき、敷居が極めて低いイベント |
| 数日遊んだプレイヤー | 家を建てる以外に何ができる？ | 明確な時点と、一緒に遊ぶ人 |
| 数週間遊んだ古参 | ここに残る意味は何？ | 身分、名誉、必要とされる役割 |
| しばらく離れていた人 | 戻る理由はある？ | イベントの通知 1 本がその理由になる |
| グループで喋るだけの人 | 自分はこのサーバーの一員？ | 顔を出して覚えてもらえる機会 |

:::tip イベントの本当の産物は報酬ではない
報酬は配れば終わりですが、**共通の記憶は残ります**。イベントの成否を見るときに見るのは「賞を配ったか」ではなく、「終わった後にチャットがまだ熱いか、次はいつかと誰かが聞いたか」です。終了と同時に静まり返るなら、それはイベントというより 1 回の配布です。
:::

:::warn イベントは万能薬ではない
イベントは、すでに遊べるサーバーを増幅しますが、**面白くないサーバーを修理はしません**。新規が離れる理由がスポーン地点の分かりにくさ、ラグ、誰も相手にしないことなら、イベントを開くとより多くの人に、より早くその問題が見えます。まず体験を解決し、それからイベントを語ってください。
:::

## 2. イベントの種類一覧

以下はカテゴリ別のよくあるイベントです。表の「何を用意するか」はカテゴリだけを書き、具体的にどのツールが担うかは各プラグインの公式ドキュメントで確認してください。

| 種類 | 例 | 何を用意するか | 向く人数 | リスク |
| --- | --- | --- | --- | --- |
| 建築コンテスト | テーマ建築戦、1 時間スピードビルド、スポーン地点の改装 | 区画を切った会場、採点基準、審査員、作品の保護 | 5〜50 人 | 採点が主観的で紛争になる。作品が壊される。時間切れで終わらない |
| PvP 競技会 | 1v1 の決闘、チーム戦、装備を統一したリング戦 | 競技場、統一装備の方案、審判、観戦席、リスポーン地点 | 8〜40 人 | 装備と遅延が不公平。談合で順位を稼ぐ。観戦が試合を妨げる |
| パルクール競走 | 競走コース、制限時間内のクリア、チームリレー | コース、計測方法、チェックポイントと落下の扱い | 5〜30 人 | コースの抜け道を突かれる。切断で記録が無効になる。計測の定義が曖昧 |
| 宝探し / 謎解き | 宝の地図、座標の謎、制限時間付きの探索 | 手がかりの設計、隠し場所の一覧、答え合わせの担当 | 10〜100 人 | 手がかりが事前に漏れる。マップファイルを直接開く人が出る |
| Boss / レイドの夜 | 強敵への集団挑戦、制限時間付きの討伐、ドロップの配分 | 戦闘の会場、難易度と人数の整合、ドロップのルール | 10〜30 人 | 人数が足りず倒せない。ドロップの配分で喧嘩になる。サーバーの負荷が高い |
| 季節のイベント | ハロウィン、新年、サーバー周年 | 装飾、期間限定の遊び方、季節の報酬 | 全サーバー | 日程が重なる。装飾の変更が通常の遊び方に影響する |
| コミュニティ目標 | 全サーバー共同の建設、累計の収集目標 | 進捗の表示、貢献の記録、段階ごとの報酬 | 全サーバー | 少数が抱え込む。途中で進捗が止まりやる気を失う |
| 新規歓迎会 | 集団での歓迎、古参が新規を導く、新規向けの回 | 当番の人員、説明の流れ、歓迎のパッケージ | 5〜20 人 | 古参が目立ちすぎる。新規が話に入れない。一方通行の講義になる |
| ストーリー / RP イベント | 台本の上演、陣営対抗、ワールドイベント | 台本、役の割り当て、会場と道具、進行役 | 10〜30 人 | 台本が中断される。設定どおりに動かない人がいる。準備量が極めて大きい |

### 2.1 種類ごとの設計の要点

| 種類 | 設計で最も力を入れるところ | 最もよくある失敗 |
| --- | --- | --- |
| 建築コンテスト | 採点基準を事前に公開し、採点できる数項目に分解する | 審査員が好みで点を付け、参加者がその場で納得しない |
| PvP 競技会 | 装備、エンチャント、ポーション、遅延の 4 項目を統一するか明示する | 自分で貯めた装備を持ち込み、試合が一方的な蹂躙になる |
| パルクール競走 | 計測の始点と終点を一意にし、再現できるようにする | 近道をする人が出るのに、規約に「チェックポイント必須」がない |
| 宝探し / 謎解き | 手がかりの難易度を段階化し、最初の 10 分は全員にやることがあるようにする | 最初の謎で全員が詰まり、10 分で解散する |
| Boss / レイドの夜 | 人数と難易度を合わせ、ドロップのルールを事前に明示する | 討伐後の配分で喧嘩になり、倒せないより傷つく |
| 季節のイベント | 装飾と期間限定の遊び方をワンクリックで戻せるようにする | 終了後も装飾が本拠地に残り、長期的に体験を損なう |
| コミュニティ目標 | 進捗を見えるようにし、個人の貢献を記録する | 目標が大きすぎて、3 日後には誰も触れなくなる |
| 新規歓迎会 | 新規を主役にし、古参は導く役に徹する | 管理者の一方通行の講演会になる |
| ストーリー / RP イベント | 台本にプレイヤーが自由に動ける余地を残す | プレイヤーが台本どおりに動かず、進行役がその場で固まる |

:::note 小規模サーバーは「準備コストの低い」種類を優先する
人手が少ないとき、パルクール競走、宝探し、新規歓迎会の費用対効果は、ストーリーイベントや大型レイドよりはるかに高いです。**イベントの規模は、あなたが投じられる準備時間に合わせる**のであって、想像上のサーバー規模に合わせるのではありません。
:::

### 2.2 サーバーの種類でイベントを選ぶ

同じイベントでも、サーバーの種類が違えば結果は正反対になり得ます。種類を選ぶ前に、自分のサーバーのポジショニングを見てください（ポジショニングの書き方は [宣伝と集客](/tutorials/ops/promotion)）。

| サーバーの種類 | 優先して検討するイベント | できるだけ避けるイベント |
| --- | --- | --- |
| バニラサバイバルサーバー | 建築コンテスト、コミュニティ共同建設、宝探し、季節のイベント | 高強度の PvP 競技、ワールドの状態を壊す遊び方 |
| レッドストーン技術（生電）/ 技術サーバー | 技術チャレンジ、メカニズムの謎解き、全サーバー共同の建設 | 大量のエンティティとエフェクトに依存する混戦型 |
| ミニゲームサーバー | ランク戦、週次大会、期間限定モードのローテーション | 長期的な積み上げがないと参加できないイベント |
| RP / ロールプレイサーバー | ストーリーイベント、陣営対抗、ワールドイベント | 純粋な競技系、設定と無関係な娯楽 |
| 統合版（基岩版）/ クロスプラットフォームサーバー | 敷居が低く、クライアントの MOD に依存しないイベント | 特定のクライアント機能に依存する遊び方 |
| MOD サーバー | MOD のメカニズムと結びついたイベント | MOD のメカニズムと衝突する、または追加のクライアント設定が必要なイベント |

## 3. イベントをどう企画するか

### 3.1 時間を決める：まずプレイヤーがどのタイムゾーンにいるかを確認する

ここが最も間違えやすく、最も見落とされやすい手順です。あなたのプレイヤーは複数のタイムゾーンに散らばっているか、あなたが住んでいないタイムゾーンに集中しているかもしれません。

- **あなたではなくプレイヤーを基準に**。中心となるプレイヤー層が別のタイムゾーンにいるなら、イベントの時間は彼らの生活時間に合わせます。たとえあなたにとって未明でも。
- **まず聞いてから決める**。グループで簡単な投票をしたほうが、自分で推測するよりはるかに有効です。
- **タイムゾーンを明記する**。告知に「20:00」だけでは足りません。「北京時間 20:00」と書き、主要なプレイヤーのタイムゾーンに換算した時刻も添えます。
- **平日の昼間、試験週間、連休の移動ピークを避ける**。週末の夜が最も安定した選択です。
- **十分な余裕を持たせる**。小規模なイベントは少なくとも 2〜3 日前、大規模なイベントは 1〜2 週間前から。

### 3.2 事前に、繰り返し告知する

1 回だけの通知は通知していないのと同じです。プレイヤーは 3 日前のメッセージは覚えませんが、繰り返し現れる同じ時点は覚えます。

- **少なくとも 3 回**：日程を決めたとき、1〜2 日前、開始 1〜2 時間前のリマインド。
- **内容を一致させる**。3 回の告知で時刻、場所、ルールが変わってはいけません。変えるなら「どこを変えたか」を明示します。
- **複数の経路で届ける**：ゲーム内の告知、グループの告知、サーバーリストページの紹介、入室時のウェルカムメッセージ。宣伝経路の選び方は [宣伝と集客](/tutorials/ops/promotion) を参照。
- **「どう参加するか」を告知に書く**。プレイヤーが参加方法を知るために誰かに聞かなければならない状態にしないでください。

### 3.3 ルールを書き下ろす

口頭のルールは、紛争が起きた瞬間に消えます。**書き下ろしたルールは、どんな議論よりも強い。**

- 「何が許され、何が禁止され、誰が判定し、引き分けはどうするか、違反をどう処理するか」を書く。
- ルールはイベントの開始前に公開し、問題が起きてから補足するのではありません。
- ルールは短く。1 画面を超えるルールは誰も読みません。最も重要な 3〜5 条を先頭に置きます。
- サーバー全体の規約と衝突する場合は全体の規約が優先します。[コミュニティ規範](/rules) を参照。

### 3.4 会場は事前に建て、事前に読み込む

**イベントが始まってから会場を作り始めてはいけません。** 現場での設営はほぼ必ず遅れ、プレイヤーの待ち時間が離脱に変わります。

- **独立したワールドかインスタンスで会場を用意する**のが第一候補で、次が「スポーンから遠く離れた場所に建てる」。前者の利点は、メインワールドに影響せず、メインワールドのチャンク読み込みを占有せず、終了後にまとめて停止できることです。
- **メインワールドに建てるしかない場合**は、スポーン地点と主要な建築エリアから離れた場所を選び、プレイヤーがテレポートしてきたときに大量のチャンクを巻き込んで読み込まないようにします。
- **関連するチャンクを事前に読み込んでおく**。最初のチャンク読み込みは最も高価な操作の 1 つです。開始前に会場を歩き、関連する領域を読み込み済みの状態にしておけば、開幕のラグを明確に減らせます。事前読み込みの具体的な方法は、サーバーと使うプラグインによります。
- **会場は開始前に一通り演習する**。頭の中で 10 回シミュレーションするより、自分で 1 回流すほうが役に立ちます。

### 3.5 役割を人に割り当てる

1 人でイベントを運営するのは、緊急時の計画がないのと同じです。少なくとも以下の役割を明確にし、人手が足りないときは同一人物が兼ねてもかまいませんが、**責任者がいる**必要があります。

| 役割 | 何を担うか | 何人必要か | よくある誤り |
| --- | --- | --- | --- |
| 進行役 | 流れを宣言し、テンポを制御し、開幕と締めを担う | 1 人 | 進行しながら技術対応もして、どちらも手が回らない |
| 審判 | 勝敗を判定し、違反と紛争を処理する | 1〜2 人 | 審判が同時に参加し、判定の信憑性が失われる |
| 建築 / 会場 | 開始前に会場と道具を準備する | 1 人以上 | 当日になっても会場を直している |
| 技術サポート | 切断、ラグ、テレポートの失敗、権限の問題を処理する | 1 人 | 担当がおらず、問題が起きても全員が黙る |
| 記録 | スクリーンショット、録画、結果と貢献を記録する | 1 人 | イベントは終わったのに、使える画像が 1 枚もない |

:::tip 審判は参加できない
厳しく見えますが、**最も紛争が少ない**やり方です。どうしても人手が足りないなら、審判は自分が関わる試合を外れ、判定の過程を公開してください。信憑性を一度失うと、以降のすべてのイベントが疑われます。
:::

### 3.6 緊急時の計画

イベント当日は必ず何かが起きます。違いは準備があるかどうかだけです。

| 起こり得る問題 | 現場での対応 | 事前にやっておくこと |
| --- | --- | --- |
| サーバーのラグ、TPS の低下 | 進行を止めるか短縮し、同時に動くエンティティとエフェクトを減らす | 事前に負荷試験をし、簡略版の流れを用意する |
| 主要なプレイヤーが切断 | 再接続の待ち時間を示し、超過はルールどおりに処理する | 規約に「切断したらどうするか」を書く |
| 人数が想定よりはるかに少ない | 少人数のグループ制に変える、または自由参加に変える | 「人数が少なくても遊べる」代替案を用意する |
| 人数が想定よりはるかに多い | 分割して進行する、または会場と回を追加する | 収容の上限を事前に見積もる |
| 誰かがチートや破壊をした | 直ちに隔離し、規約どおりに処理し、事後に記録を残す | 規約に判定と処分を明記する |
| 時間が大幅に超過 | 後半の段階を削り、まず締めを確保する | 各段階に時間の上限を設ける |
| 報酬を配れない | 名簿を記録し、終了後に追って配る | 配布の方法と権限を事前に確認する |

### 3.7 イベント計画のテンプレート

次のテンプレートを埋め終えれば、イベントはほぼ準備できています。**埋められない空欄が、まだ準備できていない場所です。**

```
イベント名：______（何なのかを一文で言える）
時間：______（日付 + 開始時刻 + 予想所要時間 + タイムゾーン）
場所：______（ワールド / 座標 / インスタンスかどうか。プレイヤーはどう行くか）
参加方法：______（どう申し込むか、当日参加できるか、チームを組むか）
ルール：______（許されることと禁止、判定基準、引き分けの扱い）
報酬：______（順位と内容、配布の方法と時期）
担当者：______（進行 / 審判 / 建築 / 技術サポート / 記録はそれぞれ誰か）
緊急時の計画：______（ラグ、切断、人数の異常、チートのときにどうするか）
```

## 4. 報酬と経済の安全

### 4.1 報酬が経済を壊す理由

報酬はイベントで最も制御を失いやすい部分です。プレイヤーの資産に直接リソースを注入するからです。経済システムの弱点とよくある事故は [経済と遊び方プラグイン](/tutorials/ops/gameplay-plugins) を参照してください。イベントでは、とくに 3 つの状況に警戒が必要です。

- **報酬の規模が制御できない**。1 回のイベントで配る量が、プレイヤーが普通に数日遊んで産出する量を超えると、市場はその場で壊れます。
- **報酬が繰り返し稼げる**。イベントに何度でも参加でき、毎回同じものを配るなら、それは「イベント」ではなく「資源のダンジョン」になります。
- **報酬が希少資源に結びついている**。経済体系の基軸通貨をイベントの賞品にするのは、経済に時限爆弾を仕掛けるのと同じです。

### 4.2 外見の報酬と物質の報酬

| 報酬の種類 | 例 | 経済への影響 | 向く場面 |
| --- | --- | --- | --- |
| 外見系 | 称号、ペット、装飾アイテム、建築の展示枠 | ほぼ影響なし。繰り返し換金もされない | ほぼすべてのイベントの第一候補 |
| 名誉系 | ランキングの順位、告知での称賛、専用の身分表示 | 影響なし | 競技系、コンテスト系 |
| 記念系 | イベント専用の記念品、記念の建築 | 影響はごく小さい。取引不可か数量限定が前提 | 季節のイベント、周年 |
| 利便系 | 1 回限りのテレポート、一時的な強化、便利アイテム | 強さと取引可否による | 慎重に。長期的な積み上がりを避ける |
| 物質系 | 通貨、希少な素材、強力な装備 | 経済に直接影響し、インフレを起こし得る | 少量、1 回限り、総量を厳しく管理 |

:::warn サバイバルサーバーでクリエイティブ専用のアイテムを配らない
**サバイバルサーバーでクリエイティブモードでしか得られないアイテムを配ると、ほぼ確実に問題が起きます。** そうしたアイテムは通常の遊び方では得られないため、プレイヤーの手に渡った瞬間に複製不可能な希少品となり、闇市場、詐欺、「管理者が知り合いに配っている」という指摘を生みます。報酬を特別に見せたいなら、規約の境界を壊すアイテムではなく、称号、装飾、展示枠を使ってください。
:::

### 4.3 配布は記録に残す

- **報酬の一覧を事前に決める**。当日にその場で積み増さない。
- **受賞者ごとに配布時刻を記録する**。「確かに 1 位だったのに受け取っていない」という紛争を避けます。
- **配布の経路をできるだけ統一する**。「誰かが内緒で受け取った」という疑念を減らします。
- **報酬の内容を公示する**。公開された報酬の一覧そのものが公平性の一部です。

## 5. 公平性と悪用の防止

技術面のチートと破壊の防止は [アンチチートと荒らし対策](/tutorials/java/anticheat) を参照してください。この節で扱うのは、イベントのルール面での公平性です。

### 5.1 チームは均衡していなければならない

チーム戦の公平性は、分けるその瞬間に決まります。最強の数人を同じチームにすると、試合は 30 秒で終わり、残りは付き合わされるだけです。

- **能力で分け、関係で分けない**。プレイヤーに自分で仲間を選ばせると、ほぼ必ず「上手い人同士が固まる」ことが起きます。
- **分け方の根拠を公開する**。「申し込み順に蛇腹で割り当てる」だけでも、書いてあれば密室の操作より信頼できます。
- **ハンデの仕組みを用意する**。たとえば弱いチームに追加の資源、強いチームの装備に上限を設ける。
- **観戦を許す**。敗退した人がただ待つだけなら、次の回には申し込みません。

### 5.2 サブアカウントとアカウント共有

イベントで最もよくある、しかも最も見つけにくい悪用です。ランキングと報酬の配布の両方を壊します。

- **規約で明確に禁止する**。複数アカウントでの参加とアカウント共有を禁じ、判定方法と結果も書きます。
- **アカウントではなくプレイヤーで集計する**。同一人物の複数アカウントは同一人物として扱います。
- **異常なシグナルに注意する**。同じ IP、同じ時刻のログイン、アカウント間のアイテム移動、イベントの期間だけ現れるアカウント。
- **処分には証拠が必要**。疑いは証拠ではありません。処分は記録を残さなければ、正常なプレイヤーを傷つけます。

### 5.3 途中から参加するプレイヤー

イベントが始まってから入室した人は、扱いを間違えると双方を敵に回します。

- **規約に事前に書く**。途中参加が可能か、参加した場合に成績へ算入するか、報酬を受け取れるか。
- **統一した基準を示す**。最もよくあるのは、観戦と自由参加は認めるが成績は次の回から、という扱いです。
- **その場で規約を変えない**。1 人のために規約を変えるのは、すでに参加した全員への不公平です。

### 5.4 その場の紛争をどう処理するか

紛争は必ず起きます。鍵は、あらかじめ処理の経路があるかどうかです。

- **まず規約を見て、それから現場を見る**。規約があれば規約で判定し、その場の思いつきで判断しない。
- **判定は理由を公開して説明する**。一言でもかまいません。
- **感情のままに決めない**。誰かがあなたを罵倒したことと、その人が規約に違反したかは別です。
- **紛争が大きくなったら一時停止する**。5 分止めるほうが、全員が見ている前で口論するよりましです。
- **事後にまとめて振り返る**。規約に書き切れていなかった点は次の回に補います。その場で勝ち負けを争うより価値があります。

## 6. 技術的な準備

### 6.1 会場

- **独立したワールドかインスタンスを優先**し、次にメインワールドの遠隔地。理由は 3.4 を参照。
- **開始前に流れを一通り通す**。テレポート、リスポーン、計測、報酬の配布の各段階を含めて。
- **終了後に片付ける**。臨時の会場、臨時の権限、臨時の道具はワンクリックで戻せるように。さもないとサーバーに残り続けます。
- **開始前にメインワールドを急に変えない**。変更のリスクは当日に集中して噴出します。

### 6.2 ミニゲームの仕組みと独立したミニゲームサーバー

- **小規模なイベント**は通常、「ミニゲーム / アリーナ」系のプラグイン 1 つで足ります。会場の隔離、チーム、得点、リスポーンを担います。
- **大規模または高頻度のイベント**は、独立した minigame サーバーに置き、プロキシでプレイヤーを送るほうが向きます。[プロキシ](/tutorials/java/proxy) を参照。利点は、イベントの遊び方がメインワールドを汚さず、負荷も分かれることです。
- **サーバーをまたぐイベントはもう一度検証する**。プロキシ越しのテレポート、権限の継承、チャットのチャンネル、報酬の配布は、またいだ時点で問題が起き得ます。開始前に検証してください。
- **具体的なプラグイン名、コマンド、設定項目は各プラグインの公式ドキュメントに従ってください。** 本記事では挙げません。バージョンで変わるうえ、設定をそのまま写すのは書かないより危険なことが多いからです。

### 6.3 イベントの前後でバックアップする

イベントは「ワールドの状態が最も集中して変化する」時間帯です。会場を壊す人、報酬を持ち去る人、妙な場所で切断する人が出ます。バックアップの方法と検証は [バックアップと復元](/tutorials/java/backup) を参照してください。

- **イベント前のバックアップ**：事故が起きたら開始前の状態へ直接戻せます。
- **イベント後のバックアップ**：イベントの成果（建築、記録、報酬の配布）を固定します。
- **バックアップは復元できることを検証する**。検証していないバックアップはバックアップに数えません。

### 6.4 ラグのリスク

:::warn 大きなイベントはサーバーが最も重くなる時間帯
**人数が多く、エンティティが多く、エフェクトが多いイベントは、年間で最もサーバーが重くなり、クラッシュしやすい瞬間です。** 大量のプレイヤーが同じ区域に集中し、同時に大量のエンティティとパーティクルが生まれ、同時に大量のプラグインのロジックが走るため、負荷は普段のピークをはるかに超えます。

だから**事前に測る**。実際に近い人数と流れでリハーサルを 1 回行い、TPS と MSPT の変化を観察してください。リハーサルでフレームが落ちるなら、本番はもっと悪くなります。分析方法は [spark でサーバー性能を分析する](/tutorials/ops/spark) を参照。同時に「簡略版の流れ」を用意し、重くなったらすぐ切り替えられるようにします。
:::

イベント前の技術チェックは、この表で 1 項目ずつ確認できます。

| 確認項目 | なぜ重要か |
| --- | --- |
| 会場のチャンクを事前に読み込んだ | 開幕にチャンクが集中して読み込まれて重くなるのを避ける |
| プレイヤーのテレポートとリスポーン地点を試験した | テレポートの失敗はイベントを直接中断させる |
| 権限と一時的な身分を設定した | 進行役と審判には相応の権限が必要 |
| 報酬の配布手順を演習した | 配れないのは、配らないより見苦しい |
| 観戦と傍聴の経路を用意した | 敗退した人にもやることを与える |
| 前後のバックアップを手配した | 事故の後に既知の状態へ戻せる |
| 代替の流れを用意した | ラグや人数の異常時にすぐ切り替えられる |
| 記録の担当を配置した | 事後にスクリーンショット、結果、フィードバックが必要 |

## 7. イベントの後

イベントが終わった瞬間、仕事はまだ半分です。**締めのないイベントは、開催していないのと同じ。**

### 7.1 結果とスクリーンショットの公開

- 順位、受賞者名簿、判定の根拠を公開する。
- スクリーンショットや録画を公開する。これは「イベントが本当に起きて、本当に人が来た」ことを示せる唯一のものであり、次のイベントの最高の宣伝素材でもあります。
- 結果を長期的にアクセスできる場所に固定し、チャットログに埋もれさせない。

### 7.2 手伝ってくれた人への感謝

- 進行、審判、建築、技術サポートに公開で感謝する。**手伝ってくれる人はあなたの最も希少な資源**であり、見られる必要があります。
- 誰が何をしたかを記録する。次のイベントでは、この名簿があなたの班になります。
- 参加者にも反応を示す。一言のまとめでもかまいません。

### 7.3 フィードバックを集める

- **具体的に問う**。「楽しかった？」だけにしない。「どの段階が最も退屈だったか」「どこで詰まったか」「次は何を遊びたいか」を聞きます。
- **フィードバックの窓口を 1 つに固定する**。意見を各グループに散らばらせない。
- **「意見」と「感情」を分ける**。誰かが罵倒したからといって、その意見に価値がないわけではありませんが、従わなければならないわけでもありません。

### 7.4 振り返りの記録

イベントのたびに短い記録を書き、次の内容を含めます。

- 実際の参加人数と予想との差；
- どの段階が時間超過し、どの段階に誰も来なかったか；
- どんな技術的問題が出て、どう解決したか；
- 紛争をどう判定し、規約のどこが書き切れていなかったか；
- 次に変える 3 つのこと。

この記録は長くなくてかまいませんが、**必ず書いてください**。3 か月後には、なぜ 5 分止まったのかを覚えていません。

### 7.5 決まったリズムを作る

散発的なイベントは熱意に頼り、継続するイベントはリズムに頼ります。プレイヤーに「いつ必ず何かが起きるか」を知らせるほうが、毎回の場当たり的な通知よりはるかに有効です。

| リズム | 規模 | 目的 | 注意 |
| --- | --- | --- | --- |
| 週 1 回の小さなイベント | 30〜60 分、準備コストが低い | 日常の活発さを保ち、新規に入口を与える | 種類を回す。毎週パルクールにしない |
| 月 1 回の大きなイベント | 2 時間以上、事前の準備が必要 | 話題を作り、離れたプレイヤーを呼び戻す | 1〜2 週間前から宣伝する |
| 季節 / 周年のイベント | 現実の季節に合わせる | 流れに乗って流入と復帰を狙う | 日程が他の大きなイベントと重ならないように |
| 長期的なコミュニティ目標 | 数週間にわたる | 全サーバーに共通の目標を与える | 進捗が見えなければならない |

:::tip リズムはアイデアより重要
プレイヤーはあなたがどのイベントを開いたかは覚えませんが、「このサーバーは毎週土曜の夜にイベントがある」ことは覚えます。**予測できること自体が魅力です。** 週に 1 回の素朴な小さなイベントを続けるほうが、3 か月に 1 回の盛大なイベントを開いて消えるよりよいです。
:::

## 8. 1 ページのイベントチェックリスト

### 8.1 イベントの前に

- [ ] イベントの種類を決め、投じられる準備時間と釣り合っている
- [ ] 主要なプレイヤーのタイムゾーンで時間を決め、タイムゾーンを明記した
- [ ] 少なくとも 2〜3 日前（大規模は 1〜2 週間前）から宣伝を始めた
- [ ] 宣伝を少なくとも 3 回行い、内容が前後で一致している
- [ ] 規約が成文化され、公開され、判定基準と引き分けの扱いを含む
- [ ] 会場を独立したワールドかインスタンスに建て、事前に読み込んだ
- [ ] 流れを一通りリハーサルした。テレポート、計測、報酬の配布を含む
- [ ] 進行、審判、建築、技術サポート、記録の担当者を人単位で決めた
- [ ] 審判は参加しない（または関係する回を外れた）
- [ ] 報酬の一覧を決め、経済への影響の規模を見積もった
- [ ] サバイバルサーバーでクリエイティブ専用のアイテムを配っていない
- [ ] チームの分け方を決めて公開し、仕組みの上でできるだけ均衡させた
- [ ] 複数アカウントとアカウント共有の判定方法を規約に書いた
- [ ] 途中参加、切断、時間超過の扱いを規約に書いた
- [ ] 緊急時の計画を用意した：ラグ、切断、人数の異常、チート
- [ ] イベント前のバックアップを終え、復元できることを検証した
- [ ] イベント後のバックアップを手配した
- [ ] 主要なプレイヤーと観戦者の経路を用意した

### 8.2 イベントの最中に

- [ ] 開幕に流れ、規約、時間の上限をまず説明する
- [ ] 各段階の長さを管理し、超過したら次の段階へ進む
- [ ] 紛争は規約で判定し、理由を公開して説明する
- [ ] 重くなったら直ちに簡略版の流れへ切り替える
- [ ] 全体を記録する：スクリーンショット、録画、順位、受賞者名簿

### 8.3 イベントの後に

- [ ] 結果と受賞者名簿を公開し、判定の根拠を添えた
- [ ] スクリーンショットか録画を公開した
- [ ] 手伝ってくれた人に公開で感謝した
- [ ] 報酬を一覧どおりに配布し、記録を残した
- [ ] フィードバックを集め、意見と感情を分けた
- [ ] 振り返りの記録を書いた。次に変える 3 つのことを含む
- [ ] 臨時の会場、臨時の権限、臨時の道具を片付けた
- [ ] 次のイベントの時間を公開した
