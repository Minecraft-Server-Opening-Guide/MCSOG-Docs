サーバーで問題が起きる典型は 2 つです。

1 つ目：プレイヤーがグループで「サーバーが落ちた」と言い、パネルを開くと確かに起動していないので、そこから調べ始める。**これは事後分析**で、道具は [spark でサーバー性能を分析する](/tutorials/ops/spark) です。

2 つ目：ディスクの空きが 3% しかなく、バックアップスクリプトが 3 日連続で失敗し、メモリが swap を使い始めるまで上がっているのに、**あなたはまったく知らない**。セーブデータが書けなくなるまで気づかない。

この記事は 2 つ目を扱います。核心の問いは 1 つだけです。**事故が起きる前にマシンのほうからあなたに知らせに来させるには、どうすればよいか。**

本記事は [spark でサーバー性能を分析する](/tutorials/ops/spark) と補完関係にあります。spark は「さっきなぜ重かったか」に答え、監視とアラートは「いま事故になりそうか」に答えます。データ保全は [バックアップと復元](/tutorials/java/backup) と [遠隔地バックアップ](/tutorials/ops/offsite-backup)、ホストの強化は [システムのセキュリティ強化](/tutorials/ops/system-security) を参照してください。

:::warn 本記事の設定は公式ドキュメントに従ってください
以下に登場するポート、パス、サービス名、設定キーは**ディストリビューション、導入方法、ソフトウェアのバージョンで変わります**。サンプルの役割は「何を設定すべきか」を示すことであり、**そのままコピーできる完成品ではありません**。適用する前に、Prometheus、node_exporter、Grafana、Uptime Kuma、NUT の公式ドキュメント、および自分のシステムで実際に生成された設定ファイルと照合してください。
:::

## 1. 監視は結局何を監視しているのか

まずまったく異なる 2 種類を分けます。「監視が役に立たない」という挫折感の多くは、両者を混同することから来ます。**資源とサービスの状態**（CPU、メモリ、ディスクの空きと I/O、ネットワーク、サービスが動いているか、証明書が期限切れに近いか）は客観的な数字で、曲線にでき、しきい値のアラートに向きます。**ゲーム体験の指標**（TPS、MSPT、プレイヤー数、ログイン失敗率）はサーバー側が公開して初めて得られ、「プレイヤーの実感」の代理指標です。第 1 類は**必ず監視**します。悪化が漸進的で目に見えないからです。第 2 類は**監視する価値があります**が、限界を知っておく必要があります。TPS は平均量でスパイクを均してしまい、MSPT が良くてもプレイヤーが重いと言うなら、問題はネットワークかクライアントかもしれません。

### 1.1 必ず監視すべき一覧

| 項目 | なぜ必須か | 典型的な悪化の仕方 |
| --- | --- | --- |
| 可用性 / 稼働時間 | サービスが落ちても誰も気づかないのは、最も深刻で最もよくある事故 | プロセスのクラッシュ、OOM による kill、起動時に自動起動しない |
| TPS / MSPT | プレイヤーの体験を直接決め、「最適化すべきか」の根拠にもなる | エンティティの堆積、プラグインのホットスポット、チャンク生成 |
| CPU | メインスレッドは単一スレッドで、**1 コアを使い切れば TPS が落ちる**。他のコアが暇でも | プレイヤーの増加、レッドストーン装置、ホストのオーバーセール |
| メモリ | ヒープも常駐メモリも緩やかに上がり、**swap を使い始めたら災害の前兆** | メモリリーク、ワールドの肥大化、エンティティが回収されない |
| ディスクの空き | **満杯になるとサーバーはセーブデータを書けない**。データを壊す類 | バックアップの堆積、ログの急増、コアダンプ |
| ディスク I/O | ワールドの保存、チャンクの読み込み、バックアップはすべて I/O を食う。**遅いとき CPU は暇そうに見える** | 機械式ディスク、SSD の満杯間近、バックアップとゲームの取り合い |
| ネットワーク | 帯域の飽和とパケットロスはプレイヤーを切断させる。しかも**サーバー自身の指標は完全に正常** | 攻撃、バックアップのアップロードが上りを占有、回線の故障 |
| プレイヤー数 | 業務の指標であり、**最も敏感な異常検知器**でもある。突然ゼロになるのはたいてい他のどのアラートより早い | サーバーダウン、攻撃、ログインの拒否 |
| バックアップの成否 | バックアップが失敗しても何も感じない。**それが必要になる日まで** | ディスク満杯、権限の変更、スクリプトのエラーが見逃される |
| 証明書の有効期限 | パネル、ステータスページ、Web サイトが HTTPS なら、**期限切れの当日に初めて露出する** | 更新の忘れ、自動更新タスクの失敗 |

:::tip ディスクの空きがなぜ先頭なのか
一覧のなかで**唯一、データを直接壊す**項目だからです。CPU が高く TPS が低くても、プレイヤーはつらいだけ。ディスクが満杯になるとサーバーはワールドの保存に失敗し、失うのは数時間の進行度、場合によってはセーブデータ全体です。だからアラートを 1 本しか設定しないなら、ディスクにしてください。
:::

## 2. 事後分析と事前アラート

この 2 つの言葉はよく混ぜて使われますが、解く問題はまったく違います。

| | 事後分析 | 事前アラート |
| --- | --- | --- |
| 発動の時機 | 問題がすでに起き、プレイヤーに影響が出ている | 問題が形成されつつある、または起きた直後 |
| 典型的な道具 | spark、ログ、`crash-reports/` | Uptime Kuma、Prometheus + Alertmanager、systemd の `OnFailure` |
| 答える問い | 「さっき何が起きたのか」 | 「いま事故になりそうか」 |
| 出力 | コールツリー、フレイムグラフ、エラースタック | 通知 1 本。「どうすべきか」を添えて |
| 限界 | **過去しか説明できない** | **あらかじめ思いついた問題しか見つけられない** |

**どちらも欠かせませんが、優先度は違います。** 事前アラートがなければ、サーバーが落ちたことをプレイヤーの口から知ります。事後分析がなければ、落ちたことは分かっても理由が分からず、次も落ちます。

### 2.1 「spark を見れば十分」が誤りである理由

よくある誤解は「定期的に spark で健康レポートを見ればいい」というものです。spark の健康レポートは確かに長期状態の良い道具ですが、**あなたが能動的に見に行く**ものです。深夜 3 時にディスクが満杯になるとき、誰も進んで spark を開きません。アラートの本質は**「能動的に見る」を「受動的に知らされる」に変える**ことで、「毎日見る時間がない」ことが致命的でなくなることです。

:::note 監視ですべてを見つけられると思わない
監視が見つけられるのは**あなたがすでに思いついて収集した**問題だけです。「あるプラグインが毎日未明にメモリを 200 MB 増やす」という問題に初めて出会ったとき、それを証明できる指標は通常ありません。**正しいやり方は、事故が 1 回起きたら監視を 1 本足すこと。** 監視の体系は育てていくもので、一度に揃うものではありません。
:::

## 3. まず最も安いところから：コストゼロの 3 つの方案

Prometheus を入れる前に、この 3 つをやってください。ほとんどの「サーバーが落ちても誰も知らない」場面をカバーでき、ほとんど時間もかかりません。

### 3.1 外部からの可用性チェック：Uptime Kuma

考え方は単純です。**あなたのサーバーの外にあるマシンに、一定間隔でドアをノックさせる**。なぜ「あなたのサーバーの外」でなければならないか。サーバーが丸ごと停電し、ネットワークが切れ、システムが固まるとき、**それ自身の上で動く監視スクリプトも一緒に死ぬ**ので、何も報告できません。この点が外部監視とローカル監視の最も本質的な違いです。

Uptime Kuma はセルフホストの監視ツールで、公式は「使いやすいセルフホストの監視ツール」と位置づけています。監視の種類は HTTP(S)、TCP、HTTP(S) のキーワードと JSON クエリ、WebSocket、Ping、DNS レコード、Push、Steam のゲームサーバー、Docker コンテナなどをカバーし、公式 README には **20 秒**のチェック間隔に対応すると書かれています。通知の経路には Telegram、Discord、Gotify、Slack、Pushover、メール（SMTP）などがあり、公式は **90 以上**の通知サービスがあるとしています。ほかに多言語、複数のステータスページ、証明書情報、プロキシ対応、2FA もあります。Minecraft サーバーにとって最も実用的な監視は 3 つです。

| 監視の種類 | 何を監視するか | 注意 |
| --- | --- | --- |
| TCP ポート | サーバーのプロセスがポートを待ち受けているか | **プロセスが生きていても固まっていればポートは通る**。「重さ」は測れない |
| Ping | ホストに到達できるか | ネットワーク層が生きていることしか示せない |
| HTTP(S) | パネル、ステータスページ、Web サイトが使えるか | ついでに証明書の期限も見られる |

**監視は別のマシンか別のサービス提供者に置いてください。** 同じマシンに置くと、停電のときにサーバーと一緒に消えます。

### 3.2 systemd：サービス自身に失敗を報告させる

サーバーを systemd で管理しているなら（[システムのセキュリティ強化](/tutorials/ops/system-security) を参照）、「サービスが落ちた」ことは systemd がもともと知っています。あなたはそれを教えてもらうだけでよい。**よく混同される 2 つのオプションをまず分けてください**。`Restart=on-failure` はプロセスの異常終了時に**自動で再起動**し（長期稼働のサービスはすべて設定すべきで、故障時間を短くするために使います）、`OnFailure=` はサービスが failed 状態に入ったときに**別の unit を起動**します（通知、現場の収集、片付けに使います）。

`Restart=` は「自己修復」、`OnFailure=` は「アラート」です。**両方設定します**が、`Restart=` がアラートの代わりになるとは考えないでください。サービスがクラッシュと再起動を繰り返しているなら、`Restart=` はそのループを続けさせるだけで、あなたは何も知りません。最小のアラート用 unit と、サーバーの unit からそれを参照する行：

```ini
# /etc/systemd/system/mc-alert@.service
[Unit]
Description=Send an alert for a failed unit (%i)
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
# %i（失敗したサービスの名前）を通知スクリプトへ渡す
ExecStart=/usr/local/bin/mc-notify.sh "systemd unit %i entered the failed state"

# --- 以下はサーバーの unit の [Unit] セクション ---
# サービスが failed 状態に入ったとき、テンプレートのインスタンス mc-alert@<このサービスの名前>.service を起動する
OnFailure=mc-alert@%n.service
```

変更したら `systemctl daemon-reload` を忘れずに。そのうえで**実際に 1 回落として検証**してください。検証していないアラートは、アラートがないのと同じです。

:::warn クラッシュと再起動のループは問題を覆い隠す
`Restart=always` と「プレイヤーが気づかない」が組み合わさると、**10 分に 1 回落ちる**サーバーが完全に正常に見えることがあります。**アラートは「たまの再起動」と「再起動し続けている」を区別できなければなりません**。さもないと静かに長く騙されます。`systemctl status` の再起動回数と直近の終了時刻を確認してください。
:::

### 3.3 cron 1 本 + チェックスクリプト 1 本

最も原始的で最も信頼できる方案：cron に毎分スクリプトを走らせ、異常を見つけたら 0 以外の終了コードで終わり、cron のメールかあなたの通知スクリプトが結果を送り出します。

**重要な取り決め：スクリプトは終了コードで結果を表す。** `0` はすべて正常、**0 以外は事故**。こうすれば cron でも systemd timer でも他のスケジューラでも、同じ判断の論理が使えます。

```bash
#!/usr/bin/env bash
# /usr/local/bin/mc-healthcheck.sh
# 終了コードの取り決め：0 = 正常、0 以外 = 異常（cron / systemd では失敗として扱われる）
set -uo pipefail
PORT="25565"        # サーバーが待ち受けるポート
WARN_DISK=85        # ディスク使用率のアラートライン（パーセント）
fail=0
note() { printf '%s\n' "$*"; }
bad()  { printf 'FAIL: %s\n' "$*"; fail=1; }

# 1) TCP ポートを誰かが待ち受けているか（ss のフィルタ式は引用符で囲み、shell に分割されないようにする）
if command -v ss >/dev/null 2>&1; then
  if ss -lnt "( sport = :${PORT} )" | grep -q .; then
    note "port ${PORT}: listening"
  else
    bad "port ${PORT} is not listening"
  fi
fi
# 2) サーバーのプロセスが存在するか（角括弧の書き方で pgrep が自分自身にマッチするのを避ける。実際のプロセス名に合わせて調整）
if pgrep -f '[s]erver\.jar' >/dev/null 2>&1; then
  note "server process: present"
else
  bad "server process not found"
fi
# 3) ルートファイルシステムの使用率（df -P で出力形式を安定させ、列で解析しやすくする）
used="$(df -P / | awk 'NR==2 {gsub(/%/,"",$5); print $5}')"
if [ -n "${used}" ] && [ "${used}" -ge "${WARN_DISK}" ]; then
  bad "disk usage on / is ${used}% (threshold ${WARN_DISK}%)"
else
  note "disk usage on /: ${used:-unknown}%"
fi
exit "${fail}"
```

cron に設定します（毎分 1 回）：

```bash
# crontab -e
* * * * * /usr/local/bin/mc-healthcheck.sh || /usr/local/bin/mc-notify.sh "healthcheck failed on $(hostname)"
```

:::warn cron のメールはしばしばブラックホール
多くのシステムで、cron のメールは MTA が設定されていないか、誰も見ないメールボックスに入ります。**「cron が通知してくれる」と仮定しないでください**。必ず自分で 1 回検証します。スクリプトを必ず失敗するように書き換えて、通知が本当にあなたの手元へ届くか見てください。

上の例では `/usr/local/bin/mc-notify.sh` を使っていますが、**これは自分で実装する必要があります**。最も簡単なのは Webhook に POST を 1 本送るか、Uptime Kuma の Push 監視のアドレスを呼ぶことです。どの経路を選ぶかは手元にある道具によります。**具体的なインターフェースはその道具の公式ドキュメントに従ってください**。
:::

:::note TPS と MSPT をスクリプトに取り込むには
上のスクリプトが TPS と MSPT を確認していないのは、**この 2 つの値が OS の層にない**からです。サーバー、プラグイン、MCDR が公開して初めて得られます。値を取った後の判断自体は単純ですが、shell は整数の比較しかできず、小数には `awk` が必要です。

```bash
mspt="$(your-command-to-read-mspt 2>/dev/null)"
if [ -n "${mspt}" ] && awk -v v="${mspt}" -v m="50" 'BEGIN {exit !(v > m)}'; then
  bad "MSPT ${mspt} exceeds 50"
fi
```

**値の取り方はコア、バージョン、プラグインによって異なります。使用している方案の公式ドキュメントに従ってください。**
:::

## 4. 本格的な方案：node_exporter + Prometheus + Grafana

コストゼロの 3 つの方案は「落ちたかどうか」は教えてくれますが、「ディスクがどう上がってきたか」「メモリが何時から登り始めたか」には答えられません。後者を実現するには、**履歴データを保存して曲線にできる**体系が必要です。

### 4.1 3 つのコンポーネントの役割

| コンポーネント | 役割 | 一言で理解する |
| --- | --- | --- |
| node_exporter | 収集器（exporter） | ホストの CPU、メモリ、ディスク、ネットワークなどの指標を HTTP インターフェース上のテキストにし、誰かが取りに来るのを待つ |
| Prometheus | 時系列データベース + 取得器 | **定期的に能動的に取りに行き**、exporter が公開する指標を時系列として保存し、規則に従ってアラートの要否を判断する |
| Grafana | 可視化 | Prometheus に接続し、時系列をグラフにし、パネルに組み上げる |
| Alertmanager | アラートの経路 | Prometheus が「アラートすべき」と判断した後、グループ化、重複排除、サイレンス、送信を担う（第 6 節を参照） |

**「プル（pull）」というモデルの理解が重要**です。exporter が Prometheus へデータを押し出すのではなく、**Prometheus が定期的に取りに行きます**。副作用は有用で、あるターゲットを取得できないとき Prometheus 自身が「それは落ちている」と分かります。この `up` 指標そのものが最も基礎的な可用性監視です。

### 4.2 node_exporter と最小の systemd unit

node_exporter は単体のバイナリで、起動すると既定のポートで指標を公開します。公式ドキュメントが示す検証方法：

```bash
./node_exporter                              # フォアグラウンドで直接動かす
curl http://localhost:9100/metrics           # 指標が読めることを確認する（既定のポートは 9100）
curl http://localhost:9100/metrics | grep "node_"   # node_ 接頭辞のホスト指標だけを見る
```

公式ドキュメントは、ホストの指標が `node_` の接頭辞を持つと説明しています。たとえば `node_cpu_seconds_total`（CPU の各モードの累積時間。`rate()` と組み合わせて使用率にする）、`node_filesystem_avail_bytes`（ファイルシステムが非 root ユーザーに使わせられるバイト数）、`node_network_receive_bytes_total`（NIC の累積受信バイト数）。上流リポジトリの例の unit は **socket アクティベーション**（`Requires=node_exporter.socket` と `--web.systemd-socket`）を使うので、そのファイルは**単独では使えず**、socket unit とセットで必要です。以下では socket アクティベーションに依存しない、より直接的な書き方を示します。

```ini
# /etc/systemd/system/node_exporter.service
[Unit]
Description=Prometheus Node Exporter
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
# ディストリビューションのパッケージで入れた場合、ユーザーとバイナリのパスは通常パッケージが用意する（よくあるのは prometheus-node-exporter）
User=node_exporter
Group=node_exporter
# バイナリのパスは導入方法で異なる。上流のバイナリは /usr/local/bin/node_exporter が一般的
ExecStart=/usr/local/bin/node_exporter --web.listen-address=:9100
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

有効化して検証します。

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now node_exporter
systemctl status node_exporter --no-pager
curl -s http://127.0.0.1:9100/metrics | head
```

:::warn パス、ユーザー、ポートは実際に合わせて変える
上の `User=`、`ExecStart=` のパス、待ち受けポートは**あくまで例**です。ディストリビューションのパッケージと上流のバイナリでは導入先が違い、ユーザーが存在するかもパッケージ次第です。**ポート 9100 は既定値であり、規定値ではありません**。変えたら Prometheus のターゲットのアドレスも合わせて変えます。また node_exporter の一部のコレクタ（とくに systemd やログを読むもの）は忙しいマシンでコストが小さくありません。**コンテナ内ではホストの指標を取るために追加のマウントが必要なことが多い**です。どのコレクタを有効にするかは、導入しているバージョンの公式ドキュメントと `--help` の出力に従ってください。
:::

### 4.3 Prometheus の最小設定

以下は Prometheus 公式の node_exporter ガイドが示す最小の取得設定に、規則の評価とアラートに必要な項目を補ったものです。

```yaml
# /etc/prometheus/prometheus.yml
global:
  scrape_interval: 15s      # 公式の既定は 1m。ここでは明示的に 15s にする
  scrape_timeout: 10s       # 取得間隔より大きくできない。公式の既定は 10s
  evaluation_interval: 1m   # 規則の評価間隔。公式の既定は 1m

rule_files:                 # アラート規則のファイル（第 5 節に内容の例）
  - /etc/prometheus/rules/*.yml

alerting:                   # アラートと判定した後に誰へ渡すか（第 6 節）
  alertmanagers:
    - static_configs:
        - targets:
            - 127.0.0.1:9093

scrape_configs:
  - job_name: node          # ホストの指標：公式ガイドの最小例
    static_configs:
      - targets: ['localhost:9100']

  - job_name: prometheus    # 自分自身を取得し、それ自体が健全かを確認しやすくする
    static_configs:
      - targets: ['localhost:9090']
```

設定を検証して再読み込みします。

```bash
# 公式同梱の検証ツールを使い、構文エラーを抱えたまま再起動するのを避ける
promtool check config /etc/prometheus/prometheus.yml
# 再読み込み（起動時に --web.enable-lifecycle を有効にしている必要がある）
curl -X POST http://127.0.0.1:9090/-/reload
```

:::note ポートとパスは既定値
`9090`（Prometheus）と `9093`（Alertmanager）はこの 2 つのプロジェクトの**既定のポート**で、起動引数か設定で変更できます。設定ファイルのパスはディストリビューションと導入方法で異なり、`/etc/prometheus/` は Debian 系でよくある場所にすぎません。**そのまま写さず、まず自分のシステムでファイルがどこにあるか確認してください。**
:::

### 4.4 Grafana

Grafana の役割は Prometheus のデータを描くことで、既定のポートは `3000`、設定とデータのディレクトリは導入方法で変わります。Minecraft のホストなら、まず 4 枚のグラフで十分です。ディスク使用率（`node_filesystem_avail_bytes` と `node_filesystem_size_bytes`）、CPU 使用率（`rate(node_cpu_seconds_total[5m])`）、メモリと swap（`node_memory_*`）、ディスク I/O の待ち（`rate(node_cpu_seconds_total{mode="iowait"}[5m])`）。

:::tip パネルは「先週と比べてどうか」に答えられること
現在値が 1 つだけのパネルはほとんど価値がありません。**どのグラフも時間範囲を切り替えられる**ようにして初めて、「ディスクはいつから加速して減り始めたか」「メモリはどのバージョンの更新後から増え始めたか」が見えます。だから履歴データを保存する必要があり、いまこの瞬間だけを見るのではだめなのです。
:::

## 5. アラートのしきい値：いくつにして、なぜか

しきい値は敏感であればよいものではありません。**緩すぎれば事故はすでに起きており、厳しすぎれば 3 日目にすべての通知を無視し始めます。** 以下はコミュニティでよく使われる出発点です。自分のベースラインに合わせて調整してください。

| 項目 | 推奨する出発点 | なぜその値か | よくある誤報の原因 |
| --- | --- | --- | --- |
| ディスク使用率 | **85% を超えたら** | 満杯になる前に処理する時間を確保する。満杯は保存の失敗に直結する | 一時的なバックアップファイルの占有、ログローテーションの遅れ |
| MSPT | **50 ms を継続的に超える** | 50 ms は 20 TPS に対応する 1 tick の予算。長期的に超えると TPS はもう保てない | 単発のスパイクが平均に隠されるので、「継続」の条件を足す |
| バックアップタスクの失敗 | **1 回でも失敗したらアラート** | バックアップの失敗には他の症状がなく、それ自身の報告に頼るしかない | スクリプトの終了コードの誤り、一時的なディスク満杯 |
| サービスが動いていない | **`systemd` の状態が failed か active でない** | 最も基礎的な可用性。誰かが知る必要がある | 計画内の再起動にメンテナンス時間を設定していない |
| メモリが高く swap を使い始めた | **swap の使用量が継続的に 0 より大きい** | ページングが始まると遅延が崖のように悪化する。**「メモリは高いが swap なし」は通常メモリを無駄にしているだけで、必ずしもアラートは不要** | システムにもともと少量の swap 活動がある |
| CPU が継続的に高い | **継続的に 1 コアの飽和に近い** | Minecraft のメインスレッドは単一スレッドで、**1 コアを使い切れば TPS が落ちるのに十分**。他のコアが暇かは関係ない | バックアップ、ワールド生成などの正常なピーク |
| 証明書の期限 | **残り 14 日未満** | 自動更新の失敗を処理する時間を確保する | 複数ドメインの証明書のうち 1 つしか監視していない |

### 5.1 本当に使えるアラート規則 1 本

「50 を超えたら」という条件自体に問題があります。一瞬のスパイクで発火します。「継続的に超える」を表すには `for` を組み合わせます。

```yaml
# /etc/prometheus/rules/minecraft.yml
groups:
  - name: minecraft-host
    rules:
      - alert: HostDiskSpaceLow
        # ディスクの空き比率が 15% 未満（使用率が 85% 超）
        expr: |
          (node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
            / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}) < 0.15
        for: 15m          # これだけ継続して初めてアラート。一時的な揺らぎを避ける
        labels:
          severity: critical
        annotations:
          summary: "ディスクの空きが 15% 未満（マウントポイント {{ $labels.mountpoint }}）"
          description: "ホスト {{ $labels.instance }} の空き容量が少なくなっています。ディスクが満杯になるとサーバーはワールドを保存できません。"

      - alert: HostHighMemoryWithSwap
        # 使用中の swap が継続的に 0 より大きい
        expr: node_memory_SwapTotal_bytes - node_memory_SwapFree_bytes > 0
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "ホストが swap を使い始めました"

      - alert: NodeExporterDown
        # 取得の失敗：ターゲットに到達できないか、exporter が落ちている
        expr: up{job="node"} == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "ホストの指標を取得できません（{{ $labels.instance }}）"
```

**`for` と `expr` の分担に注意**：`expr` は「いま条件を満たすか」、`for` は「どれだけの間満たし続けているか」を判断します。**`for` のないアラートはほぼ確実にうるさくなります。**

:::warn TPS と MSPT は自分でつなぎ込む必要がある
上の規則は node_exporter の指標しか使っておらず、**TPS と MSPT は見えません**。ゲーム内の指標を監視するには、それらを Prometheus の指標として公開するもの（サーバーのプラグイン、MCDR のスクリプト、自前の exporter）が必要です。**具体的な方案はコア、バージョン、プラグインによって異なります。本記事では具体的な実装は示しません。使用している方案の公式ドキュメントに従ってください。**
:::

### 5.2 サービスが動いているか

サービスレベルの監視には 3 つの書き方があり、**重ねて使えます**。systemd の `OnFailure`（単純で追加のコンポーネントが不要だが、**failed 状態しかカバーできず**、固まっているが終了していないプロセスは検出できない）、外部からのポート探査（「プロセスはあるがサービスが通じない」を発見できる。別のマシンが必要）、自前のスクリプト + cron（柔軟で任意の条件を確認できるが、自分で保守する）。3 つともコストは低いのに、カバーする場面は違います。

## 6. アラート疲れ：通知に意味を持たせ続けるには

これは監視の体系で**最も過小評価される**部分です。10 分に 1 回鳴り、毎回誤報のアラートは、数日のうちにすべての通知を完全に無視するようあなたを訓練します。**そのとき監視の体系は事実上すでに機能しておらず、あなたがまだ気づいていないだけです。**

### 6.1 原因ではなく症状をアラートする

| 反例（原因をアラート） | 正例（症状をアラート） |
| --- | --- |
| 「CPU 使用率が 80% を超えた」 | 「TPS が 15 未満で 5 分続いている」 |
| 「ディスク I/O の待ちが高い」 | 「ディスクの空きが 15% 未満」 |
| 「あるプロセスが再起動した」 | 「サービスが 1 時間に 3 回以上再起動した」 |
| 「メモリ使用率が 70% を超えた」 | 「swap を使い始めた」 |

理由は、**原因がプレイヤーに影響するとは限らないが、症状は必ず影響する**からです。CPU が高くても TPS が正常なら、このマシンはまだ耐えています。TPS が落ちれば、原因が何であれプレイヤーはつらい。

### 6.2 重複排除、グループ化、サイレンス

アラートの仕組みには 3 つの基本能力が必要です。さもないと 1 回の事故が 100 本の通知になります。

| 能力 | 役割 | 例 |
| --- | --- | --- |
| 重複排除（deduplication） | 同じ問題は 1 回だけ通知する | ディスクが満杯になるとディスクに書く操作はすべて失敗するが、受け取るべきは「ディスク満杯」の 1 本だけ |
| グループ化（grouping） | 関連するアラートを 1 本にまとめる | 1 回の停電で 10 台が同時にオフラインになる。10 本ではなく 1 本にまとめるべき |
| サイレンス（silencing） | 計画メンテナンス中は通知しない | サーバーを再起動している最中に、そのことでアラートを受け取りたくない |

Prometheus のエコシステムでは、この 3 つは Prometheus 自身ではなく **Alertmanager** が担います。**ここが多くの人が落とす部分**です。Prometheus だけ入れて Alertmanager を入れないと、手に入るのはそれぞれ勝手に鳴る通知の山です。

### 6.3 経路は 1 つだけにし、すべてのアラートに処理できる人を

実用的な規律：**すべてのアラートを同じ経路に流す。** 理由は現実的で、経路が 3 つあると「この経路の通知は重要でない」という分類を始め、最後には 3 つとも見なくなります。**経路 1 つ、規則 1 本、見る場所 1 か所**にして初めて、「鳴ったら必ず何かある」という条件反射ができます。

アラートを 1 本公開する前に、もう 1 つ自問してください。**それが鳴ったら、自分は何をするのか？** 答えが「分からない、まず見てみる」なら、そのアラートは**まだ公開すべきではありません**。処理の手順を先に決めてから有効にします。それが次の節のランブックです。

## 7. アラートが鳴った後：ランブック

**ランブック（runbook）**は「あるアラートが鳴ったらどうするか」を前もって書いた手順です。形式主義ではありません。アラートは最も状態のよくないときに鳴る可能性が高いからです。深夜、通勤中、別のことをしている最中。

最小限の使えるランブックは、アラートごとに 4 行で足ります。

```text
アラート名：HostDiskSpaceLow
意味：ホストのいずれかのマウントポイントの空きが 15% 未満
手順 1：df -h でどのマウントポイントか、どれくらいの速さで増えているかを確認する
手順 2：最も容量を占めるディレクトリを探す：du -sh /srv/minecraft/* | sort -h
        よくある犯人：バックアップの堆積、ローテーションされていないログ、コアダンプファイル
手順 3：安全に削除できるもの（期限切れのバックアップ、古いログ）を片付け、サーバーがまだディスクに書けることを確認する
手順 4：すぐに片付けられないなら、継続的にディスクへ書くタスクを先に止め、プレイヤーに通知する
```

### 7.1 4 つの一般的な対応原則

| 原則 | なぜ |
| --- | --- |
| **まず止血、それから原因** | プレイヤーがまだ影響を受けているなら、まずサービスを戻す。調査は後でできる |
| **現場を残す** | 再起動の前にログと状態をコピーする。[インシデント対応とフォレンジック](/tutorials/ops/incident-forensics) を参照 |
| **再起動だけで済ませない** | 再起動はワールドを読み直すだけ。**根本原因が残っていれば、問題は同じ速さで戻ってくる** |
| **対応の過程を記録する** | 次に同じアラートが鳴ったとき、必要なのは今回の記録そのもの |

### 7.2 実際の処理の順序

「TPS が 10 に落ちた」を例にすると、妥当な順序はこうです。**現象の確認（TPS、MSPT、プレイヤー数、`uptime`）→ サーバー側かホスト側かの判断 → サーバー側なら spark profiler を 1 回走らせてコールツリーを取る。ホスト側なら CPU の制限、メモリ、ディスク I/O を見る → まず応急手段でプレイヤーが遊べるようにする → 最後に振り返って監視を 1 本足す**。最初の 2 段階の判断材料は [spark でサーバー性能を分析する](/tutorials/ops/spark) を参照してください。

## 8. 家庭用ホストをどう監視するか

家庭用ホストとデータセンター環境の違いは、主に**データセンターが代わりに解決してくれる問題を抱えている**ことです。商用電源、空調、入退室管理、常駐の運用。関連する背景は [家庭用 PC での開設と保守](/tutorials/ops/home-hosting) を参照してください。

### 8.1 停電の検知と自動シャットダウン：NUT

家庭用ホストの最も典型的な故障は**商用電源の中断**です。「サーバーのクラッシュ」とは違い、クラッシュは通常セーブデータを壊しませんが、**書き込み中のハードな電源断は書きかけのファイルを残し**、軽ければ数チャンクを失い、重ければセーブデータが読み込めなくなります。だから UPS の位置づけは「安全に停止する時間を稼ぐ」ことで、**NUT（Network UPS Tools）**は Linux で最も汎用的な監視方案です。3 層に分かれ、**ドライバが UPS と通信し、`upsd` がサーバー、`upsmon` が監視クライアント**で、`upsmon` は `upsd` から状態を読み、必要に応じてシャットダウンを起こします。状態を読むコマンドは `upsc`（読み取り専用のクライアント）です。

```bash
upsc -l                       # 設定済みの UPS の名前をすべて一覧する
upsc myups                    # ある UPS のすべての変数を見る
upsc myups ups.status         # 状態だけを見る：OL 商用電源 / OB バッテリー / LB 低バッテリー
upsc myups battery.charge     # 残量のパーセント
upsc myups battery.runtime    # 予想される持続時間（秒）
```

UPS の状態をアラートにつなぐのは簡単です。`ups.status` に `OB`（on battery）が含まれるかを見るだけです。**状態が取れないときに黙って見逃さず**、「不明」としてアラートにしてください。

:::warn NUT の細部はディストリビューションとバージョンで変わる
パッケージ名とサービス名はディストリビューションで異なり（Debian 系は `nut-server`、`nut-client`、RHEL 系は `nut-server`、`nut-monitor` が一般的）、設定ディレクトリも `/etc/nut/` と `/etc/ups/` の 2 通りあります。**NUT 2.8.0 から `master`/`slave` が `primary`/`secondary` に改名**され、旧表記も互換のため受け付けられます。変数名もドライバと機種で変わることがあるので、**まず `upsc` で実際の変数を一覧してからスクリプトを書いてください**。完全な設定は [ラック、スイッチと UPS](/tutorials/ops/hardware-rack) を参照。
:::

### 8.2 停電の後に自分で起動できるか、過熱しないか

監視は「停電した」ことを教えてくれますが、**給電が戻った後にマシンが自分で起動できるかは BIOS/UEFI の設定次第**で、監視とは関係ありません。これは組み立て時に設定しておく必要があり、さもないと停電のたびに自分で電源ボタンを押しに行くことになります。家庭環境にはデータセンターの空調もなく、**夏の高温は現実の故障源**です。CPU とファンの回転数は `lm-sensors` の `sensors` コマンドで読め、ディスクの温度は通常 `smartctl -a` の SMART 属性にあります。**どのセンサーが読めるかはマザーボードとセンサーチップ次第**です。

:::note 温度のしきい値はハードウェアで異なる
CPU ごとに正常な動作温度は大きく違い、**汎用のアラート温度は存在しません**。正しいやり方は、使っている型番の仕様書を調べ、しきい値を「日常より明らかに高いが、クロック低下の点より低い」位置に置くことです。まず数日動かしてベースラインを記録し、それからしきい値を決めます。
:::

家庭用ホストでさらに見るべきは 4 つです。**上流の回線**（家庭回線は PPPoE の再接続や一時的な揺らぎがあり、サーバーの指標は正常なのにプレイヤーが全員切断する）、**グローバル IP の変化**（固定 IP がないとき DDNS の更新に失敗するとプレイヤーが接続できない）、**ディスクの SMART 属性**（家庭用ディスクにはエンタープライズ向けの冗長設計がなく、不良セクタを早く見つけられれば 1 回データを救える）、**スリープと休止**（システムがスリープするとサーバーは止まる。関連する設定が無効になっていることを必ず確認する）。

## 9. 導入の順序とチェックリスト

一度にスタック全部を入れないでください。この順で進めれば、各段階が独立して価値を生みます。**外部からの探査 + 通知の経路 1 つ**（「サーバーが落ちても誰も知らない」を解決）→ **systemd の `OnFailure` と `Restart=`**（サービスのクラッシュの自動復旧と通知）→ **cron のヘルスチェックスクリプト 1 本**（ディスクの満杯間近、プロセスの消失）→ **node_exporter + Prometheus + Grafana**（傾向が見え、「いつから悪くなったか」に答えられる）→ **アラート規則 + Alertmanager**（「グラフを見る」から「通知される」へ）→ **アラートごとにランブックを書く**（深夜に通知を受け取ったとき、何をすべきか分かる）。

### 9.1 公開前のチェックリスト

| 確認項目 | なぜ必ず確認するか |
| --- | --- |
| 監視自体が監視対象のマシンの上にない | マシン全体の停電で、ローカルの監視も一緒に消える |
| 通知の経路を実際に 1 回検証した | 検証していないアラートはアラートがないのと同じ |
| アラートが「継続」と「瞬間」を区別できる | `for` などの条件を使う。さもないと必ずうるさくなる |
| すべてのアラートに対応するランブックがある | ないと、ただあなたを起こすだけ |
| ディスクのアラートのしきい値が「満杯」より余裕を持って低い | ディスク満杯はデータを壊す類の故障 |
| バックアップの失敗がアラートになる | バックアップの失敗には他の症状がない |
| 証明書の期限を監視している | 期限切れの当日に初めて露出する |
| 計画メンテナンス時にサイレンスの仕組みがある | ないと再起動 1 回で通知の山 |
| 履歴データを振り返れる | 単点のスナップショットでは傾向を説明できない |
| ログと指標をどこで見るか知っている | [ログとエラーの調査](/tutorials/faq/errors) を参照 |

### 9.2 よくある誤り

| 誤り | 結果 |
| --- | --- |
| CPU とメモリだけを監視する | ディスク、バックアップ、証明書という「自分からは叫ばない」3 類の故障を落とす |
| アラートを生の指標に直結する | 瞬間的な揺らぎのたびに通知し、すぐ無視される |
| 通知を 3 つの経路へ送る | 3 つとも真面目に見なくなる |
| 入れてから放置する | しきい値は業務とともに変わり、半年後にはすべて無効になる |
| 監視するだけで演習しない | 本当に事故が起きたときに、通知が送れないと気づく |
| 監視を同じマシンに置く | 最も必要になるあの故障のとき、それはいない |
