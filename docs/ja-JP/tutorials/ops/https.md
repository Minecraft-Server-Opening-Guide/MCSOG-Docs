パネルが開かない、ブラウザが「この接続はプライベートではありません」と言う、Web マップが真っ白になる。こうした事故の**かなりの部分の根本原因は 1 つだけです。証明書が期限切れになった。** これは本来まったく避けられる障害です。有効期限が明確で、しかも自動更新できるからです。

この記事では 3 つのことを整理します。**TLS が守るもの（そして守らないもの）**、**証明書と秘密鍵はそれぞれ何か**、**更新という作業を二度と覚えておかなくて済むようにする方法**。パネル自体のセキュリティ設定は [パネル管理ツールの利用とセキュリティ](/tutorials/ops/panels)、証明書の期限切れのアラートは [監視とアラート](/tutorials/ops/monitoring) を参照してください。
:::warn 本記事の設定は公式ドキュメントに従ってください
以下に登場する**パッケージ名、コマンドの引数、設定キー、既定のパス、ディレクトリ構造は、ディストリビューション、導入方法、ソフトウェアのバージョンで変わります**。サンプルの役割は「何を設定すべきか」を示すことであり、**そのままコピーできる完成品ではありません**。適用する前に、certbot、Let's Encrypt、nginx、使用しているディストリビューションの公式ドキュメント、および自分のシステムで実際に生成されたファイルと照合してください。
:::

## 1. まず範囲を切り分ける：ゲームの通信は HTTPS ではない

ここが最も混同され、最も誤解される点です。

| 通信 | プロトコル | 既定のポート | TLS 証明書が必要か |
| --- | --- | --- | --- |
| Java 版のゲーム通信 | Minecraft 自身の TCP プロトコル | 25565 | **不要。証明書はまったく役に立たない** |
| 統合版（基岩版）のゲーム通信 | UDP（RakNet） | 19132 | **不要** |
| パネルの Web 画面 | HTTPS | 443（または選んだポート） | **必要** |
| Web マップ（Dynmap、Squaremap、BlueMap など） | HTTPS | 443 | **必要** |
| Web サイト、ステータスページ、MCDR の Web プラグイン、各種 API | HTTPS | 443 | **必要** |
| RCON | それ自身の TCP プロトコル | 25575 | TLS ではない。**インターネットに露出しない** |

**結論：HTTPS 証明書は「Web 側」のためのものです。** 証明書を入れるかどうかは、プレイヤーが入室できるか、中間者攻撃を受けるかとは**一切関係ありません**。

### 1.1 Java 版のログイン時の暗号化とは何か

Java 版のログイン段階には確かに暗号化がありますが、それは **Minecraft プロトコル自身の仕組み**で、ゲームのプロトコルが定めるものであり、**X.509 証明書とも Let's Encrypt とも無関係**です。HTTPS 証明書と「ゲーム通信の暗号化」を同じものと見なすことが、多くの設定が方向を誤る出発点です。

### 1.2 Web 側に TLS が必須な理由

Web 側が運ぶのは**資格情報と身元**だからです。パネルのログインパスワード、セッション Cookie、API キーとトークンは、**平文の HTTP では同じネットワークにいる人にそのまま見えます**。さらに現代のブラウザは HTTP のページを「安全でない」と表示し、パネルの利用者が警告を無視することに慣れてしまえば、その習慣自体がセキュリティ上の問題です。パネルはインターネットに開放した瞬間から継続的にスキャンされます。[よくあるネットワーク攻撃と Minecraft 特有の防御](/tutorials/ops/attack-defense) を参照してください。

## 2. 証明書と秘密鍵

### 2.1 それぞれ何か

| | 証明書（certificate） | 秘密鍵（private key） |
| --- | --- | --- |
| 本質 | 公開鍵 + 身元情報 + CA の署名 | 秘匿しなければならない鍵素材 |
| 公開できるか | **できる**。もともと各訪問者に配るもの | **絶対にできない** |
| 漏れた場合 | なし（もともと公開情報） | **秘密鍵を手にした人はあなたのサイトを騙れる** |
| 期限 | 有効期限があり、**更新が必須** | 通常は証明書と一緒に交換される。それ自体は「期限切れ」にならない |

**証明書は身分証、秘密鍵は印鑑です。** 身分証は人に見せられますが、印鑑をなくしたら災難です。

### 2.2 よくあるファイルと関係

ACME クライアントでよくある出力を例にします（**具体的なファイル名は使うクライアントに従ってください**）。

| ファイル | 内容 | どこで使うか |
| --- | --- | --- |
| `fullchain.pem` | あなたの証明書 + 中間証明書 | **Web サーバーの `ssl_certificate`** |
| `privkey.pem` | 秘密鍵 | **Web サーバーの `ssl_certificate_key`** |
| `chain.pem` / `cert.pem` | 中間証明書 / あなたの証明書のみ | 通常は単独で使わない |

**最もよくある罠**：`cert.pem` だけを設定して中間証明書を落とし、「あるブラウザでは開けるが、あるブラウザでは開けない」状態になる。**`fullchain.pem` を使えばこの問題は起きません。**

### 2.3 SNI：1 つの IP に複数のサイト

現代の TLS クライアントはハンドシェイク時に **SNI（Server Name Indication）** を送り、Web サーバーはそれを見て証明書を選びます。だから 1 台のマシンに複数のサイトを置くことができ、それぞれが自分の証明書を使えます。一方で、**コマンドラインで証明書を検査するときは SNI の引数が必須**です（`openssl s_client -servername ...`）。さもないと別の証明書を見てしまい、誤った結論に至ります（第 8 節を参照）。

## 3. Let's Encrypt、ACME と「自動更新が必須」であること

### 3.1 ACME とは

**ACME は証明書の自動発行と自動更新のためのプロトコル**です。Let's Encrypt は最も広く知られた ACME の証明書認証局（CA）で、発行するドメイン検証（DV）証明書は**無料**です。鍵は「自動」にあります。ACME の設計目標は、「申請、検証、発行、更新、配備」という一連の流れを無人で回すことです。これ以外にも ACME の CA は存在します（**あなたに適するかは各公式ドキュメントに従ってください**）。

### 3.2 90 日は問題ではない。手動更新こそが問題

Let's Encrypt が発行する証明書の**有効期間は 90 日**です（公式ドキュメントに従う）。多くの人の第一反応は「短すぎる、面倒だ」ですが、**この反応自体が問題の在りかです**。

- 90 日は**意図的**です。「更新を忘れる」を「数年一度の事故」から「自動化しなければ生き残れない常態」に変えるためです。
- **「期限が来たら手で更新しよう」という方案は必ず失敗します**。年 4 回、何年も連続で失敗しないことは、人にはできません。出張、PC の買い替え、通知メールが迷惑メールフォルダに入る。どんな小さなことでも、ある日突然期限切れになります。
- 正しい心構えは、**「証明書は期限切れになるか」を「自分が覚えておくこと」から「システムが自分で処理すること」に変え**、そのうえで**それを監視する**ことです（第 12 節を参照）。

### 3.3 よくある ACME クライアント

certbot（公式ドキュメントが最も充実し、プラグインも多い）、acme.sh（純粋な shell、DNS API の対応が広い）、lego（Go の単一ファイル）、そして Caddy のような **ACME を内蔵した Web サーバー**。本記事は certbot を例にします。

**同じドメイン群を 2 つのクライアントで同時に管理しないでください**。2 組の自動タスクが互いの設定を上書きし、問題が起きたときに調査に時間がかかります。

## 4. certbot の実践

### 4.1 インストール：公式の説明に従う

certbot の導入方法はディストリビューションとバージョンで大きく変わります。**公式のインストール手順に従ってください**。よくある入手元は 3 つです。**ディストリビューションのリポジトリ**（最も手軽だがバージョンは古め）、**snap**（公式ドキュメントがよく勧める。バージョンは新しめ）、**pip / 仮想環境**（柔軟だが依存を自分で扱う）。**nginx プラグインを使うには対応するプラグインパッケージも必要**です（よくある名前は `python3-certbot-nginx` のような形。具体的なパッケージ名はディストリビューションに従う）。導入後は `certbot --version` で確認し、**バージョンが違えばサブコマンドや引数も変わり得る**ことに注意してください。

### 4.2 3 つの発行方式とそれぞれの適用場面

| コマンド | 何をするか | 適用 | 注意 |
| --- | --- | --- | --- |
| `certbot --nginx -d panel.example.com` | nginx プラグイン：設定を自動で変更し、リダイレクトも自動で設定する | nginx が動いていて、設定を自分で掌握している | **あなたの nginx 設定を変更します**。変更前にバックアップするかバージョン管理に入れる |
| `certbot certonly --standalone -d panel.example.com` | 一時的なサービスを自分で立てて 80 番を占有する | マシンにまだ Web サービスがない | **nginx を止める必要があります**。止めないと 80 が使われて失敗する |
| `certbot certonly --webroot -w /var/www/certbot -d panel.example.com` | 検証ファイルを指定ディレクトリに書き、既存の nginx に配信させる | **リバースプロキシの場面で最もよく使う** | nginx に `.well-known/acme-challenge/` の location を設定しておく必要がある |

「nginx がパネルをリバースプロキシする」マシンでは、**webroot か nginx プラグインを推奨**します。前者は設定への変更が最小で、後者は最も手軽です。**standalone はまだ Web サービスがない場合か、一時的に止めてよい場合だけ**に向きます。発行時には**期限通知用のメールアドレス**を求められます（省略できますが、**記入を強く勧めます**。自動更新が失敗したときに、いち早く知らせてくれる唯一の相手だからです）。

### 4.3 更新の試験

**この段階は省けません。** 検証するのは「30 日後に自動更新が本当に走ったとき、成功するか」です。

```bash
# 演習：証明書を実際に差し替えず、本番環境の発行枠も消費しない（テスト環境を使う）
sudo certbot renew --dry-run

# 現在管理している証明書、パス、期限を確認する
sudo certbot certificates
```

**`--dry-run` は最も安価な検証方法です。これを一度も走らせていない自動更新は、自動更新がないのと同じです。**
:::warn むやみに --force-renewal を使わない
`--force-renewal`（および同種の強制引数）は即座に再発行します。**頻繁な強制発行は CA のレート制限に触れ、本当に必要なときに発行できなくなることがあります。** 調査ではまず `--dry-run` を使い、どうしても強制が必要なときは、原因と制限の規則を確認してからにしてください（CA の公式ドキュメントに従う）。
:::

### 4.4 自動更新：systemd timer か cron か

**certbot は通常、自動更新のタスクを同梱しています。自分でもう 1 つ書く必要はありません。** よくある形は 2 つです。**systemd timer**（`certbot.timer` など。多くのディストリビューションと snap 導入はこちら）と **cron タスク**（`/etc/cron.d/certbot` など。古い導入方法）。やることは**それが存在し、動いていることを確認する**だけです。

```bash
# systemd の経路
systemctl list-timers | grep -i certbot

# cron の経路
ls -l /etc/cron.d/ | grep -i certbot
```

**自分でもう 1 本 cron を書くと、2 組のタスクが喧嘩します。** 自動更新の既定の動作は通常、**毎日 1〜2 回チェックし、残りの有効期間が約 30 日を切ったときだけ実際に更新する**というものです（正確なしきい値とスケジュールはクライアントと公式ドキュメントに従う）。だから「毎日走っている」は「毎日発行している」と同じではありません。

### 4.5 更新の後に Web サーバーを再読み込みさせる

更新はディスク上のファイルを差し替えるだけで、**動いている nginx は新しい証明書を自動では読みません**（起動時か再読み込み時にしか読みません）。だから配備フックを用意します。

```bash
# 方法 1：更新コマンドに deploy hook を書く（例）
sudo certbot renew --deploy-hook "systemctl reload nginx"

# 方法 2：スクリプトをフックのディレクトリに置く。更新が成功するたびに実行される
# /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

フックのスクリプトには実行権限を付けるのを忘れずに。**フックが本当に効いているかを検証する最良の方法は、`--dry-run` を 1 回走らせて nginx が再読み込みされるか観察する**ことです（`--dry-run` のフックの扱いはバージョンで異なることがあります。**公式ドキュメントに従ってください**）。

## 5. nginx の TLS 設定

### 5.1 完全な例

以下は「nginx がパネルをリバースプロキシする」マシンでの、**構造が完全な**設定です（ドメイン、ポート、パスはすべてプレースホルダー）。

```nginx
# /etc/nginx/conf.d/panel.conf
# ポート <panel-port> はプレースホルダーです。パネルが実際に待ち受けるローカルポートに置き換えてください。

server {
    listen 80;
    listen [::]:80;
    server_name panel.example.com;

    # 証明書の検証ファイル：certbot の --webroot のパスと一致させる
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    # それ以外のリクエストは一律 HTTPS へリダイレクトする
    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name panel.example.com;

    # ACME クライアントが発行・更新する。実際のパスを使ってください
    # 注意：archive の下のバージョン番号付きの実ファイルではなく、live ディレクトリ下のシンボリックリンクを使う
    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    # 現代の TLS のみ許可する。TLS 1.0/1.1 は主要ブラウザで廃止済み
    ssl_protocols TLSv1.2 TLSv1.3;
    # 暗号スイートの選択をクライアントに任せる（現代の推奨。TLS 1.3 はこのオプションを見ない）
    ssl_prefer_server_ciphers off;

    # 任意のセッション再利用。有効化の可否と引数は nginx の公式ドキュメントに従う
    ssl_session_cache shared:SSL:10m;

    # HTTP/2：nginx 1.25.1 以降は独立したディレクティブ。より古い版では listen 443 ssl http2; と書く
    http2 on;

    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        # パネルのコンソールは WebSocket に依存するため、Upgrade ヘッダを転送する必要がある
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # パネルはこれを見て「外部は HTTPS」と判断し、正しいリンクと安全な Cookie を生成する
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

変更したら必ず構文を検査してから再読み込みします。

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### 5.2 行ごとの説明（間違えやすいところだけ）

| 設定 | 理由 |
| --- | --- |
| `listen 443 ssl;` | **`ssl` 引数を落とせない**。ないと nginx はこの server で TLS を有効にしない |
| `ssl_certificate` / `ssl_certificate_key` | 前者は `fullchain.pem`、後者は `privkey.pem`。パスは**使うクライアントが決める**ので、そのまま写さない |
| `ssl_protocols TLSv1.2 TLSv1.3;` | 現代のブラウザの下限は TLS 1.2。明示したほうが既定値に頼るより明確 |
| `ssl_prefer_server_ciphers off;` | 現代はクライアントに選ばせるのが推奨。TLS 1.3 の暗号スイートはこのオプションの影響を受けない |
| `.well-known/acme-challenge/` の location | HTTP-01 検証の着地点。`--webroot` を使うときは `-w` のパスと**必ず**一致させる |
| `location / { return 301 ...; }` | HTTP から HTTPS へのリダイレクト。**challenge の location より後ろに置く**ことに注意（nginx はより具体的な接頭辞を優先する） |
| `X-Forwarded-Proto` | これがないと、パネルが `http://` のリンクを生成したり、安全な Cookie の設定を拒否したりする |
| `http2 on;` | **バージョン依存**：nginx 1.25.1 以降にしかない独立ディレクティブ |
:::tip 証明書のパスに live ディレクトリを使う理由
ACME クライアントは通常、発行のたびにできる実ファイルを `archive/` のようなディレクトリ（連番付き）に置き、`live/` の下に最新を指す**シンボリックリンク**を作ります。**設定では `live/` の下のパスを参照すべきです**。更新後に自動で新しいファイルを指しますが、`archive/` の下の具体的なファイル名は更新のたびに変わります。
:::

### 5.3 暗号スイートと「既定値で通常は足りる」

ネット上に出回る nginx の TLS 設定には、長い `ssl_ciphers` が付いていることがよくあります。**多くの場合それは不要です**。

- **nginx 自身の既定値は現代のバージョンでは通常安全**で、しかもバージョンとともに更新されます。
- 数年前の暗号スイート一覧を手で写すと、**新しい、より良いスイートを除外してしまう**ことがあります。
- 細かく制御したいときは、Mozilla の SSL 設定ジェネレーターのような長期的に保守されている情報源を参照し、**適当なブログを真似しないでください**。
:::note OCSP stapling の現状
歴史的には `ssl_stapling on;` と `ssl_stapling_verify on;`（`ssl_trusted_certificate` と併用）の設定がよく勧められました。**しかし Let's Encrypt は OCSP サービスの停止と CRL への移行を発表しています**。そのため LE の証明書に対して OCSP stapling を設定しても意味がありません。**正確な時期と現状は Let's Encrypt の公式アナウンスに従ってください**。古いチュートリアルをそのまま写さないこと。
:::

## 6. 検証方式：HTTP-01 と DNS-01

ACME は「あなたがこのドメインを制御している」ことを証明する必要があります。主流の方式は 2 つです。

| | HTTP-01 | DNS-01 |
| --- | --- | --- |
| 証明の仕方 | `http://ドメイン/.well-known/acme-challenge/<token>` に指定の内容のファイルを置く | `_acme-challenge.ドメイン` に指定の内容の TXT レコードを追加する |
| ネットワーク要件 | **80 番がインターネットから到達できる必要がある**（リダイレクトは追従可） | 内向きのポートは一切不要 |
| ワイルドカードを発行できるか | **できない** | **できる** |
| 自動化の難しさ | 低い（webroot / nginx プラグインで足りる） | DNS 事業者の API 資格情報が必要 |
| 主なリスク | 80 がファイアウォール / セキュリティグループに塞がれる、CDN に遮られる、リダイレクトの設定ミス | **API 資格情報の漏洩はドメインの制御権の漏洩と同じ** |

### 6.1 HTTP-01 のよくある失敗原因

**クラウドのセキュリティグループで 80 を許可していない**（最も多い：ホストのファイアウォールは開けたが、クラウド側のセキュリティグループを開けていない）、**80 が他のサービスに使われている**（`--standalone` のときに nginx がまだ動いている）、**リダイレクトが検証リクエストも飛ばしてしまう**（challenge の location はリダイレクトより前に置くか、リダイレクト規則で `/.well-known/` を通す）、**手前に CDN / リバースプロキシがある**（検証リクエストがオリジンに届かない。CDN の説明に従って処理する）。

### 6.2 DNS-01 の注意点

レコード名は通常 `_acme-challenge` です（**DNS 事業者とクライアントのドキュメントに従ってください**）。**DNS の反映には時間がかかる**ので、手でレコードを追加した直後に検証を押さないこと。**API 資格情報は最小権限**にし、変更が必要なレコードだけを許可し、アカウントのグローバルキーを使わない。資格情報をサーバーに置くときは**権限を絞り**、Git にコミットしないこと。

### 6.3 DNS-01 が必須になる場面

- **ワイルドカード証明書**を発行したい。
- **80 番を外部に開放できない**（事業者に遮断されている、CGNAT の内側、社内ネットワークの制限）。
- ドメインが**このマシンを直接指していない**（手前に CDN、ロードバランサー、複数のオリジン）。
- **証明書の発行を Web サービスに一切依存させたくない**（たとえば HTTP 以外のサービス向けに発行する）。

## 7. ワイルドカード証明書

ワイルドカード証明書は 1 階層のサブドメインをカバーでき、代償は**DNS-01 しか使えない**ことです。

```bash
# 注意：*.example.com は example.com 自身を含まない。通常は両方を書く
sudo certbot certonly --manual --preferred-challenges dns \
  -d example.com -d '*.example.com'
```

要点：

- **`*.example.com` は `example.com` に一致せず**、`a.b.example.com` にも一致しません（ワイルドカードは 1 階層だけ）。必要なら一緒に `-d` へ書きます。
- ワイルドカードは**便利ですが、爆発半径も広げます**。秘密鍵が漏れれば、すべてのサブドメインが同時に影響を受けます。
- `--manual` を使うということは、**更新にも人手が要る**ということです。DNS API の自動プラグインに置き換えない限り。**手動のワイルドカード + 更新忘れは、非常によくある組み合わせの事故です。**
- サブドメインの数が少ないなら、**1 枚ずつ発行する（HTTP-01 で自動更新）ほうが気楽**なことが多いです。

## 8. 更新が失敗した後に何が起きるか

### 8.1 症状

| 現象 | 原因 |
| --- | --- |
| ブラウザがページ全体をブロックし、証明書の期限切れ / 不安全と表示する | 証明書が期限切れ |
| パネルにログインできない、または API クライアントがすべてエラーになる | 同上。「続行」の選択肢を出さないクライアントもある |
| Web マップが読み込めない | マップの静的リソースが HTTPS を通る |
| 「昨日までは使えたのに、今朝突然だめになった」 | 期限切れは**瞬間的に起きる**。徐々にではない |

### 8.2 どう調べるか

```bash
# この証明書が誰に署名され、いつ期限切れになるかを見る（-servername が必須。ないと別サイトの証明書を見ることがある）
echo | openssl s_client -connect panel.example.com:443 -servername panel.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# 完全なチェーン（中間証明書を含む）を見たいとき
openssl s_client -connect panel.example.com:443 -servername panel.example.com -showcerts </dev/null
```

出力では 2 つの日付に注目します。**`notBefore`（有効開始）と `notAfter`（期限）**。`notAfter` が過去なら、問題は確定です。

**同時にローカルのファイルの期限も見てください**（見ているのが CDN 上の証明書で、オリジンのものではない可能性があります）。

```bash
sudo openssl x509 -in /etc/letsencrypt/live/panel.example.com/fullchain.pem -noout -subject -dates
sudo certbot certificates
```
:::warn サービスを再起動するだけでは無駄
証明書が期限切れになった後、**nginx を再起動しても新しくなりません**。正しい順序は、**まず更新を成功させ**（`sudo certbot renew` を実行し、それが報告するエラーを解決する）、**それから nginx を再読み込み**することです。逆にやると時間を無駄にするだけです。
:::

### 8.3 HSTS は事態を悪化させる

HSTS（`Strict-Transport-Security` レスポンスヘッダ）を有効にしていると、ブラウザは**一定期間 HTTPS を強制し、利用者に「続行」を押させません**。証明書が期限切れになると、ページは**完全に迂回できない**エラーになります。HSTS 自体は良いもの（ダウングレード攻撃を防ぎます）ですが、その代償を覚えておいてください。**「証明書は常に有効であるべき」を「望ましい」から「絶対の要件」に変えます**。有効にする前に、自動更新と監視が整っていることを確認してください。

## 9. 証明書ファイルと権限

秘密鍵はこの体系で唯一、本当に秘匿が必要なものです。

```bash
# 秘密鍵は所有者だけが読めるように。ディレクトリも同様に絞る
sudo chmod 700 /etc/letsencrypt/archive /etc/letsencrypt/live
sudo chmod 600 /etc/letsencrypt/archive/<ドメイン>/privkey*.pem
sudo chown root:root /etc/letsencrypt/archive/<ドメイン>/privkey*.pem

# 確認：group/other が読める状態になっていないこと
ls -l /etc/letsencrypt/live/<ドメイン>/
```

要点：

- **`chmod 600` + 所有者 root** はよくある安全なやり方です。ACME クライアントは通常、自分で妥当な権限を設定します。**まず現状を見てから変更**してください。
- **秘密鍵を Web のルートディレクトリ、一時ディレクトリ、チャットツール、Git リポジトリにコピーしないでください。** 他のサービスに渡す必要があるときは、`chmod 644` ではなく権限グループや ACL を考えます。
- nginx の **master プロセスは通常 root で起動**するため、root 所有の秘密鍵を読めます。**導入方法が違う場合（コンテナ、非 root での実行）は、証明書を読むユーザーに権限があることを確認**してください。さもないと「設定は正しいのに起動に失敗する」という症状になります。
- **`chmod -R 777 /etc/letsencrypt` は絶対に誤り**です。権限エラーは消えますが、同時に秘密鍵をマシン上の全ユーザーに渡すことになります。
- **バックアップは証明書も一緒に考える**必要がありますが、**バックアップ内の秘密鍵も暗号化して保管**してください（[遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照）。

## 10. リバースプロキシの連鎖

HTTPS を nginx で終端し、リクエストをさらにパネルへ転送するとき、**「プロトコル」という話は連鎖の中で 2 つの別の概念になります**。

```text
プレイヤーのブラウザ  --HTTPS-->  nginx（TLS 終端）  --HTTP(127.0.0.1)-->  パネル
```

そこから生まれるよくある 3 つの問題：

| 問題 | 現れ方 | 対処 |
| --- | --- | --- |
| パネルが生成するリンクが `http://` になる | ページ内のリソースやリダイレクトをブラウザが遮る | `X-Forwarded-Proto $scheme` を転送し、パネルの公式ドキュメントに従って「外部アドレス / 信頼するプロキシ」を設定する |
| パネルが「接続が安全でない」と判断し、Cookie の設定を拒否する | ログイン直後に切断される | 同上。パネルによっては設定で HTTPS を明示する必要がある |
| WebSocket がつながらない | コンソールが真っ白、ずっと読み込み中 | `Upgrade` と `Connection` ヘッダを転送し、`proxy_http_version 1.1` を設定する |

**手前にもう 1 層 CDN がある場合**（Cloudflare など）、連鎖は「ブラウザ → CDN（TLS 終端）→ オリジン（さらに別の TLS）」になり、両端が**それぞれ自分の証明書と設定を持ちます**。**オリジンの証明書を検証するか、どのモードを使うかは CDN 事業者の挙動であり、公式ドキュメントに従ってください**。こうした連鎖で「どの証明書が期限切れなのか」を調べるとき、第 8 節の `-servername` を使った検査が役に立ちます。

パネル側の完全な設定は [パネル管理ツールの利用とセキュリティ](/tutorials/ops/panels) を参照してください。

## 11. 自己署名証明書：どこまで許容できるか

自己署名証明書（自分が CA になって自分に署名する）は**「無料の HTTPS」ではありません**。その位置づけは次のとおりです。

| 場面 | 使えるか |
| --- | --- |
| 自分だけが内部ネットワークからアクセスする（たとえば [家庭用 PC での開設と保守](/tutorials/ops/home-hosting) の内部ネットワークの場面）うえで、自己署名の CA を自分の端末の信頼ストアに入れられる | **使える** |
| 一時的なテスト、まだドメインを割り当てていない段階 | **使える**。ただしいつでも差し替えられることを理解しておく |
| インターネットに公開し、プレイヤーや共同管理者が使う | **使えない**。全員にブラウザの警告が出る |
| API クライアント、ボット、プラグインから呼ぶ | **通常はだめ**。多くのクライアントは信頼できない証明書を既定で拒否し、**検証を無視するよう設定を変えるのはさらに悪い選択** |

知っておくべき現実：

- **ブラウザの警告は「設定で消す」ことはできません**。利用者に見えるのは「この接続はプライベートではありません」で、「詳細 → 続行」を手で押す必要があります。**これは利用者に警告を無視することを訓練し、それ自体がセキュリティ上の問題になります。**
- 自己署名証明書で警告を出さないようにするには、**自己署名の CA をすべてのクライアント端末にインポート**する必要があります。端末が増えると、この保守コストは無料の証明書を 1 枚申請する手間を超えます。
- 内部の場面で本当に必要なら、**mkcert**、**step-ca** のような内部 CA 専用のツールを使うほうが、`openssl req` を手で叩くより間違えにくいです（**具体的な使い方は各公式ドキュメントに従ってください**）。
- 自己署名証明書のサイトで HSTS を有効にすることは**絶対にしないでください**。

## 12. 監視とチェックリスト

**証明書の期限切れは「完全に事前に分かる」障害**なので、祈るのではなく監視すべきです。最低要件は、**残りの有効期間が 14 日を切ったらアラート**。方法は 2 つあり、**両方やることを勧めます**。

1. **外部からの HTTPS 検査**：このマシンの外にある監視から数分おきにパネルのアドレスへリクエストし、証明書の期限を検査します。多くの監視ツール（Uptime Kuma など）の HTTPS 監視は証明書の情報を直接表示します。[監視とアラート](/tutorials/ops/monitoring) を参照。
2. **ローカルでの期限検査**：サーバー上で証明書ファイルを読んで残り日数を計算し、監視の指標に書き込むか、直接通知を送ります。

```bash
# 1 行版：残り日数を出力する（date の -d は GNU の書き方。他のシステムでは対応する日付コマンドを使う）
sudo openssl x509 -in /etc/letsencrypt/live/panel.example.com/fullchain.pem -noout -enddate \
  | cut -d= -f2 \
  | xargs -I{} date -d "{}" +%s \
  | awk -v now="$(date +%s)" '{ printf "残り %d 日\n", ($1 - now) / 86400 }'
```
:::tip アラートは「更新が成功しなかった」ことを捉えられなければならない
「証明書があと何日か」を監視するだけでは足りません。**30 日前から「まもなく期限切れ」と鳴り、あなたがそのアラートに慣れてしまう**からです。より良い組み合わせは、**更新タスクの失敗アラート**（timer/cron の失敗通知）**と**「残り日数 < 14 日」のアラートです。前者は「自動更新が壊れた」ことを教え、後者は最後の受け皿になります。
:::

### 12.1 公開前のチェックリスト

| 確認項目 | どうやるか | 合格基準 |
| --- | --- | --- |
| 証明書を発行した | `certbot certificates` | ドメインが正しく、期限が未来 |
| 完全なチェーンを使っている | nginx の設定の `ssl_certificate` を見る | `fullchain.pem` を指している。単独の `cert.pem` ではない |
| プロトコルのバージョンが正しい | ブラウザか `openssl s_client` で検査 | TLS 1.2 / 1.3 でネゴシエートされる |
| HTTP から HTTPS へリダイレクトする | `http://` で 1 回アクセスする | 301/308 でリダイレクトし、混在コンテンツの警告が出ない |
| 検証のパスが使える | `curl -I http://ドメイン/.well-known/acme-challenge/<テストファイル>` | 200 を返す（リダイレクトに飲み込まれない） |
| 自動更新のタスクが動いている | `systemctl list-timers` か `/etc/cron.d/` を見る | 更新タスクが 1 つだけ存在する |
| 更新の演習が通った | `certbot renew --dry-run` | エラーがない |
| 更新後に再読み込みされる | deploy hook を確認する | 更新の成功後に nginx が本当に再読み込みされる |
| 秘密鍵の権限を絞り、漏洩したコピーがない | `ls -l` + `stat`。ディスクと Git の履歴も検索する | 所有者以外は読めず、秘密鍵は証明書のディレクトリと暗号化したバックアップにしか存在しない |
| 期限のアラートを設定した | 監視パネル | しきい値をわざと大きくして、アラートが出ることを 1 回確認する |
| パネル / マップが本当に使える | ブラウザで実際に 1 回アクセスする | ログイン、コンソール、マップが正常で、証明書の警告が出ない |
