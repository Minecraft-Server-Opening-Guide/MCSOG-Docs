これまでの記事はソフトウェア層の話でした。Java を入れ、サーバーを選び、プラグインを設定し、バックアップを取る。この記事は**物理層**の話です。サーバーをラックに収めた後、「3 か月連続で問題なく動くか」を本当に決めるものごとです。

対象は**家のタワー型 1 台**から**データセンターの 1U マシン**まで。型番、メーカー、ファームウェアのバージョンで変わるパラメータには、本文で「型番による」と明記し、具体的な数字を勝手に作ることはしません。

## 1. まず 3 つの層を分ける

| 層 | 何を気にするか | 失敗したときの現れ方 |
| --- | --- | --- |
| **アプリケーション層** | サーバーコア、プラグイン、設定 | クラッシュ、ラグ、エラー |
| **システム層** | Java、メモリ、ファイアウォール、バックアップ | 起動しない、侵入される、データを失う |
| **物理層** | ラック、電源、LAN ケーブル、冷却、帯域外管理 | **マシン全体の電源断、過熱によるクロック低下、遠隔から手が届かない** |

物理層の特徴は、**普段はまったく意識せず、事故が起きたときに最も立て直しにくい**ことです。データセンターのマシンが通信を失えば、できることはたいてい電話して電源ボタンを押してもらうことだけです。だからこの層のお金と時間は「予防」に使うのが最も割に合います。

## 2. ラックの基礎：19 インチ、U 高、レール

標準ラックは **EIA-310 / IEC 60297** 系の規格に由来し、重要な数字はいくつかあります。

| 項目 | 数値 | 説明 |
| --- | --- | --- |
| 取付幅 | 19 インチ = **482.6 mm** | 両側の取付フランジ間の内幅 |
| 1U の高さ | **44.45 mm**（1.75 インチ） | U 数はすべてこの整数倍 |
| 42U フルハイトラック | 有効な取付高さ約 **1866.9 mm** | 全体の外高は通常約 2000 mm。メーカーによる |
| よくある奥行き | 600 / 800 / 1000 / 1200 mm | **サーバー用ラックは通常 800 mm 以上必要** |

よくある仕様：**1U**（最も薄く、冷却の余裕が最小、ファン回転数が最高、最も騒がしい）、**2U**（冷却と拡張の余裕が明らかに良く、ディスクやハーフハイトの PCIe カードを多く積める）、**4U**（フルハイトのカードや多数のドライブベイが積め、タワー型に近い静かさ）。家庭用や小規模なら 2U/4U か、いっそタワー型を優先してください。1U マシンの騒音（よくあるのは 60〜80 dBA 程度。型番による）は寝室には向きません。

取付穴には 2 種類あります。

- **角穴ラック**：**ケージナット（cage nut）** + M6 ねじを使う。最も一般的。
- **ねじ穴ラック**：10-32 か M6 のねじを直接ねじ込む。ケージナットは不要。

EIA-310 の穴は**3 つで 1 組の繰り返し**（間隔 15.875 mm / 15.875 mm / 12.7 mm）で、レールを取り付けるときはこの組に合わせる必要があります。さもないと上下の機器がずれます。

**レール（rail kit）**は落とし穴が最も多い部分です。

- **固定レール**：載せたら引き出せない。安く、しっかりしている。
- **スライドレール**：マシンを丸ごと引き出して保守できる。通常は**ケーブルマネジメントアーム（CMA）**付きで、価格は高い。
- レールは**メーカー / 型番専用**のことが多く、しかも**対応する奥行きの範囲が限られます**。ラックを買う前にレールの対応最小 / 最大奥行きを確認してください。600 mm のラックには長い筐体のサーバーの多くは収まりません。
- スライドレールには**ケーブルの余裕**を確保してください。さもないと引き出したときに LAN ケーブルや電源ケーブルを引きちぎります。

ラックには U を消費しない**縦置き 0U PDU**（第 15 節を参照）や、1U を使う横置き PDU、ケーブル整理板、ブランクパネルもあります。

## 3. エアフロー：前面吸気・背面排気、コールド / ホットアイル、「吸気口を絶対に塞がない」

ほとんどのラックサーバーは**前面吸気、背面排気**です。冷たい空気を前面パネルから吸い、熱い空気を背面から出します。データセンターの配置の論理はここから来ています。

- **コールドアイル**：ラックの正面。空調がここへ冷風を送る。
- **ホットアイル**：ラックの背面。機器が排出した熱風がここに集まり、戻っていく。
- 理想は**コールド / ホットアイルの分離**（閉鎖通路か適切な配置）で、熱風が吸気口へ再び吸い込まれないようにする。

いくつかの厳格な規律：

1. **吸気口を絶対に塞がない**。前面パネルを塞ぐ、密閉した棚に押し込む、壁に密着させる。どれも過熱によるクロック低下やダウンに直結します。
2. **空き U にはブランクパネルを付ける**。空きがあると、ラック後方の熱風が前方へ回り込み、上の機器に吸い直されます。
3. **防塵フィルターを定期的に洗う**。目詰まりしたフィルターは吸気口を塞いだのと同じです。
4. **ラックの扉は十分に通気性を**。通常は開口率が高いこと（多くは 60% 以上。具体的にはメーカーの仕様）が求められ、無垢のガラス扉は高密度な機器にとって災難です。
5. **ファンの向きの型番に注意**。一部のスイッチと電源は**反転可能なエアフロー**（ポート側吸気 / ポート側排気）に対応し、これは**別の SKU**です。ラックの気流の向きに合わせて発注する必要があり、混在させるとコールド / ホットアイルが崩れます。
6. **吸気温度を見る。データセンターの室温を見ない**。温度センサーは機器の吸気口の近くに置きます。データセンターの環境温度には ASHRAE の推奨許容範囲があります（等級 A1–A4 で異なる）が、**機器の吸気温度**こそがクロック低下の有無を本当に決める量です。

コロケーションでは通常、ラックの正面しか制御できません。データセンター側のコールド / ホットアイルの規定に従い、自分の都合で機器を逆向きに取り付けたりしないでください。

## 4. Minecraft 用のサーバーハードウェア選び：シングルコア優先

Minecraft サーバーの tick ループの目標は **20 TPS**、つまり 1 tick あたり **50 ms** の予算です。メインスレッドが世界のロジックの大部分を担います。エンティティ、レッドストーン、ブロック更新、プレイヤーの移動、ほとんどのチャンク読み込みのスケジューリング。したがって：

**シングルコア性能（周波数 × IPC）はコア数より重要です。**

| ワークロード | スレッドの特徴 |
| --- | --- |
| メインの tick ループ（エンティティ、レッドストーン、プレイヤー、多くのブロックロジック） | ほぼ単一スレッド。TPS を決める |
| チャンク生成 / ライティング（Paper などで非同期化した後） | マルチスレッド化できる。コアが多いほど有利 |
| プラグイン / MOD の非同期タスク、データベース、マップ描画 | マルチスレッド化できる |
| 複数のサーバーインスタンスを同時に動かす | コア数が直接線形に効く |

結論：

- 中規模のバニラ / Paper サーバーを 1 つ動かすだけなら、**高周波の 2〜4 コア**が低周波の 16 コアに勝ることがよくあります。
- コアが多いのは**無駄ではありません**が、単一インスタンスへの限界効用は逓減します。
- CPU を選ぶときは**シングルスレッドのスコア**（各種ベンチマークのシングルコア成績）を見て、「何コア何スレッド」だけを見ないこと。
- **コンシューマー向けプラットフォームかサーバー向けプラットフォームか**の取捨：コンシューマー向け（Ryzen、Core）は通常シングルコアが強く、安く、静か。サーバー向け（Xeon E、Xeon Silver、EPYC など）は ECC、IPMI、冗長電源、より多くのメモリチャネルとドライブベイを提供します。**型番による世代差が大きいので、メーカーの仕様ページに従ってください。**

メモリについては、小規模なバニラサーバーで 4〜8 GB、中規模かプラグインありで 8〜16 GB、大型の統合パックで 16 GB 以上がよくある範囲です。**メモリを増やしても効果はありません**（[サーバーの設定](/tutorials/java/config) を参照）が、少なすぎると GC で頻繁にラグります。

## 5. ECC と非 ECC

**ECC（Error-Correcting Code）**メモリは 1 ビットの誤りを訂正し、2 ビットの誤りを検出し（SEC-DED）、訂正できない誤りを報告します。**性能は上がりません**。上がるのは**長期稼働の信頼性**です。

- 数か月連続で動かすマシンでは、メモリの誤りが起きる確率は低くありません。非 ECC メモリの誤りは**静かなデータ破損**として現れることが多く、ワールドファイルが壊れても後から原因はまったく分かりません。
- ECC は **CPU + マザーボード + メモリモジュールの 3 つが同時に対応**している必要があり、どれが欠けてもだめです。
- **UDIMM（アンバッファード）**はコンシューマー向け / エントリーサーバーでよく使われ、**RDIMM / LRDIMM（レジスタ / ロードリデュース）**はサーバー向けプラットフォームでしか使えませんが、1 本あたりの容量が大きく、1 チャネルに多く挿せます。
- **DDR5 のオンダイ ECC（on-die ECC）はエンドツーエンドの ECC とは別物**です。DDR5 チップ内部の仕組みで、システムには報告されず、帯域外の ECC の代わりにはなりません。
- ECC の誤りは BMC/IPMI の SEL ログや Linux の EDAC サブシステム（`/sys/devices/system/edac/`、`edac-util` など）で監視できます。

**結論**：家庭用の娯楽サーバーなら非 ECC でも許容できます。**インターネットに長期間公開し、プレイヤーデータが重要なサーバーには ECC を勧めます**。ECC と非 ECC、RDIMM と UDIMM の**混挿は通常起動しない**ので、メモリを増やす前にマザーボードの QVL 互換リストを確認してください。

## 6. ストレージ：SSD / NVMe と耐久性

| インターフェース | 典型的なシーケンシャル帯域 | 備考 |
| --- | --- | --- |
| SATA SSD | 約 500〜560 MB/s | SATA 6 Gb/s の制限を受けるが、ランダム性能は機械式よりはるかに良い |
| NVMe PCIe 3.0 x4 | 約 3.5 GB/s | 型番による |
| NVMe PCIe 4.0 x4 | 約 7 GB/s | 型番による |
| NVMe PCIe 5.0 x4 | 約 14 GB/s | 型番による。発熱が明らか |

**Minecraft にとって、シーケンシャル帯域は基本的にボトルネックではありません**。体験を本当に左右するのは：

- **4K ランダム読み書きのレイテンシとキュー深度の挙動**（チャンクファイル、ログ、データベース）。
- **書き込み増幅と SLC キャッシュを使い切った後の速度低下**（大量の保存やバックアップのとき）。
- **停電保護（PLP）**：エンタープライズ向けのドライブは PLP を備え、停電時に途中の書き込みをディスクへ落とせます。コンシューマー向けには通常なく、**UPS で補う**ことになります（第 13 節を参照）。

**耐久性**は **TBW（総書き込みバイト数）** か **DWPD（1 日あたりの全容量書き込み回数）**で測ります。要点：

- TLC は QLC より耐久性と持続書き込みの性能が良い。QLC は大きな書き込みの後に明らかに速度が落ちる。
- **DRAM キャッシュのないドライブ**（HMB に頼る）はランダム負荷で弱いことが多く、軽い負荷に向きます。
- Minecraft 自体の書き込み量は誇張されたものではありません。サーバーは定期的にワールドを保存し（バニラで約 5 分ごと。Spigot/Paper は `spigot.yml` の `ticks-per.autosave` で調整できる）、さらにログとプレイヤーデータがあります。
- ただし**プラグインは書き込みを明確に増やします**。CoreProtect のような記録系プラグイン、Dynmap/BlueMap のマップ描画、頻繁な自動バックアップは、いずれも継続的にディスクへ書きます。
- したがって**システムディスクとデータディスクを分ける**、**バックアップは別のディスクか NAS/HDD に書く**のがよくあるやり方です。
- **RAID はバックアップではありません**。RAID 1 は 1 台のドライブ故障には耐えられますが、誤削除、ランサムウェア、rm -rf には耐えられません。遠隔地バックアップは依然として必須です（[バックアップと復元](/tutorials/java/backup) を参照）。

## 7. 冗長電源（1+1）とコロケーション環境

**1+1 冗長電源**とは、マシンにホットスワップ可能な電源モジュールが 2 つあり、どちらかが故障しても片方だけでマシン全体の負荷をまかなえることを指します。誤解しやすい点をいくつか。

- **各モジュールが単独で全負荷を担える必要があります**。「半分ずつ」ではありません。選定時はマシン全体のピーク消費電力で単一モジュールの容量を選びます。
- 本当に意味があるのは**2 系統給電（A/B フィード）**です。電源 A と B を**別の PDU / 別の分岐**に接続します。2 つのモジュールを同じ電源タップに挿すと、そのタップのブレーカーが落ちた時点で 1+1 は存在しないのと同じです。
- コロケーションのラックは通常 A/B の 2 系統の商用電源を提供しますが、**データセンターによっては 2 系統目が追加料金**です。契約前に確認してください。
- 1+1 が防ぐのは「電源モジュールの故障」と「片系統の給電故障」で、**2 系統同時の停電は防げません**。それは UPS と発電機の仕事です。
- 冗長電源はファンの騒音とわずかな効率損失をもたらします。電源効率の等級（80 PLUS の各段階）は電気代と発熱に影響し、長期のコロケーションでは注目に値します。

## 8. IPMI / BMC の帯域外管理

**BMC（ベースボード管理コントローラ）**はサーバーのマザーボード上の独立した小さなシステムで、待機電源から給電され、**OS がシャットダウンしていても、OS が入っていなくてもオンライン**です。メーカーごとに実装名が違い、Dell は iDRAC、HPE は iLO、Lenovo は XClarity Controller、Supermicro / ASRock Rack / GIGABYTE などは通常そのまま BMC か IPMI と呼びます。プロトコルは伝統的に **IPMI 2.0** で、現代の代替が **Redfish**（HTTPS ベースの REST インターフェース）です。

できること：

- **リモート KVM**：マシンの前に座っているように画面を見てキーボードを打てる。BIOS に入ることもできる。
- **仮想メディア**：ローカルの ISO を光学ドライブとしてマウントし、OS の導入やレスキューに使う。
- **電源制御**：電源オン、オフ、再起動、強制電源断。
- **センサーとログ**：温度、ファン、電圧、SEL イベントログ。
- **Serial over LAN**：シリアルのリダイレクトでコンソールを見る。

よくあるポート（**具体的なポートと実装はメーカー / 型番で変わります**）：

| 用途 | よくあるポート |
| --- | --- |
| IPMI RMCP / RMCP+ | UDP 623 |
| BMC の Web 画面 | TCP 80 / 443 |
| リモート KVM（一部の実装） | TCP 5900 / 5901 など |
| Redfish | TCP 443 |

:::warn IPMI は絶対にインターネットへ露出させない
これは保守的な助言ではなく、明確な業界の合意です。理由：IPMI 2.0 には歴史的に認証回避系の脆弱性があり（有名な cipher 0 / RAKP 関連など）、多くのメーカーのファームウェアには**既定のアカウントとパスワード**が付いています（具体的な既定値は型番とファームウェアのバージョンで変わるので、必ず自分で変更してください）。一部の実装は管理通信の暗号化が弱く、Web 画面にも大量の脆弱性が出ています。**BMC を手に入れることはマシン全体を手に入れること**です。遠隔で電源を入れ、イメージをマウントし、OS を入れ直せます。

正しいやり方：
- BMC は**独立した管理セグメント / VLAN** に接続し、業務用のポートと混ぜない。
- そのセグメントは**インターネットへの経路を持たない**。アクセスが必要なときは VPN か踏み台を経由する。
- 既定のパスワードを変更し、使わないサービスを止め（たとえば IPMI over LAN が不要なら切る）、アクセス可能な送信元 IP を制限する。
- BMC のファームウェアを速やかに更新する（BMC ファームウェアの脆弱性は現実の攻撃面です）。
- IPMI より Redfish を優先する。
:::

## 9. スイッチ：アンマネージドとマネージド

| 能力 | アンマネージド | マネージド（L2 / L2+） |
| --- | --- | --- |
| プラグアンドプレイ | はい | 設定が必要 |
| VLAN（802.1Q） | なし | あり（access / trunk ポート） |
| リンクアグリゲーション（LACP、802.3ad） | なし | あり |
| ポートミラーリング（SPAN） | なし | あり。パケットキャプチャの切り分けに必須 |
| SNMP 監視 | なし | あり（v2c / v3） |
| STP / RSTP のループ防止 | 通常は基本的な実装あり | あり |
| IGMP snooping（マルチキャスト最適化） | なし | あり |
| ポートセキュリティ / ストーム抑制 / DHCP snooping | なし | あり |

選び方：

- **家に 1〜2 台、フラットな 1 つのネットワーク**：アンマネージドのギガビットスイッチで十分。安く、故障点がなく、壊れたら交換するだけ。
- **ラックがあり、業務 / 管理セグメントを分け、リンクアグリゲーションやキャプチャをしたい**：マネージドにする。VLAN で BMC、業務通信、ゲストネットワークを分けられ、第 8 節の安全要件の前提になります。

必ず覚えておく概念が 2 つ：

1. **スイッチは NAT もしないし、ポート転送もしない**。L2 スイッチは MAC で転送するだけ。L3 スイッチは VLAN 間をルーティングできますが、**通常 NAT はしません**。インターネットからのポートマッピングはルーター / ファイアウォールが行います（[ソフトウェアルーターとポート転送](/tutorials/ops/router-firewall) を参照）。
2. 家庭用の「ルーター」は実は**ルーティング + スイッチング + 無線 AP** の一体型です。純粋なスイッチと混同しないでください。

## 10. 速度の選択とアップリンクの収束比

| 規格 | よくある媒体 | 距離 |
| --- | --- | --- |
| 1000BASE-T（1GbE） | Cat5e / Cat6 | 100 m |
| 2.5GBASE-T / 5GBASE-T | Cat5e / Cat6（802.3bz） | 100 m |
| 10GBASE-T | Cat6 で約 55 m、Cat6a で 100 m | 配線規格とメーカーの表明による |
| 10GBASE-SR | OM3 / OM4 マルチモードファイバー | 約 300 m / 400 m |
| 10GBASE-LR | OS2 シングルモードファイバー | 約 10 km |
| SFP+ DAC / AOC | 銅線ダイレクト / アクティブ光ケーブル | ラック内の短距離。通常は数メートル |

**Minecraft ではいつ重要になるか？**

- プレイヤー 1 人が使う帯域は実はごく小さく（平均で数十〜数百 kbit/s 程度。入室してチャンクを読み込むときにバーストする）、**1GbE のサーバー 1 台で多くのプレイヤーを連れられます**。
- **1GbE がほとんどの開設場面での正解**です。
- 2.5GbE/10GbE が本当に役に立つのは、**ストレージ / NAS / バックアップ、仮想マシンの移行、多数のサーバー間の内部通信**です。
- 「プロに見えるから」という理由で MC サーバーに 10GbE を載せないでください。そのお金は UPS や ECC に使うほうが価値があります。

**アップリンクと収束比（oversubscription）**：アクセスポートの総帯域とアップリンク帯域の比です。たとえば 24 のギガビットポートに 2 つの 10 ギガビットアップリンクなら、24 Gb/s のアクセスに対して 20 Gb/s のアップリンクで約 1.2:1。ギガビットアップリンク 1 本なら 24:1 です。小さなラックならギガビットのアップリンクで十分です。**LACP が束ねるのは総帯域で、単一のフローはやはり 1 本のリンクを通ります**（ハッシュによる経路選択）。そのため 1 つのバックアップタスクが集約帯域を使い切れるとは限りません。

**PoE は電話、カメラ、無線 AP にしか関係しません**。サーバーは PoE では動きません。規格の対照：802.3af は 1 ポートあたり約 15.4 W（受電側で約 12.95 W）、802.3at/PoE+ は約 30 W（約 25.5 W）、802.3bt Type 3/4 は約 60 W / 90 W。機器全体の PoE 総電力の予算は限られており（型番による差が大きい）、高出力の機器を複数つなぐ前に予算を計算してください。

## 11. ハードウェアファイアウォール：「境界」という層を補うもの

**ホストのファイアウォール**（Windows ファイアウォール、ufw、firewalld、nftables）は**自分自身のマシン**しか守らず、しかも OS が起動してから効きます。できないことは：

- ネットワーク境界での**ステートフル検査**（conntrack による接続状態の追跡）と、通信がどのホストにも届く前に捨てること。
- **NAT / ポート転送**（これはルーター / ファイアウォールの役割）。
- **サイト間 VPN**（2 つの拠点の内部ネットワークをつなぐ）と**リモートアクセス VPN**。
- **統一したポリシー**：1 か所で規則を定義し、セグメント全体をカバーする。各マシンで繰り返し設定するのではなく。
- **ログと監査の集中**：誰がいつどのポートに接続しようとしたか。
- **DMZ の分割**：インターネットに露出するサービスと内部のマシンを分ける（第 12 節を参照）。
- ホストの電源が入っていない、OS が落ちた、侵入された後でも**依然として遮断し続ける**こと。

形態は 2 つあります。

- **専用のハードウェア機器**（各社のファイアウォール / UTM / NGFW 機器）。
- **x86 + ファイアウォール用ディストリビューション**：pfSense（FreeBSD 系）、OPNsense、OpenWrt など。普通の x86 マシンで動き、費用対効果が高く機能も十分で、小さなラックによく合います。選定と設定は [ソフトウェアルーターとポート転送](/tutorials/ops/router-firewall) を参照。

**仕様書の性能の数字には必ず注意してください**：

| 指標 | 意味 |
| --- | --- |
| Firewall throughput | 通常は大きなパケットで、深い検査なしの素の転送能力 |
| IPS / NGFW throughput | 深い検査を有効にした後の能力。**素の転送のごく一部であることが多い** |
| VPN throughput | 暗号化トンネルのスループット。アルゴリズムと CPU による |
| Concurrent sessions | 同時接続テーブルの容量 |
| New sessions/sec | 新規接続の確立速度 |

**各社の測定方法が違います**（パケット長、プロトコル、機能の有効化の有無がすべて異なる）。メーカーをまたいで数字を直接比べても意味はなく、**メーカーの公式 datasheet の測定条件に従ってください**。

Minecraft の場面では、接続数は数百から数千、帯域の需要は通常数百 Mbit/s 未満です。**エントリークラスの機器 1 台か、小さな x86 のソフトウェアルーター 1 台で十分すぎるほど**です。大型の NGFW を買う理由は VPN、セグメント分割、管理能力であるべきで、「MC は多くのスループットを必要とする」ではありません。

## 12. トポロジと DMZ

標準的な順序：

```text
インターネット (WAN)
   |
光回線終端装置 / ONT
   |
[ ファイアウォール / ルーター ]        <- NAT、ポート転送、状態検査、VPN はすべてここ
   |
[ スイッチ ]                 <- VLAN 分割、リンクアグリゲーション
   |----------|----------|
[ MC サーバー ] [ 管理マシン ] [ BMC 管理ポート ]
```

**DMZ** は**独立したセグメント / インターフェース / VLAN** で、「インターネットに開放する必要がある」サービス（パネル、Web サービスなど）を置きます。規則の考え方：

- WAN から DMZ：本当に必要なポートだけを許可する。
- **DMZ から LAN：既定で拒否**（またはごく少数の必要な通信だけ許可）。
- LAN から DMZ：管理を許可する。
- こうすれば、インターネット側のサービスが破られても、攻撃者は DMZ に閉じ込められ、内部のデータベースや他のマシンには手が届きません。

:::warn コンシューマー向けルーターの「DMZ ホスト」は別物
多くの家庭用ルーターの「DMZ」機能は、**すべてのポート**を無条件に 1 台の内部マシンへ転送します。それはセグメント分割ではなく、1 台のマシンをインターネットに完全に裸で置くことです。**この機能は使わないでください**。ポートごとに転送してください。
:::

その他の境界の規律：WAN 側の管理画面を閉じる、既定のパスワードを変える、不要なら UPnP/NAT-PMP を切る、ログを有効にする、ファイアウォールの設定を定期的にバックアップする。また、**ファイアウォールはアプリケーション層の脆弱性は防げません**。サーバー自体の脆弱性やプラグインの RCE は、パッチと権限管理で対処します（[セキュリティプラグイン](/tutorials/ops/security-java) を参照）。

## 13. UPS：何を守るのか

| 脅威 | UPS で解決するか | 説明 |
| --- | --- | --- |
| 完全な停電 | する（限られた時間） | バッテリーで優雅なシャットダウンか発電機の起動まで持たせる |
| 電圧降下 / 低電圧（brownout） | する | AVR 付きの機種は昇圧で補償できる |
| サージ / スパイク | 部分的 | クランプ能力はあるが、**直撃雷は保証範囲外** |
| 周波数 / 電圧の変動 | 機種による | 常時インバータ式が最も徹底している |
| 過負荷 | しない | 過負荷はそのままバイパスかシャットダウンになる |
| バッテリーの劣化 | しない | 定期的な交換が必要 |

**VA と W の違い**：VA は皮相電力（電圧 × 電流）、W は有効電力で、両者の比が力率（PF）です。仕様書には両方が載ります（たとえば 1500 VA / 900 W）。**W で選定**し、余裕を持たせてください。負荷は長期的に定格 W の 60%〜80% 以内に収め、同時に VA の上限も超えないことを確認します。

**バッテリーの持続時間は線形ではありません**：負荷が半分になっても**持続時間がちょうど 2 倍になるわけではなく**（鉛蓄電池の Peukert 効果とインバータの固定損失）、バッテリーは時間と温度で劣化します。**メーカーの持続時間曲線に従ってください**。自分で線形に推定しないこと。

**波形**：

- 常時商用給電式と多くのラインインタラクティブ式は、バッテリーモードで**擬似正弦波（階段波）**を出力します。
- 常時インバータ式（ダブルコンバージョン）は**純正弦波**を出力します。
- **アクティブ PFC の電源は正弦波入力を前提に設計**されており、階段波では唸り、切り替えの失敗、最悪シャットダウンが起き得ます。**使えるかどうかは電源の型番による**ので、電源メーカーの仕様に従ってください。
- 結論：**アクティブ PFC の電源には純正弦波の UPS を優先**。モーター系の負荷にも純正弦波を使ってください。

**3 つのトポロジ**：

| 種類 | 切り替え時間 | 出力波形 | 特徴 |
| --- | --- | --- | --- |
| 常時商用給電式 / オフライン式 | 通常数ミリ秒〜十数ミリ秒 | 多くは階段波 | 最も安く、保護能力は最も弱い |
| ラインインタラクティブ式 | 通常 2〜10 ms | 多くは階段波。純正弦波の機種もある | 小さなラックで最も一般的。AVR 付き |
| 常時インバータ式 / ダブルコンバージョン | 0（常にインバータ） | 純正弦波 | 電圧安定化と絶縁が最良。発熱、騒音、消費電力、価格はすべて高い |

切り替え時間と波形は**いずれも型番で変わります**。具体的な datasheet を見てください。

**負荷の粗い見積もり**：1U サーバー 250〜400 W（CPU とドライブベイによる）、スイッチ 30〜60 W、ファイアウォール 20〜40 W。合計にさらに 30% の余裕を見て、UPS の **W 定格**で選定し、持続時間が「少なくとも自動シャットダウンが終わるまで」持つことを確認します（通常は 10〜15 分で十分）。

## 14. UPS の監視と NUT による自動シャットダウン

UPS は**ホストに通知できる**ときだけ意味があります。さもないと停電後に 10 分多く持っただけで、そのまま強制的に落ちます。接続方法：

| 方法 | 説明 |
| --- | --- |
| USB HID | 現代の UPS で最も一般的。`usbhid-ups` ドライバが直接対応する |
| USB-シリアル | 一部の機種はシリアルプロトコル。`nutdrv_qx` などのドライバをよく使う |
| RS-232 シリアル | **ピン配置がメーカー専用のことが多い**。たとえば一部の APC 機種は特定型番の専用ケーブル（940-0024C の類）を使う。普通のクロスケーブルで動くとは限らず、**機種による** |
| SNMP 管理カード | エンタープライズ向けの UPS はネットワークカードを追加でき、ネットワーク経由で監視できる。**カードの型番はメーカーで変わる** |

**NUT（Network UPS Tools）**は Linux で最も汎用的な方案で、3 層に分かれます。**ドライバ（driver）が UPS との通信を担い、upsd がサーバー、upsmon が監視クライアント**です。upsmon は upsd から状態を読み、必要に応じてシャットダウンを起こします。

パッケージ名とサービス名は**ディストリビューションで異なります**。Debian/Ubuntu は通常 `nut-server`（upsd）と `nut-client`（upsmon）で、新しい版では `nut-driver-enumerator` / `nut-driver@myups` も使います。RHEL/Fedora 系のサービス名は `nut-server` と `nut-monitor` が一般的。設定ファイルのディレクトリは Debian 系が `/etc/nut/`、一部のディストリビューション（SUSE 系など）は `/etc/ups/` です。**以下の例は Debian/Ubuntu のパスで示します**。

`/etc/nut/ups.conf`：

```ini
# myups という名前の UPS を定義する
[myups]
    driver = usbhid-ups
    port = auto
    desc = "Rack UPS"
```

`/etc/nut/upsd.users`（`upsmon` が upsd にログインするためのアカウント）：

```ini
[monuser]
    password = secret
    upsmon primary
```

`/etc/nut/upsmon.conf`（最小限の使える設定）：

```conf
MONITOR myups@localhost 1 monuser secret master
MINSUPPLIES 1
SHUTDOWNCMD "/sbin/shutdown -h +0"
POLLFREQ 5
POLLFREQALERT 5
HOSTSYNC 15
DEADTIME 15
POWERDOWNFLAG /etc/killpower
```

説明と注意点：

- `MONITOR` 行の書式は `MONITOR <ups> <powervalue> <username> <password> <mode>` です。`1` はこの UPS がシステムに 1 系統の電源を供給していることを示し、`master` はバッテリーが尽きる前にこのマシンがシャットダウンを起こす責任を負うことを示します。
- **NUT 2.8.0 から `master`/`slave` が `primary`/`secondary` に改名**され、旧表記も互換のため受け付けられます。新しいドキュメントと例は `primary` を使うことが多いので、**導入しているバージョンの公式ドキュメントに従ってください**。
- `/etc/nut/upsd.users` と `upsmon.conf` はパスワードを含むため、Debian 系では `root:nut` かつ権限 `640` にします。さもないと `upsmon` が起動を拒否することがあります。
- `upsd` は既定で **TCP 3493** を待ち受けます。ローカルで監視するだけなら、**ネットワークへ露出させないでください**。どうしても複数マシンで監視するなら、ファイアウォールで送信元アドレスを制限します。

よく使うコマンド：

```bash
upsc myups                     # UPS のすべての変数を一覧する
upsc myups ups.status          # 状態だけを見る。OL（商用電源）/ OB（バッテリー）/ LB（低バッテリー）など
upscmd -l myups                # この UPS が対応する即時コマンドを一覧する
upsrw -l myups                 # 書き込み可能な変数を一覧する
systemctl restart nut-server   # 設定変更後に再起動する（サービス名はディストリビューションで変わる）
upsmon -c fsd                  # 強制シャットダウンの演習。慎重に
```

**バッテリーの交換と自己診断**：

- よくある制御弁式鉛蓄電池（VRLA/AGM）の寿命は通常 **3〜5 年**です。**環境温度が高いほど寿命は短くなり**（工学の経験則では約 10 ℃上昇ごとに寿命がほぼ半減。経験則です）。
- 多くの UPS は 2 週間ごとに自動で自己診断を行い、手動でも起動できます（パネルのボタン、または `upscmd myups test.battery.start.quick`。コマンド名は機種による）。
- **自己診断が失敗したとき、または持続時間が要件を下回ったときにバッテリーを交換します**。同じ直列のバッテリーは組ごと交換してください。
- リチウム電池（LiFePO4 など）の機種は通常寿命が長いですが、**具体的な型番による**。
- 古いバッテリーは現地の規定に従って回収し、気軽に捨てないこと。

## 15. ケーブルと給電の安全

**給電**

- **電源タップを直列につながない**（タップにタップ）。直列にすると接触抵抗が増え、ブレーカーの協調が効かなくなり、1 つの壁コンセントが過負荷になり得ます。ラックでは**ラックマウント PDU** を使ってください。
- PDU には横置き 1U と縦置き 0U があります。コンセントは **IEC 60320 C13（約 10 A 級）** と **C19（約 16 A 級）** が一般的で、入力は C14/C20 です。**計測型か遠隔制御可能な** PDU を選ぶと、切り分けと遠隔からの再起動が楽になります。
- **UPS の出力を PDU に接続し、保護したい機器をその PDU に接続します**。重要な機器を壁に直接挿さないでください。
- **分岐の容量を把握する**：中国でよくある 10 A / 250 V のコンセントは約 2200 W。北米の NEMA 5-15 は 15 A / 120 V の分岐で約 1800 VA で、規格上は連続負荷を通常 80%（約 1440 W）までにします。英国の BS 1363 は 13 A。**実際は現場の電気設計と電気工事士の判断に従ってください。上限ぎりぎりで走らせないこと。**
- **接地**：アース線の足を折らない、「3 極から 2 極」の変換アダプタを使わない、ラックは等電位ボンディングを行う。浮いた接地は感電と火災のリスクであり、原因不明の間欠的な故障も生みます。

**ケーブル**

- **両端にラベルを貼る**：片端には接続先の機器とポート、もう片端には戻り先を書く。データセンターでラベルのないケーブルは、ケーブルがないのと同じです。
- 簡単なトポロジ図か表を残す（どのマシンのどのポートがどのスイッチのどのポートにつながっているか）。
- ケーブルの束は**マジックテープ**で。結束バンドはケーブルを締め付け、変更のたびに切る必要があります。
- **光ファイバーは曲げ半径に注意**（一般にケーブル径の 10 倍以上。具体的にはメーカーの仕様）。折り目を付けないこと。銅線も長期的に過度に曲げないでください。
- 強電と弱電はできるだけ経路を分ける。スライドレールを使うときはケーブルに十分な余裕を取り、ケーブルマネジメントアームも検討する。
- **予備部品を常備する**：各長さの LAN ケーブルを 1 本ずつ、C13/C19 の電源ケーブル、SFP+/DAC モジュール、ケージナットとねじ、予備のディスク 1 台。コロケーション環境では、remote hands の 1 回の出張費がこれらの予備部品よりはるかに高いことがよくあります。

## 16. ラック搭載前のチェックリスト

- [ ] ラックの奥行きとレールの対応範囲が合っており、U の位置を計画し保守の空間も確保した
- [ ] 空き U にブランクパネルを付け、前面の吸気口を塞がず、防塵フィルターもきれい
- [ ] 電源 A/B を別々の PDU / 別の分岐に接続し、各系統が UPS を経由している
- [ ] 分岐の総負荷を計算し、定格値を超えていない（余裕を含む）
- [ ] 接地が正常で、アースを壊すような変換部品を一切使っていない
- [ ] BMC の既定パスワードを変更し、独立した管理セグメントに接続し、**インターネットから到達できないことを確認した**
- [ ] スイッチに業務 / 管理 / ゲストの VLAN を設定した（マネージドスイッチを使う場合）
- [ ] インターネットには必要なポートだけを開放している（Java は `TCP 25565`、統合版は `UDP 19132`）。**RCON の `TCP 25575` とデータベースのポートは露出していない**
- [ ] ファイアウォール / ルーターの設定をエクスポートしてバックアップし、WAN 側の管理を閉じた
- [ ] UPS を監視に接続し、**自動シャットダウンを実際に 1 回演習した**
- [ ] すべてのケーブルの両端にラベルを貼り、トポロジの記録を更新した
- [ ] 予備部品（LAN ケーブル、電源ケーブル、モジュール、ディスク）を用意した

ポートの早見表（既定値。いずれも変更可能）：

| 用途 | プロトコル / ポート |
| --- | --- |
| Java 版のゲーム | TCP 25565 |
| 統合版（基岩版）のゲーム | UDP 19132 |
| Query（任意） | UDP 25565 |
| RCON（**露出禁止**） | TCP 25575 |
| IPMI / BMC | UDP 623 など |
| SNMP | UDP 161 / 162 |
| NUT | TCP 3493 |
