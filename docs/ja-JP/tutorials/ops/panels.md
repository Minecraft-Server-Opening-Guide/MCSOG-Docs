これまでの記事は「あなたがマシンにログインして自分でコマンドを打つ」話でした。この記事はもう 1 つのよくある運用の形を扱います。**サーバーを Web パネルに任せる**——ブラウザを開けばインスタンスを起動・停止でき、コンソールを見て、ファイルを送り、設定を変えられる。

パネルは確かに便利ですが、**このマシンで最も権限が強く、最も標的にされやすいサービス**でもあります。だから本記事の重点は「パネルに何ができるか」ではなく、**パネルを使うことで攻撃面が何を増やし、それをどう取り戻すか**です。

:::note 本記事の位置づけ
本記事は**使い方とセキュリティの境界**だけを扱い、各パネルの公式インストールドキュメントの代わりにはなりません。インストールのコマンド、既定のポート、ディレクトリ構造は**すべて公式ドキュメントに従ってください**。本記事は公式の出典と照合済みの既定値だけを示し、出典を明記します。
:::

## 1. パネルにできること、その代償

### 1.1 パネルが通常提供する能力

| 能力 | 具体的な現れ方 | 本当に楽になる場面 |
| --- | --- | --- |
| **Web 管理画面** | ブラウザで起動、停止、再起動、状態確認ができ、コマンドを大量に覚えなくてよい | スマートフォンから応急的に再起動する |
| **複数インスタンスの管理** | 1 台のマシンで複数のサーバーを同時に動かし、まとめて切り替える | サバイバル、クリエイティブ、テストのサーバーが同居する |
| **コンソールへのアクセス** | Web 上でリアルタイムのログを見て、直接コマンドを送る | 遠隔からサーバーダウンの原因を調べる |
| **ファイルマネージャー** | jar、設定、ワールドファイルのアップロード、ダウンロード、編集 | プレイヤーに MOD パックを配る、プラグインを足す |
| **スケジュールタスク** | 定時再起動、定時バックアップ、定時にコマンドを実行する | 毎日未明に再起動してメモリを解放する |
| **ユーザーとサブユーザーの権限** | 管理者や共同管理者に一部のインスタンスの操作権を割り当てる | 共同管理者に再起動は許すが SSH は渡さない |
| **資源の統計** | CPU、メモリ、ディスク、同時接続数のグラフ | 設定の問題かマシンの能力不足かを判断する |
| **Docker 連携** | コンテナでインスタンスを隔離し、資源を制限する | 複数インスタンスが互いに干渉しない |

:::note 機能の集合はパネルごとに違う
上の表は「パネルという種類のツール」のよくある能力で、**具体的なパネルが提供するか、入口がどこかは、そのパネルの公式ドキュメントと実際の画面に従ってください**。
:::

### 1.2 代償の一覧

| 代償 | 説明 |
| --- | --- |
| **保守すべきサービスが 1 つ増える** | パネル自体が Web アプリで、更新し、セキュリティ告知を見て、自分のデータをバックアップする必要がある |
| **攻撃面が広がる** | 待ち受けポートが 1 つ、アカウントの体系が 1 組、API が 1 本増える |
| **権限が高度に集中する** | パネル（とくにデーモン）は任意のプロセスを起動し、インスタンスのディレクトリを読み書きできる。手に入れることは、このマシンのすべてのサーバーを手に入れること |
| **リバースプロキシが複雑になる** | パネルはしばしば WebSocket を必要とし、パネルによってはブラウザがデーモンへ直結することを要求する（3.1 を参照） |
| **故障面が広がる** | パネルが落ちてもサーバーは落ちていないが、一時的に管理手段を失うことはある |

:::warn リスクを一文で理解する
**パネルは「もう 1 つのソフトウェア」ではなく、「このマシンのすべてのゲームサーバーの主電源スイッチ」です。** そのログイン画面をインターネットに開放することは、マシン全体の管理権をインターネットにぶら下げることと同じです。
:::

### 1.3 まず信頼境界を引く

パネルを使う前に、この線を頭の中で明確にしてください。

- **パネルが制御できるもの = その実行身分が制御できるもの。**
- パネルが root で動いているなら、パネルの任意のリモートコード実行の脆弱性はマシン全体の陥落に等しい。
- **デーモンの API 自体が「コマンドを実行する」インターフェース**です。それが存在意義だからです。だから一度露出すれば、shell をインターネットにぶら下げるのと同じです。

## 2. MCSManager（MCSM）

### 2.1 公式の位置づけ

MCSManager の公式リポジトリは自分自身をこう説明しています。**「迅速な導入、分散アーキテクチャ、マルチユーザー、現代的な Minecraft と Steam のゲームサーバー管理パネル」**（英語版は "Quick deployment, distributed, multi-user, modern management panel for Minecraft and Steam game servers"）。公式ドキュメントはさらに、**オープンソースで分散型、ワンクリック導入**の、Minecraft と Steam のゲームサーバーを扱うコントロールパネルであり、複数の物理サーバーを一元管理し、任意のホストにゲームサーバーを作成でき、安全で信頼できるマルチユーザーの権限システムを提供すると説明しています。

この一節の 3 つのキーワードが、その位置づけです。

| キーワード | 意味 |
| --- | --- |
| **ワンクリック導入** | インストールスクリプトを提供し、自動でシステムサービスに登録する |
| **分散** | 1 つのパネルが**複数台**のマシンを管理できる |
| **マルチユーザー** | アカウントと権限の体系を内蔵し、SSH ではなく権限を共同管理者に分けられる |

### 2.2 アーキテクチャ：パネル 1 つ + デーモン 1 つ以上

公式ドキュメントは MCSManager を 2 つに分けています。

| コンポーネント | 公式が説明する役割 |
| --- | --- |
| **Panel（Web パネル）** | ユーザー管理、デーモンへの接続、多くの操作の認可、API |
| **Daemon（デーモン）** | プロセスの管理（インスタンスが実際に動く場所）、Docker イメージの管理、ファイル管理、リアルタイムの端末通信 |

「分散」の意味はここにあります。**パネル自体はサーバーを動かしません**。命令を各マシンのデーモンへ送り、デーモンがそのマシンでインスタンスを起動・管理します。だから「パネル 1 台 + デーモンノード N 台」という構成が可能です。

:::warn コンポーネント名、インストールコマンド、既定のポート、ディレクトリ構造は公式ドキュメントに従ってください
MCSManager のサービス名、インストールスクリプトのアドレス、既定のポート、データディレクトリはバージョンで変わり得ます。**本記事に挙げた数値は執筆時点の公式ドキュメントの既定値にすぎません。公式ドキュメントと、あなたのマシンの実際の設定ファイルに従ってください。** 本番環境では、確認していないポートやパスをそのまま写さないこと。
:::

**本記事が公式ドキュメントと照合済みの既定値（対照用。それでも自分で確認することを勧めます）：**

| 項目 | 公式ドキュメントの既定値 | 備考 |
| --- | --- | --- |
| パネルの Web ポート | `23333` | Web 設定ファイルの `httpPort` で変更できる |
| デーモンのポート | `24444` | デーモン設定ファイルの `port` で変更できる |
| Linux のサービス名 | `mcsm-web`、`mcsm-daemon` | systemd サービス |
| スクリプトのインストール先 | `/opt/mcsmanager` | 公式の例のパス |
| Web 設定ファイル | `<Web インストール先>/data/SystemConfig/config.json` | `httpPort`、`httpIp`、`loginCheckIp` などを含む |
| デーモン設定ファイル | `<Daemon インストール先>/data/Config/global.json` | `port`、`key`、`defaultInstancePath` などを含む |
| デーモンの鍵 | 上記 `global.json` の `key` フィールド | デーモンの起動時にも表示される |

:::tip 非常に見落とされやすい公式の警告
公式の「分散デプロイ」ドキュメントには明記されています。デーモンだけを動かすノードでは、**必ず先に Web サービスを停止して無効化**しなければ、**誰でも初期設定ページにアクセスしてあなたのサーバーを乗っ取れてしまう**：

```bash
systemctl stop mcsm-web
systemctl disable mcsm-web
```

この警告は単独で覚える価値があります。**「止め忘れたあの Web サービス」が、そのまま完全な陥落になります。**
:::

### 2.3 インストールと初回ログイン

公式の Linux ワンクリックインストールスクリプト（公式ドキュメントが強調：システムサービスに登録するため、**root 権限で実行する必要がある**）：

```bash
sudo su -c "wget -qO- https://script.mcsmanager.com/setup.sh | bash"
```

:::note 中国語版と英語版のドキュメントでスクリプトのアドレスが違う
公式の英語ドキュメントは `setup.sh`、中国語ドキュメントは `setup_cn.sh` を使います。**参照している言語版の公式ドキュメントが示すアドレスに従ってください**。記憶でスクリプトの URL を組み立てないこと。公式ドキュメントには Docker インストールと環境隔離（Docker）の章もあり、具体的な手順は同じく公式ドキュメントに従います。
:::

インストール後、公式ドキュメントに従って 2 つのサービスを起動します（公式はどちらも欠かせないと強調しています）。

```bash
# まずデーモンを起動し、それから Web サービスを起動する
systemctl start mcsm-daemon.service
systemctl start mcsm-web.service

# 起動時の自動起動が必要なとき
systemctl enable mcsm-web.service
systemctl enable mcsm-daemon.service
```

手動インストールの場合、公式ドキュメントが示す起動方法は `./install.sh`、`./start-daemon.sh`、`./start-web.sh` で、手動起動には screen などのツールで引き継ぐ必要があり、さもないと SSH が切れた時点でプロセスがシステムに終了されると注意しています。Windows 版は公式の説明ではアーカイブをダウンロードして展開して実行します（アーカイブにランチャーが含まれていれば、ランチャーから起動してもかまいません）。

**初回ログインで必ずやること（順序を入れ替えない）：**

1. 管理者アカウントでパネルにログインする（初期のアカウント情報は公式ドキュメントとインストールの出力に従う）。
2. **直ちに既定のパスワードを変更**し、他のサイトとは違う長いパスワードを使う。
3. 3.5 の方法で HTTPS のリバースプロキシの背後に置く、または少なくとも送信元 IP を制限する。
4. 待ち受けアドレスとポートを確認し、デーモンをインターネットへ直接露出していないことを確かめる。

### 2.4 典型的な流れ：導入からインスタンスの起動まで

公式の「Java 版の構築」ドキュメントが示す流れはおおよそ次のとおりです（細部は公式ドキュメントに従う）。

| 手順 | 何をするか | 注意 |
| --- | --- | --- |
| 1 | パネル + デーモンを入れる（または公式ドキュメントに従って Docker を使う） | ノードのマシンにはデーモンのサービスだけを残す |
| 2 | ログインして既定のパスワードを変更する | 2.3 を参照 |
| 3 | パネルでデーモンのノードを確認または追加する | アドレスと鍵が必要。公式ドキュメントはアドレスが IP、ドメイン、`ws://` / `wss://` の接頭辞にも対応すると説明している |
| 4 | 「インスタンス」ページで「作成」を押す | マーケットから入れるか、「直接作成」して実行するノードを選べる |
| 5 | 起動コマンドを入力する | 公式の例：`java -Dfile.encoding=UTF-8 -jar "paper-<version>.jar"`。`-Xms` / `-Xmx` を足せる |
| 6 | サーバーのファイルをアップロードする | パネルの「ファイル管理」でコアの jar をアップロードする |
| 7 | インスタンスのコンソールで「起動」を押し、ログを観察する | 初回起動では通常「設定ファイル」で `eula.txt` を `eula=true` に変える必要がある |
| 8 | 共同管理者用のサブアカウントを作り、必要なインスタンスだけを認可する | 「すべてのインスタンス + ファイル管理」は与えないこと |

公式ドキュメントはさらに、インスタンスのデータは既定で `<Daemon インストール先>/data/InstanceData/<instance-id>/`、インスタンスの設定は `<Daemon インストール先>/data/InstanceConfig/<instance-id>.json`（起動コマンドなどの設定を含む）にあると説明しています。**この 2 か所は「失うと再構築が難しい」ものなので、必ずバックアップの対象に入れてください。**

:::warn 起動コマンドのメモリ引数に欲張らない
公式ドキュメントはとくに警告しています。**マシンのメモリをすべて JVM に割り当てないでください**。OS 自身も資源を必要とし、さもないとマシン全体が落ちることがあります。`-Xmx` はマシンの物理メモリより明らかに小さくしてください。
:::

### 2.5 パネルが本当に役立つ場面

- **複数インスタンス**：十数のサーバーを SSH で 1 つずつ再起動するのは現実的ではありません。
- **共同管理者に限られた権限を渡す**：再起動とログ閲覧は許すが、**SSH は渡さない**。これがパネルの最大のセキュリティ上の利益です。
- **定時再起動とバックアップ**：パネル系のツールは通常スケジュールタスクを提供します。**MCSManager が提供するか、入口がどこか、どう設定するかは、公式ドキュメントと実際の画面に従ってください**。
- **複数マシンの管理**：パネル 1 つ + デーモン複数で、入口を統一できる。
- **コマンドラインに不慣れな人に使わせる**：操作をパネルの機能の範囲に限定するほうが、shell をそのまま渡すより安全なことがよくあります。

## 3. パネルのセキュリティ（最重要）

### 3.1 第一原則：パネルとデーモンの API は絶対にインターネットへ直接露出しない

この 1 条は他のすべての項目を足したより重要です。

:::warn デーモンのポートを絶対にインターネットへ露出させない
デーモン API の役割は**プロセスの起動、ファイルの読み書き、コマンドの実行**です。本質的に**リモートコード実行のインターフェース**で、外側に認可の層が 1 枚かぶっているだけです。**一度露出すれば、攻撃者は鍵の漏洩、認可の迂回、未修正の脆弱性のどれか 1 つで、あなたのマシン上で任意のコマンドを実行できます。** パネルの Web 側も同じですが、少なくともログイン画面が 1 枚あります。
:::

正しいやり方：

1. **パネル**：`127.0.0.1` か内部アドレスにバインドし、HTTPS のリバースプロキシで外部へ出し、さらに送信元の制限（VPN、IP ホワイトリスト、ファイアウォール規則）を加えます。
2. **デーモン**：パネルのホスト（および直結が必要なクライアント）だけにアクセスを許します。
3. **「便利だから」という理由でデーモンのポートを `0.0.0.0` に開けないでください。**

:::note MCSManager の特殊性：ブラウザがデーモンへ直結する必要がある
MCSManager の公式「ネットワーク構成」ドキュメントの説明：パネルが大容量の通信（ファイルのアップロード、コンソールのログ）のボトルネックになるのを避けるため、**これらの通信はブラウザがデーモンと直接やり取りします**。そのため公式ドキュメントは、デーモンのアドレスは**LAN のアドレスではいけない**と指摘しています。さもないとデーモンの状態が「接続中」のまま止まります。

これには必ず知っておくべき結果が 2 つあります。

- パネルを HTTPS にするなら、**各デーモンにも個別に HTTPS のリバースプロキシを設定**し、パネル上でアドレスを `wss://...` に変える必要があります。公式ドキュメントは、ブラウザが非 HTTPS の WebSocket でデーモンへ接続することを**拒否する**と明言しています。
- 「デーモンは内部ネットワークだけ」という一般的な助言は、MCSManager では公式ドキュメントのネットワーク構成に従って具体化する必要があります。**公式ドキュメントが示す HTTPS リバースプロキシの方案で設定するか、VPN やトンネルで「ブラウザからデーモン」の経路を保護する**のであって、単純にポートをインターネットへ露出するのではありません。

**具体的な設定方法は、公式ドキュメントの「ネットワーク構成」と「NGINX 経由で HTTPS を使う」の 2 篇に従ってください。**
:::

### 3.2 root で動かさない

| 状況 | 事実（公式ドキュメントから） | 推奨 |
| --- | --- | --- |
| MCSManager のワンクリックスクリプト | 公式ドキュメントは**システムサービスに登録するため、スクリプトを root 権限で実行する必要がある**と説明している | インストールは root でよいが、**インスタンスはできるだけ専用ユーザーかコンテナで隔離する**。公式には「環境隔離（Docker）」のドキュメントもある |
| Pterodactyl Wings | 公式ドキュメントが示す systemd ユニットは `User=root` | これは公式の設計（Wings は Docker を制御する必要がある）。**コンテナでインスタンスを隔離すること自体がその緩和手段** |
| 汎用のサーバーパネル | 通常、システムサービスや Web サイトを管理するため高い権限が必要 | ゲームサーバーとこうしたパネルを同じ信頼境界に混ぜない（4.2 を参照） |

原則：**root を使わずに済むなら使わない。高い権限が必要なら、隔離（専用ユーザー、コンテナ、専用マシン）で爆発半径を囲い込む。**

### 3.3 資格情報とアカウント

- **直ちに既定のパスワードを変更する。** 既定のパスワードは自動スキャナの最初の標的です。
- **長く、唯一の**パスワードを使い、できればパスワードマネージャーに生成させる。**パネルのパスワードの漏洩 = すべてのインスタンスの陥落。**
- **パネルが二段階認証に対応しているなら必ず有効にする**。対応の有無と有効化の方法は**公式ドキュメントに従ってください**。
- **サブユーザーと権限を定期的に監査する**：誰がまだいるか？まだ必要か？権限を与えすぎていないか？「ファイル管理 + すべてのインスタンス」はほぼ shell を渡すのと同じです。
- **不要になったアカウントを削除する**。退職した共同管理者、テスト用のアカウント、使わなくなった API キーを含みます。
- パネルのパスワードをスクリーンショット、チャットの記録、Git リポジトリ、サーバーのディレクトリ内のテキストファイルに書かないこと。

### 3.4 パネル自体を最新に保つ

パネルは Web アプリで、**自分自身の脆弱性の歴史**があります。やるべきこと：

- 公式リポジトリの Release とセキュリティ告知を購読する。
- 公式ドキュメントの「更新」の章が示す手順でアップグレードする。
- アップグレードの前に**パネル自身のデータをバックアップする**（3.7 を参照）。

:::warn MCSManager のアップグレード時の落とし穴
公式の「更新とリセット」ドキュメントの注意：ワンクリックスクリプトの更新は **`mcsm-web` を自動で再度有効化**します。ノードのマシンで意図的に Web サービスを無効化している場合（2.2 を参照）、更新後に**必ずもう一度手動で停止して無効化**してください。さもないと初期設定ページが再び露出します。
:::

### 3.5 待ち受けアドレスとリバースプロキシ（nginx の例）

考え方は、**パネルはループバックアドレスだけにバインドし、nginx が外部へ HTTPS を提供する**。以下のポートは**プレースホルダー**なので、自分のパネルのポートに置き換えてください。

```nginx
# /etc/nginx/conf.d/panel.conf
# <panel-port> はプレースホルダーです。パネルが実際に待ち受けるローカルポートに置き換えてください。
# 証明書のパスは使う証明書ツールが決めます。以下の例のパスをそのまま写さないこと。

server {
    listen 80;
    server_name panel.example.com;
    # リダイレクトのみ。証明書の発行と更新の方法は、使う証明書ツールのドキュメントに従う
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name panel.example.com;

    # 使う証明書ツールが生成・更新する。実際のパスに置き換える（たとえば certbot の出力パス）
    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    # パネルのコンソールは WebSocket に依存するため、Upgrade ヘッダを転送する必要がある
    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # パネルは大きなサーバーや MOD パックのファイルをアップロードすることがある。0 は無制限
        client_max_body_size 0;

        # コンソールは長い接続。バッファリングされたり早く切られたりしないように
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

いくつかの補足：

- `proxy_http_version 1.1` と `Upgrade` / `Connection` の 3 つのヘッダが WebSocket の鍵で、**1 つでも欠けるとコンソールがつながらない**ことがあります。
- `ssl_certificate` と `ssl_certificate_key` の**パスは使う証明書ツール**（certbot など）**から来ます**。ツールや導入方法でパスが違うので、**そのまま写さないでください**。
- パネルの公式ドキュメントが独自のリバースプロキシの例を提供しているなら（MCSManager の公式には NGINX、IIS、Caddy の 3 篇があります）、**公式ドキュメントに従ってください**。デーモンの経路はしばしば別途の設定が必要だからです。
- 設定を変えたら、まず構文を検査してから再読み込みします（MCSManager の公式ドキュメントも、先に検証してから再読み込みするよう求めています）。

```bash
sudo nginx -t
sudo nginx -s reload
```

### 3.6 ファイアウォール

必要なものだけを開き、それ以外は既定で拒否します。

| ポート | 誰に開放するか | 説明 |
| --- | --- | --- |
| 80 / 443 | インターネット | パネルの入口（または選んだ HTTPS のポート）。80 はリダイレクトと証明書の検証だけに使う |
| パネルのローカルポート | **同じマシンだけ** | パネルが `127.0.0.1` にバインドされているなら外部への開放は不要 |
| デーモンのポート | **パネルのホストだけ**（または公式の構成に従って送信元を限定） | 絶対にインターネットへ開放しない。具体的なポートは公式ドキュメントに従う |
| ゲームのポート | インターネット（必要に応じて） | プレイヤーの入口 |
| SSH | 自分の管理 IP | 鍵ログインだけを許可することを勧める |

例（ポートとセグメントはすべて**プレースホルダー**です。実際の設定に置き換えてください。コマンドの文法は使用しているディストリビューションのドキュメントと照合してください）：

```bash
# ufw の例
sudo ufw default deny incoming
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp
# パネルのホストだけにデーモンのポートへのアクセスを許可する
sudo ufw allow from <panel-host-ip> to any port <daemon-port> proto tcp
sudo ufw enable
sudo ufw status verbose
```

ポートと規則の全体的な考え方は [ネットワークセキュリティの基礎](/tutorials/ops/network-security) と [ルーターとファイアウォール](/tutorials/ops/router-firewall) を参照してください。

### 3.7 パネル自身のデータをバックアップする

**パネルのデータディレクトリには、すべてのインスタンスの定義、ユーザー、設定が入っています。これを失うと、サーバーのファイルはあってもパネル上は「何もない」状態になります。**

| 何をバックアップするか | 説明 |
| --- | --- |
| パネルのデータベースと設定ディレクトリ | ユーザー、権限、インスタンスの定義、スケジュールタスク |
| デーモンの設定 | ポート、鍵、インスタンスの設定 |
| インスタンスのデータディレクトリ | ワールド、プラグイン、設定（通常は最も容量が大きい） |

:::warn パスは公式ドキュメントに従ってください
パネルごとにデータディレクトリの位置が違います。**必ず公式ドキュメントで確認してからバックアップスクリプトに書いてください**。推測でパスを書かないこと。

MCSManager を例にすると、公式ドキュメントが示す位置は、Web の設定が `<Web インストール先>/data/SystemConfig/config.json`、デーモンの設定が `<Daemon インストール先>/data/Config/global.json`、インスタンスのデータが `<Daemon インストール先>/data/InstanceData/<instance-id>/`、インスタンスの設定が `<Daemon インストール先>/data/InstanceConfig/<instance-id>.json` です。公式の「更新とリセット」ドキュメントはさらに直接、**アップグレードの前に `web/data` と `daemon/data` の 2 つのディレクトリを別の場所へバックアップする**ことを勧めています。
:::

バックアップの提案：

- パネルのデータのバックアップは**オフラインか遠隔地**に置き、しかも**パネル自身のプロセスがその場所に書き込めない**ようにします（さもないとパネルが侵入されたときにバックアップも一緒に消されます）。
- バックアップにはパネルのデータベースと鍵が入るので、**必ず暗号化するか権限を厳しく制限**してください。
- 定期的に**復元演習**を行います。バックアップするだけで復元しないのは、バックアップしないのと同じです。具体的な方法は [バックアップと復元](/tutorials/java/backup) と [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照。

### 3.8 パネルが侵入されたらどうなるか

最悪のケースを明確に書いておくと、何を防ぐべきかが分かります。

| 攻撃者が手に入れるもの | 結果 |
| --- | --- |
| パネルのアカウント | **すべてのインスタンス**を制御：セーブデータの削除、設定の変更、キック、自分に op を付与 |
| パネル + ファイル管理 | 悪意ある jar やプラグインをアップロードし、バックドアをサーバーへ持ち込む |
| デーモンの API | **マシン上で任意のコマンドを実行**（それが本来の機能）、通常はそのまま shell に等しい |
| パネルのデータベースや鍵 | 持続的なアクセス：パスワードを変えても、古い API キーとセッションが有効なことがある |
| バックアップディレクトリの書き込み権限 | **あなたのバックアップを削除**し、復元できなくする（ランサムや報復的なデータ削除のよくある手口） |

だから：**パネルが侵入された疑いがあれば、「マシン全体が陥落した」として扱ってください。**

1. 直ちにパネルとデーモンのインターネット側の入口を遮断する（パスワードではなくファイアウォールを変える）。
2. **すべての**資格情報を交換する：パネルのアカウント、デーモンの鍵、サーバー内の RCON パスワード、データベースのパスワード、クラウド事業者の API キー。
3. 新しい管理者アカウント、新しい API キー、異常なスケジュールタスクが現れていないか確認する。
4. サーバーのディレクトリに不審な jar、プラグイン、定時スクリプトが置かれていないか確認する。
5. **クリーンと分かっている**バックアップから復元する。侵入されたマシン上で「掃除して使い続ける」のではない。
6. 露出の原因（ポートの露出、弱いパスワード、パッチ未適用のいずれか）を振り返る。[ネットワークセキュリティの基礎](/tutorials/ops/network-security) と [システムのセキュリティ強化](/tutorials/ops/system-security) を参照。

完全な対応の流れは [インシデント対応とフォレンジック](/tutorials/ops/incident-forensics) を参照してください。

## 4. その他のパネルと選び方

### 4.1 Pterodactyl

Pterodactyl の公式の説明：**無料でオープンソースのゲームサーバー管理パネルで、PHP、React、Go で構築され、安全のために設計され、すべてのゲームサーバーが隔離された Docker コンテナで動き**、エンドユーザーに直感的な Web 画面を提供します。MIT ライセンスのオープンソースプロジェクトで、公式は bcrypt のパスワードハッシュ、AES-256-CBC の暗号化、すぐ使える HTTPS 対応を強調しています。

そのアーキテクチャは MCSManager と同じく「パネル + ノードのデーモン」の類です。公式の用語集の定義は次のとおりです。

| 用語 | 公式の意味 |
| --- | --- |
| **Panel** | Pterodactyl のパネル自体。ノードとサーバーを追加するために使う |
| **Node** | Wings のインスタンスを動かす物理マシン |
| **Wings** | Go で書かれた新しい世代のサービス。Docker と Panel に接続し、パネルから安全にサーバーを制御する |
| **Server** | パネルが作成し、ノード上で動くインスタンス。1 つのノードに複数置ける |
| **Docker / Image / Container** | 隔離された実行環境。各サーバーは独立したコンテナで動き、CPU とメモリを制限し、互いに干渉しない |
| **Nest / Egg** | Nest は通常 1 つのゲームかサービスに対応し、Egg はある種類のゲームの具体的な設定を保存する |
| **Yolks** | Egg の仕組みと対になるコア Docker イメージの集合 |

要点（すべて公式ドキュメントから）：

- Wings は **Linux のみ対応**で、公式は Windows 環境では動かせないと明言しています。Docker が動くシステムが必要で、OpenVZ や LXC のような仮想化は通常だめです（公式は `systemd-detect-virt` で自己確認することを勧めています）。
- 公式のインストール手順は、まずパネルでノードを作成し、パネルが生成した設定をノード上の `/etc/pterodactyl/config.yml` として貼り付け（または「トークンを生成」が示すコマンドを使い）、それから Wings を systemd サービスとして動かします。
- 公式が示す systemd ユニットは `User=root` で、これは公式の設計です。
- 公式ドキュメントの説明：**パネルで SSL を有効にするなら、Wings もその FQDN の証明書を設定する必要がある。**
- ノードには allocation（IP とポートの組み合わせ）を設定する必要があり、各サーバーに少なくとも 1 つ必要です。公式は **`127.0.0.1` を使わない**よう注意しています。

:::note 個別に照合していない内容
Pterodactyl の**具体的なインストールコマンド、既定のポート、ディレクトリ構造、バージョンの要件はバージョンで変わります**。本記事では列挙せず、**すべて公式ドキュメントに従ってください**。パネルのインストールは公式 Panel の Getting Started、ノードのデーモンは公式 Wings の Installing Wings ドキュメントを参照してください。
:::

### 4.2 汎用のサーバーパネル（1Panel、宝塔など）

この類のツールは**ゲームサーバーのパネルではありません**。管理するのは**OS のレベル**のもの——Web サイト、データベース、コンテナ、ファイル、スケジュールタスク、ファイアウォールなどです。

1Panel を例にすると、公式の位置づけは**「現代的でオープンソースの Linux サーバー運用管理パネル」**（軽量な AI 管理プラットフォームでもあります）で、直感的で使いやすい Web 管理画面を提供し、ホストの監視、ファイル、データベース、コンテナ、スケジュールタスクを管理でき、WordPress、Halo などのサイト構築プログラムと深く連携します。公式は WAF、ログ監査、バックアップなどのセキュリティ機能も提供しています。

**ゲームパネルとの違い：**

| 観点 | ゲームサーバーのパネル | 汎用のサーバーパネル |
| --- | --- | --- |
| 管理対象 | ゲームのインスタンス（プロセスかコンテナ） | システムサービス、Web サイト、データベース、コンテナ |
| ゲームを理解するか | コンソールを見て、プラグインを送り、起動コマンドを設定できる | 通常は理解せず、普通のプロセスかコンテナとして扱うしかない |
| 権限の範囲 | インスタンスとデーモン | **しばしばシステム全体** |
| 典型的な用途 | 複数インスタンス、共同管理者への分権 | サイト構築、サービスの運用、Docker の管理 |

**汎用パネルでゲームサーバーを管理するリスク：**

- **権限がより大きい**：この類のパネルは通常、システムサービスとファイルを管理する必要があり、侵入されたときの影響範囲はゲームパネルより大きい。
- **ゲームを理解しない**：「まず stop を送り、ワールドの保存が終わるのを待つ」といった細部を代わりに処理してくれず、サーバーを普通のプロセスとして強制終了しがちです。
- **層が 1 つ増える**：「ゲームサーバーのデプロイ方法」と「汎用パネル」の 2 つを同時に保守することになり、攻撃面が重なります。
- **歴史的に重大な脆弱性が出ている**：汎用パネルはインターネットスキャンの重点的な標的です。**どのパネルも「インターネットに面した基盤」として扱うべきです**。速やかな更新、送信元の制限、強力な認証の有効化。**具体的な脆弱性の情報は各ベンダーの公式セキュリティ告知に従い、第三者の噂に頼らないでください。**

:::tip より堅い組み合わせ
汎用パネルが本当に必要な場合（たとえば同じマシンに Web サイトもある）、**ゲームサーバーは独立したマシン、独立したユーザー、独立したコンテナに置き**、汎用パネルの権限とゲームのインスタンスを同じ信頼境界に混ぜないでください。システムレベルの強化は [システムのセキュリティ強化](/tutorials/ops/system-security) を参照。
:::

### 4.3 比較表

| パネル | 位置づけ | 独立したデーモンが必要か | 誰に向くか | 主なリスク |
| --- | --- | --- | --- | --- |
| **MCSManager** | オープンソースで分散型、マルチユーザーの Minecraft と Steam のゲームサーバー管理パネル | **必要**（Panel + Daemon。複数ノード可） | 複数インスタンス、複数マシン、共同管理者への分権が必要なサーバー主 | デーモンがリモートコード実行の面。ブラウザがデーモンへ直結するためリバースプロキシが複雑。更新で Web サービスが再び有効化されることがある |
| **Pterodactyl** | 無料オープンソースのゲームサーバーパネル。インスタンスは隔離された Docker コンテナで動く | **必要**（Panel + 各ノードの Wings） | コンテナで隔離したい、マルチユーザーと複数ノードの場面 | Docker と Linux に依存。Wings は公式が root で動かす。導入と保守の敷居が高い。導入方法とポートは公式ドキュメントに従う |
| **1Panel** | 現代的でオープンソースの Linux サーバー運用管理パネル（汎用） | 不要（自身がシステムレベルの管理パネル） | サイト構築、データベースとコンテナの管理、汎用の運用 | **システムレベルの権限**で攻撃面が大きい。ゲームサーバーを専門に理解しない。脆弱性の影響範囲が大きい |
| **宝塔などの汎用パネル** | 汎用のサーバー運用パネル | 不要 | サイト構築と汎用の運用 | 1Panel の類と同じ。**インストールコマンド、既定のポート、セキュリティ機能は公式ドキュメントに従う** |
| **パネルを使わない（SSH + systemd）** | 直接管理 | 不要 | 単一のマシン、少数のインスタンス | 追加の攻撃面がない。ただし unit、ログ、更新はすべて自分で保守する |

## 5. 実践的な提案

### 5.1 導入の順序

1. **まずシステムを強化する**（専用ユーザー、SSH 鍵、ファイアウォール、自動更新）。[システムのセキュリティ強化](/tutorials/ops/system-security) を参照。
2. **それからパネルを入れる**。入れた直後に既定のパスワードを変更する。
3. **パネルを HTTPS のリバースプロキシの背後に置き**、送信元を制限する（VPN、IP ホワイトリスト、ファイアウォール規則）。
4. **最後にデーモンのノードを接続する**。ノードにはデーモンのサービスだけを残し、余分な Web サービスを止める。
5. インスタンスを作成し、ファイルをアップロードし、コンソールを通す。
6. スケジュールタスクとバックアップを設定する。
7. 共同管理者用のサブアカウントを作り、最小限の権限を認可する。

**「インターネットに裸で晒した」状態でまず動かす、というのはやめてください**。パネルがインターネットに露出している 1 分 1 分がスキャンされています。

### 5.2 強化のチェックリスト

- [ ] パネルとデーモンのどちらも**インターネットから直接到達できない**
- [ ] パネルに HTTPS でアクセスでき、WebSocket も正常
- [ ] 既定のパスワードを変更済み。二段階認証に対応しているものは有効化済み
- [ ] パネルとデーモンの設定ファイルの権限を絞った（鍵やパスワードを含むファイルを全員が読めるようにしない）
- [ ] インスタンスは専用ユーザーかコンテナで動き、root ではない
- [ ] パネルのデータをバックアップし、その場所にパネルが書き込めない
- [ ] 公式のセキュリティ告知を購読し、自分の更新の流れを明確にした
- [ ] サブユーザーの権限を監査した
- [ ] ノードのマシンに初期設定ページが残っていない
- [ ] 侵入された後の応急手順を把握している

### 5.3 何を監視するか

| 監視項目 | なぜ |
| --- | --- |
| **パネルのログイン失敗回数** | ブルートフォースの最初のシグナル。パネルによっては「ログイン失敗で IP を BAN」のような設定項目がある（MCSManager の Web 設定には `loginCheckIp` があり、**具体的な意味と挙動は公式ドキュメントに従う**） |
| **異常な新規インスタンス** | 攻撃者はよく新しいインスタンスを作って別のものを動かす |
| **異常なスケジュールタスク** | 定時タスクは永続化のよくある手口 |
| **新しく増えた管理者や API キー** | 永続化のバックドア |
| **資源の急増** | CPU、メモリ、帯域がマイニングやパケット送信に使われる |
| **パネルとデーモンのバージョン** | 速やかにパッチを当てる |
| **異常な外向きの接続** | ゲームサーバーは通常、大量のアドレスへ能動的に接続しない |

ログの位置と監査のコマンドは [システムのセキュリティ強化](/tutorials/ops/system-security)、侵入後の対応は [インシデント対応とフォレンジック](/tutorials/ops/incident-forensics) を参照してください。

### 5.4 パネルを使うべきでない場面

パネルは既定の選択肢ではありません。次の場合は**通常パネルは不要**です。

- **マシン 1 台、サーバー 1 つだけ**：SSH + systemd のほうが単純で、攻撃面も 1 つ少ない。[アクセス可能な環境へのデプロイ](/tutorials/java/deploy) を参照。
- **自分だけが使い、コマンドラインに慣れている**：パネルの利益（可視化、分権）は使わず、コスト（サービスが 1 つ、アカウントが 1 組増える）だけを払うことになります。
- **マシンの性能が厳しい**：パネル自体もメモリを食うので、メモリの小さいマシンでは割に合いません。
- **保守するつもりがない**：**更新しないパネルは、パネルがないより危険です。**

逆に、次のどれか 1 つでも当てはまれば、パネルは通常価値があります。複数インスタンス、複数マシン、共同管理者に限られた権限を渡す必要、スケジュールタスクが必要、コマンドラインに不慣れな人に使わせる必要。
