技術的なチュートリアルは「プラグインの入れ方、前提は何か」までで十分ですが、サーバーが「ゲーム」らしくなるかを本当に決めるのは**経済と遊び方のプラグイン**です。お金はどこから来るのか、ショップの値段をどう決めるのか、クエストは何を報酬にするのか、称号をどう見せるのか、箱から何が出るのか。

この記事では**カテゴリ**ごとに、それぞれのプラグインが何をしているのか、代償は何か、リスクはどこにあるのかを整理します。特定のプラグイン名を挙げる段落では、そのプラグインの**公式ページ**（公式リポジトリ、公式ドキュメントサイト）で確認できる能力だけを書きます。確認できない部分はカテゴリの説明にとどめ、具体的な名前をでっち上げません。前提依存の基礎知識は [プラグイン入門](/tutorials/java/plugins) と [よく使う前提プラグイン](/tutorials/java/plugin-deps) を参照してください。
:::warn 遊び方プラグインは「コード」であり「コンテンツパック」ではない
遊び方プラグインを 1 つ入れるたびに、あなたは次のものを 1 つずつ増やします。更新を追い続ける必要があるコード、他のプラグインと衝突し得るコード、アイテム増殖に悪用され得るコード、そしてメインスレッドの性能を継続的に食うコード。**遊び方プラグインは多ければよいものではありません**。まず何を解決したいのかをはっきりさせてからプラグインを探してください。「他のサーバーにもあるから」で入れてはいけません。
:::

## 1. まず正しいメンタルモデルを持つ

プラグインを選ぶ前に、4 つのことをはっきりさせてください。

| 問い | なぜ重要か |
| --- | --- |
| このプラグインは何を解決するのか | 言えないなら入れない。入れたのに誰も使わなければ、性能とリスクのコストを払い損になる |
| 何に依存しているか | 前提が欠けると読み込みに失敗するか、機能が黙って無効になる。[よく使う前提プラグイン](/tutorials/java/plugin-deps) を参照 |
| データをどこに保存するか | ファイル型の保存は、サーバー移行、分割、バックアップで挙動がまったく変わる |
| プレイヤーに悪用され得るか | 「アイテムや通貨を生み出せる」プラグインはすべて、増殖の入口になり得る |

遊び方プラグインのリスクは大きく 4 種類に分けられ、以降の各節で繰り返し登場します。

- **経済リスク**：通貨や高価値のアイテムを無から生み出し、インフレを招く。
- **セキュリティリスク**：複製の脆弱性、権限の迂回、コマンドインジェクション。
- **性能リスク**：tick ごとの追加計算、エンティティ数、データベースへの問い合わせ頻度。
- **運営リスク**：プレイヤーが不公平だと感じる、コンテンツを遊び尽くされる、作者が更新を止めて古いバージョンに縛られる。

## 2. 分類の全体表

まず全体を見てから、節ごとに展開します。

| カテゴリ | 何を増やすか | 難易度 | 性能の負荷 | 主なリスク |
| --- | --- | --- | --- | --- |
| 経済システム（API + 実装） | 通貨、残高、送金の基礎 | 中 | 低（データベースの書き込みと問い合わせ） | 通貨の供給が制御できずインフレ。データ破損 |
| ショップ | 売買の経路、価格を付ける場所 | 中 | 低〜中（ショップ数と問い合わせ頻度による） | 価格の誤り、無限買取、増殖 |
| クエストと実績 | 目標感、日々のリテンション | 中〜高（コンテンツ設計のコストが高い） | 低〜中 | 報酬が経済を突き抜ける。コンテンツを遊び尽くされる |
| 称号と肩書き | 身分の表示、社会的な記号 | 低 | 極めて低い | 課金の強さと結びつくと信頼を損なう |
| ガチャとクレート | ランダム報酬、短期的な刺激 | 中 | 低〜中（演出とアナウンス） | ギャンブル依存、有料のランダム報酬のコンプライアンスと倫理 |
| 職業とスキル | 長期的な成長線 | 中〜高 | 中（高頻度のイベント購読） | 産出の暴走。サバイバルの遊び方と衝突 |
| ミニゲームとパルクール | 独立した遊び方、多人数の交流 | 高 | 中〜高（独立したワールドとインスタンス） | 人数不足で空回り。保守コストが高い |
| 領地と保護 | 財産の安心感 | 中 | 中（ブロックイベントと問い合わせ） | ルールが複雑で新規が離脱。経済と連動すると崩れやすい |
| 科技系の大型コンテンツ | まったく別のゲーム体験 | とても高い | 高（大量のカスタムアイテムと機械のロジック） | 性能、バージョンアップの困難、習得の敷居が高い |
| アンチチートと記録 | 秩序と追跡可能性 | 中 | 中（記録系プラグインは継続的にディスクへ書く） | 記録が不完全。入れるのが遅いと履歴を追えない |
:::tip 表の使い方
「難易度」は**あなたが設定して保守するコスト**であり、プラグイン自体の複雑さではありません。設定項目が千行を超えるプラグインは、ドキュメントがどれだけ揃っていても、あなたの時間を大量に食います。**まず自分の時間の予算を計算し、それから性能の予算を計算してください。**
:::

## 3. 経済システム：必ず 2 層になる

### 3.1 API と実装は分けて理解する

初心者が最もはまりやすい罠です。**Vault を入れても経済システムにはなりません**。

Vault の公式の位置づけは **Bukkit の抽象ライブラリ**です（公式リポジトリの説明：*Vault of common APIs for Bukkit Plugins*、README のタイトル：*Vault - Abstraction Library for Bukkit*）。それ自体は通貨を 1 単位も生み出さず、統一されたインターフェースの組を定義して、「経済機能を必要とするプラグイン」と「実際に経済機能を提供するプラグイン」が会話できるようにするだけです。開発者向け API は別の VaultAPI リポジトリに分離されています（公式 README の説明）。

だから経済システムは常に**2 層**です。

| 層 | 役割 | 例（公式ページに従う） |
| --- | --- | --- |
| 抽象層 | 「残高を調べる、引く、足す」インターフェースを定義する | Vault |
| 実装層 | 実際に残高データを持ち、加減を実行する | EssentialsX の経済モジュール、CMI の経済システム、XConomy など |

| Vault のような抽象層が提供するもの | 誰が実装するか | 誰が呼ぶか |
| --- | --- | --- |
| 経済（Economy） | 具体的な経済プラグイン | ショップ、クエスト、ガチャ、領地の維持費 |
| 権限（Permission） | 権限プラグイン（LuckPerms など） | 権限の判定が必要なプラグイン |
| チャット（Chat） | チャット系プラグイン | チャットの送信や整形が必要なプラグイン |

確認できる具体的な事実がいくつかあります。

- **EssentialsX** の公式モジュール説明には、コア jar が大部分のコマンド、看板、kit **および経済システム**を含むと書かれています（*signs, kits and the economy*）。つまり EssentialsX 本体を入れれば、すでに経済の実装があります。
- **CMI** の公式ページには、**Economy system（残高ランキングを含む）**と **Cheque system（お金をアイテムにする）**を提供すると書かれています。同時に、CMI の経済を Vault の体系に接続するには、公式が提供する Vault のバージョンか経済注入モジュールを併用し、設定ファイルの経済スイッチを有効にする必要があると説明しています。
- **XConomy** の公式リポジトリの説明は「複数サーバー間のデータ同期に対応した経済プラグイン」で、複数サーバーで 1 つの残高を共有する場面に向きます。使う前に、現在のメンテナンス状況があなたのバージョン要件を満たすか自分で確認してください。
- **Jobs Reborn** の公式ページは依存項目に **Vault** を挙げています。これが「遊び方プラグインが抽象層を通じて経済を呼ぶ」典型例です。
:::note まず「誰がお金を管理しているのか」を確認する
経済の問題を調べるとき、最初に問うのは「ショップのプラグインが壊れていないか」ではなく、「**いま実際に経済の実装を提供しているのはどのプラグインか**」です。「残高が 0 になった」「引き落としが効かない」の多くは、経済の実装を 2 つ同時に入れているか、抽象層がデータを持たない実装を指していることが原因です。
:::

### 3.2 物理的な通貨アイテム

**通貨をアイテムにする**ことをサポートする実装もあります（たとえば CMI の公式ドキュメントにある Cheque / 小切手システム：金額を含むアイテムを作り、プレイヤー間で流通させられます）。この設計には長所と短所があります。

- 長所：取引に実体感があり、RP やオフラインの受け渡しに向く。オフラインでも渡せる。
- リスク：アイテムが複製されたり、不正に取得されたり、サーバー間の移動で失われたりすると、通貨が制御不能になる。しかも「アイテムの形のお金」はプラグイン層の取引記録を迂回する。

物理的な通貨を使うなら、**同時に 3 つのことを解決する必要があります**。アイテムが偽造できないこと（アイテムデータの検証に依存）、取引に記録があること、紛失に申立ての手続きがあること。

### 3.3 通貨は管理者が作るのか、プレイヤーが稼ぐのか

これは経済設計の最初の決定であり、最も重要な 1 票です。

| 方式 | お金の出どころ | 結果 |
| --- | --- | --- |
| 管理者が作る（配布、システムへの売却） | コマンドとショップの買い取り | 単純で直接的だが、極めてインフレしやすい。強力な回収手段が必須 |
| プレイヤーが稼ぐ（労働、取引、クエスト） | 遊び方からの産出 | より健全だが設計コストが高い。産出速度を制御できる必要がある |
| 混合 | システムが基礎収入を配り、プレイヤー間で流通する | 現実に最も多い。要点はシステムの配布量を「通貨の発行量」として管理すること |

## 4. ショップ

ショップは経済の**流通経路**であり、最も事故が起きやすい場所でもあります。なぜなら「何にいくらの値が付くか」を直接決めるからです。

### 4.1 操作の形：看板 / チェストショップか GUI ショップか

| 形 | 特徴 | 向く場面 |
| --- | --- | --- |
| 看板 / チェストショップ | プレイヤーがチェストをワールドに置き、看板で値札を付ける。コマンドなしで売買できる | プレイヤー間の自由市場、商業エリアの集積 |
| GUI ショップ | メニュー画面でカテゴリをたどって購入する。管理者が商品表を設定する | 管理者ショップ、初心者ガイド、品目の多い買い取り |

確認できる公式の説明：

- **ChestShop**：公式リポジトリの説明は *The original chest & sign shop plugin for Minecraft Servers running Bukkit/Spigot/Paper. Est. 2011*（最も初期のチェストと看板のショッププラグイン）。
- **QuickShop-Hikari**：公式リポジトリの説明に、プレイヤーがコマンドを一切使わずにチェストからアイテムを売買できるショッププラグインであると書かれ、プレイヤーが実際には提供されるコマンドを使う必要がないことを強調しています。
- **Shopkeepers**：公式 README に、サーバー主が「カスタムの村人ショップ」を設置でき、**2 種類のショップ**を同時にサポートすると書かれています。**管理者ショップ（在庫無限）**と**プレイヤーショップ（コンテナから取り出す）**です。
- **GUI ショップ系**：メニューを操作の形にするショッププラグイン（たとえば EconomyShopGUI。その公式リポジトリ Gypopo/EconomyShopGUI-API の説明は "The API of EconomyShopGUI" で、他のプラグインが連携するためのもの）。

### 4.2 プレイヤーショップと管理者ショップ

| 種類 | 在庫 | 価格を決める人 | 経済的な意味 |
| --- | --- | --- | --- |
| 管理者ショップ | 無限 | サーバー主 | システムレベルの通貨の蛇口と回収所。インフレを直接決める |
| プレイヤーショップ | プレイヤー自身の商品 | プレイヤー | プレイヤー間の流通。サーバー主はルールと場所を用意するだけ |

### 4.3 「サーバーに売る」と「プレイヤー間で取引する」は別物

これはプレイヤーに最も丁寧に説明すべき点です。

- **サーバーに売る**：サーバーが無限に買い取るので、**通貨の発行**に等しい。買い取り価格が発行価格、買い取り量が発行量です。
- **プレイヤー間の取引**：一方が払い、一方が品を渡す。通貨の総量は変わらず、移動するだけです。

「経済が壊れた」サーバーの多くは、管理者ショップの**無限買い取り価格**に問題があります。あるアイテムが安定して無限にシステムへ売れるなら、プレイヤーはそれを札束製造機に変えます。

### 4.4 ショップ経済が崩壊する典型経路

| 崩壊の仕方 | 仕組み | 予防 |
| --- | --- | --- |
| 無限買い取りの価格が高すぎる | プレイヤーがそのアイテムを大量に生産してシステムへ売る | 買い取り表を定期的に見直す。1 人あたりの買い取り量に上限を設ける |
| 複製の脆弱性 | アイテム数が無から倍になり、システムへ売って金に換える | 第 9 節を参照。産出型の遊び方にはすべて記録を持たせる |
| 売却価格の書き間違い（0 が 1 つ足りない） | 1 回の取引で経済を突き抜ける | 価格を変えたらまずテストサーバーで検証する。設定変更の記録を残す |
| 高価なアイテムが誰も売らない | 通貨が入るだけで出ていかず、インフレ | 回収手段を設計する。第 10 節を参照 |
| ショップがプレイヤー間送金に使われる | 資金洗浄や脱税の経路になる | ルールを明確にする。必要なら取引に課税する |
:::warn ショップの価格表は経済の設定ファイルであり、適当に埋める表ではない
買い取り価格を 1 つ変える前に、一度計算してください。**1 人のプレイヤーが 1 時間でそのアイテムをどれだけ産出できるか？買い取り価格を掛けたものが、その人の 1 時間あたりの札束印刷速度です。** この数字が「普通に 1 時間遊んで稼げる金額」と桁で違うなら、経済は数日のうちに必ず壊れます。
:::

## 5. クエストと実績

クエストシステムが解決するのは**目標感**の問題です。プレイヤーがログインしたとき、「今日は何をするか」が明確になります。

確認できる公式の説明：

- **Quests**（PikaMug）：公式リポジトリの説明は「使いやすくオープンソースで、Minecraft サーバー上でクエストを作成・実行するためのプラグイン」。
- **BetonQuest**：公式リポジトリの説明は「高度で強力なクエストスクリプトプラグイン」。RPG 風の会話を内蔵し、40 以上の他のプラグインと連携します。「台本があり、会話があり、分岐がある」重量級のコンテンツサーバーに向きます。

### 5.1 デイリー / ウィークリークエスト

- **デイリークエスト**は安定したログインの理由になりますが、報酬は小さくする必要があります。デイリー報酬の設計目標は「やる価値がある」であり、「やらなければならない」ではありません。
- **ウィークリークエスト**は大きめの報酬を載せるのに向きます。産出速度に天然の上限（週 1 回）があるからです。
- **クエストをサインイン配布にしてはいけません**。純粋な「クリックすればお金がもらえる」は、経済を時間に応じた紙幣印刷に変えます。

### 5.2 報酬設計は経済を突き抜けてはいけない

クエスト報酬には安全な 3 つの形があります。

| 形 | 説明 | リスク |
| --- | --- | --- |
| 外見と称号 | 数値に影響しない | 低（称号で強さを売らない前提で） |
| 消耗品と利便性 | ポーション、テレポート券、修理券 | 中（1 時間あたりの産出を計算する必要がある） |
| 通貨と高価値アイテム | 直接お金を配る、装備を配る | 高（1 時間あたりの産出上限から逆算して価格を決める必要がある） |

判断基準はこうです。**クエスト報酬は、すでにある通貨の出どころと同じ 1 枚の表で比較できなければならない。** クエストの 1 時間あたりの収益が他の遊び方よりはるかに高いなら、プレイヤーはクエストだけをやり、他のコンテンツはすべて廃れます。

## 6. 称号と肩書き

称号は**表示層**に属し、その価値は数値ではなく「他人に見えること」から来ます。

| 種類 | 実装方法 | 説明 |
| --- | --- | --- |
| 権限型の接頭辞 / 接尾辞 | 権限プラグインが meta を保存し、チャットや TAB 系のプラグインが描画する | 最も一般的で、権限グループと自然に結びつく |
| 装飾的な称号 | プレイヤーが自分で選んで表示するテキスト | 通常は専用の称号プラグインと解除条件が必要 |
| 遊び方内の肩書き | 遊び方プラグイン自体が提供する（たとえば職業プラグインが表示する職名） | 例：Jobs Reborn の公式ドキュメントにある Chat Titles 機能 |

確認できる事実：**LuckPerms** の公式リポジトリの説明は「Minecraft サーバー向けの権限プラグイン」で、権限と接頭辞のメタデータを保存する役割を担います。一方で **EssentialsX の公式モジュールドキュメント**には、プレイヤーに接頭辞と接尾辞を持たせるには **Vault と LuckPerms** が必要だと明記されています。つまり、**「誰が接頭辞を保存するか」と「誰が接頭辞を表示するか」は通常同じプラグインではありません**。表示の段階はチャット系か TAB 系のプラグインが担います。詳しくは [チャット、メニューと MOTD](/tutorials/java/cosmetic) を参照してください。

設計上の 2 本のレッドライン：

- 称号は売ってよい（支援者の表示として）が、**強さを伴ってはいけません**。
- 称号システムは取り消せなければなりません。プレイヤーが規約に違反したら、すぐにその称号を外せる必要があります。

## 7. ガチャとクレート

クレート（Crates）は「ランダム報酬」の遊び方で、短期的な刺激は極めて強く、長期的な議論も極めて大きいものです。

### 7.1 報酬表の仕組み

主流のクレートプラグインの中核は、**重み付きの報酬表**です。

- 各報酬に**重み（weight）**があり、重みが大きいほど当たりやすい。
- 報酬はよく**レアリティ（rarity）**でグループ化され、レアリティが抽選確率に影響する。
- 鍵には**実体の鍵**（取引・譲渡できる）と**仮想の鍵**（プレイヤーに紐づく）がある。
- 通常は**開封コスト、クールダウン、権限要件、回数上限**などの制限もある。

確認できる公式の説明：

- **CrazyCrates**：公式の説明は「サーバーに無制限の数のクレートを追加し、11 種類のクレートタイプを提供する」。公式ドキュメントサイトは docs.crazycrew.us で、導入手順は Paper 以上のサーバーを要求し、報酬のテスト用に `/crazycrates debug` を提供しています。
- **ExcellentCrates**：公式 Wiki にレアリティの重み（rarity weights）、報酬の重み（weights）、開封コスト（open cost）、クールダウン、マイルストーン、報酬の回数上限（roll limits）が列挙され、**仮想の鍵**（公式の説明では、鍵が共有・取引・販売されるのを**防ぐ**ことが目的）と**報酬ログ**（抽選のたびに専用のログファイルへ記録する）を明確に提供しています。

この 2 点は運営に直接価値があります。**仮想の鍵**は「鍵が売買されない」ことを制御でき、**報酬ログ**は問題が起きたときに裏付けを取れます。

### 7.2 ギャンブルと依存：正面から向き合うべき問題

ランダム報酬は心理的な仕組みとしてギャンブルと非常に似ています。変動比率の強化、あと少しで当たる感覚、サンクコスト。サーバー主として、自分から上限を設ける必要があります。

- **「もう 1 回引けば当たる」という話法を使わない**。これは意図的な誘導です。
- **確率を公開する**。報酬表と重みはプレイヤーに見えるようにすべきで、少なくとも規約で説明します。
- **上限を設ける**。1 日 / 1 週間の開封回数の上限、1 人あたりの報酬上限は、暴走のリスクを明確に下げます。
- **未成年を守る**。プレイヤー層が若いなら、とくに重要です。

### 7.3 有料のランダム報酬：コンプライアンスと倫理の警告
:::warn 有料のランダム報酬をやってはいけない
**ランダム報酬を実際の通貨での支払いと結びつけること（有料の開封 / ガチャ）は、一部の国と地域で専用の法規やプラットフォームの規則に縛られ、ギャンブル的なコンテンツと認定されたり、決済チャネルやプラットフォームの方針に違反したりする可能性があります。** こうした規則は変わり、地域差も大きいため、あなたは他人のやり方をそのまま真似るのではなく、自分に適用される法律とプラットフォームの要件を自分で確認する必要があります。

運営の観点からも、より現実的な理由があります。**有料のランダム報酬は「pay-to-win 論争」の増幅器**です。「金を払えば強くなれるのか」という問いを曖昧なものから具体的なものに変えてしまい、プレイヤーの許容度は極めて低いものです。**推奨するのは、鍵は遊び方（イベント、クエスト、貢献）からのみ得られ、実際の通貨では販売しないことです。**
:::

## 8. 遊び方の分類

### 8.1 職業とスキル

- **Jobs Reborn**：公式ページの説明は「完全に設定可能なプラグインで、破壊、設置、討伐、釣り、クラフトなどの行動で報酬を得られる。職業ベース（class-based professions）で、仕事をこなすと経験値を得る」。公式は同時に Vault 依存、MySQL の任意利用、独自のポイント経済、デイリークエスト、チャットの肩書きなどの特徴を挙げています。
- **mcMMO**：公式サイトの位置づけは「Spigot/Paper 向けの RPG プラグイン」で、スキル、レベルアップ、スーパースキル、ランキング、パーティ（party）システムを提供し、設定項目も多数あります。

この類のリスクは**産出**に集中します。スキルのレベルが収益を押し上げ、職業報酬が直接お金を配る。両者が重なると「遊ぶほど豊かになる」正のフィードバックが簡単に生まれます。公開前に必ず**カンストしたプレイヤーの 1 時間あたりの収益**を見積もってください。

### 8.2 ミニゲームとパルクール

この 2 つは通常**独立したワールドか独立したインスタンス**を必要とし、「同時接続人数」に厳しい要件があります。

- 人数が足りないと試合が成立せず、プレイヤーが見るのは空っぽの会場で、この遊び方がないより傷つきます。
- 保守コストが高い。マップ、ルール、バランス、不具合のすべてに継続的な投入が必要です。
- メインのサーバーが安定し、安定した同時接続人数が出てから検討することを勧めます。開設当初の最初の一群のプラグインにはしないでください。

具体的なプラグインの選択肢は広く、品質の差も明らかです。**各プラグインの公式ページと更新履歴に従ってください**。本記事では名前を挙げた推薦はしません。

### 8.3 領地、保護、経済の連動

領地システムの中核的な価値は**財産の安心感**です。これがなければ、プレイヤーは長期的な建設に投資したがりません。確認できる公式の説明：

- **GriefPrevention**：公式リポジトリの説明は「2011 年以来、Minecraft サーバー向けの公式のセルフサービス型荒らし対策 Bukkit プラグイン」。
- **WorldGuard**：公式リポジトリの説明は「Minecraft サーバーを保護し、プレイヤーが区域を区切れるようにする」。

経済と連動させるときは注意してください。**領地の費用（購入、更新、面積あたりの課金）は極めて優れた通貨の回収手段ですが、価格が高すぎると新規プレイヤーを門前払いします**。領地の価格は「新規が最初の数時間で稼げる金額」に合わせるのがよく、「古参の残高」に合わせるのではありません。保護体系の分担は [領地と保護](/tutorials/java/protection) と [アンチチートと荒らし対策](/tutorials/java/anticheat) を参照してください。

### 8.4 科技系の大型コンテンツ（Slimefun の類）

**Slimefun4** の公式リポジトリの説明は「ユニークで、MOD パックのように遊べる Spigot/Paper プラグイン」で、2013 年からバックパック、ジェットパック、リアクターなど大量のコンテンツを提供しています。

この類のプラグインは**サーバーの中にもう 1 つゲームを入れる**のと同じです。

| 代償 | 具体的な現れ方 |
| --- | --- |
| 性能 | 大量のカスタムアイテム、機械のロジック、定期タスク |
| バージョンアップ | サーバーのバージョンに依存し、アップグレードは対応待ちになることが多い |
| 習得の敷居 | 新規プレイヤーが新しい体系一式に直面し、離脱しやすい |
| 互換性 | アイテム、クラフト、ドロップで他のプラグインと衝突しやすい |

科技サーバーをやると決めたなら、**「これは新しいゲームだ」という仕様で計画してください**。独立したガイド、独立したチュートリアル、独立した性能予算を用意し、「プラグインをもう 1 つ足す」と考えないことです。

## 9. アンチチートと経済の安全

**複製の脆弱性（dupe）は経済システムの最大の敵**です。ルールを変えず、数量だけを変える。そして数量が制御不能になれば、価格、ショップ、クエスト報酬はすべて意味を失います。

### 9.1 原則

- **産出型の遊び方にはすべてログを持たせる**。ログがなければ「増殖されたのかどうか」すら判断できません。
- **取引を 1 件ずつ記録する**。誰がいつ、誰と、何を、いくらで取引したか。事後の追跡はこれらの記録に完全に依存します。
- **監査の軌跡を残す**。BAN、ロールバック、手動の配布はすべて記録を残し、「権限の濫用」という指摘を避け、振り返りにも使います。
- **権限を最小化する**。権限ノードで済むなら OP を与えない。1 つのワールドに限定できるなら全サーバーに与えない。[[JAVA] セキュリティプラグイン](/tutorials/ops/security-java) を参照。
- **ロールバックの計画を持つ**。事故の後にどの時点へ戻せるかは、バックアップの方針次第です。[バックアップと復元](/tutorials/java/backup) を参照。

確認できる事実：**CoreProtect** の公式リポジトリの説明は「Minecraft サーバー向けの、極めて高速なデータ記録と荒らし対策ツール」。記録するのは**ブロックとコンテナのレベルでの行為**で、「物がなぜ消えたか」を調べる第一級の証拠になります。[アンチチートと荒らし対策](/tutorials/java/anticheat) で、防御体系全体における位置づけを説明しています。

### 9.2 禁止アイテムが経済に流れ込むリスク

いわゆる「禁止アイテム」とは、脆弱性、コマンド、プラグインの不具合によって産出された、本来存在すべきでないアイテム（異常なエンチャント、不正な数量、バランスを壊す道具）のことです。その害は次の点にあります。

- プレイヤーの手に渡った瞬間、**正常な資産として取引に参加し**、経済全体を汚染する。
- 発見が遅いほど、ロールバックの代償が大きくなる（数十人のプレイヤーを戻す必要があるかもしれない）。
- 処理には根拠が必要です。**まず記録で出どころを確認し、それから回収の範囲を決める**。感覚で人を BAN してはいけません。

推奨：高価値のアイテムには「出どころを追える」仕組みを用意し、規約に「禁止アイテムは一律回収する」と明記してください。

## 10. 経済バランスの設計

経済システムの本質は**貯水池**です。入水と出水がおおよそ釣り合っていなければなりません。

| 方向 | 手段 | 説明 |
| --- | --- | --- |
| 通貨の出どころ（入水） | 管理者ショップの買い取り、クエスト報酬、職業の収益、イベント報酬 | どの出どころも「1 時間あたりいくら産出できるか」を計算できなければならない |
| 通貨の回収（出水） | ショップでの販売（プレイヤーがシステムの品を買う）、取引税、領地の購入と更新、修理費、テレポート費、ガチャの鍵 | 出水が足りなければ必ずインフレする。最もよくある設計の欠落 |

### 10.1 インフレの典型的な症状

- 古参の残高が「何でも買える」水準になり、ショップが意味を失う。
- 新規が「永遠に追いつけない」と感じて、そのまま去る。
- 高価なアイテムが買い占められ、価格がさらに上がる。
- プレイヤー間の取引が通貨を迂回して「物々交換」になり始める。

### 10.2 必ず用意する回収手段

少なくとも 3〜4 種類を用意し、しかも**遊び方に自然に溶け込ませる**こと。「罰金」にしないでください。

- **取引税**：プレイヤーショップの成立時に徴収し、自動で回収され、しかも活発さと正の相関になる。
- **領地の維持費**：面積か時間で課金し、「土地を占める」ことにコストを持たせる。
- **修理とエンチャントのコスト**：装備の維持に通貨を消費させ、回収量がゲームの進行とともに増える。
- **利便サービス**：テレポート、ステータスの振り直し、名前の変更などの有料サービス。
:::tip 感覚ではなくデータで経済を調整する
定期的に記録してください。サーバー全体の通貨量、上位 10% のプレイヤーの残高の割合、1 日あたりの通貨の増加量、1 日あたりの回収量。**「1 日の増加」が「1 日の回収」を上回り続けているなら、インフレはすでに起きています**。まだ価格に現れていないだけです。
:::

## 11. 導入の順序

遊び方を一度に全部入れないでください。推奨する最小限の順序：

1. **最小の経済**：経済の実装を 1 つだけ（抽象層は別に）入れる。残高が保存・取得できるか、データがどこに落ちるか、バックアップがそれを含むかを確認する。
2. **基礎的な回収**：まずテレポート費、修理費、領地費のうち 1 つを作る。**回収手段のない経済を外部に開放しない。**
3. **ショップ**：まず管理者ショップ（価格を制御できる）を作り、買い取り表が札束製造機にならないことを確認する。自由市場が必要になってからプレイヤーショップを足す。
4. **クエスト**：安定した通貨の出どころと回収ができてから、クエストでプレイヤーをあなたが体験してほしい内容へ導く。
5. **外見と称号**：表示層は最後に。数値に影響しないが、長期のプレイヤーの帰属意識を明確に高める。
6. **ガチャとクレート**：最後に置き、「鍵は遊び方からのみ産出する」を貫く。

1 段階足すたびに 1〜2 週間観察してください。通貨の総量、プレイヤーの行動、TPS。**問題が出たら前の段階へ戻るのであって、さらに足し続けるのではありません。**

## 12. 公開前のチェックリスト

- [ ] すべての遊び方プラグインについて「何を解決するか」を説明できる
- [ ] 前提の依存をすべて導入し、コンソールに読み込みエラーがない
- [ ] 経済の実装は**1 つ**だけで、他のプラグインは抽象層を通じて呼んでいる
- [ ] すべての通貨の出どころについて「1 時間あたりの産出上限」を見積もれる
- [ ] 通貨の回収手段が少なくとも 3〜4 種類あり、実際に効いている
- [ ] 管理者ショップの買い取り表を一度「札束印刷速度」で計算した
- [ ] クエスト報酬と通貨の出どころを同じ収益表で比較した
- [ ] 称号と外見が数値の強さを一切提供していない
- [ ] ガチャの鍵は遊び方からのみ得られ、実際の通貨では販売していない
- [ ] 産出型の遊び方と取引にはすべてログがある
- [ ] 記録系プラグイン（CoreProtect の類）を開設の**前に**導入した
- [ ] バックアップの方針が経済のデータベースとプレイヤーデータを網羅している
- [ ] 禁止アイテムの処理手順を規約に書き込んだ
- [ ] ロールバックの計画があり、1 回演習した
- [ ] 遊び方プラグインを足すたびに、導入前後の TPS と MSPT の変化を記録した
