サーバーが「重い」のは現象であり、原因ではありません。プレイヤーが重いと言うとき、あるプラグインがメインスレッドを占有しているのかもしれないし、エンティティが多すぎるのかもしれない、プレイヤーが走り回ってチャンクがリアルタイム生成されているのかもしれない、あるいはホストの CPU が制限されていたりオーバーセールされていたりするのかもしれません。**spark の価値は、「重い」を感覚から、指して見せられる証拠に変えること**にあります。どの呼び出し経路が、どのプラグインが、何パーセントを占めているのか。

本記事は spark 自体の使い方だけを扱います。チューニングの方向は [性能の最適化](/tutorials/java/optimize)、エンティティの堆積は [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag)、クラッシュとエラーは [[JAVA] よくある質問](/tutorials/faq/faq-java) を参照してください。

:::warn コマンドは公式ドキュメントに従ってください
本記事に挙げるコマンドとオプションは spark の公式ドキュメント（spark.lucko.me/docs）と PaperMC のドキュメントに由来し、1 条ずつ照合しています。**spark はプラットフォームやメジャーバージョンによって使えるサブコマンドとオプションが多少異なります**。作業の前に `/spark` か Tab 補完で、あなたのバージョンが対応する引数を確認してください。記憶でオプションを組み立てないこと。
:::

## 1. spark とは何か、どう入れるか

### 1.1 3 つの部分からできている

spark は性能分析ツール（profiler）で、公式は「Minecraft のクライアント、サーバー、プロキシ向けの性能分析器」と位置づけ、3 つの能力からなります。

| コンポーネント | 答えられる問い |
| --- | --- |
| Profiler（サンプリング分析器） | CPU 時間はどのメソッド、どのプラグインに使われているか？ |
| Memory Inspection（メモリ検査） | ヒープで何が最も多くを占めているか？GC の停止は多いか？ |
| Health Reporting（健全性レポート） | TPS、CPU、メモリ、ディスクの長期的な状態はどうか？ |

同時に Web サイトでもあります。spark.lucko.me は公式サイトであり、オンラインのレポートビューア（viewer）でもあります。ゲーム内でサンプリングを 1 回走らせるとデータがアップロードされ、リンクが返ってきます。ブラウザで開けばコールツリーやフレイムグラフが見られます。

まず持っておくべき認識がいくつかあります。

- **spark はサンプリング型（sampling）の分析器**です。公式は "spark vs. others" で、サンプリング分析は数値の精度では通常インストルメンテーション（instrumentation）に劣るが、対象のプログラムをほとんど遅くしないため、実際には本物の実行状況をよりよく反映できると説明しています。
- **「すべて」を記録します**。公式は timings との比較で、timings は分析する範囲を人が事前に定義する必要があり、イベントの回数を集計でき、分析器に不慣れな初心者にやさしいと指摘しています。一方 spark は事前の定義が不要で、すべての呼び出しスタックを記録するため、「結局どの 1 行が遅いのか」に答えるのに向きます。
- **サーバープラグインだけではない**。spark は Java エージェントとして任意の JVM プログラム（バニラのサーバーを含む）に載せられ、バニラのサーバーには難読化解除のマッピングを自動で適用します。

### 1.2 プラットフォームごとの導入

公式のダウンロードページ（https://spark.lucko.me/download）はプラットフォームごとに別のパッケージを配布します。**まず自分のプラットフォームを選んでからダウンロード**し、jar を該当するディレクトリに置いてサーバーを再起動すれば有効になります。

| プラットフォーム | 公式ダウンロードページの項目 | 置き場所 | 備考 |
| --- | --- | --- | --- |
| Bukkit / Spigot / Paper / Purpur | Bukkit (Paper/Spigot) | `plugins/` | サーバープラグイン。Paper 1.21+ は内蔵。下記を参照 |
| Fabric | Fabric | `mods/` | MOD 形式 |
| Forge | Forge | `mods/` | MOD 形式 |
| NeoForge | NeoForge | `mods/` | MOD 形式 |
| Velocity | Velocity | `plugins/` | プロキシ。コマンドの接頭辞が違う。1.4 を参照 |
| BungeeCord | BungeeCord | `plugins/` | プロキシ。コマンドの接頭辞が違う。1.4 を参照 |
| Sponge | Sponge (API 12) | `mods/` | 公式ダウンロードページに個別に記載 |
| クライアント（Fabric/Forge など） | 対応するプラットフォームのパッケージ | `mods/` | クライアントの重さを分析する。コマンドは `/sparkc` |
| 任意の JVM プログラム / バニラサーバー | Standalone (Java Agent) | 起動引数 | 1.3 を参照 |

:::note Paper 1.21 以降は内蔵済み
公式のインストールドキュメントは明記しています。**Paper 1.21 以降は spark をサーバーに同梱しているので、プラグインを別途入れる必要はありません**。内蔵版より新しい spark が必要なときだけ、独立したプラグインの jar を `plugins/` に置き、起動引数に `-Dpaper.preferSparkPlugin=true` を足して内蔵版を上書きします。
:::

:::warn 公式サイトからのみダウンロードする
jar を `plugins/` に置くことは、サーバー全体の制御をそれに渡すことを意味します。**公式のダウンロードページ https://spark.lucko.me/download から取得してください**。出どころの不明な転載パッケージやネットドライブのファイルを使わないこと。ダウンロードページには "Other Platforms"（Folia、Geyser、Minestom、Nukkit、Hytale など）もあり、公式はこれらがコミュニティ提供で as-is のサポートだと説明しています。使う前に自分で評価してください。
:::

### 1.3 独立したエージェント（Standalone Agent）

対象が「標準的なサーバー」でない場合（バニラのサーバー、自前の Java プログラムなど）は、エージェント方式で載せます。起動時に載せる：

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar -jar application.jar [application args]
```

エージェントの待ち受けポートを指定することもできます。

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar=port=2222 -jar application.jar [application args]
```

エージェントが対応する引数（複数はカンマ区切り）：

| 引数 | 意味 |
| --- | --- |
| `port={port}` | エージェントが待ち受けるポート。既定は `2222` |
| `start` | 載せた直後にサンプリングを開始する |
| `open` | 載せた後にビューアのリンクをコンソール / ログへ出力する |

例：

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar=port=2222,start,open -jar application.jar
```

プログラムが**すでに動いている**場合は、プロセスに直接アタッチできます（`<pid>` をプロセス番号に置き換える）。

```bash
java -jar spark-x.y.z-standalone-agent.jar <pid>
java -jar spark-x.y.z-standalone-agent.jar <pid> port=2222
```

PID を付けずにこの jar を実行すると、現在のすべての Java プロセスとその PID を一覧します。アタッチに成功すると、**接続方法がアタッチされたプログラム自身のコンソール / ログに出力されます**。案内に従って SSH のセッションで接続すれば、通常の spark コマンドを実行でき、`exit` でそのセッションを抜けます。

### 1.4 読み込まれたことを確認する

最も直接的な確認方法：**引数なしで `/spark` を実行する**。バージョンと使えるサブコマンドの一覧が表示されます。不明なコマンドと言われる、または何も出ないなら、読み込まれていません。

順に確認してください。jar の置き場所が正しいか（`plugins/` か `mods/` か）、プラットフォームのパッケージを選んだか、サーバーを本当に再起動したか、起動ログに spark の読み込み情報があるか。

コマンドの接頭辞はプラットフォームで異なり、公式ドキュメントがとくに注記しています。

| 環境 | 使うコマンド |
| --- | --- |
| サーバー（Bukkit 系、Fabric/Forge のサーバー） | `/spark` |
| BungeeCord | `/sparkb` |
| Velocity | `/sparkv` |
| Forge/Fabric の**クライアント** | `/sparkc` |

権限については、`spark` 権限が必要か、各サブコマンド自身の権限ノードを使います。公式ドキュメントが挙げる権限ノードには `spark.profiler`、`spark.health`、`spark.ping`、`spark.tps`、`spark.tickmonitor`、`spark.gc`、`spark.gcmonitor`、`spark.heapsummary`、`spark.heapdump`、`spark.activity` があります。多くの場合**自分を OP に設定すれば足ります**。

:::tip 見落とされやすい設定
spark の設定項目 `overrideTpsCommand` は既定で `true` で、しかも**Bukkit 系のサーバーでのみ有効**です。つまり既定では `/tps` は spark に引き継がれ、出力は spark の TPS ビューになります。
:::

## 2. まず全体の健全性を見る

### 2.1 TPS と MSPT とは何か

まず tick ループを理解します（公式の "The Tick Loop" ガイド）。

- Minecraft サーバーの目標は**毎秒 20 tick を実行する**こと、つまり**50 ミリ秒に 1 tick**です。
- 1 tick でやることは、プレイヤーから届くパケットの処理（移動、ブロックの設置 / 破壊、エンティティへの攻撃）、プレイヤーと他のエンティティの位置の更新、世界の変化のプレイヤーへのブロードキャスト、 mob のスポーンと AI・経路探索の処理、レッドストーンの更新の処理などです。
- ある tick が 50 ミリ秒**より短く**終われば、サーバーは残りの時間「眠り」、次の tick を始めるべき時刻まで待ちます。**睡眠は健全です**。
- ある tick が 50 ミリ秒を**超える**と、次の tick は遅らせるしかありません。tick は並行実行できないからです。すべてが「右へずれ」、同じ 1 秒で完了する tick が減り、プレイヤーには遅く、重く感じられます。

2 つの指標はここから来ています。

| 指標 | 正式名 | 意味 | 目標値 |
| --- | --- | --- | --- |
| TPS | ticks per second | 1 秒あたり平均で何 tick 完了するか | **20** |
| MSPT | milliseconds per tick | 1 tick あたり平均で何ミリ秒かかるか | **50 以下** |

公式ドキュメントの説明では、`/spark tps` の出力には MSPT の**最小値、中央値、95 パーセンタイル、最大値**も含まれ、spark は良し悪しに応じてこれらの数字を緑、黄、赤に自動で色分けします。

**最大値が重要な理由**：上の指標はいずれも平均か統計量です。公式は tick ループのガイドでとくに注意を促しています。「ほとんどの tick は 20 ミリ秒で済む（健全）のに、まれに 300 ミリ秒かかる tick がある（不健全）」という状況は十分に起こり得て、これが**ラグのスパイク（lag spike）**です。平均はスパイクを均してしまうので、平均 TPS だけを見ると問題を見落とします。

### 2.2 /spark tps

```text
/spark tps
```

TPS と CPU 使用率を表示します。これが毎回の調査の**最初の一歩**です。まず「本当に重いのか」を確認し、それから分析器を使うか決めます。

### 2.3 /spark health

`health` サブコマンドはサーバーの健全性レポートを生成し、**TPS、CPU、メモリ、ディスクの使用状況を含みます**。公式ドキュメントが示す使い方：

```text
/spark health
/spark health upload
/spark health show
/spark health show --memory
/spark health show --network
```

| コマンド | 動作 |
| --- | --- |
| `/spark health` | ビューアで開く。**live dashboard モードで、データは 10 秒ごとに自動更新** |
| `/spark health upload` | **静的**な健全性レポートをアップロードする。自動更新はしない |
| `/spark health show` | ブラウザを開かず、コンソールに基礎レポートを直接表示する |
| `/spark health show --memory` | JVM のメモリ使用状況を追加する |
| `/spark health show --network` | システムのネットワーク使用状況を追加する |

### 2.4 /spark ping

```text
/spark ping
/spark ping --player <username>
```

引数なしでは**すべてのプレイヤーの平均 ping**（往復遅延 RTT）を表示し、`--player` を付けると特定のプレイヤーの現在の ping を見ます。

**なぜ独立して挙げるのか**：プレイヤーが「重い」と言うとき、サーバーの tick が遅いのか、その人からデータセンターまでのネットワーク経路が悪いだけなのかが分かりません。ping が高く MSPT が正常なら、問題はネットワーク経路にあり、サーバーの設定を変えても無駄です。この段階は**ネットワークの問題と tick の問題を切り分ける**ためのものです。

### 2.5 一定期間の変化をどう見るか

1 回の `/spark tps` はスナップショットにすぎません。傾向を見るには `/spark health` の live dashboard を使います。公式の説明では 10 秒ごとに自動更新されるので、1 本のタイムラインとして、TPS、MSPT、CPU が**持続的に低い**のか、**周期的に落ちる**のかを観察できます。

| 形 | 説明 | 次の一手 |
| --- | --- | --- |
| TPS が持続的に低く、MSPT が持続的に高い | メインスレッドが長期的に処理しきれていない | そのまま profiler でホットスポットを探す |
| TPS はほとんど正常で、ときどき落ちる | ラグのスパイク | tickmonitor で特定し、`--only-ticks-over` でサンプリングする |

:::note 「低い TPS + 正常な MSPT」をどう理解するか
tick ループの仕組みから推論すると、MSPT が本当に正常（どの tick も 50 ミリ秒の予算内で終わる）なら、TPS が長期的に低いままにはならないはずです。tick 間の睡眠がリズムを埋め合わせるからです。だから「TPS は低いが MSPT は正常」というとき疑うべきは「あるプラグインの書き方が遅い」ではなく、**外部の要因**です。サーバーが止められた（長時間の stop-the-world、ワールドの保存、ホストのサスペンドや移行）、ホストの CPU が制限された、他のテナントに奪われた、あるいは**データ自体が間違っている**。

最後の点には公式の根拠があります。spark の指標はすべてサーバーのイベントと Java / システムの API から取っており、公式は "About spark metrics" で、**コンテナ内で動かすと CPU / メモリなどの指標がときどき誤って報告される**（Pterodactyl などの環境）と明言しています。「おかしく見えるなら、spark が得ている生データがおかしい可能性が高い」と。ただし補足すると、**「低い TPS + 正常な MSPT は外部要因を指す」は本記事が tick ループの仕組みから行った推論で、公式ドキュメントが直接この結論を出しているわけではありません**。CPU 使用率、ホストの負荷、GC ログと合わせて判断してください。
:::

## 3. サンプリング分析（profiler）

### 3.1 コマンドとオプション

以下のコマンドとオプションはすべて公式の Command Usage ページに由来します。

基本操作：

| コマンド | 役割 |
| --- | --- |
| `/spark profiler start` | 既定のモードでサンプリングを開始する |
| `/spark profiler stop` | 停止して結果を見る（既定ではアップロードしてリンクを返す） |
| `/spark profiler cancel` | サンプリングを停止し、結果を**アップロードしない** |
| `/spark profiler open` | サンプリングがバックグラウンドで動いているとき、止めずにビューアのページを開く |
| `/spark profiler info` | 現在のサンプリングの状態を見る |

よく使うオプション：

| オプション | 役割 |
| --- | --- |
| `--timeout <seconds>` | 指定時間で自動停止する |
| `--only-ticks-over <milliseconds>` | **その時間を超えた tick だけを記録する**。スパイクを捕まえるのに使う |
| `--thread *` | すべてのスレッドを追跡する |
| `--thread <thread name>` | 指定したスレッドだけを追跡する |
| `--thread <pattern> --regex` | 追跡するスレッド名を正規表現で指定する |
| `--interval <milliseconds>` | サンプリングの間隔。既定は 4 |
| `--alloc` | CPU ではなく**メモリの割り当て**（メモリの圧力）を分析する |
| `--alloc --alloc-live-only` | 割り当て分析で、サンプリング終了時にまだ回収されていないオブジェクトだけを残す |
| `--alloc --interval <bytes>` | 割り当て分析のサンプリング粒度。既定は `524287`（約 512 KB） |
| `--combine-all` | すべてのスレッドを 1 つのルートノードの下にまとめる |
| `--not-combined` | スレッドプール内のスレッドをまとめない |
| `--ignore-sleeping` | sleeping 状態でないスレッドのサンプルだけを記録する |
| `--force-java-sampler` | async サンプラーではなく Java サンプラーを強制する |
| `stop --comment <comment>` | 停止時に備考を付ける。ビューアに表示される |
| `stop --save-to-file` | 結果を設定ディレクトリ下のファイルに保存し、**アップロードしない** |

組み合わせの例（公式ガイドと Paper のドキュメントにある書き方）：

```text
/spark profiler start --timeout 60
/spark profiler start --timeout 600
/spark profiler start --only-ticks-over 150
/spark profiler stop --comment "変更前のベースライン"
/spark profiler stop --save-to-file
```

:::note 「引数なしの /spark profiler」について
公式ドキュメントは profiler の操作を `start`、`stop`、`cancel`、`open`、`info` という明確なサブコマンドとして書いており、「引数なしの `/spark profiler`」を独立した動作として説明していません。また公式の設定ドキュメントは、spark の**バックグラウンド分析器が既定で有効**（設定項目 `backgroundProfiler` の既定は `true`）と説明しており、その場合は `/spark profiler stop` や `/spark profiler open` で**すでに走っている 1 回**を操作できます。したがって**サブコマンドで書くこと。裸のコマンドの挙動を仮定しないでください**。
:::

### 3.2 標準的な流れ

```text
1. 問題が起きている最中であることを確認する（公式の強調：profiling は問題の発生中に行わないと何も採れない）
2. サンプリングを開始：/spark profiler start --timeout 60
3. サーバーを実際の負荷で 30〜60 秒動かす（プレイヤーがオンラインで、操作を再現する）
4. 時間になれば自動停止。チャット欄かコンソールに spark.lucko.me/xxxx のリンクが出る
5. ブラウザでそのリンクを開く
6. まず "Server thread"（サーバーのメインスレッド）を見て、最も幅の広いノードから下へたどる
```

時間の選び方：問題が**いま起きている**なら 30〜60 秒で十分です。問題が**断続的**なら、より長い `--timeout`（Paper の公式ドキュメントの例は `--timeout 600`、つまり 10 分）にするか、第 3.6 節のスパイク向けのやり方に切り替えます。

### 3.3 ビューアでレポートを読む

公式の "Using the viewer" ページがビューアの構造を明確に説明しています。

**スレッド（Threads）**：レポートを開くとまずスレッドの一覧が出ます。スレッドは「プログラムの中で何かの仕事をする作業員」と考えると分かりやすいです。サーバーについては、**通常本当に見るべきは "Server thread"**、つまりゲームを動かすメインスレッドだけです。ルートノード（スレッド自身）は常に 100% と表示されます。100% のサンプリング時間がこのスレッドで費やされているからです。

**コールフレーム / ノード（Call frames）**：各ノードは 3 つの情報を示します。**名前**、**そのスレッドの総時間に対する割合**、そして**ミリ秒数（ホバーで表示）**です。ノードをクリックすると子ノードが展開されます。

サーバーのスレッドを展開したときの典型的な形（公式の例）：

```text
Server thread
  java.lang.Thread.run()
    MinecraftServer.run()
      MinecraftServer.tick()        <- 実際に仕事をしている場所
      Thread.sleep()                <- 睡眠。健全。無視してよい
```

**睡眠の割合が最初に見るべきもの**です。公式は tick ループのガイドで目安を示しています。

| 睡眠（waitForNextTick / sleep）の割合 | 意味 |
| --- | --- |
| 高いほどよい（公式の例では 81%） | サーバーに余裕があり、突発的な負荷に耐えられる |
| 20% 未満 | サーバーはすでに忙しく、一部の tick はすでに詰まっているかもしれない |
| 5% 未満 | ほぼ詰まっていると見てよい。余裕はない |

**ただしこれらはすべて平均値です**。公式はとくに、スパイクは平均に均されるので、「睡眠の割合が高い」は「ラグのスパイクがない」と同じではないと強調しています。

**3 つのビュー**（上部のツールバーで切り替え）：

| ビュー | 内容 | いつ使うか |
| --- | --- | --- |
| All（既定） | 完全に展開できるコールツリー | 割合をたどって下へ探す |
| Flat | **最も遅い 250 個のメソッド呼び出し**を最上位に並べる | 「全体で誰が最も時間を使っているか」を素早く見る |
| Sources | **プラグイン / MOD ごとに 1 本のツリー**を作り、最上位がその出どころの発した呼び出し | 「どのプラグインか」を直接特定する |

Flat ビューにはさらに 2 つの軸があります。Display は **Top Down**（通常の向き。展開して子呼び出しを見る）と **Bottom Up**（逆向き。展開して「誰がそれを呼んだか」を見る）を選べ、Sort は **Total Time**（子呼び出しを含む総時間）と **Self Time**（メソッド自身の所要時間）を選べます。

**フレイムグラフ（Flame Graph）**：上部の炎のアイコンを押すか、ノードを右クリックして "View as Flame Graph" を選びます。公式の説明：**ノードの幅がそのノードの占める時間の割合に対応**し、ノードをクリックするとそのノードに「フォーカス」してページいっぱいに広げられます。よく言う「いちばん幅の広いものを見る」はここを指します。

**難読化解除のマッピング（Deobfuscation）**：Minecraft のクライアントとサーバーはクラス名とメソッド名を難読化しています。ビューアは**どのマッピングを適用すべきかを既定で自動判定**します。判定が違うときは、ページ右上のドロップダウンで手動で選びます。

**ブックマーク**：`alt` を押しながらメソッド呼び出しをクリックするか、右クリックで "Toggle bookmark" を選ぶと、そのメソッドがハイライトされ、**ブックマークは URL にエンコードされます**。このブックマーク付きのリンクを渡せば、相手が開いたときに同じ場所が自動で展開・ハイライトされます。「ここだよと指し示す」最も手軽な方法です。

### 3.4 サーバーのスレッドと非同期スレッド

- **Server thread**：tick ループのあるメインスレッド。性能の問題のほとんどはここです。
- **非同期スレッド（async threads）**：プラグインの非同期タスク、チャンクの保存、ネットワーク IO（Netty）、GC のスレッドなど。これらは**tick の予算を直接は食いません**が、CPU を奪ったり、メインスレッドとロックを争ったりすれば、メインスレッドに影響します。

公式ドキュメントの `--thread *` の説明は「**すべての**スレッドを追跡する」です。つまり既定ではすべてのスレッドがサンプリングに含まれるわけではありません。**あるプラグインが重い仕事を非同期スレッドへ投げている疑いがある**（CPU は高いのにサーバーのスレッドは忙しくなさそうに見える）なら、明示的に `--thread *` を付けて採り直してください。

### 3.5 時間を特定のプラグインに帰属させる

これが spark が timings より実用的な点です。**レポートにプラグイン自身のパッケージ名が現れます**。

たとえばサーバーのスレッドに幅の広いものが現れたら：

```text
com.example.shop.ShopManager.tickShops()
```

なら、`com.example.shop` のプラグインがそれをやっています。判断の方法：

1. All ビューで割合をたどって展開し、「プラグインらしい」パッケージ名（通常は逆ドメイン。`me.lucko.`、`com.example.` など）が出るまで進みます。
2. あるいは **Sources ビュー**に切り替えます。**プラグイン / MOD ごとにツリーを作る**ので、最も「太い」ツリーが容疑者です。
3. 最上位がサーバー自身のメソッド（NMS）なら、早合点しないこと。**Bottom Up** を使うか展開を続けて、**誰がそれを呼んでいるか**を見ます。あるプラグインがイベントや API 経由でそのサーバーのコードを呼び出している可能性が高いです。

### 3.6 ラグのスパイクを狙い撃つ：tickmonitor と only-ticks-over

スパイクは平均に隠されるので、公式は専用の組み合わせを用意しています。

第 1 段階として、`tickmonitor` で「どれくらい遅ければ異常か」を調べます。

| コマンド | 役割 |
| --- | --- |
| `/spark tickmonitor` | 監視の仕組みを**オン / オフ**する（もう一度実行するとオフ） |
| `/spark tickmonitor --threshold <percent>` | 平均の tick 時間より指定した割合だけ**長い** tick だけを報告する |
| `/spark tickmonitor --threshold-tick <milliseconds>` | 指定したミリ秒を**超えた** tick だけを報告する |
| `/spark tickmonitor --without-gc` | 監視は有効にするが、GC 活動に関する報告を止める |

公式の説明：既定のしきい値は **100%** で、「この tick の所要時間が平均の 2 倍」のときだけ報告します。より敏感にしたいなら下げます。たとえば：

```text
/spark tickmonitor --threshold-tick 50
/spark tickmonitor --threshold-tick 70
```

第 2 段階として、`--only-ticks-over` でそれらの異常な tick だけを採ります。

```text
/spark profiler start --only-ticks-over 150
```

公式の目安：しきい値は**50 から 100 の間を勧めるが、必ず「重い」tick の実際の所要時間より小さくする**こと。さもないとスパイクそのものを除外してしまいます。公式の例では重い動作が 300 ミリ秒を超えるので、150 ミリ秒にして「念のため」の余裕を取っています。

こうして採ったレポートでは、「正常な」ゲームの仕事がすべて除外され、残るのはスパイクそのものなので、ホットスポットが非常にはっきりします。

## 4. その他の診断ツール

| コマンド | 何に答えるか | いつ使うか |
| --- | --- | --- |
| `/spark tps` | いま本当に重いのか？TPS、MSPT、CPU はいくつか？ | 毎回の調査の最初の一歩。設定変更の前後の比較 |
| `/spark health` | 全体の健全性はどうか（TPS、CPU、メモリ、ディスク）？ | 継続して観察したいとき。live dashboard は 10 秒ごとに更新 |
| `/spark health upload` | 同上だが、共有できる静的なスナップショットが欲しい | 人に見せる、保管する |
| `/spark health show` | ブラウザを開かず、コンソールで直接見る | SSH 環境で素早く見る。`--memory` か `--network` を足す |
| `/spark ping` | プレイヤーの遅延は高いか？ネットワークの問題か tick の問題か？ | プレイヤーが「重い」と言ったとき、まずこの 2 つを分ける |
| `/spark profiler start` | CPU 時間はどのメソッド、どのプラグインに使われているか？ | 「本当に重い」と確認した後 |
| `/spark tickmonitor` | どの tick が異常に遅いか？どれくらいの頻度か？ | 断続的なラグ、スパイク |
| `/spark gc` | GC の履歴はどうか？停止は頻繁か？ | メモリや GC がラグの原因と疑うとき |
| `/spark gcmonitor` | GC を継続的に見て、起きたら報告する | GC のスパイクを疑うとき。1 回有効にし、再現し、また止める |
| `/spark heapsummary` | ヒープでどのオブジェクトが最も多くを占めているか？ | メモリリークを疑うとき。結果はビューアへアップロードされる |
| `/spark heapdump` | 完全なヒープスナップショット（`.hprof`） | MAT などのオフラインツールで深掘りする必要があるとき。ファイルは非常に大きい |
| `/spark activity` | 最近誰が spark を使い、何をしたか？ | 複数人で管理しているとき、他人がサンプリングしていないか確認する。`--page <n>` でページを送る |

以下、間違えやすい細部を補足します。

### 4.1 GC 関連：/spark gc と /spark gcmonitor

`/spark gc` はサーバーの **GC（ガベージコレクション）の履歴**を表示し、「GC がサーバーを遅くしているか」に答えます。

`/spark gcmonitor` は GC 監視の仕組みを**オン / オフ**します（もう一度実行するとオフ）。価値は**ラグと突き合わせられる**ことです。まず監視を有効にし、ラグを 1 回再現し、その時刻に対応する GC 活動があったかを見ます。時間が合えば、方向はメモリと GC のパラメータへ移り、プラグインのホットスポットを探すのではありません。

### 4.2 メモリ関連：/spark heapsummary と /spark heapdump

両者の違いは重要です。

| コマンド | 生成物 | 用途 |
| --- | --- | --- |
| `/spark heapsummary` | ヒープの**要約**。ビューアへアップロードする | 「どの種類のオブジェクトがメモリを最も占めているか」を素早く見て、リークの疑いを判断する |
| `/spark heapdump` | 完全な `.hprof` ファイルをディスクへ書く | オフラインで専門ツールを使い、オブジェクトの参照チェーンを深掘りする |

`/spark heapdump` のオプションは `--compress <type>` で、対応する圧縮形式は `gzip`、`xz`、`lzma` です。公式ドキュメントは `--include-non-live`（到達不能なオブジェクトを含める）と `--run-gc-before`（生成前に JVM に GC を 1 回実行させる）を**非推奨（deprecated）と明記**しています。`heapsummary` の `--run-gc-before` も同様に非推奨です。

:::warn heapdump は非常に重い
完全なヒープダンプは、**ヒープの大きさと同程度のファイルをディスクに書き**、その過程で JVM に明らかな停止を起こします。本番環境でピーク時に気軽に実行しないこと。まずディスクの空きを確認してください。
:::

## 5. レポートから問題を特定する

### 5.1 判断表

まず前提を 1 つ。**メソッド名はバージョン、サーバーの実装、マッピングの集合で変わります**。公式のビューアの例では `WorldServer.doTick()`、`WorldServer.tickEntities()` のような名前（古めのマッピングに対応）が使われていますが、別のバージョンでは `ServerLevel.tick`、`Level.tickEntities` などに見えるかもしれません。**名前を覚えず、形と割合を見てください**。ビューアの自動難読化解除も利用します。

| レポートの現象 | おおむねの結論 | 次の一手 |
| --- | --- | --- |
| ある**プラグインのパッケージ名**（`com.example.shop` など）がサーバーのスレッドで最も大きい割合を占める | そのプラグインがボトルネック | 更新する、代替を探す、発動頻度を制限する。レポートのリンクを作者へ送る |
| `Entity.tick` や `Level.tickEntities`（古いマッピングでは `WorldServer.tickEntities`）が大半 | **エンティティが多すぎる** | [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) を参照：ドロップ品の片付け、スポーンの制限、描画距離とエンティティ関連の設定を下げる |
| チャンク関連の呼び出し（`ChunkMap`、`ChunkGenerator` など）が大半 | **チャンクの生成か読み込み** | マップの事前生成を行い、プレイヤーの新規探索によるリアルタイム生成を減らす |
| ホッパーとブロックエンティティの tick（`hopper`、`LevelChunk.tickBlockEntities` など） | **レッドストーン、ホッパー、ブロックエンティティの負荷** | ホッパーに速度制限をかけ、農場を統合し、常時読み込みチャンクのレッドストーン装置を減らす |
| タイムラインに長い GC の停止が現れる | **メモリか GC の設定** | ヒープサイズと GC のパラメータを調整する。まず `heapsummary` でリークを除外する |
| **特定のワールドや特定の区域だけ**が遅い | 特定の農場か建築物 | 座標を特定し、その場で解体・制限するか、独立したサーバーへ分ける |
| `waitForNextTick` や sleep の割合が非常に低い（5% 未満） | サーバー全体に余裕がない | 単点の問題ではなく容量不足。負荷を減らすかシングルコア性能を上げる |
| sleep の割合は高いのに、プレイヤーは重いと言う | 平均がスパイクを隠している | 第 3.6 節へ：`tickmonitor` と `--only-ticks-over` |

### 5.2 帰属のよくある 2 つの誤解

**誤解 1：NMS のメソッドを見て「サーバーの問題」と思う。** `Entity.tick` のようなメソッドはサーバーのコードですが、**それを呼び出しているのはプラグイン、プレイヤーの行動、農場の設計**かもしれません。Flat ビューで **Bottom Up** に展開し、「誰がそれを呼んだか」を探します。

**誤解 2：Total Time だけを見て結論を出す。** あるメソッドの Total Time が高くても、多くの子メソッドを呼んでいるだけ（それ自身は「殻」）のことがあります。**Self Time** の並びに切り替え、**本当に自分の時間を使っている**メソッドを見てください。そこが変えるべき場所です。

### 5.3 必ず前後で比較する

1 枚のレポートは「いまこうなっている」ことしか示せず、「これを変えると効くか」は示せません。正しいやり方：

```text
1. サンプリング A：/spark profiler stop --comment "変更前のベースライン"
2. 変更を 1 か所だけ行う
3. できるだけ同じ条件でサンプリング B（プレイヤー数、時間帯、同じ区域かどうか）
4. 2 つのレポートで同じノードの割合の変化を比べる
5. 良くならなければその変更を戻し、次の仮説を試す
```

一度に 1 つの変数だけを変えてください。さもないと帰属できません。比較で見るのは**同じノードの割合の変化**で、絶対値ではありません。2 回のサンプリングで総時間やプレイヤー数が違うことがあるからです。

## 6. 実践の流れと注意点

### 6.1 サンプリング自体にもコストがある

spark はサンプリング型の分析器で、コストはインストルメンテーションよりずっと小さいですが、**ゼロではありません**。

- バックグラウンド分析器は**既定で有効**で、サンプリング間隔の既定は **10 ミリ秒**（設定項目 `backgroundProfilerInterval`）。
- サンプリングのエンジンは既定で `async`（async-profiler）で、公式は Java/WarmRoast のエンジンより正確（セーフポイントのサンプリング偏りの影響を受けない）と説明し、**システムが対応していれば自動で使われる**としています。Linux か macOS で x86_64/aarch64 のアーキテクチャが必要で、コンテナ内では `libstdc++` を補う必要があるかもしれません。
- **割り当て分析（`--alloc`）と heapdump はより重い**：前者は HotSpot のデバッグシンボルが必要（Java 11 以降は通常同梱）、後者は大きなファイルを書き、JVM を停止させます。

:::warn 分析器を動かしっぱなしにしない
サンプリングは特定の問いに答えるためのもので、採ったら止めます。`--timeout` で自分で止めさせるのが最も気楽です。**すでに重いサーバーに分析器を長期間載せておくのは、状況を悪くするだけです。**
:::

### 6.2 レポートの共有とプライバシー

公式ドキュメントの「共有」についての説明は前向きです。レポートは自動でビューアにアップロードされリンクが返り、**そのリンクは自由に人へ送れます**。調査を手伝う人へ、あるいはプラグインや MOD の作者へ、問題を示すために送れます。ブックマークの仕組みは「自分が指しているのはこの行」を URL にエンコードします。

ただし、はっきりさせておくべきことがいくつかあります。

1. **アップロードが既定の動作**です。`/spark profiler stop` は既定でアップロードし、`/spark profiler stop --save-to-file` だけが**設定ディレクトリ下のファイルに保存してアップロードしません**。
2. **公式ドキュメントは「レポートを非公開にする」スイッチを説明していません**。本記事が照合したページには、アクセス制御や非公開レポートについての説明が一切ありません。したがって**レポートのリンクは「手に入れた人は誰でも開ける」ものとして扱ってください**。
3. **生データも取得できます**。公式の "Raw spark data" ページの説明：リンクに `?raw=1` を付けると JSON のメタデータが得られ、`https://spark-usercontent.lucko.me/<code>` に直接リクエストして生データ（種類は `application/x-spark-sampler`、`application/x-spark-heap`、`application/x-spark-health`）を取ることすらできます。つまり、**あの短いコード自体がアクセスの資格情報**です。
4. **メタデータには身元の情報が含まれます**。公式の例のメタデータには、発起人のユーザー名と UUID があります。リンクを公開の場に貼る前に、この点を考えてください。
5. **ローカルで開く**：アップロードしたくないときは、`.sparkprofile` か `.sparkheap` のファイルをビューアのページのドロップ領域へドラッグすれば、ローカルで見られます。
6. 助けを求めるなら、PaperMC の公式ドキュメントの提案は**spark のレポートを持って彼らの Discord の `#paper-help` チャンネルへ**（これは Paper 公式が示す経路です）。

### 6.3 1 回の完全なサンプリングのチェックリスト

```text
準備
[ ] 読み込まれていることを確認：/spark
[ ] 現在の状態を記録：/spark tps
[ ] 問題が起きている最中であることを確認（でないと何も採れない）
[ ] ディスクの空きが十分か確認（とくに heapdump するかもしれないとき）
サンプリング
[ ] 全体が持続的に重い   -> /spark profiler start --timeout 60
[ ] 断続的なスパイク     -> まず /spark tickmonitor でしきい値を探し、それから /spark profiler start --only-ticks-over <ms> --timeout <s>
[ ] 非同期スレッドを疑う -> --thread * を足す。メモリの割り当てを疑う -> --alloc を足す（コストはより大きい）
[ ] いつまでも走らせない
レポートを読む
[ ] まず Server thread の sleep の割合を見る
[ ] 最も幅の広いノードから下へ、割合をたどって進む
[ ] Sources ビューで具体的なプラグインへ帰属させる
[ ] Flat と Self Time で「本当に自分が時間を使っている」メソッドを探す
[ ] Bottom Up で「誰がこの遅いメソッドを呼んだか」を探す
[ ] スパイクの場面では --only-ticks-over が効いたか確認（レポートに大量の正常な tick がないこと）
結論と再検証
[ ] 結論を書く：どのプラグイン、どの種類のエンティティ、どの区域、それとも容量不足
[ ] 一度に 1 か所だけ変え、変えたら同じ条件でもう一度採る
[ ] --comment でレポートにタグを付け、比較用にリンクを残す
```

### 6.4 spark を使うべきでない場面

プレイヤーの遅延が高いだけなら、まず `/spark ping`。それはネットワーク経路の問題かもしれません。サーバーが起動しない、またはクラッシュするならログとクラッシュレポートを見ます。profiler は役に立ちません。TPS は正常なのにプレイヤーが「重い」と言うなら、クライアントの描画、描画距離、ネットワークの揺らぎかをまず確認し、やたらに分析器を載せないこと。

あわせて読む：[性能の最適化](/tutorials/java/optimize)（設定と JVM のチューニング）、[エンティティとドロップ品の堆積](/tutorials/faq/entity-lag)（エンティティが多すぎる）、[システムのセキュリティ強化](/tutorials/ops/system-security)（ホスト側の強化）、[バックアップと復元](/tutorials/java/backup)（変更前の保険）。

> spark のコマンドとオプションは公式ドキュメントに従ってください。プラットフォームによって使えるコマンドが多少異なります。
