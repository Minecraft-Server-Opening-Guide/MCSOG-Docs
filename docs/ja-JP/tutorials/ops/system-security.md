[ネットワークセキュリティの基礎](/tutorials/ops/network-security) が扱うのは「外部の人が入ってこられるか」です。この記事は逆向きの問題を扱います。**誰かがすでに入り込んでいる（あるいは自分が操作を誤った）と仮定して、このマシンはどこまで耐えられるか。**

システム強化の目標は「絶対的な安全」ではありません。それは存在しません。目標は**権限を狭め、入口を減らし、痕跡を残す**ことで、1 度のミスがマシン全体の陥落にならないようにすることです。

## 1. アカウントと権限

### 1.1 サーバーを root で動かしてはいけない理由

| root で動かすリスク | 具体的な結果 |
| --- | --- |
| **脆弱性がそのままマシン全体の陥落になる** | サーバー、プラグイン、MOD の脆弱性を突かれると、攻撃者が継承するのは root 権限。システムファイルを書き換え、バックドアを仕込み、データを消し飛ばせる |
| **プラグインは第三者のコード** | フォーラムから落とした jar はサーバーと同じ権限で動く。**root で動かすということは、マシン全体を赤の他人の作者に預けることです。** |
| **誤操作が取り返しのつかないことになる** | パスを間違えた削除コマンドは、一般ユーザーならサーバーのディレクトリを壊すまで。root ならシステム全体を壊し得る |
| **ファイルの所有者が乱れる** | root が作った `world/`、ログ、設定ファイルは一般ユーザーでは変更できず、以後の保守のたびに `sudo` が必要になり、最終的に「何でも root でやる」悪い習慣が身につく |

:::warn パネルが root で動いているからといって、サーバーも root であるべきとは限らない
多くのパネルは管理の都合で高い権限で動き、あなたの代わりにサーバーを起動します。**これはパネルの信頼境界の問題であり、「サーバーは root で動かすべき」という理由にはなりません。** パネルが実行ユーザーを指定できるなら、専用ユーザーを指定してください。
:::

### 1.2 専用のシステムユーザーを作る

```bash
sudo useradd -r -m -d /opt/mcserver mcserver
```

| 引数 | 役割 |
| --- | --- |
| `-r` | **システムユーザー**を作成する（UID はシステム用の予約範囲から割り当てられ、通常はパスワードを作らず、期限もない） |
| `-m` | 同時にホームディレクトリを作成する（`-r` は既定で**作成しない**ため、明示が必要） |
| `-d /opt/mcserver` | ホームディレクトリを `/opt/mcserver` に指定する |
| `mcserver` | ユーザー名 |

**ディレクトリを作成し、所有者をこのユーザーに渡します**。

```bash
sudo mkdir -p /opt/mcserver/survival /opt/mcserver/backups
sudo chown -R mcserver:mcserver /opt/mcserver
sudo chmod 750 /opt/mcserver
```

`chown -R` はディレクトリと**既存の中身**の所有者・グループをまとめて `mcserver` に変えます（再帰が必要なときだけ `-R` を使います）。`chmod 750` は所有者に読み書き実行、同じグループに読み実行、その他に権限なしを与えます。`id mcserver` と `ls -ld /opt/mcserver` でユーザーとディレクトリの所有者を確認してください。

:::tip 専用ユーザーをログインできなくする
このアカウントをサービスの実行だけに使い、対話的なログインが不要なら、シェルを禁止できます。

```bash
sudo usermod -s /usr/sbin/nologin mcserver
```

**注意**：`nologin` は `sudo -iu mcserver` のような切り替えも妨げます。中に入って保守する必要があるなら、`/bin/bash` のまま鍵と権限で制御するか、必要時に一時的に戻してください。**システム上の `nologin` のパスは `/usr/sbin/nologin` か `/sbin/nologin` のことがあるので、確認してから変更してください。**
:::

### 1.3 sudo を意識的に使う

`sudo` の価値は、**権限昇格のたびに記録が残る**（システムログに書かれる）ことと、「特定のユーザーが特定のコマンドだけを実行できる」ところまで絞れることです。

- **`sudo su -` して中に居座らない**。これでは「どのコマンドを誰がいつ実行したか」という記録の層が失われます。
- **必要に応じて昇格する**。単発のコマンドは `sudo コマンド` で、セッション全体を root にしないでください。
- **sudoers は `visudo` で編集する**。構文チェックをしてくれます。`/etc/sudoers` を直接いじって 1 文字間違えると、全員が昇格できなくなる恐れがあります。

```bash
sudo visudo
```

**推奨するやり方**：`/etc/sudoers` の本体を直接編集するのではなく、`/etc/sudoers.d/` に独立した断片を置き、`sudo visudo -f /etc/sudoers.d/mcadmin` で編集して構文チェックを受けます。断片ではコマンド単位まで絞れます。たとえば特定の管理者にサーバーの再起動だけを許す：

```
mcadmin ALL=(root) /usr/bin/systemctl restart minecraft
mcadmin ALL=(root) /usr/bin/systemctl status minecraft
```

**誰に sudo 権限があるかを監査する**：

```bash
getent group sudo    # Debian / Ubuntu の sudo グループ
getent group wheel   # RHEL 系の wheel グループ
sudo grep -rHv '^#\|^$' /etc/sudoers /etc/sudoers.d/
```

:::warn 設定して終わりにせず、定期的に見直す
**退職した管理者、一時的に手伝った友人、初期テストで追加したアカウント**は、長期間 sudo グループに残ります。定期的に見直し、不要になった人を外してください（`sudo deluser USERNAME sudo` または `sudo gpasswd -d USERNAME wheel`）。
:::

### 1.4 不要なアカウントを止める

- **ログイン可能なアカウントをすべて確認する**（シェルを取れるアカウントこそが本当の入口です）：

```bash
awk -F: '$7 !~ /(nologin|false)$/ {print $1, $3, $7}' /etc/passwd
```

- **不要になったアカウントをロックする**：

```bash
sudo usermod -L USERNAME          # パスワードをロックする
sudo usermod -s /usr/sbin/nologin USERNAME   # 同時にログインを禁止する
```

- **重点的に調べる**：`/etc/passwd` で UID が `0` のアカウントは**`root` だけ**でなければなりません。余分なものはバックドアです。

```bash
awk -F: '$3 == 0 {print $1}' /etc/passwd
```

## 2. ファイル権限：最小権限をディレクトリに落とす

### 2.1 まず権限ビットを理解する

`ls -l` の出力の 1 列目、たとえば `-rwxr-x---` は 3 つの組に分かれます。**所有者 / グループ / その他**で、各組 3 桁（読み `r`=4、書き `w`=2、実行 `x`=1）です。

| 権限 | 数値 | 適用 |
| --- | --- | --- |
| `rwx------` | `700` | 所有者だけが使う私有ディレクトリ |
| `rwxr-x---` | `750` | サーバーのルートディレクトリ。所有者は書き込み可、同じグループは入れる、その他は完全に見えない |
| `rw-r-----` | `640` | 所有者が読み書き、同じグループが読み取りだけの設定ファイル |
| `rw-------` | `600` | **パスワードを含むファイル**。所有者だけが見られる |
| `rwxrwxrwx` | `777` | **いかなる場合も使わない** |

### 2.2 `777` が危険な理由

`chmod -R 777` はネット上で最も広まった「万能の解決策」です。`Permission denied` が出たら 777。その実際の意味はこうです。**システム上のどのユーザーも、陥落したどのサービスのプロセスも、このディレクトリの中のすべてを読み、変更し、削除できる。**

| 結果 | 説明 |
| --- | --- |
| **どのローカルアカウントでもサーバーを改変できる** | 陥落した低権限のサービス（たとえばある Web アプリ）が `plugins/` にバックドアの jar を放り込み、次の再起動で発動する |
| **パスワードファイルが全員に見える** | `server.properties` の RCON パスワード、`.env` のデータベースのパスワードが丸見えになる |
| **セーブデータを自由に破壊できる** | どのプロセスでも `world/` を削除できる |
| **本当の問題を覆い隠す** | 権限エラーの根本原因はたいてい「所有者が違う」こと。`777` は症状を覆うだけで、問題は残ったまま |

:::warn 正しい直し方は権限を緩めることではなく、所有者を直すこと
`Permission denied` が出たら、まず**誰が動かしていて、どのファイルを触ろうとしているか**を見ます。

```bash
ls -l /opt/mcserver/survival/server.properties
```

所有者が `root` で、サービスが `mcserver` として動いているなら、正しい対処はこうです。

```bash
sudo chown mcserver:mcserver /opt/mcserver/survival/server.properties
```

**`chmod 777` ではありません。再帰的な権限変更（`chmod -R 777`）はサーバー上では高危険な操作です。実行しないでください。**
:::

### 2.3 サーバーディレクトリの推奨権限

```bash
# サーバーディレクトリ全体を専用ユーザーの所有にする
sudo chown -R mcserver:mcserver /opt/mcserver

# 所有者は全権。同じグループは読み取りと進入のみ。その他は権限なし
sudo chmod -R u=rwX,g=rX,o= /opt/mcserver

# ディレクトリ自体にはその他の権限を一切与えない
sudo chmod 750 /opt/mcserver
```

`u=rwX,g=rX,o=` は**シンボリックモード**です。`X`（大文字）は「ディレクトリ、またはすでに実行ビットがあるファイルにだけ実行権限を付ける」という意味で、無思考の `-R 755` より「ファイルは実行可能であるべきでない」という原則に沿います。**`chmod -R 777` を使わず、サーバーディレクトリで `o+w`（その他が書き込み可）も使わないでください。**

### 2.4 重点的に守るもの

| 対象 | 理由 | 推奨 |
| --- | --- | --- |
| `world/`、`world_nether/`、`world_the_end/` | セーブデータはプレイヤーが投じたすべて。壊されると取り返しがつかない | 所有者 `mcserver`、その他は権限ゼロ。**定期的なオフラインバックアップ**（第 5 節を参照） |
| `server.properties` | RCON パスワード、ポート、`online-mode` などの重要なスイッチを含む | `640`、所有者 `mcserver` |
| `.env`、パスワードを含むスクリプト | データベースのパスワード、API キー | **`600`**、所有者だけが読み書き |
| `ops.json`、`whitelist.json` | 誰が管理者権限を得るかを決める | `640`、変更後に中身を再確認 |
| 秘密鍵ファイル（`id_ed25519` など） | 漏れればログイン権を明け渡すのと同じ | **`600`**、`.ssh` ディレクトリは `700` |
| バックアップファイル | 完全なパスワードとセーブデータを含むことが多い | **Web からアクセスできるディレクトリに置かない**。遠隔地にも 1 部 |

```bash
# 資格情報のファイルは所有者だけに
chmod 600 /opt/mcserver/survival/.env
ls -l /opt/mcserver/survival/.env
# 期待：-rw------- 1 mcserver mcserver ... .env
```

:::note バックアップは権限を変えるので、復元時に所有者を戻す
`cp -a`、`tar`、`rsync -a` のように**属性を保持する**方法でバックアップすれば、復元後の所有者と権限も正しくなります。中身だけをコピーした場合、復元後に所有者が root になり、サーバーがセーブデータを書けなくなることがあります。復元したら `ls -ld` で一度確認してください。
:::

## 3. システムの更新

**侵入のほとんどは「すでに修正済みなのに、あなたがパッチを当てていない」脆弱性を突いています。** 更新を保つことは、あらゆる強化策のなかで最も費用対効果が高い 1 つです。

### 3.1 セキュリティ更新の自動化という考え方

自動更新の考え方はこうです。**セキュリティパッチは自動で入れ、それ以外の更新は自分で決める**。

| ディストリビューション | ツール | 設定ファイル |
| --- | --- | --- |
| Ubuntu / Debian | `unattended-upgrades` | `/etc/apt/apt.conf.d/20auto-upgrades`、`/etc/apt/apt.conf.d/50unattended-upgrades` |
| RHEL / Rocky / AlmaLinux / Fedora | `dnf-automatic` | `/etc/dnf/automatic.conf` |

**Ubuntu / Debian**：

```bash
sudo apt update
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

`20auto-upgrades` のよくある内容：

```ini
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
```

- `Update-Package-Lists "1"`：毎日 1 回パッケージ索引を更新する。
- `Unattended-Upgrade "1"`：条件を満たす更新を毎日自動でインストールする（**既定ではセキュリティ更新のみ**。具体的な範囲は `50unattended-upgrades` の `Unattended-Upgrade::Allowed-Origins` で決まる）。

**RHEL 系**：

```bash
sudo dnf install -y dnf-automatic
sudo systemctl enable --now dnf-automatic.timer
```

`/etc/dnf/automatic.conf` で「セキュリティ更新だけを自動適用する」に関係するよくある設定：

```ini
[commands]
upgrade_type = security
apply_updates = yes
```

**動作しているかの確認**：`systemctl status unattended-upgrades`（Debian / Ubuntu）または `systemctl status dnf-automatic.timer`（RHEL 系）。

:::warn 具体的な設定項目と既定値はバージョンで変わる
上はあくまでよくある書き方です。**ディストリビューションやバージョンが違えば、設定ファイル名、選択肢名、既定の範囲も異なり得ます**（たとえば「セキュリティ以外の更新を含むか」「古いカーネルを自動削除するか」）。変更の前に、使っているバージョンの公式ドキュメントと照合し、`systemctl status` でサービスが本当に動いていることを確認してください。**設定したことと有効になったことは別です。**
:::

### 3.2 むやみに自動再起動しない

自動更新でパッチを**インストールする**ことと**再起動する**ことは別です。カーネル、glibc、systemd といったコンポーネントの更新は、**再起動して初めて本当に有効になります**。**無条件の自動再起動は有効にしないでください**。理由は次のとおりです。

- **ゲームサーバーにはプレイヤーがいる**。深夜の再起動はプレイ中のプレイヤーを切断し、進行度を失わせ、セーブデータの問題を引き起こすこともある。
- **再起動の失敗は長時間のダウンになる**。新しいカーネルがドライバや環境と合わなければマシンが起動せず、気づくのは翌日かもしれない。
- **再起動後にサーバーが自動で起動するとは限らない**。サービスが `enable` されているかによる（第 4 節を参照）。

**推奨するやり方**：

| やり方 | 説明 |
| --- | --- |
| **メンテナンス時間** | プレイヤーが最も少ない時間帯（たとえば火曜の未明）を固定し、事前に告知して手動で再起動する |
| **通知してから再起動** | サーバーのコマンドでカウントダウンを放送し、プレイヤーを安全にログアウトさせる |
| **古いカーネルを残す** | 古いカーネルを自動削除しない。問題が起きたときに戻せる |
| **再起動後すぐに検証** | サービスが動いているか、ポートに到達できるか、ログに異常がないか |

`[ -f /var/run/reboot-required ] && cat /var/run/reboot-required`（Debian / Ubuntu）または `sudo dnf needs-restarting -r`（RHEL 系）で、再起動待ちかどうかを確認できます。

:::tip まず一度再起動して、自分で起動できることを確かめる
**プレイヤーがいない**ときに手動で 1 回マシンを再起動し、「サービスの自動起動」が本当に効くか検証してください。**検証していない自動起動は、自動起動がないのと同じです。**
:::

## 4. サービスの強化（systemd）

### 4.1 基本の unit

`/etc/systemd/system/minecraft.service`：

```ini
[Unit]
Description=Minecraft Server
After=network.target

[Service]
Type=simple
User=mcserver
Group=mcserver
WorkingDirectory=/opt/mcserver/survival
ExecStart=/usr/lib/jvm/java-21-openjdk-amd64/bin/java -Xms2G -Xmx4G -jar server.jar nogui
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

| ディレクティブ | 役割 |
| --- | --- |
| `User=` / `Group=` | **専用ユーザーで動かす**。書かないと既定で root として動く。これが最もよくある強化の穴。 |
| `WorkingDirectory=` | サーバーの作業ディレクトリ。相対パス（`world/`、`plugins/`）はこれを基準にする。 |
| `ExecStart=` | 起動コマンド。**絶対パスで書く必要がある**。systemd は `PATH` を解決しない。 |
| `Restart=on-failure` | 異常終了時に再起動する。正常な `stop` では発動しない。 |
| `RestartSec=10` | 再起動の前に 10 秒待つ。クラッシュ時に空回りしてログを溢れさせない。 |

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
```

:::note 既存のチュートリアルの unit は screen を使っている
[環境の準備](/tutorials/java/environment) の例は `screen` でコンソールを保持し、入室してコマンドを打ちやすくしています。**どちらの書き方でもかまいません**。本記事の例は `Type=simple` で Java プロセスを直接動かすもので、以下に示す強化オプションを重ねるのにより適しています。**注意：`screen` と `ProtectSystem=strict` のような強化を組み合わせる場合、`screen` が必要とするソケットのディレクトリが書き込み可能か確認してください。**
:::

### 4.2 リソースの制限

リソースを制限することは、「メモリリークでマシン全体を道連れにする」ことも「攻撃されたときにマシンを食い尽くされる」ことも防ぎます。

```ini
[Service]
LimitNOFILE=65535
MemoryMax=6G
```

| ディレクティブ | 役割 | 注意 |
| --- | --- | --- |
| `LimitNOFILE` | 開けるファイルディスクリプタの上限 | プレイヤーが多くチャンク読み込みも多いと既定値では足りないことがあり、「接続が拒否された」り不可解な IO エラーになったりする |
| `MemoryMax` | このサービスの**メモリのハード上限** | 超えるとカーネルの OOM で殺される。**`-Xmx` より明らかに大きくする必要がある**。JVM 自身、メタスペース、スレッドスタック、ダイレクトメモリはこの外側にあるため |

:::warn `MemoryMax` を `-Xmx` より小さくするのは典型的な誤り
`-Xmx4G` は Java ヒープだけを制限します。ヒープ上限 4G の Minecraft サーバーは、**実際の常駐メモリが 5G を超えることがあります**。`MemoryMax` を `4G` にすると、サービスが繰り返し殺されて再起動し、ログには「プロセスが突然消えた」としか残りません。

**推奨**：`MemoryMax` には少なくとも 30% の余裕を持たせ（たとえば `-Xmx4G` に `MemoryMax=6G`）、`systemctl status` の実際のメモリ使用量を見て調整してください。
:::

### 4.3 権限を制限し、ファイルシステムを守る

これらのディレクティブは、サービスが**触るべきものだけに触れられる**ようにします。サーバーやプラグインが陥落しても、攻撃者が与えられる被害は枠の内側に収まります。

```ini
[Service]
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/opt/mcserver/survival
```

| ディレクティブ | 役割 |
| --- | --- |
| `NoNewPrivileges=yes` | プロセスが setuid / setgid のプログラムで昇格することを禁止する。**ほとんど副作用のない強化項目なので、全部入れることを勧める。** |
| `PrivateTmp=yes` | サービスに**専用の `/tmp` と `/var/tmp`** を与え、他のプロセスの一時ファイルを見ることも影響することもできなくする |
| `ProtectSystem=strict` | **ファイルシステム全体を読み取り専用でマウント**する（`/dev`、`/proc`、`/sys` を除く）。サービスは `ReadWritePaths` に列挙したパスにしか書き込めない |
| `ProtectHome=yes` | `/home`、`/root`、`/run/user` をサービスから**見えなくする**（空のディレクトリと同等） |
| `ReadWritePaths=` | `ProtectSystem=strict` と組み合わせ、**書き込みを許可するパスを明示する**。**これを書かないと、サーバーはセーブデータすら書けない。** |

:::warn `ProtectSystem=strict` を足したらサービスが起動しない、まずここを見る
よくある原因：

1. **`ReadWritePaths` を忘れた**、またはパスが間違っている（絶対パスで、`WorkingDirectory` と一致している必要がある）。
2. **バックアップスクリプトやプラグインが別の場所に書く**（たとえば `/var/log`、`/srv`）。それも `ReadWritePaths` に加える必要がある。
3. **Java が一時ディレクトリに書く必要がある**：`PrivateTmp=yes` で通常は足りますが、サーバーが固定の一時パスを明示的に設定しているなら、それも加えます。

**調べ方**：`sudo systemctl status minecraft` と `sudo journalctl -u minecraft -n 100` が「権限が拒否された」パスを直接示してくれます。
:::

:::note 強化オプションが使えるかは systemd のバージョン次第
上記のディレクティブは比較的新しい systemd では使えますが、**具体的な対応状況はバージョンで変わります**。`systemd-analyze security minecraft.service` で、サービスに実際に効いているサンドボックスの設定を確認できます。「露出度」のスコアと項目ごとの説明が出るので、感覚でディレクティブを足すよりはるかに確実です。バージョンによって採点基準や項目名が異なるため、**あなたのシステムの実際の出力に従ってください**。
:::

## 5. バックアップもセキュリティ制御である

ここまでの節は「システムを支配される」ことを防いできました。しかし**どんな強化でも防げない**脅威が 2 種類あります。

| 脅威 | 現れ方 |
| --- | --- |
| **ランサムウェア** | アクセスできるすべてのファイルを暗号化する。**同じマシンにマウントされたバックアップも一緒に暗号化される。** |
| **内部からの破壊 / 誤操作** | 管理者やプラグインの `rm -rf` 1 発、あるいは悪意ある「協力者」によるデータ削除と逃亡 |

**結論：バックアップの意味は「ハードウェア故障への備え」だけではありません。ランサムウェアと破壊に対抗できる唯一の手段です。ただし、バックアップが攻撃者の手の届かない場所にあることが前提です。**

| 原則 | やり方 |
| --- | --- |
| **オフライン** | 少なくとも 1 部は、**普段マウントせず、ネットワークにもつながない**媒体（外付けディスク、オブジェクトストレージのスナップショット）に置く |
| **遠隔地** | ローカルディスクが壊れたりデータセンターで事故が起きたりすると、ローカルのバックアップも一緒に消える |
| **バージョン管理** | 最新の 1 部だけを残すと、「セーブデータがずっと前から壊れていたのに気づかなかった」場合に打つ手がなくなる |
| **権限** | バックアップファイルには通常、完全なパスワードとセーブデータが入る。**Web からアクセスできるディレクトリに置かず**、権限は第 2 節に従って絞る |

具体的な操作（一貫性のあるバックアップ、`save-off` / `save-on`、保持方針、復元手順）は [バックアップと復元](/tutorials/java/backup) を参照してください。**復元を検証していないバックアップはバックアップに数えません。**

:::warn バックアップディレクトリにサーバーの書き込み権限を与えない
サーバーのプロセス（またはそれが読み込むプラグイン）がバックアップディレクトリに書けるなら、陥落したプラグイン 1 つで**すべてのバックアップを削除したり暗号化したりできます**。バックアップディレクトリはサーバーのディレクトリの外に置き、**サービスアカウントに書き込み権限を与えないでください**。
:::

## 6. 監査と日常の衛生

強化は一度きりの作業ではありません。以下のチェックは**定期的に流す**か、少なくともシステムに変更を加えた後に流してください。

### 6.1 チェックリストとコマンド

| 確認項目 | コマンド | 期待する結果 |
| --- | --- | --- |
| **待ち受けポート** | `sudo ss -tlnp` | 把握しているサービスだけが待ち受けている。見慣れないポートは調べる |
| **UDP の待ち受け** | `sudo ss -ulnp` | 同上（統合版 / Geyser は UDP を使う） |
| **ログイン失敗** | `sudo lastb \| head` | 大量の記録はブルートフォースを受けている証拠（root が必要。記録しないシステムもある） |
| **ログイン成功** | `last -n 20` | 知らないユーザーや送信元 IP がない |
| **UID 0 のアカウント** | `awk -F: '$3 == 0 {print $1}' /etc/passwd` | `root` だけ |
| **ログイン可能なアカウント** | `awk -F: '$7 !~ /(nologin\|false)$/ {print $1, $7}' /etc/passwd` | 把握している人だけ |
| **sudo 権限** | `getent group sudo` / `getent group wheel` | 退職者や一時的なアカウントがない |
| **スケジュールタスク** | `sudo crontab -l`、`ls -l /etc/cron.*`、`systemctl list-timers --all` | 自分が作っていないタスクがない |
| **systemd のユニット** | `systemctl list-units --type=service --state=running` | 見慣れないサービスがない |
| **未使用のパッケージ** | `sudo apt autoremove --dry-run` / `sudo dnf autoremove` | 削除対象が本当に不要であることを確認する |
| **サービスのサンドボックス評価** | `systemd-analyze security minecraft.service` | スコアは低いほどよい。項目ごとに提案を見る |

:::warn 見慣れない項目は真剣に受け止める
- **作っていない cron タスクや systemd ユニット**：永続化のバックドアかもしれないし、あるパッケージに同梱されているものかもしれない。**まず出どころを調べてから削除するか決める**。
- **見慣れない待ち受けポート**：まず `sudo ss -tlnp` でプロセスの PID を探し、`ps -p PID -o pid,user,cmd` で何なのかを見る。
- **見慣れないアカウント**：すぐに削除せず、まずホームディレクトリ、`authorized_keys`、ログイン記録を見て、すでに使われていないかを判断する。
:::

### 6.2 インストールする面を最小化する

**入れるソフトウェアが少ないほど、突かれる脆弱性も少なくなります。**

- **デスクトップ環境を入れない**。クラウドサーバーにデスクトップを入れると、不要なサービスとポートが大量に付いてきます（[OS の選択](/tutorials/java/os) を参照）。
- **使わないサービスを入れない**：FTP、Samba、印刷サービス、データベース（サーバーが使わないなら）。
- **サービスの状態を確認する**。不要なサービスは「入っているが起動していない」ではなく `disable` かつ `stop` にすべきです。依存の連鎖で起動してくることがあります。`systemctl is-enabled <service-name>` で確認し、`sudo systemctl disable --now <service-name>` で停止します。

### 6.3 1 ページの早見表

- [ ] サーバーは**専用ユーザー**で動いており、root ではない（`ps -o user,cmd -C java` または `systemctl status` で確認）
- [ ] サーバーディレクトリの所有者が正しく、**777 がない**
- [ ] パスワードを含むファイルの権限が **600** で、Web ディレクトリにも Git リポジトリにもない
- [ ] 自動セキュリティ更新が有効で、**動作していることを確認済み**。無条件の自動再起動は**有効にしていない**
- [ ] systemd unit に `User=`、`WorkingDirectory=`、`Restart=` を設定した
- [ ] `LimitNOFILE` を設定し、`MemoryMax` が **`-Xmx` より明らかに大きい**
- [ ] 必要に応じて `NoNewPrivileges`、`PrivateTmp`、`ProtectSystem`、`ReadWritePaths` を有効にした
- [ ] マシンを一度再起動し、**サービスが自動起動する**ことを確認した
- [ ] **オフライン / 遠隔地**のバックアップがあり、サービスアカウントがバックアップディレクトリに**書き込めない**
- [ ] 上記の監査コマンドを定期レビューに組み込んだ
