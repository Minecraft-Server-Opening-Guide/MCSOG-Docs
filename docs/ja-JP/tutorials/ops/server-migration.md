移行（migration）とは、**サーバー一式をある環境から別の環境へ丸ごと移すこと**です。より良いハードウェアに替える、サービス提供者を変える、ネットワーク品質の悪いデータセンターから出る、あるいは単にコストを下げる。これは「新しいサーバーをゼロから組む」よりはるかに危険です。新規構築の失敗は一時的にサーバーがないだけですが、**移行の失敗は、元のサーバーがすでに止まり、新しいサーバーも起動しない状態**です。

この記事では移行の全手順とチェックリストを扱います。どのファイルを移すか、どのファイルに触れてはいけないかは [サーバー構成](/tutorials/java/structure) を、バックアップの範囲と復元演習は [バックアップと復元](/tutorials/java/backup) と [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照してください。

## 1. いつ移行すべきか

| きっかけ | 典型的なシグナル | 移行時にとくに注意する点 |
| --- | --- | --- |
| ハードウェアの更新 | TPS が長期的に低い、メモリが逼迫、ディスク IO が飽和、しかも最適化の余地がない | 新しいマシンでは CPU のコア数よりシングルコア性能が重要。まずボトルネックが本当にハードウェアか確認する |
| サービス提供者の変更 | チケットの返信がない、オーバーセールが深刻、夜逃げの噂、課金が不透明 | データの国外持ち出しとコンプライアンス、外向きトラフィック費、解約前に新しい環境が使えることを確認する |
| ネットワークの悪い地域から出る | プレイヤーの遅延が高い、経路が大きく迂回、パケットロス、DDoS 対策がない | 目標地域の回線品質は**実測**する。業者の宣伝だけを見ない |
| コスト削減 | 請求の負担が大きい、または長期間遊休の割に構成が過剰 | 安いマシンは CPU を共有しディスクも遅いことが多い。まず負荷試験をしてから移す |
| アーキテクチャの変更 | 単体からグループサーバーへ、パネルの追加、データベースの追加 | これはもはや「移行」ではなく「再構築 + データ移設」であり、別の計画が必要 |

:::note その場で解決できるなら移行しない
移行の各段階には停止とデータのリスクがあります。**メモリが足りないだけなら、移行よりメモリ増設のほうが安い。遅延が高いだけなら、まず経路やプロキシの設定を疑ってください。** 移行は「本当に解決できない」場面のために取っておきましょう。
:::

## 2. 移行前のチェックリスト

移行で最も失敗しやすいのは `rsync` ではなく、**「元のマシンで何が動いているか、自分でも把握していない」**ことです。まず一覧を書き出してから手を動かします。

| 確認項目 | 調べ方 | 合格基準 |
| --- | --- | --- |
| このマシンで動いているサービス | `systemctl list-units --type=service --state=running`、`ss -tlnp`、`docker ps`、`crontab -l` | すべての項目の用途を説明でき、一緒に移すかどうかも分かっている |
| ゲームとコアのバージョン | サーバーの起動ログ、`/version`、コアのファイル名 | 「ゲームバージョン + コア名 + コアのビルド番号」まで記録する |
| プラグイン / MOD のバージョン一覧 | `plugins/`、`mods/` のディレクトリ一覧 | 一覧ファイルがある（バージョン番号を再現できる）。ディレクトリそのものだけでは不十分 |
| Java のバージョン | `java -version` | 新旧のマシンで一致。**Java のアップグレードは別件なので、移行と一緒にやらない** |
| OS とカーネル | `cat /etc/os-release`、`uname -a` | 差異（ディストリビューション、glibc、ファイルシステム）を把握している |
| DNS レコードと TTL | `dig +noall +answer example.com`、`dig _minecraft._tcp.example.com SRV` | レコード種別（A / AAAA / SRV）と現在の TTL を記録している |
| 誰にアクセス権があるか | SSH 公開鍵、パネルのアカウント、サービス提供者のアカウント、共同管理者の一覧 | 移行後に**1 件ずつ確認**し、削除すべきものは削除する |
| バックアップが復元できるか | 実際に 1 回復元演習を行う | 「バックアップファイルがある」ではなく、**「復元して起動できた」** |
| 外部依存 | データベース、オブジェクトストレージ、API キー、Webhook、監視 | 新しいマシンから到達でき、資格情報が有効 |

:::warn 検証していないバックアップでの移行は賭け
`rsync --delete` のパスの誤り、ディスク満杯、権限の不備、アーカイブの切り詰め。どれか 1 つでも、停止してから「使えるコピーがない」ことに気づきます。**作業前に、オフラインで復元可能と検証済みのバックアップが必須**で、メンテナンス時間中はそれを削除しないでください。取得しただけで検証していないバックアップは、バックアップがないのと同じです。
:::

## 3. 必ず移すもの

次の表の各行は、実際の事故で漏れたものです。**ワールドを漏らすのは災難ですが、起動方法を漏らすのは「データはあるのにサービスが起動しない」です。**

| 項目 | 場所（`/opt/mcserver` を例に） | 漏らした場合の結果 |
| --- | --- | --- |
| ワールドデータ | `world/`、`world_nether/`、`world_the_end/`（名前は `server.properties` の `level-name` に従う） | **最も深刻**。プレイヤーの建築、インベントリ、進行度がすべて失われる |
| プラグイン / MOD 本体 | `plugins/`、`mods/` | 入室後に機能が欠け、または MOD の不一致でプレイヤーのクライアントが入れない |
| プラグイン / MOD の設定 | `plugins/<プラグイン名>/`、`config/` | 権限、経済、領地、テレポート地点、ガチャの抽選プールがすべて既定値に戻る |
| コアの設定 | `server.properties` | ポート、難易度、正規アカウント認証、描画距離、ホワイトリストの有無がすべて既定値になる |
| コア自身の設定 | `bukkit.yml`、`spigot.yml`、`paper-*.yml`、`purpur.yml` | 最適化パラメータとワールドの既定値が失われ、性能が明らかに変わり得る |
| 名簿ファイル | `ops.json`、`whitelist.json`、`banned-players.json`、`banned-ips.json` | 管理者権限が失われる、または BAN が効かずホワイトリストが形骸化する |
| プレイヤー名のキャッシュ | `usercache.json` | 通常は再生成できるが、オフラインモードでは UUID と表示名の対応が一時的に乱れる |
| 起動スクリプト | `start.sh`、`起動.bat`、Java の引数 | **最もよくある漏れ**。サービスが起動しない、または引数が違ってメモリ / 性能が異常になる |
| systemd unit | `/etc/systemd/system/minecraft.service` | 起動時に自動起動せず、クラッシュしても再起動しない。`WorkingDirectory` を誤ると空のワールドを新規作成してしまう |
| 定期タスク | `crontab -l`、`/etc/cron.d/`、systemd timer | バックアップ、再起動、クリーンアップのタスクがすべて消え、しかも**ずっと後になって気づく** |
| ファイアウォール規則 | `ufw status`、`firewall-cmd --list-all`、クラウドのセキュリティグループ | ポートが通らずプレイヤーが接続できない。または古い規則の欠落で意図せず露出する |
| TLS 証明書 | `/etc/letsencrypt/`、`/etc/ssl/` | パネル、マップ、リソースパックなどの HTTPS サービスが中断、または証明書の警告 |
| MCDR のデータ | MCDR の実行ディレクトリにある `config.yml`、`permission.yml`、`plugins/` | ボットの権限、コマンドの別名、プラグインの状態が失われる（具体的なファイル名と構造は MCDR の公式ドキュメントに従う） |
| パネルのデータ | パネル自身の設定とインスタンス定義のディレクトリ | サーバーのファイルはあるのに、パネル上は「何もない」状態になる。詳しくは [サーバーパネル](/tutorials/ops/panels) |
| 資格情報のファイル | `.env`、`rcon.password`、データベースのパスワード、クラウドストレージの鍵 | サービスが起動しない、または起動しても依存先に接続できない |
| リバースプロキシの設定 | Nginx / Caddy のサイトファイルと証明書のパス | ドメインでのアクセスが 502 になり、「サーバーが起動していない」と誤認しやすい |
| 監視とアラート | プローブ、エージェント、アラート規則 | 問題が起きたときに**誰も通知を受け取らない**。最も危険な「静かな失敗」 |

### 移さなくてよいもの

| 項目 | 理由 |
| --- | --- |
| `logs/`、`crash-reports/` | 容量が大きい。古い問題を調べるときに別途取り出す |
| `cache/`、`libraries/`、`versions/` | 起動時に自動で再生成される |
| `world/session.lock` | 実行中のロックファイル。移行先では削除すべきで、サーバーが自分で再生成する |
| 旧マシン上の一時アーカイブ、`*.tar.gz` | 数百 GB の一時ファイルまで一緒に同期しやすい |

## 4. 移行の方法

### 4.1 SSH 経由の rsync（第一候補）

`rsync` は差分だけを転送し、権限とタイムスタンプを保持し、SSH の暗号化経路を使うため、移行で最もよく使われる方法です。

```bash
# 1 回目：サーバーを動かしたまま「事前同期」を行い、大半のデータを先に移す
rsync -aHAX --numeric-ids --delete --info=progress2 \
  --exclude='logs/' \
  --exclude='crash-reports/' \
  --exclude='cache/' \
  --exclude='libraries/' \
  --exclude='versions/' \
  --exclude='session.lock' \
  /opt/mcserver/ \
  mcserver@203.0.113.20:/opt/mcserver/
```

| オプション | 役割 |
| --- | --- |
| `-a` | アーカイブモード（`-rlptgoD` と同等）。再帰的にコピーし、シンボリックリンク、権限、時刻、グループ、デバイスファイルを保持する |
| `-H` | ハードリンクを保持する |
| `-A` | ACL を保持する |
| `-X` | 拡張属性（xattr）を保持する |
| `--numeric-ids` | 数値の UID/GID で対応付ける。**マシンをまたぐ場合は必須**。ないと所有者が乱れる |
| `--delete` | 移行先を移行元と一致させる（**もろ刃の剣**。移行元での誤削除も同期される） |
| `--info=progress2` | 全体の進捗を表示する（rsync 3.1 以降） |

**`--delete` を含むコマンドは、初回に必ず `-n`（`--dry-run`）と `-i`（変更を 1 件ずつ表示）を付けて一度実行し**、削除すべきでないものを消さないことを確認してください。

```bash
rsync -aHAX --numeric-ids --delete -n -i \
  --exclude='logs/' --exclude='cache/' \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

:::warn 移行元パスの末尾のスラッシュは適当に書けない
`/opt/mcserver/`（スラッシュあり）は「このディレクトリの中身を同期する」、`/opt/mcserver`（スラッシュなし）は「移行先に `mcserver` というディレクトリを作ってその中に入れる」という意味です。**`--delete` と組み合わせて書き間違えると、移行先のディレクトリ構造全体を壊しかねません。**
:::

### 4.2 tar + scp（データ量が少ない、rsync がない場合）

`rsync` がない、またはデータ量がごく小さいときは、パイプで直接アーカイブして転送し、中間ファイルを残さない方法が使えます。

```bash
# 旧マシンで実行：アーカイブし、SSH 経由で新マシンに展開する
tar -C /opt/mcserver -czf - \
  --exclude='logs' --exclude='crash-reports' --exclude='cache' \
  --exclude='libraries' --exclude='versions' --exclude='session.lock' \
  . | ssh mcserver@203.0.113.20 'mkdir -p /opt/mcserver && tar -C /opt/mcserver -xzf -'
```

一度ファイルに落としてから送ることもできます。

```bash
tar -czf /tmp/mcserver-2026-10-04.tar.gz -C /opt/mcserver .
scp /tmp/mcserver-2026-10-04.tar.gz mcserver@203.0.113.20:/tmp/
```

欠点は**毎回全量で、差分がなく、中断するとやり直し**です。数百 GB のワールドには向きません。

### 4.3 サービス提供者レベルのスナップショット / ボリューム複製（最速）

同じサービス提供者の内部で移行する場合、通常はシステムディスクやデータディスクの**スナップショットを取得し、そのスナップショットを新しいインスタンスに接続**できます。あるいはクラウドディスクを旧インスタンスからデタッチし、新インスタンスにアタッチします。ネットワーク越しにファイルをコピーするより数桁速い方法です。

必ず注意してください。

- **スナップショットの「一貫性」は、取得時にサーバーがディスクへ書き込んでいたかで決まります。** 信頼できるスナップショットを取るには、まず停止する（または少なくとも `save-all` + `save-off`）、取得後に `save-on` します。
- ボリュームのマウントパス、デバイス名、ファイルシステムの UUID が変わることがあります。`/etc/fstab` は UUID を使うか再設定しないと、新しいインスタンスが起動しません。
- サービス提供者やリージョンをまたぐ場合、通常は**直接ディスクを接続できず**、ネットワーク経由のコピーしかありません。
- スナップショットには旧マシンの SSH ホスト鍵、旧 IP の設定、パネルの資格情報が含まれます。**移行後に資格情報をローテーションしてください**。

### 4.4 2 回同期する必要がある理由

| 段階 | サーバーの状態 | 目的 |
| --- | --- | --- |
| 1 回目の同期 | **稼働中** | 数十〜数百 GB の既存データを先に移し、メンテナンス時間を「数時間」から「数分」に縮める |
| 2 回目の同期 | **停止後** | 差分だけを転送し、移行先を停止した瞬間のデータと一致させる |

1 回目の同期中もサーバーはディスクへ書き込んでいるため、そのコピー**自体は一貫していません**。価値は「大部分のファイルがすでに配置済み」という点だけであり、正しさは 2 回目の同期に完全に依存します。したがって：

- 2 回目の同期は**必ず停止後**に行い、停止後に旧マシンを再起動しないでください（また再同期が必要になります）。
- `rsync` は既定で「サイズ + 更新時刻」で再送の要否を判断します。より厳密に内容で比較するには、2 回目に `--checksum`（`-c`）を付けます。**遅くなるが、「サイズが同じでタイムスタンプが保持され、内容だけが違う」ファイルを見落とさない。**
- 2 回目の同期が終わったら、**もう一度検証する（次の節を参照）**。「コマンドがエラーを出さなかった」だけで開設しないでください。

## 5. メンテナンス時間：段階的な作業

事前にメンテナンスの時刻を告知し（所要時間の見込みと補償の案も伝える）、次の順序で実行します。**各段階で結果を確認してから次へ進んでください。**

1. **変更の凍結**：共同管理者に設定を変えない、プラグインを入れないよう伝えます。実行中のバックアップやクリーンアップのタスクが移行と衝突しないことを確認します。

2. **バックアップが使えることを再確認**：オフラインのバックアップが存在し、検証に通り、これから削除・上書きするパス上に**ない**ことを確認します。

3. **DNS の TTL を下げる**：まだ下げていなければ、ここで 60〜300 秒に下げます（反映には古い TTL の失効待ちが必要なので、実際には**24〜48 時間前**に行う必要があります。第 6 節を参照）。

4. **サーバーを停止**：

```bash
sudo systemctl stop minecraft
pgrep -a java          # 出力がないこと。プロセスが本当に終了したか確認する
```

5. **最終同期**（第 4.1 節のコマンドから `--exclude` の不要なものを外し、`-c` を加える）：

```bash
rsync -aHAX --numeric-ids --delete --checksum --info=progress2 \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

6. **検証**：両端で一覧を生成して比較します。パスは**相対パス**でなければファイル名が一致しません。

```bash
# 旧マシン
cd /opt/mcserver && find . -type f -print0 | sort -z | xargs -0 sha256sum > /tmp/old.sha256

# 新マシン（同じコマンドで /tmp/new.sha256 に出力）、その後：
diff /tmp/old.sha256 /tmp/new.sha256 && echo "検証に成功"
```

Windows では `Get-FileHash -Algorithm SHA256` でファイルごとに比較できます。データ量が少なければサイズとファイル数だけを比べてもかまいません。

```powershell
Get-ChildItem -Recurse -File C:\mcserver | Measure-Object -Property Length -Sum
```

7. **新しいマシンで実行期の残留物を消す**：

```bash
rm -f /opt/mcserver/world/session.lock
```

8. **新しいマシンの環境を確認**：Java のバージョンが旧マシンと一致（`java -version`）、ディレクトリの所有者が正しい、`server.properties` のポートが他のサービスと競合していない。

9. **ホスト用のサービスをインストールして起動**：

```bash
sudo cp minecraft.service /etc/systemd/system/minecraft.service
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
journalctl -u minecraft -n 50 --no-pager
```

10. **同じクライアントで実測**：まず新しい IP へ直結し（第 6 節を参照）、入室後に主要な建築、コンテナの中身、インベントリ、権限、プラグインのコマンドが正常か確認します。

11. **DNS を切り替え**：新しいサーバーが正常だと確認してから、レコードを新しい IP に向けます。

12. **旧マシンをしばらく残す**：**すぐに解約したり再インストールしたりしないでください**。それはロールバックの目標です（第 9 節を参照）。

## 6. DNS と切り替え

### TTL は事前に下げる

DNS レコードにはキャッシュ時間（TTL）があります。TTL が 24 時間なら、レコードを切り替えても**最長 24 時間は旧 IP に解決されるプレイヤーが残ります**。

```bash
# 現在の解決結果と TTL を確認する
dig +noall +answer mc.example.com
dig +noall +answer mc.example.com AAAA
dig +noall +answer _minecraft._tcp.mc.example.com SRV
```

**手順は**こうです。移行の 24〜48 時間前に TTL を 60〜300 秒へ下げる -> 古い TTL の失効を待つ -> 移行する -> レコードを切り替える -> 安定を確認してから TTL を大きめの値に戻す（解決の負荷を減らす）。

### 切り替え前に新しいサーバーをどう試験するか

**新しいサーバーを検証しないまま DNS を変えないでください。** 安全な試験方法は 2 つあります。

| 方法 | やり方 | 適用範囲 |
| --- | --- | --- |
| hosts ファイル | 自分のマシンの hosts でドメインを新しい IP に向ける | 自分にしか影響しない。サーバー主と共同管理者が先に確認するのに向く |
| 新しい IP へ直結 | クライアントに `203.0.113.20:25565` を直接入力する | 誰でも使える。**DNS に依存しない** |

```text
# Windows: C:\Windows\System32\drivers\etc\hosts
# Linux / macOS: /etc/hosts
203.0.113.20  mc.example.com
```

:::tip 必ず「同じクライアント」で試験する
別の PC、別のネットワーク、別のゲームバージョンで試験しても、それはプレイヤーの実際の体験ではありません。**普段遊んでいるクライアントで、同じ回線から一度接続する**ことで初めて検証になります。
:::

### SRV レコードを忘れない

多くのサーバーは SRV レコードを使い、プレイヤーがドメインだけを入力すればよい（ポートを書かなくてよい）ようにしています。移行時には**SRV の指す先も同時に変える**必要があります。さもないとプレイヤーは旧マシンへ案内されたままです。

```text
_minecraft._tcp.mc.example.com. 300 IN SRV 0 5 25565 mc.example.com.
```

### 旧マシンはロールバックの目標として残す

切り替え後、**少なくともメンテナンス時間 1 回分のあいだ**（一般的には 24〜72 時間。プレイヤー規模と許容できる停止時間によります）は残します。

- 旧マシンは**いつでも起動できる状態**に保つ（設定、データ、Java 環境に触れない）。
- ただし、新旧 2 台で同じドメインを同時に外部へ提供しては**いけません**。プレイヤーのデータが 2 つのワールドに分裂し、後から統合できなくなります。
- 旧マシンがまだ DNS で解決される場合（TTL が失効していない）、旧マシンのサーバーは**停止したまま**にし、ロールバックが必要なときだけ起動する運用も考えられます。

## 7. IP が変わると連鎖する影響

IP が変わると、「IP を基準にしている」ものがすべて無効になります。**この節を落とすと、症状はたいてい「プレイヤーは入れるのに、ある機能が訳もなく動かない」です。**

| 影響を受けるもの | 症状 | 対処 |
| --- | --- | --- |
| 他のサービスの許可リスト | データベース、オブジェクトストレージ、外部 API が接続を拒否する | 新しい IP を許可リストに加え、古い IP を外す |
| RCON / パネルの IP 許可リスト | パネルでインスタンスがオフライン表示、RCON に接続できない | パネルとデーモンの allowlist の両方を更新する（設定項目は各パネルの公式ドキュメントに従う） |
| ファイアウォール / クラウドのセキュリティグループ | ポートが通らない、またはリバースプロキシがバックエンドに接続できない | 新しいマシンに規則を追加し、**旧マシンは忘れずに閉じる**。露出面を残さない |
| TLS 証明書とリバースプロキシ | HTTPS でエラー、証明書のドメインが一致しない | 証明書はマシンと一緒に移すか再発行する。プロキシの upstream を新しい IP に変える |
| Geyser / Floodgate とグループサーバー | 統合版（基岩版）のプレイヤーが入れない、または全員の IP がプロキシの IP になる | 転送の設定も一緒に移す。詳しくは [統合版サードパーティコアの導入](/tutorials/bedrock/third-party-setup) と [プロキシ](/tutorials/java/proxy) |
| IP BAN リスト | `banned-ips.json` の項目が古い環境を指している。または転送設定が変わって**全員がプロキシ IP として表示され、1 件の BAN が全サーバーに及ぶ** | 移行後に転送が効いているか確認してから、IP BAN を整理するか決める |
| 監視とアラート | プローブが旧 IP を見続け、新しいサーバーが落ちても誰も気づかない | プローブの対象を更新し、**わざと 1 回アラートを発火させて**経路が通ることを確認する |
| バックアップのタスク | バックアップがまだ旧マシンから取得している、または新しいマシンのバックアップが未設定 | [バックアップと復元](/tutorials/java/backup) と [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照 |
| ホワイトリストの統合版プレイヤー | 統合版のプレイヤーは XUID に紐づくため、通常は**IP の変化の影響を受けない** | 通常は変更不要。ただし転送や権限のプラグインが IP に依存するなら再確認する |

:::note IP BAN について
IP BAN はもともと長期の運用に向きません（家庭回線の IP は変わり、データセンターの IP は再利用されます）。移行の前後に BAN リストへ IP の項目が大量にある場合は、**まず有効かどうかを確認してから残すか決めて**ください。むやみにそのまま持ち込まないように。
:::

## 8. 移行後の検証チェックリスト

| 検証項目 | 検証方法 | 合格基準 |
| --- | --- | --- |
| プレイヤーが入室できる | 実際のクライアント（クロスプラットフォームを有効にしているなら統合版も）でそれぞれ 1 回入る | 入れる、チャットできる、移動と相互作用が正常 |
| TPS / MSPT が正常 | `/tps`、`/spark tps`、またはコア固有のコマンド | 旧マシンと同じ水準で、持続的なティック落ちがない |
| プラグイン / MOD がすべて読み込まれる | 起動ログで `Enabling`、`Loaded`、エラーのキーワードを検索する | `Could not load` がなく、バージョンの不整合もない |
| 設定が反映されている | 権限、経済、領地、テレポート地点を抜き取り確認する | 移行前と一致 |
| 名簿が正しい | `/whitelist list`、`/op` 関連のコマンド、または名簿ファイルを直接見る | 管理者とホワイトリストが旧サーバーと一致 |
| バックアップが新しいマシンで動く | バックアップスクリプトを手動で 1 回実行する | アーカイブが生成され、サイズが妥当で、**実際に展開できる** |
| 監視を更新済み | 監視パネルを見る | 新しい IP にハートビートがあり、旧 IP のアラートは止まっている |
| 定期タスク | `crontab -l`、`systemctl list-timers` | バックアップ、再起動、クリーンアップのタスクがすべてあり、時刻も正しい |
| 性能とディスク | `df -h`、`iostat`、メモリ使用量 | ディスクの余裕が十分で、明らかな IO のボトルネックがない |
| 旧マシンの停止 | 次を参照 | **ロールバックの期間が終わってから**解約または再インストールする |

## 9. ロールバックの計画

ロールバックは「もう一度移し戻す」ことではなく、**「既知の使える状態へ戻す」**ことです。だからロールバックの計画は移行の**前に**書いておく必要があります。

1. **発動条件を定義する**：どうなったらロールバックするか？（例：新しいサーバーが 2 時間以内に安定起動しない、ワールドの検証に失敗する、主要なプラグインが動かない、TPS が旧マシンの半分しかなく原因を特定できない。）
2. **ロールバックの動作を明確にする**：DNS を旧 IP に戻す -> 旧マシンでサービスを起動する -> 告知する -> 事後に分析する。
3. **ロールバックの目標を残す**：旧マシンのサーバーディレクトリ、Java 環境、systemd unit、ファイアウォール規則を**そのまま**残す。ロールバックの期間が終わるまで。
4. **データの取捨の規則を用意する**：新しいサーバーがすでにしばらく動き、プレイヤーが遊んでいた場合、**旧ワールドの進行度は遅れています**。ロールバックはこの期間の進行度の喪失を意味するか、新しいワールドのセーブを人手で戻す必要があります（その場合「新しいワールド」のほうが最新のデータです）。**この判断はロールバックの前に決めておく必要があり、やりながら考えてはいけません。**
5. **ロールバックも検証する**：旧マシンで起動する前に、そのデータが停止時と一致していること（バックアップスクリプトに書き換えられていない、誤って削除されていない）を確認します。

:::warn 最悪のケースは「両方が動いている」こと
新旧 2 台が同時に外部へサービスを提供すると（たとえば DNS のキャッシュで一部のプレイヤーが旧サーバーへ、一部が新サーバーへ接続する）、**プレイヤーのデータが 2 つのワールドに分裂します**。この分裂は通常、自動では統合できず、どちらか一方のデータの喪失を受け入れるしかありません。**切り替えの前に旧サーバーを止めることが、この事故を避ける最も簡単な方法です。**
:::

## 10. まとめ

- **まず棚卸し、それから作業**：移行の失敗はたいてい技術の問題ではなく、「自分が何を動かしているかを忘れていた」ことです。
- **バックアップは検証済みでなければならない**：検証していないバックアップはバックアップではなく、心の安らぎです。
- **2 回同期する**：1 回目は予熱（稼働中）、2 回目は確定（停止後）。その間に旧サーバーを再起動しない。
- **試験してから切り替える**：hosts ファイルか IP 直結で新しいサーバーを検証し、それから DNS を変える。
- **TTL は事前に下げる**：これだけは「必ず前もってやる」手順です。直前の TTL 変更では間に合いません。
- **ロールバックの目標を残す**：旧マシンはゴミではなく、あなたの退路です。
