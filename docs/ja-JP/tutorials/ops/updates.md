「更新」は運用のなかで最も日常的で、最も事故りやすい操作です。プラグインの導入に失敗しても機能が 1 つ足りないだけですが、**更新の失敗はセーブデータが開けなくなることにつながります**。この記事では、サーバーコア、プラグイン、MOD、MCDR の更新の流れを再利用できる 1 つのやり方にまとめます。要点は「次へ」を押すことではなく、**各段階に残す退路**です。

始める前に 2 本読んでおくことを勧めます。[バックアップと復元](/tutorials/java/backup)（更新の前にバックアップと復元ができないといけない）、[サーバー構成](/tutorials/java/structure)（自分が触ろうとしているのはどのファイルなのかを把握する）。

## 1. 更新の鉄則

以下の 6 条を重要度順に並べます。**どれか 1 つでも飛ばすと、「10 分の更新」が「丸 1 日の救出」になり得ます。**

### 1.1 まずバックアップし、バックアップを検証する

バックアップは「アーカイブを作って終わり」ではありません。**本当に使える**ことを確認する必要があります。ファイルが存在する、サイズが妥当、中身を一覧できる、できればテスト用ディレクトリで実際に 1 回展開できる。

```bash
# Linux：アーカイブが存在し、サイズが妥当で、中身を一覧できることを確認する
ls -lh /opt/mcserver/backups/world-20261004.tar.gz
tar -tzf /opt/mcserver/backups/world-20261004.tar.gz | head
```

```powershell
# Windows：一時ディレクトリへ展開し、中身が完全であることを確認する
Get-Item C:\mcserver\backups\world-20261004.zip | Select-Object Name, Length, LastWriteTime
Expand-Archive -Path C:\mcserver\backups\world-20261004.zip -DestinationPath C:\mcserver\verify -Force
Get-ChildItem C:\mcserver\verify | Select-Object Name
```

:::warn 検証していないバックアップはバックアップではない
「バックアップスクリプトは実はずっと前から失敗していた」「アーカイブが空だった」「`db/` だけコピーして `level.dat` をコピーしていなかった」。これらは本当に事故が起きた日に気づきます。**少なくとも毎月 1 回、実際に復元してください**。流れは [バックアップと復元](/tutorials/java/backup) を参照。
:::

### 1.2 更新ログを読む

更新ログで探すのは 4 つです。バージョン番号の見栄えではありません。

| 探すもの | なぜ重要か |
| --- | --- |
| **破壊的変更** | 設定キーの改名、コマンドの改名、データ形式の変化は、既存の設定を直接無効にする |
| **新しい最低要件** | サーバーとプラグインの Java バージョン、ローダーのバージョン、依存プラグインのバージョン |
| **データ移行の説明** | 移行コマンドを手で実行する必要があるか、先に中間バージョンへ上げる必要があるか |
| **既知の問題** | 作者がすでに認めている不具合。出たばかりの壊れたバージョンを避けられる |

### 1.3 独立したインスタンスで先に試す

「テスト用インスタンス」を用意します。別のディレクトリ、別のポート、別のワールドのコピー。**すべての更新はまずテスト用インスタンスで通し、それから本番に触ります。**

```bash
# Linux：バックアップからテスト用インスタンスをそのまま展開する
mkdir -p /opt/mcserver/test
tar -xzf /opt/mcserver/backups/full-20261004.tar.gz -C /opt/mcserver/test
```

```powershell
# Windows：同様
New-Item -ItemType Directory -Force -Path C:\mcserver\test
Expand-Archive -Path C:\mcserver\backups\full-20261004.zip -DestinationPath C:\mcserver\test -Force
```

テスト用インスタンスではポートを変えてください（`server.properties` の `server-port`）。さもないと動いているサーバーと同じポートを取り合います。

### 1.4 メンテナンス時間を選ぶ

プレイヤーが最も少ない時間帯（通常は未明か平日の午前）を選び、大会や新規開拓などのイベントを避け、**所要時間の 2 倍を見込み**、問題が起きたときに自分がその場にいることを確認します。コンソールを見ている人がいてこそ、即座にロールバックできます。

### 1.5 常にロールバックの経路を残す

**中核原則：置き換えたファイルはすべて、バージョン番号付きの名前で残す。**

```text
server-1.21.1.jar            # 旧コア。いつでも戻せる
MyPlugin-1.0.0.jar.bak       # 旧プラグイン
world-20261004/              # 更新前のワールドのバックアップ
config.yml.20261004.bak      # 更新前の設定
```

:::tip ロールバックの経路は更新の前に考える
更新の前に自分に問いかけてください。「10 分後に戻すとしたら、具体的にどのコマンドを打つか？」**答えられないなら、まず更新しないでください。**
:::

### 1.6 停止を事前に告知する

グループ、告知板、サーバーの MOTD で、何時に始め、どれくらいかかり、何を更新し、問題が起きたらどうするかを伝えます。プレイヤーが最も嫌うのは停止そのものではなく、**なぜ入れないのか分からず、どれくらい待てばいいかも分からない**ことです。

### 1.7 問題が起き得る状況

| リスク | 典型的な現れ方 | 結果 | 予防 |
| --- | --- | --- | --- |
| ワールドが新バージョンに書き換えられる | 新バージョンで 1 回起動した後、旧コアに戻すとセーブデータがエラーになる、または読み込めない | **不可逆**。バックアップへの巻き戻ししかない | 新バージョンで初めて起動する前に完全バックアップを取る。旧コアと旧ディレクトリも残す |
| Java バージョンの不一致 | 起動即クラッシュ。ログに `UnsupportedClassVersionError` | サービスが起動しない | 第 2.2 節の表に従って Java を合わせる |
| プラグインが新コアと非互換 | `/plugins` に赤字、またはコンソールに `NoSuchMethodError` が流れる | 機能の欠落、最悪起動できない | プラグインの対応バージョンと更新ログを見て、テスト用インスタンスで先に試す |
| 設定キーが改名・削除される | プラグインが既定の設定を再生成し、元の設定が「消える」 | 機能が既定値で動き、プレイヤーに影響する | 更新前に設定ディレクトリをバックアップし、更新後に 1 項目ずつ照合する |
| MOD とローダーの不一致 | 起動クラッシュ。ログに MOD 名とクラスエラー | MOD 側がまったく起動しない | ローダー、ゲームバージョン、MOD の 3 つを揃える |
| 統合版のプロトコル不一致 | サーバー更新後にプレイヤーが入れず、クライアントの更新を求められる | プレイヤーの離脱。iOS のプレイヤーはダウングレードできない | 更新前にプレイヤーのクライアントが追随できるか確認する |
| 改ざんされたファイルを落とす | コアやプラグインは動くが挙動がおかしい | セキュリティ事故 | 公式か公式が認めた配布ページからのみダウンロードする |
| メンテナンス時間の見積もり違い | プレイヤーがすでにグループで「まだ入れないの」と聞いている | 評判と信頼の損傷 | 所要時間の 2 倍を見込み、事前に告知する |
| ディスク満杯 | 展開に失敗、またはセーブデータが書けない | セーブデータの破損 | 更新前に空き容量を確認する |
| 権限と所有者の変化 | Linux で新しいファイルの所有者が root になり、サーバーのユーザーが書けない | プラグインの設定が保存できない | 更新後に `chown -R` でサーバー専用ユーザーへ戻す |

## 2. サーバーコアの更新

### 2.1 共通の流れ

1. **停止する**。コンソールで `stop` を実行し、正常に終了するのを待つ。**プロセスを直接殺さない**。
2. **現在のバージョンを記録する**（コアのバージョン番号、ビルド番号、起動スクリプトの jar ファイル名）。
3. **旧コアを改名して控える**。バージョンの接尾辞を付ける。
4. **公式の配布元から新しいコアをダウンロードする**。第三者の統合パックの jar を使わない。
5. **新しいコアを配置する**。ファイル名を起動スクリプトと一致させる（さもないとスクリプトがファイルを見つけられません。起動スクリプトの書き方は [サーバーの起動](/tutorials/java/start) を参照）。
6. **起動してコンソールを見張る**。起動したら離席しない。
7. **検証する**：コンソールにエラーがない、`/plugins` が正常、自分で入室して一通り歩く。さらに**しばらく観察して**から旧 jar を削除するか決める。

```text
stop
```

```bash
# Linux
cd /opt/mcserver/survival
mv server.jar server-1.21.1.jar                 # 旧コアを改名して控える
cp ~/downloads/server-1.21.4.jar ./server.jar   # 公式ダウンロードページのファイルに差し替える
./start.sh
```

```powershell
# Windows
Set-Location C:\mcserver\survival
Rename-Item server.jar server-1.21.1.jar
Copy-Item "$env:USERPROFILE\Downloads\server-1.21.4.jar" .\server.jar
.\start.bat
```

入室後の検証動作：

```text
/version        サーバーのバージョンを確認する
/plugins        プラグインの読み込み状態を確認する（赤は読み込み失敗）
```

:::tip 旧コアはすぐに消さない
少なくとも「新バージョンがメンテナンス周期を 1 回りし、ワールドもすべて正常」になるまでは残してください。jar は数百 MB ですが、その代わりにいつでも戻せます。
:::

### 2.2 バージョンの飛び越しは無料ではない：まず Java を揃える

**Java のバージョンが合わないとサーバーは起動即クラッシュ**し、ログに `UnsupportedClassVersionError` が出ます。次の表は [環境の準備（Windows と Linux）](/tutorials/java/environment) と一致させており、そのまま再利用できます。

| Minecraft Java 版 | 公式が要求する Java | 説明 |
| --- | --- | --- |
| 26.1 以降 | **Java 25** | 最新の要件（26.1 以降） |
| 1.20.5 – 1.21.x | **Java 21** | 1.20.5 が 21 を要求する最初の正式版 |
| 1.18 – 1.20.4 | **Java 17** | 現在最もよく使われる組み合わせ |
| 1.17 – 1.17.1 | **Java 16** | Java 17 でも正常に起動する |
| 1.12 – 1.16.5 | **Java 8** | 多くの古い統合パックが今もこの段階に残っている |
| 1.7.10 以前 | 公式の要件は低い | 実際には Java 8 が広く使われている |

:::note 上の表の出典
1.20.5 / 1.18 / 1.17 / 1.12 などの区切りは Mojang の公式バージョン一覧（`piston-meta.mojang.com` の各バージョンの `javaVersion.majorVersion` フィールド）に基づきます。26.1 以降が Java 25 を要求するのは Minecraft Wiki のバージョン要件一覧に基づきます。経験からの推測ではありません。
:::

- **Paper、Purpur、Spigot、Fabric、Forge の要件は公式と同じ**です。1.20.5 以上は Java 21、1.18 – 1.20.4 は Java 17 が必要です。
- 上の表は**最低要件**です。Java のバージョンが高すぎると一部のプラグインや MOD が非互換になることがあり、**要件に厳密に合わせることを勧めます**。
- **統合版（BDS）に Java は不要**です。C++ のプログラムで、`bedrock_server`（Windows では `bedrock_server.exe`）を直接動かします。

**複数のメジャーバージョンをまたぐときは一気に飛ばさないでください。** 中間のバージョンが設定形式、ワールド形式、プラグイン API を変えていることがあり、必要なら 1 バージョンずつ上げます（たとえば 1.19 → 1.20 → 1.21）。1 回上げるたびに検証してください。

### 2.3 ワールド形式：アップグレードはほぼ一方通行

:::warn 新バージョンで開いたワールドが、旧バージョンで開けるとは限らない
新しいバージョンでサーバーを起動した後、ワールドのチャンクとエンティティのデータは**新しい形式で書き換えられている**可能性があります。コアを旧バージョンに戻すと、軽ければエラーが流れ、重ければ**ワールドが読み込めません**。これは一方通行で、「旧形式に変換し直す」公式ツールはありません。
:::

したがって：

- 新バージョンで初めて起動する前に、**完全バックアップを取る**（`world/`、`world_nether/`、`world_the_end/`。カスタムのワールド名は `server.properties` の `level-name` に従う）。
- 戻すときは**ワールドごと戻す**。旧コアに戻すのと**同時に**、更新前のバックアップでワールドを上書きします。jar だけを戻してはいけません。
- 先に互換性を検証したいなら、テスト用インスタンスで新バージョンを動かしてください。**本番のワールドで試さないこと**。

### 2.4 Paper / Purpur / Leaves / Leaf

この一群のコアの更新方法はまったく同じです。**jar を差し替える**。公式のバニラと同じワールド形式を共有するので、第 2.3 節の結論もそのまま当てはまります。

注意が必要なのは設定だけです。

| 状況 | 説明 |
| --- | --- |
| 設定にキーが増える | 初回起動時にコアが欠けているキーを**既定値で書き足して**設定ファイルに追記する |
| 設定のキーが削除・改名される | 古いキーが残ったまま無効になることも、無視されることもある。挙動が黙って変わり得る |
| ビルド番号の変化 | 同じゲームバージョンでもビルドが違えば挙動が変わる可能性がある。ビルドログを読む |

やり方：更新前にサーバーディレクトリ全体（少なくとも各 `*.yml`）をコピーし、更新後に差分を比べます。

```bash
# Linux：更新前後の設定を比較する
diff -u paper-global.yml.bak paper-global.yml
```

```powershell
# Windows：更新前後の設定を比較する
Compare-Object (Get-Content .\paper-global.yml.bak) (Get-Content .\paper-global.yml)
```

:::tip 公式の配布元
Paper は <https://papermc.io/>、Purpur は <https://purpurmc.org/>。Leaves、Leaf などのコアは各公式の配布ページに従ってください。**アグリゲータサイトやネットドライブの jar を使わないこと**。
:::

### 2.5 Fabric / Forge / NeoForge

MOD 側はプラグイン側より厳しく縛られます。**ローダーのバージョン、ゲームのバージョン、個々の MOD の 3 つが相互に一致している必要があります**。

| コンポーネント | 何に一致する必要があるか | 一致しないときの症状 |
| --- | --- | --- |
| ローダー（Fabric / Forge / NeoForge） | ゲームのバージョンに結びつき、特定のバージョン範囲しか対応しない | ローダーが入らない、またはサーバーが起動しない |
| 個々の MOD | ゲームのバージョン、ローダーのバージョン、それが依存する他の MOD | 起動クラッシュ。ログに MOD 名とクラスエラーが出る |
| サーバーとクライアントの MOD | 双方に入れる必要がある MOD は一致が必要 | プレイヤーが入れない、または入室直後に蹴られる |

**ローダーのアップグレードは通常、MOD の同時更新を要求します**。MOD は特定バージョンのローダー API 向けにコンパイルされているからです。典型的な失敗の症状は**起動即クラッシュ**で、ログに MOD 名とクラスエラー（`NoClassDefFoundError`、`ClassNotFoundException`、`NoSuchMethodError` など）が並びます。Forge 系では必須依存の不足を直接示すこともあり（`Missing or unsupported mandatory dependencies`）、クライアントは MOD の組み合わせが非互換だと告げることがあります。

推奨する更新の順序：

1. まず、目標のゲームバージョンに対応するローダーのバージョンがあることを確認する。
2. テスト用インスタンスでローダーを上げ、起動できることを確認する（この時点で MOD はすべて外しておいてよい）。
3. MOD を分割して戻す（1 群戻すごとに起動し、どの MOD が問題か特定しやすくする）。最後にサーバーとクライアントを一緒に更新し、MOD の一覧を両側で揃える。

### 2.6 統合版の BDS

統合版のバージョン制約は Java 版と異なります。**クライアントのプロトコルがサーバーのビルドと一致している必要があり**、プロトコルが変われば古いクライアントはそのまま接続できません（原理は [プロトコルのバージョンとバージョン選択](/tutorials/bedrock/protocol) を参照）。

| 要点 | 説明 |
| --- | --- |
| クライアントのプロトコル | サーバーを更新したら、プレイヤーは一致するバージョンのクライアントを使う必要がある。一致しないと更新を求められる |
| iOS の制約 | iOS のプレイヤーは**ストアの最新版しか入れられず**、指定した旧バージョンは入れられない。したがって「旧バージョンに固定する」は iOS のプレイヤーを諦めるのと同じ |
| セーブデータの場所 | BDS のセーブデータはすべて `worlds/` の下にある。**更新前に全体をバックアップする必要がある** |
| 設定ファイル | `server.properties`、`allowlist.json`、`permissions.json`、`valid_known_packs.json` はすべてあなたのデータで、新しいパッケージに上書きされてはいけない |

更新の手順：公式のダウンロードページから該当プラットフォームのアーカイブを取得し、**一時ディレクトリへ展開**して、実行ファイルだけを元のディレクトリへ置きます。

```bash
# Linux：一時ディレクトリへ展開し、バイナリだけを差し替える（ファイル名は実際のバージョンに置き換える）
unzip bedrock-server-new.zip -d /tmp/bds-new
mv bedrock_server bedrock_server-old
cp /tmp/bds-new/bedrock_server .
chmod +x bedrock_server
```

```powershell
# Windows：同様（アーカイブには同梱の DLL もあるのでコピー漏れしないこと）
Expand-Archive -Path "$env:USERPROFILE\Downloads\bedrock-server-new.zip" -DestinationPath C:\bds-new -Force
Rename-Item .\bedrock_server.exe bedrock_server-old.exe
Copy-Item C:\bds-new\bedrock_server.exe .
```

:::warn アーカイブごと展開して上書きしない
公式のアーカイブにも既定の `server.properties`、`allowlist.json`、`permissions.json` などが入っています。**アーカイブごと上書きすると、あなたの設定とホワイトリストが上書きされます。** プログラムのファイルだけを取り、データと設定はそのままにし、`worlds/` が差し替えられていないことを確認してください。
:::

ディレクトリ構造とローダーのバージョン制約は [BDS サーバー](/tutorials/bedrock/bds) を参照してください。第三者のローダーも特定のバージョン範囲しか対応しないので、**サーバーを上げる前にローダーが追随しているか確認**してください。

### 2.7 ダウングレード：最もよくある人為的なデータ損失

:::warn 新バージョンでワールドを開いた後のコアのダウングレードはデータ損失に等しい
「更新したらプラグインが非互換だったので、急いで旧コアに戻した」は運用で最もよくある自傷行為です。**コアは戻せても、ワールドは戻せるとは限りません。**
正しいやり方は、コアを戻すのと**同時に**、更新前の完全バックアップでワールドも戻すことです。jar だけを戻してワールドを戻さないと、開けないセーブデータが残る可能性が高いです。
:::

更新後に本当にダウングレードするなら、順序は次のとおりです。

1. サーバーを停止する。
2. **現在の**（新バージョンに書き換えられた）ワールドディレクトリを改名して控える。そのまま削除しないこと。問題を調べる証拠になります。
3. 更新前のワールドのバックアップを展開し、元の位置に戻す。
4. 旧コアの jar に戻す。
5. 起動し、ログとセーブデータを確認する。
6. プレイヤーに主要な建築とアイテムが正常か確認してもらう。

## 3. プラグインの更新

プラグインの更新はコアの更新より頻繁で、**設定構造の変化**で問題が起きやすいです。基本の操作は [プラグイン入門](/tutorials/java/plugins) を参照してください。

### 3.1 更新前に確認する 4 つのこと

| 確認項目 | どこで見るか | 見ないとどうなるか |
| --- | --- | --- |
| 対応するサーバーのバージョン | プラグインの配布ページの対応バージョン一覧 | 読み込みに失敗し、`/plugins` が赤字になる |
| 対応する Java のバージョン | プラグインの配布ページまたは更新ログ | 読み込み時にクラスのバージョンエラー |
| 前提の依存が揃っているか、バージョンは足りるか | プラグインの説明の Requires / Dependencies。[よく使う前提プラグイン](/tutorials/java/plugin-deps) を参照 | 必須の前提が欠けるとプラグインは読み込みに失敗する |
| 更新ログの破壊的変更 | 配布ページの changelog / release notes | 設定が無効になる、データが移行されない |

最もよく依存される前提は **Vault、PlaceholderAPI、ProtocolLib、LuckPerms** です。多くのプラグインがこれらを必須または任意の前提として使うので、更新の前に存在とバージョンが要件を満たすことを確認してください。

### 3.2 流れ

1. **停止する**（またはホットリロードの能力の限界を明確に受け入れる。3.5 を参照）。
2. `plugins/<プラグイン名>/` ディレクトリを**バックアップする**。データベースを使うプラグインはデータベースも一緒にバックアップします。
3. **旧 jar を改名して控える**。バージョン番号を付ける。
4. **新しい jar を配置する**。
5. **起動し、コンソールを見る**。
6. **`/plugins` で状態を確認する**（赤はプラグインが認識されたが読み込みに失敗した状態）。さらに**プラグイン自身のコマンドを試して**、機能が本当に使えることを確認します。

```powershell
# Windows
Set-Location C:\mcserver\survival\plugins
Rename-Item MyPlugin-1.0.0.jar MyPlugin-1.0.0.jar.bak
Copy-Item "$env:USERPROFILE\Downloads\MyPlugin-1.1.0.jar" .
```

```bash
# Linux
cd /opt/mcserver/survival/plugins
mv MyPlugin-1.0.0.jar MyPlugin-1.0.0.jar.bak
cp ~/downloads/MyPlugin-1.1.0.jar .
```

```text
/plugins
```

:::note 赤い項目はまずコンソールを見る
読み込み失敗の原因は必ずコンソールと `logs/latest.log` に出力されています。**ログを開いてプラグイン名で検索する**ほうが、グループで「プラグインが赤くなった」と説明するよりずっと速いです。
:::

### 3.3 設定の移行

| 状況 | 推奨するやり方 |
| --- | --- |
| 設定項目が増えただけ | プラグインに既定値を生成させればよい。通常は介入不要 |
| 設定キーが改名・再構成された | **旧設定のコピーを残し**、更新ログと照合して 1 項目ずつ移す |
| 設定が複数ファイルに分割された | 同様に旧ファイルを残し、公式の説明に従って移行する |
| データの移行が必要（データベース、プレイヤーデータ） | 公式の移行手順に従う。**先にデータベースをバックアップする** |

:::tip プラグインにまず既定の設定を再生成させる
2 つの YAML を手でマージするより確実な順序は、**まず新バージョンに完全な既定設定を生成させ**、それから旧設定と照らして自分の値を 1 項目ずつ埋め戻すことです。手でのマージはインデント、重複キー、型（文字列と数値）で間違えやすく、YAML のエラーメッセージはたいてい分かりにくいです。
:::

### 3.4 依存を優先：まず前提を更新する

**まず前提を更新し、それからそれに依存するプラグインを更新します。** 逆にすると、「前提のインターフェースは変わったのに、上位のプラグインが古いインターフェースを呼んでいる」という `NoSuchMethodError` / `NoClassDefFoundError` が起きます。

同様に、あるプラグインが複数のプラグインの前提になっている場合、その 1 回の更新がいくつものプラグインに同時に影響し得ます。更新後は関連する機能を一通り触ってください。

### 3.5 プラグインマネージャー：できること、できないこと

PlugManX、ServerUtils のような「プラグインを管理するプラグイン」は、サーバーの稼働中に他のプラグインを読み込み、外し、再読み込みできます。その**能力の境界**は明確です。

| 状況 | ホットリロードで解決できるか |
| --- | --- |
| 設定を変えただけ | プラグイン自身の `reload` で足りる |
| 問題のあるプラグインを一時的に無効化 | できる。これがホットリロードの最も価値ある使い方 |
| プラグインのバージョンを変える（jar の差し替え） | 勧めない。停止して差し替えるべき |
| プラグインがコマンド、権限、リスナー、レシピ、ワールド生成器を登録している | 外した後に残留が残りやすく、再読み込みで壊れやすい |
| プラグインがデータベース接続、スレッドプール、大量の静的キャッシュを保持している | 外しても資源が解放されないことが多い |
| 同じプラグインを繰り返し読み込み・解除する | クラスローダーが回収されず、メモリが上がり続ける |
| MOD 側 | プラグインマネージャーは MOD を扱えない |
| サーバーのバニラの `/reload` | 勧めない。プラグインの状態が乱れやすい |

:::warn 本番サーバーをホットリロードだけに頼らない
ホットリロードは「プラグインを一時的に止めて問題が消えるか見る」ことと、設定の素早い試行に向きます。**正式なバージョン更新や依存の変更は、停止して再起動する流れを通すべきです。** より詳しい切り分けの流れは [プラグイン管理と切り分け](/tutorials/java/plugin-manage) を参照。
:::

### 3.6 公式の配布元からのみダウンロードする

:::warn 非公式の転載 jar を使わない
アグリゲータのダウンロードサイト、ネットドライブ、グループのファイルにある「日本語化版」「クラック版」「統合版」のプラグインは、再パッケージされている可能性が高いです。**ファイル名とバージョン番号が同じでも、中身が違うことがあります。**
公式の配布ページを優先してください。SpigotMC、Modrinth、Hangar、作者自身の GitHub Releases。ハッシュが提供されていればハッシュを照合し、有料プラグインは公式の購入ページを通してください。
:::

## 4. MCDR の更新

MCDR（MCDReforged）はサーバーコアの外側を包むマネージャーで、Python 3 で書かれています。これを更新しても**あなたのサーバーコアとワールドには触りません**。リスクは主に**それ自身の設定と Python プラグイン**にあります。基本の概念は [MCDR サーバーマネージャー](/tutorials/java/mcdr) を参照してください。

### 4.1 導入方法：pip を使い、ソースの zip を使わない

MCDR は PyPI に公開されており、公式ドキュメントが示す導入方法は pip です。

```bash
# Windows
pip install mcdreforged

# Linux
pip3 install mcdreforged
```

:::warn ソースの zip をダウンロードして動かさない
ネット上の多くのチュートリアルは GitHub からアーカイブを落として展開するよう促しますが、**公式ドキュメントはそれが時代遅れのやり方だと明言しています**。MCDR は 2021 年初頭の v1.0 以降、ソースからのインストールを使っていません。あなたが MCDR の開発者で、何をしているか分かっている場合を除き、pip で導入してください。
:::

### 4.2 Python のバージョン要件

公式ドキュメントが示す対応関係：

| MCDR のバージョン | Python の依存 |
| --- | --- |
| < 2.10 | >= 3.6 |
| >= 2.10 | >= 3.8 |
| >= 2.15 | **>= 3.9** |

MCDR を上げる前に、自分の Python のバージョンが目標のバージョンの要件を満たすことを確認してください。システムの Python が古すぎるなら、先に Python を上げる（または公式ドキュメントが勧める隔離環境の方式に変える）必要があります。

### 4.3 更新のコマンド

**MCDR を動かしているそのインタプリタで更新します**。具体的なコマンドは最初にどう入れたかによります。

```bash
# グローバルの pip（Windows。-U は --upgrade）
pip install mcdreforged -U

# グローバルの pip（Linux）
pip3 install mcdreforged -U

# pipx が管理する隔離環境
pipx upgrade mcdreforged

# 仮想環境：まず有効化してから更新する
# source venv/bin/activate        （POSIX）
# venv\Scripts\Activate.ps1       （Windows PowerShell）
pip install mcdreforged -U
```

バージョンを確認します。出力は `MCDReforged v2.16.0` のような形です。

```bash
mcdreforged -V
```

:::warn 更新したのが MCDR の使っているものとは限らない
システムの Python、仮想環境、pipx の環境が同時に存在すると、`pip install -U` で上がるのが MCDR の実際に使っているものとは限りません。**更新したのに `mcdreforged -V` が古いバージョン番号のままなら、たいていこれが原因です**。まず MCDR がどう起動しているか（どのインタプリタ、どの環境）を確認し、その環境で更新してください。
:::

:::note その他の導入方法
- **pipx**：`pipx upgrade mcdreforged` で更新します。Python の依存を入れるには `pipx inject mcdreforged <パッケージ名>` を使います。
- **Docker**：公式イメージのドキュメントに従ってイメージタグを変えます。具体的な書き方は公式ドキュメントの Docker の章に従ってください。
- **国内ネットワーク**：コマンドに `-i https://pypi.tuna.tsinghua.edu.cn/simple` を足してミラーで高速化できます。これは公式ドキュメントが示しているやり方です。
- **システムのパッケージマネージャー**：公式ドキュメントはこれで MCDR を入れることを**強く勧めていません**。プラグインの依存を管理しにくいからです。
:::

### 4.4 メジャーバージョンを上げる前に移行ガイドを読む

公式ドキュメントには独立した「移行ガイド」の章があり、**0.x から 1.x** と **1.x から 2.x** の 2 部が含まれます。

メジャーバージョンのアップグレードは、設定ファイルの形式（旧 `config.yml` の項目が改名・廃止される）、プラグイン API（旧 API に依存する MCDR プラグインが読み込みに失敗したり挙動がおかしくなったりする）、コマンドとコマンドラインのインターフェース（起動引数、サブコマンドが調整される）を変え得ます。**だから MCDR のアップグレードは、しばしば MCDR プラグインの更新も意味します。** 上げる前に対応する移行ドキュメントを読み、その手順に従ってください。記憶で古いチュートリアルを写さないこと。

### 4.5 アップグレードの前に何をバックアップするか

| 内容 | 場所 |
| --- | --- |
| MCDR 自身の設定 | `config.yml`。**MCDR の作業ディレクトリ**にある |
| MCDR のプラグイン | 既定では `plugins/`。実際は設定項目 `plugin_directories` に従う |
| 権限ファイルとログ | 問題の調査に役立つ。一緒に保管することを勧める |

:::note MCDR は設定項目を自分で補う
公式ドキュメントの説明：起動時に MCDR は `config.yml` を読み込み、**欠けているオプションを設定ファイルの末尾に追記**します。設定ファイルが存在しなければ既定の設定を生成して終了します。したがってアップグレード後に設定へ新しいキーが増えるのは正常です。ただし**だからといって旧設定が正しく移行されたと決めつけないでください**。移行ガイドと更新ログと照合する必要があります。
:::

MCDR には `check_update` という設定項目（既定 `true`）もあり、24 時間ごとに更新を検知します。稼働中は `!!MCDR reload config`（短縮形 `!!MCDR r cfg`）で設定を再読み込みできます。**MCDR のアップグレードの主なリスクは MCDR 自身ではなく、プラグインの互換性です**。

### 4.6 ロールバック

問題が起きたら、MCDR を直前のバージョンに固定できます。

```bash
# まず PyPI の mcdreforged プロジェクトページで、戻す具体的なバージョン番号を確認する
pip install mcdreforged==2.15.0
mcdreforged -V
```

- **バージョン番号は必ず PyPI で確認してください**。記憶で書かないこと。pipx の環境は `pipx install --force mcdreforged==<バージョン>` で上書きインストールできます（具体的な書き方は pipx の公式ドキュメントに従う）。
- アップグレードのときに MCDR プラグインも更新したなら、**プラグインも一緒に戻す**必要があります。新しいプラグインと古い MCDR の組み合わせも同じように壊れます。

## 5. 更新のチェックリスト

| 更新対象 | 更新の前に | 更新後の検証 | ロールバックの方法 |
| --- | --- | --- | --- |
| **サーバーコア** | 完全バックアップ（ワールド + 設定 + プラグイン）。目標バージョンが要求する Java の確認。旧 jar を改名して控える。更新ログを読む | コンソールにエラーがない。`/plugins` が正常。`/version` が正しい。自分で入室して一通り歩く。10〜30 分観察する | 停止して旧 jar に戻す。新バージョンで起動済みなら、**ワールドもバックアップで戻す** |
| **プラグイン** | `plugins/<プラグイン名>/` とデータベースをバックアップ。対応するサーバーのバージョン、Java のバージョン、前提の依存を確認。更新ログの破壊的変更を読む | `/plugins` に赤字がない。コンソールに `NoSuchMethodError` などの異常がない。プラグイン自身のコマンドが使える。関連機能を一通り触る | 停止して旧 `.jar.bak` を元の名前に戻す。設定も旧コピーへ戻す |
| **MOD とローダー** | `mods/` と `config/` をバックアップ。ローダーが目標のゲームバージョンに対応するか確認。各 MOD の目標バージョンを一覧にする | 起動にクラッシュがない。ログに MOD のクラスエラーがない。クライアントが入室でき、MOD の不足を告げられない | 旧ローダーと旧 `mods/` ディレクトリに戻す。クライアントも同期して戻す |
| **MCDR** | 現在のバージョンを記録（`mcdreforged -V`）。`config.yml` とプラグインのディレクトリをバックアップ。メジャーバージョンなら移行ガイドを先に読む | `mcdreforged -V` が新しいバージョンを示す。MCDR が正常に起動しサーバーを立ち上げる。MCDR プラグインが正常に読み込まれる | `pip install mcdreforged==<旧バージョン>`（バージョン番号は PyPI に従う）。MCDR プラグインも同期して戻す |
| **OS のソフトウェアパッケージ** | 現在のバージョンを記録。メンテナンス時間内であることを確認。可能なら先にシステムのスナップショットかイメージを取る | 再起動後にサーバーが自動で起動する。**Java がついでに更新されていないか確認**。ポートとファイアウォールの規則が変わっていない | ディストリビューションのバージョン戻し、またはシステムのスナップショット。必要なら Java のパッケージを固定する（`apt-mark hold` など） |

### 保守のリズムの提案

**毎月 1 回**、コア、プラグイン、MOD、MCDR、システムパッケージを定例で確認する。**セキュリティ関連を優先**（ログイン認証、権限、アンチチートに修正が出たらできるだけ早く追随する）。**不要なら更新しない**——安定して動いていてセキュリティ上の問題がないバージョンは触らなくてよく、更新の利益がリスクを上回る必要があります。更新のたびに**記録を残す**（いつ、どのバージョンからどのバージョンへ、誰が、ロールバックしたか）。次に問題が起きたときに素早くたどれます。
