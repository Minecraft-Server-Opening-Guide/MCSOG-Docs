攻撃を受けたその瞬間、マシンの上には 2 種類のものが同時に存在します。**記録できる証拠**と、**数分後には永久に消える状態**です。この記事が扱うのは後者、再起動・再インストール・何かの BAN の前に、まず現場を固定することです。予防的な内容は [ネットワークセキュリティの基礎](/tutorials/ops/network-security) と [よくあるネットワーク攻撃と防御](/tutorials/ops/attack-defense) を参照してください。

:::warn 本記事は法律の助言の代わりにはならない
フォレンジックのコマンド、ログの保存要件、個人情報の取り扱いの規則は**OS、ディストリビューション、サービス提供者、司法管轄によって異なります**。環境で変わる箇所は本文で明記します。プレイヤーの個人データに関わる場合や、法的手続きに入る可能性がある場合は、**専門家に相談し、現地の法律とデータセンターの方針に従ってください**。
:::

## 1. 「まずフォレンジック」が第一条の鉄則である理由

### 1.1 証拠は消える

多くの人が攻撃を受けたときに最初にやるのは**再起動**か**再インストール**です。これは最悪の選択です。**再起動はネットワーク層の証拠をほぼすべて破壊します**。

| 証拠 | 場所 | 消え方 | おおよその寿命 |
| --- | --- | --- | --- |
| プロセス、開いているソケット | メモリ | プロセスの終了、再起動 | 秒〜分 |
| 現在の接続（established） | カーネルのソケットテーブル | 接続の終了 | 秒 |
| conntrack の接続追跡テーブル | カーネルのメモリ | エントリのタイムアウト（設定による） | 秒〜時間 |
| ARP / 近隣テーブル | カーネルのメモリ | エントリの失効 | 分 |
| NIC の送受信とドロップのカウンタ | カーネルのカウンタ | **再起動か NIC のリセットで 0 に戻る** | 再起動で失う |
| ファイアウォール規則のヒット数 | カーネルの netfilter | **再起動で 0。`iptables -Z` でも 0** | 再起動で失う |
| キャプチャファイル（pcap） | ディスク | 削除か、ディスク満杯による上書きのみ | 永続 |
| システムログ / サービスログ | ディスク | ローテーション後の圧縮、削除 | 日〜週 |
| アプリケーションログ（`logs/latest.log`） | ディスク | ローテーション、新しいログによる上書き | 日 |
| 設定、スクリプト、定期タスク | ディスク | 「ついでに直して」上書きされる | 永続だが改変されやすい |
| クラッシュレポート `crash-reports/` | ディスク | 通常は自動削除されない | 永続 |
| 事業者の流量グラフ / 攻撃レポート | 事業者側 | 事業者の保存期間で消える | 日〜月 |

**重要な区別**：**揮発性の証拠（volatile）**はメモリにあり、再起動で消えます。**永続的な証拠（persistent）**はディスクにありますが、ローテーション、上書き、誤った変更で失われます。順序は常に**まず揮発性のものを固定し、それから永続的なものを集める**です。

### 1.2 再起動が壊すもの

1 回の再起動は同時に次を壊します。現在のすべての TCP 接続と送信元 IP の分布（単点か分散かを判断する主な材料）、conntrack テーブル（誰と誰が通信し、パケットがどの規則で処理されたか）、NIC カウンタの履歴累積値とドロップ数、**ファイアウォール規則のヒット数**（「自分の規則がどれだけ止めたか」の唯一の確かな証拠）、メモリ上の不審なプロセス（攻撃がすでにホストに落ちていれば、再起動は相手の掃除を手伝うことになる）、そして未書き込みのログバッファです。

:::warn 「再起動しない」は「対応しない」ではない
現場を保ちながら緩和はできます。ファイアウォール規則の追加、速度制限、流量を高防御へ切り替える、一時的な BAN。**ただし変更はすべて記録してください**（第 3 節を参照）。変更そのものが証拠を変えるからです。
:::

### 1.3 正しい順序

```text
1. 再起動しない、再インストールしない、電源を切らない（ホストが完全に制御されたと確認した場合を除く）
2. まずパケットキャプチャ（tcpdump）—— ネットワークの証拠が最も揮発しやすい
3. カーネルの状態を取る（ss、conntrack、ip -s link、ファイアウォールのカウンタ）
4. プロセスとサービスの状態を取る（ps、systemctl、journalctl）
5. ログと設定をコピーする（コピーを操作し、原本は触らない）
6. ハッシュを計算し、イベントログを書き、タイムラインを記録する（タイムゾーンを統一）
7. それからようやく緩和と強化を始める
```

## 2. 何を取るか（正しいコマンド付き）

:::warn インターフェース名とパスはシステムで異なる
以下では `eth0` を例の NIC 名として使います。**実際には `ens3`、`enp1s0`、`eno1`、`bond0` などかもしれません**。`ip -br link` か `ip addr` で確認してください。同様に、ログのディレクトリ、サービス名、ファイアウォールのツールはディストリビューションで異なります。
:::

```bash
ip -br link
# 出力例（あなたのものは違う）：
# lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
# eth0             UP             aa:bb:cc:dd:ee:ff <BROADCAST,MULTICAST,UP,LOWER_UP>
```

### 2.1 パケットキャプチャ：tcpdump

```bash
# Java 版（TCP 25565）
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap 'port 25565'

# 統合版 / Geyser（UDP 19132）
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap 'udp port 19132'
```

| 引数 | 意味 | なぜそうしなければならないか |
| --- | --- | --- |
| `-i eth0` | NIC を指定する | **実際のインターフェース名に変える**。指定しないと tcpdump が自分で選び、間違えることがある |
| `-nn` | 名前解決をしない（IP とポートを数字のまま） | 逆引き DNS は**キャプチャを遅くし、パケットを取りこぼす**。さらに深刻なのは、攻撃流量があなたに**外部へ大量の DNS クエリを出させ、「いま攻撃を受けている」と相手に知らせる**こと |
| `-s 0` | パケット全体を取得し、切り詰めない | 既定では先頭の数バイトしか取らず、**ペイロードが切り詰められるとプロトコルの中身を分析できない**。`0` は完全な長さを意味する |
| `-w ファイル` | pcap に書き出す | 下の説明を参照 |
| `'port 25565'` | BPF のフィルタ式 | 単一引用符で shell の解釈を防ぐ。`port` は TCP と UDP の両方にマッチする |

**なぜ端末に表示せずファイルに書く必要があるか**：攻撃中はパケットのレートが毎秒数十万に達することがあり、解析結果を端末へ出すと tcpdump が**自分でボトルネックになり大量に取りこぼし**、しかも画面が流れて端末が意味を失います。`-w` はバイナリを直接書くので、コストがはるかに小さい。**ディスクも忘れないこと**：`-s 0` と高速な流量では数分で数十 GB を書き出します。まず空き容量を見て、`-c` でパケット数を制限するか、`-C` でサイズごとにローテーションし `-W` でファイル数を制限します。

```bash
# 200000 パケットだけ取って止める
sudo tcpdump -i eth0 -nn -s 0 -c 200000 -w /var/log/incident-cap.pcap 'port 25565'

# 1 ファイル 100 MB、最大 20 個（合計約 2 GB）で自動ローテーション
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap -C 100 -W 20 'port 25565'

df -h /var/log    # まず空き容量を見る
```

:::tip パケットが取れないとき
**権限**：キャプチャには `CAP_NET_RAW` が必要で、`sudo` を使います（`setcap` はリスク面を広げるので勧めません）。**インターフェースの選択ミス**：コンテナ内の NIC はホストと違い（`docker0`、`veth*`、`br-*` などが一般的）、ホストの `eth0` ではすべての流量が見えないことがあります。**流量がすでに上流でクリーニングされている**：事業者のクリーニング後、あなたの NIC に届くのは正常な流量だけかもしれません。これこそ事業者へ流量データを求める理由です（2.6 を参照）。**クラウドのセキュリティグループ**：一部のプラットフォームでは、流量がインスタンスに届く前に捨てられ、ローカルでは取れません。
:::

取ったらまず粗い統計を出します（`tcpdump -r` で 1 パケットずつ画面に流さないこと）。より細かいプロトコル分析は**オフライン**で別のマシンの Wireshark / `tshark` で行い、**本番機で取りながら分析しないでください**。

```bash
# パケット数だけ数える
sudo tcpdump -nn -r /var/log/incident-2026-10-04-1200.pcap -q | wc -l

# 送信元 IP の出現回数トップ 20
sudo tcpdump -nn -r /var/log/incident-2026-10-04-1200.pcap -q 2>/dev/null \
  | awk '{print $3}' | cut -d. -f1-4 | sort | uniq -c | sort -rn | head -20
```

### 2.2 ファイアウォールの状態とカウンタ

```bash
sudo iptables -L -v -n
sudo iptables -t nat -L -v -n

sudo nft list ruleset
sudo nft list counters
```

- `-L` は規則を一覧し、`-v` は**各規則のパケット数とバイト数**を表示し、`-n` は名前解決をしません（理由は `-nn` と同じ）。`-t nat` は NAT テーブル（DNAT/SNAT/ポート転送）で、「流量がどこへ転送されたか」を調べるには必ず見ます。
- **カウンタの意味**：`DROP`/`REJECT` 規則のカウンタは**規則がどれだけの流量を止めたかを直接証明**し、振り返りと事業者への説明で最も強い数字です。**再起動か `iptables -Z` で 0 に戻る**ので、対応の早い段階で取る必要があります。
- `nft list ruleset` は規則セット全体（集合とカウンタを含む）を出力し、`nft list counters` は名前付きの counter オブジェクトだけを一覧します。**独立したカウンタを持つのは、counter オブジェクトを明示的に定義した規則だけ**で、通常の規則のインラインカウンタは `counter packets N bytes M` として `list ruleset` に現れます。**nft のサブコマンドと出力形式はバージョンで変わるため、`man nft` とディストリビューションのドキュメントに従ってください。**

```bash
sudo iptables -L -v -n        > /root/incident/fw-iptables.txt 2>&1
sudo iptables -t nat -L -v -n > /root/incident/fw-iptables-nat.txt 2>&1
sudo nft list ruleset         > /root/incident/fw-nft.txt 2>&1
```

### 2.3 接続テーブル

```bash
# 確立済みの Java 接続
ss -tan state established '( sport = :25565 )'

# UDP ソケット（統合版には「接続」の概念がないので、待ち受けと送受信キューを見る）
ss -uan

# ソケット総量の要約（各状態のカウント。大量の半開接続かを判断する）
ss -s

# SYN-RECV を含む。接続洪水の痕跡が見える
ss -tan '( dport = :25565 or sport = :25565 )'

# 送信元 IP ごとの接続数を集計し、「単点集中」の送信元を探す
ss -tan state established '( sport = :25565 )' | awk 'NR>1 {print $5}' \
  | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
```

`ss -tan` の `t`=TCP、`a`=すべての状態、`n`=数値形式（同じく DNS 解決を避ける）。

**conntrack**（`conntrack-tools` が必要で、カーネルで `nf_conntrack` が有効であること）：

```bash
sudo conntrack -L    # 現在追跡しているすべての接続を出力する
sudo conntrack -S    # CPU ごとのエラーカウント
sudo conntrack -C    # 現在のエントリ数（まずこれを見て、-L するか決める）
```

- `conntrack -L` は**接続数が非常に多いと遅くなったり固まったりする**ので、まず `conntrack -C` で規模を見ます。
- `conntrack -S` は `insert_failed`、`drop`、`early_drop`、`error` などを出力します。**`insert_failed` や `early_drop` が増えているなら接続追跡テーブルが満杯**で、そのとき新しい接続は捨てられます。**これ自体が悪用可能なサービス拒否**であり、「帯域は飽和していないのにプレイヤーが接続できない」の重要な手がかりです。

```bash
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

:::warn conntrack がそもそも存在しないことがある
次の場合は conntrack が見えません。**カーネルが `nf_conntrack` モジュールを読み込んでいない**、**純粋な nftables で接続追跡を有効にしていない**、**`conntrack-tools` が未インストール**、**コンテナの名前空間からホストのテーブルが見えない**、**一部のクラウドのカスタムカーネルがこの機能を削っている**。**あなたの操作ミスではありません**。`ss`、`ip -s link`、ファイアウォールのカウンタに切り替えてください。逆に、一部の大容量メモリのホストでは既定の `nf_conntrack_max` が非常に高く、**エントリのタイムアウトもディストリビューションと設定で異なるので、他所の数値をそのまま写さないこと**。
:::

### 2.4 NIC のカウンタとレート

```bash
ip -s link show eth0
cat /proc/net/dev
```

`ip -s link` の `RX`/`TX` の段には **bytes / packets / errors / dropped / overrun / mcast** が出ます。とくに **`dropped` と `overrun` が鍵**です。これらは**流量が NIC かカーネルの処理能力を超えている**ことを示し、帯域が飽和していなくてもすでにパケットを落としています。`cat /proc/net/dev` はすべてのインターフェースの同じカウンタを出すので、全体のスナップショットに向きます（**累積値で、再起動で 0 に戻る。2 回のサンプリングの差だけが意味を持つ**）。

```bash
# sysstat が入っているとき、連続サンプリングでレートを観察する（1 秒ごとに 5 回）
sar -n DEV 1 5
```

:::note sar の 2 つの前提
1. **`sysstat` がインストールされていること**（Debian/Ubuntu：`sudo apt install sysstat`、RHEL 系：`sudo dnf install sysstat`）。
2. **履歴データの収集が有効になっていること**（通常は sysstat の systemd タイマーか cron が集めます）。**一度も有効にしていなければ、`sar` は今からしか集められず、攻撃が起きたときの履歴レートは見られません**。これこそ普段から監視を有効にすべき理由です。間隔引数付きの `sar -n DEV 1 5` は**リアルタイムの収集**で、履歴データの有効化には左右されません。
:::

`iftop` と `nload` は**任意のリアルタイム観察ツール**です。

```bash
sudo iftop -i eth0    # 接続ペアごとにリアルタイムの帯域を表示する
sudo nload eth0       # シンプルな送受信の流量カーブ
```

:::warn リアルタイムツールでは証拠にならない
`iftop` / `nload` は**端末の中のリアルタイム計器**で、閉じれば消え、**フォレンジックの材料にはなりません**。応急時に方向を素早く判断するのには問題ありませんが、**同時に tcpdump でディスクへ落とす必要があります**。この類のツール自体も高いパケットレートでは取りこぼすので、**その数字を正確な統計として扱わないこと**。パッケージ名はディストリビューションで異なり、EPEL のような追加リポジトリを先に有効にする必要があるものもあります。
:::

### 2.5 プロセスとサービスの証拠

```bash
ps auxf
systemctl status <service>
journalctl -u <service> --since "1 hour ago"
```

- `ps auxf`：**プロセスツリー**ですべてのプロセスを一覧し、いるはずのないものがないか見ます。異常なマイナー、`/tmp` から動く実行ファイル、`java` を名乗りながら妙なパスを指すプロセス。**陥落したホストでは `ps` 自体が置き換えられたりハイジャックされたりし得るので、重要な結論は複数の方法で交差検証してください。**
- `systemctl status <service>`：サービスの状態と直近数行のログ。サービス名は導入方法によります。たとえば `minecraft`、`mcserver`、`paper` で、**固定ではありません**。
- `journalctl -u <service> --since "1 hour ago"`：systemd のログ。`--since`/`--until` に対応し、`"1 hour ago"`、`"2026-10-04 12:00:00"`、`"today"` と書けます。**既定ではローカルタイムゾーンで表示され、`--utc` を付けると UTC を強制**します。フォレンジックでは `--utc` に統一することを強く勧めます。ログがすでにローテーションされている場合は、`journalctl -u <service> --since ... --no-pager > ファイル` で書き出すか、`journalctl --file` でアーカイブを読みます。

Minecraft 側：

| パス | 内容 | 注意 |
| --- | --- | --- |
| `logs/latest.log` | 現在のログ | **サーバーの再起動で上書きされる**。再起動の前に必ずコピーする |
| `logs/YYYY-MM-DD-N.log.gz` | 過去のログ（日付 / 連番でローテーション） | 圧縮済みだが有効な証拠 |
| `crash-reports/` | クラッシュレポート | 通常は自動で消えず、スタックと JVM の情報を含む |
| `plugins/*/` | 各プラグイン自身のログとデータベース | **形式はプラグイン次第**。ログイン記録、コマンド監査、BAN 記録などが多い |
| `banned-ips.json` / `banned-players.json` | BAN の名簿 | あなたが行った対応の記録で、タイムラインの一部 |
| `usercache.json` / `ops.json` | プレイヤーと管理者の対応 | UUID と名前を対応づける |

```bash
# 移動ではなくコピー。原本は決して変更しない
sudo cp -a /srv/minecraft/logs /root/incident/mc-logs
sudo cp -a /srv/minecraft/crash-reports /root/incident/mc-crash-reports
```

`cp -a` はタイムスタンプと権限を保持し、**これがフォレンジックでは重要**です。`cp -r` は更新時刻を現在時刻に変えてタイムラインを壊します。**アプリケーション層のログはネットワーク層より役に立つことがよくあります**。ネットワーク層は「4 万の接続があった」としか言えませんが、アプリケーション層は「あるアカウントが 3 分間に 900 回ログインを試した」と言えます。権限グループ、ログイン、経済、アンチチートのプラグインは通常記録を残しており、**「誰が、何をしたか」を特定する主要な情報源**です。具体的な位置と形式は各プラグインのドキュメントを確認してください。

### 2.6 クラウド / データセンター側の証拠

**あなたが見る流量は、すべての流量ではありません。** 事業者はより上流にいて、あなたのインスタンスが**捨てられる前**の受信流量（セキュリティグループやネットワーク ACL で捨てられた流量はあなたのマシンではまったく見えません）、**攻撃の総帯域とパケットレート**（pps/Mbps）とクリーニングの発動有無、攻撃の種類の判断と送信元の分布、そしてプラットフォーム側のフローログ（flow logs）の能力を見られます。**提供の有無、課金の有無、保存期間は事業者ごとに大きく違うので、事業者のドキュメントに従ってください**。

**やるべきこと：すぐにチケットを開く**。攻撃を受けていること、流量の詳細と攻撃レポートの提供を求め、高防御 IP への切り替えやクリーニングの有効化が必要かを尋ねます。**「攻撃された」とだけ書かないでください**。具体的な内容は第 5 節を参照。

## 3. 証拠を正しく保全する

### 3.1 すべての証拠のハッシュを取る

```bash
cd /root/incident
sha256sum incident-*.pcap > incident.sha256
```

**ハッシュの役割は「自分が収集した後に誰も改変していない」ことを証明すること**です。

- **ハッシュファイルはハッシュ対象と別に保存する**（別のディレクトリ、別のディスク、できれば別の場所にもう 1 部）。同じディレクトリに置くと、ファイルを変更できる人はハッシュも変更でき、証明力がゼロになります。
- **検証**：`sha256sum -c incident.sha256`。**ハッシュファイルには相対パスか絶対パスが記録されるので、場所を移すと検証は失敗します**。これはファイルの破損ではなく、パスが変わっただけです。
- **pcap だけでなく、すべての証拠に対して行う**：

```bash
find /root/incident -type f -print0 | sort -z | xargs -0 sha256sum > /root/incident.sha256
```

`find -print0` と `xargs -0` は空白を含むファイル名を正しく扱うため、`sort -z` は順序を安定させて比較しやすくするためです。**ハッシュファイルは証拠のディレクトリの外に書き**、さらにオフライン媒体にもう 1 部コピーします。

### 3.2 原本は決して触らない

- **分析はコピーだけで行う**。`tcpdump -r` は読み取り専用で安全です。「修復」「変換」「結合」はすべてコピーに対して行います。
- ディスク全体のフォレンジックでは、標準的なやり方は `dd` でイメージを取り、直ちにイメージのハッシュを計算することです。

```bash
# 注意：出力先の容量は元のデバイスより大きい必要がある。この操作は出力先を完全に上書きする
sudo dd if=/dev/sda of=/mnt/evidence/sda.img bs=4M conv=noerror,sync status=progress
sha256sum /mnt/evidence/sda.img > /mnt/evidence/sda.img.sha256
```

:::warn dd の破壊性
`dd` の `of=` が指すデバイスを**無条件に上書き**します。**実行前に必ず `lsblk` で元と出力先のデバイス名を確認してください。1 文字間違えるとデータが失われます。** 確信が持てないなら実行しないこと。
:::

### 3.3 タイムライン：タイムゾーンを必ず明記する

**これが最も多く、最も深刻な誤りです**。`journalctl` のローカル時刻、事業者の UTC 時刻、プラグインのログの時刻を 1 枚の表に混ぜると、事象の順序が完全に崩れ、逆の結論に至ることすらあります。

1. **UTC で統一して記録**し、文書に「以下の時刻はすべて UTC」と明示する。
2. 同時に**ローカルのタイムゾーンと UTC のオフセット**を記録し、ローカルのログと照合できるようにする。
3. ISO 8601 形式を使い、`10/04/2026` のような曖昧な書き方を避ける。

```bash
date -u +%FT%TZ      # 例：2026-10-04T09:32:21Z
date +%FT%T%:z       # 例：2026-10-04T17:32:21+08:00
timedatectl          # システムのタイムゾーンと NTP 同期の状態を見る
```

`date -u +%FT%TZ` は `Z` の接尾辞が付いた UTC 時刻を出力します。**`Z` は UTC を意味し、タイムゾーンの略号ではありません**（`CST` と書かないこと。少なくとも 3 つの異なるタイムゾーンに対応します）。

:::warn 時計自体が間違っていることがある
ホストの時計が不正確、または NTP が同期していないと、**すべてのログのタイムスタンプが信用できません**。`timedatectl` で `System clock synchronized` が `yes` かを確認し、現在のオフセットを記録します。**ずれを発見したらイベントログに明記**してください。さもないと機器をまたいだ時刻合わせで誤った結論に至ります。
:::

### 3.4 イベントログを書く（対応しながら記録する）

| 記録項目 | 説明 |
| --- | --- |
| 発見の時刻 | 誰が、どうやって発見したか（プレイヤーの報告、監視のアラート、自分で見た） |
| 現象 | 具体的な現れ方。ラグ、切断、接続不能、帯域の飽和 |
| 各操作の時刻 | **タイムゾーンを含む**。「自分が何をしたか」を明記 |
| 自分が行った変更 | 追加したファイアウォール規則、速度制限、BAN した IP、切り替えた解決 |
| 証拠のファイル名 | 各ファイルが何で、いつ取ったか |
| 連絡した相手 | 事業者のチケット番号、時刻、相手の返答の要点 |
| 現在の状態 | 攻撃がまだ続いているか |

:::warn 緩和措置そのものが証拠を変える
止血のために足したファイアウォール規則は、**その後に取れる流量の特徴を変えます**（本来届いていたパケットが捨てられ、取れなくなる）。これは避けられませんが、**必ず記録してください**。**規則を追加した時点**を書き（以降の分析はそれを境にする）、できれば**規則を変える前に 1 回パケットを取る**（30 秒でもよい）、規則の**完全な内容**を記録し、「速度制限を足した」とだけ書かないこと。さもないと「なぜ 14:05 以降に攻撃流量が突然消えたのか」を後から説明できません。
:::

### 3.5 ファイルの権限とデータ保護

```bash
chmod 700 /root/incident
chmod 600 /root/incident/*
chmod 600 /root/incident.sha256
```

- 証拠には**プレイヤーの IP、アカウント名、チャットの内容、ログインの資格情報かもしれないもの**が含まれ、**既定で機密データとして扱うべき**です。ディレクトリは `700`（所有者だけが入れる）、ファイルは `600`（所有者だけが読み書き）。
- 「見やすいから」という理由で証拠を Web ディレクトリに置いたり `chmod 777` にしたり**しないでください**。
- **転送**は `scp` / `rsync -e ssh`（SSH の暗号化経路）を使い、平文の FTP やメールの添付を使わないこと。
- **データ保護**：プレイヤーの個人データに関わる場合は**適用される法規に注意**（EU の GDPR、各地の個人情報保護法など）。多くの管轄では IP アドレスも個人情報と見なされます。原則は**必要な範囲だけを集め、用途を限定し（セキュリティインシデントの調査）、アクセスを制限し、期限が来たら削除する**。**具体的な義務は国・地域で異なるため、現地の法律とあなたのプライバシーポリシーに従ってください。**
- 証拠（とくにプレイヤーのチャットと IP を含む pcap）をフォーラムやグループに「鑑定をお願いします」と**公開しないでください**。

## 4. 帰属：何が分かり、何が分からないか

**無実の第三者を攻撃者と見なすことは、実際の害を生み、あなた自身の申立ても信用を失わせます。**

### 4.1 送信元 IP を偽造した UDP 流量：ほぼ帰属できない

UDP は**コネクションレス**のプロトコルで、**送信元 IP のフィールドは自由に偽造でき**、偽造したパケットは何の応答も受け取らずに送れます。したがって：

- **UDP 洪水（ほとんどの UDP 反射増幅を含む）の送信元 IP は偽造されており、通常はまったく帰属できません。**
- ある IP が UDP 洪水で最も多く現れたからといって、それを通報したり BAN したり公開の場で非難したり**しないでください**。**その IP はなりすまされた被害者である可能性が極めて高い**です。
- 個別 IP の BAN は偽造流量に**意味がありません**（偽造値を変えるだけ）。正しいやり方は**上流での流量クリーニング、速度制限、プロトコルの特徴によるフィルタ**です。

残る手がかりは少数あります。攻撃が特定のサービス（DNS、NTP、memcached、CLDAP など）を使っていると分かれば、**そのサーバーは「悪用されたオープンサーバー」**であり攻撃者ではありません。送信元 IP と送信元ポートに安定した規則性があれば調査の価値はありますが、**結論は慎重に**。流量経路上の中間機器（事業者側）はより多くの情報を見られます。

### 4.2 TCP 攻撃：送信元 IP は通常本物だが、それでも「攻撃者」ではない

TCP は**3 ウェイハンドシェイク**が必要で、ハンドシェイクを完了するには返答を受け取れなければなりません。したがって **Minecraft に対する TCP 攻撃**——ボットの大量入室（bot join）、接続洪水、状態クエリ（status ping）の連打——は**送信元 IP が通常は本物**で、調査できます。**ただし「本物の IP」は「攻撃者本人」ではありません**。**侵入された第三者のホスト**（バックドアを仕込まれた VPS、乗っ取られた家庭用ルーター）、**プロキシ / VPN / 空港の出口**、**Tor の出口ノード**、**共有 NAT の後ろの誰か**かもしれません。正しい表現は**「その IP が攻撃流量に参加した」であり、「その IP の所有者が攻撃者だ」ではありません**。この区別は通報のときに非常に重要です。

### 4.3 反射 / 増幅：源は無実の第三者

反射増幅攻撃の**被害者は 2 人**です。あなたと、**悪用されたオープンサーバー**です。それらが悪用されるのは、管理者が**DNS、NTP、memcached などの UDP サービスを誤ってインターネットに開放している**からです。

- **反射源を攻撃者として報告しないでください**。**「ある IP 上のサービスがオープンな反射源で、悪用されている」**と報告します。
- これらの IP の `abuse@` へ通知を送るのは**役に立ちます**（管理者が直せば反射面が消えます）が、**口調は「あなたのサービスが悪用されている」であり、「あなたが攻撃している」ではありません**。
- 判断の根拠：**応答パケットが要求パケットよりはるかに大きく**（増幅率）、**送信元がよく知られた UDP サービスのポート**であること。

### 4.4 「単点集中」と「分散」を区別する

| 観察される特徴 | より可能性の高い性質 | できること |
| --- | --- | --- |
| **単一または少数の IP が接続の大半を占める** | 単点攻撃、侵入されたホスト、試験的なスキャン | その IP を調べる価値がある。一時的な BAN で止血できる |
| **数千数万の IP が、それぞれ少量だけ送る** | 分散したボットネット、または偽造された送信元 | IP の BAN は無効。上流でのクリーニングと速度制限に頼る |
| **TCP のハンドシェイクが完了し、接続数が安定して増える** | 本物の送信元（bot 入室系） | IP の調査 + 上流の防御 + 入室の速度制限 |
| **大量の SYN があるが、その後のハンドシェイクがない** | SYN 洪水（送信元は偽造の可能性） | SYN cookies の有効化、上流でのクリーニング |
| **UDP の大きなパケットが押し寄せ、送信元ポートが固定** | 反射増幅 | プロトコル / ポートでフィルタ、上流でのクリーニング。**送信元 IP を通報しない** |
| **流量は多くないのにサービスが極端に遅い** | アプリケーション層の攻撃か資源の枯渇 | アプリケーションログ、接続追跡テーブル、ホストの資源を見る |

**核心の判断**：**少数の IP に集中 = 追う価値がある。膨大な IP に分散 = 追えないか追い切れないので、防御へ切り替える。**

### 4.5 IP を調べた後に何をするか

```bash
whois 203.0.113.10
```

`whois` の出力には通常、**網段の帰属（netname/descr）、所属する組織、国、そして `abuse` の連絡先メール**が含まれます。注意：

- **`whois` のクライアントは必ずしも入っていません**（Debian/Ubuntu：`sudo apt install whois`、RHEL 系：`sudo dnf install whois`）。
- **RIR（地域インターネットレジストリ）ごとに出力形式が違い**、`abuse-c`、`OrgAbuseEmail`、`abuse-mailbox` などのフィールド名もまちまちです。**人が読むこと。スクリプトで無理にマッチさせないでください。**
- より推奨されるのは **RDAP**（Registration Data Access Protocol）で、WHOIS の**現代的な HTTP の代替**です。構造化された JSON を返し、自動的な問い合わせに対応します。IANA がブートストラップサービスを提供しており（`https://rdap.org/ip/<IP>` は該当する RIR へリダイレクトします）、**各 RIR の具体的な URL とフィールドは各 RIR のドキュメントに従ってください**。

**ASN の帰属**：その IP がどの自律システム（AS）に属し、どの事業者 / データセンターのものかを特定すると、「あるクラウドの VPS」なのか「ある国の住宅回線」なのかの判断に役立ちます。調べ方には各 RIR の RDAP サービス、`whois -h whois.radb.net` などがありますが、**ツールとデータソースは多く、網羅性にも差がある**ので、結論を単一の情報源だけに頼らないでください。

**abuse の連絡先**：WHOIS/RDAP の **`abuse@` メール**（または abuse のフォーム）が**正しい通報の入口**です。**IP を所有するデータセンター / ホスティング事業者の abuse 部門へ送るのであって、ある無作為なプレイヤーの回線 ISP へ送るのではありません**。データセンターは自分の網段内のマシンに対して実際の対応能力（サービスの停止）を持ちますが、ISP は侵入された家庭用ルーター 1 台には通常とても鈍い対応しかしません。**証拠を添えてください**：タイムゾーン付きの時間枠、プロトコルとポート、送信元 IP の一覧、パケット数とレート、pcap のハッシュ値。**証拠のない通報は通常無視されます**。複数の網段にまたがる場合は**それぞれに通報**し、グループで公開して名指ししないこと。

### 4.6 法律と境界

- **規則は国・地域で異なります**。何が犯罪か、どのログを保存するか、自分でデータを取得してよいかは、国ごとに違います。**本記事は法律の助言を構成しません。**
- **推奨する順序**：まず**事業者**へ連絡する（流量をクリーニングでき、上流のデータを見られ、abuse の手続きがある）。深刻で継続する攻撃（恐喝、データ窃取、明確な犯罪行為）は、それから**警察 / サイバー犯罪の通報機関**を検討し、完全な証拠チェーンを保存します。
- **絶対に報復しないでください**。攻撃元へ DDoS を仕掛ける（いわゆる DDoS-back）、相手のホストへ侵入する、「逆にハックし返す」は、**ほぼすべての管轄でそれ自体が違法行為**であり、あなたを被害者から被告に変え、本来正当な立場を破壊します。
- **攻撃者の IP を人肉したり公開で懸賞をかけたりしないでください**。無実の第三者を傷つける可能性があり、嫌がらせやプライバシーの侵害を構成し得ます。

## 5. 報告とエスカレーション

**「攻撃されました、すぐ対応してください」では、ほとんど有効な応答は得られません。** 有効なチケットは、相手が 30 秒で何をすべきか判断できるものです。

```text
件名：[DDoS/攻撃] インスタンス <instance-id>/<ip> が攻撃を受けています。支援と流量データを依頼します

1. 影響を受ける資産
   - グローバル IP：203.0.113.10
   - ポート/プロトコル：25565/TCP（Java 版）、19132/UDP（統合版）
   - インスタンス ID / 注文番号：<記入>

2. 時間枠（タイムゾーンを明記してください）
   - 開始：2026-10-04 09:12 UTC（ローカル時刻 17:12、UTC+8）
   - 終了：継続中 / 09:40 UTC に停止
   - ピークの時間帯：09:20 - 09:35 UTC

3. 攻撃の種類と規模（判明している範囲）
   - 種類の判断：UDP 反射増幅（NTP/DNS の疑い）/ TCP 接続洪水 / ボットの入室
   - 観測されたレート：約 XX Mbps、約 XX kpps（出典：ローカルの ip -s link のカウンタ）
   - NIC のドロップ：RX dropped が 0 から XXXXX へ増加（同期間）

4. 実施済みの緩和
   - 09:25 UTC に iptables の規則で単一 IP の同時接続数を制限
   - 09:30 UTC に送信元 IP を BAN（TCP にのみ有効）
   - 再起動も再インストールもしておらず、現場は保全済み

5. 依頼
   - その時間帯にこのインスタンスへ入った流量の統計と攻撃レポートの提供
   - 流量クリーニングまたは高防御 IP を有効にできるか / 有効になっているかの確認
   - プラットフォーム側のフローログがあれば、その書き出しの支援

6. 証拠ファイル
   - incident-2026-10-04-0915.pcap（sha256: <ハッシュ>）
   - fw-iptables.txt、ss-established.txt、conntrack.txt
   - 必要に応じて完全な証拠パッケージを提供できます
```

| 要素 | なぜ必須か |
| --- | --- |
| **タイムゾーン付きの時間枠** | 相手は膨大なログからあなたの流量を特定する必要があり、時刻が不正確では見つけられない |
| **攻撃の種類と規模** | 「クリーニング」と「調査」のどちらの手続きに回すかを決める |
| **影響を受ける IP / ポート** | どの資産が狙われているかを確認する |
| **まだ継続しているか** | 緊急度を決める |
| **実施済みの緩和** | 双方の重複作業と相互の干渉を避ける |
| **証拠のファイル名** | やり取りを追跡可能にする |

**abuse 通報について**：事業者は通常、自分の網段内のホストが他者を攻撃している件を扱う abuse のメールか通報フォームを持っています。**具体的なアドレスは事業者の公式サイト / WHOIS の記録に従ってください**。**彼らはあなたが見えない流量を見られます**（上流のルーティング、クリーニング機器、プラットフォームのフローログ）。あなたが端の視点を提供し、彼らがネットワークの視点を提供し、両方合わせて初めて完全になります。**プライバシーの制約**：事業者は**プライバシーポリシーや法律の制限により、他の顧客の詳細をあなたに伝えられないことがあります**。これは正常で、**「IP の一覧をくれない」からといって彼らが動いていないと決めつけないでください**。チケット番号と各返信の時刻を追跡し続け、完全なやり取りのタイムラインを作ります（これもイベントログの一部です）。

## 6. インシデントの後

**振り返りのないインシデント対応は、1 回やっただけの無駄です。**

### 6.1 振り返りで答えるべき問い

| 問い | 具体的に何を見るか |
| --- | --- |
| **何が効いたか？** | どのファイアウォール規則がヒットしたか？クリーニングは効いたか？速度制限のしきい値は妥当だったか？ |
| **何が効かなかったか？** | どの措置がまったく効果がなかったか？どれが逆に正常なプレイヤーを傷つけたか？ |
| **どれくらいで復旧したか？** | 発見から緩和までの実際の所要時間。ボトルネックはどこだったか（発見が遅い？判断が遅い？計画がない？） |
| **攻撃者は戻ってきたか？** | 時間枠と送信元の分布を比べ、同じ波か新しい波かを判断する |
| **データの損失はあったか？** | セーブデータは完全か？ロールバックしたか？バックアップは使えたか？ |
| **何が露出したか？** | アカウント、鍵、パネルのパスワードが途中で見られた、または漏れたか？ |

### 6.2 強化の動作

- **速度制限（rate limit）**：接続の頻度、IP あたりの同時接続数、入室のレートに上限を設けます。**最も効果的で最も安い層**です。たとえば `iptables` の `hashlimit`/`connlimit` モジュール、またはサーバープラグイン層の入室の速度制限（**具体的なモジュール名と文法はカーネルとツールチェーンで異なるので、設定の前にモジュールが使えるか確認してください**）。
- **プロキシ / 高防御**：実在の IP を隠します（TCPShield 系のプロキシ、事業者の高防御 IP、CDN の TCP 転送）。**注意**：プロキシはネットワーク層の洪水は防げますが、**アプリケーション層の攻撃（bot 入室、プロトコルの脆弱性）は防げません**。それにはサーバー側の検証と速度制限が必要です。
- **事業者 / データセンターの変更**：事業者がクリーニングを提供しない、または攻撃がその網段の固定の標的を狙う場合、移行は現実的な選択です。**移行の前に、新しい環境に DDoS 防御とクリーニングの能力があるか確認してください。**
- **ホワイトリスト**：知人だけの小規模サーバーは**`white-list=true` をそのまま有効にするのが最も徹底した方案**です。攻撃者は接続できず、入室系の攻撃で資源を消耗させられません。
- **露出面の削減**：不要なポート（RCON、query、パネル）を閉じます。[ネットワークセキュリティの基礎](/tutorials/ops/network-security) を参照。ホスト側の強化は [システムのセキュリティ強化](/tutorials/ops/system-security) を参照。
- **監視とアラート**：**次の攻撃のときは、プレイヤーに怒られて目覚めるのではなく、監視に起こされて目覚めたいものです。** 少なくとも帯域、接続数、TPS、プロセスの生存を監視します。

### 6.3 バックアップは無事か、オフラインか

- **バックアップが本当に復元できることを検証する**。「ファイルがある」だけではだめです。復元演習は [バックアップと復元](/tutorials/java/backup) と [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照。
- **少なくとも 1 部のコピーがオフライン**（または不変 / 読み取り専用）であることを確認する。攻撃がホストの侵入を伴う場合、**オンラインで書き込み可能なバックアップはすでに暗号化されたり削除されたりしているかもしれません**。
- **バックアップの時点を確認する**：攻撃中にロールバックしたなら、**どの時点へ戻すか**、プレイヤーのデータがどれだけ巻き戻るかを明確にします。

### 6.4 資格情報と鍵のローテーション

**露出の可能性が少しでもあれば、漏れたと仮定してすべてローテーションします。**

| 対象 | 動作 |
| --- | --- |
| パネル / 管理画面のアカウントのパスワード | 直ちに変更し、二段階認証があれば有効にする |
| SSH の秘密鍵 | 鍵ペアを作り直し、古い公開鍵を削除し、`authorized_keys` に余分な項目がないか確認する |
| RCON のパスワード | 変更する。`enable-rcon` がインターネットに開放されていないことを確認する |
| データベースのアカウント | パスワードを変更し、`root@%` のような広すぎる権限がないか確認する |
| クラウドの API キー / アクセスキー | コンソールで失効させて作り直し、異常な呼び出しの記録がないか確認する |
| サービスアカウント / トークン（プラグイン、バックアップ、監視） | 1 つずつ失効させて作り直す |
| プレイヤーのアカウント | プラグインのデータベースが漏れたなら、**プレイヤーにパスワード変更を通知する** |

**同時に確認**：`~/.ssh/authorized_keys`、`/etc/passwd` と `/etc/shadow` に新しいアカウントがないか、`crontab -l` と `/etc/cron.*` に不審な定期タスクがないか、systemd に異常な unit がないか。**これらの確認はフォレンジックを終えてから行い、発見した内容を記録してください。**

### 6.5 経験のチェックリスト

```text
[ ] 発見は早かったか？監視のアラートは帯域、接続数、TPS、プロセスの生存をカバーしていたか？
[ ] 文書化した計画はあったか？（誰が判断し、誰が事業者へ連絡し、誰がプレイヤーへ告知するか）
[ ] パケットキャプチャは早かったか？先に再起動して証拠を失っていないか？
[ ] タイムラインのタイムゾーンは統一したか？
[ ] ハッシュを計算し、証拠と別に保存したか？
[ ] 正常なプレイヤーを誤って BAN しなかったか？誤 BAN はどう解除するか？
[ ] 事業者へのチケットに完全なタイムラインと証拠を記録したか？
[ ] バックアップは復元可能と検証済みか、オフラインのコピーはあるか？
[ ] 露出した可能性のある資格情報はすべてローテーションしたか？
[ ] 「今回学んだこと」を頭の中ではなく文書に書いたか？
```

## 7. そのまま使えるフォレンジックスクリプト

次のスクリプトは、第 2 節の**揮発性**の部分をタイムスタンプ付きのディレクトリへ一括で集め、ハッシュを計算して要約を出力します。**使い方：`sudo bash capture-evidence.sh`**（キャプチャと conntrack には root が必要）。**実行前に確認**：インターフェース名（スクリプトはデフォルトルートのインターフェースを自動検出します）、証拠のディレクトリ（既定は `/root/incident`）、キャプチャの時間とパケット数の上限。**スクリプトは読み取り専用の収集だけを行い、設定を変更せず、サービスも再起動しません。**

```bash
#!/usr/bin/env bash
#
# capture-evidence.sh - Minecraft サーバーが攻撃を受けたときの揮発性証拠を収集する
#
# 使い方: sudo bash capture-evidence.sh
#
# 特徴:
#   - 読み取り専用の収集。システム設定を変更せず、サービスも再起動しない
#   - 任意のツールは command -v で判定し、無い場合は記録してスキップする
#   - すべての収集結果の SHA-256 を計算し、要約を独立したファイルに書く
#
# 注意: インターフェース名、サービス名、ログのパスはシステムで異なる。下の変数を必要に応じて変更すること。

set -u

# ---------------- 調整可能なパラメータ ----------------
IFACE="${IFACE:-}"                            # 空欄ならデフォルトルートのインターフェースを自動検出
CAPTURE_SECONDS="${CAPTURE_SECONDS:-60}"      # パケットキャプチャの秒数
CAPTURE_PACKETS="${CAPTURE_PACKETS:-200000}"  # パケット数の上限。ディスク満杯を防ぐ
MC_TCP_PORT="${MC_TCP_PORT:-25565}"           # Java 版のポート
MC_UDP_PORT="${MC_UDP_PORT:-19132}"           # 統合版 / Geyser のポート
MC_SERVICE="${MC_SERVICE:-}"                  # systemd のサービス名。空欄ならスキップ
MC_DIR="${MC_DIR:-}"                          # サーバーのディレクトリ。空欄ならログのコピーをスキップ
BASE_DIR="${BASE_DIR:-/root/incident}"

STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
OUT="${BASE_DIR%/}/incident-${STAMP}"

# ---------------- 事前チェック ----------------
if [ "$(id -u)" -ne 0 ]; then
  echo "エラー: 実行には root 権限（パケットキャプチャと conntrack に必要）。実行は sudo で行ってください。" >&2
  exit 1
fi

mkdir -p "$OUT" || { echo "エラー: 作成失敗 $OUT" >&2; exit 1; }
chmod 700 "$BASE_DIR" 2>/dev/null || true
chmod 700 "$OUT" 2>/dev/null || true

if [ -z "$IFACE" ]; then
  IFACE="$(ip route show default 2>/dev/null | awk '/default/ {print $5; exit}')"
fi
if [ -z "$IFACE" ]; then
  IFACE="eth0"
  echo "警告: 自動検出できなかったため eth0。指定は IFACE=... を使ってください。" >&2
fi

echo "==> 証拠ディレクトリ: $OUT"
echo "==> 収集インターフェース: $IFACE"
echo "==> 収集時刻: $STAMP (UTC)"
echo "==> ディスクの空き容量:"
df -h "$OUT" 2>/dev/null || true

# ---------------- 収集関数 ----------------
capture() {
  _name="$1"
  shift
  echo "  - $_name"
  "$@" > "${OUT}/${_name}.txt" 2>&1 || echo "    (コマンドが失敗しましたが出力は保存済みです)"
}

{
  echo "収集開始(UTC): $(date -u +%FT%TZ)"
  echo "ローカル時刻: $(date +%FT%T%:z)"
  echo "ホスト名: $(hostname)"
  echo "カーネル: $(uname -a)"
  echo "稼働時間: $(uptime)"
  echo "インターフェース: $IFACE"
  echo "Java ポート: $MC_TCP_PORT  UDP ポート: $MC_UDP_PORT"
} > "${OUT}/meta.txt" 2>&1
chmod 600 "${OUT}/meta.txt" 2>/dev/null || true

echo "==> システムとプロセスの状態を収集"
capture ps-auxf ps auxf
capture ss-summary ss -s
capture ss-tcp-all ss -tan
capture ss-udp ss -uan
capture ss-tcp-listen ss -tlnp
capture ip-addr ip -br addr
capture ip-route ip route show
capture ip-neigh ip neigh show
capture uptime uptime
capture date-utc date -u +%FT%TZ
capture timedatectl timedatectl
capture df-h df -h

if command -v ss >/dev/null 2>&1; then
  echo "  - ss-java-established"
  ss -tan state established "( sport = :${MC_TCP_PORT} )" \
    > "${OUT}/ss-java-established.txt" 2>&1 || true
  echo "  - ss-source-ranking"
  ss -tan state established "( sport = :${MC_TCP_PORT} )" 2>/dev/null \
    | awk 'NR>1 {print $5}' | cut -d: -f1 \
    | sort | uniq -c | sort -rn | head -50 \
    > "${OUT}/ss-source-ranking.txt" 2>&1 || true
fi

echo "==> ネットワークインターフェースのカウンタを収集"
if command -v ip >/dev/null 2>&1; then
  echo "  - ip-s-link"
  ip -s link show "$IFACE" > "${OUT}/ip-s-link.txt" 2>&1 || true
fi
[ -r /proc/net/dev ] && capture proc-net-dev cat /proc/net/dev
if command -v sar >/dev/null 2>&1; then
  capture sar-dev sar -n DEV 1 5
else
  echo "sar が未インストールのため、リアルタイムの速度サンプリングをスキップします（sysstat が提供する sar）" > "${OUT}/sar-dev.txt"
fi

echo "==> ファイアウォールの状態とカウンタを収集"
if command -v iptables >/dev/null 2>&1; then
  capture fw-iptables iptables -L -v -n
  capture fw-iptables-nat iptables -t nat -L -v -n
else
  echo "iptables は利用できません" > "${OUT}/fw-iptables.txt"
fi
if command -v nft >/dev/null 2>&1; then
  capture fw-nft nft list ruleset
  capture fw-nft-counters nft list counters
else
  echo "nft は利用できません" > "${OUT}/fw-nft.txt"
fi

echo "==> 接続追跡テーブルを収集（利用可能な場合）"
if command -v conntrack >/dev/null 2>&1; then
  capture conntrack-list conntrack -L
  capture conntrack-stats conntrack -S
  capture conntrack-count conntrack -C
else
  echo "conntrack コマンドが利用できません（要 conntrack-tools、カーネルで nf_conntrack）" \
    > "${OUT}/conntrack-list.txt"
fi
[ -r /proc/sys/net/netfilter/nf_conntrack_count ] \
  && capture conntrack-sysctl cat /proc/sys/net/netfilter/nf_conntrack_count
[ -r /proc/sys/net/netfilter/nf_conntrack_max ] \
  && capture conntrack-max cat /proc/sys/net/netfilter/nf_conntrack_max

echo "==> サービスとログを収集"
if [ -n "$MC_SERVICE" ] && command -v systemctl >/dev/null 2>&1; then
  capture systemctl-status systemctl status "$MC_SERVICE" --no-pager
  if command -v journalctl >/dev/null 2>&1; then
    capture journalctl-1h \
      journalctl -u "$MC_SERVICE" --since "1 hour ago" --utc --no-pager
  fi
else
  echo "未指定の MC_SERVICE のため、サービスの状態収集をスキップします（使い方: MC_SERVICE=minecraft sudo -E bash $0）" \
    > "${OUT}/systemctl-status.txt"
fi

if [ -n "$MC_DIR" ] && [ -d "$MC_DIR" ]; then
  echo "  - サーバーログをコピー（-a でタイムスタンプを保持）"
  [ -d "${MC_DIR}/logs" ] && cp -a "${MC_DIR}/logs" "${OUT}/mc-logs" 2>/dev/null || true
  [ -d "${MC_DIR}/crash-reports" ] \
    && cp -a "${MC_DIR}/crash-reports" "${OUT}/mc-crash-reports" 2>/dev/null || true
else
  echo "未指定の MC_DIR のため、サーバーログのコピーをスキップします（使い方: MC_DIR=/srv/minecraft sudo -E bash $0）" \
    > "${OUT}/mc-logs-note.txt"
fi

echo "==> 短時間のパケットキャプチャ ${CAPTURE_SECONDS}s / 最大 ${CAPTURE_PACKETS} パケット"
if command -v tcpdump >/dev/null 2>&1; then
  PCAP="${OUT}/capture-${STAMP}.pcap"
  timeout "$CAPTURE_SECONDS" tcpdump -i "$IFACE" -nn -s 0 \
    -c "$CAPTURE_PACKETS" -w "$PCAP" \
    "port ${MC_TCP_PORT} or udp port ${MC_UDP_PORT}" 2>"${OUT}/tcpdump.log" || true
  echo "  - パケットキャプチャのファイル: $PCAP"
  echo "  - パケット数の統計:"
  tcpdump -nn -r "$PCAP" -q 2>/dev/null | wc -l | tee "${OUT}/pcap-packet-count.txt" || true
  echo "  - 送信元 IP ランキング(上位 30):"
  tcpdump -nn -r "$PCAP" -q 2>/dev/null | awk '{print $3}' | cut -d. -f1-4 \
    | sort | uniq -c | sort -rn | head -30 > "${OUT}/pcap-source-ranking.txt" || true
else
  echo "tcpdump が未インストールのため、パケットキャプチャができません。速やかにインストールして再収集してください（Debian/Ubuntu: apt install tcpdump）" \
    > "${OUT}/tcpdump.log"
fi

echo "==> ハッシュ計算 SHA-256"
find "$OUT" -type f ! -name 'SHA256SUMS' -print0 \
  | sort -z | xargs -0 sha256sum > "${OUT}/SHA256SUMS" 2>/dev/null || true
# チェックサムを証拠ディレクトリの外にもう 1 部保存し、同時に改変されるのを避ける
cp "${OUT}/SHA256SUMS" "${BASE_DIR%/}/SHA256SUMS-${STAMP}.txt" 2>/dev/null || true
find "$OUT" -type f -exec chmod 600 {} + 2>/dev/null || true

echo
echo "=================== 収集サマリ ==================="
echo "証拠ディレクトリ : $OUT"
echo "開始時刻 : $(head -n 1 "${OUT}/meta.txt" 2>/dev/null)"
echo "インターフェース     : $IFACE"
echo "ファイル数 : $(find "$OUT" -type f | wc -l)"
echo "占有容量 : $(du -sh "$OUT" 2>/dev/null | cut -f1)"
echo "パケットキャプチャのファイル : $(ls -1 "${OUT}"/*.pcap 2>/dev/null | head -n 1)"
echo "チェックサムのファイル : ${BASE_DIR%/}/SHA256SUMS-${STAMP}.txt"
echo "------------------------------------------------"
echo "次のステップ（重要）:"
echo "  1. 再起動しない、再インストールしない。揮発性の証拠は再起動で失われる。"
echo "  2. 直ちに証拠を別のマシンかオフライン媒体へコピーする:"
echo "     scp -r root@<ローカルIP>:$OUT ./evidence/"
echo "  3. イベントログを書き、時刻は UTC で統一し、ローカルのタイムゾーンのオフセットを明記する。"
echo "  4. 事業者にチケットを開き、時間枠と証拠のファイル名を添える（ドキュメント第 5 節を参照）。"
echo "================================================"
```

| 項目 | 説明 |
| --- | --- |
| `set -u` であり `set -e` ではない | 収集スクリプトは**取れるものをできるだけ取り切る**べきで、ある任意のコマンドの失敗で収集全体を中断すべきではない |
| `command -v` によるガード | **任意のツール**（`sar`、`nft`、`conntrack`、`tcpdump`、`systemctl`）にだけ使う。中核のコマンド（`ip`、`ss`）は存在する前提 |
| `timeout` | キャプチャの時間を制限する。**`timeout` は GNU coreutils に属し、ほとんどの Linux ディストリビューションに同梱**。極小のイメージにはないことがある |
| `-c "$CAPTURE_PACKETS"` | パケット数の上限で、攻撃中にディスクが満杯になるのを防ぐ。**時間とパケット数のどちらか先に満たしたほうが効く** |
| `cp -a` | ログ原本の**タイムスタンプと権限**を保持する。これはフォレンジックの基本要件 |
| キャプチャのフィルタ | `'port 25565 or udp port 19132'`：**`port` は TCP/UDP の両方にマッチする**ので、`port 25565` と `udp port 19132` に分けて書き、19132 の TCP まで取り込まないようにする |
| チェックサム | ディレクトリ内に 1 部、**さらに `BASE_DIR` の下にもう 1 部**。厳密さが要る場面では、チェックサムと証拠を別のマシンに保存する |
| サービス名とパス | `MC_SERVICE`、`MC_DIR` は**あなたの導入に合わせて必ず記入**する。スクリプトには推測できない |
| コンテナ環境 | コンテナ内で動かす場合、`IFACE` と `MC_DIR` は**コンテナのネットワーク名前空間内の**インターフェースとパスを指す |

:::warn 収集スクリプトは判断の代わりにならない
スクリプトの役割は**揮発性の証拠をディスクへ落とす**ことですが、**「これは何の攻撃か、通報すべきか、高防御へ切り替えるべきか」の判断は依然として人**が行います。スクリプトを走らせた後は第 1 節から第 6 節の流れを続け、とくに**イベントログを書く**ことと**事業者へ連絡する**ことを忘れないでください。
:::
