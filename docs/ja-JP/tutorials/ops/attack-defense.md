[ネットワークセキュリティの基礎](/tutorials/ops/network-security) が扱うのは「ドアをきちんと閉める」ことです。必要なポートだけを開け、送信元を制限し、SSH を強化する。この記事はもう 1 つの状況を扱います。**ドアは閉まっているが、誰かがトラックでドアに突っ込んできている**。

まず、不愉快ですがはっきり言っておくべき結論を 1 つ。**流量型の攻撃（volumetric）は、サーバーの設定だけでは解決できません**。この記事ではその理由と、その前提で**本当に**できることを説明します。

## 1. 攻撃の種類の分類

OSI の層で大きく分けると、あなたが出会う攻撃はほぼこの 2 類に入ります。

### 1.1 第 3・4 層：流量型とプロトコル型

| 攻撃 | プロトコル | 特徴 | 主な影響 |
| --- | --- | --- | --- |
| **UDP flood** | UDP | 大量の UDP パケットを特定のポートやランダムなポートへ浴びせる | 帯域の飽和、NIC とソフトウェア割り込みの飽和 |
| **SYN flood** | TCP | `SYN` だけを送ってハンドシェイクを完了させず、接続テーブルを埋める | 新規接続の失敗、`backlog` の溢れ |
| **ICMP flood** | ICMP | 大量の `echo request`（ping） | 帯域と割り込みのコスト |
| **反射増幅** | UDP | 送信元 IP を偽造して第三者へ問い合わせを送り、返答をあなたへ浴びせる | 帯域の飽和。**しかも見えるのは無実の第三者** |

**反射増幅（reflection / amplification）**の原理は独立して説明する価値があります。攻撃者は**あなたの IP** を送信元として偽造し、多数の公開サービス（DNS リゾルバ、NTP、memcached、SSDP、CLDAP）へ**ごく小さなリクエスト**を送ります。それらのサーバーは**大きなレスポンス**を「リクエスト元」、つまりあなたへ返します。あなたが受け取る流量 = 攻撃者が送った流量 × 増幅率。

**増幅率（amplification factor）** = レスポンスのバイト数 / リクエストのバイト数。第三者のサービスの設定に依存し、プロトコル、実装、バージョンで大きく異なります。したがって次の表は**桁感の参考**であり、正確な値として扱わないでください。

| 反射源 | よくあるポート | 増幅率の桁 | 説明 |
| --- | --- | --- | --- |
| DNS | UDP `53` | 数十倍程度 | レスポンスの大きさと EDNS の対応による |
| NTP | UDP `123` | 数百倍程度 | 主に歴史的に `monlist` クエリが悪用された。現代の NTP は既定で制限済み |
| memcached | UDP `11211` | 極めて高い（数万倍に達することも） | 影響は極大だが、インターネットに露出した UDP 版 memcached があることが前提 |
| SSDP | UDP `1900` | 数十倍程度 | 家庭用ルーターやスマートデバイスの UPnP サービス |
| CLDAP | UDP `389` | 数十倍程度 | 露出した LDAP サービス |

:::warn 「送信元 IP が偽造されている」とはどういうことか
UDP は**コネクションレス**のプロトコルです。カーネルは UDP パケットを受け取っても「この送信元アドレスが本当に返答を受け取れるか」を先に検証しません。だから攻撃者は送信元 IP を自由に書け、**それをあなたの IP にできます**。

結果が決定的に重要です。**あなたが捕まえたパケットの送信元アドレスは偽物です**。**送信元 IP を偽造した UDP 流量では、追跡も IP の BAN もほぼ無意味**です。BAN すれば無実の第三者を傷つけるだけです。
:::

### 1.2 第 7 層：アプリケーション層の攻撃（Minecraft 特有）

アプリケーション層の攻撃は帯域を狙わず、**あなたのプログラムの処理能力**を狙います。どのリクエストも CPU、メモリ、データベース接続を消費し、攻撃者のコストはあなたのコストよりはるかに低い。

Minecraft 関連のアプリケーション層攻撃は主に 3 類で、本記事では後にそれぞれの節を設けます。

| 種類 | 一言の説明 | 参照 |
| --- | --- | --- |
| **状態クエリ（MOTD ping）の洪水** | サーバーリストを狂ったように更新させ、応答の組み立てを繰り返させる | 第 4 節 |
| **ボットによる負荷テスト（bot / 偽プレイヤー）** | 大量のロボットが入室するか半開の接続を張り、枠と資源を埋める | 第 5 節 |

### 1.3 決定的な違い：攻撃者を特定できるか

これが本記事で最も重要な分かれ目です。

| 流量の種類 | 攻撃者を特定できるか | 理由 |
| --- | --- | --- |
| **送信元 IP を偽造した UDP 流量** | **ほぼできない** | 送信元アドレスが偽物で、返答は攻撃者に届かない |
| **TCP ベースのロボット攻撃** | **通常できる** | TCP 接続を張るには 3 ウェイハンドシェイクが必要で、ハンドシェイクは**相手の IP が実際に到達可能**であることを要求する |
| **ログイン / 入室系の攻撃** | **通常できる** | ハンドシェイクの後に進むには、まず実在の TCP 接続が必要 |

**実践上の意味**：

- UDP の洪水に対して残る手段は「速度制限 + 上流でのクリーニング」だけで、**IP の BAN は期待できません**。
- TCP のロボット洪水には、**接続層の制限（connlimit、接続頻度）とアカウント層の検証（`online-mode`、ホワイトリスト）が有効**です。相手は実在のアドレスを晒さなければならず、（正規アカウント認証を有効にしていれば）実在のアカウントを持たなければならないからです。

## 2. DDoS の基礎：「攻撃者の IP を BAN する」が効かない理由

### 2.1 DDoS とは

**DoS** は 1 本の流量でサービスを使えなくすること、**DDoS（Distributed DoS）** は**何千何万台**もの、異なるネットワーク・異なる事業者のマシンで同時に攻撃することです。これらのマシンは通常、感染した一般の機器、安価な VPS、IoT 機器で、まとめて**ボットネット（botnet）**と呼びます。鍵は「1 台がどれだけ強いか」ではなく**集約帯域**です。1000 台がそれぞれ 10 Mbps 出せば、10 Gbps になります。

### 2.2 「攻撃者の IP を BAN する」が流量型攻撃に効かない理由

これは最も一般的な誤解なので、最後まで説明する価値があります。

1. **流量はすでにあなたの回線の上にあります。** あなたのファイアウォール（`iptables` / `nftables` / Windows ファイアウォール）は**あなたのマシンかあなたのルーターの上**で動きます。攻撃流量がこの NIC に届いた時点で、**あなたの上り回線はすでに埋まっています**。ファイアウォールにできるのは「これらのパケットを捨てる」ことだけで、**捨てても帯域は戻りません**。回線は依然として満杯で、正常なプレイヤーは依然として接続できません。
2. **捨てること自体も資源を食います。** 大量の小さなパケットは NIC の割り込みとソフトウェア割り込み（softirq）で大量の CPU を消費し、ひどいときは SSH すら入れず、ログも書けなくなります。
3. **送信元 IP は膨大で、しかも変化し続けます。** 100 万件のブラックリストを維持することは不可能ですし、偽造された UDP の送信元アドレスでは、リストは無実の人で埋まります。
4. **ボトルネックはあなたの上流にあります。** 耐えられるかを決めるのは、**データセンターの接続帯域**と、**事業者 / サービス提供者があなたの手前でクリーニングしているか**であり、あなたのマシン上の規則ではありません。

### 2.3 サービス提供者とデータセンターが本当にできること

| 手段 | どの層で効くか | 説明 |
| --- | --- | --- |
| **容量（capacity）** | 上流 | データセンターの接続帯域が攻撃流量より大きければ、攻撃は「痛くない」。最も根本的な層 |
| **上流でのクリーニング（scrubbing）** | 上流 | 流量をまずクリーニングセンターへ引き込み、濾過してから戻す。**流量型攻撃への主要な手段** |
| **境界での速度制限（rate limiting）** | 上流かあなたの境界 | あなたのマシンに入る前に速度を制限し、バックエンドを守る |
| **構成の変更** | あなたの設計 | プロキシでオリジンを隠す、サービスを防御のある入口の後ろへ置く、静的資源を CDN に任せる |

:::warn 「クラウドサーバーには DDoS 防御が付いている」で足りると考えない
各クラウド事業者の無料防御は、**しきい値、クリーニングの方式、発動の条件、追加課金の有無、高防御 IP の提供の有無**が大きく異なり、条項も変わります。**買う前に公式ドキュメントと契約条件を読んでください**。無料防御のしきい値、超過後にブラックホール（あなたの IP をそのまま塞ぐ）かクリーニングか、高防御製品があるか、IP を変える方針はどうか。**これらの細部は本記事では推測せず、使用する事業者の公式説明に従ってください。**
:::

## 3. UDP flood と統合版の露出面

### 3.1 統合版が本質的に攻撃されやすい理由

| 事実 | 結果 |
| --- | --- |
| 統合版は **UDP `19132`**（IPv6 は `19133`）を使う | UDP はコネクションレスで偽造しやすく、**攻撃しやすく追跡しにくい** |
| **Geyser** も UDP を待ち受ける（既定は統合版と同じ。設定可） | Java サーバーはクロスプレイを有効にした時点で UDP の入口が 1 つ増える |
| UDP にハンドシェイクがない | 攻撃者は実在の IP も、何かの交渉の完了も必要としない。**1 バイト送れば 1 パケット** |
| サーバーが応答する必要がある | 一部のクエリ系リクエストは処理コストがリクエスト自体より高く、天然の増幅面になる |

### 3.2 攻撃を受けているときの症状

- **帯域の曲線が飽和する**のに、サーバーのログには何の異常も出ないことがある。
- **TPS は正常なのにプレイヤーが頻繁にタイムアウトする**：サーバー自体は重くなく、**ネットワーク経路**が埋まっている。
- NIC の受信レートが急上昇し、`softirq` の占有が高くなり、SSH が極端につながりにくく、まったくつながらなくなることもある。

観察用のコマンド（いずれも読み取り専用の問い合わせ）：

```bash
# UDP の待ち受けソケット（ss が表示するのはソケットで、流量ではない）
ss -uanp

# NIC の累積送受信とドロップのカウンタ（実際の NIC 名に変える。eth0 / ens3 など）
ip -s link show dev eth0

# カーネルのカウンタ。2 回サンプリングした差分を比べる
cat /proc/net/dev

# ファイアウォール規則のヒット数（root が必要）
sudo iptables -L INPUT -v -n

# nftables：カウンタや動的集合を持つ規則を見る
sudo nft list ruleset
```

:::note カウンタはどう見れば意味があるか
`/proc/net/dev`、`ip -s link`、`nft list ruleset` が示すのは**累積値**です。「いま攻撃を受けているか」を判断するには**単位時間あたりの増分**を見ます。十数秒あけて 2 回サンプリングし、`RX bytes` / `RX packets` の差を比べ、Mbps と pps に換算します。1 回のサンプリングでは何も分かりません。
:::

### 3.3 防御：まず露出面を狭める

**最も重要な 1 条：本当に必要な UDP ポートだけを開ける。** 純粋な Java サーバー（Geyser もクロスプレイもない）は、UDP ポートを**インターネットに開ける必要はありません**。統合版か Geyser が必要なときだけ `19132`（および本当に必要な IPv6 の `19133`）を開けます。「チュートリアルに書いてあったから」で UDP ポートをいくつも開けないこと。不要なポートを閉じれば、攻撃面はそのまま消えます。

### 3.4 ホスト側の速度制限：iptables の hashlimit

`hashlimit` モジュールは「あるキー」（ここでは送信元 IP）ごとに速度を集計し、しきい値を超えたら規則にヒットさせます。

```bash
# 1) まず「記録するだけで捨てない」規則で、実際の流量のベースラインを観察する（まず 1〜2 日動かすのを推奨）
sudo iptables -A INPUT -p udp --dport 19132 \
  -m hashlimit --hashlimit-above 200/sec --hashlimit-burst 400 \
  --hashlimit-mode srcip --hashlimit-name mc-udp-observe \
  -j LOG --log-prefix "MC-UDP-OVER: " --log-level 4

# 2) 観察してしきい値が妥当だと確認してから、実際に捨てる規則を足す
sudo iptables -A INPUT -p udp --dport 19132 \
  -m hashlimit --hashlimit-above 200/sec --hashlimit-burst 400 \
  --hashlimit-mode srcip --hashlimit-name mc-udp \
  -j DROP
```

引数の説明：

| 引数 | 意味 |
| --- | --- |
| `--hashlimit-above 200/sec` | 送信元 IP 1 つが 200 パケット/秒を超えたらヒット。**単位の接尾辞は必須**（`/sec`、`/min`、`/hour`、`/day`）。裸の数字は多くのバージョンでエラーになる |
| `--hashlimit-burst 400` | 許容するバースト量。バーストの窓のうち最初の 400 パケットを通し、正常な瞬間的な揺らぎを許容する |
| `--hashlimit-mode srcip` | **送信元 IP** ごとに集計する（`srcport`、`dstport` なども使える） |
| `--hashlimit-name mc-udp` | カーネル内のテーブル名。**同名の規則はカウンタを共有する**ので、観察用と破棄用は別の名前にする |
| `-j LOG` / `-j DROP` | 前者はカーネルログ（`dmesg` / `journalctl -k`）に記録して観察に使う。後者は黙って捨てる。`-j REJECT` も使えるが、UDP の REJECT は ICMP を返すので通常は不要 |

:::warn これらのコマンドが使えるかはカーネルとバージョン次第
`hashlimit` はカーネルが `xt_hashlimit` モジュールに対応している必要があり、`iptables` が `-m hashlimit` のときに自動で読み込める必要があります。**規則の文法は `iptables-legacy` と `iptables-nft` の 2 つのフロントエンドで同じですが、永続化の方法は異なります。** モジュールやオプションが見つからないと言われたら、あなたのシステムの `iptables --version`、`modinfo xt_hashlimit` の結果とディストリビューションのドキュメントを照合してください。また `iptables` の規則は**既定では永続化されず**、再起動で消えます。保存の方法は [ネットワークセキュリティの基礎](/tutorials/ops/network-security) を参照。
:::

### 3.5 ホスト側の速度制限：nftables の動的集合 + `limit rate over`

`nftables` の現代的なやり方は、**送信元 IP ごとの動的集合**を作り、しきい値を超えた送信元アドレスに印を付け、それから捨てる、というものです。

以下は**そのまま読み込める**最小の例です（`mc-udp-limit.nft` として保存し、`sudo nft -f mc-udp-limit.nft` で読み込みます）。

```bash
#!/usr/sbin/nft -f

# まず同名の古いテーブルを消し、二重読み込みのエラーを避ける。実行前に、他に依存する規則がないことを確認する
table inet mcguard
delete table inet mcguard

table inet mcguard {
    set udp_flood_v4 {
        type ipv4_addr
        flags dynamic, timeout
        timeout 10m
    }

    chain input {
        type filter hook input priority 0; policy accept;
        udp dport 19132 jump udp_guard
    }

    chain udp_guard {
        # 送信元 1 つが 200/秒（バースト 400）を超えたら集合に追加する
        update @udp_flood_v4 { ip saddr limit rate over 200/second burst 400 packets }
        # 制限された送信元をカーネルログに書いて観察しやすくする。その後そのまま捨てる
        ip saddr @udp_flood_v4 log prefix "MC-UDP-OVER: " level warn
        ip saddr @udp_flood_v4 drop
    }
}
```

要点の説明：

| 文法 | 意味 |
| --- | --- |
| `set ... { type ipv4_addr; flags dynamic, timeout; timeout 10m; }` | 動的集合。要素は自動で期限切れになり、**無限に増えない** |
| `limit rate over 200/second burst 400 packets` | 200/秒を**超えた**ときだけヒット（対して `limit rate` は「超えない」）。`over` はキーワード |
| `update @set { ... }` | ヒットしたときキー（`ip saddr`）を**集合へ書き込む** |
| `ip saddr @set drop` | 集合にある送信元アドレスを一律に捨てる。したがって**1 回ヒットすると、その送信元は集合が期限切れになるまで捨て続けられる**。例は `ip saddr`（IPv4）だけで集合を作っており、**IPv6 には別に `ipv6_addr` の集合と対応する規則が必要** |

:::warn 上記の nftables の書き方はバージョンに依存する
`flags dynamic, timeout`、`limit rate over`、`update @set` はいずれも比較的新しい文法です。**あなたのシステムの `nft --version` と nftables の公式 wiki に従ってください**。読み込む前に `sudo nft -c -f mc-udp-limit.nft`（`-c` は構文検査で、実際には読み込まない）を勧めます。**規則セットを書き間違えると、自分をドアの外に閉じ込めることがあります**。必ずクラウドの VNC かレスキューコンソールがあることを確認してください。
:::

### 3.6 速度制限の代償：正常なプレイヤーも傷つく

**すべての速度制限の規則は、潜在的な誤検知の源です。** **正常なプレイヤーは 200 パケット/秒も送りません**が、**ネットワークの揺らぎ、パケットロスによる再送、一部のクライアント / プラグインのバースト的な挙動**は短時間のピークを生みます。しきい値を低くすれば**実在のプレイヤーを傷つけ**、しかも原因を突き止めにくくなります。高くすれば攻撃流量はとっくに通り抜けています。

だから推奨するのは**まず観察し、それから捨てる**ことです。

1. まず `LOG`（iptables）か `log`（nftables）の規則だけを足し、しきい値は**想定する正常なピークの数倍**に置く。
2. 1〜2 日観察し、ログに「正常に見える」IP がどれだけ出るかを見て、誤検知がないと確認してから `DROP` に変える。
3. 公開後もプレイヤーの反応を見続け、いつでも調整する。

:::tip 速度制限は「ダメージ軽減」であり「免疫」ではない
ホスト側の速度制限は**低強度**の洪水の被害を明確に減らし、高強度の洪水が回線を飽和させるのを**少し遅らせる**こともできますが、**10 Gbps の攻撃に 1 Gbps の回線を飽和させないようにすることはできません**。本当の解決策は常に上流にあります。
:::

## 4. MOTD / 状態クエリの洪水（Minecraft 特有）

### 4.1 状態クエリのプロトコルとは

Minecraft のクライアントがサーバーリストに「同時接続数 / MOTD / 遅延 / バージョン / アイコン」を表示できるのは、**状態クエリ**のおかげです。その特徴は、**どのクライアントでも問い合わせでき、ログインもアカウントも入室も不要**なことです。

| プラットフォーム | 問い合わせの方法 | 転送 |
| --- | --- | --- |
| **Java 版** | Server List Ping（現代の状態リクエスト。ゲームポート上） | **TCP**、既定 `25565` |
| **統合版（基岩版）** | Unconnected Ping / Pong（RakNet） | **UDP**、既定 `19132` |

攻撃者がこれを好む理由は単純です。**送信コストが極めて低く**（ごく小さなリクエスト）、**応答コストがより高い**（サーバーは MOTD、プレイヤー一覧、アイコン、バージョン情報を組み立てる）。**増幅できる**（送信元 IP を被害者のアドレスに偽造し、応答を他人へ向けられる）。**偵察できる**（まず大量のクエリで応答能力を測り、同時接続数を見て、背後に防御があるかを判断してから、攻撃の規模を決める）。

### 4.2 query プロトコルを閉じる：できるが、何を閉じるのかを理解する

バニラの `server.properties` に関連するキーが 2 つあります。

```properties
enable-query=false
query.port=25565
```

:::warn query を閉じることは MOTD を隠すことではない
- **query プロトコル**（`enable-query`）は歴史的な遺物である **GameSpy4 クエリプロトコル**で、**UDP** を使い、既定のポートは `query.port` が指定します。第三者のツール / サイトがサーバー情報を問い合わせるためのものです。
- **サーバーリストに見える状態情報（MOTD、人数、遅延）** は**現代の Server List Ping** を使い、Java 版では**ゲームポート上の TCP 状態リクエスト**です。query とは**まったく別の 2 つの仕組み**です。

したがって、**`enable-query` を `false` にしても、サーバーがプレイヤーのサーバーリストから消えることも、MOTD が隠れることもありません**。あなたがほぼ確実に必要としない、余分な問い合わせの入口を 1 つ閉じるだけです。第三者のクエリツールが不要なら、閉じるのは露出面を減らす良いことですが、ping の洪水を防げるとは期待しないでください。
:::

### 4.3 状態ポートへの速度制限

考え方は第 3 節とまったく同じで、TCP に置き換えるだけです。

```bash
# Java 版：送信元 IP 1 つあたりの TCP 25565 への「新規接続」の速度を制限する
# 注意：これは新規接続にだけ効き、確立済みの接続には影響しない。だからプレイ中のプレイヤーには影響しない
sudo iptables -A INPUT -p tcp --dport 25565 --syn \
  -m hashlimit --hashlimit-above 10/sec --hashlimit-burst 20 \
  --hashlimit-mode srcip --hashlimit-name mc-ping \
  -j DROP
```

要点：`--syn` は**接続を開始する**パケットだけにマッチし、**すでにオンラインのプレイヤーを傷つけません**。しきい値（例は 10/秒）は実際の状況に合わせて調整します。プレイヤー 1 人は正常なら数回問い合わせるだけですが、**同じ NAT の出口の後ろの複数のプレイヤーは送信元 IP を共有します**。学校、ネットカフェ、家庭の共有ネットワークは誤検知しやすいので、`1/sec` にしないでください。nftables の等価な書き方は、第 3.5 節の集合の型を `ipv4_addr` に、マッチの条件を `tcp dport 25565` に変え、`tcp flags syn` を足します。

### 4.4 プロキシでバックエンドを守る

**プロキシ（Velocity / BungeeCord）を最前面に置き**、バックエンドのサーバーはプロキシからの接続だけを受け付けるのは、費用対効果の高い一歩です。

- プレイヤーの接続はまずプロキシに届き、**バックエンドのサーバーの IP はプレイヤーの一覧に現れません**。攻撃者はまず実在のアドレスを見つける必要があります。
- プロキシは接続頻度の制限ができ、転送の鍵の検証と組み合わせれば、**検証を通らない接続はそのまま拒否**できます。バックエンドのサーバーもプロキシだけを信頼する設定にできます（転送モードに関係する設定で、**キー名はソフトウェアとバージョンで異なります。自分で生成した設定と公式ドキュメントに従ってください**）。

プロキシの構築と転送の設定は [プロキシ](/tutorials/java/proxy) を参照してください。

### 4.5 Minecraft 専用のフィルタサービス

世の中には**Minecraft 向けのフィルタ / 防御サービス**があります（TCPShield のような類）。プレイヤーはまず事業者の接入点へ接続し、事業者がプロトコル層の識別とフィルタを行い、きれいな流量をあなたのバックエンドへ転送します。

**この類のサービスは通常「選択肢」であり「必需品」ではありません**。理由は、具体的な能力（どのバージョンに対応するか、統合版 / UDP に対応するか、Geyser に対応するか、特定の転送モードを要求するか、価格と流量の枠）が**事業者ごとに大きく違い、製品の反復で変わる**こと。第三者を挟むことは**プレイヤーの流量が第三者を通る**ことであり、プライバシーと信頼を評価する必要があること。設定は通常、バックエンドが事業者の IP からの接続だけを受け付けることを要求し、**設定を誤ると全サーバーが到達不能に直結する**ことです。

**結論：評価できる選択肢として扱い、実際の能力は事業者の公式ドキュメントに従ってください。本記事は代わって保証しません。**

### 4.6 統合版についての正直な結論

**統合版は状態 ping を完全には閉じられません**。クライアントがサーバーリストの情報を表示するのに使うので、サーバーは RakNet の unconnected ping に応答しなければなりません。したがって統合版の ping 洪水への対策は 2 つだけです。

1. **上流での防御 / クリーニング**（最も有効。事業者次第）。
2. **境界かホストで送信元 IP ごとに UDP を制限する**（第 3.4 / 3.5 節の規則で `--dport 19132` を使うだけ）。

## 5. ボットによる負荷テスト（bot / 偽プレイヤーの洪水）

### 5.1 何か

**ボットによる負荷テスト**とは、自動化されたプログラムで大量の「プレイヤー」や「半端なプレイヤー」を作り、**枠を埋め、CPU とメモリを焼き、チャットのゴミを作り、実在のプレイヤーを入れなくさせる**ことです。

よくある変種：

| 変種 | やり方 | 主な消費 |
| --- | --- | --- |
| **接続洪水（connection flood）** | TCP 接続を完了するだけで、Minecraft のプロトコルのやり取りを一切しない | 接続テーブル、ファイルディスクリプタ、ハンドシェイクのコスト |
| **ログイン洪水（login flood）** | ハンドシェイクとログイン開始を送るが、ログインを完了しない | ログイン段階の CPU、認証リクエスト、メモリ |
| **偽プレイヤーの放置（idle bots）** | 完全に入室した後、その場で動かない | プレイヤーの枠、エンティティ / チャンクの読み込み、メモリ |
| **チャット / コマンドの連投** | 入室後に高頻度でチャットやコマンドを送る | メインスレッドの解析、ログ IO、連投による妨害 |
| **アイテム / 相互作用リクエストの連投** | 高頻度のパケットで相互作用のロジックを起こす | サーバーのメインスレッド、アンチチートプラグインのコスト |

:::note ゲームサーバーがとくに偽プレイヤーを恐れる理由
Minecraft は**状態を持つ長い接続**のサービスです。Web サーバーは 1 つのリクエストを処理したら切断し、コストを薄くできます。Minecraft はプレイヤーが 1 人増えるたびに、**メモリに常駐し、チャンクを読み込み、エンティティを同期し、接続を維持**します。同じ攻撃コストで、ゲームサーバーへの被害は静的サイトよりはるかに大きい。
:::

### 5.2 防御（有効性の順）

#### 第 1 位：`online-mode=true`（Java）/ Xbox Live の検証（統合版）

**これが単独で最も有効な措置です。** 正規アカウント認証を有効にすると、入室には**実在の Mojang/Microsoft アカウント**が必要になり、ボットの作成者は偽プレイヤー 1 体ごとに実在のアカウントを用意しなければなりません。コストは「ほぼゼロ」から「アカウント単位の課金」へ一瞬で変わります。

Java 版の `server.properties`：

```properties
online-mode=true
```

:::warn オフラインモードの代償はよく考える
`online-mode=false` は、**誰でも任意の ID で入室できる**ことを意味します。管理者のなりすまし、他のプレイヤーの名前のなりすましも含みます。これは身元の層の穴で、ファイアウォールでは埋められません。**代償を完全に理解し、ホワイトリストやログインプラグインで身元の検証を補う場合にだけ、オフラインモードを検討してください。** 関連する議論は [サーバーの設定](/tutorials/java/config) を参照。
:::

統合版には `online-mode` というキーはなく、**Xbox Live の身元検証**を使います。具体的なスイッチの名前と既定値は**サーバーソフトウェア（公式 BDS と各種の第三者統合版サーバー）とバージョンで異なります**。自分で生成した `server.properties` と公式ドキュメントに従ってください。**ただし原則として、「便利だから」で身元の検証を無効にしないでください。**

#### 第 2 位：ホワイトリスト / 許可リスト

小規模なサーバーには、**ホワイトリストがどんな速度制限より徹底した方案**です。知らない人はそもそも接続できず、ボットにはドアをくぐる資格すらありません。

Java 版の `server.properties`：

```properties
white-list=true
enforce-whitelist=true
```

| キー | 役割 |
| --- | --- |
| `white-list` | 名簿にあるプレイヤーだけログインを許す |
| `enforce-whitelist` | 名簿が変わったとき、**名簿にないオンラインのプレイヤーを即座に蹴る**。このキーを変えないと、新しく追加した名簿はプレイヤーが再接続するまで効かない |

名簿はコンソール / ゲーム内のコマンドで維持します（`whitelist add <プレイヤー名>`、`whitelist list` など。**具体的な文法はあなたのサーバーのバージョンに従ってください**）。

統合版はサーバーのルートディレクトリにある **`allowlist.json`** を使い、通常は `allowlist` 関連のコマンドが自動で維持します。**ファイルの形式とスイッチのキー名はサーバーソフトウェアとバージョンで変わります。自分で生成した `allowlist.json` と公式ドキュメントに従い、チュートリアルの例のファイルをそのまま写さないでください。**

#### 第 3 位：接続頻度の制限（`spigot.yml`）

Spigot とその派生コア（Paper、Purpur など）の `spigot.yml` には接続スロットルの設定があり、キーのパスは次のとおりです。

```yaml
settings:
  connection-throttle: 4000
```

| 項目 | 説明 |
| --- | --- |
| `connection-throttle` | **同じ送信元アドレスで 2 回接続する間に必要なミリ秒数**。例の `4000` = 4 秒。`-1` は通常、スロットルの**無効**を意味する |
| 既定値 | **コアとバージョンで異なる**。よくある既定は 4000 ミリ秒だが、あなたのものがそうだとは仮定しない |

**何を止められるか**：同じ IP が繰り返し素早く再接続するスクリプト。
**何を止められないか**：大量の異なる IP からの分散した偽プレイヤー（各 IP は 1 回しか接続せず、スロットルはまったく発動しない）。

:::warn スロットルの値を大きくしすぎない
数十秒にすると**正常なプレイヤーに深刻な影響**が出ます。切断後に再接続するまで長く待たされ、複数人が 1 つの出口 IP を共有する家庭やネットカフェはそもそも入れなくなります。既定値から始め、本当に必要なときだけ小幅に調整することを勧めます。
:::

#### 第 4 位：ファイアウォールでの接続数の制限

**送信元 IP 1 つあたりの同時接続数**を制限し、接続洪水と半開のログインに効きます。

```bash
# iptables：IPv4 アドレス 1 つあたり、25565 への同時接続を最大 8 本まで
sudo iptables -A INPUT -p tcp --dport 25565 \
  -m connlimit --connlimit-above 8 --connlimit-mask 32 \
  -j REJECT --reject-with tcp-reset
```

| 引数 | 意味 |
| --- | --- |
| `--connlimit-above 8` | 8 本の同時接続を超えたらヒット |
| `--connlimit-mask 32` | **/32** でまとめる。つまり「IPv4 アドレスごと」に別々に数える |
| `-j REJECT --reject-with tcp-reset` | そのまま拒否して RST を返す（`-j DROP` も使えるが、REJECT のほうがクライアントは固まらず早く失敗できる） |

nftables の等価な書き方（コネクショントラッキングのカウントを使う）：

```bash
#!/usr/sbin/nft -f

table inet mcguard
delete table inet mcguard

table inet mcguard {
    chain input {
        type filter hook input priority 0; policy accept;
        # 送信元アドレス 1 つあたり、追跡中の TCP 接続を最大 8 本まで
        tcp dport 25565 ct count over 8 reject with tcp reset
    }
}
```

:::warn 同時接続数は実際の遊び方に合わせて決める
実在のプレイヤーは通常 1 本の接続しか使いません（一部の MOD / プラグインを入れたクライアントはもっと使うかもしれません）。ただし**同じ NAT の出口の複数のプレイヤーは送信元 IP を共有**するので、しきい値を 2 や 3 にすると正常なプレイヤーをそのまま蹴ります。**8 はあくまで例です。プレイヤーの分布に合わせて調整してください**。`ct count` はコネクショントラッキング（`nf_conntrack`）が正常に動いている必要があるので、`ct` 関連のモジュールやテーブル項目を無効にしていないことを確認してください。
:::

#### 第 5 位：Paper のパケットリミッタ（packet limiter）

Paper は**グローバル設定**にパケットリミッタを提供しています。プレイヤーごとに**受信パケットの速度**を集計し、しきい値を超えたら**そのプレイヤーを蹴り**、ログに記録できます。「入室後に小さなパケットを狂ったように送る」攻撃（第 5.1 節のアイテム / 相互作用の連投、一部の偽プレイヤーの挙動など）に効きます。

:::warn チュートリアルの設定構造をそのまま写さない
**この設定ブロックのキー名、階層、既定値は Paper のバージョンやブランチによって変わってきました。** 正しいやり方は、まずサーバーを普通に 1 回起動して**自分で設定ファイルを生成させる**こと。自分で生成したファイルを開き、パケットリミッタ関連のブロックを見つけ、**ファイルの実際の構造に従って**変更します。ネット上の断片をコピーするのではありません。変更後に起動ログに設定の解析警告が出ないか確認します。

そのため本節は**あえて具体的なキー名と数値を示しません**。古くなっているかもしれない構造を書くほうが、書かないより危険です。
:::

#### 第 6 位：バックエンドをプロキシの後ろへ隠す

第 4.4 節と同じです。**バックエンドのサーバーのポートをインターネットへ直接開放せず**、プロキシの IP からの接続だけを許可します。こうすれば、誰かがあなたの実在の IP を手に入れても、まずプロキシの層を突破する必要があります。設定は [プロキシ](/tutorials/java/proxy) を参照してください。

#### アンチボットプラグインについて

コミュニティには各種の「アンチ偽プレイヤー / アンチボット / 入室検証」プラグイン（画像認証、コマンド認証、速度制限など）があります。それらは**攻撃コストを上げられます**。とくに低品質なスクリプトに対して。ただし**いずれもアプリケーション層**にあり、攻撃流量はすでにあなたのサーバーに届き、ハンドシェイクと一部のログイン資源をすでに消費しています。しかも**品質はまちまち**で、一部のプラグイン自体に性能や互換性の問題があります。

**自分で評価することを勧めます**。まだ保守されているか、オープンソースか、あなたのサーバーのバージョンと互換か、テストサーバーで 1 回負荷試験をしてから本番へ。

### 5.3 `max-players` はソフトリミット

```properties
max-players=20
```

`max-players` が決めるのは**サーバーリストに表示される上限**と、**ログイン段階**でその人数を超えたプレイヤーを拒否することだけです。**洪水対策ではありません**。ボットは**ログイン段階ですでに CPU、認証リクエスト、メモリを消費**しており、拒否される前にコストは払われています。接続洪水（TCP 接続を張るだけ）は**この判断にまったく到達しません**。帯域やクエリの洪水にも影響しません。

**`max-players` は容量の宣言として扱い、防御の手段として扱わないでください。**

## 6. 実践の防御チェックリスト

### 6.1 層別のチェックリスト（「必須」から「あれば尚可」まで）

| 優先度 | 措置 | 説明 |
| --- | --- | --- |
| **必須** | `online-mode=true`（Java）/ Xbox Live の検証を維持（統合版） | 単独で最も有効なアンチ偽プレイヤー措置 |
| **必須** | 本当に必要なポートだけを開ける | 露出していないサービスは攻撃できない。UDP ポートはとくに抑制する |
| **必須** | ホストのファイアウォールは既定で受信を拒否し、ホワイトリストのポートだけを通す | [ネットワークセキュリティの基礎](/tutorials/ops/network-security) を参照 |
| **必須** | システムとソフトウェアを速やかに更新し、権限を絞る | [システムのセキュリティ強化](/tutorials/ops/system-security) を参照 |
| **必須** | 定期的なバックアップ。**少なくとも 1 部はオフライン / 遠隔地** | ランサムと報復的なデータ削除への最後の防衛線。[バックアップと復元](/tutorials/java/backup) を参照 |
| **強く推奨** | ホワイトリスト / 許可リスト（小規模サーバー） | 知らない人はそもそも接続できない |
| **強く推奨** | ゲームポートの送信元 IP ごとの速度制限 | 第 3.4 / 3.5 / 4.3 / 5.2 節の規則 |
| **強く推奨** | 監視とアラート（帯域、接続数、CPU、プレイヤー数）と、防御の条項が明確な事業者の選択 | 第 6.3 節を参照 |
| **推奨** | プロキシを前に置き、バックエンドを直接露出しない | [プロキシ](/tutorials/java/proxy) を参照 |
| **推奨** | 統合版 / クロスプレイのプレイヤーは [スマートフォンプレイヤーのサポート](/tutorials/java/mobile) を参考に入口を計画する | クロスプレイは追加の UDP 露出面を持ち込む |
| **推奨** | 文書化したインシデント対応の計画 | 第 6.4 節を参照 |
| **あれば尚可** | Minecraft 専用のフィルタサービス | 能力は事業者次第。まず小規模に検証する |
| **あれば尚可** | アンチボットプラグイン | 自分で評価し、唯一の防衛線にしない |

### 6.2 攻撃の種類と対応表

| 攻撃の種類 | 本当に役に立つもの | ほぼ役に立たないもの |
| --- | --- | --- |
| **UDP flood（送信元 IP の偽造）** | 上流でのクリーニングと容量、必要な UDP ポートだけを開けること、境界での送信元 IP ごとの速度制限 | 個別 IP の BAN、サーバーのプラグイン、`max-players` |
| **反射増幅（DNS / NTP / memcached / SSDP / CLDAP）** | **上流でのクリーニング**（これが唯一有効な層）、データセンターの容量 | ホスト側のあらゆる規則（回線はすでに満杯）、第三者への苦情（あなたも被害者） |
| **SYN flood** | 上流でのクリーニング、カーネルの `syn` 関連パラメータの調整、ロードバランサー / プロキシ層での吸収 | アプリケーション層の速度制限、ホワイトリスト |
| **MOTD / 状態 ping の洪水** | 送信元ごとの TCP 接続速度の制限、プロキシを前に置く、上流でのフィルタ | `enable-query` を閉じる（それが扱うのはこれではない）、IP の BAN（量が多く分散している） |
| **統合版の ping 洪水** | 上流での防御、送信元 IP ごとの UDP `19132` の速度制限 | ping を閉じる（**できない**）、サーバーの設定 |
| **接続洪水 / ログイン洪水（半開のログイン）** | ファイアウォールの `connlimit` / `ct count`、`online-mode` か身元検証、プロキシを前に置く、上流でのクリーニング | `max-players`、チャットのフィルタ、ホワイトリスト（オフラインモードではログイン後に効く） |
| **偽プレイヤーの放置 / 連投** | `online-mode` + ホワイトリスト、`connection-throttle`、パケットリミッタ、管理コマンドでの対応 | 帯域の防御（この類の攻撃はほとんど帯域を使わない） |
| **脆弱性の悪用 / 権限昇格** | 速やかな更新、最小権限、`online-mode` | ファイアウォール（狙われるのはアプリケーション層） |

### 6.3 監視とアラート：アラートのない監視は監視がないのと同じ

少なくとも「いま攻撃を受けているか」に答えられる必要があります。

| 指標 | どこで見るか | 異常の特徴 |
| --- | --- | --- |
| **帯域 / 受信レート** | 事業者のコンソールの流量グラフ、`/proc/net/dev`、`ip -s link`、`vnstat` | 過去のピークをはるかに超え、しかもプレイヤー数は増えていない |
| **接続数** | `ss -tan state established \| wc -l`、`ss -s` | 接続数が急増するのにプレイヤー数は変わらない |
| **CPU とソフトウェア割り込み** | `top`、`mpstat -P ALL 1` | プレイヤーは少ないのに `%soft` が非常に高い（小さなパケットの洪水でよくある） |
| **プレイヤー数とログイン失敗** | サーバーのログ、パネル | 大量のログイン試行、大量の異常な ID |
| **ファイアウォールのヒット数** | `iptables -L -v -n`、`nft list ruleset` | 速度制限の規則のヒット数が増え続ける |

```bash
# 確立済みの接続数（ss -s でソケットの全体像も見る）
ss -tan state established | wc -l

# コアごとの CPU（ソフトウェア割り込みを含む）を毎秒更新
mpstat -P ALL 1

# NIC の累積カウンタ（2 回のサンプリングの差を見る）
ip -s link show dev eth0

# カーネルログの速度制限のヒット記録（LOG / log 規則と併用）
sudo journalctl -k | grep -i 'MC-UDP-OVER' | tail -n 20
```

:::tip 事業者のパネルに当直を代わってもらう
多くのクラウドのコンソールは**帯域の曲線とアラート**を提供します。しきい値を「過去のピーク + 余裕」に置き、発動したら通知を受け取る。**これは後からログを漁るよりはるかに役に立ちます**。具体的な設定の経路は事業者によって異なるので、公式ドキュメントに従ってください。
:::

### 6.4 インシデント対応の計画（1 枚の紙）

攻撃を受けたその瞬間は、考えるときではありません。前もって書いておきます。

1. **判断**：6.3 の指標と照合し、まず**攻撃**なのか**自分の不具合**なのか（プラグインの無限ループ、バックアップがディスク IO を占有、ワールドファイルの破損によるラグ）を確認する。
2. **止血と支援要請**：耐えられるなら耐える。耐えられないときは一時的に**ホワイトリストの IP だけ / プロキシの IP だけ**を許可し、同時に事業者へ障害を報告し、時刻、現象、流量の特徴を伝え、クリーニングが発動したか、IP を変える必要があるかを尋ねる。
3. **証拠の保全と復旧**：流量のグラフ、ログ、`ss` の出力を保存する。**これらが申立てと振り返りの唯一の根拠**です。攻撃が止まったら TPS、接続数、ワールドの完全性を確認してから、一時的な制限を解除します。
4. **振り返り**：攻撃の規模はどれくらいだったか？どの層が耐え、どの層が耐えられなかったか？次は何を買い、何を設定するか？

:::warn バックアップは攻撃の一部であり、追加項目ではない
**ランサムと報復的なデータ削除**は実在する攻撃の手法です。攻撃者がパネルや RCON の権限を手に入れて最初にやることは、しばしばバックアップの削除です。だから、**少なくとも 1 部のバックアップはオフライン媒体か遠隔地にあり、サーバーのマシンの書き込み可能なパスにマウントされていない**必要があります。具体的な方案は [バックアップと復元](/tutorials/java/backup) を参照。
:::

## 7. 正直な境界

3 つの文をここに書いておきます。本記事に誤った期待を持たないために。

1. **サーバーの設定では大規模な流量型攻撃を止められません。** `iptables`、`nftables`、プラグイン、`max-players` のどれも、**攻撃流量がすでに届いた後**に動きます。1 Gbps の回線が 10 Gbps の攻撃に向き合えば、設定がどんなに完璧でも無駄です。**唯一の本当の解決策は上流の容量とクリーニング能力です。**
2. **上流の能力は買うもので、設定するものではありません。** サービスの選定時に DDoS の条項を見極めてください。無料防御のしきい値はいくつか、超過後はクリーニングかブラックホールか、UDP に対応するか、高防御 IP はあるか、IP の変更は有料か。**これらの問いを攻撃を受けた当日に聞くのでは遅すぎます。**
3. **すべての速度制限は潜在的な誤検知です。** 速度制限はバースト的な流量の実在のプレイヤー、出口 IP を共有するネットカフェや家庭のネットワークを傷つけます。**まず観察し、それから捨て、調整を続ける**。ネットから写したしきい値をそのまま本番に載せないでください。
