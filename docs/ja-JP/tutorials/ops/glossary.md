サーバー開設の途中で詰まる人の多くは、操作ができないのではなく、**他人が何を言っているか分からない**のです。「MSPT はいくつ？」「このプラグインに前提はある？」「オフラインサーバー？」——どの一言にも、説明されていない言葉が隠れています。

この記事では、当サイトの各チュートリアルに繰り返し登場する名詞をまとめて説明します。**テーマ別にグループ化**し、各項目に日本語名、対応する英語、1〜2 文でそれが何かを示し、どの記事で詳しく扱うかを添えます。

## 0. この記事の使い方

| あなたの状況 | 提案 |
| --- | --- |
| 完全な初心者で、まだ動かせていない | まずこの記事を読まずに、[サーバーコアの選び方](/tutorials/java/core) と [サーバーの起動](/tutorials/java/start) をそのままやってみて、分からない言葉が出たら戻って調べる |
| 動かせるが、エラーや他人の助言が分からない | 第 1、2、3 節を重点的に。この 3 節はコミュニティのやり取りで最も頻出 |
| 統合版のサーバーを開きたい | 第 4 節を重点的に。**統合版と Java 版の用語はほとんど通用しない** |
| 技術向け（生電）のサーバーを作りたい | 第 5 節を重点的に。どのコアを選ぶべきかがここで決まる |
| すでに長期的にサーバーを保守している | 第 6 節を重点的に。この節の言葉は「データを守れるか」に直結する |

:::note 辞書として使い、暗記しない
用語集の価値は**検索**にあり、記憶にはありません。チュートリアルで知らない言葉に出会ったら、ここに戻ってブラウザのページ内検索で 1 回探せば十分です。本当に覚えるべきは 1 つだけ。**不確かな既定値に出会ったら、公式ドキュメントとローカルで生成された設定ファイルを調べる**。
:::

:::warn バージョンとベンダーの差
Minecraft サーバーのエコシステムでは、**既定値、設定キー名、使えるコマンドのほとんどがバージョンとブランチで変わります**。本記事は「この言葉が何を意味するか」だけを説明し、**あるキーの現在のバージョンでの具体的な既定値は保証しません**。設定を変えるときは、使用しているコアの公式ドキュメントとローカルで生成された設定ファイルに従ってください。
:::

## 1. 性能の分類

この一群の言葉は同じ問いに答えます。**サーバーはいま重いのか、どこが重いのか。**

| 用語 | 英語 | 解説 | 関連ドキュメント |
| --- | --- | --- | --- |
| ティック / tick | tick | サーバーのメインループの 1 回の実行。バニラの目標は毎秒 20 回、つまり 1 tick が約 50 ミリ秒。エンティティ、レッドストーン、ブロック更新、プレイヤーの移動、ほとんどのチャンクのスケジューリングがこのループで行われる | [性能の最適化](/tutorials/java/optimize) |
| TPS | Ticks Per Second | 1 秒に実際に完了した tick の数。バニラの上限は 20 で、サーバーが処理しきれないと 20 を下回る。**これは「結果」であり「原因」ではない** | [spark でサーバー性能を分析する](/tutorials/ops/spark) |
| MSPT | Milliseconds Per Tick | 1 tick あたりの平均のミリ秒数。tick の所要時間とも呼ぶ。TPS と同じことの裏表で、**所要時間が長期的に 50 ms を超えると TPS は 20 を保てない** | [spark でサーバー性能を分析する](/tutorials/ops/spark) |
| 50 ms の予算 | 50 ms budget | 毎秒 20 tick から導かれる 1 tick の時間上限。**平均値としての予算**であることに注意。たまに 1 tick が 200 ms 使い、残りが速ければ TPS は 20 に近いままでも、プレイヤーは瞬間的なラグを感じる | [性能の最適化](/tutorials/java/optimize) |
| ラグ / 重い | lag | プレイヤーの主観的な感覚で、**指標ではない**。サーバーの tick が遅い、ネットワークが揺れている、クライアントの描画の問題かもしれない。調査の第一歩はこれを具体的な指標に翻訳すること | [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) |
| GC の停止 | GC pause | Java のガベージコレクションで、アプリケーションのスレッドが停止させられる時間。ヒープが大きいほど、回収器が合っていないほど 1 回の停止は長くなり、**周期的に一瞬止まる**形で現れ、持続的に遅くなるのではない | [性能の最適化](/tutorials/java/optimize) |
| TPS の低下と MSPT のスパイク | TPS drop vs MSPT spike | 2 つの異なる現象。**TPS の低下**は通常、持続的な資源不足（CPU の制限、エンティティの過多）。**MSPT のスパイク**は短時間の所要時間の突き上げ（チャンク生成、大規模なレッドストーン、GC）。区別して初めて正しい直し方を選べる | [spark でサーバー性能を分析する](/tutorials/ops/spark) |

### 1.1 「重い」が指標にならない理由

「重い」は少なくとも 4 つのまったく異なる現象に対応し、直し方はそれぞれ違います。

| 現象 | 典型的な特徴 | まず何を見るか |
| --- | --- | --- |
| メインスレッドが処理しきれない | TPS が長期的に 20 未満、MSPT が安定して高め | spark の profiler のコールツリー |
| 瞬間的なスパイク | TPS の平均は悪くないが、プレイヤーは「一瞬止まる」と言う | spark の tick 所要時間の分布、GC の記録 |
| ホストの資源不足 | サーバーのプロセス自体は遅くないが、CPU が制限され、ディスクが遅く、メモリがスワップアウトされている | `uptime`、`free -h`、ホストの監視 |
| ネットワークの問題 | サーバーはすべて正常で、一部のプレイヤーだけ遅延が高い | `/spark ping`、プレイヤーとデータセンターの間の経路 |

**この 4 つを分けることが、ラグの調査で最も重要な一歩です。** 関連する方法は [spark でサーバー性能を分析する](/tutorials/ops/spark) を参照してください。

### 1.2 しきい値は魔法の数字ではない

コミュニティでよく言われる「TPS が 20 未満なら問題」「MSPT が 50 を超えたら見る」は**経験的なしきい値**で、「ちょっと見てみる」きっかけであり、「必ず故障」ではありません。本当の判断材料は**あなた自身の過去のベースライン**です。普段 MSPT が 35 なら、突然 45 に上がれば調べる価値があります。普段 48 なら、50 はむしろ平常です。ベースラインの作り方は [監視とアラート](/tutorials/ops/monitoring) を参照してください。

### 1.3 TPS と MSPT が「同期しない」理由

よくある困惑：「TPS は 20 なのに、プレイヤーはまだ重いと言う」。矛盾ではありません。理由は少なくとも 3 つあります。

| 状況 | なぜ TPS は正常に見えるか |
| --- | --- |
| 平均がスパイクを隠す | TPS は**一定期間の平均**で、たまの長い tick が大量の正常な tick に均される |
| クライアント側が重い | サーバーの tick は完全に正常だが、プレイヤーの PC が描画しきれない、または描画距離を開きすぎている |
| ネットワークが重い | サーバーはすべて正常だが、プレイヤーからデータセンターの経路が揺れているかパケットロスしている |
| ホスト側が重い | サーバーのプロセスが CPU 制限やメモリのスワップアウトを受けるが、本人は「少し遅いだけ」と感じる |

だから判断の順序はこうです。**まずサーバー側かそうでないかを確認し、それから具体的な調査に入る**。`/spark ping`、ホストの CPU とメモリ、各地域のプレイヤーの遅延が、この段階の入力です。方法は [spark でサーバー性能を分析する](/tutorials/ops/spark) を参照してください。

### 1.4 tick と「サーバーの時刻」の副作用

世界のロジックのほとんどが tick ループで進むため、**tick が遅くなるとゲーム内の多くのものが同時に遅くなります**。作物の成長、かまどの進行、レッドストーンのタイミング、 mob の移動。だから「TPS が 15 に落ちた」は、プレイヤーの体感では「25% 遅くなった」だけでは済みません。時間に依存するすべての仕組みが一緒に遅くなり、正確なタイミングに依存する装置はそのまま動かなくなることがあります。関連する仕組みは [生電とレッドストーン](/tutorials/java/redstone) を参照してください。

:::tip まずどれを見るか
プレイヤーが重いと言ったら、**まず TPS と MSPT、それから CPU の使用率**。TPS が低く MSPT が正常なら、問題はサーバーのメインスレッドになく、ホストの CPU、メモリの回収、ネットワークを見るべきです。関連する推論と、コンテナ環境についての公式の注意は [spark でサーバー性能を分析する](/tutorials/ops/spark) を参照。
:::

## 2. サーバーの分類

この一群の言葉はこう答えます。**あなたが動かしているのは何というプログラムで、それは何でできているのか。**

| 用語 | 英語 | 解説 | 関連ドキュメント |
| --- | --- | --- | --- |
| コア / サーバーコア | server core / server software | 実際に `java -jar` で起動するサーバープログラム。Paper、Fabric、BDS など。**「コア」は公式の用語ではなく**、サーバーの実装に対する国内コミュニティの慣習的な呼び方 | [サーバーコアの選び方](/tutorials/java/core) |
| プラグイン | plugin | サーバーのプロセス内で動き、サーバーが提供する API で機能を拡張するプログラム。通常は `.jar` で `plugins/` に置く。**プラグイン側（Paper 系）だけが対応** | [プラグインの基礎](/tutorials/java/plugins) |
| MOD | mod | ゲームのコードを直接変更する拡張。`mods/` に置き、ゲームのバージョンと厳密に対応させる必要がある。**MOD 側（Fabric、Forge、NeoForge）だけが対応** | [サーバーの選択](/tutorials/java/core) |
| 前提 / 依存 | dependency | あるプラグインや MOD が動く前に、同時に入れておく必要がある別のプラグインや MOD。前提が欠けた典型的な現れ方は**読み込みの失敗で、ログに何が足りないかが書かれる** | [プラグインの依存](/tutorials/java/plugin-deps) |
| プロキシ / クロスサーバー | proxy | プレイヤーがまずここへ接続し、そこから後ろの実在のサーバーへ接続を転送する。複数サーバーの相互移動、入口の統一、ログインの統一に使う | [プロキシ](/tutorials/java/proxy) |
| BungeeCord | BungeeCord | 最も早い成熟したプロキシの実装。そのプラグインメッセージのチャネルは後に他のプロキシも互換対応し、事実上の標準の 1 つになった | [プロキシ](/tutorials/java/proxy) |
| Velocity | Velocity | 現代のプロキシ実装で、性能とセキュリティの設計が優れている。**モダンフォワーディング（modern forwarding）**はプロキシとバックエンドが鍵を共有する必要があり、設定を誤るとサーバーに入れない | [プロキシ](/tutorials/java/proxy) |
| バックエンドサーバー | backend server | プロキシの後ろで実際に遊び方を担うサーバーのインスタンス。プレイヤーがプロキシ上で「サーバーを切り替える」のは、実際にはあるバックエンドとの接続を切り、別のバックエンドへ接続すること | [プロキシ](/tutorials/java/proxy) |
| ロビー | lobby | 特殊なバックエンドサーバー。プレイヤーはログイン後にまずここへ着き、NPC かコマンドで各遊び方のサーバーへ入る。通常はプラグインが少なく、設定も軽い | [プロキシ](/tutorials/java/proxy) |
| MCDR | MCDReforged | サーバーの隣に置き、コンソールの出力を解析しコマンドを送ることで動く**サーバー管理フレームワーク**。サーバー自体は変更しないため、コアの種類に縛られない | [MCDR](/tutorials/java/mcdr) |

### 2.1 「プラグイン側」と「MOD 側」は 2 本の平行線

初心者が最も混同するのがこの 2 語です。「同じものの 2 つの呼び方」ではなく、**互換性のない 2 つの拡張の仕組み**です。

| | プラグイン（plugin） | MOD（mod） |
| --- | --- | --- |
| 読み込み位置 | `plugins/` | `mods/` |
| 典型的なコア | Paper、Spigot、Purpur、Folia | Fabric、Forge、NeoForge |
| 拡張の方法 | サーバーが提供する API を呼ぶ | ゲームのコードを直接変更する |
| バージョンの対応 | 比較的緩く、マイナーバージョンをまたいでも使えることが多い | 極めて厳格で、完全に対応させる必要がある |
| 典型的な用途 | 管理、権限、経済、ミニゲーム | 新コンテンツ、新メカニズム、クライアントの機能 |

**Fabric で Bukkit のプラグインを使う、Paper で Forge の MOD を使う、はいずれも既定では成立しません**。追加のブリッジの方案が必要で、しかも互換性や性能を犠牲にすることがよくあります。コアを選ぶときは、まずどちら側が必要かをはっきりさせてください。[サーバーコアの選び方](/tutorials/java/core) を参照。

### 2.2 プロキシは「加速器」ではない

「クロスサーバー」という言葉は、遅延を下げてくれるように聞こえがちです。**ネットワーク経路は最適化しません**。役割は複数のサーバーを 1 つに見せることです。入口のアドレスを統一し、プレイヤーがサーバー間を移動するときに新しい IP へ再接続せずに済み、ログインと権限を集中管理できる。同時に新しい複雑さ（転送の鍵、バックエンドの認証、プレイヤーデータの同期）を持ち込むので、設定の前に [プロキシ](/tutorials/java/proxy) を読んでください。

:::warn プロキシを入れたらバックエンドを直接露出しない
バックエンドのサーバーは、プロキシからの接続だけを受け付けるべきです。**バックエンドのポートをインターネットに開放すると、プレイヤーはプロキシを迂回して直結できます**。プロキシ上のログイン検証、権限の制限、ホワイトリストはすべて無効になります。関連するポートとファイアウォールの設定は [ネットワークセキュリティの基礎](/tutorials/ops/network-security) を参照。
:::

## 3. Java 版の概念

この一群の言葉は Java 版のエコシステムの「業界用語」で、出現頻度が最も高いものです。

| 用語 | 英語 | 解説 | 関連ドキュメント |
| --- | --- | --- | --- |
| Bukkit | Bukkit | 初期にバニラのサーバーへプラグイン API を提供したプロジェクト。後のサーバーはほぼすべてその API を共通の方言としたため、プラグインはよく「Bukkit プラグイン」と呼ばれる | [サーバーコアの選び方](/tutorials/java/core) |
| Spigot | Spigot | Bukkit の後継ブランチで、長くプラグイン側の事実上の標準であり、後に多くのブランチの起点になった | [サーバーコアの選び方](/tutorials/java/core) |
| Paper | Paper | 現在最も主流の Spigot ブランチで、性能とメカニズムの修正を大量に行い、保守を続けている。**性能のために一部のバニラの挙動を変えており**、それが生電との衝突の根源 | [サーバーコアの選び方](/tutorials/java/core) |
| Purpur | Purpur | Paper を基にしたブランチで、設定可能な遊び方の選択肢を大量に追加している | [サーバーコアの選び方](/tutorials/java/core) |
| Folia | Folia | Paper を基にしたブランチで、世界を区域に分けて並行に tick する。**プラグインの互換性と引き換えにマルチコアを活用**し、区域をまたぐ相互作用の挙動も Paper と異なる | [サーバーコアの選び方](/tutorials/java/core) |
| API | Application Programming Interface | サーバーがプラグインに呼ばせるために提供するプログラミングのインターフェース。**API で書いたプラグインはバージョンをまたいでも比較的安定**し、内部実装に直接触れると逆になる | [プラグインの基礎](/tutorials/java/plugins) |
| NMS | net.minecraft.server | サーバーの内部クラスがあるパッケージ名で、「API を迂回して内部実装を直接呼ぶ」ことの代名詞にもなる。**これらの内部構造には互換性の保証がなく**、バージョンが上がると失効し得る | [プラグインの基礎](/tutorials/java/plugins) |
| api-version | api-version | `plugin.yml` のフィールドで、プラグインがどのバージョンの Paper API 向けに書かれたかを宣言する。公式ドキュメントの説明：**サーバーのバージョンがその値より低いとプラグインの読み込みを拒否する**。書かないと旧式のプラグインとして読み込まれ、警告が出る | [プラグインの基礎](/tutorials/java/plugins) |
| YAML | YAML Ain't Markup Language | ほとんどのプラグインと Paper 系の設定ファイルが使う形式。**インデントがそのまま文法**で、空白を使い、タブを使わない。インデントを間違えるとそのまま解析に失敗する | [サーバーの設定](/tutorials/java/config) |
| 正規アカウント認証 | online-mode | `server.properties` の `online-mode`。有効にするとサーバーは Mojang のセッションサービスにプレイヤーの身元を問い合わせる | [サーバーの設定](/tutorials/java/config) |
| オフラインサーバー | offline-mode / cracked server | `online-mode=false` のサーバー。プレイヤー名は自由に書け、**誰でも他人の名前を騙れる**。公式の UUID も得られない | [サーバーの設定](/tutorials/java/config) |
| UUID | Universally Unique Identifier | プレイヤーの一意な識別子。正規サーバーでは Mojang のセッションサービスが与え、オフラインサーバーではサーバーが名前から導出する。**同名なら同じ UUID、改名すれば別人** | [よく使うサーバーコマンド](/tutorials/java/commands) |
| ホワイトリスト | whitelist | 名簿のプレイヤーだけ入室を許す仕組み。関連するキーは `white-list`、名簿のファイルは `whitelist.json`。`enforce-whitelist` は再読み込み後に名簿にないオンラインのプレイヤーを蹴るかどうかを決める | [サーバーの設定](/tutorials/java/config) |
| OP / 管理者 | operator | サーバーの管理コマンドの権限を持つプレイヤー。`ops.json` に記録される。**OP を与えることは大きな権限を渡すこと**なので、渡す前に考える | [よく使うサーバーコマンド](/tutorials/java/commands) |
| RCON | Remote Console | ネットワーク経由でサーバーへコンソールコマンドを送るプロトコル。既定のポートは 25575。**暗号化されず**、パスワードもコマンドも傍受され得る。**ローカルか暗号化トンネルの中だけで使うべき** | [ネットワークセキュリティの基礎](/tutorials/ops/network-security) |

### 3.1 これらのコアの関係

並列する 5 つの選択肢ではなく、**継承の連鎖**です。

```text
バニラサーバー (vanilla)
  └─ Bukkit / CraftBukkit  プラグイン API を提供
       └─ Spigot           性能と修正
            └─ Paper       大量の最適化と修正（現在の主流）
                 ├─ Purpur 遊び方の選択肢を追加
                 └─ Folia  区域化した並行 tick
```

この連鎖を理解する効用は、**Paper の設定ファイルに Spigot と Bukkit のキーが出てくる**（`spigot.yml`、`bukkit.yml`）ことです。上流から継承しているからです。見慣れないファイル名を見たら、まず連鎖のどの層に属するかを考えてください。

### 3.2 正規アカウント認証、UUID、ホワイトリストの関係

この 3 語はよく一緒に議論されます。**互いに決め合う**からです。

- **正規サーバー**（`online-mode=true`）：プレイヤーの身元は Mojang のセッションサービスが確認し、UUID はアカウント単位です。**改名しても身元は変わらない**。ホワイトリスト、権限、経済データはすべてこの UUID に紐づきます。
- **オフラインサーバー**（`online-mode=false`）：サーバーがプレイヤー名から UUID を導出します。**改名すれば別人になり**、他人の名前を騙れば他人になりすましたことになります。

正規サーバーをオフラインサーバーへ変える（またはその逆）と、**既存プレイヤーの UUID が変わります**。結果としてホワイトリスト、権限、経済データ、領地がすべて人と合わなくなります。これは「スイッチを 1 つ変える」話ではなく、移行の前に必ずバックアップを取り、身元の対応を確認してください。[バックアップと復元](/tutorials/java/backup) を参照。

:::warn RCON をインターネットに露出させない
RCON の設計目標はローカルか信頼できるネットワーク内での遠隔管理で、**プロトコル自体が暗号化されません**。これをインターネットにマッピングするのは、コンソールをスキャナに渡すのと同じです。遠隔で使う必要があるときは SSH トンネルか VPN を通してください。[ネットワークセキュリティの基礎](/tutorials/ops/network-security) を参照。
:::

### 3.3 設定ファイルは 3 種類。混ぜないこと

初心者の最もよくある混乱の源は、階層の違う設定ファイルを同じものとして扱うことです。実際には役割がはっきり分かれています。

| 種類 | 典型的なファイル | 誰が生成するか | 間違えるとどうなるか |
| --- | --- | --- | --- |
| サーバー本体の設定 | `server.properties` | サーバーの初回起動時に生成 | キー名を間違えると無視されるか既定値に戻る。**変更は再起動で反映** |
| サーバーブランチの設定 | `spigot.yml`、`bukkit.yml`、`paper-world-defaults.yml` など | 該当するブランチの初回起動時に生成 | メカニズムと性能に影響する。**生電の場面ではとくに敏感** |
| プラグインの設定 | `plugins/<plugin-name>/config.yml` など | プラグインの初回読み込み時に生成 | 形式の誤りはプラグインの読み込み失敗につながる。**原因は通常ログに書かれる** |

実用的な経験則：**どの設定ファイルも、変える前にコピーを取る**。設定ファイルはプレーンテキストで容量もごく小さく、バックアップのコストはほぼゼロですが、壊した後の調査コストは非常に高いです。バックアップの範囲とロールバックの流れは [バックアップと復元](/tutorials/java/backup) を参照してください。

### 3.4 ホワイトリストと OP は別物

この 2 語はよく一緒に語られますが、制御する対象はまったく違います。

| | ホワイトリスト（whitelist） | OP（operator） |
| --- | --- | --- |
| 何を制御するか | **誰が入室できるか** | **入室した後に何ができるか** |
| 置き場所 | `whitelist.json` | `ops.json` |
| 関連するスイッチ | `white-list`、`enforce-whitelist` | `op-permission-level` が OP の既定の権限レベルを決める |
| よくある誤解 | ホワイトリストを有効にすれば安全だと思う | OP は「コマンドが少し増えるだけ」だと思う |

**OP を与えることは、世界を変えるコマンドを実行できることを含む大きな権限を渡すこと**です。渡す前に、相手が誰か、その権限を取り戻せるかを考えてください。関連するコマンドは [よく使うサーバーコマンド](/tutorials/java/commands) を参照。

## 4. 統合版の概念

統合版のエコシステムは Java 版とほとんど重ならず、用語も独自の体系です。

| 用語 | 英語 | 解説 | 関連ドキュメント |
| --- | --- | --- | --- |
| BDS | Bedrock Dedicated Server | Microsoft が公式に公開する統合版専用のサーバー。**オープンソースではなく**、プラグインの能力は限られ、通常はビヘイビアパックとスクリプトで拡張する | [統合版 BDS](/tutorials/bedrock/bds) |
| プロトコルバージョン | protocol version | クライアントとサーバーが通信するデータ形式のバージョン。**統合版のクライアントは自動で更新される**ので、サーバーが追随しないと接続できず、統合版サーバーで最もよくある故障 | [統合版のプロトコルとバージョン](/tutorials/bedrock/protocol) |
| Addon | add-on | 統合版の拡張コンテンツの総称。ビヘイビアパック、リソースパックなどで構成され、ワールドの設定から読み込む | [統合版サーバーの種類](/tutorials/bedrock/type) |
| ビヘイビアパック | behavior pack | Addon のうちロジックとルールを担う部分。エンティティの追加、ドロップの変更、スクリプトの記述ができる | [統合版サーバーの種類](/tutorials/bedrock/type) |
| リソースパック | resource pack | Addon のうち外見と音を担う部分。テクスチャ、モデル、効果音、画面の文字 | [統合版サーバーの種類](/tutorials/bedrock/type) |
| allowlist.json | allowlist.json | 統合版サーバーのホワイトリストのファイルで、`server.properties` の `allow-list` スイッチに対応する。**ファイル名が Java 版の `whitelist.json` と異なる** | [統合版 BDS](/tutorials/bedrock/bds) |
| permissions.json | permissions.json | 統合版サーバーでプレイヤーの権限レベルを指定するファイル。レベルは visitor、member、operator。`server.properties` の `default-player-permission-level` が新規プレイヤーの既定のレベルを決める | [統合版 BDS](/tutorials/bedrock/bds) |
| Xbox Live 認証 | Xbox Live authentication | 統合版のアカウント体系。**リモート（非 LAN）のサーバーへ接続するときは常に Xbox Live の認証が必要**で、`online-mode` は主にローカルと LAN の場面に影響する | [統合版のプロトコルとバージョン](/tutorials/bedrock/protocol) |
| Nukkit | Nukkit | Java で書かれた統合版サーバーの実装で、Bukkit に似たプラグイン API を提供する。元のプロジェクトの活発さは大きく低下している | [サードパーティの統合版サーバー](/tutorials/bedrock/third-party) |
| PMMP | PocketMine-MP | PHP で書かれた統合版サーバーの実装で、プラグインのエコシステムが成熟し、コミュニティも大きい | [サードパーティの統合版サーバー](/tutorials/bedrock/third-party) |
| PNX | PowerNukkitX | Nukkit の活発な後継ブランチの 1 つで、保守を続けて新しいバージョンに追随することを目標にしている | [サードパーティの統合版サーバー](/tutorials/bedrock/third-party) |

### 4.1 統合版サーバーが「更新したら入れなくなる」理由

**クライアントは自動で更新されるが、サーバーは更新されない**からです。公式 BDS の更新のテンポはクライアントのバージョンに縛られ、サードパーティの実装の追随は通常もっと遅いです。プレイヤーのスマートフォンのクライアントが新しいバージョンになっても、サーバーは古いプロトコルバージョンのままで、結果として接続できません。

これが「プロトコルバージョン」という言葉が統合版で極めて頻出する理由でもあります。対応の方法と各実装の追随状況は [統合版のプロトコルとバージョン](/tutorials/bedrock/protocol) を参照してください。

### 4.2 サードパーティの実装は自分で評価する

Nukkit、PMMP、PNX はいずれも**公式のサーバーではありません**。バニラのメカニズムの再現度、更新の速さ、プラグインの品質には大きな差があります。選ぶ前に 3 つを確認してください。**必要なプロトコルバージョンに追随しているか**、**プラグインのエコシステムが要件を満たすか**、**プロジェクトが最近も保守されているか**。[サードパーティの統合版サーバー](/tutorials/bedrock/third-party-setup) を参照。

:::note 用語をバージョン間で流用しない
`whitelist.json`（Java 版）と `allowlist.json`（統合版）は別のファイルです。Java 版の「プラグイン」と統合版の「ビヘイビアパック」は同じ類のものではありません。**グループで質問するときは、まずどのバージョンかを明記する**と、往復を大量に省けます。
:::

## 5. 生電と技術の分類

この一群の言葉は「技術向けサバイバル」（生電）のプレイヤーの日常で、**性能の最適化と最も衝突しやすい**種類の要求でもあります。

| 用語 | 英語 | 解説 | 関連ドキュメント |
| --- | --- | --- | --- |
| 生電 | technical Minecraft | 「サバイバル + 回路」。レッドストーン装置、 mob トラップ、正確なブロックとエンティティの挙動を核とする技術向けサバイバル。**バニラの挙動が変更されているかに極めて敏感** | [生電とレッドストーン](/tutorials/java/redstone) |
| モブトラップ | mob farm / mob grinder | スポーンの仕組みを利用して生物を集中させて倒し、ドロップ品を得る装置。同時に**性能の大食い**でもある。エンティティが多く、ドロップ品が多く、チャンクが常時読み込まれる | [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) |
| レッドストーンクロック | redstone clock | 周期的にレッドストーンの信号を出力し、他の装置を定時に起動する回路。**高周波のクロックは MSPT スパイクの典型** | [生電とレッドストーン](/tutorials/java/redstone) |
| TNT 複製 | TNT duplication | 特定のバージョンの仕組みを利用して TNT エンティティを複製する技で、多くの大型工事の基礎。**一部のサーバーブランチは性能やバランスのためにこの挙動を変えており**、複製が効かなくなる | [生電とレッドストーン](/tutorials/java/redstone) |
| エンティティの有効範囲 | entity activation range | Spigot 系が導入した仕組み。**一定の距離を超えたエンティティは読み込まれないのではなく、tick の頻度が下がる**。小さくすると CPU を節約できるが、遠くの装置の挙動がおかしくなる | [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) |
| チャンクの読み込み / 強制読み込み | chunk loading / force load | チャンクは読み込まれて初めて tick する。プレイヤー、スポーン地点のチャンク、ポータル、`/forceload`、プラグインが読み込みを維持できる。**強制読み込みは人為的に長期間読み込んだままにすること**で、代償は常駐する CPU とメモリのコスト | [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) |
| モブの上限 | mob cap | 1 つのワールドに同時に存在できる生物の数の上限。`bukkit.yml` の `spawn-limits` などで設定し、Paper 系はワールド単位での上書きや、プレイヤーごとの計算にもできる | [エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) |

### 5.1 「読み込み」と「tick」は別物

初心者はこの 2 語を混ぜて使いますが、異なる段階を表します。

| 段階 | 意味 | 典型的なコスト |
| --- | --- | --- |
| 読み込み（load） | チャンクのデータがメモリ上にあり、読み書きできる | メモリ、ディスク I/O |
| tick | チャンク内のエンティティ、ブロックエンティティ、ランダム tick が規則どおり進む | CPU（メインスレッド） |

チャンクは**読み込まれても tick されない**ことがあり（たとえばシミュレーション距離の外）、強制読み込みによって**長期間、読み込まれかつ tick される**こともあります。ドロップ品そのものがチャンクの読み込みを維持するわけではありませんが、そのチャンクが別の理由で読み込まれたままなら、中のドロップ品は tick され続け、溜まり続けます。この区別が「エンティティが増え続ける」の調査の鍵です。[エンティティとドロップ品の堆積](/tutorials/faq/entity-lag) を参照してください。

### 5.2 最適化と生電はしばしば両立しない

「有効範囲を小さくし、モブの上限を下げ、ホッパーの検査を緩める」と TPS は良くなりますが、**農場や装置はそのまま動かなくなります**。村人が補充しなくなり、 mob トラップが生産しなくなり、アイテムの分離に依存する装置が崩れます。生電サーバーは逆であるべきです。バニラの挙動に影響する項目をバニラに戻すか、バニラに近いコアへ変える。[生電とレッドストーン](/tutorials/java/redstone) と [性能の最適化](/tutorials/java/optimize) を参照してください。

:::warn 設定を変える前にバックアップ
「性能のため」のどんな変更もゲームのメカニズムを変え得ます。**変える前に設定ファイルをバックアップし、変えた後に装置を再試験する**のが、生電サーバーの決まった流れです。バックアップの範囲は [バックアップと復元](/tutorials/java/backup) を参照。
:::

## 6. 運用の分類

この一群の言葉は、「サーバーを長期的に保守すべきものとして扱う」ようになって必ず出会うものです。

| 用語 | 英語 | 解説 | 関連ドキュメント |
| --- | --- | --- | --- |
| バックアップ | backup | ワールドと設定を、事故のときに復元できるコピーにすること。**コピーするだけで復元を検証しないのは、バックアップに数えない** | [バックアップと復元](/tutorials/java/backup) |
| 遠隔地バックアップ | offsite backup | バックアップのコピーを**ホストと異なる物理的な場所か、異なるサービス提供者**に置くこと。ホストの全損、侵入、データセンターの事故のとき、ローカルのバックアップも一緒に消える | [遠隔地バックアップ](/tutorials/ops/offsite-backup) |
| 3-2-1 原則 | 3-2-1 rule | 一般的なバックアップの経験則。**少なくとも 3 部のコピー、2 種類の異なる媒体、そのうち 1 部は遠隔地**。経験のまとめであり、規格ではない | [遠隔地バックアップ](/tutorials/ops/offsite-backup) |
| 遠隔地 | off-site | ホストと同じ物理的な場所になく、同じ事故の影響を受けない保存場所。**同じマシンの別のディレクトリ、同じマシンの別のディスクは、遠隔地に数えない** | [遠隔地バックアップ](/tutorials/ops/offsite-backup) |
| UPS | Uninterruptible Power Supply | 無停電電源装置。主な価値は「停電しても遊び続けられる」ことではなく、**サーバーが安全に停止する数分を稼ぐ**ことで、書き込み中のハードな電源断によるセーブデータの破損を避ける | [ラック、スイッチと UPS](/tutorials/ops/hardware-rack) |
| パネル | panel / control panel | Web 画面でサーバーを管理するツール。起動停止、コンソール、ファイル管理、バックアップなどを提供し、Pterodactyl、MCSManager などが代表的。**同時に新しい攻撃面でもある** | [パネル管理](/tutorials/ops/panels) |
| デーモン | daemon | バックグラウンドに常駐し、具体的な処理を担うプログラム。パネルの構成では通常、管理対象の各マシンで 1 つのデーモンが動き、**Web 側との通信は重点的に強化する必要がある** | [パネル管理](/tutorials/ops/panels) |
| DDoS | Distributed Denial of Service | 分散型サービス拒否攻撃。大量の送信元からの流量で、対象の帯域や接続資源を埋める。**ホスト側にできることは限られ、通常はサービス提供者が上流でクリーニングする必要がある** | [よくあるネットワーク攻撃と防御](/tutorials/ops/attack-defense) |
| 速度制限 | rate limiting | 単位時間あたりの接続数やリクエスト数を能動的に制限し、少数の送信元が資源を使い切るのを避ける。**緩和の手段であり、根治の手段ではない**。厳しくしすぎると正常なプレイヤーを傷つける | [よくあるネットワーク攻撃と防御](/tutorials/ops/attack-defense) |
| フォレンジック | forensics | 再起動、再インストール、BAN の前に、**数分後には永久に消える現場**を固定すること。プロセス、接続、ログ、タイムライン。**順序を間違えると証拠は消える** | [インシデント対応とフォレンジック](/tutorials/ops/incident-forensics) |
| 事後分析 | post-mortem analysis | 事故の後に「そのとき何が起きたか」を調べること。**過去を説明できるだけで、次を止められない** | [spark でサーバー性能を分析する](/tutorials/ops/spark) |
| 事前アラート | alerting | 問題がプレイヤーに影響する前に、システムから能動的に知らせること。事後分析とは補完の関係で、代替ではない | [監視とアラート](/tutorials/ops/monitoring) |
| ディスク I/O の待ち | I/O wait | CPU がディスクの読み書きの完了を待って空回りしている時間の割合。**これが高いとき、サーバーは「計算していない」ように見えるのに、とにかく遅い** | [ラック、スイッチと UPS](/tutorials/ops/hardware-rack) |
| ランブック | runbook | 「あるアラートが鳴ったらどうするか」を前もって書いた処理手順。**ランブックのないアラートは、深夜にあなたを起こして、どう扱えばいいか分からない問題を見せるだけ** | [監視とアラート](/tutorials/ops/monitoring) |

### 6.1 「バックアップ」という言葉は誤用がひどい

日常の会話で「バックアップした」は、少なくとも 4 つの異なることを指し得ます。

| 言い方 | 実際の意味 | 足りるか |
| --- | --- | --- |
| 「world フォルダをコピーした」 | 同じマシン上のコピーがある | 誤削除は防げるが、マシン全体の故障は防げない |
| 「バックアップスクリプトが毎日動いている」 | 定時に実行されるタスクがある | **終了コードを見ないと成功したか分からない** |
| 「バックアップファイルはある」 | ディスク上にアーカイブがある | **復元を検証していないならバックアップに数えない** |
| 「バックアップから 1 回復元した」 | 実際に別の場所で復元して起動に成功した | これが使えるバックアップ |

4 つの層のうち、本当に命を救えるのは最後の層だけです。**復元の検証方法**は [遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照してください。

### 6.2 UPS が運用の言葉である理由

停電と「サーバーが落ちた」は性質の違う出来事だからです。**サーバーのクラッシュは通常セーブデータを壊しません**（プロセスは異常終了するが、ファイルシステムは一貫したまま）。一方、**書き込み中のハードな電源断は書きかけのファイルを残し**、軽ければ数チャンクを失い、重ければセーブデータが読み込めなくなります。

だから UPS の位置づけは「サーバーが安全に停止する機会を作る」ことで、「停電してもプレイヤーが遊べる」ことではありません。選定、NUT の監視、自動シャットダウンの設定は [ラック、スイッチと UPS](/tutorials/ops/hardware-rack) と [家庭用 PC での開設と保守](/tutorials/ops/home-hosting) を参照してください。

:::tip 最も見落とされる 1 条
上の言葉のうち、繰り返し無視されるのは**「復元の検証」**です。バックアップファイルがあり、スクリプトの終了コードが 0 でも、サーバーを復元できるとは限りません。定期的に本当に 1 回復元してください。[遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照。
:::

## 7. 用語に対応するよく使うコマンド

用語は具体的なコマンドに落ちて初めて役に立ちます。次の表は、前の節で最もよく出る言葉と「現状をひと目見る」コマンドを対応させたものです。**これらのコマンドの出力形式はディストリビューションとバージョンで変わるため、あなたのシステムの実際の出力に従ってください。**

| 確認したい言葉 | コマンド | 何を見るか |
| --- | --- | --- |
| ホスト全体の負荷 | `uptime` | 末尾の 3 つの数字は 1、5、15 分の平均負荷。**CPU のコア数と一緒に見る**。1 コアの飽和は 1.00 |
| メモリとスワップ | `free -h` | `available` の列を重点的に。`free` より「あとどれだけ使えるか」に近い |
| ディスクの空き | `df -h` | マウントポイントごとの残り容量。**ディスクが満杯だとサーバーはセーブデータを書けない** |
| ディスクの健全性 | `smartctl -a /dev/sdX` | 通電時間、書き込み量、再割り当てセクタなどの属性。コマンドは `smartmontools` のもの |
| ネットワーク接続の概要 | `ss -s` | 各種 socket の総数。**接続数の異常な増加はメモリの枯渇より先に現れることが多い** |
| 待ち受けポート | `ss -lntp` / `ss -lunp` | TCP / UDP がそれぞれどのポートを、どのプロセスが持っているか |
| サービスの状態 | `systemctl status <service-name>` | active か、直近の終了、直近のログの断片 |
| サービスのログ | `journalctl -u <service-name>` | `--since "1 hour ago"` で範囲を絞る。**フォレンジックのときは `--utc` を付ける** |
| HTTP の可用性 | `curl -s -o /dev/null -w '%{http_code}' <URL>` | 状態コードだけを出力。スクリプトの判断に組み込みやすい |
| UPS の状態 | `upsc <ups-name>` | `ups.status` が `OL` なら商用電源、`OB` ならバッテリー給電。変数名は NUT のドキュメントと機種に従う |

:::tip 1 回の結果だけを見ない
`free -h` と `df -h` は**スナップショット**で、1 回の結果ではほとんど何も分かりません。役に立つのは**傾向**です。ディスクが毎週増えているか、メモリが毎日登っているか。傾向は定時の収集が必要です。[監視とアラート](/tutorials/ops/monitoring) を参照。
:::

## 8. 用語の関係

ばらばらの名詞を暗記しても役に立ちません。**いくつかの因果の連鎖につなげて**初めて役に立ちます。

| やりたいこと | 先に理解すべき用語 | なぜ |
| --- | --- | --- |
| サーバーが重いか判断する | tick、TPS、MSPT、50 ms の予算 | 「重い」を指標に翻訳して初めて調査を始められる |
| サーバーコアを選ぶ | プラグイン、MOD、生電、プロキシ | コアが使える拡張と、バニラの挙動が変わっているかを決める |
| プラグインを設定する | YAML、前提、API、NMS、api-version | 「プラグインが赤くなる」の多くはこの数語に由来する |
| プレイヤーを管理する | online-mode、UUID、ホワイトリスト、OP | 身元と権限はすべて UUID に紐づく |
| 統合版サーバーを開く | BDS、プロトコルバージョン、ビヘイビアパック、allowlist.json | 統合版は独自の体系で、Java 版の経験は通用しない |
| データを守る | バックアップ、遠隔地、3-2-1、UPS、フォレンジック | 事故のときに救えるのはこれらだけ |
| 長期的に保守する | パネル、デーモン、DDoS、速度制限、監視とアラート | サーバーを継続的に見守るべきものとして扱う |

## 10. 症状の対照表

| 見えている現象 | まず思い浮かべる用語 | どこを見るか |
