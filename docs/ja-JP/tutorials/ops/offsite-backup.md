ローカルのバックアップは「うっかり消した」は救えても、「ディスクが壊れた」「マシンを盗まれた」「データセンターで事故が起きた」は救えません。**遠隔地バックアップ（offsite backup）が解決するのは、こうした「環境ごと消える」災害**です。この記事ではその原理、設定、保守を整理します。

ローカルバックアップの基礎（何をバックアップするか、一貫性の要件、ロールバックの流れ）は [バックアップと復元](/tutorials/java/backup) を参照してください。本記事は、ローカルバックアップがすでにあり、そのコピーを外へ出す段階を前提とします。

## 1. 3-2-1 原則

3-2-1 は広く引用されるバックアップの経験則です。

| 数字 | 意味 | MC サーバーへの落とし込み |
| --- | --- | --- |
| **3** | データのコピーを**3 部**以上保つ（1 部が本番 + 2 部がバックアップ） | 稼働中のサーバーディレクトリ + ローカルのバックアップディスク + 遠隔地のコピー |
| **2** | **2 種類以上の異なる媒体 / ストレージ**を使う | たとえば内蔵 SSD + 外付けディスク + オブジェクトストレージ |
| **1** | 少なくとも**1 部は遠隔地**に | クラウドストレージ、別のマシン、別の物理的な場所 |

### 「同じディスク上のバックアップ」がバックアップにならない理由

バックアップを**サーバーと同じディスク**に書くと、防げる障害は 1 種類だけです。誤削除、設定の誤り、プラグインによるセーブデータの破壊。**ディスク自体の故障**（バックアップも一緒に消える）、**マシン全体の故障**（マザーボードや電源が焼けて 2 台のディスクが同時に逝く）、**ランサムウェア**（書き込めるボリュームはすべて暗号化される）、**人為的な破壊**（誰かがディレクトリごと `rm -rf` した、マシンを持ち去った）、そして**火災、水害、盗難**は防げません。

### 3 つの典型的な災害シナリオ

| シナリオ | ローカルのバックアップで足りるか | 遠隔地バックアップの役割 |
| --- | --- | --- |
| ディスクの故障 / マシンの廃棄 | 足りない（バックアップが同じディスクなら） | 遠隔地のコピーから直接復元する |
| ランサムウェアが書き込めるボリュームをすべて暗号化 | **足りない** | 読み取り専用か不変の遠隔地コピーが唯一の出口 |
| 事業者の夜逃げ / データセンターの事故 / アカウントの乗っ取り | **足りない** | コピーが自分のストレージにある |

:::warn 遠隔地のコピーは「バックアッププログラムが書けて、攻撃者が消せない」ものでなければならない
遠隔地のストレージが同じ資格情報、同じ書き込み可能なアカウントなら、ランサムウェアは同じように消せます。**読み取り専用 / 不変（object lock、WORM、append-only）にできるならそうする**。できないまでも、少なくともバックアップ用アカウントには書き込み権限だけを与え、削除権限は与えないでください。
:::

## 2. 何をバックアップし、何をしないか

| 必要性 | 内容 | 説明 |
| --- | --- | --- |
| 必須 | `world/`、`world_nether/`、`world_the_end/` | **セーブデータ本体。最も重要**。カスタムのワールド名は `level-name` に従う |
| 必須 | `server.properties` | ポート、難易度、正規アカウント認証、`level-name` など |
| 必須 | `ops.json`、`whitelist.json`、`banned-ips.json`、`banned-players.json` | 権限と BAN の名簿 |
| 必須 | `plugins/`（各プラグインの設定とデータベースを含む） | プラグイン本体と設定。データを別の場所に書くプラグインもあるので注意 |
| 必須 | `mods/`、`config/`（MOD 側） | MOD 側専用。`config/` には MOD の設定が入る |
| 必須 | コア自身の設定（`bukkit.yml` / `spigot.yml` / `paper-*.yml` など） | コアによって異なる |
| 必須 | 起動スクリプト、systemd unit、cron の項目 | **漏れやすい**。復元時にこれがないと起動できない |
| 任意 | `logs/`、`crash-reports/` | 問題の調査に役立つが、容量が大きくなる |
| 不要 | `libraries/`、`versions/`、`cache/` | 自動で再生成できる |

:::tip 「起動方法」もバックアップすべきデータとして扱う
「セーブデータは復元したのにサービスが起動しない」はよくある事故で、原因は起動スクリプト、Java の引数、systemd unit、定期タスクがバックアップされていないことです。**これらも設定と一緒にバックアップの範囲に入れてください。**
:::

### 一貫性：サーバーが書き込んでいる最中にコピーしない

**サーバーがセーブデータを書き込んでいる最中にそのままコピーしないでください**。書きかけのチャンクファイルを複製してしまい、復元後にセーブデータが壊れます。正しい方法は 2 つです。

**方法 A：ホットバックアップ（停止しない）**

```text
save-all        まずデータをディスクへ書き出す
save-off        自動保存を止める（バックアップ中に書き込みが続かないように）
（この時点でコピー / アーカイブを実行）
save-on         バックアップが終わったら自動保存を戻す
```

**方法 B：停止してのバックアップ（最も確実）**

```text
stop            安全に停止する
（ディレクトリ全体をコピー / アーカイブする）
（再起動する）
```

方法 A は**サーバーのコンソールへコマンドを送る**必要があります。systemd で管理していて起動方法がコンソール入力を受け取れるなら、`screen`/`tmux` で注入するか、RCON を有効にして遠隔からコマンドを送ります（**RCON の設定方法はコアとバージョンで異なるため、公式ドキュメントに従ってください**）。

:::warn アーカイブツールが読んでいる間もサーバーは書き続ける
`tar`、`rsync`、`restic` はすべて**読みながらたどります**。`save-all` を実行した直後でも、`save-off` をしていなければ、サーバーは走査の途中で新しいデータを書き込み、**アーカイブに一貫性のない組み合わせが入り得ます**。`save-off` の段階は省けません。
:::

## 3. SSH 経由の rsync

`rsync` は最も古典的な遠隔地の差分同期の方案です。変化した部分だけを送り、SSH の暗号化経路を通り、ほぼすべての Linux ディストリビューションに入ります。

### 完全なコマンド例

```bash
rsync -aHAX --delete --numeric-ids --info=progress2 \
  --exclude='logs/' \
  --exclude='crash-reports/' \
  --exclude='cache/' \
  --exclude='libraries/' \
  --exclude='versions/' \
  --exclude='*.tar.gz' \
  --link-dest=/srv/backup/mcserver/2026-10-03 \
  /opt/mcserver/ \
  backup@backup.example.com:/srv/backup/mcserver/2026-10-04/
```

### 項目ごとの説明

| オプション | 役割 |
| --- | --- |
| `-a` | アーカイブモード。`-rlptgoD` と同等（再帰、シンボリックリンク、権限、時刻、グループ、デバイスファイルを保持） |
| `-H` | ハードリンクを保持する（**サーバーのディレクトリにハードリンクがあると、付けないと複数に展開される**） |
| `-A` | ACL（アクセス制御リスト）を保持する |
| `-X` | 拡張属性（xattr）を保持する |
| `--delete` | 移行先で「移行元に存在しない」ファイルを削除し、移行先を移行元と一致させる。**これはもろ刃の剣**。移行元での誤削除も同期される |
| `--numeric-ids` | ユーザー名 / グループ名ではなく数値の UID/GID で対応付ける。マシンをまたぐ場合や、移行先に同名のユーザーがいない場合は**必須** |
| `--info=progress2` | 全体の進捗を表示する（rsync 3.1 以降） |
| `--exclude` | バックアップ不要なディレクトリを除外する |
| `--link-dest=DIR` | **ハードリンクスナップショット**：DIR と内容が同じファイルはコピーせず、移行先にハードリンクを作る。結果として、各日付のディレクトリは完全なコピーに見えるが、実際は差分の容量しか使わない |

:::warn `-A` と `-X` は両側の対応が必要
ACL と xattr の保持には、rsync が十分に新しいこと、移行先のファイルシステムがこれらの機能に対応していること、そして**すべてのファイルの ACL/xattr を読むために通常 root で実行する必要**があります。移行先のファイルシステム（一部のネットワークストレージなど）が対応していないと、rsync はエラーを出すか黙って捨てます。**不安ならまず `-A -X` を外してください**。
:::

### まず dry-run

**`--delete` を含むコマンドは、初回に必ず `-n`（`--dry-run`）を付けて一度実行してください**。

```bash
rsync -aHAX --delete --numeric-ids -n -i \
  --exclude='logs/' --exclude='cache/' \
  /opt/mcserver/ backup@backup.example.com:/srv/backup/mcserver/
```

`-n`（`--dry-run`）は何をするかを表示するだけで実際には変更せず、`-i`（`--itemize-changes`）は変更を 1 件ずつ列挙するので、`--delete` が何を消すかを確認できます。**出力に「消えては困るもの」がないことを確認してから `-n` を外してください。**

### SSH のパスワードなしログイン

バックアップスクリプトは無人で動く必要があるので、鍵でログインします。

```bash
ssh-keygen -t ed25519 -C "mc-backup@home"
ssh-copy-id backup@backup.example.com
ssh backup@backup.example.com 'echo ok'
```

`ssh-keygen -t ed25519` は Ed25519 の鍵ペアを生成し、既定では `~/.ssh/id_ed25519`（秘密鍵）と `~/.ssh/id_ed25519.pub`（公開鍵）に置きます。**秘密鍵にパスフレーズを設定するほうが安全ですが、定期タスクでは ssh-agent か `keychain` がないと対話なしで使えません。無人で動くバックアップ機では通常パスフレーズを設定しないので、そのぶん権限を厳しく制限する必要があります。** `ssh-copy-id` は公開鍵を移行先の `~/.ssh/authorized_keys` に追記します。**一部のプラットフォーム（Windows の OpenSSH や一部の軽量システム）にはこのコマンドがない**ことがあるので、その場合は公開鍵の中身を手で追記してください。移行先の `authorized_keys` ではこの鍵を制限することを勧めます。

```text
from="203.0.113.10",command="/usr/bin/rrsync -wo /srv/backup/mcserver/",no-port-forwarding,no-pty ssh-ed25519 AAAA... mc-backup@home
```

`rrsync` は rsync に同梱される制限付きのラッパースクリプトで、指定したディレクトリへの書き込みだけを許可します。**`rrsync` のパスと可用性はディストリビューションで異なります**（Debian/Ubuntu は `rsync` パッケージに入っていて、パスは `/usr/bin/rrsync` のことがあります）。使う前に確認してください。

### cron の例

```cron
0 4 * * * /usr/local/bin/mc-backup.sh >> /var/log/mc-backup.log 2>&1
```

5 つのフィールドは順に、分、時、日、月、曜日です。したがって `0 4 * * *` は**毎日 04:00**、`>> /var/log/mc-backup.log 2>&1` は標準出力と標準エラーをログに追記し、後から終了コードとエラーを確認できるようにします。**cron の環境変数はごく少なく（`PATH` も短い）なので、スクリプトでは絶対パスを使ってください**。ログのローテーションが必要なら `/etc/logrotate.d/` に規則を追加します。さもないとログは増え続けます。

## 4. バックアップスクリプトの骨格

以下は**そのまま使える bash の骨格**です。まず書き込みを凍結し、ワールドと設定をアーカイブし、期限切れのアーカイブを片付け、それから rsync で遠隔地へ送り、結果をログに書きます。

```bash
#!/usr/bin/env bash
# 遠隔地バックアップスクリプトの骨格。環境に合わせて変数を変更してください。
set -euo pipefail

SERVER_DIR="/opt/mcserver"                 # サーバーのディレクトリ（末尾にスラッシュを付けない）
BACKUP_ROOT="/srv/backup/mcserver"         # ローカルバックアップのルート（SERVER_DIR と別ディスクを推奨）
LOG_FILE="/var/log/mc-backup.log"
KEEP_DAYS=14                               # ローカルアーカイブの保持日数
REMOTE="backup@backup.example.com:/srv/backup/mcserver"   # 遠隔地のターゲット

STAMP="$(date +%F_%H%M%S)"
ARCHIVE="${BACKUP_ROOT}/mcserver-${STAMP}.tar.gz"

log() { printf '%s %s\n' "$(date '+%F %T')" "$*"; }
fail() { log "ERROR: $*"; exit 1; }

# スクリプト自身の出力もログに書く。cron のリダイレクトは二重の保険
exec >>"${LOG_FILE}" 2>&1
log "=== backup start ${STAMP} ==="

[ -d "${SERVER_DIR}" ] || fail "server directory not found: ${SERVER_DIR}"
mkdir -p "${BACKUP_ROOT}"

# 停止してのバックアップが最も確実。停止できない場合は、コンソールへ save-all / save-off を送り、アーカイブ後に save-on する
START_AFTER=0
if systemctl is-active --quiet minecraft.service; then
    log "stopping minecraft.service for a consistent backup"
    systemctl stop minecraft.service
    START_AFTER=1
fi

tar -czf "${ARCHIVE}" \
    --exclude='logs' \
    --exclude='crash-reports' \
    --exclude='cache' \
    --exclude='libraries' \
    --exclude='versions' \
    --exclude='*.tar.gz' \
    -C "${SERVER_DIR}" .

[ -s "${ARCHIVE}" ] || fail "archive is missing or empty: ${ARCHIVE}"
log "archive created: ${ARCHIVE} ($(du -h "${ARCHIVE}" | cut -f1))"

# 直近 KEEP_DAYS 日分のローカルアーカイブを残し、それ以外を削除する（初回は -delete を外して対象を確認するのを推奨）
find "${BACKUP_ROOT}" -maxdepth 1 -name 'mcserver-*.tar.gz' -type f -mtime "+${KEEP_DAYS}" -print -delete

# 遠隔地へ同期する。ローカルの誤削除が同期されないよう、意図的に --delete は使わない
rsync -aHAX --numeric-ids --info=progress2 "${BACKUP_ROOT}/" "${REMOTE}/"
log "offsite sync finished"

if [ "${START_AFTER}" -eq 1 ]; then
    log "starting minecraft.service again"
    systemctl start minecraft.service
fi

log "=== backup ok ${STAMP} ==="
exit 0
```

### 使い方

```bash
sudo install -m 750 mc-backup.sh /usr/local/bin/mc-backup.sh
sudo /usr/local/bin/mc-backup.sh
tail -20 /var/log/mc-backup.log
```

必ず知っておくべき点：

- `set -euo pipefail` は、スクリプトを**エラーで即座に終了**させます。「バックアップは失敗したのにスクリプトは走り続け、最後に成功と報告する」のを避けます。
- **停止してのバックアップが最も確実**です。停止できないなら、`systemctl stop` をコンソールへの `save-all` / `save-off` に置き換え、アーカイブの完了後に `save-on` します（第 2 節を参照）。
- `find ... -mtime "+${KEEP_DAYS}" -delete` は**先に表示してから削除**します。初回は `-delete` を外し、マッチしたファイルが正しいことを確認してください。
- **遠隔地への同期は追加のみで、`--delete` は使わない**。さもないとローカルのアーカイブを誤って消したとき、遠隔地のコピーも同期して消えます。どうしてもミラー同期がしたいなら、ローカルの削除ロジックが絶対に信頼できることを確認してください。
- `systemctl` の unit 名、`tar` の除外パスは、実際のディレクトリに合わせて調整してください。**`tar` の `--exclude` はアーカイブ内のパスにマッチし、書き方が rsync と完全には同じではありません**。GFS 方式の保持（毎日 / 毎週 / 毎月）が必要なら、`find` を手書きするより restic の `forget --keep-*` のほうが楽です。

:::warn スクリプトの `--delete` は必ずよく考える
`rsync --delete` は移行先を移行元と完全に一致させます。**移行元が権限やマウントの失敗、パスの誤りで空のディレクトリになった場合、`--delete` は遠隔地のコピーも空にします。** これはバックアップ事故の古典的な原因です。
:::

## 5. その他のツールと選択

### restic：重複排除、暗号化、スナップショット

restic はスナップショット方式のバックアップツールで、**重複排除と暗号化を内蔵**します。「多くの履歴を残したいが容量は使いたくない」場面に向きます。

```bash
# 1. リポジトリを初期化する（1 回だけ）
export RESTIC_REPOSITORY="sftp:backup@backup.example.com:/srv/restic/mcserver"
export RESTIC_PASSWORD_FILE="/root/.config/restic/mcserver.pass"
restic init

# 2. バックアップ
restic -r "${RESTIC_REPOSITORY}" backup /opt/mcserver

# 3. スナップショットを見る
restic snapshots

# 4. 保持方針：毎日 7 個、毎週 4 個。その後、参照されていないデータを掃除する
restic forget --keep-daily 7 --keep-weekly 4 --prune
```

`RESTIC_PASSWORD_FILE` は **`chmod 600` にしたパスワードファイル**を指し、スクリプトに書き込んではいけません。`restic forget` はスナップショットの参照を消すだけで、**`--prune` を付けないと実際には容量を回収しません**。`--prune` は時間がかかるので、メンテナンス時間に置くのが望ましいです。復元は `restic restore latest --target /tmp/restore-test` で行います。リポジトリはローカルのディレクトリ、SFTP、S3 互換ストレージなど多様なバックエンドに置けます（**対応バックエンドの一覧は公式ドキュメントに従ってください**）。

### rclone：クラウドストレージの同期

rclone は「クラウドストレージの rsync」で、多数のオブジェクトストレージとネットドライブのバックエンドに対応します。

```bash
# 1. リモートを対話形式で設定する。名前はたとえば myremote
rclone config

# 2. ローカルのディレクトリをリモートへ同期する（リモートの余分なファイルも削除される。方向と意味に注意）
rclone sync /srv/backup/mcserver myremote:mcserver-backup --progress

# 3. 両端が一致するか検証する
rclone check /srv/backup/mcserver myremote:mcserver-backup
```

`rclone sync` は移行先を移行元と**完全に一致**させ、移行先の余分なファイルを削除します。追加だけしたいなら `rclone copy` を使います。`rclone check` は両端のファイルを比較します（既定ではサイズとハッシュを比較。**ハッシュに対応するかはバックエンド次第**）。`rclone config` は対話形式ですが、画面のない環境でも設定ファイルを手で書けます（パスは `rclone config file` で確認）。資格情報はそのファイルに入るので、**権限を `chmod 600` まで絞って**ください。

### 素の tar + scp

最も単純な組み合わせで、追加の依存がありません。

```bash
tar -czf /tmp/mcserver-$(date +%F).tar.gz -C /opt/mcserver .
scp /tmp/mcserver-$(date +%F).tar.gz backup@backup.example.com:/srv/backup/
```

**データ量がごく小さく、バックアップの頻度が低い**場面に向きます。欠点は、**毎回全量転送、重複排除なし、暗号化なし（SSH 経路を除く）、検証なし**で、データが大きくなると使えなくなることです。

### 比較

| ツール | 重複排除 | 暗号化 | 差分 | クラウド対応 | 複雑さ | 向く場面 |
| --- | --- | --- | --- | --- | --- | --- |
| **rsync** | いいえ（`--link-dest` で容量を節約） | いいえ（SSH 経路に依存） | はい（ファイル単位） | マウントが必要、または他のツールと併用 | 低 | SSH のターゲットがあり、構造が単純なディレクトリ |
| **restic** | **はい** | **はい（内蔵）** | はい（ブロック単位） | 多様なバックエンド（S3、SFTP など） | 中 | 多くの履歴を残したい、暗号化が必要 |
| **rclone** | いいえ | 転送の暗号化はバックエンド次第 | はい（ファイル単位） | **最も広い** | 中 | ターゲットがネットドライブ / オブジェクトストレージ |
| **tar + scp** | いいえ | いいえ | いいえ（全量） | ターゲットが scp できること | **最も低い** | データ量が小さく、たまのバックアップ |

## 6. 暗号化と鍵の管理

**遠隔地のコピーは必ず暗号化してください。** コピーを他人のストレージに置くのは、データを第三者に預けるのと同じです。オブジェクトストレージの鍵の漏洩、共有リンクの設定ミス、クラウドアカウントの乗っ取りは、いずれもセーブデータを直接露出させます（そこにはプレイヤーの IP、チャット記録、個人情報が含まれることもよくあります）。

- **restic は暗号化を内蔵**：リポジトリはパスワードから鍵を導出します。**パスワードを失えばデータは永久に開けません**。**rsync / rclone / tar+scp は中身を暗号化しません**。転送層（SSH、HTTPS）に頼るか、自分で先に暗号化します。

```bash
# gpg でアーカイブを対称暗号化する（対話形式でパスワードを入力）
gpg --symmetric --cipher-algo AES256 mcserver-2026-10-04.tar.gz

# 復号
gpg --decrypt mcserver-2026-10-04.tar.gz.gpg > mcserver-2026-10-04.tar.gz
```

### パスワードをどこに置くか

**バックアップのリポジトリ / ターゲットのストレージ自体には絶対に置かない**。**バックアップスクリプトと同じ書き込み可能なディレクトリにも置かない**。許容できるのは、**パスワードマネージャーに記録する**（人が読める）ことと、**バックアップ機の権限を厳しくしたファイルに置く**（スクリプトが読める）ことです。

```bash
sudo install -d -m 700 -o root -g root /root/.config/restic
sudo sh -c 'printf "%s" "あなたのパスワード" > /root/.config/restic/mcserver.pass'
sudo chmod 600 /root/.config/restic/mcserver.pass
sudo chown root:root /root/.config/restic/mcserver.pass
```

**パスワードはオフラインの記録を 1 部持ってください**（紙に書いて鍵をかける、別の端末のパスワードマネージャーに入れる）。**暗号化したバックアップ + パスワードの紛失 = データの全喪失**で、暗号化しないより徹底的に失います。鍵ファイル（SSH の秘密鍵、rclone の設定）も同様に `chmod 600` にし、**バックアップ専用の最小権限のアカウントだけ**にしてください。

:::warn 暗号化は「パスワードを設定すれば終わり」ではない
パスワードの強度、パスワードの保管、鍵のローテーションを考える必要があります。**スクリプトに書かれた弱いパスワードは、安全性がほぼゼロです。** また、暗号化すると**圧縮率は下がります**（暗号文は圧縮できない）ので、先に圧縮してから暗号化します。
:::

## 7. クラウドとオブジェクトストレージのターゲット

| 種類 | 例 | 特徴 |
| --- | --- | --- |
| 別のマシン / NAS | 友人の家の NAS、2 台目の VPS | 安く、制御できるが、自分で保守する必要 |
| S3 互換オブジェクトストレージ | 各種の S3 互換サービス、自前の MinIO | 標準 API。restic/rclone が直接対応 |
| コールドストレージ / アーカイブ | 各社の「アーカイブ」「コールド」階層 | **単価は極めて低いが、取り出しが遅く、取り出し量で課金されることも** |
| ネットドライブ | rclone が対応するネットドライブ | 安いか無料だが、**速度制限、アカウント停止の可能性、唯一のコピーには不適** |

### 必ず注意すべきコストの罠

- **出口の通信費（egress）**：多くのオブジェクトストレージは**アップロードは無料、ダウンロードは有料**です。数百 GB のバックアップを 1 回復元すると、1 年分の保存より高くつくことがあります。**買う前に料金ページの取り出しと出口の価格を見てください。**
- **リクエスト料**：リクエスト数で課金するバックエンドでは、小さなファイルが多いと費用が上がります。
- **最低保存期間**：一部のアーカイブ階層はデータを最低 30/90/180 日保存することを要求し、早く削除しても全期間分を請求します。
- **取り出しの遅延**：アーカイブ階層からの復元は数時間かかることがあり、**「事故が起きてすぐ復元したい」場面には向きません**。少なくとも「即座に復元できる」コピーを 1 部残すことを勧めます。

### ライフサイクルと保持の規則

オブジェクトストレージは通常、**ライフサイクル規則（lifecycle rule）**に対応し、N 日を超えたオブジェクトを**より安い階層へ移す**、N 日後に**自動削除**して保持方針を実現する、未完了の分割アップロード（multipart upload）の残骸を掃除する、といったことができます。**最後のものは隠れた費用のよくある出どころです**。**具体的な規則の文法、対応する階層名、最短期間は事業者ごとに異なるため、各事業者のドキュメントに従ってください**。他社の例をそのまま写さないこと。

## 8. 保持方針の設計

### 何部残すか

| 階層 | よくある数 | 用途 |
| --- | --- | --- |
| 毎日 | 7 - 14 部 | 「昨日 / 一昨日に書き壊した」への対応 |
| 毎週 | 4 - 8 部 | 「数週間後に気づいた問題」への対応 |
| 毎月 / 毎年 | 毎月 6 - 12 部、毎年 1 - 3 部 | 長期の保管、ゆっくり進む破損への対応 |

原則は、**「問題に気づくまでに必要な最長の期間をカバーする」**ことです。セーブデータの破損は**その日のうちに気づくとは限らない**ので、十分に長く残してください。

### ディスク容量の見積もり

ワールドの大きさを `W` とすると、圧縮後はおよそ `0.4W - 0.7W`（**圧縮率は中身次第。region ファイルの圧縮は平凡なので、実測を基準に**）。

| 方式 | 容量の使用 |
| --- | --- |
| 毎回独立の `tar.gz` を `N` 部 | 約 `N x 0.5W` |
| rsync の `--link-dest` によるハードリンクスナップショット | 約 `0.5W + 変化量 x (N-1)`。**変化量が鍵** |
| restic の重複排除スナップショット | ハードリンクスナップショットと同程度かそれ以下。重複排除の粒度による |

例：ワールド 5 GB、独立アーカイブを 14 部、圧縮率 0.5 なら約 `14 x 2.5 = 35 GB`。`--link-dest` のスナップショットに変え、毎日の変化が 100 MB なら約 `2.5 GB + 13 x 0.1 GB = 3.8 GB`。**差は大きく、スナップショット方式に変える価値があります。**

### 古いバックアップを安全に片付ける

- **新しいバックアップが使えると検証する前に古いものを削除しない**。順序は常に、**新しいバックアップを生成 -> 新しいバックアップを検証 -> 問題ないと確認 -> それから古いものを片付ける**。
- **「最も古いが使えると分かっている」コピーを少なくとも 1 部残す**（「破損がずっと前から存在した」場合への備え）。片付ける操作は**先に dry-run するか、ファイルの一覧を表示して**マッチの範囲を確認する。
- 遠隔地側の片付けは**ローカルより保守的に**（多めに残し、削除を遅らせる）。遠隔地のコピーが最後の防衛線だからです。

:::warn 自動削除は「データ削除の自動化」
書き間違えた `find ... -delete` や `--delete` は、履歴を一度にすべて消し得ます。**片付けのロジックは公開前にテスト用のディレクトリで 1 回走らせ、消してはいけないファイルにマッチしないことを確認してください。**
:::

## 9. 保守

### 復元したことのないバックアップはバックアップではない

この規則はいくら強調しても足りません。**バックアップスクリプトが毎日「成功」していることと、バックアップから本当に復元できることは、まったく別の話です。** よくあるのは、権限、パス、ディスク満杯でスクリプトが数週間失敗し続けて誰も気づかない、アーカイブが空だった、暗号化のパスワードがとうに違っていた、といったケースです。

### 四半期ごとの復元演習の流れ

1. **コピーを 1 つ選ぶ**。できれば**遠隔地のコピー**を選び、「転送の過程で壊れていないか」も一緒に検証します。
2. **隔離したテスト用ディレクトリへ復元する**。本番のディレクトリは絶対に上書きしないこと。

```bash
mkdir -p /tmp/restore-test
tar -xzf /srv/backup/mcserver/mcserver-2026-10-04_040001.tar.gz -C /tmp/restore-test
ls -la /tmp/restore-test
```

3. **主要なファイルが存在し、空でないことを確認する**：`world/level.dat`、`server.properties`、`plugins/` 下の設定。
4. **別のポートでテスト用インスタンスを起動する**：テスト用ディレクトリを複製し、`server.properties` のポートを別の値に変え（たとえば `server-port=25566`、`query.port=25566`、`rcon.port=25567`）、起動してログを観察します。入室後に主要な建築、コンテナの中身、プレイヤーのインベントリと権限を確認し、チャンクやセーブデータ関連のエラーが出ないことを確かめます。
5. **記録して片付ける**：演習の日付、所要時間、遭遇した問題を書きます（**これがバックアップの可用性を証明できる唯一の証拠です**）。その後、テスト用インスタンスを削除し、記録は残します。

:::tip 復元の手順を文書にしておく
事故が起きた当日は「どう復元するか」を調べる時ではありません。**前もってコマンドを 1 枚の紙に書き**、演習のときにそれに従い、問題を見つけたら更新してください。
:::

### 完全性の検証

| 手段 | コマンド | 説明 |
| --- | --- | --- |
| restic のリポジトリ検査 | `restic check` | リポジトリの構造とメタデータを検証する。`--read-data` を付けると**すべてのデータブロックを読む**ので、遅いがより徹底的 |
| tar の中身を一覧 | `tar -tzf archive.tar.gz >/dev/null` | 一覧を読んで展開し、**切り詰めや破損したアーカイブ**を発見できる |
| チェックサムの比較 | `sha256sum archive.tar.gz` | バックアップ時に記録したハッシュと比較し、転送後に内容が一致することを確認 |
| rclone の検証 | `rclone check src dst` | 両端のファイルを比較する（能力はバックエンドがハッシュに対応するか次第） |
| 試しの展開 | `tar -xzf archive.tar.gz -C /tmp/check` | 最も直接的な検証：本当に展開できるか |

**チェックサムは別に保存してください**（たとえばアーカイブと一緒に `.sha256` ファイルを書く）。さもないと「バックアップ自身のハッシュでバックアップを検証する」ことになり、意味がありません。

### バックアップが本当に走ったかを監視する

**終了コードを見る**（cron の失敗時はログに 0 以外の終了コードが残る。`set -e` のスクリプトはエラーで早期終了する）、**ログを見る**（`tail -20 /var/log/mc-backup.log` で最後の行が成功の印か確認する）、**成果物を見る**（新しいアーカイブのタイムスタンプが今日で、サイズが妥当な範囲にあり、0 バイトでも異常に小さくもない）。さらに重要なのは**能動的なアラート**です。スクリプトの失敗時にメールやメッセージを送らせます（`mail`、`curl` で Webhook を叩くなど）。**「通知がない」は「すべて正常」ではありません**。できれば**ハートビート型の監視**にして、毎日成功したら 1 回報告し、報告がなければアラートにします。

### よくある失敗の原因

| 現象 | よくある原因 | 調べる方向 |
| --- | --- | --- |
| ディスク満杯 / アーカイブが 0 バイト | ローカルのバックアップディスクが満杯、保持方針が効いていない | `df -h`、片付けのロジックを確認 |
| SSH の認証失敗 | 鍵が差し替えられた、`authorized_keys` の権限が不正、アカウントがロックされた | 手で 1 回 `ssh backup@host 'echo ok'` を実行する |
| ホスト鍵の変更警告 | ターゲットの再インストールや IP の再利用で `known_hosts` の記録が古い | **まず相手の身元を確認**してから `known_hosts` を更新する |
| 権限エラー（Permission denied） | バックアップアカウントが移行元を読めない、移行先のディレクトリに書けない | ディレクトリの権限と所有者を確認し、必要なら root で実行する |
| 資格情報の期限切れ / 暗号化のパスワードが違う | クラウドストレージの鍵が期限切れ、パスワードのローテーション後にスクリプトを更新していない | 鍵を更新し、手で `restic snapshots` を実行して検証する |
| アーカイブの中身が不完全 | `save-off` を忘れた、`--exclude` の誤りで主要なディレクトリを除外した | `tar -tzf` で中身を一覧して照合する |
| 同期で良いデータを消した | 移行元のパスの誤り + `--delete` | 直ちに同期を止め、より古いコピーから復元する |

:::warn エラーログを読む。「ファイルができたか」だけを見ない
ファイルができた ≠ 中身が正しい。**アーカイブのサイズ、終了コード、チェックサムのうち、少なくとも 2 つは確認してください。**
:::

## 10. チェックリスト

| 項目 | 要件 | 確認の頻度 |
| --- | --- | --- |
| 3-2-1 の充足 | 少なくとも 3 部のコピー、2 種類の媒体、1 部は遠隔地 | 四半期ごとに見直す |
| バックアップの範囲 | ワールド、設定、名簿、プラグイン / MOD と設定、起動スクリプト | 設定を変えるたび |
| 一貫性 | 停止してのバックアップ、または `save-all` + `save-off` -> アーカイブ -> `save-on` | バックアップのたび |
| 自動化 | cron / systemd timer で定時実行し、ログがある | 導入時 |
| 暗号化と権限 | 遠隔地のコピーを暗号化、パスワードをオフラインに保管、パスワードと秘密鍵は `chmod 600`、アカウントは最小権限 | 四半期ごとに見直す |
| 保持方針 | 毎日 / 毎週 / 毎月の部数が明確で、片付けのロジックを試験済み | 四半期ごとに見直す |
| 容量 | ローカルと遠隔地の空きが十分 | 毎週 |
| 検証 | `restic check` / `tar -tzf` / チェックサムの比較が通る | 毎月 |
| 監視 | 失敗すればアラート、成功すればハートビート | 導入時と毎月の見直し |
| 復元演習 | テスト用ディレクトリへ復元し、別のポートで起動して検証 | **四半期ごと** |
| 遠隔地の可用性 | ダウンロード / 復元ができ、出口の費用が許容できる | 四半期ごと |
| 文書 | 復元の手順、パスワードの場所、ターゲットのアドレスを文書で記録 | 半年ごと |

## 11. まとめ

- **同じディスク上のバックアップはバックアップではない**：命を救うコピーは別の場所にあり、できれば遠隔から削除できないこと。
- **一貫性は速度より優先**：サーバーが書き込んでいる最中にコピーしない。
- **暗号化 + パスワードのオフライン保管**：遠隔地のコピーは必ず暗号化し、パスワードを失えばすべて失う。
- **保持方針は試験を通す**：片付けのロジックは「データ削除の自動化」であり、公開前に必ず検証する。
- **四半期に 1 回、本当に復元する**：これがバックアップの有効性を証明できる唯一の方法。
