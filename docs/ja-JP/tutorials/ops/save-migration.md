**何百時間も遊んだシングルプレイのセーブデータをサーバーへ移すのは、「成功したように見えて実際には何かが失われている」操作の代表例です。** ディレクトリ名が 1 文字違えば、入室した瞬間に真っ新な空のワールドになります。ネザーとエンドのフォルダを移し忘れれば、ポータルの先は未生成の地形です。プレイヤーデータの名前を変えなければ、人は入れてもインベントリ、進捗、統計がすべてゼロになります。この記事では、セーブデータの実際の構造、2 種類のディレクトリ配置、サーバーが本当に期待しているもの、そして信頼できる移行手順を整理します。

移行の前に [バックアップと復元](/tutorials/java/backup) を読み終えてください。手順の最初と最後はどちらもバックアップです。サーバーのディレクトリと設定ファイルの関係は [サーバー構成](/tutorials/java/structure) と [サーバーの設定](/tutorials/java/config) を参照してください。

## 1. まず把握する：シングルプレイのセーブデータには何があるか

シングルプレイのセーブデータは `.minecraft/saves/<ワールド名>/` の下にある 1 つのディレクトリです（Windows では通常 `%APPDATA%\.minecraft\saves\<ワールド名>\`）。1 つのまとまったファイルではなく、**数十から数万のファイル**の集まりです。

| パス | 内容 | 説明 |
| --- | --- | --- |
| `level.dat` | ワールドの全体情報 | NBT 形式で、ワールド名、生成設定とシード、ゲームルール、スポーン地点、時刻、`DataVersion` などを含む |
| `level.dat_old` | 直前の `level.dat` のバックアップ | ワールドの読み込み時に自動で作られる。一緒にコピーしてよい |
| `level.dat_new` | 書き込み途中の一時ファイル | 正常終了後は通常存在しない。あれば前回の書き込みが中断された証拠 |
| `session.lock` | ワールドの占有ロック | 1.16 以降は中身が U+2603 の 1 文字（雪だるまの記号）。**コピーしない**。サーバーが自分で再生成する |
| `region/` | オーバーワールドのリージョンファイル `r.<x>.<z>.mca` | 地形とブロックのデータ。容量の大部分を占める |
| `entities/` | オーバーワールドのエンティティデータ | 1.17 以降 `region/` から分離して独立保存 |
| `poi/` | オーバーワールドの注目点 | 1.14 以降に存在。村人のベッドと作業台、ポータル、養蜂箱、ロードストーンなど |
| `data/` | ワールド全体の雑多なデータ | スコアボード、襲撃、マップ、コマンドの保存など |
| `playerdata/<uuid>.dat` | プレイヤーデータ | インベントリ、位置、体力、経験値など。**ファイル名がそのままプレイヤーの UUID** |
| `advancements/<uuid>.json` | 進捗（実績） | 同じく UUID で命名 |
| `stats/<uuid>.json` | 統計 | 同じく UUID で命名 |
| `datapacks/` | ワールド単位のデータパック | グローバルなデータパックとは異なり、ワールドに付随する |
| `DIM-1/`、`DIM1/` | ネザーとエンド | 古い配置。名前は旧版の数値ディメンション ID（-1 と 1）に由来する |
| `dimensions/<名前空間>/<パス>/` | カスタムディメンション | 1.16 以降に対応。26.1 以降は 3 つの既定ディメンションもここへ移動 |
| `resources.zip` | ワールド同梱のリソースパック | 26.1 以降は `resourcepacks/` サブディレクトリへ移動 |

:::note `DIM-1/` がないからといって壊れているわけではない
ネザーとエンドのフォルダは、**そのディメンションに初めて入ったとき**に生成されます。一度もエンドへ行っていなければ、セーブデータに `DIM1/` はありません。これは正常で、サーバーはプレイヤーが初めて入るときに自分で作成します。
:::

## 2. 2 種類の配置：`DIM` フォルダと `dimensions/`

ここが移行で最も間違えやすいところで、必ずバージョンごとに分けて見る必要があります。

| バージョン範囲 | オーバーワールド | ネザー | エンド | カスタムディメンション |
| --- | --- | --- | --- | --- |
| 1.2.1 – 1.13（Anvil 以降） | セーブデータのルート（`region/`、`data/` など） | `DIM-1/` | `DIM1/` | 非対応 |
| 1.14 – 1.15 | 同上。`poi/` が増える | `DIM-1/` | `DIM1/` | 非対応 |
| 1.16 – 26.0 | 同上。1.17 以降は `entities/` も増える | `DIM-1/` | `DIM1/` | `dimensions/<名前空間>/<パス>/` |
| 26.1（スナップショット 6）以降 | `dimensions/minecraft/overworld/` | `dimensions/minecraft/the_nether/` | `dimensions/minecraft/the_end/` | `dimensions/<名前空間>/<パス>/` |

要点：

- **古い配置（1.16 – 26.0 以前）**：2 つの既定ディメンションは固定のディレクトリ名 `DIM-1`（ネザー、ディメンション ID `-1`）と `DIM1`（エンド、ディメンション ID `1`）を使います。これらは**セーブデータのルート直下**に、`region/` と同列に置かれます。
- **`dimensions/` 配置**：1.16 でカスタムディメンションが導入されて以降、既定でないディメンションは**リソースロケーション**で保存されます。すなわち `dimensions/<名前空間>/<パス>/` で、たとえば `dimensions/mydatapack/skylands/` です。26.1 スナップショット 6 の再構成後は、**3 つの既定ディメンションもこの配置に変わり**、`DIM-1`/`DIM1` は使われなくなります。
- 同じ 26.1 のセーブデータでは、プレイヤーデータもルートから `players/` の下へ移りました：`players/data/<uuid>.dat`、`players/advancements/<uuid>.json`、`players/stats/<uuid>.json`。

## 3. サーバーが期待するディレクトリ

サーバーは**作業ディレクトリ**（`--universe` で基準パスを変更できます）の下で、`server.properties` の `level-name` が指定するディレクトリを探します。既定は `world` です。そのパスが存在し、妥当なワールド（`level.dat` がある）であればそれを読み込みます。**そうでなければサーバーはそのパスに真っ新なワールドを生成します**。ここが重要で、エラーで止まることはありません。これが「確かにセーブデータをコピーしたのに、入室したら空のワールド」の原因です。

シングルプレイのセーブデータは 3 つのディメンションを 1 つのディレクトリツリーに詰め込みますが、サーバーは既定で 3 つのディメンションを**3 つの同列のディレクトリ**に置きます。

| シングルプレイ側のもの | サーバー側の位置 | 説明 |
| --- | --- | --- |
| セーブデータのルート内容：`level.dat`、`region/`、`entities/`、`poi/`、`data/`、`playerdata/`、`advancements/`、`stats/`、`datapacks/` | `world/` | オーバーワールド。`level-name` が指すディレクトリ |
| `DIM-1/` | `world_nether/` | ネザー |
| `DIM1/` | `world_the_end/` | エンド |
| `dimensions/<名前空間>/<パス>/` | 対応するディメンションのディレクトリ | サーバーにも同じデータパック / MOD が入っている場合のみ意味がある |
| `session.lock` | コピーしない | サーバーの起動時に自分で再生成する |
| `level.dat_old` | `level.dat` と一緒に `world/` へ | 直前の `level.dat` のバックアップにすぎない。残しておいて害はない |

ディレクトリ名は固定ではありません。`level-name` に接尾辞を付けて導出されます。`level-name=myworld` なら通常 `myworld/`、`myworld_nether/`、`myworld_the_end/` です。

:::warn サーバーの稼働中にセーブデータをコピーしてはいけない
サーバーが `region/*.mca` を書き込んでいる最中のコピーは、**書きかけのチャンクファイル**を複製する可能性が高く、復元するとチャンクの欠落、ブロックの破損、最悪の場合はワールドが読み込めなくなります。`session.lock` も両側に同時に存在し、ロックが衝突します。正しい順序は常に、`stop` で停止する（またはコンソールで `save-all` → `save-off` を実行するが、移行の場面では**停止を強く推奨**）→ コピー → 起動、です。
:::

:::tip 最も確実な方法：サーバーにまずディレクトリを作らせる
ディレクトリ名を手で推測しないでください。まず目的の `level-name` でサーバーを一度起動し（空のワールドが生成されます）、停止し、実際にどのディレクトリが作られたかを観察してから、セーブデータの中身を**それらのディレクトリへ流し込みます**。こうすれば、コアが `world_nether` を使うのか、ディメンションを `world/dimensions/` に置くのかに関係なく、配置を間違えません。
:::

## 4. プレイヤーデータ：なぜ自動では付いてこないのか

`playerdata/`、`advancements/`、`stats/` のファイル名は**すべてプレイヤーの UUID** です。サーバーはプレイヤーを読み込むときに UUID でファイルを探し、ファイル名が一致しなければ新しいプレイヤーとして扱います。インベントリは空、実績はゼロ、統計もゼロです。

UUID がどこから来るかは、サーバーがどう人を識別するかによります。

| 場面 | UUID の出どころ | 結果 |
| --- | --- | --- |
| シングルプレイのセーブデータ | ワールドに保存されたローカルプレイヤーの UUID（26.1 以降は `level.dat` の `singleplayer_uuid`、それ以前は `Player` タグ）。`playerdata/` のファイル名もこれ | これが「移行元」 |
| サーバーの `online-mode=true` | Microsoft/Mojang アカウントの正規 UUID | 通常はシングルプレイ側の UUID と**異なる** |
| サーバーの `online-mode=false`（オフライン / 非正規モード） | プレイヤー名から決定的に計算：`UUID.nameUUIDFromBytes(("OfflinePlayer:" + 名前).getBytes(UTF_8))`。バージョン 3（MD5）の UUID | 正規 UUID と**異なり**、しかも同名のプレイヤーはどのオフラインサーバーでも同じ UUID になる |

つまり、**シングルプレイのワールドがたまたま同じアカウントの UUID で作られていた場合を除き、プレイヤーデータは自動では有効になりません**。

対処方法（推奨順）：

1. **まずプレイヤーに一度入室させる**。サーバーがその UUID のデータファイルを作成し、作業ディレクトリの `usercache.json` に書き込みます。
2. 停止し、`usercache.json`（または `world/playerdata/` に新しく現れたファイル名）から**移行先の UUID** を読み取ります。
3. 移行元のファイルを**改名**して移行先の UUID に合わせます。上書きではありません：`playerdata/<旧UUID>.dat` → `playerdata/<新UUID>.dat`。`advancements/`、`stats/` も同様です。先に旧ファイルをバックアップしておけば、間違えても戻せます。
4. 移行前に **`online-mode` を決めておく**。オフラインモードにすると決めたら、後から正規モードに戻さないでください。オフラインのプレイヤー全員の UUID が変わり、「セーブデータが巻き戻った」ような挙動になります。

同じく UUID で索引される `ops.json` と `whitelist.json` もあります。ワールドをコピーしてもこれらは付いてこないため、サーバー側で `/op`、`/whitelist add` をやり直す（または正しい UUID でこの 2 つの JSON を手で編集する）必要があります。

## 5. 移行手順

### 5.1 移行前に記録する

- 移行元のセーブデータの**ゲームバージョン**（`level.dat` の `DataVersion`、またはクライアントのメインメニューのバージョン番号）。**サーバーのバージョンはセーブデータより低くできません**。低いと読み込みを拒否されます。ワールドのダウングレードは安全ではありません。
- 移行先の `level-name`（ディレクトリ名を決める）。
- 移行元のセーブデータのサイズ：`du -sh` で確認し、移行先のディスクに収まり、バックアップの余裕もあることを確かめる。
- 移行前にワールド内で検証可能な事実をいくつか記録する：スポーン地点の座標、`/seed` の値、ある建築物の座標、ネザーポータルの位置。

### 5.2 停止とバックアップ

```bash
# サーバー側：まず安全に停止する
sudo systemctl stop minecraft
# systemd 管理でない場合はコンソールで stop を実行し、プロセスが本当に終了したか確認する

# 移行元：まずアーカイブして控えを取る（クライアントのマシンで）
cd ~/.minecraft/saves
tar -czf MyWorld-20261004.tar.gz MyWorld

# 移行先：現在の（空または古い）ワールドディレクトリを改名して控える。そのまま削除しない
cd /opt/minecraft/server
mv world world_before_migration
```

Windows では、`%APPDATA%\.minecraft\saves` で `MyWorld` フォルダを右クリックして圧縮するのが対応する操作です。

### 5.3 ファイルのコピー

`rsync -a` を推奨します。不要なディレクトリを除外でき、中断しても再開でき、エラー時には明確な情報を出します。**移行元パスの末尾の `/` は「ディレクトリの中身をコピーする」を意味します**。これを落としたり間違えたりすると、ディレクトリが 1 段余分に入ります。

```bash
# オーバーワールド：2 つのディメンションディレクトリとロックファイルを除外し、残りをすべて world/ へ
rsync -a --exclude 'DIM-1' --exclude 'DIM1' --exclude 'session.lock' \
  "/home/you/.minecraft/saves/MyWorld/" /opt/minecraft/server/world/

# ネザーとエンド：それぞれの同列ディレクトリへ
rsync -a "/home/you/.minecraft/saves/MyWorld/DIM-1/" /opt/minecraft/server/world_nether/
rsync -a "/home/you/.minecraft/saves/MyWorld/DIM1/"  /opt/minecraft/server/world_the_end/
```

移すディレクトリが少数なら `cp -a` のほうが直感的です。`-a` はタイムスタンプ、権限、シンボリックリンクを保持します。

```bash
# 項目ごとにコピー（存在しないものはスキップ：たとえば一度もエンドへ行っていなければ DIM1 はない）
cd "/home/you/.minecraft/saves/MyWorld"
cp -a level.dat level.dat_old region entities poi data datapacks \
      playerdata advancements stats /opt/minecraft/server/world/ 2>/dev/null

cp -a DIM-1/. /opt/minecraft/server/world_nether/
cp -a DIM1/.  /opt/minecraft/server/world_the_end/
```

Windows では `robocopy` を使います（注意：`robocopy` の終了コードは **0〜7 がすべて成功**で、`1` は「ファイルがコピーされた」を意味します。失敗と取り違えないでください）。

```bat
robocopy "%APPDATA%\.minecraft\saves\MyWorld" "C:\mc\server\world" /E /XD DIM-1 DIM1 /XF session.lock
robocopy "%APPDATA%\.minecraft\saves\MyWorld\DIM-1" "C:\mc\server\world_nether" /E
robocopy "%APPDATA%\.minecraft\saves\MyWorld\DIM1"  "C:\mc\server\world_the_end" /E
```

コピー後に所有者を修正します（Linux で専用ユーザーとしてサーバーを動かしている場合は必須。さもないと `Failed to save` が出ます）。

```bash
sudo chown -R minecraft:minecraft \
  /opt/minecraft/server/world \
  /opt/minecraft/server/world_nether \
  /opt/minecraft/server/world_the_end
```

:::tip 大きなセーブデータは圧縮してから送り、ネットワーク越しにのんびりコピーしない
数十 GB の `region/` をファイルごとにネットワーク転送すると非常に遅く、一度中断すればやり直しです。より確実なのは、移行元でアーカイブして（`tar -czf MyWorld.tar.gz MyWorld`、チャンクデータは圧縮率がたいてい良好です）から送り、届いてから展開する方法です。`rsync -az --partial` でも転送時の圧縮とレジュームが使えます。
:::

### 5.4 `level-name` の修正

サーバーの `server.properties` を開き、ディレクトリ名と `level-name` が**完全に一致**することを確認します（Linux は大文字小文字を区別するので、`MyWorld` と `myworld` は別のディレクトリです）。

```properties
level-name=world
```

### 5.5 起動して観察する

```bash
sudo systemctl start minecraft
# 起動の過程をリアルタイムで見て、セーブデータ関連のエラーを重点的に探す
tail -f /opt/minecraft/server/logs/latest.log
# systemd 管理なら stdout は journal に入る
journalctl -u minecraft.service -f
```

起動ログで重点的に確認するのは、`Failed to load` がないこと、ディメンション関連の例外がないこと、`Preparing spawn area` が正常に終わること、`No space left on device` がないことです。

### 5.6 入室して検証する

第 10 節の検証チェックリストを参照してください。**すぐにサーバーを全員に開放しないでください**。ホワイトリストで 1〜2 人だけ入れて、問題がないことを確認します。

### 5.7 本番の移行の前に一度演習する

重要なワールドなら、**まずローカルで別のポートと一時的な `level-name` を使ってテスト用インスタンスを起動し**、手順一式を流してください。演習はディレクトリ名、バージョン、権限、UUID の問題を事前に露出させ、しかも本番環境にはまったく影響しません。

```properties
# テスト用インスタンスの server.properties（本番と別のディレクトリに置き、干渉を避ける）
level-name=world_test
server-port=25566
online-mode=false
white-list=false
```

```bash
cd /opt/minecraft/testserver
java -Xms2G -Xmx2G -jar server.jar --nogui
```

演習が通ってから、本番インスタンスで同じことをします。テスト用ディレクトリは使い終わったら丸ごと削除してかまいません。

## 6. `level.dat` に手を入れるべきか

`level.dat` はワールドの「身分証 + 設定表」で、ワールド名、生成設定とシード、ゲームルール、スポーン地点、時刻、難易度、有効なデータパックの一覧が入っています。中身は **NBT のバイナリ**で、通常はさらに gzip 圧縮されています。

結論は単純です。**手で編集しないでください。**

- テキストエディタで開くとファイルが壊れます。NBT エディタで変更するにしてもバージョン差に向き合う必要があります（たとえば 26.1 以降、ゲームルールやワールド生成設定などは `data/` の下へ分離されました）。
- 間違えるとワールドが読み込めなくなり、`level.dat_old` で必ず救えるとは限りません。
- **変更したいもののほとんどには正規の入口があります**。難易度、ゲームモード、描画距離、ホワイトリストは `server.properties`、ゲームルール、時刻、天候、スポーン地点、データパックはゲーム内コマンド（`/gamerule`、`/time set`、`/weather clear`、`/setworldspawn`、`/datapack`）。
- `level-seed` は**ワールドの作成時にのみ有効**です。既存のワールドのシードは設定を変えても入れ替えられません。
- 「中身をちょっと見たい」ときは、NBT 閲覧ツールで**読み取り専用**で開き、その前に必ずコピーを取ってください。

移行の場面での正しいやり方は、**`level.dat` をそのまま運び、移行の途中で触らない**ことです。ワールドが動き、検証が通り、バックアップが整ってから、設定とコマンドで調整します。

## 7. データパック（`datapacks/`）

- ワールド単位のデータパックはワールドディレクトリ下の `datapacks/`（シングルプレイは `saves/<ワールド名>/datapacks/`、サーバーは `world/datapacks/`）に置かれ、ワールドに付随して移動します。ワールドをコピーすれば一緒に移ります。
- **有効 / 無効の一覧は `level.dat` に記録されている**ため、移した後に有効化し直す必要は通常ありません。`/datapack list` で確認し、必要なら `/datapack enable <名前>` / `/datapack disable <名前>` を使い、変更後は `/reload` で反映します。
- **バージョンを合わせる必要があります**。データパックは対象の `pack_format` を宣言しており、サーバーのバージョンが合わないと読み込みを拒否されたり警告が出たりします。
- **ディメンションを追加するデータパックはとくに注意**。そうしたワールドには `dimensions/<名前空間>/<パス>/` ディレクトリがあり、サーバーにも同じデータパックが入っていないと、そのディメンションは読み込まれません。データが消えるわけではありませんが、プレイヤーは入れなくなります。
- ワールド同梱のリソースパック（旧バージョンは `resources.zip`、26.1 以降は `resourcepacks/` の下）は自動ではプレイヤーに配信されません。カスタムのテクスチャをプレイヤーに見せるには、`server.properties` で `resource-pack` を設定する必要があります。

## 8. MOD のセーブデータ、バージョン間、統合版

### 8.1 MOD（Forge/NeoForge/Fabric）のセーブデータをプラグイン側へ移す

これはディレクトリ名に次ぐ 2 番目に大きな落とし穴です。**プラグイン側（Spigot/Paper など）は MOD が追加したブロック、アイテム、エンティティを認識しません。**

- MOD のブロックはワールド内で未知のブロックになります（通常は空気、石、またはプレースホルダーのブロックとして現れます）。これらのチャンクは**一度読み込まれて再保存されると、元のデータがその場で上書きされることがあり**、後から MOD を入れ直しても必ずしも救えません。
- MOD のアイテムはインベントリやコンテナから消え、MOD のエンティティ（機械、生物）は破棄されます。
- MOD のディメンション（`dimensions/<MOD の名前空間>/...`）は、対応する MOD がないと読み込めません。

正しいやり方は、**まずバックアップし、捨ててよいコピーで読み込んでみて**、ログに未知のブロックとレジストリ関連のエラーがどれだけ出るかを数えることです。損失が許容できると確認してから本番の移行を行います。許容できないなら MOD 側を使い続けるか、いっそ新規に始めます。

### 8.2 バージョン間

- **セーブデータのバージョンがサーバーより高い**：サーバーは読み込みを拒否します（`DataVersion` の検査）。安全な方法はサーバーをアップグレードすることだけで、ワールドをダウングレードすることではありません。
- **セーブデータのバージョンがサーバーより低い**：サーバーはデータ修復（DataFixer）でワールドをアップグレードします。通常は問題なく進みますが、**アップグレードは不可逆**です。新しいバージョンで一度読み込むと、古いバージョンでは開けなくなります。だからアップグレードの前に、手を付けていないバックアップを必ず残してください。
- 複数のメジャーバージョンをまたぐ場合は、段階的に上げるほうが安全です（たとえば 1.20 から 1.21 へ）。1 段階ごとに検証します。[バージョン更新](/tutorials/ops/updates) を参照してください。

### 8.3 統合版（基岩版）

Java 版のワールドと統合版のワールドは形式がまったく異なり、**そのまま相互に読み込むことはできません**。第三者の変換ツールが必要で、変換は通常は非可逆です（レッドストーン、エンティティ、一部ブロックの挙動）。統合版のサーバーディレクトリ構成は [BDS サーバー](/tutorials/bedrock/bds) を参照してください。

## 9. よくある失敗パターン

| 現象 | 根本原因 | 対処 |
| --- | --- | --- |
| 入室すると真っ新な空のワールド | ディレクトリ名と `level-name` が不一致、またはそのディレクトリに `level.dat` がないため、サーバーがワールドを**新規作成**した | 停止してディレクトリ名を照合する。旧ディレクトリを改名して控え、コピーし直す |
| ワールドには入れるが、ネザー / エンドが真新しい地形 | `DIM-1/`、`DIM1/` を `world_nether/`、`world_the_end/` へ移していない、または階層を間違えた（ディレクトリが 1 段多い） | 停止してから正しいディレクトリへコピーし直す |
| ワールドには入れるが、プレイヤーが「ゼロから」になる | プレイヤーデータのファイル名（UUID）がサーバーの認識する UUID と一致しない | 第 4 節に従い `playerdata/`、`advancements/`、`stats/` を改名する |
| サーバーがワールドの読み込みを拒否する | セーブデータのバージョン（`DataVersion`）がサーバーより高い | サーバーをアップグレードする。ワールドのダウングレードは**しない** |
| 一部のチャンクが欠落し、ブロックが壊れる | コピー時にサーバーがまだ稼働していた、またはディスクが満杯 | バックアップからコピーし直す。まずディスク容量を解決する |
| ログに `Failed to save` が出る | ファイルの所有者 / 権限が正しくなく、サーバーのユーザーが書き込めない | `chown -R` でサーバーの実行ユーザーに合わせる |
| Linux で「ファイルはあるのにサーバーはないと言う」 | 大文字小文字の不一致（`MyWorld` と `myworld`） | ディレクトリ名と `level-name` を統一する |
| 起動が `Preparing spawn area` で長く止まる | ワールドが大きく、初回の読み込みに時間がかかる。ディスク I/O のボトルネックの可能性もある | 気長に待ち、CPU / ディスクの使用率を観察する。何度も再起動しない |
| ホワイトリスト / OP が効かない | `whitelist.json`、`ops.json` はワールドの中にないため再構築が必要 | `/whitelist add`、`/op` をやり直すか、正しい UUID で手動編集する |
| 移行後に頻繁にラグる | シングルプレイとサーバーでは負荷のモデルが違う（描画距離、シミュレーション距離、エンティティ数） | `view-distance`、`simulation-distance` を調整する。[最適化](/tutorials/java/optimize) を参照 |

## 10. 検証チェックリスト

1 項目ずつ確認し、すべて通ってから外部に開放してください。

| 確認項目 | 方法 |
| --- | --- |
| ワールドディレクトリに `level.dat` がある | `ls -la /opt/minecraft/server/world/level.dat` |
| リージョンファイルの数が移行元と一致する | 両側で `find world/region -name '*.mca' \| wc -l` を実行して比較 |
| 3 つのワールドの容量が想定どおり | `du -sh /opt/minecraft/server/world*` |
| 起動ログにセーブデータのエラーがない | `grep -n -i "failed\|unknown dimension\|no space" logs/latest.log` |
| シードが一致する | ゲーム内の `/seed` を、移行前に記録した値と比較 |
| 時刻とゲームルールが一致する | `/time query daytime`、`/gamerule keepInventory` など |
| スポーン地点が一致する | `/setworldspawn` の前に現在のスポーン地点を見て、移行前と比較 |
| 主要な建築物が存在する | 記録した座標へテレポートして目視確認 |
| ネザーが一致する | `/execute in minecraft:the_nether run tp @s 0 64 0` で既知のポータルと地形を確認 |
| エンドが一致する | エンドへ入り、エンダードラゴンの状態、エンドポータルと帰還ポータルを確認 |
| プレイヤーの進行度が戻った | インベントリ、経験値、進捗画面、統計を確認 |
| 権限とホワイトリストが正しい | `/whitelist list`、`/op` で確認 |
| サーバーがディスクに書き込める | `sudo -u minecraft test -w /opt/minecraft/server/world && echo writable` |
| バックアップが効いている | すぐにバックアップスクリプトを手で 1 回実行し、新しいワールドが対象に含まれたことを確認 |

## 11. 移行の後

- **`online-mode`、ホワイトリスト、正規アカウント認証を確定**してからプレイヤーデータを蓄積し始めてください。途中で認証モードを切り替えると UUID が変わります。
- **すぐに完全バックアップを取り**、遠隔地 / オフラインのコピーへ送ってください。[遠隔地バックアップ](/tutorials/ops/offsite-backup) を参照。
- サーバーの負荷に合わせて `view-distance`、`simulation-distance`、`max-players` を設定し直してください。シングルプレイのセーブデータは通常「一人用の描画距離」で生成されているため、サーバーへ移した後に、より遠い描画距離に合わせて周辺チャンクを再生成する必要があるかもしれません。
- ログローテーションとディスク監視を追加し、移したばかりの大きなワールドでディスクが満杯にならないようにしてください。[ログ管理とローテーション](/tutorials/ops/logs) と [監視とアラート](/tutorials/ops/monitoring) を参照。
- **統合版（BDS）は別問題**です。Java 版のワールドと統合版のワールドはまったく別の形式で、そのまま相互に読み込むことはできません。第三者の変換ツールが必要で、変換は通常は非可逆です。統合版のサーバーディレクトリ構成は [BDS サーバー](/tutorials/bedrock/bds) を参照してください。
