統合版のサーバー構築で出会う「起動しない / つながらない / 入れるがおかしい」は、症状がよく似ています：プレイヤー側は「入れない」としか言わず、サーバー側はプロセスすら上がっていないことがあります。本記事は [[BE] よくある質問](/tutorials/faq/faq-be) の詳細版で、「まず分類、次に特定」の順に展開し、各手順の判断基準をできるだけ明確に書きます。
:::tip この記事の使い方
まず第 1 節の分類表を見て、自分がどの種類かを判断し、該当する節へ飛んでください。第 5 節はゼロから始める完全な切り分け順、第 6 節は助けを求めるときに何を出すかを扱います。
:::

## 1. まず分類：つながらない / 起動しない / 入れるが異常

分類の判断基準は：**サーバーのプロセスが動いているか、ポートを待ち受けているか？**

| 現象 | どの種類か | どの節を見るか |
| --- | --- | --- |
| ランチャーのウィンドウが一瞬で消える、またはコマンドラインがすぐプロンプトに戻る | 起動しない | 第 2 節 |
| コンソールにエラーが出て、プロセスがそもそも上がっていない | 起動しない | 第 2 節 |
| プロセスは動き、コンソールも正常なのに、プレイヤーがつながらない | つながらない | 第 3 節 |
| プレイヤーは入れるが、ラグ、セーブデータ異常、権限がおかしい | 入れるが異常 | 第 4 節 |
| 一部のプレイヤーは入れるが、他は入れない | つながらない | 第 3 節（まずプロトコルバージョンとクライアントのプラットフォームを確認） |
| ポート検査ツールは「通過」と言うのに、プレイヤーは入れない | つながらない | 第 3.2 節（ツールが TCP しか測っていないことが多い） |
| 昨日は平気だったのに、今日は全員入れない | つながらない | 第 3.1 節（クライアントの自動更新でプロトコルが変わった） |
| サーバーは起動するが、数分遊ぶと自分で終了する | 入れるが異常 | 第 4.1、4.2 節 |
:::note まずプロセスの状態を確認し、それから他を語る
「つながらない」と「起動しない」は切り分けの経路がまったく違います。最初の一歩は常に、プロセスがまだ生きているか、ポートを待ち受けているかの確認です（第 5 節）。この手順を飛ばすと、以降の判断はすべて推測になります。
:::

## 2. サーバーが起動しない（BDS とサードパーティコア）

### 2.1 BDS：アーキテクチャ、ランタイム、システム要件

BDS は**ネイティブコンパイル**されたプログラムでスクリプトではないため、OS とランタイムを選びます。

| 項目 | 要件 | 説明 |
| --- | --- | --- |
| アーキテクチャ | **x86-64** | 公式が提供するのは Windows と Linux の x86-64 ビルドのみ。ARM デバイス（Raspberry Pi など）は公式サポート外 |
| Windows | Windows 10 10.0.15063 以降、または Windows Server 2016 以降 | 併せて **Microsoft Visual C++ ランタイム**（VC++ Redistributable）が必要 |
| Linux | 公式サポートは **Ubuntu 22.04 以降**のみ | 他の x86-64 ディストリビューションもライブラリが揃っていれば動く。**glibc 2.35 以上**を含む |
| メモリ | 最低 4 GB | プレイヤーが 10 人を超えると通常はより多く必要。ディスクは 1 GB の余裕を推奨 |

ランタイム欠如の典型的な現れ方：Windows では BDS が Microsoft Visual C++ ランタイムに依存し、**欠けていると起動の瞬間に DLL が足りないと報告されるか、ウィンドウが一瞬で消え**、コンソールには何も出ないことが多いです。Linux では glibc が古い場合、**動的ライブラリの読み込み失敗**（`error while loading shared libraries` の類）がよくあります。具体的に必要なランタイムと libc のバージョンは **BDS 公式のダウンロードページと release notes** を優先し、第三者のチュートリアルのバージョン番号をそのまま真似しないでください。
:::warn BDS は Java 版のようにメモリを指定できない
Java 版は `-Xms` / `-Xmx` でヒープを制御できますが、**BDS に対応する起動引数はありません**。自分でメモリを管理するので、ワールドの規模、エンティティ数、プレイヤー数を制限して間接的に使用量を抑えるしかありません。だから「BDS にメモリ引数を追加する」類の助言は無効です。
:::

### 2.2 Linux：実行権限と作業ディレクトリ

Linux で最もよくある「起動しない」原因は 2 つで、どちらも操作の層です。**1 つは実行権限がない** —— 圧縮ファイルから展開した `bedrock_server` には既定で `+x` が付きません：

```bash
chmod +x bedrock_server
```

**もう 1 つは作業ディレクトリが違う** —— BDS の公式の使い方は**自分のディレクトリで実行する**ことで、動的ライブラリの検索パスをカレントディレクトリに向けます：

```bash
cd /opt/bedrock-server
LD_LIBRARY_PATH=. ./bedrock_server
```

BDS の**データはすべて作業ディレクトリに保存**され、展開した初期ファイルがそこにあることを前提にします。したがって：systemd などで起動するときは必ず `WorkingDirectory` を設定してください。そうしないとプロセスの作業ディレクトリが `/` になりえます。別のディレクトリからバイナリを実行すると、軽ければ間違ったディレクトリに新しい設定ファイルとワールドが勝手に生成され、ひどければ同じディレクトリのライブラリが見つからず起動に失敗します。`LD_LIBRARY_PATH=.` の `.` は**カレント作業ディレクトリ**を指し、バイナリのあるディレクトリではない点にも注意してください。
:::tip 「起動しない」の最初のコマンド
サーバーのディレクトリで手動で `LD_LIBRARY_PATH=. ./bedrock_server` を 1 回実行し、エラーをそのまま最後まで読んでください。多くの問題はこの段階で露見し、ログを漁るよりずっと速いです。
:::

### 2.3 改名とパスの落とし穴

BDS のメインプログラムは改名できますが、**勧めません**。改名すると、それを参照するすべての場所を同期して変える必要があります：起動スクリプト（`.bat` / `.sh`）、デスクトップのショートカット、パネルやデーモンに設定した起動コマンド、そして第 2.2 節の `LD_LIBRARY_PATH=. ./bedrock_server` のコマンド自体。どれか 1 つでも漏れると、「クリックしても反応しない」か「ファイルが見つからない」になります。すでに改名して起動しないなら、まず元の名前に戻して検証し、それから個別に直すか決めてください。

同じく問題になりやすいのが**パスそのもの**です：サーバーのディレクトリは英数字のみ、空白なし、特殊記号なしのパスに置くことを勧めます。日本語のパスは一部のパネルや起動スクリプトで読み込みに失敗し、エラーも分かりにくいのが普通です。

### 2.4 Nukkit 系：Java のバージョンとビルドの整合

Nukkit 系（Nukkit / PowerNukkitX など）は **Java** のプログラムで、2 点を確認します：

- **Java のバージョンが足りるか**：新しい分岐は通常より新しい Java を要求し、古すぎると起動の瞬間に `UnsupportedClassVersionError` の類を投げます。エラーには必要なバージョンが直接書かれているのが普通で、**そのコアの公式ドキュメントを優先**します。
- **ビット数が合っているか**：64 ビットの OS には必ず 64 ビットの Java。32 ビットの Java はメモリ上限のため起動時や実行中に落ちます。

より見えにくいのが**ビルドとプロトコルバージョンの不一致**です：コアのビルド自体は起動するがクライアントがつながらない、あるいはサーバーのバージョンが古いと表示される。この層はまず [統合版サードパーティコアの導入](/tutorials/bedrock/third-party-setup) を見てください。完全なバージョン整合の説明があります。

### 2.5 PocketMine-MP：PHP のバージョンと拡張

PMMP は **PHP** のプログラムで、公式の要件は：**64 ビット CPU + 64 ビット OS**、メモリ 1 GB 以上；デュアルコア以上は**推奨**であって必須ではありません；公式は Windows、Linux、macOS をできるだけサポートし、原則として 64 ビット PHP が動き拡張が揃うプラットフォームなら動きます。

最もつまずきやすい 2 点：**PHP のバージョンと拡張** —— PMMP は特定バージョンの PHP と一群の拡張を必要とし、バージョンが違うか拡張が読み込まれないと起動時にエラーになります。よくあるのはある PHP 拡張の読み込み失敗（`opcache` など）；**具体的に必要な拡張と最低 PHP バージョンは PMMP 公式ドキュメントの Setup requirements を優先**。**OS 標準の PHP を気軽に使わない** —— ディストリビューションのリポジトリの PHP は古く拡張も不完全なことが多く、Windows では他のソフトが入れた PHP が残っていることもあります。PMMP 公式は**各 OS 向けにパッケージした PHP ランタイム**を提供しており（リリースページで OS ごとのファイルを取る）、解凍すればすぐ使えます。**任意のシステム PHP ではなく、公式パッケージの PHP を使うことを勧めます。**
:::warn どの PHP を呼んでいるか先に確認
`php -v` を実行し、出力が使うつもりのバージョンとビット数であることを確認してください。起動スクリプトに素の `php` と書くと `PATH` の最初のものが使われ、あなたが入れたものではない可能性が高いです。
:::

### 2.6 ポートが使用中

ポート衝突の現れ方は：プロセスが起動直後に終了し、コンソールがポートを bind できないと表示します。

**統合版特有の落とし穴**が 1 つあります：`server.properties` の `enable-lan-visibility` は既定で有効で、LAN 内でサーバーを探すクライアントに応答する役割です。有効なとき、**`server-port` / `server-portv6` を別の値に変えても、サーバーは既定の 19132 / 19133 を bind しに行きます**。だから同じマシンで 2 つ目の統合版サーバーを開くと、ポートを変えても衝突することがあります。LAN での発見が不要ならこのオプションを切って避けられます。具体的な挙動は公式ドキュメントを優先。なお `server-port` の有効範囲は **1–65535** の整数です。

### 2.7 server.properties の書き方の誤り

Bedrock の `server.properties` は**行ごとの `キー=値` テキスト**で、`#` で始まる行はコメントです。型を間違えたり範囲外の値を書くと、起動に失敗するか、そのオプションが無視されて「変えたのに効かない」になります。確認済みの有効な値を直接照合できます：

```properties
server-port=19132
server-portv6=19133
allow-list=true
gamemode=survival
difficulty=easy
default-player-permission-level=member
tick-distance=4
view-distance=32
max-players=10
compression-algorithm=zlib
```

| キー | 有効な値 / 範囲 |
| --- | --- |
| `server-port` / `server-portv6` | 1–65535 の整数 |
| `allow-list` | `true` / `false` |
| `gamemode` | `survival` / `creative` / `adventure` |
| `difficulty` | `peaceful` / `easy` / `normal` / `hard` |
| `default-player-permission-level` | `visitor` / `member` / `operator` |
| `tick-distance` | 4–12 の整数 |
| `view-distance` | 5 以上の整数 |
| `max-players` | 正の整数 |
| `compression-algorithm` | `zlib` / `snappy` |
:::warn 編集前にバックアップ、編集はプレーンテキストエディタで
メモ帳のような**プレーンテキストエディタ**で変更し、書式を挿入するエディタ（リッチテキストのオフィスソフトなど）を使わないでください。見えない文字が書き込まれて解析に失敗します。変更前に `server.properties` をコピーしてください。ある値に何が許されるかは**公式ドキュメントを優先**します。
:::

## 3. つながらない（cannot connect）

### 3.1 プロトコル／バージョンの不一致

統合版で**最も多い**接続できない原因で、しかもプレイヤー側にほぼ自救の余地がありません：アプリストアは既定で自動更新し、クライアントが更新されるとプロトコルが変わります。この層はここで繰り返さず、[プロトコルのバージョンとバージョン選択](/tutorials/bedrock/protocol) を直接見てください。要点は 2 つだけ：クライアントのプロトコルがサーバーのプロトコルと**一致**しないと入れない；iOS のプレイヤーはストアの最新版しか入れられないので、「プレイヤーにダウングレードさせる」道は iOS 層では塞がっています。クライアントとサーバーのバージョンが一致しないとき、プレイヤーには「サーバーが古すぎる」類の表示が出ます。**具体的な文言は公式を優先**します。

### 3.2 UDP と TCP：ポート、ファイアウォール、セキュリティグループ

統合版は**UDP を使う** —— これは Java 版とまったく違い、「ポート検査は通るのにプレイヤーが入れない」の最大の原因です。

| 項目 | 値 |
| --- | --- |
| 既定の IPv4 ポート | **19132 / UDP** |
| 既定の IPv6 ポート | **19133 / UDP** |
| 開放が必要な場所 | OS のファイアウォール**と**クラウドのセキュリティグループ。両方 |
| ルーターのポート転送 | プロトコルは必ず **UDP** を選ぶ。TCP しか選べないなら UDP の規則を別に作る |
:::warn TCP しか測らないツールは嘘をつく
多くのオンライン「ポート検査」ツールは既定で TCP しか探りません。TCP が通ることは UDP が通ることを意味しません。統合版のポートを確認するときは、必ず **UDP** を測ってください。
:::

また、多くのトンネルサービスは既定で TCP のみ対応なので、方案を選ぶときは **UDP** に対応しているか確認してください。クロスプレイ（スマホ／統合版のプレイヤーを Java サーバーに入れる、またはその逆）の場面は [スマホプレイヤーの受け入れ](/tutorials/java/mobile) を参照。

### 3.3 CGNAT / 公衆 IPv4 がない / 二重 NAT

サーバーは正常に動き、ファイアウォールも開放しているのに外部からつながらない —— 問題は事業者側にあることが多いです。

| 状況 | 判断 | 対処の方向 |
| --- | --- | --- |
| ルーターの WAN 側が**プライベートアドレスか共有アドレス**（CGNAT） | 独占の公衆 IPv4 がなく、ポート転送の転送先がない | 事業者に公衆 IP を申請するか、UDP 対応のトンネル／仮想 LAN 方案に変える |
| **二重 NAT**：光回線のモデムの後ろにもう 1 台ルーター | 転送が片方にしかなく、経路が途中で切れている | 転送は**インターネットに直接つながる機器**で行い、次のホップの転送もつなげる |
| 公衆 IP が動的 | アドレスが変わり、プレイヤーが覚えられない | ダイナミック DNS サービスか、トンネル方案に変える |
| IPv6 の公衆 IP しかない | 一部のプレイヤーの回線が IPv6 非対応 | IPv4 側の到達性も確認する |

ポート転送ができない場合、よくある代替が**仮想 LAN** です：サーバーとプレイヤーを同じ仮想ネットワークに参加させ、プレイヤーはその仮想ネットワークの IP で接続します。コミュニティでよく使われるのは ZeroTier、Radmin VPN、Hamachi などで、具体的な設定はそれぞれの公式ドキュメントを参照してください。

### 3.4 LAN での発見 vs IP で接続

この 2 つの接続方法は経路が違い、症状も違います。

| | LAN での発見 | IP / ドメインで接続 |
| --- | --- | --- |
| プレイヤーがすること | 何もしない。サーバーが「ゲーム」画面の上部に現れる | サーバーを手動で追加し、アドレスとポートを入力 |
| 前提 | 双方が同じ LAN 内にいる | サーバーが外部から到達可能（ポート転送かトンネル） |
| 影響するもの | `enable-lan-visibility`、UDP 19132/19133 が使えるか | 公衆 IP、ファイアウォール、セキュリティグループ、トンネル |

見落としやすい点：**統合版はポートを明示する必要があります**。Java 版のように SRV レコードでポートを省略できません。だからアドレス欄とポート欄の両方を正しく埋めます；LAN での発見はブロードキャスト／マルチキャストに依存し、一部の仮想ネットワーク、コンテナネットワーク、セグメントをまたぐネットワークでは動きません。その場合は IP 接続に変えるしかありません；**同じマシンから自分に接続する**とループバックやファイアウォールの規則で失敗することがあるので、別の端末で試すと「サーバーが到達不能」なのか「このマシン自身の問題」なのかを素早く切り分けられます。

### 3.5 コンソール機（Xbox / PlayStation / Switch）

コンソール機は**ゲーム内で IP を直接入力してサーバーに参加できません**。よくある 2 つの道は：**カスタム DNS**（ドメインの解決先をあなたのサーバーに向け、コンソールがドメイン経由で参加する）と、**LAN**（コンソールとサーバーを同じ LAN に置き、LAN での発見で参加する）です。
:::note プラットフォームの方針は変わるし、各プラットフォームで違う
コンソール側の制限は**プラットフォームの方針とバージョンで変わります**。資料によっては、コンソール版は全体として LAN 経由に寄っており、とくに Switch は選択肢がより狭い（Realms／公式推奨サーバーのみの可能性）と指摘されています。**あるプラットフォームが現在何に対応しているかは、公式ドキュメントとプラットフォームの説明を優先**し、古いチュートリアルをそのまま真似しないでください。
:::

### 3.6 クライアント側の確認

最も安く済む可能性を先に除外してから、サーバーに触ります：**アドレスの形式**では、アドレス欄には IP かドメインだけを書き、**ポートはポート欄に**書く。`ip:port` を丸ごとアドレス欄に入れると、一部のバージョンでは解析に失敗します；**ポート**は既定 19132 で、サーバーがポートを変えたらプレイヤー側も変える；**同じバージョンか** —— 統合版のクライアントは Java 版のサーバーに**直接入れず**（逆も同じ）、クロスプレイには追加の方案が必要（[スマホプレイヤーの受け入れ](/tutorials/java/mobile) を参照）；**クライアントのバージョンはサーバーのバージョンと同じでなければならず**、統合版は古いクライアントで新しいサーバーに接続できません。最後に**別の端末、別の回線で試す**と、サーバーの問題か、プレイヤーの回線の問題か、プレイヤーの端末の問題かがすぐ分かります。

### 3.7 サードパーティコア特有の事情

サードパーティコアは**公式サーバーのすべてのプロトコル機能とゲーム内容を実装しているとは限らない**ので、「同じクライアントで公式サーバーには正常に入れるのに、自分のサーバーではおかしい」は正常な現象で、設定ミスとは限りません。PocketMine-MP を例にすると、公式ドキュメントが明確に説明しています：PMMP は Minecraft のすべての遊びの機能を実装して**いません**。理由は開発者が余暇で維持しており、公式の更新速度に追いつくのが難しいためです；執筆時点で欠けている機能には**モブ、レッドストーン、トロッコ、ディメンション**が含まれます。

もう 1 つの要点は**コアのビルドとプロトコルバージョンの整合**です：コアがクライアントに報告するバージョンがクライアントに受け入れられなければ、プレイヤーには「サーバーのバージョンが古い」類の表示が出ます。PMMP 公式 FAQ の対処は：サーバーのコンソールで `version` コマンドを実行し、現在のコアが対応する Minecraft のバージョンを確認し、それに基づいて新しいコアのビルドを選ぶ。公式は同時に、**新しいパッチバージョンの間では時に（常にではない）コアを更新せずに互換できる**と説明しています。

## 4. 入れるが異常（works but behaves oddly）

### 4.1 ラグとメモリ

**ラグの第一の判断基準はシングルコア性能です。** BDS のモブ演算はシングルスレッドで行われるため、快適さは主にシングルコア性能で決まり、マップが大きいほど重くなります。これは [BDS サーバー](/tutorials/bedrock/bds) でも説明しています。

| 調整できる方向 | 説明 |
| --- | --- |
| `tick-distance` を下げる | 有効範囲 4–12、既定 4。大きいほど演算に参加するチャンクが増える |
| `view-distance` を下げる | 5 以上が必要、既定 32。主に配信範囲に影響 |
| エンティティ／モブ農場の規模を減らす | エンティティがシングルスレッド演算の主要な負荷 |
| シングルコアの強いマシンに替える | 最も直接的だがコストも最大 |
| `max-threads` | Bedrock にこの項目（最大スレッド数）はあるが、**シングルスレッドのボトルネックは変えられない**。これでラグが解決すると期待しない |

PHP コアについて：PMMP 公式ドキュメントは、マルチコアの活用が「悪名高いほど下手」だと明言しています。PMMP を動かすためにマシンを買うなら、**マルチコアより高周波を優先**すべきです。

**メモリが増え続けることについて**：BDS にはメモリがゆっくり増える既知の問題があります。重要な注意は ——
:::warn 無理にメモリを解放しない
無理にメモリを解放すると、プレイヤーがリソースパック／Addon をダウンロードするとき**進行バーが止まり**、しかも**サーバーの再起動でしか復旧できません**。正しいやり方は定時再起動の時間帯を計画することで、「メモリが高いから消しておく」ではありません。
:::

### 4.2 チャンクとワールドデータの問題

BDS のワールドデータは **`worlds/`** ディレクトリの下にあり、ワールドごとに 1 つのサブフォルダです。非常に重要な挙動があります：

> サーバーは起動時に `worlds/` の中から **`server.properties` の `level-name` と同名**のディレクトリを探します。見つかればそれを使い、**見つからなければ新しいワールドを作ります**。

つまり **`level-name` を 1 文字間違えてもサーバーはエラーを出さず、静かに新しいワールドを生成します** —— プレイヤーには「自分のセーブデータが消えた」と見えます。だから「セーブデータが変わった」と気づいたら、まず `level-name` と `worlds/` のディレクトリ名を照合してください。

| 現象 | 考えられる原因 | 対処 |
| --- | --- | --- |
| ワールドの読み込み失敗／起動時にワールド関連のエラー | セーブデータの破損、または前回の保存が中断された | **起動の繰り返しを止め**、バックアップから復元 |
| コアを替えたらワールドが読めない | サードパーティコアのセーブデータ互換性は公式 BDS に劣る | 元のコアに戻すか、コアのドキュメントに従って移行 |
| ワールドをインポートしても反映されない | ディレクトリ名が `level-name` と一致しない | ワールドのディレクトリを `level-name` の値に改名 |
| セーブデータが丸ごと失われた | 一部のファイルしかバックアップしていない | `worlds/` の**ディレクトリ全体**をバックアップ |

バックアップからの復元の完全な手順は [バックアップと復元](/tutorials/java/backup) を参照。
:::tip コピーやバックアップの前に正常に停止する
コンソールで `stop` を実行し、プロセスが本当に終了してから `worlds/` をコピーしてください。プロセスがまだファイルを書いている最中にコピーすると、「見た目は完全だが実際は壊れている」セーブデータが得られがちです。
:::

### 4.3 アドオンパックとリソースパック

2 つの前提：**統合版形式のパックでなければならない** —— Java 版のデータパック／リソースパックと統合版のアドオンパックは別物で、互換しません；**パックは正しく配置され登録される必要がある** —— ファイルをコピーしただけでは、サーバーは自動で有効にしません。確認済みのディレクトリと登録方法は次のとおりです：

| 種類 | 配置先ディレクトリ |
| --- | --- |
| ビヘイビアパック（Behavior Pack） | `development_behavior_packs` |
| リソースパック（Resource Pack） | `development_resource_packs` |

あるワールドでパックを有効にするには、**そのワールドの作業ディレクトリ**に対応するマニフェストファイルを作り、パックの UUID とバージョンを書きます。UUID はパック自身の `manifest.json` から取ります：

```json
[
    {
        "pack_id": "33556fcf-d192-4d5f-96a0-29357702af7b",
        "version": [ 1, 0, 0 ]
    }
]
```

うち：ビヘイビアパックは `world_behavior_packs.json`、リソースパックは `world_resource_packs.json` に書きます；複数のパックが衝突する場合、**前に並ぶパックが優先**されます。

そのほかの要点：**`texturepack-required=true`** はクライアントにサーバーのリソースパックのダウンロードを強制し、有効にするとプレイヤーが自分で有効にしたクライアントのリソースパック（マーケットのパックを含む）が無効になります；**マーケットプレイスのパックはサーバーに適用できません**；サーバーのルートディレクトリには **`valid_known_packs.json`** もあり、これはサーバーが維持する**既知のパックの一覧**で、サーバーはこれで検証します。その正確な形式と維持の流れは**公式ドキュメントを優先**し、日常の操作は上の「ディレクトリに置く + world_*_packs.json を書く」流れで十分です；**クライアントがリソースパックのダウンロードで止まる**場合、パック自体の問題のほかに、サーバーのメモリ状態が原因のこともあります（4.1 を参照）。そのときはサーバーの再起動で復旧することが多いです。

PMMP には公式の既知問題もあります：**サーバーが大きめのリソースパックを使うと接続問題が出る**（公式の例は 1 MB を超えるパック）。公式の切り分け手段は大きなパックを外して再試行すること；もう 1 つ有効な可能性がある回避策は `pocketmine.yml` の `network.max-mtu-size` を段階的に下げる（たとえば毎回 100 下げて測る）ことですが、公式はこれが**回避策**にすぎず帯域効率を下げるので、根本原因を探すべきだと説明しています。

### 4.4 権限とホワイトリスト

BDS の権限とホワイトリストは**2 つの独立したファイル**で、フィールドも違い、混同しやすいです。**管理者（OP）は `permissions.json`** にあり、項目は `xuid` と `permission` で構成されます：

```json
[
    {
        "permission": "operator",
        "xuid": "451298348"
    }
]
```

- `permission` の有効な値は 3 つだけ：**`operator` / `member` / `visitor`**。
- **`online-mode` は有効でなければなりません**。XUID はオンラインでアカウントを検証する必要があるからです。
- サーバーの稼働中にこのファイルを変更した場合、**`permission reload`** を実行しないと反映されません；`permission list` で現在の権限を確認できます。
- リストにない新規プレイヤーには `default-player-permission-level` の設定が適用されます。ファイルを編集する以外に、**ゲーム内で直接**プレイヤーの権限を変えることもできます。

**ホワイトリストは `allowlist.json`** にあり、項目のフィールドは：

| フィールド | 意味 |
| --- | --- |
| `name` | プレイヤーの**ゲーム名／ニックネーム（gamertag）**。完全に一致する必要がある |
| `xuid` | プレイヤーの XUID。**すでに `name` を書いていればこの項目は省略できる** |
| `ignoresPlayerLimit` | `true` のとき、そのプレイヤーは人数が満杯でも入れる |

いくつかの重要な挙動：`name` だけを書いた場合、**同名のプレイヤーが接続したときに XUID が自動で補われます**。つまり名前を間違えるとその人は永遠に入れず、自動で訂正もされません；**ホワイトリストは `online-mode` が有効なときだけ機能します**。正規アカウント認証を切ると、プレイヤーはホワイトリストの名前を騙って入れるので、ホワイトリストは形だけになります；プレイヤーが**gamertag を変えた**あと、古い名前の項目は一致しなくなるので更新が必要です；ファイルを手で編集したときにサーバーが動いていたなら、対応する reload コマンドで変更を反映させる必要があります。

| 現象 | 考えられる原因 | 対処 |
| --- | --- | --- |
| OP のはずの人が OP でない | 項目が `permissions.json` にない、または書いたが reload していない | 項目を補って reload、またはゲーム内で直接設定 |
| `permissions.json` に足したのに効かない | `online-mode` が切れており XUID を検証できない | `online-mode` を有効にする |
| ホワイトリストの人が入れない | `name` が実際の gamertag と完全一致していない（大文字小文字、空白、改名） | 正確な名前を確認するか、XUID を直接書く |
| 誰でも入れる | ホワイトリストが有効でない、または `online-mode` が切れている | `allow-list` と `online-mode` を確認 |
:::note フィールド名は公式ドキュメントを優先
上記のフィールド名と挙動は公式の説明によります。**バージョン間でフィールドや既定値が調整されることがあります**。実際は BDS 公式ドキュメント（および同梱の `bedrock_server_how_to.html`）を優先してください。
:::

### 4.5 Java 版との挙動の違い

プレイヤーが報告する多くの「バグ」は、実は**2 つのバージョンがもともと違う**だけです：レッドストーンの仕組み、モブのスポーン規則などに違いがあります。この層はここで繰り返し説明せず、[JAVA と統合版](/wiki/editions) を直接見てください。

## 5. 切り分けの順序

次の順で進めば、各手順で可能性を半分に減らせます。**手順を飛ばさない**こと。

1. **サーバーのプロセスが本当に動いているか確認。** コンソールのウィンドウが残っているか、プロセス一覧にまだあるか。
2. **ポートを待ち受けているか確認。** Linux と Windows のコマンドは下記。
3. **ポートとプロトコルを確認。** ポート番号が正しいか、開放しているのが **UDP** か（既定 19132、IPv6 は 19133）。
4. **クライアントのバージョンを確認。** クライアントとサーバーのバージョンは一致が必要。[プロトコルのバージョンとバージョン選択](/tutorials/bedrock/protocol) を参照。
5. **ネットワークの経路を確認。** LAN / 公衆 IP / トンネルで経路が違う。CGNAT や二重 NAT がないか。
6. **サーバーのコンソールとログを見る。** エラーの原文はどんな推測より価値があります。BDS の起動とエラーはコンソールに出力されます。
7. **権限とホワイトリストを確認。** プレイヤーはキックされたのか、そもそも接続できていないのか？ キックなら通常コンソールに理由が出ます。
8. **ワールドとアドオンパックの完全性を確認。** `level-name` が `worlds/` 下のディレクトリ名と一致するか；パックが正しいディレクトリにあり登録されているか。

手順 2 のコマンド：Linux は `ss -ulnp | grep 19132`（`-u` は UDP のみ）；Windows は `netstat -ano | findstr 19132`（`-a` はすべての接続と待ち受け、`-n` は名前解決なし、`-o` はプロセス ID を表示）；PowerShell なら `Get-NetUDPEndpoint -LocalPort 19132` がより直感的です。

```bash
ss -ulnp | grep 19132
```

```bat
netstat -ano | findstr 19132
```

**現象の対照表：**

| 現象 | まず何を調べるか | よくある原因 |
| --- | --- | --- |
| プロセスがない | コンソールのエラー原文 | ランタイムの欠如、Java / PHP のバージョン違い、ポートの使用中、設定の書き間違い |
| プロセスはあるがポートを待ち受けていない | 起動ログに bind 失敗があるか | ポートの使用中、`enable-lan-visibility` が 19132/19133 を奪って bind |
| ポートは待ち受け、本機からはつながるが外部からは駄目 | 公衆からの到達性 | セキュリティグループ／ファイアウォールが UDP を開放していない、CGNAT、二重 NAT |
| ポート検査は通るがプレイヤーが入れない | 検査ツールが TCP か UDP か | TCP しか開放していない |
| サーバーのバージョンが古いと表示される | クライアントとサーバーのバージョン | プロトコルの不一致。サードパーティコアのビルドが古すぎる |
| 入れるが入ってすぐ落ちる | コンソールにキックの理由があるか | ホワイトリスト、権限、人数上限 |
| 入れるがとても重い | シングルコアの使用率、`tick-distance`、エンティティ数 | シングルコアのボトルネック、マップが大きすぎる |
| セーブデータが「消えた」 | `level-name` と `worlds/` のディレクトリ名 | `level-name` の書き間違いで、サーバーが新しいワールドを作った |
| アドオンパックが効かない | パックの種類と配置先 | ディレクトリを間違えた、world_*_packs.json を書いていない |

## 6. 助けを求めるときに何を出すか

以下を一度に全部出すと、何往復も節約できます：

| 出す情報 | なぜ必要か |
| --- | --- |
| **サーバーコアとビルドのバージョン** | BDS のバージョン番号、または Nukkit 系 / PMMP のコア名とビルド番号。コアによって切り分けの経路が違う |
| **ゲームバージョン / プロトコルバージョン** | クライアントとサーバーがそれぞれ何のバージョンか。統合版の第一の切り分け項目 |
| **OS とアーキテクチャ** | Windows か Linux か、ディストリビューションとバージョン、64 ビットか、x86-64 か |
| **コンソールのエラーの完全な原文** | **言い換えない、半分だけ切り取らない**。エラー原文のキーワードが問題を直接指す |
| **最近何を変えたか** | コアを上げた？ ポートを変えた？ アドオンパックを足した？ `server.properties` を変えた？ |
| **以前は正常だったか** | 「一度も成功していない」と「昨日までは平気だった」はまったく別の経路 |
| **すでに試したこと** | 同じ提案を繰り返さないため。どの方向が除外済みかも分かる |
| **ネットワークの状況** | LAN か公衆か、公衆 IP があるか、どのトンネルか、ポート転送をどう設定したか |
:::tip エラー原文の出し方
コンソールの出力をそのままテキストとしてコピーするか、ログファイルを貼ってください。**写真、スクリーンショット、最後の 1 行だけ**は切り分けを遅くします。出力が長い場合は、1 行だけ残すのではなく、エラーの前後をそれぞれ数行残してください。
:::
