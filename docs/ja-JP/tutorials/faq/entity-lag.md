サーバーの TPS が 20 から 1 桁に落ち、`/spark tps` が MSPT を長期的に 50 ms 超と示しているのに、CPU 使用率は高くなくメモリも爆発していない —— この類のラグは、マシンが足りないのではなく**エンティティ（entity）とブロックエンティティ（block entity）の堆積**である可能性が高いです。

エンティティ系のラグには 2 つの特徴があります：**メモリはあまり食わないのに、メインスレッドの CPU は確実に食う**；そして**再起動で数分しか緩和されない**。発生源が残っていれば、堆積はすぐ戻ります。本記事は「なぜ重いか → ドロップアイテム → モブ → ホッパー → 調べ方 → 誤解」の順で説明します。

:::note 適用範囲
本記事は Java 版サーバー（バニラ / Spigot / Paper 系）を主対象にします。文中の設定キーはどのファイルに属するかを明記します。**コアやバージョンが違えば構造と既定値は変わります**。作業前に手元に生成された設定ファイルを確認してください。
:::

## 1. なぜエンティティは性能キラーなのか

### 1.1 すべてがメインスレッドで順番待ちする

Minecraft サーバーの主ロジックは**シングルスレッドの tick ループ**です：毎秒 20 tick、1 tick の予算は **50 ms**（いわゆる MSPT）。すべてのワールド、すべてのエンティティ、すべてのブロックエンティティの演算が、この 1 本のスレッドで順番に処理されます。

```
1 秒 = 20 tick、1 tick の予算は 50 ms
MSPT 40 ms  → TPS 20（健全）
MSPT 60 ms  → TPS は 16 前後まで低下（重くなり始める）
MSPT 200 ms → TPS 5（ほぼ遊べない）
```

だから「エンティティが多い」が致命的なのは、それが**この唯一のスレッドの時間予算を直接消費する**からです。CPU が何コアあっても、メモリをどれだけ与えても、メインスレッドは救えません（詳細は [パフォーマンス最適化](/tutorials/java/optimize)）。

### 1.2 各エンティティは毎 tick 何をしているか

1 つのエンティティは毎 tick、通常これらの段階を通ります：

- **AI と目標選択**：goal selector、経路探索（pathfinding）、センサー（sensor）の走査；
- **物理と衝突**：重力、移動、他のエンティティやブロックとの衝突判定；
- **タイマー**：着火、ポーション効果、消滅（despawn）のカウントダウン；
- **結合チェック**：ドロップアイテムと経験値オーブは、近くに結合できる同種があるか確認する；
- **追跡と同期**：どのプレイヤーに位置更新を送る必要があるかの判断。

モブ系のエンティティがこれらの項目を最も多く占め（とくに経路探索とセンサー）、ドロップアイテム単体のコストはずっと小さいですが**数は簡単に 1 万を超えます** —— これが「1 チャンクに数千のドロップアイテム」が「数十匹のゾンビ」より致命的な理由です。

### 1.3 分類：何が tick し、何がしないか

| 種類 | 毎 tick 演算するか | 説明 |
| --- | --- | --- |
| モブ / 動物 / モンスター | する | 最もコストが大きい類：AI、経路探索、センサー、衝突 |
| ドロップアイテム（アイテムエンティティ） | する | 単体は安いが、極端な量まで堆積する。消滅カウントダウンと結合チェックがある |
| 経験値オーブ | する | ドロップアイテムと同様。コアは通常、結合を制限するオプションを提供する |
| 発射物（矢、トライデント、雪玉、ファイアボール、エンダーパール） | する | 純粋な物理演算。`spigot.yml` に `arrow-despawn-rate`、`trident-despawn-rate`（Paper 公式ドキュメントでは現在 1200）がある |
| トロッコ / ボート | する | エンティティ + 衝突 + 乗員のロジック。ホッパー付きトロッコはさらにアイテムを運ぶ |
| 額縁 / 絵画 / リードの結び目などの吊り下げエンティティ | する（低頻度） | `spigot.yml` の `hanging-tick-frequency`（Spigot wiki の記録では既定 100）が更新間隔を制御する |
| アーマースタンド / マーカー（marker） | する | どちらもエンティティ。Paper の `paper-world-defaults.yml` に `entities.armor-stands.tick`、`entities.markers.tick`（現在の既定はいずれも `true`）があり、切るとコストを節約できる |
| スポナー | する | ブロックエンティティ。毎 tick、スポーン可能区域を計算する |
| ホッパー | する | ブロックエンティティ。古典的な性能キラー。第 4 節を参照 |
| かまど / 溶鉱炉 / 燻製器 | 燃焼中のみ | 待機中のかまどに毎 tick のロジックはない |
| チェスト / 樽 / シュルカーボックス | しない（自体は tick しない） | 純粋なコンテナに毎 tick のブロックエンティティロジックはなく、開かれたりホッパーからアクセスされたときにコストが生じる |
| コマンドブロック | しない（起動時のみ） | 待機中は演算しない |

:::warn 「コンテナブロック」は「常に計算している」ではない
最も混同しやすい点：**チェストやかまどのような「コンテナブロック」自体は毎 tick 演算しません**。毎 tick 演算するのはブロックに付いた**ブロックエンティティ（block entity）**で、しかも ticker を持つもの（ホッパー、スポナー、燃焼中のかまど）だけが CPU を食います。だから「チェストに物がたくさん」は重くなく、「ホッパーの列が長くて暇」が重いのです。
:::

### 1.4 チャンクの読み込みとチャンク tick は別物

エンティティは**tick しているチャンク**でのみ演算され、「読み込まれている」チャンクが tick しているとは限りません。Paper の `/paper chunkinfo` は現在のチャンクをいくつかに分類します（定義は Paper 公式コマンドドキュメントを参照）：

| 種類 | 意味 |
| --- | --- |
| Entity Ticking | 完全に tick：エンティティ、ブロック、スポーンがすべて動く |
| Block Ticking | 通称 lazy chunk：ブロックのロジックは動くがエンティティは tick しない |
| Full | 通称 border chunk：tick しないがブロックとエンティティにアクセスできる |
| Inactive | アクセス不可。チャンク生成中のみ |
| Total | 以上の合計 |

これで 2 つのよくある現象が説明できます：

- **遠くのモブが必ずしもサーバーを重くしない**：そのチャンクが Block Ticking や Full にすぎず、エンティティが tick されていない可能性がある；
- **読み込みは演算ではない**：`/paper holderinfo` が示すのはメモリ上に保持しているチャンク数で、CPU 上の tick 負荷とは別物。

:::note ドロップアイテムは自分でチャンクを読み込まない
厳密には、ドロップアイテム自体がチャンクを「読み込む」ことは**ありません**。バニラでチャンクの読み込みを維持するのはプレイヤー、スポーン地点チャンク、ポータル、`/forceload`、プラグインです。ただしそのチャンクが上記の理由で読み込まれたままなら、中のドロップアイテムは tick され続け、堆積し続けます。
:::

### 1.5 エンティティの有効範囲（activation range）

「読み込まれているが近くに誰もいない」エンティティが CPU を無駄に食わないよう、Spigot 系は**エンティティの有効範囲**を導入しました：この距離を超えたエンティティは**読み込まれなくなるのではなく、tick の頻度が下がります**。

Paper 公式ドキュメントの `spigot.yml` の `entity-activation-range` の説明は：エンティティが正常に tick する、プレイヤーとの距離（単位はブロック）；この範囲を超えるとエンティティの tick 頻度が下がる；0 以下にするとその分類の間引きが無効になり、読み込まれたエンティティはどれだけ遠くても正常に tick する、というものです。

Paper のドキュメントが現在示す構造は次のとおりです（**既定値はバージョンで変わるため、手元のファイルを優先**）：

```yaml
# spigot.yml → world-settings.default
entity-activation-range:
  animals: 32
  monsters: 32
  raiders: 64
  misc: 16
  water: 16
  villagers: 32
  flying-monsters: 32
  wake-up-inactive:
    animals-every: 1200
    animals-for: 100
    animals-max-per-tick: 4
    monsters-every: 400
    monsters-for: 100
    monsters-max-per-tick: 8
    villagers-every: 600
    villagers-for: 100
    villagers-max-per-tick: 4
    flying-monsters-every: 200
    flying-monsters-for: 100
    flying-monsters-max-per-tick: 8
  villagers-work-immunity-after: 100
  villagers-work-immunity-for: 20
  villagers-active-for-panic: true
  tick-inactive-villagers: true
  ignore-spectators: false
```

必ず知っておくべき代償が 2 つ：

- `tick-inactive-villagers`（Paper のドキュメントでは現在の既定 `true`）を切ると、**村人がバニラどおりに働かなくなり**、プレイヤーが近くにいないと補充されません；
- `wake-up-inactive` は「眠っている」エンティティをどれだけの頻度で起こすかを決め、けちりすぎると装置や農場の挙動が明らかにおかしくなります。

[レッドストーン技術とレッドストーン](/tutorials/java/redstone) と合わせて：**レッドストーン技術サーバーではここを慎重に動かす**か、いっそ Fabric / Leaves に切り替えてください。

## 2. ドロップアイテムの堆積

### 2.1 よくある原因

- **農場に撃破と回収の閉ループがない**：トラップタワーがドロップアイテムをそのまま地面に落とす；
- **サボテン / サトウキビ / 自動農場が産物を地面に吐き出す**；
- **プレイヤーが気軽に物を捨てる**：インベントリ整理、死亡ドロップ、引っ越しのゴミ捨て；
- **TNT / 砂の複製機**のような複製装置が生むエンティティ；
- **ホッパーの線が切れている**：対象のチェストが満杯、ホッパーが詰まっている、チャンクのアンロードでアイテムが途中で止まるのに上流は生産を続ける；
- **`/give` の濫用やコマンドブロックのループ配布**；
- **農場の夜通し稼働**：スポーン地点チャンク、`/forceload`、プラグインが強制読み込みするチャンクでは、無人のときも装置が動く。

### 2.2 なぜドロップアイテムはそれほど痛いのか

- **単体は安いが数が恐ろしい**：1 チャンクに数千のドロップアイテムがあれば、積み上がって無視できない MSPT になる；
- **結合は思ったより積極的でない**：バニラのアイテムはごく近距離でしか結合しない。Paper の `entities.behavior.only-merge-items-horizontally`（現在の既定 `false`）は同じ高さのアイテムだけを結合するかを制御し、`true` にすると視覚的な異常を避けられるが**結合はさらに少なくなる**；
- **各ドロップアイテムが tick される**：物理、消滅カウントダウン、結合チェックがすべて付いてくる；
- **ホッパーがそれらを走査する**：ホッパー上方のドロップアイテムは、ホッパーが動き続ける原因の 1 つ（第 4 節）；
- **プレイヤーが近づくとインベントリに吸い込まれ**、追加のインベントリとネットワークのコストが生じる；
- **セーブデータも大きくなる**：エンティティはチャンクのセーブデータに書き込まれるので、量が多いと保存時間と容量が増える。

### 2.3 診断

まず**数を把握できる**手段を使い、感覚で判断しないこと：

| 手段 | 用途 |
| --- | --- |
| `/paper entity list minecraft:item` | Paper のコマンド。現在 tick しているエンティティを列挙し、`Total Ticking: N, Total Non-Ticking: M` の形で出力し、種類ごとに（ticking 数、非 ticking 数）を示す。ドロップアイテムが非 ticking 側に大量に出るなら、有効範囲外で間引かれている。総量には依然注意 |
| `/spark tps`、`/spark health` | まず「本当に重いのか」、TPS かメモリかディスクかを判断 |
| `/spark profiler start --timeout 60` | サンプリング後、呼び出しツリーで `ItemEntity.tick`、`Entity.tick` の割合を見る |
| `/spark tickmonitor --threshold-tick 100` | 100 ms を超えた tick だけを報告し、現場の操作と合わせて特定する |
| `/paper chunkinfo` | 各ワールドの読み込みチャンクの種類分布を見て、「読み込みすぎ」か「エンティティが多すぎ」かを判断 |
| `/forceload query` | どのチャンクが強制読み込みされているかを調べる（この類のチャンクの農場が最も暴走しやすい） |
| `/debug start` / `/debug stop` | バニラ標準の性能サンプリング。debug profile を生成する |

spark の完全な使い方とグラフの読み方は [spark で性能を分析する](/tutorials/ops/spark) を参照。

**`/kill @e[type=item]` は鈍器**で、応急時のみ使います：

```bash
# 現在読み込み済みのチャンク内のすべてのドロップアイテムを整理
/kill @e[type=item]

# 範囲を限定：実行者を中心に 64 ブロック以内
/kill @e[type=item,distance=..64]
```

:::warn ドロップアイテムの整理は取り消せない
地上のすべてのアイテムを**無差別に削除**します：プレイヤーが落としたばかりの物、農場が回収中の物、死亡ドロップの装備、すべて消え、復元できません。**プレイヤーがオンラインのときに全サーバーで気軽に実行しない**こと。長期的な方案にもしないこと —— 30 分後にはまた地面が埋まります。
:::

**「あるチャンクに数千のエンティティがいる」をどう特定するか？** エンティティの総数は「多い」ことしか教えてくれず、「どこに」は教えてくれません。この順で探します：

1. まず `/paper chunkinfo` で「チャンクの読み込みすぎ」という原因を除外する；
2. 次に spark でサンプリングし、ワールドごと・区域ごとのホットスポットを比較する。または `/spark tickmonitor --threshold-tick 100` を動かしながら疑わしい区域へ行き、tick が明らかに長くなるか見る；
3. `@e` セレクタで範囲を数える：疑わしい位置に立って `/execute if entity @e[type=item,distance=..16]` を実行し、コマンドのフィードバックの成功回数から桁を判断する（フィードバックの形式はバージョンで異なるので実際の出力を優先）；
4. 長期的に見張る必要があるなら、チャンクごとにエンティティ数を一覧できるプラグインやパネルツールを使う。

:::tip timings は旧バージョンの話
旧 Paper の性能レポートは **timings** でした。Paper の公式ドキュメントは現在 `/tps`、`/mspt` を「`/spark` に置き換えられた」範疇に入れています —— **spark が使えるなら spark を使う**。レポートの基準が統一され、比較もしやすいです。
:::

### 2.4 対処

**最初の一歩は常に設計を変えることであり、設定を変えることではありません。** 農場を閉ループにします：撃破室 + 水流かホッパー付きトロッコでの回収 + 直接チェストへ。産物が地面に落ちないようにします。

**2 歩目が設定とプラグイン**です。

**ドロップアイテムの寿命**：バニラの仕組みでは約 5 分（6000 tick）で消えます。多くのコアはこの時間を調整でき、アイテムの種類ごとに設定できるものもありますが、**キー名、階層、既定値はコアとバージョンで異なります**。手元に生成された設定ファイルと公式ドキュメントを優先してください。

**定時整理プラグイン**（コミュニティでよくあるのは ClearLag の類）。選型と設定では次を重点的に確認します：

- **整理の間隔**：どれだけの頻度で整理するか（5〜10 分が多い）；
- **対象**：`item` だけか、経験値オーブや発射物、モブも一緒に消すか（後者は誤爆しやすい）；
- **事前の告知**：整理の前にカウントダウンを出し、プレイヤーが拾っている最中に消されないようにする；
- **保護ルール**：独自名のアイテムを除外、プレイヤーの死亡ドロップを除外、指定ワールドや指定区域を除外（産物の回収区域はとくに除外）；
- **互換性**：プラグインが自分のコアとゲームバージョンに対応しているか確認（[プラグイン入門](/tutorials/java/plugins) を参照）。

**結合半径 `merge-radius`**：これは Spigot / Paper 系に実在するキーで、`spigot.yml` の world-settings の下にあり、アイテムと経験値オーブの 2 項目に分かれます。Paper 公式ドキュメントが現在示す構造は：

```yaml
# spigot.yml → world-settings.default
merge-radius:
  item: 0.5
  exp: -1
```

注意すべきは**2 つの権威あるドキュメントが一致していない**ことです：Spigot wiki は同じキー群の既定値を item 2.5 / exp 3.0 と記録し、「アイテム／経験値オーブが地面上で結合する範囲」と説明しています；Paper 公式ドキュメントの exp の説明は「生成の瞬間に結合する。バニラにはこの挙動がなく、0 以下にすると無効」です。

:::tip 既定値の不一致こそ、手元のファイルを見るべき理由
同じキーでもコアやバージョンで既定値が違うのは、この類の最適化では常態です。**結合半径を大きくする**とドロップアイテムが早く積み上がりエンティティ数が減りますが、代償は**バニラの挙動の変更**で、アイテムの分離に依存する装置に影響しえます。レッドストーン技術サーバーでは慎重に。関連するキーに Paper の `entities.behavior.experience-merge-max-value`（現在の既定 `-1`、つまり経験値オーブ結合後の最大値を制限しない）があります。
:::

**セーブデータ側の保険**：Paper の `chunks.entity-per-chunk-save-limit` は、チャンクごとに**保存／読み込み**するある種類のエンティティ数を制限できます（Paper のドキュメントでは `experience_orb: -1` は無制限を意味し、`<entity-type>` ごとに設定できます）。制限するのは保存と読み込みの段階で、その場でエンティティを削除するわけではありません。「経験値オーブが一面に落ちる」ような場面の保険に向きます。

**無人のときに農場を動かさない**：`/forceload` を濫用しないこと。Paper の `unsupported-settings.disable-world-ticking-when-empty`（現在の既定 `false`、公式が明確に「サポート外」と記すオプション）は、プレイヤーも強制読み込みチャンクもないときにワールドの tick を止められます —— **変更前にバージョンの挙動を確認**。

## 3. エンティティの堆積（モブ）

### 3.1 よくある原因

- **スポナーの長期稼働**：とくに撃破／回収をしていないスポナー；
- **未照明の洞窟と夜間のスポーン**：プレイヤーの活動区域の地下がモブだらけ；
- **無制限の繁殖**：牛、羊、豚、鶏が一面に；
- **ペットが散らばる**：手懐けたオオカミ、ネコ、ウマがマップ中各所に；
- **村人の繁殖ホール**：村人が 100 を超えると POI 照会と経路探索のコストが顕著；
- **襲撃／行商人の堆積**：終わらない襲撃、誰も相手にしない行商人とそのラマ；
- **エンティティ密集型のレッドストーン装置**：トロッコの列、アーマースタンド、ドロップアイテムの連鎖；
- **ポータル産のピグリン**：Paper は `nerf-pigmen-from-nether-portals`（現在の既定 `false`）でこの挙動を切れます。

### 3.2 診断

- **spark profiler**：ホットスポットは `Entity.tick`、経路探索関連のメソッド、センサーの走査、村人の POI 照会に出ることが多い；
- **`/spark health`**：TPS、CPU、メモリ、ディスクの 4 つのうちどれが危ないかを確認；
- **`/paper entity list`**：エンティティの種類の分布を見る（どの種類の数が異常か）；
- **`/paper mobcaps`**：あるワールドの全体のスポーン上限と実際の占有、スポーン可能チャンク数を見る；
- **`/paper playermobcaps`**：プレイヤー 1 人ごとのローカルなスポーン上限を見る；
- **`/paper chunkinfo`**：エンティティ数とチャンクの読み込み状況を対応させ、「ある強制読み込みチャンクがスポーンさせている」のかを判断。

### 3.3 対処

**（1）エンティティの有効範囲**：1.5 節を参照。最も効果的で最も装置を傷つけやすい段階なので、変更前に設定をバックアップし、変更後に農場を再テストします。

**（2）スポーン範囲 `mob-spawn-range`**：単位はチャンクで、プレイヤーの周囲どれだけ離れた場所までスポーンできるかを制御します。Paper 公式ドキュメントは現在 `8`、Spigot wiki は `6` と記録 —— **またバージョンで変わる既定値**です。手元のファイルを優先してください。小さくするとスポーンするモブの総量は減りますが、一部のトラップタワーの効率が落ちることがあります。

**（3）ワールドごとのスポーン上限**：`bukkit.yml` の `spawn-limits`。Paper 公式ドキュメントが現在示す既定値は：

```yaml
# bukkit.yml
spawn-limits:
  monsters: 70
  animals: 10
  water-animals: 5
  water-ambient: 20
  water-underground-creature: 5
  axolotls: 5
  ambient: 15
```

Paper はさらに `paper-world-defaults.yml` で同じ上限をワールドごとに上書きできます（`entities.spawning.spawn-limits`。現在の既定はすべて `-1` で、`bukkit.yml` の値を使う）。また `entities.spawning.per-player-mob-spawns`（現在の既定 `true`）が、スポーン上限をプレイヤーごとに計算するか全体で共有するかを決めます。

**（4）ゲームルール**：バニラ標準で、最も即効性のある段階。

```bash
# 自然スポーンを止める（バニラの既定は true）—— トラップタワーが無効になる点に注意
/gamerule doMobSpawning false

# モブのドロップを止める（バニラの既定は true）
/gamerule doMobLoot false

# ランダム tick の速度。バニラの既定は 3。下げると作物の成長、延焼、氷雪の形成にも影響
/gamerule randomTickSpeed 3
```

:::warn ゲームルールは「一刀両断」
`doMobSpawning`、`doMobLoot` を切ると、**それに依存する遊びがすべて一緒に無効になります**（トラップタワー、経験値ファーム、ウィザースケルトンの頭の回収など）。イベントサーバーや一時的な消火には向きますが、長期的に最適化手段として入れっぱなしにするものではありません。
:::

**（5）スポナー関連**：

```yaml
# spigot.yml → world-settings.default
nerf-spawner-mobs: false
```

Paper のドキュメントの `nerf-spawner-mobs` の説明は「スポナーが生むモブの AI の大部分を無効にする」（現在の既定 `false`）。`true` にするとかなりの AI コストを節約できますが、スポナー産のモブの挙動は明らかに変わります。Paper には `tick-rates.mob-spawner`（現在の既定 `1`）もあり、スポナーがスポーン可能区域を計算しエンティティを生成する頻度を制御します。

**（6）スポナー制御プラグイン**：多くのプラグインがスポナーの有効距離、1 分あたりの生成数、プレイヤーの在席要求を制限できます。選型では同じくコアとバージョンの互換性を確認し、「戻せる、ホワイトリストできる」方案を優先します。

**（7）農場の設計**：撃破室 + 回収の閉ループ + 速やかな消滅が、どの設定よりも確実な解法です。ドロップアイテムが地面に落ちなければ、エンティティ数は暴走しません。

**（8）装飾的なエンティティ**：アーマースタンド、マーカー（marker）はどちらもエンティティです。Paper の `entities.armor-stands.tick`（現在の既定 `true`。公式の説明は「切るとアーマースタンドの tick を止められ、アーマースタンドが多いときに性能が上がる」）と `entities.markers.tick`（現在の既定 `true`。公式は他のエンティティの乗員としての挙動に影響しうると注意）は必要に応じて切れます。

**（9）強制消滅**：Paper の `entities.spawning.despawn-time.<entity-type>`（現在の既定 `disabled`）は指定したエンティティ種別に強制消滅時間を設定できます；`entities.spawning.despawn-ranges` はランダム消滅距離を制御します（既定は `default`、つまりバニラの規則を使う）。どちらもバニラの挙動を変えるので、動かす前に何を変えるか考えてください。

## 4. ブロックエンティティとホッパー

### 4.1 ホッパーが古典的な元凶である理由

ホッパーは**ブロックエンティティ**で、そのチャンクが tick されている間、毎 tick やることがあります：

- 上方に吸い込めるドロップアイテムがあるか、引き出せるコンテナがあるかを確認する；
- クールダウンに従ってアイテムを運ぶ（バニラは 8 tick に 1 回で、`spigot.yml` の `ticks-per.hopper-transfer` に対応）；
- コンテナへのアクセスで追加コストが生じ、プラグインが搬送イベント（InventoryMoveItemEvent）を購読しているとさらに大きくなる。

Paper 公式ドキュメントの `spigot.yml` の関連キーの説明は：

- `ticks-per.hopper-transfer`（現在の既定 `8`）：ホッパーがアイテムを運ぶ間隔の tick；
- `ticks-per.hopper-check`（現在の既定 `1`）：ホッパーがアイテムの引き出しを確認する間隔の tick；
- `hopper-amount`（現在の既定 `1`）：ホッパーが 1 回に運ぶアイテム数。上限はスタックサイズ；
- `hopper-can-load-chunks`（現在の既定 `false`）：「ホッパーがチャンクを読み込むか」に関わるスイッチ。意味と既定値は公式ドキュメントと手元の設定を優先。

Spigot wiki はさらに注意しています：`hopper-check` を大きくすると**同期がずれてほとんどのホッパー装置が壊れる**。つまり、この類の「性能最適化」はレッドストーン技術の場面ではほぼ必ず問題を起こします。

```yaml
# spigot.yml → world-settings.default
ticks-per:
  hopper-transfer: 8
  hopper-check: 1
hopper-amount: 1
```

### 4.2 ホッパーのコストを減らす方法

| やり方 | 説明 | 代償 |
| --- | --- | --- |
| 長いホッパーの列を水流／氷の道に置き換える | アイテムを水で流し、終点にホッパーを 1 つ置いて回収 | 物流の再設計が必要 |
| ドロッパーで 1 本のホッパーの線に集める | 「チェストごとにホッパー 1 つ」の重複を減らす | レッドストーンの制御が必要 |
| 遊休ホッパーを解体する | 廃止した装置、壊れた物流の線は世界に残っていても tick する | なし |
| ホッパー付きトロッコで運ぶ | エンティティ 1 つでホッパーの列 1 本分。長距離に向く | トロッコ自体もエンティティ |
| コアのホッパー最適化を有効にする | たとえば Paper の `hopper` セクション | 搬送イベントに依存するプラグインに影響しうる |
| 満杯のホッパーの仕事を減らす | Paper の `hopper.cooldown-when-full`（現在の既定 `true`） | なし。既定で有効な最適化 |

Paper の `paper-world-defaults.yml` にはホッパー専用のセクションがあります：

```yaml
# paper-world-defaults.yml
hopper:
  cooldown-when-full: true
  disable-move-event: false
  ignore-occluding-blocks: false
```

- `cooldown-when-full`：Paper のドキュメントの説明は「ホッパーが満杯のとき、新しいアイテムの引き出しを試み続けるのではなく短いクールダウンを与える」；
- `disable-move-event`：搬送イベントを切ってコストを節約するが、**そのイベントに依存するプラグインは無効になる**；
- `ignore-occluding-blocks`：遮蔽ブロックに関するチェックを無視する。

:::note 構造と既定値はバージョンで変わる
上のセクションの形は Paper のバージョンによって変わっています（たとえば `cooldown-when-full` は以前 `enabled` / `movement-ticks` を持つ子ノードでした）。**手元に生成された `paper-world-defaults.yml` と Paper 公式ドキュメントを優先**してください。
:::

### 4.3 ついでに：コンテナの更新と「サポート外」のスイッチ

Paper の `tick-rates.container-update`（現在の既定 `1`）は、サーバーがコンテナとインベントリを更新する頻度を制御します。Paper 公式ドキュメントは明確に警告しています：**1 より大きくするとアイテムの非同期／複製（ghosting）を起こし、採掘の進行が不可解にリセットされたように見え、「サーバーが重い」ような視覚的な錯覚も生みうる**。動かす価値のない最適化項目です。

Paper の `unsupported-settings.ticking.block-entities` と `ticking.chunks`（現在の既定はいずれも `true`、公式が「サポート外」と記す）は、ブロックエンティティやチャンクの tick をまとめて止められます。**本番サーバーで触らないでください** —— ゲームロジックを切るのと同じです。

## 5. 切り分けの流れ

エンティティ系のラグの切り分け順は他の性能問題と同じです：**まず測る、次に特定する、最後に手を動かす**。

### 5.1 7 つの手順

1. **測る**：`/spark tps` で TPS と MSPT、`/spark health` で CPU かメモリかディスクかを見る。「本当にメインスレッドが使い切られている」ことを確認してから先へ。
2. **ホットスポットを探す**：`/spark profiler start --timeout 60`。サンプリング後に呼び出しツリーを見る —— `Entity.tick`、`ItemEntity.tick`、ブロックエンティティの tick、経路探索／センサーのメソッド。どの枝が最も太いかが主嫌疑。グラフの読み方は [spark で性能を分析する](/tutorials/ops/spark) を参照。
3. **チャンクと種類を特定**：`/paper entity list` で種類の分布、`/paper chunkinfo` でチャンクの種類の分布、`/forceload query` で強制読み込みを調べる。
4. **性質を判断**：**設計の問題**（農場が閉ループでない、装置を誰も見ていない）か、**設定の問題**（スポーン範囲、有効範囲が緩すぎる）か。ほとんどの場合は設計の問題です。
5. **まず設計を変える**：撃破室を足す、回収を足す、廃止した装置を解体する、農場を無人のまま夜通し動かさない。変えたら測る。
6. **それから設定を調整**：設計を変えても足りないときだけ、`spigot.yml` / `bukkit.yml` / `paper-world-defaults.yml` のエンティティ関連の項目を動かす。**1 回に 1 項目だけ**、変更前にバックアップ（[サーバーの設定](/tutorials/java/config) を参照）。
7. **再測定して記録**：変えたらすぐ同じ場面（同じ装置、同じ時間帯、同じ人数）で再測定し、MSPT が本当に下がったか確認する。「何を、なぜ、どう効いたか」を変更ログに書く。**再測定のない最適化はやっていないのと同じ。**

### 5.2 早見表

| 現象 | 考えられる原因 | まず何を調べるか | 対処 |
| --- | --- | --- | --- |
| 地面にドロップアイテムが散乱し、TPS がじわじわ下がる | 農場に回収の閉ループがない、ホッパーの線が切れている、プレイヤーが捨てている | `/paper entity list minecraft:item`、spark の呼び出しツリー | 農場の設計を直す。定時整理プラグインで保険 |
| ある区域に来ると重く、離れると平気 | そのチャンクに大量のエンティティか密集した装置 | `/paper chunkinfo`、`/forceload query`、spark でワールド／区域ごとに比較 | 装置を解体・改修。不要な強制読み込みを解除 |
| 夜や地下でスポーンしたあとに重くなる | 未照明区域のスポーン | `/paper entity list`、`/paper mobcaps` | 洞窟を照明。`mob-spawn-range` を締める。必要なら `doMobSpawning` |
| 村人ホールの近くで重い | 村人の数、POI 照会と経路探索のコスト | spark の村人関連のホットスポット、`/paper entity list minecraft:villager` | 繁殖を制限。必要なら `tick-inactive-villagers` を切る（バニラの挙動が変わる） |
| 多くの装置が遊休でも重い | ホッパー、スポナー、アーマースタンドなどのブロックエンティティとエンティティが空回り | spark のブロックエンティティとエンティティ tick の割合 | 遊休装置を解体。コアのホッパー最適化を有効に。アーマースタンドの tick を切る |
| 再起動直後は正常、その後また重い | 発生源が未処理 | 復帰に要する時間を観察し、上の切り分けと照合 | 手順 1〜5 に戻り、発生源を処理する。再起動を繰り返さない |
| メモリを大量に与えても重い | ボトルネックはメインスレッドの CPU で、ヒープではない | `/spark health` の CPU と MSPT | 本記事に従ってエンティティを処理。[パフォーマンス最適化](/tutorials/java/optimize) を参照 |
| 整理プラグインを入れても重い | 対象／間隔が違う、または原因がドロップアイテムでない | spark の呼び出しツリー | まずホットスポットを確認してから、そのプラグインを残すか決める |

Java 版の各エラーと落とし穴の症状の早見表は [[JAVA] よくある質問](/tutorials/faq/faq-java) を参照。

## 6. よくある誤解

**誤解 1：再起動で解決する。**
再起動はワールドを読み込み直すだけで、しばらくは「軽くなった」ように見えます。トラップタワーが地面に物を落とし続け、ホッパーの線が切れたままで、強制読み込みチャンクが開いたままなら、堆積は同じ速度で戻ります。再起動は**応急手段**で、修復手段ではありません。

**誤解 2：メモリ（`-Xmx`）を増やせばエンティティのラグが治る。**
エンティティのラグは**メインスレッドの CPU** の問題で、ヒープの問題ではありません。どれだけ与えても tick はその 1 本のスレッドで走ります。`-Xmx` が大きすぎるとかえって GC の停止が長くなります。まずホットスポットを見つけてください。

**誤解 3：エンティティの上限は厳しくするほどよい。**
有効範囲、スポーン範囲、結合半径を攻めすぎると、**農場とレッドストーン技術の装置がそのまま無効になります**：村人が補充しない、トラップタワーが産出しない、アイテムの分離に依存する装置がめちゃくちゃになる。レッドストーン技術サーバーではまず [レッドストーン技術とレッドストーン](/tutorials/java/redstone) を見て、必要なら Fabric / Leaves に替えてください。Paper 系の中で挙動を原型を留めないほど変えるのではありません。

**誤解 4：`/kill @e` は万能薬。**
プレイヤーが手懐けたペット、装備付きのアーマースタンド、回収中の産物も一緒に消え、**取り消せません**。`/kill @e[type=item]` はいくらか穏やかですが、それでもプレイヤーや農場の地上にある正当なアイテムを消します。実行前に「これらのエンティティにプレイヤーの財産が含まれていないか」を考えてください。

**誤解 5：エンティティが多い＝重い。**
数は種類と位置で見ます。1 万のドロップアイテムが 1 チャンクに固まり、そばにプレイヤーがいれば災難です。1 万のドロップアイテムが 100 個の Block Ticking にすぎないチャンクに分散していれば、ほとんどコストを生まないかもしれません。**まず tick のホットスポット、それから数。**

**誤解 6：「最適化プラグイン」を入れれば解決する。**
最適化プラグインの多くは、上の設定項目を GUI や定時タスクに包んだだけです。**発生源を解決しなければ、整理は問題を「継続的な重さ」から「周期的に一瞬重くなる」に変えるだけ。** プラグインとコアの互換性も確認が必要で、質の悪いプラグイン自体がホットスポットになりえます。

**誤解 7：一度最適化すれば終わり。**
サーバーは生きています：新しい装置、新しい農場、新しいプレイヤーが負荷を変えます。主要な指標（TPS/MSPT、エンティティの数の桁）を日常の巡回に入れるほうが、一度きりの調整よりずっと役に立ちます。

---

> 設定項目の名前と既定値はコアとバージョンで変わります。手元に生成された設定ファイルと公式ドキュメントを優先してください。
