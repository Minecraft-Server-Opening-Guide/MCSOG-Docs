統合版の最適化は Java 版とほとんど別物です。Java 版にはプラグインがあり、`spark` があり、調整できる設定項目が数十個あります；公式の統合版サーバー（BDS）は**回せるつまみが非常に少なく**、しかも多くのキーはバージョンによって名前すら違います。だから統合版の「最適化」の重心は、設定ファイルを漁ることではなく**ワールドの設計**と**ハードウェア**にあります。

本記事は公式 **BDS** だけを扱います。まだサーバーを動かしていないなら、まず [BDS サーバー](/tutorials/bedrock/bds) を読んでください。サードパーティコアを使っているなら、第 7 節まで飛ばして構いません。

## 1. 統合版の性能モデルは Java 版と違う

| 比較項目 | Java 版（Paper など） | 統合版（公式 BDS） |
| --- | --- | --- |
| ワールドシミュレーション | メインスレッドが tick するが、コアが多数の最適化スイッチを提供 | ワールドシミュレーションはほぼ**単一スレッド**に載り、コアが多くてもあまり助けにならない |
| プラグインのエコシステム | 極めて豊富。最適化の多くはプラグインで行う | 公式サーバーは**プラグイン非対応**。代替はアドオンパックとスクリプト API |
| 調整できる項目 | コア設定 + プラグイン設定で数十項目 | `server.properties` で性能に関わるのはごく数項目 |
| メモリ制御 | `-Xmx` / `-Xms` で自分で指定 | **メモリ引数がない**。プログラムが自分で OS に要求する |
| 分析ツール | `spark` のフレームグラフ、各種 profiler | **`spark` がない**。成熟したフレームグラフの手順もない |
| ホットリロード | 一部の場面で可能 | `/reload` 非対応。設定を変えたら再起動のみ |

最も重要なのは**シングルコアの周波数が上限を決める**ことです：

- ワールドシミュレーションは 1 つのスレッドで動き、余ったコアは主にネットワーク、セーブデータの書き込みなどの周辺作業を分担します；
- したがって「16 コア 2.0 GHz」のマシンは通常「4 コア 4.5 GHz」のマシンに勝てません；
- マシンを選ぶときはまずシングルコア性能、次にコア数を見ます。
:::warn Java 版の最適化の経験はそのまま持ち込めない
以下は BDS には**存在しません**。Java のチュートリアルどおりにやらないでください：

- `spark` のフレームグラフ（BDS 非対応。詳細は第 8 節）；
- Paper / Spigot の `paper.yml`、`spigot.yml` の設定一式；
- エンティティの有効範囲、スポーン上限、1 tick あたりのエンティティ数といったプラグイン／コアのスイッチ；
- 最適化系プラグイン（公式サーバーにプラグインの仕組みがない）。

持ち込めるのは**概念**だけです：同時に読み込むチャンクを減らす、エンティティを減らす、高頻度レッドストーンを減らす。
:::

## 2. 調整できるもの：`server.properties`
:::warn どんなキーがあり、既定値がいくつかは BDS のバージョンで変わる
BDS のバージョンによって、`server.properties` の**キー名、値の範囲、既定値が異なることがあります**：後から追加されたキーもあれば、あるバージョンで改名されたり複数のキーに分割されたりしたものもあります（移動検証の一群が典型例です）。

だから本記事はこれらのキーが**何をしているか**、動かすと何を支払うかだけを説明します。**自分のサーバーディレクトリの `server.properties` を開いて項目ごとに照合してください**：公式が生成する既定ファイルには、各キーの上にその意味、許容範囲、既定値がコメントで書かれています。それがあなたのバージョンにとって最も正確な説明です。
:::

### 2.1 主要な性能キー

| キー | 役割 | 下げたときの代償 | 推奨する方向 |
| --- | --- | --- | --- |
| `view-distance` | サーバーがプレイヤーへ送るチャンクデータの距離、つまり「どこまで見えるか」（公式の既定 32、範囲の下限 5） | 遠くが霧がかり、地形が「飛び出す」ように見えて観感が悪くなる | **優先して動かす項目**：プレイヤーの端末が一般的、または帯域が厳しいなら下げる |
| `tick-distance` | プレイヤーの周囲どれだけのチャンクが**実際に演算に参加するか**（スポーン、作物、レッドストーン、流体）（公式の既定 4、範囲 4-12） | 遠くの装置、農場、レッドストーン回路が止まりうる | 描画距離より直接 CPU に効く。「遠距離の装置」が不要なら小さめに保つ |
| `max-threads` | サーバーが使おうとするスレッド数の上限（公式の既定 8、0 は無制限。このキーを削除した場合も同じになる版がある） | 低くしすぎるとネットワークやセーブデータなど周辺作業が待ち行列になる | **ワールドシミュレーションをマルチコアに分割するものではない**。上げても速くならないので、まず既定のまま |
| `player-idle-timeout` | プレイヤーが放置して何分でキックされるか | 放置プレイヤーが早く切れ、放置の需要に影響 | ほぼゼロコストの負荷軽減。自分の放置ルールに合わせて決める |
| `compression-threshold` | どれくらいの大きさのパケットから圧縮するか | 低くするとより多くのパケットを圧縮し、**CPU を食う**が帯域は節約 | まずボトルネックを見る：帯域が厳しければ下げ、CPU が厳しければ上げる |
| `compression-algorithm` | ネットワークの圧縮アルゴリズム（`zlib` / `snappy` などの選択肢が一般的） | 圧縮率の低いアルゴリズムに変えると、帯域を CPU と引き換えることになる | 帯域が十分なら速いアルゴリズム、帯域が厳しければ圧縮率の高いもの |

このいくつかについて、明確にしておくことが 3 点あります：

1. `view-distance` と `tick-distance` は**別の話**です：前者は「見えるか」、後者は「演算するか」。描画距離を下げるのは主に見た目に影響し、シミュレーション距離を下げると装置に影響します。
2. `max-threads` は**スレッドの上限**であり、「ワールドシミュレーションを並列化するスイッチ」ではありません。大きくしてもシングルコアのボトルネックは消えません。
3. `player-idle-timeout` は数少ない**ほとんど副作用のない**負荷軽減項目です：放置プレイヤーを蹴れば、読み込むチャンクが減り、エンティティの計算も減ります。

### 2.2 移動検証・チート対策に関わるキー

これらのキーは**性能のスイッチではありません**が、「最適化項目」と勘違いして調整されがちなので、個別に説明します：

| キー | 役割 | 検証を緩めたときの代償 | 推奨する方向 |
| --- | --- | --- | --- |
| `server-authoritative-movement`（一部のバージョン） | サーバー権威の移動。値は数ある検証モードの 1 つで、サーバー権威に寄るほど厳しい | 緩めるほど位置補正は減るが、**チートの余地が広がる** | 公開サーバーでは既定のまま、またはより厳しく |
| `server-authoritative-movement-strict`（一部のバージョン） | プレイヤー位置をより厳しく検証し、補正がより頻繁 | 切ると揺れは減るが、壁抜けやテレポートを見つけにくくなる | 「性能のため」に切らない |
| `player-position-acceptance-threshold` | クライアントとサーバーの位置の**許容度** | 低くすると補正が頻繁になり、高遅延のプレイヤーが「引き戻され」やすい | 遅延が一般的に高く、プレイヤーが頻繁に引き戻されるときだけ小幅に緩め、これが安全との引き換えだと理解する |
:::warn チート対策を性能のスイッチにしない
位置補正には確かにネットワークのコストがありますが、それと引き換えに「プレイヤーが勝手にテレポートできない」を得ています。少しの CPU や帯域を節約するために検証を緩めるのは、典型的な割に合わない取引です。**遅延が一般的に高く、プレイヤーが頻繁に引き戻されるとき**だけ小幅な調整を検討し、何と何を引き換えているかを理解してください。
:::

### 2.3 そのほか存在しうるキー

バージョンによって、性能に少し関わるキーも見られます。たとえば：

- **可視チャンクの生成**をクライアント側に任せるスイッチ：サーバーの仕事は減るが、代償は低スペックのクライアントがより重くなる；
- アドオンパックとスクリプトの**コンテンツログ**と**ウォッチドッグ**に関するキー：スクリプトのエラー、スクリプトが遅すぎる、メモリ超過を見つけるためのもの。

これらは**存在するか、何という名前か、既定値がいくつかもバージョンで変わります**。ここでは具体的なキー名と数値を挙げません。手元のファイルと公式ドキュメントを優先してください。使う前に、自分のバージョンに本当にそのキーがあるか確認し、ネット上の別バージョンの設定をそのまま真似しないでください。

### 2.4 サンプルの断片

```properties
# 描画距離：まず下げて、観感と CPU の変化を観察する
view-distance=12

# シミュレーション距離：遠距離の装置が不要なら小さめに保つ
tick-distance=4

# スレッド上限：既定のまま。速度を上げるスイッチだと思わない
max-threads=8

# 放置キック：自分の放置ルールに合わせて決める
player-idle-timeout=15

# 圧縮：帯域が厳しければ既定、CPU が厳しければしきい値を上げる
compression-threshold=1
compression-algorithm=zlib
```

上の数値は**あくまで例**で、既定値でも推奨値でもありません。手元のファイルのコメントと照合し、自分に合う値に変えてください。
:::note 変更後は必ず再起動
BDS は `/reload` に対応していません。`server.properties` を変えたら、コンソールから正常に `stop` してから起動し直してください。プロセスを直接殺さないこと。
:::

## 3. 本当の大物：ワールドの設計

統合版では、**設定できるものは少ないが、建てられるものは多い**。ほとんどの「サーバーが重い」は最終的にマップに帰着します：

| 負荷の発生源 | 対処の方向 |
| --- | --- |
| 同時に読み込むチャンクが多すぎる | `view-distance` と `tick-distance` を下げ、常時読み込み区域（ticking area）を最小限にする |
| 常時読み込みの装置が多すぎる | 「人がいなくても動く」装置はすべて CPU を消費し続ける。不要なものは解体するか止める |
| レッドストーンクロックが回り続ける | 高頻度クロックは典型的な負荷源。低頻度の方案で済むなら高頻度を使わない |
| エンティティが多すぎる | モブ、ドロップアイテム、トロッコの堆積。農場の規模を抑え、ドロップアイテムをこまめに回収・整理する |
| 農場が大きすぎる | 需要をはるかに超える生産量の農場は純粋な負担。規模を縮めるか必要時のみ動かす |
| ドロップアイテムの堆積 | 回収と破棄の設計が悪いとエンティティが長期間残る |

いくつか補足：

- **常時読み込み区域（ticking area）**は、指定したチャンクをプレイヤーがいなくても演算し続けさせます。便利ですが、区域ごとに CPU を消費し続けるので、**使い終わったら削除**。
- **エンティティの堆積**には典型的な症状があります：CPU の総使用率は高く見えないのに、サーバー全体が重い。このとき対処すべきはエンティティ数と複雑なチャンクで、別のパラメータを探すことではありません。
- **引き算を優先**：使っていない農場を 3 つ解体するほうが、設定ファイルを 10 回調整するより効くのが普通です。
:::tip まず引き算、それからパラメータ
統合版では、「最適化」の第一手段は**建てない、動かさない、読み込まない**ことです。パラメータはごく狭い範囲でしか助けになりません。
:::

エンティティとドロップアイテムの切り分けの考え方は [エンティティとドロップアイテムの堆積によるラグ](/tutorials/faq/entity-lag) を参照。ただし注意：**あの記事の診断ツールは Java 版のもの**（`spark`、TPS と MSPT の指標など）で統合版では使えませんが、**「エンティティを減らす、ドロップアイテムを減らす、常時読み込みの装置を減らす」という設計原則は共通**で、そのまま参考にできます。

### 3.1 常時読み込み区域と「オフライン装置」

常時読み込み区域（ticking area）は統合版では珍しい諸刃の剣です：

- **利点**：プレイヤーがいなくても、指定チャンクのレッドストーン、流体、作物、モブが通常どおり演算され、装置がオフラインで産出できる；
- **代償**：これらのチャンクはプレイヤーの有無に関係なく**ずっと**メインスレッドの時間を占有する；
- **提案**：本当に必要な区域にだけ有効にし、用が済んだら削除。「人がいるときだけ動かす」に変えられる装置は常時読み込みにしない。

切り分けのときはまず 3 つの問いを自分に：この装置はまだ必要か？人がいないときにも動かさねばならないか？その産出は本当に使えるか？1 つでも「いいえ」があれば、止めるべきです。

## 4. チャンク、ワールドの大きさ、プリ生成

描画距離とワールドの規模は別の勘定です：

- **描画距離の勘定**：`view-distance` が大きいほど、各プレイヤーが入場・移動・区域をまたぐときに送るチャンクデータが増え、CPU と帯域が一緒に上がります。最大の CPU／帯域のレバーであり、同時にプレイヤーが最も直接感じる観感の項目でもあります。
- **ワールドの大きさの勘定**：プレイヤーが探索した区域はすべてセーブデータに書き込まれます。ワールドが大きく古いほど `worlds/` ディレクトリが大きくなり、**起動、保存、バックアップがすべて遅く**なり、ディスク I/O の圧力も大きくなります。

できること：

1. **活動範囲を制限する**：「ワールドボーダー」の発想でプレイヤーを遊ぶ必要のある区域に集め、ワールドを無限に拡張させない。あなたのバージョンやコアが既成のボーダーコマンドを提供するか、どう使うかは公式ドキュメントを優先。
2. **目的のない遠出を促さない**：走り回るだけで新しいチャンクが生成され続け、新しいチャンクの生成はラグのよくある発生源です。
3. **スポーン地点をきれいに保つ**：スポーン地点の周辺は通常最も頻繁に読み込まれる区域で、建築、エンティティ、レッドストーンは少ないほどよい。
4. **古い区域を定期的に整理する**：使わなくなったワールドや区域は速やかに整理し、操作の前に**バックアップ**。

**プリ生成**については正直に言います：**公式 BDS はプリ生成ツールを提供しておらず**、選べる手段は Java 版よりずっと少ないです。

| 手段 | 公式 BDS の対応 | 説明 |
| --- | --- | --- |
| 内蔵のプリ生成コマンド | 非対応 | 公式サーバーにそうしたコマンドはない |
| 管理者が事前に走り回る | 対応（普通のゲーム行為） | 最も確実で依存もゼロ。欠点は時間がかかること |
| 常時読み込み区域 | 対応 | 解決するのは「人がいなくても演算する」ことで**プリ生成ではなく**、しかも性能を消費し続ける |
| Java 版のツール（Chunky など） | BDS 非対応 | そうしたツールは Java 版サーバーと MOD プラットフォーム向け |
| サードパーティのプリ生成ツール | 公式の能力範囲外 | 使う前に自分の BDS バージョンに対応しているか確認し、**先にワールドをバックアップ** |
:::warn 「統合版のワンクリックプリ生成」を信じない
ネットで見かける統合版の「プリ生成プラグインやツール」は、ほとんどがサードパーティコアかコミュニティのツールで、**公式 BDS の能力範囲ではありません**。使うならそのツール自身の公式ドキュメントを優先し、本記事や他のバージョンの説明から推測しないでください。
:::

統合版のプリ生成手段は限られており、頼れるのは主に**事前の走り回り**と**ワールド規模の制御**です。

## 5. メモリの挙動

統合版のメモリの挙動は Java 版とまったく違います：

- **メモリ引数がない**。BDS に `-Xmx` のようなスイッチはなく、初期と最大のメモリはプログラムが自分で OS に要求し、起動引数で指定できません。
- **使用量は時間とともにゆっくり増える**。長時間稼働後は起動直後より明らかに多くなります。広く観察されている現象です。
- **無理にメモリを解放しない**。「メモリクリーン」「強制解放」系のツールで使用量を抑えると、**プレイヤーがリソースパックやアドオンパックをダウンロードするとき進行バーが止まり**、サーバーが不安定になることもあります。**再起動が解法**で、これは [BDS サーバー](/tutorials/bedrock/bds) の説明と同じです。

正しいやり方は**定時再起動を組む**ことです：

| やり方 | 説明 |
| --- | --- |
| 定時再起動 | 閑散時間に 1 回再起動し、長期間溜まったメモリを OS に返す |
| 再起動の周期 | **公式の推奨値はない**。判断の問題：プレイヤー数、ワールドの大きさ、アドオンパックの数、メモリ増加の曲線を見る。毎日 1 回も数日ごと 1 回も使われている |
| 穏やかな停止 | コンソールの `stop` で正常に落としてから起動し、セーブデータや統計ファイルの破損を避ける |
| 事前の告知 | **再起動の前にゲーム内とグループで告知**し、緩衝時間を設けて、走り回り中や対戦中に突然切られないようにする |
:::tip 再起動の間隔をどう決めるか
他人の「毎日 3 回再起動」をそのまま真似しないでください。まず数日記録します：起動後どれだけでメモリがマシンの許容を超えるか、プレイヤーがいつ最も多いか。**プレイヤーが多くアドオンパックが多いなら短く、小規模で少ないなら長く**。
:::

## 6. ハードウェアとホスティングの選択

統合版のハードウェアの第一原則も**シングルコア性能優先**です：

| 優先度 | 項目 | 理由 |
| --- | --- | --- |
| 1 | シングルコアの周波数と性能 | ワールドシミュレーションがシングルスレッド。弱いシングルコアが重さを直接決める |
| 2 | SSD か NVMe | チャンクの読み書き、セーブデータの保存、バックアップはすべてディスク I/O。HDD やネットワークストレージは明らかに遅くなる |
| 3 | メモリ容量 | 余裕を残す。プレイヤー、ワールド、アドオンパックが多いほど必要 |
| 4 | コア数 | 役には立つが、上の 3 つの後 |

「安い VPS が不可解に重い」理由：

- 安いプランは**低周波・多コア・オーバーセール共有**の CPU がよくあります。BDS はシングルコアを食い、共有 CPU は隣人に奪われるため、周期的なラグと遅延の揺れが出ます；
- 「バースト性能」型のインスタンスは普段は暇に見え、CPU クレジットが尽きると全体が遅くなります；
- HDD やネットワークストレージはチャンクの読み書きを遅くし、プレイヤーが走り回るときに最も表れます；
- メモリが不足すると OS がページングを始め、「サーバー全体がカクカク」という症状になります。
:::warn コンテナと仮想化は追加で CPU を奪う
BDS をコンテナや仮想マシンで動かすなら、**CPU の上限（limit / quota）が BDS を飢えさせる**ことがあります：シングルコアが使い切られたときに制限され、周期的な「一瞬のカクつき」になります。CPU の割り当てを十分にし、他の高負荷サービスと同じマシンに詰め込まないでください。Docker でのデプロイの詳細は [Docker で統合版サーバーをデプロイする](/tutorials/bedrock/docker) を参照。
:::

### 6.1 ホスティング選択の早見表

| あなたの状況 | 提案 |
| --- | --- |
| プレイヤーが少なく予算も限られる | シングルコアの強いマシン 1 台のほうが、多コアのオーバーセール VPS よりたいてい安定する |
| 長期稼働と固定のプレイヤーがいる | CPU の周波数を明示し、オーバーセールでないプランを選び、まず小規模で試してから拡張する |
| コンテナでデプロイする | CPU の割り当てを十分にし、高負荷サービスとの同居を避け、ポートとデータボリュームに注意。[Docker で統合版サーバーをデプロイする](/tutorials/bedrock/docker) を参照 |
| プラグインのエコシステムが欲しい | それは BDS の路線ではありません。まず第 7 節を |

## 7. サードパーティコアの性能差

プラグインとマルチコアが欲しいなら、BDS の道ではありません：

| コア | 言語 | 性能の特徴 |
| --- | --- | --- |
| Nukkit 系（PowerNukkitX を含む） | Java | マルチコアと最適化が売り。プラグインシステムと多数の調整項目がある |
| PocketMine-MP | PHP | プラグインのエコシステムが最大だが、高負荷でボトルネックが明白。インタプリタ言語自体のコストもある |

性能モデル、設定項目、使えるツールはどれも BDS と異なり、**最適化の経験を互いに流用できません**。たとえば `spark` は Nukkit に対応しますが **BDS には非対応**。PMMP や Nukkit のチューニング記事を BDS にそのまま持ち込んでも、たいてい無駄骨です。
:::warn まず自分がどちらの道を望むか確認する
BDS を選ぶのは「公式、安定、調整項目が少ない」こと；サードパーティコアを選ぶのは「プラグインが多く調整項目も多いが、公式実装ではない」こと。取捨選択と導入は [サードパーティコア（Nukkit / PNX / PMMP）](/tutorials/bedrock/third-party) と [統合版サードパーティコアの導入](/tutorials/bedrock/third-party-setup) を参照。
:::

## 8. どう測るか

まず明確に：**統合版に `spark` はありません**。`spark` が対応するのは Java 版の一連のプラットフォームと一部のコミュニティプラットフォームで、**Bedrock Dedicated Server は含まれません**。だから BDS でフレームグラフを期待せず、Java 版の「TPS と MSPT を見る」手順もそのまま持ち込まないでください。

使える手段：

| 手段 | 使い方 |
| --- | --- |
| ホスト側の監視 | CPU（とくに**シングルコアの使用率**）、メモリ、ディスク I/O、ネットワーク帯域を見る。やり方は [監視とアラート](/tutorials/ops/monitoring) |
| BDS のコンソール出力 | 起動と終了の情報、エラー、アドオンパックやスクリプト関連の警告を見る |
| プレイヤーのフィードバック | 「いつ重いか、何人オンラインか、どの区域で重いか」はどの指標より直接的であることが多い |
| 変更前後の比較 | 1 回に 1 項目だけ変え、変更前後の CPU 使用率とプレイヤーの体感を記録する |
:::note 1 回に 1 項目だけ変える
フレームグラフがないので、唯一信頼できるのは**変数の制御**です：1 項目変え、比較可能な時間だけ観察し、記録してから次を変える。5 項目同時に変えると、どれが効いたのか、逆効果だったのか永遠に分かりません。
:::

測定の規律は次に従うことを勧めます：

1. **1 回に 1 つの変数だけ**変え、他は変えない；
2. **比較可能な時間帯に測る**：同じ時間帯、近いオンライン人数、近い遊び方（どちらも走り回っている、あるいはどちらも放置している）；
3. **ログに記録する**：何を変えたか、いつ変えたか、変更前後の指標とプレイヤーの体感；
4. **十分に長く観察する**：チャンク生成やメモリ増加のような現象は時間がかかるので、変更直後に結論を出すと誤判定しやすい。

ホスト側の記録の簡単な例（Linux、あくまで例）：

```bash
# 5 秒ごとに全体と各コアの負荷をサンプリング。「総使用率は低いのに単核が使い切られている」を見つけやすい
top -b -d 5 -n 60 > cpu-sample.log
```

Windows ではタスクマネージャーやパフォーマンスモニターで同じものを見られます。**重点は総使用率ではなく単核の曲線**です。

## 9. チューニングの順序

この順でやると費用対効果が最も高く、逆順だと無駄にお金を使いがちです：

1. **ワールドの設計**：まず引き算。読み込みを減らし、常時読み込みの装置を減らし、不要な農場を止め、レッドストーンクロックを抑え、エンティティとドロップアイテムを制御する。効果が最大で費用ゼロ。
2. **描画距離とシミュレーション距離**：`view-distance`、`tick-distance`、`player-idle-timeout`、圧縮関連のキーを調整。ほぼ無料で即効性あり。
3. **ハードウェア**：シングルコア性能を優先し、次にメモリ、SSD、コア数。費用はかかるが効く。
4. **再起動の計画**：自分に合う再起動周期を決めて事前に告知。対症療法だが、長期的なメモリの累積は解決できる。
5. **コアの変更**：上の 4 つをすべて終え、本当にプラグインやマルチコアが必要なときだけ Nukkit 系や PMMP を検討。

### 9.1 仕上げのチェックリスト

| # | チェック項目 | 完了の基準 |
| --- | --- | --- |
| 1 | バージョンにどんなキーがあるか確認 | 手元の `server.properties` を開き、キー名と既定値を項目ごとに照合した |
| 2 | ワールドの設計 | 不要な農場と装置を止め、常時読み込み区域を整理し、高頻度レッドストーンを抑えた |
| 3 | 描画距離とシミュレーション距離 | `view-distance` と `tick-distance` をプレイヤーの端末と帯域に合わせて調整し、装置を壊していない |
| 4 | 放置と圧縮 | `player-idle-timeout` を設定し、圧縮関連のキーをボトルネックの方向に合わせて調整した |
| 5 | ハードウェア | シングルコア性能とディスク I/O がボトルネックなら優先して解決。コンテナには十分な CPU 割り当て |
| 6 | 再起動の計画 | 周期があり、告知があり、`stop` で穏やかに停止している |
| 7 | 測定の記録 | 変更のたびに前後の記録があり、1 回に 1 項目だけ変えている |
| 8 | チート対策 | 性能のために移動検証を緩めておらず、またはリスクを明確に受け入れている |

統合版の最適化は結局 3 行に尽きます：**シングルコアの周波数が上限を決め、ワールドの設計が下限を決め、定時再起動が長期的な安定を決める。**
