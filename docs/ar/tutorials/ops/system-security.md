[أساسيات أمان الشبكة](/tutorials/ops/network-security) تعالج «هل يستطيع من في الخارج الدخول». وهذه المقالة تعالج الاتجاه الآخر: **بافتراض أن أحدهم دخل فعلًا (أو أنك أنت أخطأت في التشغيل)، فكم يتحمّل هذا الجهاز.**

هدف تقوية النظام ليس «الأمان المطلق» — فهو غير موجود — بل **تضييق الصلاحيات، وتقليل المداخل، وترك آثار**، حتى لا يتحوّل خطأ واحد إلى سقوط الجهاز كله.

## أولًا: الحسابات والصلاحيات

### 1.1 لماذا لا يجوز إطلاقًا تشغيل الخادم بـ root

| خطر التشغيل بـ root | الأثر المحدّد |
| --- | --- |
| **الثغرة تعني سقوط الجهاز مباشرةً** | عند استغلال ثغرة في الخادم أو الملحق أو المود، يرث المهاجم صلاحيات root، فيستطيع تعديل ملفات النظام وتثبيت أبواب خلفية وحذف البيانات كلها |
| **الملحق كود طرف ثالث** | فملف jar الذي نزّلته من منتدى يعمل بالصلاحيات نفسها التي يعمل بها الخادم. **والتشغيل بـ root يعني تسليم الجهاز كله لمؤلّف لا تعرفه.** |
| **الخطأ لا يمكن تداركه** | أمر حذف بمسار خاطئ، بتشغيل مستخدم عادي يخرّب دليل الخادم في أسوأ حال؛ وبتشغيل root قد يخرّب النظام كله |
| **اختلال مالك الملفات** | فـ`world/` والسجلات وملفات الإعداد التي ينشئها root لا يستطيع المستخدم العادي تعديلها، فتحتاج كل صيانة إلى `sudo`، وينتهي بك الأمر إلى عادة «كل شيء بـ root» |

:::warn تشغيل اللوحة بـ root لا يعني أن الخادم يجب أن يعمل بـ root
كثير من اللوحات تعمل بصلاحيات عالية لتسهيل الإدارة، وتشغّل الخادم عنك. **وهذا مسألة حدود ثقة في اللوحة، ولا يصلح حجّة لـ«الخادم يجب أن يعمل بـ root».** فإن كانت اللوحة تدعم تحديد مستخدم التشغيل فحدّد مستخدمًا مخصّصًا.
:::

### 1.2 إنشاء مستخدم نظام مخصّص

```bash
sudo useradd -r -m -d /opt/mcserver mcserver
```

| الوسيط | الدور |
| --- | --- |
| `-r` | إنشاء **مستخدم نظام** (يُخصَّص له UID من نطاق النظام المحجوز، ولا كلمة مرور له عادةً ولا ينتهي) |
| `-m` | إنشاء دليل المنزل أيضًا (`-r` **لا** ينشئه افتراضيًا، فيجب تحديده صراحةً) |
| `-d /opt/mcserver` | تحديد دليل المنزل `/opt/mcserver` |
| `mcserver` | اسم المستخدم |

**وأنشئ الدليل وسلّم ملكيته إليه**:

```bash
sudo mkdir -p /opt/mcserver/survival /opt/mcserver/backups
sudo chown -R mcserver:mcserver /opt/mcserver
sudo chmod 750 /opt/mcserver
```

`chown -R` يحوّل مالك الدليل **ومحتواه الموجود** ومجموعته إلى `mcserver` (ولا تستخدم `-R` إلا عند الحاجة إلى التكرار)؛ و`chmod 750` يتيح للمالك القراءة والكتابة والتنفيذ، وللمجموعة القراءة والتنفيذ، ويسلب الآخرين كل صلاحية. وتأكّد من المستخدم ومالك الدليل بـ`id mcserver` و`ls -ld /opt/mcserver`.

:::tip امنع المستخدم المخصّص من تسجيل الدخول
إن كان هذا الحساب لتشغيل الخدمة فقط ولا يحتاج دخولًا تفاعليًا، فيمكن منع shell الخاص به:

```bash
sudo usermod -s /usr/sbin/nologin mcserver
```

**لاحظ**: `nologin` يمنع التبديل بـ`sudo -iu mcserver` وأمثاله. فإن كنت تحتاج الدخول للصيانة، فاستخدم `/bin/bash` واضبط الوصول بالمفاتيح والصلاحيات، أو أعِد التغيير مؤقتًا عند الحاجة. **ومسار `nologin` على النظام قد يكون `/usr/sbin/nologin` أو `/sbin/nologin`، فتأكّد قبل التغيير.**
:::

### 1.3 استخدام sudo بوعي

قيمة `sudo` في أنه **يترك أثرًا عند كل رفع صلاحية** (يُكتب في سجل النظام)، ويمكن ضبطه بدقة على «مستخدم معيّن لا يشغّل إلا أوامر محدّدة».

- **لا تستخدم `sudo su -` وتبقى داخله**. فذلك يضيّع طبقة تسجيل «أي أمر شغّله من ومتى».
- **ارفع الصلاحية عند الحاجة**: استخدم `sudo الأمر` للأمر الواحد، ولا تُبقِ الجلسة كلها تحت root.
- **حرّر sudoers بـ`visudo`**. فهو يفحص الصيغة؛ والتعديل المباشر على `/etc/sudoers` بخطأ حرف واحد قد يمنع الجميع من رفع الصلاحية.

```bash
sudo visudo
```

**والتصرف الموصى به**: لا تعدّل ملف `/etc/sudoers` الرئيسي مباشرةً، بل ضع مقطعًا مستقلًا في `/etc/sudoers.d/`، وحرّره بـ`sudo visudo -f /etc/sudoers.d/mcadmin` للحصول على فحص الصيغة. ويمكن في المقطع تحديد الأوامر بدقة، مثلًا السماح لمشرف معيّن بإعادة تشغيل الخادم فقط:

```
mcadmin ALL=(root) /usr/bin/systemctl restart minecraft
mcadmin ALL=(root) /usr/bin/systemctl status minecraft
```

**ودقّق من يملك صلاحية sudo**:

```bash
getent group sudo    # مجموعة sudo في Debian / Ubuntu
getent group wheel   # مجموعة wheel في عائلة RHEL
sudo grep -rHv '^#\|^$' /etc/sudoers /etc/sudoers.d/
```

:::warn راجع دوريًا، ولا تنسَ بعد الإعداد
**المشرف الذي غادر، والصديق الذي ساعد مؤقتًا، والحساب الذي أُضيف في اختبار مبكّر** — كلها تبقى في مجموعة sudo مدة طويلة. ويُنصح بالمراجعة كل فترة، وإزالة من لم يبقَ بحاجة إليه (`sudo deluser اسم-المستخدم sudo` أو `sudo gpasswd -d اسم-المستخدم wheel`).
:::

### 1.4 تعطيل الحسابات غير اللازمة

- **افحص كل الحسابات القابلة للدخول** (فالحساب الذي يحصل على shell هو المدخل الحقيقي):

```bash
awk -F: '$7 !~ /(nologin|false)$/ {print $1, $3, $7}' /etc/passwd
```

- **أقفل الحسابات التي لم تبقَ لازمة**:

```bash
sudo usermod -L اسم-المستخدم          # أقفل كلمة المرور
sudo usermod -s /usr/sbin/nologin اسم-المستخدم   # وامنع الدخول في الوقت نفسه
```

- **ابحث تحديدًا** عن الحسابات التي UID لها `0` في `/etc/passwd`: **يجب ألا يكون فيها إلا `root` وحده**. وما زاد فهو باب خلفي:

```bash
awk -F: '$3 == 0 {print $1}' /etc/passwd
```

## ثانيًا: أذونات الملفات — تطبيق أقل صلاحية على الأدلة

### 2.1 افهم بتات الصلاحية أولًا

العمود الأول في مخرجات `ls -l`، مثل `-rwxr-x---`، ينقسم إلى ثلاث مجموعات: **المالك / المجموعة / الآخرون**، وكل مجموعة ثلاثة أرقام (قراءة `r`=4، وكتابة `w`=2، وتنفيذ `x`=1).

| الصلاحية | الرقم | الاستخدام |
| --- | --- | --- |
| `rwx------` | `700` | دليل خاص لا يستخدمه إلا المالك |
| `rwxr-x---` | `750` | جذر الخادم: المالك يكتب، والمجموعة تدخل، والآخرون لا يرونه إطلاقًا |
| `rw-r-----` | `640` | ملف إعداد: المالك يقرأ ويكتب، والمجموعة تقرأ فقط |
| `rw-------` | `600` | **الملفات التي تحوي كلمات مرور**، لا يراها إلا المالك |
| `rwxrwxrwx` | `777` | **لا تستخدمه في أي حال** |

### 2.2 لماذا `777` خطر

`chmod -R 777` هو «الحل السحري» الأكثر انتشارًا على الإنترنت — عند رؤية `Permission denied` استخدم 777. ومعناه الفعلي: **أي مستخدم على النظام، وأي عملية خدمة مخترقة، يستطيع قراءة كل شيء في هذا الدليل وتعديله وحذفه.**

| الأثر | ملاحظة |
| --- | --- |
| **أي حساب محلي يستطيع تعديل الخادم** | خدمة مخترقة بصلاحيات منخفضة (مثل تطبيق ويب) تستطيع وضع ملف jar باب خلفي في `plugins/`، ليسري عند إعادة التشغيل التالية |
| **ملفات كلمات المرور مرئية للجميع** | فكلمة مرور RCON في `server.properties` وكلمة مرور قاعدة البيانات في `.env` مكشوفتان تمامًا |
| **الأرشيف قابل للتخريب من أي أحد** | أي عملية تستطيع حذف `world/` |
| **إخفاء المشكلة الحقيقية** | فجذر خطأ الصلاحيات هو «المالك خاطئ» عادةً، و`777` يغطّي العَرَض وتبقى المشكلة |

:::warn الإصلاح الصحيح ليس توسيع الصلاحيات، بل تصحيح المالك
عند رؤية `Permission denied`، انظر أولًا **من يعمل، وأي ملف يريد تعديله**:

```bash
ls -l /opt/mcserver/survival/server.properties
```

فإن كان المالك `root` والخدمة تعمل بـ`mcserver`، فالتصرف الصحيح:

```bash
sudo chown mcserver:mcserver /opt/mcserver/survival/server.properties
```

**لا** `chmod 777`. **وتغيير الصلاحيات تكرارًا (`chmod -R 777`) عملية عالية الخطورة على الخادم، فلا تنفّذها.**
:::

### 2.3 الصلاحيات الموصى بها لدليل الخادم

```bash
# دليل الخادم كله مملوك للمستخدم المخصّص
sudo chown -R mcserver:mcserver /opt/mcserver

# المالك بكل الصلاحيات؛ والمجموعة قراءة ودخول؛ والآخرون لا شيء
sudo chmod -R u=rwX,g=rX,o= /opt/mcserver

# الدليل نفسه لا يُمنح الآخرون فيه أي صلاحية
sudo chmod 750 /opt/mcserver
```

`u=rwX,g=rX,o=` هو **الوضع الرمزي**: و`X` (بحرف كبير) تعني «أضف صلاحية التنفيذ للأدلة، أو للملفات التي لها بت تنفيذ أصلًا»، وهو أقرب إلى مبدأ «الملفات لا يجب أن تكون قابلة للتنفيذ» من `-R 755` الأعمى. **لا تستخدم `chmod -R 777`، ولا تستخدم `o+w` (كتابة الآخرين) على دليل الخادم.**

### 2.4 العناصر التي تحتاج حماية خاصة

| العنصر | لماذا | التوصية |
| --- | --- | --- |
| `world/`، و`world_nether/`، و`world_the_end/` | الأرشيف هو كل ما استثمره اللاعبون، وتخريبه لا يُستدرك | المالك `mcserver`، والآخرون بلا صلاحية؛ و**نسخ احتياطي دوري بلا اتصال** (انظر القسم الخامس) |
| `server.properties` | يحوي كلمة مرور RCON والمنافذ و`online-mode` وغيرها من المفاتيح الحسّاسة | `640`، والمالك `mcserver` |
| `.env` والسكربتات التي تحوي كلمات مرور | كلمة مرور قاعدة البيانات وAPI Key | **`600`**، لا يقرأها ويكتبها إلا المالك |
| `ops.json`، و`whitelist.json` | تحدّد من يحصل على صلاحيات المشرف | `640`، وراجع محتواها بعد كل تعديل |
| ملفات المفاتيح الخاصة (`id_ed25519` وغيرها) | تسريبها يعني تسليم حق الدخول | **`600`**، ودليل `.ssh` بـ`700` |
| ملفات النسخ الاحتياطي | تحوي كلمات المرور والأرشيف كاملًا غالبًا | **لا تضعها في دليل متاح للويب**؛ ونسخة خارج الموقع |

```bash
# ملفات البيانات السرية للمالك وحده
chmod 600 /opt/mcserver/survival/.env
ls -l /opt/mcserver/survival/.env
# المتوقّع: -rw------- 1 mcserver mcserver ... .env
```

:::note النسخ يغيّر الصلاحيات، فأعد المالك عند الاستعادة
إذا نسخت بطريقة **تحفظ السمات** مثل `cp -a` أو `tar` أو `rsync -a`، يكون المالك والصلاحيات صحيحة بعد الاستعادة. أما إن نسخت المحتوى فقط، فقد يصبح المالك root بعد الاستعادة ولا يستطيع الخادم كتابة الأرشيف — فتذكّر فحص ذلك بـ`ls -ld` بعد الاستعادة.
:::

## ثالثًا: تحديث النظام

**أغلب الاختراقات تستغل ثغرات «أُصلحت لكنك لم تُطبّق الترقيع».** فإبقاء النظام محدّثًا أعلى بند قيمةً بين كل إجراءات التقوية.

### 3.1 مفهوم أتمتة التحديثات الأمنية

فكرة التحديث التلقائي: **تُثبَّت الترقيعات الأمنية تلقائيًا، وتقرّر أنت بقية التحديثات**.

| التوزيعة | الأداة | ملف الإعداد |
| --- | --- | --- |
| Ubuntu / Debian | `unattended-upgrades` | `/etc/apt/apt.conf.d/20auto-upgrades`، و`/etc/apt/apt.conf.d/50unattended-upgrades` |
| RHEL / Rocky / AlmaLinux / Fedora | `dnf-automatic` | `/etc/dnf/automatic.conf` |

**Ubuntu / Debian**:

```bash
sudo apt update
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

والمحتوى الشائع لـ`20auto-upgrades`:

```ini
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
```

- `Update-Package-Lists "1"`: تحديث فهرس الحزم مرة يوميًا.
- `Unattended-Upgrade "1"`: تثبيت الترقيات المؤهّلة تلقائيًا كل يوم (**ولا تشمل إلا التحديثات الأمنية افتراضيًا**، والنطاق المحدّد يحدّده `Unattended-Upgrade::Allowed-Origins` في `50unattended-upgrades`).

**عائلة RHEL**:

```bash
sudo dnf install -y dnf-automatic
sudo systemctl enable --now dnf-automatic.timer
```

والإعدادات الشائعة في `/etc/dnf/automatic.conf` المتعلقة بـ«تثبيت التحديثات الأمنية فقط وتطبيقها تلقائيًا»:

```ini
[commands]
upgrade_type = security
apply_updates = yes
```

**والتحقق من أنه يعمل**: `systemctl status unattended-upgrades` (في Debian / Ubuntu) أو `systemctl status dnf-automatic.timer` (في عائلة RHEL).

:::warn بنود الإعداد وقيمها الافتراضية تتغيّر بحسب النسخة
ما سبق صيغة شائعة فقط. **وأسماء ملفات الإعداد وأسماء الخيارات ونطاقها الافتراضي قد تختلف بين التوزيعات والنسخ** (مثلًا «هل تشمل التحديثات غير الأمنية» و«هل تُنظَّف الأنوية القديمة تلقائيًا»). راجع قبل التعديل توثيق النسخة التي تستخدمها، وتأكّد بـ`systemctl status` أن الخدمة تعمل فعلًا. **والإعداد لا يعني السريان.**
:::

### 3.2 لا تُعِد التشغيل تلقائيًا على العمياء

**تثبيت** الترقيعات شيء و**إعادة التشغيل** شيء آخر. فتحديثات مكوّنات مثل النواة وglibc وsystemd **لا تسري فعليًا إلا بعد إعادة التشغيل**. **ولا تفعّل إعادة تشغيل تلقائية غير مشروطة**، والسبب:

- **خادم اللعبة فيه لاعبون**. فإعادة التشغيل في منتصف الليل تُسقط من يلعب، وقد تُفقد تقدّمًا، وقد تُطلق مشكلة في الأرشيف.
- **فشل إعادة التشغيل يعني توقفًا طويلًا**. فإن لم تتوافق النواة الجديدة مع تعريفاتك أو بيئتك لم يقم الجهاز، وقد تكتشف ذلك في اليوم التالي.
- **الخدمة لا تقوم بنفسها بالضرورة بعد إعادة التشغيل**. وهذا يتوقّف على هل الخدمة `enable` (انظر القسم الرابع).

**والتصرف الموصى به**:

| التصرف | ملاحظة |
| --- | --- |
| **نافذة صيانة** | حدّد فترة يكون فيها اللاعبون أقلّ (مثلًا فجر الثلاثاء)، وأعلن مسبقًا، وأعد التشغيل يدويًا |
| **أشعر ثم أعد التشغيل** | استخدم أمر بثّ عدًّا تنازليًا في الخادم، ليخرج اللاعبون بأمان |
| **أبقِ النواة القديمة** | لا تحذف الأنوية القديمة تلقائيًا، للتمكّن من التراجع عند مشكلة |
| **تحقّق فورًا بعد إعادة التشغيل** | هل الخدمة تعمل، وهل المنفذ يُوصل إليه، وهل في السجل شذوذ |

واستخدام `[ -f /var/run/reboot-required ] && cat /var/run/reboot-required` (في Debian / Ubuntu) أو `sudo dnf needs-restarting -r` (في عائلة RHEL) للتحقق من انتظار إعادة التشغيل.

:::tip أعد التشغيل مرة أولًا وتأكّد أنه يقوم بنفسه
أعد تشغيل الجهاز يدويًا في **وقت لا يوجد فيه لاعبون**، للتحقق من أن «التشغيل التلقائي عند الإقلاع» يعمل فعلًا. **والتشغيل التلقائي غير المُتحقَّق منه كعدم وجوده.**
:::

## رابعًا: تقوية الخدمة (systemd)

### 4.1 وحدة أساسية

`/etc/systemd/system/minecraft.service`:

```ini
[Unit]
Description=Minecraft Server
After=network.target

[Service]
Type=simple
User=mcserver
Group=mcserver
WorkingDirectory=/opt/mcserver/survival
ExecStart=/usr/lib/jvm/java-21-openjdk-amd64/bin/java -Xms2G -Xmx4G -jar server.jar nogui
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

| التوجيه | الدور |
| --- | --- |
| `User=` / `Group=` | **التشغيل بمستخدم مخصّص**. وبدون كتابتهما يعمل الخادم بـ root افتراضيًا — وهذا أكثر ثغرة تقوية شيوعًا. |
| `WorkingDirectory=` | دليل عمل الخادم. والمسارات النسبية (`world/` و`plugins/`) تُحسب منه. |
| `ExecStart=` | أمر التشغيل. **ويجب كتابة مسار مطلق**، فـ systemd لا يحلّل `PATH`. |
| `Restart=on-failure` | إعادة التشغيل عند الخروج الشاذ. و`stop` الطبيعي لا يطلقه. |
| `RestartSec=10` | الانتظار 10 ثوانٍ قبل إعادة التشغيل، تجنّبًا لدوران سريع عند الانهيار. |

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
```

:::note وحدات الدروس الموجودة تستخدم screen
مثال [تحضير البيئة](/tutorials/java/environment) يستعين بـ`screen` للاحتفاظ بوحدة التحكّم، تسهيلًا لإدخال الأوامر أثناء اللعب. **والطريقتان صالحتان**؛ ومثال هذه المقالة يستخدم `Type=simple` لتشغيل عملية Java مباشرةً، وهو أنسب لإضافة خيارات التقوية أدناه. **ولاحظ: عند الجمع بين `screen` وخيار تقوية مثل `ProtectSystem=strict`، تأكّد من قابلية كتابة دليل socket الذي يحتاجه `screen`.**
:::

### 4.2 تحديد الموارد

تحديد الموارد يمنع «تسريب الذاكرة من إسقاط الجهاز»، ويمنع أيضًا «استنزاف الجهاز عند التعرّض لهجوم».

```ini
[Service]
LimitNOFILE=65535
MemoryMax=6G
```

| التوجيه | الدور | ملاحظة |
| --- | --- | --- |
| `LimitNOFILE` | الحدّ الأعلى لعدد واصفات الملفات المفتوحة | عند كثرة اللاعبين وتحميل المناطق قد لا تكفي القيمة الافتراضية، ويظهر ذلك كـ«الاتصال مرفوض» أو أخطاء IO غامضة |
| `MemoryMax` | **الحدّ الأعلى الصارم للذاكرة** لهذه الخدمة | تجاوزه يعني قتلًا بـ OOM من النواة. **ويجب أن يكون أكبر بوضوح من `-Xmx`**، لأن JVM نفسها وmetaspace ومكدّسات الخيوط والذاكرة المباشرة كلها خارجها |

:::warn ضبط `MemoryMax` أصغر من `-Xmx` خطأ نموذجي
`-Xmx4G` يحدّ كومة Java فقط. فخادم Minecraft بحدّ كومة 4G قد يبلغ **استهلاكه المقيم الفعلي 5G فأكثر**. فإن ضبطت `MemoryMax` على `4G` فسيُقتل الخدمة ويُعاد تشغيلها مرارًا، ولا ترى في السجل إلا «العملية اختفت فجأة».

**والتوصية**: اترك في `MemoryMax` هامشًا لا يقلّ عن 30% (مثلًا `-Xmx4G` مع `MemoryMax=6G`)، وراقب الاستهلاك الفعلي في `systemctl status` ثم اضبط.
:::

### 4.3 تقييد الصلاحيات وحماية نظام الملفات

هذه التوجيهات تجعل الخدمة **تلمس ما يجب أن تلمسه فقط**. وحتى لو اخترق الخادم أو أحد الملحقات، يبقى ما يستطيع المهاجم إحداثه محصورًا.

```ini
[Service]
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/opt/mcserver/survival
```

| التوجيه | الدور |
| --- | --- |
| `NoNewPrivileges=yes` | منع العملية من رفع صلاحيتها عبر برامج setuid / setgid. **بند تقوية بلا أعراض جانبية تقريبًا، ويُنصح بإضافته دائمًا.** |
| `PrivateTmp=yes` | منح الخدمة **`/tmp` و`/var/tmp` خاصّين**، فلا ترى ملفات العمليات الأخرى المؤقتة ولا تؤثر فيها |
| `ProtectSystem=strict` | تركيب **نظام الملفات كله للقراءة فقط** (ما عدا `/dev` و`/proc` و`/sys`). ولا تكتب الخدمة إلا في المسارات المذكورة في `ReadWritePaths` |
| `ProtectHome=yes` | جعل `/home` و`/root` و`/run/user` **غير مرئية** للخدمة (كأنها أدلة فارغة) |
| `ReadWritePaths=` | يعمل مع `ProtectSystem=strict`، و**يسرد صراحةً المسارات المسموح بالكتابة فيها**. **وبدونه لا يستطيع الخادم كتابة الأرشيف حتى.** |

:::warn إن لم تقم الخدمة بعد `ProtectSystem=strict` فانظر هنا أولًا
الأسباب الشائعة:

1. **نسيان `ReadWritePaths`**، أو خطأ في المسار (يجب أن يكون مطلقًا، ومطابقًا لـ`WorkingDirectory`).
2. **سكربت النسخ أو الملحق يحتاج الكتابة في مكان آخر** (مثل `/var/log` أو `/srv`)، فيلزم إضافته إلى `ReadWritePaths`.
3. **Java تحتاج دليلًا مؤقتًا للكتابة**: و`PrivateTmp=yes` يكفي عادةً، لكن إن كان الخادم يحدّد مسارًا مؤقتًا ثابتًا صراحةً فأضفه أيضًا.

**وطريقة التشخيص**: `sudo systemctl status minecraft` و`sudo journalctl -u minecraft -n 100` يعطيان مسار «الصلاحية مرفوضة» مباشرةً.
:::

:::note توافر خيارات التقوية يتوقّف على نسخة systemd
هذه التوجيهات متاحة على نسخ systemd الحديثة، لكن **الدعم المحدّد يتغيّر بحسب النسخة**. واستخدام `systemd-analyze security minecraft.service` يعرض إعدادات العزل السارية فعلًا للخدمة: فهو يعطي تقييم «درجة التعرّض» وشرحًا بندًا بندًا، وهو أدقّ من إضافة التوجيهات بالحدس. ومعايير التقييم وأسماء البنود قد تختلف بين النسخ، **فاعتمد المخرجات الفعلية على نظامك**.
:::

## خامسًا: النسخ الاحتياطي ضابط أمني أيضًا

الأقسام السابقة تمنع «السيطرة على النظام»، لكن هناك نوعان آخران من التهديدات **لا تصدّهما أي تقوية**:

| التهديد | المظهر |
| --- | --- |
| **برامج الفدية** | تشفّر كل ملف تستطيع الوصول إليه. **والنسخ المركّبة على الجهاز نفسه تُشفَّر معها.** |
| **التخريب الداخلي / الخطأ** | أمر `rm -rf` من مشرف أو ملحق، أو «شريك» خبيث يحذف كل شيء ويرحل |

**والخلاصة: معنى النسخ الاحتياطي ليس «الوقاية من عطل العتاد» فقط، بل هو الوسيلة الوحيدة لمقاومة الفدية والتخريب — بشرط ألا تكون النسخة في مكان يصل إليه المهاجم.**

| المبدأ | التطبيق |
| --- | --- |
| **بلا اتصال** | نسخة واحدة على الأقل على وسيط **غير مركّب وغير متصل بالشبكة** في الأوقات العادية (قرص خارجي، أو لقطة في تخزين كائني) |
| **خارج الموقع** | فعطل قرص الجهاز أو حادث في مركز البيانات يُفني النسخة المحلية معه |
| **بإصدارات** | إبقاء أحدث نسخة فقط يعني الاستسلام عند «الأرشيف كان معطوبًا منذ زمن ولم يُكتشف» |
| **الصلاحيات** | ملفات النسخ تحوي كلمات مرور وأرشيفًا كاملًا عادةً، **فلا تضعها في دليل متاح للويب**، وشدّد صلاحياتها حسب القسم الثاني |

والعمليات المحدّدة (النسخ المتسق، و`save-off` / `save-on`، وسياسة الاحتفاظ، وعملية الاستعادة) في [النسخ الاحتياطي والاستعادة](/tutorials/java/backup). **والنسخة التي لم تُجرَّب استعادتها لا تُعدّ نسخة.**

:::warn لا تمنح الخادم صلاحية الكتابة في دليل النسخ
إن كان بإمكان عملية الخادم (أو ملحق محمّل فيها) الكتابة في دليل النسخ، فملحق مخترق يستطيع **حذف كل نسخك أو تشفيرها**. ضع دليل النسخ خارج دليل الخادم، و**لا تمنح حساب الخدمة صلاحية كتابة فيه**.
:::

## سادسًا: التدقيق والنظافة اليومية

التقوية ليست إجراءً لمرة واحدة. ويُنصح **بتشغيل هذه الفحوص دوريًا**، أو على الأقل بعد أي تعديل على النظام.

### 6.1 قائمة الفحص والأوامر

| البند | الأمر | النتيجة المتوقّعة |
| --- | --- | --- |
| **المنافذ المستمعة** | `sudo ss -tlnp` | لا يستمع إلا ما تعرفه من خدمات؛ والمنفذ الغريب يجب التحقق منه |
| **استماع UDP** | `sudo ss -ulnp` | كما سبق (إصدار Bedrock / Geyser يستخدم UDP) |
| **محاولات الدخول الفاشلة** | `sudo lastb \| head` | كثرة السجلات تعني تعرّضًا للتخمين (يحتاج root؛ وبعض الأنظمة لا تسجّل افتراضيًا) |
| **الدخول الناجح** | `last -n 20` | لا مستخدم أو IP مصدر لا تعرفه |
| **حسابات UID 0** | `awk -F: '$3 == 0 {print $1}' /etc/passwd` | `root` فقط |
| **الحسابات القابلة للدخول** | `awk -F: '$7 !~ /(nologin\|false)$/ {print $1, $7}' /etc/passwd` | لا أحد لا تعرفه |
| **صلاحيات sudo** | `getent group sudo` / `getent group wheel` | لا حساب مغادر أو مؤقت |
| **المهام المجدولة** | `sudo crontab -l`، و`ls -l /etc/cron.*`، و`systemctl list-timers --all` | لا مهمة لم تُنشئها |
| **وحدات systemd** | `systemctl list-units --type=service --state=running` | لا خدمة غريبة |
| **حزم غير مستخدمة** | `sudo apt autoremove --dry-run` / `sudo dnf autoremove` | تأكّد أن ما سيُحذف غير مفيد فعلًا |
| **تقييم عزل الخدمة** | `systemd-analyze security minecraft.service` | التقييم أقلّ أفضل، واقرأ التوصيات بندًا بندًا |

:::warn البنود الغريبة تُؤخذ بجدّية
- **مهمة cron أو وحدة systemd لم تُنشئها**: قد تكون بابًا خلفيًا للاستمرار، وقد تكون من حزمة برمجية — **فتحقّق من مصدرها قبل تقرير الحذف**.
- **منفذ استماع غريب**: ابحث أولًا بـ`sudo ss -tlnp` عن PID العملية، ثم انظر ما هي بـ`ps -p PID -o pid,user,cmd`.
- **حساب غريب**: لا تحذفه مباشرةً، بل انظر أولًا إلى دليل منزله و`authorized_keys` وسجلات الدخول، لتحديد هل استُخدم فعلًا.
:::

### 6.2 تصغير سطح التثبيت

**كلما قلّت البرمجيات المثبَّتة قلّت الثغرات القابلة للاستغلال.**

- **لا تثبّت بيئة سطح مكتب**. فتثبيت سطح مكتب على خادم سحابي يجلب خدمات ومنافذ كثيرة غير لازمة (انظر [اختيار نظام التشغيل](/tutorials/java/os)).
- **لا تثبّت خدمات لا تستخدمها**: FTP، وSamba، وخدمات الطباعة، وقواعد البيانات (إن لم يحتجها الخادم).
- **تأكّد من حالة الخدمات**: الخدمة غير اللازمة يجب أن تكون `disable` و`stop`، لا «مثبَّتة لكن غير مشغّلة» — فقد تُشغّلها سلسلة التبعيات. افحص بـ`systemctl is-enabled <service-name>`، وأوقفها بـ`sudo systemctl disable --now <service-name>`.

### 6.3 صفحة مرجعية سريعة

- [ ] الخادم يعمل **بمستخدم مخصّص**، لا بـ root (تأكّد بـ`ps -o user,cmd -C java` أو `systemctl status`)
- [ ] مالك دليل الخادم صحيح، و**لا وجود لـ 777**
- [ ] صلاحيات الملفات التي تحوي كلمات مرور **600**، وليست في دليل ويب ولا في مستودع Git
- [ ] التحديثات الأمنية التلقائية مفعّلة و**مؤكَّد أنها تعمل**؛ و**لم** تُفعّل إعادة تشغيل تلقائية غير مشروطة
- [ ] وحدة systemd تضبط `User=` و`WorkingDirectory=` و`Restart=`
- [ ] `LimitNOFILE` مضبوط، و`MemoryMax` **أكبر بوضوح** من `-Xmx`
- [ ] فُعّلت `NoNewPrivileges` و`PrivateTmp` و`ProtectSystem` و`ReadWritePaths` حسب الحاجة
- [ ] أُعيد تشغيل الجهاز مرة، وتأكّد **تشغيل الخدمة التلقائي عند الإقلاع**
- [ ] توجد نسخة **بلا اتصال / خارج الموقع**، وحساب الخدمة **لا يستطيع الكتابة** في دليل النسخ
- [ ] أُدرجت أوامر التدقيق أعلاه في مراجعة دورية
