اللوحة لا تُفتح، والمتصفّح يقول «اتصالك ليس خاصًّا»، وخريطة الويب بيضاء تمامًا — وفي مثل هذه الحوادث **يكون السبب الجذري واحدًا في نسبة معتبرة منها: انتهاء الشهادة.** وكان يمكن تجنّب هذا العطل تمامًا، لأن له تاريخ انتهاء واضحًا، ويمكن تجديده تلقائيًا.

وتوضّح هذه المقالة ثلاثة أمور: **ما الذي تحميه TLS فعلًا (وما لا تحميه)**، و**ما الشهادة وما المفتاح الخاص**، و**كيف تجعل التجديد أمرًا لا يحتاج أن تتذكّره أبدًا**. وإعداد الأمان للوحة نفسها في [استخدام أدوات إدارة اللوحات وأمانها](/tutorials/ops/panels)، وتنبيه انتهاء الشهادة في [المراقبة والتنبيهات](/tutorials/ops/monitoring).
:::warn الإعداد في هذه المقالة يتبع التوثيق الرسمي
**أسماء الحزم ووسائط الأوامر ومفاتيح الإعداد والمسارات الافتراضية وبنية الأدلة أدناه كلها تتغيّر بحسب التوزيعة وطريقة التثبيت وإصدار البرمجيات.** والغرض من الأمثلة بيان «ما يُضبط»، **وليست منتجًا جاهزًا للنسخ الحرفي**. فقبل التطبيق راجع التوثيق الرسمي لـ certbot وLet's Encrypt وnginx وتوزيعتك، والملفات التي أنشأها نظامك فعلًا.
:::

## 1. حدّد النطاق أولًا: حركة اللعب ليست HTTPS

وهذه أكثر نقطة تُخلط وتُساء فهمها:

| الترافيك | البروتوكول | المنفذ الافتراضي | هل يحتاج شهادة TLS |
| --- | --- | --- | --- |
| حركة لعب إصدار Java | بروتوكول TCP الخاص بـ Minecraft | 25565 | **لا، والشهادة بلا أثر عليه** |
| حركة لعب إصدار Bedrock | UDP (RakNet) | 19132 | **لا** |
| صفحة اللوحة | HTTPS | 443 (أو المنفذ الذي تختاره) | **نعم** |
| خريطة الويب (Dynmap، وSquaremap، وBlueMap وغيرها) | HTTPS | 443 | **نعم** |
| الموقع، وصفحة الحالة، وملحقات Web في MCDR، وواجهات API | HTTPS | 443 | **نعم** |
| RCON | بروتوكول TCP الخاص به | 25575 | ليس TLS؛ **ولا تعرّضه للإنترنت العام** |

**والخلاصة: شهادة HTTPS لـ«جهة الويب».** فتثبيت الشهادة أو عدمه **لا علاقة له** بقدرة اللاعبين على الدخول ولا بالتعرّض لهجوم رجل في المنتصف.

### 1.1 إذن ما هذا التشفير عند تسجيل الدخول في إصدار Java

إصدار Java فيه تشفير فعلًا في مرحلة تسجيل الدخول، لكنه **آلية بروتوكول Minecraft نفسه**، يحدّدها بروتوكول اللعبة، **ولا علاقة لها بشهادات X.509 ولا بـ Let's Encrypt**. واعتبار شهادة HTTPS و«تشفير حركة اللعب» شيئًا واحدًا هو بداية انحراف كثير من اتجاهات الإعداد.

### 1.2 ولماذا يبقى TLS واجبًا على جهة الويب

لأن جهة الويب تنقل **بيانات الاعتماد والهوية**: كلمة مرور اللوحة، وكوكي الجلسة، وAPI Key وToken، **وكلها مرئية لمن هو على الشبكة نفسها في HTTP الصريح**. إضافةً إلى أن المتصفّحات الحديثة تضع على صفحات HTTP وسم «غير آمن»، وبمجرد أن يعتاد مستخدم اللوحة على تجاهل التحذيرات تصبح تلك العادة مشكلة أمنية بحدّ ذاتها. واللوحة بمجرد فتحها للإنترنت تُمسح باستمرار، انظر [أنواع الهجمات الشبكية الشائعة والدفاع المتخصص لـ Minecraft](/tutorials/ops/attack-defense).

## 2. الشهادة والمفتاح الخاص

### 2.1 ما كلٌّ منهما

| | الشهادة (certificate) | المفتاح الخاص (private key) |
| --- | --- | --- |
| الجوهر | مفتاح عام + معلومات هوية + توقيع CA | مادة مفتاحية يجب أن تبقى سرًّا |
| هل يمكن نشرها | **نعم**، فهي تُرسل أصلًا لكل زائر | **لا يجوز إطلاقًا** |
| أثر التسريب | لا شيء (فهي معلومة عامة أصلًا) | **من يحصل على المفتاح الخاص يستطيع انتحال موقعك** |
| الانتهاء | لها صلاحية، و**يجب تجديدها** | تُستبدل مع الشهادة عادةً، ولا «تنتهي» بنفسها |

**الشهادة بطاقة هوية، والمفتاح الخاص خاتم.** فبطاقة الهوية تُرى، وخاتمك إن ضاع فالمصيبة.

### 2.2 الملفات الشائعة وعلاقتها

بمثال مخرجات عملاء ACME الشائعة (**وأسماء الملفات المحدّدة بحسب عميلك**):

| الملف | المحتوى | يُستخدم في |
| --- | --- | --- |
| `fullchain.pem` | شهادتك + الشهادة الوسيطة | **`ssl_certificate` في خادم الويب** |
| `privkey.pem` | المفتاح الخاص | **`ssl_certificate_key` في خادم الويب** |
| `chain.pem` / `cert.pem` | الشهادة الوسيطة / شهادتك وحدها | لا يلزم استخدامهما منفردين عمومًا |

**وأكثر مأزق شيوعًا**: ضبط `cert.pem` وحدها وإغفال الشهادة الوسيطة، فتصبح النتيجة «بعض المتصفّحات تفتح وبعضها لا». **واستخدام `fullchain.pem` يمنع هذه المشكلة.**

### 2.3 SNI: عدة مواقع على IP واحد

عملاء TLS الحديثون يرسلون **SNI (Server Name Indication)** في المصافحة، ويختار خادم الويب الشهادة بناءً عليها. فوضع عدة مواقع على جهاز واحد ممكن، ولكلٍّ شهادته؛ و**عند فحص الشهادة بسطر الأوامر يجب تمرير وسيط SNI** (`openssl s_client -servername ...`)، وإلا رأيت شهادة أخرى واستنتجت استنتاجًا خاطئًا (انظر القسم 8).

## 3. Let's Encrypt وACME و«التجديد التلقائي واجب»

### 3.1 ما هو ACME

**ACME بروتوكول لإصدار الشهادات وتجديدها تلقائيًا.** وLet's Encrypt أشهر جهة إصدار شهادات (CA) تعمل بـ ACME، وشهادات التحقق من النطاق (DV) التي تصدرها **مجانية**. والمفتاح في كلمة «تلقائي»: فهدف ACME أن تعمل سلسلة «الطلب، والتحقق، والإصدار، والتجديد، والنشر» كلها بلا إشراف. وهناك أيضًا جهات ACME أخرى (**وهل تناسبك يتبع توثيق كلٍّ منها الرسمي**).

### 3.2 التسعون يومًا ليست المشكلة، التجديد اليدوي هو المشكلة

الشهادات التي تصدرها Let's Encrypt **صلاحيتها 90 يومًا** (بحسب التوثيق الرسمي). وردّ فعل كثيرين الأول «قصيرة جدًا، متعبة» — **وردّ الفعل هذا نفسه هو المشكلة**:

- التسعون يومًا **مقصودة**: فهي تحوّل «نسيان التجديد» من «حادث مرة كل بضع سنوات» إلى «وضع طبيعي لا يبقى معه إلا الأتمتة».
- **وأي حلّ من نوع «سأجدّد يدويًا قبل الانتهاء» سيفشل**: أربع مرات في السنة، لسنوات متصلة بلا خطأ — وهذا ما لا يقدر عليه الإنسان؛ فالسفر، أو تغيير الحاسوب، أو ذهاب بريد الإشعار إلى المهملات، أيّها يجعلها تنتهي فجأة في يوم ما.
- والموقف الصحيح: **حوّل «هل ستنتهي الشهادة» من «أمر يجب أن أتذكّره» إلى «أمر يتولّاه النظام»**، ثم **راقبه** (انظر القسم 12).

### 3.3 عملاء ACME الشائعون

certbot (الأكمل توثيقًا والأكثر ملحقات)، وacme.sh (shell خالص، ودعم واسع لـ DNS API)، وlego (ملف Go واحد)، وخوادم ويب **مدمج فيها ACME** مثل Caddy. وتستخدم هذه المقالة certbot مثالًا.

**ولا تستخدم عميلين لإدارة النطاق نفسه**: فمهمتان تلقائيتان ستتجاوز كلٌّ منهما إعداد الأخرى، وستبحث طويلًا عند وقوع مشكلة.

## 4. تطبيق certbot

### 4.1 التثبيت: بحسب التعليمات الرسمية

طريقة تثبيت certbot تختلف اختلافًا كبيرًا بحسب التوزيعة والنسخة، **فاعتمد تعليمات التثبيت الرسمية**. والمصادر الشائعة ثلاثة: **مستودعات التوزيعة** (الأسهل، والنسخة قديمة غالبًا)، و**snap** (يوصي به التوثيق الرسمي غالبًا، والنسخة أحدث)، و**pip / بيئة افتراضية** (مرن، وتتولّى التبعيات بنفسك). **واستخدام ملحق nginx يحتاج حزمة الملحق المقابلة** (والاسم الشائع مثل `python3-certbot-nginx`، والاسم المحدّد بحسب توزيعتك). وبعد التثبيت تأكّد بـ`certbot --version`، ولاحظ أن **الأوامر الفرعية والوسائط قد تختلف بحسب النسخة**.

### 4.2 ثلاث طرق إصدار وسياق كلٍّ منها

| الأمر | ماذا يفعل | يناسب | ملاحظة |
| --- | --- | --- | --- |
| `certbot --nginx -d panel.example.com` | ملحق nginx: يعدّل الإعداد تلقائيًا ويضبط التحويل | nginx يعمل والإعداد في يدك | **سيعدّل إعداد nginx لديك**، فانسخه احتياطيًا أو أدخله في إدارة النسخ قبل التعديل |
| `certbot certonly --standalone -d panel.example.com` | يشغّل خدمة مؤقتة تحتلّ المنفذ 80 | لا توجد خدمة ويب على الجهاز | **يجب إيقاف nginx**، وإلا فشل لأن المنفذ 80 محتلّ |
| `certbot certonly --webroot -w /var/www/certbot -d panel.example.com` | يكتب ملف التحقق في دليل محدّد، ويقدّمه nginx الحالي | **الأكثر استخدامًا في سياق الوكيل العكسي** | يلزم ضبط `location` لـ`.well-known/acme-challenge/` في nginx |

وللجهاز الذي يعمل «وكيلًا عكسيًا للوحة بـ nginx» **يُنصح بـ webroot أو ملحق nginx**: فالأول أقل تغييرًا للإعداد، والثاني أقل عناءً. **وstandalone لا يصلح إلا حين لا توجد خدمة ويب بعد، أو حين تقبل إيقاف الخدمة مؤقتًا.** ويُطلب عند الإصدار **بريد إلكتروني لتذكير الانتهاء** (يمكن تخطّيه، لكن **يُنصح بملئه بشدة**: فهو الشخص الوحيد الذي قد يخبرك مسبقًا عند فشل التجديد التلقائي).

### 4.3 اختبار التجديد

**هذه الخطوة لا تُختصر.** فهي تتحقق من «إن عمل التجديد التلقائي فعلًا بعد 30 يومًا، فهل سينجح»:

```bash
# بروفة: لا تستبدل الشهادة فعلًا، ولا تستهلك حصة الإصدار في بيئة الإنتاج (تستخدم بيئة الاختبار)
sudo certbot renew --dry-run

# اطبع الشهادات المُدارة حاليًا ومساراتها وتواريخ انتهائها
sudo certbot certificates
```

**و`--dry-run` أرخص وسيلة تحقق. فالتجديد التلقائي الذي لم يُجرَّب به كالتجديد التلقائي غير الموجود.**
:::warn لا تستخدم --force-renewal على عجل
`--force-renewal` (وما شابهه من وسائط الإجبار) يعيد الإصدار فورًا. **والإصدار القسري المتكرّر قد يُطلق حدّ المعدّل عند CA، فتصبح عاجزًا عن الإصدار حين تحتاجه فعلًا.** فاستخدم `--dry-run` أولًا في التشخيص؛ وإن احتجت الإجبار فعلًا فتأكّد أولًا من السبب وقواعد الحدّ (بحسب توثيق CA الرسمي).
:::

### 4.4 التجديد التلقائي: systemd timer أم cron

**يأتي certbot عادةً بمهمة تجديد تلقائي، فلا تحتاج إلى كتابة واحدة.** والصيغتان الشائعتان: **مؤقّت systemd** (مثل `certbot.timer`، وهو مسار معظم التوزيعات وتثبيت snap) و**مهمة cron** (مثل `/etc/cron.d/certbot`، وهو تثبيت أقدم). وكل ما يلزم أن **تتأكّد من وجودها وأنها تعمل**:

```bash
# مسار systemd
systemctl list-timers | grep -i certbot

# مسار cron
ls -l /etc/cron.d/ | grep -i certbot
```

**وإن كتبت مهمة cron إضافية فستتنازع المهمتان.** والسلوك الافتراضي للتجديد التلقائي **فحص مرة أو مرتين يوميًا، ولا يُجديد فعلًا إلا حين تقلّ الصلاحية المتبقية عن نحو 30 يومًا** (والعتبة والجدولة المحدّدتان بحسب العميل والتوثيق الرسمي) — فـ«تعمل كل يوم» لا يعني «تُصدر كل يوم».

### 4.5 بعد التجديد يجب إعادة تحميل خادم الويب

التجديد يبدّل الملفات على القرص فقط، **وnginx العامل لا يقرأ الشهادة الجديدة تلقائيًا** (يقرأها عند التشغيل أو إعادة التحميل). فلذلك يُضبط خطّاف نشر:

```bash
# الطريقة الأولى: اكتب خطّاف النشر في أمر التجديد (مثال)
sudo certbot renew --deploy-hook "systemctl reload nginx"

# الطريقة الثانية: ضع السكربت في دليل الخطّافات، فيُنفَّذ بعد نجاح أي تجديد
# /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

ولا تنسَ منح سكربت الخطّاف صلاحية التنفيذ. **وأفضل طريقة للتحقق من سريان الخطّاف أن تنفّذ `--dry-run` مرة وتراقب هل أُعيد تحميل nginx** (ومعالجة `--dry-run` للخطّافات قد تختلف بحسب النسخة، **فاعتمد التوثيق الرسمي**).

## 5. إعداد TLS في nginx

### 5.1 مثال كامل

فيما يلي إعداد **كامل البنية** على جهاز يعمل «وكيلًا عكسيًا للوحة بـ nginx» (والنطاق والمنفذ والمسارات كلها عناصر بديلة):

```nginx
# /etc/nginx/conf.d/panel.conf
# المنفذ <panel-port> عنصر بديل، فاستبدله بالمنفذ المحلي الذي تستمع عليه اللوحة فعلًا.

server {
    listen 80;
    listen [::]:80;
    server_name panel.example.com;

    # ملف تحقّق الشهادة: مطابق لمسار --webroot في certbot
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    # بقية الطلبات تُحوَّل كلها إلى HTTPS
    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name panel.example.com;

    # يصدرها ويجدّدها عميل ACME لديك، فاستخدم المسارات الفعلية
    # لاحظ استخدام الرابط الرمزي في دليل live، لا الملف الحقيقي المرقّم في archive
    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    # اسمح بـ TLS الحديث فقط؛ فـ TLS 1.0/1.1 مهجوران في المتصفّحات السائدة
    ssl_protocols TLSv1.2 TLSv1.3;
    # دع العميل يختار حزم التشفير (الممارسة الحديثة الموصى بها؛ وTLS 1.3 لا ينظر في هذا الخيار أصلًا)
    ssl_prefer_server_ciphers off;

    # إعادة استخدام الجلسات اختيارية؛ وهل تُفعّل وبأي وسائط بحسب توثيق nginx الرسمي
    ssl_session_cache shared:SSL:10m;

    # HTTP/2: في nginx 1.25.1 فأحدث يُستخدم توجيه مستقل؛ والنسخ الأقدم تكتب listen 443 ssl http2;
    http2 on;

    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        # وحدة تحكّم اللوحة تعتمد WebSocket، فيجب تمرير ترويسة Upgrade
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # تحكم اللوحة بهذا على أن «الخارج HTTPS»، فتولّد روابط صحيحة وكوكيز آمنة
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

وبعد التعديل افحص الصيغة أولًا ثم أعد التحميل:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### 5.2 شرح سطرًا سطرًا (ما يسهل الخطأ فيه فقط)

| الإعداد | لماذا |
| --- | --- |
| `listen 443 ssl;` | **وسيط `ssl` لا يُغفل**، وإلا لم يُفعّل nginx TLS على هذا الـ server |
| `ssl_certificate` / `ssl_certificate_key` | الأول يستخدم `fullchain.pem` والثاني `privkey.pem`؛ والمسارات **يحدّدها عميلك**، فلا تنسخها |
| `ssl_protocols TLSv1.2 TLSv1.3;` | الحدّ الأدنى للمتصفّحات الحديثة TLS 1.2؛ وكتابته صراحةً أوضح من الاعتماد على الافتراضي |
| `ssl_prefer_server_ciphers off;` | الحديث يوصي بترك الاختيار للعميل؛ وحزم TLS 1.3 لا تتأثر بهذا الخيار أصلًا |
| `location` الخاص بـ`.well-known/acme-challenge/` | موضع تحقّق HTTP-01؛ وعند استخدام `--webroot` **يجب** أن يطابق مسار `-w` |
| `location / { return 301 ...; }` | تحويل HTTP إلى HTTPS؛ ولاحظ أنه **يأتي بعد location التحقّق** (فـ nginx يرجّح البادئة الأكثر تحديدًا) |
| `X-Forwarded-Proto` | بغيابه قد تولّد اللوحة روابط `http://` أو ترفض ضبط كوكيز آمنة |
| `http2 on;` | **مرتبط بالنسخة**: هذا التوجيه المستقل موجود منذ nginx 1.25.1 |
:::tip لماذا يُستخدم مسار live للشهادة
يضع عميل ACME الملفات الحقيقية لكل إصدار في دليل مثل `archive/` (مرقّم)، ثم ينشئ في `live/` **روابط رمزية** إلى الأحدث. **والإعداد يجب أن يشير إلى المسار تحت `live/`**: فهو يشير تلقائيًا إلى الملف الجديد بعد التجديد، أما أسماء الملفات المحدّدة تحت `archive/` فتتغيّر مع كل تجديد.
:::

### 5.3 عن حزم التشفير و«القيم الافتراضية تكفي عادةً»

في إعدادات nginx TLS المتداولة على الإنترنت مقطع `ssl_ciphers` طويل. **وفي معظم الحالات لا تحتاجه**:

- **القيم الافتراضية في nginx آمنة على النسخ الحديثة عادةً**، وتُحدَّث مع النسخة.
- ونسخ قائمة حزم من سنوات، **قد يستبعد حزمًا جديدة أفضل**.
- وعند الحاجة إلى تحكّم دقيق، ارجع إلى مصادر مُصانة مثل مولّد إعداد SSL في Mozilla، **لا إلى مدوّنة عشوائية**.
:::note وضع OCSP stapling الآن
كان يُوصى تاريخيًا بضبط `ssl_stapling on;` و`ssl_stapling_verify on;` (مع `ssl_trusted_certificate`). **لكن Let's Encrypt أعلنت إيقاف خدمة OCSP والتحوّل إلى CRL**، فلم يبقَ معنى لضبط OCSP stapling لشهادات LE. **والتوقيت المحدّد والوضع الحالي بحسب إعلان Let's Encrypt الرسمي**، فلا تنسخ الدروس القديمة.
:::

## 6. طرق التحقق: HTTP-01 وDNS-01

يحتاج ACME إلى إثبات «أنك تتحكّم في هذا النطاق». وطريقتان سائدتان:

| | HTTP-01 | DNS-01 |
| --- | --- | --- |
| كيف يُثبت | وضع ملف بمحتوى محدّد في `http://النطاق/.well-known/acme-challenge/<token>` | إضافة سجل TXT بمحتوى محدّد في `_acme-challenge.النطاق` |
| متطلبات الشبكة | **المنفذ 80 يجب أن يكون متاحًا من الإنترنت العام** (ويمكن متابعة التحويل) | لا يحتاج أي منفذ دخول |
| هل يصدر شهادة شاملة | **لا** | **نعم** |
| صعوبة الأتمتة | منخفضة (webroot / ملحق nginx يكفي) | تحتاج بيانات اعتماد API لمزوّد DNS |
| الخطر الرئيسي | حجب المنفذ 80 بجدار حماية/مجموعة أمان، أو اعتراض CDN، أو خطأ في التحويل | **تسريب بيانات API يعني تسريب التحكّم في النطاق** |

### 6.1 أسباب فشل HTTP-01 الشائعة

**عدم السماح بالمنفذ 80 في مجموعة أمان السحابة** (الأشيع: جدار حماية الجهاز مفتوح ومجموعة أمان المنصّة مغلقة)؛ **احتلال خدمة أخرى للمنفذ 80** (ففي `--standalone` يكون nginx ما زال يعمل)؛ **تحويل يأخذ طلب التحقّق معه** (فيجب أن يأتي location التحقّق قبل التحويل، أو أن يسمح التحويل بـ`/.well-known/`)؛ **وجود CDN / وكيل عكسي في الأمام** (فلا يصل طلب التحقّق إلى الأصل، ويلزم اتباع تعليمات CDN).

### 6.2 نقاط الانتباه في DNS-01

اسم السجل عادةً `_acme-challenge` (**وبحسب مزوّد DNS وتوثيق العميل**)؛ و**سريان DNS يحتاج وقتًا**، فلا تنقر التحقّق فور إضافة السجل يدويًا؛ و**بيانات API بأدنى صلاحية**، فلا تمنح إلا السجلات المطلوب تعديلها، ولا تستخدم مفتاح الحساب الشامل؛ وعند تخزين البيانات على الخادم **تُشدَّد صلاحياتها**، ولا تُرفع إلى Git.

### 6.3 متى يجب استخدام DNS-01

- عند إصدار **شهادة شاملة (wildcard)**.
- **حين يتعذّر فتح المنفذ 80** (محجوب من المشغّل، أو خلف CGNAT، أو مقيّد بشبكة الشركة).
- حين **لا يشير النطاق إلى هذا الجهاز مباشرةً** (CDN في الأمام، أو موازن حِمل، أو عدة أصول).
- حين تريد **أن يكون إصدار الشهادة مستقلًّا تمامًا عن خدمة الويب** (مثلًا لخدمة غير HTTP).

## 7. الشهادة الشاملة (Wildcard)

الشهادة الشاملة تغطّي مستوى واحدًا من النطاقات الفرعية، وثمنها **أنها تحتاج DNS-01 فقط**:

```bash
# لاحظ: *.example.com لا تشمل example.com نفسها، فاكتب الاثنين عادةً
sudo certbot certonly --manual --preferred-challenges dns \
  -d example.com -d '*.example.com'
```

والنقاط المهمة:

- **`*.example.com` لا تطابق `example.com`**، ولا تطابق `a.b.example.com` (فالشاملة تغطّي مستوى واحدًا). وإن احتجتها فاكتبها في `-d` معها.
- الشاملة **مريحة، لكنها توسّع دائرة الانفجار**: فتسريب المفتاح الخاص يصيب كل النطاقات الفرعية معًا.
- استخدام `--manual` يعني **أن التجديد يحتاج تدخّلًا بشريًا أيضًا** — إلا إن استبدلته بملحق تلقائي عبر DNS API. **والشاملة اليدوية + نسيان التجديد تركيبة حوادث شائعة جدًا.**
- وإن كان عدد نطاقاتك الفرعية قليلًا، **فإصدارها واحدًا واحدًا (بتجديد تلقائي عبر HTTP-01) أقل عناءً عادةً** من شهادة شاملة.

## 8. ماذا يحدث بعد فشل التجديد

### 8.1 الأعراض

| الظاهرة | السبب |
| --- | --- |
| اعتراض المتصفّح للصفحة كلها مع رسالة انتهاء الشهادة/عدم الأمان | الشهادة منتهية |
| تعذّر الدخول إلى اللوحة، أو أخطاء في كل عملاء API | كما سبق؛ وبعض العملاء لا يعطيك خيار «المتابعة» |
| خريطة الويب لا تُحمَّل | موارد الخريطة الثابتة تمرّ بـ HTTPS |
| «كان يعمل، ثم توقّف فجأة صباح يوم ما» | الانتهاء يحدث **في لحظة**، ولا تدرّج فيه |

### 8.2 كيف تفحص

```bash
# اطبع من أصدر هذه الشهادة ومتى تنتهي (مع -servername إلزاميًا، وإلا فقد ترى شهادة موقع آخر)
echo | openssl s_client -connect panel.example.com:443 -servername panel.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# لعرض السلسلة كاملة (بما فيها الشهادة الوسيطة)
openssl s_client -connect panel.example.com:443 -servername panel.example.com -showcerts </dev/null
```

وفي المخرجات ركّز على تاريخين: **`notBefore` (بدء السريان) و`notAfter` (الانتهاء)**. فإن كان `notAfter` في الماضي فقد تأكّدت المشكلة.

**وافحص كذلك تاريخ انتهاء الملف المحلي** (فقد تكون ترى شهادة CDN لا شهادة الأصل):

```bash
sudo openssl x509 -in /etc/letsencrypt/live/panel.example.com/fullchain.pem -noout -subject -dates
sudo certbot certificates
```
:::warn إعادة تشغيل الخدمة وحدها لا تنفع
بعد انتهاء الشهادة **لن تجعلها إعادة تشغيل nginx جديدة**. والترتيب الصحيح: **نجّد بنجاح أولًا** (`sudo certbot renew`، وحلّ ما يبلّغ عنه من أخطاء)، **ثم أعد تحميل nginx**. والعكس إهدار للوقت.
:::

### 8.3 HSTS يجعل الأمر أسوأ

إن فعّلت HSTS (ترويسة `Strict-Transport-Security`) فسيفرض المتصفّح **HTTPS مدةً، ولن يتيح للمستخدم النقر على «المتابعة»**، وعند انتهاء الشهادة تصبح الصفحة خطأً **لا يمكن تجاوزه إطلاقًا**. وHSTS جيد بذاته (فهو يمنع هجمات التخفيض)، لكن تذكّر ثمنه: **يجعل «بقاء الشهادة صالحة دائمًا» من «أفضل» إلى «إلزامي»**. فتأكّد قبل تفعيله من جاهزية التجديد التلقائي والمراقبة.

## 9. ملفات الشهادة والصلاحيات

المفتاح الخاص هو الشيء الوحيد في هذه المنظومة الذي يحتاج سرّية حقيقية:

```bash
# المفتاح الخاص للمالك فقط بالقراءة؛ والدليل يُشدَّد كذلك
sudo chmod 700 /etc/letsencrypt/archive /etc/letsencrypt/live
sudo chmod 600 /etc/letsencrypt/archive/<النطاق>/privkey*.pem
sudo chown root:root /etc/letsencrypt/archive/<النطاق>/privkey*.pem

# تحقّق: لا يجوز أن يكون مقروءًا للمجموعة/الآخرين
ls -l /etc/letsencrypt/live/<النطاق>/
```

والنقاط المهمة:

- **`chmod 600` + مالك root** ممارسة شائعة وآمنة. وعميل ACME يضبط صلاحيات معقولة بنفسه عادةً، **فانظر الحالة أولًا ثم عدّل**.
- **لا تنسخ المفتاح الخاص إلى جذر الويب، ولا إلى دليل مؤقت، ولا إلى أداة دردشة، ولا إلى مستودع Git.** وإن احتجت منحه لخدمة أخرى ففكّر في مجموعة صلاحيات أو ACL، لا في `chmod 644`.
- **عملية master في nginx تبدأ بـ root عادةً**، فتستطيع قراءة المفتاح المملوك لـ root؛ **وإن كانت طريقة نشرك مختلفة (حاويات، أو تشغيل بلا root) فتأكّد أن المستخدم الذي يقرأ الشهادة يملك الصلاحية**، وإلا ظهر العَرَض كـ«الإعداد صحيح والخدمة لا تقوم».
- **`chmod -R 777 /etc/letsencrypt` خطأ محقّق**: فهو يحلّ خطأ الصلاحيات ويسلّم المفتاح الخاص لكل مستخدم على الجهاز.
- **النسخ الاحتياطي يشمل الشهادة**، لكن **المفتاح الخاص داخل النسخة يجب أن يُحفظ مشفّرًا كذلك** (انظر [النسخ الاحتياطي خارج الموقع](/tutorials/ops/offsite-backup)).

## 10. سلسلة الوكيل العكسي

حين تُنهي nginx جلسة HTTPS ثم تُمرّر الطلب إلى اللوحة، **تصبح «البروتوكول» مفهومين مختلفين في السلسلة**:

```text
متصفّح اللاعب  --HTTPS-->  nginx (ينهي TLS)  --HTTP(127.0.0.1)-->  اللوحة
```

وينتج عن ذلك ثلاث مشكلات شائعة:

| المشكلة | المظهر | المعالجة |
| --- | --- | --- |
| الروابط التي تولّدها اللوحة `http://` | يعترض المتصفّح موارد الصفحة أو تحويلاتها | مرّر `X-Forwarded-Proto $scheme`، واضبط «العنوان الخارجي / الوكيل الموثوق» بحسب توثيق اللوحة الرسمي |
| اللوحة ترى «الاتصال غير آمن» فترفض ضبط الكوكي | انقطاع فوري بعد تسجيل الدخول | كما سبق؛ وبعض اللوحات تحتاج إعلان HTTPS صراحةً في الإعداد |
| WebSocket لا يتصل | وحدة التحكّم بيضاء وتدور بلا نهاية | مرّر ترويستَي `Upgrade` و`Connection`، واضبط `proxy_http_version 1.1` |

**وإن وُجد في الأمام CDN** (مثل Cloudflare) فتصبح السلسلة «المتصفّح ← CDN (ينهي TLS) ← الأصل (جلسة TLS أخرى)»، و**كل طرف يحتاج شهادته وإعداده**؛ **وهل تُتحقّق شهادة الأصل وبأي نمط، سلوك مزوّد CDN ويتبع توثيقه الرسمي**. وفي مثل هذه السلسلة تكون طريقة الفحص بـ`-servername` في القسم 8 مفيدة جدًا في تحديد «شهادة من انتهت».

وإعداد جهة اللوحة كاملًا في [استخدام أدوات إدارة اللوحات وأمانها](/tutorials/ops/panels).

## 11. الشهادة الموقّعة ذاتيًا: متى تُقبل

الشهادة الموقّعة ذاتيًا (أن تكون أنت CA وتوقّع لنفسك) **ليست «HTTPS مجانيًا»**، وتموضعها:

| السياق | هل تصلح |
| --- | --- |
| أنت وحدك تصل من الشبكة الداخلية (مثل سياق الشبكة الداخلية في [فتح الخادم على حاسوب منزلي وصيانته](/tutorials/ops/home-hosting))، وتستطيع تثبيت CA الموقّعة ذاتيًا في مخزن ثقة أجهزتك | **تصلح** |
| اختبار مؤقّت، أو مرحلة لم يُربط فيها نطاق بعد | **تصلح**، لكن مع العلم أنها ستُستبدل في أي وقت |
| موجّهة للإنترنت العام، وللاعبين أو المساعدين | **لا تصلح**: فكل الناس سيرون تحذير المتصفّح |
| لعملاء API والبوتات والملحقات | **لا تصلح عادةً**: فكثير من العملاء يرفض الشهادات غير الموثوقة افتراضيًا، و**تعديل الإعداد لتجاهل التحقّق خيار أسوأ** |

وحقائق يجب معرفتها:

- **تحذير المتصفّح لا يمكن «ضبطه بعيدًا»**: فما يراه المستخدم «اتصالك ليس خاصًّا»، ويحتاج إلى النقر على «متقدّم ← متابعة». **وهذا يدرّب المستخدم على تجاهل التحذيرات، وهي مشكلة أمنية بحدّ ذاتها.**
- ولكي لا تُصدر الشهادة الموقّعة ذاتيًا تحذيرًا، **يجب استيراد CA الموقّعة ذاتيًا إلى كل جهاز عميل**؛ وبكثرة الأجهزة تتجاوز كلفة صيانة ذلك كلفة طلب شهادة مجانية.
- وإن احتجت ذلك فعلًا في سياق داخلي، فاستخدم أدوات مخصّصة لـ CA الداخلية مثل **mkcert** و**step-ca**، فهي أقل عرضةً للخطأ من كتابة `openssl req` يدويًا (**والاستخدام المحدّد بحسب توثيق كلٍّ الرسمي**).
- **ولا تُفعّل HSTS أبدًا** على موقع بشهادة موقّعة ذاتيًا.

## 12. المراقبة والقائمة

**انتهاء الشهادة عطل «يمكن معرفته مسبقًا تمامًا»**، فيجب أن يكون مُراقبًا لا مأمولًا. والحدّ الأدنى: **التنبيه عند بقاء أقل من 14 يومًا**. والطريقتان **يُنصح بهما معًا**:

1. **فحص HTTPS خارجي**: دع مراقبة على جهاز آخر تطلب عنوان اللوحة كل بضعة دقائق، وتفحص تاريخ انتهاء الشهادة. فكثير من أدوات المراقبة (مثل Uptime Kuma) تعرض معلومات الشهادة في مراقبة HTTPS مباشرةً. انظر [المراقبة والتنبيهات](/tutorials/ops/monitoring).
2. **فحص محلي للانتهاء**: اقرأ ملف الشهادة على الخادم واحسب الأيام المتبقية، واكتبها في مؤشر مراقبة أو أرسل إشعارًا مباشرةً.

```bash
# نسخة سطر واحد: اطبع الأيام المتبقية (وسيط -d في date كتابة GNU، وعلى أنظمة أخرى استخدم أمر التاريخ المقابل)
sudo openssl x509 -in /etc/letsencrypt/live/panel.example.com/fullchain.pem -noout -enddate \
  | cut -d= -f2 \
  | xargs -I{} date -d "{}" +%s \
  | awk -v now="$(date +%s)" '{ printf "المتبقي %d يومًا\n", ($1 - now) / 86400 }'
```
:::tip يجب أن يكشف التنبيه «فشل التجديد»
مراقبة «كم يومًا بقيت للشهادة» وحدها لا تكفي — **فستنبّه قبل 30 يومًا بأنها «على وشك الانتهاء»، وقد تعتاد ذلك التنبيه**. والتركيبة الأفضل: **تنبيه فشل مهمة التجديد** (إشعار فشل timer/cron) **مع** تنبيه «الأيام المتبقية < 14». فالأول يخبرك «أن التجديد التلقائي تعطّل»، والثاني هو الشبكة الأخيرة.
:::

### 12.1 قائمة التحقّق قبل الإطلاق

| البند | كيف | معيار النجاح |
| --- | --- | --- |
| الشهادة صادرة | `certbot certificates` | النطاق صحيح، وتاريخ الانتهاء في المستقبل |
| تُستخدم السلسلة الكاملة | انظر `ssl_certificate` في إعداد nginx | يشير إلى `fullchain.pem`، لا إلى `cert.pem` وحدها |
| نسخة البروتوكول صحيحة | افحص بالمتصفّح أو بـ`openssl s_client` | التفاوض على TLS 1.2 / 1.3 |
| HTTP يحوّل إلى HTTPS | افتح بـ`http://` مرة | تحويل 301/308، وبلا تنبيه محتوى مختلط |
| مسار التحقّق متاح | `curl -I http://النطاق/.well-known/acme-challenge/<ملف-اختبار>` | يعيد 200 (ولا يبتلعه التحويل) |
| مهمة التجديد التلقائي تعمل | `systemctl list-timers` أو انظر `/etc/cron.d/` | مهمة تجديد واحدة فقط |
| بروفة التجديد نجحت | `certbot renew --dry-run` | بلا أخطاء |
| إعادة التحميل بعد التجديد | افحص خطّاف النشر | إعادة تحميل nginx فعلًا بعد نجاح التجديد |
| صلاحيات المفتاح مشدّدة وبلا نسخ مسرّبة | `ls -l` + `stat`، وابحث في القرص وتاريخ Git | غير مقروء لغير المالك، والمفتاح موجود فقط في دليل الشهادة ونسخه المشفّرة |
| تنبيه الانتهاء مضبوط | لوحة المراقبة | ارفع العتبة متعمّدًا للتحقق من إرسال التنبيه مرة |
| اللوحة/الخريطة تعمل فعلًا | افتحها بالمتصفّح مرة | الدخول ووحدة التحكّم والخريطة طبيعية، وبلا تحذير شهادة |
