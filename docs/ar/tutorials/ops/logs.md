**السجل هو الدليل الوحيد عند التشخيص، وهو المتهم الأول في ملء قرص الخادم.** فالخادم والملحقات والوسيط واللوحة وsystemd وDocker وnginx كلها تكتب على القرص، وكلها تقريبًا بلا سقف افتراضي. وتوضّح هذه المقالة: أين توجد السجلات، وكيف تقيس قبل أن تعالج، والكتابة الصحيحة لـ logrotate، وحدود السعة في journald وDocker، وقائمة صيانة يمكن اتباعها.

أما كيف تقرأ السجل عند تشخيص عطل بعينه فانظر [المراقبة والتنبيهات](/tutorials/ops/monitoring)؛ وإخراج السجلات مع الحفظ خارج مركز البيانات انظر [النسخ خارج الموقع](/tutorials/ops/offsite-backup).

## 1. ما السجلات الموجودة فعلًا على مضيف Minecraft

لنفكّك كلمة «سجل» أولًا. ففي معظم حوادث «امتلأ القرص بلا سبب»، ليس الجاني `logs/latest.log`.

| المصدر | المسار النموذجي | الوصف |
| --- | --- | --- |
| سجل الخادم الرئيسي | `logs/latest.log` | السجل المكتوب حاليًا، بترميز UTF-8، ونهايات أسطر LF على Linux وCRLF على Windows |
| سجلات الخادم التاريخية | `logs/YYYY-MM-DD-N.log.gz` | سجلات قديمة يدوّرها النواة نفسها، مضغوطة بـ gzip |
| تقارير الانهيار | `crash-reports/crash-YYYY-MM-DD_HH.MM.SS-server.txt` | ملف لكل انهيار، ومكدّسه طويل، وحجم الواحد من مئات KB إلى عدة MB |
| سجلات الملحقات | `plugins/<الملحق>/logs/*.log` و`plugins/<الملحق>/*.log` | **الموضع يختلف بحسب الملحق**، فبعضها يكتب في دليل الملحق وبعضها في `logs/` بالخادم مباشرةً |
| سجلات الوسيط | `<دليل-الوسيط>/logs/latest.log` | لـ Velocity / BungeeCord دليل عمل و`logs/` مستقلان |
| سجل وحدة systemd | `journalctl -u minecraft.service` | عند الإدارة بـ systemd يدخل stdout/stderr إلى journal افتراضيًا |
| سجلات النظام | `/var/log/syslog` و`/var/log/messages` و`/var/log/kern.log` | الأسماء تختلف بحسب التوزيعة |
| سجلات الدخول والأمان | `/var/log/auth.log` (عائلة Debian) و`/var/log/secure` (عائلة RHEL) | آثار هجمات SSH هنا، وتنمو بسرعة على الأجهزة المكشوفة |
| سجلات nginx | `/var/log/nginx/access.log` و`error.log` | توجد حتمًا عند تمرير اللوحة أو الخريطة أو وكيل الويب عبر nginx |
| سجلات اللوحة | دليل اللوحة نفسه | لوحات مثل MCSManager وPterodactyl تكتب سجلاتها، وكثيرًا ما تكتب في قاعدة البيانات كذلك |
| سجلات Docker | `/var/lib/docker/containers/<معرّف-الحاوية>/<معرّف-الحاوية>-json.log` | السواقة الافتراضية `json-file`، و**لا تدوير افتراضيًا** |
| ملفات جهة JVM | `logs/gc.log` و`hs_err_pid<pid>.log` و`*.jfr` | تُولَّد عند تفعيل سجل GC أو JFR أو عند انهيار JVM، ويسهل نسيانها |

:::note لا تنسَ ما يكتبه JVM نفسه
معاملات تشغيل مثل `-Xlog:gc*:file=logs/gc.log:time,uptime,level,tags:filecount=5,filesize=10M` تضع سجل GC إضافيًا في `logs/`؛ وعند انهيار JVM يُترك `hs_err_pid<pid>.log` في دليل العمل. وهذه ليست في منظومة تدوير Minecraft، فتُعالج منفصلة.
:::

## 2. كيف يقتل السجل الخادم

لنمو السجل ثلاث صور نموذجية، والثالثة أخطرها:

1. **نمو طبيعي**: لاعبون يدخلون ويخرجون، والملحقات تكتب يوميًا، فيكبر تدريجيًا.
2. **نمو مفاجئ**: جهاز مكشوف يُمسح ويُختبر ضغطًا وتُغرق اتصالاته، وكل اتصال قد يكتب سطرًا.
3. **غمر دوري**: ملحق يطلق استثناءً داخل `onTick`، أو مهمة تفشل كل ثانية — **20 سطرًا في الثانية**، أي نحو 1.7 مليون سطر يوميًا، وبحساب 150 بايت للسطر **نحو 250 MB يوميًا**، ولا يتوقف من نفسه.

وامتلاء القرص ليس «سجلًا كبر قليلًا»، بل يُدمّر أشياء أخرى معه:

:::warn أعراض امتلاء القرص: الحفظ والملحقات واللوحة معًا
- **فشل حفظ العالم**: يظهر في السجل `Failed to save chunk` و`java.io.IOException: No space left on device`، فينقطع اللاعبون وترجع القطع.
- **فشل كتابة إعداد/قاعدة بيانات الملحق**: SQLite يخطئ `database or disk is full`، وMySQL يخطئ `Disk full`، وقد تُكتب بيانات الصلاحيات والاقتصاد والأملاك نصف كتابة.
- **موت الخادم في أسوأ لحظة**: تعذّر كتابة `level.dat` عند الإغلاق، أو انهيار العملية مباشرةً، فتظهر فجوة بين حالة العالم بعد إعادة التشغيل وآخر حفظ ناجح.
- **تعطّل اللوحة وSSH معًا**: اللوحة لا تكتب السجل والجلسة، فلا يبقى لك مدخل «أصعد وأنظر».
- **قد تُستهلك الـ inode أيضًا**: يُظهر `df -h` مساحة متبقية، لكن `df -i` بلغ 100%، والأثر كامتلاء القرص نفسه.
:::

:::tip لا تضع دليل السجلات ودليل الحفظ في القسم نفسه إن أمكن
إن سمحت الظروف، ضع `logs/` (أو نقطة تركيب السجلات كلها) على قسم أو قرص مستقل. فحتى لو خرج السجل عن السيطرة يبقى الحفظ قابلًا للكتابة، وأسوأ ما يحدث فقدان السجل لا الحفظ.
:::

## 3. قِس ثم عالج: أربعة أوامر تكشف الحالة

قِس قبل أن تمسّ شيئًا. والأوامر التالية قراءة فقط، ولا تُفسد شيئًا.

```bash
# 1) حجم دليل سجلات الخادم
du -sh /opt/minecraft/server/logs

# 2) المساحة المتبقية وعدد inode المتبقي
df -h
df -i

# 3) كم يشغل journald (ضروري عند الإدارة بـ systemd)
journalctl --disk-usage

# 4) اعثر على كل ملفات السجلات التي تتجاوز 100 MB
find /opt/minecraft/server -type f -name '*.log*' -size +100M

# إضافة: أي دليل يستهلك أكبر مساحة على الجهاز
sudo du -x -h -d 1 /var | sort -h | tail -n 10
```

وعند قراءة النتائج انتبه إلى ثلاثة أمور:

- `du -sh` يقيس **الاستهلاك الحالي**، و`find ... -size +100M` يجد **ملفًا واحدًا كبيرًا**، وبالجمع بينهما تفرّق بين «ملفات صغيرة كثيرة» و«ملف وحش واحد».
- حين يبلغ `IUse%` في `df -i` نسبة 100%، فحتى لو أظهر `df -h` مساحة متبقية لا يستطيع الخادم كتابة أي شيء.
- خرج `journalctl --disk-usage` هو الاستهلاك الفعلي لدليل journal؛ وهو لا يظهر في `du -sh logs/`، ويسهل إغفاله.

## 4. سياسة احتفاظ Minecraft بالسجلات

تدوّر النواة نفسها طبقة: فيُحوَّل `latest.log` الحالي إلى `YYYY-MM-DD-N.log.gz` بالتاريخ، و`N` ترتيب اليوم.

**وعدد النسخ المحفوظة وإمكان ضبطه يعتمد كليًا على النواة.** فبعض النوى تحتفظ بعدد محدود من أحدث النسخ بلا مفتاح، وبعضها يوفّر مفاتيح في ملف الإعداد بأسماء وقيم افتراضية مختلفة. ولا نخمّن هنا: **المرجع توثيق نواتك الرسمي وملف إعدادها**، فابحث في دليل النواة عن بنود `log` ذات الصلة، أو اقرأ فصل «السجلات» في توثيق النواة.

وإن لم توفّر النواة ضبط عدد النسخ، فاتركه لـ logrotate أو سكربت تنظيف على مستوى النظام (الأقسام التالية). وانتبه كذلك إلى أن تقارير الانهيار في `crash-reports/` **لا تشارك** في تدوير سجلات النواة، فتتراكم بلا حدّ في حلقة انهيار.

## 5. ضبط logs/ بـ logrotate

logrotate أداة Linux القياسية لتدوير السجلات، وهي مثبَّتة مسبقًا في كل التوزيعات تقريبًا، وتعمل افتراضيًا عبر `logrotate.timer` (أو cron) مرة يوميًا. والإعداد يوضع في ملف تحت `/etc/logrotate.d/`.

### 5.1 إعداد نموذجي كامل

```conf
# /etc/logrotate.d/minecraft
# ملاحظة: لا يجوز أن يكون هذا الملف قابلًا للكتابة من group أو world، وإلا رفض logrotate تحميله لأسباب أمنية.

/opt/minecraft/server/logs/latest.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
    su minecraft minecraft
}

# اختياري: سجلات تكتبها الملحقات نفسها، واضبط المسارات بحسب واقعك
/opt/minecraft/server/plugins/*/logs/*.log {
    weekly
    rotate 8
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

واستبدل `/opt/minecraft/server` و`minecraft` بالمسار واسم المستخدم الحقيقيين على جهازك. والبدل في الكتلة الثانية آمن: فالملفات المدوّرة تصير `*.log.1` أو `*.log.1.gz`، فلا يطابقها `*.log` بعد ذلك.

### 5.2 ما تفعله كل تعليمة

| التعليمة | الوظيفة |
| --- | --- |
| `daily` | تدوير مرة يوميًا (بشرط أن logrotate نفسه يُستدعى يوميًا، وهو الافتراضي في التوزيعات) |
| `rotate 14` | الاحتفاظ بـ 14 نسخة تاريخية، وحذف الخامسة عشرة (الأقدم) |
| `compress` | ضغط الملفات التاريخية بـ gzip، وهو يوفّر عادةً أكثر من 90% من المساحة |
| `delaycompress` | **عدم ضغط** النسخة المدوّرة للتو، وضغطها في التدوير التالي |
| `missingok` | عدم الخطأ عند غياب الملف (مفيد حين لم يبدأ الخادم أو تغيّر الدليل) |
| `notifempty` | عدم التدوير إذا كان الملف فارغًا، لتجنّب صنع أرشيفات فارغة كثيرة |
| `copytruncate` | **النسخ أولًا ثم تفريغ الملف الأصلي في موضعه**، لا إعادة تسميته |
| `su minecraft minecraft` | تنفيذ التدوير بهوية المستخدم/المجموعة المحددين؛ ويُستحسن إضافتها حين يكون دليل السجلات ملكًا لمستخدم الخادم |

### 5.3 لماذا `copytruncate` مهم لخادم يعمل

طريقة التدوير الافتراضية هي **rename**: يعيد logrotate تسمية `latest.log` إلى `latest.log.1`، ثم (وفق التعليمة `create`) ينشئ `latest.log` فارغًا. والمشكلة أن **عملية Java أخذت مقبض ذلك الملف عند بدئها**: فبعد إعادة التسمية يواصل الخادم الكتابة في «الملف الذي أُعيدت تسميته»، ويبقى `latest.log` الجديد فارغًا دائمًا، فيبدو السجل «مختفيًا» حتى إعادة تشغيل الخادم.

و`copytruncate` يفعل غير ذلك: **ينسخ المحتوى أولًا، ثم يقتطع الملف الأصلي إلى 0 بايت**. فالـ inode لم يتغيّر، ويواصل الخادم الكتابة في المقبض نفسه، فيظهر السجل الجديد في `latest.log` طبيعيًا بلا إعادة تشغيل.

وكلفتها يجب توضيحها:

- بين «اكتمال النسخ» و«الاقتطاع» نافذة زمنية قصيرة جدًا، **وتضيع فيها كتابات السجل القليلة الجديدة** (بضعة أسطر عادةً).
- ولذلك يتعارض `copytruncate` مع `create` (فالملف الأصلي لا يتحرّك، فلا إجراء إنشاء).
- وإن كان السجل مهمًا إلى حدّ لا يجوز فيه فقدان سطر، فالطريقة الصحيحة أن يعيد الخادم فتح ملف السجل بنفسه (ومعظم النوى لا توفّر إشارة لذلك)، أو تقبل خسارة هذه الأسطر — وهي مقبولة عادةً في خادم Minecraft.

:::tip بالمناسبة: `delaycompress` وُجد ليتعاون مع `copytruncate`
بعض البرامج تبقى بعد التدوير مدة قصيرة تحمل مقبض الملف القديم وتواصل الكتابة فيه. و`delaycompress` يبقي `latest.log.1` المدوّر للتو غير مضغوط، فيمنع تلف الأرشيف بسبب «الضغط أثناء الكتابة»، ويؤجّل الضغط إلى التدوير التالي.
:::

### 5.4 التحقق والتشخيص

بعد تعديل الإعداد **شغّله تجريبيًا أولًا، ولا تنتظر اليوم التالي**:

```bash
# تشغيل تجريبي: يطبع ما سيفعله فقط، ولا يغيّر الملفات
sudo logrotate -d /etc/logrotate.d/minecraft

# بعد التأكد نفّذ تدويرًا قسريًا مرة للتحقق الفوري
sudo logrotate -f /etc/logrotate.d/minecraft

# انظر النتيجة: يجب أن يظهر latest.log وlatest.log.1 (أو .1.gz)
ls -lh /opt/minecraft/server/logs
```

والمزالق الشائعة:

- **الإعداد لم يسري**: تأكد أن `logrotate.timer` يعمل، بفحص `systemctl list-timers logrotate.timer`.
- **خطأ صلاحيات**: لا يجوز أن يكون `/etc/logrotate.d/minecraft` قابلًا للكتابة من group/world؛ ويجب أن يستطيع المستخدم المحدد في `su` الكتابة في دليل السجلات.
- **سجلات تحت `/etc` أو `/usr` لا تدور**: خدمة `logrotate.service` في التوزيعة تحمل افتراضيًا `ProtectSystem=full`، فيمنع تعديل الملفات تحت هذين الدليلين — لذا وضع الخادم والسجلات في مواضع مثل `/opt` أو `/srv` أقل عناءً.
- **الملف يكبر ولم يُدوَّر**: `notifempty` لا يمنع تدوير ملف غير فارغ، لكن سريان `daily` مشروط بـ«وقت آخر تدوير»، وترى منطق الحكم في خرج `-d`.

## 6. حدود سعة systemd وjournald

عند إدارة الخادم بـ systemd يستقبل journald الـ stdout/stderr افتراضيًا. ولـ journald سقف عام، ويُضبط في `/etc/systemd/journald.conf`:

```ini
# /etc/systemd/journald.conf
[Journal]
Storage=persistent
SystemMaxUse=1G
SystemMaxFileSize=100M
MaxRetentionSec=1month
```

| بند الإعداد | المعنى |
| --- | --- |
| `Storage=` | `persistent` يكتب إلى `/var/log/journal`، و`volatile` في الذاكرة فقط، و`auto` بحسب وجود الدليل، و`none` بلا تخزين |
| `SystemMaxUse=` | أقصى ما يشغله journal على القرص (الافتراضي نحو 10% من نظام الملفات، بحدّ 4G) |
| `SystemMaxFileSize=` | سقف ملف journal الواحد (الافتراضي نحو 1/8 من `SystemMaxUse`، بحدّ 128M) |
| `MaxRetentionSec=` | أطول مدة احتفاظ بالبنود، و`0` يعني إيقاف الحذف الزمني |
| `SystemKeepFree=` | أقل مساحة تُترك لاستخدامات أخرى؛ ويأخذ journald الأشدّ من هذا و`SystemMaxUse` |

وبعد التعديل أعد تشغيل الخدمة ونفّذ استرجاعًا يدويًا مرة:

```bash
sudo systemctl restart systemd-journald

# اعرض الاستهلاك الحالي
journalctl --disk-usage

# استرجاع يدوي (اختر واحدًا أو اجمع بينها)
sudo journalctl --vacuum-size=500M
sudo journalctl --vacuum-time=30d
sudo journalctl --vacuum-files=20
```

:::warn journald يحذف الملفات «المؤرشفة» فقط
`--vacuum-*` و`SystemMaxUse=` يحذفان ملفات journal **المؤرشفة** فقط، ولا يُحذف الملف النشط المكتوب حاليًا. فبعد الاسترجاع قد **يبقى الاستهلاك أعلى قليلًا من السقف** الذي ضبطته، وهذا طبيعي وليس إعدادًا لم يسري.
:::

## 7. تدوير سجلات حاويات Docker

سواقة `json-file` الافتراضية في Docker **لا تدوّر شيئًا**: فكلما طال عمل الحاوية كبر `/var/lib/docker/containers/<ID>/<ID>-json.log`، وهو مقبض ملف تحتفظ به خدمة Docker، فلا يحرّر `rm` المباشر المساحة فورًا.

والحدّ عند تشغيل حاوية واحدة:

```bash
docker run -d --name mc \
  --log-driver json-file \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  your-minecraft-image
```

والقيم الافتراضية على مستوى الخدمة تُكتب في `/etc/docker/daemon.json`:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

وبعد التعديل يلزم إعادة تشغيل الخدمة، و**الحاويات الموجودة تحتاج إعادة إنشاء ليسري**:

```bash
sudo systemctl restart docker

# اعرض إعداد السجل ومسار ملف السجل لحاوية معينة
docker inspect --format='{{.HostConfig.LogConfig}}' mc
docker inspect --format='{{.LogPath}}' mc

# في الحالات الطارئة اقتطع الملف أولًا ثم افحص على مهل (يعمل مع الحاوية العاملة أيضًا)
sudo truncate -s 0 "$(docker inspect --format='{{.LogPath}}' mc)"

# متابعة السجلات اليومية
docker logs --tail 200 -f mc
docker system df
```

وعند استخدام Docker Compose يُكتب تحت الخدمة:

```yaml
services:
  mc:
    image: your-minecraft-image
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

## 8. سجلات nginx واللوحة والوسيط

- **nginx**: `/var/log/nginx/access.log` و`error.log`. وحزمة nginx في التوزيعة **تأتي** بإعداد logrotate، فالتدوير يجري عادةً؛ وإن كان الموقع يُمسح من الإنترنت فسينتفخ `access.log` بشكل شاذ، ويمكنك إيقاف سجل الوصول للموارد الساكنة، أو تخصيص ملف سجل لموقع اللوحة وإضافة `maxsize 200M`.
- **اللوحة**: دليل سجلات اللوحة + قاعدة البيانات. وسجلات اللوحة ليست في `logs/` عادةً، فلا تظن أن تنظيف `logs/` يحلّ كل شيء.
- **الوسيط**: لـ Velocity / BungeeCord دليل عمل و`logs/` مستقلان، ويحتاجان **كتلة logrotate منفصلة** أو قاعدة تنظيف.
- **سجلات الوصول للوكيل العكسي واللوحة تحوي عناوين IP للاعبين**: وهذه تُعالج كبيانات خصوصية عند التجميع والإرسال، راجع [أمان النظام](/tutorials/ops/system-security).

## 9. تجميع السجلات في موضع واحد (اختياري)

التشخيص على جهاز واحد يكفي، لكن مع كثرة الأجهزة أو عند الحاجة إلى «سجلات تبقى ولو سقط الجهاز» يلزم التجميع.

**الطريقة A: تحويل rsyslog** (منظومة syslog التقليدية، مباشرة وبسيطة)

```conf
# /etc/rsyslog.d/50-forward.conf
# @@ يعني TCP و@ يعني UDP؛ استخدم TCP في الإنتاج
*.* @@10.0.0.5:514
```

وعلى جهة الاستقبال يجب تشغيل rsyslog أيضًا (مع السماح باتصالات ذلك المضيف). والسجلات تحوي أسماء لاعبين وعناوين IP وربما محتوى دردشة، **فلا تُحوَّل إلا داخل شبكة موثوقة، أو مع TLS/RELP**.

**الطريقة B: تحويل journald** (منظومة systemd)

```ini
# /etc/systemd/journald.conf
[Journal]
ForwardToSyslog=yes
ForwardToSocket=10.0.0.5:4444
```

وتستقبل جهة الاستقبال بـ `systemd-journal-remote`. وانتبه إلى تنبيه التوثيق الرسمي: **التحويل يتم تزامنيًا**، فبطء جهة الاستقبال يُبطئ journald ثم يُبطئ الخدمة الكاتبة للسجل — فتوخَّ الحذر مع `ForwardToConsole=` في الإنتاج، وقيّم `ForwardToSocket=` بالطريقة نفسها.

**الطريقة C: نقل دوري** (الأقل عناءً والأقل عرضةً للمشكلات)

زامن `logs/` و`crash-reports/` يوميًا بـ `rsync` / `rclone` إلى جهاز آخر أو إلى تخزين كائنات، واحتفظ بعدة أيام. وهي ليست لحظية، لكنها لا تحتاج خدمة مقيمة ولا تؤثر في أداء الخادم، والطريقة في [النسخ خارج الموقع](/tutorials/ops/offsite-backup).

## 10. البحث الفعّال في السجلات

السجلات تبلغ عدة GB، واستراتيجية البحث أهم من الأمر نفسه: **ضيِّق النطاق بالوقت أو باسم الملف أولًا، ثم طابق النص.**

| الهدف | الأمر |
| --- | --- |
| متابعة السجل الحالي لحظيًا | `tail -f logs/latest.log` |
| عرض آخر 200 سطر | `tail -n 200 logs/latest.log` |
| إيجاد الاستثناءات مع أرقام الأسطر | `grep -n "Exception" logs/latest.log` |
| إحصاء مرات الظهور | `grep -c "OutOfMemoryError" logs/latest.log` |
| البحث في سجل مضغوط | `zgrep -n "Exception" logs/2026-10-01-1.log.gz` |
| البحث في كل السجلات التاريخية | `zgrep -c "Exception" logs/*.log.gz` |
| استعلام سجل وحدة بمدى زمني | `journalctl -u minecraft.service --since "2026-10-01" --until "2026-10-02"` |
| عرض التحذيرات وما فوق فقط | `journalctl -u minecraft.service -p warning -n 100 --no-pager` |
| متابعة الوحدة لحظيًا | `journalctl -u minecraft.service -f` |
| تصفية المحتوى (systemd 237+) | `journalctl -u minecraft.service -g "Exception" --since today` |
| سجل الإقلاع السابق | `journalctl -b -1` |

وبعض العادات العملية:

- **لا تنفّذ `grep` مباشرةً على `latest.log` بحجم 5 GB**: ابدأ بـ `tail -n 5000` أو اختر `*.log.gz` بحسب التاريخ، فالفرق في السرعة بمقدار رتبة.
- `zgrep` يقرأ `.gz` مباشرةً، فلا تفكّ الضغط بـ `gunzip` أولًا — فالملف المفكوك يشغل مساحة إضافية، وهو خطر خصوصًا حين يكون القرص على وشك الامتلاء.
- استخدم `journalctl -o short-iso` ليكون الطابع الزمني مع المنطقة الزمنية، فلا تخطئ في المقارنة بين الأجهزة.
- بعد تحديد غمر ملحق ما، **عالج السبب الجذري أولًا** (أوقف التنقيح، أو رقِّ الملحق، أو عطّله مؤقتًا)، ثم نظّف السجل، وإلا عاد ونما من جديد.

## 11. سكربت التنظيف والمهام المجدولة

logrotate يتولّى «التدوير»، ويبقى سكربت يعالج ما لا يتولّاه: ملفات `.log.gz` التي دوّرتها النواة نفسها، وتقارير الانهيار المتراكمة، والتنبيه على الحجم.

```bash
#!/usr/bin/env bash
# /usr/local/bin/mc-log-cleanup.sh
set -euo pipefail

SERVER_DIR="/opt/minecraft/server"
LOG_DIR="$SERVER_DIR/logs"
CRASH_DIR="$SERVER_DIR/crash-reports"

# 1) حذف السجلات المضغوطة التي دوّرتها النواة وتجاوزت 30 يومًا
find "$LOG_DIR" -type f -name '*.log.gz' -mtime +30 -delete

# 2) الاحتفاظ بأحدث 20 تقرير انهيار فقط
if [ -d "$CRASH_DIR" ]; then
    ls -1t "$CRASH_DIR"/crash-*.txt 2>/dev/null | tail -n +21 | xargs -r rm -f
fi

# 3) سرد السجلات التي ما زالت تتجاوز 100 MB ليراجعها إنسان
find "$SERVER_DIR" -type f -name '*.log*' -size +100M -exec ls -lh {} +
```

```bash
chmod +x /usr/local/bin/mc-log-cleanup.sh
```

**الجدولة بـ cron (يوميًا 04:15):**

```bash
# crontab -e  (أو استخدم /etc/cron.d/mc-log-cleanup، ولاحظ أن الأخير يحتاج كتابة اسم المستخدم)
15 4 * * * /usr/local/bin/mc-log-cleanup.sh >> /var/log/mc-log-cleanup.log 2>&1
```

**الجدولة بمؤقّت systemd (موصى بها: لها سجل، وحالتها مرئية، والتنفيذات الفائتة تُعوَّض):**

```ini
# /etc/systemd/system/mc-log-cleanup.service
[Unit]
Description=Clean up Minecraft server logs

[Service]
Type=oneshot
User=minecraft
Group=minecraft
ExecStart=/usr/local/bin/mc-log-cleanup.sh
```

```ini
# /etc/systemd/system/mc-log-cleanup.timer
[Unit]
Description=Run Minecraft log cleanup daily

[Timer]
OnCalendar=*-*-* 04:15:00
Persistent=true
RandomizedDelaySec=10m

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now mc-log-cleanup.timer
systemctl list-timers mc-log-cleanup.timer
journalctl -u mc-log-cleanup.service -n 50 --no-pager
```

:::tip سكربت التنظيف «يحذف ما ولّده أولًا، ثم ينبّه»
لا تبدأ السكربت بـ `rm -rf logs/*`: فذلك يحذف الدليل معه. والترتيب الصحيح: **حذف الأرشيفات بالعمر ← ضبط عدد تقارير الانهيار ← الإبلاغ عن الملفات الشاذة الحجم أو الشاذة الحداثة**. والذي يحتاج نظرة بشرية فعلًا هو «نما السجل 3 GB اليوم» بذاته.
:::

## 12. قائمة الصيانة

| التكرار | الإجراء | الأمر / الموضع |
| --- | --- | --- |
| يوميًا (تلقائيًا) | تدوير سجلات الخادم والملحقات بـ logrotate | `logrotate.timer`، والإعداد في `/etc/logrotate.d/minecraft` |
| يوميًا (تلقائيًا) | سكربت التنظيف يحذف الأرشيفات القديمة ويضبط عدد تقارير الانهيار | `mc-log-cleanup.timer` |
| أسبوعيًا | فحص مستوى القرص والـ inode | `df -h` و`df -i` |
| أسبوعيًا | فحص استهلاك journal وأكبر ملفات السجل | `journalctl --disk-usage` و`find ... -size +100M` |
| أسبوعيًا | فحص تكاثر تقارير الانهيار (قد يكون حلقة انهيار) | `ls -1t crash-reports/ \| head` |
| شهريًا | مراجعة إعداد logrotate وعدد النسخ وهل ما زال مناسبًا | `logrotate -d /etc/logrotate.d/minecraft` |
| شهريًا | التأكد من وصول بيانات جديدة فعلًا إلى السجلات المجمّعة/خارج الموقع | وقت تعديل دليل الاستقبال أو تخزين الكائنات |
| بعد كل تغيير | تشغيل تجريبي بعد تغيير مسار أو مستخدم أو اسم وحدة | `sudo logrotate -d` |
| بعد الحادث | أرشفة المسرح قبل التنظيف | انسخ `latest.log` و`crash-reports/` المعنيين ثم ابدأ |
