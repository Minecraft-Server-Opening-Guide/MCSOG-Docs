النسخ الاحتياطي المحلي ينقذ من «حذف الأرشيف بخطأ يد»، ولا ينقذ من «تلف القرص» أو «سرقة الجهاز» أو «حادث في مركز البيانات». **والنسخ الاحتياطي خارج الموقع (offsite backup) هو حلّ هذا النوع من الكوارث التي «تُفني البيئة كلها معًا»**. توضّح هذه المقالة مبدؤه وإعداده وصيانته.

وأساسيات النسخ المحلي (ما يُنسخ، ومتطلبات الاتساق، وعملية الاستعادة) في [النسخ الاحتياطي والاستعادة](/tutorials/java/backup)؛ وتفترض هذه المقالة أن لديك نسخًا محليًا بالفعل، وأنك تريد الآن إرسال نسخة إلى الخارج.

## 1. قاعدة 3-2-1

3-2-1 قاعدة تجريبية للنسخ الاحتياطي واسعة الاستشهاد:

| الرقم | المعنى | تطبيقه على خادم MC |
| --- | --- | --- |
| **3** | الاحتفاظ بـ**3 نسخ** من البيانات على الأقل (1 إنتاج + 2 نسخ احتياطية) | دليل الخادم العامل + قرص النسخ المحلي + نسخة خارج الموقع |
| **2** | استخدام **وسيطين/تخزينين مختلفين** على الأقل | مثلًا SSD داخلي + قرص خارجي + تخزين كائني |
| **1** | **نسخة واحدة خارج الموقع** على الأقل | تخزين سحابي، أو جهاز آخر، أو موقع فيزيائي آخر |

### لماذا «النسخة على القرص نفسه» لا تُعدّ نسخة

كتابة النسخة على **القرص نفسه الذي عليه الخادم** تصدّ عطلًا واحدًا فقط: الحذف الخاطئ، أو خطأ الإعداد، أو إفساد الملحق للأرشيف. ولا تصدّ **تلف القرص نفسه** (فتذهب النسخة معه)، ولا **عطل الجهاز** (احتراق اللوحة أو المزوّد، فيذهبان القرصان معًا)، ولا **برامج الفدية** (تشفّر كل وحدة تخزين قابلة للكتابة تراها)، ولا **التخريب البشري** (أمر `rm -rf` للدليل كله، أو سرقة الجهاز)، ولا **الحريق والغرق والسرقة**.

### ثلاث سيناريوهات كوارث نمطية

| السيناريو | هل يكفي النسخ المحلي | دور النسخ خارج الموقع |
| --- | --- | --- |
| تلف القرص / إتلاف الجهاز | لا يكفي (إن كانت النسخة على القرص نفسه) | الاستعادة مباشرةً من نسخة خارج الموقع |
| تشفير برامج الفدية لكل وحدات التخزين القابلة للكتابة | **لا يكفي** | النسخة للقراءة فقط أو غير القابلة للتغيير هي المخرج الوحيد |
| هروب المزوّد / حادث مركز البيانات / سرقة الحساب | **لا يكفي** | النسخة على تخزينك أنت |

:::warn النسخة خارج الموقع يجب أن «يكتبها برنامج النسخ ولا يستطيع المهاجم حذفها»
إن كان التخزين خارج الموقع يستخدم بيانات الاعتماد نفسها والحساب القابل للكتابة نفسه، فبرامج الفدية تستطيع حذفها أيضًا. **فإن أمكن جعلها للقراءة فقط/غير قابلة للتغيير (object lock، WORM، append-only) فافعل**؛ وعلى الأقل امنح حساب النسخ صلاحية الكتابة دون صلاحية الحذف.
:::

## 2. ما يُنسخ وما لا يُنسخ

| الضرورة | المحتوى | ملاحظة |
| --- | --- | --- |
| واجب | `world/`، و`world_nether/`، و`world_the_end/` | **جسم الأرشيف، وهو الأهم**؛ وأسماء العوالم المخصّصة بحسب `level-name` |
| واجب | `server.properties` | المنفذ والصعوبة والتحقق الأصلي و`level-name` وغيرها |
| واجب | `ops.json`، و`whitelist.json`، و`banned-ips.json`، و`banned-players.json` | الصلاحيات وقوائم الحجب |
| واجب | `plugins/` (مع إعداد كل ملحق وقواعد بياناته) | جسم الملحقات وإعدادها؛ ولاحظ أن بعض الملحقات تكتب بياناتها في مكان آخر |
| واجب | `mods/`، و`config/` (جهة المودات) | خاصّ بجهة المودات؛ و`config/` فيه إعداد المودات |
| واجب | إعداد النواة نفسه (`bukkit.yml` / `spigot.yml` / `paper-*.yml` وغيرها) | يختلف بحسب النواة |
| واجب | سكربت التشغيل، ووحدة systemd، وبنود cron | **يسهل إغفالها**، وبدونها لا يقوم الخادم عند الاستعادة |
| اختياري | `logs/`، و`crash-reports/` | مفيدة في التشخيص، لكن حجمها قد يكبر |
| غير لازم | `libraries/`، و`versions/`، و`cache/` | تُعاد بناؤها تلقائيًا |

:::tip اعتبر «طريقة التشغيل» بيانات تُنسخ أيضًا
«استُعيد الأرشيف لكن الخدمة لا تقوم» حادث شائع، والسبب أن سكربت التشغيل ووسائط Java ووحدة systemd والمهام المجدولة لم تُنسخ. **فأدرجها في نطاق النسخ مع الإعداد.**
:::

### الاتساق: لا تنسخ أبدًا والخادم يكتب على القرص

**لا تنسخ مباشرةً والخادم يكتب الأرشيف** — فقد تنسخ ملف منطقة نصف مكتوب، فيتلف الأرشيف بعد الاستعادة. وطريقتان صحيحتان:

**الطريقة A: نسخ ساخن (بلا إيقاف)**

```text
save-all        ادفع البيانات إلى القرص أولًا
save-off        أوقف الحفظ التلقائي (تجنّبًا للكتابة أثناء النسخ)
(نفّذ النسخ/الضغط الآن)
save-on         أعِد الحفظ التلقائي بعد النسخ
```

**الطريقة B: نسخ مع إيقاف الخادم (الأثبت)**

```text
stop            أوقف الخادم بأمان
(انسخ/اضغط الدليل كله)
(أعد التشغيل)
```

والطريقة A تحتاج **إرسال أوامر إلى وحدة تحكّم الخادم**. فإن كان الخادم مُدارًا بـ systemd وكانت طريقة التشغيل تستقبل إدخال وحدة التحكّم، فيمكن الحقن بـ`screen`/`tmux`، أو تفعيل RCON وإرسال الأوامر عن بُعد (**وطريقة إعداد RCON تختلف بحسب النواة والنسخة، فاعتمد التوثيق الرسمي**).

:::warn أداة الضغط تقرأ والخادم ما زال يكتب
`tar` و`rsync` و`restic` كلها **تقرأ وتجول** في الوقت نفسه. وحتى لو نفّذت `save-all` للتوّ، فبدون `save-off` سيظلّ الخادم يكتب بيانات جديدة أثناء الجولة، **وقد تظهر في الأرشيف تركيبة غير متسقة**. وخطوة `save-off` لا تُختصر.
:::

## 3. rsync عبر SSH

`rsync` هو الحل الكلاسيكي للمزامنة التزايدية خارج الموقع: ينقل المتغيّر فقط، ويمرّ بقناة SSH مشفّرة، ويمكن تثبيته على كل توزيعات Linux تقريبًا.

### أمر نموذجي كامل

```bash
rsync -aHAX --delete --numeric-ids --info=progress2 \
  --exclude='logs/' \
  --exclude='crash-reports/' \
  --exclude='cache/' \
  --exclude='libraries/' \
  --exclude='versions/' \
  --exclude='*.tar.gz' \
  --link-dest=/srv/backup/mcserver/2026-10-03 \
  /opt/mcserver/ \
  backup@backup.example.com:/srv/backup/mcserver/2026-10-04/
```

### شرح بندًا بندًا

| الخيار | الدور |
| --- | --- |
| `-a` | وضع الأرشيف، ويعادل `-rlptgoD` (تكراري، مع الحفاظ على الروابط الرمزية والصلاحيات والوقت والمجموعة وملفات الأجهزة) |
| `-H` | الحفاظ على الروابط الصلبة (**وإن وُجدت روابط صلبة في دليل الخادم، فبدونه تُفكّ إلى نسخ متعددة**) |
| `-A` | الحفاظ على ACL (قوائم التحكّم في الوصول) |
| `-X` | الحفاظ على السمات الموسّعة (xattr) |
| `--delete` | حذف ملفات «لم تبقَ في المصدر» من الجهة الهدف، لجعل الهدف مطابقًا للمصدر. **وهو سلاح ذو حدّين**: فالحذف الخاطئ في المصدر يُزامَن |
| `--numeric-ids` | التعيين بأرقام UID/GID لا بأسماء المستخدمين/المجموعات. **واجب** عند تغيير الجهاز أو غياب مستخدم مماثل على الهدف |
| `--info=progress2` | إظهار التقدّم الكلي (rsync 3.1 فأحدث) |
| `--exclude` | استثناء الأدلة غير اللازمة للنسخ |
| `--link-dest=DIR` | **لقطة بالروابط الصلبة**: فالملفات المطابقة لمحتوى DIR لا تُنسخ، بل تُنشأ لها روابط صلبة في الهدف، فتبدو كل لقطة بتاريخ كامل نسخة كاملة، بينما تشغل مساحة تزايدية فقط |

:::warn `-A` و`-X` يحتاجان دعمًا على الطرفين
الحفاظ على ACL وxattr يحتاج نسخة rsync حديثة، ونظام ملفات هدف يدعم هذه السمات، و**يحتاج عادةً التشغيل بـ root** لقراءة ACL/xattr لكل الملفات. وإن لم يدعم نظام الملفات الهدف ذلك (مثل بعض التخزينات الشبكية) أظهر rsync خطأً أو أسقطها بصمت. **فإن لم تكن متأكدًا فاحذف `-A -X` أولًا**.
:::

### جرّب أولًا بـ dry-run

**أي أمر فيه `--delete` يجب تشغيله أولًا مع `-n` (`--dry-run`)**:

```bash
rsync -aHAX --delete --numeric-ids -n -i \
  --exclude='logs/' --exclude='cache/' \
  /opt/mcserver/ backup@backup.example.com:/srv/backup/mcserver/
```

`-n` (`--dry-run`) يعرض ما سيُفعل دون تعديل فعلي، و`-i` (`--itemize-changes`) يسرد التغييرات بندًا بندًا، لتتأكد مما سيحذفه `--delete`. **فإن لم تجد في المخرجات «ما يُحذف بغير قصد» فأزل `-n`.**

### تسجيل الدخول بلا كلمة مرور عبر SSH

سكربت النسخ يجب أن يعمل بلا إشراف، لذا استخدم الدخول بالمفاتيح:

```bash
ssh-keygen -t ed25519 -C "mc-backup@home"
ssh-copy-id backup@backup.example.com
ssh backup@backup.example.com 'echo ok'
```

`ssh-keygen -t ed25519` يولّد زوج مفاتيح Ed25519، ويُوضع افتراضيًا في `~/.ssh/id_ed25519` (الخاص) و`~/.ssh/id_ed25519.pub` (العام). **ووضع عبارة مرور للمفتاح الخاص أكثر أمانًا، لكن المهام المجدولة تحتاج ssh-agent أو `keychain` لتجنّب التفاعل؛ وأجهزة النسخ بلا إشراف لا تضع عبارة مرور عادةً، ولذلك يجب تقييد صلاحياتها بصرامة.** و`ssh-copy-id` يضيف المفتاح العام إلى `~/.ssh/authorized_keys` على الجهاز الهدف؛ **وبعض المنصّات (مثل OpenSSH على Windows أو أنظمة مختصرة) قد لا تملك هذا الأمر**، فأضف محتوى المفتاح يدويًا. ويُنصح بتقييد هذا المفتاح في `authorized_keys` على الجهاز الهدف:

```text
from="203.0.113.10",command="/usr/bin/rrsync -wo /srv/backup/mcserver/",no-port-forwarding,no-pty ssh-ed25519 AAAA... mc-backup@home
```

`rrsync` سكربت تغليف مقيَّد مرفق مع rsync، لا يسمح إلا بالكتابة في دليل محدّد. **ومسار `rrsync` وتوافره يختلفان بحسب التوزيعة** (في Debian/Ubuntu داخل حزمة `rsync`، والمسار قد يكون `/usr/bin/rrsync`)، فتأكّد قبل الاستخدام.

### مثال cron

```cron
0 4 * * * /usr/local/bin/mc-backup.sh >> /var/log/mc-backup.log 2>&1
```

الحقول الخمسة هي: الدقيقة، والساعة، واليوم، والشهر، ويوم الأسبوع، فـ`0 4 * * *` تعني **كل يوم 04:00**؛ و`>> /var/log/mc-backup.log 2>&1` يضيف المخرجات القياسية والأخطاء إلى السجل، تسهيلًا لفحص رمز الخروج والأخطاء لاحقًا. **ومتغيّرات بيئة cron قليلة جدًا (`PATH` قصير)، فيجب استخدام مسارات مطلقة في السكربت**؛ وإن احتجت تدوير السجلات فأضف قاعدة في `/etc/logrotate.d/`، وإلا نما السجل بلا حدّ.

## 4. هيكل سكربت النسخ

فيما يلي **هيكل bash جاهز للاستخدام**: يجمّد الكتابة أولًا، ويضغط العالم والإعداد، وينظّف الأرشيفات المنتهية، ثم يزامن خارج الموقع، ويكتب النتيجة في السجل.

```bash
#!/usr/bin/env bash
# هيكل سكربت نسخ احتياطي خارج الموقع. عدّل المتغيّرات بحسب بيئتك.
set -euo pipefail

SERVER_DIR="/opt/mcserver"                 # دليل الخادم (بلا شرطة في النهاية)
BACKUP_ROOT="/srv/backup/mcserver"         # جذر النسخ المحلي (يُفضّل أن يكون على قرص مختلف عن SERVER_DIR)
LOG_FILE="/var/log/mc-backup.log"
KEEP_DAYS=14                               # عدد أيام الاحتفاظ بالأرشيفات المحلية
REMOTE="backup@backup.example.com:/srv/backup/mcserver"   # الهدف خارج الموقع

STAMP="$(date +%F_%H%M%S)"
ARCHIVE="${BACKUP_ROOT}/mcserver-${STAMP}.tar.gz"

log() { printf '%s %s\n' "$(date '+%F %T')" "$*"; }
fail() { log "ERROR: $*"; exit 1; }

# مخرجات السكربت نفسه تُكتب في السجل أيضًا، وإعادة التوجيه في cron احتياط إضافي فقط
exec >>"${LOG_FILE}" 2>&1
log "=== backup start ${STAMP} ==="

[ -d "${SERVER_DIR}" ] || fail "server directory not found: ${SERVER_DIR}"
mkdir -p "${BACKUP_ROOT}"

# النسخ مع إيقاف الخادم هو الأثبت. وإن تعذّر الإيقاف، غيّره إلى إرسال save-all / save-off إلى وحدة التحكّم، ثم save-on بعد الضغط
START_AFTER=0
if systemctl is-active --quiet minecraft.service; then
    log "stopping minecraft.service for a consistent backup"
    systemctl stop minecraft.service
    START_AFTER=1
fi

tar -czf "${ARCHIVE}" \
    --exclude='logs' \
    --exclude='crash-reports' \
    --exclude='cache' \
    --exclude='libraries' \
    --exclude='versions' \
    --exclude='*.tar.gz' \
    -C "${SERVER_DIR}" .

[ -s "${ARCHIVE}" ] || fail "archive is missing or empty: ${ARCHIVE}"
log "archive created: ${ARCHIVE} ($(du -h "${ARCHIVE}" | cut -f1))"

# أبقِ الأرشيفات المحلية خلال KEEP_DAYS يومًا واحذف الباقي (يُنصح بإزالة -delete في أول تشغيل للتحقق من النطاق)
find "${BACKUP_ROOT}" -maxdepth 1 -name 'mcserver-*.tar.gz' -type f -mtime "+${KEEP_DAYS}" -print -delete

# المزامنة إلى خارج الموقع. تعمّدنا عدم استخدام --delete، تجنّبًا لمزامنة حذف محلي خاطئ
rsync -aHAX --numeric-ids --info=progress2 "${BACKUP_ROOT}/" "${REMOTE}/"
log "offsite sync finished"

if [ "${START_AFTER}" -eq 1 ]; then
    log "starting minecraft.service again"
    systemctl start minecraft.service
fi

log "=== backup ok ${STAMP} ==="
exit 0
```

### تعليمات الاستخدام

```bash
sudo install -m 750 mc-backup.sh /usr/local/bin/mc-backup.sh
sudo /usr/local/bin/mc-backup.sh
tail -20 /var/log/mc-backup.log
```

وأمور يجب معرفتها:

- `set -euo pipefail` يجعل السكربت **يتوقّف فورًا عند أي خطأ**، تجنّبًا لـ«فشل النسخ واستمرّ السكربت وأبلغ بالنجاح في النهاية».
- **النسخ مع إيقاف الخادم هو الأثبت**؛ وإن تعذّر الإيقاف فاستبدل `systemctl stop` بإرسال `save-all` / `save-off` إلى وحدة التحكّم، ثم `save-on` بعد الضغط (انظر القسم 2).
- `find ... -mtime "+${KEEP_DAYS}" -delete` **يطبع ثم يحذف**، ويُنصح في أول تشغيل بإزالة `-delete` للتأكد من صحة الملفات المطابقة.
- **استخدم المزامنة خارج الموقع بالإضافة لا `--delete`**، وإلا اختفت النسخة خارج الموقع عند حذف الأرشيف المحلي خطأً. وإن أردت فعلًا مزامنة مرآتية فتأكّد من موثوقية منطق الحذف المحلي تمامًا.
- اسم وحدة `systemctl` ومسارات استثناء `tar` تُعدّل بحسب أدلتك الفعلية؛ **و`--exclude` في `tar` يطابق مسارًا داخل الأرشيف، وصيغته ليست مطابقة تمامًا لـ rsync**. وإن احتجت احتفاظًا بنمط GFS (يومي/أسبوعي/شهري)، فاستخدام `forget --keep-*` في restic أسهل من كتابة `find` يدويًا.

:::warn `--delete` في السكربت يجب أن يُفكَّر فيه بوضوح
`rsync --delete` يجعل الهدف مطابقًا للمصدر تمامًا. **فإن صار المصدر دليلًا فارغًا بسبب صلاحيات أو فشل تركيب أو مسار خاطئ، فسيُفرّغ `--delete` النسخة خارج الموقع أيضًا.** وهذا سبب كلاسيكي لحوادث النسخ.
:::

## 5. أدوات أخرى والاختيار

### restic: إزالة التكرار والتشفير واللقطات

restic أداة نسخ بنمط اللقطات، **وفيها إزالة تكرار وتشفير مدمجان**، وتصلح لحالة «تريد الاحتفاظ بنسخ تاريخية كثيرة دون استهلاك مساحة كبيرة».

```bash
# 1. تهيئة المستودع (مرة واحدة فقط)
export RESTIC_REPOSITORY="sftp:backup@backup.example.com:/srv/restic/mcserver"
export RESTIC_PASSWORD_FILE="/root/.config/restic/mcserver.pass"
restic init

# 2. النسخ
restic -r "${RESTIC_REPOSITORY}" backup /opt/mcserver

# 3. عرض اللقطات
restic snapshots

# 4. سياسة الاحتفاظ: 7 لقطات يومية و4 أسبوعية، ثم نظّف البيانات غير المشار إليها
restic forget --keep-daily 7 --keep-weekly 4 --prune
```

`RESTIC_PASSWORD_FILE` يشير إلى **ملف كلمة مرور بصلاحية `chmod 600`**، ولا تكتبه في السكربت. و`restic forget` يحذف مراجع اللقطات فقط، **ولا تُسترد المساحة فعلًا إلا بـ`--prune`**، و`--prune` يستغرق وقتًا طويلًا، ويُنصح بجدولته في نافذة الصيانة. والاستعادة بـ`restic restore latest --target /tmp/restore-test`. ويمكن وضع المستودع على دليل محلي أو SFTP أو تخزين متوافق مع S3 وغيرها من الخلفيات (**وقائمة الخلفيات المدعومة بحسب التوثيق الرسمي**).

### rclone: مزامنة التخزين السحابي

rclone هو «rsync التخزين السحابي»، ويدعم عددًا كبيرًا من خلفيات التخزين الكائني والأقراص السحابية.

```bash
# 1. إعداد طرف بعيد تفاعليًا، باسم مثلًا myremote
rclone config

# 2. مزامنة دليل محلي إلى الطرف البعيد (سيحذف الملفات الزائدة هناك، فانتبه للاتجاه والدلالة)
rclone sync /srv/backup/mcserver myremote:mcserver-backup --progress

# 3. تحقّق من تطابق الطرفين
rclone check /srv/backup/mcserver myremote:mcserver-backup
```

`rclone sync` يجعل الهدف **مطابقًا تمامًا** للمصدر، ويحذف الملفات الزائدة في الهدف؛ وإن أردت بالإضافة فقط فاستخدم `rclone copy`. و`rclone check` يقارن ملفات الطرفين (يقارن الحجم والبصمة افتراضيًا، **ودعم البصمة يتوقّف على الخلفية**). و`rclone config` تفاعلي، ويمكن في بيئة بلا واجهة كتابة ملف الإعداد يدويًا (`rclone config file` يعرض المسار)؛ والبيانات السرية تُحفظ في ذلك الملف، **فتشدّد صلاحياته إلى `chmod 600`**.

### tar + scp فقط

أبسط تركيبة، بلا أي تبعية إضافية:

```bash
tar -czf /tmp/mcserver-$(date +%F).tar.gz -C /opt/mcserver .
scp /tmp/mcserver-$(date +%F).tar.gz backup@backup.example.com:/srv/backup/
```

تصلح لحالة **حجم بيانات صغير وتكرار نسخ منخفض**. وعيوبها: **نقل كامل في كل مرة، وبلا إزالة تكرار، وبلا تشفير (عدا قناة SSH)، وبلا تحقّق**، فلا تصلح عند كبر البيانات.

### مقارنة

| الأداة | إزالة التكرار | التشفير | تزايدي | دعم السحابة | التعقيد | تصلح لـ |
| --- | --- | --- | --- | --- | --- | --- |
| **rsync** | لا (يوفّر المساحة بـ`--link-dest`) | لا (يعتمد على قناة SSH) | نعم (ملفًا ملفًا) | يحتاج تركيبًا أو أدوات أخرى | منخفض | وجود هدف SSH وأدلة بسيطة البنية |
| **restic** | **نعم** | **نعم (مدمج)** | نعم (كتلةً كتلة) | خلفيات متعددة (S3، وSFTP وغيرها) | متوسط | الاحتفاظ بنسخ تاريخية كثيرة والحاجة إلى تشفير |
| **rclone** | لا | تشفير النقل بحسب الخلفية | نعم (ملفًا ملفًا) | **الأوسع** | متوسط | الهدف قرص سحابي/تخزين كائني |
| **tar + scp** | لا | لا | لا (كامل) | يحتاج هدفًا يقبل scp | **الأدنى** | حجم بيانات صغير ونسخ متقطّع |

## 6. التشفير وإدارة المفاتيح

**النسخة خارج الموقع يجب أن تكون مشفّرة.** فوضع النسخة على تخزين غيرك يعني تسليم البيانات لطرف ثالث؛ وتسريب مفاتيح التخزين الكائني، أو خطأ في رابط مشترك، أو سرقة حساب سحابي، كلها تكشف الأرشيف مباشرةً (وفيه غالبًا عناوين IP لاعبين وسجلات دردشة ومعلومات قد تكون خاصة).

- **restic فيه تشفير مدمج**: يستمدّ المستودع مفتاحه من كلمة المرور، **وضياع كلمة المرور يعني تعذّر فتح البيانات نهائيًا**؛ **وrsync / rclone / tar+scp لا تشفّر المحتوى بنفسها**، فإما تعتمد على طبقة النقل (SSH، وHTTPS)، أو تشفّر أنت أولًا:

```bash
# شفّر أرشيفًا تشفيرًا متماثلًا بـ gpg (سيطلب كلمة المرور تفاعليًا)
gpg --symmetric --cipher-algo AES256 mcserver-2026-10-04.tar.gz

# فكّ التشفير
gpg --decrypt mcserver-2026-10-04.tar.gz.gpg > mcserver-2026-10-04.tar.gz
```

### أين توضع كلمة المرور

**لا تضعها أبدًا في مستودع النسخ/التخزين الهدف نفسه**، و**لا تضعها في دليل قابل للكتابة مع سكربت النسخ**. والتصرف المقبول أن **تُسجَّل في مدير كلمات مرور** (ليقرأها الإنسان)، و**تُوضع في ملف بصلاحيات صارمة على جهاز النسخ** (ليقرأه السكربت):

```bash
sudo install -d -m 700 -o root -g root /root/.config/restic
sudo sh -c 'printf "%s" "كلمة-المرور-الخاصة-بك" > /root/.config/restic/mcserver.pass'
sudo chmod 600 /root/.config/restic/mcserver.pass
sudo chown root:root /root/.config/restic/mcserver.pass
```

**ويجب أن تكون لكلمة المرور نسخة مسجّلة بلا اتصال** (مكتوبة على ورق محفوظ في مكان مغلق، أو في مدير كلمات مرور على جهاز آخر). **فنسخة مشفّرة + كلمة مرور ضائعة = ضياع كل البيانات**، وهو أشدّ اكتمالًا من عدم التشفير. وملفات المفاتيح (المفتاح الخاص SSH، وإعداد rclone) كذلك بصلاحية `chmod 600`، و**بحساب مخصّص للنسخ بأدنى صلاحية**.

:::warn التشفير ليس «ضبط كلمة مرور وانتهى»
قوة كلمة المرور وحفظها وتدوير المفاتيح كلها يجب أن تُراعى. **وكلمة مرور ضعيفة مكتوبة في السكربت أمانها صفر تقريبًا.** وأيضًا: **تنخفض نسبة الضغط بعد التشفير** (فالنص المشفّر غير قابل للضغط)، فاضغط ثم شفّر.
:::

## 7. أهداف السحابة والتخزين الكائني

| النوع | أمثلة | السمات |
| --- | --- | --- |
| جهاز آخر / NAS | NAS في بيت صديق، أو VPS ثانٍ | رخيص وقابل للتحكّم، لكنه يحتاج صيانة بنفسك |
| تخزين كائني متوافق مع S3 | خدمات متوافقة مع S3، أو MinIO ذاتيًا | API معياري، وrestic/rclone يدعمانه مباشرةً |
| تخزين بارد / أرشيفي | درجات «الأرشيف» و«البارد» عند المزوّدين | **سعر الوحدة منخفض جدًا، والاسترجاع بطيء وقد يُفوتر بحسب الكمية المسترجعة** |
| أقراص سحابية | خلفيات الأقراص التي يدعمها rclone | رخيصة أو مجانية، لكن **بتحديد سرعة، وقد يُحجب الحساب، ولا تصلح نسخة وحيدة** |

### مزالق التكلفة التي يجب الانتباه إليها

- **رسم ترافيك الخروج (egress)**: كثير من خدمات التخزين الكائني **ترفع مجانًا وتنزّل برسم**. فاستعادة نسخة بمئات الجيجابايت قد تكلّف أكثر من سنة تخزين. **فانظر في صفحة التسعير إلى سعر الاسترجاع والخروج قبل الشراء.**
- **رسم الطلبات**: الخلفيات التي تُفوتر بعدد الطلبات ترتفع كلفتها عند كثرة الملفات الصغيرة.
- **أدنى مدة تخزين**: بعض درجات الأرشيف تطلب تخزينًا لا يقلّ عن 30/90/180 يومًا، والحذف المبكر يُفوتر للمدة كاملة.
- **تأخير الاسترجاع**: قد تحتاج استعادة درجة الأرشيف ساعات، **فلا تصلح لـ«استعادة فورية عند الحادث»**، ويُنصح بالاحتفاظ بنسخة واحدة على الأقل «قابلة للاستعادة فورًا».

### دورة الحياة وقواعد الاحتفاظ

خدمات التخزين الكائني تدعم عادةً **قواعد دورة الحياة (lifecycle rule)**، لنقل العناصر الأقدم من N يومًا **إلى درجة تخزين أرخص**، أو **حذفها تلقائيًا** بعد N يومًا لتنفيذ سياسة الاحتفاظ، وتنظيف بقايا الرفع المجزّأ غير المكتمل (multipart upload) — **وهذا الأخير مصدر شائع للتكاليف الخفية**. **وصيغة القواعد المحدّدة وأسماء الدرجات المدعومة وأدنى المدد تختلف بين المزوّدين، فاعتمد توثيق كل مزوّد**، ولا تنسخ أمثلة غيرك.

## 8. تصميم سياسة الاحتفاظ

### كم نسخة تُحتفظ

| المستوى | العدد الشائع | الغرض |
| --- | --- | --- |
| يومي | 7 - 14 نسخة | مواجهة «فساد حدث أمس/أول أمس» |
| أسبوعي | 4 - 8 نسخ | مواجهة «مشكلة اكتُشفت بعد أسابيع» |
| شهري / سنوي | 6 - 12 شهريًا و1 - 3 سنويًا | حفظ طويل المدى، ومواجهة التلف البطيء |

والمبدأ: **«أن تغطّي أطول مدة تحتاجها لاكتشاف المشكلة»**. فتلف الأرشيف **لا يُكتشف في اليوم نفسه عادةً**، فيجب أن تبقى مدة كافية.

### تقدير مساحة القرص

بافتراض أن حجم العالم `W`، فبعد الضغط يصبح نحو `0.4W - 0.7W` (**ونسبة الضغط تتوقّف على المحتوى، وضغط ملفات region متوسط، فاعتمد القياس**).

| الطريقة | المساحة المشغولة |
| --- | --- |
| `tar.gz` مستقل في كل مرة، مع الاحتفاظ بـ`N` نسخة | نحو `N x 0.5W` |
| لقطة `--link-dest` بالروابط الصلبة في rsync | نحو `0.5W + مقدار التغيّر x (N-1)`، **ومقدار التغيّر هو المفتاح** |
| لقطة restic بإزالة التكرار | في رتبة اللقطة بالروابط الصلبة أو أقل، بحسب دقّة إزالة التكرار |

مثال: عالم 5 GB، والاحتفاظ بـ14 أرشيفًا مستقلًا، بنسبة ضغط 0.5 يحتاج نحو `14 x 2.5 = 35 GB`؛ وبتحويله إلى لقطة `--link-dest`، فإن تغيّر 100 MB يوميًا يصبح نحو `2.5 GB + 13 x 0.1 GB = 3.8 GB`. **والفارق كبير، ويستحق تغيير الطريقة إلى اللقطات.**

### تنظيف النسخ القديمة بأمان

- **لا تحذف النسخة القديمة قبل التحقق من صلاحية الجديدة أبدًا**. والترتيب دائمًا: **أنشئ الجديدة ← تحقّق من الجديدة ← تأكّد من سلامتها ← ثم نظّف القديمة**.
- **أبقِ نسخة واحدة «الأقدم لكن المعروفة الصلاحية»** (لمواجهة «تلف موجود منذ زمن»)، و**نفّذ التنظيف بـ dry-run أو بطباعة قائمة الملفات** أولًا للتأكد من نطاق المطابقة.
- **التنظيف على جهة خارج الموقع يجب أن يكون أكثر تحفّظًا** من المحلي (نسخ أكثر وحذف مؤجّل)، فالنسخة خارج الموقع هي خط الدفاع الأخير.

:::warn التنظيف التلقائي هو «أتمتة حذف البيانات»
`find ... -delete` أو `--delete` مكتوب خطأً قد يمسح كل التاريخ دفعةً واحدة. **وأي منطق تنظيف يجب تشغيله في دليل اختبار قبل نشره، والتأكد من أنه لن يطابق ملفات لا يجب حذفها.**
:::

## 9. الصيانة

### النسخة التي لم تُستعَد ليست نسخة

هذه القاعدة لا يُبالغ في تأكيدها. **فنجاح سكربت النسخ يوميًا شيء، وقدرة النسخة على الاستعادة فعلًا شيء مختلف تمامًا.** والشائع أن يفشل السكربت أسابيع بسبب صلاحيات أو مسار أو امتلاء قرص دون أن يلاحظ أحد؛ أو أن الأرشيف الناتج فارغ؛ أو أن كلمة مرور التشفير لم تبقَ صحيحة.

### عملية تجربة استعادة ربع سنوية

1. **اختر نسخة**: يُفضّل **نسخة خارج الموقع**، ليتحقّق معها من «هل تلفت أثناء النقل».
2. **استعِد إلى دليل اختبار معزول**، ولا تغطِّ دليل الإنتاج أبدًا:

```bash
mkdir -p /tmp/restore-test
tar -xzf /srv/backup/mcserver/mcserver-2026-10-04_040001.tar.gz -C /tmp/restore-test
ls -la /tmp/restore-test
```

3. **افحص وجود الملفات المهمة وأنها غير فارغة**: `world/level.dat`، و`server.properties`، وإعدادات `plugins/`.
4. **شغّل نسخة اختبار على منفذ مختلف**: انسخ دليل الاختبار، وغيّر المنافذ في `server.properties` إلى قيم أخرى (مثلًا `server-port=25566` و`query.port=25566` و`rcon.port=25567`)، وشغّل وراقب السجل؛ وبعد الدخول افحص المباني المهمة ومحتويات الحاويات وحقائب اللاعبين والصلاحيات، وتأكّد من عدم وجود أخطاء تتعلق بالمناطق أو الأرشيف.
5. **سجّل ثم نظّف**: اكتب تاريخ التجربة ومدتها والمشكلات التي واجهتها (**فهذا دليلك الوحيد على صلاحية النسخة**)، ثم احذف نسخة الاختبار، واحفظ السجل.

:::tip اكتب خطوات الاستعادة في مستند
يوم الحادث ليس وقت دراسة «كيف نستعيد». **اكتب الأوامر في صفحة واحدة مسبقًا**، واتبعها في التجربة، وحدّثها عند اكتشاف مشكلة.
:::

### التحقق من السلامة

| الوسيلة | الأمر | ملاحظة |
| --- | --- | --- |
| فحص مستودع restic | `restic check` | يفحص بنية المستودع والبيانات الوصفية؛ وإضافة `--read-data` **تقرأ كل كتل البيانات**، أبطأ لكنها أشمل |
| سرد محتوى tar | `tar -tzf archive.tar.gz >/dev/null` | يقرأ ويفكّ القائمة، فيكشف **الأرشيف المقطوع أو التالف** |
| مقارنة البصمة | `sha256sum archive.tar.gz` | قارنها بالبصمة المسجّلة وقت النسخ، للتأكد من تطابق المحتوى بعد النقل |
| تحقّق rclone | `rclone check src dst` | يقارن ملفات الطرفين (والقدرة تتوقّف على دعم الخلفية للبصمة) |
| محاولة فكّ | `tar -xzf archive.tar.gz -C /tmp/check` | التحقق الأكثر مباشرة: هل تُفكّ فعلًا |

**ويجب حفظ البصمة منفصلة** (مثلًا ملف `.sha256` مع الأرشيف)، وإلا فـ«التحقق من النسخة ببصمتها نفسها» بلا معنى.

### راقب هل جرى النسخ فعلًا

**انظر رمز الخروج** (عند فشل cron يظهر رمز خروج غير صفري في السجل؛ وسكربت فيه `set -e` يتوقّف عند الخطأ)، و**انظر السجل** (`tail -20 /var/log/mc-backup.log` للتأكد أن السطر الأخير علامة نجاح)، و**انظر الناتج** (طابع الأرشيف الجديد هو اليوم، وحجمه في نطاق معقول، لا صفر ولا صغير بشكل شاذ). والأهم **التنبيه الاستباقي**: اجعل السكربت يرسل بريدًا أو رسالة عند الفشل (`mail`، أو `curl` إلى Webhook وغيرها). **و«لا رسالة» لا تعني «كل شيء سليم»**، والأفضل **مراقبة بنبضة قلب** — يُبلَّغ مرة عند النجاح يوميًا، ويُنبَّه عند غياب التبليغ.

### أسباب الفشل الشائعة

| الظاهرة | السبب الشائع | اتجاه التشخيص |
| --- | --- | --- |
| امتلاء القرص / أرشيف 0 بايت | امتلاء قرص النسخ المحلي، أو عدم سريان سياسة الاحتفاظ | `df -h`، وافحص منطق التنظيف |
| فشل مصادقة SSH | تبديل المفتاح، أو خطأ صلاحيات `authorized_keys`، أو قفل الحساب | شغّل يدويًا `ssh backup@host 'echo ok'` |
| إنذار تغيّر مفتاح المضيف | إعادة تثبيت الجهاز الهدف أو إعادة استخدام الـ IP، فقدم سجل `known_hosts` | **تأكّد من هوية الطرف أولًا**، ثم حدّث `known_hosts` |
| خطأ صلاحيات (Permission denied) | حساب النسخ لا يقرأ ملفات المصدر، أو الدليل الهدف غير قابل للكتابة | افحص صلاحيات الأدلة ومالكها، واستخدم root عند الحاجة |
| انتهاء بيانات الاعتماد / خطأ كلمة مرور التشفير | انتهاء مفتاح التخزين السحابي؛ أو تدوير كلمة المرور دون تحديث السكربت | حدّث المفتاح، وتحقّق يدويًا بـ`restic snapshots` |
| محتوى الأرشيف ناقص | نسيان `save-off`، أو `--exclude` خاطئ استثنى دليلًا مهمًا | افحص المحتوى بـ`tar -tzf` |
| المزامنة حذفت بيانات سليمة | مسار المصدر خاطئ + `--delete` | أوقف المزامنة فورًا، واستعد من نسخة أقدم |

:::warn اقرأ سجل الأخطاء، لا «هل أُنشئ ملف»
إنشاء الملف ≠ صحة المحتوى. **فحجم الأرشيف ورمز الخروج والبصمة: افحص اثنين منها على الأقل.**
:::

## 10. قائمة التحقّق

| البند | المتطلب | تكرار الفحص |
| --- | --- | --- |
| تغطية 3-2-1 | 3 نسخ على الأقل، ووسيطان، ونسخة خارج الموقع | مراجعة ربع سنوية |
| نطاق النسخ | العالم، والإعداد، والقوائم، والملحقات/المودات وإعدادها، وسكربت التشغيل | بعد كل تعديل إعداد |
| الاتساق | نسخ مع إيقاف الخادم، أو `save-all` + `save-off` ← ضغط ← `save-on` | كل نسخة |
| الأتمتة | تنفيذ مجدول بـ cron / systemd timer، مع سجل | عند النشر |
| التشفير والصلاحيات | تشفير النسخة خارج الموقع، وحفظ كلمة المرور بلا اتصال، و`chmod 600` لكلمة المرور والمفتاح الخاص، وأدنى صلاحية للحساب | مراجعة ربع سنوية |
| سياسة الاحتفاظ | أعداد يومية/أسبوعية/شهرية واضحة، ومنطق تنظيف مُختبر | مراجعة ربع سنوية |
| المساحة | مساحة كافية محليًا وخارج الموقع | أسبوعيًا |
| التحقق | نجاح `restic check` / `tar -tzf` / مقارنة البصمة | شهريًا |
| المراقبة | تنبيه عند الفشل، ونبضة عند النجاح | عند النشر، ومراجعة شهرية |
| تجربة الاستعادة | استعادة إلى دليل اختبار وتشغيل على منفذ مختلف للتحقق | **ربع سنويًا** |
| التوافر خارج الموقع | تأكيد إمكانية التنزيل/الاستعادة، وقبول رسم الخروج | ربع سنويًا |
| التوثيق | خطوات الاستعادة، وموضع كلمة المرور، وعنوان الهدف مسجّلة كتابةً | نصف سنويًا |

## 11. خلاصة

- **النسخة على القرص نفسه ليست نسخة**: النسخة التي تنقذ فعلًا يجب أن تكون في مكان آخر، والأفضل ألا تكون قابلة للحذف عن بُعد.
- **الاتساق أولى من السرعة**: لا تنسخ والخادم يكتب على القرص.
- **تشفير + حفظ كلمة المرور بلا اتصال**: النسخة خارج الموقع يجب أن تكون مشفّرة، وضياع كلمة المرور يعني ضياع كل شيء.
- **سياسة الاحتفاظ تحتاج اختبارًا**: منطق التنظيف «أتمتة حذف بيانات»، ويجب التحقق منه قبل النشر.
- **استعِد فعلًا مرة كل ربع سنة**: وهي الطريقة الوحيدة لإثبات صلاحية النسخة.
