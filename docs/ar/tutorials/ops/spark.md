«تقطيع» الخادم ظاهرة لا سبب. فقول اللاعب إن هناك تقطيعًا قد يعني أن ملحقًا أشبع الخيط الرئيسي، أو أن الكيانات كثيرة، أو أن لاعبًا يجول فيولّد مناطق آنيًا، أو أن معالج المضيف محدود السرعة أو مفرط البيع. **وقيمة spark في تحويل «التقطيع» من إحساس إلى دليل يمكن الإشارة إليه**: أي مسار استدعاء، وأي ملحق، وبأي نسبة.

وتتناول هذه المقالة spark نفسه فقط. أما اتجاهات الضبط فانظر [تحسين الأداء](/tutorials/java/optimize)، وتراكم الكيانات في [تراكم الكيانات والعناصر المتساقطة](/tutorials/faq/entity-lag)، والانهيارات والأخطاء في [[JAVA] الأسئلة الشائعة](/tutorials/faq/faq-java).

:::warn الأوامر تتبع التوثيق الرسمي
الأوامر والخيارات المذكورة هنا مأخوذة من توثيق spark الرسمي (spark.lucko.me/docs) ومن توثيق PaperMC، وقد روجعت بندًا بندًا. **والأوامر الفرعية والخيارات المتاحة في spark تختلف قليلًا بين المنصّات والإصدارات الرئيسية**؛ فقبل الشروع استخدم `/spark` أو الإكمال التلقائي بـ Tab للتأكد من الوسائط التي تدعمها نسختك، ولا تركّب الخيارات من الذاكرة.
:::

## 1. ما هو spark وكيف يُثبَّت

### 1.1 يتكوّن من ثلاثة أجزاء

spark أداة تحليل أداء (profiler)، ويصفها مشروعها بأنها «محلّل أداء لعميل Minecraft وخادمه ووكيله»، وتتكوّن من ثلاث قدرات:

| المكوّن | السؤال الذي يجيب عنه |
| --- | --- |
| Profiler (محلّل بالاعتيان) | على أي طرق وأي ملحقات يُصرف وقت المعالج؟ |
| Memory Inspection (فحص الذاكرة) | ما أكثر ما يشغل الكومة؟ وهل توقّفات GC كثيرة؟ |
| Health Reporting (تقرير الصحة) | كيف هي حالة TPS والمعالج والذاكرة والقرص على المدى الطويل؟ |

وهو موقع أيضًا: فـ spark.lucko.me موقع رسمي وعارض تقارير على الإنترنت (viewer) في الوقت نفسه. فتشغّل اعتيانًا داخل اللعبة، وتُرفع البيانات، فيُعطى لك رابط، تفتحه في المتصفّح فترى شجرة الاستدعاء ومخطط اللهب وغيرها.

وأمور يجب تكوين فهمها أولًا:

- **spark محلّل بالاعتيان (sampling)**. ويوضّح المشروع في «spark vs. others» أن الاعتيان أقل دقّة عدديًا من الإدراج (instrumentation) عادةً، لكنه لا يُبطئ البرنامج الهدف تقريبًا، ولذلك يعكس التنفيذ الحقيقي أفضل في الممارسة.
- **يسجّل «كل شيء»**. ويشير المشروع في مقارنته بـ timings إلى أن timings يحتاج تعريف مناطق التحليل يدويًا مسبقًا، ويستطيع إحصاء الأحداث، وهو أسهل على المبتدئ غير الملمّ بالمحلّلات؛ أما spark فلا يحتاج تعريفًا مسبقًا ويسجّل مكدّس الاستدعاء كله، فهو أنسب للإجابة عن «أي سطر كود بالضبط هو البطيء».
- **ليس ملحق خادم فقط**. فـ spark يمكن تثبيته كـ Java agent على أي برنامج JVM (بما فيه الخادم الأصلي vanilla)، ويطبّق تلقائيًا خريطة إزالة التشويش على الخادم الأصلي.

### 1.2 كيف يُثبَّت على كل منصّة

صفحة التنزيل الرسمية (https://spark.lucko.me/download) توزّع حزمًا مختلفة بحسب المنصّة. **اختر منصّتك أولًا ثم نزّل**، وضع ملف jar في الدليل المقابل، وأعد تشغيل الخادم ليسري.

| المنصّة | بند صفحة التنزيل الرسمية | أين يوضع | ملاحظة |
| --- | --- | --- | --- |
| Bukkit / Spigot / Paper / Purpur | Bukkit (Paper/Spigot) | `plugins/` | ملحق خادم؛ وPaper 1.21+ فيه مدمج، انظر أدناه |
| Fabric | Fabric | `mods/` | بصيغة مود |
| Forge | Forge | `mods/` | بصيغة مود |
| NeoForge | NeoForge | `mods/` | بصيغة مود |
| Velocity | Velocity | `plugins/` | جهة الوكيل؛ وبادئة الأمر مختلفة، انظر 1.4 |
| BungeeCord | BungeeCord | `plugins/` | جهة الوكيل؛ وبادئة الأمر مختلفة، انظر 1.4 |
| Sponge | Sponge (API 12) | `mods/` | مُدرج منفصلًا في صفحة التنزيل الرسمية |
| العميل (Fabric/Forge وغيرهما) | حزمة المنصّة المقابلة | `mods/` | لتحليل تقطيع العميل؛ والأمر `/sparkc` |
| أي برنامج JVM / الخادم الأصلي | Standalone (Java Agent) | وسائط التشغيل | انظر 1.3 |

:::note Paper 1.21 فأحدث فيه مدمج
يوضّح توثيق التثبيت الرسمي: **Paper 1.21 أو أحدث يُضمّن spark داخل الخادم، فلا يلزم تثبيت ملحق**. ولا تضع jar الملحق المستقل في `plugins/` إلا إن كنت تحتاج spark أحدث من المدمج، مع إضافة `-Dpaper.preferSparkPlugin=true` إلى وسائط التشغيل لتجاوز النسخة المدمجة.
:::

:::warn نزّل من الموقع الرسمي فقط
وضع jar في `plugins/` يعني تسليم السيطرة على الخادم كله له. **فاحصل عليه من صفحة التنزيل الرسمية https://spark.lucko.me/download**، ولا تستخدم حزم نقل مجهولة أو ملفات أقراص سحابية. وفي صفحة التنزيل قسم «Other Platforms» (Folia، وGeyser، وMinestom، وNukkit، وHytale وغيرها)، ويوضّح المشروع أن هذه يقدّمها المجتمع وتُدعم «كما هي» (as-is)، فقيّمها بنفسك قبل الاستخدام.
:::

### 1.3 الوكيل المستقل (Standalone Agent)

حين لا يكون الهدف «خادمًا معياريًا» (مثل الخادم الأصلي أو برنامج Java ذاتي)، استخدم طريقة الوكيل. ويُثبَّت عند التشغيل:

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar -jar application.jar [application args]
```

ويمكن تحديد منفذ استماع الوكيل:

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar=port=2222 -jar application.jar [application args]
```

والوسائط التي يدعمها الوكيل (تُفصل بفواصل):

| الوسيط | المعنى |
| --- | --- |
| `port={port}` | منفذ استماع الوكيل، والافتراضي `2222` |
| `start` | بدء الاعتيان فور التثبيت |
| `open` | طباعة رابط العارض إلى وحدة التحكّم/السجل بعد التثبيت |

مثال:

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar=port=2222,start,open -jar application.jar
```

وإن كان البرنامج **يعمل بالفعل** فيمكن الإلحاق بالعملية مباشرةً (استبدل `<pid>` برقم العملية):

```bash
java -jar spark-x.y.z-standalone-agent.jar <pid>
java -jar spark-x.y.z-standalone-agent.jar <pid> port=2222
```

وعند تشغيل هذا الـ jar بلا PID يسرد كل عمليات Java الحالية وأرقامها. وبعد نجاح الإلحاق، **تُطبع طريقة الاتصال في وحدة التحكّم/سجل البرنامج المُلحَق نفسه**؛ واتبع التعليمات للاتصال بجلسة SSH، فتستطيع تنفيذ أوامر spark المعتادة، وتخرج من الجلسة بـ`exit`.

### 1.4 تأكيد نجاح التحميل

أكثر طريقة تحقق مباشرة: **نفّذ `/spark` بلا أي وسيط**، فيطبع النسخة وقائمة الأوامر الفرعية المتاحة. فإن ظهرت رسالة أمر غير معروف أو لم تظهر مخرجات، فالتحميل لم ينجح.

وأفحص بالترتيب: هل وُضع jar في الدليل الصحيح (`plugins/` أم `mods/`)، وهل اختيرت حزمة المنصّة الصحيحة، وهل أُعيد تشغيل الخادم فعلًا، وهل في سجل التشغيل معلومات تحميل spark.

وبادئة الأمر تختلف بحسب المنصّة، ويوسمها التوثيق الرسمي خاصةً:

| البيئة | الأمر المستخدم |
| --- | --- |
| الخادم (عائلة Bukkit، وخوادم Fabric/Forge) | `/spark` |
| BungeeCord | `/sparkb` |
| Velocity | `/sparkv` |
| **عميل** Forge/Fabric | `/sparkc` |

وأما الصلاحيات: تحتاج صلاحية `spark`، أو عقد الصلاحية الخاص بكل أمر فرعي. والعقد التي يسردها التوثيق الرسمي تشمل `spark.profiler` و`spark.health` و`spark.ping` و`spark.tps` و`spark.tickmonitor` و`spark.gc` و`spark.gcmonitor` و`spark.heapsummary` و`spark.heapdump` و`spark.activity`. وفي معظم الحالات **يكفي أن تجعل نفسك OP**.

:::tip إعداد يسهل إغفاله
بند إعداد `overrideTpsCommand` في spark قيمته الافتراضية `true`، و**يسري في خوادم عائلة Bukkit فقط**: أي أن `/tps` يُتولّى بـ spark افتراضيًا، ومخرجاته هي عرض TPS الخاص بـ spark.
:::

## 2. انظر الصحة العامة أولًا

### 2.1 ماذا تعني TPS وMSPT بالضبط

افهم حلقة tick أولًا (دليل «The Tick Loop» الرسمي):

- هدف خادم Minecraft هو **تنفيذ 20 tick في الثانية**، أي **tick واحد كل 50 مللي ثانية**.
- وما يُفعل في tick واحد يشمل: معالجة حزم اللاعبين (الحركة، ووضع/تدمير البلوكات، ومهاجمة الكيانات)، وتحديث مواضع اللاعبين والكيانات الأخرى، وبثّ تغيّرات العالم إلى اللاعبين، وتوليد الوحوش ومعالجة الذكاء وتحديد المسار، ومعالجة تحديثات Redstone، وغيرها.
- فإن استغرق tick **أقل من** 50 مللي ثانية «ينام» الخادم في الوقت المتبقي، حتى يحين بدء tick التالي. **والنوم صحيّ**.
- وإن استغرق tick **أكثر من** 50 مللي ثانية فلا يمكن إلا تأخير tick التالي، لأن الـ tick لا يُنفّذ بالتوازي. فتنتقل كل الأمور «إلى اليمين»، ويقلّ عدد الـ ticks المنجزة في الثانية نفسها، وما يشعر به اللاعب هو البطء والتقطيع.

ومن هنا جاء مؤشران:

| المؤشر | الاسم الكامل | المعنى | القيمة المستهدفة |
| --- | --- | --- | --- |
| TPS | ticks per second | متوسط عدد الـ ticks المنجزة في الثانية | **20** |
| MSPT | milliseconds per tick | متوسط الميلي ثانية لكل tick | **50 أو أقل** |

ويوضّح التوثيق الرسمي أن مخرجات `/spark tps` تضم أيضًا **أدنى MSPT ووسيطه والمئين 95 وأقصاه**، وأن spark يلوّن هذه الأرقام تلقائيًا أخضر أو أصفر أو أحمر بحسب جودتها.

**ولماذا الأقصى مهم**: المؤشرات السابقة متوسطات أو إحصاءات. ويذكّر التوثيق في دليل حلقة tick بأنه ممكن تمامًا أن «معظم الـ ticks تستغرق 20 مللي ثانية (صحي)، وبعضها يستغرق 300 مللي ثانية (غير صحي)»، وهذه هي **ذروة التقطيع (lag spike)** — فالمتوسط يبسّط الذروة، ولذلك يُفلت من النظر إلى TPS المتوسط وحده.

### 2.2 /spark tps

```text
/spark tps
```

يطبع TPS ونسبة استخدام المعالج. وهذه **الخطوة الأولى** في كل تشخيص: تأكّد أولًا «هل هناك تقطيع فعلًا»، ثم قرّر هل يلزم تشغيل محلّل.

### 2.3 /spark health

الأمر الفرعي `health` يولّد تقرير صحة الخادم، **ويضم TPS والمعالج والذاكرة واستخدام القرص**. والاستخدام الذي يذكره التوثيق الرسمي:

```text
/spark health
/spark health upload
/spark health show
/spark health show --memory
/spark health show --network
```

| الأمر | السلوك |
| --- | --- |
| `/spark health` | يفتح في العارض، **بوضع live dashboard، وتتحدّث البيانات كل 10 ثوانٍ** |
| `/spark health upload` | يرفع تقرير صحة **ثابتًا** لا يتحدّث تلقائيًا |
| `/spark health show` | يطبع التقرير الأساسي في وحدة التحكّم مباشرةً، بلا متصفّح |
| `/spark health show --memory` | يضيف معلومات استخدام ذاكرة JVM |
| `/spark health show --network` | يضيف معلومات استخدام شبكة النظام |

### 2.4 /spark ping

```text
/spark ping
/spark ping --player <username>
```

وبلا وسائط يعرض **متوسط ping لكل اللاعبين** (زمن الذهاب والعودة RTT)؛ ومع `--player` يعرض ping لاعب معيّن الآن.

**ولماذا يُذكر منفصلًا**: قول اللاعب «هناك تقطيع» قد يعني بطء tick في الخادم، أو قد يعني فقط سوء رابط شبكته إلى مركز البيانات. فـ ping المرتفع مع MSPT طبيعي يعني أن المشكلة في مسار الشبكة، ولا يفيد تعديل إعداد الخادم. وهذه الخطوة **لفصل مشكلة الشبكة عن مشكلة tick**.

### 2.5 كيف ترى التغيّر عبر فترة

`/spark tps` مرة واحدة لقطة فقط. ولرؤية الاتجاه استخدم live dashboard في `/spark health`: ويوضّح التوثيق أنه يتحدّث كل 10 ثوانٍ، فيمكن اعتباره خطًّا زمنيًا لمراقبة هل TPS وMSPT والمعالج **منخفضة باستمرار** أم **تهبط دوريًا**.

| الشكل | ملاحظة | الخطوة التالية |
| --- | --- | --- |
| TPS منخفض باستمرار وMSPT مرتفع باستمرار | الخيط الرئيسي لا يلحق على المدى الطويل | شغّل profiler مباشرةً للبحث عن النقاط الساخنة |
| TPS طبيعي معظم الوقت ويهبط أحيانًا | ذروة تقطيع | حدّدها بـ tickmonitor، ثم اعتن بـ`--only-ticks-over` |

:::note كيف نفهم «TPS منخفض + MSPT طبيعي»
بالاستنتاج من آلية حلقة tick: إن كان MSPT طبيعيًا فعلًا (كل tick ينجز داخل ميزانية 50 مللي ثانية)، فلا يجب أن يكون TPS منخفضًا طويلًا، لأن النوم بين الـ ticks يكمل الإيقاع. فحين يظهر «TPS منخفض لكن MSPT طبيعي» فما يجب أن تشكّ فيه ليس «ملحقًا مكتوبًا ببطء»، بل **عوامل خارجية**: توقّف الخادم (مثل stop-the-world طويل، أو حفظ العالم، أو تعليق المضيف أو ترحيله)، أو تحديد معالج المضيف أو استحواذ مستأجر آخر عليه، أو **أن البيانات نفسها خاطئة**.

وهذه النقطة الأخيرة لها أساس رسمي: فمؤشرات spark كلها مأخوذة من أحداث الخادم وواجهات Java/النظام، ويوضّح التوثيق في «About spark metrics» أن **مؤشرات المعالج والذاكرة قد تُبلَّغ خطأً أحيانًا عند التشغيل في حاوية** (بيئات مثل Pterodactyl)، وأنه «إن بدت غير صحيحة فالمرجّح أن البيانات الخام التي وصلت إلى spark غير صحيحة». وما يلزم توضيحه: **«TPS منخفض + MSPT طبيعي يشير إلى عوامل خارجية» استنتاج مبني في هذه المقالة على آلية حلقة tick، والتوثيق الرسمي لا يقرّر هذا الاستنتاج مباشرةً**، فاحكم مع استخدام المعالج وحمل المضيف وسجل GC.
:::

## 3. الاعتيان (profiler)

### 3.1 الأوامر والخيارات

كل الأوامر والخيارات التالية من صفحة Command Usage الرسمية.

العمليات الأساسية:

| الأمر | الدور |
| --- | --- |
| `/spark profiler start` | بدء الاعتيان بالوضع الافتراضي |
| `/spark profiler stop` | الإيقاف وعرض النتيجة (يرفع ويعطي رابطًا افتراضيًا) |
| `/spark profiler cancel` | الإيقاف **بلا رفع** النتيجة |
| `/spark profiler open` | فتح صفحة العرض مباشرةً والاعتيان يعمل في الخلفية، بلا إيقافه |
| `/spark profiler info` | عرض حالة الاعتيان الحالية |

والخيارات الشائعة:

| الخيار | الدور |
| --- | --- |
| `--timeout <seconds>` | إيقاف تلقائي عند انتهاء المدة |
| `--only-ticks-over <milliseconds>` | **تسجيل الـ ticks التي تتجاوز هذه المدة فقط**، لاصطياد الذروات |
| `--thread *` | تتبّع كل الخيوط |
| `--thread <thread name>` | تتبّع خيط محدّد فقط |
| `--thread <pattern> --regex` | مطابقة أسماء الخيوط بتعبير نمطي |
| `--interval <milliseconds>` | فاصل الاعتيان، والافتراضي 4 |
| `--alloc` | تحليل **تخصيص الذاكرة** (ضغط الذاكرة) لا المعالج |
| `--alloc --alloc-live-only` | في تحليل التخصيص أبقِ فقط العناصر التي لم تُحرَّر عند انتهاء الاعتيان |
| `--alloc --interval <bytes>` | دقّة الاعتيان في تحليل التخصيص، والافتراضي `524287` (نحو 512 KB) |
| `--combine-all` | دمج كل الخيوط تحت عقدة جذر واحدة |
| `--not-combined` | عدم تجميع خيوط تجمّع الخيوط معًا |
| `--ignore-sleeping` | تسجيل عيّنات الخيوط غير النائمة فقط |
| `--force-java-sampler` | إجبار استخدام محلّل Java بدل محلّل async |
| `stop --comment <comment>` | إرفاق ملاحظة عند الإيقاف، تُعرض في العارض |
| `stop --save-to-file` | حفظ النتيجة في ملف داخل دليل الإعداد، **بلا رفع** |

وأمثلة مركّبة (كما في الدليل الرسمي وتوثيق Paper):

```text
/spark profiler start --timeout 60
/spark profiler start --timeout 600
/spark profiler start --only-ticks-over 150
/spark profiler stop --comment "خط الأساس قبل التعديل"
/spark profiler stop --save-to-file
```

:::note عن «/spark profiler بلا وسائط»
يصف التوثيق الرسمي تشغيل profiler بالأوامر الفرعية الصريحة `start` و`stop` و`cancel` و`open` و`info`، ولا يصف «`/spark profiler` بلا وسائط» كفعل مستقل. كما يوضّح توثيق الإعداد أن **المحلّل الخلفي مفعّل افتراضيًا** (بند الإعداد `backgroundProfiler` قيمته `true`)، وفي هذه الحالة يمكنك استخدام `/spark profiler stop` أو `/spark profiler open` مباشرةً للتعامل مع **الاعتيان الجاري بالفعل**. ولذلك: **اكتب بالصيغة الفرعية، ولا تفترض سلوك الأمر المجرّد**.
:::

### 3.2 العملية القياسية

```text
1. تأكّد أن المشكلة تحدث الآن (يؤكد التوثيق: يجب أن يجري الاعتيان أثناء حدوث المشكلة، وإلا لن يُلتقط شيء)
2. ابدأ الاعتيان: /spark profiler start --timeout 60
3. دع الخادم يعمل بحِمل حقيقي 30 إلى 60 ثانية (لاعبون متصلون، وتكرار العملية)
4. يتوقّف تلقائيًا عند المدة؛ ويظهر في الدردشة أو وحدة التحكّم رابط spark.lucko.me/xxxx
5. افتح هذا الرابط في المتصفّح
6. انظر أولًا "Server thread" (الخيط الرئيسي للخادم)، وانقر من أعرض عقدة إلى أسفل
```

واختيار المدة: إن كانت المشكلة **تحدث الآن** فـ 30 إلى 60 ثانية تكفي؛ وإن كانت **متقطّعة** فاستخدم `--timeout` أطول (المثال في توثيق Paper الرسمي `--timeout 600`، أي 10 دقائق)، أو انتقل إلى طريقة الذروات في القسم 3.6.

### 3.3 قراءة التقرير في العارض

صفحة «Using the viewer» الرسمية تشرح بنية العارض بوضوح.

**الخيوط (Threads)**: أول ما تراه عند فتح التقرير قائمة خيوط. ويمكن فهم الخيط بأنه «العامل الذي يقوم بعمل ما في البرنامج». وبالنسبة إلى الخادم، **ما يهمّ فعلًا عادةً هو "Server thread" وحده**، أي الخيط الرئيسي المسؤول عن تشغيل اللعبة. والعقدة الجذرية (الخيط نفسه) تُظهر 100% دائمًا، لأن 100% من زمن الاعتيان مصروف في هذا الخيط.

**إطارات الاستدعاء / العقد (Call frames)**: كل عقدة تعرض ثلاثة أمور — **الاسم**، و**نسبة زمن هذا الخيط**، و**عدد الميلي ثانية (يظهر عند التحويم)**. والنقر على عقدة يوسّع أبناءها.

والشكل النمطي عند توسيع خيط الخادم (المثال الرسمي):

```text
Server thread
  java.lang.Thread.run()
    MinecraftServer.run()
      MinecraftServer.tick()        <- المكان الذي يجري فيه العمل الفعلي
      Thread.sleep()                <- نوم، صحيّ، ويمكن تجاهله
```

**ونسبة النوم أول ما يُنظر إليه**. وقد أعطى التوثيق في دليل حلقة tick قيمًا تجريبية:

| نسبة النوم (waitForNextTick / sleep) | المعنى |
| --- | --- |
| كلما زادت كان أفضل (81% في المثال الرسمي) | للخادم فائض يستطيع تحمّل الأحمال المفاجئة |
| أقل من 20% | الخادم مشغول جدًا، وبعض الـ ticks قد تكون متقطّعة بالفعل |
| أقل من 5% | يمكن اعتبار أنه متقطّع، وبلا فائض |

**وهذه كلها متوسطات**، ويؤكد التوثيق أن الذروات تُبسَّط بالمتوسط، فـ«نسبة نوم عالية» لا تعني «لا ذروة تقطيع».

**والعروض الثلاثة** (تُبدَّل من شريط الأدوات العلوي):

| العرض | المحتوى | متى يُستخدم |
| --- | --- | --- |
| All (الافتراضي) | شجرة الاستدعاء الكاملة القابلة للتوسيع | اتّبع النسبة نزولًا |
| Flat | **أبطأ 250 استدعاء دالّة** مسطّحة في المستوى الأعلى | نظرة سريعة على «من يستهلك أكثر إجمالًا» |
| Sources | **شجرة لكل ملحق/مود على حدة**، والمستوى الأعلى هو الاستدعاءات الصادرة من ذلك المصدر | تحديد «أي ملحق» مباشرةً |

ولعرض Flat بُعدان: Display فيه **Top Down** (الاتجاه الطبيعي، توسيع لرؤية الاستدعاءات الفرعية) و**Bottom Up** (بالعكس، توسيع لرؤية «من استدعاه»)؛ وSort فيه **Total Time** (الزمن الكلي مع الاستدعاءات الفرعية) و**Self Time** (زمن الدالّة نفسها).

**مخطط اللهب (Flame Graph)**: يمكن النقر على أيقونة اللهب في الأعلى، أو النقر بالزر الأيمن على عقدة واختيار «View as Flame Graph». ويوضّح التوثيق: **عرض العقدة يوازي نسبة الزمن التي تشغلها**؛ والنقر على عقدة «يركّز» عليها ويملأ الصفحة. و«انظر إلى أعرض شريط» التي تُقال كثيرًا تعني هذا.

**إزالة التشويش (Deobfuscation)**: أسماء الأصناف والدوال في عميل Minecraft وخادمه مشوّشة. والعارض **يتعرّف تلقائيًا على الخريطة الواجب تطبيقها** افتراضيًا؛ فإن لم يتعرّف فاخترها يدويًا من القائمة المنسدلة أعلى يمين الصفحة.

**الإشارات المرجعية**: اضغط `alt` وانقر على استدعاء دالّة، أو انقر بالزر الأيمن واختر «Toggle bookmark»، فتُبرَز الدالّة، **وتُشفَّر الإشارة في الرابط** — فأرسل هذا الرابط المعلَّم لغيرك، فيفتحه ويتوسّع تلقائيًا ويُبرز الموضع نفسه. وهذا أقلّ الطرق عناءً «للإشارة لغيرك».

### 3.4 خيط الخادم والخيوط غير المتزامنة

- **Server thread**: الخيط الرئيسي الذي تعمل فيه حلقة tick، وفيه معظم مشكلات الأداء.
- **الخيوط غير المتزامنة (async threads)**: مهام الملحقات غير المتزامنة، وحفظ المناطق، وشبكة IO (Netty)، وخيوط GC وغيرها. وهي **لا تستهلك ميزانية tick مباشرةً**، لكن إن نازعت المعالج أو تنازعت الأقفال مع الخيط الرئيسي فستؤثر فيه رغم ذلك.

ووصف `--thread *` في التوثيق الرسمي هو «تتبّع **كل** الخيوط»، وهذا يعني أن الخيوط ليست كلها داخلة في الاعتيان افتراضيًا. **فإن شككت في أن ملحقًا يرمي العمل الثقيل على خيط غير متزامن** (ويظهر ذلك كمعالج مرتفع بينما خيط الخادم يبدو غير مشغول)، فاعتن صراحةً بـ`--thread *` مرة أخرى.

### 3.5 كيف تُنسب الوقت إلى ملحق معيّن

هذا أنفع ما في spark مقارنةً بـ timings: **تظهر في التقرير أسماء حزم الملحق نفسه**.

فمثلًا إن ظهر في خيط الخادم شريط عريض:

```text
com.example.shop.ShopManager.tickShops()
```

فالملحق `com.example.shop` هو من يفعل ذلك. وطريقة الحكم:

1. في عرض All توسّع نزولًا مع النسبة، حتى ترى اسم حزمة «يشبه ملحقًا» (وهو نطاق معكوس عادةً، مثل `me.lucko.` أو `com.example.`).
2. أو انتقل مباشرةً إلى **عرض Sources**، فهو **يبني شجرة لكل ملحق/مود**، وأكثرها «سمنة» هو المشتبه فيه.
3. وإن كان المستوى الأعلى دالّة للخادم نفسه (NMS) فلا تستعجل الحكم: استخدم **Bottom Up** أو واصل التوسيع لترى **من استدعاه** — والمرجّح أن ملحقًا أطلق هذا الكود عبر حدث أو واجهة.

### 3.6 اصطياد ذروات التقطيع: tickmonitor مع only-ticks-over

الذروات تُغطّيها المتوسطات، ولذلك أعطى التوثيق تركيبة مخصّصة.

أولًا، حدّد بـ`tickmonitor` «كم بطيئًا يُعدّ شاذًّا»:

| الأمر | الدور |
| --- | --- |
| `/spark tickmonitor` | **مفتاح** تشغيل نظام المراقبة (نفّذه مرة أخرى للإيقاف) |
| `/spark tickmonitor --threshold <percent>` | الإبلاغ عن الـ ticks **التي تتجاوز متوسط زمن tick بنسبة محدّدة** فقط |
| `/spark tickmonitor --threshold-tick <milliseconds>` | الإبلاغ عن الـ ticks **التي تتجاوز عدد ميلي ثانية محدّدًا** فقط |
| `/spark tickmonitor --without-gc` | تشغيل المراقبة مع إيقاف التقارير المتعلقة بنشاط GC |

ويوضّح التوثيق أن العتبة الافتراضية **100%**، أي لا يُبلَّغ إلا حين «يستغرق هذا الـ tick ضعف المتوسط». ولزيادة الحساسية خفّضها، مثلًا:

```text
/spark tickmonitor --threshold-tick 50
/spark tickmonitor --threshold-tick 70
```

وثانيًا، اعتن بهذه الـ ticks الشاذة فقط بـ`--only-ticks-over`:

```text
/spark profiler start --only-ticks-over 150
```

والخبرة التي يذكرها التوثيق: **يُنصح بأن تكون العتبة بين 50 و100، لكن يجب أن تكون أقل من الزمن الفعلي لـ ticks «التقطيع» لديك**، وإلا استُثنيت الذروة نفسها. وفي مثال التوثيق تجاوز فعل التقطيع 300 مللي ثانية، فأُخذت 150 «للاحتياط».

وبهذا تُستثنى من التقرير كل أعمال اللعب «الطبيعية»، ويبقى الذروة نفسها، فتتضح النقاط الساخنة جدًا.

## 4. أدوات تشخيص أخرى

| الأمر | عن أي سؤال يجيب | متى يُستخدم |
| --- | --- | --- |
| `/spark tps` | هل هناك تقطيع الآن؟ وكم TPS وMSPT والمعالج؟ | أول خطوة في كل تشخيص؛ وللمقارنة قبل تعديل الإعداد وبعده |
| `/spark health` | كيف الصحة العامة (TPS، والمعالج، والذاكرة، والقرص)؟ | عند الحاجة إلى مراقبة متصلة؛ وlive dashboard يتحدّث كل 10 ثوانٍ |
| `/spark health upload` | كما سبق، لكن لقطة ثابتة قابلة للمشاركة | لإرسالها لغيرك، وللحفظ |
| `/spark health show` | بلا متصفّح، في وحدة التحكّم مباشرةً | نظرة سريعة في بيئة SSH؛ وأضف `--memory` أو `--network` |
| `/spark ping` | هل زمن تأخير اللاعبين مرتفع؟ هل المشكلة شبكة أم tick؟ | حين يقول اللاعبون «تقطيع»، افصل النوعين أولًا |
| `/spark profiler start` | على أي طرق وأي ملحقات يُصرف وقت المعالج؟ | بعد التأكد من «وجود تقطيع فعلي» |
| `/spark tickmonitor` | أي الـ ticks بطيئة بشكل شاذ؟ وكل كم تحدث؟ | التقطيع المتقطّع والذروات |
| `/spark gc` | كيف تاريخ GC؟ وهل التوقّفات متكرّرة؟ | عند الشك في أن الذاكرة أو GC تسبب التقطيع |
| `/spark gcmonitor` | مراقبة GC باستمرار والإبلاغ عند حدوثه | عند الشك في ذروة GC؛ شغّله، وكرّر الحالة، ثم أوقفه |
| `/spark heapsummary` | أي الكائنات يشغل الكومة أكثر؟ | عند الشك في تسريب ذاكرة؛ وتُرفع النتيجة إلى العارض |
| `/spark heapdump` | لقطة كومة كاملة (`.hprof`) | للتحليل العميق بأداة خارجية مثل MAT؛ والملف كبير |
| `/spark activity` | من استخدم spark مؤخرًا وماذا فعل؟ | في الإدارة المشتركة للتأكد هل يعتني غيرك؛ و`--page <n>` للتنقّل |

وفيما يلي بعض التفاصيل التي يسهل إساءة استخدامها.

### 4.1 ما يتعلق بـ GC: /spark gc و/spark gcmonitor

`/spark gc` يطبع **تاريخ GC (جمع القمامة)** في الخادم، ويجيب عن «هل GC يبطئ الخادم».

و`/spark gcmonitor` **مفتاح** تشغيل نظام مراقبة GC (نفّذه مرة أخرى للإيقاف). وقيمته في **محاذاته مع التقطيع**: شغّل المراقبة أولًا، وكرّر حالة تقطيع، ثم انظر هل وافق لحظة التقطيع نشاط GC مقابلاً. فإن تطابق الزمن تحوّل الاتجاه إلى الذاكرة ووسائط GC، لا إلى البحث عن نقاط ساخنة في الملحقات.

### 4.2 ما يتعلق بالذاكرة: /spark heapsummary و/spark heapdump

الفرق بينهما مهم:

| الأمر | الناتج | الاستخدام |
| --- | --- | --- |
| `/spark heapsummary` | **ملخّص** الكومة، ويُرفع إلى العارض | نظرة سريعة على «أي نوع من الكائنات يشغل الذاكرة أكثر»، للحكم على احتمال التسريب |
| `/spark heapdump` | ملف `.hprof` كامل، يُكتب على القرص | تحليل سلاسل مراجع الكائنات بعمق بأداة متخصّصة خارجية |

وخيار `/spark heapdump` هو `--compress <type>`، وأنواع الضغط المدعومة `gzip` و`xz` و`lzma`. ويوسم التوثيق الرسمي `--include-non-live` (تضمين الكائنات غير القابلة للوصول) و`--run-gc-before` (اقتراح تشغيل JVM لـ GC قبل التوليد) **بأنهما مهجوران (deprecated)**؛ و`--run-gc-before` في `heapsummary` مهجور كذلك.

:::warn heapdump ثقيل
تفريغ الكومة الكامل **يكتب ملفًا في رتبة حجم الكومة على القرص**، ويُحدث في JVM توقفًا واضحًا. فلا تنفّذه في ذروة العمل على بيئة الإنتاج، وتأكّد من مساحة القرص أولًا.
:::

## 5. تحديد المشكلة من التقرير

### 5.1 جدول القرار

وقبل ذلك مقدّمة: **أسماء الدوال تتغيّر بحسب النسخة وتنفيذ الخادم ومجموعة الخرائط**. فمثال العارض الرسمي يستخدم أسماء مثل `WorldServer.doTick()` و`WorldServer.tickEntities()` (وهي خرائط أقدم)؛ وفي نسخ أخرى قد ترى `ServerLevel.tick` و`Level.tickEntities` وغيرها. **لا تحفظ الأسماء، بل انظر الشكل والنسبة**، واستفد من إزالة التشويش التلقائية في العارض.

| الظاهرة في التقرير | الاستنتاج المرجّح | الخطوة التالية |
| --- | --- | --- |
| **اسم حزمة ملحق** (مثل `com.example.shop`) الأعلى نسبةً في خيط الخادم | ذلك الملحق هو عنق الزجاجة | رقِّه، أو ابحث عن بديل، أو حدّد تكرار إطلاقه؛ وأرسل رابط التقرير للمؤلّف |
| `Entity.tick` أو `Level.tickEntities` (وفي الخرائط القديمة `WorldServer.tickEntities`) يشكّل الحصة الكبرى | **الكيانات كثيرة** | انظر [تراكم الكيانات والعناصر المتساقطة](/tutorials/faq/entity-lag): نظّف العناصر المتساقطة، وحدّد التوليد، وخفّض مسافة العرض والإعدادات المتعلقة بالكيانات |
| استدعاءات متعلقة بالمناطق (`ChunkMap` و`ChunkGenerator` وغيرها) تشكّل الحصة الكبرى | **توليد المناطق أو تحميلها** | نفّذ توليدًا مسبقًا للخريطة، لتقليل التوليد الآني الناتج عن استكشاف اللاعبين مناطق جديدة |
| tick القمع (hopper) وكيانات البلوكات (`hopper` و`LevelChunk.tickBlockEntities` وغيرها) | **حِمل Redstone والقمع وكيانات البلوكات** | حدّد سرعة القمع، وادمج المزارع، وقلّل آلات Redstone في المناطق الدائمة التحميل |
| توقّفات GC طويلة على الخط الزمني | **الذاكرة أو إعداد GC** | اضبط حجم الكومة ووسائط GC؛ واستخدم `heapsummary` أولًا لاستبعاد التسريب |
| **عالم واحد أو منطقة واحدة** فقط بطيئة | مزرعة أو بناء معيّن | حدّد الإحداثيات، وفكّكه في مكانه أو قيّده، أو انقله إلى خادم مستقل |
| نسبة `waitForNextTick` أو النوم منخفضة جدًا (أقل من 5%) | لا فائض في الخادم كله | ليست مشكلة نقطة واحدة، بل سعة غير كافية: قلّل الحِمل أو ارفع أداء النواة الواحدة |
| نسبة النوم عالية واللاعبون ما زالوا يقولون إن هناك تقطيعًا | المتوسط غطّى الذروة | اتبع القسم 3.6: `tickmonitor` مع `--only-ticks-over` |

### 5.2 مأزقان شائعان في النسبة

**المأزق الأول: رؤية دالّة NMS فتُظنّ «مشكلة الخادم».** فدوال مثل `Entity.tick` كود الخادم، لكن **من يطلقها قد يكون ملحقًا أو سلوك لاعب أو تصميم مزرعة**؛ فاستخدم عرض Flat مع **Bottom Up** لتجد «من استدعاه».

**المأزق الثاني: الحكم من Total Time وحده.** فدالّة قد يكون Total Time فيها مرتفعًا لأنها تستدعي دوالّ فرعية كثيرة (فهي «قشرة»)؛ فبدّل الترتيب إلى **Self Time** لترى الدوالّ **التي تصرف الزمن على نفسها فعلًا**، وهي ما يجب تعديله.

### 5.3 المقارنة قبل وبعد إلزامية

التقرير الواحد يوضّح «الحال الآن»، ولا يوضّح «هل يفيد هذا التعديل». والتصرف الصحيح:

```text
1. الاعتيان A: /spark profiler stop --comment "خط الأساس قبل التعديل"
2. نفّذ تغييرًا واحدًا فقط
3. اعتن B في أقرب الظروف تشابهًا (عدد اللاعبين، والفترة، وهل في المنطقة نفسها)
4. قارن تغيّر نسبة العقدة نفسها في التقريرين
5. إن لم يتحسّن فارجع عن هذا التعديل، وجرّب الفرضية التالية
```

غيّر متغيّرًا واحدًا في المرة، وإلا تعذّرت النسبة. وفي المقارنة انظر إلى **تغيّر النسبة للعقدة نفسها**، لا إلى القيمة المطلقة — لأن مدة الاعتيان وعدد اللاعبين قد يختلفان.

## 6. العملية الميدانية وما يجب الانتباه إليه

### 6.1 للاعتيان كلفة

spark محلّل بالاعتيان، وكلفته أقل بكثير من الإدراج، لكنها **ليست صفرًا**:

- المحلّل الخلفي **مفعّل افتراضيًا**، وفاصل الاعتيان الافتراضي **10 مللي ثانية** (بند الإعداد `backgroundProfilerInterval`).
- محرّك الاعتيان هو `async` (async-profiler) افتراضيًا، ويوضّح التوثيق أنه أدقّ من محرّكي Java/WarmRoast (لا يتأثر بانحياز الاعتيان عند نقاط الأمان)، **ويُستخدم تلقائيًا حين يدعمه النظام**. ويشترط Linux أو macOS بمعمارية x86_64/aarch64؛ وفي الحاويات قد يلزم إضافة `libstdc++`.
- **تحليل التخصيص (`--alloc`) وheapdump أثقل**: الأول يحتاج رموز تنقيح HotSpot (وهي موجودة في Java 11 فأحدث عادةً)، والثاني يكتب ملفًا كبيرًا ويُوقف JVM.

:::warn لا تدع المحلّل يعمل باستمرار
الاعتيان للإجابة عن سؤال محدّد، فإذا انتهى توقّف. واستخدام `--timeout` ليوقف نفسه أريح حلّ. **وإبقاء المحلّل معلّقًا على خادم متقطّع أصلًا لا يفعل سوى تفاقم الحال.**
:::

### 6.2 مشاركة التقرير والخصوصية

التوثيق الرسمي إيجابي في حديثه عن «المشاركة»: يُرفع التقرير إلى العارض تلقائيًا ويُعطى لك رابط، **ويمكن إرسال هذا الرابط بحرية** — لمن يساعدك في التشخيص، أو لمؤلّفي الملحقات والمودات، للإشارة إلى المشكلة. وآلية الإشارات المرجعية تُشفّر «أقصد هذا السطر» في الرابط.

لكن أمورًا يجب معرفتها:

1. **الرفع سلوك افتراضي**. فـ`/spark profiler stop` يرفع افتراضيًا؛ و`/spark profiler stop --save-to-file` وحده هو **الحفظ في ملف داخل دليل الإعداد بلا رفع**.
2. **التوثيق الرسمي لا يصف مفتاحًا «لجعل التقرير خاصًّا»**. وفي الصفحات التي روجعت لهذه المقالة لا يوجد أي بيان عن التحكّم في الوصول أو التقارير الخاصة. **ولذلك اعتبر رابط التقرير «مفتوحًا لكل من يحصل عليه»**.
3. **البيانات الخام قابلة للجلب**. توضّح صفحة «Raw spark data» الرسمية: إضافة `?raw=1` إلى الرابط تعطي بيانات JSON وصفية؛ ويمكن حتى طلب البيانات الخام من `https://spark-usercontent.lucko.me/<code>` مباشرةً (والأنواع `application/x-spark-sampler` و`application/x-spark-heap` و`application/x-spark-health`). أي أن **سلسلة الرمز القصير نفسها بيانات اعتماد للوصول**.
4. **البيانات الوصفية تحوي معلومات هوية**. فمثال التوثيق الرسمي يتضمن اسم المستخدم وUUID لمَن بدأ. ففكّر في هذا قبل لصق الرابط في مكان عام.
5. **الفتح المحلي**: إن لم ترد الرفع، يمكنك سحب ملف `.sparkprofile` أو `.sparkheap` إلى منطقة الإسقاط في صفحة العارض وعرضه محليًا.
6. وإن كان الغرض طلب المساعدة، فنصيحة توثيق PaperMC الرسمي أن **تأخذ تقرير spark إلى قناة Discord `#paper-help`** (وهي القناة التي يعطيها Paper رسميًا).

### 6.3 قائمة الاعتيان الكامل

```text
التحضير
[ ] تأكّد من التحميل: /spark
[ ] سجّل الحالة الحالية: /spark tps
[ ] تأكّد أن المشكلة تحدث الآن (وإلا لم يُلتقط شيء)
[ ] تأكّد من كفاية مساحة القرص (خصوصًا إن كان heapdump محتملًا)
الاعتيان
[ ] تقطيع مستمر عام   -> /spark profiler start --timeout 60
[ ] ذروات متقطّعة   -> أولًا /spark tickmonitor لتحديد العتبة، ثم /spark profiler start --only-ticks-over <ms> --timeout <s>
[ ] شك في خيط غير متزامن -> أضف --thread *؛ وشك في تخصيص الذاكرة -> أضف --alloc (أعلى كلفة)
[ ] لا تدعه يعمل بلا حدّ زمني
قراءة التقرير
[ ] انظر أولًا نسبة النوم في Server thread
[ ] انقر من أعرض عقدة نزولًا، واتبع النسبة
[ ] استخدم عرض Sources للنسبة إلى ملحق محدّد
[ ] استخدم Flat مع Self Time للعثور على الدوالّ «المستهلكة لوقتها فعلًا»
[ ] استخدم Bottom Up للعثور على «من استدعى هذه الدالّة البطيئة»
[ ] في حالة الذروات تأكّد من سريان --only-ticks-over (ولا يجب أن يحوي التقرير ticks طبيعية كثيرة)
الاستنتاج والتحقق
[ ] اكتب الاستنتاج: أي ملحق، وأي نوع كيانات، وأي منطقة، أم سعة غير كافية
[ ] غيّر موضعًا واحدًا فقط، ثم اعتن مرة أخرى بالظروف نفسها
[ ] علّم التقرير بـ--comment، واحفظ الرابط للمقارنة
```

### 6.4 متى لا تستخدم spark

حين يكون اللاعبون فقط ذوي زمن تأخير مرتفع فاستخدم `/spark ping` أولًا، فالمشكلة قد تكون في مسار الشبكة؛ وحين لا يقوم الخادم أو ينهار فاذهب إلى السجلات وتقارير الانهيار، فالمحلّل لا يفيد؛ وحين يكون TPS طبيعيًا وما زال اللاعبون يقولون «تقطيع»، فتأكّد أولًا هل الأمر يتعلق بعرض العميل أو مسافة العرض أو تذبذب الشبكة، ولا تشغّل المحلّل على العمياء.
