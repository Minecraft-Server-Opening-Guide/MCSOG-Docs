المقالات السابقة تناولت «تدخل إلى الجهاز وتكتب الأوامر بنفسك». وهذه تتناول أسلوبًا آخر شائعًا في التشغيل: **تسليم الخادم إلى لوحة تحكّم ويب** — تفتح المتصفّح فتشغّل النسخ وتوقفها، وتنظر وحدة التحكّم، وترفع الملفات، وتعدّل الإعداد.

اللوحة مفيدة فعلًا، لكنها **أعلى خدمة صلاحيةً على هذا الجهاز وأكثرها عرضةً لأن تكون هدفًا**. فليس محور هذه المقالة «ما تستطيع اللوحة فعله»، بل **ما يضيفه استخدامها إلى سطح الهجوم، وكيف تستعيده**.

:::note موقع هذه المقالة
تتناول هذه المقالة **طريقة الاستخدام وحدود الأمان** فقط، ولا تُغني عن التوثيق الرسمي لتثبيت كل لوحة. فأوامر التثبيت والمنافذ الافتراضية وبنية الأدلة **تتبع التوثيق الرسمي كله**؛ وتعطي المقالة فقط القيم الافتراضية التي روجعت مع المصادر الرسمية، مع بيان المصدر.
:::

## 1. ما تستطيع اللوحة فعله، وما ثمنه

### 1.1 القدرات التي تقدّمها اللوحة عادةً

| القدرة | المظهر المحدّد | متى توفّر عناءً فعلًا |
| --- | --- | --- |
| **واجهة إدارة ويب** | تشغيل وإيقاف وإعادة تشغيل وعرض الحالة من المتصفّح، بلا حفظ أوامر كثيرة | إعادة تشغيل طارئة من الهاتف |
| **إدارة نسخ متعددة** | تشغيل عدة خوادم على جهاز واحد والتبديل بينها موحّدًا | وجود خادم بقاء وإبداع واختبار معًا |
| **الوصول إلى وحدة التحكّم** | رؤية السجل الحيّ في الصفحة وإرسال الأوامر مباشرةً | تشخيص سبب انهيار الخادم عن بُعد |
| **مدير الملفات** | رفع وتنزيل وتحرير jar والإعداد وملفات العالم | تغيير حزمة لاعبين، وإضافة ملحق |
| **المهام المجدولة** | إعادة تشغيل مجدولة، ونسخ مجدول، وتنفيذ أوامر مجدول | إعادة تشغيل كل فجر لتحرير الذاكرة |
| **صلاحيات المستخدمين والفرعيين** | منح مشرف أو مساعد صلاحية تشغيل بعض النسخ | تمكين المساعد من إعادة تشغيل الخادم بلا منحه SSH |
| **إحصاءات الموارد** | منحنيات المعالج والذاكرة والقرص وعدد المتصلين | الحكم: هل المشكلة في الإعداد أم في الجهاز |
| **تكامل Docker** | عزل النسخ بالحاويات وتقييد مواردها | عدم تداخل النسخ المتعددة |

:::note مجموعة الوظائف تختلف بحسب اللوحة
الجدول أعلاه القدرات الشائعة لـ«أدوات اللوحات» هذه الفئة، **وهل تقدّمها لوحة معيّنة، وأين مدخلها، يتبع توثيق تلك اللوحة وواجهتك الفعلية**.
:::

### 1.2 قائمة الأثمان

| الثمن | ملاحظة |
| --- | --- |
| **خدمة إضافية تحتاج صيانة** | فاللوحة تطبيق ويب، تحتاج تحديثًا ومتابعة إعلانات أمنية ونسخًا لبياناتها |
| **اتساع سطح الهجوم** | منفذ استماع إضافي، ومنظومة حسابات إضافية، وواجهة API إضافية |
| **تمركز عالٍ للصلاحيات** | فاللوحة (خصوصًا خدمتها الحارسة) تستطيع تشغيل أي عملية وقراءة وكتابة أدلة النسخ، ومن يحصل عليها يحصل على كل خوادم هذا الجهاز |
| **وكيل عكسي أكثر تعقيدًا** | فاللوحة تحتاج WebSocket غالبًا؛ وبعض اللوحات تطلب من المتصفّح الاتصال بالخدمة الحارسة مباشرةً (انظر 3.1) |
| **اتساع سطح الأعطال** | سقوط اللوحة لا يعني سقوط الخادم، لكنك قد تفقد وسيلة الإدارة مؤقتًا |

:::warn فهم الخطر في جملة
**اللوحة ليست «برنامجًا آخر»، بل «المفتاح العام لكل خوادم اللعبة على هذا الجهاز».** ففتح صفحة تسجيل دخولها للإنترنت العام يعني تعليق إدارة الجهاز كله على الإنترنت.
:::

### 1.3 ارسم حدود الثقة أولًا

قبل استخدام اللوحة، ارسم هذا الخط في ذهنك بوضوح:

- **ما تستطيع اللوحة التحكّم فيه = ما تستطيع هوية تشغيلها التحكّم فيه.**
- فإن كانت اللوحة تعمل بـ root، فثغرة تنفيذ كود عن بُعد واحدة فيها تعني سقوط الجهاز كله.
- **وواجهة API للخدمة الحارسة هي بذاتها واجهة «تنفيذ أوامر»** — وهذا معنى وجودها. فبمجرد تعريضها يكون الأمر كتعليق shell على الإنترنت.

## 2. MCSManager (MCSM)

### 2.1 التوصيف الرسمي

يصف مستودع MCSManager الرسمي نفسه بأنه: **«لوحة إدارة حديثة لخوادم Minecraft وSteam، بتثبيت سريع وبنية موزّعة ومستخدمين متعددين»** (والنصّ الإنجليزي: "Quick deployment, distributed, multi-user, modern management panel for Minecraft and Steam game servers"). ويوضّح التوثيق الرسمي كذلك أنها **مفتوحة المصدر وموزّعة وتُثبَّت بأمر واحد**، وأنها لوحة تحكّم لخوادم Minecraft وSteam، تساعدك على إدارة عدة خوادم فيزيائية مركزيًا، وإنشاء خوادم ألعاب على أي مضيف، وتوفّر منظومة صلاحيات متعددة المستخدمين آمنة وموثوقة.

والكلمات الثلاث المفتاحية في هذا النصّ هي تموضعها:

| الكلمة | المعنى |
| --- | --- |
| **تثبيت بأمر واحد** | توفّر سكربت تثبيت يسجّل نفسه خدمة نظام |
| **موزّعة** | لوحة واحدة تستطيع إدارة **عدة** أجهزة |
| **متعددة المستخدمين** | منظومة حسابات وصلاحيات مدمجة، تتيح منح الصلاحية لمساعد بدل منحه SSH |

### 2.2 البنية: لوحة واحدة + خدمة حارسة أو أكثر

يقسّم التوثيق الرسمي MCSManager إلى جزأين:

| المكوّن | المسؤولية في الوصف الرسمي |
| --- | --- |
| **Panel (لوحة الويب)** | إدارة المستخدمين، والاتصال بالخدمة الحارسة، وتوثيق معظم العمليات، وAPI |
| **Daemon (الخدمة الحارسة)** | إدارة العمليات (حيث تعمل النسخ فعلًا)، وإدارة صور Docker، وإدارة الملفات، والتواصل الحيّ مع الطرفية |

ومعنى «موزّعة» هنا: **اللوحة نفسها لا تشغّل الخوادم**، بل ترسل الأوامر إلى الخدمات الحارسة على الأجهزة، فتشغّل الخدمة الحارسة النسخ وتديرها محليًا. فيمكنك أن تكون «لوحة واحدة + N عقدة حارسة».

:::warn أسماء المكوّنات وأوامر التثبيت والمنافذ الافتراضية وبنية الأدلة تتبع التوثيق الرسمي
قد تتغيّر أسماء خدمات MCSManager وعنوان سكربت التثبيت والمنافذ الافتراضية ودليل البيانات بحسب النسخة. **والقيم المذكورة هنا تمثّل القيم الافتراضية في التوثيق الرسمي وقت الكتابة فقط، فاعتمد التوثيق الرسمي وملف الإعداد الفعلي على جهازك.** ولا تنسخ في بيئة الإنتاج أي منفذ أو مسار لم تتحقّق منه.
:::

**والقيم الافتراضية التي روجعت مع التوثيق الرسمي (لل مقارنة، ويُستحسن التأكد بنفسك):**

| البند | القيمة الافتراضية في التوثيق الرسمي | ملاحظة |
| --- | --- | --- |
| منفذ ويب اللوحة | `23333` | يُعدّل في `httpPort` في ملف إعداد الويب |
| منفذ الخدمة الحارسة | `24444` | يُعدّل في `port` في ملف إعداد الخدمة الحارسة |
| أسماء خدمات Linux | `mcsm-web`، و`mcsm-daemon` | خدمات systemd |
| دليل تثبيت السكربت | `/opt/mcsmanager` | مسار المثال الرسمي |
| ملف إعداد الويب | `<دليل تثبيت Web>/data/SystemConfig/config.json` | يضم `httpPort` و`httpIp` و`loginCheckIp` وغيرها |
| ملف إعداد الخدمة الحارسة | `<دليل تثبيت Daemon>/data/Config/global.json` | يضم `port` و`key` و`defaultInstancePath` وغيرها |
| مفتاح الخدمة الحارسة | حقل `key` في `global.json` أعلاه | وتطبعه الخدمة الحارسة عند التشغيل أيضًا |

:::tip تحذير رسمي يسهل إغفاله جدًا
يوضّح توثيق «النشر الموزّع» الرسمي: على العقدة التي تشغّل الخدمة الحارسة فقط **يجب أولًا إيقاف خدمة الويب وتعطيلها**، وإلا **استطاع أي أحد الوصول إلى صفحة الإعداد الأولية والاستيلاء على خادمك**:

```bash
systemctl stop mcsm-web
systemctl disable mcsm-web
```

وهذا التحذير يستحق الحفظ منفردًا: **«خدمة الويب التي نسيت إيقافها» تعني سقوطًا كاملًا.**
:::

### 2.3 التثبيت وأول تسجيل دخول

سكربت التثبيت الرسمي لأمر واحد على Linux (ويشدّد التوثيق الرسمي: لأنه يسجّل خدمة نظام، **فيجب تشغيله بصلاحية root**):

```bash
sudo su -c "wget -qO- https://script.mcsmanager.com/setup.sh | bash"
```

:::note عنوان السكربت يختلف بين الوثيقة الصينية والإنجليزية
يستخدم التوثيق الإنجليزي الرسمي `setup.sh`، والصيني `setup_cn.sh`. **فاعتمد العنوان الذي يعطيه التوثيق الرسمي باللغة التي تقرأها**، ولا تكتب عنوان السكربت من الذاكرة. وللتوثيق الرسمي أيضًا فصل تثبيت Docker وعزل البيئة (Docker)، وخطواته تتبع التوثيق الرسمي كذلك.
:::

وبعد التثبيت شغّل الخدمتين بحسب التوثيق الرسمي (ويشدّد على أن إحداهما لا تُغني عن الأخرى):

```bash
# شغّل الخدمة الحارسة أولًا، ثم خدمة الويب
systemctl start mcsm-daemon.service
systemctl start mcsm-web.service

# عند الحاجة إلى التشغيل التلقائي عند الإقلاع
systemctl enable mcsm-web.service
systemctl enable mcsm-daemon.service
```

وفي التثبيت اليدوي، طريقة التشغيل التي يعطيها التوثيق الرسمي هي `./install.sh` و`./start-daemon.sh` و`./start-web.sh`، مع تنبيه إلى أن التشغيل اليدوي يحتاج أداة مثل screen لتولي العملية، وإلا أنهى النظام العملية بعد انقطاع SSH. ونسخة Windows يوضّح التوثيق الرسمي أنها تُنزَّل كأرشيف مضغوط ويُفكّ ثم يُشغَّل (وإن كان الأرشيف يحوي مشغّلًا فيمكن التشغيل به).

**وما يجب فعله عند أول تسجيل دخول (ولا تُقلب الترتيب):**

1. ادخل إلى اللوحة بحساب مشرف (ومعلومات الحساب الأولية بحسب التوثيق الرسمي ومخرجات تثبيتك).
2. **بدّل كلمة المرور الافتراضية فورًا**، واستخدم كلمة مرور طويلة مختلفة عن بقية مواقعك.
3. ضعها خلف وكيل عكسي HTTPS كما في 3.5، أو قيّد عناوين المصدر على الأقل.
4. افحص عنوان الاستماع والمنفذ، وتأكّد من عدم تعريض الخدمة الحارسة للإنترنت العام مباشرةً.

### 2.4 سير العمل النمطي: من التثبيت إلى تشغيل نسخة

الخطوات التي يعطيها توثيق «إعداد إصدار Java» الرسمي إجمالًا كما يلي (والتفاصيل بحسب التوثيق الرسمي):

| الخطوة | ما تفعل | ملاحظة |
| --- | --- | --- |
| 1 | ثبّت اللوحة + الخدمة الحارسة (أو استخدم Docker بحسب التوثيق الرسمي) | أبقِ على عقدة العمل الخدمة الحارسة وحدها |
| 2 | سجّل الدخول وبدّل كلمة المرور الافتراضية | انظر 2.3 |
| 3 | تأكّد من عقدة الخدمة الحارسة أو أضفها في اللوحة | تحتاج عنوانًا ومفتاحًا؛ ويوضّح التوثيق الرسمي أن العنوان يقبل IP والنطاق، ويقبل بادئتي `ws://` / `wss://` |
| 4 | انقر «إنشاء» في صفحة «النسخ» | ويمكن التثبيت من السوق، أو «إنشاء مباشر» واختيار العقدة المراد التشغيل عليها |
| 5 | اكتب أمر التشغيل | مثال رسمي: `java -Dfile.encoding=UTF-8 -jar "paper-<version>.jar"`، ويمكن إضافة `-Xms` / `-Xmx` |
| 6 | ارفع ملفات الخادم | ارفع jar النواة بـ«إدارة الملفات» في اللوحة |
| 7 | انقر «تشغيل» في وحدة تحكّم النسخة وراقب السجل | أول تشغيل يحتاج عادةً تغيير `eula.txt` إلى `eula=true` في «ملفات الإعداد» |
| 8 | أنشئ حسابًا فرعيًا للمساعد، وامنحه النسخ اللازمة فقط | لا تمنحه «كل النسخ + إدارة الملفات» |

ويوضّح التوثيق الرسمي كذلك أن بيانات النسخة في `<دليل تثبيت Daemon>/data/InstanceData/<معرّف النسخة>/` افتراضيًا، وإعداد النسخة في `<دليل تثبيت Daemon>/data/InstanceConfig/<معرّف النسخة>.json` (وفيه أمر التشغيل وغيره). **وهذان الموضعان «يصعب إعادة بنائهما بعد الضياع»، فيجب إدخالهما في النسخ الاحتياطي.**

:::warn لا تطمع في وسائط الذاكرة في أمر التشغيل
يحذّر التوثيق الرسمي تحديدًا: **لا تخصّص كل ذاكرة الجهاز لـ JVM**، فنظام التشغيل نفسه يحتاج موارد، وإلا فقد ينهار الجهاز كله. ويجب أن يكون `-Xmx` أقلّ بوضوح من ذاكرة الجهاز الفيزيائية.
:::

### 2.5 متى تفيدك اللوحة فعلًا

- **نسخ متعددة**: فإعادة تشغيل عشرة خوادم واحدًا واحدًا عبر SSH غير عملي.
- **منح المساعد صلاحية محدودة**: ليعيد التشغيل ويقرأ السجل **بلا SSH** — وهذا أكبر مكسب أمني للوحة.
- **إعادة تشغيل ونسخ مجدولان**: أدوات اللوحات توفّر قدرة المهام المجدولة عادةً، **وهل يوفّرها MCSManager وأين مدخلها وكيف تُضبط، يتبع التوثيق الرسمي وواجهتك الفعلية**.
- **إدارة عدة أجهزة**: لوحة واحدة + خدمات حارسة متعددة، ومدخل موحّد.
- **لمن لا يعرف سطر الأوامر**: تقييد العمل داخل حدود وظائف اللوحة أأمن غالبًا من منح shell مباشرةً.

## 3. أمان اللوحة (الأهم)

### 3.1 المبدأ الأول: لا تعرّض اللوحة وAPI الخدمة الحارسة للإنترنت العام مباشرةً

هذا البند أهمّ من كل ما سواه مجتمعًا:

:::warn لا تعرّض منفذ الخدمة الحارسة للإنترنت العام
مهمة API الخدمة الحارسة هي **تشغيل العمليات وقراءة وكتابة الملفات وتنفيذ الأوامر** — فهي في جوهرها **واجهة تنفيذ كود عن بُعد**، ملفوفة بطبقة توثيق فقط. **وبمجرد تعريضها، لا يحتاج المهاجم إلا تسريب مفتاح واحد أو تجاوز توثيق واحد أو ثغرة غير مُرقَّعة لينفّذ أي أمر على جهازك.** والأمر نفسه في جهة ويب اللوحة، لكن عندها صفحة تسجيل دخول على الأقل.
:::

والتصرف الصحيح:

1. **اللوحة**: اربطها بـ`127.0.0.1` أو بعنوان داخلي، وأخرجها عبر وكيل عكسي HTTPS، وأضف طبقة تقييد للمصدر (VPN، أو قائمة IP بيضاء، أو قاعدة جدار حماية).
2. **الخدمة الحارسة**: لا تسمح بالوصول إلا لمضيف اللوحة (والعملاء الذين يحتاجون اتصالًا مباشرًا).
3. **ولا تفتح منفذ الخدمة الحارسة على `0.0.0.0` «للتسهيل».**

:::note ما يميّز MCSManager: المتصفّح يحتاج الاتصال بالخدمة الحارسة مباشرةً
يوضّح توثيق «بنية الشبكة» الرسمي في MCSManager: لتجنّب أن تصبح اللوحة عنق زجاجة للترافيك الكثيف (رفع الملفات، وسجلات وحدة التحكّم)، **يتواصل المتصفّح مع الخدمة الحارسة مباشرةً في هذا الترافيك**. ولذلك يوضّح التوثيق أن عنوان الخدمة الحارسة **لا يجوز أن يكون عنوانًا في الشبكة المحلية**، وإلا بقي حالة الخدمة الحارسة على «جارٍ الاتصال».

وتبعًا لذلك نتيجتان يجب معرفتهما:

- إن رقّيت اللوحة إلى HTTPS، **فكل خدمة حارسة تحتاج وكيلًا عكسيًا HTTPS مستقلًا أيضًا**، ويجب تغيير العنوان في اللوحة إلى `wss://...`؛ فالتوثيق الرسمي يوضّح أن المتصفّح **يرفض** الاتصال بالخدمة الحارسة عبر WebSocket غير مشفّر.
- والنصيحة العامة «الخدمة الحارسة في الشبكة الداخلية فقط» تُنفَّذ في MCSManager بحسب بنية الشبكة في التوثيق الرسمي: **إما بإعداد وكيل عكسي HTTPS كما يوضّح التوثيق الرسمي، أو بحماية مسار «المتصفّح إلى الخدمة الحارسة» بـ VPN أو نفق**، ولا تُعرّض المنفذ للإنترنت العام ببساطة.

**وكيفية الإعداد المحدّدة تتبع فصلَي «بنية الشبكة» و«استخدام HTTPS عبر NGINX» في التوثيق الرسمي.**
:::

### 3.2 لا تشغّل بـ root

| الحالة | الواقع (من التوثيق الرسمي) | التوصية |
| --- | --- | --- |
| سكربت MCSManager بأمر واحد | يوضّح التوثيق الرسمي أن **السكربت يجب أن يعمل بصلاحية root لأنه يسجّل خدمة نظام** | التثبيت يمكن بـ root، لكن **النسخ يُفضّل عزلها بمستخدم مخصّص أو حاوية**؛ وللتوثيق الرسمي فصل «عزل البيئة (Docker)» |
| Pterodactyl Wings | وحدة systemd في التوثيق الرسمي فيها `User=root` | هذا تصميم رسمي (فـ Wings يحتاج التحكّم في Docker)؛ **وعزل النسخ بالحاويات هو وسيلة التخفيف نفسها** |
| لوحات الخوادم العامة | تحتاج عادةً صلاحيات عالية لإدارة خدمات النظام والمواقع | لا تخلط خادم اللعبة مع هذه اللوحات في حدود ثقة واحدة (انظر 4.2) |

والمبدأ: **ما يمكن تشغيله بلا root فلا تشغّله به؛ وحين يلزم ارتفاع الصلاحية، حاصر دائرة الانفجار بالعزل (مستخدم مستقل، أو حاوية، أو جهاز مستقل).**

### 3.3 بيانات الاعتماد والحسابات

- **بدّل كلمة المرور الافتراضية فورًا.** فالكلمة الافتراضية أول هدف للماسحات الآلية.
- استخدم كلمة مرور **طويلة وفريدة**، والأفضل أن يولّدها مدير كلمات مرور. **وتسريب كلمة مرور اللوحة = سقوط كل النسخ.**
- **إن دعمت اللوحة التحقّق بخطوتين ففعّله إلزاميًا**؛ وهل تدعمه وكيف يُفعّل، **بحسب التوثيق الرسمي**.
- **دقّق المستخدمين الفرعيين والصلاحيات دوريًا**: من بقي؟ وهل ما زال يحتاجه؟ وهل مُنحت صلاحية أكثر من اللازم؟ فـ«إدارة الملفات + كل النسخ» تكاد تساوي منح shell.
- **احذف الحسابات غير اللازمة**، بما فيها المساعدون المغادرون، والحسابات التجريبية، ومفاتيح API غير المستخدمة.
- ولا تكتب كلمة مرور اللوحة في لقطة شاشة، ولا في سجل دردشة، ولا في مستودع Git، ولا في ملف نصّي داخل دليل الخادم.

### 3.4 أبقِ اللوحة محدّثة

اللوحة تطبيق ويب، **ولها تاريخ ثغرات**. وما يجب فعله:

- اشترك في إصدارات المستودع الرسمي وإعلاناته الأمنية.
- رقِّ بحسب العملية التي يذكرها فصل «التحديث» في التوثيق الرسمي.
- **انسخ بيانات اللوحة نفسها احتياطيًا** قبل الترقية (انظر 3.7).

:::warn مأزق في ترقية MCSManager
ينبّه توثيق «التحديث وإعادة الضبط» الرسمي: تحديث السكربت بأمر واحد **يعيد تفعيل `mcsm-web` تلقائيًا**. فإن كنت قد عطّلت خدمة الويب عمدًا على عقدة (انظر 2.2)، **فيجب بعد التحديث إيقافها وتعطيلها يدويًا مرة أخرى**، وإلا ظهرت صفحة الإعداد الأولية من جديد.
:::

### 3.5 عنوان الاستماع والوكيل العكسي (مثال nginx)

الفكرة: **ترتبط اللوحة بعنوان الرجوع فقط، ويقدّم nginx خدمة HTTPS للخارج.** والمنافذ أدناه **عناصر بديلة**، فاستبدلها بمنفذ لوحتك.

```nginx
# /etc/nginx/conf.d/panel.conf
# <panel-port> عنصر بديل، فاستبدله بالمنفذ المحلي الذي تستمع عليه اللوحة فعلًا.
# مسار الشهادة يحدّده أداة الشهادات لديك، فلا تنسخ المسارات في المثال أدناه.

server {
    listen 80;
    server_name panel.example.com;
    # للتحويل فقط؛ وطريقة إصدار الشهادة وتجديدها بحسب توثيق أداة الشهادات التي تستخدمها
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name panel.example.com;

    # تولّدها وتجدّدها أداة الشهادات لديك، فاستبدلها بالمسارات الفعلية (مثل مخرجات certbot)
    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    # وحدة تحكّم اللوحة تعتمد WebSocket، فيجب تمرير ترويسة Upgrade
    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # قد ترفع اللوحة ملفات خادم أو حزمًا كبيرة؛ و0 تعني بلا حدّ
        client_max_body_size 0;

        # وحدة التحكّم اتصال طويل، فلا تدعها تُخزَّن مؤقتًا أو تُقطع مبكرًا
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

وبعض التوضيحات:

- `proxy_http_version 1.1` مع ترويستَي `Upgrade` / `Connection` هي مفتاح WebSocket، **وإغفال واحدة منها قد يمنع اتصال وحدة التحكّم**.
- **مسارات** `ssl_certificate` و`ssl_certificate_key` **تأتي من أداة الشهادات لديك** (certbot وغيرها)، وتختلف باختلاف الأداة وطريقة النشر، **فلا تنسخها**.
- وإن كان التوثيق الرسمي للوحة يوفّر مثال وكيل عكسي خاصًّا به (ولـ MCSManager ثلاثة فصول رسمية: NGINX وIIS وCaddy)، **فاعتمد التوثيق الرسمي** — لأن مسار الخدمة الحارسة يحتاج إعدادًا منفصلًا غالبًا.
- وبعد التعديل افحص الصيغة أولًا ثم أعد التحميل (وتوثيق MCSManager الرسمي يطلب التحقق قبل إعادة التحميل كذلك):

```bash
sudo nginx -t
sudo nginx -s reload
```

### 3.6 جدار الحماية

افتح ما يجب فقط، وارفض الباقي افتراضيًا:

| المنفذ | لمن يُفتح | ملاحظة |
| --- | --- | --- |
| 80 / 443 | الإنترنت العام | مدخل اللوحة (أو منفذ HTTPS الذي تختاره)؛ و80 للتحويل والتحقّق من الشهادة فقط |
| منفذ اللوحة المحلي | **الجهاز نفسه فقط** | فإن رُبطت اللوحة بـ`127.0.0.1` فلا حاجة إلى السماح الخارجي |
| منفذ الخدمة الحارسة | **مضيف اللوحة فقط** (أو بحسب متطلبات البنية الرسمية للتقيد بالمصدر) | لا يُفتح للإنترنت العام أبدًا؛ والمنفذ المحدّد بحسب التوثيق الرسمي |
| منافذ اللعبة | الإنترنت العام (بحسب الحاجة) | مدخل اللاعبين |
| SSH | عنوان IP الإداري | يُفضّل السماح بالدخول بالمفتاح فقط |

ومثال (المنافذ والنطاقات كلها **عناصر بديلة**، فاستبدلها بإعدادك الفعلي؛ وصيغة الأوامر بحسب توثيق توزيعتك):

```bash
# مثال ufw
sudo ufw default deny incoming
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp
# اسمح لمضيف اللوحة فقط بالوصول إلى منفذ الخدمة الحارسة
sudo ufw allow from <panel-host-ip> to any port <daemon-port> proto tcp
sudo ufw enable
sudo ufw status verbose
```

والفكرة الكاملة للمنافذ والقواعد في [أساسيات أمان الشبكة](/tutorials/ops/network-security) و[الموجّه وجدار الحماية](/tutorials/ops/router-firewall).

### 3.7 انسخ بيانات اللوحة نفسها احتياطيًا

**دليل بيانات اللوحة يحوي تعريف كل النسخ والمستخدمين والإعدادات. وضياعه يعني بقاء ملفات الخادم و«لا شيء» في اللوحة.**

| ما تنسخه | ملاحظة |
| --- | --- |
| قاعدة بيانات اللوحة ودليل إعدادها | المستخدمون، والصلاحيات، وتعريف النسخ، والمهام المجدولة |
| إعداد الخدمة الحارسة | المنفذ، والمفتاح، وإعداد النسخ |
| دليل بيانات النسخ | العالم، والملحقات، والإعداد (وهو الأكبر حجمًا عادةً) |

:::warn المسارات بحسب التوثيق الرسمي
موضع دليل بيانات كل لوحة مختلف، **فيجب تأكيده من التوثيق الرسمي قبل كتابته في سكربت النسخ**، ولا تكتب مسارًا بالتخمين.

وبمثال MCSManager، المواضع التي يعطيها التوثيق الرسمي: إعداد الويب في `<دليل تثبيت Web>/data/SystemConfig/config.json`، وإعداد الخدمة الحارسة في `<دليل تثبيت Daemon>/data/Config/global.json`، وبيانات النسخ في `<دليل تثبيت Daemon>/data/InstanceData/<معرّف النسخة>/`، وإعداد النسخة في `<دليل تثبيت Daemon>/data/InstanceConfig/<معرّف النسخة>.json`. أما توثيق «التحديث وإعادة الضبط» الرسمي فيوصي مباشرةً: **انسخ الدليلين `web/data` و`daemon/data` إلى مكان آخر قبل الترقية.**
:::

وتوصيات النسخ:

- تُحفظ نسخة بيانات اللوحة **بلا اتصال أو خارج الموقع**، **ولا تستطيع عملية اللوحة نفسها الكتابة في ذلك الموضع** (وإلا حُذفت النسخة معًا عند اختراق اللوحة).
- والنسخة تحوي قاعدة بيانات اللوحة ومفاتيحها، **فيجب تشفيرها أو تقييد صلاحياتها بصرامة**.
- ونفّذ **تجربة استعادة** دورية — فالنسخ بلا استعادة كالنسخ غير الموجود. والطريقة المحدّدة في [النسخ الاحتياطي والاستعادة](/tutorials/java/backup) و[النسخ الاحتياطي خارج الموقع](/tutorials/ops/offsite-backup).

### 3.8 ماذا يحدث إن اختُرقت اللوحة

اكتب أسوأ حالة بوضوح لتعرف ما يجب أن تمنعه:

| ما يحصل عليه المهاجم | النتيجة |
| --- | --- |
| حساب اللوحة | التحكّم في **كل النسخ**: حذف الأرشيف، وتغيير الإعداد، وطرد اللاعبين، ومنح نفسه op |
| اللوحة + إدارة الملفات | رفع jar أو ملحق خبيث، وإدخال باب خلفي إلى الخادم |
| API الخدمة الحارسة | **تنفيذ أي أمر على الجهاز** (وهذه وظيفتها أصلًا)، وهو غالبًا يساوي shell مباشرةً |
| قاعدة بيانات اللوحة أو مفاتيحها | وصول مستديم: فحتى لو بدّلت كلمة المرور قد يبقى مفتاح API القديم والجلسات صالحة |
| صلاحية الكتابة في دليل النسخ | **حذف نسخك الاحتياطية**، فتتعذّر الاستعادة (وهي طريقة شائعة في الفدية والانتقام) |

ولذلك: **بمجرد الشك في اختراق اللوحة، تعامل مع الأمر كـ«الجهاز كله سقط».**

1. اقطع فورًا مدخل الإنترنت العام للوحة والخدمة الحارسة (بتعديل جدار الحماية، لا بتغيير كلمة المرور فقط).
2. بدّل **كل** بيانات الاعتماد: حساب اللوحة، ومفتاح الخدمة الحارسة، وكلمة مرور RCON في الخادم، وكلمة مرور قاعدة البيانات، وAPI Key لمزوّد السحابة.
3. افحص ظهور حسابات مشرف جديدة، أو مفاتيح API جديدة، أو مهام مجدولة شاذة.
4. افحص دليل الخادم: هل دُسّت فيه ملفات jar أو ملحقات أو سكربتات مجدولة مريبة.
5. استعِد من نسخة **معروفة النظافة**، لا أن «تنظّف قليلًا وتواصل» على جهاز مخترق.
6. راجع سبب التعرّض (منفذ مكشوف، أم كلمة مرور ضعيفة، أم ترقيع فائت)، انظر [أساسيات أمان الشبكة](/tutorials/ops/network-security) و[تقوية أمان النظام](/tutorials/ops/system-security).

والعملية الكاملة للمعالجة في [الطوارئ والتحقيق](/tutorials/ops/incident-forensics).

## 4. لوحات أخرى وكيف تختار

### 4.1 Pterodactyl

يصف Pterodactyl نفسه رسميًا بأنه: **لوحة إدارة خوادم ألعاب مجانية ومفتوحة المصدر، مبنية بـ PHP وReact وGo؛ مصمّمة للأمان، وكل خوادم الألعاب تعمل في حاويات Docker معزولة**، ويقدّم للمستخدم النهائي واجهة ويب بديهية. وهو مشروع مفتوح المصدر برخصة MIT، ويشدّد رسميًا على تجزئة كلمات المرور بـ bcrypt، والتشفير AES-256-CBC، ودعم HTTPS جاهزًا.

وبنيته تنتمي إلى فئة «لوحة + خدمة حارسة على العقد» نفسها. والتعريفات في قائمة المصطلحات الرسمية:

| المصطلح | المعنى الرسمي |
| --- | --- |
| **Panel** | لوحة Pterodactyl نفسها، وتُستخدم لإضافة العقد والخوادم |
| **Node** | الجهاز الفيزيائي الذي تشغّل عليه نسخة Wings |
| **Wings** | خدمة الجيل الجديد المكتوبة بـ Go، تتصل بـ Docker وPanel، وتتحكّم في الخوادم بأمان عبر اللوحة |
| **Server** | نسخة ينشئها اللوحة وتعمل على عقدة؛ وقد تكون للعقدة عدة نسخ |
| **Docker / Image / Container** | بيئة تشغيل معزولة؛ وكل خادم يعمل في حاوية مستقلة لتقييد المعالج والذاكرة وتجنّب التداخل |
| **Nest / Egg** | الـ Nest يقابل لعبة أو خدمة عادةً، والـ Egg يحفظ إعداد فئة معيّنة من اللعبة |
| **Yolks** | مجموعة صور Docker الأساسية المرافقة لمنظومة Egg |

والنقاط المهمة (وكلها من التوثيق الرسمي):

- Wings **يدعم Linux فقط**، ويوضّح التوثيق أن بيئة Windows لا تصلح؛ ويلزم نظام يستطيع تشغيل Docker، وأنواع المحاكاة الافتراضية مثل OpenVZ وLXC لا تصلح عادةً (ويقترح التوثيق الفحص بـ`systemd-detect-virt`).
- وعملية التثبيت الرسمية: أنشئ العقدة في اللوحة أولًا، ثم الصق الإعداد الذي تولّده اللوحة في `/etc/pterodactyl/config.yml` على العقدة (أو استخدم الأمر الذي يعطيه «توليد رمز»)، ثم شغّل Wings كخدمة systemd.
- ووحدة systemd التي يعطيها التوثيق الرسمي فيها `User=root`، وهذا تصميم رسمي.
- ويوضّح التوثيق الرسمي: **عند تفعيل SSL في اللوحة يجب أن يضبط Wings شهادة لنطاقه المؤهّل (FQDN) أيضًا.**
- وتحتاج العقدة إلى إعداد allocation (تركيبة IP ومنفذ)، ولكل خادم واحد منها على الأقل؛ وينبّه التوثيق إلى **عدم استخدام `127.0.0.1`**.

:::note ما لم يُراجَع بندًا بندًا
**أوامر التثبيت المحدّدة والمنافذ الافتراضية وبنية الأدلة ومتطلبات النسخ في Pterodactyl تتغيّر بحسب النسخة**، ولا تسردها هذه المقالة، **فاعتمد التوثيق الرسمي كله**: تثبيت اللوحة في Getting Started في توثيق Panel الرسمي، والخدمة الحارسة للعقدة في Installing Wings في توثيق Wings الرسمي.
:::

### 4.2 لوحات الخوادم العامة (1Panel وBaota وغيرهما)

هذه الأدوات **ليست لوحات خوادم ألعاب**، بل تدير **أمورًا على مستوى نظام التشغيل**: المواقع، وقواعد البيانات، والحاويات، والملفات، والمهام المجدولة، وجدار الحماية وغيرها.

وبمثال 1Panel، التوصيف الرسمي هو **«لوحة حديثة ومفتوحة المصدر لإدارة تشغيل خوادم Linux»** (وهي أيضًا منصّة إدارة خفيفة للذكاء الاصطناعي)، وتقدّم واجهة إدارة ويب بديهية لإدارة مراقبة المضيف والملفات وقواعد البيانات والحاويات والمهام المجدولة، وتتكامل بعمق مع برامج إنشاء المواقع مثل WordPress وHalo؛ وتوفّر رسميًا قدرات أمان مثل WAF وتدقيق السجلات والنسخ الاحتياطي.

**والفرق بينها وبين لوحات الألعاب:**

| البُعد | لوحة خوادم الألعاب | لوحة الخوادم العامة |
| --- | --- | --- |
| موضوع الإدارة | نسخ الألعاب (عملية أو حاوية) | خدمات النظام، والمواقع، وقواعد البيانات، والحاويات |
| هل تفهم اللعبة | ترى وحدة التحكّم، وترفع الملحقات، وتضبط أمر التشغيل | لا تفهمها عادةً، وتديرها كعملية أو حاوية عادية |
| نطاق الصلاحية | النسخ والخدمة الحارسة | **النظام كله في كثير من الأحيان** |
| الاستخدام النمطي | نسخ متعددة، ومنح المساعد صلاحية | إنشاء مواقع، وتشغيل خدمات، وإدارة Docker |

**ومخاطر إدارة خادم لعبة بلوحة عامة:**

- **صلاحيات أوسع**: فهذه اللوحات تحتاج إدارة خدمات النظام والملفات عادةً، وسطح تأثيرها عند الاختراق أوسع من لوحة ألعاب.
- **لا تفهم اللعبة**: فهي لا تتولّى تفاصيل مثل «أرسل stop وانتظر انتهاء حفظ العالم»، ويسهل أن تقتل الخادم قتلًا قسريًا كعملية عادية.
- **طبقة إضافية**: فأنت تصون «طريقة نشر خادم اللعبة» و«اللوحة العامة» معًا، ويتضاعف سطح الهجوم.
- **ظهرت فيها ثغرات خطيرة تاريخيًا**: فلوحات الخوادم العامة هدف رئيسي للمسح على الإنترنت. **وأي لوحة يجب التعامل معها كـ«بنية تحتية موجّهة للإنترنت»** — تحديث في حينه، وتقييد المصدر، وتفعيل مصادقة قوية. **ومعلومات الثغرات المحدّدة بحسب الإعلانات الأمنية الرسمية لكل مصنّع، ولا تعتمد على الشائعات.**

:::tip تركيبة أثبت
إن احتجت لوحة عامة فعلًا (مثل وجود موقع على الجهاز نفسه)، **فضع خادم اللعبة على جهاز مستقل، أو مستخدم مستقل، أو حاوية مستقلة**، ولا تخلط صلاحيات اللوحة العامة ونسخ الألعاب في حدود ثقة واحدة. والتقوية على مستوى النظام في [تقوية أمان النظام](/tutorials/ops/system-security).
:::

| --- | --- | --- | --- | --- |

## 5. توصيات عملية

### 5.1 ترتيب التثبيت

1. **قوِّ النظام أولًا** (مستخدم مخصّص، ومفاتيح SSH، وجدار حماية، وتحديث تلقائي)، انظر [تقوية أمان النظام](/tutorials/ops/system-security).
2. **ثم ثبّت اللوحة**، وبدّل كلمة المرور الافتراضية فورًا.
3. **ضع اللوحة خلف وكيل عكسي HTTPS**، وقيّد المصدر (VPN، أو قائمة IP بيضاء، أو قاعدة جدار حماية).
4. **وأخيرًا اربط عقد الخدمة الحارسة**، وأبقِ على العقدة الخدمة الحارسة فقط، وأوقف خدمات الويب الزائدة.
5. أنشئ نسخة، وارفع الملفات، وشغّل وحدة التحكّم.
6. اضبط المهام المجدولة والنسخ الاحتياطي.
7. أنشئ حسابًا فرعيًا للمساعد، وامنحه أدنى صلاحية.

**ولا** تشغّله أولًا «مكشوفًا على الإنترنت» ثم تصلح لاحقًا — فكل دقيقة تكون اللوحة فيها مكشوفة على الإنترنت تُمسح.

### 5.2 قائمة التقوية

- [ ] اللوحة والخدمة الحارسة **غير قابلتين للوصول مباشرةً من الإنترنت العام**
- [ ] اللوحة تُفتح عبر HTTPS، وWebSocket يعمل
- [ ] كلمة المرور الافتراضية مبدّلة؛ ومَن تدعم التحقّق بخطوتين فعّله
- [ ] صلاحيات ملفات إعداد اللوحة والخدمة الحارسة مشدّدة (والملفات التي تحوي مفاتيح أو كلمات مرور لا تكون مقروءة للجميع)
- [ ] النسخ تعمل بمستخدم مخصّص أو في حاوية، لا بـ root
- [ ] بيانات اللوحة منسوخة، وموضع النسخة لا تستطيع اللوحة الكتابة فيه
- [ ] مشترك في الإعلانات الأمنية الرسمية، وعملية التحديث لديك واضحة
- [ ] صلاحيات المستخدمين الفرعيين مدقّقة
- [ ] لا توجد صفحة إعداد أولية متبقّية على جهاز العقدة
- [ ] خطوات الطوارئ بعد الاختراق معروفة

### 5.3 ما يجب مراقبته

| بند المراقبة | لماذا |
| --- | --- |
| **عدد محاولات الدخول الفاشلة للوحة** | الإشارة الأولى للتخمين. وبعض اللوحات فيها بند إعداد من نوع «حجب IP عند فشل الدخول» (وفي إعداد ويب MCSManager يوجد `loginCheckIp`، **ومعناه وسلوكه المحدّدان بحسب التوثيق الرسمي**) |
| **نسخ جديدة شاذة** | فالمهاجم ينشئ نسخًا لتشغيل أمور أخرى غالبًا |
| **مهام مجدولة شاذة** | المهام المجدولة أسلوب شائع للاستمرار |
| **مشرفون أو مفاتيح API جديدة** | أبواب خلفية للاستمرار |
| **قفزة مفاجئة في الموارد** | المعالج أو الذاكرة أو النطاق تُستَخدم للتعدين أو إرسال الحزم |
| **نسخ اللوحة والخدمة الحارسة** | الترقيع في حينه |
| **اتصالات صادرة شاذة** | فخادم اللعبة لا يجب أن يتصل بعدد كبير من العناوين من نفسه عادةً |

ومواضع السجلات وأوامر التدقيق في [تقوية أمان النظام](/tutorials/ops/system-security)؛ والمعالجة بعد الاختراق في [الطوارئ والتحقيق](/tutorials/ops/incident-forensics).

### 5.4 متى لا تستخدم لوحة

اللوحة ليست الخيار الافتراضي. وهذه الحالات **لا تحتاج** لوحة عادةً:

- **جهاز واحد وخادم واحد**: فـ SSH + systemd أبسط، وسطح هجوم أقل. راجع [النشر إلى بيئة يمكن الوصول إليها](/tutorials/java/deploy).
- **أنت وحدك تستخدمه وتتقن سطر الأوامر**: فعائد اللوحة (التمثيل البصري، وتوزيع الصلاحيات) لا تحتاجه، وثمنها (خدمة إضافية، ومنظومة حسابات إضافية) تدفعه.
- **موارد الجهاز مشدودة**: فاللوحة نفسها تستهلك ذاكرة، وهي غير مجدية على جهاز بذاكرة صغيرة.
- **لا تنوي صيانتها**: **فلوحة غير محدّثة أخطر من عدم وجود لوحة.**

وبالمقابل، يكفي تحقّق أي بند من التالي لتستحق اللوحة عادةً: عدة نسخ، أو عدة أجهزة، أو الحاجة إلى منح المساعد صلاحية محدودة، أو الحاجة إلى مهام مجدولة، أو الحاجة إلى إتاحتها لمن لا يعرف سطر الأوامر.
