في لحظة التعرّض للهجوم يوجد على الجهاز نوعان من الأشياء في الوقت نفسه: **أدلة يمكن تسجيلها**، و**حالات ستختفي نهائيًا بعد دقائق**. وتتناول هذه المقالة النوع الثاني — تثبيت الوضع قبل إعادة التشغيل أو التثبيت أو حجب أي شيء. والمحتوى الوقائي في [أساسيات أمان الشبكة](/tutorials/ops/network-security) و[أنواع الهجمات الشائعة والدفاع](/tutorials/ops/attack-defense).

:::warn هذه المقالة لا تُغني عن رأي قانوني
أوامر التحقيق ومتطلبات حفظ السجلات وقواعد معالجة المعلومات الشخصية **تختلف بحسب نظام التشغيل والتوزيعة والمزوّد والاختصاص القضائي**؛ وكل ما يتغيّر بحسب البيئة سيُوسَم بوضوح. وعند التعامل مع بيانات شخصية للاعبين أو احتمال دخول إجراءات قانونية، **استشر مختصًّا والتزم بالقانون المحلي وسياسة مركز البيانات**.
:::

## 1. لماذا «التحقيق أولًا» قاعدة حديدية

### 1.1 الأدلة تختفي

أول ما يفعله أكثر الناس عند التعرّض لهجوم هو **إعادة التشغيل** أو **إعادة التثبيت**. وهذا أسوأ اختيار: **فإعادة التشغيل تُفني تقريبًا كل أدلة طبقة الشبكة**.

| الدليل | الموضع | طريقة الاختفاء | مدة البقاء التقريبية |
| --- | --- | --- | --- |
| العمليات والمقابس المفتوحة | الذاكرة | انتهاء العملية، أو إعادة التشغيل | من ثوانٍ إلى دقائق |
| الاتصالات الحالية (established) | جدول مقابس النواة | إغلاق الاتصال | ثوانٍ |
| جدول تتبّع الاتصالات conntrack | ذاكرة النواة | انتهاء صلاحية البند (بحسب الإعداد) | من ثوانٍ إلى ساعات |
| جدول ARP / الجيران | ذاكرة النواة | انتهاء صلاحية البند | دقائق |
| عدّادات استقبال/إرسال/فقد الحزم في البطاقة | عدّادات النواة | **تُصفَّر بإعادة التشغيل أو إعادة ضبط البطاقة** | تضيع بإعادة التشغيل |
| عدّاد إصابة قواعد جدار الحماية | netfilter في النواة | **يُصفَّر بإعادة التشغيل؛ و`iptables -Z` يصفّره أيضًا** | تضيع بإعادة التشغيل |
| ملف التقاط الحزم (pcap) | القرص | لا يُفقد إلا بالحذف أو بالكتابة فوقه عند الامتلاء | مستديم |
| سجلات النظام / سجلات الخدمة | القرص | تُضغط وتُحذف بعد التدوير | من أيام إلى أسابيع |
| سجلات التطبيق (`logs/latest.log`) | القرص | التدوير، أو الكتابة فوقها بسجل جديد | أيام |
| الإعداد والسكربتات والمهام المجدولة | القرص | تُكتب فوقها «بإصلاح سريع» | مستديمة لكنها قابلة للتعديل |
| تقارير الانهيار `crash-reports/` | القرص | لا تُحذف تلقائيًا عمومًا | مستديمة |
| مخطط الترافيك / تقرير الهجوم عند المزوّد | جهة المزوّد | تُنظَّف بحسب مدة الاحتفاظ عند المزوّد | من أيام إلى أشهر |

**والتمييز الأساسي**: **الأدلة المتلاشية (volatile)** في الذاكرة وتضيع بإعادة التشغيل؛ و**الأدلة المستديمة (persistent)** على القرص، لكنها تُفقد بالتدوير أو الكتابة فوقها أو التعديل الخاطئ. والترتيب دائمًا **تثبيت المتلاشي أولًا، ثم جمع المستديم**.

### 1.2 ماذا تُدمّر إعادة التشغيل

إعادة التشغيل الواحدة تُدمّر في الوقت نفسه: توزيع كل اتصالات TCP الحالية وعناوين مصدرها (وعليه يعتمد أساسًا الحكم: هجوم نقطة واحدة أم موزّع)، وجدول conntrack (من يتواصل مع من، وأي قاعدة تعالج الحزم)، والقيم التراكمية التاريخية لعدّادات البطاقة وعدد الحزم المفقودة، و**عدّاد إصابة قواعد جدار الحماية** (الدليل الصلب الوحيد على «كم أوقفت قواعدي فعلًا»)، والعمليات المريبة في الذاكرة (فإن كان الهجوم قد استقرّ على المضيف فإعادة التشغيل تعني تنظيف الوضع للمهاجم)، ومخازن السجلات المؤقتة التي لم تُكتب على القرص.

:::warn «لا تعِد التشغيل» لا تعني «لا تتصرف»
يمكنك التخفيف مع الحفاظ على الوضع: إضافة قواعد جدار حماية، وتحديد المعدّل، وتحويل الترافيك إلى حماية متقدّمة، وحجب مؤقت. **لكن سجّل كل تعديل** (انظر القسم 3)، لأن التعديل نفسه يغيّر الأدلة.
:::

### 1.3 الترتيب الصحيح

```text
1. لا تعِد التشغيل ولا تُعِد التثبيت ولا تُطفئ (إلا إذا تأكّدت السيطرة الكاملة على المضيف)
2. التقط الحزم أولًا (tcpdump) —— فأدلة الشبكة أسرع ما يتلاشى
3. التقط حالة النواة (ss، وconntrack، وip -s link، وعدّادات جدار الحماية)
4. التقط حالة العمليات والخدمات (ps، وsystemctl، وjournalctl)
5. انسخ السجلات والإعداد (اعمل على نسخ، ولا تمسّ الأصل)
6. احسب البصمات، واكتب سجل الحادث، وسجّل الخط الزمني (بتوقيت موحّد)
7. وبعد ذلك فقط ابدأ التخفيف والتقوية
```

## 2. ماذا تلتقط (مع الأوامر الصحيحة)

:::warn أسماء الواجهات والمسارات تختلف بحسب النظام
يُستخدم `eth0` أدناه اسمًا توضيحيًا لبطاقة الشبكة. **والواقع قد يكون `ens3` أو `enp1s0` أو `eno1` أو `bond0` وغيرها**؛ تأكّد بـ`ip -br link` أو `ip addr`. وبالمثل، فأدلة السجلات وأسماء الخدمات وأدوات جدار الحماية تختلف بين التوزيعات.
:::

```bash
ip -br link
# مثال للمخرجات (مخرجاتك ستختلف):
# lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
# eth0             UP             aa:bb:cc:dd:ee:ff <BROADCAST,MULTICAST,UP,LOWER_UP>
```

### 2.1 التقاط الحزم: tcpdump

```bash
# إصدار Java (TCP 25565)
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap 'port 25565'

# إصدار Bedrock / Geyser (UDP 19132)
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap 'udp port 19132'
```

| الوسيط | المعنى | لماذا لا بدّ منه |
| --- | --- | --- |
| `-i eth0` | تحديد البطاقة | **استبدله باسم واجهتك الفعلي**؛ وبدون تحديد يختار tcpdump بنفسه وقد يخطئ |
| `-nn` | بلا تحليل أسماء (IP والمنافذ أرقامًا) | فـ DNS العكسي **يبطئ الالتقاط ويُسقط حزمًا**؛ والأخطر أن ترافيك الهجوم يدفعك إلى **إطلاق استعلامات DNS كثيرة للخارج، أي إخبار الطرف الآخر «أنا تحت هجوم»** |
| `-s 0` | التقاط الحزمة كاملة بلا قطع | فالافتراضي يلتقط أول بايتات فقط، **وبعد قطع الحمولة يتعذّر تحليل محتوى البروتوكول**؛ و`0` تعني الطول الكامل |
| `-w ملف` | الكتابة في pcap | انظر الشرح أدناه |
| `'port 25565'` | تعبير تصفية BPF | علامات التنصيص المفردة تمنع تفسير shell؛ و`port` يطابق TCP وUDP معًا |

**ولماذا يجب الكتابة في ملف لا الطباعة على الطرفية**: فمعدّل الحزم أثناء الهجوم قد يبلغ مئات الآلاف في الثانية، وطباعة نتائج التحليل على الطرفية تجعل tcpdump **عنق زجاجة بنفسه فيُسقط حزمًا كثيرة**، ويملأ الشاشة فتفقد الطرفية معناها؛ و`-w` يكتب ثنائيًا مباشرةً، وكلفته أقل بكثير. **ولا تنسَ القرص**: فـ`-s 0` مع ترافيك سريع قد يكتب عشرات الجيجابايت في دقائق، فانظر المساحة المتبقية أولًا، وحدّ عدد الحزم بـ`-c`، أو دوّر بحسب الحجم بـ`-C` وحدّ عدد الملفات بـ`-W`:

```bash
# توقّف بعد 200000 حزمة فقط
sudo tcpdump -i eth0 -nn -s 0 -c 200000 -w /var/log/incident-cap.pcap 'port 25565'

# 100 MB لكل ملف، و20 ملفًا كحدّ أقصى (نحو 2 GB)، مع تدوير تلقائي
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap -C 100 -W 20 'port 25565'

df -h /var/log    # انظر المساحة المتبقية أولًا
```

:::tip ماذا لو لم تُلتقط حزم
**الصلاحيات**: الالتقاط يحتاج `CAP_NET_RAW`، فاستخدم `sudo` (`setcap` يوسّع سطح الخطر، ولا يُنصح به). **خطأ الواجهة**: فبطاقة الشبكة داخل الحاوية تختلف عن المضيف (الشائع `docker0` و`veth*` و`br-*`)، وقد لا يرى `eth0` على المضيف كل الترافيك. **الترافيك يُنقّى في مسار جانبي**: فبعد تنقية المزوّد قد لا يصل إلى بطاقتك إلا الترافيك الطبيعي — وهذا بالذات سبب طلب بيانات الترافيك من المزوّد (انظر 2.6). **مجموعة أمان المنصّة السحابية**: فترافيك بعض المنصّات يُسقط قبل وصوله إلى النسخة، فلا يلتقطه الجهاز.
:::

وبعد الالتقاط نفّذ إحصاءً خشنًا (لا تستخدم `tcpdump -r` لصبّ الحزم على الشاشة)؛ والتحليل البروتوكولي الأدقّ يُنصح به **بلا اتصال** على جهاز آخر بـ Wireshark / `tshark`، **ولا تحلّل أثناء الالتقاط على جهاز الإنتاج**.

```bash
# احسب الحزم فقط
sudo tcpdump -nn -r /var/log/incident-2026-10-04-1200.pcap -q | wc -l

# أكثر 20 عنوان مصدر ظهورًا
sudo tcpdump -nn -r /var/log/incident-2026-10-04-1200.pcap -q 2>/dev/null \
  | awk '{print $3}' | cut -d. -f1-4 | sort | uniq -c | sort -rn | head -20
```

### 2.2 حالة جدار الحماية والعدّادات

```bash
sudo iptables -L -v -n
sudo iptables -t nat -L -v -n

sudo nft list ruleset
sudo nft list counters
```

- `-L` يسرد القواعد، و`-v` يعرض **عدّاد الحزم وعدّاد البايتات لكل قاعدة**، و`-n` بلا تحليل أسماء (للسبب نفسه في `-nn`)؛ و`-t nat` هو جدول NAT (DNAT/SNAT وتحويل المنافذ)، ولا مفرّ من النظر إليه لتشخيص «إلى أين حُوّل الترافيك».
- **ومعنى العدّادات**: العدّادات على قواعد `DROP`/`REJECT` **تثبت مباشرةً كم ترافيك أوقفته القاعدة**، وهي أقوى رقم في المراجعة وفي شرح الأمر للمزوّد. **وإعادة التشغيل أو `iptables -Z` تصفّرها**، فيجب التقاطها في مرحلة مبكّرة من المعالجة.
- و`nft list ruleset` يعطي مجموعة القواعد كاملة (مع المجموعات والعدّادات)؛ و`nft list counters` يسرد كائنات counter المسمّاة فقط. **والقواعد التي فيها كائن counter معرّف صراحةً وحدها لها عدّاد مستقل**، وعدّاد القواعد العادية يظهر ضمنيًا كـ`counter packets N bytes M` في `list ruleset`. **وأوامر nft الفرعية وصيغة مخرجاتها تتغيّر بحسب النسخة، فاعتمد `man nft` وتوثيق التوزيعة.**

```bash
sudo iptables -L -v -n        > /root/incident/fw-iptables.txt 2>&1
sudo iptables -t nat -L -v -n > /root/incident/fw-iptables-nat.txt 2>&1
sudo nft list ruleset         > /root/incident/fw-nft.txt 2>&1
```

### 2.3 جدول الاتصالات

```bash
# اتصالات Java القائمة
ss -tan state established '( sport = :25565 )'

# مقابس UDP (إصدار Bedrock لا مفهوم «اتصال» فيه، فانظر الاستماع وطوابير الإرسال/الاستقبال)
ss -uan

# ملخّص إجمالي للمقابس (عدّ كل حالة، للحكم على كثرة الاتصالات نصف المفتوحة)
ss -s

# مع SYN-RECV، لرؤية آثار إغراق الاتصالات
ss -tan '( dport = :25565 or sport = :25565 )'

# إحصاء الاتصالات بحسب IP المصدر، لإيجاد المصادر «المركّزة في نقطة واحدة»
ss -tan state established '( sport = :25565 )' | awk 'NR>1 {print $5}' \
  | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
```

وفي `ss -tan` الحرف `t`=TCP، و`a`=كل الحالات، و`n`=بصيغة رقمية (لتجنّب تحليل DNS كذلك).

**وconntrack** (يحتاج `conntrack-tools` وأن يكون `nf_conntrack` مفعّلًا في النواة):

```bash
sudo conntrack -L    # صدّر كل الاتصالات المتتبَّعة حاليًا
sudo conntrack -S    # عدّادات الأخطاء لكل معالج
sudo conntrack -C    # عدد البنود الحالي (انظر إليه أولًا، ثم قرّر هل تنفّذ -L)
```

- `conntrack -L` **قد يكون بطيئًا أو يتوقّف عند كثرة الاتصالات**، فقيّم الحجم أولًا بـ`conntrack -C`.
- و`conntrack -S` يُخرج `insert_failed` و`drop` و`early_drop` و`error` وغيرها. **ونموّ `insert_failed` أو `early_drop` يعني امتلاء جدول تتبّع الاتصالات**، وعندها تُسقط الاتصالات الجديدة — **وهذا بذاته حجب خدمة قابل للاستغلال**، وهو خيط رئيسي في «النطاق غير ممتلئ واللاعبون لا يتصلون».

```bash
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

:::warn قد لا يوجد conntrack أصلًا
لا يظهر conntrack في الحالات التالية: **النواة لم تحمّل وحدة `nf_conntrack`**، أو **nftables صرف بلا تتبّع اتصالات**، أو **`conntrack-tools` غير مثبّتة**، أو **مساحة أسماء الحاوية لا ترى جدول المضيف**، أو **بعض نوى المنصّات السحابية المخصّصة اقتطعت هذه الوظيفة**. **وهذا ليس خطأً منك**، فاستخدم `ss` و`ip -s link` وعدّادات جدار الحماية. وبالمقابل، فبعض المضيفات ذات الذاكرة الكبيرة لها `nf_conntrack_max` مرتفع افتراضيًا، **ومدد انتهاء البنود تختلف بحسب التوزيعة والإعداد، فلا تنسخ أرقام غيرك**.
:::

### 2.4 عدّادات البطاقة والمعدّل

```bash
ip -s link show eth0
cat /proc/net/dev
```

مقطع `RX`/`TX` في `ip -s link` يعطي **bytes / packets / errors / dropped / overrun / mcast**. و**`dropped` و`overrun` هما المفتاح**: فهما يعنيان **أن الترافيك تجاوز قدرة البطاقة أو النواة على المعالجة**، وأن الحزم تُفقد حتى لو لم يمتدئ النطاق. و`cat /proc/net/dev` يعطي العدّادات نفسها لكل الواجهات، ويصلح للقطة شاملة (**قيم تراكمية تُصفَّر بإعادة التشغيل، ولا معنى إلا لفرق عيّنتين**).

```bash
# إن كانت sysstat مثبّتة، اعتن متتاليًا لمراقبة المعدّل (كل ثانية، 5 مرات)
sar -n DEV 1 5
```

:::note شرطان لـ sar
1. **يجب أن تكون `sysstat` مثبّتة** (في Debian/Ubuntu: `sudo apt install sysstat`؛ وفي عائلة RHEL: `sudo dnf install sysstat`).
2. **يجب أن يكون جمع البيانات التاريخية مفعّلًا** (يجمعه مؤقّت systemd أو cron في sysstat عادةً). **وإن لم يُفعّل قطّ فلا يستطيع `sar` الجمع إلا من الآن، ولا يرى المعدّل التاريخي لحظة الهجوم** — وهذا بالذات سبب تشغيل المراقبة في الأوقات العادية. و`sar -n DEV 1 5` بوسيط الفاصل **جمع لحظي**، ولا يتأثر بتفعيل البيانات التاريخية.
:::

و`iftop` و`nload` **أداتا مراقبة لحظية اختياريتان**:

```bash
sudo iftop -i eth0    # عرض النطاق اللحظي بحسب زوج الاتصال
sudo nload eth0       # منحنى بسيط للترافيك الداخل والخارج
```

:::warn الأدوات اللحظية لا تصلح دليلًا
`iftop` / `nload` **مقياسان لحظيان في الطرفية**، ويختفيان بالإغلاق، **ولا يصلحان مادة تحقيق**. واستخدامهما للحكم السريع على الاتجاه في الطوارئ لا بأس به، لكن **يجب الالتقاط بـ tcpdump على القرص في الوقت نفسه**. وهذه الأدوات نفسها تُسقط حزمًا عند ارتفاع معدّل الحزم، **فلا تأخذ أرقامها إحصاءً دقيقًا**. وأسماء حزم التثبيت تختلف بحسب التوزيعة، وبعضها يحتاج تفعيل مستودعات إضافية مثل EPEL.
:::

### 2.5 أدلة العمليات والخدمات

```bash
ps auxf
systemctl status <service>
journalctl -u <service> --since "1 hour ago"
```

- `ps auxf`: يسرد كل العمليات **كشجرة**، لترى هل هناك ما لا يجب أن يكون — معدّن شاذ، أو ملف تنفيذي يعمل من `/tmp`، أو عملية تتنكّر في صورة `java` وتشير إلى مسار غريب. **وعلى مضيف مخترق قد يكون `ps` نفسه مستبدلًا أو مخطوفًا، فالاستنتاجات المهمة تحتاج تحقّقًا متقاطعًا بعدة طرق.**
- `systemctl status <service>`: حالة الخدمة وآخر أسطر سجلها. واسم الخدمة يتوقّف على طريقة النشر، مثل `minecraft` أو `mcserver` أو `paper`، **وهو غير ثابت**.
- `journalctl -u <service> --since "1 hour ago"`: سجل systemd، ويدعم `--since`/`--until`، ويمكن كتابة `"1 hour ago"` و`"2026-10-04 12:00:00"` و`"today"`. **والعرض افتراضيًا بالتوقيت المحلي، وإضافة `--utc` تفرض UTC**، ويُنصح بشدة بتوحيد `--utc` في التحقيق. وإن كانت السجلات مدوّرة فصدّرها بـ`journalctl -u <service> --since ... --no-pager > ملف`، أو اقرأ ملفات الأرشيف بـ`journalctl --file`.

وعلى جهة Minecraft:

| المسار | المحتوى | ملاحظة |
| --- | --- | --- |
| `logs/latest.log` | السجل الحالي | **يُكتب فوقه عند إعادة تشغيل الخادم**، فيجب نسخه قبل إعادة التشغيل |
| `logs/YYYY-MM-DD-N.log.gz` | السجلات التاريخية (تدوير يومي/بالرقم) | مضغوطة، وما زالت دليلًا صالحًا |
| `crash-reports/` | تقارير الانهيار | لا تُنظَّف تلقائيًا عمومًا، وفيها المكدّس ومعلومات JVM |
| `plugins/*/` | سجلات كل ملحق وقواعد بياناته | **الصيغة تختلف بحسب الملحق**، والشائع سجلات الدخول وتدقيق الأوامر وسجلات الحجب |
| `banned-ips.json` / `banned-players.json` | قوائم الحجب | تسجّل ما فعلته من معالجات، وهي جزء من الخط الزمني |
| `usercache.json` / `ops.json` | تعيين اللاعبين والمشرفين | تربط الـ UUID بالأسماء |

```bash
# انسخ ولا تنقل، ولا تعدّل الأصل أبدًا
sudo cp -a /srv/minecraft/logs /root/incident/mc-logs
sudo cp -a /srv/minecraft/crash-reports /root/incident/mc-crash-reports
```

`cp -a` يحافظ على الطوابع الزمنية والصلاحيات، **وهذا مهم جدًا في التحقيق** — فـ`cp -r` يغيّر وقت التعديل إلى الوقت الحالي، فيُفسد الخط الزمني. **وسجلات طبقة التطبيق أنفع غالبًا من طبقة الشبكة**: فطبقة الشبكة تقول «هناك 40 ألف اتصال»، وطبقة التطبيق تقول «حساب معيّن حاول الدخول 900 مرة في 3 دقائق»؛ ومجموعات الصلاحيات والدخول والاقتصاد ومكافحة الغش كلها تسجّل عادةً، **وهي المصدر الرئيسي لتحديد «من فعل ماذا»**، ومواضعها وصيغها في توثيق كل ملحق.

### 2.6 الأدلة عند جهة السحابة / مركز البيانات

**ما تراه من ترافيك لا يساوي الترافيك كله.** فالمزوّد في منبع أبعد، ويرى الترافيك الداخل إلى نسختك **قبل إسقاطه** (فالترافيك الذي تُسقطه مجموعة الأمان/ACL الشبكية لا يظهر على جهازك أصلًا)، و**إجمالي نطاق الهجوم ومعدّل حزمه** (pps/Mbps) وهل أُطلقت التنقية، وتقدير نوع الهجوم وتوزيع مصادره، وقدرة سجلات التدفّق (flow logs) على جهة المنصّة — **وهل تُقدَّم وهل تُفوتر وكم مدة الاحتفاظ تختلف كثيرًا بين المزوّدين، فاعتمد توثيق المزوّد**.

**وما يجب فعله: افتح تذكرة فورًا**، موضّحًا أنك تحت هجوم، وطالبًا تفاصيل الترافيك وتقرير الهجوم، وسائلًا هل يلزم تبديل IP الحماية المتقدّمة أو تفعيل التنقية. **ولا تكتب فقط «تعرضت لهجوم»**، والتفاصيل في القسم 5.

## 3. الحفظ الصحيح للأدلة

### 3.1 احسب بصمة لكل الأدلة

```bash
cd /root/incident
sha256sum incident-*.pcap > incident.sha256
```

**ودور البصمة إثبات «أن أحدًا لم يعدّل الملف بعد جمعه»**:

- **يجب حفظ ملف البصمة منفصلًا عن الملفات المبصومة** (دليل مختلف، وقرص مختلف، والأفضل نسخة في مكان آخر). فوضعه في الدليل نفسه يعني أن من يستطيع تعديل الملف يستطيع تعديل البصمة، فتنعدم القيمة الإثباتية.
- **والتحقق**: `sha256sum -c incident.sha256`. **وملف البصمة يسجّل مسارات نسبية أو مطلقة، فبعد نقل الموقع يفشل التحقق** — وهذا ليس تلفًا في الملف، بل تغيّر المسار.
- **وافعل ذلك لكل الأدلة**، لا لملفات pcap فقط:

```bash
find /root/incident -type f -print0 | sort -z | xargs -0 sha256sum > /root/incident.sha256
```

و`find -print0` مع `xargs -0` يعالج أسماء الملفات التي فيها مسافات بشكل صحيح؛ و`sort -z` يضمن ثبات الترتيب، تسهيلًا للمقارنة. **ويكتب ملف البصمة خارج دليل الأدلة**، وتُنسخ منه نسخة إلى وسيط بلا اتصال.

### 3.2 لا تمسّ الأصل أبدًا

- **حلّل على النسخ فقط**. فـ`tcpdump -r` للقراءة فقط وآمن؛ وأي «إصلاح» أو «تحويل» أو «دمج» يُنفّذ على نسخة.
- وفي تحقيق قرص كامل، الطريقة المعيارية هي `dd` إلى صورة ثم حساب بصمة الصورة فورًا:

```bash
# لاحظ: سعة الهدف يجب أن تتجاوز سعة المصدر؛ وهذه العملية تكتب فوق جهاز الهدف بالكامل
sudo dd if=/dev/sda of=/mnt/evidence/sda.img bs=4M conv=noerror,sync status=progress
sha256sum /mnt/evidence/sda.img > /mnt/evidence/sda.img.sha256
```

:::warn القوة التدميرية لـ dd
أي جهاز يشير إليه `of=` في `dd` **يُكتب فوقه بلا شرط**. **فتأكّد إلزاميًا بـ`lsblk` من اسمَي جهاز المصدر والهدف قبل التنفيذ، فحرف واحد خاطئ يتلف البيانات.** وإن لم تكن متأكدًا فلا تنفّذ.
:::

### 3.3 الخط الزمني: يجب كتابة المنطقة الزمنية

**وهذا أكثر الأخطاء شيوعًا وأخطرها**: خلط وقت `journalctl` المحلي، ووقت المزوّد بـ UTC، ووقت سجلات الملحق في جدول واحد، فيختلّ ترتيب الأحداث تمامًا، وقد تصل إلى استنتاج معاكس.

1. **سجّل بـ UTC موحّد**، واكتب صراحةً في المستند «كل الأوقات التالية بـ UTC».
2. وسجّل **المنطقة الزمنية للجهاز وفرق UTC**، للمقارنة مع السجلات المحلية.
3. واستخدم صيغة ISO 8601، تجنّبًا لصيغ ملتبسة مثل `10/04/2026`.

```bash
date -u +%FT%TZ      # مثال: 2026-10-04T09:32:21Z
date +%FT%T%:z       # مثال: 2026-10-04T17:32:21+08:00
timedatectl          # اعرض المنطقة الزمنية للنظام وحالة مزامنة NTP
```

`date -u +%FT%TZ` يُخرج وقت UTC بلاحقة `Z`، **و`Z` تعني UTC لا اختصارًا لمنطقة زمنية** (لا تكتب `CST`، فهي تقابل ثلاث مناطق مختلفة على الأقل).

:::warn الساعة نفسها قد تكون خاطئة
عندما تكون ساعة المضيف غير مضبوطة أو NTP غير متزامن، **تصبح كل طوابع السجلات غير موثوقة**. افحص `System clock synchronized` في `timedatectl` هل هي `yes`، وسجّل مقدار الانحراف الحالي. **وإن اكتشفت انحرافًا فبيّنه في سجل الحادث**، وإلا أدّت المقارنة بين الأجهزة إلى استنتاج خاطئ.
:::

### 3.4 اكتب سجل الحادث (سجّل أثناء المعالجة)

| البند | ملاحظة |
| --- | --- |
| وقت الاكتشاف | من، وبأي وسيلة (ملاحظات اللاعبين، أو تنبيه المراقبة، أو رؤيتك) |
| الظاهرة | المظهر المحدّد: تقطيع، أو انقطاع، أو تعذّر اتصال، أو امتلاء النطاق |
| وقت كل فعل | **مع المنطقة الزمنية**، واكتب «ما فعلته» |
| التعديلات التي نفّذتها | قواعد جدار الحماية المضافة، وتحديد المعدّل، والـ IP المحجوب، والتحليل المبدَّل |
| أسماء ملفات الأدلة | ما هو كل ملف، ومتى التُقط |
| من تواصلت معه | رقم تذكرة المزوّد، والوقت، وخلاصة ردّه |
| الحالة الحالية | هل الهجوم مستمرّ |

:::warn إجراءات التخفيف نفسها تغيّر الأدلة
كل قاعدة جدار حماية تضيفها لإيقاف النزيف **تغيّر سمات الترافيك الملتقط بعده** (فالحزم التي كانت تصل تُسقط الآن ولا تُلتقط). وهذا لا مفرّ منه، لكن **يجب تسجيله**: سجّل **لحظة إضافة القاعدة** (وتكون حدًّا للتحليل بعده)، وحاول **التقاط دورة حزم قبل تعديل القواعد** (ولو 30 ثانية)، وسجّل **محتوى القاعدة كاملًا** لا «أضفت تحديد معدّل». وإلا تعذّر تفسير «لماذا اختفى ترافيك الهجوم فجأةً بعد 14:05».
:::

### 3.5 صلاحيات الملفات وحماية البيانات

```bash
chmod 700 /root/incident
chmod 600 /root/incident/*
chmod 600 /root/incident.sha256
```

- الأدلة تحوي **عناوين IP للاعبين، وأسماء حسابات، ومحتوى دردشة، وبيانات دخول محتملة**، و**يجب اعتبارها بيانات حسّاسة افتراضيًا**. فالدليل `700` (لا يدخله إلا المالك)، والملفات `600` (لا يقرأها ويكتبها إلا المالك).
- **ولا** تضع الأدلة في دليل ويب أو `chmod 777` «لتسهيل العرض».
- و**النقل** بـ`scp` / `rsync -e ssh` (عبر SSH مشفّر)، لا بـ FTP صريح أو مرفقات بريد.
- **وحماية البيانات**: عند التعامل مع بيانات شخصية للاعبين **انتبه للقوانين السارية** (مثل GDPR في الاتحاد الأوروبي، وقوانين حماية المعلومات الشخصية في مناطق أخرى) — فكثير من الاختصاصات تعدّ عنوان IP معلومة شخصية. والمبدأ **جمع النطاق الضروري فقط، وتحديد الغرض (تحقيق حادث أمني)، وتقييد الوصول، والحذف عند الانتهاء**. **والالتزامات المحدّدة تختلف بحسب الدولة/المنطقة، فاعتمد القانون المحلي وسياسة الخصوصية لديك.**
- **ولا** تنشر الأدلة (خصوصًا pcap التي تحوي دردشة اللاعبين وعناوينهم) في منتدى أو مجموعة «طلبًا للتشخيص».

## 4. النسبة: ما يمكن التحقق منه وما لا يمكن

**اعتبار طرف ثالث بريء مهاجمًا يُحدث ضررًا حقيقيًا، ويُفقد شكواك مصداقيتها.**

### 4.1 ترافيك UDP بمصدر مزوّر: لا نسبة تقريبًا

UDP بروتوكول **بلا اتصال**، و**حقل IP المصدر قابل للتزوير كيفما شاء**، والحزمة المزوّرة لا تحتاج استقبال أي ردّ لتُرسل. ولذلك:

- **IP المصدر في إغراق UDP (ومعظم انعكاسات UDP المضمّخة) مزوّر، ولا يمكن نسبته عادةً إطلاقًا.**
- **ولا** تشكُ على IP لمجرّد أنه الأكثر ظهورًا في إغراق UDP، ولا تحجبه ولا تتّهمه علنًا — **فذلك الـ IP ضحية مُنتحَل على الأرجح**.
- وحجب IP واحد أمام الترافيك المزوّر **بلا معنى** (فتغيير قيمة التزوير كافٍ)، والتصرف الصحيح **تنقية الترافيك في المنبع، وتحديد المعدّل، والترشيح بحسب سمات البروتوكول**.

وقليل من الخيوط الباقية: إن أمكن تحديد أن الهجوم يستخدم خدمة معيّنة (DNS أو NTP أو memcached أو CLDAP وغيرها)، **فذلك الخادم «خادم مفتوح مستغَلّ»** لا مهاجم؛ وإن كان لعنوان المصدر ومنفذه نمط مستقرّ فله قيمة تحقيقية، **لكن الاستنتاج يجب أن يكون حذرًا**؛ والأجهزة الوسيطة على مسار الترافيك (جهة المزوّد) ترى معلومات أكثر.

### 4.2 هجمات TCP: IP المصدر حقيقي عادةً، لكنه ليس «المهاجم»

TCP يحتاج **مصافحة ثلاثية**، وإتمام المصافحة يشترط استقبال الحزم العائدة، ولذلك فـ**هجمات TCP الموجّهة إلى Minecraft** — دخول البوتات بأعداد كبيرة (bot join)، وإغراق الاتصالات، وإغراق استعلام الحالة (status ping) — **مصدرها حقيقي عادةً**، ويمكن التحقيق فيه. **لكن «IP حقيقي» لا يعني «المهاجم نفسه»**: فقد يكون **مضيفًا ثالثًا مخترقًا** (VPS بباب خلفي، أو موجّه منزلي مخترق)، أو **مخرج وكيل / VPN / خدمة عبور**، أو **عقدة خروج Tor**، أو **مستخدمًا خلف NAT مشترك**. والتعبير الصحيح: **«هذا الـ IP شارك في ترافيك الهجوم»، لا «مالك هذا الـ IP هو المهاجم».** وهذا الفرق مهم جدًا في الشكوى.

### 4.3 الانعكاس / التضخيم: المصدر طرف ثالث بريء

لهجوم الانعكاس والتضخيم **ضحيّتان**: أنت، و**تلك الخوادم المفتوحة المستغَلّة**. واستُغلّت لأن مديريها **فتحوا خدمات UDP مثل DNS وNTP وmemcached للإنترنت العام**.

- **لا تُبلّغ عن مصدر الانعكاس كمهاجم**، بل أبلِغ عن **«خدمة على IP كذا مصدر انعكاس مفتوح ويُساء استخدامه»**؛
- وإرسال إشعار إلى `abuse@` لتلك العناوين **مفيد** (فبإصلاح المدير يختفي سطح الانعكاس)، لكن **بنبرة «خدمتك يُساء استخدامها» لا «أنت تهاجمني»**؛
- وأساس الحكم: **حزمة الاستجابة أكبر بكثير من حزمة الطلب** (معامل التضخيم)، و**المصدر منفذ خدمة UDP معروف**.

### 4.4 التمييز بين «التركّز في نقطة» و«التوزّع»

| السمة الملاحظة | الطبيعة الأرجح | ما يمكن فعله |
| --- | --- | --- |
| **IP واحد أو قليل يحتكر معظم الاتصالات** | هجوم نقطة واحدة، أو مضيف مخترق، أو مسح استطلاعي | يستحق التحقيق في ذلك الـ IP؛ ويمكن حجبه مؤقتًا لإيقاف النزيف |
| **آلاف الـ IPs، كلٌّ يرسل قليلًا** | شبكة أجهزة موزّعة أو مصدر مزوّر | حجب الـ IP بلا فائدة؛ والاعتماد على التنقية في المنبع وتحديد المعدّل |
| **إتمام مصافحة TCP ونموّ مستقرّ في الاتصالات** | مصدر حقيقي (فئة دخول البوتات) | التحقيق في الـ IP + الحماية في المنبع + تقييد الدخول |
| **SYN كثيرة بلا مصافحة لاحقة** | إغراق SYN (قد يكون مصدره مزوّرًا) | تفعيل SYN cookies، والتنقية في المنبع |
| **حزم UDP كبيرة تتدفّق ومنفذ المصدر ثابت** | انعكاس وتضخيم | الترشيح بحسب البروتوكول/المنفذ، والتنقية في المنبع، **ولا تشكُ على IP المصدر** |
| **النطاق صغير والخدمة بطيئة جدًا** | قد يكون هجوم طبقة تطبيق أو استنزاف موارد | انظر سجلات التطبيق وجدول تتبّع الاتصالات وموارد المضيف |

**والحكم الجوهري**: **قليل من الـ IPs مركّزة = يستحق التتبّع؛ وكثرة موزّعة = لا يمكن تتبّعها أو لا تنتهي، فانتقل إلى الحماية.**

### 4.5 ماذا تفعل بعد معرفة الـ IP

```bash
whois 203.0.113.10
```

مخرجات `whois` تحوي عادةً **تبعية النطاق (netname/descr)، والجهة المالكة، والدولة، وبريد التواصل `abuse`**. ولاحظ:

- **عميل `whois` غير مثبّت افتراضيًا بالضرورة** (في Debian/Ubuntu: `sudo apt install whois`؛ وفي عائلة RHEL: `sudo dnf install whois`)؛
- **صيغة مخرجات كل RIR (سجل الإنترنت الإقليمي) مختلفة**، وأسماء الحقول `abuse-c` و`OrgAbuseEmail` و`abuse-mailbox` وغيرها تتباين، **فتُقرأ بشريًا لا بمطابقة سكربت صارمة**؛
- والأفضل **RDAP** (Registration Data Access Protocol)، فهو **البديل HTTP الحديث** لـ WHOIS، ويعيد JSON منظّمًا ويدعم الاستعلام الآلي. وتوفّر IANA خدمة توجيه (`https://rdap.org/ip/<IP>` تحوّل إلى الـ RIR المقابل)، **والعناوين والحقول المحدّدة لكل RIR بحسب توثيقه**.

**وتبعية ASN**: تحديد أي نظام مستقل (AS) وأي مشغّل/مركز بيانات يملك ذلك الـ IP، يساعد في الحكم هل هو «VPS على سحابة ما» أم «نطاق منزلي في دولة ما». والوسائل: خدمة RDAP لكل RIR، و`whois -h whois.radb.net` وغيرها، **والأدوات والمصادر كثيرة وتغطيتها متفاوتة**، فلا تبنِ الاستنتاج على مصدر واحد.

**وبريد abuse**: **بريد `abuse@`** في WHOIS/RDAP (أو نموذج abuse) هو **مدخل الإبلاغ الصحيح**: **أرسل إلى قسم abuse في مركز البيانات / مزوّد الاستضافة المالك لذلك الـ IP، لا إلى مزوّد خدمة إنترنت لاعب عشوائي** — فمركز البيانات يملك قدرة معالجة فعلية على الأجهزة في نطاقه (يمكنه إيقاف الخدمة)، أما مزوّد الخدمة فحركته بطيئة عادةً أمام موجّه منزلي مخترق. **وأرفق الأدلة**: نافذة زمنية بمنطقة زمنية، والبروتوكول والمنفذ، وقائمة عناوين المصدر، وعدد الحزم والمعدّل، وبصمة pcap؛ **فالشكوى بلا دليل تُتجاهل عادةً**. وعند تعدد النطاقات **أبلغ عن كلٍّ على حدة**، ولا تسمّ أسماء علنًا في المجموعات.

### 4.6 القانون والحدود

- **القواعد تختلف بحسب الدولة/المنطقة**: ما يُعدّ جريمة، وأي السجلات يجب حفظها، وهل يمكن جمع البيانات بنفسك — تختلف بين الدول. **وهذه المقالة لا تُشكّل رأيًا قانونيًا.**
- **والترتيب الموصى به**: تواصل أولًا مع **المزوّد** (فهو يستطيع تنقية الترافيك ورؤية بيانات المنبع، وله إجراء abuse)؛ ثم في الهجمات الجسيمة والمستمرّة (فدية، أو سرقة بيانات، أو جريمة واضحة) فكّر في **الشرطة / جهة الإبلاغ عن جرائم الإنترنت**، مع حفظ سلسلة الأدلة كاملة.
- **ولا تنتقم أبدًا**: فإطلاق DDoS على مصدر الهجوم (ما يُسمّى DDoS-back)، أو اختراق جهازه، أو «الاختراق المضاد»، **جريمة بذاتها في كل الاختصاصات تقريبًا**، وتحوّلك من ضحية إلى متّهم، وتُفني موقفك المحقّ أصلًا.
- **ولا تنشر بيانات شخصية / مكافآت علنية** على IP المهاجم: فقد تُصيب طرفًا ثالثًا بريئًا، وقد تُعدّ مضايقة أو انتهاكًا للخصوصية.

## 5. الإبلاغ والتصعيد

**«تعرضت لهجوم، عالجوا الأمر بسرعة» لن تحصل على استجابة فعّالة تقريبًا.** والتذكرة الفعّالة هي التي تتيح للطرف الآخر أن يعرف ماذا يفعل في 30 ثانية:

```text
الموضوع: [DDoS/هجوم] النسخة <معرّف النسخة/IP> تتعرض لهجوم، نطلب المساعدة وبيانات الترافيك

1. الأصول المتأثرة
   - IP العام: 203.0.113.10
   - المنفذ/البروتوكول: 25565/TCP (إصدار Java)، و19132/UDP (إصدار Bedrock)
   - معرّف النسخة / رقم الطلب: <املأ>

2. النافذة الزمنية (يرجى ذكر المنطقة الزمنية)
   - البداية: 2026-10-04 09:12 UTC (التوقيت المحلي 17:12، UTC+8)
   - النهاية: ما زال مستمرًّا / توقّف عند 09:40 UTC
   - فترة الذروة: 09:20 - 09:35 UTC

3. نوع الهجوم وحجمه (المعروف منه)
   - تقدير النوع: انعكاس وتضخيم UDP (يُشتبه في NTP/DNS) / إغراق اتصالات TCP / دخول بوتات
   - المعدّل الملاحظ: نحو XX Mbps، ونحو XX kpps (المصدر: عدّادات ip -s link على الجهاز)
   - فقد الحزم في البطاقة: RX dropped من 0 إلى XXXXX (في الفترة نفسها)

4. التخفيف المنفَّذ
   - 09:25 UTC إضافة قاعدة iptables لتقييد الاتصالات المتزامنة لكل IP
   - 09:30 UTC حجب عناوين المصدر (فعّال على TCP فقط)
   - لم نُعِد التشغيل ولم نُعِد التثبيت، والوضع محفوظ

5. الطلب
   - تزويدنا بإحصاءات الترافيك الداخل إلى هذه النسخة في تلك الفترة وتقرير الهجوم
   - تأكيد إمكان تفعيل/تفعيل تنقية الترافيك أو IP الحماية المتقدّمة
   - إن كانت لديكم سجلات تدفّق على جهة المنصّة، فساعدونا في تصديرها

6. ملفات الأدلة
   - incident-2026-10-04-0915.pcap (sha256: <البصمة>)
   - fw-iptables.txt، وss-established.txt، وconntrack.txt
   - يمكن تزويدكم بحزمة الأدلة الكاملة عند الحاجة
```

| العنصر | لماذا هو ضروري |
| --- | --- |
| **نافذة زمنية بمنطقة زمنية** | فالطرف الآخر يجب أن يحدّد ترافيكك في سجلات هائلة، والوقت الخاطئ يعني عدم العثور عليه |
| **نوع الهجوم وحجمه** | يحدّد هل يمضون في مسار «التنقية» أم «التشخيص» |
| **الـ IP / المنفذ المتأثر** | لتأكيد الأصل الذي يُضرب |
| **هل ما زال مستمرًّا** | يحدّد درجة الإلحاح |
| **التخفيف المنفَّذ** | تجنّب تكرار العملية وتداخل الطرفين |
| **أسماء ملفات الأدلة** | لتكون المراسلة قابلة للتتبّع |

**وعن الإبلاغ إلى abuse**: للمزوّد عادةً بريد abuse أو نموذج إبلاغ، لمعالجة «أجهزة في نطاقه تهجم على غيرها»، **والعنوان المحدّد بحسب موقع المزوّد وسجل WHOIS**. **وهم يرون ترافيكًا لا تراه** (توجيه المنبع، وأجهزة التنقية، وسجلات التدفّق على المنصّة) — فأنت تعطي منظور الطرفية وهم منظور الشبكة، ولا يكتمل إلا بهما معًا. **وقيود الخصوصية**: قد **يتعذّر على المزوّد إبلاغك بتفاصيل عملاء آخرين بسبب سياسة الخصوصية أو القانون**، وهذا طبيعي، **فلا تحكم بعدم جدّيتهم لمجرّد أنهم «لا يعطون قائمة الـ IPs»**. تابع وسجّل رقم التذكرة ووقت كل ردّ، لتشكّل خطًّا زمنيًا كاملًا للمراسلة (وهو جزء من سجل الحادث).

## 6. بعد الحادث

**استجابة طوارئ بلا مراجعة كأنها لم تُقم.**

### 6.1 أسئلة المراجعة

| السؤال | ما تنظر إليه تحديدًا |
| --- | --- |
| **ما الذي نجح؟** | أي قاعدة جدار حماية أصابت؟ وهل سريان التنقية كان فعّالًا؟ وهل عتبة تحديد المعدّل معقولة؟ |
| **ما الذي لم ينجح؟** | أي الإجراءات بلا أثر؟ وأيّها أصاب اللاعبين الطبيعيين بدلًا من ذلك؟ |
| **كم استغرق التعافي؟** | المدة الفعلية من الاكتشاف إلى التخفيف، وأين عنق الزجاجة (بطء الاكتشاف؟ بطء الحكم؟ غياب خطة؟) |
| **هل عاد المهاجم؟** | قارن النافذة الزمنية وتوزيع المصادر، للحكم: الموجة نفسها أم موجة جديدة |
| **هل هناك فقد بيانات؟** | هل الأرشيف سليم؟ وهل حدثت استعادة؟ وهل النسخة صالحة؟ |
| **ما الذي انكشف؟** | هل ظهرت أو سُرّبت حسابات أو مفاتيح أو كلمات مرور لوحة في أثناء ذلك؟ |

### 6.2 إجراءات التقوية

- **تحديد المعدّل (rate limit)**: ضع سقوفًا لتكرار الاتصال، وعدد الاتصالات المتزامنة لكل IP، ومعدّل الدخول. **وهذه أنجع طبقة وأرخصها**. مثلًا وحدتا `hashlimit`/`connlimit` في `iptables`، أو تقييد الدخول على مستوى ملحقات الخادم (**وأسماء الوحدات وصيغها تختلف بحسب النواة وسلسلة الأدوات، فتأكّد من توافر الوحدة قبل الإعداد**).
- **الوكيل / الحماية المتقدّمة**: أخفِ الـ IP الحقيقي (وكيل من فئة TCPShield، أو IP حماية متقدّمة من المزوّد، أو تمرير TCP في CDN). **لاحظ**: الوكيل يصدّ الإغراق في طبقة الشبكة، **ولا يصدّ هجمات طبقة التطبيق (دخول البوتات، وثغرات البروتوكول)**، وتلك تحتاج تحققًا وتقييدًا على جهة الخادم.
- **تغيير المزوّد / مركز البيانات**: إن لم يوفّر المزوّد تنقية، أو كان الهجوم على هدف ثابت في ذلك النطاق، فالترحيل خيار واقعي. **وتأكّد قبل الترحيل من قدرة البيت الجديد على حماية DDoS والتنقية.**
- **القائمة البيضاء**: لخادم دائرة معارف صغيرة، **تفعيل `white-list=true` مباشرةً هو الحلّ الأشمل** — فالمهاجم لا يستطيع الدخول أصلًا، فلا يستطيع استنزاف مواردك بهجمات الدخول.
- **تقليل سطح التعرّض**: أغلق المنافذ غير اللازمة (RCON، وquery، واللوحة)، انظر [أساسيات أمان الشبكة](/tutorials/ops/network-security)؛ وتقوية جهة المضيف في [تقوية أمان النظام](/tutorials/ops/system-security).
- **المراقبة والتنبيهات**: **في الهجوم القادم تريد أن يوقظك التنبيه، لا شتائم اللاعبين.** راقب على الأقل النطاق، وعدد الاتصالات، وTPS، وحياة العملية.

### 6.3 هل النسخة سليمة وهل هي بلا اتصال

- **تحقّق من إمكان الاستعادة فعلًا**، لا من «وجود الملف». وتجربة الاستعادة في [النسخ الاحتياطي والاستعادة](/tutorials/java/backup) و[النسخ الاحتياطي خارج الموقع](/tutorials/ops/offsite-backup).
- **تأكّد أن نسخة واحدة على الأقل بلا اتصال** (أو غير قابلة للتغيير / للقراءة فقط). فإن صاحب الهجوم اختراق للمضيف، **فقد تكون النسخة المتصلة القابلة للكتابة مشفّرة أو محذوفة**.
- **افحص توقيت النسخة**: إن حدثت استعادة أثناء الهجوم، فبيّن **إلى أي نقطة زمنية استعدت**، وكم سيرجع تقدّم اللاعبين.

### 6.4 تدوير بيانات الاعتماد والمفاتيح

**بمجرد وجود احتمال أي انكشاف، افترض التسريب، ودوّر الكل.**

| العنصر | الفعل |
| --- | --- |
| كلمة مرور اللوحة / الخلفية | بدّلها فورًا، وفعّل التحقّق بخطوتين (إن وُجد) |
| المفتاح الخاص SSH | ولّد زوجًا جديدًا، واحذف القديم العام، وافحص `authorized_keys` هل فيه بنود زائدة |
| كلمة مرور RCON | بدّلها؛ وتأكّد أن `enable-rcon` غير مفتوح للإنترنت العام |
| حساب قاعدة البيانات | بدّل كلمة المرور، وافحص وجود تصريح واسع مثل `root@%` |
| API Key / Access Key لمنصّة السحابة | أبطِلها وأعد إنشاءها في وحدة التحكّم، وافحص سجلات الاستدعاء الشاذة |
| حساب الخدمة / Token (الملحقات، والنسخ، والمراقبة) | أبطِل وأعد الإنشاء واحدًا واحدًا |
| حسابات اللاعبين | إن سُرّبت قاعدة بيانات الملحق، **أبلغ اللاعبين بتغيير كلمات مرورهم** |

**وافحص كذلك**: `~/.ssh/authorized_keys`، وهل في `/etc/passwd` و`/etc/shadow` حسابات جديدة، وهل في `crontab -l` و`/etc/cron.*` مهام مجدولة مريبة، وهل في systemd وحدات شاذة. **وهذه الفحوص تُنفّذ بعد إتمام التحقيق، وتُسجَّل نتائجها.**

### 6.5 قائمة الدروس

```text
[ ] هل كان الاكتشاف في حينه؟ وهل غطّت تنبيهات المراقبة النطاق وعدد الاتصالات وTPS وحياة العملية؟
[ ] هل توجد خطة مكتوبة؟ (من يحكم، ومن يتواصل مع المزوّد، ومن يعلن للاعبين)
[ ] هل كان الالتقاط في حينه؟ وهل ضاعت أدلة بسبب إعادة تشغيل أولًا؟
[ ] هل وُحّدت المنطقة الزمنية في الخط الزمني؟
[ ] هل حُسبت البصمات وحُفظت منفصلة عن الأدلة؟
[ ] هل حدث حجب خاطئ للاعبين طبيعيين؟ وكيف رُفع؟
[ ] هل سجّلت تذكرة المزوّد الخط الزمني والأدلة كاملة؟
[ ] هل النسخة مُتحقَّق من استعادتها، وهل توجد نسخة بلا اتصال؟
[ ] هل دُوّرت كل بيانات الاعتماد المحتمل انكشافها؟
[ ] هل كُتب «ما تعلّمناه هذه المرة» في مستند، لا في الرأس؟
```

## 7. سكربت تحقيق جاهز للاستخدام

السكربت التالي يجمع الجزء **المتلاشي** من القسم 2 في دليل بطابع زمني، ويحسب البصمات ويطبع ملخّصًا. **والاستخدام: `sudo bash capture-evidence.sh`** (فالالتقاط وconntrack يحتاجان root). **وقبل التشغيل تأكّد من** اسم الواجهة (يكتشف السكربت واجهة المسار الافتراضي تلقائيًا)، ودليل الأدلة (الافتراضي `/root/incident`)، ومدة الالتقاط وسقف عدد الحزم. **والسكربت يجمع للقراءة فقط، ولا يعدّل أي إعداد ولا يعيد تشغيل أي خدمة.**

```bash
#!/usr/bin/env bash
#
# capture-evidence.sh - يجمع الأدلة المتلاشية عند التعرّض لهجوم على خادم Minecraft
#
# الاستخدام: sudo bash capture-evidence.sh
#
# السمات:
#   - جمع للقراءة فقط، لا يعدّل إعداد النظام ولا يعيد تشغيل الخدمات
#   - الأدوات الاختيارية تُفحص بـ command -v، وتُسجَّل وتُتخطّى عند غيابها
#   - تُحسب SHA-256 لكل النتائج، ويُكتب الملخّص في ملف مستقل
#
# لاحظ: أسماء الواجهات والخدمات ومسارات السجلات تختلف بحسب النظام، فعدّل المتغيّرات أدناه بحسب حاجتك.

set -u

# ---------------- وسائط قابلة للضبط ----------------
IFACE="${IFACE:-}"                            # تركه فارغًا يعني اكتشاف واجهة المسار الافتراضي تلقائيًا
CAPTURE_SECONDS="${CAPTURE_SECONDS:-60}"      # ثواني الالتقاط
CAPTURE_PACKETS="${CAPTURE_PACKETS:-200000}"  # سقف عدد الحزم، منعًا لامتلاء القرص
MC_TCP_PORT="${MC_TCP_PORT:-25565}"           # منفذ إصدار Java
MC_UDP_PORT="${MC_UDP_PORT:-19132}"           # منفذ إصدار Bedrock / Geyser
MC_SERVICE="${MC_SERVICE:-}"                  # اسم خدمة systemd، وتركه فارغًا يعني التخطّي
MC_DIR="${MC_DIR:-}"                          # دليل الخادم، وتركه فارغًا يعني تخطّي نسخ السجلات
BASE_DIR="${BASE_DIR:-/root/incident}"

STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
OUT="${BASE_DIR%/}/incident-${STAMP}"

# ---------------- فحوص مسبقة ----------------
if [ "$(id -u)" -ne 0 ]; then
  echo "خطأ: يلزم صلاحية root (الالتقاط و conntrack يحتاجانها). شغّله بـ sudo فقط." >&2
  exit 1
fi

mkdir -p "$OUT" || { echo "خطأ: تعذّر إنشاء $OUT" >&2; exit 1; }
chmod 700 "$BASE_DIR" 2>/dev/null || true
chmod 700 "$OUT" 2>/dev/null || true

if [ -z "$IFACE" ]; then
  IFACE="$(ip route show default 2>/dev/null | awk '/default/ {print $5; exit}')"
fi
if [ -z "$IFACE" ]; then
  IFACE="eth0"
  echo "تحذير: تعذّر اكتشاف واجهة المسار الافتراضي، والرجوع إلى eth0، استخدم IFACE=... للتجاوز." >&2
fi

echo "==> دليل الأدلة: $OUT"
echo "==> واجهة الجمع: $IFACE"
echo "==> وقت الجمع: $STAMP (UTC)"
echo "==> المساحة المتبقية على القرص:"
df -h "$OUT" 2>/dev/null || true

# ---------------- دالة الجمع ----------------
capture() {
  _name="$1"
  shift
  echo "  - $_name"
  "$@" > "${OUT}/${_name}.txt" 2>&1 || echo "    (أعاد الأمر قيمة غير صفرية، والمخرجات محفوظة)"
}

{
  echo "بدء الجمع(UTC): $(date -u +%FT%TZ)"
  echo "التوقيت المحلي: $(date +%FT%T%:z)"
  echo "اسم المضيف: $(hostname)"
  echo "النواة: $(uname -a)"
  echo "زمن التشغيل: $(uptime)"
  echo "الواجهة: $IFACE"
  echo "Java منفذ: $MC_TCP_PORT  UDP منفذ: $MC_UDP_PORT"
} > "${OUT}/meta.txt" 2>&1
chmod 600 "${OUT}/meta.txt" 2>/dev/null || true

echo "==> جمع حالة النظام والعمليات"
capture ps-auxf ps auxf
capture ss-summary ss -s
capture ss-tcp-all ss -tan
capture ss-udp ss -uan
capture ss-tcp-listen ss -tlnp
capture ip-addr ip -br addr
capture ip-route ip route show
capture ip-neigh ip neigh show
capture uptime uptime
capture date-utc date -u +%FT%TZ
capture timedatectl timedatectl
capture df-h df -h

if command -v ss >/dev/null 2>&1; then
  echo "  - ss-java-established"
  ss -tan state established "( sport = :${MC_TCP_PORT} )" \
    > "${OUT}/ss-java-established.txt" 2>&1 || true
  echo "  - ss-source-ranking"
  ss -tan state established "( sport = :${MC_TCP_PORT} )" 2>/dev/null \
    | awk 'NR>1 {print $5}' | cut -d: -f1 \
    | sort | uniq -c | sort -rn | head -50 \
    > "${OUT}/ss-source-ranking.txt" 2>&1 || true
fi

echo "==> جمع عدّادات البطاقة"
if command -v ip >/dev/null 2>&1; then
  echo "  - ip-s-link"
  ip -s link show "$IFACE" > "${OUT}/ip-s-link.txt" 2>&1 || true
fi
[ -r /proc/net/dev ] && capture proc-net-dev cat /proc/net/dev
if command -v sar >/dev/null 2>&1; then
  capture sar-dev sar -n DEV 1 5
else
  echo "sar غير مثبّتة، وتُتخطّى عيّنات المعدّل اللحظي (توفرها حزمةsysstat)" > "${OUT}/sar-dev.txt"
fi

echo "==> جمع حالة جدار الحماية وعدّاداته"
if command -v iptables >/dev/null 2>&1; then
  capture fw-iptables iptables -L -v -n
  capture fw-iptables-nat iptables -t nat -L -v -n
else
  echo "iptables غير متاح" > "${OUT}/fw-iptables.txt"
fi
if command -v nft >/dev/null 2>&1; then
  capture fw-nft nft list ruleset
  capture fw-nft-counters nft list counters
else
  echo "nft غير متاح" > "${OUT}/fw-nft.txt"
fi

echo "==> جمع جدول تتبّع الاتصالات (إن توافر)"
if command -v conntrack >/dev/null 2>&1; then
  capture conntrack-list conntrack -L
  capture conntrack-stats conntrack -S
  capture conntrack-count conntrack -C
else
  echo "conntrack أمر غير متاح (يحتاج conntrack-tools، والنواة تحتاج تفعيل nf_conntrack، وهو وحدة نواة)" \
    > "${OUT}/conntrack-list.txt"
fi
[ -r /proc/sys/net/netfilter/nf_conntrack_count ] \
  && capture conntrack-sysctl cat /proc/sys/net/netfilter/nf_conntrack_count
[ -r /proc/sys/net/netfilter/nf_conntrack_max ] \
  && capture conntrack-max cat /proc/sys/net/netfilter/nf_conntrack_max

echo "==> جمع الخدمات والسجلات"
if [ -n "$MC_SERVICE" ] && command -v systemctl >/dev/null 2>&1; then
  capture systemctl-status systemctl status "$MC_SERVICE" --no-pager
  if command -v journalctl >/dev/null 2>&1; then
    capture journalctl-1h \
      journalctl -u "$MC_SERVICE" --since "1 hour ago" --utc --no-pager
  fi
else
  echo "لم يُحدّد MC_SERVICE، وتُتخطّى حالة الخدمة (الاستخدام: MC_SERVICE=minecraft sudo -E bash $0، ثم أعد التشغيل)" \
    > "${OUT}/systemctl-status.txt"
fi

if [ -n "$MC_DIR" ] && [ -d "$MC_DIR" ]; then
  echo "  - نسخ سجلات الخادم، مع الحفاظ على الطوابع الزمنية"
  [ -d "${MC_DIR}/logs" ] && cp -a "${MC_DIR}/logs" "${OUT}/mc-logs" 2>/dev/null || true
  [ -d "${MC_DIR}/crash-reports" ] \
    && cp -a "${MC_DIR}/crash-reports" "${OUT}/mc-crash-reports" 2>/dev/null || true
else
  echo "لم يُحدّد MC_DIR، ويُتخطّى نسخ سجلات الخادم (الاستخدام: MC_DIR=/srv/minecraft sudo -E bash $0، ثم أعد التشغيل)" \
    > "${OUT}/mc-logs-note.txt"
fi

echo "==> التقاط قصير ${CAPTURE_SECONDS}s / بحدّ ${CAPTURE_PACKETS} حزمة"
if command -v tcpdump >/dev/null 2>&1; then
  PCAP="${OUT}/capture-${STAMP}.pcap"
  timeout "$CAPTURE_SECONDS" tcpdump -i "$IFACE" -nn -s 0 \
    -c "$CAPTURE_PACKETS" -w "$PCAP" \
    "port ${MC_TCP_PORT} or udp port ${MC_UDP_PORT}" 2>"${OUT}/tcpdump.log" || true
  echo "  - ملف الالتقاط: $PCAP"
  echo "  - إحصاء الحزم:"
  tcpdump -nn -r "$PCAP" -q 2>/dev/null | wc -l | tee "${OUT}/pcap-packet-count.txt" || true
  echo "  - IP ترتيب عناوين المصدر (أول 30):"
  tcpdump -nn -r "$PCAP" -q 2>/dev/null | awk '{print $3}' | cut -d. -f1-4 \
    | sort | uniq -c | sort -rn | head -30 > "${OUT}/pcap-source-ranking.txt" || true
else
  echo "tcpdump غير مثبّت، ولا يمكن الالتقاط. ثبّته في أسرع وقت وأعد الجمع(Debian/Ubuntu: apt install tcpdump، ثم أعد الجمع)" \
    > "${OUT}/tcpdump.log"
fi

echo "==> حساب SHA-256"
find "$OUT" -type f ! -name 'SHA256SUMS' -print0 \
  | sort -z | xargs -0 sha256sum > "${OUT}/SHA256SUMS" 2>/dev/null || true
# احفظ نسخة من البصمات خارج دليل الأدلة، تجنّبًا لتعديلها في الوقت نفسه
cp "${OUT}/SHA256SUMS" "${BASE_DIR%/}/SHA256SUMS-${STAMP}.txt" 2>/dev/null || true
find "$OUT" -type f -exec chmod 600 {} + 2>/dev/null || true

echo
echo "=================== ملخّص الجمع ==================="
echo "دليل الأدلة : $OUT"
echo "وقت البدء : $(head -n 1 "${OUT}/meta.txt" 2>/dev/null)"
echo "الواجهة     : $IFACE"
echo "عدد الملفات : $(find "$OUT" -type f | wc -l)"
echo "المساحة المشغولة : $(du -sh "$OUT" 2>/dev/null | cut -f1)"
echo "ملف الالتقاط : $(ls -1 "${OUT}"/*.pcap 2>/dev/null | head -n 1)"
echo "ملف التحقق : ${BASE_DIR%/}/SHA256SUMS-${STAMP}.txt"
echo "------------------------------------------------"
echo "الخطوات التالية (مهمة):"
echo "  1. لا تُعِد التشغيل ولا تُعِد تثبيت النظام، فالأدلة المتلاشية تضيع بإعادة التشغيل."
echo "  2. انسخ الأدلة فورًا إلى جهاز آخر أو وسيط بلا اتصال:"
echo "     scp -r root@<IP-الجهاز>:$OUT ./evidence/"
echo "  3. اكتب سجل الحادث، بتوقيت عالمي موحّد، مع ذكر فرق توقيت الجهاز."
echo "  4. افتح تذكرة عند المزوّد، وأرفق النافذة الزمنية وأسماء ملفات الأدلة (انظر القسم 5 في المستند)."
echo "================================================"
```

| البند | ملاحظة |
| --- | --- |
| `set -u` لا `set -e` | فسكربت الجمع يجب أن **يجمع ما يمكن جمعه**، وفشل أمر اختياري لا يجوز أن يقطع الجمع كله |
| حراسة `command -v` | تُستخدم مع **الأدوات الاختيارية** فقط (`sar`، و`nft`، و`conntrack`، و`tcpdump`، و`systemctl`)؛ والأوامر الأساسية (`ip`، و`ss`) يُفترض وجودها |
| `timeout` | تحدّ مدة الالتقاط؛ و**`timeout` من GNU coreutils، وتأتي معها معظم توزيعات Linux**، وقد تغيب في الصور المصغّرة جدًا |
| `-c "$CAPTURE_PACKETS"` | سقف عدد الحزم، منعًا لامتلاء القرص أثناء الهجوم؛ **وأيّهما تحقّق أولًا (المدة أم العدد) هو الذي يسري** |
| `cp -a` | يحافظ على **الطوابع الزمنية والصلاحيات** لسجلات الأصل، وهذا شرط أساسي في التحقيق |
| مرشّح الالتقاط | `'port 25565 or udp port 19132'`: **`port` يطابق TCP/UDP معًا**، فكُتب `port 25565` مع `udp port 19132`، تجنّبًا لالتقاط TCP على 19132 |
| البصمة | نسخة داخل الدليل، **ونسخة أخرى تحت `BASE_DIR`**؛ وفي الحالات الصارمة حقًا يجب حفظ البصمات والأدلة على جهازين مختلفين |
| اسم الخدمة والمسارات | `MC_SERVICE` و`MC_DIR` **يجب ملؤهما بحسب نشرك**، فالسكربت لا يخمّن |
| بيئة الحاويات | عند التشغيل في حاوية يجب أن يشير `IFACE` و`MC_DIR` إلى **واجهة ومسار داخل مساحة أسماء شبكة الحاوية** |

:::warn سكربت الجمع لا يُغني عن الحكم
السكربت مسؤول عن **كتابة الأدلة المتلاشية على القرص**، لكن **الحكم «ما هذا الهجوم، وهل نشكو، وهل ننتقل إلى حماية متقدّمة» يبقى للإنسان**. وبعد انتهاء السكربت اتبع العملية في الأقسام 1 إلى 6، ولا تنسَ خصوصًا **كتابة سجل الحادث** و**التواصل مع المزوّد**.
:::
