أن يتمكن الآخرون من الاتصال بخادمك يعني **أنهم يستطيعون مسحه كذلك**. فمن أول يوم لفتح الخادم، سيُجرَّب عنوان IP العام لديك مرارًا بماسحات المنافذ وسكربتات التخمين وأدوات الهجوم «الواسعة» — **وليس لأنك أغضبت أحدًا، بل لأنك مكشوف على الإنترنت**.

وتتناول هذه المقالة الحماية على مستوى الشبكة: **أي المنافذ تُفتح، وكيف يُضبط جدار الحماية، وكيف تُقوّى SSH، وماذا تفعل عند التعرّض لهجوم**. أما التقوية داخل النظام ففي [تقوية أمان النظام](/tutorials/ops/system-security).


:::warn حاويات Docker تتجاوز جدار حماية الجهاز
كل قواعد `ufw` / `firewalld` في هذه الصفحة **لا تعمل على المنافذ التي تعرضها حاويات Docker**. فDocker يُدرج قواعده في `iptables` قبل جدار حماية النظام، فلا يمنع `ufw deny` منفذ الحاوية.

وللتقييد الفعلي اربط المنفذ بواجهة الاسترجاع (`-p 127.0.0.1:25565:25565`) أو استخدم سلسلة `DOCKER-USER`. والتفاصيل في [نشر نسخة Java بـ Docker ← الشبكة وجدار الحماية](/tutorials/java/docker).
:::

## أولًا: اعرف سطح الهجوم أولًا

### 1.1 المنافذ التي تحتاج فتحها فعلًا

| الاستخدام | البروتوكول | المنفذ الافتراضي | هل يُفتح للإنترنت |
| --- | --- | --- | --- |
| **Minecraft نسخة Java** | TCP | `25565` | نعم (مدخل اللاعبين) |
| **نسخة Bedrock / Geyser** | UDP | `19132` | نعم (يحتاجه خادم العبور بين النسختين) |
| **بروتوكول الاستعلام (query)** | UDP | `25565` | لا يُحتاج عادةً |
| **كونسول RCON البعيد** | TCP | `25575` | **أبدًا** |
| **قاعدة البيانات** (MySQL / MariaDB) | TCP | `3306` | **أبدًا** |
| **Redis** | TCP | `6379` | **أبدًا** |
| **اللوحة** (مختلف لوحات الويب الإدارية) | TCP | بحسب اللوحة | **أبدًا** |
| **SSH** | TCP | `22` | نعم، لكن **قيّد المصدر** |

:::warn القيم الافتراضية للمنافذ قد تكون عُدّلت
الجدول أعلاه هو **القيمة الافتراضية من المصنع** لكل برنامج. وإن كنت عدّلت `server-port` أو `query.port` أو `rcon.port` في `server.properties`، أو عدّلت منفذ الاستماع في اللوحة، **فالمرجع إعدادك الفعلي**. وقواعد جدار الحماية يجب أن تطابق المنفذ الفعلي، وإلا فإما تعذّر الاتصال أو بقي ثقب.
:::

### 1.2 عن RCON وقاعدة البيانات: لماذا يجب إغلاقهما

- **RCON هو «صلاحية إدارة بلا واجهة»**. فكلمة مرور واحدة تشتري قدرة تنفيذ أي أمر في الكونسول. وبمجرد كشفه للإنترنت يستطيع المهاجم `op` نفسه، أو محو الحفظ، أو طرد كل اللاعبين. **والطريقة الصحيحة `enable-rcon=false`، وإن احتجت إدارة بعيدة فمن نفق SSH أو لوحة عبر الاسترجاع المحلي.**
- **كشف منفذ قاعدة البيانات أكثر مداخل تسرّب البيانات شيوعًا**. فحين تسمح MySQL لـ `root` بالدخول من أي مضيف (`root@%`)، تُخمَّن كلمة المرور الضعيفة في دقائق، فتُسرَّب حسابات اللاعبين وتجزئات كلمات مرورهم وسجلات شرائهم.
- **كشف منفذ اللوحة يعني تعليق التحكم في الجهاز كله على الإنترنت**. فلللوحة صفحة دخول، وقد تكون فيها ثغرة، وهي تعمل عادةً بصلاحيات عالية.

ومبدأ أساسي: **أي منفذ ليس «للاعبين» لا يُفتح للإنترنت.** وإن احتجت وصولًا بعيدًا لنفسك فاستخدم نفق SSH (انظر القسم الرابع) لا الكشف المباشر.

### 1.3 أمران تفعلهما في الطريق

- **تأكد من عنوان الاستماع**: يجب أن ترتبط قاعدة البيانات واللوحة وRCON بـ `127.0.0.1` لا `0.0.0.0`. فبعد الربط بالاسترجاع، حتى لو أخطأت في جدار الحماية لن يتصل الخارج.
- **تأكد من `online-mode`**: أبقِ `online-mode=true` في نسخة Java (`server.properties`). فالوضع دون اتصال يتيح لأي شخص انتحال معرّف غيره، وهو ثقب على مستوى الهوية لا يسدّه جدار الحماية. والتفاصيل في [إعداد الخادم](/tutorials/java/config).

## ثانيًا: جدار الحماية طبقتان لا واحدة

وهذه أكثر نقطة يغفلها المبتدئ:

| الطبقة | الموضع | من يديرها | مثال |
| --- | --- | --- | --- |
| **مجموعة أمان السحابة / ACL الشبكة** | في جهة المنصة السحابية، والحركة **لم تصل جهازك بعد** | لوحة المزوّد السحابي | مجموعة أمان Alibaba Cloud، ومجموعة أمان Tencent Cloud، وAWS Security Group |
| **جدار حماية المضيف** | داخل نظام التشغيل، `netfilter` / `nftables` | تضبطه أنت على الجهاز | `ufw` و`firewalld` و`iptables` و`nftables` |

**والطبقتان تُضبطان معًا.** فبضبط مجموعة الأمان وحدها تفقد الحماية حين يُنقل الجهاز إلى شبكة أخرى أو تُوسَّع مجموعة الأمان؛ وبضبط جدار حماية المضيف وحده، فمجموعة الأمان الافتراضية في كثير من المنصات السحابية قد تكون واسعة أصلًا، أي أنك تترك الباب الأول مفتوحًا.

:::warn لا تُكتب هنا مسارات العمليات في المنصات السحابية
أسماء القوائم ومستوياتها ومصطلحاتها تختلف بين لوحات السحابة («مجموعة أمان» و«جدار حماية» و«ACL الشبكة» تُستخدم متبادلة)، **ولا تخمّن هذه المقالة مسارات قوائم محددة**. والمرجع توثيق مزوّدك الرسمي. والذي يمكن تأكيده: **قواعد الواردة (ingress) يجب أن تكون رفضًا كليًا افتراضيًا، ولا يُسمح إلا بالمنافذ التي سردتها.**
:::

### 2.1 ufw (شائع في Ubuntu / Debian)

`ufw` واجهة أمامية لـ `iptables` / `nftables`، ويناسب الحالات أحادية الجهاز.

```bash
sudo apt update
sudo apt install -y ufw

# مهم: اسمح بـ SSH أولًا ثم فعّل الرفض الافتراضي، وإلا أغلقت الباب على نفسك
sudo ufw allow from 203.0.113.10 to any port 22 proto tcp

sudo ufw default deny incoming
sudo ufw default allow outgoing

sudo ufw allow 25565/tcp
sudo ufw allow 19132/udp

sudo ufw enable
sudo ufw status verbose
```

و`sudo ufw status verbose` يطبع السياسة الحالية والقواعد، والطبيعي أن ترى `Default: deny (incoming), allow (outgoing)` والبنود التي فتحتها.

**والترتيب مهم**: إن نفّذت `sudo ufw enable` قبل السماح بـ SSH وانقطع اتصالك، فلا يبقى إلا الدخول من VNC / كونسول الإنقاذ في المنصة السحابية.

### 2.2 firewalld (شائع في RHEL / Rocky / AlmaLinux / Fedora)

```bash
sudo dnf install -y firewalld
sudo systemctl enable --now firewalld

sudo firewall-cmd --permanent --add-port=25565/tcp
sudo firewall-cmd --permanent --add-port=19132/udp

# اسمح لـ SSH من عنوان IP الإدارة فقط
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="203.0.113.10" port port="22" protocol="tcp" accept'

sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

و`--permanent` يكتب في الإعداد الدائم، و**يلزم `--reload` (أو إعادة تشغيل firewalld) ليسري**. والتعديل بلا `--permanent` وقتي ويضيع بعد إعادة التشغيل — ولكل من الطريقتين استخدامه، فلا تخلط بينهما وتظن أنك ضبطت.

### 2.3 iptables (الكتابة التقليدية)

```bash
# اسمح بالاتصالات القائمة وبالاسترجاع
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -i lo -j ACCEPT

# اسمح لـ SSH من عنوان IP الإدارة فقط
sudo iptables -A INPUT -p tcp -s 203.0.113.10 --dport 22 -j ACCEPT

# مدخل اللاعبين
sudo iptables -A INPUT -p tcp --dport 25565 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 19132 -j ACCEPT

# الرفض الافتراضي
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
```

وقواعد `iptables` **لا تُثبَّت افتراضيًا**، وتضيع بإعادة التشغيل. وللحفظ:

```bash
sudo apt install -y iptables-persistent
sudo netfilter-persistent save
```

### 2.4 nftables (الكتابة الحديثة)

```bash
sudo nft add table inet filter
sudo nft add chain inet filter input '{ type filter hook input priority 0; policy drop; }'
sudo nft add rule inet filter input ct state established,related accept
sudo nft add rule inet filter input iif lo accept
sudo nft add rule inet filter input ip saddr 203.0.113.10 tcp dport 22 accept
sudo nft add rule inet filter input tcp dport 25565 accept
sudo nft add rule inet filter input udp dport 19132 accept
```

:::note ufw وfirewalld في التوزيعات الحديثة هما nftables في العمق
في النوى والتوزيعات الأحدث صار `ufw` / `firewalld` يستخدمان خلفية `nftables` افتراضيًا. **ولا تُفعّل واجهتين معًا** (كأن تفتح `ufw` و`firewalld` معًا)، فهما يغطي كل منهما قواعد الآخر، ويصير التشخيص عذابًا. **اختر واحدة وأتقنها.**
:::

### 2.5 «فتح المنفذ» و«تقييد المصدر» أمران مختلفان

| الكتابة | المعنى | الخطر |
| --- | --- | --- |
| `sudo ufw allow 22/tcp` | **أي شخص يستطيع الاتصال بالمنفذ 22** | العالم كله يستطيع تخمين SSH لديك |
| `sudo ufw allow from 203.0.113.10 to any port 22 proto tcp` | **لا يتصل بالمنفذ 22 إلا `203.0.113.10`** | إن تغيّر ذلك الـ IP وجب تعديل القاعدة |

أما مدخل اللاعبين (`25565`) **فيجب** فتح مصدره، فاللاعبون من كل مكان. لكن خدمات **تستخدمها أنت وحدك** كـ SSH واللوحة وRCON وقاعدة البيانات، **يجب دائمًا تقييد مصدرها**.

:::tip ماذا لو لم يكن لديك IP ثابت
عنوان IP العام للاشتراك المنزلي يتغيّر. والخيارات: طلب IP ثابت من المشغّل، أو استخدام VPN / خادم قفز من المزوّد السحابي، أو مفاتيح SSH مع fail2ban لتقليل الخطر. **وانتبه: تقييد SSH بعنوان IP متغيّر يمنع اتصالك بعد تغيّره** — فتأكد أولًا من وجود قناة إنقاذ VNC في المنصة السحابية.
:::

## ثالثًا: تقوية SSH

SSH مدخل الإدارة، وأكثر منفذ يُخمَّن. وترتيب التقوية المُستحسن: **تأكد أولًا أن الدخول بالمفتاح يعمل، ثم أغلق الدخول بكلمة المرور**.

### 3.1 اضبط الدخول بالمفتاح أولًا

ولّد المفتاح على جهازك (إن لم يكن موجودًا):

```bash
ssh-keygen -t ed25519 -C "mc-admin"
```

وانقل المفتاح العام إلى الخادم:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub mcadmin@203.0.113.10
```

**والتحقق**: افتح طرفية جديدة وسجّل الدخول بالمفتاح بنجاح، ثم واصل الخطوة التالية.

### 3.2 عدّل إعداد sshd

حرّر `/etc/ssh/sshd_config` (بـ `sudo`):

```ini
PubkeyAuthentication yes
PasswordAuthentication no
PermitRootLogin no
KbdInteractiveAuthentication no
```

| بند الإعداد | الوظيفة |
| --- | --- |
| `PubkeyAuthentication yes` | السماح بمصادقة المفتاح العام (أساس الدخول بالمفتاح) |
| `PasswordAuthentication no` | **إغلاق مصادقة كلمة المرور**، فتفقد سكربتات التخمين هدفها مباشرةً |
| `PermitRootLogin no` | **منع دخول root مباشرةً**، فيجب على المهاجم تخمين اسم مستخدم عادي أولًا |
| `KbdInteractiveAuthentication no` | إغلاق مصادقة لوحة المفاتيح التفاعلية، لمنع تجاوز `PasswordAuthentication no` |

:::warn بعد التعديل تحقق من الصيغة ثم أعد التحميل
تحقق أولًا من صيغة الإعداد بـ `sudo sshd -t`، و**بعد نجاحه** نفّذ `sudo systemctl reload ssh` (وفي بعض التوزيعات `sshd`). فإن أعدت تشغيل SSH بإعداد خاطئ فقد تُغلق عليك تمامًا.
:::

**افحص القيم السارية فعلًا** (فقد تغطّيها مقاطع `Include`):

```bash
sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin|pubkeyauthentication'
```

:::note كتابة ملف الإعداد تتغيّر مع الإصدارات
تدعم OpenSSH الأحدث وضع مقاطع `.conf` في `/etc/ssh/sshd_config.d/`، و**إعدادات المقطع تتقدّم عادةً على الملف الرئيسي**. فإن كان في توزيعتك هذا الدليل فانظر بـ `ls /etc/ssh/sshd_config.d/` قبل التعديل هل فيه تغطية. **والأولوية الدقيقة مرجعها الخرج الفعلي لـ `sshd -T` على نظامك وتوثيق OpenSSH الرسمي.**
:::

### 3.3 تغيير المنفذ الافتراضي: اختياري وأثره محدود

غيّر منفذ SSH من `22` إلى غيره (مثل `2222`):

```ini
Port 2222
```

**ما يجلبه**: الماسحات التلقائية تمسح `22` غالبًا، فتغيير المنفذ يقلّل ضجيج السجل والتخمين العابث كثيرًا.

**وما لا يجلبه**: **ليس إجراءً أمنيًا**. فالمسح الموجّه يستطيع إيجاد SSH لديك على كل المنافذ. لذا تغيير المنفذ **لا يُغني** عن الدخول بالمفتاح وتقييد المصدر.

وإن غيّرت المنفذ فتذكّر تحديث قواعد جدار الحماية، و**أبقِ المنفذ القديم مفتوحًا حتى ينجح التحقق من الجديد**، وإلا أغلقت على نفسك كذلك.

### 3.4 fail2ban: إضافة اختيارية

**المفهوم**: يقرأ fail2ban السجل، فإذا وجد عنوان IP فشل في المصادقة مرارًا في وقت قصير **حجبه مؤقتًا** بقاعدة جدار حماية.

**والمفهوم المحوري هو jail**: الـ jail = سجل + طقم قواعد مطابقة + مجموعة معاملات حجب. وتُكتب الـ jails المفعّلة في `.conf` تحت `/etc/fail2ban/jail.d/` أو في `/etc/fail2ban/jail.local`.

```ini
[sshd]
enabled = true
port = ssh
backend = systemd
maxretry = 5
findtime = 10m
bantime = 1h
```

- `maxretry`: عدد الفشل المسموح؛ و`findtime`: نافذة الإحصاء؛ و`bantime`: مدة الحجب.
- و`backend = systemd` يناسب التوزيعات الحديثة التي يجمع فيها systemd-journald السجلات؛ وإن كانت توزيعتك تكتب في `/var/log/auth.log` فاستخدم `logpath` المقابل وفق التوثيق الرسمي.

```bash
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

:::warn لا تجعل fail2ban تميمة حظ
- إنه يحجب **عناوين IP التي فشلت** فقط، وهو **علاج لاحق** لا يمنع الموجة الأولى.
- **وحجب عنوان خطأ يمنعك أنت من الدخول**، فلا تُطل `bantime` (كأن تجعله شهورًا).
- وبنود الإعداد وقيمها الافتراضية **تتغيّر بحسب التوزيعة والإصدار**، وما سبق كتابة شائعة، فقارنه بتوثيق إصدارك.
- وتثبيت fail2ban **لا** يبيح لك إعادة فتح `PasswordAuthentication`.
:::

## رابعًا: DDoS والإساءة: ما تستطيعه وما لا تستطيعه

### 4.1 لماذا تُضرب خوادم الألعاب

- **العتبة منخفضة جدًا**: خدمات الهجوم تُباع بالكمية، وبضعة دولارات تكفي لشنّ واحد.
- **الدافع بسيط**: منافسة، أو انتقام لاعب، أو «تسلية» فحسب، أو مجرد إصابة عابرة من ماسح.
- **وخادم اللعبة هشّ خصوصًا**: فـ Minecraft **اتصال طويل الحالة**، ومصافحة TCP واحدة تستهلك موارد الخادم. ونفس عرض النطاق الموجّه إلى خدمة ويب قد يُبطئها فقط، أما على خادم لعبة فقد يجمّده أو يُسقطه.

### 4.2 ما تستطيعه

| الوسيلة | الوصف |
| --- | --- |
| **حماية المنبع / المزوّد** | يوفّر المزوّد السحابي عادةً تنظيف DDoS أساسيًا. **وهذه أنفع طبقة**، لأن الحركة تُعالَج قبل وصولها جهازك. |
| **تحديد السرعة وعدد الاتصالات** | تقييد عدد الاتصالات ومعدل الجديد لكل IP في جدار الحماية أو طبقة الوكيل، يصدّ الطوفان الضعيف. |
| **إخفاء الأصل بالوكيل** | اجعل اللاعبين يتصلون بوكيل، ولا يقبل الخادم الحقيقي إلا اتصال الوكيل (مع مفتاح التحويل). انظر [خادم الوسيط](/tutorials/java/proxy). |
| **القائمة البيضاء / مراجعة الدخول** | أشدّ وسيلة في الخوادم الصغيرة: **من لا تعرفه لا يتصل أصلًا**. |
| **تحديد المعدل في طبقة التطبيق** | تقييد معدل الاتصال في الخادم أو الملحق يخفّف مضايقة «الاتصال ثم القطع». |

### 4.3 ما لا تستطيعه، وخطأ شائع

:::warn «حجب عنوان المهاجم» لا يفيد مع الهجمات الحجمية
هذا أكثر فهم خاطئ شائع. فالهجوم الحجمي (volumetric) خصائصه:

- عناوين المصدر **بالآلاف وتتغيّر باستمرار** (وكثير منها أجهزة مصابة)، فلا تنتهي من حجبها؛
- **وجدار حمايتك يأتي بعد حركة الهجوم** — فحين تسري قواعد الحجب يكون النطاق قد امتلأ. وفي لحظة انسداد الرابط، لا يستطيع جهازك إحسان «تنفيذ قاعدة الحجب» نفسها.

**والخلاصة**: حجب IP فعّال مع مضايِق واحد، وغير فعّال أساسًا مع الهجوم الحجمي. **والمنبع وحده يحلّه**، وهذا يعني: **اقرأ بند حماية DDoS في المزوّد عند الشراء**، لا أن تبحث عن حل يوم الضرب.
:::

:::note ماذا تفعل أولًا عند الضرب
1. **تأكد هل هو هجوم فعلًا**: انظر منحنى النطاق وعدد الاتصالات والمعالج، وفرّق بين «هجوم» و«خطأ في كودك يولّد حلقة لا نهائية».
2. **تواصل مع المزوّد**: اشرح الحالة، واسأل هل فُعّل التنظيف، وهل يلزم تغيير IP.
3. **النجاة أولًا**: عند الحاجة استخدم قائمة بيضاء مؤقتة، ليبقى الخادم حيًّا.
4. **احفظ الأدلة**: احتفظ بالسجلات ومخططات الحركة، للاستئناف لدى المزوّد.
:::

## خامسًا: نظافة المفاتيح وبيانات الاعتماد

في دليل الخادم معلومات حساسة كثيرة: كلمة مرور RCON في `server.properties`، وكلمة مرور قاعدة البيانات، وحساب اللوحة، وAPI Key للمزوّد السحابي.

| القاعدة | الطريقة |
| --- | --- |
| **لا تُودَع في Git أبدًا** | الإعدادات الحاوية لكلمات مرور، و`.env`، وملفات المفاتيح كلها في `.gitignore`. **فإيداعها مرة يعني تسرّبًا دائمًا**، فتاريخ السجل يحتفظ بها. |
| **شدّد صلاحيات ملفات الاعتماد** | `chmod 600` (المالك فقط يقرأ ويكتب)، و`chmod 640` عند الحاجة (المالك يقرأ ويكتب، والمجموعة تقرأ). |
| **استخدم ملف بيئة لا التضمين الصلب** | ضع القيم الحساسة في ملف مثل `.env`، ويقرأ الكود متغيرات البيئة فقط. |
| **إن تسرّبت فبدّلها، ولا تكتفِ بالحذف** | حذف الملف **لا** يُبطل كلمة مرور تسرّبت. **يجب إعادة توليدها / إلغاؤها في الخدمة المقابلة.** |

```bash
# ملف الاعتماد للمالك فقط قراءةً وكتابةً
chmod 600 /opt/mcserver/survival/.env

# تأكد من الصلاحيات
ls -l /opt/mcserver/survival/.env
# الخرج المتوقع شبيه بـ: -rw------- 1 mcserver mcserver ... .env
```

:::warn ترتيب المعالجة بعد تسرّب كلمة مرور
1. **بدّلها فورًا**: أعد تعيين كلمة المرور / ألغِ المفتاح في الخدمة المقابلة (وهذه الخطوة هي وقف النزيف الحقيقي).
2. **افحص نطاق التأثير**: انظر السجل، وتأكد هل استُخدمت.
3. **نظّف التاريخ**: أزلها من تاريخ Git (بأدوات مثل `git filter-repo`)، لكن **لا تتوقع أن تُصلح قيمة تسرّبت فعلًا**.
4. **راجع الأسباب**: لماذا أُودعت؟ أضف `.gitignore` وفحصًا قبل الإيداع.
:::

ويُستحسن في كلمة مرور قاعدة البيانات أيضًا: **حساب مستقل لكل خدمة** (لا تستخدم `root` للجميع)، و**منح الصلاحية على قواعد الحاجة فقط**، و**تقييد المصدر إلى المضيف المحلي أو الشبكة الداخلية**.

## سادسًا: المراقبة: كيف تكتشف من يستكشفك

**لا تحتاج مراقبة الشاشة 7×24**، لكن تحتاج معرفة «من أين يُرى الشذوذ».

### 6.1 ماذا تنظر إليه

| الموضع | ماذا يُرى منه |
| --- | --- |
| `/var/log/auth.log` (Debian / Ubuntu) | سجلات نجاح وفشل دخول SSH |
| `/var/log/secure` (عائلة RHEL) | كما سبق |
| `journalctl -u ssh` | سجلات SSH التي يجمعها systemd |
| `sudo fail2ban-client status sshd` | عدد عناوين IP المحجوبة وقائمتها الآن |
| `sudo lastb` | محاولات الدخول الفاشلة (**يحتاج root، وبعض الأنظمة لا تسجّلها افتراضيًا**) |
| `ss -tlnp` | المنافذ المستمع عليها حاليًا، لكشف خدمة مكشوفة دون قصد |

```bash
# انظر آخر حالات فشل SSH (Debian / Ubuntu)
sudo grep 'Failed password' /var/log/auth.log | tail -n 20

# إحصاء عناوين المصدر الأكثر فشلًا
sudo grep 'Failed password' /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head

# من يستمع على المنافذ
sudo ss -tlnp
```

### 6.2 ما يُعدّ شذوذًا

- **كثرة `Failed password` في وقت قصير**: تخمين نموذجي.
- **دخول ناجح في وقت / من مصدر لا تعرفه**: **وهذه أخطر إشارة**، وتعني احتمال تسرّب بيانات الاعتماد.
- **ظهور مستخدم لم تنشئه**: قد يكون حساب باب خلفي أُنشئ.
- **منافذ استماع غريبة**: قد يكون برنامج تعدين أو باب خلفي ثُبّت.
- **ارتفاع شاذ في المعالج / النطاق بلا لاعبين**: قد يُستخدم جهازك مصدر هجوم.

:::tip دع السجل يناوب عنك
إن لم ترغب في تفتيش السجل يوميًا فاستخدم ملخصات مجدولة من `logwatch` أو `journalctl`، أو اضبط تنبيهات للأحداث الحرجة. **والمهم أن «يقرأه أحد»** — فسجل لا يقرأه أحد كسجل غير موجود.
:::

## سابعًا: قائمة الفحص قبل الإطلاق

- [ ] **الطبقتان مضبوطتان**: مجموعة أمان السحابة وجدار حماية المضيف، مع رفض الواردة افتراضيًا
- [ ] لا تُفتح إلا المنافذ المطلوبة فعلًا (Java `TCP 25565`، Bedrock / Geyser `UDP 19132`)
- [ ] `enable-rcon` باقٍ على `false`، أو RCON يستمع على `127.0.0.1` فقط
- [ ] منافذ قاعدة البيانات واللوحة **غير مكشوفة للإنترنت**
- [ ] SSH مضبوط بالدخول بالمفتاح، و`PasswordAuthentication no` و`PermitRootLogin no` ساريان (تحقق بـ `sshd -T`)
- [ ] SSH مقيّد المصدر، أو على الأقل يحميه fail2ban
- [ ] صلاحيات الملفات الحاوية لكلمات المرور `600`، و**ليست في مستودع Git**
- [ ] `online-mode` باقٍ على `true` (إلا إذا كنت تعرف كلفة الوضع دون اتصال بوضوح)
- [ ] تعرف بند حماية DDoS في المزوّد، وتعرف بمن تتصل عند الضرب
- [ ] تُحقّق من وصول المنافذ من **جهاز خارجي**
