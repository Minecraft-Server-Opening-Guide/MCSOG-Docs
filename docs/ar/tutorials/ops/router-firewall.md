الخادم يعمل على الجهاز، وجدار الحماية يسمح، ومع ذلك لا يستطيع اللاعبون الاتصال — والمشكلة تكاد تكون دائمًا في **تلك القفزات بين الإنترنت العام وجهازك**. توضّح هذه المقالة مسؤولية كل قفزة، وكيف تُضبط، وبأي ترتيب تُشخَّص المشكلة عند تعذّر الاتصال.

وما تقدّمه هذه المقالة هو **مفاهيم + أمثلة سطر أوامر**. أما أسماء قوائم الواجهة الرسومية ومواضعها وخياراتها فتختلف اختلافًا هائلًا بين النسخ والمصنّعين والبرامج الثابتة، وكل ما هو من هذا النوع سيُوسَم بوضوح، ولن ندّعي أنه واحد في كل مكان.

## 1. ماذا يفعل الموجّه فعلًا

«الموجّه» المنزلي في الحقيقة جهاز واحد متكامل يقوم بخمسة أمور في الوقت نفسه. وفهمها منفصلة يمنع الالتباس عند التشخيص:

| الوظيفة | الدور | المظهر عند حدوث مشكلة |
| --- | --- | --- |
| **التوجيه** | تمرير حزم IP بين WAN وLAN | لا إنترنت إطلاقًا |
| **NAT** | تحويل العناوين الداخلية إلى عامة (SNAT)، والتحويل العكسي وفق قواعد (DNAT، أي تحويل المنافذ) | الشبكة الداخلية تتصل بالإنترنت، والخارج لا يستطيع الدخول |
| **DHCP** | توزيع IP والبوابة وDNS على أجهزة الشبكة الداخلية تلقائيًا | الأجهزة لا تحصل على عنوان، أو يتغيّر عنوانها عشوائيًا |
| **DNS** | تمرير/تخزين تحليل الأسماء، وتوفير أسماء داخلية | `ping` على IP ينجح والاسم لا ينجح |
| **جدار الحماية** | تصفية ذات حالة تحدّد أي الترافيك يعبر | عند خطأ في القواعد: يمرّ كل شيء أو لا يمرّ شيء |

**وإعادة توجيه المنافذ (port forwarding) في جوهرها DNAT**: أخذ الحزم «الموجّهة إلى منفذ معيّن على IP العام»، وكتابة عنوان الوجهة والمنفذ من جديد، ثم تمريرها إلى جهاز داخلي. وهي أمر مختلف عن «السماح في جدار الحماية»:

- **NAT يحدّد إلى أين تذهب الحزمة**؛
- **وقاعدة التصفية تحدّد هل تعبر الحزمة**.

ويجب أن يتحقّق الأمران معًا ليصري تحويل المنافذ فعّالًا. ولهذا السبب «أضفت تحويل المنفذ في أنظمة مثل pfSense ومع ذلك لا يعمل» — فقاعدة التصفية لم تسمح (والنسخ الحديثة تنشئ القاعدة المقابلة تلقائيًا عادةً، انظر القسم 5).

وشرط تحويل المنافذ أن يكون **للجهاز الهدف IP داخلي ثابت**: إما **ربط DHCP ثابت** على الموجّه (وهو الموصى به)، أو ضبط IP ثابت على المضيف واستثناء العنوان من نطاق DHCP. وإلا فتغيّر IP بعد إعادة التشغيل يجعل التحويل يشير إلى الهواء.

## 2. الموجّه المنزلي والموجّه البرمجي

| الخيار | يناسب | الميزات | الثمن |
| --- | --- | --- | --- |
| **جهاز منزلي متكامل** | الاحتياجات البسيطة | جاهز من العلبة، واستهلاك منخفض، ولاسلكي | وظائف قليلة، وخيارات إعداد محدودة، وبرامج المصنّع تتوقف عن الصيانة غالبًا |
| **OpenWrt** (مثبّت على موجّه عتادي مدعوم أو على x86) | التحكّم العميق والتكلفة المنخفضة | إدارة حزم، وإعداد UCI قابل للبرمجة النصية، ومجتمع نشط | يحتاج صيانة بنفسك؛ والتفليش فيه خطر إتلاف الجهاز؛ وأداء تعريفات اللاسلكي يختلف اختلافًا كبيرًا بحسب الطراز |
| **pfSense / OPNsense** (x86) | من يريد قدرات جدار حماية/VPN كاملة | جدار حماية ذات حالة، وNAT، وIPsec/WireGuard/OpenVPN، ومخططات ترافيك، وشبكات متعددة | يحتاج جهاز x86 وبطاقتي شبكة أو أكثر؛ وكثرة الوظائف تعني سطح إعداد أوسع |

:::note مسار القائمة ليس معرفة
واجهات OpenWrt وpfSense وOPNsense عُدّلت مرارًا بين النسخ (تغيير أسماء الخيارات، ونقل مواضعها، وتغيّر القيم الافتراضية). **احفظ المفاهيم ومعاني ملفات الإعداد، فهي أبقى من حفظ «أي قائمة تنقر»**. أمثلة سطر الأوامر في هذه المقالة واجهات مستقرة؛ أما المواضع المحدّدة في الواجهة الرسومية فراجع توثيق النسخة التي ثبّتها.
:::

## 3. OpenWrt: إعداد تحويل المنافذ بـ UCI

إعداد جدار الحماية في OpenWrt في `/etc/config/firewall`، ويُعدَّل بـ`uci`. وفيما يلي الصيغة المعيارية لتحويل `TCP 25565` من الخارج إلى `192.168.1.10:25565` في الشبكة الداخلية:

```bash
# 1. أضف مقطع جدار حماية من نوع redirect
uci add firewall redirect

# 2. اضبط حقول هذا المقطع الجديد (العنصر الأخير في القائمة)
uci set firewall.@redirect[-1].name='Minecraft'
uci set firewall.@redirect[-1].target='DNAT'
uci set firewall.@redirect[-1].src='wan'
uci set firewall.@redirect[-1].src_dport='25565'
uci set firewall.@redirect[-1].dest='lan'
uci set firewall.@redirect[-1].dest_ip='192.168.1.10'
uci set firewall.@redirect[-1].dest_port='25565'
uci set firewall.@redirect[-1].proto='tcp'

# 3. ثبّت الإعداد ودع جدار الحماية يعيد توليد القواعد
uci commit firewall
/etc/init.d/firewall reload
```

ومعاني الحقول:

| الحقل | المعنى |
| --- | --- |
| `name` | اسم القاعدة، للتعريف فقط، ويمكن اختيار أي اسم |
| `target` | `DNAT` يعني تحويل عنوان الوجهة. **وهي القيمة الافتراضية لمقطع redirect**، وكتابتها صراحةً أوضح |
| `src` | المنطقة التي يأتي منها الترافيك، وهنا `wan` |
| `src_dport` | المنفذ الذي يُقصَد على جهة الإنترنت العام |
| `dest` | المنطقة التي يُحوَّل إليها، وهنا `lan` |
| `dest_ip` | IP الجهاز الهدف في الشبكة الداخلية |
| `dest_port` | المنفذ الهدف في الشبكة الداخلية |
| `proto` | البروتوكول، `tcp` / `udp` / `tcp udp` (محلّل الإعداد يقبل قائمة بروتوكولات مفصولة بمسافة) |

والعمليات الشائعة والنقاط التي يجب الانتباه إليها:

```bash
uci show firewall                 # اطبع الإعداد الحالي وتأكّد أن القاعدة كُتبت فعلًا
uci delete firewall.@redirect[0]  # احذف القاعدة redirect رقم 0 (والترقيم بحسب مخرجات uci show)
uci commit firewall
/etc/init.d/firewall reload
```

- `uci set` يعدّل الإعداد في الذاكرة فقط، و**يلزم `uci commit` ليُكتب في `/etc/config/firewall`**؛
- `reload` يعيد توليد القواعد وتحميلها، ولا يحتاج إلى إعادة تشغيل الموجّه؛
- **OpenWrt 22.03 وما بعدها تستخدم fw4 (خلفية nftables) افتراضيًا**، و21.02 وما قبلها fw3 (خلفية iptables). وصيغة `/etc/config/firewall` متطابقة أساسًا بينهما، لكن **الدروس التي تكتب أوامر `iptables` مباشرةً لا تصلح على النسخ الجديدة**، والمقابل هو `nft`؛
- **يمكن أن يختلف المنفذ الخارجي والداخلي** (بكفاية تغيير `src_dport`). وتغيير المنفذ الخارجي يقلّل احتمال المسح، لكن **هذا تقليل للضوضاء لا إجراء أمني**.

**وفي إصدار Bedrock (UDP) أو عند الحاجة إلى تحويل TCP/UDP معًا**، اكتب البروتوكول قائمة:

```bash
uci set firewall.@redirect[-1].proto='tcp udp'
```

## 4. OpenWrt: ربط DHCP ثابت

يجب أن يكون IP الهدف في تحويل المنافذ مستقرًا. وعلى OpenWrt يُربَط IP ثابت بعنوان MAC:

```bash
uci add dhcp host
uci set dhcp.@host[-1].name='mcserver'
uci set dhcp.@host[-1].mac='AA:BB:CC:DD:EE:FF'
uci set dhcp.@host[-1].ip='192.168.1.10'
uci set dhcp.@host[-1].dns='1'          # اختياري: سجّل هذا الاسم في DNS المحلي أيضًا

uci commit dhcp
/etc/init.d/dnsmasq restart
```

وملاحظات:

- `mac` هو MAC بطاقة شبكة الجهاز الهدف، **وحالة الأحرف لا تهم عادةً، لكن الصيغة يجب أن تكون ست مجموعات ست عشرية مفصولة بنقطتين**؛
- يجب أن يكون `ip` داخل نطاق LAN، و**ألا يقع في نطاق DHCP الديناميكي** (نطاق OpenWrt الديناميكي يبدأ افتراضيًا عند `100` غالبًا، و`192.168.1.10` آمن عادةً، لكن اعتمد إعدادك الفعلي)؛
- ما يُعاد تشغيله بعد تغيير إعداد `dhcp` هو **dnsmasq**، لا firewall؛
- ويمكن أيضًا ضبط IP ثابت على جهة المضيف، لكن **اختر طريقة واحدة فقط**، فإعداد الجانبين معًا يسبب تعارضًا.

## 5. pfSense / OPNsense: المفاهيم نفسها والأسماء تتغيّر

هذان النظامان FreeBSD + جدار حماية pf، ومفاهيمهما متصلة بـ OpenWrt، لكن طريقة العمل مختلفة تمامًا (الواجهة الرسومية أساسًا، وفيها أيضًا config.xml). والمفاهيم الأساسية:

| المفهوم | ملاحظة |
| --- | --- |
| **الواجهات (Interfaces)** | عادةً WAN وLAN وواجهة OPT اختيارية؛ وكل واجهة تقابل بطاقة شبكة أو VLAN |
| **تحويل المنافذ** | في **Firewall > NAT > Port Forward** تُضاف خريطة: تحديد الواجهة والبروتوكول ومنفذ الوجهة وIP الهدف والمنفذ |
| **قاعدة التصفية المرتبطة** | **NAT والتصفية أمران مختلفان**. والنسخ الأحدث **تنشئ قاعدة السماح المقابلة تلقائيًا** عند حفظ التحويل؛ وفي النسخ الأقدم خيار تأشير مثل "Add associated filter rule". **والسلوك المحدّد يتغيّر بحسب النسخة، فتحقّق في `Firewall > Rules` من وجود القاعدة فعلًا.** |
| **الأسماء البديلة (Aliases)** | **Firewall > Aliases** يتيح تعريف عدة منافذ أو عناوين باسم واحد، وتُستدعى الأسماء في القواعد، وهذا أسهل للصيانة |
| **الربط الثابت** | في صفحة خدمة DHCP (في pfSense `Services > DHCP Server`؛ وفي OPNsense صفحة DHCP المعنية) يُربَط IP ثابت بعنوان MAC |
| **انعكاس NAT (reflection)** | ليتيح لأجهزة الشبكة الداخلية الوصول إلى الخدمات الداخلية بالـ IP العام. وهو مغلق افتراضيًا غالبًا، وطريقة فتحه وأسماء خياراته تتغيّر بحسب النسخة |
| **نسخ الإعداد** | في pfSense `Diagnostics > Backup & Restore`؛ وفي OPNsense `System > Configuration > Backups`. **وبعد كل تعديل صدّر الإعداد إلزاميًا** |

وفروق النسخ التي تستحق انتباهًا إضافيًا:

- **OPNsense استبدلت خدمة DHCP الافتراضية من ISC dhcpd إلى Kea منذ 24.7**، فتبدّلت مواضع قوائم الربط الثابت تبعًا لذلك؛
- pfSense منقسم إلى خطّي CE وPlus، وقد يختلف موضع الوظيفة نفسها؛
- وأسماء الواجهة في الاثنين تغيّرت مرارًا على مدى سنوات من التطوير.

لذا: **مسار القائمة يتبع توثيق النسخة التي ثبّتها**، لكن المفاهيم الخمسة «واجهات WAN/LAN، وتحويل منافذ NAT، وقاعدة التصفية المرتبطة، والأسماء البديلة، والربط الثابت» قائمة في أي نسخة.

## 6. IPv4 العام وCGNAT

**قبل إعداد تحويل المنافذ، تأكّد أولًا هل لديك IPv4 عام أصلًا.** والطريقة بسيطة:

1. انظر **IP الذي حصلت عليه واجهة WAN** في صفحة حالة الموجّه؛
2. ومن جهاز آخر (مثل بيانات الهاتف) افتح أي موقع «ما هو IP الخاص بي»، وانظر **IP الذي يراه الخارج**؛
3. فإن **تطابقا** وكان العنوان ليس خاصًا، فلديك IPv4 عام.

والمؤشرات:

| الظاهرة | المعنى |
| --- | --- |
| IP الـ WAN داخل `10.0.0.0/8` أو `172.16.0.0/12` أو `192.168.0.0/16` | عنوان شبكة داخلية للمشغّل، أي NAT متعدد الطبقات نموذجيًا |
| IP الـ WAN داخل `100.64.0.0/10` | **نطاق مخصّص لـ CGNAT (RFC 6598)**، أي لا IPv4 عام تقريبًا بشكل مؤكّد |
| أول قفزات `traceroute` عناوين خاصة | هناك NAT على مستوى المشغّل في الوسط |
| IP الـ WAN عام، والخارج لا يستطيع الاتصال | قد يكون المشغّل أغلق منافذ الدخول، أو تحويلك/جدار حمايتك غير مضبوط، فتحقّق خطوةً خطوة |

:::warn لا تفترض أن «مكالمة واحدة تكفي للحصول على IP عام»
سياسات المشغّلين والمناطق والباقات تختلف اختلافًا كبيرًا: بعضها يمنحه مجانًا، وبعضها برسم، وبعضها لا يقدّمه صراحةً، وبعضها يمنحه لخطوط الأعمال فقط. **يمكنك الطلب، لكن لا تعتبره حلًّا مضمونًا**، وجهّز مسارًا بديلًا.
:::

وحالتان شائعتان أخريان «تبدوان كأنها بلا IP عام»:

- **NAT مزدوج**: جهاز المودم الضوئي يقوم بالاتصال وNAT بنفسه، ثم يقوم موجّهك بـ NAT مرة أخرى. والحل تحويل المودم إلى **وضع الجسر (bridge)** (ليقوم موجّهك بالاتصال)، أو إجراء تحويل منافذ على المودم أيضًا (فيلزم التحويل في الطبقتين).
- **إغلاق منافذ من المشغّل**: شائع في منافذ مثل 80/443 في بعض المناطق. واستخدام منفذ غير معياري يتجاوز ذلك عادةً، **وسياسة الإغلاق تختلف بحسب المشغّل والمنطقة**.

## 7. ثلاث طرق عندما لا يوجد IPv4 عام

| الخيار | المبدأ | الثمن |
| --- | --- | --- |
| **طلب IP عام** | أن يمنحك المزوّد عنوانًا قابلًا للدخول | قد يكون مجانيًا أو برسم أو مرفوضًا؛ وقد لا يكون ثابتًا |
| **التحوّل إلى IPv6** | IPv6 في معظم المناطق قابل للوصول من الإنترنت، ويكفي فتح جدار الحماية (انظر القسم 8) | يلزم أن يكون لدى اللاعب IPv6 أيضًا؛ ونسبة التغطية تختلف اختلافًا كبيرًا بين الشبكات |
| **VPS وسيط / نفق** | استخدام خادم بـ IP عام كنقطة عبور، تُعاد إليه حزم الترافيك إلى منزلك | قفزة إضافية، والزمن التأخيري والاستقرار يتوقّفان على عقدة العبور؛ وله كلفة نطاق |

والطرق الشائعة في وساطة VPS:

- **frp**: تشغيل `frpc` داخل المنزل و`frps` على الـ VPS، وربط منفذ الـ VPS بالخدمة الداخلية. إعداده بسيط، ويصلح لتحويل منفذ واحد (المثال في [النشر إلى بيئة يمكن الوصول إليها](/tutorials/java/deploy))؛
- **WireGuard + DNAT**: بناء نفق بين جهاز المنزل والـ VPS، ثم DNAT لترافيك الدخول على الـ VPS إلى العنوان الداخلي داخل النفق. مرن ومشفّر، لكنه يتطلّب صيانة التوجيه وقواعد التحويل بنفسك؛
- **خدمات النفق التجارية**: أقل عناءً، لكنها محدودة الترافيك/النطاق عادةً، و**جودتها متفاوتة**.

وعند الاختيار لاحظ: **إصدار Bedrock يستخدم UDP**، وكثير من حلول النفق تدعم TCP فقط افتراضيًا، فيحتاج UDP إلى تأكيد إضافي أو دفع. كما أن الوساطة تضيف **زمنًا تأخيريًا بمستوى عشرات الميلي ثانية** (بحسب المسافة الجغرافية)، فقيّم ذلك مسبقًا في أنماط اللعب الحسّاسة للزمن التأخيري.

## 8. IPv6: منطق تحويل المنافذ تغيّر

التغيّر الجوهري في IPv6 أن **العناوين تكفي، فلا حاجة إلى NAT عادةً**. ولذلك:

- لم تبقَ طبقة «تحويل المنافذ» (DNAT)، بل حلّ محلّها **السماح بترافيك الدخول في جدار الحماية**؛
- ولكل جهاز عادةً **عنوان قابل للتوجيه عالميًا**، ويُوصل إليه مباشرةً؛
- والسياسة الافتراضية لجدار الحماية هي المفتاح: **البرامج الثابتة مثل OpenWrt ترفض افتراضيًا اتصالات الدخول من جهة WAN**، فيجب أن تضيف قاعدة سماح صراحةً.

والسماح بـ`TCP 25565` لمضيف معيّن على OpenWrt:

```bash
uci add firewall rule
uci set firewall.@rule[-1].name='Allow-Minecraft-v6'
uci set firewall.@rule[-1].src='wan'
uci set firewall.@rule[-1].dest='lan'
uci set firewall.@rule[-1].dest_ip='2001:db8:abcd:1::10'
uci set firewall.@rule[-1].proto='tcp'
uci set firewall.@rule[-1].dest_port='25565'
uci set firewall.@rule[-1].family='ipv6'
uci set firewall.@rule[-1].target='ACCEPT'
uci commit firewall
/etc/init.d/firewall reload
```

**ومشكلة البادئة** هي أشهر مأزق في فتح الخادم على IPv6:

- نطاق المنزل يحصل عادةً على بادئة من المزوّد عبر **DHCPv6-PD (تفويض البادئة)** (الشائع `/56` أو `/60` أو `/64`، بحسب المزوّد)، ثم يوزّعها الموجّه على الشبكة الداخلية؛
- **وبادئة كثير من المزوّدين غير ثابتة**، فقد تتغيّر بإعادة الاتصال، أو إعادة تشغيل المودم الضوئي، أو تعديل من جهة المشغّل؛
- وبمجرد تغيّر البادئة يصبح `dest_ip` في القاعدة أعلاه باطلًا، ولا يستطيع اللاعبون الاتصال؛
- ومسارات المعالجة: اطلب من المزوّد **بادئة ثابتة** (وقد لا يمنحها)؛ أو اجعل المضيف يستخدم **معرّف واجهة مستقرًا** (مثل تثبيت اللاحقة في SLAAC/DHCPv6)، ثم **حدّث قواعد جدار الحماية تلقائيًا** بسكربت في `hotplug.d/iface` أو في مهمة مجدولة؛ ويمكن أيضًا استخدام بادئة توجيه تمنحها خدمة نفق (وهو حلّ طرف ثالث يحتاج تقييم استقراره بنفسك).

ونقاط أخرى تخصّ IPv6:

- عند اتصال اللاعب يجب استخدام **الأقواس المربعة**: `[2001:db8:abcd:1::10]:25565`؛
- ويُترك `server-ip` في `server.properties` فارغًا ليستمع إلى IPv4/IPv6 معًا (الفراغ = الربط بكل الواجهات)؛
- **وقسم معتبر من اللاعبين لا يملك IPv6 صالحًا** (خصوصًا في بعض المناطق وشبكات الهاتف)، فالأفضل أن يكون IPv6 **مكمّلًا** لـ IPv4 لا المدخل الوحيد؛
- ويمكن استخدام عناوين ULA (`fd00::/8`) في الشبكة الداخلية لعنونة داخلية مستقرة، لكن **الوصول من الخارج يظلّ معتمدًا على البادئة التي يمنحها المزوّد**.

## 9. أمان الحدود: حوّل ما تحتاجه فعلًا فقط

كل قاعدة تحويل منافذ هي باب تفتحه على الإنترنت. والمبادئ:

1. **حوّل المنافذ الضرورية فقط**. فـ Minecraft يحتاج `TCP 25565` فقط (`UDP 19132` لإصدار Bedrock).
2. **لا تحوّل هذه المنافذ أبدًا** (وهي أكثر مداخل الاختراق شيوعًا):
   - `TCP 25575` RCON (البروتوكول نفسه غير مشفّر، أي تسليم وحدة التحكّم)؛
   - `TCP 3306` MySQL/MariaDB، و`TCP 5432` PostgreSQL، و`TCP 6379` Redis، و`TCP 27017` MongoDB، و`TCP 9200` Elasticsearch؛
   - `TCP 2375` / `2376` Docker API؛
   - `TCP 445` SMB؛
   - `UDP 623` IPMI (انظر [خوادم الرفوف والمحوّلات وجدران الحماية العتادية وUPS](/tutorials/ops/hardware-rack))؛
   - `TCP 3493` NUT.
3. **لا تعرّض لوحات الإدارة مباشرةً**. فلوحات مثل Pterodactyl وBaota أهداف عالية الخطورة: سطح تأثير الثغرات واسع، وبمجرد الوصول إليها تُسيطر على الجهاز كله.
4. **استخدم منفذًا خارجيًا غير معياري لمداخل الإدارة مثل RDP / SSH** (مثلًا تحويل `50022` الخارجي إلى `22` الداخلي). وهذا يقلّل المسح الآلي فقط، **ولا يُغني عن المصادقة والتقوية** — فالمفتاح يبقى لازمًا، والتحقق بخطوتين يبقى لازمًا.
5. **فضّل VPN على التعريض**. فلتستخدم لوحة الإدارة بنفسك، الأثبت بناء نفق VPN، وتستمع اللوحة إلى العنوان الداخلي وحده.
6. **لا تفعّل UPnP / NAT-PMP على الحدود** إلا إن كنت تحتاجه فعلًا. فهو يتيح لبرامج الشبكة الداخلية ثقب جدار الحماية بنفسها، أي تسليم سياسة الحدود إلى التطبيقات.
7. **اضبط تحديد المعدّل على جدار الحماية** (مثلًا تحديد معدّل الاتصالات الجديدة على `25565`)، فيخفّف ذلك جزءًا من طوفان الاتصالات؛ واستخدمه مع تحديد الاتصالات في الخادم.
8. **فعّل حجب تسجيل الدخول مثل fail2ban على خدمات اللوحات**، وحدّثها بانتظام.

## 10. WireGuard: طريقة أكثر أمانًا من تعريض المنافذ

الفكرة: **لا تعرّض منفذ الإدارة للعالم، بل دع أجهزة الخارج تدخل الشبكة الداخلية أولًا**. وWireGuard هو أبسط خيار حاليًا — تنفيذ في النواة (دخل الخط الرئيسي في Linux 5.6)، وإعداد قصير، وقائم على UDP.

وتوليد زوج المفاتيح:

```bash
wg genkey | tee privatekey | wg pubkey > publickey
chmod 600 privatekey
```

وجهة الخادم (الجهة ذات IP العام، مثل VPS أو موجّهك البرمجي):

```ini
# /etc/wireguard/wg0.conf
[Interface]
Address = 10.10.0.1/24
ListenPort = 51820
PrivateKey = <المفتاح الخاص للخادم>

[Peer]
PublicKey = <المفتاح العام للعميل>
AllowedIPs = 10.10.0.2/32
```

والعميل (حاسوبك المحمول أو هاتفك):

```ini
# /etc/wireguard/wg0.conf
[Interface]
Address = 10.10.0.2/24
PrivateKey = <المفتاح الخاص للعميل>

[Peer]
PublicKey = <المفتاح العام للخادم>
Endpoint = vpn.example.com:51820
AllowedIPs = 10.10.0.0/24
PersistentKeepalive = 25
```

والنقاط المهمة:

- **`AllowedIPs` على جهة الخادم تعني في الوقت نفسه «أي عناوين مصدر يُسمح لهذا الطرف باستخدامها» و«ترافيك هذه العناوين يُرسل إلى هذا الطرف»**، وكتابة `10.10.0.2/32` تعني مضيفًا واحدًا؛ وكتابة `10.10.0.0/24` على جهة العميل تعني **أن ترافيك نطاق VPN فقط يمرّ بالنفق** (تقسيم المسار)، وكتابة `0.0.0.0/0, ::/0` تعني **وكيلًا شاملًا**؛
- **`PersistentKeepalive = 25` يوضع على الجهة الواقعة خلف NAT**، للحفاظ على الخريطة، ليتيح للخادم الاتصال به مبادرًا؛
- ولا تحتاج جهة العميل إلى `Endpoint` لتعمل (حين يتصل بها الخادم مبادرًا)، لكن تُكتب عادةً لتبدأ هي؛
- ويكفي السماح بـ`UDP 51820` على **جهة الخادم** (والمنفذ قابل للتخصيص)، ولا يحتاج العميل أي منفذ دخول؛
- وإن أردت أن يصل عميل VPN إلى الشبكة الداخلية كلها أو إلى الإنترنت، فعلى الخادم تفعيل تمرير IP وإجراء MASQUERADE/NAT في nftables/iptables؛
- وطريقة إعداد WireGuard على OpenWrt عبر UCI (مقطع واجهة `wireguard` في `/etc/config/network`) أو `luci-app-wireguard`، **وهي مختلفة عن صيغة wg-quick أعلاه**، لكن مفاهيم المفاتيح و`AllowedIPs` و`Endpoint` متطابقة تمامًا؛
- ولا تنسَ أيضًا: **اجعل صلاحيات ملف المفتاح الخاص `600`، ولا ترفعه إلى مستودع Git**.

## 11. ترتيب التشخيص: من الداخل إلى الخارج، طبقةً طبقة

حين يتعذّر اتصال اللاعب، **لا تشكّ في المشغّل من أول لحظة**. اتبع هذا الترتيب، فكل خطوة تعطي نتيجة «نعم/لا»:

**الخطوة 1: هل الخدمة على المضيف تستمع فعلًا**

```bash
ss -tlnp            # استماع TCP
ss -ulnp            # استماع UDP (لإصدار Bedrock)
```

- انظر عنوان الاستماع: فإن كان `127.0.0.1:25565` فـ**الجهاز نفسه فقط يستطيع الاتصال**، ويجب تغييره إلى `0.0.0.0` (أو تركه فارغًا / تحديد IP داخلي)؛
- وترك **`server-ip` فارغًا** في `server.properties` لإصدار Java يعني الربط بكل الواجهات، وكتابة `127.0.0.1` تجعل الخارج غير قادر على الوصول؛
- وتأكّد من أن الخادم أكمل التشغيل فعلًا (برؤية سجل مثل `Done`)، لا أنه متوقّف في مرحلة التشغيل.

**الخطوة 2: هل سمح جدار حماية المضيف**

```bash
sudo ufw status verbose          # Ubuntu/Debian
sudo firewall-cmd --list-all     # عائلة RHEL/Fedora
sudo nft list ruleset            # nftables
sudo iptables -S                 # iptables القديم
```

وعلى Windows افحص قواعد الدخول، وتأكّد أن موقع الشبكة معرّف «شبكة خاصة» لا «شبكة عامة». **وعلى الخادم السحابي افحص مجموعة الأمان إضافةً إلى ذلك** — فمجموعة الأمان وجدار حماية النظام موضعان مستقلان للسماح، ولا يكفي أحدهما.

**الخطوة 3: هل قاعدة تحويل المنافذ صحيحة**

- القاعدة موجودة، وIP الهدف هو IP الجهاز **الحالي** (تأكّد أولًا من سريان ربط DHCP)؛
- البروتوكول صحيح (TCP أم UDP)؛
- المنفذ الخارجي والداخلي غير مكتوبين بالعكس؛
- **اختبر من الخارج لا من الداخل**: فانعكاس NAT (hairpin) في كثير من الموجّهات مغلق افتراضيًا، ووصول الشبكة الداخلية إلى نفسها بالـ IP العام سيفشل، وهذا لا يعني أن التحويل غير مضبوط. تحقّق ببيانات الهاتف أو بأداة فحص خارجية.

**الخطوة 4: المشغّل / CGNAT**

- ارجع إلى طريقة القسم 6، وتأكّد من تطابق IP الـ WAN مع IP الذي يراه الخارج؛
- استخدم `traceroute` (`tracert` على Windows) لفحص أول القفزات: هل فيها عناوين خاصة؛
- فإن تأكّد أنك خلف CGNAT فلن يعمل تحويل المنافذ مهما ضبطته، ولا يبقى إلا مسار القسم 7.

**الخطوة 5: جهة العميل**

- هل العنوان والمنفذ مكتوبان صحيحًا، وهل النطاق يُحلّ إلى IP الحالي (فتغيّر IP الديناميكي شائع جدًا)؛
- هل جدار حماية العميل/شبكة الشركة يحجب ذلك المنفذ (بعض شبكات الشركات تسمح بـ 80/443 فقط)؛
- هل اللاعب يستخدم IPv4 أم IPv6، وهل يطابق مكدّس الخادم المفتوح؛
- هل نسخة العميل متوافقة مع الخادم (عدم تطابق نسخة البروتوكول يُرفض مباشرةً، انظر [بروتوكول فتح الخادم وإعداداته الموصى بها](/tutorials/java/protocol))؛
- هل الخادم على قائمة بيضاء، وهل هو في حالة فشل تحقّق بسبب `online-mode`.

**التأكيد بالتقاط الحزم**: على جهاز الخادم نفّذ

```bash
sudo tcpdump -ni any port 25565
```

ثم دع عميلًا خارجيًا يتصل. **فرؤية الحزم تدخل** تعني أن سلسلة التحويل قبلها سليمة، والمشكلة على جهة المضيف (جدار الحماية/الاستماع)؛ و**عدم رؤية أي حزمة** يعني أن المشكلة في الخارج أكثر (التحويل/المشغّل).

## 12. قائمة التحقّق قبل الإطلاق

- [ ] تأكّدت من أن لديك **IPv4 عامًا**، أو اخترت بديلًا (IPv6 / وساطة VPS / نفق)
- [ ] للجهاز الهدف **IP داخلي ثابت** (ربط DHCP ثابت أو عنوان ثابت على المضيف، وطريقة واحدة فقط)
- [ ] حوّلت `TCP 25565` فقط (وإصدار Bedrock يضيف `UDP 19132`)
- [ ] **RCON `25575`، ومنافذ قواعد البيانات، وDocker API، وIPMI لم تُعرَّض أيّها**
- [ ] لوحة الإدارة غير متصلة بالإنترنت مباشرةً، أو يُوصل إليها عبر VPN
- [ ] برنامج الموجّه/جدار الحماية محدّث، وإدارة جهة WAN مغلقة، وكلمة المرور الافتراضية مبدّلة
- [ ] تحقّقت من الوصول إلى المنفذ من **الخارج** (لا من الداخل)
- [ ] إن كنت تستخدم IPv6: تحقّقت هل تتغيّر البادئة، ولديك طريقة لتحديث القواعد
- [ ] الإعداد مُصدَّر كنسخة احتياطية (الموجّه وجدار الحماية كلاهما)
- [ ] على جهة الخادم جدار حماية للمضيف أيضًا، و**السماح في الموضعين متطابق**
