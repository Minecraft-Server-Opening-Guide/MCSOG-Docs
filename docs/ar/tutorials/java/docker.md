كانت المقالات السابقة تثبّت Java على المضيف مباشرةً وتشغّل jar الخادم مباشرةً. وهذه المقالة تستبدل ذلك بـ**الحاويات**: تصف الخادم مع بيئة تشغيله في ملف `docker-compose.yml` واحد، وتترك التشغيل لـ Docker.

الحاوية ليست إلزامية، لكنها تحلّ عدة مشكلات مزمنة: **تلوّث المضيف بإصدارات Java، وإعادة كل شيء عند تغيير الجهاز، وعدم القدرة على الرجوع بعد تحديث فاشل**. والكلفة أن تتعلّم طبقة أدوات إضافية، وأن تتخذ «الأحجام والنسخ الاحتياطي» انضباطًا تنفّذه.

## 1. لماذا الحاويات

### 1.1 الفوائد

| الفائدة | التجلّي المحدد |
| --- | --- |
| **بيئة نظيفة بلا تداخل** | وقت تشغيل Java داخل الصورة، ولا يحتاج المضيف تثبيت أي JDK؛ وتشغيل خادمي 1.20 و1.21 معًا لا يستدعي التنازع على إصدار Java في النظام |
| **قابلية الإعادة** | وسم الصورة ونوع النواة والإصدار والذاكرة والمنافذ كلها في ملف واحد، فحين تغيّر الجهاز تنقل الملف فقط |
| **سهولة الرجوع** | انسخ `/data` احتياطيًا قبل الترقية، وإن ظهرت مشكلة بعدها أعد رقم الإصدار وأعد التشغيل؛ ويمكن تثبيت وسم الصورة كذلك |
| **إدارة عمليات مريحة** | إعادة التشغيل بعد الانهيار والإقلاع مع النظام تتولاهما سياسة `restart`، بلا كتابة وحدة systemd بنفسك |
| **حذف نظيف** | إذا لم تعد تريده تحذف الحاوية والحجم، ولا تبقى أدلة ومستخدمون متناثرون على المضيف |

### 1.2 الكلفة والشروط المسبقة

| الكلفة | الوصف |
| --- | --- |
| **طبقة إضافية للتعلّم** | مفاهيم الصورة والحاوية والحجم والشبكة وCompose لا مفرّ منها؛ وعند الخطأ يجب أن تعرف قراءة `docker compose logs` |
| **انضباط الأحجام والنسخ الاحتياطي** | الحفظ ليس في «الدليل الذي تعرفه»، بل في الحجم؛ وعدم النسخ الاحتياطي يعني عدم وجود نسخة |
| **كلفة أداء صغيرة لكنها ليست صفرًا** | طبقة NAT إضافية في الشبكة وطبقة overlay إضافية في نظام الملفات، والكلفة عادةً أقل بكثير من عنق الخادم نفسه؛ لكن **ضبط حدود الذاكرة والمعالج خطأً يُبطئ الخادم أو يقتله مباشرةً** |
| **بعض النوى/الملحقات تحتاج تعديلًا** | الملحقات التي تحتاج إدخالًا من الكونسول أو منافذ إضافية أو إصدار Java محددًا أو تعتمد مكتبات أصلية قد تحتاج إعدادًا إضافيًا؛ التفاصيل في [تحسين الأداء](/tutorials/java/optimize) و[إدارة الملحقات](/tutorials/java/plugin-manage) |

:::note الحاوية ليست جهازًا افتراضيًا
الحاوية والمضيف يتشاركان النواة، فـ«العزل» يعني عزلًا على مستوى العمليات ونظام الملفات، لا حدًّا أمنيًا. وroot داخل الحاوية لا يساوي root على المضيف تلقائيًا، لكن **من تمنحه صلاحية Docker فكأنك منحته root على المضيف**.
:::

## 2. تثبيت Docker وإضافة Compose

لا تنسخ «سكربتات تثبيت بأمر واحد» مجهولة المصدر. وفيما يلي مسار التثبيت اليدوي الكامل لـ **Ubuntu / Debian** (مع شرح وظيفة كل أمر)، وللتوزيعات الأخرى وWindows / macOS انظر المداخل الرسمية في آخر هذا القسم.

### 2.1 تحديث النظام وتنظيف الإصدارات القديمة

```bash
sudo apt update
sudo apt upgrade -y
```

تحقق أولًا هل النظام يحمل حزمًا قديمة مثل `docker.io` و`docker-compose` و`podman-docker` و`containerd` و`runc` — فهي **تتعارض** مع النسخة الرسمية (تنازع المنافذ وملفات الإعداد والاعتماديات):

```bash
sudo apt remove $(dpkg --get-selections docker.io docker-compose docker-compose-v2 docker-doc podman-docker containerd runc 2>/dev/null | cut -f1)
```

وتفكيك الأمر: `dpkg --get-selections` يسرد الحزم المثبَّتة، و`cut -f1` يأخذ أسماء الحزم فقط، و`apt remove` يزيلها واحدةً واحدة.

:::note تنبيه
إن لم يكن النظام قد ثبّت Docker قط، فسيقول هذا الأمر «لم يتم العثور على هذه الحزم»، **وهذا طبيعي** ويمكن تجاهله.
:::

### 2.2 تثبيت المتطلبات المسبقة

يستخدم مستودع Docker الرسمي HTTPS، فيحتاج النظام إلى قدرة التحقق من الشهادات والتنزيل:

```bash
sudo apt install -y ca-certificates curl
```

- `ca-certificates`: مجموعة الشهادات الجذرية، تتيح للنظام التحقق من هوية مواقع HTTPS، وتتجنّب أخطاء الشهادة عند تنزيل المفاتيح.
- `curl`: أداة تنزيل سطرية، تُستخدم لجلب المفتاح العام GPG الخاص بـ Docker.

### 2.3 إضافة مفتاح Docker الرسمي GPG

يحتاج مدير الحزم إلى «مفتاح عام بتوقيع رقمي» للتحقق من مصدر البرمجيات، لمنع تنزيل حزم مُعدَّلة.

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

وشرح كل سطر:

- `install -m 0755 -d /etc/apt/keyrings`: إنشاء دليل مخصص لمفاتيح مصادر الطرف الثالث، بصلاحية `rwxr-xr-x`.
- `curl -fsSL ... -o ...`: تنزيل المفتاح العام وحفظه. `-f` فشل صامت عند الخطأ (بلا كتابة صفحة الخطأ)، و`-s` صمت، و`-S` إظهار الخطأ مع الصمت، و`-L` متابعة التحويلات، و`-o` تحديد مسار الخرج.
- `chmod a+r`: منح صلاحية القراءة لكل المستخدمين. **وهذه الخطوة لا تُترك**، وإلا فشل `apt update` في قراءة المفتاح.

وإن فشل `curl` بسبب الشبكة، استخدم `wget` بدلًا منه:

```bash
sudo wget -O /etc/apt/keyrings/docker.asc https://download.docker.com/linux/ubuntu/gpg
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

### 2.4 إضافة مستودع APT الرسمي لـ Docker

```bash
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc
EOF
```

- هذا هو **تنسيق DEB822** (يدعمه Ubuntu 22.04+ وDebian الأحدث)، وهو أوضح من `sources.list` القديم ذي السطر الواحد.
- `Suites` يقرأ بـ `$(. /etc/os-release && echo ...)` **اسم إصدار الجهاز ديناميكيًا** (مثل `jammy` و`noble` و`bookworm`)، فيضمن مطابقة المستودع لإصدار النظام مطابقةً صارمة؛ ويمكنك أيضًا كتابة الاسم صريحًا.
- `Signed-By` يشير إلى المفتاح السابق، فيضمن أن كل حزمة تُنزَّل من هذا المستودع موقّعة رسميًا من Docker.

:::warn تنبيه لمستخدمي Debian
عنوان المستودع على Debian هو `https://download.docker.com/linux/debian`، واسم الإصدار من `VERSION_CODENAME` (مثل `bookworm`)، والكتابة كما أعلاه مع استبدال `ubuntu` بـ `debian`.
:::

### 2.5 تثبيت محرّك Docker وCompose

```bash
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

ووظائف المكوّنات:

| اسم الحزمة | الوظيفة |
| --- | --- |
| `docker-ce` | محرّك Docker Community Edition الأساسي، يتولّى إنشاء الحاويات وإدارتها |
| `docker-ce-cli` | عميل سطر الأوامر، يوفّر أمر `docker` |
| `containerd.io` | وقت تشغيل الحاويات الأدنى، يدير دورة حياة الحاوية |
| `docker-buildx-plugin` | إضافة البناء، تدعم بناء صور متعددة المنصات |
| `docker-compose-plugin` | إضافة Compose v2، توفّر أمر `docker compose` |

### 2.6 التشغيل والتحقق

```bash
sudo systemctl start docker
sudo systemctl enable docker
sudo systemctl status docker
```

ظهور `active (running)` يعني السلامة (اضغط `q` للخروج من صفحة الحالة). و`enable` يجعل Docker يبدأ مع النظام.

ثم تحقق بالصورة الرسمية للاختبار من «القدرة على السحب والتشغيل»:

```bash
sudo docker run --rm hello-world
```

وظهور `Hello from Docker!` يعني سلامة البيئة.

### 2.7 إعداد مسرّع مرايا محلي (مُستحسن للخوادم داخل الصين)

طبقات صور Docker Hub تُنزَّل من داخل الصين عادةً ببطء أو تنتهي مهلتها. ويمكن إعداد مسرّع **بلا تغيير اسم الصورة**، ليمر `docker pull` تلقائيًا عبر موقع مرآة.

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<EOF
{
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://hub.rat.dev",
    "https://dockerproxy.net"
  ]
}
EOF
sudo systemctl daemon-reload
sudo systemctl restart docker
```

والتحقق من سريانه:

```bash
docker info | grep -A5 "Registry Mirrors"
```

:::warn عن مواقع المرايا من طرف ثالث
مواقع التسريع المذكورة أعلاه **خدمات طرف ثالث يصونها المجتمع**، وتوفّرها وسياسات تحديد سرعتها وأمانها تتغيّر في أي وقت، وقد تتوقف خدمتها يومًا ما.

- استخدمها **لسحب الصور العامة فقط**، ولا تمرّر صورًا خاصة أو بيانات اعتماد عبرها؛
- إن تعطّل موقع منها فاحذفه من القائمة ثم `systemctl restart docker`؛
- والطريقة الأكثر استقرارًا في الإنتاج أن تبني مستودع صور خاصًا بك (مثل Harbor)، أو تستخدم خدمة صور حاويات من مزوّد سحابي.
:::

وثمة طريقة مؤقتة أخرى هي **إضافة بادئة أمام اسم الصورة مباشرةً** (مثل `docker run docker.1ms.run/hello-world`)، لكن اسم الصورة المسحوبة يحمل البادئة حينها، وتُعدّ **صورتين مختلفتين** عن الصورة نفسها بلا بادئة، فيكثر السحب المكرّر ويهدر القرص، و**لا يُنصح بها على المدى الطويل**.

### 2.8 عن مجموعة مستخدمي docker

على Linux يمكن إضافة المستخدم إلى مجموعة `docker` للاستغناء عن `sudo`:

```bash
sudo usermod -aG docker $USER
# يلزم تسجيل الدخول من جديد (أو newgrp docker) ليسري
```

:::warn هذا يعادل منح المستخدم صلاحية root على المضيف
فيمكنه تركيب أي دليل، وتشغيل حاويات ذات امتيازات، وتعديل iptables. وهذا مقبول على جهاز شخصي، **لكنه يستدعي الحذر على خادم متعدد المستخدمين**. والتقوية ذات الصلة في [تقوية أمان النظام](/tutorials/ops/system-security).
:::

### 2.9 المداخل الرسمية للمنصات الأخرى

| المنصة | المدخل الرسمي |
| --- | --- |
| Linux (مختلف التوزيعات) | [Install Docker Engine](https://docs.docker.com/engine/install/) |
| إضافة Compose على Linux | [Install the Compose plugin](https://docs.docker.com/compose/install/linux/) |
| Windows / macOS | [Docker Desktop](https://docs.docker.com/desktop/) |

وبعد التثبيت تأكد من أمرين: **أن خدمة Docker تعمل**، و**أن Compose هو إضافة v2 (`docker compose` بمسافة في الوسط، لا `docker-compose`)**.

```bash
docker --version
docker compose version
docker run --rm hello-world
```

:::warn عن مجموعة مستخدمي docker
على Linux، إضافة المستخدم إلى مجموعة `docker` تتيح تشغيل Docker بلا `sudo`، لكن **هذا يعادل منح المستخدم صلاحية root على المضيف** (تركيب أي دليل، وتشغيل حاويات ذات امتيازات). وهذا مقبول على جهاز شخصي، ويستدعي الحذر على خادم متعدد المستخدمين. والتقوية ذات الصلة في [تقوية أمان النظام](/tutorials/ops/system-security).
:::

## 3. الصورة: `itzg/minecraft-server`

أكثر الصور استخدامًا في مجتمع نسخة Java هي **`itzg/minecraft-server`** (صيانتها نشطة وتوثيقها مكتمل، وتدعم Vanilla / Paper / Purpur / Fabric / NeoForge / Forge وغيرها من النوى). وقد حوّلت خطوات «تنزيل النواة، وتوليد الإعداد، وقبول EULA، وتشغيل RCON» إلى متغيرات بيئة.

```bash
docker pull itzg/minecraft-server
```

:::warn اختر مصدر الصورة وثبّت الوسم
اسحب من الصور الرسمية أو المصانة طويلًا فقط؛ و**لا تستخدم `latest` دائمًا في الإنتاج** — فالـ `latest` قد يتحوّل بهدوء إلى إصدار جديد بعد `pull` ما، وعند المشكلة لن تعرف هل تغيّر الإعداد أم الإصدار. وإن أردت ملاحقة الأحدث فاكتب رقم الإصدار صريحًا وانسخ احتياطيًا قبل الترقية.
:::

## 4. ملف `docker-compose.yml` كامل

أنشئ دليلًا جديدًا (مثل `~/mcsog-java`)، وأنشئ فيه `docker-compose.yml`:

```yaml
services:
  minecraft:
    image: itzg/minecraft-server
    container_name: mcsog-java
    ports:
      - "25565:25565/tcp"
    environment:
      EULA: "TRUE"
      TYPE: "PAPER"
      VERSION: "1.21.11"
      MEMORY: "4G"
      ONLINE_MODE: "TRUE"
      ENABLE_RCON: "true"
      RCON_PASSWORD: "change-me-to-a-long-random-string"
      TZ: "Asia/Shanghai"
    volumes:
      - mcsog-java-data:/data
    stdin_open: true
    tty: true
    restart: unless-stopped

volumes:
  mcsog-java-data:
    name: mcsog-java-data
```

ولا يحتاج Compose v2 إلى حقل `version:` في الأعلى **بعد الآن**، وإن كتبته يُتجاهل (وبعض الإصدارات تنبّه إليه).

وشرح البنود:

| الحقل | الوظيفة |
| --- | --- |
| `image` | أي صورة تُستخدم. حذف الوسم يعني `:latest`، وهو غير موصى به |
| `container_name` | اسم حاوية ثابت، تستخدمه لاحقًا في `logs` / `exec` / `attach`، وهو أسهل تذكّرًا من الاسم المولَّد تلقائيًا |
| `ports` | `منفذ-المضيف:منفذ-الحاوية/البروتوكول`. ونسخة Java هي **TCP 25565**، وكتابتها `"25565:25565/tcp"` أقل عرضةً لسوء الفهم |
| `environment` | الإعدادات التي تقرأها الصورة، انظر جدول القسم 6 |
| `volumes` | `اسم-الحجم:/data`. **الحفظ والملحقات والإعدادات كلها في `/data`**، وهو الشيء الوحيد الذي لا يجوز فقده في النشر كله |
| `stdin_open: true` | إبقاء الإدخال القياسي للحاوية مفتوحًا، وإلا تعذّر عليك **الكتابة** في كونسول الخادم |
| `tty: true` | تخصيص طرفية زائفة، ليكون للكونسول تفاعل وصدى طبيعيان (يُستخدم مع `docker attach`) |
| `restart: unless-stopped` | إعادة الرفع تلقائيًا بعد الانهيار أو إعادة تشغيل المضيف؛ لكنه **لا يُرفع تلقائيًا بعد `docker compose stop` اليدوي**، وهو سلوك منطقي |

والسبب في كتابة `name: mcsog-java-data` صراحةً في `volumes` هو جعل اسم الحجم **قابلًا للتوقّع**. فبدونها يضيف Compose بادئة اسم المشروع تلقائيًا (فيصير `mcsogjava_mcsog-java-data` وأشباهه)، فيسهل الخطأ في اسم الحجم عند كتابة أوامر النسخ الاحتياطي لاحقًا.

:::note `EULA=TRUE` شرط قانوني لا مفتاح تقني
`EULA: "TRUE"` يعني **أنك قرأت [اتفاقية ترخيص المستخدم النهائي لـ Minecraft](https://aka.ms/MinecraftEULA) ووافقت عليها**. وهذا شرط مسبق لاستخدام برمجيات الخادم، والصورة تكتب إقرارك في `eula.txt` فقط. وإن لم تكتب هذا المتغير (أو كتبته `FALSE`) خرج الخادم فور بدئه. فاقرأ الاتفاقية فعلًا قبل التعبئة.
:::

:::tip أجرِ «فحصًا» بعد كل تعديل
بعد كل تعديل لملف compose شغّل `docker compose config` أولًا: فهو يطبع المنافذ والأحجام ومتغيرات البيئة بعد فكّها، ويخطئ في موضعه عند أي خطأ كتابي، وهو أسرع بكثير من تفتيش السجل بعد التشغيل.
:::

```bash
docker compose config
```

## 5. الشبكة وجدار الحماية (أكثر الأقسام مزالق)

هذا القسم أهم جزء في المقالة. فسلوك شبكة Docker **مختلف تمامًا عن حدس «ثبّت برنامجًا وافتح منفذًا»**، وكثير من مشكلات «جدار الحماية فاتح ومع ذلك يُمسح المنفذ»، و«الشبكة الداخلية تعطّلت فجأة»، و«بعد تغيير الجهاز لا يتصل» جذورها هنا.

### 5.1 جدار حماية النظام لا يضبط Docker

**الخلاصة أولًا: قواعد `ufw` و`firewalld` و`iptables` التي تكتبها بيدك كلها باطلة تجاه المنافذ التي تعرضها حاويات Docker.**

والسبب في ترتيب إقلاع Docker وموضع القواعد:

- عند إقلاع خدمة Docker **تنشئ بنفسها** قواعد `iptables`، منها سلسلة `DOCKER` في جدول `nat` وسلاسل `DOCKER` و`DOCKER-ISOLATION` و`DOCKER-USER` في جدول `filter`.
- وتُدرَج هذه القواعد **قبل** قواعد جدار حماية النظام (في أول سلسلة `FORWARD`)، ويمرّر Docker بحزم في سلسلة `FORWARD` من تلقاء نفسه.
- والنتيجة: تصل الحزم إلى قواعد Docker قبل أن تصل إلى قواعد `ufw`.

وطريقة التحقق (**يُستحسن أن تجريها فعلًا، فأثرها أعمق**):

```bash
# 1. ارفض المنفذ صراحةً أولًا
sudo ufw deny 25565/tcp

# 2. تأكد أن القاعدة سارية
sudo ufw status numbered

# 3. شغّل حاوية تعرض هذا المنفذ
docker run -d --name test-web -p 25565:80 nginx

# 4. اتصل من جهاز آخر
#    telnet IP-العام-الخاص-بك 25565
#    ← سينجح. فقد تُجاوَز رفض ufw تمامًا.
```

### 5.2 الحلول الأربعة الصحيحة

**الحل الأول: اربط المنفذ بواجهة الاسترجاع (موصى به، وهو الأكثر أمانًا وأبسطها)**

```yaml
services:
  mc:
    ports:
      - "127.0.0.1:25565:25565/tcp"
```

بعد إضافة البادئة `127.0.0.1:` يستمع المضيف على هذا المنفذ **على واجهة الاسترجاع فقط**، و**يتعذّر الاتصال به من الإنترنت مباشرةً**. وللإتاحة للخارج، يحوّله وكيل عكسي على المضيف:

```nginx
# /etc/nginx/nginx.conf (وحدة stream، تحويل في الطبقة الرابعة)
stream {
    upstream mc_backend {
        server 127.0.0.1:25565;
    }
    server {
        listen 25565;
        proxy_pass mc_backend;
        proxy_timeout 300s;
    }
}
```

وبهذا تعود قواعد جدار الحماية فعّالة: فالخارج لا يصل إلا إلى Nginx، وNginx يحوّل إلى الحاوية على واجهة الاسترجاع المحلية. **ونسخة Bedrock (UDP) تنطبق عليها الطريقة نفسها، بـ `listen 19132 udp;`.**

**الحل الثاني: استخدام سلسلة `DOCKER-USER`**

`DOCKER-USER` سلسلة تحفظها Docker رسميًا و**لا يغطيها Docker بنفسه**، وتناسب تقييد المصادر:

```bash
# اسمح لمنفذ 25565 من المصدر المحدد فقط، وأسقط الباقي
sudo iptables -I DOCKER-USER -p tcp --dport 25565 ! -s 203.0.113.0/24 -j DROP

# اعرض القواعد
sudo iptables -L DOCKER-USER -n --line-numbers
```

وانتبه:

- استخدم `-I` (الإدراج في الأول) لا `-A`، لتتجنّب أن تسبقك قواعد تمرير سابقة.
- القواعد **تُفقد بعد إعادة التشغيل**، فتحتاج `iptables-persistent` أو سكربت إقلاع لتثبيتها.
- هذه السلسلة تعالج حركة **التحويل** فقط، ولا تعمل في نمط الشبكة `host` (انظر 5.4).

**الحل الثالث: استخدام [ufw-docker](https://github.com/chaifeng/ufw-docker) ليعود UFW يضبط الحاويات (موصى به لمن «يريد إبقاء UFW المدخل الموحّد»)**

الحلّان السابقان إما يغيّران طريقة ربط المنفذ (الحل الأول)، أو يستدعيان صيانة قواعد iptables يدويًا (الحل الثاني). **وإن أردت أن تبقى إدارة كل قواعد جدار الحماية بأداة `ufw` وحدها**، فهذا السكربت أقلّها عناءً:

فكرته ليست «التجاوز» أو «التعطيل»، بل **إعادة ربط سلسلة `DOCKER-USER` التي تحفظها Docker بسلسلة التحويل في UFW**، فيصبح أمر `ufw route` يدير منافذ الحاويات مباشرةً.

**التثبيت (ثلاثة أوامر)**:

```bash
sudo wget -O /usr/local/bin/ufw-docker \
  https://github.com/chaifeng/ufw-docker/raw/master/ufw-docker
sudo chmod +x /usr/local/bin/ufw-docker
sudo ufw-docker install
```

يفعل `ufw-docker install` أمرين: **ينسخ** `/etc/ufw/after.rules` احتياطيًا، ثم **يضيف** القواعد في آخر الملف (وأهمها `-A DOCKER-USER -j ufw-user-forward`). وهو **لا** يغيّر إعداد Docker، فيبقى Docker يدير الشبكة بنفسه.

وتحقق بعد التثبيت:

```bash
ufw-docker check     # تحقق هل كُتبت القواعد
ufw-docker status    # اعرض قواعد التحويل المفتوحة حاليًا
```

:::warn أعد تشغيل الخادم بعد التثبيت
ينبّه المؤلف صراحةً: **أحيانًا لا تسري القواعد بعد إعادة تشغيل UFW**، وعندها يكفي إعادة تشغيل الخادم. وفي الإنتاج رتّب نافذة صيانة.
:::

**الاستخدام اليومي** (بأخذ منفذ 25565 في نسخة Java مثالًا):

```bash
# اسمح بالوصول الخارجي إلى منفذ الحاوية 25565 (انتبه: املأ[منفذ الحاوية]لا منفذ المضيف)
sudo ufw route allow proto tcp from any to any port 25565

# سحب السماح (الإلغاء)
sudo ufw route delete allow proto tcp from any to any port 25565

# اعرض قواعد حاوية معينة فقط
ufw-docker list mc

# اسمح باسم الحاوية مباشرةً (كتابة مختصرة يوفّرها السكربت)
sudo ufw-docker allow mc 25565
sudo ufw-docker allow mc 25565/tcp

# اسحب قواعد حاوية معينة
sudo ufw-docker delete allow mc 25565
```

**ونسخة Bedrock (UDP) بالطريقة نفسها**:

```bash
sudo ufw route allow proto udp from any to any port 19132
sudo ufw-docker allow mc-bedrock 19132/udp
```

**ماذا لو تغيّر IP الحاوية**: يتغيّر IP بعد إعادة إنشاء الحاوية، ويوفّر السكربت أمر إعادة تحميل:

```bash
sudo ufw-docker reload
```

**لماذا `ufw route` (سلسلة التحويل) لا `ufw allow` (سلسلة الإدخال)**:

| الأمر | النطاق | الخطر |
| --- | --- | --- |
| `ufw allow 25565` | يفتح 25565 على **المضيف والحاوية معًا** | قد يكشف خدمات المضيف عرضًا |
| `ufw route allow … port 25565` | يفتح حركة التحويل إلى الحاوية **فقط** | يبقى 25565 على المضيف مغلقًا، والحدود واضحة |

**اختياري: تحديد نطاقات شبكية مخصصة مسموح لها بالوصول إلى الحاويات**

الثقة الافتراضية بالنطاقات الخاصة القياسية فقط (`10.0.0.0/8` و`172.16.0.0/12` و`192.168.0.0/16`). وإن كانت شبكتك الداخلية بنطاق آخر:

```bash
# اكتشاف نطاقات كل شبكات Docker تلقائيًا (أعد التنفيذ بعد إضافة/حذف شبكة)
sudo ufw-docker install --docker-subnets

# أو حدّدها صريحًا
sudo ufw-docker install --docker-subnets 192.168.207.0/24 10.207.0.0/16
```

**كيف تزيله إن لم تعد تحتاجه**:

```bash
sudo ufw-docker uninstall   # يستعيد إعداد UFW ويحذف الملفات المثبَّتة
```

**فوائد هذا الحل وكلفته**:

| | الوصف |
| --- | --- |
| ✓ لا تعطّل iptables في Docker | فالحاويات تصل إلى الإنترنت كما هي، ولا تحتاج صيانة يدوية عند إضافة شبكة Docker |
| ✓ أداة واحدة من البداية للنهاية | منافذ المضيف بـ `ufw allow`، ومنافذ الحاويات بـ `ufw route allow`، وكلها مرئية في `ufw status` |
| ✓ يدعم IPv6 وSwarm | يحدّث `after6.rules` عند الحاجة؛ وفي نمط Swarm يمكن إدارته من عقدة الإدارة |
| ✗ سكربت طرف ثالث | ليس مكوّنًا رسميًا من Docker أو Canonical، فتتابع تحديثه وتدقيقه بنفسك (والسكربت قصير، ويُستحسن قراءته) |
| ✗ تملأ منفذ الحاوية | مع `-p 8080:80` تستخدم `80` لا `8080`، وهذه أكثر نقطة يُخطئ فيها |
| ✗ يحتاج إعادة تشغيل الخادم بعد أول تثبيت | انظر التحذير أعلاه |

**الحل الرابع: إيقاف إدارة iptables في Docker (غير موصى به للمبتدئ)**

```json
// /etc/docker/daemon.json
{
  "iptables": false
}
```

وبعد التعديل `sudo systemctl restart docker`. والكلفة:

- **تعيين المنافذ (`-p`) يبطل**، لأن قواعد NAT لم تعد تُولَّد تلقائيًا؛
- ولا تصل الحاويات إلى الإنترنت افتراضيًا، فتحتاج ضبط SNAT بنفسك؛
- ويتأثر الاتصال بين الحاويات عبر الجسر كذلك.

فلا تفعل ذلك إلا إذا كنت تعرف تمامًا أنك ستتولّى NAT بنفسك.

### 5.3 طرق كتابة تعيين المنفذ الثلاث والفرق بينها

| الكتابة | عنوان الاستماع | من يصل | الحالة المناسبة |
| --- | --- | --- | --- |
| `-p 25565:25565` | `0.0.0.0` (كل الواجهات) | **الإنترنت + الشبكة الداخلية كليًا** | مقبول فقط إن كنت قد أمنت بمجموعة أمان/جدار سحابي |
| `-p 127.0.0.1:25565:25565` | الاسترجاع فقط | **الجهاز نفسه فقط** | **موصى به**: مع وكيل عكسي أو نفق SSH |
| `-p 192.168.1.10:25565:25565` | واجهة محددة | تلك الشبكة فقط | خادم داخلي/شبكة محلية صرفة |

**النقطة الجوهرية**: السلوك الافتراضي لـ `-p 25565:25565` هو الربط بـ `0.0.0.0`، أي **بمجرد التعيين يكون المنفذ مفتوحًا للإنترنت** (ومجموعة أمان المزوّد السحابي بوابة أخرى، لكنها ليست جدار حماية الجهاز). وكثيرون يظنون «لم أمسّ جدار الحماية فالأمر آمن»، والمنفذ في الحقيقة مفتوح كليًا.

### 5.4 كيف تختار من أنماط الشبكة الخمسة

| النمط | الوصف | المزايا | العيوب | متى تستخدمه |
| --- | --- | --- | --- | --- |
| `bridge` (الافتراضي) | تتصل الحاوية بجسر `docker0` وتخرج عبر NAT | عزل جيد ومنافذ مضبوطة | طبقة NAT إضافية؛ ولا وصول إلا بـ `-p` | **معظم الحالات** |
| `host` | **تستخدم الحاوية مكدّس شبكة المضيف مباشرةً**، بلا جسر وبلا NAT | أفضل أداء وأدنى تأخير | **فقدان كامل لعزل الشبكة**؛ وتعارض المنافذ؛ ويُتجاهل `-p`؛ ولا تسري قواعد جدار Docker | الأداء الأقصى أو المنافذ المعقّدة |
| `macvlan` | تمنح الحاوية MAC مستقلًا وIP على الشبكة المحلية، فتبدو كجهاز حقيقي في الشبكة | **يمكن اكتشافها مباشرةً داخل الشبكة** (قائمة Bedrock المحلية، وبث LAN في نسخة Java) | تحتاج تعاون المبدّل/الموجّه؛ وبعض بيئات السحابة لا تدعمها | اللعب المحلي والحالات التي تحتاج الاكتشاف بالبث |
| `overlay` | شبكة افتراضية عبر عدة مضيفين (تستخدمها Swarm) | تجميع عدة أجهزة | تعقيد مرتفع | النشر على عدة أجهزة |
| `none` | بلا شبكة | عزل تام | لا تتصل الحاوية بالشبكة | مهام حوسبة دون اتصال فقط |

```yaml
# مثال على نمط host (انتبه: قسم ports بلا معنى هنا)
services:
  mc:
    network_mode: host
    environment:
      SERVER_PORT: "25565"
```

:::warn في نمط host يصبح جدار الحماية «فعّالًا» فعلًا، لكن المنفذ مفتوح تمامًا كذلك
نمط `host` لا يمرّ بقواعد NAT في Docker، فيستطيع `ufw` **حينها** صدّ المنفذ. لكن الحاوية تحتل منفذ المضيف مباشرةً، و**بمجرد أن يستمع الخادم يمكن الاتصال به من الإنترنت**، والأمان يعتمد كليًا على جدار حماية نظامك ومجموعة الأمان. فتأكد من صحة القواعد قبل الاستخدام.
:::

### 5.5 تعارض نطاق `docker0` (السبب الأول لانقطاع الشبكة الداخلية فجأة)

يمنح Docker جسر `docker0` النطاق **`172.17.0.0/16`** افتراضيًا، ثم يحتل مع كل شبكة مخصصة جديدة `172.18.0.0/16` و`172.19.0.0/16`…

**والمشكلة**: إن كانت **شبكة شركتك الداخلية أو VPN أو الشبكة الداخلية للمزوّد السحابي** تستخدم `172.17.x.x` كذلك، فسيوجد على المضيف مسارَان يشيران إلى النطاق نفسه، ويظهر ذلك كالتالي:

- انتهاء مهلة وصول الحاويات إلى الخدمات الداخلية؛
- تقطّع الاتصال ببعض العناوين الداخلية من المضيف؛
- انقطاع SSH إلى أجهزة أخرى فجأة.

**التشخيص**:

```bash
ip route | grep 172
docker network inspect bridge --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

**الإصلاح** (تغيير مجمّع العناوين الافتراضي في Docker، **ويحتاج إعادة تشغيل Docker، فينقطع كل الحاويات لحظات**):

```json
// /etc/docker/daemon.json
{
  "default-address-pools": [
    { "base": "10.201.0.0/16", "size": 24 }
  ]
}
```

```bash
sudo systemctl restart docker
# الشبكات المخصصة الموجودة لا تتغيّر تلقائيًا، فاحذفها وأعد إنشاءها
docker network ls
docker network rm <اسم-الشبكة>
```

ومبدأ اختيار مجمّع العناوين: **تجنّب كل نطاقاتك الداخلية** (والشائع تجنّب ما تستخدمه فعلًا من `10.0.0.0/8` و`172.16.0.0/12` و`192.168.0.0/16`). وإن كانت شبكتك الداخلية تحتل `10.x`، فاستخدم نطاق NAT بمستوى المشغّل مثل `100.64.0.0/16`.

### 5.6 كيف تصل الحاويات بعضها إلى بعض

**داخل الشبكة المخصصة نفسها، استخدم «اسم الخدمة» كاسم مضيف، لا `localhost`.**

```yaml
services:
  mc:
    networks: [mcnet]
  backup:
    networks: [mcnet]
    environment:
      TARGET: "mc:25565"     # صحيح: اسم الخدمة
      # TARGET: "127.0.0.1:25565"  # خطأ: هذا هو حاوية backup نفسها
networks:
  mcnet:
    driver: bridge
```

ونقاط إضافية:

- **شبكة `bridge` الافتراضية لا تدعم تحليل أسماء الخدمات**، فلا بد من إنشاء شبكة بنفسك (`docker network create` أو `networks` في Compose). وCompose ينشئ شبكة للمشروع افتراضيًا، فلا مشكلة عادةً مع Compose.
- **IP الحاوية يتغيّر بعد إعادة الإنشاء**، فلا تكتب IP الحاوية في أي إعداد، واكتب اسم الخدمة دائمًا.
- لإتاحة وصول الحاوية إلى خدمة على **المضيف** (مثل MySQL على المضيف)، استخدم `host.docker.internal` (وفي Linux أضف `host-gateway` في `extra_hosts`)، أو `--network host`.

### 5.7 مرجع سريع للمزالق الشبكية الشائعة

| العَرَض | السبب | المعالجة |
| --- | --- | --- |
| فتح `ufw` أو رفضه لا يغيّر سلوك منفذ الحاوية | Docker يتجاوز جدار حماية النظام | استخدم `-p 127.0.0.1:` أو سلسلة `DOCKER-USER` |
| منفذ لم تقصد فتحه ويمكن الوصول إليه من الإنترنت | `-p` يربط `0.0.0.0` افتراضيًا؛ وجدار النظام لا يضبط الحاويات | غيّره إلى `-p 127.0.0.1:منفذ-المضيف:منفذ-الحاوية`، انظر §5.3 |
| انتهاء مهلة وصول الحاويات إلى الخدمات الداخلية | تعارض نطاق `docker0` مع الشبكة الداخلية | غيّر `default-address-pools` وأعد إنشاء الشبكات |
| خادم Bedrock لا يظهر في القائمة المحلية | نمط `bridge` لا يحوّل البث | استخدم `macvlan` أو `host` |
| عنوان الاتصال يبطل بعد إعادة إنشاء الحاوية | تغيّر IP الحاوية | استخدم اسم الخدمة، ولا تكتب IP |
| تعذّر الاتصال بخدمة المضيف من الحاوية | `localhost` يعني الحاوية نفسها | استخدم `host.docker.internal` أو شبكة `host` |
| `ports` لا يعمل في نمط `host` | نمط `host` لا يستخدم تعيين المنافذ | عدّل منفذ استماع الخادم مباشرةً |
| تقطّع/انتهاء مهلة عابر في نقل الحزم الكبيرة | عدم تطابق MTU (عند بعض المزوّدين) | اضبط `"mtu": 1400` في `daemon.json` أو القيمة الموصى بها من المزوّد |
| ضياع قواعد `DOCKER-USER` بعد إعادة التشغيل | قواعد iptables غير مثبَّتة | استخدم `iptables-persistent` أو سكربت إقلاع |

### 5.8 قائمة تعرّض آمنة للخارج

افحص بهذا الترتيب، فأي بند غير محقق قد يعني «تظن أنه مغلق وكل شيء مفتوح»:

1. **مجموعة أمان المزوّد السحابي**: افتح المنافذ والمصادر المطلوبة فقط (وإن أمكن مصدر ثابت فلا تستخدم `0.0.0.0/0`).
2. **ربط المنفذ**: `-p 127.0.0.1:...` لا `-p ...`.
3. **الوكيل العكسي**: Nginx `stream` أو frp وغيرهما يتولّى الخارج، ولا يخرج منفذ الحاوية من الجهاز.
4. **جدار حماية النظام**: ما زال فعّالًا للخدمات **غير الحاوية**، فاضبطه كالمعتاد.
5. **الاختبار الفعلي**: نفّذ من **جهاز آخر** `telnet IP-العام المنفذ`، أو استخدم أداة فحص منافذ على الإنترنت للتأكد من أن المنافذ **غير المفتوحة** غير قابلة للوصول فعلًا.
6. **لا تعيّن RCON إلى الإنترنت أبدًا** (انظر الشرح أسفل جدول متغيرات البيئة في §6).

## 6. التشغيل وقراءة السجل ودخول الكونسول والإيقاف

```bash
docker compose up -d
```

يحتاج التشغيل الأول إلى تنزيل نواة الخادم وتوليد العالم، **فمرور دقائق إلى ربع ساعة أمر طبيعي**، ولا تظنه معلّقًا:

```bash
docker compose logs -f
```

وظهور شيء مثل `Done (xx.xxxs)! For help, type "help"` يعني نجاح الإقلاع. و`Ctrl+C` يخرج من متابعة السجل فقط، **ولا يوقف الخادم**.

وللدخول إلى الكونسول وتنفيذ الأوامر (الصورة تضم `rcon-cli` وتسجّل الدخول تلقائيًا بـ `RCON_PASSWORD`):

```bash
docker compose exec -it mcsog-java rcon-cli
docker compose exec -it mcsog-java rcon-cli list
docker compose exec -it mcsog-java rcon-cli save-all
```

وعند الحاجة إلى كونسول تفاعلي حقيقي (إدخال متواصل وصدى لحظي) استخدم `attach`:

```bash
docker attach mcsog-java
```

:::warn مزلقتان في لوحة المفاتيح مع attach
`Ctrl+C` داخل `docker attach` يرسل إشارة المقاطعة إلى عملية الخادم، **أي أنه يغلق الخادم مباشرةً** (وقد يتلف الحفظ). والطريقة الصحيحة للخروج `Ctrl+P` ثم `Ctrl+Q` (فصل، والحاوية تواصل العمل). ولتنفيذ أمر واحد في العمل اليومي، قدّم `rcon-cli`.
:::

والإيقاف والحذف:

```bash
docker compose stop
docker compose down
```

| الأمر | ماذا يفعل | البيانات في الحجم |
| --- | --- | --- |
| `docker compose stop` | يوقف الحاوية، والحاوية باقية | محفوظة |
| `docker compose start` | يشغّل حاوية موقوفة | محفوظة |
| `docker compose down` | يوقف **ويحذف الحاوية والشبكة** | محفوظة |
| `docker compose down -v` | كل ما سبق **مع حذف الحجم** | **تُفقد كلها** |

:::danger لا تُضف `-v` بلا تفكير
`docker compose down -v` يحذف حجم `/data`، أي الحفظ والملحقات والإعدادات معًا. ولا تستخدمه إلا بعد التأكد من رغبتك في «البدء من الصفر تمامًا» مع وجود نسخة احتياطية صالحة.
:::

## 7. متغيرات البيئة المستخدمة في أمثلة المقالة

يسرد الجدول التالي المتغيرات المستخدمة في ملف compose أعلاه، مع بعض الإضافات الأكثر استخدامًا. **والقيم الافتراضية تتغيّر مع إصدار الصورة، فالمرجع حتمًا توثيق الصورة الرسمي.**

| المتغير | الوظيفة | قيمة مثال |
| --- | --- | --- |
| `EULA` | إقرار الموافقة على Minecraft EULA، وتركه يفشل الإقلاع | `"TRUE"` |
| `TYPE` | نوع نواة الخادم | `"PAPER"` و`"VANILLA"` و`"FABRIC"` و`"NEOFORGE"` |
| `VERSION` | إصدار Minecraft، ويجب أن يكون مدعومًا من تلك النواة | `"1.21.11"` و`"LATEST"` |
| `MEMORY` | كومة JVM المخصصة للخادم | `"4G"` |
| `ONLINE_MODE` | هل يتحقق من الحسابات الأصلية (يقابل `online-mode`) | `"TRUE"` / `"FALSE"` |
| `ENABLE_RCON` | هل يُفعّل كونسول RCON البعيد | `"true"` |
| `RCON_PASSWORD` | كلمة مرور RCON، **ويجب تغييرها إلى كلمة قوية** | سلسلة عشوائية طويلة |
| `RCON_PORT` | منفذ استماع RCON (الافتراضي 25575، **لا تعيّنه إلى الإنترنت**) | `"25575"` |
| `TZ` | المنطقة الزمنية للحاوية، وتؤثر في توقيت السجل | `"Asia/Shanghai"` |
| `DIFFICULTY` | صعوبة اللعب | `"normal"` |
| `MOTD` | الوصف الظاهر في قائمة الخوادم | `"MCSOG Java"` |
| `MAX_PLAYERS` | أقصى عدد لاعبين | `"20"` |
| `OPS` | أسماء اللاعبين الممنوحين صلاحية الإدارة مباشرةً، مفصولة بفواصل | `"Alice,Bob"` |
| `WHITELIST` | أسماء اللاعبين في القائمة البيضاء، مفصولة بفواصل | `"Alice,Bob"` |
| `ENFORCE_WHITELIST` | هل تُفرض القائمة البيضاء | `"TRUE"` |
| `PUID` / `PGID` | التشغيل بهوية مستخدم/مجموعة محددة (لمشكلة مالك التركيب الربطي، **والاستخدام مرجعه توثيق الصورة**) | `"1000"` |

:::note RCON هو «صلاحية إدارة بلا واجهة»
`ENABLE_RCON: "true"` يستمع على `25575` داخل الحاوية فقط. **ولا تعيّن `25575` إلى الإنترنت**: فبروتوكول RCON غير مشفّر، وكلمة مرور واحدة تعني الكونسول. وإن احتجت إدارة بعيدة فاستخدم نفق SSH أو لوحة، انظر [أساسيات أمان الشبكة](/tutorials/ops/network-security).
:::

## 8. ماذا يوجد في `/data`

الحاوية «لمرة واحدة»، والحجم ليس كذلك. وكل ما يلي داخل `/data`:

| المسار | المحتوى |
| --- | --- |
| `/data/world/` | حفظ العالم الرئيسي (وللنيثر والإنك دليل مستقل لكل منهما) |
| `/data/plugins/` | ملفات jar الملحقات وإعداداتها |
| `/data/mods/` | المودات (تُستخدم عندما تكون `TYPE` نواة مودات) |
| `/data/server.properties` | إعداد الخادم (المنفذ والصعوبة و`online-mode` وغيرها) |
| `/data/eula.txt` | إقرار EULA، يكتبه متغير `EULA` |
| `/data/logs/` | سجل الخادم |

فإذن: **الحاوية تُحذف كما تشاء، والحجم لا يُحذف.** وللتأكد من موضع الحجم:

```bash
docker volume ls
docker volume inspect mcsog-java-data
```

## 9. النسخ الاحتياطي والاستعادة

موضوع النسخ الاحتياطي هو `/data`، لا الحاوية. وأضمن طريقة **إيقاف الخادم ثم الحزم**:

```bash
mkdir -p backups
docker compose stop
docker run --rm \
  -v mcsog-java-data:/data:ro \
  -v "$PWD/backups":/backup \
  alpine \
  tar czf /backup/mcsog-java-$(date +%Y%m%d-%H%M).tar.gz -C /data .
docker compose start
```

وفي Windows PowerShell استبدل مسار التركيب بـ `-v "${PWD}\backups:/backup"` (Docker Desktop).

وإن كان لا بد من البقاء متصلًا وعدم إيقاف الخادم، فاستخدم أوامر الكونسول لضمان الاتساق:

```bash
docker compose exec -it mcsog-java rcon-cli save-all
docker compose exec -it mcsog-java rcon-cli save-off
```

`save-all` يكتب بيانات الذاكرة إلى القرص، و`save-off` يوقف الحفظ التلقائي، فلا تحدث كتابات جديدة أثناء الحزم. وبعد الحزم أعد التفعيل:

```bash
docker compose exec -it mcsog-java rcon-cli save-on
```

وعند الاستعادة **أوقف الحاوية أولًا**، ثم أفرغ الحجم وفكّ الحزمة (وهذه الخطوة تغطّي المحتوى الحالي للحجم):

```bash
docker compose stop
docker run --rm \
  -v mcsog-java-data:/data \
  -v "$PWD/backups":/backup \
  alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/mcsog-java-20261004-1200.tar.gz -C /data"
docker compose start
```

:::warn الحاوية ليست نسخة احتياطية
تشغيل الخادم في حاوية **لا يعني** أن البيانات آمنة. فالحجم والحاوية على القرص نفسه، وحذف الحجم خطأً أو تلف القرص أو تشفير برامج الفدية يأخذها كلها. فاحتفظ بنسخة **خارج الجهاز أو بعيدة** على الأقل، والطريقة في [النسخ الاحتياطي والاستعادة](/tutorials/java/backup) و[النسخ خارج الموقع](/tutorials/ops/offsite-backup). **والنسخة التي لم تُختبر استعادتها ليست نسخة.**
:::

## 10. تحديث الصورة وتبديل النواة والإصدار

لترقية الصورة (إصلاح خطأ أو ملاحقة إصدار جديد):

```bash
docker compose pull
docker compose up -d
```

والترتيب مهم: **انسخ احتياطيًا، ثم pull، ثم up**. فـ `docker compose up -d` يعيد إنشاء الحاوية عند اكتشاف تغيّر الصورة أو الإعداد، لكن الحجم يُركَّب كما هو، فلا يضيع الحفظ — بشرط ألا تكون حذفت الحجم.

ولتغيير نوع النواة أو إصدارها، عدّل متغيرات البيئة فقط ثم أعد `up -d`:

```yaml
    environment:
      TYPE: "FABRIC"
      VERSION: "1.21.11"
```

| التغيير | ماذا يحدث | ملاحظات |
| --- | --- | --- |
| تعديل `VERSION` فقط | تنزيل نواة الإصدار الجديد | **ترقية صيغة الحفظ أحادية الاتجاه**، والحفظ الجديد لا يُفتح عادةً بالإصدار القديم؛ ولا بد من نسخة احتياطية قبل الترقية |
| تعديل `TYPE` (بين نوى الملحقات) | تبديل jar النواة، ويبقى `plugins/` صالحًا | يجب توافق الملحقات مع النواة/الإصدار |
| تعديل `TYPE` (من نواة ملحقات إلى نواة مودات) | يبدأ الخادم بقراءة `mods/` | و`plugins/` الحالي لا يعمل، وقد يحتاج العالم معالجة توافق إضافية |
| تعديل `MEMORY` | إعادة إنشاء الحاوية وتخصيص الكومة من جديد | لا تتجاوز نسبة معقولة من ذاكرة المضيف المتاحة |

## 11. إضافة الملحقات والمودات

ثلاث طرق، اختر واحدة بحسب عادتك.

**الطريقة A: التركيب الربطي (الأسهل لتعديل الملفات)**

غيّر `volumes` إلى دليل على المضيف:

```yaml
    volumes:
      - ./data:/data
```

وبعدها تعمل على `./data/plugins/` و`./data/server.properties` من المضيف مباشرةً. وعلى Linux انتبه إلى مسألة المالك (انظر القسم 11).

**الطريقة B: نسخ الملفات إلى الحجم (مع إبقاء الحجم المسمّى)**

```bash
docker cp ./MyPlugin.jar mcsog-java:/data/plugins/
docker compose restart
```

**الطريقة C: ترك التنزيل التلقائي للصورة**

توفّر الصورة متغيرات لسحب الملحقات/المودات تلقائيًا بحسب المصدر (مثل تثبيت ملحق برقم مورد Spiget، أو مود بمشروع Modrinth). وأسماء هذه المتغيرات وقيمها **مرجعها توثيق الصورة الرسمي**، فتحقق قبل الاستخدام.

وبعد تعديل الإعداد تدعم معظم الملحقات إعادة التحميل داخل اللعبة، لكن **إعادة التشغيل أضمن**:

```bash
docker compose restart
```

## 12. المزالق الشائعة

| العَرَض | السبب | المعالجة |
| --- | --- | --- |
| يخرج فور البدء، والسجل يذكر EULA | لم يُضبط `EULA: "TRUE"` | أضف المتغير ثم `docker compose up -d` |
| يقتل النظام الحاوية، ويظهر OOM في السجل | `MEMORY` أكبر مما يستطيع المضيف منحه | قلّل `MEMORY`، أو أضف ذاكرة؛ واترك هامشًا على المضيف كذلك |
| الإنترنت لا يتصل وكل شيء داخل الحاوية سليم | المنفذ غير معيّن، أو مجموعة الأمان لا تفتحه | اكتب `25565/tcp` في `ports`؛ وافتحه في **مجموعة أمان السحابة**. لاحظ: **جدار حماية النظام (ufw/firewalld) لا يعمل على منافذ الحاويات**، انظر §5.1 |
| تعذّر الكتابة في `/data` من الحاوية، والسجل يذكر خطأ صلاحيات | مالك التركيب الربطي على Linux لا يطابق مستخدم الحاوية | صحّح مالك دليل المضيف، أو استخدم متغيرات تعيين المستخدم التي توفّرها الصورة (`PUID`/`PGID`، **المرجع توثيق الصورة**) |
| «اختفى» الحفظ بعد إعادة إنشاء الحاوية | حُذف الحجم (مثل `down -v`)، أو نُسي تركيب `/data` | توقف فورًا واستعد من النسخة الاحتياطية؛ وثبّت اسم الحجم لاحقًا وأدرجه في النسخ الاحتياطي |
| الكونسول لا يقبل الكتابة | نقص `stdin_open: true` و`tty: true` | أضفهما وأعد إنشاء الحاوية |
| `docker compose` يقول إنه ليس أمرًا | مثبَّت `docker-compose` القديم (v1) | ثبّت إضافة Compose v2 وفق التوثيق الرسمي، والأمر `docker compose` |
| التعديل لم يسري | عُدّل الملف فقط ولم تُعد إنشاء الحاوية | `docker compose up -d` لتفعيل الإعداد |

ويُستحسن أن تجري الفحص اليومي (حالة الحاويات واستهلاك الموارد والمساحة المتبقية) مع [المراقبة والتنبيهات](/tutorials/ops/monitoring).
