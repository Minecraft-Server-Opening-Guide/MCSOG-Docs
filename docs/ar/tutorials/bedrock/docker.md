خادم Bedrock الرسمي هو **BDS**، وهو بلا منظومة ملحقات وببنية أدلة بسيطة، فيناسب وضعه في حاوية تمامًا: الصورة تتولّى تنزيل BDS الرسمي وقبول EULA وتعيين المنافذ، وأنت لا تصون إلا حجمًا واحدًا وملف `docker-compose.yml`.

وتتناول هذه المقالة **تشغيل BDS داخل حاوية**. أما بنية أدلة BDS نفسه وخصائص ذاكرته ومزالكه المعروفة ففي [خادم BDS](/tutorials/bedrock/bds).

:::warn تذكّر أولًا: نسخة Bedrock تستخدم UDP
نسخة Java تستخدم **TCP 25565**، ونسخة Bedrock تستخدم **UDP 19132** (وIPv6 هو `19133/udp`). **وفتح TCP فقط أو تعيينه فقط يعني «الخادم يعمل ولا يدخل أحد»، وبلا أي رسالة خطأ.** وهذا أكثر مزالق فتح خادم Bedrock شيوعًا، وستكرّره هذه المقالة.
:::

## 1. لماذا الحاويات

| الفائدة | التجلّي المحدد |
| --- | --- |
| **بيئة نظيفة** | BDS الرسمي برنامج ثنائي، والحاوية تحزمه مع مكتباته، فلا يحتاج المضيف تثبيت أي اعتماديات |
| **قابلية الإعادة** | الإصدار والمنافذ ونمط اللعب والصعوبة واسم العالم كلها في ملف واحد، فانتقل بين الأجهزة بنقله |
| **سهولة الرجوع** | انسخ `/data` قبل الترقية، وإن ظهرت مشكلة أعد `VERSION` وأعد التشغيل |
| **حذف نظيف** | إن لم تعد تريده احذف الحاوية والحجم، ولا تبقى ملفات على المضيف |
| **اتساق عابر للمنصات** | BDS الرسمي يوفّر نسختَي Windows وLinux فقط؛ وباستخدام حاوية بنسخة Linux على Windows تصبح طريقة العمل مطابقة تمامًا لما على الخادم |

والكلفة موجودة كذلك:

| الكلفة | الوصف |
| --- | --- |
| **طبقة إضافية للتعلّم** | مفاهيم الصورة والحاوية والحجم وCompose لا مفرّ منها، والتشخيص يبدأ من `docker compose logs` |
| **انضباط الأحجام والنسخ الاحتياطي** | حفظ العالم في الحجم، وعدم النسخ الاحتياطي يعني عدم وجود نسخة |
| **كلفة أداء صغيرة لكنها ليست صفرًا** | طبقة NAT في الشبكة وطبقة overlay في نظام الملفات؛ والعنق الحقيقي عادةً **محاكاة BDS أحادية الخيط للعالم**، فحدّ المعالج يجب أن يكون كافيًا |
| **لا منظومة ملحقات** | BDS لا يدعم الملحقات، والحاوية لا تغيّر ذلك؛ والمحتوى الإضافي لا يبقى إلا في صورة حزم سلوك/موارد داخل دليل البيانات |

## 2. تثبيت Docker وإضافة Compose

ثبّت وفق التوثيق الرسمي، ولا تستخدم سكربتات تثبيت مجهولة المصدر:

| المنصة | المدخل الرسمي |
| --- | --- |
| Linux (بحسب التوزيعة) | [Install Docker Engine](https://docs.docker.com/engine/install/) |
| إضافة Compose على Linux | [Install the Compose plugin](https://docs.docker.com/compose/install/linux/) |
| Windows / macOS | [Docker Desktop](https://docs.docker.com/desktop/) |

```bash
docker --version
docker compose version
docker run --rm hello-world
```

:::note طريقان على Windows
يمكنك على Windows تنزيل الحزمة المضغوطة الرسمية وتشغيل الـ exe داخلها (صفحة التنزيل [صفحة تنزيل BDS الرسمية من Minecraft](https://www.minecraft.net/en-us/download/server/bedrock))، أو استخدام حل الحاوية في هذه المقالة. وميزة حل الحاوية **مطابقة العمل لما على خادم Linux**، فلا إعادة تعلّم عند الترحيل.
:::

## 3. الصورة: `itzg/minecraft-bedrock-server`

صورة Bedrock الشائعة في المجتمع هي **`itzg/minecraft-bedrock-server`** (صيانتها نشطة، ومن منظومة المؤلف نفسه لصورة نسخة Java).

```bash
docker pull itzg/minecraft-bedrock-server
```

:::note علاقتها بحزمة التنزيل الرسمية
توفّر [صفحة تنزيل BDS](https://www.minecraft.net/en-us/download/server/bedrock) الرسمية حزمة مضغوطة تحتاج أن تفكّها وتعدّل الإعداد وتشغّلها بنفسك. **وما تفعله الصورة المجتمعية: تنزيل BDS الرسمي بدلًا عنك عند إقلاع الحاوية، وكتابة متغيرات البيئة في `server.properties` وغيره من الإعدادات.**

فإذن: **آلية تنزيل الصورة لـ BDS (عنوان التنزيل، وتحليل الإصدار، وطريقة التخزين المؤقت) مرجعها توثيق الصورة الرسمي**، وقد تختلف بين إصدارات الصورة. وإن أردت التحكم الكامل فاستخدم الحزمة الرسمية ونشرًا يدويًا وفق [خادم BDS](/tutorials/bedrock/bds).
:::

## 4. ملف `docker-compose.yml` كامل

```yaml
services:
  bedrock:
    image: itzg/minecraft-bedrock-server
    container_name: mcsog-bedrock
    ports:
      - "19132:19132/udp"
      - "19133:19133/udp"
    environment:
      EULA: "TRUE"
      SERVER_NAME: "MCSOG Bedrock"
      GAMEMODE: "survival"
      DIFFICULTY: "normal"
      LEVEL_NAME: "MCSOG"
      ONLINE_MODE: "TRUE"
      TZ: "Asia/Shanghai"
    volumes:
      - mcsog-bedrock-data:/data
    stdin_open: true
    tty: true
    restart: unless-stopped

volumes:
  mcsog-bedrock-data:
    name: mcsog-bedrock-data
```

ولا يحتاج Compose v2 إلى حقل `version:` في الأعلى.

| الحقل | الوظيفة |
| --- | --- |
| `image` | الصورة المستخدمة؛ ويُستحسن تثبيت الوسم في الإنتاج، ولا تستخدم `latest` دائمًا |
| `container_name` | اسم حاوية ثابت، لتسهيل `logs` / `attach` |
| `ports` | **يجب كتابة `/udp`**. فـ `19132` منفذ IPv4 الرئيسي، و`19133` منفذ IPv6 (ويمكن عدم تعيينه إن لم يكن هناك عملاء IPv6، لكن تعيينه لا يضر) |

:::warn Docker يتجاوز جدار حماية النظام (وينطبق على Bedrock كذلك)
قواعد `ufw` و`firewalld` **لا تعمل على المنافذ التي تعرضها حاويات Docker**: فDocker يُدرج قواعده في `iptables` قبل جدار حماية النظام، فلا يمنع `ufw deny 19132/udp` الوصول الخارجي كذلك.

ونسخة Bedrock تستخدم **UDP**، وهو أسهل إغفالًا، فاضبط الأمور بالطرق التالية:

1. **اربط المنفذ بواجهة الاسترجاع** (موصى به): `-p 127.0.0.1:19132:19132/udp`، ثم يحوّله وكيل عكسي على المضيف للخارج؛
2. **استخدم سلسلة `DOCKER-USER`** لتقييد المصادر؛
3. **مجموعة أمان** المزوّد السحابي كشبكة أمان (وهذه الطبقة لا تتأثر بـ Docker).

وإضافةً، إن أردت أن يظهر الخادم في **قائمة الشبكة المحلية** (فـ Bedrock يعتمد على بث UDP للاكتشاف)، فنمط `bridge` لا يستطيع ذلك، ويلزم نمط `macvlan` أو `host`.

والشرح الكامل (بما فيه تعارض النطاقات ومقارنة أنماط الشبكة وجدول التشخيص) في [نشر نسخة Java بـ Docker ← الشبكة وجدار الحماية](/tutorials/java/docker#5-网络与防火墙最容易踩坑的一节).
:::
| `environment` | الإعدادات التي تقرأها الصورة، انظر القسم 6 |
| `volumes` | `اسم-الحجم:/data`. **العالم والإعداد والحزم الإضافية كلها في `/data`** |
| `stdin_open: true` | فتح الإدخال القياسي، وإلا تعذّر **إدخال الأوامر** في كونسول BDS |
| `tty: true` | تخصيص طرفية زائفة، مع `docker attach` لكونسول تفاعلي |
| `restart: unless-stopped` | إعادة الرفع بعد الانهيار أو إعادة تشغيل المضيف؛ ولا يُرفع تلقائيًا بعد `docker compose stop` اليدوي |

والسبب في كتابة `name:` صراحةً في `volumes` جعل اسم الحجم **قابلًا للتوقّع** (وإلا أضاف Compose بادئة اسم المشروع)، فلا تخطئ أوامر النسخ الاحتياطي في اسم الحجم.

:::note `EULA=TRUE` شرط قانوني
`EULA: "TRUE"` يعني **أنك قرأت [اتفاقية ترخيص المستخدم النهائي لـ Minecraft](https://aka.ms/MinecraftEULA) ووافقت عليها**. وبلا هذا المتغير يخرج BDS فور بدئه، فتدخل الحاوية في حلقة إعادة تشغيل.
:::

:::tip أجرِ «فحصًا» قبل التشغيل
بعد كل تعديل لملف compose شغّل `docker compose config`: فيُطبع المنافذ والأحجام ومتغيرات البيئة بعد فكّها، ويخطئ في موضعه عند أي خطأ كتابي. **وخصوصًا `/udp`، فغيابه يظهر هنا.**
:::

```bash
docker compose config
```

## 5. التشغيل وقراءة السجل ودخول الكونسول والإيقاف

```bash
docker compose up -d
```

ويحتاج التشغيل الأول إلى تنزيل BDS، فاصبر:

```bash
docker compose logs -f
```

وظهور سجل مثل `[INFO] Server started.` يعني نجاح الإقلاع. و`Ctrl+C` يخرج من متابعة السجل فقط، ولا يوقف الخادم.

ونسخة Bedrock **لا تملك RCON**، فلا يتوفر `rcon-cli`، ودخول الكونسول لا يبقى إلا بـ `attach`:

```bash
docker attach mcsog-bedrock
```

وبعد attach تستطيع إدخال أوامر BDS كما في نافذة محلية، مثل:

```text
list
say hello
save hold
save resume
stop
```

:::warn مزلقة لوحة المفاتيح في attach
`Ctrl+C` داخل `docker attach` يرسل إشارة المقاطعة إلى BDS، **أي أنه يغلق الخادم مباشرةً** (وقد يتلف الحفظ). والخروج الصحيح `Ctrl+P` ثم `Ctrl+Q` (فصل، والحاوية تواصل العمل). وعند الحاجة إلى إغلاق حقيقي أدخل أمر `stop` وانتظر خروج العملية.
:::

والإيقاف والحذف:

```bash
docker compose stop
docker compose down
```

| الأمر | ماذا يفعل | البيانات في الحجم |
| --- | --- | --- |
| `docker compose stop` | يوقف الحاوية، والحاوية باقية | محفوظة |
| `docker compose start` | يشغّل حاوية موقوفة | محفوظة |
| `docker compose down` | يوقف ويحذف الحاوية والشبكة | محفوظة |
| `docker compose down -v` | كل ما سبق **مع حذف الحجم** | **تُفقد كلها** |

:::danger لا تُضف `-v` بلا تفكير
`docker compose down -v` يحذف حجم `/data`، أي حفظ العالم معه. ولا تستخدمه إلا بعد التأكد من رغبتك في البدء من الصفر تمامًا مع وجود نسخة احتياطية صالحة.
:::

## 6. متغيرات البيئة المستخدمة في أمثلة المقالة

| المتغير | الوظيفة | قيمة مثال |
| --- | --- | --- |
| `EULA` | إقرار الموافقة على Minecraft EULA، وتركه يفشل الإقلاع | `"TRUE"` |
| `SERVER_NAME` | اسم الخادم (يقابل `server-name`) | `"MCSOG Bedrock"` |
| `GAMEMODE` | نمط اللعب الافتراضي | `"survival"` / `"creative"` |
| `DIFFICULTY` | صعوبة اللعب | `"normal"` / `"peaceful"` |
| `LEVEL_NAME` | اسم العالم (المرحلة)، و**يحدّد كذلك اسم المجلد داخل `worlds/`** | `"MCSOG"` |
| `ONLINE_MODE` | هل يتحقق من حسابات Xbox Live | `"TRUE"` / `"FALSE"` |
| `TZ` | المنطقة الزمنية للحاوية، وتؤثر في توقيت السجل | `"Asia/Shanghai"` |
| `VERSION` | تحديد إصدار BDS؛ وتركه يتبع الأحدث عادةً | `"LATEST"` |
| `SERVER_PORT` | منفذ الاستماع IPv4 (الافتراضي 19132) | `"19132"` |
| `SERVER_PORT_V6` | منفذ الاستماع IPv6 (الافتراضي 19133) | `"19133"` |
| `MAX_PLAYERS` | أقصى عدد لاعبين | `"20"` |
| `VIEW_DISTANCE` | مدى الرؤية | `"12"` |
| `LEVEL_SEED` | بذرة العالم | رقم أو نص |
| `ALLOW_LIST` | هل تُفعّل القائمة البيضاء | `"true"` / `"false"` |

:::note القيم الافتراضية تتغيّر
القيم الافتراضية بين الأقواس في الجدول تقابل الإعداد الافتراضي الشائع في BDS، و**قد تُعدَّل بعد تحديث الصورة، فالمرجع توثيق الصورة الرسمي**. ومبدأ الإنتاج: **اكتب البنود الحرجة صراحةً دائمًا**، ولا تعتمد على الافتراضي.
:::

:::warn اسم خادم غير ASCII
يدعم `SERVER_NAME` العربية، لكن بعض العملاء القديمة تعرضها مشوّشة. وعند بلاغ اللاعبين عن تشويه، ابدأ بتبديل الاسم إلى ASCII للاختبار. ويُستحسن أن يكون `LEVEL_NAME` ASCII كذلك: فهو يصير اسم دليل، والمحارف الخاصة تجلب متاعب لا لزوم لها.
:::

## 7. ماذا يوجد في `/data`

| المسار | المحتوى |
| --- | --- |
| `/data/worlds/<LEVEL_NAME>/` | **حفظ العالم** (`db/` و`level.dat` و`level_name.txt` وغيرها) |
| `/data/server.properties` | إعداد الخادم (المنفذ والصعوبة والنمط ومفتاح القائمة البيضاء وغيرها) |
| `/data/allowlist.json` | بيانات القائمة البيضاء |
| `/data/permissions.json` | بيانات المشرفين (OP) |
| `/data/valid_known_packs.json` | قائمة الحزم الإضافية المعروفة |
| `/data/behavior_packs/` و`/data/resource_packs/` | حزم السلوك وحزم الموارد (موضع المحتوى الإضافي) |

وحفظ BDS **كله تحت `worlds/`**، بمجلد فرعي لكل عالم. وما تكتبه في `LEVEL_NAME` يصير اسم الدليل:

```text
/data/worlds/MCSOG/db/
```

:::warn تغيير `LEVEL_NAME` يعني تبديل العالم
إذا تغيّر `LEVEL_NAME` بحث BDS عن دليل الاسم الجديد؛ فإن لم يجده **ولّد عالمًا فارغًا جديدًا**، فيبدو العالم القديم «مختفيًا» (وهو في الحجم فعلًا). فتحقق من اسم دليل الحفظ قبل تغيير الاسم.
:::

## 8. النسخ الاحتياطي والاستعادة

موضوع النسخ هو `/data`، وأهمّه `/data/worlds/`. وأضمن طريقة **إيقاف الخادم ثم الحزم**:

```bash
mkdir -p backups
docker compose stop
docker run --rm \
  -v mcsog-bedrock-data:/data:ro \
  -v "$PWD/backups":/backup \
  alpine \
  tar czf /backup/mcsog-bedrock-$(date +%Y%m%d-%H%M).tar.gz -C /data .
docker compose start
```

وفي Windows PowerShell استبدل مسار التركيب بـ `-v "${PWD}\backups:/backup"` (Docker Desktop).

وإن تعذّر إيقاف الخادم، فوفّر BDS أوامر اتساق حفظ خاصة به (تُدخل في كونسول `docker attach`):

```text
save hold
save query
```

`save hold` يجعل الخادم يوقف الكتابة ويحافظ على اتساق الملفات، و`save query` يسرد الملفات التي يجب نسخها حاليًا. وبعد اكتمال النسخ أعد التفعيل:

```text
save resume
```

:::note لماذا لا تُنسخ طريقة نسخة Java
نسخة Java تستخدم `save-all` / `save-off` / `save-on`، وBDS في نسخة Bedrock يستخدم **`save hold` / `save query` / `save resume`**، والطقمان لا يعملان معًا. أما النسخ مع إيقاف الخادم فينطبق على الاثنين، وهو الأقل عناءً.
:::

وعند الاستعادة أوقف الحاوية أولًا، ثم أفرغ الحجم وفكّ الحزمة:

```bash
docker compose stop
docker run --rm \
  -v mcsog-bedrock-data:/data \
  -v "$PWD/backups":/backup \
  alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/mcsog-bedrock-20261004-1200.tar.gz -C /data"
docker compose start
```

:::warn الحاوية ليست نسخة احتياطية
الحجم والحاوية على القرص نفسه، وحذف الحجم خطأً أو تلف القرص أو برامج الفدية يأخذها كلها. فاحتفظ بنسخة **خارج الجهاز أو بعيدة** على الأقل، انظر [النسخ الاحتياطي والاستعادة](/tutorials/java/backup) و[النسخ خارج الموقع](/tutorials/ops/offsite-backup). **والنسخة التي لم تُختبر استعادتها ليست نسخة.**
:::

## 9. تحديث الصورة وإصدار BDS

```bash
docker compose pull
docker compose up -d
```

والترتيب كما هو: **انسخ احتياطيًا، ثم pull، ثم up**.

| التغيير | ماذا يحدث | ملاحظات |
| --- | --- | --- |
| `docker compose pull` | جلب إصدار جديد من الصورة | بعد السحب يجب `up -d` لإعادة إنشاء الحاوية وسريان التغيير |
| تعديل `VERSION` | تنزيل BDS بالإصدار المقابل من جديد | يجب تطابق إصدار العميل وBDS؛ وانسخ الحفظ احتياطيًا قبل الترقية |
| عدم كتابة `VERSION` | يتبع أحدث BDS عادةً | مريح، لكنه **غير قابل للإعادة**؛ وعند المشكلة لا تعرف هل تغيّر الإصدار أم الإعداد |

:::note عدم تطابق الإصدار أكثر أسباب «تعذّر الاتصال» شيوعًا
عند عدم تطابق عميل Bedrock مع BDS، **يرى اللاعب الخادم عادةً لكنه لا يدخل**. وتثبيت `VERSION` يضمن الحصول على الإصدار نفسه في كل إعادة تشغيل؛ وإن أردت ملاحقة الأحدث فاقبل «تغيّر الإصدار بعد إعادة تشغيل ما»، وأبلغ اللاعبين مسبقًا.
:::

## 10. المحتوى الإضافي: BDS بلا منظومة ملحقات

لا يدعم BDS إلا **حزم السلوك وحزم الموارد** الرسمية، وليس له نظام ملحقات كـ Bukkit، والحاوية لا تغيّر ذلك. وعند الحاجة إلى قدرة ملحقات يجب تبديل الخادم إلى طرف ثالث، انظر [خادم BDS](/tutorials/bedrock/bds) و[حلول الخوادم من طرف ثالث](/tutorials/bedrock/third-party).

ووضع المحتوى الإضافي:

| المحتوى | موضع الوضع |
| --- | --- |
| حزم السلوك | `/data/behavior_packs/` |
| حزم الموارد | `/data/resource_packs/` |
| حزم خاصة بالعالم | الدليل المقابل تحت `/data/worlds/<LEVEL_NAME>/` |

**الطريقة A: التركيب الربطي (الأسهل لتعديل الملفات)**

```yaml
    volumes:
      - ./data:/data
```

وبعدها تعمل على `./data/behavior_packs/` من المضيف مباشرةً.

**الطريقة B: النسخ إلى الحجم**

```bash
docker cp ./MyAddon.mcpack mcsog-bedrock:/data/
docker compose restart
```

وبعد تعديل الإعداد أو تبديل حزمة، **إعادة تشغيل الحاوية أضمن**:

```bash
docker compose restart
```

## 11. الأداء والذاكرة: نقطتان خاصتان بنسخة Bedrock

### 11.1 محاكاة العالم أحادية الخيط، فلا تُخنق المعالج

حساب الكائنات ومحاكاة العالم في BDS أحاديان أساسًا، و**السلاسة تعتمد على أداء النواة الواحدة**، وكلما كبرت الخريطة زاد الجهد. وكلفة الحاوية نفسها صغيرة، لكن **ضبط حصة معالج منخفضة جدًا للحاوية يجوّع الخادم مباشرةً**: فيظهر هبوط TPS وتقطيع اللاعبين وبطء تحميل القطع.

```yaml
    cpus: "2.0"
```

:::warn لا تحدّ المعالج «لتوفير الموارد»
ما لم تكن تعرف بوضوح ما يعمل أيضًا على هذا الجهاز وقد أجريت اختبار ضغط، **فلا تضبط سقف معالج لحاوية BDS** (مثل `cpus: "0.5"`). فطبيعة BDS أحادية الخيط تجعله حسّاسًا جدًا لتردد النواة الواحدة ولوجود «نواة متاحة في أي لحظة». والضبط ذو الصلة في [تحسين الأداء](/tutorials/java/optimize).
:::

وأما الذاكرة:

```yaml
    mem_limit: "4g"
```

`mem_limit` سقف صارم، **وضبطه أدنى من الحاجة الفعلية يجعل Docker يقتل الحاوية بـ OOM** (والتجلّي إعادة تشغيل الخادم بلا سابق إنذار). وإن لم تكن متأكدًا فلا تضع سقفًا أولًا، وراقب الاستهلاك الفعلي بـ `docker stats` ثم قرّر.

:::warn لا تُجبر تنظيف الذاكرة
استهلاك BDS للذاكرة ينمو ببطء مع الوقت، **فلا تستخدم أداة لتنظيف الذاكرة قسرًا**: فذلك يوقف شريط تقدّم تنزيل اللاعبين لحزم المواد/الحزم الإضافية. **والمعالجة الصحيحة إعادة تشغيل الخادم**، وهذا مطابق لشرح [خادم BDS](/tutorials/bedrock/bds).
:::

## 12. تشخيص الأعطال

| العَرَض | السبب | المعالجة |
| --- | --- | --- |
| **إعادة تشغيل متكررة** للحاوية | EULA غير موافق عليها، أو `LEVEL_NAME` بمحارف غير صالحة، أو المنفذ مشغول، أو ذاكرة غير كافية، أو `VERSION` غير صالح | انظر أولًا `docker compose logs --tail=200`، فالشاشة الأولى من السجل تذكر السبب عادةً |
| الخادم يعمل و**لا يدخل أحد** | عُيّن/فُتح TCP فقط؛ أو مجموعة الأمان لم تفتح **UDP** | اكتب `"19132:19132/udp"` في `ports`، وافتح UDP 19132 في **مجموعة أمان السحابة**. وجدار حماية النظام لا يعمل على الحاويات، انظر التحذير أعلاه |
| الشبكة المحلية تتصل والإنترنت لا | مشكلة تعيين المنفذ/مجموعة الأمان | انظر [النشر في بيئة متاحة للجميع](/tutorials/java/deploy) و[الموجّه وجدار الحماية](/tutorials/ops/router-firewall) |
| العالم «اختفى» ووُلّدت خريطة جديدة | تغيّر `LEVEL_NAME`، أو رُكّب الحجم الخطأ | أعد `LEVEL_NAME` إلى الاسم السابق؛ وتأكد أن الحجم المركّب هو نفسه |
| اللاعب يرى الخادم ولا يدخل | عدم تطابق إصدار العميل مع BDS، أو اعتراض القائمة البيضاء/التحقق الأصلي | ثبّت `VERSION`، وافحص `ALLOW_LIST` و`ONLINE_MODE` |
| الحاوية لا تكتب في `/data` (تركيب ربطي على Linux) | مالك دليل المضيف لا يطابق مستخدم الحاوية | صحّح مالك الدليل؛ واستخدم طريقة تعيين المستخدم الواردة في توثيق الصورة عند الحاجة |
| إعادة تشغيل مفاجئة للخادم | سقف ذاكرة صارم منخفض جدًا فأطلق OOM | ارفع `mem_limit` أو أزله، وراقب بـ `docker stats` |
| الكونسول لا يقبل الكتابة | نقص `stdin_open: true` و`tty: true` | أضفهما وأعد إنشاء الحاوية |

ويُستحسن أن تجري الفحص اليومي (حالة الحاويات واستهلاك المعالج/الذاكرة والمساحة المتبقية) مع [المراقبة والتنبيهات](/tutorials/ops/monitoring).
