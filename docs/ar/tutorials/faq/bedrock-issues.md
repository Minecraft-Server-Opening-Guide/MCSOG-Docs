المشكلات التي تصادفها عند فتح خادم Bedrock — «لا يقوم / لا يتصل / يدخل لكن السلوك خاطئ» — تتشابه ظاهريًا كثيرًا: فاللاعب لا يقول إلا «لا أستطيع الدخول»، والخادم قد لا تكون عمليته قامت أصلًا. وهذه نسخة موسّعة من [[BE] الأسئلة الشائعة](/tutorials/faq/faq-be)، تسير بترتيب «صنّف أولًا، ثم حدّد»، وتحاول كتابة معيار كل خطوة بوضوح.
:::tip كيف تستخدم هذه المقالة
انظر أولًا جدول التصنيف في القسم 1، وحدّد أي فئة تصادفها، ثم انتقل إلى القسم المقابل مباشرةً. والقسم 5 يعطي ترتيب تشخيص كاملًا من الصفر؛ والقسم 6 يوضّح أي المعلومات تقدّمها عند طلب المساعدة.
:::

## 1. صنّف أولًا: لا يتصل / لا يقوم / يدخل لكن بشذوذ

ومعيار التصنيف: **هل عملية الخادم تعمل فعلًا، وهل تستمع على منفذ؟**

| الظاهرة | إلى أي فئة تنتمي | أي قسم تنظر |
| --- | --- | --- |
| نافذة المشغّل تظهر وتختفي، أو يعود سطر الأوامر إلى المطالبة فورًا | لا يقوم | القسم 2 |
| وحدة التحكّم تُظهر أخطاءً، والعملية لم تقم أصلًا | لا يقوم | القسم 2 |
| العملية تعمل ووحدة التحكّم طبيعية، لكن اللاعبين لا يتصلون | لا يتصل | القسم 3 |
| اللاعب يدخل، لكن هناك تقطيع أو شذوذ في الأرشيف أو خطأ في الصلاحيات | يدخل لكن بشذوذ | القسم 4 |
| بعض اللاعبين يدخلون وآخرون لا | لا يتصل | القسم 3 (افحص أولًا نسخة البروتوكول ومنصّة العميل) |
| أداة فحص المنافذ تقول «ناجح» واللاعبون ما زالوا لا يدخلون | لا يتصل | القسم 3.2 (غالبًا الأداة فحصت TCP فقط) |
| كان يعمل أمس، واليوم لا يدخل أحد | لا يتصل | القسم 3.1 (تحديث العميل التلقائي غيّر البروتوكول) |
| الخادم يقوم، لكنه يخرج بنفسه بعد دقائق من اللعب | يدخل لكن بشذوذ | القسمان 4.1 و4.2 |
:::note تأكّد من حالة العملية أولًا، ثم تحدّث عن غيرها
مسار تشخيص «لا يتصل» و«لا يقوم» مختلف تمامًا. والخطوة الأولى دائمًا التأكد من بقاء العملية واستماعها على المنفذ (القسم 5). وبتخطّي هذه الخطوة يصبح كل حكم لاحق تخمينًا.
:::

## 2. الخادم لا يقوم (BDS والنوى من طرف ثالث)

### 2.1 BDS: المعمارية ومكتبات التشغيل ومتطلبات النظام

BDS برنامج **مُترجم أصليًا** لا سكربت، فهو يفرض شروطًا على النظام ومكتبات التشغيل.

| البند | المتطلب | ملاحظة |
| --- | --- | --- |
| المعمارية | **x86-64** | توفّر الجهة الرسمية بناءات x86-64 لـ Windows وLinux فقط؛ وأجهزة ARM (مثل Raspberry Pi) خارج نطاق الدعم الرسمي |
| Windows | Windows 10 10.0.15063 فأحدث، أو Windows Server 2016 فأحدث | ويلزم **مكتبة تشغيل Microsoft Visual C++** (VC++ Redistributable) |
| Linux | تدعم الجهة الرسمية **Ubuntu 22.04 فأحدث** فقط | وتعمل توزيعات x86-64 أخرى إذا اكتملت المكتبات، بما فيها **glibc 2.35 فأحدث** |
| الذاكرة | 4 GB حدًّا أدنى | وتحتاج أكثر عادةً عند تجاوز 10 لاعبين؛ ويُنصح بحجز 1 GB للقرص |

وعن المظهر النمطي لغياب مكتبة التشغيل: على Windows يعتمد BDS على مكتبة تشغيل Microsoft Visual C++، **وغيابها يظهر عادةً كخطأ عن DLL ناقص في لحظة التشغيل، أو كنافذة تختفي فورًا**، ووحدة التحكّم خالية غالبًا؛ وعلى Linux مع glibc أقدم يظهر عادةً **فشل تحميل مكتبة ديناميكية** (من نوع `error while loading shared libraries`). ومكتبة التشغيل ونسخة libc المطلوبتان بدقّة **بحسب صفحة تنزيل BDS الرسمية وrelease notes**، ولا تنسخ أرقام النسخ من دروس طرف ثالث.
:::warn لا يمكن تحديد الذاكرة في BDS كما في إصدار Java
يمكن في إصدار Java التحكّم في حجم الكومة بـ`-Xms` / `-Xmx`، **ولا وسائط تشغيل مقابلة في BDS**. فهو يدير ذاكرته بنفسه، ولا تستطيع التحكّم في استهلاكه إلا بشكل غير مباشر بتقييد حجم العالم وعدد الكيانات وعدد اللاعبين. فالنصيحة من نوع «أضف وسائط ذاكرة إلى BDS» غير صالحة.
:::

### 2.2 Linux: صلاحية التنفيذ ودليل العمل

أشهر سببي «لا يقوم» على Linux عمليان. **الأول غياب صلاحية التنفيذ** — فـ`bedrock_server` المستخرج من الأرشيف لا يحمل `+x` افتراضيًا:

```bash
chmod +x bedrock_server
```

**والثاني دليل عمل خاطئ** — فالاستخدام الرسمي لـ BDS هو **تشغيله داخل دليله**، مع توجيه مسار البحث عن المكتبات الديناميكية إلى الدليل الحالي:

```bash
cd /opt/bedrock-server
LD_LIBRARY_PATH=. ./bedrock_server
```

و**بيانات BDS كلها تُحفظ في دليل العمل**، وهو يتوقّع أن تكون الملفات الأولية المفكوكة هناك. ولذلك: عند التشغيل بـ systemd أو بغيره اضبط `WorkingDirectory` إلزاميًا، وإلا فقد يكون دليل عمل العملية `/`؛ وتنفيذ الملف التنفيذي من دليل آخر قد يولّد ملفات إعداد وعالمًا جديدين في الدليل الخطأ في أفضل الحالات، وقد يفشل التشغيل مباشرةً لعدم إيجاد المكتبات في الدليل نفسه في أسوأها. ولاحظ أيضًا أن `.` في `LD_LIBRARY_PATH=.` تعني **دليل العمل الحالي**، لا دليل الملف التنفيذي.
:::tip أول أمر لتشخيص «لا يقوم»
شغّل `LD_LIBRARY_PATH=. ./bedrock_server` يدويًا داخل دليل الخادم، واقرأ الخطأ كما هو. فكثير من المشكلات تنكشف في هذه الخطوة، وهي أسرع بكثير من تقليب السجلات.
:::

### 2.3 مزالق تغيير الاسم والمسار

يمكن تغيير اسم برنامج BDS الرئيسي، لكن **لا يُنصح به**. فبعد التغيير يجب تحديث كل موضع يشير إليه: سكربت التشغيل (`.bat` / `.sh`)، واختصار سطح المكتب، وأمر التشغيل المضبوط في اللوحة أو الخدمة الحارسة، وأمر `LD_LIBRARY_PATH=. ./bedrock_server` نفسه في القسم 2.2. وإغفال أي موضع يُنتج «نقرت فلا شيء يحدث» أو «خطأ ملف غير موجود». فإن كنت قد غيّرت الاسم ولم يقم، فأعِد الاسم القديم للتحقق، ثم قرّر هل تعدّل المواضع واحدًا واحدًا.

والمسار نفسه موضع خطأ كذلك: يُنصح بوضع دليل الخادم في مسار بحروف لاتينية صرفة، بلا مسافات ولا رموز خاصة. فالمسار العربي أو ذو المحارف غير اللاتينية يسبب فشل قراءة في بعض اللوحات وسكربتات التشغيل، والخطأ عادةً يصعب فهمه.

### 2.4 عائلة Nukkit: مطابقة نسخة Java والبناء

عائلة Nukkit (Nukkit / PowerNukkitX وغيرها) برامج **Java**، ويجب تأكيد أمرين:

- **هل نسخة Java كافية**: فالفروع الحديثة تطلب Java أحدث عادةً، والتثبيت الأقدم يرمي عند التشغيل خطأً من نوع `UnsupportedClassVersionError`، ويُكتب في الخطأ عادةً النسخة المطلوبة، **فاعتمد التوثيق الرسمي لتلك النواة**.
- **هل عدد البتّات صحيح**: فنظام 64-بت يجب أن يقابله Java 64-بت. وJava 32-بت ينهار عند التشغيل أو في المنتصف بسبب سقف الذاكرة.

والأخفى هو **عدم مطابقة البناء لنسخة البروتوكول**: فبناء النواة نفسه يقوم، لكن العميل لا يتصل أو تظهر رسالة بأن نسخة الخادم قديمة. ولهذه الطبقة انظر أولًا [البدء مع نوى Bedrock من طرف ثالث](/tutorials/bedrock/third-party-setup)، فهناك شرح كامل لمطابقة النسخ.

### 2.5 PocketMine-MP: نسخة PHP والإضافات

PMMP برنامج **PHP**، ومتطلباته الرسمية: **معالج 64-بت + نظام تشغيل 64-بت**، وذاكرة من 1 GB؛ ونواتان فأكثر **توصية** لا شرط؛ وتدعم الجهة الرسمية Windows وLinux وmacOS قدر الإمكان، ومبدئيًا أي منصّة تشغّل PHP 64-بت وإضافاتها كاملة.

وأكثر مأزقين: **نسخة PHP والإضافات** — فـ PMMP يحتاج نسخة PHP محدّدة ومجموعة إضافات، وإن كانت النسخة خاطئة أو الإضافة غير محمّلة ظهر خطأ عند التشغيل، ومن الشائع فشل تحميل إضافة PHP (مثل `opcache`)؛ **وأي الإضافات يلزم وأدنى نسخة PHP، بحسب Setup requirements في توثيق PMMP الرسمي**. **ولا تستخدم PHP النظام كما هو** — فـ PHP في مستودعات التوزيعات أقدم عادةً وإضافاته ناقصة، وعلى Windows قد يكون هناك PHP تركه برنامج آخر؛ وقد وفّرت PMMP رسميًا **مكتبة تشغيل PHP مجمّعة لكل نظام** (تُؤخذ من صفحة إصداراتها بحسب نظام التشغيل)، وتُفكّ وتُستخدم مباشرةً. **والموصى به استخدام PHP المجمّعة رسميًا، لا أي PHP نظام.**
:::warn تأكّد أولًا أي PHP تنادي
نفّذ `php -v` وتأكّد أن المخرجات هي النسخة وعدد البتّات التي تريد. فإن كان سكربت التشغيل يكتب `php` مجرّدة فسيأخذ أول ما في `PATH`، وهو ليس ما ثبّته أنت على الأرجح.
:::

### 2.6 المنفذ محتلّ

مظهر تعارض المنافذ: العملية تقوم ثم تخرج فورًا، وتُظهر وحدة التحكّم تعذّر ربط (bind) المنفذ.

وهناك **مأزق خاص بإصدار Bedrock**: `enable-lan-visibility` في `server.properties` مفعّل افتراضيًا، ووظيفته الاستجابة لعملاء البحث عن الخوادم في الشبكة المحلية. وعند تفعيله، **فإن غيّرت `server-port` / `server-portv6` إلى قيم أخرى سيبقى الخادم يربط 19132 / 19133 الافتراضيين**. ففتح خادم Bedrock ثانٍ على الجهاز نفسه قد يتعارض ولو غيّرت المنفذ؛ وإن لم تحتج إلى الاكتشاف المحلي فيمكن إغلاق هذا الخيار لتجنّب ذلك، والسلوك المحدّد بحسب التوثيق الرسمي. ولاحظ أيضًا أن النطاق الصالح لـ`server-port` عدد صحيح **1–65535**.

### 2.7 خطأ في كتابة server.properties

ملف `server.properties` في Bedrock **نصّ `مفتاح=قيمة` سطرًا سطرًا**، والأسطر التي تبدأ بـ`#` تعليقات. وكتابة نوع خاطئ أو قيمة خارج النطاق قد تُفشل التشغيل، أو تُتجاهل القيمة فتصبح النتيجة «غيّرت ولم يسرِ». وهذه بعض القيم الصالحة المؤكّدة للمقارنة المباشرة:

```properties
server-port=19132
server-portv6=19133
allow-list=true
gamemode=survival
difficulty=easy
default-player-permission-level=member
tick-distance=4
view-distance=32
max-players=10
compression-algorithm=zlib
```

| المفتاح | القيم الصالحة / النطاق |
| --- | --- |
| `server-port` / `server-portv6` | عدد صحيح 1–65535 |
| `allow-list` | `true` / `false` |
| `gamemode` | `survival` / `creative` / `adventure` |
| `difficulty` | `peaceful` / `easy` / `normal` / `hard` |
| `default-player-permission-level` | `visitor` / `member` / `operator` |
| `tick-distance` | عدد صحيح 4–12 |
| `view-distance` | عدد صحيح 5 فأكثر |
| `max-players` | عدد صحيح موجب |
| `compression-algorithm` | `zlib` / `snappy` |
:::warn انسخ احتياطيًا قبل التحرير، وحرّر بمحرّر نصّ صرف
حرّر بمحرّر **نصّ صرف** مثل Notepad، لا بمحرّر يُدخل تنسيقًا (كبيانات مكتبية غنية)، وإلا كُتبت محارف غير مرئية فأفشلت التحليل. وانسخ `server.properties` قبل التعديل. وأي القيم مسموحة فعلًا **بحسب التوثيق الرسمي**.
:::

## 3. لا يتصل (cannot connect)

### 3.1 عدم تطابق البروتوكول / النسخة

وهذا **أشهر** أسباب عدم الاتصال في إصدار Bedrock، ولا يملك اللاعب مجالًا للنجاة: فمتجر التطبيقات يحدّث تلقائيًا، وبمجرد تحديث العميل يتغيّر البروتوكول. ولن نعيد تفصيل هذه الطبقة هنا، بل انظر [نسخة البروتوكول واختيار النسخة](/tutorials/bedrock/protocol). والنقطتان فقط: يجب أن يكون بروتوكول العميل **مطابقًا** لبروتوكول الخادم ليدخل اللاعب؛ ولاعبو iOS لا يستطيعون إلا تثبيت أحدث نسخة من المتجر، فطريق «اطلب من اللاعب التخفيض» مسدود لجمهور iOS. وعند عدم تطابق نسخة العميل مع نسخة الخادم يرى اللاعب رسالة من نوع «الخادم قديم»، **ونصّ الرسالة المحدّد بحسب الرسمي**.

### 3.2 UDP وTCP: المنافذ وجدار الحماية ومجموعة الأمان

إصدار Bedrock **يعمل على UDP**، وهذا يختلف تمامًا عن إصدار Java، وهو السبب الأول لـ«فحص المنفذ ناجح واللاعبون لا يدخلون».

| البند | القيمة |
| --- | --- |
| منفذ IPv4 الافتراضي | **19132 / UDP** |
| منفذ IPv6 الافتراضي | **19133 / UDP** |
| مواضع السماح المطلوبة | جدار حماية النظام **و**مجموعة أمان السحابة، كلتاهما |
| تحويل المنافذ في الموجّه | يجب اختيار **UDP**؛ وإن لم يتوفّر إلا TCP فيلزم إنشاء قاعدة UDP مستقلة |
:::warn الأدوات التي تفحص TCP فقط تخدعك
كثير من أدوات «فحص المنفذ» على الإنترنت تفحص TCP افتراضيًا. ونجاح منفذ TCP لا يعني نجاح منفذ UDP. وعند تأكيد منفذ Bedrock يجب أن تفحص **UDP** صراحةً.
:::
ولاحظ أيضًا أن أغلب خدمات اختراق النفق تدعم TCP فقط افتراضيًا، فتأكّد من دعمها **UDP** عند اختيار الحل. وسياق العبور بين النسختين (إدخال لاعبي الهاتف / Bedrock إلى خادم Java أو العكس) في [دعم لاعبي الهاتف](/tutorials/java/mobile).

### 3.3 CGNAT / لا IPv4 عام / NAT مزدوج

الخادم يعمل جيدًا، وجدار الحماية سمح، والخارج ما زال لا يتصل — والمشكلة غالبًا على جهة المشغّل.

| الحالة | الحكم | اتجاه المعالجة |
| --- | --- | --- |
| واجهة WAN في الموجّه حصلت على **عنوان خاص أو مشترك** (CGNAT) | لا تملك IPv4 عامًا حصريًا، فتحويل المنافذ بلا وجهة | اطلب IP عامًا من المشغّل، أو استخدم نفقًا / شبكة افتراضية تدعم UDP |
| **NAT مزدوج**: مودم ضوئي بعده موجّه آخر | التحويل مُجرى على واحد فقط، والرابط مقطوع في المنتصف | يجب إجراء التحويل على **الجهاز المتصل بالإنترنت مباشرةً**، وتوصيل تحويل القفزة التالية به |
| IP العام ديناميكي | العنوان يتغيّر فلا يتذكّره اللاعب | استخدم خدمة نطاق ديناميكي، أو حل نفق |
| يوجد IPv6 عام فقط | شبكة بعض اللاعبين لا تدعم IPv6 | تحقّق من قابلية الوصول على جهة IPv4 كذلك |

وحين يتعذّر تحويل المنافذ، فالبديل الشائع هو **شبكة افتراضية محلية**: يُدخل الخادم واللاعبون في شبكة افتراضية واحدة، ثم يتصل اللاعبون بعنوان تلك الشبكة. والشائع في المجتمع ZeroTier وRadmin VPN وHamachi وغيرها، وإعدادها في توثيق كلٍّ الرسمي.

### 3.4 الاكتشاف المحلي مقابل الاتصال بالـ IP

طريقتا الاتصال تسلكان مسارين مختلفين، والأعراض تختلف كذلك.

| | الاكتشاف المحلي | الاتصال بـ IP / النطاق |
| --- | --- | --- |
| ما على اللاعب فعله | لا شيء، فيظهر الخادم أعلى شاشة «اللعب» | إضافة الخادم يدويًا، وإدخال العنوان والمنفذ |
| الشرط | أن يكون الطرفان في الشبكة المحلية نفسها | أن يكون الخادم قابلًا للوصول من الخارج (تحويل منافذ أو نفق) |
| ما يؤثر فيه | `enable-lan-visibility`، وتوافر UDP 19132/19133 | IP العام، وجدار الحماية، ومجموعة الأمان، والنفق |

وبعض النقاط التي يسهل إغفالها: **يجب تحديد المنفذ صراحةً في إصدار Bedrock**، فهو لا يدعم حذف المنفذ عبر سجل SRV كما في إصدار Java، فيجب ملء حقلي العنوان والمنفذ صحيحًا؛ والاكتشاف المحلي يعتمد على البثّ/البثّ المتعدّد، ولا يعمل في بعض الشبكات الافتراضية أو شبكات الحاويات أو الشبكات العابرة للنطاقات، وعندها لا يبقى إلا الاتصال بالـ IP؛ و**الاتصال بالجهاز نفسه** قد يفشل بسبب قواعد الرجوع أو جدار الحماية، وتجربة جهاز آخر تميّز فورًا بين «الخادم غير قابل للوصول» و«مشكلة في هذا الجهاز نفسه».

### 3.5 منصّات الأجهزة (Xbox / PlayStation / Switch)

**لا يمكن إدخال IP داخل اللعبة للانضمام إلى خادم** على منصّات الأجهزة. والطريقان الشائعان: **DNS مخصّص** (توجيه تحليل النطاق إلى خادمك ليدخل الجهاز عبر النطاق)، و**الشبكة المحلية** (أن يكون الجهاز والخادم في الشبكة المحلية نفسها، والدخول بالاكتشاف المحلي).
:::note سياسات المنصّات تتغيّر، وتختلف بينها
قيود جهة الأجهزة **تتغيّر بحسب سياسة المنصّة والنسخة**. وتشير مصادر إلى أن نسخ الأجهزة تميل عمومًا إلى الشبكة المحلية فقط، وأن نطاق خيارات Switch أضيق (قد يقتصر على Realms / الخوادم الموصى بها رسميًا). **وما تدعمه منصّة معيّنة الآن بحسب التوثيق الرسمي وبيانات المنصّة**، ولا تنسخ الدروس القديمة.
:::

### 3.6 الفحص على جهة العميل

استبعد أبسط الاحتمالات قبل المسّ بالخادم: **صيغة العنوان**: يُكتب في حقل العنوان IP أو النطاق فقط، **والمنفذ في حقل المنفذ**، وإدخال `ip:port` كاملًا في حقل العنوان يفشل تحليله في بعض النسخ؛ **والمنفذ** الافتراضي 19132، فإن غيّره الخادم وجب تغييره عند اللاعب؛ **وهل النسخة نفسها** — فعملاء Bedrock **لا** يدخلون خوادم Java مباشرةً (والعكس كذلك)، والعبور بين النسختين يحتاج حلًّا إضافيًا، انظر [دعم لاعبي الهاتف](/tutorials/java/mobile)؛ **ويجب أن تكون نسخة العميل مطابقة لنسخة الخادم**، فإصدار Bedrock لا يدعم اتصال عميل قديم بخادم أحدث. وأخيرًا **جرّب جهازًا آخر وشبكة أخرى**، فهذا يميّز فورًا بين مشكلة الخادم ومشكلة شبكة اللاعب ومشكلة جهازه.

### 3.7 حالات خاصة بالنوى من طرف ثالث

النوى من طرف ثالث **لا تنفّذ كل سمات بروتوكول الخادم الرسمي ومحتوى اللعبة بالضرورة**، فـ«العميل نفسه يعمل على الخادم الرسمي ولا يعمل على خادمي» ظاهرة طبيعية، وليست خطأ إعداد بالضرورة. وبمثال PocketMine-MP، يوضّح التوثيق الرسمي أن PMMP **لم** تنفّذ كل خصائص اللعب في Minecraft، والسبب أن المطوّرين يصونونه في أوقات فراغهم ويصعب عليهم ملاحقة سرعة تحديثات الجهة الرسمية؛ والخصائص الغائبة وقت الكتابة تشمل **المخلوقات (mobs)، وRedstone، وعربات المناجم، والأبعاد**.

ونقطة أخرى هي **مطابقة بناء النواة لنسخة البروتوكول**: فالنسخة التي تبلّغها النواة للعميل يجب أن يقبلها العميل، وإلا رأى اللاعب رسالة من نوع «نسخة الخادم قديمة». وأسلوب معالجة PMMP في أسئلتها الشائعة الرسمية: نفّذ أمر `version` في وحدة تحكّم الخادم، وانظر نسخة Minecraft التي تدعمها النواة الحالية، واختر بناءً أحدث للنواة بحسب ذلك؛ وتوضّح الجهة الرسمية كذلك أن **نسخ الترقيع الأحدث قد تتوافق أحيانًا (لا دائمًا) دون تحديث النواة**.

## 4. يدخل لكن بشذوذ (works but behaves oddly)

### 4.1 التقطيع والذاكرة

**وأول معيار للتقطيع أداء النواة الواحدة.** فحسابات المخلوقات في BDS تُنجَز على خيط واحد، فالسلاسة تتوقّف أساسًا على أداء النواة الواحدة، وكلما كبرت الخريطة زاد التقطيع، وهذا موضّح في [خادم BDS](/tutorials/bedrock/bds).

| الاتجاهات القابلة للتعديل | ملاحظة |
| --- | --- |
| تخفيض `tick-distance` | النطاق الصالح 4–12، والافتراضي 4. وكلما كبرت القيمة زادت المناطق الداخلة في الحساب |
| تخفيض `view-distance` | يجب أن يكون 5 فأكثر، والافتراضي 32. ويؤثر أساسًا في نطاق الإرسال |
| تقليل حجم مزارع الكيانات / المخلوقات | فالكيانات هي الحِمل الرئيسي على الخيط الواحد |
| الانتقال إلى جهاز بنواة واحدة أقوى | الأكثر مباشرةً والأعلى كلفة |
| `max-threads` | موجود في Bedrock (أقصى عدد خيوط)، لكنه **لا يغيّر عنق زجاجة الخيط الواحد**، فلا تتوقّع أن يحلّ التقطيع |

وعن نوى PHP: يوضّح توثيق PMMP الرسمي أنها «سيئة الصيت» في استغلال الأنوية المتعددة، فإن كنت تشتري جهازًا لتشغيل PMMP **ففضّل التردد العالي على كثرة الأنوية**.

**وعن النمو المستمر للذاكرة**: في BDS مشكلة معروفة هي الزيادة البطيئة في الذاكرة. والتنبيه المهم هو —
:::warn لا تنظّف الذاكرة قسريًا
تنظيف الذاكرة قسريًا يجعل **شريط التقدّم يتوقّف** عند تنزيل اللاعب لحزمة المواد / Addon، **ولا يُستعاد إلا بإعادة تشغيل الخادم**. والتصرف الصحيح تخطيط نافذة إعادة تشغيل دورية، لا «أرى الذاكرة مرتفعة فأنظّفها».
:::

### 4.2 مشكلات المناطق وبيانات العالم

بيانات عالم BDS في دليل **`worlds/`**، ولكل عالم دليل فرعي. وهناك سلوك بالغ الأهمية:

> يبحث الخادم عند التشغيل في `worlds/` عن دليل **يحمل اسم `level-name` نفسه في `server.properties`**. فإن وجده استخدمه؛ **وإن لم يجده أنشأ عالمًا جديدًا**.

وهذا يعني أن **خطأ حرف واحد في `level-name` لا يُظهر خطأً، بل يولّد عالمًا جديدًا بهدوء** — وما يراه اللاعب هو «أرشيفي اختفى». فحين تلاحظ «تغيّر الأرشيف» فأول ما تفحصه اسم `level-name` واسم الدليل في `worlds/`.

| الظاهرة | السبب المحتمل | المعالجة |
| --- | --- | --- |
| فشل تحميل العالم / خطأ متعلق بالعالم عند التشغيل | الأرشيف تالف، أو الحفظ السابق قُوطِع | **أوقف إعادة التشغيل المتكرّرة**، واستعِد من نسخة |
| تعذّر قراءة العالم بعد تغيير النواة | توافق أرشيف النوى من طرف ثالث أقل من BDS الرسمي | أعِد النواة الأصلية، أو رحّل بحسب توثيق النواة |
| استيراد العالم لا يسري | اسم الدليل لا يطابق `level-name` | أعِد تسمية دليل العالم إلى قيمة `level-name` |
| ضياع الأرشيف كله | نُسخت ملفات جزئية فقط | انسخ **الدليل كله** `worlds/` |

وعملية الاستعادة الكاملة من نسخة في [النسخ الاحتياطي والاستعادة](/tutorials/java/backup).
:::tip أوقف الخادم طبيعيًا قبل النسخ أو الاحتياط
نفّذ `stop` في وحدة التحكّم، وانتظر خروج العملية فعلًا ثم انسخ `worlds/`. فالنسخ والعملية ما زالت تكتب قد يعطيك أرشيفًا «يبدو كاملًا وهو تالف».
:::

### 4.3 الحزم الإضافية وحزم الموارد

مقدّمتان: **يجب أن تكون الحزمة بصيغة Bedrock** — فحزم بيانات / موارد إصدار Java وحزم Bedrock الإضافية منظومتان لا تتبادلان؛ **ويجب وضع الحزمة وتسجيلها بشكل صحيح** — فمجرد نسخ الملفات لا يفعّلها الخادم تلقائيًا. والأدلة المسجّلة وطريقة التسجيل كما يلي:

| النوع | دليل الوضع |
| --- | --- |
| حزمة السلوك (Behavior Pack) | `development_behavior_packs` |
| حزمة الموارد (Resource Pack) | `development_resource_packs` |

ولتفعيل حزمة لعالم ما، يُنشأ ملف قائمة مقابل في **دليل عمل ذلك العالم**، يُكتب فيه UUID الحزمة ونسختها؛ والـ UUID من `manifest.json` الخاص بالحزمة:

```json
[
    {
        "pack_id": "33556fcf-d192-4d5f-96a0-29357702af7b",
        "version": [ 1, 0, 0 ]
    }
]
```

حيث تُكتب حزمة السلوك في `world_behavior_packs.json`، وحزمة الموارد في `world_resource_packs.json`؛ وعند تعارض عدة حزم، **الأسبقية للحزمة الأسبق في الترتيب**.

ونقاط أخرى: **`texturepack-required=true`** يفرض على العميل تنزيل حزمة موارد الخادم، وبعد تفعيله تبطل حزم الموارد التي فعّلها اللاعب في عميله (بما فيها حزم المتجر)؛ **وحزم المتجر (Marketplace) لا يمكن تطبيقها على الخادم**؛ وفي جذر الخادم ملف **`valid_known_packs.json`** هو **قائمة الحزم المعروفة** التي يصونها الخادم ويستخدمها في التحقّق، وصيغته الدقيقة وعملية صيانته **بحسب التوثيق الرسمي**، ويكفي في العمل اليومي اتباع «ضع في الدليل + اكتب world_*_packs.json»؛ و**توقّف العميل عند تنزيل حزمة الموارد** قد يكون سببه — عدا الحزمة نفسها — حالة ذاكرة الخادم (انظر 4.1)، وإعادة تشغيل الخادم تستعيدها غالبًا.

ولـ PMMP مشكلة معروفة رسميًا: **مشكلات اتصال عند استخدام الخادم لحزمة موارد كبيرة** (والجهة الرسمية تضرب مثلًا حزمة أكبر من 1 MB). ووسيلة التشخيص التي تعطيها الجهة الرسمية إزالة الحزمة الكبيرة وإعادة المحاولة؛ وقد يفيد حل بديل هو تخفيض `network.max-mtu-size` في `pocketmine.yml` تدريجيًا (مثلًا 100 في كل مرة ثم الاختبار)، لكن الجهة الرسمية توضّح أن هذا **حل بديل** يخفض كفاءة النطاق، ويجب البحث عن السبب الجذري.

### 4.4 الصلاحيات والقائمة البيضاء

صلاحيات BDS وقائمته البيضاء **ملفّان مستقلان**، وحقولهما مختلفة، ويخلط بينهما كثيرون. **المشرف (OP) في `permissions.json`**، والبند يتكوّن من `xuid` و`permission`:

```json
[
    {
        "permission": "operator",
        "xuid": "451298348"
    }
]
```

- القيم الصالحة لـ`permission` ثلاث فقط: **`operator` / `member` / `visitor`**.
- **`online-mode` يجب أن يكون مفعّلًا**، لأن XUID يحتاج تحقّقًا بحساب متصل.
- وإن عُدّل الملف والخادم يعمل، فلن يسري إلا بعد **`permission reload`**؛ و`permission list` يعرض الصلاحيات الحالية.
- واللاعب الجديد غير الموجود في القائمة يخضع لإعداد `default-player-permission-level`. ويمكن **تعديل صلاحية اللاعب داخل اللعبة** بدل تحرير الملف.

**والقائمة البيضاء في `allowlist.json`**، وحقول بندها:

| الحقل | المعنى |
| --- | --- |
| `name` | **اسم اللعب / اللقب (gamertag)** للاعب، ويجب أن يتطابق تمامًا |
| `xuid` | XUID اللاعب؛ **وإن كُتب `name` فيمكن حذف هذا الحقل** |
| `ignoresPlayerLimit` | إن كان `true` فيمكن للاعب الدخول ولو كان العدد ممتلئًا |

وبعض السلوكيات المفتاحية: عند كتابة `name` وحدها، **يُكمل XUID تلقائيًا بعد اتصال اللاعب بالاسم نفسه**، أي أن خطأ الاسم يعني أن هذا الشخص لا يدخل أبدًا ولا يُصحَّح تلقائيًا؛ **والقائمة البيضاء لا تسري إلا مع تفعيل `online-mode`**، فبعد إغلاق التحقق الأصلي يستطيع اللاعب الدخول باسم موجود في القائمة البيضاء، فتصبح بلا معنى؛ وبعد **تغيير اللاعب لـ gamertag** لا يطابق بند الاسم القديم، فيجب تحديثه؛ وعند تحرير الملف يدويًا والخادم يعمل يلزم أمر reload المقابل ليسري التعديل.

| الظاهرة | السبب المحتمل | المعالجة |
| --- | --- | --- |
| من يجب أن يكون OP ليس كذلك | البند غير مكتوب في `permissions.json`، أو كُتب ولم يُنفَّذ reload | أضف البند وأعد التحميل، أو اضبط داخل اللعبة |
| أُضيف إلى `permissions.json` ولم يسرِ | `online-mode` مغلق، فلا يمكن التحقق من XUID | فعّل `online-mode` |
| من في القائمة البيضاء لا يدخل | `name` لا يطابق gamertag الفعلي تمامًا (حالة الأحرف، أو المسافات، أو تغيير الاسم) | تحقّق من الاسم بدقّة، أو اكتب XUID مباشرةً |
| أي أحد يدخل | القائمة البيضاء غير مفعّلة، أو `online-mode` مغلق | افحص `allow-list` و`online-mode` |
:::note أسماء الحقول بحسب التوثيق الرسمي
أسماء الحقول والسلوكيات أعلاه مأخوذة من الشرح الرسمي. **وقد تُعدَّل الحقول أو القيم الافتراضية بين النسخ**، والمرجع الفعلي توثيق BDS الرسمي (وملف `bedrock_server_how_to.html` المرافق للحزمة).
:::

### 4.5 فروق السلوك عن إصدار Java

كثير من «الأخطاء» التي يبلّغ عنها اللاعبون هي في الحقيقة **اختلاف أصيل بين النسختين**: فآليات Redstone، وقواعد توليد المخلوقات، وغيرها تختلف. ولن نعيد شرح هذه الطبقة هنا، بل انظر [JAVA مقابل Bedrock](/wiki/editions).

## 5. ترتيب التشخيص

اتبع الترتيب التالي، فكل خطوة تشطب نصف الاحتمالات. **ولا تتخطَّ خطوة.**

1. **تأكّد أن عملية الخادم تعمل فعلًا.** انظر هل نافذة وحدة التحكّم ما زالت موجودة، وهل العملية في قائمة العمليات.
2. **تأكّد أنها تستمع على المنفذ.** والأوامر على Linux وWindows أدناه.
3. **تأكّد من المنفذ والبروتوكول.** هل رقم المنفذ صحيح، وهل المسموح هو **UDP** (الافتراضي 19132، وIPv6 هو 19133).
4. **تأكّد من نسخة العميل.** يجب أن تكون نسخة العميل مطابقة لنسخة الخادم، انظر [نسخة البروتوكول واختيار النسخة](/tutorials/bedrock/protocol).
5. **تأكّد من مسار الشبكة.** فالشبكة المحلية / IP العام / النفق مسارات مختلفة؛ وهل هناك CGNAT أو NAT مزدوج.
6. **انظر إلى وحدة تحكّم الخادم وسجله.** فنصّ الخطأ أغلى من أي تخمين. وBDS يطبع التشغيل والأخطاء في وحدة التحكّم.
7. **تأكّد من الصلاحيات والقائمة البيضاء.** هل طُرد اللاعب أم لم يتصل أصلًا؟ والطرد يُظهر سببه في وحدة التحكّم عادةً.
8. **تأكّد من سلامة العالم والحزم الإضافية.** هل `level-name` يطابق اسم الدليل في `worlds/`؛ وهل الحزمة في الدليل الصحيح ومسجّلة.

وأوامر الخطوة 2: على Linux استخدم `ss -ulnp | grep 19132` (و`-u` لـ UDP فقط)؛ وعلى Windows استخدم `netstat -ano | findstr 19132` (و`-a` لكل الاتصالات والاستماع، و`-n` بلا تحليل أسماء، و`-o` لعرض رقم العملية)؛ وفي PowerShell أوضح منها `Get-NetUDPEndpoint -LocalPort 19132`.

```bash
ss -ulnp | grep 19132
```

```bat
netstat -ano | findstr 19132
```

**وجدول مقابلة الأعراض:**

| الظاهرة | ما تفحصه أولًا | السبب الشائع |
| --- | --- | --- |
| العملية غير موجودة | نصّ الخطأ في وحدة التحكّم | غياب مكتبة تشغيل، أو نسخة Java / PHP خاطئة، أو منفذ محتلّ، أو خطأ إعداد |
| العملية موجودة والمنفذ لا يستمع | هل في سجل التشغيل فشل bind | منفذ محتلّ، أو `enable-lan-visibility` يربط 19132/19133 |
| المنفذ يستمع، والجهاز نفسه يتصل والخارج لا | قابلية الوصول من الإنترنت | مجموعة أمان / جدار حماية لم يسمح بـ UDP، أو CGNAT، أو NAT مزدوج |
| فحص المنفذ ناجح واللاعبون لا يدخلون | هل الأداة تفحص TCP أم UDP | لم يُسمح إلا TCP |
| رسالة بأن نسخة الخادم قديمة | نسخة العميل والخادم | عدم تطابق البروتوكول؛ أو بناء النواة من طرف ثالث قديم جدًا |
| يدخل ثم يُقطع فورًا | هل في وحدة التحكّم سبب الطرد | القائمة البيضاء، أو الصلاحيات، أو سقف اللاعبين |
| يدخل لكن بتقطيع شديد | استهلاك النواة الواحدة، و`tick-distance`، وعدد الكيانات | عنق زجاجة النواة الواحدة، أو خريطة كبيرة جدًا |
| الأرشيف «اختفى» | `level-name` واسم الدليل في `worlds/` | خطأ في `level-name`، فأنشأ الخادم عالمًا جديدًا |
| الحزمة الإضافية لا تسري | نوع الحزمة ودليل وضعها | دليل خاطئ، أو عدم كتابة world_*_packs.json |

## 6. ماذا تقدّم عند طلب المساعدة

أعطِ ما يلي كاملًا مرة واحدة، توفّر دورات مراسلة كثيرة:

| المعلومة المطلوبة | لماذا تلزم |
| --- | --- |
| **نواة الخادم ونسخة البناء** | رقم نسخة BDS، أو اسم نواة عائلة Nukkit / PMMP ورقم بنائها. ومسار التشخيص يختلف بحسب النواة |
| **نسخة اللعبة / نسخة البروتوكول** | أي نسخة عند العميل وأيها عند الخادم، وهي أول بند تشخيص في Bedrock |
| **نظام التشغيل والمعمارية** | Windows أم Linux، والتوزيعة ونسختها، وهل 64-بت، وهل x86-64 |
| **نصّ الخطأ الكامل من وحدة التحكّم** | **لا تنقل بالمعنى، ولا تقتطع نصفه**. فالكلمات المفتاحية في النصّ تحدّد المشكلة مباشرةً |
| **آخر ما غيّرته** | ترقية النواة؟ تغيير المنفذ؟ إضافة حزمة؟ تعديل `server.properties`؟ |
| **هل كان يعمل سابقًا** | «لم ينجح قط» و«كان يعمل أمس» مسارا تشخيص مختلفان تمامًا |
| **ما جرّبته سابقًا** | لتجنّب تكرار الاقتراحات؛ وليتبيّن أي الاتجاهات استُبعد |
| **حالة الشبكة** | شبكة محلية أم إنترنت، وهل يوجد IP عام، وأي نفق تستخدم، وكيف ضُبط تحويل المنافذ |
:::tip كيف تعطي نصّ الخطأ
انسخ مخرجات وحدة التحكّم كنصّ، أو ألصق ملف السجل. **والتصوير الفوتوغرافي ولقطات الشاشة ولصق السطر الأخير فقط** كلها تبطئ التشخيص. وإن كانت المخرجات طويلة فأبقِ عدة أسطر قبل الخطأ وبعده، لا جملة واحدة.
:::
