Официальный сервер Bedrock — это **BDS**: у него нет системы плагинов и простая структура каталогов, поэтому он отлично подходит для контейнера. Образ скачивает официальный BDS, принимает EULA и пробрасывает порты, а вам остаётся вести один том и один `docker-compose.yml`.

Эта статья — о **запуске BDS в контейнере**. Структура каталогов, особенности памяти и известные проблемы самого BDS — в статье [Сервер BDS](/tutorials/bedrock/bds).

:::warn Сразу запомните: Bedrock работает по UDP
Java Edition использует **TCP 25565**, Bedrock — **UDP 19132** (для IPv6 — `19133/udp`). **Если открыть или пробросить только TCP, картина будет «сервер вроде работает, но никто не подключается», причём без единой ошибки.** Это самая частая ловушка при подъёме сервера Bedrock, и в этой статье мы повторим её не раз.
:::

## 1. Зачем контейнеризация

| Выгода | Как проявляется |
| --- | --- |
| **Чистое окружение** | Официальный BDS — бинарная программа; контейнер упаковывает её вместе с библиотеками, и на хосте не нужно ставить никаких зависимостей |
| **Воспроизводимость** | Версия, порты, игровой режим, сложность, имя мира записаны в одном файле — перенесли на другую машину и запустили |
| **Простой откат** | Перед обновлением сделайте резервную копию `/data`; если что-то пошло не так — верните прежнее значение `VERSION` и перезапустите |
| **Чистое удаление** | Не нужно — удалите контейнер и том, на хосте не останется мусора |
| **Одинаковость на всех платформах** | Официальный BDS есть только для Windows и Linux; запуск Linux-версии BDS в контейнере на Windows даёт ровно те же действия, что и на сервере |

Цена тоже есть:

| Цена | Описание |
| --- | --- |
| **Лишний слой для изучения** | Понятия образа, контейнера, тома и Compose никуда не деть, а разбор проблем начинается с `docker compose logs` |
| **Дисциплина томов и резервных копий** | Сохранения мира лежат в томе; не сделали копию сами — значит копии нет |
| **Накладные расходы небольшие, но не нулевые** | Сеть добавляет слой NAT, файловая система — слой overlay; настоящее узкое место обычно — **однопоточная симуляция мира в BDS**, поэтому лимит CPU нужно задавать с запасом |
| **Нет экосистемы плагинов** | BDS сам по себе не поддерживает плагины, и контейнер это не меняет; дополнительный контент попадает в каталог данных только в виде паков поведения/паков ресурсов |

## 2. Установка Docker и плагина Compose

Ставьте по официальной документации, не используйте установочные скрипты неизвестного происхождения:

| Платформа | Официальный вход |
| --- | --- |
| Linux (по дистрибутиву) | [Install Docker Engine](https://docs.docker.com/engine/install/) |
| Плагин Compose для Linux | [Install the Compose plugin](https://docs.docker.com/compose/install/linux/) |
| Windows / macOS | [Docker Desktop](https://docs.docker.com/desktop/) |

```bash
docker --version
docker compose version
docker run --rm hello-world
```

:::note Два пути на Windows
В Windows можно скачать официальный архив и запускать exe из него (страница загрузки — [Официальная страница загрузки BDS от Minecraft](https://www.minecraft.net/en-us/download/server/bedrock)), а можно использовать контейнерный вариант из этой статьи. Плюс контейнера — **действия полностью совпадают с работой на сервере Linux**, и при будущей миграции не придётся переучиваться.
:::

## 3. Образ: `itzg/minecraft-bedrock-server`

Обычно в сообществе для Bedrock берут образ **`itzg/minecraft-bedrock-server`** (активно поддерживается, та же экосистема автора, что и у образа для Java Edition).

```bash
docker pull itzg/minecraft-bedrock-server
```

:::note Как он связан с официальным архивом
Официальная [страница загрузки BDS](https://www.minecraft.net/en-us/download/server/bedrock) даёт архив, который нужно самому распаковать, настроить и запустить. **Образ сообщества делает следующее: при старте контейнера скачивает за вас официальный BDS и записывает переменные окружения в `server.properties` и другие конфигурации.**

Поэтому: **конкретный механизм скачивания BDS образом (адрес загрузки, разбор версии, кэширование) определяется официальной документацией образа**, в разных версиях образа он может отличаться. Если хотите полностью всё контролировать — разворачивайте вручную из официального архива по статье [Сервер BDS](/tutorials/bedrock/bds).
:::

## 4. Полный `docker-compose.yml`

```yaml
services:
  bedrock:
    image: itzg/minecraft-bedrock-server
    container_name: mcsog-bedrock
    ports:
      - "19132:19132/udp"
      - "19133:19133/udp"
    environment:
      EULA: "TRUE"
      SERVER_NAME: "MCSOG Bedrock"
      GAMEMODE: "survival"
      DIFFICULTY: "normal"
      LEVEL_NAME: "MCSOG"
      ONLINE_MODE: "TRUE"
      TZ: "Asia/Shanghai"
    volumes:
      - mcsog-bedrock-data:/data
    stdin_open: true
    tty: true
    restart: unless-stopped

volumes:
  mcsog-bedrock-data:
    name: mcsog-bedrock-data
```

Compose v2 **не требует** поля верхнего уровня `version:`.

| Поле | Назначение |
| --- | --- |
| `image` | Используемый образ; в продакшене лучше фиксировать тег, а не вечно брать `latest` |
| `container_name` | Фиксированное имя контейнера, удобно для `logs` / `attach` |
| `ports` | **`/udp` указывать обязательно**. `19132` — основной порт IPv4, `19133` — порт IPv6 (без клиентов IPv6 можно не пробрасывать, но проброс не повредит) |

:::warn Docker обходит системный firewall (для Bedrock это тоже верно)
Правила `ufw` и `firewalld` **не действуют на порты, проброшенные контейнерами Docker**: Docker вставляет свои правила `iptables` перед системным firewall, поэтому `ufw deny 19132/udp` тоже не остановит доступ извне.

Bedrock работает по **UDP**, и его легче упустить из виду, поэтому обязательно закройте доступ так:

1. **Привязать порт только к loopback** (рекомендуется): `-p 127.0.0.1:19132:19132/udp`, а наружу выставить через обратный прокси на хосте;
2. **Ограничить источник через цепочку `DOCKER-USER`**;
3. Подстраховаться **группой безопасности** облачного провайдера (на этот уровень Docker не влияет).

Кроме того, если хотите, чтобы сервер появлялся в **списке локальной сети** (Bedrock находит серверы через UDP-широковещание), режим `bridge` этого не позволит — нужен режим сети `macvlan` или `host`.

Полное описание (включая конфликты подсетей, сравнение режимов сети и таблицу диагностики) — в статье [Развёртывание Java Edition в Docker → Сеть и firewall](/tutorials/java/docker#5-%E7%BD%91%E7%BB%9C%E4%B8%8E%E9%98%B2%E7%81%AB%E5%A2%99%E6%9C%80%E5%AE%B9%E6%98%93%E8%B8%A9%E5%9D%91%E7%9A%84%E4%B8%80%E8%8A%82).
:::
| `environment` | Конфигурация, которую читает образ, см. раздел 6 |
| `volumes` | `имя тома:/data`. **Мир, конфигурация и дополнительные паки — всё в `/data`** |
| `stdin_open: true` | Открывает стандартный ввод, иначе нельзя **вводить команды** в консоль BDS |
| `tty: true` | Выделяет псевдотерминал, вместе с `docker attach` даёт интерактивную консоль |
| `restart: unless-stopped` | Автоматически поднимает контейнер после падения или перезагрузки хоста; после ручного `docker compose stop` сам не поднимется |

Явное `name:` в `volumes` нужно, чтобы имя тома было **предсказуемым** (иначе Compose добавит префикс имени проекта), и команда резервного копирования не указала не на тот том.

:::note `EULA=TRUE` — это требование закона
`EULA: "TRUE"` означает, что **вы прочитали и приняли [Лицензионное соглашение конечного пользователя Minecraft](https://aka.ms/MinecraftEULA)**. Без этой переменной BDS сразу завершится после запуска, и контейнер уйдёт в цикл перезапусков.
:::

:::tip Перед запуском проведите «осмотр»
Каждый раз после правки файла compose запускайте `docker compose config`: порты, тома и переменные окружения будут развёрнуто напечатаны, а ошибки вылезут сразу. **Особенно `/udp` — забытый суффикс видно именно здесь.**
:::

```bash
docker compose config
```

## 5. Запуск, просмотр логов, вход в консоль, остановка

```bash
docker compose up -d
```

Первый запуск скачивает BDS, наберитесь терпения:

```bash
docker compose logs -f
```

Если видите в логах строки вроде `[INFO] Server started.` — сервер поднялся. `Ctrl+C` только выходит из режима слежения за логами и не останавливает сервер.

В Bedrock **нет RCON**, поэтому `rcon-cli` недоступен, и в консоль можно попасть только через `attach`:

```bash
docker attach mcsog-bedrock
```

После attach можно вводить команды BDS так же, как в локальном окне, например:

```text
list
say hello
save hold
save resume
stop
```

:::warn Ловушка клавиш в attach
В `docker attach` нажатие `Ctrl+C` отправляет сигнал прерывания в BDS, **что равно прямому выключению сервера** (сохранение может повредиться). Правильный выход — `Ctrl+P`, затем `Ctrl+Q` (detach, контейнер продолжает работать). Когда сервер действительно нужно выключить, введите команду `stop` и дождитесь завершения процесса.
:::

Остановка и удаление:

```bash
docker compose stop
docker compose down
```

| Команда | Что делает | Данные в томе |
| --- | --- | --- |
| `docker compose stop` | Останавливает контейнер, контейнер остаётся | Сохраняются |
| `docker compose start` | Запускает остановленный контейнер | Сохраняются |
| `docker compose down` | Останавливает и удаляет контейнер и сеть | Сохраняются |
| `docker compose down -v` | Всё вышеперечисленное **плюс удаление тома** | **Полностью теряются** |

:::danger Не добавляйте `-v` по привычке
`docker compose down -v` удалит том `/data`, то есть вместе с ним уйдут сохранения мира. Используйте это, только когда точно решили начать с нуля и у вас есть рабочая резервная копия.
:::

## 6. Переменные окружения из примеров статьи

| Переменная | Назначение | Пример значения |
| --- | --- | --- |
| `EULA` | Подтверждает согласие с Minecraft EULA, без неё запуск не удастся | `"TRUE"` |
| `SERVER_NAME` | Имя сервера (соответствует `server-name`) | `"MCSOG Bedrock"` |
| `GAMEMODE` | Игровой режим по умолчанию | `"survival"` / `"creative"` |
| `DIFFICULTY` | Сложность игры | `"normal"` / `"peaceful"` |
| `LEVEL_NAME` | Имя мира (уровня), **оно же определяет имя папки в `worlds/`** | `"MCSOG"` |
| `ONLINE_MODE` | Проверять ли аккаунт Xbox Live | `"TRUE"` / `"FALSE"` |
| `TZ` | Часовой пояс контейнера, влияет на время в логах | `"Asia/Shanghai"` |
| `VERSION` | Указывает версию BDS; если не задано, обычно берётся последняя | `"LATEST"` |
| `SERVER_PORT` | Порт прослушивания IPv4 (по умолчанию 19132) | `"19132"` |
| `SERVER_PORT_V6` | Порт прослушивания IPv6 (по умолчанию 19133) | `"19133"` |
| `MAX_PLAYERS` | Максимальное число игроков | `"20"` |
| `VIEW_DISTANCE` | Дальность прорисовки | `"12"` |
| `LEVEL_SEED` | Сид мира | Число или строка |
| `ALLOW_LIST` | Включён ли белый список | `"true"` / `"false"` |

:::note Значения по умолчанию меняются
Значения по умолчанию в скобках таблицы соответствуют типичной конфигурации BDS; **после обновления версии образа они могут измениться, обязательно сверяйтесь с официальной документацией образа**. Принцип продакшена: **ключевые пункты всегда прописывайте явно**, не полагайтесь на значения по умолчанию.
:::

:::warn Имя сервера не в ASCII
`SERVER_NAME` поддерживает кириллицу, но часть старых клиентов показывает её как «кракозябры». Если игроки жалуются на искажённые символы, сначала переключитесь на имя из чистого ASCII для проверки. `LEVEL_NAME` тоже лучше задавать в ASCII: оно становится именем каталога, а специальные символы создают лишние проблемы.
:::

## 7. Что находится в `/data`

| Путь | Содержимое |
| --- | --- |
| `/data/worlds/<LEVEL_NAME>/` | **Сохранение мира** (`db/`, `level.dat`, `level_name.txt` и т. п.) |
| `/data/server.properties` | Конфигурация сервера (порт, сложность, режим, включение белого списка и т. п.) |
| `/data/allowlist.json` | Данные белого списка |
| `/data/permissions.json` | Данные администраторов (OP) |
| `/data/valid_known_packs.json` | Список известных дополнительных паков |
| `/data/behavior_packs/`, `/data/resource_packs/` | Паки поведения и паки ресурсов (место размещения дополнительного контента) |

Сохранения BDS **целиком лежат в `worlds/`**, по подкаталогу на мир. Что записано в `LEVEL_NAME`, так и называется каталог:

```text
/data/worlds/MCSOG/db/
```

:::warn Смена `LEVEL_NAME` — это смена мира
Если `LEVEL_NAME` изменился, BDS будет искать каталог с новым именем; не найдёт — **создаст совершенно новый пустой мир**, и старый мир «исчезнет» (на самом деле он остался в томе). Перед изменением имени проверьте имя каталога сохранения.
:::

## 8. Резервное копирование и восстановление

Объект резервного копирования — `/data`, главное — `/data/worlds/`. Самый надёжный способ — **остановить сервер и только потом упаковывать**:

```bash
mkdir -p backups
docker compose stop
docker run --rm \
  -v mcsog-bedrock-data:/data:ro \
  -v "$PWD/backups":/backup \
  alpine \
  tar czf /backup/mcsog-bedrock-$(date +%Y%m%d-%H%M).tar.gz -C /data .
docker compose start
```

В Windows PowerShell замените путь монтирования на `-v "${PWD}\backups:/backup"` (Docker Desktop).

Если остановить сервер нельзя, у BDS есть собственные команды согласованности сохранения (их нужно вводить в консоли через `docker attach`):

```text
save hold
save query
```

`save hold` приостанавливает запись на сервере и сохраняет согласованность файлов, `save query` выводит список файлов, которые нужно скопировать. После копирования возобновите работу:

```text
save resume
```

:::note Почему Bedrock нельзя копировать по образцу Java Edition
В Java Edition используют `save-all` / `save-off` / `save-on`, а в BDS для Bedrock — **`save hold` / `save query` / `save resume`**, эти наборы команд не взаимозаменяемы. Резервное копирование с остановкой сервера подходит в обоих случаях и требует меньше всего нервов.
:::

При восстановлении сначала остановите контейнер, очистите том и распакуйте архив:

```bash
docker compose stop
docker run --rm \
  -v mcsog-bedrock-data:/data \
  -v "$PWD/backups":/backup \
  alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/mcsog-bedrock-20261004-1200.tar.gz -C /data"
docker compose start
```

:::warn Контейнер — это не резервная копия
Том и контейнер лежат на одном диске, поэтому случайное удаление тома, отказ диска или программа-вымогатель унесут и то и другое. Держите хотя бы одну **офлайн- или внешнюю** копию, см. [Резервное копирование и восстановление](/tutorials/java/backup) и [Внешнее резервное копирование](/tutorials/ops/offsite-backup). **Резервная копия, восстановление которой вы не проверяли, не считается резервной копией.**
:::

## 9. Обновление образа и версии BDS

```bash
docker compose pull
docker compose up -d
```

Порядок прежний: **сначала резервная копия, потом pull, потом up**.

| Изменение | Что произойдёт | На что обратить внимание |
| --- | --- | --- |
| `docker compose pull` | Скачивает новую версию образа | После скачивания обязательно нужен `up -d`, иначе контейнер не пересоздастся и изменения не вступят в силу |
| Изменение `VERSION` | Образ заново скачивает соответствующую версию BDS | Версии клиента и BDS должны совпадать; перед обновлением сделайте резервную копию сохранений |
| Без `VERSION` | Обычно берётся последняя версия BDS | Удобно, но **не воспроизводимо**; при проблеме нельзя понять, изменилась версия или конфигурация |

:::note Несовпадение версий — самая частая причина «не подключается»
Когда версия клиента Bedrock не совпадает с версией BDS, игрок обычно **видит сервер, но войти не может**. Фиксированный `VERSION` даёт одну и ту же версию при каждом перезапуске; если хотите идти за последней версией, примите тот факт, что «после очередного перезапуска версия изменится», и предупредите игроков заранее.
:::

## 10. Дополнительный контент: в BDS нет системы плагинов

BDS поддерживает только официальные **паки поведения (behavior packs) и паки ресурсов (resource packs)**, системы плагинов, как в Bukkit, здесь нет, и контейнер этого не меняет. Когда нужны возможности плагинов, придётся переходить на сторонний сервер, см. [Сервер BDS](/tutorials/bedrock/bds) и [Сторонние серверные решения](/tutorials/bedrock/third-party).

Куда класть дополнительный контент:

| Контент | Место размещения |
| --- | --- |
| Паки поведения | `/data/behavior_packs/` |
| Паки ресурсов | `/data/resource_packs/` |
| Паки, привязанные к миру | Соответствующий каталог внутри `/data/worlds/<LEVEL_NAME>/` |

**Способ A: привязанное монтирование (удобнее всего менять файлы)**

```yaml
    volumes:
      - ./data:/data
```

После этого работайте прямо на хосте с `./data/behavior_packs/`.

**Способ B: скопировать в том**

```bash
docker cp ./MyAddon.mcpack mcsog-bedrock:/data/
docker compose restart
```

После изменения конфигурации или замены пака **надёжнее всего перезапустить контейнер**:

```bash
docker compose restart
```

## 11. Производительность и память: две особенности Bedrock

### 11.1 Симуляция мира однопоточная, не зажимайте CPU

Обсчёт сущностей и симуляция мира в BDS в основном однопоточные, **плавность зависит от производительности одного ядра**, и чем больше карта, тем тяжелее. Сам контейнер создаёт мало накладных расходов, но **слишком низкая квота CPU для контейнера буквально заморит сервер голодом**: TPS падает, игроки лагают, чанки грузятся медленно.

```yaml
    cpus: "2.0"
```

:::warn Не ограничивайте CPU ради «экономии ресурсов»
Если вы точно не знаете, что ещё работает на этой машине, и не проводили нагрузочное тестирование, **не задавайте BDS-контейнеру лимит CPU** (например, `cpus: "0.5"`). Однопоточность BDS делает его очень чувствительным к частоте ядра и к «всегда доступному одному ядру». О тонкой настройке см. [Оптимизация производительности](/tutorials/java/optimize).
:::

По памяти:

```yaml
    mem_limit: "4g"
```

`mem_limit` — жёсткий предел: **если задать его ниже реальной потребности, контейнер убьёт OOM** (проявляется как перезапуск сервера без всяких причин). Если не уверены, сначала не ставьте лимит, понаблюдайте за фактическим потреблением через `docker stats` и потом решите.

:::warn Не освобождайте память принудительно
Потребление памяти BDS медленно растёт со временем, **не освобождайте память принудительно инструментами**: это приводит к зависанию полосы загрузки у игроков, скачивающих паки ресурсов/дополнительные паки. **Правильный способ — перезапустить сервер**, это совпадает с указаниями статьи [Сервер BDS](/tutorials/bedrock/bds).
:::

## 12. Диагностика проблем

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Контейнер **перезапускается по кругу** | EULA не принята, в `LEVEL_NAME` недопустимые символы, порт занят, не хватает памяти, неверный `VERSION` | Сначала посмотрите `docker compose logs --tail=200`: первый экран лога обычно прямо указывает причину |
| Сервер работает, но **никто не подключается** | Проброшен или открыт только TCP; в группе безопасности не открыт **UDP** | В `ports` укажите `"19132:19132/udp"` и откройте UDP 19132 в **группе безопасности облака**. Системный firewall на контейнеры не действует, см. предупреждение выше |
| В локальной сети подключается, из интернета нет | Проблема с пробросом портов/группой безопасности | См. [Развёртывание в доступной среде](/tutorials/java/deploy) и [Маршрутизатор и firewall](/tutorials/ops/router-firewall) |
| Мир «пропал», создалась новая карта | Изменён `LEVEL_NAME` или смонтирован не тот том | Верните прежнее имя `LEVEL_NAME`; проверьте, что смонтирован тот же том |
| Игроки видят сервер, но войти не могут | Версия клиента не совпадает с BDS, либо мешает белый список/проверка аккаунта | Зафиксируйте `VERSION`, проверьте `ALLOW_LIST` и `ONLINE_MODE` |
| Контейнер не может писать в `/data` (привязанное монтирование в Linux) | Владелец каталога на хосте не совпадает с пользователем в контейнере | Исправьте владельца каталога; при необходимости используйте способ сопоставления пользователей из документации образа |
| Сервер перезапускается без причины | Слишком низкий жёсткий предел памяти вызывает OOM | Увеличьте или снимите `mem_limit`, наблюдайте через `docker stats` |
| В консоли нельзя вводить текст | Не хватает `stdin_open: true` и `tty: true` | Добавьте их и пересоздайте контейнер |

Ежедневный осмотр (состояние контейнера, потребление CPU/памяти, свободное место на диске) лучше проводить вместе с [Мониторингом и оповещениями](/tutorials/ops/monitoring).
