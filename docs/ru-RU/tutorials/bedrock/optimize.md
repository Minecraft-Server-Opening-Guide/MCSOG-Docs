Подход к оптимизации Bedrock и Java Edition — это почти две разные дисциплины. В Java Edition есть плагины, есть `spark`, есть десятки настраиваемых параметров; у официального сервера Bedrock (BDS) **очень мало ручек**, да и названия многих ключей в разных версиях отличаются. Поэтому центр тяжести «оптимизации» в Bedrock — **дизайн мира** и **железо**, а не поиск по файлам конфигурации.

Эта статья только про официальный **BDS**. Если сервер ещё не запущен, начните с [Сервера BDS](/tutorials/bedrock/bds). Если вы используете стороннее ядро, сразу переходите к разделу 7.

## 1. Модель производительности Bedrock отличается от Java Edition

| Параметр сравнения | Java Edition (Paper и др.) | Bedrock (официальный BDS) |
| --- | --- | --- |
| Симуляция мира | Тик в главном потоке, но ядро даёт массу переключателей оптимизации | Симуляция мира в основном упирается в **один поток**, лишние ядра мало помогают |
| Экосистема плагинов | Крайне богатая, много оптимизаций делается плагинами | Официальный сервер **не поддерживает плагины**, их заменяют дополнительные паки и скриптовый API |
| Настраиваемые параметры | Конфигурация ядра плюс конфигурация плагинов, десятки пунктов | В `server.properties` по производительности всего несколько пунктов |
| Управление памятью | Задаётся вручную через `-Xmx` / `-Xms` | **Нет параметров памяти**, программа сама запрашивает её у ОС |
| Инструменты анализа | Пламенные графы `spark`, разные profiler'ы | **Нет `spark`** и нет зрелого процесса работы с пламенными графами |
| Горячая перезагрузка | В части случаев возможна | `/reload` не поддерживается, после правки конфигурации только перезапуск |

Самое важное: **предел задаёт частота одного ядра**:

- Симуляция мира идёт в одном потоке, а дополнительные ядра в основном берут на себя сеть, запись сохранений и другую периферийную работу;
- Поэтому машина «16 ядер 2.0 GHz» обычно проигрывает машине «4 ядра 4.5 GHz»;
- При выборе машины сначала смотрите на производительность одного ядра, потом на число ядер.
:::warn Опыт оптимизации Java Edition нельзя переносить
Перечисленного ниже на BDS **просто нет**, не повторяйте за руководствами по Java:

- Пламенные графы `spark` (BDS не поддерживается, подробности в разделе 8);
- Конфигурации `paper.yml`, `spigot.yml` от Paper / Spigot;
- Радиус активации сущностей, лимиты спавна, число сущностей на тик и подобные переключатели плагинов или ядер;
- Плагины оптимизации (в официальном сервере нет системы плагинов).

Переносить можно только **понятия**: меньше одновременно загруженных чанков, меньше сущностей, меньше высокочастотного редстоуна.
:::

## 2. Что можно настроить: `server.properties`
:::warn Какие есть ключи и каковы значения по умолчанию — зависит от версии BDS
В разных версиях BDS **имена ключей, диапазоны значений и значения по умолчанию в `server.properties` могут отличаться**: какие-то ключи появились позже, какие-то в некоторой версии переименованы или разбиты на несколько ключей (группа проверки перемещения — типичный пример).

Поэтому статья объясняет только, **что эти ключи делают** и чем приходится платить за их изменение. **Откройте `server.properties` в каталоге своего сервера и сверьте каждый пункт**: в официально сгенерированном файле над каждым ключом есть строка комментария с его смыслом, допустимым диапазоном и значением по умолчанию — именно она наиболее точна для вашей версии.
:::

### 2.1 Основные ключи производительности

| Ключ | Назначение | Цена снижения | Рекомендуемое направление |
| --- | --- | --- | --- |
| `view-distance` | Насколько далеко сервер отправляет игроку данные чанков, то есть «как далеко видит игрок» (официальное значение по умолчанию 32, нижняя граница диапазона 5) | Вдали появляется туман, рельеф «выскакивает», картинка ухудшается | **Первый пункт, который стоит трогать**: снижайте, если устройства игроков в целом слабые или узкая полоса |
| `tick-distance` | В каком радиусе вокруг игрока чанки **реально обсчитываются** (спавн мобов, посевы, редстоун, жидкости) (официальное значение по умолчанию 4, диапазон 4-12) | Дальние машины, фермы и редстоун-схемы могут остановиться | Влияет на CPU прямее, чем дальность прорисовки; если «дальние машины» не нужны, держите небольшим |
| `max-threads` | Сколько потоков сервер максимум пытается использовать (официальное значение по умолчанию 8, 0 означает без ограничения; в некоторых версиях удаление ключа даёт тот же эффект) | Слишком низкое значение может поставить в очередь сеть, сохранения и другие периферийные задачи | **Он не разносит симуляцию мира по ядрам**; больше — не значит быстрее, держите значение по умолчанию |
| `player-idle-timeout` | Через сколько минут бездействия игрока выкидывает | Афк-игроки отключаются раньше, это мешает тем, кто держит афк | Способ снизить нагрузку почти без побочных эффектов, задавайте по своим правилам афк |
| `compression-threshold` | С какого размера сетевой пакет начинает сжиматься | Ниже значение — больше пакетов сжимается, **больше ест CPU**, меньше трафик | Сначала найдите узкое место: узкая полоса — снижайте, нехватка CPU — повышайте |
| `compression-algorithm` | Алгоритм сжатия сети (обычно варианты вроде `zlib` / `snappy`) | Смена на алгоритм с меньшей степенью сжатия означает обмен трафика на CPU | При достаточной полосе берите более быстрый алгоритм, при узкой — с большей степенью сжатия |

Про эти пункты нужно прояснить три вещи:

1. `view-distance` и `tick-distance` — **две разные вещи**: первое определяет «видно или нет», второе — «считается или нет». Снижение дальности прорисовки влияет в основном на картинку, снижение дальности симуляции — на машины.
2. `max-threads` — это **предел числа потоков**, а не «переключатель параллельной симуляции мира». Увеличение не уберёт узкое место одного ядра.
3. `player-idle-timeout` — один из немногих пунктов снижения нагрузки **почти без побочных эффектов**: выкинули афк-игрока — меньше загруженных чанков и меньше обсчёта сущностей.

### 2.2 Ключи, связанные с проверкой перемещения и античитом

Эти ключи **не переключатели производительности**, но их часто трогают как «оптимизацию», поэтому разберём отдельно:

| Ключ | Назначение | Цена ослабления проверки | Рекомендуемое направление |
| --- | --- | --- | --- |
| `server-authoritative-movement` (в части версий) | Серверный авторитет перемещения, принимает одно из нескольких значений режима проверки; чем ближе к серверному авторитету, тем строже | Ослабление означает меньше коррекций позиции, но **больше пространства для читов** | На публичном сервере держите значение по умолчанию или строже |
| `server-authoritative-movement-strict` (в части версий) | Более строгая проверка позиции игрока, коррекции чаще | Отключение означает меньше дёрганья, но проход сквозь стены и телепорты труднее заметить | Не отключайте ради «экономии производительности» |
| `player-position-acceptance-threshold` | **Допуск** расхождения позиции клиента и сервера | Ниже значение — коррекции чаще, игроки с высоким пингом чаще «откатываются» | Ослабляйте немного только при повсеместно высоком пинге и частых откатах, ясно понимая, что это компромисс по безопасности |
:::warn Не считайте античит переключателем производительности
Коррекция позиции действительно создаёт сетевую нагрузку, но взамен даёт «игрок не может произвольно телепортироваться». Ослаблять проверку, чтобы сэкономить немного CPU или трафика, — типичный пример убыточного обмена. Только при **повсеместно высоком пинге и частых откатах** игроков стоит подумать о небольшой правке, и при этом понимать, чем вы платите.
:::

### 2.3 Другие возможные ключи

В разных версиях можно встретить ещё несколько ключей, связанных с производительностью, например:

- Переключатель, отдающий **генерацию видимых чанков** клиенту: сервер делает меньше работы, цена — более слабые клиенты лагают сильнее;
- Ключи, связанные с **журналом содержимого** и **сторожевым таймером** для дополнительных паков и скриптов: нужны, чтобы замечать ошибки скриптов, слишком медленные скрипты и превышение лимита памяти.

**Есть ли они, как называются и каковы значения по умолчанию — всё зависит от версии**, поэтому конкретные имена и числа здесь не приводятся: ориентируйтесь на свой локальный файл и официальную документацию. Перед использованием убедитесь, что в вашей версии эти ключи действительно есть, и не копируйте конфигурации других версий из интернета.

### 2.4 Пример фрагмента

```properties
# Дальность прорисовки: сначала снижайте, наблюдая за картинкой и CPU
view-distance=12

# Дальность симуляции: если дальние машины не нужны, держите небольшой
tick-distance=4

# Предел потоков: держите значение по умолчанию, не считайте его ускорителем
max-threads=8

# Кик за бездействие: задавайте по своим правилам афк
player-idle-timeout=15

# Сжатие: при узкой полосе оставьте по умолчанию, при нехватке CPU порог можно поднять
compression-threshold=1
compression-algorithm=zlib
```

Приведённые значения — **всего лишь пример**, это не значения по умолчанию и не рекомендация. Сверьтесь с комментариями в своём локальном файле и поставьте подходящие вам.
:::note После правки обязателен перезапуск
BDS не поддерживает `/reload`. После изменения `server.properties` нормально выключите сервер командой `stop` в консоли и запустите снова, не убивайте процесс.
:::

## 3. Главное: дизайн мира

В Bedrock **настроить можно мало, а построить — много**. Абсолютное большинство случаев «сервер лагает» в итоге сводится к карте:

| Источник нагрузки | Направление работы |
| --- | --- |
| Слишком много одновременно загруженных чанков | Снизить `view-distance` и `tick-distance`, свести постоянно загруженные области (ticking area) к минимуму |
| Слишком много постоянно загруженных машин | Каждая машина, которая «работает и без людей», постоянно ест CPU; ненужные разберите или остановите |
| Редстоун-часы работают постоянно | Высокочастотные часы — типичный источник нагрузки; если можно низкочастотное решение, не берите высокочастотное |
| Слишком много сущностей | Мобы, дроп, вагонетки накапливаются; ограничьте размер ферм, вовремя собирайте или убирайте дроп |
| Слишком большие фермы | Ферма, чей выход сильно превышает потребности, — чистая нагрузка; уменьшите масштаб или включайте по необходимости |
| Накопление дропа | Неудачный дизайн сбора и уничтожения оставляет сущности надолго |

Несколько пояснений:

- **Постоянно загруженная область (ticking area)** заставляет указанные чанки обсчитываться и без игроков. Это удобно, но каждая область постоянно ест CPU — **сделали дело, удаляйте**.
- **Накопление сущностей** имеет типичный симптом: общая загрузка CPU вроде невысокая, но весь сервер лагает. Тогда нужно заниматься числом сущностей и сложными чанками, а не искать очередной параметр.
- **Сначала вычитание**: разобрать три ненужные фермы обычно эффективнее, чем десять раз перебирать конфигурацию.
:::tip Сначала вычитание, потом параметры
В Bedrock первый инструмент «оптимизации» — **меньше строить, меньше гонять, меньше загружать**. Параметры помогают лишь в очень узком диапазоне.
:::

О подходах к диагностике сущностей и дропа можно почитать в [Лагах из-за накопления сущностей и дропа](/tutorials/faq/entity-lag). Но нужно предупредить: **инструменты диагностики в той статье — из Java Edition** (например, `spark`, метрики TPS и MSPT), в Bedrock они не работают; зато **принцип дизайна «меньше сущностей, меньше дропа, меньше постоянно загруженных машин» универсален**, и его можно взять напрямую.

### 3.1 Постоянно загруженные области и «офлайн-машины»

Постоянно загруженная область (ticking area) — редкий в Bedrock обоюдоострый инструмент:

- **Плюс**: когда игроков нет, редстоун, жидкости, посевы и мобы в указанных чанках продолжают обсчитываться, машины могут работать офлайн;
- **Цена**: эти чанки **постоянно** занимают время главного потока, независимо от того, есть ли игроки;
- **Рекомендация**: включайте только для действительно нужных областей и удаляйте, когда дело сделано; машины, которые можно перевести в режим «работает при игроках», не стоит держать постоянно загруженными.

При диагностике сначала задайте себе три вопроса: эта машина ещё нужна? Она обязана работать без людей? Её продукция действительно используется? Если хотя бы на один ответ «нет» — её пора выключать.

## 4. Чанки, размер мира и предгенерация

Дальность прорисовки и масштаб мира — два разных счёта:

- **Счёт дальности прорисовки**: чем больше `view-distance`, тем больше данных чанков нужно отправлять каждому игроку при входе, движении и переходе между областями, и CPU с трафиком растут вместе. Это самый большой рычаг по CPU и трафику, но одновременно и то, что игрок ощущает напрямую.
- **Счёт размера мира**: все исследованные игроками области записываются в сохранение. Чем больше и старше мир, тем больше каталог `worlds/`, **тем медленнее запуск, сохранение и резервное копирование**, и тем выше нагрузка на дисковый ввод-вывод.

Что можно сделать:

1. **Ограничить зону активности**: по идее «границы мира» держите игроков в нужных для игры областях, а не давайте миру бесконечно расти. Есть ли в вашей версии или ядре готовая команда границ и как её использовать — смотрите официальную документацию.
2. **Не поощрять бесцельные походы**: исследование карты само по себе постоянно генерирует новые чанки, а генерация новых чанков — частая причина лагов.
3. **Держать точку возрождения в порядке**: район вокруг точки возрождения обычно загружается чаще всего, поэтому построек, сущностей и редстоуна там должно быть как можно меньше.
4. **Периодически архивировать старые области**: неиспользуемые миры или области вовремя убирайте, но перед операцией **сначала сделайте резервную копию**.

Про **предгенерацию** скажем честно: **в официальном BDS нет инструмента предгенерации**, доступных вариантов гораздо меньше, чем в Java Edition.

| Способ | Поддерживает ли официальный BDS | Описание |
| --- | --- | --- |
| Встроенная команда предгенерации | Нет | В официальном сервере такой команды нет |
| Заранее пробежать карту администратором | Да (это обычное игровое поведение) | Надёжнее всего, без зависимостей, минус — время |
| Постоянно загруженные области | Да | Решают «обсчёт без игроков», а **не** предгенерацию, и постоянно расходуют производительность |
| Инструменты Java Edition (например, Chunky) | BDS не поддерживается | Такие инструменты рассчитаны на серверы Java Edition и модовые платформы |
| Сторонние инструменты предгенерации | Вне официальных возможностей | Перед использованием убедитесь, что инструмент поддерживает вашу версию BDS, и **сначала сделайте резервную копию мира** |
:::warn Не верьте в «предгенерацию для Bedrock в один клик»
То, что в интернете называют «плагинами или инструментами предгенерации» для Bedrock, в большинстве случаев относится к сторонним ядрам или инструментам сообщества и **не входит в возможности официального BDS**. Если используете — опирайтесь на их собственную официальную документацию, не угадывайте по этой статье или описаниям других версий.
:::

Возможности предгенерации в Bedrock ограничены, полагаться можно в основном на **заранее пробеганную карту** и **контроль масштаба мира**.

## 5. Поведение памяти

Поведение памяти в Bedrock совершенно не такое, как в Java Edition:

- **Нет параметров памяти**. В BDS нет переключателей вроде `-Xmx`: начальный и максимальный объём программа запрашивает у ОС сама, задать их в параметрах запуска нельзя.
- **Потребление медленно растёт со временем**. После долгой работы оно заметно выше, чем сразу после запуска, — это повсеместно наблюдаемое явление.
- **Не освобождайте память принудительно**. Если давить на потребление инструментами «очистки памяти» и «принудительного освобождения», **у игроков зависнет полоса загрузки при скачивании паков ресурсов или дополнительных паков**, а сервер может стать нестабильным. **Решение — перезапуск**, это совпадает с указаниями в статье [Сервер BDS](/tutorials/bedrock/bds).

Правильный подход — **запланировать перезапуски**:

| Подход | Описание |
| --- | --- |
| Плановый перезапуск | Один перезапуск в часы низкой нагрузки возвращает системе накопившуюся память |
| Период перезапуска | **Официальных рекомендаций нет**, это вопрос суждения: смотрите на число игроков, размер мира, количество дополнительных паков и кривую роста памяти. Кто-то делает раз в день, кто-то раз в несколько дней |
| Аккуратная остановка | Нормально выключите сервер командой `stop` в консоли и запустите снова, чтобы не повредить сохранения и файлы статистики |
| Заранее предупредить | **Перед перезапуском сообщите игрокам в игре и в чате** и оставьте запас времени, чтобы игроков не выкинуло посреди исследования карты или боя |
:::tip Как определить интервал перезапуска
Не копируйте чужое «перезапускать три раза в день». Сначала несколько дней ведите записи: через сколько после запуска память вырастает до неприемлемого уровня, когда игроков больше всего. **Больше игроков и паков — интервал короче; маленький сервер с малым числом паков — интервал может быть длиннее.**
:::

## 6. Выбор железа и хостинга

Первый принцип железа для Bedrock всё тот же — **приоритет производительности одного ядра**:

| Приоритет | Пункт | Почему |
| --- | --- | --- |
| 1 | Частота и производительность одного ядра | Симуляция мира в одном потоке, слабое ядро напрямую определяет наличие лагов |
| 2 | SSD или NVMe | Чтение и запись чанков, сохранение, резервные копии — всё это дисковый ввод-вывод; механический диск и сетевое хранилище заметно тормозят |
| 3 | Объём памяти | Нужен запас; чем больше игроков, мир и паков, тем больше нужно |
| 4 | Число ядер | Полезно, но после трёх пунктов выше |

Почему «дешёвый VPS непонятно почему лагает»:

- В дешёвых тарифах обычно **низкочастотный, многоядерный, перепроданный и разделяемый** CPU. BDS ест одно ядро, а разделяемый CPU отбирают соседи — отсюда периодические лаги и дрожание задержки;
- Экземпляры «с burst-производительностью» обычно выглядят свободными, но как только кредит CPU исчерпан, всё замедляется разом;
- Механический диск или сетевое хранилище замедляют чтение и запись чанков, что заметнее всего при исследовании карты;
- При нехватке памяти система начинает свопинг, и картина — «весь сервер дёргается».
:::warn Контейнеры и виртуализация дополнительно отбирают CPU
Если вы запускаете BDS в контейнере или виртуальной машине, **лимит CPU (limit / quota) может заморить BDS голодом**: когда одно ядро загружено полностью, его начинают троттлить, и это проявляется периодическими «подвисаниями». Дайте достаточную долю CPU и не ставьте BDS на одну машину с другими тяжёлыми сервисами. Детали развёртывания в Docker — в статье [Развёртывание сервера Bedrock в Docker](/tutorials/bedrock/docker).
:::

### 6.1 Краткий справочник по хостингу

| Ваша ситуация | Рекомендация |
| --- | --- |
| Игроков немного, бюджет ограничен | Машина с сильным одним ядром обычно стабильнее многоядерного перепроданного VPS |
| Нужна долгая работа, есть постоянные игроки | Берите тариф с явно указанной частотой CPU и без перепродажи; сначала попробуйте в малом масштабе, потом расширяйтесь |
| Развёртывание в контейнере | Дайте достаточную долю CPU, не ставьте рядом с тяжёлыми сервисами, следите за портами и томами данных, см. [Развёртывание сервера Bedrock в Docker](/tutorials/bedrock/docker) |
| Нужна экосистема плагинов | Тогда это уже не путь BDS, сначала посмотрите раздел 7 |

## 7. Различия производительности сторонних ядер

Если вам нужны плагины и многоядерность, то это уже не путь BDS:

| Ядро | Язык | Особенности производительности |
| --- | --- | --- |
| Семейство Nukkit (включая PowerNukkitX) | Java | Ставка на многоядерность и оптимизацию, есть система плагинов и масса настраиваемых пунктов |
| PocketMine-MP | PHP | Самая большая экосистема плагинов, но под высокой нагрузкой узкое место заметно, сам интерпретируемый язык создаёт накладные расходы |

Их модель производительности, параметры конфигурации и доступные инструменты отличаются от BDS, **опыт оптимизации нельзя переносить между ними**. Например, `spark` поддерживает Nukkit, но **не поддерживает BDS**; копирование статей по тюнингу PMMP или Nukkit на BDS обычно даёт только пустую трату времени.
:::warn Сначала определите, какой путь вам нужен
Выбрать BDS — значит «официально, стабильно, мало настраиваемых пунктов»; выбрать стороннее ядро — значит «много плагинов, много настраиваемых пунктов, но не официальная реализация». О компромиссах и начале работы см. [Сторонние ядра (Nukkit / PNX / PMMP)](/tutorials/bedrock/third-party) и [Начало работы со сторонними ядрами Bedrock](/tutorials/bedrock/third-party-setup).
:::

## 8. Как измерять

Сразу проясним: **в Bedrock нет `spark`**. `spark` поддерживает ряд платформ Java Edition и часть платформ сообщества, **Bedrock Dedicated Server в их число не входит**. Поэтому на BDS не надейтесь на пламенные графы и не копируйте процесс Java Edition «смотреть TPS и MSPT».

Доступные средства:

| Средство | Как использовать |
| --- | --- |
| Мониторинг на уровне хоста | Смотрите CPU (особенно **загрузку одного ядра**), память, дисковый ввод-вывод, сетевой трафик. Как это делать — в [Мониторинге и оповещениях](/tutorials/ops/monitoring) |
| Вывод консоли BDS | Сообщения запуска и остановки, ошибки, предупреждения по дополнительным пакам и скриптам |
| Обратная связь игроков | «Когда лагает, сколько человек онлайн, в какой области лагает» часто прямее любых метрик |
| Сравнение до и после изменения | Меняйте по одному пункту, записывайте загрузку CPU и ощущения игроков до и после |
:::note Меняйте по одному пункту за раз
Без пламенных графов единственный надёжный способ — **контролируемые переменные**: изменили один пункт, понаблюдали сопоставимое время, записали, перешли к следующему. Изменив пять пунктов сразу, вы никогда не узнаете, какой из них помог или навредил.
:::

Дисциплину измерений рекомендуем такую:

1. **Меняйте только одну переменную**, остальное оставляйте неизменным;
2. **Измеряйте в сопоставимые периоды**: то же время суток, похожее число игроков онлайн, похожий геймплей (например, все исследуют карту или все в афк);
3. **Записывайте в журнал**: что изменили, когда, метрики и ощущения игроков до и после;
4. **Наблюдайте достаточно долго**: такие явления, как генерация чанков и рост памяти, требуют времени, чтобы проявиться; поспешный вывод сразу после изменения легко ошибочен.

Простой пример записи на уровне хоста (Linux, только для иллюстрации):

```bash
# Каждые 5 секунд снимаем общую и поядерную нагрузку, чтобы заметить «общая невысокая, но одно ядро загружено полностью»
top -b -d 5 -n 60 > cpu-sample.log
```

В Windows то же самое можно смотреть в диспетчере задач или мониторе производительности, **важен график одного ядра, а не общая загрузка**.

## 9. Порядок тюнинга

Делайте в этом порядке — так выгоднее всего; обратный порядок легко приводит к пустым тратам:

1. **Дизайн мира**: сначала вычитание — меньше загрузки, меньше постоянно загруженных машин, остановить ненужные фермы, сдержать редстоун-часы, контролировать сущности и дроп. Наибольшая отдача и бесплатно.
2. **Дальность прорисовки и симуляции**: настройте `view-distance`, `tick-distance`, `player-idle-timeout` и ключи сжатия. Почти бесплатно и сразу заметно.
3. **Железо**: приоритет производительности одного ядра, затем память, SSD, число ядер. Стоит денег, но работает.
4. **План перезапусков**: определите подходящий вам период и предупредите заранее. Лечит симптом, но решает проблему накопления памяти за долгую работу.
5. **Смена ядра**: только когда первые четыре пункта сделаны и вам действительно нужны плагины или многоядерность, думайте о семействе Nukkit или PMMP.

### 9.1 Финальный чек-лист

| # | Пункт проверки | Критерий выполнения |
| --- | --- | --- |
| 1 | Понятно, какие ключи есть в вашей версии | Открыт локальный `server.properties`, сверены имена ключей и значения по умолчанию |
| 2 | Дизайн мира | Ненужные фермы и машины остановлены, постоянно загруженные области очищены, высокочастотный редстоун сдержан |
| 3 | Дальность прорисовки и симуляции | `view-distance` и `tick-distance` настроены под устройства игроков и полосу и не сломали машины |
| 4 | Афк и сжатие | `player-idle-timeout` задан, ключи сжатия настроены под направление узкого места |
| 5 | Железо | Если узкое место в одном ядре или дисковом вводе-выводе — решено в первую очередь; у контейнера достаточно доли CPU |
| 6 | План перезапусков | Есть период, есть предупреждение, выключение аккуратное через `stop` |
| 7 | Записи измерений | По каждому изменению есть записи до и после, и менялся только один пункт |
| 8 | Античит | Проверка перемещения не ослаблена ради производительности либо риск явно принят |

Оптимизация Bedrock в итоге сводится к трём фразам: **частота одного ядра определяет верхний предел, дизайн мира определяет нижний, плановые перезапуски определяют долгосрочную стабильность.**
