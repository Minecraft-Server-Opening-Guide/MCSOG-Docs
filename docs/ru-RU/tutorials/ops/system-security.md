[Основы сетевой безопасности](/tutorials/ops/network-security) отвечают на вопрос «может ли кто-то снаружи войти». Эта статья про другое направление: **предположим, кто-то уже вошёл (или вы сами ошиблись) — сколько выдержит эта машина.**

Цель укрепления системы — не «абсолютная безопасность» (её не существует), а **сужение прав, сокращение входов и оставление следов**, чтобы одна ошибка не превращалась в захват всей машины.

## 1. Аккаунты и права

### 1.1 Почему ни в коем случае нельзя запускать сервер от root

| Риск запуска от root | Конкретные последствия |
| --- | --- |
| **Уязвимость сразу равна захвату машины** | После эксплуатации уязвимости сервера, плагина или мода атакующий наследует права root и может менять системные файлы, ставить бэкдоры, уничтожить все данные |
| **Плагин — сторонний код** | Скачанный с форума jar работает с теми же правами, что и сервер. **Запуск от root означает, что вы отдали всю машину незнакомому автору.** |
| **Ошибочную команду не отменить** | Ошибочная команда удаления с неверным путём под обычным пользователем максимум уничтожит каталог сервера; под root — может уничтожить всю систему |
| **Путаница владельцев файлов** | Созданные root `world/`, журналы и конфигурация обычному пользователю недоступны, и каждая процедура обслуживания требует `sudo`, что в итоге формирует привычку «всё делать от root» |

:::warn Запуск панели от root не означает, что и сервер должен работать от root
Многие панели работают с высокими правами для удобства управления и запускают сервер за вас. **Это вопрос границы доверия панели и не является основанием для «сервер должен работать от root».** Если панель позволяет указать пользователя запуска, укажите выделенного пользователя.
:::

### 1.2 Создание выделенного системного пользователя

```bash
sudo useradd -r -m -d /opt/mcserver mcserver
```

| Параметр | Действие |
| --- | --- |
| `-r` | Создать **системного пользователя** (UID из системного диапазона, обычно без пароля и без срока действия) |
| `-m` | Одновременно создать домашний каталог (`-r` по умолчанию **не** создаёт его, нужно указать явно) |
| `-d /opt/mcserver` | Назначить домашним каталогом `/opt/mcserver` |
| `mcserver` | Имя пользователя |

**Создание каталогов и передача их во владение**:

```bash
sudo mkdir -p /opt/mcserver/survival /opt/mcserver/backups
sudo chown -R mcserver:mcserver /opt/mcserver
sudo chmod 750 /opt/mcserver
```

`chown -R` меняет владельца и группу каталога и **уже существующего содержимого** на `mcserver` (используйте `-R` только когда нужна рекурсия); `chmod 750` даёт владельцу чтение, запись и выполнение, группе — чтение и выполнение, остальным — ничего. Проверьте пользователя и владельца каталога через `id mcserver` и `ls -ld /opt/mcserver`.

:::tip Запретить выделенному пользователю вход
Если аккаунт нужен только для запуска службы и интерактивный вход не требуется, можно запретить ему shell:

```bash
sudo usermod -s /usr/sbin/nologin mcserver
```

**Учтите**: `nologin` блокирует и такие способы переключения, как `sudo -iu mcserver`. Если вам всё же нужно заходить под ним для обслуживания, используйте `/bin/bash` и контроль по ключам и правам либо временно верните shell. **Путь к `nologin` в системе может быть `/usr/sbin/nologin` или `/sbin/nologin`, проверьте перед изменением.**
:::

### 1.3 Осознанное использование sudo

Ценность `sudo` в том, что **каждое повышение прав оставляет след** (пишется в системный журнал) и можно точно ограничить, «какой пользователь может выполнять только такие-то команды».

- **Не делайте `sudo su -` и не оставайтесь в нём надолго**. Так теряется слой записей «какая команда кем и когда выполнена».
- **Повышайте права по необходимости**: для одной команды — `sudo команда`, а не целая сессия под root.
- **Редактируйте sudoers через `visudo`**. Он проверяет синтаксис; правка `/etc/sudoers` напрямую с одной ошибкой может лишить всех возможности повышать права.

```bash
sudo visudo
```

**Рекомендуемый подход**: не менять основной `/etc/sudoers`, а положить отдельный фрагмент в `/etc/sudoers.d/` и редактировать его через `sudo visudo -f /etc/sudoers.d/mcadmin`, чтобы получить проверку синтаксиса. Во фрагменте можно ограничить вплоть до команд, например разрешить конкретному администратору только перезапуск сервера:

```
mcadmin ALL=(root) /usr/bin/systemctl restart minecraft
mcadmin ALL=(root) /usr/bin/systemctl status minecraft
```

**Аудит тех, у кого есть sudo**:

```bash
getent group sudo    # группа sudo в Debian / Ubuntu
getent group wheel   # группа wheel в RHEL
sudo grep -rHv '^#\|^$' /etc/sudoers /etc/sudoers.d/
```

:::warn Проверяйте регулярно, а не настраивайте и забывайте
**Ушедшие администраторы, друзья, помогавшие временно, аккаунты, добавленные на ранних тестах**, остаются в группе sudo надолго. Рекомендуется периодически проверять и удалять тех, кому больше не нужно (`sudo deluser имя sudo` или `sudo gpasswd -d имя wheel`).
:::

### 1.4 Отключение ненужных аккаунтов

- **Проверьте все аккаунты с возможностью входа** (настоящий вход — это аккаунт, получивший shell):

```bash
awk -F: '$7 !~ /(nologin|false)$/ {print $1, $3, $7}' /etc/passwd
```

- **Заблокируйте ненужные аккаунты**:

```bash
sudo usermod -L имя          # заблокировать пароль
sudo usermod -s /usr/sbin/nologin имя   # заодно запретить вход
```

- **Отдельно проверьте**: аккаунт с UID `0` в `/etc/passwd` **должен быть только `root`**. Всё лишнее — бэкдор:

```bash
awk -F: '$3 == 0 {print $1}' /etc/passwd
```

## 2. Права на файлы: минимальные права на уровне каталогов

### 2.1 Сначала разберём биты прав

Первый столбец вывода `ls -l`, например `-rwxr-x---`, делится на три группы: **владелец / группа / остальные**, по три бита в каждой (чтение `r`=4, запись `w`=2, выполнение `x`=1).

| Права | Число | Когда подходят |
| --- | --- | --- |
| `rwx------` | `700` | Приватный каталог, доступный только владельцу |
| `rwxr-x---` | `750` | Корень сервера: владелец пишет, группа входит, остальные не видят ничего |
| `rw-r-----` | `640` | Файл конфигурации: владелец читает и пишет, группа только читает |
| `rw-------` | `600` | **Файлы с паролями**, доступны только владельцу |
| `rwxrwxrwx` | `777` | **Не использовать никогда** |

### 2.2 Почему `777` опасны

`chmod -R 777` — самое распространённое «универсальное решение» из интернета: увидел `Permission denied` — ставь 777. Фактический смысл: **любой пользователь системы и любой взломанный процесс службы может читать, изменять и удалять всё в этом каталоге.**

| Последствие | Пояснение |
| --- | --- |
| **Любой локальный аккаунт может изменить сервер** | Взломанная служба с низкими правами (например, какое-то веб-приложение) может подложить бэкдор-jar в `plugins/`, и он сработает после следующего перезапуска |
| **Файлы с паролями видны всем** | Пароль RCON в `server.properties` и пароль базы в `.env` открыты |
| **Сохранения можно разрушить произвольно** | Любой процесс может удалить `world/` |
| **Настоящая проблема скрыта** | Причина ошибки прав обычно в «неверном владельце», а `777` лишь закрывает симптом, проблема остаётся |

:::warn Правильное исправление — не ослабить права, а исправить владельца
При `Permission denied` сначала посмотрите, **кто работает и какой файл нужно изменить**:

```bash
ls -l /opt/mcserver/survival/server.properties
```

Если владелец `root`, а служба работает под `mcserver`, правильно так:

```bash
sudo chown mcserver:mcserver /opt/mcserver/survival/server.properties
```

**А не** `chmod 777`. **Рекурсивное изменение прав (`chmod -R 777`) на сервере — опасная операция, не выполняйте её.**
:::

### 2.3 Рекомендуемые права каталога сервера

```bash
# Весь каталог сервера принадлежит выделенному пользователю
sudo chown -R mcserver:mcserver /opt/mcserver

# Владельцу всё; группе чтение и вход; остальным ничего
sudo chmod -R u=rwX,g=rX,o= /opt/mcserver

# Самому каталогу не давайте прав остальным
sudo chmod 750 /opt/mcserver
```

`u=rwX,g=rX,o=` — **символьный режим**: `X` (заглавная) означает «добавить право выполнения только каталогам или файлам, у которых оно уже есть», что лучше соответствует принципу «файл не должен быть исполняемым», чем бездумный `-R 755`. **Не используйте `chmod -R 777` и не давайте на каталоге сервера `o+w` (запись для остальных).**

### 2.4 Что защищать в первую очередь

| Объект | Почему | Рекомендация |
| --- | --- | --- |
| `world/`, `world_nether/`, `world_the_end/` | Сохранения — всё, что вложили игроки; разрушенное не вернуть | Владелец `mcserver`, остальным никаких прав; **регулярная офлайн-копия** (см. раздел 5) |
| `server.properties` | Содержит пароль RCON, порты, `online-mode` и другие важные переключатели | `640`, владелец `mcserver` |
| `.env`, скрипты с паролями | Пароли баз, API Key | **`600`**, только владелец читает и пишет |
| `ops.json`, `whitelist.json` | Определяют, кто получает права администратора | `640`, после изменений проверяйте содержимое |
| Файлы приватных ключей (`id_ed25519` и др.) | Утечка равна передаче права входа | **`600`**, каталог `.ssh` — `700` |
| Файлы резервных копий | Часто содержат полные пароли и сохранения | **Не класть в каталог, доступный из веба**; одна копия в другом месте |

```bash
# Файл учётных данных только для владельца
chmod 600 /opt/mcserver/survival/.env
ls -l /opt/mcserver/survival/.env
# Ожидается: -rw------- 1 mcserver mcserver ... .env
```

:::note Копии меняют права, при восстановлении возвращайте владельца
Копируйте способами, **сохраняющими атрибуты** (`cp -a`, `tar`, `rsync -a`), тогда после восстановления владелец и права будут правильными. Если скопировать только содержимое, после восстановления владельцем может стать root, и сервер снова не сможет писать сохранения — проверьте через `ls -ld` после восстановления.
:::

## 3. Обновление системы

**Подавляющее большинство взломов использует уязвимости, «уже исправленные, но у вас не пропатченные».** Поддержание обновлений — самое выгодное из всех мер укрепления.

### 3.1 Идея автоматизации обновлений безопасности

Идея автоматических обновлений: **патчи безопасности ставятся сами, остальные обновления решаете вы**.

| Дистрибутив | Инструмент | Файлы конфигурации |
| --- | --- | --- |
| Ubuntu / Debian | `unattended-upgrades` | `/etc/apt/apt.conf.d/20auto-upgrades`, `/etc/apt/apt.conf.d/50unattended-upgrades` |
| RHEL / Rocky / AlmaLinux / Fedora | `dnf-automatic` | `/etc/dnf/automatic.conf` |

**Ubuntu / Debian**:

```bash
sudo apt update
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

Типичное содержимое `20auto-upgrades`:

```ini
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
```

- `Update-Package-Lists "1"`: обновлять индекс пакетов раз в день.
- `Unattended-Upgrade "1"`: ежедневно автоматически ставить подходящие обновления (**по умолчанию только обновления безопасности**, конкретный диапазон определяется `Unattended-Upgrade::Allowed-Origins` в `50unattended-upgrades`).

**RHEL**:

```bash
sudo dnf install -y dnf-automatic
sudo systemctl enable --now dnf-automatic.timer
```

Частые настройки в `/etc/dnf/automatic.conf`, связанные с «только обновления безопасности, применять автоматически»:

```ini
[commands]
upgrade_type = security
apply_updates = yes
```

**Проверка, что работает**: `systemctl status unattended-upgrades` (Debian / Ubuntu) или `systemctl status dnf-automatic.timer` (RHEL).

:::warn Конкретные параметры и значения по умолчанию зависят от версии
Выше приведены лишь частые варианты. **В разных дистрибутивах и версиях имена файлов конфигурации, имена опций и диапазон по умолчанию могут различаться** (например, «включать ли не-безопасные обновления», «удалять ли автоматически старые ядра»). Перед изменением сверьтесь с официальной документацией вашей версии и убедитесь через `systemctl status`, что служба действительно работает. **Настроено не значит работает.**
:::

### 3.2 Не включайте слепую автоперезагрузку

Автоматическая **установка** патчей и **перезагрузка** — разные вещи. Обновления ядра, glibc, systemd **вступают в силу только после перезагрузки**. **Не включайте безусловную автоперезагрузку**, потому что:

- **На игровом сервере есть игроки**. Ночная перезагрузка отключит играющих, может потерять прогресс и вызвать проблемы с сохранениями.
- **Неудачная перезагрузка равна долгому простою**. Если новое ядро несовместимо с вашими драйверами или окружением, машина не запустится, и вы можете узнать об этом только на следующий день.
- **После перезагрузки сервер не обязательно поднимется сам**. Это зависит от того, `enable` ли служба (см. раздел 4).

**Рекомендуемая практика**:

| Практика | Пояснение |
| --- | --- |
| **Окно обслуживания** | Фиксированный период с минимумом игроков (например, ночь вторника), объявленный заранее, с ручной перезагрузкой |
| **Сначала предупредить, потом перезагружать** | Транслировать обратный отсчёт командой сервера, чтобы игроки вышли безопасно |
| **Сохранять старое ядро** | Не удаляйте старые ядра автоматически, при проблеме можно откатиться |
| **Сразу проверить после перезагрузки** | Работает ли служба, доступен ли порт, нет ли ошибок в журнале |

Проверить, ожидается ли перезагрузка, можно через `[ -f /var/run/reboot-required ] && cat /var/run/reboot-required` (Debian / Ubuntu) или `sudo dnf needs-restarting -r` (RHEL).

:::tip Сначала перезагрузите один раз и убедитесь, что машина поднимается сама
Вручную перезагрузите машину **без игроков** и проверьте, что «автозапуск службы при включении» действительно работает. **Непроверенный автозапуск равен его отсутствию.**
:::

## 4. Укрепление службы (systemd)

### 4.1 Базовый unit

`/etc/systemd/system/minecraft.service`:

```ini
[Unit]
Description=Minecraft Server
After=network.target

[Service]
Type=simple
User=mcserver
Group=mcserver
WorkingDirectory=/opt/mcserver/survival
ExecStart=/usr/lib/jvm/java-21-openjdk-amd64/bin/java -Xms2G -Xmx4G -jar server.jar nogui
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

| Директива | Действие |
| --- | --- |
| `User=` / `Group=` | **Запуск под выделенным пользователем**. Если не указать, по умолчанию запускается от root — самая частая дыра в укреплении. |
| `WorkingDirectory=` | Рабочий каталог сервера. Относительные пути (`world/`, `plugins/`) считаются от него. |
| `ExecStart=` | Команда запуска. **Обязательно абсолютный путь**, systemd не разбирает `PATH`. |
| `Restart=on-failure` | Перезапуск при аварийном выходе. Обычный `stop` его не вызывает. |
| `RestartSec=10` | Ждать 10 секунд перед перезапуском, чтобы при падении не было шквала попыток. |

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
```

:::note В существующих руководствах unit использует screen
Пример в [Подготовке среды](/tutorials/java/environment) использует `screen`, чтобы сохранить консоль для ввода команд в игру. **Оба варианта допустимы**; в примере статьи используется `Type=simple` с прямым запуском процесса Java, что лучше сочетается с опциями укрепления ниже. **Учтите: при сочетании `screen` с такими мерами, как `ProtectSystem=strict`, нужно убедиться, что каталог сокета, нужный `screen`, доступен для записи.**
:::

### 4.2 Ограничение ресурсов

Ограничение ресурсов защищает и от «утечка памяти утянет всю машину», и от «при атаке машина будет загружена полностью».

```ini
[Service]
LimitNOFILE=65535
MemoryMax=6G
```

| Директива | Действие | Замечание |
| --- | --- | --- |
| `LimitNOFILE` | Предел числа открытых файловых дескрипторов | При большом числе игроков и загрузке чанков значения по умолчанию может не хватить, проявляется как «в соединении отказано» или странные ошибки ввода-вывода |
| `MemoryMax` | **Жёсткий предел памяти** службы | При превышении ядро убивает процесс по OOM. **Должен быть заметно больше `-Xmx`**, потому что сам JVM, metaspace, стеки потоков и прямая память находятся вне этого предела |

:::warn `MemoryMax` меньше `-Xmx` — типичная ошибка
`-Xmx4G` ограничивает только кучу Java. У сервера Minecraft с кучей 4G **резидентная память может доходить до 5G и выше**. Если поставить `MemoryMax` равным `4G`, служба будет снова и снова убиваться и перезапускаться, а в журнале вы увидите только «процесс внезапно исчез».

**Рекомендация**: оставляйте в `MemoryMax` не менее 30 % запаса (например, `-Xmx4G` с `MemoryMax=6G`) и смотрите фактическое потребление в `systemctl status`, прежде чем корректировать.
:::

### 4.3 Ограничение прав и защита файловой системы

Эти директивы позволяют службе **трогать только то, что ей положено**. Даже если сервер или плагин взломан, масштаб разрушений ограничен.

```ini
[Service]
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/opt/mcserver/survival
```

| Директива | Действие |
| --- | --- |
| `NoNewPrivileges=yes` | Запрещает процессу повышать права через setuid / setgid программы. **Мера почти без побочных эффектов, добавляйте везде.** |
| `PrivateTmp=yes` | Даёт службе **собственные `/tmp` и `/var/tmp`**, она не видит и не влияет на временные файлы других процессов |
| `ProtectSystem=strict` | Монтирует **всю файловую систему только для чтения** (кроме `/dev`, `/proc`, `/sys`). Служба может писать только по путям из `ReadWritePaths` |
| `ProtectHome=yes` | Делает `/home`, `/root`, `/run/user` **невидимыми** для службы (как пустые каталоги) |
| `ReadWritePaths=` | Вместе с `ProtectSystem=strict` **явно перечисляет разрешённые для записи пути**. **Без этой строки сервер не сможет записать даже сохранения.** |

:::warn Если после `ProtectSystem=strict` служба не поднимается, смотрите сюда
Частые причины:

1. **Забыли `ReadWritePaths`** или указали неверный путь (нужен абсолютный и совпадающий с `WorkingDirectory`).
2. **Скрипт копирования или плагин пишет в другое место** (например, `/var/log`, `/srv`), его нужно добавить в `ReadWritePaths`.
3. **Java нужно писать во временный каталог**: `PrivateTmp=yes` обычно достаточно, но если сервер явно настроен на фиксированный временный путь, его тоже нужно добавить.

**Как разбираться**: `sudo systemctl status minecraft` и `sudo journalctl -u minecraft -n 100` прямо покажут путь, на котором «в доступе отказано».
:::

:::note Доступность опций укрепления зависит от версии systemd
Приведённые директивы доступны в сравнительно новых systemd, но **конкретная поддержка зависит от версии**. Через `systemd-analyze security minecraft.service` можно посмотреть фактически действующие настройки песочницы: он даёт оценку «степени открытости» и пояснения по пунктам, что надёжнее добавления директив наугад. Критерии оценки и имена пунктов в разных версиях могут отличаться, **ориентируйтесь на фактический вывод в вашей системе**.
:::

## 5. Резервное копирование тоже средство безопасности

Предыдущие разделы защищают от «систему взяли под контроль», но есть два класса угроз, **против которых не помогает никакое укрепление**:

| Угроза | Проявление |
| --- | --- |
| **Шифровальщик** | Шифрует все файлы, к которым у вас есть доступ. **Копии на той же машине будут зашифрованы вместе с ними.** |
| **Внутреннее разрушение или ошибка** | Администратор или плагин с одной командой `rm -rf`, либо злонамеренный «партнёр», удаливший данные и ушедший |

**Вывод: смысл резервных копий не только в «защите от поломки железа», это единственное средство против вымогательства и разрушения — при условии, что копия лежит там, куда атакующий не дотянется.**

| Принцип | Как делать |
| --- | --- |
| **Офлайн** | Хотя бы одна копия на носителе, который **обычно не смонтирован и не подключён к сети** (внешний диск, снимок объектного хранилища) |
| **Другое место** | При поломке локального диска или аварии в дата-центре локальные копии исчезнут вместе с ним |
| **Версионность** | Если хранить только последнюю копию, случай «сохранение давно испорчено, но не замечено» не решается |
| **Права** | В копиях обычно есть полные пароли и сохранения, **не кладите их в каталог, доступный из веба**, права закрывайте по разделу 2 |

Конкретные действия (согласованное копирование, `save-off` / `save-on`, политика хранения, порядок восстановления) — см. [Резервное копирование и восстановление](/tutorials/java/backup). **Копия без проверенного восстановления не считается копией.**

:::warn Не давайте службе право записи в каталог копий
Если процесс сервера (или загруженный им плагин) может писать в каталог копий, то взломанный плагин **удалит или зашифрует все ваши копии**. Держите каталог копий вне каталога сервера и **не давайте сервисному аккаунту право записи в него**.
:::

## 6. Аудит и повседневная гигиена

Укрепление — не разовое действие. Проверки ниже рекомендуется **выполнять регулярно**, а как минимум после каждого изменения системы.

### 6.1 Чек-лист и команды

| Пункт проверки | Команда | Ожидаемый результат |
| --- | --- | --- |
| **Прослушиваемые порты** | `sudo ss -tlnp` | Слушают только известные вам службы; незнакомые порты нужно выяснить |
| **Прослушивание UDP** | `sudo ss -ulnp` | То же (Bedrock / Geyser используют UDP) |
| **Неудачные входы** | `sudo lastb \| head` | Множество записей означает перебор (нужен root; часть систем по умолчанию не ведёт учёт) |
| **Успешные входы** | `last -n 20` | Нет незнакомых пользователей или исходных IP |
| **Аккаунты с UID 0** | `awk -F: '$3 == 0 {print $1}' /etc/passwd` | Только `root` |
| **Аккаунты с возможностью входа** | `awk -F: '$7 !~ /(nologin\|false)$/ {print $1, $7}' /etc/passwd` | Только известные вам люди |
| **Права sudo** | `getent group sudo` / `getent group wheel` | Нет ушедших или временных аккаунтов |
| **Задачи по расписанию** | `sudo crontab -l`, `ls -l /etc/cron.*`, `systemctl list-timers --all` | Нет задач, которых вы не создавали |
| **Юниты systemd** | `systemctl list-units --type=service --state=running` | Нет незнакомых служб |
| **Неиспользуемые пакеты** | `sudo apt autoremove --dry-run` / `sudo dnf autoremove` | Убедитесь, что удаляется действительно ненужное |
| **Оценка песочницы службы** | `systemd-analyze security minecraft.service` | Чем ниже оценка, тем лучше; смотрите рекомендации по пунктам |

:::warn К незнакомым записям относитесь серьёзно
- **Задачи cron или юниты systemd, которых вы не создавали**: возможен бэкдор для закрепления, а возможно, их принёс какой-то пакет — **сначала выясните происхождение, потом решайте, удалять ли**.
- **Незнакомый прослушиваемый порт**: сначала `sudo ss -tlnp` найдите PID процесса, затем `ps -p PID -o pid,user,cmd` посмотрите, что это.
- **Незнакомый аккаунт**: не удаляйте сразу, посмотрите домашний каталог, `authorized_keys` и записи входов, чтобы понять, не использовали ли его уже.
:::

### 6.2 Минимизация поверхности установки

**Чем меньше установлено ПО, тем меньше уязвимостей можно использовать.**

- **Не устанавливайте графическое окружение**. Установка десктопа на облачном сервере тянет массу ненужных служб и портов (см. [Выбор операционной системы](/tutorials/java/os)).
- **Не устанавливайте ненужные службы**: FTP, Samba, службы печати, базы данных (если сервер их не использует).
- **Проверяйте состояние служб**: ненужные должны быть `disable` и `stop`, а не «установлены, но не запущены» — их может поднять цепочка зависимостей. Смотрите через `systemctl is-enabled имя`, отключайте через `sudo systemctl disable --now имя`.

### 6.3 Быстрая шпаргалка на одну страницу

- [ ] Сервер работает под **выделенным пользователем**, не от root (проверьте через `ps -o user,cmd -C java` или `systemctl status`)
- [ ] Владелец каталога сервера верный, **нет 777**
- [ ] Права файлов с паролями — **600**, они не в веб-каталоге и не в репозитории Git
- [ ] Автоматические обновления безопасности включены и **подтверждено, что работают**; безусловная автоперезагрузка **не** включена
- [ ] В unit systemd заданы `User=`, `WorkingDirectory=`, `Restart=`
- [ ] Настроен `LimitNOFILE`, и `MemoryMax` **заметно больше** `-Xmx`
- [ ] По необходимости включены `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem`, `ReadWritePaths`
- [ ] Машина хотя бы раз перезагружена, подтверждён **автозапуск службы**
- [ ] Есть **офлайн-копия или копия в другом месте**, и сервисный аккаунт **не может писать** в каталог копий
- [ ] Команды аудита выше включены в регулярную проверку
