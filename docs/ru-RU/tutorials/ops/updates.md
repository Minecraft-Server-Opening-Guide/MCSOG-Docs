«Обновление» — самое рутинное и самое аварийное действие в эксплуатации. Неудачная установка плагина максимум лишает функции, **неудачное обновление может сделать сохранения неоткрываемыми**. Статья связывает обновление ядра сервера, плагинов, модов и MCDR в повторяемую процедуру, где важно не «нажать Далее», а **путь отхода, оставленный на каждом шаге**.

Перед началом рекомендуется прочитать две статьи: [Резервное копирование и восстановление](/tutorials/java/backup) (до обновления нужно уметь делать копии и восстанавливаться) и [Структура сервера](/tutorials/java/structure) (понимать, какие именно файлы вы трогаете).

## 1. Железные правила обновления

Шесть пунктов ниже упорядочены по важности. **Пропуск любого из них может превратить «десятиминутное обновление» в «целый день спасения».**

### 1.1 Сначала копия, и копия проверенная

Копия — это не «упаковал и всё», нужно убедиться, что она **действительно рабочая**: файл существует, размер разумный, содержимое перечисляется, а лучше один раз реально распаковать в тестовом каталоге.

```bash
# Linux: убедиться, что архив есть, размер разумный, содержимое перечисляется
ls -lh /opt/mcserver/backups/world-20261004.tar.gz
tar -tzf /opt/mcserver/backups/world-20261004.tar.gz | head
```

```powershell
# Windows: распаковать во временный каталог и убедиться в полноте содержимого
Get-Item C:\mcserver\backups\world-20261004.zip | Select-Object Name, Length, LastWriteTime
Expand-Archive -Path C:\mcserver\backups\world-20261004.zip -DestinationPath C:\mcserver\verify -Force
Get-ChildItem C:\mcserver\verify | Select-Object Name
```

:::warn Непроверенная копия не считается копией
«Скрипт копирования давно падает», «архив пустой», «скопировали только `db/`, а `level.dat` забыли» — всё это выясняется в день настоящей аварии. **Как минимум раз в месяц реально восстанавливайтесь**, порядок — в [Резервном копировании и восстановлении](/tutorials/java/backup).
:::

### 1.2 Читайте журнал обновлений

В журнале обновлений искать нужно четыре вещи, а не красоту номера версии:

| Что искать | Почему важно |
| --- | --- |
| **Ломающие изменения** | Переименование ключей конфигурации, команд, изменение формата данных сразу делают текущую конфигурацию нерабочей |
| **Новые минимальные требования** | Версии Java для сервера и плагинов, версия загрузчика, версии зависимых плагинов |
| **Инструкции по миграции данных** | Нужно ли вручную выполнять команды миграции, нужно ли сначала обновиться до промежуточной версии |
| **Известные проблемы** | Признанные автором баги, которые позволяют обойти только что выпущенную плохую версию |

### 1.3 Сначала попробовать на отдельном экземпляре

Подготовьте «тестовый экземпляр»: другой каталог, другой порт, другая копия мира. **Любое обновление сначала проходит на тестовом экземпляре, и только потом трогает продакшен.**

```bash
# Linux: развернуть тестовый экземпляр прямо из копии
mkdir -p /opt/mcserver/test
tar -xzf /opt/mcserver/backups/full-20261004.tar.gz -C /opt/mcserver/test
```

```powershell
# Windows: аналогично
New-Item -ItemType Directory -Force -Path C:\mcserver\test
Expand-Archive -Path C:\mcserver\backups\full-20261004.zip -DestinationPath C:\mcserver\test -Force
```

В тестовом экземпляре нужно поменять порт (`server-port` в `server.properties`), иначе он будет бороться за тот же порт с работающим сервером.

### 1.4 Выберите окно обслуживания

Выберите время с минимумом игроков (обычно ночь или утро рабочего дня), избегайте соревнований и стартов новых миров, **заложите двойное время** и убедитесь, что при проблеме вы сами будете на месте — только когда кто-то смотрит в консоль, возможен своевременный откат.

### 1.5 Всегда оставляйте путь отката

**Ключевой принцип: любой заменённый файл сохраняется под именем с номером версии.**

```text
server-1.21.1.jar            # старое ядро, можно вернуть в любой момент
MyPlugin-1.0.0.jar.bak       # старый плагин
world-20261004/              # копия мира до обновления
config.yml.20261004.bak      # конфигурация до обновления
```

:::tip Путь отката нужно продумать до обновления
Перед обновлением спросите себя: «если через десять минут мне нужно будет откатиться, какие именно команды я выполню?» **Не можете ответить — не обновляйтесь.**
:::

### 1.6 Объявите простой заранее

Сообщите в чате группы, на доске объявлений, в MOTD сервера: во сколько начнётся, сколько ожидается, что обновится, что делать при проблемах. Игроки больше всего не любят не простой, а **непонимание, почему не заходят и сколько ждать**.

### 1.7 Ситуации, в которых могут возникнуть проблемы

| Риск | Типичное проявление | Последствия | Профилактика |
| --- | --- | --- | --- |
| Мир перезаписан новой версией | Новая версия запускалась один раз, после возврата старого ядра сохранение выдаёт ошибку или не загружается | **Необратимо**, остаётся откат к копии | Перед первым запуском новой версии сделать полную копию и сохранить старое ядро и старый каталог |
| Несовпадение версии Java | Падение сразу при запуске, в журнале `UnsupportedClassVersionError` | Служба не поднимается | Согласовать Java по таблице раздела 2.2 |
| Плагин несовместим с новым ядром | Красный текст в `/plugins` или `NoSuchMethodError` в консоли | Пропадает функциональность, вплоть до невозможности запуска | Сначала посмотреть поддерживаемые версии и журнал обновлений плагина, сначала попробовать на тестовом экземпляре |
| Ключ конфигурации переименован или удалён | Плагин создаёт конфигурацию по умолчанию, прежние настройки «исчезают» | Функции работают по умолчанию, влияя на игроков | Перед обновлением скопировать каталог конфигурации, после обновления сверить по пунктам |
| Мод не соответствует загрузчику | Падение при запуске, в журнале имя мода и ошибка класса | Модовое ядро вообще не поднимается | Согласовать загрузчик, версию игры и моды вместе |
| Несовпадение протокола Bedrock | После обновления сервера игроки не заходят, просят обновить клиент | Отток игроков, игроки iOS не могут откатиться | До обновления убедиться, что клиенты игроков смогут обновиться |
| Скачан подменённый файл | Ядро или плагин работает, но ведёт себя странно | Инцидент безопасности | Скачивать только с официальных или официально одобренных страниц релизов |
| Неверно оценено окно обслуживания | Игроки уже спрашивают в чате «почему не заходят» | Потеря репутации и доверия | Заложить двойное время, объявить заранее |
| Диск заполнен | Распаковка не удалась или сохранение не пишется | Повреждение сохранений | До обновления проверить свободное место |
| Изменились права и владелец | В Linux у новых файлов владелец root, пользователь сервера не может писать | Конфигурация плагина не сохраняется | После обновления сделать `chown -R` на выделенного пользователя сервера |

## 2. Обновление ядра сервера

### 2.1 Общая процедура

1. **Остановить сервер**. В консоли выполнить `stop`, дождаться нормального выхода, **не убивайте процесс**.
2. **Записать текущую версию** (версия ядра, номер сборки, имя jar в скрипте запуска).
3. **Переименовать старое ядро для страховки**, добавив суффикс версии.
4. **Скачать новое ядро из официального источника**, не берите jar из сторонних сборок.
5. **Положить новое ядро**, имя файла должно совпадать с ожидаемым в скрипте запуска (иначе скрипт не найдёт файл; о написании скрипта запуска — см. [Запуск сервера](/tutorials/java/start)).
6. **Запустить и смотреть в консоль**, не уходите сразу после запуска.
7. **Проверить**: в консоли нет ошибок, `/plugins` в порядке, сами зайдите на сервер и пройдитесь, и **понаблюдайте некоторое время**, прежде чем решать об удалении старого jar.

```text
stop
```

```bash
# Linux
cd /opt/mcserver/survival
mv server.jar server-1.21.1.jar                 # переименовать старое ядро для страховки
cp ~/downloads/server-1.21.4.jar ./server.jar   # заменить файлом с официальной страницы загрузки
./start.sh
```

```powershell
# Windows
Set-Location C:\mcserver\survival
Rename-Item server.jar server-1.21.1.jar
Copy-Item "$env:USERPROFILE\Downloads\server-1.21.4.jar" .\server.jar
.\start.bat
```

Проверки после входа на сервер:

```text
/version        посмотреть версию сервера
/plugins        посмотреть состояние загрузки плагинов (красный — сбой загрузки)
```

:::tip Старое ядро пока не удаляйте
Оставьте его хотя бы до момента «новая версия отработала полный цикл обслуживания и мир в порядке». Один jar на несколько сотен MB в обмен на возможность откатиться в любой момент.
:::

### 2.2 Прыжок через версии не бесплатен: сначала согласуйте Java

**При несовпадении версии Java сервер падает при запуске**, в журнале появляется `UnsupportedClassVersionError`. Таблица ниже согласована с [Подготовкой среды (Windows и Linux)](/tutorials/java/environment) и используется повторно:

| Minecraft Java Edition | Требуемая официально Java | Пояснение |
| --- | --- | --- |
| 26.1 и новее | **Java 25** | Новейшее требование (с 26.1) |
| 1.20.5 – 1.21.x | **Java 21** | 1.20.5 — первый стабильный релиз, требующий 21 |
| 1.18 – 1.20.4 | **Java 17** | Самое распространённое сочетание |
| 1.17 – 1.17.1 | **Java 16** | С Java 17 тоже нормально запускается |
| 1.12 – 1.16.5 | **Java 8** | Множество старых сборок до сих пор здесь |
| 1.7.10 и раньше | Официально требования ниже | На практике обычно используют Java 8 |

:::note Источник таблицы
Границы 1.20.5 / 1.18 / 1.17 / 1.12 взяты из официального списка версий Mojang (поле `javaVersion.majorVersion` каждой версии на `piston-meta.mojang.com`); требование Java 25 с 26.1 — из списка требований к версиям Minecraft Wiki. Это не эмпирические догадки.
:::

- **Требования Paper, Purpur, Spigot, Fabric, Forge совпадают с официальными**: для 1.20.5 и новее нужна Java 21, для 1.18 – 1.20.4 — Java 17.
- Таблица выше — **минимальные требования**; при слишком высокой версии Java часть плагинов и модов может быть несовместима, **рекомендуется строго следовать требованию**.
- **Bedrock (BDS) Java не нужна**, это программа на C++, запускается напрямую `bedrock_server` (в Windows — `bedrock_server.exe`).

**Через несколько крупных версий не перескакивайте одним шагом.** Промежуточные версии могли изменить формат конфигурации, формат мира и API плагинов; при необходимости обновляйтесь по одной версии (например, 1.19 → 1.20 → 1.21), проверяя после каждого шага.

### 2.3 Формат мира: обновление почти всегда в одну сторону

:::warn Мир, открытый новой версией, не гарантированно откроется в старой
После запуска сервера новой версией данные чанков и сущностей в мире могли быть **перезаписаны в новом формате**. При возврате ядра на старую версию в лучшем случае журнал засыплет ошибками, в худшем **мир не загрузится**. Это односторонний процесс, официального инструмента «преобразовать обратно в старый формат» нет.
:::

Поэтому:

- Перед первым запуском новой версии **сделайте полную копию** (`world/`, `world_nether/`, `world_the_end/`, для своих имён миров — по `level-name` из `server.properties`).
- При откате **откатывайте вместе с миром**: **одновременно** с возвратом старого ядра перезапишите мир копией до обновления, а не только верните jar.
- Чтобы проверить совместимость заранее, запускайте новую версию на тестовом экземпляре, **не на продакшен-мире**.

### 2.4 Paper / Purpur / Leaves / Leaf

Обновление этих ядер одинаково: **заменить jar**. Они используют тот же формат мира, что и официальная ваниль, поэтому вывод раздела 2.3 действует и здесь.

Обратить внимание нужно только на конфигурацию:

| Ситуация | Пояснение |
| --- | --- |
| В конфигурации появились новые ключи | При первом запуске ядро **дописывает недостающие ключи значениями по умолчанию** в файл конфигурации |
| Ключ удалён или переименован | Старый ключ может сохраниться, но перестать действовать, либо игнорироваться; поведение может тихо измениться |
| Изменился номер сборки | Разные сборки одной версии игры тоже могут менять поведение, почитайте журнал сборки |

Практика: перед обновлением скопировать весь каталог сервера (как минимум все `*.yml`), после обновления сравнить различия.

```bash
# Linux: сравнить конфигурацию до и после обновления
diff -u paper-global.yml.bak paper-global.yml
```

```powershell
# Windows: сравнить конфигурацию до и после обновления
Compare-Object (Get-Content .\paper-global.yml.bak) (Get-Content .\paper-global.yml)
```

:::tip Официальные источники
Paper — <https://papermc.io/>, Purpur — <https://purpurmc.org/>. Для Leaves, Leaf и подобных ядер ориентируйтесь на их официальные страницы релизов, **не берите jar с агрегаторов и файлообменников**.
:::

### 2.5 Fabric / Forge / NeoForge

Модовое ядро «зажато» жёстче плагинного: **версия загрузчика, версия игры и каждый мод должны соответствовать друг другу**.

| Компонент | Чему должен соответствовать | Симптом несоответствия |
| --- | --- | --- |
| Загрузчик (Fabric / Forge / NeoForge) | Привязан к версии игры, поддерживает только определённый диапазон версий | Загрузчик не устанавливается или сервер не запускается |
| Каждый мод | Соответствие версии игры, версии загрузчика и других модов, от которых он зависит | Падение при запуске, в журнале имя мода и ошибка класса |
| Моды сервера и клиента | Моды, требующие установки с обеих сторон, должны совпадать | Игрок не может войти или его сразу выкидывает после входа |

**Обновление загрузчика обычно требует обновления модов**: моды скомпилированы под API загрузчика конкретной версии. Типичный симптом — **падение при запуске**, в журнале видно имя мода вместе с ошибкой класса, например `NoClassDefFoundError`, `ClassNotFoundException`, `NoSuchMethodError`; в семействе Forge также прямо сообщается об отсутствии обязательных зависимостей (`Missing or unsupported mandatory dependencies`), а клиент может сообщить о несовместимости набора модов.

Рекомендуемый порядок обновления:

1. Сначала убедитесь, что для целевой версии игры есть доступная версия загрузчика.
2. На тестовом экземпляре обновите загрузчик и убедитесь, что он запускается (моды можно пока убрать все).
3. Возвращайте моды партиями (после каждой партии запускайте, чтобы понять, какой мод виноват), в конце обновите сервер и клиент вместе, выровняв список модов с обеих сторон.

### 2.6 Bedrock BDS

Ограничения версий у Bedrock отличаются от Java Edition: **протокол клиента должен совпадать со сборкой сервера**, при смене протокола старый клиент просто не подключится (принцип — см. [Версии протокола и выбор версии](/tutorials/bedrock/protocol)).

| Пункт | Пояснение |
| --- | --- |
| Протокол клиента | После обновления сервера игроки должны использовать клиент соответствующей версии; при несовпадении будет предложено обновиться |
| Ограничение iOS | Игроки на iOS **могут установить только последнюю версию из магазина**, конкретную старую версию поставить нельзя. Поэтому «зафиксировать старую версию» означает отказаться от игроков на iOS |
| Расположение сохранений | Все сохранения BDS находятся в `worlds/`, **перед обновлением обязательно копировать целиком** |
| Файлы конфигурации | `server.properties`, `allowlist.json`, `permissions.json`, `valid_known_packs.json` — ваши данные, новый пакет не должен их перезаписывать |

Шаги обновления: взять со страницы официальных загрузок архив для соответствующей платформы, **распаковать во временный каталог** и взять только исполняемый файл, положив его в прежний каталог.

```bash
# Linux: распаковать во временный каталог, заменить только бинарник (имя файла — под реальную версию)
unzip bedrock-server-new.zip -d /tmp/bds-new
mv bedrock_server bedrock_server-old
cp /tmp/bds-new/bedrock_server .
chmod +x bedrock_server
```

```powershell
# Windows: аналогично (в архиве есть сопутствующие DLL, не забудьте их скопировать)
Expand-Archive -Path "$env:USERPROFILE\Downloads\bedrock-server-new.zip" -DestinationPath C:\bds-new -Force
Rename-Item .\bedrock_server.exe bedrock_server-old.exe
Copy-Item C:\bds-new\bedrock_server.exe .
```

:::warn Не распаковывайте архив целиком поверх каталога
В официальном архиве есть и своя копия `server.properties`, `allowlist.json`, `permissions.json` и других файлов. **Распаковка целиком перезапишет вашу конфигурацию и белый список.** Берите только файлы программы, данные и конфигурацию оставляйте как есть и убедитесь, что `worlds/` не заменён.
:::

Структура каталогов и ограничения версий загрузчиков — см. [Сервер BDS](/tutorials/bedrock/bds): сторонние загрузчики тоже поддерживают только определённые диапазоны версий, **перед обновлением сервера убедитесь, что загрузчик уже догнал**.

### 2.7 Понижение версии: самая частая потеря данных по вине человека

:::warn После того как мир открыт новой версией, понижение ядра равно потере данных
«После обновления выяснилось, что плагин несовместим, скорее вернуть старое ядро» — самое частое самоповреждение в эксплуатации. **Ядро вернуть можно, мир — не всегда.**
Правильно так: **одновременно** с возвратом ядра откатить мир полной копией до обновления; заменить только jar, не тронув мир, — значит, скорее всего, получить неоткрываемое сохранение.
:::

Если после обновления действительно нужно понижение, порядок такой:

1. Остановить сервер.
2. Переименовать **текущий** (перезаписанный новой версией) каталог мира для страховки, не удалять — это доказательство для разбора.
3. Распаковать копию мира до обновления и вернуть на место.
4. Вернуть старый jar ядра.
5. Запустить, проверить журнал и сохранения.
6. Дать игрокам подтвердить, что ключевые постройки и предметы в порядке.

## 3. Обновление плагинов

Плагины обновляются чаще ядра и легче ломаются из-за **изменений структуры конфигурации**. Базовые операции — см. [Введение в плагины](/tutorials/java/plugins).

### 3.1 Четыре проверки перед обновлением

| Пункт проверки | Где смотреть | Что будет, если не посмотреть |
| --- | --- | --- |
| Поддерживаемые версии сервера | Список совместимых версий на странице релиза плагина | Сбой загрузки, красный текст в `/plugins` |
| Поддерживаемые версии Java | Страница релиза или журнал обновлений плагина | При загрузке ошибка версии класса |
| Наличие и свежесть зависимостей | Requires / Dependencies в описании плагина, см. [Частые плагины-зависимости](/tutorials/java/plugin-deps) | При отсутствии жёсткой зависимости плагин сразу не загрузится |
| Ломающие изменения в журнале обновлений | changelog / release notes на странице релиза | Конфигурация не действует, данные не мигрированы |

Самые часто требуемые зависимости — **Vault, PlaceholderAPI, ProtocolLib, LuckPerms**: их множество плагинов использует как жёсткую или мягкую зависимость, перед обновлением убедитесь, что они на месте и версии подходят.

### 3.2 Процедура

1. **Остановить сервер** (или явно принять границы возможностей горячей перезагрузки, см. 3.5).
2. **Скопировать** каталог `plugins/<plugin-name>/`; для плагинов с базой данных скопировать и базу.
3. **Переименовать старый jar для страховки**, добавив номер версии.
4. **Положить новый jar**.
5. **Запустить, посмотреть консоль**.
6. **Проверить состояние через `/plugins`** (красный означает, что плагин распознан, но не загрузился), затем **проверить собственные команды плагина**, чтобы убедиться, что функции действительно работают.

```powershell
# Windows
Set-Location C:\mcserver\survival\plugins
Rename-Item MyPlugin-1.0.0.jar MyPlugin-1.0.0.jar.bak
Copy-Item "$env:USERPROFILE\Downloads\MyPlugin-1.1.0.jar" .
```

```bash
# Linux
cd /opt/mcserver/survival/plugins
mv MyPlugin-1.0.0.jar MyPlugin-1.0.0.jar.bak
cp ~/downloads/MyPlugin-1.1.0.jar .
```

```text
/plugins
```

:::note Красные строки — сначала в консоль
Причина сбоя загрузки обязательно печатается в консоли и в `logs/latest.log`. **Откройте журнал и найдите имя плагина** — это намного быстрее, чем описывать в чате «мой плагин покраснел».
:::

### 3.3 Миграция конфигурации

| Ситуация | Рекомендация |
| --- | --- |
| Просто добавились параметры | Дайте плагину сгенерировать значения по умолчанию, обычно вмешательство не нужно |
| Ключ переименован или конфигурация перестроена | **Сохраните копию старой конфигурации** и перенесите по пунктам по журналу обновлений |
| Конфигурация разбита на несколько файлов | Тоже сохраните старые файлы и переносите по официальным указаниям |
| Нужна миграция данных (база, данные игроков) | Выполняйте по официальной инструкции по миграции, **сначала скопируйте базу** |

:::tip Пусть плагин сначала сгенерирует конфигурацию по умолчанию
Надёжнее, чем вручную сливать два YAML: **сначала дать новой версии сгенерировать полную конфигурацию по умолчанию**, а затем перенести в неё свои значения по пунктам. При ручном слиянии легко ошибиться в отступах, дублирующихся ключах и типах (строка против числа), а сообщения об ошибках YAML обычно трудно понять.
:::

### 3.4 Приоритет зависимостей: сначала обновляйте зависимости

**Сначала обновляйте зависимости, потом зависящие от них плагины.** Если сделать наоборот, получите `NoSuchMethodError` / `NoClassDefFoundError` — «интерфейс зависимости уже изменился, а верхний плагин всё ещё вызывает старый».

Так же, если какой-то плагин служит зависимостью для нескольких, одно его обновление может повлиять сразу на несколько плагинов, и после обновления нужно пройтись по всем связанным функциям.

### 3.5 Менеджеры плагинов: что могут и чего не могут

«Плагины для управления плагинами» вроде PlugManX и ServerUtils умеют загружать, выгружать и перезагружать другие плагины на работающем сервере. Их **границы возможностей** чёткие:

| Ситуация | Решается ли горячей перезагрузкой |
| --- | --- |
| Изменена только конфигурация | Достаточно `reload` самого плагина |
| Временно отключить проблемный плагин | Да, это самое ценное применение горячей перезагрузки |
| Сменить версию плагина (заменить jar) | Не рекомендуется, следует остановить сервер и заменить |
| Плагин регистрирует команды, права, слушатели, рецепты, генераторы мира | После выгрузки часто остаются остатки, перезагрузка легко ломается |
| Плагин держит соединения с базой, пул потоков или крупный статический кеш | После выгрузки ресурсы обычно не освобождаются |
| Многократная загрузка и выгрузка одного плагина | Загрузчик классов не освобождается, память постоянно растёт |
| Модовое ядро | Менеджер плагинов не управляет модами |
| Ванильный `/reload` сервера | Не рекомендуется, легко приводит состояние плагинов в беспорядок |

:::warn На продакшене не полагайтесь только на горячую перезагрузку
Горячая перезагрузка подходит, чтобы «временно отключить плагин и посмотреть, исчезла ли проблема», и для быстрой проверки конфигурации. **Настоящее обновление версий и изменение зависимостей всё равно должно идти через остановку и перезапуск.** Подробнее о чистке — см. [Управление плагинами и очистка](/tutorials/java/plugin-manage).
:::

### 3.6 Скачивайте только из официальных источников

:::warn Не используйте jar из неофициальных перепаковок
Плагины «с переводом», «взломанные», «сборные» с агрегаторов, файлообменников и из файлов чатов могли быть перепакованы. **Имя файла и версия те же, содержимое может быть другим.**
Предпочитайте официальные страницы релизов: SpigotMC, Modrinth, Hangar, GitHub Releases самого автора. Если предоставлен хеш — сверяйте хеш; платные плагины покупайте на официальной странице.
:::

## 4. Обновление MCDR

MCDR (MCDReforged) — менеджер, обёрнутый вокруг ядра сервера, написанный на Python 3. Его обновление **не трогает ядро сервера и мир**, риск в основном в **его собственной конфигурации и Python-плагинах**. Базовые понятия — см. [Менеджер сервера MCDR](/tutorials/java/mcdr).

### 4.1 Способ установки: через pip, а не из zip исходников

MCDR опубликован на PyPI, официальная документация предписывает установку через pip:

```bash
# Windows
pip install mcdreforged

# Linux
pip3 install mcdreforged
```

:::warn Не скачивайте zip исходников для запуска
Во многих руководствах в интернете предлагается скачать архив с GitHub и распаковать — **официальная документация прямо называет это устаревшим подходом**. С начала 2021 года, с версии v1.0, MCDR больше не устанавливается из исходников. Если вы не разработчик MCDR и не понимаете точно, что делаете, устанавливайте через pip.
:::

### 4.2 Требования к версии Python

Соответствие по официальной документации:

| Версия MCDR | Зависимость от Python |
| --- | --- |
| < 2.10 | >= 3.6 |
| >= 2.10 | >= 3.8 |
| >= 2.15 | **>= 3.9** |

Перед обновлением MCDR убедитесь, что ваша версия Python соответствует требованиям целевой версии; если системный Python слишком старый, сначала обновите Python (или используйте рекомендованный в официальной документации способ с изолированным окружением).

### 4.3 Команда обновления

**Обновляйте тем интерпретатором, который запускает MCDR**; конкретная команда зависит от того, как он был установлен:

```bash
# Глобальный pip (Windows, -U это --upgrade)
pip install mcdreforged -U

# Глобальный pip (Linux)
pip3 install mcdreforged -U

# Изолированное окружение под управлением pipx
pipx upgrade mcdreforged

# Виртуальное окружение: сначала активировать, потом обновлять
# source venv/bin/activate        (POSIX)
# venv\Scripts\Activate.ps1       (Windows PowerShell)
pip install mcdreforged -U
```

Проверка версии, вывод вида `MCDReforged v2.16.0`:

```bash
mcdreforged -V
```

:::warn Обновиться может не та копия, которой пользуется MCDR
Если в системе одновременно есть системный Python, виртуальное окружение и окружение pipx, `pip install -U` обновит не обязательно ту копию, которую реально использует MCDR — **после обновления `mcdreforged -V` показывает старую версию, обычно именно по этой причине**. Сначала выясните, как запускается MCDR (какой интерпретатор, какое окружение), и обновляйте в этом окружении.
:::

:::note Другие способы установки
- **pipx**: обновление через `pipx upgrade mcdreforged`; установка Python-зависимостей для него — `pipx inject mcdreforged <пакет>`.
- **Docker**: сменить тег образа по официальной документации образа, конкретная запись — по разделу Docker официальной документации.
- **Китайская сеть**: можно добавить в команду `-i https://pypi.tuna.tsinghua.edu.cn/simple` для ускорения через зеркало, это официально рекомендованный способ.
- **Системный менеджер пакетов**: официальная документация **крайне не рекомендует** устанавливать MCDR через него, потому что трудно управлять зависимостями плагинов.
:::

### 4.4 Перед обновлением крупной версии прочитайте руководство по миграции

В официальной документации есть отдельный раздел «Руководство по миграции» с двумя частями: **0.x к 1.x** и **1.x к 2.x**.

Крупное обновление может изменить формат конфигурации (опции в старом `config.yml` переименованы или устарели), API плагинов (плагины MCDR на старом API могут не загрузиться или вести себя странно), а также команды и интерфейс командной строки (параметры запуска, подкоманды могут измениться). **Поэтому обновление MCDR часто означает и обновление плагинов MCDR.** Перед обновлением прочитайте соответствующий документ по миграции и выполняйте по его шагам, не копируйте старые руководства по памяти.

### 4.5 Что копировать перед обновлением

| Содержимое | Расположение |
| --- | --- |
| Собственная конфигурация MCDR | `config.yml` в **рабочем каталоге MCDR** |
| Плагины MCDR | По умолчанию в `plugins/`, фактически — по параметру `plugin_directories` |
| Файлы прав и журналы | Полезны при разборе, рекомендуется сохранить |

:::note MCDR сам дописывает параметры конфигурации
Официальная документация указывает: при запуске MCDR загружает `config.yml` и **дописывает недостающие опции** в конец файла; если файла конфигурации нет, генерирует конфигурацию по умолчанию и выходит. Поэтому появление новых ключей после обновления — нормально, но **не** считайте из-за этого, что старая конфигурация корректно мигрирована: сверяйтесь с руководством по миграции и журналом обновлений.
:::

У MCDR есть также параметр `check_update` (по умолчанию `true`), который проверяет обновления каждые 24 часа; на ходу можно перезагрузить конфигурацию через `!!MCDR reload config` (сокращённо `!!MCDR r cfg`). **Основной риск обновления MCDR — совместимость плагинов**, а не сам MCDR.

### 4.6 Откат

При проблемах можно зафиксировать MCDR на предыдущей версии:

```bash
# Сначала на странице проекта mcdreforged на PyPI уточните конкретную версию для отката
pip install mcdreforged==2.15.0
mcdreforged -V
```

- **Номер версии обязательно проверьте на PyPI**, не пишите по памяти; в окружении pipx можно переустановить через `pipx install --force mcdreforged==<версия>` (конкретная запись — по официальной документации pipx).
- Если при обновлении обновлялись и плагины MCDR, **плагины тоже нужно откатить**, иначе новые плагины со старым MCDR дадут те же ошибки.

## 5. Чек-лист обновления

| Объект обновления | До обновления | Проверка после | Способ отката |
| --- | --- | --- | --- |
| **Ядро сервера** | Полная копия (мир + конфигурация + плагины); проверка требуемой Java целевой версии; переименование старого jar для страховки; чтение журнала обновлений | В консоли нет ошибок; `/plugins` в порядке; `/version` верный; сами зайдите на сервер; наблюдайте 10–30 минут | Остановить сервер, вернуть старый jar; если новая версия уже запускалась, **откатить мир из копии** |
| **Плагин** | Копия `plugins/<plugin-name>/` и базы; проверка поддерживаемых версий сервера, Java и зависимостей; чтение ломающих изменений в журнале | В `/plugins` нет красного; в консоли нет `NoSuchMethodError` и подобных; команды плагина работают; пройтись по функциям | Остановить сервер, вернуть старый `.jar.bak` на место; конфигурацию тоже откатить к копии |
| **Моды и загрузчик** | Копия `mods/` и `config/`; проверка поддержки загрузчиком целевой версии игры; список целевых версий каждого мода | Запуск без падения; в журнале нет ошибок классов модов; клиент может войти без сообщений об отсутствующих модах | Вернуть старый загрузчик и старый каталог `mods/`; клиент откатить синхронно |
| **MCDR** | Записать текущую версию (`mcdreforged -V`); копия `config.yml` и каталога плагинов; для крупной версии сначала прочитать руководство по миграции | `mcdreforged -V` показывает новую версию; MCDR запускается и поднимает сервер; плагины MCDR загружаются нормально | `pip install mcdreforged==<старая версия>` (версия — по PyPI); плагины MCDR откатить синхронно |
| **Пакеты ОС** | Записать текущие версии; убедиться, что не в окне обслуживания; при возможности сделать снимок системы или образ | После перезагрузки сервер поднимается сам; **убедиться, что Java не обновилась заодно**; порты и правила брандмауэра не изменились | Откат версии средствами дистрибутива или из снимка системы; при необходимости зафиксировать пакет Java (например, `apt-mark hold`) |

### Рекомендуемый ритм обслуживания

**Раз в месяц** плановая проверка ядра, плагинов, модов, MCDR и системных пакетов; **безопасность в приоритете** (проверка входа, права, античит — обновлять как можно скорее при наличии исправлений); **без необходимости не обновляйте** — версию, которая стабильно работает и не имеет проблем безопасности, можно не трогать, выгода обновления должна быть больше риска; каждое обновление **фиксируйте в записи** (когда, с какой версии на какую, кто делал, был ли откат), чтобы при следующей проблеме быстро восстановить картину.
