Панель не открывается, браузер сообщает «ваше подключение не защищено», веб-карта пустая — в таких авариях **довольно часто причина одна: истёк сертификат.** Это сбой, который в принципе можно полностью исключить: у сертификата есть точная дата окончания, и его можно продлевать автоматически.

Статья объясняет три вещи: **что именно защищает TLS (и что не защищает)**, **чем отличаются сертификат и приватный ключ**, **как сделать продление таким, чтобы его никогда не приходилось помнить**. О безопасности самой панели — см. [Использование панелей управления и их безопасность](/tutorials/ops/panels), об оповещениях об истечении сертификата — см. [Мониторинг и оповещения](/tutorials/ops/monitoring).
:::warn Конфигурация в статье — по официальной документации
Приведённые ниже **имена пакетов, параметры команд, ключи конфигурации, пути по умолчанию и структура каталогов меняются вместе с дистрибутивом, способом установки и версией ПО**. Примеры показывают, «что настраивать», а **не являются готовыми к копированию решениями**. Перед внедрением сверьтесь с официальной документацией certbot, Let's Encrypt, nginx и вашего дистрибутива, а также с файлами, которые реально создаются в вашей системе.

## 1. Сначала очертим границы: игровой трафик — это не HTTPS

Это самое частое и самое устойчивое недоразумение:

| Трафик | Протокол | Порт по умолчанию | Нужен ли сертификат TLS |
| --- | --- | --- | --- |
| Игровой трафик Java Edition | Собственный TCP-протокол Minecraft | 25565 | **Не нужен, сертификат на него не влияет** |
| Игровой трафик Bedrock | UDP (RakNet) | 19132 | **Не нужен** |
| Веб-панель | HTTPS | 443 (или выбранный вами порт) | **Нужен** |
| Веб-карта (Dynmap, Squaremap, BlueMap и др.) | HTTPS | 443 | **Нужен** |
| Сайт, страница состояния, веб-плагин MCDR, разные API | HTTPS | 443 | **Нужен** |
| RCON | Собственный TCP-протокол | 25575 | Это не TLS; **не выставляйте в интернет** |

**Вывод: сертификат HTTPS нужен «веб-стороне».** Есть сертификат или нет — это **никак не влияет** на то, смогут ли игроки зайти и возможна ли атака «человек посередине».

### 1.1 А что насчёт шифрования при входе в Java Edition

При входе в Java Edition шифрование действительно есть, но это **собственный механизм протокола Minecraft**, заданный игровым протоколом, **и он не связан с сертификатами X.509 и Let's Encrypt**. Именно смешение сертификата HTTPS и «шифрования игрового трафика» часто уводит настройку в неверную сторону.

### 1.2 Почему на веб-стороне TLS всё-таки обязателен

Потому что веб-сторона передаёт **учётные данные и идентичность**: пароль входа в панель, сессионные Cookie, API Key и Token — **по открытому HTTP их видит любой в той же сети**. Кроме того, современные браузеры помечают HTTP-страницы как «небезопасные», а если пользователь панели привык игнорировать предупреждения, эта привычка сама по себе проблема безопасности. Панель, открытая в интернет, постоянно сканируется, см. [Основные типы сетевых атак и защита, специфичная для Minecraft](/tutorials/ops/attack-defense).

## 2. Сертификат и приватный ключ

### 2.1 Что это такое

| | Сертификат (certificate) | Приватный ключ (private key) |
| --- | --- | --- |
| Суть | Публичный ключ + данные о владельце + подпись CA | Ключевой материал, который обязательно хранится в тайне |
| Можно ли публиковать | **Да**, он и так отправляется каждому посетителю | **Категорически нет** |
| Последствия утечки | Нет (это и так открытые данные) | **Получивший ключ может выдать себя за ваш сайт** |
| Истечение | Есть срок действия, **нужно продлевать** | Обычно меняется вместе с сертификатом, сам «не истекает» |

**Сертификат — это удостоверение, приватный ключ — печать.** Удостоверение можно показывать, потеря печати — катастрофа.

### 2.2 Типичные файлы и их связь

На примере обычного вывода ACME-клиента (**конкретные имена файлов зависят от вашего клиента**):

| Файл | Содержимое | Где используется |
| --- | --- | --- |
| `fullchain.pem` | Ваш сертификат + промежуточный сертификат | **`ssl_certificate` веб-сервера** |
| `privkey.pem` | Приватный ключ | **`ssl_certificate_key` веб-сервера** |
| `chain.pem` / `cert.pem` | Промежуточный сертификат / только ваш сертификат | Обычно отдельно не нужны |

**Самая частая ловушка**: настроить только `cert.pem` и забыть промежуточный сертификат — в результате «в одних браузерах открывается, в других нет». **С `fullchain.pem` такой проблемы не будет.**

### 2.3 SNI: несколько сайтов на одном IP

Современные TLS-клиенты при рукопожатии отправляют **SNI (Server Name Indication)**, и веб-сервер по нему выбирает сертификат. Поэтому на одной машине можно держать несколько сайтов, каждый со своим сертификатом; а **при проверке сертификата из командной строки обязательно указывать параметр SNI** (`openssl s_client -servername ...`), иначе вы можете увидеть сертификат другого сайта и сделать неверный вывод (см. раздел 8).

## 3. Let's Encrypt, ACME и «обязательное автопродление»

### 3.1 Что такое ACME

**ACME — протокол автоматической выдачи и продления сертификатов.** Let's Encrypt — самый известный удостоверяющий центр (CA) ACME, он выдаёт сертификаты проверки домена (DV) **бесплатно**. Ключевое слово — «автоматически»: ACME задуман так, чтобы вся цепочка «заявка, проверка, выдача, продление, развёртывание» работала без участия человека. Существуют и другие ACME CA (**подходит ли вам конкретный — по его официальной документации**).

### 3.2 90 дней — не проблема, проблема — ручное продление

Сертификаты Let's Encrypt **действуют 90 дней** (по официальной документации). Первая реакция многих — «слишком мало, неудобно», и **сама эта реакция и есть проблема**:

- 90 дней — **намеренно**: это превращает «забыл продлить» из «случайности раз в несколько лет» в «норму, выжить в которой можно только автоматизацией».
- **Любая схема «перед истечением продлю вручную» провалится**: четыре раза в год, много лет подряд без ошибок человек не выдержит; командировка, смена компьютера, письмо в спаме — любая мелочь однажды приведёт к истечению.
- Правильный подход: **превратить «истечёт ли сертификат» из «того, что я должен помнить» в «то, что система делает сама»**, и **следить за этим** (см. раздел 12).

### 3.3 Распространённые ACME-клиенты

certbot (самая полная официальная документация, много плагинов), acme.sh (чистый shell, широкая поддержка DNS API), lego (один файл на Go), а также веб-серверы с **встроенным ACME**, например Caddy. В статье используется certbot.

**Не управляйте одним набором доменов двумя клиентами одновременно**: две автоматические задачи будут перезаписывать конфигурацию друг друга, и при проблеме вы будете искать причину очень долго.

## 4. Практика с certbot

### 4.1 Установка: по официальной инструкции

Способ установки certbot сильно зависит от дистрибутива и версии, **ориентируйтесь на официальную инструкцию по установке**. Частые источники: **репозиторий дистрибутива** (проще всего, версия часто старая), **snap** (официальная документация часто рекомендует, версия свежее), **pip / виртуальное окружение** (гибко, но зависимости нужно вести самому). **Для плагина nginx нужен соответствующий пакет плагина** (обычно с именем вроде `python3-certbot-nginx`, точное имя — по вашему дистрибутиву). После установки проверьте `certbot --version` и учтите, что **в разных версиях подкоманды и параметры могут отличаться**.

### 4.2 Три способа выдачи и их сценарии

| Команда | Что делает | Когда подходит | Замечание |
| --- | --- | --- | --- |
| `certbot --nginx -d panel.example.com` | Плагин nginx: сам правит конфигурацию и настраивает перенаправление | nginx уже работает, конфигурация под вашим контролем | **Он изменит вашу конфигурацию nginx**, перед этим сделайте копию или положите её в контроль версий |
| `certbot certonly --standalone -d panel.example.com` | Поднимает собственный временный сервис на 80-м порту | На машине ещё нет веб-сервиса | **Нужно остановить nginx**, иначе 80-й порт занят и проверка провалится |
| `certbot certonly --webroot -w /var/www/certbot -d panel.example.com` | Кладёт файл проверки в указанный каталог, его отдаёт существующий nginx | **Самый частый вариант для обратного прокси** | Нужно настроить в nginx location для `.well-known/acme-challenge/` |

Для машины «nginx — обратный прокси панели» **рекомендуется webroot или плагин nginx**: первый минимально меняет конфигурацию, второй проще всего. **standalone подходит только если веб-сервиса ещё нет или вы готовы ненадолго остановить сервис.** При выдаче запрашивается **почта для напоминаний об истечении** (можно пропустить, но **настоятельно рекомендуется указать**: это единственный, кто может предупредить вас о сбое автопродления).

### 4.3 Проверка продления

**Этот шаг пропускать нельзя.** Он проверяет, «сработает ли автопродление, когда действительно запустится через 30 дней»:

```bash
# Учебный прогон: сертификат не заменяется и квота рабочей среды не расходуется (используется тестовая среда)
sudo certbot renew --dry-run

# Показать текущие сертификаты, пути и сроки истечения
sudo certbot certificates
```

**`--dry-run` — самый дешёвый способ проверки. Автопродление, которое ни разу не прогоняли, равно его отсутствию.**
:::warn Не используйте --force-renewal без необходимости
`--force-renewal` (и похожие принудительные параметры) немедленно перевыпускает сертификат. **Частый принудительный перевыпуск может упереться в ограничения частоты CA, и в нужный момент вы не сможете выпустить сертификат.** При разборе проблем сначала используйте `--dry-run`; если принудительный перевыпуск действительно нужен, сначала разберитесь в причине и правилах ограничений (по официальной документации CA).
:::

### 4.4 Автопродление: systemd timer или cron

**certbot обычно уже содержит задачу автопродления, писать свою не нужно.** Частые формы: **systemd timer** (например, `certbot.timer`, так в большинстве дистрибутивов и при установке из snap) и **задача cron** (например, `/etc/cron.d/certbot`, более старый способ установки). Нужно лишь **убедиться, что она есть и работает**:

```bash
# Вариант systemd
systemctl list-timers | grep -i certbot

# Вариант cron
ls -l /etc/cron.d/ | grep -i certbot
```

**Если вы напишете ещё одну cron-задачу, две задачи начнут конфликтовать.** По умолчанию автопродление обычно **проверяет состояние один-два раза в сутки и реально продлевает, только когда до истечения осталось меньше примерно 30 дней** (точный порог и расписание — по клиенту и официальной документации), поэтому «оно работает каждый день» не значит «оно выпускает каждый день».

### 4.5 После продления веб-сервер нужно перезагрузить

Продление меняет только файлы на диске, **работающий nginx новые сертификаты сам не прочитает** (он читает их при запуске или перезагрузке). Поэтому нужен хук развёртывания:

```bash
# Способ первый: deploy hook в команде продления (пример)
sudo certbot renew --deploy-hook "systemctl reload nginx"

# Способ второй: положить скрипт в каталог хуков, он выполняется после любого успешного продления
# /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

Не забудьте дать скрипту хука право на выполнение. **Лучший способ проверить, что хук действительно работает, — прогнать `--dry-run` и посмотреть, перезагрузился ли nginx** (обработка хуков в `--dry-run` может зависеть от версии, **ориентируйтесь на официальную документацию**).

## 5. Настройка TLS в nginx

### 5.1 Полный пример

Ниже — **структурно полная** конфигурация машины «nginx — обратный прокси панели» (домен, порт и пути — заглушки):

```nginx
# /etc/nginx/conf.d/panel.conf
# Порт <panel-port> — заглушка, замените на локальный порт, который реально слушает панель.

server {
    listen 80;
    listen [::]:80;
    server_name panel.example.com;

    # Файлы проверки сертификата: путь должен совпадать с --webroot у certbot
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    # Все остальные запросы перенаправляются на HTTPS
    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name panel.example.com;

    # Выдаётся и продлевается вашим ACME-клиентом, используйте реальные пути
    # Используйте символические ссылки из каталога live, а не файлы с номером версии из archive
    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;

    # Только современные версии TLS; TLS 1.0/1.1 уже не поддерживаются основными браузерами
    ssl_protocols TLSv1.2 TLSv1.3;
    # Пусть набор шифров выбирает клиент (современная практика; TLS 1.3 этот параметр и так не учитывает)
    ssl_prefer_server_ciphers off;

    # Необязательное повторное использование сессии; включать ли и с какими параметрами — по документации nginx
    ssl_session_cache shared:SSL:10m;

    # HTTP/2: в nginx 1.25.1 и новее отдельная директива; в более старых пишут listen 443 ssl http2;
    http2 on;

    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        # Консоль панели работает через WebSocket, заголовок Upgrade нужно пробрасывать
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # По нему панель понимает, что «снаружи HTTPS», и строит правильные ссылки и защищённые Cookie
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

После правки обязательно сначала проверьте синтаксис, потом перезагружайте:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### 5.2 Построчные пояснения (только про частые ошибки)

| Параметр | Зачем |
| --- | --- |
| `listen 443 ssl;` | **Параметр `ssl` обязателен**, иначе nginx не включит TLS на этом server |
| `ssl_certificate` / `ssl_certificate_key` | Первый — `fullchain.pem`, второй — `privkey.pem`; пути **определяет ваш клиент**, не копируйте |
| `ssl_protocols TLSv1.2 TLSv1.3;` | Минимум для современных браузеров — TLS 1.2; явно записать понятнее, чем полагаться на значение по умолчанию |
| `ssl_prefer_server_ciphers off;` | Современная практика — пусть выбирает клиент; на наборы шифров TLS 1.3 этот параметр и так не влияет |
| location для `.well-known/acme-challenge/` | Точка проверки HTTP-01; при `--webroot` **обязательно** должен совпадать с путём из `-w` |
| `location / { return 301 ...; }` | Перенаправление с HTTP на HTTPS; учтите, что оно **идёт после location проверки** (nginx предпочитает более конкретный префикс) |
| `X-Forwarded-Proto` | Без него панель может строить ссылки `http://` или отказываться ставить защищённые Cookie |
| `http2 on;` | **Зависит от версии**: отдельная директива появилась с nginx 1.25.1 |
:::tip Почему пути к сертификатам берут из каталога live
ACME-клиент обычно складывает реальные файлы каждой выдачи в каталог вроде `archive/` (с номером), а в `live/` создаёт **символические ссылки** на последнюю версию. **В конфигурации нужно ссылаться на пути из `live/`**: после продления они сами указывают на новые файлы, а конкретные имена в `archive/` меняются при каждом продлении.
:::

### 5.3 О наборах шифров и «значений по умолчанию обычно достаточно»

В конфигурациях TLS для nginx, гуляющих по интернету, часто есть большой блок `ssl_ciphers`. **В большинстве случаев он не нужен**:

- **Собственные значения по умолчанию в современных версиях nginx обычно безопасны** и обновляются вместе с версией.
- Скопированный вручную список шифров нескольких летней давности **может, наоборот, исключить новые и лучшие наборы**.
- Если нужен тонкий контроль, берите источник, который долго поддерживается, вроде генератора конфигурации SSL от Mozilla, **а не случайный блог**.
:::note Текущее состояние OCSP stapling
Исторически часто рекомендовали `ssl_stapling on;` и `ssl_stapling_verify on;` (вместе с `ssl_trusted_certificate`). **Но Let's Encrypt объявил о прекращении службы OCSP и переходе на CRL**, поэтому настраивать OCSP stapling для сертификатов LE больше не имеет смысла. **Точные сроки и текущее состояние — по официальным объявлениям Let's Encrypt**, не копируйте старые руководства.
:::

## 6. Способы проверки: HTTP-01 и DNS-01

ACME должен доказать, что «вы управляете этим доменом». Два основных способа:

| | HTTP-01 | DNS-01 |
| --- | --- | --- |
| Как доказывается | Положить файл с заданным содержимым по адресу `http://домен/.well-known/acme-challenge/<token>` | Добавить TXT-запись с заданным содержимым в `_acme-challenge.домен` |
| Требования к сети | **80-й порт должен быть доступен из интернета** (можно с перенаправлением) | Входящие порты не нужны |
| Можно ли выпустить wildcard | **Нет** | **Да** |
| Сложность автоматизации | Низкая (webroot / плагин nginx) | Нужны API-учётные данные DNS-провайдера |
| Основной риск | 80-й закрыт брандмауэром или группой безопасности, перехвачен CDN, перенаправление настроено неверно | **Утечка API-учётных данных равна утечке контроля над доменом** |

### 6.1 Частые причины сбоя HTTP-01

**Группа безопасности облака не пропускает 80-й** (чаще всего: локальный брандмауэр открыт, а группа безопасности облака — нет); **80-й занят другой службой** (при `--standalone` всё ещё работает nginx); **перенаправление уводит и запрос проверки** (location проверки должен идти до перенаправления, либо правило перенаправления должно пропускать `/.well-known/`); **впереди CDN или обратный прокси** (запрос проверки не доходит до источника, нужно действовать по инструкции CDN).

### 6.2 Что учесть в DNS-01

Имя записи обычно `_acme-challenge` (**по документации вашего DNS-провайдера и клиента**); **DNS применяется не сразу**, не нажимайте проверку сразу после добавления записи вручную; **API-учётные данные должны иметь минимальные права**, давайте только на те записи, которые нужно менять, не используйте глобальный ключ аккаунта; если учётные данные хранятся на сервере, **права нужно ужесточить** и не коммитить их в Git.

### 6.3 Когда DNS-01 обязателен

- Нужен **wildcard-сертификат**.
- **80-й порт невозможно открыть наружу** (заблокирован оператором, вы за CGNAT, ограничения корпоративной сети).
- Домен **указывает не напрямую на эту машину** (впереди CDN, балансировщик, несколько источников).
- Вы хотите, чтобы **выдача сертификата вообще не зависела от веб-сервиса** (например, сертификат для не-HTTP-службы).

## 7. Wildcard-сертификаты

Wildcard-сертификат покрывает один уровень поддоменов, и цена этого — **только DNS-01**:

```bash
# Учтите: *.example.com не включает сам example.com, обычно нужны оба
sudo certbot certonly --manual --preferred-challenges dns \
  -d example.com -d '*.example.com'
```

Важно:

- **`*.example.com` не совпадает с `example.com`** и не совпадает с `a.b.example.com` (wildcard покрывает только один уровень). Если нужно — впишите оба в `-d`.
- Wildcard **удобен, но и расширяет радиус поражения**: при утечке приватного ключа пострадают все поддомены сразу.
- `--manual` означает, что **продление тоже будет ручным** — если не заменить его на автоматический плагин с DNS API. **Ручной wildcard плюс забытое продление — очень частая комбинация аварий.**
- Если поддоменов немного, **выпускать по одному (с автопродлением через HTTP-01) обычно спокойнее, чем один wildcard**.

## 8. Что происходит после сбоя продления

### 8.1 Симптомы

| Явление | Причина |
| --- | --- |
| Браузер блокирует страницу целиком, сообщает об истёкшем или небезопасном сертификате | Сертификат истёк |
| В панель не войти, или все API-клиенты выдают ошибки | То же; часть клиентов не предлагает «продолжить» |
| Веб-карта не загружается | Статика карты идёт по HTTPS |
| «Раньше работало, однажды утром перестало» | Истечение происходит **мгновенно**, без плавного перехода |

### 8.2 Как проверить

```bash
# Кто выдал этот сертификат и когда он истекает (нужен -servername, иначе можно увидеть сертификат другого сайта)
echo | openssl s_client -connect panel.example.com:443 -servername panel.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# Хотите увидеть всю цепочку (включая промежуточные сертификаты)
openssl s_client -connect panel.example.com:443 -servername panel.example.com -showcerts </dev/null
```

В выводе обратите внимание на две даты: **`notBefore` (начало действия) и `notAfter` (истечение)**. Если `notAfter` уже в прошлом, проблема подтверждена.

**Одновременно смотрите срок действия локального файла** (возможно, вы видите сертификат на CDN, а не на источнике):

```bash
sudo openssl x509 -in /etc/letsencrypt/live/panel.example.com/fullchain.pem -noout -subject -dates
sudo certbot certificates
```
:::warn Просто перезапустить службу бесполезно
После истечения сертификата **перезапуск nginx его не обновит**. Правильный порядок: **сначала добиться успешного продления** (`sudo certbot renew` и разобрать его ошибки), **затем перезагрузить nginx**. Обратный порядок только тратит время.
:::

### 8.3 HSTS делает хуже

Если у вас включён HSTS (заголовок `Strict-Transport-Security`), браузер **в течение определённого времени принудительно использует HTTPS и не даёт пользователю нажать «продолжить»**, и при истечении сертификата страница превращается в **ошибку, которую невозможно обойти**. Сам HSTS — хорошая вещь (защищает от атак понижения), но помните его цену: **он превращает «сертификат должен быть всегда действителен» из «желательно» в «обязательно»**. Перед включением убедитесь, что автопродление и мониторинг работают.

## 9. Файлы сертификатов и права

Приватный ключ — единственное в этой системе, что действительно нужно держать в тайне:

```bash
# Приватный ключ может читать только владелец; каталоги тоже закрываем
sudo chmod 700 /etc/letsencrypt/archive /etc/letsencrypt/live
sudo chmod 600 /etc/letsencrypt/archive/<домен>/privkey*.pem
sudo chown root:root /etc/letsencrypt/archive/<домен>/privkey*.pem

# Проверка: не должно быть доступа на чтение для group/other
ls -l /etc/letsencrypt/live/<домен>/
```

Важно:

- **`chmod 600` + владелец root** — распространённая и безопасная практика. ACME-клиент обычно сам выставляет разумные права, **сначала посмотрите текущее состояние, потом меняйте**.
- **Не копируйте приватный ключ в корень сайта, во временный каталог, в мессенджеры или в репозиторий Git.** Если ключ нужен другой службе, используйте группу прав или ACL, а не `chmod 644`.
- **Главный процесс nginx обычно запускается от root**, поэтому может читать ключ, принадлежащий root; **если у вас другой способ развёртывания (контейнеры, запуск не от root), убедитесь, что у пользователя, читающего сертификат, есть права**, иначе проявление будет «конфигурация верная, но запуск падает».
- **`chmod -R 777 /etc/letsencrypt` — абсолютно неверно**: это устраняет ошибку прав и одновременно отдаёт ключ каждому пользователю на машине.
- **Резервные копии должны учитывать и сертификаты**, но **приватный ключ в копии тоже нужно хранить зашифрованным** (см. [Резервные копии в другом месте](/tutorials/ops/offsite-backup)).

## 10. Цепочка обратного прокси

Когда HTTPS завершается на nginx, а запрос пересылается в панель, **«протокол» в цепочке превращается в два разных понятия**:

```text
Браузер игрока  --HTTPS-->  nginx (завершает TLS)  --HTTP(127.0.0.1)-->  панель
```

Отсюда три частые проблемы:

| Проблема | Проявление | Что делать |
| --- | --- | --- |
| Панель строит ссылки `http://` | Браузер блокирует ресурсы или переходы на странице | Передавайте `X-Forwarded-Proto $scheme` и настройте «внешний адрес/доверенный прокси» по официальной документации панели |
| Панель считает «соединение небезопасным» и отказывается ставить Cookie | После входа сразу выкидывает | То же; часть панелей требует явно объявить HTTPS в конфигурации |
| WebSocket не подключается | Консоль пустая, крутится индикатор | Передавайте заголовки `Upgrade` и `Connection` и задайте `proxy_http_version 1.1` |

**Если впереди есть ещё слой CDN** (Cloudflare и подобные), цепочка становится «браузер → CDN (завершает TLS) → источник (ещё один участок TLS)», и **обе стороны нуждаются в собственных сертификатах и настройках**; **проверяется ли сертификат источника и в каком режиме — это поведение провайдера CDN, ориентируйтесь на официальную документацию**. В таких цепочках при разборе «чей именно сертификат истёк» очень помогает проверка с `-servername` из раздела 8.

Полная конфигурация со стороны панели — см. [Использование панелей управления и их безопасность](/tutorials/ops/panels).

## 11. Самоподписанные сертификаты: когда это допустимо

Самоподписанный сертификат (вы сами себе CA) — **не «бесплатный HTTPS»**, его назначение:

| Сценарий | Допустимо ли |
| --- | --- |
| Только вы сами во внутренней сети (например, внутренний сценарий из [Запуска сервера на домашнем компьютере и его обслуживания](/tutorials/ops/home-hosting)), и вы можете установить свой CA в хранилище доверия своих устройств | **Да** |
| Временный тест, этап до привязки домена | **Да**, но понимайте, что его в любой момент заменят |
| Открыто в интернет, для игроков или помощников | **Нет**: все увидят предупреждение браузера |
| Для API-клиентов, ботов, плагинов | **Обычно нет**: многие клиенты по умолчанию отвергают недоверенные сертификаты, и **менять конфигурацию, чтобы игнорировать проверку, — худший выбор** |

Что нужно понимать:

- **Предупреждение браузера нельзя «настроить»**: пользователь видит «ваше подключение не защищено» и должен вручную нажать «Дополнительно → Перейти». **Это приучает пользователей игнорировать предупреждения, что само по себе проблема безопасности.**
- Чтобы самоподписанный сертификат не вызывал предупреждений, **нужно импортировать свой CA на каждое клиентское устройство**; когда устройств много, обслуживание становится дороже, чем получить бесплатный сертификат.
- Во внутренних сценариях, если это действительно нужно, используйте инструменты для внутреннего CA вроде **mkcert**, **step-ca** — с ними ошибиться труднее, чем набирать `openssl req` вручную (**конкретное использование — по их официальной документации**).
- **Никогда** не включайте HSTS на сайте с самоподписанным сертификатом.

## 12. Мониторинг и чек-лист

**Истечение сертификата — сбой, о котором можно узнать заранее**, поэтому за ним нужно следить, а не надеяться. Минимум: **оповещение, когда до истечения осталось меньше 14 дней**. Есть два способа, **рекомендуется делать оба**:

1. **Внешняя проверка HTTPS**: пусть монитор не на этой машине раз в несколько минут запрашивает адрес панели и проверяет срок истечения сертификата. Многие инструменты мониторинга (например, Uptime Kuma) в HTTPS-проверке показывают данные сертификата. См. [Мониторинг и оповещения](/tutorials/ops/monitoring).
2. **Локальная проверка срока**: на сервере читать файл сертификата и считать остаток дней, писать в метрику мониторинга или сразу отправлять уведомление.

```bash
# Однострочный вариант: печатает остаток дней (опция -d у date — синтаксис GNU, в других системах используйте свою команду даты)
sudo openssl x509 -in /etc/letsencrypt/live/panel.example.com/fullchain.pem -noout -enddate \
  | cut -d= -f2 \
  | xargs -I{} date -d "{}" +%s \
  | awk -v now="$(date +%s)" '{ printf "Осталось %d дней\n", ($1 - now) / 86400 }'
```
:::tip Оповещение должно ловить «продление не удалось»
Следить только за «сколько дней осталось» недостаточно — **оно начнёт срабатывать за 30 дней, и вы к нему привыкнете**. Лучше комбинация: **оповещение о сбое задачи продления** (уведомление о сбое timer/cron) **плюс** оповещение «осталось < 14 дней». Первое сообщает «автопродление сломалось», второе — последняя страховка.
:::

### 12.1 Чек-лист перед запуском

| Пункт проверки | Как проверить | Критерий прохождения |
| --- | --- | --- |
| Сертификат выдан | `certbot certificates` | Домен верный, срок истечения в будущем |
| Используется полная цепочка | Посмотреть `ssl_certificate` в конфигурации nginx | Указывает на `fullchain.pem`, а не на отдельный `cert.pem` |
| Версия протокола верная | Проверка браузером или `openssl s_client` | Согласуется TLS 1.2 / 1.3 |
| HTTP перенаправляется на HTTPS | Открыть один раз по `http://` | Переход 301/308 без предупреждений о смешанном содержимом |
| Путь проверки работает | `curl -I http://домен/.well-known/acme-challenge/<тестовый файл>` | Возвращает 200 (а не перенаправление) |
| Задача автопродления работает | `systemctl list-timers` или `/etc/cron.d/` | Задача продления есть и только одна |
| Учения по продлению пройдены | `certbot renew --dry-run` | Без ошибок |
| После продления будет перезагрузка | Проверить deploy hook | После успешного продления nginx действительно перезагружается |
| Права на ключ закрыты, копий нет | `ls -l` + `stat` и поиск по диску и истории Git | Не читается посторонними, ключ есть только в каталоге сертификатов и в зашифрованной копии |
| Оповещение об истечении настроено | Панель мониторинга | Намеренно увеличить порог и убедиться, что оповещение приходит |
| Панель и карта реально работают | Зайти браузером | Вход, консоль и карта в порядке, предупреждений о сертификате нет |
