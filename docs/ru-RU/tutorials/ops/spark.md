«Лагает» — это явление, а не причина. Когда игроки жалуются на лаги, виноват может быть плагин, занявший главный поток, слишком много сущностей, игрок, бегущий по карте и вызывающий генерацию чанков в реальном времени, или ограничение CPU либо перепродажа на хосте. **Ценность spark в том, что он превращает «лаги» из ощущения в доказательство, на которое можно показать пальцем**: какая цепочка вызовов, какой плагин, какой процент.

Статья только о том, как пользоваться самим spark. Направления оптимизации — см. [Оптимизация производительности](/tutorials/java/optimize), скопление сущностей — см. [Скопление сущностей и выпавших предметов](/tutorials/faq/entity-lag), падения и ошибки — см. [[JAVA] Частые вопросы](/tutorials/faq/faq-java).

Команды и опции в статье взяты из официальной документации spark (spark.lucko.me/docs) и документации PaperMC и сверены по пунктам. **Доступные подкоманды и опции spark немного различаются на разных платформах и в разных крупных версиях**; перед действиями проверьте через `/spark` или автодополнение по Tab, какие параметры поддерживает ваша версия, не набирайте опции по памяти.

## 1. Что такое spark и как его поставить

### 1.1 Он состоит из трёх частей

spark — инструмент профилирования (profiler), официально позиционируемый как «профайлер для клиента, сервера и прокси Minecraft», состоящий из трёх возможностей:

| Компонент | На какой вопрос отвечает |
| --- | --- |
| Profiler (сэмплирующий профайлер) | На какие методы и плагины уходит время CPU? |
| Memory Inspection (проверка памяти) | Что занимает больше всего в куче? Много ли пауз GC? |
| Health Reporting (отчёт о здоровье) | Каково долгосрочное состояние TPS, CPU, памяти и диска? |

Одновременно это сайт: spark.lucko.me — и официальный сайт, и онлайн-просмотрщик отчётов (viewer). Вы запускаете сэмплирование в игре, данные загружаются, вы получаете ссылку и в браузере видите дерево вызовов, flame graph и т. п.

Несколько вещей, которые нужно понять заранее:

- **spark — сэмплирующий (sampling) профайлер**. В разделе «spark vs. others» официально сказано: сэмплирование обычно уступает инструментированию (instrumentation) в числовой точности, но почти не замедляет целевую программу, поэтому на практике чаще лучше отражает реальное выполнение.
- **Он записывает «всё»**. Сравнивая с timings, официально отмечается: timings требует вручную заранее определить области анализа, умеет считать число событий и дружелюбнее к новичкам; spark не требует предварительного определения и записывает все стеки вызовов, поэтому лучше отвечает на вопрос «на какой именно строке кода медленно».
- **Это не только серверный плагин**. spark можно подключить как Java agent к любой программе на JVM (включая ванильный сервер), причём к ванильному серверу автоматически применяется маппинг деобфускации.

### 1.2 Как ставить на разных платформах

Официальная страница загрузки (https://spark.lucko.me/download) раздаёт разные пакеты по платформам. **Сначала выберите свою платформу, потом скачивайте**, положите jar в нужный каталог и перезапустите сервер.

| Платформа | Пункт на странице загрузки | Куда положить | Замечание |
| --- | --- | --- | --- |
| Bukkit / Spigot / Paper / Purpur | Bukkit (Paper/Spigot) | `plugins/` | Серверный плагин; в Paper 1.21+ уже встроен, см. ниже |
| Fabric | Fabric | `mods/` | В виде мода |
| Forge | Forge | `mods/` | В виде мода |
| NeoForge | NeoForge | `mods/` | В виде мода |
| Velocity | Velocity | `plugins/` | Прокси; префикс команды другой, см. 1.4 |
| BungeeCord | BungeeCord | `plugins/` | Прокси; префикс команды другой, см. 1.4 |
| Sponge | Sponge (API 12) | `mods/` | Отдельный пункт на странице загрузки |
| Клиент (Fabric/Forge и др.) | Пакет соответствующей платформы | `mods/` | Анализ лагов клиента; команда `/sparkc` |
| Любая программа на JVM / ванильный сервер | Standalone (Java Agent) | Параметры запуска | См. 1.3 |

:::note В Paper 1.21 и новее уже встроен
Официальная документация по установке прямо указывает: **Paper 1.21 и новее уже включает spark в сервер, отдельный плагин ставить не нужно**. Только если вам нужен spark новее встроенного, положите отдельный jar плагина в `plugins/` и добавьте в параметры запуска `-Dpaper.preferSparkPlugin=true`, чтобы перекрыть встроенную версию.
:::

:::warn Скачивайте только с официального сайта
Положить jar в `plugins/` означает отдать ему управление всем сервером. **Берите его со страницы загрузки https://spark.lucko.me/download**, не используйте перепакованные сборки неизвестного происхождения или файлы из файлообменников. На странице загрузки есть также «Other Platforms» (Folia, Geyser, Minestom, Nukkit, Hytale и др.), официально указано, что их предоставляет сообщество и они поддерживаются «как есть» (as-is), оценивайте сами перед использованием.
:::

### 1.3 Отдельный agent (Standalone Agent)

Когда цель — не «стандартный сервер» (например, ванильный сервер или собственная программа на Java), используется режим agent. Подключение при запуске:

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar -jar application.jar [application args]
```

Можно указать порт прослушивания agent:

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar=port=2222 -jar application.jar [application args]
```

Поддерживаемые параметры agent (несколько параметров через запятую):

| Параметр | Значение |
| --- | --- |
| `port={port}` | Порт прослушивания agent, по умолчанию `2222` |
| `start` | Начать сэмплирование сразу после подключения |
| `open` | После подключения вывести ссылку на просмотрщик в консоль или журнал |

Например:

```bash
java -javaagent:spark-x.y.z-standalone-agent.jar=port=2222,start,open -jar application.jar
```

Если программа **уже работает**, можно подключиться прямо к процессу (замените `<pid>` на номер процесса):

```bash
java -jar spark-x.y.z-standalone-agent.jar <pid>
java -jar spark-x.y.z-standalone-agent.jar <pid> port=2222
```

Если запустить этот jar без PID, он выведет список всех Java-процессов с их PID. После успешного подключения **способ подключения печатается в консоли или журнале самой присоединённой программы**; подключитесь по подсказке сессией SSH и выполняйте обычные команды spark, выйдя из сессии через `exit`.

### 1.4 Убедитесь, что он загрузился

Самый прямой способ: **выполнить `/spark` без параметров**, он выведет версию и список доступных подкоманд. Если выдаёт неизвестную команду или ничего не выводит, значит не загрузился.

Проверяйте по порядку: правильный ли каталог (`plugins/` или `mods/`), правильный ли пакет платформы, действительно ли перезапускали сервер, есть ли в журнале запуска сообщения о загрузке spark.

Префикс команды зависит от платформы, официальная документация специально отмечает:

| Среда | Используемая команда |
| --- | --- |
| Сервер (семейство Bukkit, сервер Fabric/Forge) | `/spark` |
| BungeeCord | `/sparkb` |
| Velocity | `/sparkv` |
| **Клиент** Forge/Fabric | `/sparkc` |

О правах: нужно право `spark` либо собственные узлы прав подкоманд. Официальная документация перечисляет узлы `spark.profiler`, `spark.health`, `spark.ping`, `spark.tps`, `spark.tickmonitor`, `spark.gc`, `spark.gcmonitor`, `spark.heapsummary`, `spark.heapdump`, `spark.activity`. В большинстве случаев **достаточно выдать себе OP**.

:::tip Одна настройка, которую легко упустить
Параметр spark `overrideTpsCommand` по умолчанию `true` и **действует только на серверах семейства Bukkit**: то есть по умолчанию `/tps` перехватывается spark и выводит его представление TPS.
:::

## 2. Сначала общее состояние здоровья

### 2.1 Что означают TPS и MSPT

Сначала поймите цикл тиков (официальное руководство «The Tick Loop»):

- Цель сервера Minecraft — **выполнять 20 тиков в секунду**, то есть **один тик за 50 миллисекунд**.
- В одном тике нужно: обработать пакеты игроков (движение, установка и разрушение блоков, атака сущностей), обновить позиции игроков и других сущностей, разослать игрокам изменения мира, заспавнить мобов и обработать ИИ и поиск пути, обработать обновления редстоуна и т. д.
- Если тик занял **меньше** 50 миллисекунд, сервер «спит» оставшееся время и продолжает, когда пора начинать следующий тик. **Сон — это здоровое состояние**.
- Если тик занял **больше** 50 миллисекунд, следующий тик можно только отложить, потому что тики не выполняются параллельно. Всё «сдвигается вправо», за ту же секунду выполняется меньше тиков, и игроки ощущают замедление и лаги.

Отсюда два показателя:

| Показатель | Полное название | Смысл | Цель |
| --- | --- | --- | --- |
| TPS | ticks per second | Сколько тиков в среднем выполняется за секунду | **20** |
| MSPT | milliseconds per tick | Сколько миллисекунд в среднем занимает тик | **50 или меньше** |

Официальная документация указывает, что вывод `/spark tps` также содержит MSPT **минимум, медиану, 95-й процентиль и максимум**, и spark автоматически окрашивает эти числа в зелёный, жёлтый или красный по качеству.

**Почему важен максимум**: все эти показатели — средние или статистики. Официальное руководство по циклу тиков особо предупреждает: вполне возможна ситуация «большинство тиков занимает 20 миллисекунд (здорово), а изредка какой-то тик занимает 300 миллисекунд (нездорово)» — это и есть **пик лагов (lag spike)**, среднее сглаживает пики, поэтому по одному среднему TPS проблему не увидеть.

### 2.2 /spark tps

```text
/spark tps
```

Выводит TPS и загрузку CPU. Это **первый шаг** каждого разбора: сначала подтвердить, «действительно ли лагает», и только потом решать, нужен ли профайлер.

### 2.3 /spark health

Подкоманда `health` создаёт отчёт о здоровье сервера, **включая TPS, CPU, память и занятость диска**. Использование по официальной документации:

```text
/spark health
/spark health upload
/spark health show
/spark health show --memory
/spark health show --network
```

| Команда | Поведение |
| --- | --- |
| `/spark health` | Открывает в просмотрщике, **режим live dashboard, данные обновляются каждые 10 секунд** |
| `/spark health upload` | Загружает **статический** отчёт о здоровье, без автообновления |
| `/spark health show` | Печатает базовый отчёт прямо в консоль, без браузера |
| `/spark health show --memory` | Добавляет сведения об использовании памяти JVM |
| `/spark health show --network` | Добавляет сведения об использовании сети системой |

### 2.4 /spark ping

```text
/spark ping
/spark ping --player <username>
```

Без параметров показывает **средний ping всех игроков** (время кругового обхода RTT); с `--player` — текущий ping конкретного игрока.

**Почему это выделено отдельно**: когда игрок говорит «лагает», это может быть медленный тик сервера, а может быть просто плохой канал от него до дата-центра. Высокий ping при нормальном MSPT означает, что проблема в сетевом пути и правка конфигурации сервера не поможет. Этот шаг служит для **разделения сетевой проблемы и проблемы тиков**.

### 2.5 Как смотреть изменение за период

Один `/spark tps` — только снимок. Чтобы увидеть тренд, используйте live dashboard `/spark health`: по официальному описанию он обновляется каждые 10 секунд, поэтому его можно считать лентой времени и наблюдать, **постоянно ли низкие** TPS, MSPT и CPU или **периодически проседают**.

| Картина | Пояснение | Следующий шаг |
| --- | --- | --- |
| TPS стабильно низкий, MSPT стабильно высокий | Главный поток постоянно не успевает | Сразу идти в profiler искать горячие точки |
| TPS большую часть времени в норме, изредка проседает | Пики лагов | Локализовать через tickmonitor, затем сэмплировать с `--only-ticks-over` |

:::note Как понимать «низкий TPS + нормальный MSPT»
По механике цикла тиков: если MSPT действительно в норме (каждый тик укладывается в бюджет 50 миллисекунд), TPS не должен стабильно быть низким, потому что сон между тиками выравнивает ритм. Поэтому при «низком TPS и нормальном MSPT» подозревать нужно не «медленный плагин», а **внешние факторы**: сервер был приостановлен (долгий stop-the-world, сохранение мира, приостановка или миграция хоста), CPU хоста ограничен или отнят другими арендаторами, либо **сами данные неверны**.

У последнего пункта есть официальное основание: все метрики spark берутся из событий сервера и API Java и системы, и официально в «About spark metrics» сказано, что **при работе в контейнере метрики CPU и памяти иногда сообщаются неверно** (окружения вроде Pterodactyl), «если выглядит неправильно, скорее всего spark получает неверные исходные данные». Оговоримся: **вывод «низкий TPS + нормальный MSPT указывает на внешние факторы» — это вывод статьи на основе механики цикла тиков, официальная документация такого вывода прямо не делает**, оценивайте вместе с загрузкой CPU, нагрузкой хоста и журналом GC.
:::

## 3. Сэмплирующий анализ (profiler)

### 3.1 Команды и опции

Все команды и опции ниже — со страницы официальной документации Command Usage.

Базовые операции:

| Команда | Действие |
| --- | --- |
| `/spark profiler start` | Начать сэмплирование в режиме по умолчанию |
| `/spark profiler stop` | Остановить и посмотреть результат (по умолчанию загружает и выдаёт ссылку) |
| `/spark profiler cancel` | Остановить сэмплирование и **не загружать** результат |
| `/spark profiler open` | Если сэмплирование уже идёт в фоне, открыть страницу просмотра, не останавливая его |
| `/spark profiler info` | Посмотреть текущее состояние сэмплирования |

Частые опции:

| Опция | Действие |
| --- | --- |
| `--timeout <seconds>` | Автоматически остановить по истечении времени |
| `--only-ticks-over <milliseconds>` | **Записывать только тики дольше указанного**, для отлова пиков |
| `--thread *` | Отслеживать все потоки |
| `--thread <thread name>` | Отслеживать только указанный поток |
| `--thread <pattern> --regex` | Сопоставлять имена потоков регулярным выражением |
| `--interval <milliseconds>` | Интервал сэмплирования, по умолчанию 4 |
| `--alloc` | Анализировать **распределение памяти** (давление на память), а не CPU |
| `--alloc --alloc-live-only` | При анализе распределения оставить только объекты, не собранные к концу сэмплирования |
| `--alloc --interval <bytes>` | Гранулярность сэмплирования распределения, по умолчанию `524287` (около 512 KB) |
| `--combine-all` | Объединить все потоки под один корневой узел |
| `--not-combined` | Не группировать потоки пула вместе |
| `--ignore-sleeping` | Записывать только сэмплы потоков, не находящихся в состоянии sleeping |
| `--force-java-sampler` | Принудительно использовать Java-сэмплер вместо async-сэмплера |
| `stop --comment <comment>` | Приложить комментарий при остановке, он отображается в просмотрщике |
| `stop --save-to-file` | Сохранить результат в файл в каталоге конфигурации, **не загружать** |

Примеры комбинаций (из официального руководства и документации Paper):

```text
/spark profiler start --timeout 60
/spark profiler start --timeout 600
/spark profiler start --only-ticks-over 150
/spark profiler stop --comment "базовая линия до изменений"
/spark profiler stop --save-to-file
```

:::note О «/spark profiler без параметров»
Официальная документация описывает работу profiler явными подкомандами `start`, `stop`, `cancel`, `open`, `info` и не описывает «`/spark profiler` без параметров» как отдельное действие. Кроме того, официальная документация по конфигурации указывает, что **фоновый профайлер spark включён по умолчанию** (параметр `backgroundProfiler` по умолчанию `true`), и в этом случае можно сразу использовать `/spark profiler stop` или `/spark profiler open`, чтобы работать с **уже идущим** сэмплированием. Поэтому: **пишите по подкомандам, не предполагайте поведение голой команды**.
:::

### 3.2 Стандартный процесс

```text
1. Убедиться, что проблема происходит сейчас (официально подчёркнуто: профилировать нужно в момент проблемы, иначе ничего не соберётся)
2. Начать сэмплирование: /spark profiler start --timeout 60
3. Дать серверу поработать под реальной нагрузкой 30-60 секунд (игроки онлайн, действия воспроизведены)
4. По истечении времени остановится автоматически; в чате или консоли появится ссылка spark.lucko.me/xxxx
5. Открыть эту ссылку в браузере
6. Сначала смотреть "Server thread" (главный поток сервера), идти вниз от самого широкого узла
```

Как выбрать длительность: если проблема **происходит прямо сейчас**, достаточно 30-60 секунд; если проблема **периодическая**, используйте более длинный `--timeout` (в официальной документации Paper пример `--timeout 600`, то есть 10 минут) либо перейдите к подходу с пиками из раздела 3.6.

### 3.3 Как читать отчёт в просмотрщике

Официальная страница «Using the viewer» хорошо объясняет структуру просмотрщика.

**Потоки (Threads)**: открыв отчёт, вы сначала видите список потоков. Поток можно понимать как «рабочего, который в программе делает что-то». Для сервера **обычно реально важен только «Server thread»** — главный поток, который выполняет игру. Корневой узел (сам поток) всегда показывает 100 %, потому что 100 % времени сэмплирования ушло в этот поток.

**Кадры вызова / узлы (Call frames)**: каждый узел показывает три вещи — **имя**, **процент от общего времени этого потока** и **число миллисекунд (при наведении)**. Нажатие на узел раскрывает его дочерние узлы.

Типичная картина при раскрытии серверного потока (официальный пример):

```text
Server thread
  java.lang.Thread.run()
    MinecraftServer.run()
      MinecraftServer.tick()        <- место, где реально идёт работа
      Thread.sleep()                <- сон, здоровое состояние, можно игнорировать
```

**Доля сна — первое, на что смотреть**. В официальном руководстве по циклу тиков даны ориентиры:

| Доля сна (waitForNextTick / sleep) | Смысл |
| --- | --- |
| Чем выше, тем лучше (в официальном примере 81 %) | У сервера есть запас, он выдержит всплеск нагрузки |
| Ниже 20 % | Сервер уже сильно загружен, часть тиков может уже лагать |
| Ниже 5 % | Можно считать, что лагает прямо сейчас, запаса нет |

**Но всё это средние значения**, официально особо подчёркнуто: пики усредняются, поэтому «высокая доля сна» не равно «нет пиков лагов».

**Три представления** (переключаются на верхней панели):

| Представление | Содержимое | Когда использовать |
| --- | --- | --- |
| All (по умолчанию) | Полное раскрываемое дерево вызовов | Идти вниз по процентам |
| Flat | **250 самых медленных вызовов методов** плоско на верхнем уровне | Быстро увидеть «кто в целом самый дорогой» |
| Sources | **Отдельное дерево по плагинам и модам**, верхний уровень — вызовы из этого источника | Сразу определить «какой плагин» |

У представления Flat есть ещё два измерения: Display — **Top Down** (обычное направление, раскрытие показывает дочерние вызовы) и **Bottom Up** (обратное, раскрытие показывает «кто это вызвал»); Sort — **Total Time** (общее время с дочерними) и **Self Time** (время самого метода).

**Flame Graph**: можно нажать значок пламени сверху или выбрать в контекстном меню узла «View as Flame Graph». Официально указано: **ширина узла соответствует доле занимаемого времени**; нажатие на узел «фокусирует» его на всю страницу. Известный совет «смотреть самую широкую полосу» — именно про это.

**Деобфускация (Deobfuscation)**: клиент и сервер Minecraft обфусцируют имена классов и методов. Просмотрщик **по умолчанию сам определяет, какой маппинг применить**; если определил неверно, выберите вручную в меню в правом верхнем углу.

**Закладки**: нажмите с зажатым `alt` на вызов метода или выберите в меню «Toggle bookmark», метод подсветится, и **закладка кодируется в URL** — отправив ссылку с закладкой другому, он откроет её с автоматически раскрытым и подсвеченным тем же местом. Это самый простой способ «показать пальцем».

### 3.4 Серверный поток и асинхронные потоки

- **Server thread**: главный поток, в котором идёт цикл тиков, здесь находится подавляющее большинство проблем производительности.
- **Асинхронные потоки (async threads)**: асинхронные задачи плагинов, сохранение чанков, сетевой ввод-вывод (Netty), потоки GC и др. Они **не занимают бюджет тика напрямую**, но если они отнимают CPU или конкурируют за блокировки с главным потоком, это всё равно влияет на главный поток.

В официальной документации `--thread *` описано как «отслеживать **все** потоки», значит по умолчанию не все потоки попадают в сэмплирование. **Если вы подозреваете, что какой-то плагин свалил тяжёлую работу в асинхронный поток** (проявляется высоким CPU при внешне незагруженном серверном потоке), снимите ещё раз явно с `--thread *`.

### 3.5 Как отнести время к конкретному плагину

Это самое практичное преимущество spark перед timings: **в отчёте появляются собственные имена пакетов плагинов**.

Например, в серверном потоке появляется очень широкая запись:

```text
com.example.shop.ShopManager.tickShops()
```

значит этим занимается плагин `com.example.shop`. Способы определить:

1. В представлении All раскрывайте вниз по процентам, пока не увидите имя пакета, «похожее на плагин» (обычно обратное доменное имя, например `me.lucko.` или `com.example.`).
2. Либо сразу переключитесь в **представление Sources**: оно **строит дерево отдельно по плагинам и модам**, и самое «толстое» дерево и есть подозреваемый.
3. Если на верхнем уровне метод самого сервера (NMS), не спешите с выводом: используйте **Bottom Up** или раскрывайте дальше, чтобы увидеть, **кто его вызвал** — скорее всего, какой-то плагин вызвал этот код сервера через событие или API.

### 3.6 Охота за пиками лагов: tickmonitor плюс only-ticks-over

Пики скрываются средними, поэтому официально предлагается специальная комбинация.

Шаг первый — через `tickmonitor` выяснить, «насколько медленно — это аномалия»:

| Команда | Действие |
| --- | --- |
| `/spark tickmonitor` | **Переключатель** системы мониторинга (повторное выполнение выключает) |
| `/spark tickmonitor --threshold <percent>` | Сообщать только о тиках, **превышающих среднюю длительность на указанный процент** |
| `/spark tickmonitor --threshold-tick <milliseconds>` | Сообщать только о тиках **дольше указанного числа миллисекунд** |
| `/spark tickmonitor --without-gc` | Включить мониторинг, но отключить сообщения об активности GC |

Официально указано: порог по умолчанию — **100 %**, то есть сообщается, когда «тик занял вдвое больше среднего». Хотите чувствительнее — уменьшайте, например:

```text
/spark tickmonitor --threshold-tick 50
/spark tickmonitor --threshold-tick 70
```

Шаг второй — через `--only-ticks-over` сэмплировать только эти аномальные тики:

```text
/spark profiler start --only-ticks-over 150
```

Официальный совет: порог **рекомендуется брать от 50 до 100, но обязательно меньше реальной длительности «лагающих» тиков**, иначе вы отфильтруете сами пики. В официальном примере лагающее действие занимало больше 300 миллисекунд, поэтому взяли 150 «с запасом».

В таком отчёте вся «нормальная» игровая работа отфильтрована, остаются сами пики, и горячие точки видны очень ясно.

## 4. Другие инструменты диагностики

| Команда | На какой вопрос отвечает | Когда использовать |
| --- | --- | --- |
| `/spark tps` | Лагает ли сейчас? Каковы TPS, MSPT, CPU? | Первый шаг каждого разбора; сравнение до и после изменения конфигурации |
| `/spark health` | Каково общее состояние (TPS, CPU, память, диск)? | Нужно длительное наблюдение; live dashboard обновляется каждые 10 секунд |
| `/spark health upload` | То же, но нужен статический снимок для передачи | Показать другим, сохранить в архив |
| `/spark health show` | Без браузера, прямо в консоли | Быстро глянуть в среде SSH; с `--memory` или `--network` |
| `/spark ping` | Высокая ли задержка у игроков? Это сеть или тики? | Игроки жалуются на лаги — сначала разделить эти две вещи |
| `/spark profiler start` | На какие методы и плагины уходит время CPU? | После подтверждения, что «действительно лагает» |
| `/spark tickmonitor` | Какие тики аномально медленные? Как часто? | Периодические лаги, пики |
| `/spark gc` | Какова история GC? Часты ли паузы? | Подозрение на память или GC как причину лагов |
| `/spark gcmonitor` | Постоянно следить за GC и сообщать о событиях | Подозрение на пики GC; включить, воспроизвести, выключить |
| `/spark heapsummary` | Какие объекты занимают больше всего в куче? | Подозрение на утечку памяти; результат загружается в просмотрщик |
| `/spark heapdump` | Полный снимок кучи (`.hprof`) | Нужен офлайн-разбор в MAT и подобных; файл очень большой |
| `/spark activity` | Кто недавно пользовался spark и что делал? | При совместном управлении проверить, не сэмплирует ли кто-то другой; `--page <n>` для страниц |

Ниже — несколько деталей, в которых легко ошибиться.

### 4.1 Про GC: /spark gc и /spark gcmonitor

`/spark gc` печатает **историю GC (сборки мусора)** сервера и отвечает на вопрос «замедляет ли GC сервер».

`/spark gcmonitor` — **переключатель** системы мониторинга GC (повторное выполнение выключает). Его ценность в **сопоставлении с лагами**: сначала включите мониторинг, воспроизведите л аг, затем посмотрите, была ли в момент лага соответствующая активность GC. Если время совпадает, направление меняется на память и параметры GC, а не на поиск горячих точек плагинов.

### 4.2 Про память: /spark heapsummary и /spark heapdump

Различие между ними важно:

| Команда | Результат | Назначение |
| --- | --- | --- |
| `/spark heapsummary` | **Сводка** кучи, загружается в просмотрщик | Быстро увидеть, «какой класс объектов занимает больше всего памяти», чтобы судить о подозрении на утечку |
| `/spark heapdump` | Полный файл `.hprof`, записывается на диск | Нужен офлайн-разбор цепочек ссылок профессиональными инструментами |

Опция `/spark heapdump` — `--compress <type>`, поддерживаются `gzip`, `xz`, `lzma`. Официальная документация помечает `--include-non-live` (включать недостижимые объекты) и `--run-gc-before` (попросить JVM сначала выполнить GC) как **устаревшие (deprecated)**; у `heapsummary` параметр `--run-gc-before` также устарел.

:::warn heapdump очень тяжёл
Полный дамп кучи **записывает на диск файл порядка размера кучи**, и процесс вызывает заметную паузу JVM. В продакшене не запускайте его в пиковые часы, сначала проверьте свободное место.
:::

## 5. Как найти проблему по отчёту

### 5.1 Таблица решений

Сначала оговорка: **имена методов меняются вместе с версией, реализацией сервера и набором маппинга**. В официальных примерах просмотрщика используются имена вроде `WorldServer.doTick()`, `WorldServer.tickEntities()` (соответствуют более старым маппингам); в других версиях вы можете увидеть `ServerLevel.tick`, `Level.tickEntities` и подобные. **Не запоминайте имена, смотрите на форму и проценты**, используя автоматическую деобфускацию просмотрщика.

| Явление в отчёте | Вероятный вывод | Следующий шаг |
| --- | --- | --- |
| Имя пакета **какого-то плагина** (например, `com.example.shop`) занимает больше всего в серверном потоке | Этот плагин и есть узкое место | Обновить, найти замену, ограничить частоту срабатывания; отправить ссылку на отчёт автору |
| `Entity.tick` или `Level.tickEntities` (в старом маппинге `WorldServer.tickEntities`) занимает основную долю | **Слишком много сущностей** | См. [Скопление сущностей и выпавших предметов](/tutorials/faq/entity-lag): чистить выпавшие предметы, ограничить спавн, уменьшить дальность прорисовки и связанные с сущностями параметры |
| Вызовы, связанные с чанками (`ChunkMap`, `ChunkGenerator` и др.), занимают основную долю | **Генерация или загрузка чанков** | Сделать предгенерацию карты, снизить генерацию в реальном времени при исследовании новых областей |
| Тик воронок и блочных сущностей (`hopper`, `LevelChunk.tickBlockEntities` и др.) | **Нагрузка редстоуна, воронок и блочных сущностей** | Ограничить скорость воронок, объединить фермы, уменьшить редстоун-машины в постоянно загруженных чанках |
| На ленте времени видны длинные паузы GC | **Память или параметры GC** | Настроить размер кучи и параметры GC; сначала исключить утечку через `heapsummary` |
| Медленно **только один мир или одна область** | Конкретная ферма или постройка | Определить координаты, разобрать на месте, ограничить или вынести на отдельный сервер |
| Доля `waitForNextTick` или sleep очень мала (ниже 5 %) | У сервера в целом нет запаса | Это не точечная проблема, а нехватка мощности: снизить нагрузку или повысить одноядерную производительность |
| Доля sleep высокая, но игроки всё равно жалуются на лаги | Среднее скрывает пики | Идти в раздел 3.6: `tickmonitor` плюс `--only-ticks-over` |

### 5.2 Два частых заблуждения при атрибуции

**Заблуждение первое: увидев метод NMS, думать, что «проблема в сервере».** Методы вроде `Entity.tick` — код сервера, но **вызвать его может плагин, поведение игрока или устройство фермы**; используйте представление Flat с **Bottom Up**, чтобы найти «кто его вызвал».

**Заблуждение второе: делать вывод по одному Total Time.** У метода может быть высокий Total Time просто потому, что он вызывает много дочерних методов (сам он «обёртка»); переключитесь на сортировку по **Self Time** и смотрите методы, **которые действительно тратят время на себя**, — именно их и нужно менять.

### 5.3 Обязательно сравнивайте до и после

Один отчёт показывает только «как сейчас» и не показывает, «помогло ли изменение». Правильный подход:

```text
1. Сэмплирование A: /spark profiler stop --comment "базовая линия до изменений"
2. Сделать и только одно изменение
3. Сэмплирование B в максимально похожих условиях (число игроков, время суток, та же ли область)
4. Сравнить изменение процента одного и того же узла в двух отчётах
5. Если не стало лучше — откатить изменение и проверить следующую гипотезу
```

Меняйте по одной переменной за раз, иначе атрибуция невозможна. При сравнении смотрите **изменение процента одного и того же узла**, а не абсолютные значения — потому что общая длительность сэмплирования и число игроков могут отличаться.

## 6. Практический процесс и замечания

### 6.1 Сэмплирование само имеет цену

spark — сэмплирующий профайлер, его накладные расходы намного меньше инструментирования, но **не нулевые**:

- Фоновый профайлер **включён по умолчанию**, интервал сэмплирования по умолчанию **10 миллисекунд** (параметр `backgroundProfilerInterval`).
- Движок сэмплирования по умолчанию `async` (async-profiler), официально указано, что он точнее движков Java/WarmRoast (не подвержен смещению сэмплирования по safe point) и **используется автоматически при поддержке системой**. Требуется Linux или macOS с архитектурой x86_64/aarch64; в контейнере может понадобиться доустановить `libstdc++`.
- **Анализ распределения (`--alloc`) и heapdump тяжелее**: первому нужны отладочные символы HotSpot (в Java 11 и новее обычно есть), второй пишет большой файл и вызывает паузу JVM.

:::warn Не держите профайлер включённым постоянно
Сэмплирование нужно, чтобы ответить на конкретный вопрос, — сняли и остановили. `--timeout` — самый спокойный способ остановить автоматически. **Постоянно висящий профайлер на уже лагающем сервере только ухудшит ситуацию.**
:::

### 6.2 Передача отчётов и приватность

Официальная документация положительно отзывается о «передаче»: отчёт автоматически загружается в просмотрщик и вы получаете ссылку, **эту ссылку можно свободно передавать** — тому, кто помогает разбираться, или авторам плагинов и модов, чтобы указать на проблему. Механизм закладок кодирует в URL и «я имею в виду эту строку».

Но несколько вещей нужно понимать:

1. **Загрузка — поведение по умолчанию**. `/spark profiler stop` по умолчанию загружает; только `/spark profiler stop --save-to-file` **сохраняет в файл в каталоге конфигурации и не загружает**.
2. **Официальная документация не описывает переключатель «сделать отчёт приватным»**. На сверенных для статьи страницах нет ни слова об управлении доступом или приватных отчётах. Поэтому **относитесь к ссылке на отчёт как к «любой, у кого она есть, может открыть»**.
3. **Исходные данные доступны**. Официальная страница «Raw spark data» указывает: добавив к ссылке `?raw=1`, можно получить метаданные JSON; можно даже запросить исходные данные напрямую по `https://spark-usercontent.lucko.me/<code>` (типы `application/x-spark-sampler`, `application/x-spark-heap`, `application/x-spark-health`). То есть **сам короткий код и есть учётные данные для доступа**.
4. **В метаданных есть сведения о личности**. В официальном примере метаданных есть имя и UUID того, кто запустил. Прежде чем публиковать ссылку в открытом месте, подумайте об этом.
5. **Локальный просмотр**: если не хотите загружать, можно перетащить файл `.sparkprofile` или `.sparkheap` в область перетаскивания на странице просмотрщика и посмотреть локально.
6. Если идёте за помощью, официальная документация PaperMC советует **прийти с отчётом spark в их канал Discord `#paper-help`** (это официально указанный Paper канал).

### 6.3 Чек-лист одного полного сэмплирования

```text
Подготовка
[ ] Убедиться, что загрузился: /spark
[ ] Записать текущее состояние: /spark tps
[ ] Убедиться, что проблема происходит сейчас (иначе ничего не соберётся)
[ ] Убедиться, что места на диске достаточно (особенно если возможен heapdump)
Сэмплирование
[ ] Постоянные лаги    -> /spark profiler start --timeout 60
[ ] Периодические пики -> сначала /spark tickmonitor для поиска порога, затем /spark profiler start --only-ticks-over <ms> --timeout <s>
[ ] Подозрение на асинхронные потоки -> добавить --thread *; подозрение на распределение памяти -> добавить --alloc (дороже)
[ ] Не оставлять его работать бесконечно
Чтение отчёта
[ ] Сначала посмотреть долю sleep в Server thread
[ ] Идти вниз от самого широкого узла, следуя за процентами
[ ] Использовать представление Sources для атрибуции конкретному плагину
[ ] Использовать Flat с Self Time, чтобы найти методы, «действительно тратящие время на себя»
[ ] Использовать Bottom Up, чтобы найти «кто вызвал этот медленный метод»

Выводы и перепроверка

```

### 6.4 Когда spark не нужен

Если у игроков просто высокая задержка, сначала `/spark ping` — возможно, проблема в сетевом пути; если сервер не запускается или падает, смотрите журналы и отчёты о падениях, профайлер здесь не поможет; если TPS в норме, а игроки всё равно говорят «лагает», сначала проверьте, не рендеринг ли клиента, дальность прорисовки или сетевые колебания, а не беритесь сразу за профайлер.
