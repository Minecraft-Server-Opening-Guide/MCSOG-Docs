Миграция — это **перенос всего сервера из одной среды в другую**: на более мощное железо, к другому провайдеру, из дата-центра с плохой сетью или просто ради экономии. Это намного опаснее, чем «поставить новый сервер с нуля»: неудачная установка нового сервера означает лишь временное отсутствие сервера, а **неудачная миграция означает, что старый сервер уже остановлен, а новый не поднимается**.

Статья описывает полный процесс миграции и чек-листы. Какие файлы переносить и какие нельзя трогать — см. [Структура сервера](/tutorials/java/structure); область копирования и учения по восстановлению — см. [Резервное копирование и восстановление](/tutorials/java/backup) и [Резервные копии в другом месте](/tutorials/ops/offsite-backup).

## 1. Когда стоит мигрировать

| Причина | Типичные сигналы | На что особенно обратить внимание при миграции |
| --- | --- | --- |
| Обновление железа | TPS стабильно низкий, памяти не хватает, диск забит по вводу-выводу, а оптимизировать уже некуда | У новой машины одноядерная производительность важнее числа ядер; сначала убедитесь, что узкое место действительно в железе |
| Смена провайдера | Тикеты никто не отвечает, сильная перепродажа, слухи об исчезновении, непрозрачные тарифы | Экспорт данных и соответствие требованиям, плата за исходящий трафик, перед расторжением убедитесь, что новая среда работает |
| Переезд из региона с плохой сетью | Высокая задержка у игроков, сильные обходные маршруты, потери пакетов, нет защиты при DDoS | Качество линии целевого региона нужно **измерять**, а не смотреть на рекламу |
| Снижение затрат | Давит счёт, или давно простаивающая конфигурация слишком велика | Дешёвые машины часто делят CPU и имеют более медленный диск, сначала нагрузочный тест, потом переезд |
| Изменение архитектуры | Один сервер превращается в сеть, добавляется панель, база данных | Это уже не «миграция», а «перестройка + перенос данных», нужен отдельный план |

:::note Что можно решить на месте — не мигрируйте
Каждый шаг миграции несёт риск простоя и потери данных. **Если не хватает только памяти, добавить память дешевле миграции; если только высокая задержка, сначала проверьте, не проблема ли это маршрутизации или конфигурации прокси.** Оставьте миграцию для случаев, которые «действительно не решаются иначе».
:::

## 2. Чек-лист перед миграцией

Самый аварийный этап миграции — не `rsync`, а **«что вообще работало на этой машине, я сам не в курсе»**. Сначала выпишите список, потом действуйте.

| Пункт | Как проверить | Критерий прохождения |
| --- | --- | --- |
| Какие службы работают на машине | `systemctl list-units --type=service --state=running`, `ss -tlnp`, `docker ps`, `crontab -l` | Для каждой можете назвать назначение и знаете, переносить ли её |
| Версия игры и ядра | Журнал запуска сервера, `/version`, имя файла ядра | Записано «версия игры + имя ядра + номер сборки ядра» |
| Список версий плагинов и модов | Список каталогов `plugins/`, `mods/` | Есть файл-список (воспроизводимые версии), а не только сам каталог |
| Версия Java | `java -version` | Одинаковая на старой и новой машине; **обновление Java — отдельная задача, не делайте её вместе с миграцией** |
| ОС и ядро | `cat /etc/os-release`, `uname -a` | Знаете различия (дистрибутив, glibc, файловая система) |
| Записи DNS и TTL | `dig +noall +answer example.com`, `dig _minecraft._tcp.example.com SRV` | Записаны типы (A / AAAA / SRV) и текущий TTL |
| У кого есть доступ | Публичные ключи SSH, аккаунты панели, аккаунт провайдера, список помощников | После миграции **сверить по пунктам**, лишнее удалить |
| Восстанавливаются ли копии | Реально провести учения по восстановлению | Не «есть файл копии», а «**восстанавливали и запускали**» |
| Внешние зависимости | База данных, объектное хранилище, API Key, Webhook, мониторинг | С новой машины доступны, учётные данные действительны |

:::warn Миграция без проверенной копии — это азартная игра
Опечатка в пути у `rsync --delete`, заполненный диск, неверные права, обрезанный архив — любое из этого может привести к тому, что «нет рабочей копии» выяснится уже после остановки сервера. **Перед началом обязательно нужна офлайн-копия с проверенным восстановлением**, и в течение окна обслуживания её нельзя удалять. Сделанная, но не проверенная копия равна отсутствию копии.
:::

## 3. Что обязательно переносить

Каждая строка таблицы ниже — то, что реально упускали в авариях. **Упустить мир — катастрофа, упустить способ запуска — «данные на месте, а служба не поднимается».**

| Пункт | Расположение (на примере `/opt/mcserver`) | Последствия упущения |
| --- | --- | --- |
| Сохранения миров | `world/`, `world_nether/`, `world_the_end/` (имена — по `level-name` из `server.properties`) | **Самые тяжёлые**: постройки, инвентари и прогресс игроков потеряны |
| Сами плагины и моды | `plugins/`, `mods/` | После входа не хватает функций, или клиент игрока не может войти из-за несовпадения модов |
| Конфигурация плагинов и модов | `plugins/<plugin-name>/`, `config/` | Права, экономика, территории, точки телепорта, пулы розыгрышей возвращаются к значениям по умолчанию |
| Конфигурация ядра | `server.properties` | Порты, сложность, проверка лицензии, дальность прорисовки, белый список снова по умолчанию |
| Собственная конфигурация ядра | `bukkit.yml`, `spigot.yml`, `paper-*.yml`, `purpur.yml` | Параметры оптимизации и значения миров по умолчанию потеряны, производительность может заметно измениться |
| Файлы списков | `ops.json`, `whitelist.json`, `banned-players.json`, `banned-ips.json` | Права администраторов потеряны, или блокировки не действуют, белый список фиктивен |
| Кэш имён игроков | `usercache.json` | Обычно восстанавливается, но в офлайн-режиме сопоставление UUID и отображаемых имён ненадолго нарушится |
| Скрипты запуска | `start.sh`, `запуск.bat`, параметры Java | **Самое частое упущение**: служба не поднимается или параметры неверны, что даёт проблемы с памятью и производительностью |
| Unit systemd | `/etc/systemd/system/minecraft.service` | Не стартует после включения, не перезапускается при падении; неверный `WorkingDirectory` ещё и создаст пустой мир |
| Задачи по расписанию | `crontab -l`, `/etc/cron.d/`, systemd timer | Копирование, перезапуски и очистка исчезают, причём **обнаружится это очень нескоро** |
| Правила брандмауэра | `ufw status`, `firewall-cmd --list-all`, группа безопасности облака | Порты закрыты, игроки не подключаются; или старых правил нет и возникает лишняя открытость |
| Сертификаты TLS | `/etc/letsencrypt/`, `/etc/ssl/` | Панель, карта, ресурспаки и другие HTTPS-службы прерываются или появляются предупреждения о сертификате |
| Данные MCDR | `config.yml`, `permission.yml`, `plugins/` в рабочем каталоге MCDR | Права ботов, псевдонимы команд и состояние плагинов потеряны (конкретные имена и структура — по официальной документации MCDR) |
| Данные панели | Собственная конфигурация панели и каталог определений экземпляров | Файлы сервера на месте, а в панели «ничего нет»; подробнее — [Панели управления сервером](/tutorials/ops/panels) |
| Файлы учётных данных | `.env`, `rcon.password`, пароль базы, ключи облачного хранилища | Служба не поднимается или после запуска не подключается к зависимостям |
| Конфигурация обратного прокси | Файлы сайтов и пути сертификатов Nginx / Caddy | Домен отдаёт 502, и это легко принять за «сервер не поднялся» |
| Мониторинг и оповещения | Пробы, агенты, правила оповещений | При проблеме **никто не получает уведомления** — самый опасный «тихий отказ» |

### Что переносить не нужно

| Пункт | Причина |
| --- | --- |
| `logs/`, `crash-reports/` | Большой объём; при разборе старых проблем возьмите отдельно |
| `cache/`, `libraries/`, `versions/` | Пересоздаются при запуске |
| `world/session.lock` | Файл блокировки времени работы, на цели его нужно удалить, сервер создаст свой |
| Временные архивы и `*.tar.gz` на старой машине | Легко синхронизировать вместе с сотнями GB временных файлов |

## 4. Способы миграции

### 4.1 rsync поверх SSH (предпочтительно)

`rsync` передаёт только изменения, сохраняет права и отметки времени, идёт по шифрованному каналу SSH — самый частый способ миграции.

```bash
# Первый раз: «предварительная синхронизация» при работающем сервере, переносим основную массу данных
rsync -aHAX --numeric-ids --delete --info=progress2 \
  --exclude='logs/' \
  --exclude='crash-reports/' \
  --exclude='cache/' \
  --exclude='libraries/' \
  --exclude='versions/' \
  --exclude='session.lock' \
  /opt/mcserver/ \
  mcserver@203.0.113.20:/opt/mcserver/
```

| Опция | Действие |
| --- | --- |
| `-a` | Режим архива (эквивалент `-rlptgoD`): рекурсия с сохранением символических ссылок, прав, времени, группы, файлов устройств |
| `-H` | Сохранять жёсткие ссылки |
| `-A` | Сохранять ACL |
| `-X` | Сохранять расширенные атрибуты (xattr) |
| `--numeric-ids` | Сопоставление по числовым UID/GID, **между машинами обязательно**, иначе владельцы перепутаются |
| `--delete` | Привести цель в соответствие с источником (**палка о двух концах**, случайное удаление в источнике синхронизируется) |
| `--info=progress2` | Показывать общий прогресс (rsync 3.1 и новее) |

**Любую команду с `--delete` первый раз нужно прогонять с `-n` (`--dry-run`) и `-i` (перечисление изменений)**, чтобы убедиться, что она не удалит лишнего:

```bash
rsync -aHAX --numeric-ids --delete -n -i \
  --exclude='logs/' --exclude='cache/' \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

:::warn Слэш в конце исходного пути нельзя ставить наугад
`/opt/mcserver/` (со слэшем) означает «синхронизировать содержимое этого каталога»; `/opt/mcserver` (без слэша) означает «создать на цели каталог `mcserver` и положить туда». **В сочетании с `--delete` ошибка может разрушить всю структуру каталогов на цели.**
:::

### 4.2 tar + scp (малый объём, когда нет rsync)

Если `rsync` нет или данных очень мало, можно упаковывать и передавать через конвейер без промежуточного файла:

```bash
# Выполняется на старой машине: упаковать и распаковать через SSH на новой
tar -C /opt/mcserver -czf - \
  --exclude='logs' --exclude='crash-reports' --exclude='cache' \
  --exclude='libraries' --exclude='versions' --exclude='session.lock' \
  . | ssh mcserver@203.0.113.20 'mkdir -p /opt/mcserver && tar -C /opt/mcserver -xzf -'
```

Можно и сначала создать файл, потом передать:

```bash
tar -czf /tmp/mcserver-2026-10-04.tar.gz -C /opt/mcserver .
scp /tmp/mcserver-2026-10-04.tar.gz mcserver@203.0.113.20:/tmp/
```

Недостатки: **каждый раз полная передача, нет инкрементальности, при обрыве начинать заново**, для сохранений на сотни GB не подходит.

### 4.3 Снимки и копирование томов на уровне провайдера (самое быстрое)

При миграции внутри одного провайдера обычно можно **сделать снимок системного или дискового тома и подключить снимок к новому экземпляру**, либо просто отмонтировать облачный диск от старого экземпляра и подключить к новому. Это на порядки быстрее копирования файлов по сети.

Обязательно учтите:

- **«Согласованность» снимка зависит от того, писал ли сервер на диск в момент снимка.** Для надёжного снимка сначала остановите сервер (или хотя бы `save-all` + `save-off`), после снимка — `save-on`.
- Путь монтирования, имена устройств и UUID файловой системы могут измениться, в `/etc/fstab` нужно использовать UUID или перенастроить, иначе новый экземпляр не запустится.
- Между провайдерами и регионами обычно **нельзя** подключать диск напрямую, остаётся только копирование по сети.
- В снимке остаются ключи хоста SSH старой машины, конфигурация старого IP, учётные данные панели — **после миграции учётные данные нужно ротировать**.

### 4.4 Почему синхронизировать нужно дважды

| Этап | Состояние сервера | Цель |
| --- | --- | --- |
| Первая синхронизация | **Работает** | Перенести десятки и сотни GB имеющихся данных и сократить окно обслуживания с «часов» до «минут» |
| Вторая синхронизация | **Остановлен** | Передать только изменения, чтобы цель совпала с данными на момент остановки |

Во время первой синхронизации сервер продолжает писать, поэтому та копия **сама по себе несогласована** — её ценность лишь в том, что «большая часть файлов уже на месте», а корректность полностью зависит от второй синхронизации. Поэтому:

- Вторая синхронизация **обязательно после остановки**, и после остановки не запускайте старую машину снова (иначе синхронизировать придётся заново).
- `rsync` по умолчанию решает о повторной передаче по «размеру + времени изменения». Для более строгого сравнения по содержимому во второй раз можно добавить `--checksum` (`-c`): **медленнее, но не пропустит файлы «того же размера, с сохранённой отметкой времени, но другого содержимого».**
- После второй синхронизации **проведите ещё одну проверку (см. следующий раздел)**, не открывайте сервер только потому, что «команда не выдала ошибок».

## 5. Окно обслуживания: пошагово

Заранее объявите время обслуживания (указав ожидаемую длительность и компенсацию), затем выполняйте по порядку. **На каждом шаге подтверждайте результат, прежде чем идти дальше.**

1. **Заморозить изменения**: сообщите помощникам, чтобы не меняли конфигурацию и не ставили плагины; убедитесь, что нет запущенных задач копирования или очистки, которые конфликтуют с миграцией.

2. **Ещё раз убедиться, что копия рабочая**: офлайн-копия существует, проверка пройдена, и она **не** лежит на пути, который вы сейчас удалите или перезапишете.

3. **Снизить TTL в DNS**: если ещё не снизили, снизьте до 60 - 300 секунд (изменение вступит в силу после истечения старого TTL, поэтому это нужно делать **за 24 - 48 часов**, см. раздел 6).

4. **Остановить сервер**:

```bash
sudo systemctl stop minecraft
pgrep -a java          # вывода быть не должно, убедитесь, что процесс действительно завершился
```

5. **Финальная синхронизация** (команда из раздела 4.1 без лишних `--exclude` и с `-c`):

```bash
rsync -aHAX --numeric-ids --delete --checksum --info=progress2 \
  /opt/mcserver/ mcserver@203.0.113.20:/opt/mcserver/
```

6. **Проверка**: сгенерируйте список на обеих сторонах и сравните. Пути должны быть **относительными**, иначе имена файлов не совпадут.

```bash
# Старая машина
cd /opt/mcserver && find . -type f -print0 | sort -z | xargs -0 sha256sum > /tmp/old.sha256

# Новая машина (та же команда, вывод в /tmp/new.sha256), затем:
diff /tmp/old.sha256 /tmp/new.sha256 && echo "проверка пройдена"
```

В Windows можно сравнивать файлы через `Get-FileHash -Algorithm SHA256`; при малом объёме достаточно сравнить размер и число файлов:

```powershell
Get-ChildItem -Recurse -File C:\mcserver | Measure-Object -Property Length -Sum
```

7. **Убрать на новой машине остатки времени работы**:

```bash
rm -f /opt/mcserver/world/session.lock
```

8. **Проверить окружение новой машины**: версия Java совпадает со старой (`java -version`), владелец каталогов верный, порт в `server.properties` не конфликтует с другими службами.

9. **Установить и запустить службу**:

```bash
sudo cp minecraft.service /etc/systemd/system/minecraft.service
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft
journalctl -u minecraft -n 50 --no-pager
```

10. **Проверить тем же клиентом**: сначала прямое подключение по новому IP (см. раздел 6), затем проверить ключевые постройки, содержимое контейнеров, инвентари, права и команды плагинов.

11. **Переключить DNS**: убедившись, что новый сервер работает, направить запись на новый IP.

12. **Сохранить старую машину на время**: **не расторгайте договор и не переустанавливайте сразу**, это ваша цель отката (см. раздел 9).

## 6. DNS и переключение

### TTL нужно снижать заранее

У записи DNS есть время кеширования (TTL). Если TTL равен 24 часам, то после переключения **до 24 часов часть игроков будет попадать на старый IP**.

```bash
# Посмотреть текущую запись и TTL
dig +noall +answer mc.example.com
dig +noall +answer mc.example.com AAAA
dig +noall +answer _minecraft._tcp.mc.example.com SRV
```

**Порядок**: за 24 - 48 часов до миграции снизить TTL до 60 - 300 секунд -> дождаться истечения старого TTL -> мигрировать -> переключить запись -> убедившись в стабильности, вернуть TTL к большему значению (чтобы снизить нагрузку на DNS).

### Как тестировать новый сервер до переключения

**Не меняйте DNS, не проверив новый сервер.** Два безопасных способа:

| Способ | Как | Когда подходит |
| --- | --- | --- |
| Файл hosts | На своей машине направить домен на новый IP | Влияет только на вас, подходит владельцу и помощникам для первой проверки |
| Прямое подключение по новому IP | Указать в клиенте `203.0.113.20:25565` | Доступно всем, **не зависит от DNS** |

```text
# Windows: C:\Windows\System32\drivers\etc\hosts
# Linux / macOS: /etc/hosts
203.0.113.20  mc.example.com
```

:::tip Обязательно тестировать «тем же клиентом»
Тестирование с другого компьютера, в другой сети, на другой версии игры — это не реальный опыт игрока. **Подключитесь один раз тем клиентом, которым играете обычно, из той же сети** — только это считается проверкой.
:::

### Не забудьте про SRV-записи

Многие серверы используют SRV-записи, чтобы игрок указывал только домен (без порта). При миграции **нужно изменить и цель SRV**, иначе игроков по-прежнему будет вести на старую машину:

```text
_minecraft._tcp.mc.example.com. 300 IN SRV 0 5 25565 mc.example.com.
```

### Старую машину оставьте как цель отката

После переключения **оставьте её минимум на одно полное окно обслуживания** (обычно 24 - 72 часа, в зависимости от числа игроков и допустимого простоя):

- Держите старую машину **готовой к запуску в любой момент** (конфигурацию, данные и окружение Java не трогайте).
- Но **не** давайте двум машинам одновременно обслуживать один домен — это раздробит данные игроков на два мира, которые потом не слить.
- Если старая машина всё ещё получает запросы по DNS (TTL не истёк), можно **оставить сервер на ней остановленным** и запускать только при необходимости отката.

## 7. IP изменился: какие последствия

Как только IP меняется, всё, что «ориентируется на IP», перестаёт работать. **Если упустить этот раздел, симптом обычно такой: «игроки заходят, но какая-то функция непонятно почему не работает».**

| Что затронуто | Симптом | Что делать |
| --- | --- | --- |
| Белые списки других служб | База данных, объектное хранилище, сторонние API отказывают в подключении | Добавить новый IP в разрешённые, убрать старый |
| Списки разрешённых IP у RCON и панели | Панель показывает экземпляр офлайн, RCON не подключается | Обновить allowlist и панели, и демона (параметры — по официальной документации панели) |
| Брандмауэр и группа безопасности облака | Порты закрыты или обратный прокси не подключается к бэкенду | Добавить правила на новой машине, **на старой закрыть**, чтобы не оставить открытость |
| Сертификаты TLS и обратный прокси | Ошибки HTTPS, несовпадение домена сертификата | Перенести сертификат вместе с машиной или перевыпустить; в прокси заменить upstream на новый IP |
| Geyser / Floodgate и сеть серверов | Игроки Bedrock не заходят, или у всех игроков IP прокси | Конфигурацию пересылки нужно переносить вместе; см. [Начало работы со сторонними ядрами Bedrock](/tutorials/bedrock/third-party-setup) и [Прокси](/tutorials/java/proxy) |
| Списки блокировки IP | Записи в `banned-ips.json` могут указывать на старую среду; либо из-за смены конфигурации пересылки **все игроки показываются как IP прокси, и блокировка одного блокирует весь сервер** | После миграции проверить, работает ли пересылка, и только потом решать про чистку блокировок IP |
| Мониторинг и оповещения | Проба смотрит на старый IP, новый сервер упал — никто не знает | Обновить цели проб и **намеренно вызвать одно оповещение**, чтобы проверить цепочку |
| Задачи копирования | Копирование всё ещё берёт данные со старой машины, или на новой не настроено | См. [Резервное копирование и восстановление](/tutorials/java/backup) и [Резервные копии в другом месте](/tutorials/ops/offsite-backup) |
| Игроки Bedrock в белом списке | Личность игрока Bedrock привязана к XUID и обычно **не зависит от смены IP** | Обычно менять не нужно; но если плагины пересылки или прав зависят от IP, перепроверьте |

:::note Про блокировку по IP
Блокировка по IP в принципе плохо подходит для долгого использования (домашние IP меняются, IP дата-центров переиспользуются). Если до или после миграции вы обнаружили в списке блокировок много IP, **сначала убедитесь, что они ещё актуальны, и только потом решайте, оставлять ли**, не переносите вслепую.
:::

## 8. Чек-лист проверки после миграции

| Пункт | Как проверить | Критерий прохождения |
| --- | --- | --- |
| Игроки могут заходить | Зайти по одному разу реальным клиентом (включая Bedrock, если включена кросс-платформа) | Заходят, пишут в чат, нормально двигаются и взаимодействуют |
| TPS / MSPT в норме | `/tps`, `/spark tps` или собственная команда ядра | Тот же порядок, что на старой машине, нет устойчивых просадок тиков |
| Все плагины и моды загрузились | Поискать в журнале запуска `Enabling`, `Loaded`, ключевые слова ошибок | Нет `Could not load`, нет несовместимости версий |
| Конфигурация действует | Выборочно проверить права, экономику, территории, точки телепорта | Совпадает с состоянием до миграции |
| Списки верны | `/whitelist list`, команды `/op` или прямо посмотреть файлы | Администраторы и белый список совпадают со старым сервером |
| Копирование работает на новой машине | Вручную запустить скрипт копирования | Архив создан, размер разумный, **и он действительно распаковывается** |
| Мониторинг обновлён | Посмотреть панель мониторинга | У нового IP есть heartbeat, оповещения по старому IP отключены |
| Задачи по расписанию | `crontab -l`, `systemctl list-timers` | Копирование, перезапуски и очистка на месте, время верное |
| Производительность и диск | `df -h`, `iostat`, занятая память | Места достаточно, явного узкого места ввода-вывода нет |
| Вывод старой машины | См. ниже | **Только после окончания окна отката** расторгать договор или переустанавливать |

## 9. План отката

Откат — это не «перенести обратно», а «**вернуться в известное рабочее состояние**». Поэтому план отката нужно написать **до** миграции:

1. **Определите условие срабатывания**: при каких обстоятельствах откатываться? (Например: новый сервер не запускается стабильно в течение 2 часов, проверка сохранений не прошла, ключевой плагин не работает, TPS вдвое ниже старой машины и причину найти не удаётся.)
2. **Опишите действия отката**: направить DNS обратно на старый IP -> запустить службу на старой машине -> объявить игрокам -> посмертный разбор.
3. **Сохраните цель отката**: каталог сервера, окружение Java, unit systemd, правила брандмауэра на старой машине **оставить как есть** до конца окна отката.
4. **Подготовьте правило выбора данных**: если новый сервер уже поработал и игроки на нём играли, **прогресс старого мира отстаёт**. Откат означает потерю прогресса за это время либо ручной перенос сохранений нового мира обратно (тогда «новый мир» и есть самые свежие данные). **Это решение нужно принять до отката, а не придумывать по ходу.**
5. **Откат тоже нужно проверять**: перед запуском старой машины убедитесь, что её данные соответствуют моменту остановки (их не изменил скрипт копирования и не удалили по ошибке).

:::warn Худший случай — «обе машины работают»
Если старый и новый серверы одновременно обслуживают домен (например, из-за кеша DNS часть игроков попадает на старый, часть на новый), **данные игроков раздробятся на два мира**. Такое разделение обычно не сливается автоматически, придётся принять потерю одной из частей. **Остановить старый сервер перед переключением — самый простой способ избежать этой аварии.**
:::

## 10. Итог

- **Сначала инвентаризация, потом действия**: провал миграции чаще не техническая проблема, а «забыл, что у меня ещё работает».
- **Копия должна быть проверена**: непроверенная копия — не копия, а психологическое успокоение.
- **Две синхронизации**: одна прогревочная (при работающем сервере), одна финальная (после остановки), между ними не перезапускайте старый сервер.
- **Сначала тест, потом переключение**: проверьте новый сервер через hosts или прямым подключением по IP, и только потом меняйте DNS.
- **TTL снижается заранее**: это единственный шаг, который «обязательно делать заранее», снизить TTL в последний момент уже не успеть.
- **Сохраните цель отката**: старая машина — не мусор, это ваш путь назад.
