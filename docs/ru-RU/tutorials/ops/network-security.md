Если к серверу могут подключиться другие, значит **его точно так же могут просканировать**. С первого дня работы ваш публичный IP будут перебирать сканеры портов, скрипты брутфорса и инструменты «широкого посева» — **не потому, что вы кому-то досадили, а просто потому, что вы торчите в интернете**.

Эта статья о защите на сетевом уровне: **какие порты открывать, как настроить firewall, как усилить SSH и что делать, когда по вам ударили**. Усиление внутри системы — в статье [Усиление безопасности системы](/tutorials/ops/system-security).


:::warn Контейнеры Docker обходят локальный firewall
Все правила `ufw` / `firewalld` из этой статьи **не действуют на порты, проброшенные контейнерами Docker**. Docker вставляет свои правила `iptables` перед системным firewall, поэтому `ufw deny` не остановит доступ к порту контейнера.

Чтобы действительно ограничить доступ, привяжите порт к loopback (`-p 127.0.0.1:25565:25565`) или используйте цепочку `DOCKER-USER`. Подробности — в статье [Развёртывание Java Edition в Docker → Сеть и firewall](/tutorials/java/docker).
:::

## 1. Сначала оцените поверхность атаки

### 1.1 Порты, которые действительно нужно открыть

| Назначение | Протокол | Порт по умолчанию | Открывать ли в интернет |
| --- | --- | --- | --- |
| **Minecraft Java Edition** | TCP | `25565` | Да (вход для игроков) |
| **Bedrock / Geyser** | UDP | `19132` | Да (нужен для кросс-платформенного сервера) |
| **Протокол query** | UDP | `25565` | Обычно не нужен |
| **Удалённая консоль RCON** | TCP | `25575` | **Никогда** |
| **База данных** (MySQL / MariaDB) | TCP | `3306` | **Никогда** |
| **Redis** | TCP | `6379` | **Никогда** |
| **Панель** (различные веб-панели управления) | TCP | Зависит от панели | **Никогда** |
| **SSH** | TCP | `22` | Да, но **с ограничением источника** |

:::warn Значения по умолчанию могли быть изменены
Таблица выше — **заводские значения по умолчанию** соответствующего ПО. Если вы меняли `server-port`, `query.port`, `rcon.port` в `server.properties` или порт прослушивания в панели, **ориентируйтесь на свою фактическую конфигурацию**. Правила firewall должны совпадать с реальными портами, иначе либо не подключиться, либо останется дыра.
:::

### 1.2 О RCON и базе данных: почему их нужно жёстко закрыть

- **RCON — это «права администратора без интерфейса»**. Один пароль даёт возможность выполнять в консоли произвольные команды. Если открыть его в интернет, атакующий сразу выдаст `op` себе, очистит сохранения и выкинет всех игроков. **Правильно — `enable-rcon=false`, а для удалённого управления использовать SSH-туннель или панель через локальный loopback.**
- **Открытый порт базы данных — самый частый вход для утечки данных**. Если MySQL разрешает `root` вход с любого хоста (`root@%`), слабый пароль взломают за считаные минуты, и утекут аккаунты игроков, хеши паролей и история покупок.
- **Открытый порт панели равноценен вывешиванию управления всей машиной в интернет**. У панели есть страница входа, но и она может иметь уязвимости, к тому же панель обычно работает с повышенными правами.

Один базовый принцип: **любой порт, который не «для игроков», не должен быть открыт в интернет.** Если нужен удалённый доступ для себя — используйте SSH-туннель (см. раздел 4), а не прямое выставление порта.

### 1.3 Две вещи, которые стоит сделать заодно

- **Проверьте адрес прослушивания**: база данных, панель и RCON должны слушать `127.0.0.1`, а не `0.0.0.0`. После привязки к loopback даже при ошибке в firewall снаружи подключиться не получится.
- **Проверьте `online-mode`**: в Java Edition держите `online-mode=true` (`server.properties`). Офлайн-режим позволяет любому выдать себя за чужой ID — это дыра на уровне идентификации, firewall её не закроет. Подробности — в статье [Настройка сервера](/tutorials/java/config).

## 2. Firewall — это два уровня, а не один

Именно это новички упускают чаще всего:

| Уровень | Где находится | Кто управляет | Пример |
| --- | --- | --- | --- |
| **Группа безопасности облака / сетевой ACL** | На стороне облачной платформы, трафик **ещё не дошёл до вашей машины** | Консоль облачного провайдера | Группы безопасности Alibaba Cloud, Tencent Cloud, AWS Security Group |
| **Firewall хоста** | Внутри ОС, `netfilter` / `nftables` | Вы сами на машине | `ufw`, `firewalld`, `iptables`, `nftables` |

**Настраивать нужно оба уровня.** Если настроить только группу безопасности, защита исчезнет при переносе машины в другую сеть или расширении группы; если только firewall хоста, то во многих облаках группа безопасности по умолчанию и так широка, то есть первая дверь остаётся открытой.

:::warn Конкретные пути в облачной консоли здесь не приводятся
Названия меню, уровни и терминология у облачных провайдеров различаются («группа безопасности», «firewall», «сетевой ACL» используются вперемешку), **поэтому статья не угадывает конкретные пути в меню**. Ориентируйтесь на официальную документацию вашего провайдера. Точно можно сказать одно: **входящие правила (ingress) по умолчанию должны запрещать всё, кроме перечисленных вами портов.**
:::

### 2.1 ufw (обычно в Ubuntu / Debian)

`ufw` — фронтенд к `iptables` / `nftables`, подходит для одиночной машины.

```bash
sudo apt update
sudo apt install -y ufw

# Важно: сначала разрешите SSH, потом включайте запрет по умолчанию, иначе запрете дверь перед собой
sudo ufw allow from 203.0.113.10 to any port 22 proto tcp

sudo ufw default deny incoming
sudo ufw default allow outgoing

sudo ufw allow 25565/tcp
sudo ufw allow 19132/udp

sudo ufw enable
sudo ufw status verbose
```

`sudo ufw status verbose` выводит текущую политику и правила; в норме вы увидите `Default: deny (incoming), allow (outgoing)` и свои разрешённые записи.

**Порядок важен**: если сначала выполнить `sudo ufw enable`, а потом разрешать SSH, и ваше соединение как раз оборвётся, попасть на машину можно будет только через VNC / консоль аварийного доступа облачной платформы.

### 2.2 firewalld (обычно в RHEL / Rocky / AlmaLinux / Fedora)

```bash
sudo dnf install -y firewalld
sudo systemctl enable --now firewalld

sudo firewall-cmd --permanent --add-port=25565/tcp
sudo firewall-cmd --permanent --add-port=19132/udp

# Разрешить SSH только с административного IP
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="203.0.113.10" port port="22" protocol="tcp" accept'

sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

`--permanent` пишет в постоянную конфигурацию, и **изменения вступают в силу только после `--reload`** (или перезапуска firewalld). Изменения без `--permanent` действуют только в рантайме и исчезают после перезапуска — у обоих способов есть применение, но не смешивайте их, думая, что всё настроено.

### 2.3 iptables (традиционный способ)

```bash
# Разрешить установленные соединения и loopback
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -i lo -j ACCEPT

# Разрешить SSH только с административного IP
sudo iptables -A INPUT -p tcp -s 203.0.113.10 --dport 22 -j ACCEPT

# Вход для игроков
sudo iptables -A INPUT -p tcp --dport 25565 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 19132 -j ACCEPT

# Запрет по умолчанию
sudo iptables -P INPUT DROP
sudo iptables -P FORWARD DROP
```

Правила `iptables` **по умолчанию не сохраняются** и теряются при перезапуске. Чтобы сохранить:

```bash
sudo apt install -y iptables-persistent
sudo netfilter-persistent save
```

### 2.4 nftables (современный способ)

```bash
sudo nft add table inet filter
sudo nft add chain inet filter input '{ type filter hook input priority 0; policy drop; }'
sudo nft add rule inet filter input ct state established,related accept
sudo nft add rule inet filter input iif lo accept
sudo nft add rule inet filter input ip saddr 203.0.113.10 tcp dport 22 accept
sudo nft add rule inet filter input tcp dport 25565 accept
sudo nft add rule inet filter input udp dport 19132 accept
```

:::note В современных дистрибутивах ufw и firewalld внутри себя используют nftables
На новых ядрах и в новых дистрибутивах `ufw` / `firewalld` по умолчанию используют бэкенд `nftables`. **Не включайте два фронтенда одновременно** (например, `ufw` и `firewalld` сразу): они перекрывают правила друг друга, и разбираться в этом крайне мучительно. **Выберите один и настройте до конца.**
:::

### 2.5 «Открыть порт» и «ограничить источник» — разные вещи

| Запись | Смысл | Риск |
| --- | --- | --- |
| `sudo ufw allow 22/tcp` | **Подключиться к порту 22 может кто угодно** | Весь мир может брутфорсить ваш SSH |
| `sudo ufw allow from 203.0.113.10 to any port 22 proto tcp` | **К порту 22 может подключиться только `203.0.113.10`** | Если этот IP изменится, придётся менять правило |

Для входа игроков (`25565`) **придётся** открыть источник всем, потому что игроки приходят отовсюду. А для SSH, панели, RCON и базы данных — сервисов **только для вас** — **источник нужно ограничивать всегда**.

:::tip Что делать без фиксированного IP
Публичный IP домашнего интернета меняется. Варианты: заказать статический IP у провайдера, использовать VPN / бастион облачного провайдера или применять SSH-ключи + fail2ban для снижения риска. **Учтите: ограничение SSH до изменяющегося IP оставит вас без доступа после смены IP** — обязательно заранее убедитесь, что у облачной платформы есть аварийный VNC-доступ.
:::

## 3. Усиление SSH

SSH — вход для управления и самый брутфорсимый порт. Рекомендуемый порядок: **сначала убедитесь, что вход по ключу работает, и только потом отключайте вход по паролю**.

### 3.1 Сначала настройте вход по ключу

Сгенерируйте ключ на своей машине (если его ещё нет):

```bash
ssh-keygen -t ed25519 -C "mc-admin"
```

Скопируйте публичный ключ на сервер:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub mcadmin@203.0.113.10
```

**Проверка**: откройте новый терминал, убедитесь, что вход по ключу успешен, и только потом переходите к следующему шагу.

### 3.2 Измените конфигурацию sshd

Отредактируйте `/etc/ssh/sshd_config` (через `sudo`):

```ini
PubkeyAuthentication yes
PasswordAuthentication no
PermitRootLogin no
KbdInteractiveAuthentication no
```

| Параметр | Назначение |
| --- | --- |
| `PubkeyAuthentication yes` | Разрешает аутентификацию по публичному ключу (основа входа по ключу) |
| `PasswordAuthentication no` | **Отключает аутентификацию по паролю**, скрипты брутфорса теряют цель |
| `PermitRootLogin no` | **Запрещает прямой вход под root**, атакующему сначала придётся угадать обычное имя пользователя |
| `KbdInteractiveAuthentication no` | Отключает клавиатурную интерактивную аутентификацию, чтобы не обойти `PasswordAuthentication no` |

:::warn После правки обязательно проверьте синтаксис и только потом перезагружайте
Сначала проверьте синтаксис командой `sudo sshd -t`, и только **после успешной проверки** выполняйте `sudo systemctl reload ssh` (в части дистрибутивов — `sshd`). Если перезапустить SSH с ошибочной конфигурацией, вы можете оказаться полностью заблокированы снаружи.
:::

**Проверка действующих значений** (конфигурация может перекрываться фрагментами из `Include`):

```bash
sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin|pubkeyauthentication'
```

:::note Синтаксис конфигурации зависит от версии
Новые OpenSSH поддерживают фрагменты `.conf` в `/etc/ssh/sshd_config.d/`, и **настройки во фрагментах обычно имеют приоритет над основным файлом**. Если в вашем дистрибутиве такой каталог есть, перед правкой выполните `ls /etc/ssh/sshd_config.d/` и проверьте перекрывающие записи. **Конкретный приоритет — по фактическому выводу `sshd -T` на вашей системе и официальной документации OpenSSH.**
:::

### 3.3 Смена порта по умолчанию: необязательно, эффект ограничен

Сменить порт SSH с `22` на другой (например, `2222`):

```ini
Port 2222
```

**Что это даёт**: автоматические сканеры в основном проверяют только `22`, и смена порта заметно сокращает шум в логах и бесполезный брутфорс.

**Чего это не даёт**: **это не мера безопасности**. Целенаправленное сканирование найдёт ваш SSH на любом порту. Поэтому смена порта **не заменяет** вход по ключу и ограничение источника.

Если меняете порт, не забудьте синхронно обновить правила firewall и **сохраняйте разрешение старого порта, пока новый не проверен**, иначе снова заблокируете себя.

### 3.4 fail2ban: необязательное дополнение

**Идея**: fail2ban читает логи, замечает, что некоторый IP за короткое время много раз провалил аутентификацию, и **временно** блокирует его правилом firewall.

**Ключевое понятие — jail**: один jail = один лог + набор правил сопоставления + набор параметров блокировки. Включаемые jail пишутся в `.conf` в `/etc/fail2ban/jail.d/` или в `/etc/fail2ban/jail.local`.

```ini
[sshd]
enabled = true
port = ssh
backend = systemd
maxretry = 5
findtime = 10m
bantime = 1h
```

- `maxretry`: допустимое число неудач; `findtime`: окно подсчёта; `bantime`: длительность блокировки.
- `backend = systemd` подходит для современных дистрибутивов, где логи собирает systemd-journald; если в вашем дистрибутиве пишется `/var/log/auth.log`, нужно по официальной документации заменить на соответствующий `logpath`.

```bash
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

:::warn Не считайте fail2ban талисманом
- Он блокирует только IP, которые **уже провалились**, это **постфактум**, и первую волну попыток он не останавливает.
- **Блокировка не того IP запрёт вас самих**, не ставьте `bantime` слишком большим (например, на месяцы).
- Параметры и значения по умолчанию **зависят от дистрибутива и версии**; выше приведён лишь распространённый вариант, сверяйтесь с официальной документацией вашей версии.
- Установка fail2ban **не даёт** права снова включить `PasswordAuthentication`.
:::

## 4. DDoS и злоупотребления: что вы можете и чего не можете

### 4.1 Почему бьют по игровым серверам

- **Порог входа крайне низкий**: атаки продаются по объёму, несколько долларов за раз.
- **Мотивы простые**: конкуренция, месть игроков, просто «ради интереса» или случайное попадание под сканер.
- **Игровые серверы особенно хрупки**: Minecraft — это **долгие соединения с состоянием**, и одно рукопожатие TCP уже занимает ресурсы сервера. Та же полоса, направленная на веб-сервис, может лишь замедлить его, а игровой сервер — заклинить или уронить.

### 4.2 Что вы можете

| Средство | Описание |
| --- | --- |
| **Защита у upstream / провайдера** | Облачные провайдеры обычно дают базовую очистку DDoS. **Это самый эффективный уровень**, потому что трафик обрабатывается до того, как дойдёт до вашей машины. |
| **Ограничение скорости и числа соединений** | Ограничение числа соединений и скорости новых подключений с одного IP на уровне firewall или обратного прокси отсекает слабые флуды. |
| **Скрытие источника через прокси** | Игроки подключаются к прокси, а реальный сервер принимает только соединения прокси (в связке с ключом пересылки). См. [Прокси](/tutorials/java/proxy). |
| **Белый список / модерация на входе** | Самый радикальный метод для небольших серверов: **незнакомый человек просто не подключится**. |
| **Ограничение на уровне приложения** | Ограничение частоты подключений на уровне сервера или плагина снижает нагрузку от «зашёл и сразу отключился». |

### 4.3 Чего вы не можете и одно частое заблуждение

:::warn «Забанить IP атакующего» бесполезно против объёмных атак
Это самое распространённое заблуждение. Объёмная атака (volumetric) характеризуется так:

- Исходные IP **тысячами и постоянно меняются** (многие — с заражённых устройств), забанить все невозможно;
- **Ваш firewall находится после атакующего трафика** — к моменту, когда правило блокировки сработает, полоса уже забита. В момент, когда канал забит, ваша машина не справится даже с «выполнением правила блокировки».

**Вывод**: блокировка IP работает против отдельного назойливого человека, но против объёмных атак практически бесполезна. **Решает только очистка на стороне upstream**, а значит: **при выборе услуги смотрите условия DDoS-защиты у провайдера**, а не ищите решение в день удара.
:::

:::note Что делать в первую очередь при ударе
1. **Убедитесь, что это действительно атака**: посмотрите график полосы, число соединений, CPU, отличите «удар» от «своего бага с бесконечным циклом».
2. **Свяжитесь с провайдером**: опишите ситуацию, спросите, включилась ли очистка, нужна ли смена IP.
3. **Сначала выживание**: при необходимости временный белый список, лишь бы сервер остался жив.
4. **Сохраните доказательства**: логи и графики трафика пригодятся для обращения к провайдеру.
:::

## 5. Гигиена ключей и учётных данных

В каталоге сервера лежит масса чувствительной информации: пароль RCON в `server.properties`, пароль базы данных, аккаунт панели, API Key облачного провайдера.

| Правило | Как делать |
| --- | --- |
| **Никогда не коммитить в Git** | Конфигурации с паролями, `.env`, файлы ключей — всё в `.gitignore`. **Один коммит равен постоянной утечке**: значение остаётся в истории. |
| **Ужесточить права на файлы с учётными данными** | `chmod 600` (только владелец читает и пишет), при необходимости `chmod 640` (владелец читает и пишет, группа только читает). |
| **Использовать файл окружения, а не хардкод** | Кладите чувствительные значения в файл вроде `.env`, код читает только переменные окружения. |
| **Утекло — меняйте, а не «просто удаляйте»** | Удаление файла **не** делает утёкший пароль недействительным. **Нужно перегенерировать / отозвать его в соответствующем сервисе.** |

```bash
# Файл с учётными данными только для владельца
chmod 600 /opt/mcserver/survival/.env

# Проверить права
ls -l /opt/mcserver/survival/.env
# Ожидаемый вывод примерно такой: -rw------- 1 mcserver mcserver ... .env
```

:::warn Порядок действий после утечки пароля
1. **Немедленно ротировать**: сбросить пароль / отозвать ключ в соответствующем сервисе (именно это останавливает кровотечение).
2. **Оценить масштаб**: посмотреть логи и убедиться, использовали ли утёкшее значение.
3. **Очистить историю**: удалить из истории Git (`git filter-repo` и подобные инструменты), но **не надейтесь, что это исправит уже утёкшее значение**.
4. **Разобрать причины**: почему это попало в коммит? Добавьте `.gitignore`, добавьте проверку перед коммитом.
:::

Для паролей базы данных также соблюдайте: **отдельный аккаунт для каждого сервиса** (не используйте везде `root`), **выдавайте права только на нужные базы**, **ограничивайте источник локальной машиной или внутренней сетью**.

## 6. Мониторинг: как заметить, что вас пробуют

**Вам не нужно смотреть в экран круглосуточно**, но нужно знать, «где видно аномалию».

### 6.1 На что смотреть

| Место | Что видно |
| --- | --- |
| `/var/log/auth.log` (Debian / Ubuntu) | Успешные и неуспешные входы по SSH |
| `/var/log/secure` (семейство RHEL) | То же самое |
| `journalctl -u ssh` | Логи SSH, собранные systemd |
| `sudo fail2ban-client status sshd` | Текущее число и список заблокированных IP |
| `sudo lastb` | Неудачные попытки входа (**нужен root, и часть систем по умолчанию их не пишет**) |
| `ss -tlnp` | Текущие слушающие порты, помогает найти случайно открытые сервисы |

```bash
# Посмотреть недавние неудачи SSH (Debian / Ubuntu)
sudo grep 'Failed password' /var/log/auth.log | tail -n 20

# Посчитать IP-источники с наибольшим числом неудач
sudo grep 'Failed password' /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head

# Посмотреть, кто слушает порты
sudo ss -tlnp
```

### 6.2 Что считается аномалией

- **Много `Failed password` за короткое время**: типичный брутфорс.
- **Успешный вход в неизвестное вам время / с неизвестного IP**: **самый опасный сигнал**, значит учётные данные могли утечь.
- **Появился пользователь, которого вы не создавали**: возможно, уже заведён бэкдор-аккаунт.
- **Незнакомый слушающий порт**: возможно, установлен майнер или бэкдор.
- **Аномально высокие CPU / трафик при отсутствии игроков**: возможно, машину используют как источник атак.

:::tip Пусть логи дежурят вместо вас
Если не хочется каждый день читать логи, используйте `logwatch`, периодические сводки `journalctl` или просто настройте оповещения на ключевые события. **Главное, чтобы кто-то смотрел** — логи, которые никто не читает, равны отсутствию логов.
:::

## 7. Чек-лист перед запуском

- [ ] **Оба уровня** — группа безопасности облака и firewall хоста — настроены, входящие по умолчанию запрещены
- [ ] Открыты только фактически нужные порты (Java `TCP 25565`, Bedrock / Geyser `UDP 19132`)
- [ ] `enable-rcon` остаётся `false`, либо RCON слушает только `127.0.0.1`
- [ ] Порты базы данных и панели **не открыты в интернет**
- [ ] SSH настроен на вход по ключу, `PasswordAuthentication no` и `PermitRootLogin no` действуют (проверено через `sshd -T`)
- [ ] SSH ограничен по IP источника либо хотя бы прикрыт fail2ban
- [ ] Права на файлы с паролями `600` и они **не лежат в репозитории Git**
- [ ] `online-mode` остаётся `true` (если только вы явно не понимаете цену офлайн-режима)
- [ ] Вы знаете условия DDoS-защиты провайдера и к кому обращаться при ударе
- [ ] Достижимость портов проверена **с внешней машины**
