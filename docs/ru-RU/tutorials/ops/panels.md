Предыдущие статьи были про «вы входите на машину и сами вводите команды». Эта статья про другой частый способ эксплуатации: **отдать сервер под управление веб-панели** — открываете браузер и запускаете экземпляры, смотрите консоль, передаёте файлы, правите конфигурацию.

Панель действительно удобна, но это **служба с самыми большими правами на машине и самая вероятная цель атаки**. Поэтому статья не про «что умеет панель», а про **что добавляется к поверхности атаки после её установки и как эту поверхность вернуть**.

:::note О чём эта статья
Статья описывает только **способ использования и границы безопасности** и не заменяет официальную документацию по установке конкретных панелей. Команды установки, порты по умолчанию и структура каталогов **берутся из официальной документации**; здесь приведены только сверенные с официальными источниками значения по умолчанию с указанием источника.
:::

## 1. Что умеет панель и какова цена

### 1.1 Что обычно предоставляет панель

| Возможность | Как проявляется | Когда действительно экономит время |
| --- | --- | --- |
| **Веб-интерфейс управления** | Запуск, остановка, перезапуск и состояние в браузере, без запоминания команд | Экстренный перезапуск с телефона |
| **Управление несколькими экземплярами** | Несколько серверов на одной машине, единое переключение | Выживание, творческий и тестовый серверы одновременно |
| **Доступ к консоли** | Живой журнал и отправка команд на веб-странице | Удалённый разбор причины падения |
| **Файловый менеджер** | Загрузка, скачивание и правка jar, конфигурации и файлов мира | Смена сборки у игроков, установка плагинов |
| **Задачи по расписанию** | Перезапуск, копирование и команды по расписанию | Ночной перезапуск для освобождения памяти |
| **Пользователи и субпользователи** | Выдача администраторам и помощникам прав на часть экземпляров | Помощник перезапускает сервер, но не получает SSH |
| **Статистика ресурсов** | Графики CPU, памяти, диска и онлайна | Понять, дело в конфигурации или в нехватке машины |
| **Интеграция с Docker** | Изоляция экземпляров контейнерами и ограничение ресурсов | Экземпляры не мешают друг другу |

:::note Набор функций зависит от панели
Таблица выше — общие возможности «класса панелей»; **предоставляет ли их конкретная панель и где находится вход — по официальной документации этой панели и вашему реальному интерфейсу**.
:::

### 1.2 Список цен

| Цена | Пояснение |
| --- | --- |
| **Появляется ещё одна служба для обслуживания** | Сама панель — веб-приложение: её нужно обновлять, читать её бюллетени безопасности, копировать её собственные данные |
| **Растёт поверхность атаки** | Ещё один прослушиваемый порт, ещё одна система аккаунтов, ещё один API |
| **Права сильно концентрируются** | Панель (особенно демон) может запускать произвольные процессы и читать/писать каталоги экземпляров; получив её, получаешь все серверы на машине |
| **Обратный прокси сложнее** | Панели часто нужен WebSocket; некоторые требуют прямого подключения браузера к демону (см. 3.1) |
| **Растёт поверхность отказов** | Падение панели не равно падению сервера, но вы можете временно потерять средства управления |

:::warn Риск в одной фразе
**Панель — не «ещё одна программа», а «главный выключатель всех игровых серверов на машине».** Если её страница входа открыта в интернет, значит управление всей машиной висит в интернете.
:::

### 1.3 Сначала очертите границу доверия

Прежде чем использовать панель, проведите эту линию мысленно:

- **Что контролирует панель = что может контролировать пользователь, от имени которого она работает.**
- Если панель работает от root, любая уязвимость удалённого выполнения кода в ней равна захвату всей машины.
- **API демона сам по себе и есть интерфейс «выполнить команду»** — в этом его смысл. Поэтому, оказавшись открытым, он равносилен shell в интернете.

## 2. MCSManager (MCSM)

### 2.1 Официальное позиционирование

Официальный репозиторий MCSManager описывает себя так: **«быстрая установка, распределённая архитектура, многопользовательский, современный панель управления игровыми серверами Minecraft и Steam»** (в англоязычной версии «Quick deployment, distributed, multi-user, modern management panel for Minecraft and Steam game servers»). Официальная документация уточняет: это **открытая, распределённая, разворачиваемая одной командой** панель управления игровыми серверами Minecraft и Steam, позволяющая централизованно управлять несколькими физическими серверами, создавать игровые серверы на любом хосте и предоставляющая надёжную систему прав для нескольких пользователей.

Три ключевых слова из этого описания и есть его позиционирование:

| Ключевое слово | Смысл |
| --- | --- |
| **Развёртывание одной командой** | Есть скрипт установки, который сам регистрирует службу в системе |
| **Распределённость** | Одна панель может управлять **несколькими** машинами |
| **Многопользовательскость** | Встроенные аккаунты и права позволяют давать права помощникам вместо SSH |

### 2.2 Архитектура: одна панель + один или несколько демонов

Официальная документация делит MCSManager на две части:

| Компонент | Обязанности по официальному описанию |
| --- | --- |
| **Panel (веб-панель)** | Управление пользователями, подключение к демонам, аутентификация большинства операций, API |
| **Daemon (демон)** | Управление процессами (там, где реально работают экземпляры), управление образами Docker, файлами, обмен с живым терминалом |

Здесь и раскрывается смысл «распределённости»: **сама панель серверы не запускает**, она отправляет команды демонам на машинах, и демон запускает и ведёт экземпляры локально. Поэтому возможна схема «одна панель + N узлов с демонами».

:::warn Имена компонентов, команды установки, порты по умолчанию и структура каталогов — по официальной документации
Имена служб, адрес скрипта установки, порты по умолчанию и каталоги данных MCSManager могут меняться вместе с версией. **Приведённые ниже значения отражают только состояние официальной документации на момент написания, ориентируйтесь на официальную документацию и фактический файл конфигурации на вашей машине.** В продакшене не копируйте ни один непроверенный порт или путь.
:::

**Значения по умолчанию, сверенные с официальной документацией (для сверки, всё равно рекомендуется проверить):**

| Пункт | Значение по умолчанию в официальной документации | Замечание |
| --- | --- | --- |
| Веб-порт панели | `23333` | Меняется через `httpPort` в конфигурации веб-панели |
| Порт демона | `24444` | Меняется через `port` в конфигурации демона |
| Имена служб Linux | `mcsm-web`, `mcsm-daemon` | Службы systemd |
| Каталог установки скриптом | `/opt/mcsmanager` | Путь из официального примера |
| Конфигурация веб-панели | `<каталог установки веб-панели>/data/SystemConfig/config.json` | Содержит `httpPort`, `httpIp`, `loginCheckIp` и др. |
| Конфигурация демона | `<каталог установки демона>/data/Config/global.json` | Содержит `port`, `key`, `defaultInstancePath` и др. |
| Ключ демона | Поле `key` в том же `global.json` | Демон также печатает его при запуске |

:::tip Одно официальное предупреждение, которое очень легко упустить
В официальной документации по «распределённому развёртыванию» прямо сказано: на узле, где работает только демон, **нужно сначала остановить и отключить веб-службу**, иначе **любой сможет зайти на страницу начальной настройки и захватить ваш сервер**:

```bash
systemctl stop mcsm-web
systemctl disable mcsm-web
```

Это предупреждение стоит запомнить отдельно: **«забытая веб-служба» — это полноценный захват машины.**
:::

### 2.3 Установка и первый вход

Официальный скрипт установки для Linux одной командой (документация подчёркивает: поскольку служба регистрируется в системе, **запускать нужно от root**):

```bash
sudo su -c "wget -qO- https://script.mcsmanager.com/setup.sh | bash"
```

:::note В китайской и английской документации адреса скриптов разные
В официальной английской документации используется `setup.sh`, в китайской — `setup_cn.sh`. **Ориентируйтесь на адрес, указанный в документации вашего языка**, не набирайте URL скрипта по памяти. В официальной документации есть также разделы про установку в Docker и изоляцию окружения (Docker), конкретные шаги — по официальной документации.
:::

После установки запустите обе службы по официальной документации (обе обязательны):

```bash
# Сначала демон, затем веб-служба
systemctl start mcsm-daemon.service
systemctl start mcsm-web.service

# Если нужен автозапуск при включении
systemctl enable mcsm-web.service
systemctl enable mcsm-daemon.service
```

При ручной установке официальная документация приводит запуск через `./install.sh`, `./start-daemon.sh`, `./start-web.sh` и предупреждает, что ручной запуск нужно держать под управлением чего-то вроде screen, иначе после отключения SSH процесс завершит система. Для Windows официально описано: скачать архив, распаковать и запустить (если в архиве есть лаунчер, можно запустить и его).

**Что обязательно сделать при первом входе (порядок не меняйте):**

1. Войти в панель под администратором (данные начального аккаунта — по официальной документации и выводу установки).
2. **Немедленно сменить пароль по умолчанию** и использовать длинный пароль, отличный от других сайтов.
3. Спрятать панель за HTTPS-обратным прокси по способу из 3.5 или хотя бы ограничить исходные IP.
4. Проверить адрес прослушивания и порт, убедиться, что демон не открыт напрямую в интернет.

### 2.4 Типичный рабочий процесс: от установки до запущенного экземпляра

Официальная документация «Сборка Java Edition» приводит примерно такой порядок (детали — по документации):

| Шаг | Что делать | Замечание |
| --- | --- | --- |
| 1 | Установить панель + демон (или по документации через Docker) | На узле оставить только службу демона |
| 2 | Войти и сменить пароль по умолчанию | См. 2.3 |
| 3 | Подтвердить или добавить узел демона в панели | Нужны адрес и ключ; по документации адрес поддерживает IP, домен, а также префиксы `ws://` / `wss://` |
| 4 | На странице «Экземпляры» нажать «Создать» | Можно установить из маркетплейса либо «создать напрямую» и выбрать узел |
| 5 | Заполнить команду запуска | Официальный пример: `java -Dfile.encoding=UTF-8 -jar "paper-<version>.jar"`, можно добавить `-Xms` / `-Xmx` |
| 6 | Загрузить файлы сервера | Через «Файловый менеджер» панели загрузить jar ядра |
| 7 | В консоли экземпляра нажать «Запустить» и смотреть журнал | При первом запуске обычно нужно в «Файлах конфигурации» поменять `eula.txt` на `eula=true` |
| 8 | Создать субаккаунт для помощника, дав права только на нужные экземпляры | Не давайте «все экземпляры + управление файлами» |

Официальная документация также указывает: данные экземпляра по умолчанию находятся в `<каталог установки демона>/data/InstanceData/<instance-id>/`, конфигурация экземпляра — в `<каталог установки демона>/data/InstanceConfig/<instance-id>.json` (в ней команда запуска и другие параметры). **Это два места, которые «потеряв, трудно восстановить», их обязательно включать в резервные копии.**

:::warn Не жадничайте с параметрами памяти в команде запуска
Официальная документация специально предупреждает: **не отдавайте JVM всю память машины**, операционной системе тоже нужны ресурсы, иначе возможна гибель всей машины. `-Xmx` должен быть заметно меньше физической памяти.
:::

### 2.5 Когда панель действительно помогает

- **Много экземпляров**: перезапускать десяток серверов вручную по SSH нереально.
- **Ограниченные права помощникам**: дать перезапуск и журналы, но **не давать SSH** — главная выгода панели по безопасности.
- **Перезапуск и копирование по расписанию**: панели обычно дают задачи по расписанию, **есть ли это у MCSManager, где вход и как настраивать — по официальной документации и вашему интерфейсу**.
- **Управление несколькими машинами**: одна панель + несколько демонов, единая точка входа.
- **Для тех, кто не знаком с командной строкой**: ограничить действия рамками панели часто безопаснее, чем дать shell.

## 3. Безопасность панели (самое важное)

### 3.1 Первый принцип: панель и API демона ни в коем случае не открывать в интернет напрямую

Этот пункт важнее всех остальных вместе взятых:

:::warn Никогда не выставляйте порт демона в интернет
Задача API демона — **запускать процессы, читать и писать файлы, выполнять команды**, по сути это **интерфейс удалённого выполнения кода**, лишь прикрытый слоем аутентификации. **Как только он открыт, атакующему достаточно одной утечки ключа, одного обхода аутентификации или одной неисправленной уязвимости, чтобы выполнить на вашей машине любую команду.** То же с веб-частью панели, просто там есть хотя бы страница входа.
:::

Правильный подход:

1. **Панель**: привязать к `127.0.0.1` или внутреннему адресу, выставить наружу через HTTPS-обратный прокси и добавить ограничение по источнику (VPN, белый список IP или правило брандмауэра).
2. **Демон**: разрешить доступ только хосту панели (и клиентам, которым нужно прямое подключение).
3. **Не открывайте порт демона на `0.0.0.0` «для удобства».**

:::note Особенность MCSManager: браузеру нужно прямое подключение к демону
Официальная документация MCSManager «Сетевая архитектура» объясняет: чтобы панель не стала узким местом для больших потоков (загрузка файлов, журнал консоли), **эти потоки идут от браузера напрямую к демону**. Поэтому в документации указано, что адрес демона **не может быть адресом локальной сети**, иначе состояние демона навсегда останется «подключение».

Отсюда два обязательных следствия:

- Если вы переводите панель на HTTPS, **для каждого демона тоже нужен отдельный HTTPS-обратный прокси**, а в панели адрес нужно сменить на `wss://...`; документация прямо говорит, что браузер **откажется** подключаться к демону по WebSocket без HTTPS.
- Общий совет «демон только во внутренней сети» в MCSManager реализуется по официальной сетевой архитектуре: **либо настроить HTTPS-обратный прокси по официальной документации, либо защитить канал «браузер — демон» через VPN или туннель**, а не просто открывать порт в интернет.

**Как именно настраивать — по официальным разделам «Сетевая архитектура» и «Использование HTTPS через NGINX».**
:::

### 3.2 Не запускайте от root

| Ситуация | Факт (из официальной документации) | Рекомендация |
| --- | --- | --- |
| Скрипт MCSManager | Документация указывает, что **из-за регистрации системной службы скрипт нужно запускать от root** | Устанавливать можно от root, но **экземпляры по возможности изолировать отдельным пользователем или контейнером**; у проекта есть отдельный документ «Изоляция окружения (Docker)» |
| Pterodactyl Wings | В официальном unit systemd указано `User=root` | Это официальный дизайн (Wings нужно управлять Docker); **изоляция экземпляров контейнерами и есть средство смягчения** |
| Универсальные панели сервера | Обычно нужны высокие права для управления системными службами и сайтами | Не смешивайте игровой сервер и такую панель в одной границе доверия (см. 4.2) |

Принцип: **если можно без root — без root; если высокие права необходимы, ограничьте радиус поражения изоляцией (отдельный пользователь, контейнер, отдельная машина).**

### 3.3 Учётные данные и аккаунты

- **Немедленно смените пароль по умолчанию.** Пароль по умолчанию — первая цель автоматических сканеров.
- Используйте **длинный и уникальный** пароль, лучше сгенерированный менеджером паролей. **Утечка пароля панели = захват всех экземпляров.**
- **Если панель поддерживает двухфакторную аутентификацию, обязательно включите**; поддерживает ли и как включать — **по официальной документации**.
- **Регулярно проверяйте субпользователей и права**: кто ещё есть? нужен ли? не дано ли лишнего? «Управление файлами + все экземпляры» почти равно shell.
- **Удаляйте ненужные аккаунты**, включая ушедших помощников, тестовые аккаунты и неиспользуемые API Key.
- Не вписывайте пароль панели в скриншоты, переписку, репозиторий Git или текстовые файлы в каталоге сервера.

### 3.4 Держите панель обновлённой

Панель — веб-приложение, **у неё есть своя история уязвимостей**. Что делать:

- Подписаться на Release и бюллетени безопасности официального репозитория.
- Обновляться по процедуре из официального раздела «Обновление».
- Перед обновлением **сделать копию собственных данных панели** (см. 3.7).

:::warn Одна ловушка при обновлении MCSManager
Официальная документация «Обновление и сброс» предупреждает: обновление скриптом **снова автоматически включает `mcsm-web`**. Если вы намеренно отключали веб-службу на узле (см. 2.2), после обновления **нужно снова вручную остановить и отключить её**, иначе страница начальной настройки опять окажется открытой.
:::

### 3.5 Адрес прослушивания и обратный прокси (пример nginx)

Идея: **панель слушает только loopback, наружу отдаёт nginx по HTTPS.** Порты ниже — **заглушки**, замените на порт вашей панели.

```nginx
# /etc/nginx/conf.d/panel.conf
# <panel-port> — заглушка, замените на локальный порт, который реально слушает панель.
# Пути к сертификатам определяет ваш инструмент сертификатов, не копируйте примеры путей ниже.

server {
    listen 80;
    server_name panel.example.com;
    # Только перенаправление; способ выдачи и продления сертификата — по документации вашего инструмента
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name panel.example.com;

    # Выдаётся и продлевается вашим инструментом сертификатов, замените на реальные пути (например, вывод certbot)
    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;

    # Консоль панели работает через WebSocket, заголовок Upgrade нужно пробрасывать
    location / {
        proxy_pass http://127.0.0.1:<panel-port>;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Панель может загружать крупные файлы сервера или сборки; 0 означает без ограничения
        client_max_body_size 0;

        # Консоль — длительное соединение, не давайте её буферизовать или обрывать слишком рано
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

Несколько замечаний:

- `proxy_http_version 1.1` вместе с заголовками `Upgrade` / `Connection` — ключ к WebSocket, **без любого из трёх консоль может не подключиться**.
- **Пути** `ssl_certificate` и `ssl_certificate_key` **берутся из вашего инструмента сертификатов** (certbot и др.), у разных инструментов и способов развёртывания пути разные, **не копируйте**.
- Если официальная документация панели даёт собственный пример обратного прокси (у MCSManager есть NGINX, IIS и Caddy), **ориентируйтесь на официальную документацию** — потому что для цепочки демона часто нужна отдельная настройка.
- После правки сначала проверьте синтаксис, потом перезагружайте (официальная документация MCSManager тоже требует сначала проверки, потом перезагрузки):

```bash
sudo nginx -t
sudo nginx -s reload
```

### 3.6 Брандмауэр

Открывайте только необходимое, остальное по умолчанию запрещено:

| Порт | Кому открыт | Пояснение |
| --- | --- | --- |
| 80 / 443 | Интернет | Вход в панель (или выбранный вами HTTPS-порт); 80 только для перенаправления и проверки сертификата |
| Локальный порт панели | **Только локально** | Если панель привязана к `127.0.0.1`, открывать наружу не нужно |
| Порт демона | **Только хост панели** (или источники по официальной архитектуре) | Никогда не открывать в интернет; конкретный порт — по официальной документации |
| Игровые порты | Интернет (по необходимости) | Вход для игроков |
| SSH | Ваш управляющий IP | Рекомендуется разрешить только вход по ключу |

Пример (порты и подсети — **заглушки**, замените на свои; синтаксис команд сверяйте с документацией дистрибутива):

```bash
# Пример ufw
sudo ufw default deny incoming
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp
# Разрешить доступ к порту демона только хосту панели
sudo ufw allow from <panel-host-ip> to any port <daemon-port> proto tcp
sudo ufw enable
sudo ufw status verbose
```

Полная логика портов и правил — см. [Основы сетевой безопасности](/tutorials/ops/network-security) и [Роутер и брандмауэр](/tutorials/ops/router-firewall).

### 3.7 Копии собственных данных панели

**В каталоге данных панели хранятся определения всех экземпляров, пользователи и конфигурация. Потеряв его, вы получите файлы сервера на месте, но «пустую панель».**

| Что копировать | Пояснение |
| --- | --- |
| База данных и каталог конфигурации панели | Пользователи, права, определения экземпляров, задачи по расписанию |
| Конфигурация демона | Порт, ключ, конфигурация экземпляров |
| Каталог данных экземпляров | Миры, плагины, конфигурация (обычно самый большой по объёму) |

:::warn Пути — по официальной документации
Расположение каталогов данных у разных панелей различается, **его нужно подтвердить по официальной документации и только потом вписывать в скрипт копирования**, не пишите пути по догадке.

На примере MCSManager официальная документация указывает: конфигурация веб-панели — `<каталог установки веб-панели>/data/SystemConfig/config.json`, конфигурация демона — `<каталог установки демона>/data/Config/global.json`, данные экземпляров — `<каталог установки демона>/data/InstanceData/<instance-id>/`, конфигурация экземпляра — `<каталог установки демона>/data/InstanceConfig/<instance-id>.json`. А документ «Обновление и сброс» прямо советует: **перед обновлением скопировать каталоги `web/data` и `daemon/data` в другое место.**
:::

Рекомендации по копированию:

- Копии данных панели должны храниться **офлайн или в другом месте**, причём **сам процесс панели не должен иметь права записи туда** (иначе при взломе панели копии удалят вместе с ней).
- В копиях есть база данных и ключи панели, **их нужно шифровать или жёстко ограничивать по правам**.
- Регулярно проводите **учения по восстановлению** — копировать без восстановления равно отсутствию копий. Методы — см. [Резервное копирование и восстановление](/tutorials/java/backup) и [Резервные копии в другом месте](/tutorials/ops/offsite-backup).

### 3.8 Что будет, если панель взломают

Опишите худший случай — и станет понятно, от чего защищаться:

| Что получил атакующий | Последствия |
| --- | --- |
| Аккаунт панели | Контроль **всех экземпляров**: удаление миров, правка конфигурации, кик игроков, выдача себе op |
| Панель + управление файлами | Загрузка вредоносного jar или плагина, бэкдор в сервере |
| API демона | **Выполнение произвольных команд на машине** (это и есть его функция), обычно равно shell |
| База данных или ключи панели | Постоянный доступ: даже после смены пароля старые API Key и сессии могут работать |
| Право записи в каталог копий | **Удаление ваших копий**, невозможность восстановления (частый приём вымогателей и мстительного удаления) |

Поэтому: **при первом подозрении на взлом панели действуйте как при «захвате всей машины».**

1. Немедленно отрезать панель и демон от интернета (правилами брандмауэра, а не только сменой пароля).
2. Заменить **все** учётные данные: аккаунт панели, ключ демона, пароль RCON сервера, пароль базы данных, API Key облачного провайдера.
3. Проверить, не появились ли новые администраторы, новые API Key, странные задачи по расписанию.
4. Проверить, не подложены ли в каталог сервера подозрительные jar, плагины и скрипты по расписанию.
5. Восстановиться из **заведомо чистой** копии, а не «почистить и продолжить» на взломанной машине.
6. Разобрать причину раскрытия (открытый порт, слабый пароль или отсутствие патча), см. [Основы сетевой безопасности](/tutorials/ops/network-security) и [Укрепление безопасности системы](/tutorials/ops/system-security).

Полный порядок действий — см. [Реагирование на инциденты и форензика](/tutorials/ops/incident-forensics).

## 4. Другие панели и как выбирать

### 4.1 Pterodactyl

Официальное описание Pterodactyl: **бесплатная открытая панель управления игровыми серверами, написанная на PHP, React и Go; спроектирована для безопасности, все игровые серверы работают в изолированных контейнерах Docker**, а конечным пользователям предоставляется понятный веб-интерфейс. Это открытый проект под лицензией MIT, официально подчёркивается хеширование паролей bcrypt, шифрование AES-256-CBC и поддержка HTTPS «из коробки».

Её архитектура относится к тому же классу «панель + демон узла». Официальный глоссарий определяет:

| Термин | Официальное значение |
| --- | --- |
| **Panel** | Сама панель Pterodactyl, служит для добавления узлов и серверов |
| **Node** | Физическая машина, на которой работает экземпляр Wings |
| **Wings** | Служба нового поколения на Go, взаимодействующая с Docker и Panel и безопасно управляющая серверами через панель |
| **Server** | Экземпляр, созданный панелью и работающий на узле; на одном узле их может быть несколько |
| **Docker / Image / Container** | Изолированная среда выполнения; каждый сервер работает в отдельном контейнере с ограничением CPU и памяти, чтобы не мешать другим |
| **Nest / Egg** | Nest обычно соответствует игре или сервису, Egg хранит конкретную конфигурацию для класса игр |
| **Yolks** | Набор основных образов Docker, идущий в комплекте с системой Egg |

Важное (всё из официальной документации):

- Wings **поддерживает только Linux**, официально указано, что в Windows работать не будет; нужна система с возможностью запускать Docker, виртуализация типа OpenVZ и LXC обычно не подходит (официально рекомендуется проверить через `systemd-detect-virt`).
- Официальный порядок установки: сначала создать узел в панели, затем вставить сгенерированную панелью конфигурацию в `/etc/pterodactyl/config.yml` на узле (или использовать команду из «Generate token»), после чего запустить Wings как службу systemd.
- В официальном unit systemd указано `User=root`, это официальный дизайн.
- Официальная документация указывает: **если на панели включён SSL, Wings тоже должен иметь сертификат для своего FQDN.**
- Узлу нужно настроить allocation (сочетание IP и порта), у каждого сервера должно быть минимум одно; официально указано **не использовать `127.0.0.1`**.

:::note Что не проверялось по пунктам
**Конкретные команды установки, порты по умолчанию, структура каталогов и требования к версиям Pterodactyl меняются вместе с версией**, статья их не перечисляет, **ориентируйтесь на официальную документацию**: установка панели — раздел Getting Started официальной документации Panel, демон узла — раздел Installing Wings официальной документации Wings.
:::

### 4.2 Универсальные панели сервера (1Panel, Baota и др.)

Это **не панели игровых серверов**, они управляют **вещами уровня операционной системы**: сайтами, базами данных, контейнерами, файлами, задачами по расписанию, брандмауэром и т. п.

На примере 1Panel официальное позиционирование — **«современная открытая панель управления эксплуатацией серверов Linux»** (а также лёгкая платформа управления ИИ), предоставляющая понятный веб-интерфейс для управления мониторингом хоста, файлами, базами данных, контейнерами и задачами по расписанию, с глубокой интеграцией с системами сайтов вроде WordPress и Halo; официально также предоставляются WAF, аудит журналов и резервное копирование.

**Чем она отличается от игровой панели:**

| Аспект | Панель игровых серверов | Универсальная панель сервера |
| --- | --- | --- |
| Что управляет | Игровые экземпляры (процессы или контейнеры) | Системные службы, сайты, базы данных, контейнеры |
| Понимает ли игру | Видит консоль, передаёт плагины, настраивает команду запуска | Обычно не понимает, управляет как обычным процессом или контейнером |
| Объём прав | Экземпляры и демон | **Часто вся система** |
| Типичное применение | Много экземпляров, права помощникам | Сайты, службы, управление Docker |

**Риски управления игровым сервером универсальной панелью:**

- **Права больше**: такие панели обычно управляют системными службами и файлами, и при взломе последствия шире, чем у игровой панели.
- **Не понимает игру**: она не сделает за вас «сначала отправить stop, дождаться сохранения мира», и легко убивает сервер как обычный процесс.
- **Появляется ещё один слой**: вы одновременно обслуживаете «способ развёртывания игрового сервера» и «универсальную панель», поверхности атаки складываются.
- **Исторически были серьёзные уязвимости**: универсальные панели — приоритетная цель сканирования из интернета. **Любую панель следует воспринимать как «инфраструктуру, смотрящую в интернет»** — своевременно обновлять, ограничивать источники, включать сильную аутентификацию. **Конкретную информацию об уязвимостях смотрите в официальных бюллетенях безопасности производителей, не полагайтесь на слухи третьих сторон.**

:::tip Более устойчивая комбинация
Если универсальная панель действительно нужна (например, на той же машине есть сайт), **держите игровой сервер на отдельной машине, под отдельным пользователем или в отдельном контейнере**, не смешивайте права универсальной панели и игровые экземпляры в одной границе доверия. Укрепление на уровне системы — см. [Укрепление безопасности системы](/tutorials/ops/system-security).
:::

### 4.3 Сравнительная таблица

| Панель | Позиционирование | Нужен ли отдельный демон | Кому подходит | Основные риски |
| --- | --- | --- | --- | --- |
| **MCSManager** | Открытая, распределённая, многопользовательская панель управления игровыми серверами Minecraft и Steam | **Да** (Panel + Daemon, возможно несколько узлов) | Владельцам с несколькими экземплярами и машинами, которым нужно давать права помощникам | Демон — поверхность удалённого выполнения кода; браузеру нужен прямой доступ к демону, обратный прокси сложнее; обновление может снова включить веб-службу |
| **Pterodactyl** | Бесплатная открытая панель игровых серверов, экземпляры в изолированных контейнерах Docker | **Да** (Panel + Wings на каждом узле) | Тем, кто хочет изоляции контейнерами, для нескольких пользователей и узлов | Зависит от Docker и Linux; Wings официально работает от root; выше порог установки и обслуживания; способ установки и порты — по официальной документации |
| **1Panel** | Современная открытая панель эксплуатации серверов Linux (универсальная) | Нет (сама является системной панелью управления) | Сайты, базы данных и контейнеры, общая эксплуатация | **Системные права**, большая поверхность атаки; не понимает игровые серверы; широкие последствия уязвимостей |
| **Универсальные панели вроде Baota** | Универсальная панель эксплуатации сервера | Нет | Сайты и общая эксплуатация | То же, что у 1Panel; **команды установки, порты по умолчанию и функции безопасности — по официальной документации** |
| **Без панели (SSH + systemd)** | Прямое управление | Нет | Одна машина, немного экземпляров | Нет дополнительной поверхности атаки; но unit, журналы и обновления обслуживать самому |

## 5. Практические рекомендации

### 5.1 Порядок установки

1. **Сначала укрепите систему** (отдельный пользователь, ключи SSH, брандмауэр, автообновления), см. [Укрепление безопасности системы](/tutorials/ops/system-security).
2. **Потом ставьте панель**, сразу после установки смените пароль по умолчанию.
3. **Спрячьте панель за HTTPS-обратным прокси** и ограничьте источники (VPN, белый список IP или правила брандмауэра).
4. **В конце подключите узлы с демонами**, на узле оставьте только службу демона и отключите лишние веб-службы.
5. Создайте экземпляр, загрузите файлы, добейтесь работы консоли.
6. Настройте задачи по расписанию и резервное копирование.
7. Создайте субаккаунты для помощников с минимальными правами.

**Не** запускайте «голую в интернете» панель «чтобы сначала заработало» — каждая минута, пока панель открыта в интернет, её сканируют.

### 5.2 Чек-лист укрепления

- [ ] Панель и демон **недоступны напрямую из интернета**
- [ ] Панель доступна по HTTPS, и WebSocket работает
- [ ] Пароль по умолчанию изменён; двухфакторная аутентификация включена, где поддерживается
- [ ] Права на файлы конфигурации панели и демона закрыты (файлы с ключами и паролями не должны быть доступны на чтение всем)
- [ ] Экземпляры работают под отдельным пользователем или в контейнере, не от root
- [ ] Данные панели скопированы, и панель не может писать в место хранения копий
- [ ] Подписка на официальные бюллетени безопасности есть, свой порядок обновления определён
- [ ] Права субпользователей проверены
- [ ] На узлах нет остатков страницы начальной настройки
- [ ] Порядок действий при взломе известен

### 5.3 Что мониторить

| Пункт мониторинга | Почему |
| --- | --- |
| **Число неудачных входов в панель** | Первый сигнал перебора. У части панелей есть настройка «блокировать IP после неудачных входов» (в конфигурации веб-панели MCSManager есть `loginCheckIp`, **точный смысл и поведение — по официальной документации**) |
| **Странные новые экземпляры** | Атакующие часто создают экземпляры, чтобы запускать на них что-то другое |
| **Странные задачи по расписанию** | Задачи по расписанию — частый способ закрепления |
| **Новые администраторы или API Key** | Бэкдор для закрепления |
| **Резкий рост ресурсов** | CPU, память и полоса уходят на майнинг или генерацию трафика |
| **Версии панели и демона** | Своевременное применение патчей |
| **Аномальные исходящие соединения** | Игровой сервер обычно не должен сам активно подключаться к массе адресов |

Расположение журналов и команды аудита — см. [Укрепление безопасности системы](/tutorials/ops/system-security); действия после взлома — см. [Реагирование на инциденты и форензика](/tutorials/ops/incident-forensics).

### 5.4 Когда панель не нужна

Панель — не вариант по умолчанию. В следующих случаях она **обычно не нужна**:

- **Одна машина, один сервер**: SSH + systemd проще и на одну поверхность атаки меньше. См. [Развёртывание в доступной среде](/tutorials/java/deploy).
- **Пользуетесь только вы и вы знакомы с командной строкой**: выгода панели (визуальность, разделение прав) вам не нужна, а цена (ещё одна служба, ещё одна система аккаунтов) остаётся.
- **Машина слабая по ресурсам**: панель сама занимает память, на машине с малой памятью это невыгодно.
- **Вы не собираетесь её обслуживать**: **необновляемая панель опаснее отсутствия панели.**

Наоборот, если выполняется любое из условий ниже, панель обычно оправдана: несколько экземпляров, несколько машин, необходимость давать помощникам ограниченные права, задачи по расписанию, использование людьми, не знакомыми с командной строкой.
