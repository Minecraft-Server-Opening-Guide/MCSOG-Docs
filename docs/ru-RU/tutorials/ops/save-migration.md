**Перенести на сервер одиночное сохранение, в которое вы играли сотни часов, — одна из операций, где легче всего «получить успех на вид и потерю на деле».** Разница в одну букву в имени каталога — и при входе вы видите совершенно новый пустой мир; папки Нижнего мира и Энда не перенесены — и за порталом не сгенерированный рельеф; данные игрока не переименованы — и человек заходит, но инвентарь, достижения и статистика обнулены. Эта статья подробно разбирает реальную структуру сохранения, две схемы каталогов, что именно ожидает сервер и как провести надёжную миграцию.

Перед миграцией прочитайте [Резервное копирование и восстановление](/tutorials/java/backup): первый и последний шаг всего процесса — резервная копия. О связи каталога сервера и конфигурации — см. [Структура сервера](/tutorials/java/structure) и [Настройка сервера](/tutorials/java/config).

## 1. Сначала посмотрим: что вообще лежит в одиночном сохранении

Одиночное сохранение — это каталог `.minecraft/saves/<имя мира>/` (в Windows обычно `%APPDATA%\.minecraft\saves\<имя мира>\`). Это не один файл, а **от десятков до десятков тысяч файлов**:

| Путь | Содержимое | Пояснение |
| --- | --- | --- |
| `level.dat` | Глобальная информация о мире | Формат NBT, содержит имя мира, настройки генерации и сид, игровые правила, точку спавна, время, `DataVersion` и др. |
| `level.dat_old` | Копия предыдущего `level.dat` | Создаётся автоматически при загрузке мира, можно копировать вместе с ним |
| `level.dat_new` | Временный файл в процессе записи | После нормального закрытия обычно отсутствует; его наличие означает, что последняя запись была прервана |
| `session.lock` | Блокировка занятости мира | С версии 1.16 содержимое — символ U+2603 (снеговик); **не копируйте**, сервер создаст его сам |
| `region/` | Региональные файлы Верхнего мира `r.<x>.<z>.mca` | Рельеф и блоки, самая объёмная часть |
| `entities/` | Данные сущностей Верхнего мира | С версии 1.17 вынесены из `region/` в отдельное хранилище |
| `poi/` | Точки интереса Верхнего мира | Существуют с 1.14; кровати и рабочие места жителей, порталы, ульи, магниты и др. |
| `data/` | Разные данные уровня мира | Табло, рейды, карты, хранилище команд и др. |
| `playerdata/<uuid>.dat` | Данные игрока | Инвентарь, позиция, здоровье, опыт и др., **имя файла — это UUID игрока** |
| `advancements/<uuid>.json` | Достижения (прогресс) | Тоже названы по UUID |
| `stats/<uuid>.json` | Статистика | Тоже названы по UUID |
| `datapacks/` | Датапаки уровня мира | Отличаются от глобальных датапаков: идут вместе с миром |
| `DIM-1/`, `DIM1/` | Нижний мир и Энд | Старая схема; имена происходят от старых числовых ID измерений (-1 и 1) |
| `dimensions/<пространство имён>/<путь>/` | Пользовательские измерения | Поддерживаются с 1.16; с 26.1 три измерения по умолчанию тоже переехали сюда |
| `resources.zip` | Ресурспак, встроенный в мир | С 26.1 перенесён в подкаталог `resourcepacks/` |

:::note Отсутствие `DIM-1/` не означает, что с сохранением что-то не так
Папки Нижнего мира и Энда создаются **при первом входе в это измерение**. Если вы никогда не были в Энде, в сохранении не будет `DIM1/` — это нормально, сервер создаст его сам при первом входе игрока.
:::

## 2. Две схемы: папки `DIM` и `dimensions/`

Это самое частое место ошибок во всей миграции, смотреть нужно по версиям:

| Диапазон версий | Верхний мир | Нижний мир | Энд | Пользовательские измерения |
| --- | --- | --- | --- | --- |
| 1.2.1 – 1.13 (начиная с Anvil) | Корень сохранения (`region/`, `data/` и др.) | `DIM-1/` | `DIM1/` | Не поддерживаются |
| 1.14 – 1.15 | То же, плюс `poi/` | `DIM-1/` | `DIM1/` | Не поддерживаются |
| 1.16 – 26.0 | То же, с 1.17 плюс `entities/` | `DIM-1/` | `DIM1/` | `dimensions/<пространство имён>/<путь>/` |
| 26.1 (снимок 6) и новее | `dimensions/minecraft/overworld/` | `dimensions/minecraft/the_nether/` | `dimensions/minecraft/the_end/` | `dimensions/<пространство имён>/<путь>/` |

Важно:

- **Старая схема (1.16 – 26.0 и раньше)**: два измерения по умолчанию используют фиксированные имена каталогов `DIM-1` (Нижний мир, ID измерения `-1`) и `DIM1` (Энд, ID измерения `1`). Они лежат прямо **в корне сохранения**, на одном уровне с `region/`.
- **Схема `dimensions/`**: после введения в 1.16 пользовательских измерений нестандартные измерения хранятся по **местоположению ресурса**, то есть `dimensions/<пространство имён>/<путь>/`, например `dimensions/mydatapack/skylands/`. После перестройки в снимке 26.1 **три измерения по умолчанию тоже перешли на эту схему**, а `DIM-1`/`DIM1` больше не используются.
- В одном и том же сохранении 26.1 данные игроков тоже переехали из корня в `players/`: `players/data/<uuid>.dat`, `players/advancements/<uuid>.json`, `players/stats/<uuid>.json`.

## 3. Какой каталог ожидает сервер

Сервер в **рабочем каталоге** (базовый путь можно изменить через `--universe`) ищет каталог, указанный в `level-name` из `server.properties`, по умолчанию `world`. Если этот путь существует и является корректным миром (есть `level.dat`), он загружается; **иначе сервер создаст по этому пути совершенно новый мир** — заметьте, он не остановится с ошибкой, и это корень «я же скопировал сохранение, а в игре пустой мир».

Одиночное сохранение складывает три измерения в одно дерево каталогов, а сервер по умолчанию держит три измерения в **трёх каталогах одного уровня**:

| Что в одиночном сохранении | Где на сервере | Пояснение |
| --- | --- | --- |
| Содержимое корня сохранения: `level.dat`, `region/`, `entities/`, `poi/`, `data/`, `playerdata/`, `advancements/`, `stats/`, `datapacks/` | `world/` | Верхний мир, то есть каталог, на который указывает `level-name` |
| `DIM-1/` | `world_nether/` | Нижний мир |
| `DIM1/` | `world_the_end/` | Энд |
| `dimensions/<пространство имён>/<путь>/` | Каталог соответствующего измерения | Имеет смысл, только если на сервере установлен тот же датапак или мод |
| `session.lock` | Не копировать | Сервер создаёт его сам при запуске |
| `level.dat_old` | Вместе с `level.dat` в `world/` | Это лишь копия предыдущего `level.dat`, держать её безвредно |

Имена каталогов не жёстко заданы: они выводятся из `level-name` плюс суффикс. При `level-name=myworld` обычно это `myworld/`, `myworld_nether/`, `myworld_the_end/`.

:::warn Никогда не копируйте сохранение при работающем сервере
Копирование в момент, когда сервер пишет `region/*.mca`, с большой вероятностью даст **недописанные файлы чанков**, и после восстановления это проявится как пропавшие чанки, перепутанные блоки и даже невозможность загрузить мир; кроме того, `session.lock` окажется с обеих сторон и вызовет конфликт блокировок. Правильный порядок всегда такой: `stop` — остановить сервер (или выполнить в консоли `save-all` → `save-off`, но при миграции **настоятельно рекомендуется просто остановить сервер**) → копировать → запускать.
:::

:::tip Самое надёжное: пусть сервер сначала создаст каталоги
Не угадывайте имена каталогов вручную. Сначала один раз запустите сервер с целевым `level-name` (получится пустой мир) → остановите → посмотрите, какие каталоги он реально создал → и **заполните эти каталоги** содержимым сохранения. Так вы не ошибётесь с местом, независимо от того, использует ядро `world_nether` или держит измерения в `world/dimensions/`.
:::

## 4. Данные игроков: почему они не переносятся сами

Имена файлов в `playerdata/`, `advancements/` и `stats/` — **это UUID игрока**. Сервер ищет файл по UUID, и при несовпадении считает игрока новым: пустой инвентарь, нулевые достижения, нулевая статистика.

Откуда берётся UUID, зависит от того, как сервер определяет личность:

| Сценарий | Источник UUID | Результат |
| --- | --- | --- |
| Одиночное сохранение | Локальный UUID игрока, сохранённый в мире (с 26.1 — `singleplayer_uuid` в `level.dat`, в более ранних версиях — тег `Player`), он же имя файла в `playerdata/` | Это «источник» |
| Сервер `online-mode=true` | Лицензионный UUID аккаунта Microsoft/Mojang | Обычно **отличается** от UUID в одиночной игре |
| Сервер `online-mode=false` (офлайн-режим) | Детерминированно вычисляется из имени игрока: `UUID.nameUUIDFromBytes(("OfflinePlayer:" + имя).getBytes(UTF_8))`, UUID версии 3 (MD5) | **Отличается** от лицензионного, причём у игрока с тем же именем UUID одинаков на любом офлайн-сервере |

То есть: **если только одиночный мир не был создан именно с UUID этого аккаунта, данные игроков сами не заработают.**

Способы решения (в рекомендуемом порядке):

1. **Сначала дайте игроку один раз зайти на сервер**, чтобы сервер создал файл данных для этого UUID и записал его в `usercache.json` рабочего каталога.
2. Остановите сервер и прочитайте **целевой UUID** из `usercache.json` (или из нового имени файла в `world/playerdata/`).
3. **Переименуйте** исходный файл в целевой UUID, а не перезаписывайте: `playerdata/<старый UUID>.dat` → `playerdata/<новый UUID>.dat`, то же для `advancements/` и `stats/`. Сначала сделайте копию старых файлов, чтобы можно было откатить при ошибке.
4. **Определите `online-mode` до миграции**: если решили использовать офлайн-режим, не переключайтесь потом на лицензионный, иначе у всех офлайн-игроков сменится UUID, и это будет выглядеть как «откат сохранения».

По UUID индексируются и `ops.json` с `whitelist.json`: копирование мира их не переносит, нужно заново выполнить на сервере `/op`, `/whitelist add` (или вручную отредактировать эти JSON с правильными UUID).

## 5. Шаги миграции

### 5.1 До миграции зафиксируйте

- **Версию игры** исходного сохранения (`DataVersion` в `level.dat` или номер версии в главном меню клиента). **Версия сервера не может быть ниже версии сохранения**, иначе загрузка будет отклонена; понижать версию мира небезопасно.
- Целевой `level-name` (определяет имена каталогов).
- Размер исходного сохранения: `du -sh`, убедитесь, что целевой диск вместит его и останется место под копии.
- До миграции запишите несколько проверяемых фактов о мире: координаты точки спавна, значение `/seed`, координаты какой-нибудь постройки, положение портала в Нижний мир.

### 5.2 Остановка сервера и резервная копия

```bash
# Со стороны сервера: сначала корректно остановить
sudo systemctl stop minecraft
# Если сервер не под systemd, выполните stop в консоли и убедитесь, что процесс действительно завершился

# Со стороны исходного сохранения: сначала упаковать для страховки (на машине клиента)
cd ~/.minecraft/saves
tar -czf MyWorld-20261004.tar.gz MyWorld

# На целевой стороне: переименовать текущий (пустой или старый) каталог мира для страховки, не удалять
cd /opt/minecraft/server
mv world world_before_migration
```

В Windows аналог — правой кнопкой заархивировать папку `MyWorld` в `%APPDATA%\.minecraft\saves`.

### 5.3 Копирование файлов

Рекомендуется `rsync -a`: он умеет исключать ненужные каталоги, продолжать прерванную передачу и внятно сообщать об ошибках. **Слэш в конце исходного пути означает «копировать содержимое каталога»**, если его пропустить или написать неверно, появится лишний уровень каталога.

```bash
# Верхний мир: исключаем два каталога измерений и файл блокировки, остальное всё в world/
rsync -a --exclude 'DIM-1' --exclude 'DIM1' --exclude 'session.lock' \
  "/home/you/.minecraft/saves/MyWorld/" /opt/minecraft/server/world/

# Нижний мир и Энд: в свои каталоги того же уровня
rsync -a "/home/you/.minecraft/saves/MyWorld/DIM-1/" /opt/minecraft/server/world_nether/
rsync -a "/home/you/.minecraft/saves/MyWorld/DIM1/"  /opt/minecraft/server/world_the_end/
```

Если переносить нужно немного каталогов, нагляднее `cp -a`. Параметр `-a` сохраняет отметки времени, права и символические ссылки:

```bash
# Копирование по пунктам (что не существует — пропускается: например, если в Энде не были, нет DIM1)
cd "/home/you/.minecraft/saves/MyWorld"
cp -a level.dat level.dat_old region entities poi data datapacks \
      playerdata advancements stats /opt/minecraft/server/world/ 2>/dev/null

cp -a DIM-1/. /opt/minecraft/server/world_nether/
cp -a DIM1/.  /opt/minecraft/server/world_the_end/
```

В Windows используйте `robocopy` (учтите: коды выхода `robocopy` **от 0 до 7 считаются успехом**, `1` означает «файлы скопированы», не считайте это сбоем):

```bat
robocopy "%APPDATA%\.minecraft\saves\MyWorld" "C:\mc\server\world" /E /XD DIM-1 DIM1 /XF session.lock
robocopy "%APPDATA%\.minecraft\saves\MyWorld\DIM-1" "C:\mc\server\world_nether" /E
robocopy "%APPDATA%\.minecraft\saves\MyWorld\DIM1"  "C:\mc\server\world_the_end" /E
```

После копирования исправьте владельца (в Linux обязательно, если сервер работает под отдельным пользователем, иначе получите `Failed to save`):

```bash
sudo chown -R minecraft:minecraft \
  /opt/minecraft/server/world \
  /opt/minecraft/server/world_nether \
  /opt/minecraft/server/world_the_end
```

:::tip Большое сохранение сначала архивируйте, а не копируйте медленно по сети
Передача десятков GB каталога `region/` файл за файлом по сети идёт очень медленно, и при обрыве начинать нужно заново. Надёжнее сначала упаковать на исходной машине (`tar -czf MyWorld.tar.gz MyWorld`, сжатие данных чанков обычно даёт хороший результат), а распаковать после передачи; `rsync -az --partial` тоже даёт сжатие передачи и докачку.
:::

### 5.4 Исправление `level-name`

Откройте `server.properties` сервера и убедитесь, что имя каталога **полностью совпадает** с `level-name` (в Linux регистр важен, `MyWorld` и `myworld` — два разных каталога):

```properties
level-name=world
```

### 5.5 Запуск и наблюдение

```bash
sudo systemctl start minecraft
# Смотреть процесс запуска в реальном времени, искать ошибки, связанные с сохранением
tail -f /opt/minecraft/server/logs/latest.log
# При управлении через systemd stdout находится в journal
journalctl -u minecraft.service -f
```

В журнале запуска обязательно убедитесь: нет `Failed to load`, нет исключений по измерениям, `Preparing spawn area` завершился нормально, нет `No space left on device`.

### 5.6 Проверка входом на сервер

См. чек-лист проверки в разделе 10. **Не открывайте сервер всем сразу**, пустите через белый список одного-двух человек и убедитесь, что всё в порядке.

### 5.7 Перед настоящей миграцией проведите репетицию

Если мир важный, **сначала поднимите тестовый экземпляр на другом порту и с временным `level-name`** и пройдите весь процесс. Репетиция заранее вскрывает проблемы с именами каталогов, версией, правами и UUID и совершенно не затрагивает продакшен.

```properties
# server.properties тестового экземпляра (в отдельном каталоге, чтобы не мешать продакшену)
level-name=world_test
server-port=25566
online-mode=false
white-list=false
```

```bash
cd /opt/minecraft/testserver
java -Xms2G -Xmx2G -jar server.jar --nogui
```

После успешной репетиции повторите всё на продакшене; тестовый каталог потом можно просто удалить целиком.

## 6. Стоит ли трогать `level.dat`

`level.dat` — это «паспорт и таблица настроек» мира: имя мира, настройки генерации и сид, игровые правила, точка спавна, время, сложность и список включённых датапаков. Внутри — **двоичный NBT**, обычно ещё и сжатый gzip.

Вывод простой: **не редактируйте его вручную.**

- Открытие текстовым редактором сразу испортит файл; правка NBT-редактором тоже сталкивается с различиями версий (например, с 26.1 игровые правила и настройки генерации мира вынесены в `data/`).
- Проявление ошибки — мир просто не загружается, а `level.dat_old` не всегда спасает.
- **У подавляющего большинства того, что хочется изменить, есть штатный вход**: сложность, режим игры, дальность прорисовки, белый список — через `server.properties`; игровые правила, время, погоду, точку спавна, датапаки — командами в игре (`/gamerule`, `/time set`, `/weather clear`, `/setworldspawn`, `/datapack`).
- Учтите, что `level-seed` **действует только при создании мира**, сид существующего мира нельзя сменить через конфигурацию.
- Когда нужно «заглянуть, что внутри», открывайте инструментом просмотра NBT **только для чтения** и предварительно сделайте копию.

Правильный подход при миграции: **перенести `level.dat` как есть и не менять его в процессе миграции**; настройки менять конфигурацией и командами уже после того, как мир запустился, проверка пройдена и копия на месте.

## 7. Датапаки (`datapacks/`)

- Датапаки уровня мира лежат в `datapacks/` внутри каталога мира (в одиночной игре — `saves/<имя мира>/datapacks/`, на сервере — `world/datapacks/`), они идут вместе с миром и переносятся при его копировании.
- **Список включённых и отключённых хранится в `level.dat`**, поэтому после переноса обычно заново включать ничего не нужно; проверьте через `/datapack list`, при необходимости используйте `/datapack enable <имя>` / `/datapack disable <имя>`, изменения применяются через `/reload`.
- **Версии должны совпадать**: датапак объявляет целевой `pack_format`, при несоответствии версии сервера загрузка будет отклонена или появится предупреждение.
- **Датапаки, добавляющие измерения, требуют особого внимания**: у такого мира будет каталог `dimensions/<пространство имён>/<путь>/`, и эти измерения загрузятся, только если на сервере установлен тот же датапак. Данные от этого не удаляются, но игроки туда не попадут.
- Встроенный в мир ресурспак (в старых версиях `resources.zip`, с 26.1 — в `resourcepacks/`) не отправляется игрокам автоматически; чтобы игроки увидели свои текстуры, настройте `resource-pack` в `server.properties`.

## 8. Модовые сохранения, разные версии и Bedrock

### 8.1 Перенос модового (Forge/NeoForge/Fabric) сохранения на плагинное ядро

Это вторая по величине ловушка после имён каталогов. **Плагинные ядра (Spigot/Paper и подобные) не знают блоков, предметов и сущностей, добавленных модами.**

- Модовые блоки в мире станут неизвестными блоками (обычно воздух, камень или блок-заглушка); **как только такие чанки загрузятся и будут сохранены заново, исходные данные могут быть перезаписаны на месте**, и вернуть мод потом может не помочь.
- Модовые предметы исчезнут из инвентарей и контейнеров, модовые сущности (машины, существа) будут отброшены.
- Модовые измерения (`dimensions/<пространство имён мода>/...`) без соответствующего мода не загрузятся.

Правильный подход: **сначала копия, затем загрузка на одноразовой копии**, посчитайте в журнале, сколько появилось неизвестных блоков и ошибок реестра; переносите, только если потеря приемлема. Если потери неприемлемы, оставайтесь на модовом ядре или начинайте с нуля.

### 8.2 Разные версии

- **Версия сохранения выше версии сервера**: сервер откажется загружать (проверка `DataVersion`). Единственный безопасный путь — обновить сервер, а не понижать мир.
- **Версия сохранения ниже версии сервера**: сервер обновит мир через DataFixer, обычно это работает, но **обновление необратимо**: после загрузки новой версией старую версию мир уже не открыть. Поэтому перед обновлением обязательно оставьте нетронутую копию.
- При переходе через несколько крупных версий надёжнее обновляться поэтапно (например, сначала 1.20, потом 1.21), проверяя на каждом шаге, см. [Обновление сервера, плагинов и MCDR](/tutorials/ops/updates).

### 8.3 Bedrock

Форматы миров Java Edition и Bedrock совершенно разные, **напрямую они друг друга не загружают**, нужны сторонние конвертеры, и конвертация обычно с потерями (редстоун, сущности, поведение части блоков). Структура каталогов сервера Bedrock — см. [Сервер BDS](/tutorials/bedrock/bds).

## 9. Типичные сценарии отказа

| Явление | Корневая причина | Что делать |
| --- | --- | --- |
| При входе совершенно новый пустой мир | Имя каталога не совпадает с `level-name`, или в каталоге нет `level.dat`, и сервер **создал** новый мир | Остановить сервер, сверить имя каталога; переименовать старый каталог для страховки и скопировать заново |
| Мир открывается, но Нижний мир и Энд — новый рельеф | `DIM-1/`, `DIM1/` не перенесены в `world_nether/`, `world_the_end/` или перенесены не на тот уровень (лишний уровень каталога) | После остановки скопировать заново в правильные каталоги |
| Мир открывается, но игрок «с нуля» | Имя файла данных игрока (UUID) не совпадает с UUID, который определил сервер | Переименовать `playerdata/`, `advancements/`, `stats/` по разделу 4 |
| Сервер отказывается загружать мир | Версия сохранения (`DataVersion`) выше версии сервера | Обновить сервер; **не** пытайтесь понизить мир |
| Часть чанков пропала, блоки перепутаны | Копирование при работающем сервере или заполненный диск | Скопировать заново из копии; сначала решить проблему места |
| В журнале `Failed to save` | Неверный владелец или права файлов, пользователь сервера не может писать | `chown -R` на пользователя, под которым работает сервер |
| В Linux «файл вроде есть, а сервер говорит, что нет» | Разный регистр (`MyWorld` и `myworld`) | Привести имя каталога и `level-name` к одному виду |
| Запуск надолго застревает на `Preparing spawn area` | Мир большой, первая загрузка требует времени; возможно, узкое место ввода-вывода диска | Терпеливо ждать, наблюдать загрузку CPU и диска; не перезапускать снова и снова |
| Не работают белый список и OP | `whitelist.json`, `ops.json` не в мире, их нужно пересоздать | Снова выполнить `/whitelist add`, `/op` или отредактировать вручную с правильными UUID |
| После миграции частые лаги | У одиночной игры и сервера разная модель нагрузки (дальность прорисовки, дистанция симуляции, число сущностей) | Настроить `view-distance`, `simulation-distance`, см. [Оптимизация производительности](/tutorials/java/optimize) |

## 10. Чек-лист проверки

Подтвердите каждый пункт и только потом открывайте сервер:

| Пункт проверки | Как проверить |
| --- | --- |
| В каталоге мира есть `level.dat` | `ls -la /opt/minecraft/server/world/level.dat` |
| Число региональных файлов совпадает с источником | Сравнить результат `find world/region -name '*.mca' \| wc -l` с обеих сторон |
| Объём трёх миров соответствует ожиданиям | `du -sh /opt/minecraft/server/world*` |
| В журнале запуска нет ошибок сохранения | `grep -n -i "failed\|unknown dimension\|no space" logs/latest.log` |
| Сид совпадает | `/seed` в игре и значение, записанное до миграции |
| Время и игровые правила совпадают | `/time query daytime`, `/gamerule keepInventory` и др. |
| Точка спавна совпадает | Перед `/setworldspawn` посмотреть текущую точку спавна и сравнить с записанной |
| Ключевые постройки на месте | Телепортироваться на записанные координаты и убедиться визуально |
| Нижний мир совпадает | `/execute in minecraft:the_nether run tp @s 0 64 0`, проверить известные порталы и рельеф |
| Энд совпадает | Войти в Энд, проверить состояние дракона, портал Энда и обратный портал |
| Прогресс игроков вернулся | Проверить инвентарь, опыт, экран достижений и статистику |
| Права и белый список корректны | Проверить `/whitelist list`, `/op` |
| Сервер может писать на диск | `sudo -u minecraft test -w /opt/minecraft/server/world && echo writable` |
| Резервные копии уже работают | Сразу вручную запустить скрипт копирования и убедиться, что новый мир попадает в копии |

## 11. После миграции

- **Зафиксируйте `online-mode`, белый список и проверку лицензии** и только потом начинайте накапливать данные игроков; смена режима аутентификации посреди работы изменит UUID.
- **Немедленно сделайте полную резервную копию** и отправьте её в копию в другом месте или офлайн, см. [Резервные копии в другом месте](/tutorials/ops/offsite-backup).
- Под нагрузку сервера заново задайте `view-distance`, `simulation-distance`, `max-players`: одиночное сохранение обычно создавалось с «одиночной» дальностью прорисовки, и после переноса на сервер может понадобиться заново сгенерировать окрестные чанки под большую дальность.
- Добавьте ротацию журналов и мониторинг диска, чтобы только что перенесённый большой мир не заполнил диск, см. [Управление журналами и ротация](/tutorials/ops/logs) и [Мониторинг и оповещения](/tutorials/ops/monitoring).
- **Bedrock (BDS) — отдельная история**: миры Java Edition и Bedrock — два совершенно разных формата, они не загружают друг друга напрямую, нужны сторонние конвертеры, и конвертация обычно с потерями. Структура каталогов сервера Bedrock — см. [Сервер BDS](/tutorials/bedrock/bds).
