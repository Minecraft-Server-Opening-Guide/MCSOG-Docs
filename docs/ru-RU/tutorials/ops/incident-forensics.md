В момент атаки на машине одновременно существуют две вещи: **доказательства, которые можно записать**, и **состояние, которое через несколько минут исчезнет навсегда**. Эта статья про второе — про то, как зафиксировать картину до перезагрузки, переустановки и любого блокирования. Профилактика — см. [Основы сетевой безопасности](/tutorials/ops/network-security) и [Основные типы сетевых атак и защита, специфичная для Minecraft](/tutorials/ops/attack-defense).

:::warn Статья не заменяет юридическую консультацию
Команды форензики, требования к хранению журналов и правила обработки персональных данных **зависят от операционной системы, дистрибутива, провайдера и юрисдикции**; везде, где что-то зависит от окружения, это отмечено. Если речь идёт о персональных данных игроков или возможном судебном разбирательстве, **обратитесь к специалисту и соблюдайте местные законы и правила дата-центра**.
:::

## 1. Почему «сначала форензика» — первое железное правило

### 1.1 Доказательства исчезают

Первое, что делает большинство при атаке, — **перезагрузка** или **переустановка**. Это худший выбор: **перезагрузка уничтожает почти все доказательства сетевого уровня**.

| Доказательство | Где | Как исчезает | Примерное время жизни |
| --- | --- | --- | --- |
| Процессы, открытые сокеты | Память | Завершение процесса, перезагрузка | От секунд до минут |
| Текущие соединения (established) | Таблица сокетов ядра | Закрытие соединения | Секунды |
| Таблица отслеживания conntrack | Память ядра | Истечение записи (по конфигурации) | От секунд до часов |
| Таблица ARP / соседей | Память ядра | Истечение записи | Минуты |
| Счётчики приёма, передачи и потерь на сетевой карте | Счётчики ядра | **Обнуляются после перезагрузки или сброса карты** | Теряются при перезагрузке |
| Счётчики попаданий правил брандмауэра | netfilter в ядре | **Обнуляются при перезагрузке; `iptables -Z` тоже обнуляет** | Теряются при перезагрузке |
| Файл захвата (pcap) | Диск | Только если удалить или перезаписать заполненным диском | Постоянно |
| Системные и служебные журналы | Диск | После ротации сжимаются, удаляются | От дней до недель |
| Журналы приложения (`logs/latest.log`) | Диск | Ротация, перезапись новым журналом | Дни |
| Конфигурация, скрипты, задачи по расписанию | Диск | Перезапись «заодно исправленным» | Постоянно, но легко изменить |
| Отчёты о падениях `crash-reports/` | Диск | Обычно не удаляются автоматически | Постоянно |
| Графики трафика и отчёты об атаке провайдера | Сторона провайдера | Очистка по срокам хранения провайдера | От дней до месяцев |

**Ключевое различие**: **изменяемые доказательства (volatile)** лежат в памяти и исчезают при перезагрузке; **постоянные (persistent)** лежат на диске, но теряются из-за ротации, перезаписи и случайных правок. Порядок всегда такой: **сначала фиксируем изменяемое, потом собираем постоянное**.

### 1.2 Что уничтожает перезагрузка

Одна перезагрузка одновременно уничтожает: распределение текущих TCP-соединений по исходным IP (именно по нему понимают, единичная атака или распределённая), таблицу conntrack (кто с кем общается, каким правилом обрабатывается пакет), накопленные значения счётчиков сетевой карты и число потерь, **счётчики попаданий правил брандмауэра** (единственное твёрдое доказательство «сколько именно отбросили мои правила»), подозрительные процессы в памяти (если атакующий уже закрепился на хосте, перезагрузка помогает ему замести следы) и не сброшенные на диск буферы журналов.

:::warn «Не перезагружать» не значит «ничего не делать»
Можно сохранять картину и одновременно снижать урон: добавить правила брандмауэра, ограничить скорость, перевести трафик на защиту, временно заблокировать. **Но любое изменение нужно записывать** (см. раздел 3), потому что изменение само меняет доказательства.
:::

### 1.3 Правильный порядок

```text
1. Не перезагружать, не переустанавливать, не выключать (кроме случая, когда хост точно полностью захвачен)
2. Сначала захват пакетов (tcpdump) — сетевые доказательства теряются быстрее всего
3. Снять состояние ядра (ss, conntrack, ip -s link, счётчики брандмауэра)
4. Снять состояние процессов и служб (ps, systemctl, journalctl)
5. Скопировать журналы и конфигурацию (работать с копиями, оригиналы не трогать)
6. Посчитать хеши, написать журнал событий, зафиксировать хронологию (в едином часовом поясе)
7. И только потом начинать смягчение и укрепление
```

## 2. Что собирать (с правильными командами)

:::warn Имена интерфейсов и пути зависят от системы
Ниже `eth0` используется как пример имени сетевой карты. **В реальности это может быть `ens3`, `enp1s0`, `eno1`, `bond0` и т. п.**; проверяйте через `ip -br link` или `ip addr`. Так же каталоги журналов, имена служб и инструменты брандмауэра в разных дистрибутивах различаются.
:::

```bash
ip -br link
# Пример вывода (у вас будет другой):
# lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
# eth0             UP             aa:bb:cc:dd:ee:ff <BROADCAST,MULTICAST,UP,LOWER_UP>
```

### 2.1 Захват пакетов: tcpdump

```bash
# Java Edition (TCP 25565)
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap 'port 25565'

# Bedrock / Geyser (UDP 19132)
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap 'udp port 19132'
```

| Параметр | Значение | Почему именно так |
| --- | --- | --- |
| `-i eth0` | Указать сетевую карту | **Замените на реальное имя интерфейса**; без указания tcpdump выберет сам и может выбрать неверно |
| `-nn` | Без разрешения имён (IP и порты остаются числами) | Обратный DNS **замедлит захват и вызовет потери пакетов**; хуже того, трафик атаки заставит вас **сделать массу DNS-запросов наружу, то есть сообщить противнику «меня атакуют»** |
| `-s 0` | Захватывать пакет целиком, без обрезки | По умолчанию захватываются первые байты, **после обрезки полезную нагрузку протокола не проанализировать**; `0` означает полную длину |
| `-w файл` | Писать в pcap | См. пояснение ниже |
| `'port 25565'` | Выражение фильтра BPF | Одинарные кавычки защищают от интерпретации shell; `port` совпадает и с TCP, и с UDP |

**Почему нужно писать в файл, а не выводить в терминал**: во время атаки скорость пакетов может достигать сотен тысяч в секунду, и вывод разобранных данных в терминал делает **сам tcpdump узким местом с массовыми потерями**, а поток текста лишает терминал смысла; `-w` пишет двоичный файл с куда меньшими накладными расходами. **Не забудьте про диск**: `-s 0` при высокой скорости может за несколько минут записать десятки GB, сначала посмотрите свободное место и ограничьте число пакетов через `-c` либо ротацию по размеру `-C` и число файлов `-W`:

```bash
# Остановиться после 200000 пакетов
sudo tcpdump -i eth0 -nn -s 0 -c 200000 -w /var/log/incident-cap.pcap 'port 25565'

# По 100 MB на файл, максимум 20 (около 2 GB), автоматическая ротация
sudo tcpdump -i eth0 -nn -s 0 -w /var/log/incident-$(date +%F-%H%M).pcap -C 100 -W 20 'port 25565'

df -h /var/log    # сначала посмотреть свободное место
```

:::tip Что делать, если пакеты не ловятся
**Права**: для захвата нужен `CAP_NET_RAW`, используйте `sudo` (`setcap` расширяет поверхность атаки, не рекомендуется). **Не тот интерфейс**: в контейнере сетевая карта отличается от хостовой (часто `docker0`, `veth*`, `br-*`), хостовая `eth0` может не видеть весь трафик. **Трафик уже очищен по пути**: после очистки у провайдера до вашей карты может доходить только нормальный трафик — именно поэтому нужно запрашивать данные трафика у провайдера (см. 2.6). **Группа безопасности облака**: на части платформ трафик отбрасывается до экземпляра, и локально его не поймать.
:::

После захвата сделайте грубую статистику (не выводите `tcpdump -r` пакет за пакетом); более тонкий анализ протоколов лучше делать **офлайн** на другой машине в Wireshark / `tshark`, **не анализируйте на продакшене параллельно с захватом**.

```bash
# Только посчитать пакеты
sudo tcpdump -nn -r /var/log/incident-2026-10-04-1200.pcap -q | wc -l

# Топ-20 исходных IP по числу появлений
sudo tcpdump -nn -r /var/log/incident-2026-10-04-1200.pcap -q 2>/dev/null \
  | awk '{print $3}' | cut -d. -f1-4 | sort | uniq -c | sort -rn | head -20
```

### 2.2 Состояние и счётчики брандмауэра

```bash
sudo iptables -L -v -n
sudo iptables -t nat -L -v -n

sudo nft list ruleset
sudo nft list counters
```

- `-L` перечисляет правила, `-v` показывает **счётчики пакетов и байтов по каждому правилу**, `-n` без разрешения имён (по той же причине, что `-nn`); `-t nat` — таблица NAT (DNAT/SNAT/проброс портов), без неё не разобраться, «куда перенаправляется трафик».
- **Смысл счётчиков**: счётчики на правилах `DROP`/`REJECT` **напрямую доказывают, сколько трафика отброшено правилом**, это самые сильные цифры для разбора и объяснения провайдеру. **Перезагрузка или `iptables -Z` их обнуляет**, поэтому снимать нужно в самом начале.
- `nft list ruleset` выводит полный набор правил (включая наборы и счётчики); `nft list counters` перечисляет только именованные объекты counter. **Отдельный счётчик есть только у правил, где объект counter определён явно**, у обычных правил встроенный счётчик отображается как `counter packets N bytes M` в `list ruleset`. **Подкоманды и формат вывода nft зависят от версии, ориентируйтесь на `man nft` и документацию дистрибутива.**

```bash
sudo iptables -L -v -n        > /root/incident/fw-iptables.txt 2>&1
sudo iptables -t nat -L -v -n > /root/incident/fw-iptables-nat.txt 2>&1
sudo nft list ruleset         > /root/incident/fw-nft.txt 2>&1
```

### 2.3 Таблица соединений

```bash
# Установленные соединения Java
ss -tan state established '( sport = :25565 )'

# UDP-сокеты (у Bedrock нет понятия «соединение», смотрим прослушивание и очереди)
ss -uan

# Сводка по сокетам (счётчики по состояниям, чтобы понять, много ли полуоткрытых соединений)
ss -s

# Включая SYN-RECV, видны следы флуда соединений
ss -tan '( dport = :25565 or sport = :25565 )'

# Число соединений по исходным IP, ищем «сосредоточенные» источники
ss -tan state established '( sport = :25565 )' | awk 'NR>1 {print $5}' \
  | cut -d: -f1 | sort | uniq -c | sort -rn | head -20
```

В `ss -tan` `t` = TCP, `a` = все состояния, `n` = числовой вид (тоже чтобы избежать DNS-разрешения).

**conntrack** (нужны `conntrack-tools` и включённый в ядре `nf_conntrack`):

```bash
sudo conntrack -L    # выгрузить все отслеживаемые соединения
sudo conntrack -S    # счётчики ошибок по CPU
sudo conntrack -C    # текущее число записей (сначала оно, потом решать про -L)
```

- `conntrack -L` **при большом числе соединений может работать очень медленно или зависнуть**, поэтому сначала оцените масштаб через `conntrack -C`.
- `conntrack -S` выводит `insert_failed`, `drop`, `early_drop`, `error` и др. **Рост `insert_failed` или `early_drop` означает, что таблица отслеживания заполнена**, и новые соединения будут отбрасываться — **это само по себе эксплуатируемый отказ в обслуживании** и ключевая подсказка «полоса не забита, но игроки не подключаются».

```bash
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
```

:::warn conntrack может вообще отсутствовать
conntrack не виден в случаях: **модуль `nf_conntrack` не загружен**, **чистый nftables без отслеживания соединений**, **не установлены `conntrack-tools`**, **в пространстве имён контейнера не видно таблиц хоста**, **на части облачных платформ кастомное ядро обрезало эту функцию**. **Это не ваша ошибка**, просто используйте `ss`, `ip -s link` и счётчики брандмауэра. И наоборот: на некоторых хостах с большой памятью `nf_conntrack_max` по умолчанию очень велик, **а время жизни записей тоже зависит от дистрибутива и конфигурации, не копируйте значения из чужих примеров**.
:::

### 2.4 Счётчики и скорость сетевой карты

```bash
ip -s link show eth0
cat /proc/net/dev
```

В разделе `RX`/`TX` команды `ip -s link` указаны **bytes / packets / errors / dropped / overrun / mcast**. Ключевые здесь — **`dropped` и `overrun`**: они означают, что **трафик превысил возможности карты или ядра**, и потери идут уже сейчас, даже если полоса не выбрана полностью. `cat /proc/net/dev` даёт те же счётчики по всем интерфейсам, удобно для общего снимка (**значения накопленные, обнуляются при перезагрузке, смысл имеет разница двух выборок**).

```bash
# Если sysstat установлен, наблюдать скорость в реальном времени (раз в секунду, 5 раз)
sar -n DEV 1 5
```

:::note Два условия для sar
1. **`sysstat` должен быть установлен** (Debian/Ubuntu: `sudo apt install sysstat`; RHEL: `sudo dnf install sysstat`).
2. **Должен быть включён сбор исторических данных** (обычно его ведёт таймер systemd или cron от sysstat). **Если сбор никогда не включался, `sar` может начать только с текущего момента и не покажет скорость во время атаки** — вот почему мониторинг нужно держать включённым заранее. `sar -n DEV 1 5` с интервалом — это **сбор в реальном времени**, он не зависит от наличия истории.
:::

`iftop` и `nload` — **необязательные инструменты наблюдения в реальном времени**:

```bash
sudo iftop -i eth0    # полоса в реальном времени по парам соединений
sudo nload eth0       # простой график входящего и исходящего трафика
```

:::warn Инструменты реального времени не сохраняют доказательств
`iftop` / `nload` — **приборные панели в терминале**, после закрытия их данных нет, **они не годятся как материал форензики**. В аварии ими удобно быстро понять направление, но **одновременно обязательно писать tcpdump на диск**. Эти инструменты сами теряют пакеты при высокой скорости, **не считайте их цифры точной статистикой**. Имена пакетов зависят от дистрибутива, в части дистрибутивов нужно сначала включить дополнительные репозитории вроде EPEL.
:::

### 2.5 Доказательства по процессам и службам

```bash
ps auxf
systemctl status <service>
journalctl -u <service> --since "1 hour ago"
```

- `ps auxf`: выводит все процессы **деревом**, чтобы увидеть то, чего быть не должно: посторонние майнеры, исполняемые файлы из `/tmp`, процессы, замаскированные под `java`, но указывающие на странный путь. **На скомпрометированном хосте сам `ps` может быть заменён или перехвачен, важные выводы нужно перепроверять несколькими способами.**
- `systemctl status <service>`: состояние службы и последние строки журнала. Имя службы зависит от способа развёртывания, например `minecraft`, `mcserver`, `paper`, **оно не фиксировано**.
- `journalctl -u <service> --since "1 hour ago"`: журнал systemd, поддерживает `--since`/`--until`, можно писать `"1 hour ago"`, `"2026-10-04 12:00:00"`, `"today"`. **По умолчанию выводит в локальной зоне, `--utc` принудительно переводит в UTC** — при форензике настоятельно рекомендуется везде использовать `--utc`. Если журнал уже ротирован, выгрузите его через `journalctl -u <service> --since ... --no-pager > файл` или читайте архивные файлы через `journalctl --file`.

Со стороны Minecraft:

| Путь | Содержимое | Замечание |
| --- | --- | --- |
| `logs/latest.log` | Текущий журнал | **Перезаписывается при перезапуске сервера**, до перезапуска обязательно скопируйте |
| `logs/YYYY-MM-DD-N.log.gz` | Исторические журналы (ротация по дням и номерам) | Уже сжаты, но остаются доказательством |
| `crash-reports/` | Отчёты о падениях | Обычно не чистятся автоматически, содержат стек и сведения о JVM |
| `plugins/*/` | Собственные журналы и базы плагинов | **Формат зависит от плагина**, часто есть записи входов, аудит команд, записи блокировок |
| `banned-ips.json` / `banned-players.json` | Списки блокировок | Фиксируют, какие меры вы принимали, часть хронологии |
| `usercache.json` / `ops.json` | Сопоставление игроков и администраторов | Связывают UUID с именами |

```bash
# Копировать, а не перемещать; оригиналы не менять ни в коем случае
sudo cp -a /srv/minecraft/logs /root/incident/mc-logs
sudo cp -a /srv/minecraft/crash-reports /root/incident/mc-crash-reports
```

`cp -a` сохраняет время изменения и права, **для форензики это важно** — `cp -r` проставит текущее время и разрушит хронологию. **Журналы прикладного уровня часто полезнее сетевых**: сеть может сказать только «было 40 тысяч соединений», а приложение — «некоторый аккаунт за 3 минуты пытался войти 900 раз»; плагины прав, входа, экономики и античита обычно оставляют записи, **именно они основной источник ответа на «кто и что сделал»**, конкретные места и форматы смотрите в документации плагинов.

### 2.6 Доказательства со стороны облака и дата-центра

**То, что видите вы, не равно всему трафику.** Провайдер находится выше по потоку и видит входящий трафик вашего экземпляра **до отбрасывания** (трафик, отброшенный группой безопасности или сетевой ACL, на вашей машине вообще не виден), **суммарную полосу и скорость пакетов атаки** (pps/Mbps) и факт срабатывания очистки, оценку типа атаки и распределение источников, а также возможности журналов потоков (flow logs) на стороне платформы — **предоставляются ли они, платные ли и сколько хранятся, сильно различается, ориентируйтесь на документацию провайдера**.

**Что делать: немедленно открыть тикет**, сообщить, что вас атакуют, запросить детали трафика и отчёт об атаке, а также спросить, нужно ли переключиться на защищённый IP или включить очистку. **Не пишите просто «меня бьют»**, конкретное содержание — в разделе 5.

## 3. Правильное сохранение доказательств

### 3.1 Посчитать хеши для всех доказательств

```bash
cd /root/incident
sha256sum incident-*.pcap > incident.sha256
```

**Смысл хеша — доказать, что «после сбора никто это не менял»**:

- **Файл хешей нужно хранить отдельно от хешируемых файлов** (другой каталог, другой диск, лучше ещё одна копия в другом месте). В одном каталоге тот, кто может изменить файл, изменит и хеш, и доказательная сила обнулится.
- **Проверка**: `sha256sum -c incident.sha256`. **В файле хешей записаны относительные или абсолютные пути, после перемещения проверка не пройдёт** — это не повреждение файла, а изменение пути.
- **Делать для всех доказательств**, а не только для pcap:

```bash
find /root/incident -type f -print0 | sort -z | xargs -0 sha256sum > /root/incident.sha256
```

`find -print0` вместе с `xargs -0` корректно обрабатывает имена с пробелами; `sort -z` обеспечивает стабильный порядок для сравнения. **Файл хешей записывается вне каталога доказательств**, и ещё одна копия — на офлайн-носитель.

### 3.2 Никогда не трогать оригиналы

- **Анализировать только копии**. `tcpdump -r` работает только на чтение, это безопасно; любое «исправление», «преобразование» или «объединение» делайте на копии.
- При форензике целого диска стандартная практика — `dd` в образ и немедленный расчёт хеша образа:

```bash
# Внимание: ёмкость цели должна быть больше исходного устройства; операция полностью перезапишет цель
sudo dd if=/dev/sda of=/mnt/evidence/sda.img bs=4M conv=noerror,sync status=progress
sha256sum /mnt/evidence/sda.img > /mnt/evidence/sda.img.sha256
```

:::warn Разрушительность dd
`dd` **безусловно перезаписывает** то устройство, на которое указывает `of=`. **Перед выполнением обязательно проверьте через `lsblk` имена исходного и целевого устройств: одна неверная буква уничтожит данные.** Если не уверены — не выполняйте.
:::

### 3.3 Хронология: часовой пояс указывать обязательно

**Это самая частая и самая серьёзная ошибка**: смешать в одной таблице локальное время из `journalctl`, UTC от провайдера и время из журналов плагинов — и порядок событий полностью перепутается, вплоть до противоположных выводов.

1. **Записывайте всё в UTC** и явно укажите в документе «все времена ниже — UTC».
2. Одновременно **запишите локальную зону и смещение от UTC**, чтобы сверяться с локальными журналами.
3. Используйте формат ISO 8601 и избегайте двусмысленных записей вроде `10/04/2026`.

```bash
date -u +%FT%TZ      # пример: 2026-10-04T09:32:21Z
date +%FT%T%:z       # пример: 2026-10-04T17:32:21+08:00
timedatectl          # часовой пояс системы и состояние синхронизации NTP
```

`date -u +%FT%TZ` выводит время UTC с суффиксом `Z`, **`Z` означает UTC, а не аббревиатуру зоны** (не пишите `CST`, она соответствует как минимум трём разным зонам).

:::warn Сами часы могут быть неверны
Если часы хоста неточны или NTP не синхронизирован, **все отметки времени в журналах недостоверны**. Проверьте через `timedatectl`, равно ли `System clock synchronized` значению `yes`, и запишите текущее смещение. **Обнаруженный дрейф нужно отметить в журнале событий**, иначе сверка между устройствами даст неверные выводы.
:::

### 3.4 Вести журнал событий (записывать по ходу действий)

| Что записывать | Пояснение |
| --- | --- |
| Время обнаружения | Кто и каким образом обнаружил (отзыв игрока, оповещение мониторинга, заметили сами) |
| Симптомы | Конкретные проявления: лаги, обрывы, невозможность подключиться, забитая полоса |
| Время каждого действия | **С указанием зоны**, что именно «я сделал» |
| Внесённые изменения | Добавленные правила брандмауэра, ограничения скорости, заблокированные IP, переключённая запись DNS |
| Имена файлов доказательств | Что в каждом файле и когда он снят |
| С кем связывались | Номер тикета провайдера, время, суть ответа |
| Текущее состояние | Продолжается ли атака |

:::warn Меры смягчения сами меняют доказательства
Каждое правило брандмауэра, добавленное для остановки кровотечения, **меняет характеристики последующего захваченного трафика** (пакеты, которые раньше доходили, теперь отбрасываются и не ловятся). Это неизбежно, но **обязательно к записи**: зафиксируйте **момент добавления правила** (дальнейший анализ ведётся от него), по возможности **сначала снимите один раунд пакетов, потом меняйте правила** (хотя бы 30 секунд), записывайте **полное содержимое правила**, а не «я добавил ограничение скорости». Иначе потом невозможно объяснить, «почему после 14:05 трафик атаки внезапно исчез».
:::

### 3.5 Права на файлы и защита данных

```bash
chmod 700 /root/incident
chmod 600 /root/incident/*
chmod 600 /root/incident.sha256
```

- Доказательства содержат **IP игроков, имена аккаунтов, содержимое чата, возможно учётные данные для входа**, **по умолчанию это следует считать чувствительными данными**. Каталог `700` (вход только владельцу), файлы `600` (чтение и запись только владельцу).
- **Не** кладите доказательства в веб-каталог и не делайте `chmod 777` «для удобства просмотра».
- **Передача** — через `scp` / `rsync -e ssh` (шифрование SSH), не по открытому FTP и не вложением в письмо.
- **Защита данных**: при работе с персональными данными игроков **учитывайте применимое законодательство** (например, GDPR в ЕС, законы о персональных данных в разных странах) — во многих юрисдикциях IP-адрес считается персональными данными. Принцип: **собирать только необходимый объём, ограничить цель (расследование инцидента безопасности), ограничить доступ, удалить по истечении срока**. **Конкретные обязанности зависят от страны и региона, ориентируйтесь на местное законодательство и вашу политику конфиденциальности.**
- **Не** публикуйте доказательства (особенно pcap с чатом и IP игроков) на форумах или в чатах «на опознание».

## 4. Атрибуция: что можно выяснить, а что нет

**Принять невиновную третью сторону за атакующего — это реальный вред, а также потеря доверия к вашей жалобе.**

### 4.1 UDP-трафик с поддельным исходным IP: атрибуция практически невозможна

UDP — **протокол без соединения**, **поле исходного IP можно подделать произвольно**, и поддельный пакет отправляется без получения какого-либо ответа. Поэтому:

- **В UDP-флуде (включая подавляющее большинство UDP-отражений с усилением) исходный IP поддельный и обычно не поддаётся атрибуции полностью.**
- **Не** жалуйтесь на IP, который чаще всего встречается в UDP-флуде, не блокируйте его и не обвиняйте публично — **этот IP с большой вероятностью сам является пострадавшей стороной, чей адрес подделали**.
- Блокировка отдельного IP против поддельного трафика **бессмысленна** (достаточно поменять поддельное значение); правильный подход — **очистка трафика у провайдера, ограничение скорости, фильтрация по признакам протокола**.

Немногие оставшиеся зацепки: если удаётся определить, что атака использует конкретную службу (DNS, NTP, memcached, CLDAP и т. п.), **тот сервер — «используемый открытый сервер», а не атакующий**; если у исходного IP и порта есть устойчивая закономерность, это всё ещё имеет ценность для расследования, но **выводы должны быть осторожными**; промежуточные устройства на пути трафика (сторона провайдера) видят больше.

### 4.2 TCP-атаки: исходный IP обычно настоящий, но это всё ещё не «атакующий»

TCP требует **трёхстороннего рукопожатия**, и для его завершения нужно получать ответные пакеты, поэтому в **TCP-атаках на Minecraft** — массовом входе ботов, флуде соединений, флуде запросов состояния (status ping) — **исходный IP обычно настоящий** и его можно расследовать. **Но «настоящий IP» не равно «сам атакующий»**: это может быть **взломанный сторонний хост** (VPS с бэкдором, взломанный домашний роутер), **выход прокси / VPN / сервиса обхода**, **выходной узел Tor** или **пользователь за общим NAT**. Правильная формулировка: **«этот IP участвовал в трафике атаки», а не «владелец этого IP — атакующий»**. В жалобе это различие очень важно.

### 4.3 Отражение и усиление: источник — невиновная третья сторона

У атаки с отражённым усилением **две жертвы**: вы и **те открытые серверы, которые используют**. Их используют потому, что администраторы **по ошибке открыли в интернет UDP-службы DNS, NTP, memcached и подобные**.

- **Не сообщайте об источнике отражения как об атакующем**, сообщайте, что **«на таком-то IP служба является открытым источником отражения и используется»**;
- Уведомление на `abuse@` таких IP **помогает** (после исправления администратором поверхность отражения исчезнет), но **тон должен быть «вашу службу используют», а не «вы меня атакуете»**;
- Критерии: **ответный пакет намного больше запроса** (коэффициент усиления), и **источник — широко известный порт UDP-службы**.

### 4.4 Различайте «сосредоточенность» и «распределённость»

| Наблюдаемая картина | Более вероятная природа | Что можно сделать |
| --- | --- | --- |
| **Один или несколько IP дают подавляющее большинство соединений** | Точечная атака, взломанный хост, тестовое сканирование | Стоит расследовать этот IP; можно временно заблокировать для остановки кровотечения |
| **Тысячи IP, каждый отправляет немного** | Распределённый ботнет или поддельные источники | Блокировка IP бесполезна; нужна очистка у провайдера и ограничение скорости |
| **TCP-рукопожатие завершается, число соединений стабильно растёт** | Настоящие источники (класс входа ботов) | Расследование IP + защита у провайдера + ограничение входа |
| **Много SYN без последующего рукопожатия** | SYN-флуд (возможны поддельные источники) | Включить SYN cookies, очистка у провайдера |
| **Вал крупных UDP-пакетов, фиксированный порт источника** | Отражённое усиление | Фильтрация по протоколу и порту, очистка у провайдера, **не жалуйтесь на исходный IP** |
| **Трафик небольшой, но служба очень медленная** | Возможно, атака прикладного уровня или исчерпание ресурсов | Смотреть журналы приложения, таблицу соединений и ресурсы хоста |

**Главный критерий**: **немного сосредоточенных IP = стоит расследовать; масса разбросанных IP = не догнать и не пересчитать, переходите к защите.**

### 4.5 Что делать, узнав IP

```bash
whois 203.0.113.10
```

Вывод `whois` обычно содержит **принадлежность сети (netname/descr), организацию, страну и контактный адрес `abuse`**. Замечания:

- **Клиент `whois` может быть не установлен** (Debian/Ubuntu: `sudo apt install whois`; RHEL: `sudo dnf install whois`);
- **У разных RIR (региональных интернет-регистратур) разный формат вывода**, поля `abuse-c`, `OrgAbuseEmail`, `abuse-mailbox` называются по-разному, **читайте вручную, не пытайтесь жёстко сопоставлять скриптом**;
- Предпочтительнее **RDAP** (Registration Data Access Protocol) — **современная HTTP-замена WHOIS**, возвращает структурированный JSON и поддерживает автоматические запросы. IANA предоставляет направляющую службу (`https://rdap.org/ip/<IP>` перенаправляет в соответствующую RIR), **конкретные URL и поля у каждой RIR — по её документации**.

**Принадлежность к ASN**: определить, к какой автономной системе (AS) и какому оператору или дата-центру относится IP, помогает понять, это «VPS в каком-то облаке» или «домашнее подключение в какой-то стране». Способы: RDAP-службы RIR, `whois -h whois.radb.net` и другие, **инструментов и источников данных много, покрытие различается**, не полагайтесь на единственный источник.

**Контакт abuse**: **адрес `abuse@`** (или форма abuse) в WHOIS/RDAP — **правильный канал жалобы**: **отправляйте в отдел abuse дата-центра или хостинг-провайдера, которому принадлежит IP, а не в случайный домашний ISP игрока** — дата-центр реально может что-то сделать с машинами в своей сети (приостановить обслуживание), а ISP на взломанный домашний роутер обычно реагирует очень медленно. **Приложите доказательства**: временное окно с указанием зоны, протоколы и порты, список исходных IP, число пакетов и скорость, хеш pcap; **жалоба без доказательств обычно игнорируется**. При нескольких сетях **жалуйтесь отдельно в каждую**, не называйте публично в чатах.

### 4.6 Закон и границы

- **Правила различаются по странам и регионам**: что считается преступлением, какие журналы хранить, можно ли самостоятельно собирать данные — везде по-разному. **Статья не является юридической консультацией.**
- **Рекомендуемый порядок**: сначала **провайдер** (он может очищать трафик, видеть данные выше по потоку и имеет процесс abuse); при серьёзной и постоянной атаке (вымогательство, кража данных, явное преступление) — **полиция или органы по киберпреступности**, сохраняя полную цепочку доказательств.
- **Категорически не мстите**: запускать DDoS против источника (так называемый DDoS-back), взламывать чужой хост или «отвечать хакерской атакой» — **почти во всех юрисдикциях это само по себе преступление**, которое превращает вас из пострадавшего в обвиняемого и уничтожает вашу изначально правую позицию.
- **Не занимайтесь доксингом и не объявляйте награду** за IP атакующего: можно задеть невиновную третью сторону, а также это может быть преследованием или нарушением приватности.

## 5. Отчёт и эскалация

**«Меня атакуют, срочно разберитесь» почти никогда не даёт результата.** Хороший тикет позволяет адресату за 30 секунд понять, что делать:

```text
Тема: [DDoS/атака] экземпляр <instance-id>/<ip> подвергается атаке, прошу помощи и данных о трафике

1. Затронутый ресурс
   - Публичный IP: 203.0.113.10
   - Порты/протоколы: 25565/TCP (Java Edition), 19132/UDP (Bedrock)
   - ID экземпляра / номер заказа: <заполнить>

2. Временное окно (укажите часовой пояс)
   - Начало: 2026-10-04 09:12 UTC (локальное время 17:12, UTC+8)
   - Конец: продолжается / прекратилось в 09:40 UTC
   - Пиковый период: 09:20 - 09:35 UTC

3. Тип и масштаб атаки (известная часть)
   - Оценка типа: UDP-отражение с усилением (предположительно NTP/DNS) / флуд TCP-соединений / массовый вход ботов
   - Наблюдаемая скорость: около XX Mbps, около XX kpps (источник: счётчики ip -s link на машине)
   - Потери на сетевой карте: RX dropped вырос с 0 до XXXXX (за тот же период)

4. Уже принятые меры
   - 09:25 UTC добавлено правило iptables, ограничивающее число соединений с одного IP
   - 09:30 UTC заблокированы исходные IP (действует только для TCP)
   - Перезагрузки и переустановки не было, картина сохранена

5. Просьбы
   - Предоставить статистику трафика, поступавшего в этот экземпляр за указанный период, и отчёт об атаке
   - Подтвердить, можно ли включить очистку трафика или защищённый IP, и включена ли она
   - Если есть журналы потоков на стороне платформы, помочь их выгрузить

6. Файлы доказательств
   - incident-2026-10-04-0915.pcap (sha256: <хеш>)
   - fw-iptables.txt, ss-established.txt, conntrack.txt
   - при необходимости предоставим полный пакет доказательств
```

| Элемент | Почему обязателен |
| --- | --- |
| **Временное окно с часовым поясом** | Провайдеру нужно найти ваш трафик в массе журналов, неточное время означает «не найдут» |
| **Тип и масштаб атаки** | Определяет, пойдут они по процессу «очистка» или «разбирательство» |
| **Затронутые IP и порты** | Подтверждает, по какому ресурсу бьют |
| **Продолжается ли атака** | Определяет срочность |
| **Уже принятые меры** | Чтобы обе стороны не дублировали действия и не мешали друг другу |
| **Имена файлов доказательств** | Делает переписку прослеживаемой |

**Про жалобы abuse**: у провайдеров обычно есть свой адрес abuse или форма жалобы для случаев «хосты в их сети атакуют других», **конкретный адрес — по сайту провайдера и записи WHOIS**. **Они видят трафик, который вы не видите** (маршрутизация выше по потоку, оборудование очистки, журналы потоков платформы) — вы даёте вид с оконечной точки, они — вид со стороны сети, и только вместе картина полная. **Ограничения приватности**: провайдер **может не сообщать вам подробности о других клиентах из-за политики конфиденциальности или закона**, это нормально, **не считайте, что они бездействуют, если «не дают список IP»**. Продолжайте следить и записывать номер тикета и время каждого ответа, формируя полную хронологию переписки (она тоже часть журнала событий).

## 6. После инцидента

**Реагирование без разбора равно потраченному впустую разу.**

### 6.1 Вопросы, на которые отвечает разбор

| Вопрос | Что смотреть конкретно |
| --- | --- |
| **Что сработало?** | Какое правило брандмауэра дало попадания? Сработала ли очистка? Разумен ли порог ограничения скорости? |
| **Что не сработало?** | Какие меры не дали эффекта? Какие, наоборот, задели нормальных игроков? |
| **Как долго восстанавливались?** | Реальное время от обнаружения до смягчения, на каком шаге узкое место (медленно обнаружили? медленно оценили? не было плана?) |
| **Вернулся ли атакующий?** | Сравните временные окна и распределение источников, одна это волна или новая |
| **Были ли потери данных?** | Целы ли сохранения? Был ли откат? Работоспособны ли копии? |
| **Что раскрылось?** | Не были ли замечены или утекли аккаунты, ключи, пароли панели? |

### 6.2 Действия по укреплению

- **Ограничение скорости (rate limit)**: поставьте пределы на частоту соединений, число одновременных соединений с одного IP, скорость входа. **Это самый эффективный и самый дешёвый слой**. Например, модули `hashlimit`/`connlimit` в `iptables` или ограничение входа на уровне плагина сервера (**конкретные имена модулей и синтаксис зависят от ядра и инструментов, перед настройкой проверьте доступность модуля**).
- **Прокси / усиленная защита**: скрыть реальный IP (прокси класса TCPShield, защищённый IP провайдера, TCP-пересылка через CDN). **Учтите**: прокси закрывает объёмные атаки сетевого уровня, **но не атаки прикладного уровня (вход ботов, уязвимости протокола)** — для них нужны проверки и ограничения на стороне сервера.
- **Смена провайдера или дата-центра**: если провайдер не даёт очистку или атака нацелена на фиксированный ресурс в этой сети, переезд — реалистичный выбор. **Перед переездом убедитесь, что у нового места есть защита от DDoS и очистка.**
- **Белый список**: для небольшого сервера знакомых **`white-list=true` — самое радикальное решение** — атакующий просто не войдёт, и атаки класса «вход» не смогут расходовать ваши ресурсы.
- **Сокращение поверхности атаки**: закройте ненужные порты (RCON, query, панель), см. [Основы сетевой безопасности](/tutorials/ops/network-security); укрепление хоста — см. [Укрепление безопасности системы](/tutorials/ops/system-security).
- **Мониторинг и оповещения**: **при следующей атаке вы хотите проснуться от мониторинга, а не от ругани игроков.** Как минимум следите за полосой, числом соединений, TPS и живостью процесса.

### 6.3 Целы ли резервные копии, есть ли офлайн-копия

- **Проверьте, что копия действительно восстанавливается**, а не просто «файл существует». Учения по восстановлению — см. [Резервное копирование и восстановление](/tutorials/java/backup) и [Резервные копии в другом месте](/tutorials/ops/offsite-backup).
- **Убедитесь, что хотя бы одна копия офлайн** (или неизменяемая / только для чтения). Если атака сопровождалась взломом хоста, **онлайн-копия с правом записи могла быть зашифрована или удалена**.
- **Проверьте точку копии**: если во время атаки был откат, нужно чётко понимать, **до какого момента восстанавливаемся** и насколько откатятся данные игроков.

### 6.4 Ротация учётных данных и ключей

**Если есть хоть какая-то вероятность раскрытия, считайте, что утекло, и меняйте всё.**

| Объект | Действие |
| --- | --- |
| Пароль панели / админки | Немедленно сменить и включить двухфакторную аутентификацию (если есть) |
| Приватный ключ SSH | Сгенерировать новую пару, удалить старый открытый ключ, проверить `authorized_keys` на лишние записи |
| Пароль RCON | Сменить; убедиться, что `enable-rcon` не открыт в интернет |
| Учётная запись базы данных | Сменить пароль, проверить, нет ли слишком широких прав вроде `root@%` |
| API Key / Access Key облачной платформы | Отозвать и пересоздать в консоли, проверить журнал вызовов на аномалии |
| Сервисные аккаунты / Token (плагины, копии, мониторинг) | Отозвать и пересоздать по одному |
| Аккаунты игроков | Если утекла база плагина, **сообщите игрокам о смене пароля** |

**Одновременно проверьте**: нет ли новых учётных записей в `~/.ssh/authorized_keys`, `/etc/passwd` и `/etc/shadow`, нет ли подозрительных задач в `crontab -l` и `/etc/cron.*`, нет ли странных юнитов в systemd. **Эти проверки делайте после завершения форензики и записывайте найденное.**

### 6.5 Чек-лист выводов

```text
[ ] Обнаружили вовремя? Покрывают ли оповещения полосу, число соединений, TPS и живость процесса?
[ ] Есть ли письменный план? (кто оценивает, кто связывается с провайдером, кто объявляет игрокам)
[ ] Захват пакетов сделан вовремя? Не потеряли ли доказательства из-за перезагрузки?
[ ] Единый ли часовой пояс в хронологии?
[ ] Посчитаны ли хеши и сохранены ли отдельно от доказательств?
[ ] Были ли ошибочные блокировки нормальных игроков? Как их снимали?
[ ] Зафиксированы ли в тикете провайдера полная хронология и доказательства?
[ ] Проверена ли восстанавливаемость копий и есть ли офлайн-копия?
[ ] Все ли потенциально раскрытые учётные данные ротированы?
[ ] Записано ли «чему научились» в документ, а не оставлено в голове?
```

## 7. Готовый скрипт сбора доказательств

Скрипт ниже собирает **изменяемую** часть из раздела 2 в каталог с отметкой времени, считает хеши и печатает сводку. **Использование: `sudo bash capture-evidence.sh`** (для захвата пакетов и conntrack нужен root). **Перед запуском проверьте** имя интерфейса (скрипт сам определяет интерфейс маршрута по умолчанию), каталог доказательств (по умолчанию `/root/incident`), длительность захвата и предел числа пакетов. **Скрипт выполняет только чтение, не меняет конфигурацию и не перезапускает службы.**

```bash
#!/usr/bin/env bash
#
# capture-evidence.sh - сбор изменяемых доказательств при атаке на сервер Minecraft
#
# Использование: sudo bash capture-evidence.sh
#
# Особенности:
#   - только чтение, не меняет конфигурацию системы, не перезапускает службы
#   - необязательные инструменты проверяются через command -v, при отсутствии фиксируются и пропускаются
#   - для всех результатов считается SHA-256, сводка пишется в отдельный файл
#
# Внимание: имена интерфейсов, служб и пути журналов зависят от системы, измените переменные ниже при необходимости.

set -u

# ---------------- Параметры ----------------
IFACE="${IFACE:-}"                            # пусто = определить интерфейс маршрута по умолчанию автоматически
CAPTURE_SECONDS="${CAPTURE_SECONDS:-60}"      # длительность захвата в секундах
CAPTURE_PACKETS="${CAPTURE_PACKETS:-200000}"  # предел числа пакетов, чтобы не заполнить диск
MC_TCP_PORT="${MC_TCP_PORT:-25565}"           # порт Java Edition
MC_UDP_PORT="${MC_UDP_PORT:-19132}"           # порт Bedrock / Geyser
MC_SERVICE="${MC_SERVICE:-}"                  # имя службы systemd, пусто = пропустить
MC_DIR="${MC_DIR:-}"                          # каталог сервера, пусто = пропустить копирование журналов
BASE_DIR="${BASE_DIR:-/root/incident}"

STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
OUT="${BASE_DIR%/}/incident-${STAMP}"

# ---------------- Предварительные проверки ----------------
if [ "$(id -u)" -ne 0 ]; then
  echo "Ошибка: нужны права root (для захвата пакетов и conntrack). Запускайте через sudo." >&2
  exit 1
fi

mkdir -p "$OUT" || { echo "Ошибка: не удалось создать $OUT" >&2; exit 1; }
chmod 700 "$BASE_DIR" 2>/dev/null || true
chmod 700 "$OUT" 2>/dev/null || true

if [ -z "$IFACE" ]; then
  IFACE="$(ip route show default 2>/dev/null | awk '/default/ {print $5; exit}')"
fi
if [ -z "$IFACE" ]; then
  IFACE="eth0"
  echo "Предупреждение: не удалось определить интерфейс маршрута по умолчанию, откат на eth0. Переопределите через IFACE=..." >&2
fi

echo "==> Каталог доказательств: $OUT"
echo "==> Интерфейс сбора: $IFACE"
echo "==> Время сбора: $STAMP (UTC)"
echo "==> Свободное место на диске:"
df -h "$OUT" 2>/dev/null || true

# ---------------- Функции сбора ----------------
capture() {
  _name="$1"
  shift
  echo "  - $_name"
  "$@" > "${OUT}/${_name}.txt" 2>&1 || echo "    (команда вернула ненулевой код, вывод всё равно сохранён)"
}

{
  echo "Начало сбора (UTC): $(date -u +%FT%TZ)"
  echo "Локальное время: $(date +%FT%T%:z)"
  echo "Имя хоста: $(hostname)"
  echo "Ядро: $(uname -a)"
  echo "Время работы: $(uptime)"
  echo "Интерфейс: $IFACE"
  echo "Java порт: $MC_TCP_PORT  UDP порт: $MC_UDP_PORT"
} > "${OUT}/meta.txt" 2>&1
chmod 600 "${OUT}/meta.txt" 2>/dev/null || true

echo "==> Собираем состояние системы и процессов"
capture ps-auxf ps auxf
capture ss-summary ss -s
capture ss-tcp-all ss -tan
capture ss-udp ss -uan
capture ss-tcp-listen ss -tlnp
capture ip-addr ip -br addr
capture ip-route ip route show
capture ip-neigh ip neigh show
capture uptime uptime
capture date-utc date -u +%FT%TZ
capture timedatectl timedatectl
capture df-h df -h

if command -v ss >/dev/null 2>&1; then
  echo "  - ss-java-established"
  ss -tan state established "( sport = :${MC_TCP_PORT} )" \
    > "${OUT}/ss-java-established.txt" 2>&1 || true
  echo "  - ss-source-ranking"
  ss -tan state established "( sport = :${MC_TCP_PORT} )" 2>/dev/null \
    | awk 'NR>1 {print $5}' | cut -d: -f1 \
    | sort | uniq -c | sort -rn | head -50 \
    > "${OUT}/ss-source-ranking.txt" 2>&1 || true
fi

echo "==> Собираем счётчики сетевой карты"
if command -v ip >/dev/null 2>&1; then
  echo "  - ip-s-link"
  ip -s link show "$IFACE" > "${OUT}/ip-s-link.txt" 2>&1 || true
fi
[ -r /proc/net/dev ] && capture proc-net-dev cat /proc/net/dev
if command -v sar >/dev/null 2>&1; then
  capture sar-dev sar -n DEV 1 5
else
  echo "sar не установлен, пропускаем выборку скорости в реальном времени (sar даёт sysstat)" > "${OUT}/sar-dev.txt"
fi

echo "==> Собираем состояние и счётчики брандмауэра"
if command -v iptables >/dev/null 2>&1; then
  capture fw-iptables iptables -L -v -n
  capture fw-iptables-nat iptables -t nat -L -v -n
else
  echo "iptables недоступен" > "${OUT}/fw-iptables.txt"
fi
if command -v nft >/dev/null 2>&1; then
  capture fw-nft nft list ruleset
  capture fw-nft-counters nft list counters
else
  echo "nft недоступен" > "${OUT}/fw-nft.txt"
fi

echo "==> Собираем таблицу отслеживания соединений (если доступна)"
if command -v conntrack >/dev/null 2>&1; then
  capture conntrack-list conntrack -L
  capture conntrack-stats conntrack -S
  capture conntrack-count conntrack -C
else
  echo "conntrack недоступен (нужны conntrack-tools и включённый в ядре nf_conntrack)" \
    > "${OUT}/conntrack-list.txt"
fi
[ -r /proc/sys/net/netfilter/nf_conntrack_count ] \
  && capture conntrack-sysctl cat /proc/sys/net/netfilter/nf_conntrack_count
[ -r /proc/sys/net/netfilter/nf_conntrack_max ] \
  && capture conntrack-max cat /proc/sys/net/netfilter/nf_conntrack_max

echo "==> Собираем службы и журналы"
if [ -n "$MC_SERVICE" ] && command -v systemctl >/dev/null 2>&1; then
  capture systemctl-status systemctl status "$MC_SERVICE" --no-pager
  if command -v journalctl >/dev/null 2>&1; then
    capture journalctl-1h \
      journalctl -u "$MC_SERVICE" --since "1 hour ago" --utc --no-pager
  fi
else
  echo "MC_SERVICE не задан, пропускаем сбор состояния службы (использование: MC_SERVICE=minecraft sudo -E bash $0)" \
    > "${OUT}/systemctl-status.txt"
fi

if [ -n "$MC_DIR" ] && [ -d "$MC_DIR" ]; then
  echo "  - копируем журналы сервера (-a сохраняет отметки времени)"
  [ -d "${MC_DIR}/logs" ] && cp -a "${MC_DIR}/logs" "${OUT}/mc-logs" 2>/dev/null || true
  [ -d "${MC_DIR}/crash-reports" ] \
    && cp -a "${MC_DIR}/crash-reports" "${OUT}/mc-crash-reports" 2>/dev/null || true
else
  echo "MC_DIR не задан, пропускаем копирование журналов сервера (использование: MC_DIR=/srv/minecraft sudo -E bash $0)" \
    > "${OUT}/mc-logs-note.txt"
fi

echo "==> Короткий захват ${CAPTURE_SECONDS}s / не более ${CAPTURE_PACKETS} пакетов"
if command -v tcpdump >/dev/null 2>&1; then
  PCAP="${OUT}/capture-${STAMP}.pcap"
  timeout "$CAPTURE_SECONDS" tcpdump -i "$IFACE" -nn -s 0 \
    -c "$CAPTURE_PACKETS" -w "$PCAP" \
    "port ${MC_TCP_PORT} or udp port ${MC_UDP_PORT}" 2>"${OUT}/tcpdump.log" || true
  echo "  - файл захвата: $PCAP"
  echo "  - число пакетов:"
  tcpdump -nn -r "$PCAP" -q 2>/dev/null | wc -l | tee "${OUT}/pcap-packet-count.txt" || true
  echo "  - рейтинг исходных IP (топ 30):"
  tcpdump -nn -r "$PCAP" -q 2>/dev/null | awk '{print $3}' | cut -d. -f1-4 \
    | sort | uniq -c | sort -rn | head -30 > "${OUT}/pcap-source-ranking.txt" || true
else
  echo "tcpdump не установлен, захват невозможен. Установите его как можно скорее и повторите сбор (Debian/Ubuntu: apt install tcpdump)" \
    > "${OUT}/tcpdump.log"
fi

echo "==> Считаем SHA-256"
find "$OUT" -type f ! -name 'SHA256SUMS' -print0 \
  | sort -z | xargs -0 sha256sum > "${OUT}/SHA256SUMS" 2>/dev/null || true
# Контрольную сумму сохраняем отдельно вне каталога доказательств, чтобы её нельзя было подменить вместе с ними
cp "${OUT}/SHA256SUMS" "${BASE_DIR%/}/SHA256SUMS-${STAMP}.txt" 2>/dev/null || true
find "$OUT" -type f -exec chmod 600 {} + 2>/dev/null || true

echo
echo "=================== Сводка сбора ==================="
echo "Каталог   : $OUT"
echo "Начало    : $(head -n 1 "${OUT}/meta.txt" 2>/dev/null)"
echo "Интерфейс : $IFACE"
echo "Файлов    : $(find "$OUT" -type f | wc -l)"
echo "Занято    : $(du -sh "$OUT" 2>/dev/null | cut -f1)"
echo "Захват    : $(ls -1 "${OUT}"/*.pcap 2>/dev/null | head -n 1)"
echo "Проверка  : ${BASE_DIR%/}/SHA256SUMS-${STAMP}.txt"
echo "------------------------------------------------"
echo "Дальнейшие шаги (важно):"
echo "  1. Не перезагружайте и не переустанавливайте систему: изменяемые данные теряются при перезагрузке."
echo "  2. Немедленно скопируйте доказательства на другую машину или офлайн-носитель:"
echo "     scp -r root@<IP хоста>:$OUT ./evidence/"
echo "  3. Заведите журнал событий, время везде в UTC, укажите смещение локальной зоны."
echo "  4. Свяжитесь с провайдером и откройте тикет, приложив временное окно и имена файлов доказательств (см. раздел 5)."
echo "================================================"
```

| Пункт | Пояснение |
| --- | --- |
| `set -u`, а не `set -e` | Скрипт сбора должен **собрать максимум возможного**, сбой необязательной команды не должен прерывать весь сбор |
| Защита через `command -v` | Используется только для **необязательных инструментов** (`sar`, `nft`, `conntrack`, `tcpdump`, `systemctl`); для основных команд (`ip`, `ss`) предполагается наличие |
| `timeout` | Ограничивает длительность захвата; **`timeout` входит в GNU coreutils, в большинстве дистрибутивов Linux есть**, в минимальных образах может отсутствовать |
| `-c "$CAPTURE_PACKETS"` | Предел числа пакетов, чтобы не заполнить диск во время атаки; **что наступит раньше — время или число пакетов — то и сработает** |
| `cp -a` | Сохраняет **отметки времени и права** оригиналов журналов, это базовое требование форензики |
| Фильтр захвата | `'port 25565 or udp port 19132'`: **`port` совпадает и с TCP, и с UDP**, поэтому написано `port 25565` плюс `udp port 19132`, чтобы не захватить TCP-трафик 19132 |
| Контрольные суммы | Одна копия остаётся в каталоге, **ещё одна сохраняется в `BASE_DIR`**; в по-настоящему строгих сценариях контрольные суммы и доказательства хранят на разных машинах |
| Имена служб и пути | `MC_SERVICE`, `MC_DIR` **нужно заполнить под своё развёртывание**, скрипт их не угадает |
| Контейнеры | При запуске в контейнере `IFACE` и `MC_DIR` должны указывать на **интерфейсы и пути внутри сетевого пространства имён контейнера** |

:::warn Скрипт сбора не заменяет решения
Скрипт отвечает за **сохранение изменяемых доказательств на диск**, но **решать «что это за атака, подавать ли жалобу, переключаться ли на усиленную защиту» по-прежнему должен человек**. После работы скрипта продолжайте по процессу разделов 1–6, особенно не забудьте **вести журнал событий** и **связаться с провайдером**.
