**Резервное копирование — единственное, что нельзя пропустить при запуске сервера.** Железо ломается, хостер исчезает, игроки разрушают, плагины портят сохранения — при реальной аварии всё остальное можно переделать, а потерянное сохранение не вернуть.

## 1. Что копировать

| Обязательность | Что |
| --- | --- |
| Обязательно | `world/`, `world_nether/`, `world_the_end/` (**сами сохранения, самое важное**) |
| Обязательно | `plugins/` (сами плагины и конфиги), `mods/` (для модовых серверов) |
| Обязательно | `server.properties`, `ops.json`, `whitelist.json`, `banned-*.json` |
| Обязательно | Конфигурация самого ядра (`bukkit.yml` / `spigot.yml` / `paper-*.yml` / yml соответствующего ядра) |
| По желанию | `logs/`, `crash-reports/` (по желанию, полезно для диагностики) |
| Не нужно | `libraries/`, `versions/`, `cache/` (пересоздаются автоматически, копировать не нужно) |

## 2. Главный принцип: копия должна быть «согласованной»

**Не копируйте напрямую, пока сервер пишет сохранение** — можно получить наполовину записанный файл чанка, и после восстановления сохранение будет повреждено.

Правильный порядок (два варианта):

**Вариант A: горячая копия (без остановки сервера)**

```
save-all        сначала сбросить данные на диск
save-off        отключить автосохранение (чтобы во время копирования ничего не записывалось)
(выполнить копирование/упаковку)
save-on         вернуть автосохранение после копии
```

**Вариант B: копия с остановкой сервера (самый надёжный)**

```
stop            безопасно остановить сервер
(скопировать/упаковать весь каталог)
(запустить снова)
```

:::tip В скрипте по расписанию лучше использовать вариант A
Вместе с задачей по расписанию в часы низкой нагрузки выполняйте «`save-all` → `save-off` → упаковка → `save-on`» — игроки почти ничего не заметят.
:::

## 3. Автоматизация

**Linux (cron)**: напишите скрипт резервного копирования (упаковка + имя по дате + очистка старых архивов) и запускайте его по расписанию через `crontab -e`.

**Windows (Планировщик заданий)**: превратите стартовый скрипт в «скрипт резервного копирования» и настройте в Планировщике запуск каждый день в фиксированное время.

**Вариант с плагином**: есть и специальные плагины резервного копирования — они делают копии через заданный интервал и хранят несколько версий, избавляя от написания скрипта. **Учтите**: такие копии тоже должны быть согласованными, и **не храните файлы копий на том же диске**.

## 4. Политика хранения

- **Храните несколько версий**: если оставить только последнюю, то при «сохранение уже повреждено, но это ещё не замечено» спасать будет нечего. Рекомендуется хранить **несколько дней ежедневных + несколько недель еженедельных** копий.
- **Следите за диском**: файлы мира постоянно растут, **регулярно удаляйте старые копии**, не заполняйте диск до отказа (при заполненном диске сервер не сможет записать сохранение — последствия серьёзные).
- **Одна копия вне сервера**: если локальный диск выйдет из строя, локальные копии пропадут вместе с ним.

:::warn Хостер может исчезнуть, дата-центр — пострадать
Держать все данные только на одной арендованной машине — отдать свою судьбу в чужие руки. **Как минимум регулярно скачивайте копии на свой компьютер или в другое хранилище**.
:::

## 5. Порядок восстановления (отката)

1. **Остановите сервер** (обязательно командой `stop`).
2. **Переименуйте текущее сохранение, чтобы сохранить его** (например, `world_broken_20261004`), **не удаляйте сразу** — если новая копия тоже окажется с проблемой, можно будет вернуться.
3. Распакуйте копию и верните `world*` в каталог сервера.
4. Запустите сервер и проверьте логи на ошибки, связанные с сохранением.
5. Попросите игроков убедиться, что ключевые постройки и предметы на месте.

## 6. Последнее напоминание

> **Резервная копия, восстановление из которой не проверено, — не резервная копия.**

Регулярно (например, раз в месяц) **действительно восстанавливайте копию в тестовой среде**. Многие узнают в день настоящей аварии, что скрипт копирования давно падал из-за прав или путей, а архив был пустым.
