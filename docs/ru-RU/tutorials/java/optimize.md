«Сервер лагает» — самая частая проблема, но **у оптимизации есть приоритеты**. Делайте в указанном ниже порядке — это выгоднее всего; обратный порядок часто означает много усилий и мало результата.

## 1. Порядок приоритетов

```
1. Железо (производительность одного ядра)   ← наибольшая выгода, но и наибольшие траты
2. Конфигурация сервера (дальность прорисовки/симуляции)  ← почти бесплатно, эффект сразу
3. Выбор ядра (семейство Paper vs ваниль)
4. Качество плагинов/модов (некачественные плагины — главная беда)
5. Параметры JVM
```

**Сразу вывод**: если одно ядро у машины слабое, **ни смена конфигурации, ни настройка параметров не спасут** — главный поток всего один.

## 2. Оптимизация конфигурации (самая выгодная)

### Дальность прорисовки и дальность симуляции

| Параметр | Влияние |
| --- | --- |
| `view-distance` | Насколько далеко видит игрок. Снижение экономит CPU и трафик, цена — туман вдали |
| `simulation-distance` | В каком радиусе чанки ещё **реально обсчитываются** (спавн мобов, редстоун, растения). **Снижать его выгоднее, чем дальность прорисовки, и это не влияет на картинку** |

На большинстве небольших серверов снижение `simulation-distance` с 10 примерно до 6 заметно снимает лаги.

### Управление сущностями на уровне Spigot

В `spigot.yml` есть несколько групп ключевых параметров, связанных с сущностями (в разных версиях названия немного отличаются):

- **Радиус активации сущностей**: с какого расстояния мобы начинают тикать; уменьшение экономит много CPU.
- **Радиус спавна**: расстояние, на котором спавнятся мобы.
- **Радиус объединения сущностей/предметов**: увеличение уменьшает число сущностей (дроп, сферы опыта), **но меняет ванильное поведение** (на техническом сервере — осторожно).
- **Максимум тиков сущностей за такт**: ограничивает обсчёт сущностей и не даёт лагам от их количества обрушить сервер.

### Конфигурация миров на уровне Paper

В `config/paper-world-defaults.yml` настраиваются: лимит столкновений сущностей, число чанков автосохранения, задержка выгрузки чанков и т. п.

:::warn Оптимизация и «ванильное поведение» — обратно пропорциональны
Многие из этих переключателей **уже имеют оптимизированные значения по умолчанию**; чем агрессивнее настройка, тем дальше от ванили. **На техническом сервере делайте наоборот — возвращайте влияющие на ванильное поведение параметры к ванильным** (см. «Технический Minecraft и редстоун»).
:::

## 3. Сначала найдите, «где именно лагает», потом действуйте

**Не оптимизируйте на ощупь**. Сначала измерьте:

| Инструмент | Назначение |
| --- | --- |
| **spark** | Самый распространённый плагин/команда профилирования; строит flame graph и прямо показывает, какой плагин/сущность/чанк ест CPU |
| Команды вроде `/tps` | Показывает текущий TPS (ниже 20 — уже потеря тактов) |
| **timings** (старый Paper) | Отчёт о производительности на старых версиях |

Снимите spark-профиль за некоторое время, **посмотрите на самую широкую полосу flame graph** и действуйте точечно. Частые виновники:

- какой-то некачественный плагин делает тяжёлую работу в цикле;
- скопление сущностей (ферма мобов без сбора, неубранный дроп);
- слишком много воронок/редстоун-устройств (воронка — классический убийца производительности);
- игроки исследуют мир, порождая массу новых чанков (см. ниже).

## 4. Предгенерация мира

**Генерация новых чанков по мере исследования мира** — важный источник лагов: генерация чанка — операция, интенсивно нагружающая CPU, и TPS мгновенно проседает.

Решение — **предгенерация**: плагин вроде `Chunky` заранее создаёт карту в определённом радиусе. Когда игрок доходит до этих мест, чанки только загружаются, без генерации.

Для **долго работающих выживальческих серверов** предгенерация почти обязательна.

## 5. Параметры JVM

- **Память**: `-Xmx` задавайте с запасом, но не чрезмерно (слишком большой объём удлиняет паузы GC). На выделенной машине можно сделать `-Xms` равным `-Xmx`, чтобы уменьшить изменение размера кучи.
- **Параметры GC**: у сообщества есть зрелые рекомендации (например, **Aikar's Flags**), а в официальной документации Paper есть генератор параметров запуска с пояснениями. **Не копируйте слепо противоречащие друг другу «магические параметры» из интернета**.
- Параметры помогают только на **уровне памяти/GC** и **не спасают от узкого места в одном ядре**.

## 6. Другие практичные меры

- **Регулярная очистка сущностей**: задайте разумное время жизни дропа и сфер опыта; есть плагины для очистки по расписанию.
- **Ограничение TNT / высокочастотного редстоуна**: на публичном сервере ограничение взрывов и быстрых редстоун-цепей заметно снижает возможность злонамеренно уронить сервер.
- **Ограничение исследования**: мировой границей (world border) ограничьте зону активности, чтобы не было бесконечной генерации.
- **Регулярный перезапуск**: это не «оптимизация», но он сбрасывает часть утечек памяти плагинов и годится как **временная мера** (лечит симптом, а не причину).
- **Апгрейд железа**: если spark показывает, что главный поток полностью занимает CPU, а конфигурация уже настроена, — **пора менять машину на более сильную в одном ядре**.

## 7. Предел оптимизации

```
Оптимизация не должна идти в ущерб «ванильному поведению» — если только оно вам точно не нужно
```

Для технического сервера: **лучше немного лагов, чем неработающие машины**.
Для обычного выживальческого сервера: **можно умеренно агрессивно**, приоритет — комфорт игры.

## Заключение

На этом полный путь запуска сервера Java Edition пройден:

```
Протокол и конфигурация → операционная система → подготовка среды → выбор ядра → запуск сервера
   → структура сервера → настройка сервера → развёртывание → частые команды
   → MCDR → плагины → технический Minecraft
   → эксплуатация → прокси → мобильные игроки → резервные копии → античит → оптимизация
```

Если нужно вернуться к какому-то звену, используйте оглавление слева. Подробное сравнение ядер — в [Сравнении серверных ядер](/wiki/compare#mcsog-h-%E6%A0%B8%E5%BF%83%E5%AF%B9%E7%85%A7).
