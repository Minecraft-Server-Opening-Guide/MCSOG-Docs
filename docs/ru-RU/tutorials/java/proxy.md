Когда сервер превращается из «одного сервера» в «группу серверов» (лобби + выживание + мини-игры…), нужен **прокси** для единой точки входа.

## 1. Что делает прокси

Прокси **сам не ведёт мир**; он делает одно: **принимает подключение игрока и перенаправляет его на один из бэкенд-серверов**.

```
Игрок → прокси (Velocity / BungeeCord)
              ├→ лобби
              ├→ выживание
              └→ мини-игры
```

Плюсы:

- **Единая точка входа**: игрок помнит один адрес; при переключении между серверами соединение не рвётся и переподключаться не нужно.
- **Единая проверка аккаунта**: проверка лицензии выполняется один раз на прокси, все бэкенды переводятся в офлайн-режим (доверие внутри).
- **Простое обслуживание**: чтобы добавить сервер, достаточно одной записи в конфигурации прокси, и игроки этого не заметят.
- **Разделение ресурсов**: лобби, сервер входа и мини-игры можно перезапускать независимо, не затрагивая остальные.

## 2. Что выбрать

| Прокси | Описание |
| --- | --- |
| **Velocity** | Современное решение, **лучше по производительности и активнее**; в новых проектах выбирайте его. Поддерживает «современную пересылку» (modern forwarding): данные проверки безопасно передаются по ключу |
| **BungeeCord** | Старое решение: зрелая экосистема, очень много материалов, на нём основано множество старых руководств. Подходит для поддержки существующих старых серверов |

> Идея у обоих одна; различаются детали конфигурации и механизм пересылки. **Для нового сервера рекомендуется Velocity**.

## 3. Ключевые моменты настройки

### 1. Прокси

- Скачайте jar прокси, положите в отдельный каталог и запускайте скриптом.
- В конфигурации зарегистрируйте **список серверов** (имя + внутренний адрес + порт).
- Проверка лицензии **включается только на прокси**: на прокси `online-mode=true`, на бэкендах обязательно `online-mode=false`.

### 2. Бэкенд-серверы

Бэкенд должен «доверять» прокси, то есть **принимать подключения только от него**:

- **Velocity**: используется **современная пересылка**; на прокси и бэкендах задаётся один и тот же `forwarding.secret`, а на бэкенде включается соответствующий режим пересылки.
- **BungeeCord**: в конфигурации бэкенда включите `bungeecord: true` (семейство Spigot) и отключите собственную проверку лицензии бэкенда.

### 3. Ключевой момент безопасности

:::warn Ключ пересылки — это ключ от сервера
Как только бэкенд доверяет пересылке прокси, **любой, кто знает ключ, может войти под именем произвольного игрока**. Поэтому:

- `forwarding.secret` **не разглашайте и не коммитьте в публичные репозитории**;
- порты бэкендов **не открывайте напрямую в интернет** — разрешите доступ только с машины прокси (ограничьте источник firewall).
:::

## 4. Замечания

- **Плагины различаются по месту установки**: одни ставятся на прокси (чат между серверами, глобальные права), другие обязательно на бэкенд. При ошибке получается «команда есть, но не реагирует».
- **Прокси добавляет один переход**: задержка немного растёт, обычно это незаметно, но при плохом канале эффект усиливается.
- **Модовые ядра плохо сочетаются**: пересылка прокси ограниченно поддерживает модовые ядра; для модовых серверов обычно нужны специальные решения.
- **Инвентарь и данные**: при переключении инвентарь и позиция игрока обрабатываются прокси и бэкендами совместно; **не используйте одну папку мира на нескольких бэкендах**.
- **Не считайте прокси «оптимизацией производительности»**: он не ускоряет, а лишь даёт **структурную** единую точку входа. Одному серверу он не нужен.

## 5. Когда нужен прокси

**Нужен**: есть несколько игровых зон, нужна единая точка входа, игроки должны свободно переключаться между серверами, нужны лобби и сервер входа.

**Не нужен**: сервер один. **Каждый слой добавляет точку отказа**; прокси на маленьком сервере лишь увеличивает расходы на обслуживание.
