Плагинов на сервере становится только больше. Бросить jar в `plugins/` легко; сложности начинаются потом: какой-то плагин нужно обновить, какой-то временно отключить из-за проблемы, какой-то jar выглядит подозрительно. Здесь три темы: правильный порядок установки и удаления, границы возможностей инструментов горячей перезагрузки и то, как понять, что плагин кто-то «тронул».

Если плагины ещё не устанавливались, сначала посмотрите [Введение в плагины](/tutorials/java/plugins).

## 1. Правильный порядок установки, обновления и удаления

### Установка

1. Убедитесь, что источник заслуживает доверия (см. раздел 5), и сразу запишите номер версии и адрес загрузки.
2. **Остановите сервер**. Большинство плагинов не поддерживают первую горячую загрузку.
3. Сделайте копию каталога `plugins/`, см. [Резервное копирование и восстановление](/tutorials/java/backup).
4. Положите `.jar` в `plugins/`.
5. Запустите сервер и следите за консолью: сообщения об успешной и неудачной загрузке печатаются здесь.
6. Проверьте состояние загрузки командой `plugins`.
7. Затем правьте конфигурацию; после правки предпочитайте собственную подкоманду `reload` плагина, а не ванильную `/reload`.

### Обновление

Обновление опаснее установки: структура конфигурации новой версии могла измениться.

| Шаг | Главное |
| --- | --- |
| Читать changelog | Проверьте, не изменился ли формат конфигурации и нет ли данных, требующих ручного переноса |
| Копия | Как минимум скопируйте `plugins/<имя плагина>/`; если задействована база данных — и её |
| Сохранить старый jar | Переименуйте старую версию в `.jar.bak` и удалите только после проверки новой |
| Замена на остановленном сервере | Не перезаписывайте используемый jar на ходу |
| Проверка после перезапуска | Посмотрите консоль, затем состояние через `plugins` |
| Скачок через крупные версии | При переходе через крупные версии (например, 1.20 → 1.21) плагин может требовать промежуточного обновления |

### Удаление

Удаление — это не просто «стереть jar».

1. Остановите сервер.
2. Уберите jar.
3. Каталог данных **не удаляйте сразу**: переименуйте в `<имя плагина>.bak` и понаблюдайте.
4. Проверьте, не зависит ли от него другой плагин как от зависимости; если да — разберитесь и с ним.
5. Уберите узлы прав, которые он оставил в плагине прав.
6. Уберите зарегистрированные им задачи по расписанию, свои команды и записи счётных таблиц.
7. Учтите оставленные им в мире предметы и блоки: без плагина они могут вызывать ошибки.

:::warn Удаление не равно очистке
Удаление jar решает только шаг «загрузки». Каталог данных, узлы прав, таблицы базы данных и зависимости других плагинов остаются на месте.
:::

## 2. Инструменты горячей перезагрузки: PlugManX и ServerUtils

Такие инструменты обычно называют **плагинами управления плагинами**: они загружают, выгружают и перезагружают другие плагины, пока сервер работает.

### PlugManX

Старый инструмент управления плагинами; его предшественник — PlugMan, теперь развивается поддерживаемый сообществом PlugManX.

| Пункт | Информация |
| --- | --- |
| Страница выпуска | SpigotMC ресурс 88135 |
| Исходники | Test-Account666/PlugManX на GitHub (старая версия — ryan-clancy/PlugMan) |
| Частые подкоманды | `load`, `unload`, `reload`, `list`, `info`, `check` |
| Типичное использование | `/plugman <подкоманда> <имя плагина>` |

Конкретные имена подкоманд и параметры меняются от версии к версии; ориентируйтесь на встроенную справку плагина.

### ServerUtils

| Пункт | Информация |
| --- | --- |
| Страница выпуска | SpigotMC ресурс 79599, Modrinth |
| Исходники | frankheijden/serverutils на GitHub |
| Поддерживаемые платформы | Spigot, BungeeCord, Velocity |

Помимо управления плагинами, он включает инструменты просмотра состояния сервера. Поскольку поддерживается и прокси, в группе серверов можно управлять плагинами централизованно на уровне прокси, не ставя отдельный экземпляр на каждый бэкенд.

### Реальные границы горячей перезагрузки

Горячая перезагрузка — не «без перезапуска»; у неё есть чёткий список того, чего она не умеет:

| Ситуация | Решается ли горячей перезагрузкой |
| --- | --- |
| Просто изменение конфигурации | Достаточно встроенного `reload` плагина |
| Временно отключить проблемный плагин | Да, это самое ценное применение горячей перезагрузки |
| Смена версии плагина (замена jar) | Не рекомендуется; заменяйте на остановленном сервере |
| Плагин регистрирует команды, права, слушатели, рецепты, генераторы мира, достижения | После выгрузки часто остаются хвосты, перезагрузка легко даёт ошибки |
| Плагин напрямую меняет внутреннюю реализацию сервера (NMS, рефлексия) | Практически невозможно |
| Плагин держит соединения с базой, пул потоков или большой статический кэш | После выгрузки ресурсы обычно не освобождаются |
| Многократная загрузка и выгрузка одного плагина | Загрузчик классов не освобождается, память растёт и в итоге OOM |
| Гибридное или модовое ядро | Менеджер плагинов не управляет модами |
| Ванильная `/reload` сервера | Не рекомендуется, легко рассинхронизирует состояние плагинов |

:::warn В продакшене не полагайтесь только на горячую перезагрузку
Горячая перезагрузка подходит для «временно отключить плагин и посмотреть, исчезла ли проблема» и быстрой проверки конфигурации. Настоящие обновления версий и изменения зависимостей по-прежнему должны идти через остановку и перезапуск.
:::

:::tip Правильное применение при диагностике
Сначала через менеджер плагинов сделайте `unload` недавно установленным плагинам и посмотрите, исчезло ли явление; убедившись, что дело в нём, переходите к штатной остановке. Это гораздо быстрее чтения логов.
:::

## 3. Частые признаки бэкдоров в плагинах

Плагин — сторонний код, работающий с правами сервера; если в него вставили бэкдор, сервер фактически отдан в чужие руки. Эти сигналы должны настораживать.

| Сигнал | Конкретное проявление |
| --- | --- |
| Аномальные права и команды | В `plugin.yml` объявлены опасные команды, не связанные с функциями: выдать себе OP, выполнить произвольную команду, читать и писать произвольные файлы |
| Обфускация кода | Имена классов — бессмысленные буквы или структура `a/b/c`; весь пакет зашифрован или расшифровывается при загрузке собственным загрузчиком классов |
| Подозрительные вызовы во время работы | Запуск дочерних процессов (`ProcessBuilder`, `Runtime.exec`), исходящие соединения (`URL.openConnection`, HTTP-запросы), прямая правка `ops.json`, загрузка удалённых классов через рефлексию |
| Маскировка под «обновлятор» | Заявляет автообновление, а на деле скачивает файлы со своего сервера и перезаписывает себя |
| Неизвестный источник | Jar, пересланный во вложении форума, на файлообменнике или в файлах группы |
| «Бесплатный премиум-плагин» | Платный плагин взломан и перепакован; взломщик обычно что-то добавил |
| Несовпадение с оригиналом | Имя и версия те же, но размер файла или хеш не совпадают, автор и сайт в `plugin.yml` изменены |
| Безобидные на вид скрытые настройки | Включённые по умолчанию `metrics`, `telemetry`, `update-check` и подобное, которые на деле отправляют данные наружу |

:::warn Не смотрите только на имя плагина
Бэкдоры часто прямо используют имя и версию известного плагина. Судить нужно по источнику файла и его содержимому, а не по имени.
:::

## 4. Безопасные источники загрузки

| Канал | Риск |
| --- | --- |
| SpigotMC, Modrinth, Hangar, Bukkit Dev и другие основные площадки | Низкий, выбирайте в первую очередь |
| GitHub Releases самого автора | Низкий, проверяйте владельца репозитория |
| Официальная страница покупки платного плагина | Низкий, не купите «перепродажу» |
| Сайты-агрегаторы, зеркала | Средний: возможна перепаковка; сверяйте хеш файла |
| Вложения форумов, файлообменники, файлы групп | Высокий |
| «Бесплатные премиум-плагины» на площадках перепродажи | Очень высокий, основная зона риска |

Критерий на самом деле прост: **можно ли проследить до файла, опубликованного самим автором, и сверить его**. То, что плагин встречается на многих сайтах, ничего не говорит о его безопасности.

:::tip Ставьте только то, что нужно
Чем меньше плагинов, тем меньше поверхность атаки и тем проще диагностика. Из плагинов с пересекающимися функциями достаточно одного.
:::

## 5. Порядок проверки при подозрении на плагин

1. **Зафиксируйте симптомы**: когда началось, что пишет консоль, жалуются ли игроки на странности.
2. **Сначала копия**: перед любыми действиями сделайте полную копию, включая `plugins/` и данные мира.
3. **Составьте список подозреваемых**: плагины, добавленные или обновлённые за последние 24–72 часа.
4. **Локализация делением пополам**: остановите сервер, отключите половину подозреваемых, перезапустите и наблюдайте; если явление исчезло — виновник среди отключённых, иначе среди второй половины.
5. **Воспроизведите отдельно**: сузив до одного плагина, сделайте `unload` только ему и проверьте, возвращается ли явление.
6. **Статический скан**: проверьте jar способом из раздела 6.
7. **Просмотрите `plugin.yml` вручную**: сверьте `author`, `website`, `main`, `commands`, `permissions` с официальной версией.
8. **Посмотрите список классов**: распакуйте jar, обратите внимание на бессмысленные имена классов и подозрительные вызовы из таблицы выше.
9. **Сравните хеши**: сопоставьте размер и хеш с официально скачанным файлом.
10. **Убедившись во вредоносности, переходите к плану реагирования**.

План реагирования:

- проверьте, не изменены ли `ops.json` и `whitelist.json`, не получил ли OP незнакомый аккаунт;
- проверьте необычные записи о входах и незнакомые файлы данных игроков;
- смените все учётные данные: пароль RCON, пароль панели, пароль базы данных, ключи SSH;
- проверьте, не добавлены ли в `plugins/` посторонние jar и не заменены ли jar ядра и скрипт запуска;
- проверьте задачи планировщика на уровне системы — не добавлен ли автозапуск;
- прочитайте логи консоли и плагинов и найдите момент первого срабатывания бэкдора;
- по ситуации предупредите игроков и откатитесь; перед откатом сохраните состояние для анализа.

## 6. Статический скан с McGuard

McGuard (сокращённо MCG) — сторонний инструмент статического сканирования от huzpsb. Он сканирует все jar в `plugins/`, **не запуская сервер**, и находит подозрительные файлы.

### Режим консоли

Положите jar MCG в корень сервера и выполните в этом каталоге:

```
java -Xmx1G -jar MCG.jar
```

После запуска будет предложено выбрать режим; обычно достаточно `0` (стандартный). Есть также экспертный и режим разработчика.

Результаты выглядят так:

| Ситуация | Вывод |
| --- | --- |
| Аномалий не найдено | Печатается только ход сканирования, блок результатов не выводится |
| Аномалии найдены | Выводится блок результатов с уровнем серьёзности и описанием причины по каждому пункту |

В описании причины указывается категория сработавшего поведения, например «возможно получение OP через установку бита прав» или «возможно выполнение удалённой команды через запуск дочернего процесса».

:::warn MCG только сообщает, но не лечит
Он ничего не меняет и не удаляет — чистить нужно вручную. Учтите также: экспертный режим сопоставляет с известными сигнатурами вредоносного кода и анализирует намерения кода, покрывая большинство образцов, не пытающихся обойти скан, но ложные срабатывания всё равно возможны.
:::

### Режим плагина

MCG можно установить и как плагин Bukkit/Spigot для постоянной защиты во время работы сервера. Официальная позиция такова: защита относительна, редкие вредоносные плагины всё ещё могут обойти контроль поведения; **не запускайте сервер, заведомо содержащий вредоносный плагин, только потому, что установлен MCG**.

:::warn Сканирование — лишь последняя линия обороны
Ни один сканер не устранит все риски; правильный путь — брать плагины из официальных каналов. Если нужно запустить серверное ядро неизвестного происхождения, сначала просканируйте его в режиме консоли, а затем попробуйте в изолированной среде вроде песочницы (например, Sandboxie).
:::

## 7. Рекомендации по повседневному обслуживанию

- не реже раза в месяц проверяйте обновления плагинов, особенно связанных с безопасностью: совместимость версий, античит;
- ведите список плагинов с именем, версией, источником и адресом загрузки, чтобы при проблеме быстро восстановить картину;
- держите рабочий и тестовый серверы раздельно и сначала погоняйте новые плагины на тестовом;
- не запускайте процесс сервера от root или Administrator — заведите отдельный аккаунт с минимально необходимыми правами;
- следите за issue и объявлениями в репозитории автора: о заражении плагина обычно сначала говорят в сообществе.
