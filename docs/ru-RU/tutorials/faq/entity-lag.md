TPS сервера падает с 20 до однозначных чисел, `/spark tps` показывает MSPT стабильно выше 50 ms, но загрузка CPU невелика и память не переполнена — такие лаги с большой вероятностью означают не нехватку машины, а **скопление сущностей (entity) и блочных сущностей (block entity)**.

У лагов от сущностей две особенности: они **почти не едят память, но реально едят CPU главного потока**, и **перезапуск даёт облегчение лишь на несколько минут** — если источник остался, скопление возвращается сразу. Статья идёт в порядке «почему лагает → выпавшие предметы → мобы → воронки → как искать → заблуждения».

:::note Область применения
Статья в основном про сервер Java Edition (ваниль / Spigot / семейство Paper). У всех ключей конфигурации указано, к какому файлу они относятся; **структура и значения по умолчанию меняются между ядрами и версиями**, перед действиями смотрите файл конфигурации, сгенерированный локально.
:::

## 1. Почему сущности убивают производительность

### 1.1 Всё встаёт в очередь в главном потоке

Основная логика сервера Minecraft — **однопоточный цикл тиков**: 20 тиков в секунду, бюджет одного тика — **50 ms** (то, что называют MSPT). Вычисления всех миров, всех сущностей и всех блочных сущностей должны уложиться в очередь на этом одном потоке.

```
1 секунда = 20 тиков, бюджет каждого тика 50 ms
MSPT 40 ms  → TPS 20 (здорово)
MSPT 60 ms  → TPS падает примерно до 16 (начинает лагать)
MSPT 200 ms → TPS 5 (играть практически невозможно)
```

Поэтому «много сущностей» и смертельно: они **напрямую расходуют бюджет времени единственного потока**. Сколько бы ядер ни было у CPU и сколько бы памяти вы ни дали, главный поток это не спасёт (подробнее — в [Оптимизации производительности](/tutorials/java/optimize)).

### 1.2 Что делает каждая сущность каждый тик

Обычно сущность каждый тик проходит такие этапы:

- **ИИ и выбор цели**: goal selector, поиск пути (pathfinding), сканирование сенсоров;
- **Физика и столкновения**: гравитация, движение, проверка столкновений с другими сущностями и блоками;
- **Таймеры**: горение, эффекты зелий, обратный отсчёт исчезновения (despawn);
- **Проверка объединения**: выпавшие предметы и сферы опыта проверяют, есть ли рядом такие же для объединения;
- **Отслеживание и синхронизация**: определение, каким игрокам нужно отправить обновление позиции.

Из этих пунктов больше всего занимают сущности-мобы (особенно поиск пути и сенсоры); отдельный выпавший предмет стоит намного меньше, но **их количество легко доходит до десятков тысяч** — вот почему «несколько тысяч выпавших предметов в одном чанке» опаснее, чем «несколько десятков зомби».

### 1.3 Классификация: что тикает, а что нет

| Категория | Считается ли каждый тик | Пояснение |
| --- | --- | --- |
| Мобы / животные / монстры | Да | Самая дорогая категория: ИИ, поиск пути, сенсоры, столкновения |
| Выпавшие предметы (сущности предметов) | Да | Один предмет дешёв, но их количество огромно; есть отсчёт исчезновения и проверка объединения |
| Сферы опыта | Да | Похожи на выпавшие предметы; ядра обычно дают опцию ограничения объединения |
| Снаряды (стрелы, трезубцы, снежки, огненные шары, эндер-жемчуг) | Да | Чистая физика; в `spigot.yml` есть `arrow-despawn-rate`, `trident-despawn-rate` (в актуальной документации Paper указано 1200) |
| Вагонетки / лодки | Да | Сущность + столкновения + логика пассажиров; вагонетка с воронкой ещё и перемещает предметы |
| Рамки / картины / узлы поводка и другие висящие сущности | Да (с низкой частотой) | Интервал обновления задаёт `hanging-tick-frequency` в `spigot.yml` (в Spigot wiki по умолчанию 100) |
| Стойки для брони / маркеры (marker) | Да | Оба являются сущностями; в `paper-world-defaults.yml` Paper есть `entities.armor-stands.tick`, `entities.markers.tick` (сейчас по умолчанию `true`), их можно отключить для экономии |
| Спавнеры | Да | Блочная сущность, каждый тик вычисляет область возможного спавна |
| Воронки | Да | Блочная сущность, классический убийца производительности, см. раздел 4 |
| Печи / доменные печи / коптильни | Только при работе | У простаивающей печи нет логики каждый тик |
| Сундуки / бочки / шалкеры | Нет (сами не тикают) | У чистого контейнера нет логики блочной сущности каждый тик, расход возникает при открытии или обращении воронки |
| Командные блоки | Нет (только при срабатывании) | В простое не вычисляются |

:::warn «Блок-контейнер» не равно «постоянно вычисляется»
Самое частое смешение: **сундуки, печи и подобные «блоки-контейнеры» сами по себе не вычисляются каждый тик**, каждый тик вычисляется **блочная сущность**, привязанная к блоку, и только те, у которых есть ticker (воронки, спавнеры, горящие печи), едят CPU. Поэтому «в сундуке много предметов» не лагает, а «длинная и простаивающая цепочка воронок» лагает.
:::

### 1.4 Загрузка чанков и тик чанков — не одно и то же

Сущности вычисляются только в **тикающих чанках**, а «загруженный» чанк не обязательно тикает. Команда Paper `/paper chunkinfo` делит текущие чанки на категории (определения — в официальной документации команд Paper):

| Тип | Смысл |
| --- | --- |
| Entity Ticking | Полный тик: сущности, блоки и спавн работают |
| Block Ticking | Обычно называемый lazy chunk: логика блоков работает, сущности не тикают |
| Full | Обычно называемый border chunk: не тикает, но блоки и сущности доступны |
| Inactive | Недоступен, используется только для генерации чанков |
| Total | Сумма выше |

Это объясняет два частых явления:

- **Дальние мобы не обязательно нагружают сервер**: их чанк может быть в состоянии Block Ticking или Full, и сущности вообще не тикают;
- **Загрузка не равна вычислению**: `/paper holderinfo` показывает число чанков в памяти, что не то же самое, что нагрузка тиков на CPU.

:::note Выпавшие предметы сами чанки не загружают
Строго говоря, выпавшие предметы сами **не** «загружают» чанк — в ванили загрузку поддерживают игроки, чанки спавна, порталы, `/forceload` и плагины. Но пока этот чанк загружен по указанным причинам, предметы в нём тикают и накапливаются.
:::

### 1.5 Радиус активации сущностей (activation range)

Чтобы сущности, «загруженные, но рядом никого нет», не ели CPU зря, в семействе Spigot введён **радиус активации сущностей**: сущности за его пределами **не перестают загружаться, но тикают реже**.

Официальная документация Paper описывает `entity-activation-range` в `spigot.yml` так: расстояние в блоках от игрока, в пределах которого сущность тикает нормально; за пределами частота тиков снижается; значение 0 или меньше отключает троттлинг категории, и загруженные сущности тикают нормально на любом расстоянии.

Структура, указанная в документации Paper сейчас (**значения по умолчанию меняются между версиями, ориентируйтесь на локальный файл**):

```yaml
# spigot.yml → world-settings.default
entity-activation-range:
  animals: 32
  monsters: 32
  raiders: 64
  misc: 16
  water: 16
  villagers: 32
  flying-monsters: 32
  wake-up-inactive:
    animals-every: 1200
    animals-for: 100
    animals-max-per-tick: 4
    monsters-every: 400
    monsters-for: 100
    monsters-max-per-tick: 8
    villagers-every: 600
    villagers-for: 100
    villagers-max-per-tick: 4
    flying-monsters-every: 200
    flying-monsters-for: 100
    flying-monsters-max-per-tick: 8
  villagers-work-immunity-after: 100
  villagers-work-immunity-for: 20
  villagers-active-for-panic: true
  tick-inactive-villagers: true
  ignore-spectators: false
```

Две цены, которые нужно знать:

- Если отключить `tick-inactive-villagers` (в документации Paper сейчас по умолчанию `true`), **жители не будут работать как в ванили**: игроку придётся стоять рядом, чтобы они пополняли товар;
- `wake-up-inactive` определяет, как часто «спящие» сущности просыпаются; слишком жадная настройка заметно ломает поведение машин и ферм.

В связке с [Техническим Minecraft и редстоуном](/tutorials/java/redstone): **на техническом сервере трогайте это осторожно** или переходите на Fabric / Leaves.

## 2. Скопление выпавших предметов

### 2.1 Частые причины

- **У фермы нет замкнутого цикла убийства и сбора**: ферма мобов просто выбрасывает дроп на землю;
- **Кактусы, тростник и автоматические фермы выплёвывают продукцию на землю**;
- **Игроки просто бросают вещи**: разбор инвентаря, дроп при смерти, выбрасывание хлама при переезде;
- **Сущности от копировальных устройств** вроде TNT или песка;
- **Цепочка воронок порвана**: целевой сундук полон, воронка забита, выгрузка чанка оставила предметы на полпути, а сверху продолжается производство;
- **Злоупотребление `/give` или командный блок, циклически выдающий предметы**;
- **Ферма работает всю ночь**: в чанках спавна, в чанках из `/forceload` и в чанках, принудительно загруженных плагинами, машины работают и без людей.

### 2.2 Почему выпавшие предметы так больно бьют

- **Один предмет дешёв, количество ужасает**: несколько тысяч предметов в чанке в сумме дают заметный MSPT;
- **Объединение работает далеко не так активно, как кажется**: ванильные предметы объединяются только на очень близком расстоянии; параметр Paper `entities.behavior.only-merge-items-horizontally` (сейчас по умолчанию `false`) определяет, объединять ли только предметы на одной высоте; значение `true` убирает часть визуальных странностей, но **объединяет меньше**;
- **Каждый предмет тикает**: физика, отсчёт исчезновения, проверка объединения — всё присутствует;
- **Воронки их сканируют**: предметы над воронкой — один из источников постоянной работы воронки (см. раздел 4);
- **При приближении игрока они втягиваются в инвентарь**, добавляя нагрузку на инвентарь и сеть;
- **Растёт и сохранение**: сущности записываются в чанк, при большом количестве растёт время сохранения и объём сохранений.

### 2.3 Диагностика

Сначала используйте средства, которые **показывают количество**, а не ощущения:

| Средство | Назначение |
| --- | --- |
| `/paper entity list minecraft:item` | Команда Paper, перечисляет сущности текущего тика, вывод вида `Total Ticking: N, Total Non-Ticking: M`, с разбивкой по типам (тикающие, не тикающие). Если выпавшие предметы массово в не-тикающей части, значит они троттлятся за пределами радиуса активации — но общее количество всё равно заслуживает внимания |
| `/spark tps`, `/spark health` | Сначала понять, «действительно ли лагает» и где — в TPS, памяти или диске |
| `/spark profiler start --timeout 60` | После сэмплирования посмотреть долю `ItemEntity.tick`, `Entity.tick` в дереве вызовов |
| `/spark tickmonitor --threshold-tick 100` | Сообщать только о тиках дольше 100 ms, в связке с действиями на месте |
| `/paper chunkinfo` | Посмотреть распределение типов загруженных чанков по мирам, понять «слишком много загружено» это или «слишком много сущностей» |
| `/forceload query` | Узнать, какие чанки принудительно загружены (фермы в таких чанках чаще всего выходят из-под контроля) |
| `/debug start` / `/debug stop` | Встроенное в ваниль сэмплирование производительности, создаёт debug profile |

Полное использование spark и чтение графиков — см. [Анализ производительности через spark](/tutorials/ops/spark).

**`/kill @e[type=item]` — это дубина**, применяйте только в аварии:

```bash
# Очистить все выпавшие предметы в загруженных чанках
/kill @e[type=item]

# Ограничить область: 64 блока вокруг исполнителя
/kill @e[type=item,distance=..64]
```

:::warn Очистка выпавших предметов необратима
Она **без разбора удаляет всё, что лежит на земле**: только что выброшенное игроком, собираемое фермой, выпавшее при смерти снаряжение — всё исчезнет без возможности восстановления. **Не выполняйте это на всём сервере при онлайн-игроках**; и не считайте это долгосрочным решением — через полчаса на земле снова будет то же самое.
:::

**Как найти «в одном чанке тысячи сущностей»?** Общее число сущностей говорит «много», но не «где». Искать можно в таком порядке:

1. Сначала через `/paper chunkinfo` исключите причину «загружено слишком много чанков»;
2. Затем сэмплирование spark: сравните горячие точки в разных мирах и областях либо с `/spark tickmonitor --threshold-tick 100` пройдитесь по подозрительной области и посмотрите, не удлиняется ли тик заметно;
3. Для подсчёта по области используйте селектор `@e`: встаньте в подозрительном месте и выполните `/execute if entity @e[type=item,distance=..16]`, по числу успехов в ответе команды оцените порядок величины (формат ответа в разных версиях различается, ориентируйтесь на фактический вывод);
4. Если нужно следить долго, используйте плагин или инструмент панели, умеющий перечислять число сущностей по чанкам.

:::tip timings — это про старые версии
В старом Paper отчёт о производительности назывался **timings**. Сейчас официальная документация Paper относит `/tps` и `/mspt` к «заменённым `/spark`» — **если можно использовать spark, используйте spark**, методика отчётов единая и сравнивать проще.
:::

### 2.4 Что делать

**Первый шаг всегда — изменить дизайн, а не конфигурацию.** Сделайте ферму замкнутой: комната убийства + сбор водой или вагонеткой с воронкой + сразу в сундук, продукция больше не падает на землю.

**И только второй шаг — конфигурация и плагины.**

**Время жизни выпавших предметов**: в ванили предмет исчезает примерно через 5 минут (6000 тиков). Большинство ядер позволяют менять это время, вплоть до настройки по типу предмета, но **имена ключей, уровень вложенности и значения по умолчанию зависят от ядра и версии**, ориентируйтесь на локально сгенерированный файл конфигурации и официальную документацию.

**Плагины периодической очистки** (в сообществе распространены решения вроде ClearLag). При выборе и настройке уточняйте:

- **Интервал очистки**: как часто (обычно 5–10 минут);
- **Что очищается**: только `item` или вместе со сферами опыта, снарядами и мобами (последнее легче задевает лишнее);
- **Предупреждение заранее**: обратный отсчёт перед очисткой, чтобы не удалить предметы в момент, когда игрок их подбирает;
- **Правила защиты**: пропускать предметы с собственными именами, дроп при смерти игрока, указанные миры или области (зону сбора продукции исключать особенно важно);
- **Совместимость**: убедитесь, что плагин поддерживает ваше ядро и версию игры (см. [Введение в плагины](/tutorials/java/plugins)).

**Радиус объединения `merge-radius`**: это реально существующий ключ семейства Spigot / Paper, находится в `spigot.yml` в world-settings и делится на предметы и сферы опыта. Структура, указанная в документации Paper сейчас:

```yaml
# spigot.yml → world-settings.default
merge-radius:
  item: 0.5
  exp: -1
```

Учтите, что **два авторитетных источника расходятся**: Spigot wiki для той же группы ключей указывает значения по умолчанию item 2.5 / exp 3.0 и описывает их как «радиус объединения предметов и сфер опыта на земле»; документация Paper про exp говорит «объединять в момент появления, в ванили такого поведения нет, значение 0 или меньше отключает».

:::tip Расхождение значений по умолчанию и есть причина смотреть локальный файл
Разные значения по умолчанию у одного ключа в разных ядрах и версиях — норма для такой оптимизации. **Увеличение радиуса объединения** позволяет предметам быстрее складываться в стопки и сокращает число сущностей, цена — **изменение ванильного поведения**, что может задеть машины, зависящие от разделения предметов; на техническом сервере применяйте осторожно. Есть и связанный ключ Paper `entities.behavior.experience-merge-max-value` (сейчас по умолчанию `-1`, то есть без ограничения максимума после объединения сфер опыта).
:::

**Подстраховка для сохранений**: параметр Paper `chunks.entity-per-chunk-save-limit` ограничивает число сущностей определённого типа, **сохраняемых и загружаемых** на чанк (в документации Paper `experience_orb: -1` означает без ограничения, можно настраивать по `<entity-type>`). Он ограничивает сохранение и загрузку, а не удаляет сущности на месте, и подходит как страховка для сценария «сферы опыта рассыпаны по всей земле».

**Не давайте ферме работать без людей**: не злоупотребляйте `/forceload`; параметр Paper `unsupported-settings.disable-world-ticking-when-empty` (сейчас по умолчанию `false`, официально помечен как «не поддерживаемый») позволяет останавливать тик мира, когда нет ни игроков, ни принудительно загруженных чанков — **перед изменением проверьте поведение своей версии**.

## 3. Скопление сущностей (мобы)

### 3.1 Частые причины

- **Спавнеры работают постоянно**: особенно без комнаты убийства и сбора;
- **Неосвещённые пещеры и ночной спавн**: под землёй рядом с зоной активности игроков полно мобов;
- **Безудержное размножение**: коровы, овцы, свиньи и куры копятся кучей;
- **Питомцы повсюду**: прирученные волки, кошки и лошади разбросаны по карте;
- **Зал размножения жителей**: когда жителей больше сотни, запросы POI и поиск пути стоят заметно;
- **Накопление рейдов и странствующих торговцев**: незаканчивающиеся рейды, никому не нужные торговцы и их ламы;
- **Плотные редстоун-устройства**: массивы вагонеток, стойки для брони, цепочки выпавших предметов;
- **Порталы плодят пиглинов**: Paper предоставляет `nerf-pigmen-from-nether-portals` (сейчас по умолчанию `false`), чтобы отключить это поведение.

### 3.2 Диагностика

- **spark profiler**: горячие точки часто в `Entity.tick`, методах поиска пути, сканировании сенсоров, запросах POI у жителей;
- **`/spark health`**: понять, какой из четырёх показателей — TPS, CPU, память или диск — в тревоге;
- **`/paper entity list`**: посмотреть распределение по типам сущностей (каких типов аномально много);
- **`/paper mobcaps`**: посмотреть глобальный лимит спавна мира и фактическое занятие, а также число чанков, где возможен спавн;
- **`/paper playermobcaps`**: посмотреть локальный лимит спавна для одного игрока;
- **`/paper chunkinfo`**: сопоставить число сущностей с загрузкой чанков, понять, не «спавнит ли в каком-то принудительно загруженном чанке».

### 3.3 Что делать

**(1) Радиус активации сущностей**: см. раздел 1.5. Это самая эффективная и самая опасная для машин настройка: перед изменением скопируйте конфигурацию, после — перепроверьте фермы.

**(2) Радиус спавна `mob-spawn-range`**: единица — чанки, определяет, на каком расстоянии вокруг игрока возможен спавн. В документации Paper сейчас указано `8`, в Spigot wiki — `6`; **снова значение по умолчанию, меняющееся между версиями**, ориентируйтесь на локальный файл. Уменьшение снижает общее число появляющихся мобов, но может снизить эффективность некоторых ферм.

**(3) Лимиты спавна по миру**: `spawn-limits` в `bukkit.yml`, значения по умолчанию из документации Paper сейчас:

```yaml
# bukkit.yml
spawn-limits:
  monsters: 70
  animals: 10
  water-animals: 5
  water-ambient: 20
  water-underground-creature: 5
  axolotls: 5
  ambient: 15
```

Paper также позволяет переопределять ту же группу лимитов по мирам в `paper-world-defaults.yml` (`entities.spawning.spawn-limits`, сейчас по умолчанию все `-1`, то есть используются значения из `bukkit.yml`). Кроме того, `entities.spawning.per-player-mob-spawns` (сейчас по умолчанию `true`) определяет, считается ли лимит спавна отдельно по игрокам или общий.

**(4) Игровые правила**: встроены в ваниль, дают самый быстрый эффект.

```bash
# Отключить естественный спавн (в ванили по умолчанию true) — учтите, это отключит фермы мобов
/gamerule doMobSpawning false

# Отключить дроп с мобов (в ванили по умолчанию true)
/gamerule doMobLoot false

# Скорость случайных тиков, в ванили по умолчанию 3; уменьшение повлияет и на рост культур, распространение огня, образование льда
/gamerule randomTickSpeed 3
```

:::warn Игровые правила бьют по всему сразу
После отключения `doMobSpawning` и `doMobLoot` **перестаёт работать всё, что от них зависит** (фермы мобов, фермы опыта, сбор голов визер-скелетов и т. п.). Это подходит для сервера мероприятий или тушения пожара, но не как долгосрочная оптимизация.
:::

**(5) Всё про спавнеры**:

```yaml
# spigot.yml → world-settings.default
nerf-spawner-mobs: false
```

Документация Paper описывает `nerf-spawner-mobs` как «отключение большей части ИИ у мобов, созданных спавнером» (сейчас по умолчанию `false`). Значение `true` экономит заметную часть затрат на ИИ, но поведение мобов из спавнера заметно изменится. У Paper есть также `tick-rates.mob-spawner` (сейчас по умолчанию `1`), задающий частоту вычисления области спавна и создания сущностей.

**(6) Плагины управления спавнерами**: многие плагины позволяют ограничить расстояние активации, число спавнов в минуту или требовать присутствия игрока. При выборе так же проверяйте совместимость с ядром и версией и предпочитайте решения, «которые можно откатить и внести в белый список».

**(7) Дизайн фермы**: комната убийства + замкнутый сбор + своевременное исчезновение — решение надёжнее любой конфигурации. Если предметы не падают на землю, число сущностей не выйдет из-под контроля.

**(8) Декоративные сущности**: стойки для брони и маркеры (marker) — тоже сущности. Параметры Paper `entities.armor-stands.tick` (сейчас по умолчанию `true`, официально: «отключение останавливает тик стоек для брони и повышает производительность, когда их много») и `entities.markers.tick` (сейчас по умолчанию `true`, официально предупреждают, что это может повлиять на их поведение как пассажиров других сущностей) можно отключать по необходимости.

**(9) Принудительное исчезновение**: параметр Paper `entities.spawning.despawn-time.<entity-type>` (сейчас по умолчанию `disabled`) задаёт принудительное время исчезновения для указанного типа сущностей; `entities.spawning.despawn-ranges` управляет расстоянием случайного исчезновения (по умолчанию `default`, то есть ванильные правила). Оба меняют ванильное поведение, перед изменением подумайте.

## 4. Блочные сущности и воронки

### 4.1 Почему воронка — классический виновник

Воронка — **блочная сущность**, и пока её чанк тикает, у неё каждый тик есть работа:

- Проверить, есть ли сверху выпавшие предметы для всасывания и контейнеры для извлечения;
- Перемещать предметы с учётом кулдауна (в ванили раз в 8 тиков, соответствует `ticks-per.hopper-transfer` в `spigot.yml`);
- Обращение к контейнеру даёт дополнительную нагрузку, а если плагин слушает событие перемещения (InventoryMoveItemEvent), нагрузка ещё больше.

Документация Paper описывает соответствующие ключи в `spigot.yml` так:

- `ticks-per.hopper-transfer` (сейчас по умолчанию `8`): интервал в тиках между перемещениями предметов воронкой;
- `ticks-per.hopper-check` (сейчас по умолчанию `1`): интервал в тиках между проверками на извлечение предметов;
- `hopper-amount` (сейчас по умолчанию `1`): сколько предметов воронка перемещает за раз, максимум — размер стопки;
- `hopper-can-load-chunks` (сейчас по умолчанию `false`): переключатель, связанный с тем, «загружает ли воронка чанки», точную семантику и значение по умолчанию смотрите в официальной документации и локальной конфигурации.

Spigot wiki дополнительно предупреждает: увеличение `hopper-check` **ломает большинство устройств на воронках из-за рассинхронизации**. То есть такая «оптимизация производительности» в техническом Minecraft почти гарантированно создаёт проблемы.

```yaml
# spigot.yml → world-settings.default
ticks-per:
  hopper-transfer: 8
  hopper-check: 1
hopper-amount: 1
```

### 4.2 Как снизить нагрузку от воронок

| Приём | Пояснение | Цена |
| --- | --- | --- |
| Заменить длинную цепочку воронок водой или ледяной дорожкой | Предметы плывут, воронка стоит только в конце для сбора | Нужно переделать логистику |
| Собирать выбрасывателями в одну линию воронок | Убирает повторение «сундук + воронка на каждый» | Нужно управление редстоуном |
| Разобрать простаивающие воронки | Брошенные машины и сломанные линии логистики в мире всё равно тикают | Нет |
| Перемещение вагонеткой с воронкой | Одна сущность заменяет линию воронок, подходит для длинных дистанций | Сама вагонетка тоже сущность |
| Включить оптимизацию воронок в ядре | Например, секция `hopper` в Paper | Может задеть плагины, зависящие от событий перемещения |
| Заставить полные воронки меньше работать | `hopper.cooldown-when-full` в Paper (сейчас по умолчанию `true`) | Нет, это оптимизация, включённая по умолчанию |

В `paper-world-defaults.yml` Paper есть отдельная секция воронок:

```yaml
# paper-world-defaults.yml
hopper:
  cooldown-when-full: true
  disable-move-event: false
  ignore-occluding-blocks: false
```

- `cooldown-when-full`: в документации Paper описано как «применять короткий кулдаун, когда воронка полна, вместо постоянных попыток извлечь новые предметы»;
- `disable-move-event`: отключает событие перемещения для экономии, но **плагины, зависящие от этого события, перестанут работать**;
- `ignore-occluding-blocks`: игнорировать проверки, связанные с перекрывающими блоками.

:::note Структура и значения по умолчанию меняются между версиями
Форма этого блока менялась в разных версиях Paper (например, `cooldown-when-full` раньше был подузлом с `enabled` / `movement-ticks`). **Ориентируйтесь на локально сгенерированный `paper-world-defaults.yml` и официальную документацию Paper.**
:::

### 4.3 Кстати: обновление контейнеров и «неподдерживаемые» переключатели

Параметр Paper `tick-rates.container-update` (сейчас по умолчанию `1`) определяет частоту обновления контейнеров и инвентарей сервером. Официальная документация Paper прямо предупреждает: **значение больше 1 приводит к рассинхронизации и дублированию предметов (ghosting), к тому же прогресс копания может странно сбрасываться, а также может создаваться видимость «лагов сервера»**. Это не та оптимизация, которую стоит трогать.

Параметры Paper `unsupported-settings.ticking.block-entities` и `ticking.chunks` (сейчас оба по умолчанию `true` и официально помечены как «не поддерживаемые») позволяют полностью отключить тик блочных сущностей или чанков. **Не трогайте их на продакшене** — это равносильно отключению игровой логики.

## 5. Порядок разбора

Порядок разбора лагов от сущностей такой же, как у других проблем производительности: **сначала измерение, потом локализация, и только затем действия**.

### 5.1 Семь шагов

1. **Измерение**: `/spark tps` смотрит TPS и MSPT, `/spark health` показывает, проблема в CPU, памяти или диске. Убедитесь, что «главный поток действительно загружен полностью», и идите дальше.
2. **Поиск горячей точки**: `/spark profiler start --timeout 60`, после сэмплирования посмотрите дерево вызовов — `Entity.tick`, `ItemEntity.tick`, тик блочных сущностей, методы поиска пути и сенсоров: самая широкая ветка и есть главный подозреваемый. Как читать — см. [Анализ производительности через spark](/tutorials/ops/spark).
3. **Локализация чанка и типа**: `/paper entity list` показывает распределение типов, `/paper chunkinfo` — распределение типов чанков, `/forceload query` — принудительную загрузку.
4. **Определите природу**: это **проблема дизайна** (ферма без замкнутого цикла, машины без присмотра) или **проблема конфигурации** (слишком щедрые радиус спавна и активации)? В подавляющем большинстве случаев это дизайн.
5. **Сначала измените дизайн**: добавьте комнату убийства и сбор, разберите брошенные машины, не оставляйте фермы работать всю ночь без людей. После изменений снова измерьте.
6. **Потом настройте конфигурацию**: если после изменения дизайна всё ещё мало, трогайте параметры сущностей в `spigot.yml` / `bukkit.yml` / `paper-world-defaults.yml`. **Меняйте по одному пункту**, перед изменением делайте копию (см. [Настройка сервера](/tutorials/java/config)).
7. **Перепроверка и запись**: сразу перепроверьте тот же сценарий (та же машина, то же время суток, то же число игроков) и убедитесь, что MSPT действительно упал; запишите «что изменили, почему, какой эффект» в журнал изменений. **Оптимизация без перепроверки равна её отсутствию.**

### 5.2 Быстрая таблица

| Явление | Возможная причина | Что проверить сначала | Что делать |
| --- | --- | --- | --- |
| На земле везде выпавшие предметы, TPS медленно падает | У фермы нет замкнутого сбора, цепочка воронок порвана, игроки разбрасывают вещи | `/paper entity list minecraft:item`, дерево вызовов spark | Починить дизайн фермы; страховка плагином периодической очистки |
| В одной области сразу лагает, уходишь — отпускает | В этом чанке много сущностей или плотные машины | `/paper chunkinfo`, `/forceload query`, сравнение по мирам и областям в spark | Переделать машины; убрать лишнюю принудительную загрузку |
| Начинает лагать после ночного спавна или спавна под землёй | Спавн в неосвещённых областях | `/paper entity list`, `/paper mobcaps` | Осветить пещеры; уменьшить `mob-spawn-range`; при необходимости `doMobSpawning` |
| Лагает рядом с залом жителей | Много жителей, затраты на POI и поиск пути | Горячие точки по жителям в spark, `/paper entity list minecraft:villager` | Ограничить размножение; при необходимости отключить `tick-inactive-villagers` (изменит ванильное поведение) |
| Лагает даже при массе простаивающих машин | Воронки, спавнеры, стойки для брони и другие блочные сущности работают вхолостую | Доля тика блочных сущностей и сущностей в spark | Разобрать простаивающие машины; включить оптимизацию воронок в ядре; отключить тик стоек для брони |
| После перезапуска ненадолго нормально, потом снова лагает | Источник не устранён | Время до восстановления проблемы и сверка с разбором выше | Вернуться к шагам 1–5 и устранить источник, а не перезапускать |
| Памяти дали много, а всё равно лагает | Узкое место — CPU главного потока, а не куча | CPU и MSPT в `/spark health` | Разбираться с сущностями по статье; см. [Оптимизацию производительности](/tutorials/java/optimize) |
| Поставили плагин очистки, а всё равно лагает | Не те объекты или интервал, либо узкое место вовсе не в выпавших предметах | Дерево вызовов spark | Сначала найти горячую точку, потом решать, нужен ли плагин |

Быстрая таблица симптомов и подводных камней Java Edition — см. [[JAVA] Частые вопросы](/tutorials/faq/faq-java).

## 6. Частые заблуждения

**Заблуждение первое: перезапуск решает проблему.**
Перезапуск лишь заново загружает мир и на короткое время выглядит «плавно». Пока ферма мобов продолжает выбрасывать вещи на землю, цепочка воронок порвана, а принудительно загруженные чанки включены, скопление вернётся с той же скоростью. Перезапуск — **аварийная мера**, а не исправление.

**Заблуждение второе: добавление памяти (`-Xmx`) лечит лаги от сущностей.**
Лаги от сущностей — проблема **CPU главного потока**, а не кучи. Сколько ни дай, тик всё равно идёт в том одном потоке; слишком большой `-Xmx` ещё и удлинит паузы GC. Сначала найдите горячую точку.

**Заблуждение третье: чем жёстче лимиты сущностей, тем лучше.**
Агрессивное уменьшение радиуса активации, радиуса спавна и радиуса объединения **выводит из строя фермы и технические машины**: жители не пополняют товар, фермы мобов не выдают дроп, устройства на разделении предметов ломаются. На техническом сервере смотрите прежде всего [Технический Minecraft и редстоун](/tutorials/java/redstone) и при необходимости переходите на Fabric / Leaves, а не переделывайте поведение в семействе Paper до неузнаваемости.

**Заблуждение четвёртое: `/kill @e` — универсальное средство.**
Оно удалит и питомцев игроков, и стойки для брони со снаряжением, и собираемую продукцию — **без возможности отмены**. `/kill @e[type=item]` мягче, но всё равно удалит законные предметы игроков и ферм на земле. Перед выполнением подумайте, «есть ли среди этих сущностей имущество игроков».

**Заблуждение пятое: много сущностей равно лагам.**
Количество нужно смотреть вместе с типом и расположением. Десять тысяч выпавших предметов в одном чанке рядом с игроком — катастрофа; десять тысяч предметов, разбросанных по сотне чанков в состоянии Block Ticking, могут почти не давать нагрузки. **Сначала горячая точка тика, потом количество.**

**Заблуждение шестое: поставить кучу «плагинов оптимизации» — и всё решится.**
Большинство таких плагинов лишь оборачивают перечисленные параметры в графический интерфейс или задачи по расписанию. **Если источник не устранён, очистка лишь превращает «постоянные лаги» в «периодические подёргивания».** Нужно также проверить совместимость плагина с ядром: некачественный плагин сам может быть горячей точкой.

**Заблуждение седьмое: оптимизировал один раз — и готово.**
Сервер живой: новые машины, новые фермы и новые игроки меняют нагрузку. Включить ключевые показатели (TPS/MSPT, порядок числа сущностей) в регулярный осмотр полезнее, чем однократная настройка.
